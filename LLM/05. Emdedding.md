# Enterprise Document Ingestion – Embedding Generation with Python, REST APIs and Amazon S3

## 1. What is embedding generation?

We have already completed three important stages:

1. **Document ingestion:** retrieving documents from SharePoint and storing them in Amazon S3.
2. **Document normalisation:** extracting information from different file formats and converting it into a common structure.
3. **Format-aware chunking:** splitting documents into meaningful pieces while preserving their source information.

Now we need to convert each chunk into an embedding.

An embedding is a numerical representation of text.

For example, imagine we have this chunk:

```text
Employees are entitled to 25 days of annual leave
each calendar year, excluding public holidays.
```

An embedding model converts that text into a vector, which is a list of floating-point numbers.

A simplified example might look like this:

```python
[
    0.0214,
    -0.0372,
    0.0815,
    0.0149,
    -0.0261
]
```

This is an illustrative shortened vector, not an actual model response.

A real embedding could contain hundreds or thousands of numbers.

The numbers represent aspects of the text's meaning in a mathematical space.

For example, the following sentences have related meanings:

```text
Employees receive 25 days of annual leave.

Staff members are entitled to 25 days of holiday
each year.
```

An embedding model should generally represent these sentences as semantically similar, even though they use different words.

This is what makes embeddings useful for semantic search.

### Why do we need embeddings?

Imagine a user asks:

```text
How many holidays do employees receive?
```

The original document might contain:

```text
Employees are entitled to 25 days of annual leave.
```

A conventional keyword search may struggle if the words in the question and the document are different.

An embedding-based search compares the numerical representations of the question and the document chunks.

It can therefore find related content even when the wording differs.

At this stage, we are not yet writing to a vector database.

2. Send the chunk text to an embedding service.

We will keep the embedding generation stage separate from vector database storage.

This is an important architectural decision.

It means we can change our vector database later without having to repeat document extraction and chunking.

## 3. Understand the input: our chunked JSONL file

In the previous lesson, we stored chunked documents in S3.

For example:

```text
s3://company-documents/processed/chunks/sharepoint/drive-123/file-001.jsonl
```

The JSONL file contains one chunk per line.

A simplified record looks like this:

```json
{
    "chunk_id": "chunk-abc123",
    "document_id": "file-001",
    "chunk_number": 1,
    "text": "Employees are entitled to 25 days of annual leave.",
    "metadata": {
        "source": {
            "system": "sharepoint",
            "drive_id": "drive-123",
            "item_id": "file-001"
        },
        "file": {
            "name": "employee_handbook.pdf",
            "extension": "pdf"

            "bucket": "company-documents",
            "key": "documents/sharepoint/drive-123/file-001"

            "pdf_page"
        ],
        "context": {
            "page_numbers": [
                12
            ]
        },
        "character_count": 58
    }
}
```

Notice that the record contains two important categories of information.

**The text:**

```python
chunk["text"]
```

This is the content that we send to the embedding model.

**The metadata:**

```python
chunk["metadata"]
```

This tells us where the content originated.

We must preserve both.

The embedding model does not need to receive all the metadata. In this implementation, we send the text and retain the metadata locally.

That avoids unnecessarily sending source identifiers and other metadata to the embedding provider.

## 4. Selecting an embedding provider

Before implementing embedding generation, we need to understand that an embedding model and a vector database are two different things.

An embedding provider generates vectors.

A vector database stores vectors and supports similarity searches.

They do not have to come from the same company.

Here are some possible options.

### Option A: OpenAI embeddings

<text>Provider: <Link url="https://platform.openai.com/docs/guides/embeddings" title="OpenAI embedding documentation"/></text>

OpenAI provides embedding models through an API.

For this lesson, we will use:

```text
text-embedding-3-small
```

Its default vector dimension is 1,536.

The API is accessed using a standard HTTPS REST request.

Advantages:

- Straightforward REST API.
- Easy to integrate with Python `requests`.
- Supports sending multiple text inputs in one request.
- Does not require an OpenAI Python SDK.

### Option B: Amazon Bedrock

<text>Provider: <Link url="https://docs.aws.amazon.com/bedrock/" title="Amazon Bedrock documentation"/></text>

Amazon Bedrock provides access to embedding models through AWS.

This can be attractive when an organisation wants its model services integrated into its AWS environment.

Advantages:

- AWS identity and access management integration.
- AWS service governance.
- Multiple model providers.
- Integration with other AWS services.

The exact request format and authentication depend on the selected Bedrock model and interface.

### Option C: Azure OpenAI

<text>Provider: <Link url="https://learn.microsoft.com/azure/ai-services/openai/" title="Azure OpenAI documentation"/></text>

Azure OpenAI provides access to OpenAI models through Azure.

This can be appropriate when an organisation has an existing Microsoft Azure architecture and governance requirements.

### Which should we use?

There is no universal enterprise requirement that says all organisations must use one particular embedding provider.

The decision should consider:

- Data protection requirements.
- Where document content is processed.
- Model quality.
- Cost.
- API throughput and rate limits.
- Network and identity requirements.
- Vector database compatibility.
- Regional data residency requirements.

For the code below, we will use OpenAI as a concrete REST API example. The architecture itself remains provider-independent.

## 5. How the embedding REST API works

The embedding process involves sending an HTTP POST request.

The OpenAI endpoint is:

```text
https://api.openai.com/v1/embeddings
```

The request contains:

- Model name.
- Text input.
- Optional dimensions.
- Authentication token.

A simplified request looks like this:

```http
POST https://api.openai.com/v1/embeddings

Authorization: Bearer YOUR_API_KEY
Content-Type: application/json
```

Request body:

```json
{
    "model": "text-embedding-3-small",
    "input": [
        "Employees are entitled to 25 days of annual leave.",
        "Employees must follow the company's attendance policy."
    ]
}
```

Notice that we are sending an array of strings.

This allows us to generate embeddings for multiple chunks in one API call.

The API returns a response containing the vectors.

A simplified response looks like this:

```json
{
    "object": "list",
    "data": [
        {
            "object": "embedding",
            "index": 0,
            "embedding": [
                0.0214,
                -0.0372,
                0.0815
            ]
        },
        {
            "object": "embedding",
            "index": 1,
            "embedding": [
                0.0141,
                -0.0295,
                0.0623
            ]
        }
    ],
    "model": "text-embedding-3-small"
}
```

The values above are illustrative and shortened.

An important detail is the `index` field.

It identifies which input corresponds to each returned vector.

Our Python implementation will use that index rather than assuming that response order can never change.

## 6. Why we should process embeddings in batches

Imagine that we have 100,000 chunks.

A poor implementation would send one API request for every chunk.

That would create 100,000 individual HTTP requests.

It could increase:

- Network overhead.
- Processing time.
- API request overhead.
- Rate-limit pressure.

Instead, we can send a batch of chunks together.

For example:

```python
BATCH_SIZE = 32
```

This means that we attempt to send up to 32 chunk texts in one API request.

Example:

```text
Batch 1:
Chunk 1
Chunk 2
...
Chunk 32

Batch 2:
Chunk 33
Chunk 34
...
Chunk 64
```

The last batch may contain fewer than 32 chunks.

The batch size is configurable.

It is not a universal API limit. It is an initial operational setting that must be tested against the provider's input and token limits, request-size limits and rate limits.

### Why not send the entire file in one request?

Because a JSONL file could contain thousands of chunks.

Sending the entire file at once would create an unnecessarily large API request and require us to hold many records in memory.

Batching provides a more controlled approach.

## 7. Important embedding parameters

The following settings control our implementation.

| Parameter | Example | Purpose |
|---|---|---|
| `EMBEDDING_MODEL` | `text-embedding-3-small` | Selects the embedding model |
| `BATCH_SIZE` | `32` | Maximum number of chunks grouped in one request |
| `REQUEST_TIMEOUT` | `90` | Maximum wait for an API request |
| `MAX_RETRIES` | `5` | Maximum retry attempts |
| `DIMENSIONS` | `None` | Uses the model's default vector dimension |
| `EMBEDDING_API_URL` | OpenAI endpoint | REST API destination |

### What are embedding dimensions?

An embedding vector has a fixed number of numerical values.

For example:

```text
text-embedding-3-small

Default dimensions: 1536
```

This means the embedding might look like:

```python
[
    0.0214,
    -0.0372,
    0.0815,
    ...
]
```

with 1,536 values.

The dimensions matter because the vector database must be configured to accept vectors of the same length.

For example:

```text
Embedding model output: 1536 dimensions

Vector database index: 1536 dimensions
```

These must match.

OpenAI's third-generation embedding models also support a `dimensions` parameter to request a smaller vector size.

For this first implementation, we will leave it unset and use the default.

We should only choose a reduced dimension after considering the selected model, the target vector database and retrieval-quality testing.

## 10. Memory management: processing large JSONL files

This is particularly important for enterprise ingestion.

Suppose our JSONL file is 2 GB.

We should not do this:

```python
with open("chunks.jsonl", "r") as file:
    all_chunks = file.readlines()
```

That loads every line into memory.

We should also avoid this:

```python
all_chunks = json.load(file)
```

Apart from requiring a JSON array rather than JSONL, it loads the entire document structure into memory.

Instead, we can use S3's streaming response:

```python
response = s3_client.get_object(
    Bucket=S3_BUCKET,
    Key=INPUT_S3_KEY
)

body = response["Body"]

for line in body.iter_lines():

    if line:

        chunk = json.loads(line)
```

This reads the input incrementally.

We can then build a small batch:

```python
batch = []

for chunk in read_chunks():

    batch.append(chunk)

    if len(batch) == BATCH_SIZE:

        process_batch(batch)

        batch = []
```

We process the batch, release it, and move to the next one.

This means our application does not need to hold all the chunks in memory.

The output is also written incrementally to a temporary JSONL file before it is uploaded to S3.

## 11. Error handling and retries

External embedding APIs can fail temporarily.

Common examples include:

| HTTP status | Meaning | What we should do |
|---|---|---|
| 400 | Invalid request | Correct the request; do not blindly retry |
| 401 | Authentication failure | Check the API key |
| 403 | Access denied | Check permissions and project access |
| 408 | Request timeout | Retry carefully |
| 429 | Rate limit | Respect `Retry-After` and retry |
| 500 | Server error | Retry with backoff |
| 502 | Bad gateway | Retry with backoff |
| 503 | Service unavailable | Retry with backoff |
| 504 | Gateway timeout | Retry with backoff |

We will implement:

- A maximum number of retries.
- Exponential backoff.
- A small random delay.
- Respect for the provider's `Retry-After` header.
- A request timeout.

For example:

```text
Attempt 1: request fails

Wait 2 seconds

Attempt 2: request fails

Wait 4 seconds

Attempt 3: request succeeds
```

The actual waiting period includes a small random component.

We will not retry every error. An invalid API key or malformed request will not be fixed by repeating the same request.

For this learning implementation, an unsuccessful batch stops the run rather than silently dropping records.

In production, we would also introduce durable checkpoints, failed-batch storage or a dead-letter queue so that we can resume without paying to regenerate embeddings for all previously successful batches.

## 13. Complete Python implementation

We will create:

```text
embedding_generator.py
```

The program will:

1. Connect to Amazon S3.
2. Read the chunked JSONL object from S3.
3. Read records one line at a time.
4. Collect a batch of chunk records.
5. Extract the text from each chunk.
6. Send the texts to the embedding REST API.
7. Receive the embedding vectors.
8. Match each vector to its original chunk using the response index.
9. Add embedding information to each original record.
10. Write enriched records to a temporary JSONL file.
11. Upload the result to S3.

### Complete code: embedding_generator.py

```python
import boto3
import requests
import json
import os
import time
import random

from pathlib import Path
from tempfile import TemporaryDirectory


# ============================================================
# 1. CONFIGURATION
# ============================================================

S3_BUCKET = "company-documents"

# Input: chunked JSONL file
INPUT_S3_KEY = (
    "processed/chunks/sharepoint/"
    "drive-123/file-001.jsonl"
)

# Output: embedded JSONL file
OUTPUT_S3_KEY = (
    "processed/embeddings/sharepoint/"
    "drive-123/file-001.jsonl"
)

# Embedding provider
EMBEDDING_API_URL = (
    "https://api.openai.com/v1/embeddings"
)

EMBEDDING_PROVIDER = "openai"

EMBEDDING_MODEL = "text-embedding-3-small"

# None means use the model's default dimensions.
DIMENSIONS = None

# Number of chunks sent in one API request.
BATCH_SIZE = 32

# Maximum API request duration.
REQUEST_TIMEOUT = 90

# Maximum retry attempts.
MAX_RETRIES = 5

# Backoff settings.
INITIAL_BACKOFF_SECONDS = 2

MAX_BACKOFF_SECONDS = 60


# ============================================================
# 2. LOAD API CREDENTIALS
# ============================================================

OPENAI_API_KEY = os.getenv("OPENAI_API_KEY")

if not OPENAI_API_KEY:

    raise RuntimeError(
        "OPENAI_API_KEY environment variable is missing"
    )


# ============================================================
# 3. INITIALISE AWS AND HTTP CLIENTS
# ============================================================

s3_client = boto3.client("s3")

http_session = requests.Session()

http_session.headers.update({
    "Authorization": f"Bearer {OPENAI_API_KEY}",
    "Content-Type": "application/json"
})


# ============================================================
# 4. READ CHUNKED JSONL FROM S3
# ============================================================

def read_chunks_from_s3(bucket, s3_key):

    """
    Read a JSONL object from S3 one line at a time.

    This avoids downloading the complete JSONL file
    into a large Python list.
    """

    response = s3_client.get_object(
        Bucket=bucket,
        Key=s3_key
    )

    body = response["Body"]

    try:

        for line_number, line in enumerate(
            body.iter_lines(),
            start=1
        ):

            if not line:

                continue

            try:

                chunk = json.loads(line)

            except json.JSONDecodeError as error:

                raise ValueError(
                    f"Invalid JSON on line {line_number}"
                ) from error

            # Validate the minimum required fields.
            if not isinstance(chunk, dict):

                raise ValueError(
                    f"Line {line_number} is not a JSON object"
                )

            if not chunk.get("chunk_id"):

                raise ValueError(
                    f"Missing chunk_id on line {line_number}"
                )

            if not isinstance(chunk.get("text"), str):

                raise ValueError(
                    f"Missing or invalid text on line {line_number}"
                )

            if not chunk["text"].strip():

                raise ValueError(
                    f"Empty chunk text on line {line_number}"
                )

            yield chunk

    finally:

        body.close()


# ============================================================
# 5. BUILD EMBEDDING API REQUEST
# ============================================================

def build_embedding_payload(texts):

    """
    Build the JSON body for the embedding REST API.
    """

    payload = {
        "model": EMBEDDING_MODEL,
        "input": texts
    }

    # Only send dimensions if explicitly configured.
    if DIMENSIONS is not None:

        payload["dimensions"] = DIMENSIONS

    return payload


# ============================================================
# 6. CALL EMBEDDING REST API WITH RETRIES
# ============================================================

def request_embeddings(texts):

    """
    Send multiple texts to the embedding API.

    Retries temporary errors such as:

    - HTTP 408
    - HTTP 429
    - HTTP 500
    - HTTP 502
    - HTTP 503
    - HTTP 504

    Authentication and invalid-request errors are not retried.
    """

    payload = build_embedding_payload(texts)

    retryable_status_codes = {
        408,
        429,
        500,
        502,
        503,
        504
    }

    for attempt in range(1, MAX_RETRIES + 1):

        try:

            response = http_session.post(
                EMBEDDING_API_URL,
                json=payload,
                timeout=REQUEST_TIMEOUT
            )

            # Retry temporary server and rate-limit errors.
            if response.status_code in retryable_status_codes:

                if attempt == MAX_RETRIES:

                    response.raise_for_status()

                retry_after = response.headers.get(
                    "Retry-After"
                )

                if retry_after:

                    try:

                        wait_seconds = float(retry_after)

                    except ValueError:

                        wait_seconds = (
                            INITIAL_BACKOFF_SECONDS
                            * (2 ** (attempt - 1))
                        )

                else:

                    wait_seconds = (
                        INITIAL_BACKOFF_SECONDS
                        * (2 ** (attempt - 1))
                    )

                wait_seconds = min(
                    wait_seconds,
                    MAX_BACKOFF_SECONDS
                )

                wait_seconds += random.uniform(0, 1)

                print(
                    f"Temporary API error "
                    f"{response.status_code}. "
                    f"Retrying in {wait_seconds:.1f} seconds."
                )

                time.sleep(wait_seconds)

                continue

            # Invalid request, authentication and other
            # non-retryable HTTP errors stop the process.
            response.raise_for_status()

            result = response.json()

            if "data" not in result:

                raise ValueError(
                    "Embedding API response has no data field"
                )

            return result

        except requests.exceptions.Timeout:

            if attempt == MAX_RETRIES:

                raise

            wait_seconds = min(
                INITIAL_BACKOFF_SECONDS * (2 ** (attempt - 1)),
                MAX_BACKOFF_SECONDS
            )

            wait_seconds += random.uniform(0, 1)

            print(
                f"Request timed out. "
                f"Retrying in {wait_seconds:.1f} seconds."
            )

            time.sleep(wait_seconds)

        except requests.exceptions.ConnectionError:

            if attempt == MAX_RETRIES:

                raise

            wait_seconds = min(
                INITIAL_BACKOFF_SECONDS * (2 ** (attempt - 1)),
                MAX_BACKOFF_SECONDS
            )

            wait_seconds += random.uniform(0, 1)

            print(
                f"Connection error. "
                f"Retrying in {wait_seconds:.1f} seconds."
            )

            time.sleep(wait_seconds)

    raise RuntimeError(
        "Embedding API request failed after all retries"
    )


# ============================================================
# 7. VALIDATE AND MATCH EMBEDDING RESPONSES
# ============================================================

def get_ordered_embeddings(api_result, expected_count):

    """
    Use the response index to match each embedding
    to the correct input text.
    """

    data = api_result.get("data", [])

    if len(data) != expected_count:

        raise ValueError(
            "Embedding response count does not match "
            "the number of input chunks"
        )

    ordered_embeddings = [None] * expected_count

    for item in data:

        index = item.get("index")

        embedding = item.get("embedding")

        if not isinstance(index, int):

            raise ValueError(
                "Invalid embedding response index"
            )

        if index < 0 or index >= expected_count:

            raise ValueError(
                f"Unexpected embedding index: {index}"
            )

        if ordered_embeddings[index] is not None:

            raise ValueError(
                f"Duplicate embedding index: {index}"
            )

        if not isinstance(embedding, list):

            raise ValueError(
                "Embedding must be a list"
            )

        if not embedding:

            raise ValueError(
                "Embedding vector is empty"
            )

        if not all(
            isinstance(value, (int, float))
            and not isinstance(value, bool)
            for value in embedding
        ):

            raise ValueError(
                "Embedding contains invalid numeric values"
            )

        ordered_embeddings[index] = embedding

    if any(
        embedding is None
        for embedding in ordered_embeddings
    ):

        raise ValueError(
            "One or more embedding results are missing"
        )

    # All vectors in the batch must have the same length.
    dimensions = {
        len(embedding)
        for embedding in ordered_embeddings
    }

    if len(dimensions) != 1:

        raise ValueError(
            "Embedding dimensions differ within the batch"
        )

    return ordered_embeddings


# ============================================================
# 8. EMBED ONE BATCH OF CHUNKS
# ============================================================

def embed_batch(chunks):

    """
    Generate embeddings for a batch of chunks.

    Original chunk records and metadata are preserved.
    """

    texts = [
        chunk["text"]
        for chunk in chunks
    ]

    api_result = request_embeddings(texts)

    embeddings = get_ordered_embeddings(
        api_result,
        expected_count=len(chunks)
    )

    dimensions = len(embeddings[0])

    enriched_records = []

    for chunk, embedding in zip(
        chunks,
        embeddings
    ):

        # Make a new record rather than changing the
        # original chunk object.
        enriched_chunk = dict(chunk)

        enriched_chunk["embedding"] = embedding

        enriched_chunk["embedding_metadata"] = {
            "provider": EMBEDDING_PROVIDER,
            "model": EMBEDDING_MODEL,
            "dimensions": dimensions
        }

        enriched_records.append(enriched_chunk)

    return enriched_records, api_result.get("usage", {})


# ============================================================
# 9. PROCESS THE COMPLETE JSONL INPUT IN BATCHES
# ============================================================

def process_chunk_file(
    bucket,
    input_key,
    local_output_path
):

    """
    Read S3 JSONL incrementally, generate embeddings
    in batches and write enriched JSONL incrementally.
    """

    batch = []

    total_chunks = 0

    total_batches = 0

    total_prompt_tokens = 0

    with open(
        local_output_path,
        "w",
        encoding="utf-8"
    ) as output_file:

        for chunk in read_chunks_from_s3(
            bucket,
            input_key
        ):

            batch.append(chunk)

            # Process when the batch reaches its limit.
            if len(batch) == BATCH_SIZE:

                records, usage = embed_batch(batch)

                for record in records:

                    output_file.write(
                        json.dumps(
                            record,
                            ensure_ascii=False
                        )
                        + "\n"
                    )

                total_chunks += len(records)

                total_batches += 1

                total_prompt_tokens += usage.get(
                    "prompt_tokens",
                    0
                )

                print(
                    f"Completed batch {total_batches}. "
                    f"Total chunks: {total_chunks}"
                )

                # Release references to the processed batch.
                batch = []

        # Process the remaining records.
        if batch:

            records, usage = embed_batch(batch)

            for record in records:

                output_file.write(
                    json.dumps(
                        record,
                        ensure_ascii=False
                    )
                    + "\n"
                )

            total_chunks += len(records)

            total_batches += 1

            total_prompt_tokens += usage.get(
                "prompt_tokens",
                0
            )

            print(
                f"Completed final batch {total_batches}. "
                f"Total chunks: {total_chunks}"
            )

    if total_chunks == 0:

        raise ValueError(
            "No chunks were found in the input file"
        )

    return {
        "total_chunks": total_chunks,
        "total_batches": total_batches,
        "total_prompt_tokens": total_prompt_tokens
    }


# ============================================================
# 10. UPLOAD EMBEDDED JSONL TO S3
# ============================================================

def upload_embedded_file(
    local_path,
    bucket,
    output_key
):

    s3_client.upload_file(
        Filename=str(local_path),

        ExtraArgs={

    print(
        f"Uploaded embedded records to "
        f"s3://{bucket}/{output_key}"
    )
```

## 14. Understanding the most important functions

Let's break down what the code actually does.

### `read_chunks_from_s3()`

This function retrieves the JSONL object from S3.

It uses:

```python
response = s3_client.get_object(
    Bucket=bucket,
    Key=s3_key
)
```

`get_object()` returns the object body as a streaming response.

We then use:

```python
body.iter_lines()
```

This lets us read one line at a time.

Each line is converted into a Python dictionary:

```python
chunk = json.loads(line)
```

The function uses `yield`.

That means it produces one chunk at a time instead of building a list containing every chunk in the file.

### `build_embedding_payload()`

This prepares the API request.

For example:

```python
payload = {
    "model": EMBEDDING_MODEL,
    "input": texts
}
```

`model` tells the provider which embedding model to use.

`input` contains the list of chunk texts.

The optional `dimensions` parameter allows us to request a specific vector length where the selected model supports it.

### `request_embeddings()`

This sends the REST API request.

The important method is:

```python
response = http_session.post(
    EMBEDDING_API_URL,
    json=payload,
    timeout=REQUEST_TIMEOUT
)
```

The `json` parameter converts our Python dictionary into JSON for the HTTP request.

The `timeout` parameter prevents our application from waiting indefinitely.

The function also handles temporary API failures and retries them.

### `get_ordered_embeddings()`

This function is particularly important.

The embedding API returns a list of vectors.

Each vector has an `index`.

For example:

```json
{
    "index": 0,
    "embedding": [0.0214, -0.0372]
}
```

The index identifies the original input position.

We use this to ensure that we associate the correct embedding with the correct chunk.

Without this check, we risk storing a vector against the wrong text.

### `embed_batch()`

This is where the actual enrichment happens.

First, we extract the text:

```python
texts = [
    chunk["text"]
    for chunk in chunks
]
```

Then we call the API:

```python
api_result = request_embeddings(texts)
```

Then we match the returned vectors with the chunks.

Finally, we add the embedding:

```python
enriched_chunk["embedding"] = embedding
```

And record the model details:

```python
enriched_chunk["embedding_metadata"] = {
    "provider": EMBEDDING_PROVIDER,
    "model": EMBEDDING_MODEL,
    "dimensions": dimensions
}
```

The original metadata remains intact.

### `process_chunk_file()`

This function controls the overall batch processing.

It reads the chunks, builds a batch and sends it for embedding generation.

When the batch reaches 32 records, it processes it and clears the batch.

This is the key memory-management mechanism.

We are not holding all the chunks or all the generated vectors in memory.

### `upload_embedded_file()`

Finally, we upload the enriched JSONL file to S3.

We use:

```python
s3_client.upload_file()
```

The output is a file containing the original chunk records plus their embedding vectors.

## 16. Important enterprise considerations

The code demonstrates the complete basic processing flow, but there are several additional requirements for an enterprise implementation.

### A. Token limits

Our previous chunking implementation used a character-based limit.

However, embedding models generally enforce token limits rather than character limits.

For example, the OpenAI `text-embedding-3-small` model has an 8,192-token maximum input length.

A 6,000-character chunk will often be below that limit, but character count is not a reliable substitute for token count.

Before production, use the appropriate tokenizer or provider-supported token counting approach to validate every chunk.

Oversized chunks should be split and reprocessed rather than repeatedly submitted as invalid requests.

### B. Model version and dimensions

Every embedded record should retain:

- Provider.
- Model.
- Dimensions.
- Optionally, a model or processing configuration version.

If we change models, we must regenerate embeddings.

Vectors from different embedding models should not be mixed in the same vector index unless the indexing and retrieval design explicitly supports that arrangement.

### C. Idempotency and duplicate processing

Suppose the same input file is processed twice.

The program above will generate the embeddings again.

That can create unnecessary cost.

A production implementation should track:

```text
chunk_id
content_hash
embedding_provider
embedding_model
dimensions
processing_status
```

If the chunk content and embedding configuration have not changed, we may reuse the existing embedding.

If the text changes, the embedding must be regenerated.

### D. Checkpointing

The example stops if an API batch fails.

It does not yet save a durable checkpoint after every successful batch.

For a large ingestion pipeline, we should record which batches or chunks have completed successfully.

That way, a failed run can resume from the last completed checkpoint.

### E. Cost and rate limits

Embedding providers charge according to their pricing model, commonly based on input tokens.

We should monitor:

- Total input tokens.
- Number of requests.
- Failed requests.
- Retry counts.
- Processing duration.
- Cost per document.
- Cost per source system.

The code records the token usage returned by successful API responses.

For larger initial backfills, providers may also offer asynchronous or batch processing options. Those can be evaluated separately from this synchronous REST implementation.

### F. S3 is not the vector database

We are deliberately storing embeddings in S3 at this stage.

S3 is useful for:

- Durable intermediate storage.
- Reprocessing.
- Auditability.
- Backup.
- Moving data between systems.

However, S3 does not automatically provide vector similarity search.

The next stage will be to take the embedded records and write them to a vector database.

## 18. What comes next?

The next stage is **vector database ingestion**.

We will take each embedded record and store it in a vector database.

That database will need to store or associate:

- Chunk ID.
- Embedding vector.
- Original text.
- Document ID.
- Source metadata.
- Page, slide or worksheet information.
- Model and dimension information.

We should not choose the vector database before understanding the options and the requirements.

Potential choices include:

- Amazon OpenSearch Service with vector search.
- Amazon Aurora PostgreSQL with pgvector.
- Pinecone.
- Other vector databases supported by the organisation.

The embedding dimension must match the vector index configuration.

The database must also support the filtering and access-control requirements of the SharePoint source documents.

**Our pipeline is now ready for the vector database stage, subject to validating the embedding provider, model, token limits and enterprise data-governance requirements.**
