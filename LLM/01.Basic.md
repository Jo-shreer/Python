
# LLM Engineering – Complete Technical Reference Guide

## 1. What are Large Language Models (LLMs)?

### What
A Large Language Model (LLM) is an AI model trained on large amounts of text and other data to understand and generate human-like language.

LLMs learn statistical patterns, relationships, grammar, context and semantic meaning from training data.

Examples:
- GPT – OpenAI
- Claude – Anthropic
- Gemini – Google
- Llama – Meta

### Why
Traditional software follows explicitly programmed rules. LLMs can interpret natural language and generate responses for tasks that are difficult to handle using fixed rules.

### How
1. Collect and prepare training data.
2. Tokenize the data into numerical token IDs.
3. Convert tokens into embeddings.
4. Process the tokens through neural network layers.
5. Learn patterns by predicting subsequent tokens.
6. Fine-tune or align the model for useful behaviour.
7. Use inference to generate responses.

### When to use
- Chatbots and virtual assistants.
- Document summarization.
- Code generation.
- Question answering.
- Information extraction.
- Natural language interfaces.
- Retrieval-Augmented Generation (RAG).

### Example

```python
from openai import OpenAI

client = OpenAI()

response = client.responses.create(
    model="YOUR_SUPPORTED_MODEL",
    input="Explain microservices architecture."
)

print(response.output_text)
```

### Pros
- Handles unstructured language.
- Supports multiple tasks.
- Reduces manual content processing.
- Enables natural language interfaces.

### Cons
- Can hallucinate.
- Requires computational resources.
- May produce inconsistent responses.
- Can have latency and token costs.
- Can inherit biases from training data.

### Production standards
- Validate model output before critical operations.
- Never assume generated answers are always correct.
- Implement monitoring and logging.
- Protect sensitive information.
- Evaluate accuracy, latency and cost.
- Use RAG or external tools when factual grounding is necessary.

## 2. How do LLMs work?

### What
LLMs work by processing input tokens and predicting the next token based on previously processed context.

For example:

Input: "The capital of France is"

The model calculates probabilities for possible next tokens. "Paris" may receive the highest probability.

### Why
Next-token prediction provides a general learning objective that allows a model to acquire language patterns, knowledge associations and reasoning-like capabilities.

### How

Typical LLM processing:

1. User submits a prompt.
2. Text is converted into tokens.
3. Tokens are converted into embeddings.
4. Positional information is incorporated.
5. Transformer layers process the representations.
6. The final hidden representation is converted into vocabulary logits.
7. Logits are converted into probabilities.
8. A decoding strategy selects the next token.
9. The process repeats until a stopping condition is reached.

### Example

```python
from transformers import pipeline

generator = pipeline(
    "text-generation",
    model="YOUR_MODEL_ID"
)

result = generator(
    "Artificial Intelligence is",
    max_new_tokens=50,
    do_sample=False
)

print(result[0]["generated_text"])
```

### Important parameters

- `max_new_tokens`: Maximum number of newly generated tokens.
- `do_sample`: Whether to sample from the probability distribution.
- `temperature`: Controls randomness when sampling.
- `top_p`: Restricts sampling to a probability mass.
- `top_k`: Restricts sampling to the highest-scoring K tokens.
- `eos_token_id`: Token ID indicating the end of a sequence.
- `pad_token_id`: Token ID used for padding sequences.

Not every model or generation API supports every parameter.

### Use cases
- Conversational AI.
- Text generation.
- Code completion.
- Content classification.
- Summarization.

### Pros
- Flexible language processing.
- General-purpose learning.
- Can perform multiple tasks with the same model.

### Cons
- Prediction does not guarantee factual correctness.
- Long generation can be expensive.
- Output depends on context and decoding configuration.

### Production standards
- Set reasonable generation limits.
- Define stopping conditions.
- Validate structured outputs.
- Handle timeouts and API failures.
- Use deterministic decoding where consistency is important.

## 3. Transformer Architecture

### What
The Transformer is a neural network architecture introduced in the 2017 research paper "Attention Is All You Need".

It uses attention mechanisms to understand relationships between tokens instead of relying primarily on sequential recurrence.

### Why
Earlier recurrent architectures such as RNNs and LSTMs processed sequences step by step, making parallel training difficult.

Transformers enable much more parallelizable processing during training.

### Main components

**1. Input embeddings**

Convert token IDs into numerical vectors.

**2. Positional encoding or positional information**

Provides information about token positions and order.

**3. Self-attention**

Calculates relationships between tokens.

**4. Multi-head attention**

Uses multiple attention heads to learn different relationships.

**5. Feed-forward network (FFN)**

Processes each token representation through neural network layers.

**6. Residual connections**

Help information and gradients flow through deep networks.

**7. Layer normalization**

Stabilizes training.

**8. Output projection**

Converts hidden representations into vocabulary logits.

### Architecture flow

```text
Input Text
    |
    v
Tokenizer
    |
    v
Token IDs
    |
    v
Token Embeddings
    |
    v
Positional Information
    |
    v
Transformer Block
    |
    +--> Multi-Head Attention
    |
    +--> Residual + Normalization
    |
    +--> Feed Forward Network
    |
    +--> Residual + Normalization
    |
    v
Output Projection
    |
    v
Logits / Probabilities
    |
    v
Next Token Generation
```

### Types of Transformer architectures

**Encoder-only**
- Reads and represents input sequences.
- Commonly used for classification and embeddings.
- Example: BERT.

**Decoder-only**
- Predicts subsequent tokens.
- Commonly used for text generation.
- Examples: GPT-style and Llama-style models.

**Encoder-decoder**
- Encodes an input and generates an output.
- Useful for sequence-to-sequence tasks.
- Example: T5.

### Code example

```python
import torch
from transformers import AutoTokenizer, AutoModel

model_name = "YOUR_MODEL_ID"

tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModel.from_pretrained(model_name)

inputs = tokenizer(
    "Explain transformer architecture",
    return_tensors="pt"
)

with torch.no_grad():
    outputs = model(**inputs)

print(outputs.last_hidden_state.shape)
```

### Important attributes
- `input_ids`: Numerical token IDs.
- `attention_mask`: Indicates which positions are valid tokens.
- `last_hidden_state`: Final contextual token representations.
- `hidden_size`: Dimension of hidden representations.
- `num_hidden_layers`: Number of Transformer layers.
- `num_attention_heads`: Number of attention heads.
- `max_position_embeddings`: Positional capacity in architectures that expose this attribute.

Exact model configuration attributes depend on the architecture.

### Pros
- Parallelizable training.
- Strong contextual representations.
- Scales effectively with model size and data.

### Cons
- Standard full attention has quadratic sequence-length complexity.
- Can require substantial GPU memory.
- Large models are expensive to train and serve.

### Production standards
- Choose an architecture appropriate to the task.
- Benchmark memory and throughput.
- Use batching and optimized attention implementations.
- Consider quantization when memory is constrained.
- Monitor GPU utilization and token throughput.

## 4. Attention Mechanism

### What
Attention is a mechanism that allows a model to determine which tokens are relevant to another token when processing a sequence.

Example:

"The animal didn't cross the road because it was tired."

Attention helps the model associate "it" with the relevant context.

### Why
Not every word in a sentence is equally important. Attention allows the model to dynamically calculate relationships between tokens.

### How

Attention uses three principal components:

- Query (Q): What information is this token looking for?
- Key (K): What information does each token provide?
- Value (V): What information should be retrieved?

Scaled dot-product attention:

Attention(Q,K,V) = softmax(QKᵀ / √dₖ)V

Where:
- Q = Query matrix.
- K = Key matrix.
- V = Value matrix.
- dₖ = Dimension of each key vector.
- Softmax = Converts scores into normalized weights.

### Types
- Self-attention: Tokens attend to other tokens in the same sequence.
- Cross-attention: One sequence attends to another sequence.
- Causal attention: Prevents a token from attending to future tokens.
- Multi-head attention: Uses multiple attention operations in parallel.

### Code example

```python
import torch
import torch.nn.functional as F

query = torch.randn(1, 4, 8)
key = torch.randn(1, 4, 8)
value = torch.randn(1, 4, 8)

scores = torch.matmul(
    query,
    key.transpose(-2, -1)
) / (8 ** 0.5)

weights = F.softmax(scores, dim=-1)

output = torch.matmul(weights, value)

print(output.shape)
```

### Use cases
- Language understanding.
- Long-context processing.
- Document analysis.
- Machine translation.
- Conversational context.

### Pros
- Captures token relationships.
- Dynamically focuses on relevant information.
- Supports parallel computation.

### Cons
- Standard attention can be memory-intensive.
- Long sequences increase computational requirements.
- Attention weights are not a complete explanation of model reasoning.

### Production standards
- Use optimized attention kernels where supported.
- Understand causal masking requirements.
- Benchmark long-context performance.
- Use context management and retrieval rather than sending unnecessary documents.

## 5. Tokens and Tokenization

### What
A token is a numerical unit representing text processed by an LLM.

A token may represent:
- A complete word.
- Part of a word.
- A punctuation mark.
- A space or text fragment.
- A special control token.

Tokenization converts text into token IDs.

### Why
Neural networks process numbers, not raw text. Tokenization converts human-readable language into numerical representations.

### How

Example:

```text
Input:
"Learning Large Language Models"

Tokenization:
["Learning", " Large", " Language", " Models"]

Token IDs:
[1234, 5678, 9012, 3456]
```

Illustrative only: actual tokenization depends on the tokenizer.

### Code example

```python
import tiktoken

encoding = tiktoken.encoding_for_model(
    "YOUR_SUPPORTED_MODEL"
)

text = "Learning Large Language Models"

tokens = encoding.encode(text)

print("Token IDs:", tokens)
print("Token count:", len(tokens))

decoded = encoding.decode(tokens)

print("Decoded:", decoded)
```

### Important attributes
- `encode()`: Converts text into token IDs.
- `decode()`: Converts token IDs back into text.
- `encode_batch()`: Encodes multiple inputs where supported.
- `special_tokens`: Tokens with special control or formatting meanings.
- `vocabulary_size`: Number of token IDs in the tokenizer vocabulary.

### When to use
- Estimating API cost.
- Checking context limits.
- Preparing model inputs.
- Chunking documents.
- Controlling prompt size.

### Pros
- Efficient numerical representation.
- Handles unfamiliar words through subword tokenization.
- Standardizes model input.

### Cons
- Token counts vary by language.
- A word does not necessarily equal one token.
- Different models can use different tokenizers.

### Production standards
- Use the tokenizer associated with the target model.
- Count both input and output tokens.
- Leave room for system instructions and tool outputs.
- Do not assume one provider's token count applies to another provider.

## 6. Context Windows

### What
The context window is the maximum amount of tokenized information a model can process within a particular request or interaction.

It may include:
- System instructions.
- Developer instructions.
- User messages.
- Conversation history.
- Retrieved documents.
- Tool results.
- Generated output, depending on the model and API limits.

### Why
The model needs context to understand the current task and maintain relevant information.

### How

Example:

```text
Context Window
--------------------------------
System Prompt          500 tokens
Conversation History  2,000 tokens
Retrieved Documents   5,000 tokens
Current Question       200 tokens
Reserved Output       1,000 tokens
--------------------------------
Total                 8,700 tokens
```

The example is illustrative.

### Important parameters
- `context_window`: Maximum supported context capacity.
- `max_input_tokens`: Maximum allowed input tokens, if separately specified.
- `max_output_tokens`: Maximum generated output tokens.
- `max_new_tokens`: Maximum additional tokens in generation APIs.
- `truncation`: Whether excess input is removed.
- `padding`: Adds tokens to align sequences in batch processing.

These are not universal parameter names; consult the provider's documentation.

### Code example

```python
from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained(
    "YOUR_MODEL_ID"
)

prompt = """
Explain RAG architecture and its components.
"""

tokens = tokenizer.encode(prompt)

print("Input token count:", len(tokens))
```

### Use cases
- Long-document question answering.
- Conversational memory.
- RAG systems.
- Codebase analysis.
- Legal and financial document processing.

### Pros
- More information can be considered in one request.
- Reduces the need to split some documents.
- Helps maintain conversation context.

### Cons
- Larger context can increase cost and latency.
- Relevant information can be overlooked.
- Long context does not guarantee perfect recall.
- Context limits still exist.

### Production standards
- Do not automatically send the entire conversation history.
- Use summarization for older conversation turns.
- Use semantic retrieval to select relevant documents.
- Reserve sufficient output tokens.
- Monitor context usage.
- Test retrieval quality at realistic context lengths.

## 7. Embeddings and Semantic Representations

### What
An embedding is a numerical vector representing the semantic characteristics of text, images or other data.

Example:

```text
"How can I reset my password?"
        |
        v
[0.12, 0.45, -0.23, 0.78, ...]
```

Similar meanings are generally represented by vectors that are closer under an appropriate similarity metric.

### Why
Traditional keyword search may miss documents that express the same meaning using different words.

Embeddings enable semantic search.

### How

1. Input text is passed into an embedding model.
2. The model generates a vector.
3. Vectors are stored in a vector database.
4. A user query is converted into a vector.
5. Similarity search retrieves relevant vectors.
6. Retrieved content is provided to an LLM.

### Similarity metrics

**Cosine similarity**

Measures the angle between two vectors.

cosine(A,B) = (A · B) / (||A|| ||B||)

**Euclidean distance**

Measures straight-line distance between vectors.

**Dot product**

Measures the product of vector components.

Metric selection should match the embedding model and indexing configuration.

### Code example

```python
from openai import OpenAI

client = OpenAI()

response = client.embeddings.create(
    model="YOUR_EMBEDDING_MODEL",
    input=[
        "How do I reset my password?",
        "How can I recover my account?"
    ]
)

for item in response.data:
    print(item.embedding[:5])
```

### Important attributes
- `input`: Text to convert into embeddings.
- `model`: Embedding model identifier.
- `dimensions`: Requested vector dimensionality, if supported.
- `encoding_format`: Returned representation format, if supported.
- `similarity_metric`: Search metric configured in the vector database.
- `chunk_size`: Number of tokens or characters used for document segmentation.

### Use cases
- Semantic search.
- RAG.
- Recommendation engines.
- Duplicate detection.
- Document clustering.
- Knowledge management.

### Pros
- Finds semantically related content.
- Supports natural-language search.
- Useful for large document collections.

### Cons
- Embeddings may lose fine-grained details.
- Quality depends on the embedding model.
- Poor chunking reduces retrieval accuracy.
- Vector storage and indexing require infrastructure.

### Production standards
- Use the same compatible embedding model for indexing and querying.
- Version embeddings when models change.
- Store document IDs and metadata.
- Apply access-control filters before retrieval.
- Evaluate retrieval using Recall@K, Precision@K and MRR.
- Consider hybrid search combining keywords and vectors.

## 8. Model Inference

### What
Inference is the process of using a trained model to generate predictions or responses.

Training changes model weights. Inference uses the trained weights to produce outputs.

### Why
Inference is how an LLM becomes available to applications and end users.

### How

1. Receive user input.
2. Validate the request.
3. Tokenize input.
4. Execute model computation.
5. Generate tokens.
6. Decode the output.
7. Return the response.

### Types of inference

**Online inference**
- Real-time API requests.
- Used by chatbots and assistants.

**Batch inference**
- Processes multiple requests together.
- Used for large-scale document processing.

**Streaming inference**
- Returns generated tokens progressively.
- Improves perceived response time.

### Code example

```python
from transformers import pipeline

generator = pipeline(
    "text-generation",
    model="YOUR_MODEL_ID",
    device_map="auto"
)

response = generator(
    "Explain machine learning.",
    max_new_tokens=100
)

print(response[0]["generated_text"])
```

### Important parameters
- `device`: CPU or GPU execution device.
- `device_map`: Controls model placement across devices.
- `batch_size`: Number of inputs processed together.
- `max_new_tokens`: Generation limit.
- `do_sample`: Sampling configuration.
- `num_return_sequences`: Number of generated sequences.
- `use_cache`: Whether supported attention key/value caches are used.

### Important performance metrics
- Time to First Token (TTFT).
- Time Per Output Token (TPOT).
- Tokens per second.
- Requests per second.
- End-to-end latency.
- GPU memory usage.

### Pros
- Enables production model serving.
- Supports real-time and batch workloads.
- Can scale through distributed infrastructure.

### Cons
- GPU infrastructure can be expensive.
- High concurrency creates resource pressure.
- Large models require careful memory management.

### Production standards
- Implement retries with controlled backoff.
- Set timeouts.
- Use batching where appropriate.
- Monitor p50, p95 and p99 latency.
- Use autoscaling where appropriate.
- Monitor throughput and GPU memory.
- Implement request limits and authentication.

## 9. Temperature, Top-P and Top-K

These are decoding parameters that control how the model chooses the next token.

### 9.1 Temperature

**What:** Controls how sharply or broadly the model samples from its token probability distribution.

**Why:** Allows control over response variability.

**How:**

Temperature modifies logits before softmax:

P(token) = softmax(logits / T)

Where T is temperature.

Typical interpretation:

- Temperature = 0 or near zero: More deterministic selection, depending on implementation.
- Temperature = 0.2: More predictable.
- Temperature = 0.7: More varied.
- Temperature = 1.0: Original distribution.
- Temperature greater than 1: Flatter probability distribution.

Exact behaviour varies by provider. Some APIs accept zero; others impose a minimum.

**When to use**
- Low: Structured extraction, predictable answers.
- Medium: General conversation.
- Higher: Creative writing and brainstorming.

**Pros**
- Controls variability.
- Easy to tune.

**Cons**
- Higher temperature can increase inconsistency.
- Lower temperature does not guarantee correctness.

### 9.2 Top-P (Nucleus Sampling)

**What:** Selects tokens from the smallest set whose cumulative probability reaches P.

Example:

```text
Token A = 0.50
Token B = 0.25
Token C = 0.15
Token D = 0.10

Top-P = 0.75

Selected candidates:
A and B
```

**Why:** Dynamically limits the candidate set according to probability mass.

**When**
- Use moderate values for conversational generation.
- Use lower values when more constrained sampling is desired.

### 9.3 Top-K

**What:** Restricts token selection to the K highest-probability candidates.

Example:

```text
Token probabilities:

A = 0.40
B = 0.30
C = 0.20
D = 0.10

Top-K = 2

Candidates:
A and B
```

**Why:** Prevents low-ranking tokens from being selected.

**When**
- Useful for controlling sampling diversity.
- Common in open-source generation frameworks.

### Comparison

| Parameter | Purpose | Main control |
|---|---|---|
| Temperature | Changes probability distribution | Randomness |
| Top-P | Restricts cumulative probability | Candidate probability mass |
| Top-K | Restricts candidate count | Number of candidates |

### Code example

```python
from transformers import pipeline

generator = pipeline(
    "text-generation",
    model="YOUR_MODEL_ID"
)

result = generator(
    "Write a short story about AI.",
    max_new_tokens=100,
    do_sample=True,
    temperature=0.7,
    top_p=0.9,
    top_k=50
)

print(result[0]["generated_text"])
```

### Important production rule
Do not blindly tune temperature, top-P and top-K together.

Change one parameter at a time and evaluate the impact.

Also, some hosted APIs do not expose top-K or may reject combinations of sampling parameters.

## 10. Hallucinations and Limitations

### What
A hallucination occurs when an LLM generates information that sounds plausible but is incorrect, unsupported or fabricated.

Example:

User: "Who wrote a fictional book called Advanced Quantum Programming in 1890?"

The model might invent an author and publication details.

### Why
LLMs generate outputs based on learned patterns and available context. They do not automatically verify every factual claim against a trusted database.

### Common causes
- Missing information.
- Ambiguous prompts.
- Outdated training information.
- Incorrect retrieved documents.
- Poor retrieval ranking.
- Excessive generation.
- Conflicting instructions.

### How to reduce hallucinations

1. Use RAG.
2. Provide trusted source documents.
3. Ask for citations or supporting evidence.
4. Validate important claims.
5. Use structured outputs.
6. Use tools or APIs for live information.
7. Allow the model to say it does not know.
8. Add evaluation and human review.

### Example

```python
prompt = """
Answer only using the supplied context.

If the answer is unavailable,
respond with: "Insufficient information."

Context:
{context}

Question:
{question}
"""
```

### Use cases
- Enterprise knowledge assistants.
- Customer support.
- Financial document analysis.
- Healthcare information systems.
- Legal research support.

### Pros of mitigation
- Improves factual reliability.
- Makes responses more auditable.
- Reduces unsupported claims.

### Cons
- RAG does not eliminate hallucinations.
- Verification adds latency and cost.
- Sources themselves may be incorrect.
- Citations can be incorrectly associated with claims.

### Production standards
- Ground factual answers in authoritative sources.
- Verify citations against retrieved documents.
- Use confidence thresholds carefully.
- Escalate high-risk decisions to humans.
- Maintain evaluation datasets.
- Track hallucination and unsupported-claim rates.

## 11. System Prompts vs User Prompts

### What

**System prompt:** High-level instructions defining the assistant's role, behaviour and constraints.

**User prompt:** The actual request or question submitted by the user.

Some APIs also expose developer messages or other instruction levels.

### Why
Separating application behaviour from user requests improves consistency and makes applications easier to maintain.

### How

Example:

```python
from openai import OpenAI

client = OpenAI()

response = client.responses.create(
    model="YOUR_SUPPORTED_MODEL",
    instructions=(
        "You are a technical assistant. "
        "Explain concepts clearly. "
        "Do not invent technical specifications."
    ),
    input="Explain REST APIs."
)

print(response.output_text)
```

### Comparison

| Feature | System instructions | User prompt |
|---|---|---|
| Purpose | Define behaviour | Request a task |
| Source | Application | End user |
| Typical content | Role and constraints | Questions and data |
| Scope | Conversation or request, depending on API | Individual request |
| Example | Act as a technical assistant | Explain Kubernetes |

### Use cases
- Enterprise assistants.
- Customer support bots.
- Coding assistants.
- Domain-specific agents.
- Structured extraction.

### Pros
- Separates application rules from user input.
- Improves consistency.
- Supports reusable prompt templates.

### Cons
- Prompt instructions can conflict.
- Prompts are not security boundaries.
- User content may contain prompt injection attacks.
- Longer prompts consume tokens.

### Production standards
- Keep instructions concise and version-controlled.
- Treat user-provided documents as untrusted data.
- Never expose secrets in prompts.
- Validate tool calls independently.
- Enforce authorization in application code, not only through prompts.
- Test prompt injection and instruction conflicts.

## 12. Open-Source vs Proprietary Models

### What

**Open-weight models:** Models whose trained weights are publicly available under their applicable licence.

**Proprietary models:** Models controlled by providers and typically accessed through APIs or restricted deployment arrangements.

Important distinction: Open weights do not necessarily mean fully open-source training data, code, or unrestricted commercial use.

### Comparison

| Feature | Open-weight | Proprietary |
|---|---|---|
| Model weights | Available under licence | Generally unavailable |
| Hosting | Often self-hostable | Usually provider-hosted |
| Customization | Greater deployment flexibility | Provider-dependent |
| Infrastructure | Customer may manage | Provider often manages |
| Control | More deployment control | Less infrastructure control |
| Maintenance | Customer responsibility | Often provider responsibility |
| Costs | Infrastructure and operations | API or service pricing |

### Examples

Open-weight model families:
- Llama.
- Mistral.
- Qwen.
- Gemma.

Proprietary model families:
- GPT.
- Claude.
- Gemini.

Availability and licence terms vary by individual model.

### When to use open-weight
- Data residency requirements.
- Custom infrastructure.
- Offline or private deployments.
- Specialized fine-tuning.
- Greater control over serving.

### When to use proprietary
- Rapid development.
- Managed infrastructure.
- Access to provider-specific tools.
- Reduced model operations overhead.

### Pros and cons

**Open-weight advantages**
- Deployment flexibility.
- Greater infrastructure control.
- Customization opportunities.

**Open-weight disadvantages**
- GPU infrastructure costs.
- Maintenance and security responsibility.
- Operational complexity.

**Proprietary advantages**
- Managed services.
- Faster integration.
- Provider-supported capabilities.

**Proprietary disadvantages**
- Vendor dependency.
- Usage costs.
- Provider-specific limitations.
- Less control over underlying model infrastructure.

### Production standards
- Review commercial licences.
- Evaluate data retention and privacy policies.
- Benchmark actual workload performance.
- Calculate total cost of ownership.
- Have a model migration strategy.
- Avoid unnecessary vendor lock-in.

## 13. GPT, Claude, Gemini and Llama

### What
These are model families developed by different AI organizations.

### Main differences

**GPT – OpenAI**
- General-purpose language and multimodal models.
- Common application patterns include reasoning, generation, coding and tool use.
- API ecosystem includes structured outputs and tool integrations, depending on model.

**Claude – Anthropic**
- General-purpose assistant models.
- Commonly used for document analysis, writing, coding and complex instruction-following.
- Supports tool-use workflows and long-context tasks depending on model.

**Gemini – Google**
- Multimodal model family.
- Integrates with Google's AI ecosystem.
- Useful for text, image, audio and video workflows depending on model.

**Llama – Meta**
- Open-weight model family.
- Can be deployed using supported hosting infrastructure.
- Offers flexibility for customization and private deployments, subject to licence terms.

### Comparison

| Criteria | GPT | Claude | Gemini | Llama |
|---|---|---|---|---|
| Organization | OpenAI | Anthropic | Google | Meta |
| Access | API/products | API/products | API/products | Weights and hosted services |
| Deployment | Provider-managed | Provider-managed | Provider-managed | Often self-hostable |
| Main consideration | Model capabilities and tools | Model capabilities and instruction following | Multimodal ecosystem | Deployment flexibility |

### How to choose
Do not select a model purely by brand.

Evaluate:
- Accuracy.
- Reasoning performance.
- Coding performance.
- Context length.
- Multimodal support.
- Tool calling.
- Latency.
- Cost.
- Privacy.
- Availability.
- Licence and deployment requirements.

- Create a provider-independent application interface.
- Maintain evaluation datasets.
- Test fallback models.
- Track model versions.
- Avoid assuming that identical prompts produce identical results across providers.

## 14. Model Selection and Trade-offs

### What
Model selection is the process of choosing an LLM that meets application requirements for quality, cost, speed, privacy and scalability.

### Why
The most powerful model is not always the best production model.

A smaller model may be faster, cheaper and sufficient for a specific business task.

### How to select

Step 1: Identify the task.

Examples:
- Classification.
- Summarization.
- Question answering.
- Code generation.
- Complex reasoning.

Step 2: Define requirements.

- Accuracy.
- Latency.
- Cost per request.
- Context length.
- Security.
- Throughput.

Step 3: Benchmark candidate models.

Step 4: Test on real-world data.

Step 5: Compare quality and total operating costs.

Step 6: Deploy with monitoring.

### Example decision matrix

| Requirement | Preferred direction |
|---|---|
| Simple classification | Small, efficient model |
| Complex reasoning | Strong reasoning model |
| High request volume | Efficient model with batching |
| Sensitive data | Approved private deployment |
| Long documents | Suitable long-context model or RAG |
| Multimodal processing | Model supporting required modalities |
| Offline inference | Locally deployable model |

### Example evaluation

```python
models = {
    "model_a": {
        "accuracy": 0.91,
        "latency_ms": 450,
        "cost_per_1000": 2.0
    },
    "model_b": {
        "accuracy": 0.94,
```

### Important trade-offs

**Accuracy vs cost**
A stronger model may improve answer quality but increase expenditure.

**Latency vs quality**
A larger model may take longer to respond.

**Context vs cost**
Longer context may increase input processing costs.

**Customization vs maintenance**
Self-hosting gives more control but increases operational responsibility.

### Pros
- Better application fit.
- More predictable spending.
- Improved user experience.

### Cons
- Benchmarking requires time.
- Results depend on evaluation data.
- Models change over time.
- A single model may not be optimal for every task.

### Production standards
- Use representative evaluation datasets.
- Measure quality and latency together.
- Test edge cases.
- Consider model routing for different task types.
- Maintain a fallback strategy.
- Re-evaluate models after version upgrades.

## 15. LLM Latency and Token Costs

### What
Latency is the time required for an LLM request to produce a response.

Token cost is the expense associated with processing input and generating output tokens.

### Why
These two metrics directly influence user experience and application operating costs.

### Types of latency

**1. Time to First Token (TTFT)**

Time from request submission until the first generated token is received.

**2. Time Per Output Token (TPOT)**

Average time required to generate each subsequent output token.

**3. End-to-End Latency**

Total time required to complete the request.

### How latency is affected
- Model size.
- Input token count.
- Output token count.
- GPU availability.
- Network overhead.
- Concurrent requests.
- Batch size.
- Attention implementation.
- Provider infrastructure.

### Token cost calculation

Formula:

Total Cost =
(Input Tokens / 1,000,000 × Input Price Per Million)
+
(Output Tokens / 1,000,000 × Output Price Per Million)

Example:

```python
input_tokens = 10000
output_tokens = 2000

input_price_per_million = 2.00
output_price_per_million = 8.00

input_cost = (
    input_tokens / 1_000_000
) * input_price_per_million

output_cost = (
    output_tokens / 1_000_000
) * output_price_per_million

total_cost = input_cost + output_cost

print("Input cost:", input_cost)
print("Output cost:", output_cost)
print("Total cost:", total_cost)
```

Illustrative prices in USD, not current provider pricing.

### Important parameters and metrics

- `input_tokens`: Tokens sent to the model.
- `output_tokens`: Tokens generated by the model.
- `max_output_tokens`: Maximum permitted generation.
- `batch_size`: Number of requests processed together.
- `concurrency`: Number of simultaneous requests.
- `timeout`: Maximum allowed request duration.
- `TTFT`: Time to first generated token.
- `TPOT`: Time per output token.
- `TPS`: Tokens generated per second.
- `p50`: Median latency.
- `p95`: Latency below which 95% of measured requests complete.
- `p99`: Latency below which 99% of measured requests complete.

### Example: Measure API latency

```python
import time
from openai import OpenAI

client = OpenAI()

start = time.perf_counter()

response = client.responses.create(
    model="YOUR_SUPPORTED_MODEL",
    input="Explain cloud computing."
)

end = time.perf_counter()

print("Response:", response.output_text)

print(
    "Total latency:",
    round(end - start, 3),
    "seconds"
)
```

This measures total request duration, not streaming TTFT or TPOT.

### How to optimize

1. Reduce unnecessary prompt tokens.
2. Retrieve only relevant documents.
3. Limit excessive output generation.
4. Use smaller models for simpler tasks.
5. Enable streaming.
6. Use caching where appropriate.
7. Batch requests when suitable.
8. Optimize GPU inference.
9. Monitor concurrency.
10. Use model routing.

### Pros of optimization
- Reduced operating costs.
- Faster user experience.
- Higher throughput.
- Better resource utilization.

### Cons
- Aggressive optimization may reduce quality.
- Caching can introduce stale results.
- Smaller models may perform poorly on complex tasks.
- Batching may increase individual request latency.

### Production standards
- Track token usage per user and application.
- Set budget limits and alerts.
- Monitor p50, p95 and p99 latency.
- Measure TTFT and TPOT for streaming workloads.
- Use rate limiting.
- Apply caching carefully.
- Track costs by model and task.
- Establish service-level objectives (SLOs).
