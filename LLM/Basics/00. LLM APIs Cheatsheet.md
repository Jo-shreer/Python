# Part 1 — Project setup

## 1. Introduction to LLM APIs

### What is an LLM API?

An LLM API allows your Python application to send information to a Large Language Model and receive generated responses.

For example, a user sends:

> Explain artificial intelligence in simple words.

Your backend sends this question to an LLM. The model generates an answer, and your backend returns it to the user.

### Why do we need LLM APIs?

LLM APIs allow applications to:
- Answer questions.
- Summarise documents.
- Translate languages.
- Generate content.
- Classify text.
- Extract structured information.
- Power AI assistants and chatbots.

### How does our application use an LLM API?

We will use three main technologies:

| Technology | Responsibility |
|---|---|
| FastAPI | Receives HTTP requests and returns HTTP responses |
| LangChain | Organises prompts, messages, model calls and output processing |
| ChatOpenAI | Communicates with the OpenAI model |

The application flow is:

```text
User
  |
  v
FastAPI endpoint
  |
  v
Validate request with Pydantic
  |
  v
LangChain prompt
  |
  v
ChatOpenAI
  |
  v
OpenAI model
  |
  v
LangChain response
  |
  v
FastAPI JSON response
  |
  v
User
```

**Important:** LangChain does not replace FastAPI. FastAPI manages your backend API, while LangChain manages the LLM interaction.


# Part 2 — API architecture and configuration

## 4. LLM API architecture

### What?

LLM API architecture describes how your application communicates with an external AI model.

### Why?

Understanding the architecture helps you separate responsibilities and troubleshoot problems.

### How?

Our application has five important stages:

**Stage 1 — Client request**

A frontend or another application sends an HTTP request.

```http
POST /chat
Content-Type: application/json
```

Example request body:

```json
{
  "session_id": "session-101",
  "question": "What is machine learning?"
}
```

**Stage 2 — FastAPI**

FastAPI receives the request and validates the JSON using Pydantic.

**Stage 3 — LangChain**

LangChain creates the prompt and combines it with the user's question and conversation history.

**Stage 4 — ChatOpenAI**

`ChatOpenAI` sends the messages to the configured OpenAI model.

**Stage 5 — Response**

The model response returns through LangChain and FastAPI to the client.

The important distinction is:

- FastAPI handles HTTP.
- LangChain handles LLM orchestration.
- ChatOpenAI handles model communication.
- OpenAI hosts and runs the model.

## 5. API authentication and configuration

### What?

Authentication verifies that an application is authorised to access the model API.

### Why?

Without authentication, the OpenAI API cannot identify and authorise your API request.

Your own FastAPI backend may also need authentication so unauthorised people cannot use your application.

### How?

There are two separate security concerns:

1. **OpenAI API authentication:** Your backend uses `OPENAI_API_KEY`.
2. **Your application's authentication:** Your backend decides which clients may call your endpoints.

Create `app/config.py`:

```python
import os
from dotenv import load_dotenv

load_dotenv()

OPENAI_API_KEY = os.getenv("OPENAI_API_KEY")
APP_API_KEY = os.getenv("APP_API_KEY")

if not OPENAI_API_KEY:
    raise RuntimeError("OPENAI_API_KEY is missing")

if not APP_API_KEY:
    raise RuntimeError("APP_API_KEY is missing")
```

### Explanation

```python
load_dotenv()
```

Loads environment variables from the `.env` file.

```python
os.getenv("OPENAI_API_KEY")
```

Reads the OpenAI API key without hardcoding it.

```python
if not OPENAI_API_KEY:
```

Checks that the required configuration exists.

**Important:** The application API key in this example is a simple demonstration of endpoint protection. A real application should normally use proper user authentication, such as OAuth2 or validated JWTs, and user-specific authorisation.

## 6. Initialising ChatOpenAI

### What?

`ChatOpenAI` is LangChain's integration for communicating with OpenAI chat models.

### Why?

It provides a consistent interface for:
- Sending messages.
- Receiving model responses.
- Streaming output.
- Calling tools.
- Producing structured output.
- Making asynchronous requests.

### How?

```python
from app.config import OPENAI_API_KEY

    temperature=0,
    timeout=30,
    max_retries=2,
```

**`api_key=OPENAI_API_KEY`**

Provides the API credential securely from configuration.

The model is initialised once when the application starts, rather than being recreated for every request.

# Part 3 — Making API requests

## 7. Making API requests with LangChain

### What?

An API request sends a question or instructions to the LLM and asks it to generate a response.

### Why?

This is the basic operation behind almost every LLM application.

### How?

The simplest LangChain example:

```python
from langchain_openai import ChatOpenAI

model = ChatOpenAI(
    model="gpt-4.1-mini",
    temperature=0
)

response = model.invoke(
    "Explain artificial intelligence in simple words."
)

print(response.content)
```

### Explain the code

```python
model.invoke(...)
```

Sends the input to the model and waits for the completed response.

```python
response.content
```

Extracts the text generated by the model.

### Expected output

```text
Artificial intelligence is technology that allows
computers to perform tasks that usually require
human intelligence, such as understanding language,
recognising images and solving problems.
```

### How does this work inside FastAPI?

Instead of calling `model.invoke()` directly from a command-line script, we expose the functionality through an HTTP endpoint.

```python
from fastapi import FastAPI
from pydantic import BaseModel
from langchain_openai import ChatOpenAI

app = FastAPI()

model = ChatOpenAI(
    model="gpt-4.1-mini",
    temperature=0
)

class ChatRequest(BaseModel):
    question: str

@app.post("/chat")
async def chat(request: ChatRequest):

    response = await model.ainvoke(
        request.question
    )

    return {
        "answer": response.content
    }
```

### Explanation

```python
app = FastAPI()
```

Creates the backend application.

```python
class ChatRequest(BaseModel):
```

Defines the expected request structure.

```python
@app.post("/chat")
```

Creates a POST endpoint called `/chat`.

```python
await model.ainvoke(...)
```

Calls the model asynchronously.

```python
return {"answer": response.content}
```

Returns the model's answer as JSON.

### Expected HTTP response

```json
{
  "answer": "Artificial intelligence allows computers to perform tasks that normally require human intelligence."
}
```

## 8. Understanding request and response formats

### What?

An API request contains the information sent to the backend. An API response contains the information returned by the backend.

### Why?

Consistent request and response structures make applications easier to integrate, validate and maintain.

### How?

Use Pydantic models.

Create `app/schemas.py`:

```python
from pydantic import BaseModel, Field

class ChatRequest(BaseModel):

    session_id: str = Field(
        min_length=1,
        max_length=100
    )

    question: str = Field(
        min_length=1,
        max_length=5000
    )


class ChatResponse(BaseModel):

    session_id: str

    answer: str

    model: str
```

### Explanation

`ChatRequest` defines what the client must send.

`session_id` identifies the conversation.

`question` contains the user's message.

`Field()` adds validation rules.

`ChatResponse` defines the format returned by the backend.

### Example request

```json
{
  "session_id": "session-101",
  "question": "What is an LLM?"
}
```

### Example response

```json
{
  "session_id": "session-101",
  "answer": "An LLM is a large language model trained to understand and generate text.",
  "model": "gpt-4.1-mini"
}
```

If the user sends an invalid request, FastAPI automatically returns a validation error instead of passing invalid data to the model.

## 9. System, user and assistant messages

### What?

Chat models use different message roles to represent a conversation.

| Message | Meaning |
|---|---|
| SystemMessage | Instructions for the assistant |
| HumanMessage | Message from the user |
| AIMessage | Message generated by the AI |

### Why?

The model needs to understand its instructions, the user's request and the previous assistant responses.

### How?

```python
from langchain_core.messages import (
    SystemMessage,
    HumanMessage
)

messages = [

    SystemMessage(
        content="You are a helpful Python teacher."
    ),

    HumanMessage(
        content="Explain Python functions."
    )

]

response = model.invoke(messages)

print(response.content)
```

### Explanation

The `SystemMessage` tells the model how to behave.

The `HumanMessage` contains the user's actual question.

The model returns an `AIMessage`.

You can inspect its content using:

```python
print(response.content)
```

### Expected output

```text
A Python function is a reusable block of code
that performs a particular task. You define it
using the def keyword.
```

**Important:** A system prompt is an instruction, not a security boundary. Your backend must still enforce permissions and validate model output.

# Part 4 — Model parameters and tokens

## 10. Model parameters

### What?

Model parameters control how the model generates responses.

Important parameters include:

- Temperature
- Top-P
- Maximum output tokens

### Why?

Different applications need different response styles and output limits.

### How?

```python
model = ChatOpenAI(
    model="gpt-4.1-mini",
    temperature=0
)
```

### Temperature

Temperature controls the randomness of generation.

| Temperature | General behaviour |
|---|---|
| 0 | More consistent |
| 0.3 | Some variation |
| 0.7 | More creative |
| 1.0 | More variation |

Examples:

For data extraction:

```python
temperature=0
```

For creative writing:

```python
temperature=0.8
```

### Top-P

Top-P controls the range of likely next tokens considered during generation.

Example:

```python
response = model.invoke(
    "Explain AI",
    top_p=0.9
)
```

Use temperature or Top-P adjustments carefully. You generally do not need to tune both simultaneously.

### Maximum output tokens

The output token limit controls how much the model can generate.

For example:

```python
response = model.invoke(
    "Explain machine learning",
    max_tokens=300
)
```

The exact supported token parameter can depend on the model and API integration version. Some models or API paths use `max_completion_tokens` instead. Check the selected model's current parameter support.

## 11. Tokenization and context windows

### What?

A token is a piece of text processed by an LLM.

A token may represent:
- A complete word.
- Part of a word.
- Punctuation.
- A space or other text unit.

A context window is the amount of input and output information a model can process in a request.

### Why?

Tokens matter because they affect:
- Input limits.
- Output limits.
- API costs.
- Conversation history.
- Performance.

### How?

Install and use `tiktoken`:

```python
import tiktoken

encoding = tiktoken.encoding_for_model(
    "gpt-4o"
)

text = "LangChain connects applications to LLMs."

tokens = encoding.encode(text)

print("Token count:", len(tokens))
```

### Explanation

`encoding_for_model()` selects a tokenizer associated with a model family.

`encode()` converts text into token IDs.

`len(tokens)` counts the resulting tokens.

### Expected output

```text
Token count: 9
```

The exact count depends on the tokenizer and text.

**Important:** This is an estimate for planning. It does not necessarily include all chat-message formatting, image, audio or other multimodal token costs.

# Part 5 — Streaming and asynchronous requests

## 12. Streaming responses

### What?

Streaming allows the application to receive parts of the model's response as they become available.

Without streaming:

```text
User sends question
       |
       v
Wait for full answer
       |
       v
Receive complete answer
```

With streaming:

```text
User sends question
       |
       v
Receive first text chunk
       |
       v
Receive next text chunk
       |
       v
Receive remaining chunks
```

### Why?

Streaming improves the user experience for long answers because the user does not need to wait for the entire response.

### How?

Basic LangChain streaming:

```python
for chunk in model.stream(
    "Explain artificial intelligence."
):

    print(
        chunk.content,
        end="",
        flush=True
    )
```

### Explanation

`model.stream()` returns chunks as the model generates them.

`chunk.content` contains the content of each chunk.

`end=""` avoids printing a newline after every chunk.

`flush=True` makes the output appear immediately.

### How to stream through FastAPI

FastAPI supports streaming responses using `StreamingResponse`.

```python
import json

from fastapi.responses import StreamingResponse
from langchain_core.output_parsers import StrOutputParser

@app.post("/chat/stream")
async def chat_stream(request: ChatRequest):

    async def generate():

        chain = model | StrOutputParser()

        async for chunk in chain.astream(
            request.question
        ):

            yield (
                "data: "
                + json.dumps({"text": chunk})
                + "\n\n"
            )

        yield "data: [DONE]\n\n"

    return StreamingResponse(
        generate(),
        media_type="text/event-stream"
    )
```

### Explanation

`StrOutputParser()` extracts text from LangChain model messages.

`chain.astream()` streams the model output asynchronously.

`yield` sends each chunk to the client without waiting for the complete answer.

`StreamingResponse` sends the chunks as an HTTP streaming response.

The example uses Server-Sent Events (SSE), where each event begins with `data:`.

### Example streamed events

```text
data: {"text": "Artificial"}

data: {"text": " intelligence"}

data: {"text": " allows computers"}

data: [DONE]
```

The actual chunk sizes and wording vary.

## 13. Asynchronous API calls

### What?

An asynchronous API call allows Python to wait for an external operation without blocking the entire event loop.

### Why?

LLM requests involve network communication. They can take several seconds.

Asynchronous operations help a FastAPI server handle multiple requests efficiently.

### How?

Use `ainvoke()` instead of `invoke()` inside an async endpoint.

```python
@app.post("/chat")
async def chat(request: ChatRequest):

    response = await model.ainvoke(
        request.question
    )

    return {
        "answer": response.content
    }
```

### Explanation

`async def` defines an asynchronous endpoint.

`await` waits for the model response without blocking the event loop in the usual synchronous way.

`ainvoke()` is LangChain's asynchronous invocation method.

### Running multiple independent requests

```python
import asyncio

async def ask_question(question):

    response = await model.ainvoke(question)

    return response.content


async def main():

    questions = [
        "What is Python?",
        "What is FastAPI?",
        "What is LangChain?"
    ]

    results = await asyncio.gather(
        *[
            ask_question(q)
            for q in questions
        ]
    )

    for result in results:
        print(result)


asyncio.run(main())
```

### Explanation

`asyncio.gather()` runs independent asynchronous tasks concurrently.

This can reduce total waiting time compared with making each request sequentially.

**Important:** Concurrency increases the number of simultaneous requests. Production systems need rate limits, concurrency controls and sensible timeouts.

# Part 6 — Error handling and rate limits

## 14. Error handling and retries

### What?

Error handling allows your application to respond safely when something goes wrong.

Common failures include:
- Invalid API credentials.
- Rate limits.
- Network problems.
- Timeouts.
- Invalid requests.
- Provider errors.

### Why?

Without error handling, a temporary API failure can cause your entire backend request to fail unexpectedly.

### How?

LangChain configuration:

```python
model = ChatOpenAI(
    model="gpt-4.1-mini",
    temperature=0,
    timeout=30,
    max_retries=2
)
```

For explicit error handling, use OpenAI exception classes:

```python
from openai import (
    AuthenticationError,
    RateLimitError,
    APITimeoutError,
    APIConnectionError,
    APIStatusError
)

async def generate_answer(question):

    try:

        response = await model.ainvoke(
            question
        )

        return response.content

    except AuthenticationError:

        return "Model authentication failed."

    except RateLimitError:

        return "The model API rate limit was reached."

    except APITimeoutError:

        return "The model request timed out."

    except APIConnectionError:

        return "Could not connect to the model API."

    except APIStatusError:

        return "The model provider returned an API error."
```

### Explanation

Each `except` block handles a different type of failure.

`max_retries=2` allows supported transient failures to be retried by the integration.

The exception handler gives the application a controlled response instead of exposing a traceback to the user.

**Production note:** Do not return raw exception details, credentials or internal system information to clients. Log the technical details securely on the server.

## 15. Rate limits and quota management

### What?

Rate limits control how frequently an application can make API requests.

A provider may limit:
- Requests per minute.
- Tokens per minute.
- Requests per day.
- Account usage or available quota.

### Why?

Rate limits protect the provider's infrastructure and help manage API capacity.

Your backend also needs limits to protect itself from excessive usage.

### How?

A simple concurrency limit:

```python
import asyncio

semaphore = asyncio.Semaphore(5)

async def limited_model_call(question):

    async with semaphore:

        response = await model.ainvoke(
            question
        )

        return response.content
```

### Explanation

`asyncio.Semaphore(5)` allows up to five tasks at a time through this semaphore in this Python process.

If five tasks are already running, another task waits.

### Important production consideration

This is not a complete rate limiter.

It does not control total usage across multiple server processes, containers or machines.

For production, consider:
- Redis-based rate limiting.
- API gateway limits.
- Per-user request quotas.
- Distributed concurrency controls.
- Background queues for high-volume workloads.

## 16. Token usage and cost management

### What?

The model API may report how many input and output tokens were used.

### Why?

Token usage helps you understand:
- How much each request costs.
- Which users consume the most resources.
- Whether prompts are unnecessarily large.
- Whether conversation history is growing too much.

### How?

```python
response = await model.ainvoke(

)

print(response.usage_metadata)
```

A response may contain:

```python
{
    "input_tokens": 15,
    "output_tokens": 50,
    "total_tokens": 65
}
```

The exact metadata depends on the model and integration.

### Calculate an estimated cost

```python
input_tokens = 1000
output_tokens = 500

# Illustrative prices only.
# Replace these with the current prices
# for your selected model.

input_price_per_million = 0.20
output_price_per_million = 0.80

input_cost = (
    input_tokens / 1_000_000
) * input_price_per_million

output_cost = (
    output_tokens / 1_000_000

total_cost = input_cost + output_cost

print("Estimated cost:", total_cost)
```

### Expected output

```text
Estimated cost: 0.0006
```

**Production note:** Use the actual model pricing and usage information applicable to your account. Some model and multimodal usage may require additional cost calculations.

## 17. Conversation history and context management

### What?

Conversation history stores previous user and assistant messages so the model can understand the ongoing conversation.

### Why?

Consider this conversation:

```text
User: My name is Alex.

Assistant: Nice to meet you, Alex.

User: What is my name?
```

If you only send the last question, the model may not know the user's name.

If you send the conversation history, it can answer using the previous context.

### How?

Use LangChain messages:

```python
from langchain_core.messages import (
    HumanMessage,
    AIMessage
)

history = [

    HumanMessage(
        content="My name is Alex."
    ),

    AIMessage(
        content="Nice to meet you, Alex."
    )

]

history.append(
    HumanMessage(
        content="What is my name?"
    )
)

response = await model.ainvoke(history)

print(response.content)
```

### Expected output

```text
Your name is Alex.
```

### Using a prompt template with history

```python
from langchain_core.prompts import (
    ChatPromptTemplate,
    MessagesPlaceholder
)

prompt = ChatPromptTemplate.from_messages([

    (
        "system",
        "You are a helpful assistant."
    ),

    MessagesPlaceholder(
        variable_name="history"
    ),

    (
        "human",
        "{question}"
    )

])
```

### Explanation

`MessagesPlaceholder` reserves a position for previous conversation messages.

`{question}` is replaced with the current user question.

You can combine the prompt with the model:

```python
chain = prompt | model

response = await chain.ainvoke({

    "history": history,

    "question": "What did I tell you earlier?"

})

print(response.content)
```

### Important production consideration

Do not use one global history list for every user.

Each user or conversation must have separate history, with proper access controls.

For production, store conversations in a database or suitable session store such as Redis or PostgreSQL.

Also limit history length and consider summarising older messages when conversations become long.

# Part 8 — Multimodal APIs and Python integration

## 18. Multimodal APIs

### What?

Multimodal AI can work with more than one type of information.

Examples include:
- Text.
- Images.
- Audio.
- Video, where supported.

### Why?

Users may want to ask questions about images, provide audio recordings or work with information that is not plain text.

### How? — Text

```python
response = await model.ainvoke(
    "Explain what a neural network is."
)

print(response.content)
```

This sends text and receives text.

### How? — Images

A vision-capable model can receive text and image content together.

```python
from langchain_core.messages import HumanMessage

message = HumanMessage(
    content=[

        {
            "type": "text",
            "text": "Describe this image."
        },

        {
            "type": "image_url",
            "image_url": {
                "url": "https://example.com/image.jpg"
            }
        }

    ]
)

response = await model.ainvoke([message])

print(response.content)
```

### Explanation

`HumanMessage` represents the user's input.

The first content block contains the text instruction.

The second content block contains an image URL.

The selected model must support image input, and the image must be accessible to the API.

### How? — Audio

Audio tasks include:

- Speech-to-text.
- Text-to-speech.
- Audio understanding.
- Voice conversations.

Audio transcription and speech generation generally use dedicated audio APIs or integrations.

A typical architecture is:

```text
Audio upload
     |
     v
Audio transcription service
     |
     v
Transcribed text
     |
     v
LangChain ChatOpenAI
     |
     v
Generated text response
     |
     v
Optional text-to-speech service
     |

Audio response
```

**Important:** `ChatOpenAI` is not a universal replacement for dedicated transcription or text-to-speech services. Choose a model and endpoint that support the specific audio task.

## 20. LLM APIs with LangChain

### What?

LangChain provides reusable components for working with language models.

Important components include:

| Component | Purpose |
|---|---|
| `ChatOpenAI` | Connects to the OpenAI model |
| `ChatPromptTemplate` | Creates reusable chat prompts |
| `MessagesPlaceholder` | Inserts conversation history |
| `StrOutputParser` | Extracts text output |
| `with_structured_output()` | Produces schema-based output |
| `ainvoke()` | Asynchronous model invocation |
| `astream()` | Asynchronous streaming |

### Why?

Without LangChain, you would need to manage prompt construction, message formatting and output handling yourself.

LangChain gives you reusable building blocks.

### How? — Prompt templates

```python
from langchain_core.prompts import (
    ChatPromptTemplate
)

from langchain_core.output_parsers import (
    StrOutputParser
)

prompt = ChatPromptTemplate.from_messages([

    (
        "system",
        "You are an experienced Python teacher."
    ),

    (
        "human",
        "Explain this topic: {topic}"
    )

])

chain = (
    prompt
    | model
    | StrOutputParser()
)

response = await chain.ainvoke({

    "topic": "Python decorators"

})

print(response)
```

### Explain the code

`ChatPromptTemplate` creates a reusable prompt.

`{topic}` is a dynamic variable.

The pipe operator `|` connects components together.

The chain works in this order:

```text
Input dictionary
      |
      v
ChatPromptTemplate
      |
      v
ChatOpenAI
      |
      v
StrOutputParser
      |
      v
Final text
```

`StrOutputParser()` extracts the generated text instead of returning the complete `AIMessage` object.

## 21. Structured output with LangChain

### What?

Structured output means asking the model to return information in a predefined format.

### Why?

Applications often need predictable data rather than free-form text.

For example, a customer support application may need:
- An answer.
- A category.
- A human escalation indicator.

### How?

```python
from pydantic import BaseModel, Field
from typing import Literal

class SupportResult(BaseModel):

    answer: str = Field(
        description="Response to the customer"
    )

    category: Literal[
        "billing",
        "technical",
        "general"
    ]

    needs_human: bool


structured_model = model.with_structured_output(
    SupportResult
)

result = await structured_model.ainvoke(
    "My payment was charged twice."
)

print(result)
```

### Explanation

`SupportResult` defines the expected structure.

`Literal` restricts the category to the allowed values.

`with_structured_output()` configures the model to return data matching the schema.

### Example output

```text
SupportResult(
    answer="I can help you investigate the duplicate payment.",
    category="billing",
    needs_human=False
)
```

**Important:** Structured output validates the shape of the response. It does not prove that the information is factually correct.

# Part 10 — Security, monitoring and debugging

## 22. API security and best practices

### What?

API security protects your application, users, data and model credentials.

### Why?

An AI backend may process private information and may incur costs every time someone calls the model.

### How?

Follow these practices:

**1. Protect API keys**

- Store secrets in environment variables or a secret manager.
- Never commit `.env`.
- Rotate exposed credentials.
- Never return secrets to frontend applications.

**2. Authenticate users**

Require valid authentication before allowing access to protected endpoints.

**3. Validate input**

Use Pydantic:

```python
from pydantic import BaseModel, Field

class ChatRequest(BaseModel):

    question: str = Field(
        min_length=1,
        max_length=5000
    )
```

**4. Apply rate limits**

Prevent users from sending unlimited requests.

**5. Protect conversation history**

Only allow users to access their own conversations.

**6. Handle model output carefully**

Model output is not automatically trustworthy. Validate data before using it for business operations.

**7. Protect sensitive actions**

Require backend authorisation and, where appropriate, human approval before performing actions such as payments, refunds or account changes.

**8. Avoid leaking private information**

Do not expose internal prompts, API keys, private records or sensitive logs.

## 23. Logging, monitoring and debugging

### What?

Logging records important application events.

Monitoring tracks how your application performs over time.

### Why?

You need to know:
- Whether requests succeed.
- How long model calls take.
- How often errors occur.
- How many tokens are consumed.
- Whether rate limits are being reached.

### How?

Basic Python logging:

```python
import logging
import time

logging.basicConfig(
    level=logging.INFO
)

logger = logging.getLogger(__name__)


async def generate_answer(question):

    start_time = time.perf_counter()

    try:

        response = await model.ainvoke(
            question
        )

        duration = (
            time.perf_counter() - start_time
        )

        logger.info(
            "Model request completed in %.2f seconds",
            duration
        )

        logger.info(
            "Token usage: %s",
            response.usage_metadata
        )

        return response.content

    except Exception:

        logger.exception(
            "Model request failed"
        )

        raise
```

### Explanation

`logging.basicConfig()` configures logging.

`logger.info()` records successful operations.

`time.perf_counter()` measures elapsed time.

`logger.exception()` records an error with its traceback.

### Example log

```text
INFO Model request completed in 1.85 seconds

INFO Token usage:
{
    'input_tokens': 20,
    'output_tokens': 70,
    'total_tokens': 90
}
```

**Production note:** Avoid logging complete prompts, customer conversations, personal information or credentials by default. Use appropriate redaction and access controls.

```python
    "/chat/stream",
    dependencies=[Depends(verify_api_key)]
)
async def chat_stream(request: ChatRequest):

    history = get_history(
        request.session_id
    )

    async def generate():

        answer_parts = []

        try:

            async for chunk in stream_chain.astream({

                "history": history,

                "question": request.question

            }):

                answer_parts.append(chunk)

                yield (
                    "data: "
                    + json.dumps({
                        "text": chunk
                    })
                    + "\n\n"
                )

            complete_answer = "".join(
                answer_parts
            )

            updated_history = history + [

                HumanMessage(
                    content=request.question
                ),

                AIMessage(
                    content=complete_answer
                )

            ]

            save_history(
                request.session_id,
                updated_history
            )

            yield "data: [DONE]\n\n"

        except Exception:

            logger.exception(
                "Streaming request failed"
            )

            yield (
                "event: error\n"
                "data: "
                + json.dumps({
                    "error": "Streaming failed"
                })
                + "\n\n"
            )

    return StreamingResponse(

        generate(),

        media_type="text/event-stream",

        headers={
            "Cache-Control": "no-cache",
            "X-Accel-Buffering": "no"
        }

    )
```

# Part 13 — Important production improvements

The complete application is a useful learning foundation, but it is not a complete production deployment.

Before deploying it for real users, improve these areas:

| Area | Production improvement |
|---|---|
| Authentication | Use proper user authentication and validated identity |
| Authorisation | Enforce access to each user's own conversations |
| Conversation storage | Replace the in-memory dictionary with Redis or a database |
| Multiple workers | Use shared storage rather than process-local state |
| Rate limiting | Add distributed per-user and per-IP limits |
| Cost control | Set usage quotas and monitor token consumption |
| Streaming | Handle disconnects, timeouts and client cancellation |
| Error handling | Map provider failures to safe application responses |
| Logging | Redact personal information and secrets |
| Monitoring | Track latency, failures, usage and availability |
| Input validation | Apply size limits and validate business data |
| Deployment | Use HTTPS, secure secret storage and appropriate server configuration |

**Important limitations in the demonstration:**

1. The in-memory `history_store` disappears when the process restarts.
2. It is not safe as shared storage when running multiple workers.
3. The example API key is a simple application-level check, not full user authentication.
4. A client-provided `session_id` is not proof that the client owns that conversation. Production applications must associate sessions with authenticated users.
5. Streaming errors occur after the HTTP response has started, so the application sends an SSE error event rather than changing the HTTP status code.
6. The application should have appropriate request limits, concurrency controls and monitoring before deployment.
