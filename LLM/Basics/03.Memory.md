# Chapter 1: Introduction to Memory in LLMs

### What?
Memory allows an LLM application to retain information from previous interactions.

Without memory, each API call is generally independent unless your application sends previous context again.

### Why?
- Remember previous questions.
- Avoid asking users for the same information.
- Personalize responses.
- Continue conversations across requests.

### How?
Store relevant information in a database and retrieve it when making the next LLM call.

### Use case
A customer tells a chatbot their name is John. Later, the chatbot remembers their name.

### Code example

```python
@app.post("/chapter1/chat")
async def basic_memory_chat(req: ChatRequest):

    with get_db() as conn:
        conn.execute(
            "INSERT INTO messages (user_id, session_id, role, content) VALUES (?, ?, ?, ?)",
            (req.user_id, req.session_id, "user", req.message)
        )

        rows = conn.execute(
            """SELECT role, content FROM messages
               WHERE user_id=? AND session_id=?
               ORDER BY id""",
            (req.user_id, req.session_id)
        ).fetchall()

    history = []

    for role, content in rows:
        if role == "user":
            history.append(HumanMessage(content=content))
        elif role == "assistant":
            history.append(AIMessage(content=content))

    response = await llm.ainvoke([
        SystemMessage(content="You are a helpful assistant."),
        *history
    ])

    with get_db() as conn:
        conn.execute(
            "INSERT INTO messages (user_id, session_id, role, content) VALUES (?, ?, ?, ?)",
            (req.user_id, req.session_id, "assistant", response.content)
        )

    return {"answer": response.content}
```

### Expected output

Request:

```json
{
  "user_id": "user123",
  "session_id": "session1",
  "message": "My name is John."
}
```

Response:

```json
{
  "answer": "Nice to meet you, John!"
}
```

# Chapter 2: Types of Memory in LLM Applications

### What?
Common memory categories include:

1. Short-term memory – recent conversation.
2. Long-term memory – information retained across sessions.
3. Working memory – temporary information needed for the current task.
4. Semantic memory – facts and knowledge.
5. Episodic memory – past events and experiences.
6. Procedural memory – instructions and learned procedures.

### Why?
Different information has different storage and retrieval requirements.

### How?
Choose a storage strategy based on the information's purpose and lifetime.

### Use case
A personal assistant might store:
- Recent conversation in short-term memory.
- User preferences in long-term memory.
- Current task details in working memory.

### Code example

```python
@app.post("/chapter2/save-memory")
async def save_memory(req: ChatRequest):

    memory_type = "long_term"

    with get_db() as conn:
        conn.execute(
            """INSERT INTO user_memories (user_id, memory)
               VALUES (?, ?)""",
            (req.user_id, f"[{memory_type}] {req.message}")
        )

    return {
        "memory_type": memory_type,
        "saved": True
    }
```

### Expected output

```json
{
  "memory_type": "long_term",
  "saved": true
}
```

# Chapter 3: Short-Term Memory (Conversation History)

### What?
Short-term memory stores messages from the current conversation or session.

### Why?
It allows the chatbot to understand follow-up questions.

### How?
Store user and assistant messages using a session ID. Retrieve recent messages for the next request.

### Use case
User: "My favourite language is Python."

User: "What is my favourite language?"

The chatbot answers: "Python."

### Code example

```python
@app.get("/chapter3/history/{user_id}/{session_id}")
async def get_history(user_id: str, session_id: str):

    with get_db() as conn:
        rows = conn.execute(
            """SELECT role, content FROM messages
               WHERE user_id=? AND session_id=?
               ORDER BY id DESC LIMIT 10""",
            (user_id, session_id)
        ).fetchall()

    return {
        "history": [
            {"role": role, "content": content}
            for role, content in reversed(rows)
        ]
    }
```

### Expected output

```json
{
  "history": [
    {
      "role": "user",
      "content": "My favourite language is Python."
    },
    {
      "role": "assistant",
      "content": "Got it!"
    }
  ]
}
```

# Chapter 4: Long-Term Memory

### What?
Long-term memory stores information that should remain available across different sessions.

### Why?
A user should not need to repeat their preferences or important details every time they open the application.

### How?
Save selected facts in persistent storage, associated with an authenticated user ID.

### Use case
A chatbot remembers that a user prefers Python examples, even in a new conversation.

# Chapter 5: Working Memory

### What?
Working memory holds temporary information needed to complete the current task.

It is usually discarded after the task finishes.

### Why?
It prevents the application from mixing temporary task information with permanent user memories.

### How?
Keep task state in a temporary object, cache, or database record with an expiry time.

### Use case
A travel assistant temporarily remembers:
- Destination: Paris
- Duration: 5 days
- Budget: €1,000

### Code example

```python
working_memory = {}


@app.post("/chapter5/task")
async def create_task(req: ChatRequest):

    working_memory[req.session_id] = {
        "task": req.message,
        "status": "in_progress"
    }

    response = await llm.ainvoke(
        f"Help complete this task: {req.message}"
    )

    return {
        "task": working_memory[req.session_id],
        "answer": response.content
    }
```

### Expected output

```json
{
  "task": {
    "task": "Plan a 5-day trip to Paris",
    "status": "in_progress"
  },
  "answer": "Let's plan your five-day Paris trip..."
}
```

**Production note:** This dictionary is only a demonstration. Use Redis or a persistent task store with TTL and session isolation in production.

# Chapter 7: Storing and Retrieving Chat History

### What?
This is the process of saving messages and loading them when needed.

### Why?
It makes conversation history persistent rather than keeping it only in application memory.

### How?
Use a database with user IDs, session IDs, timestamps, and message roles.

### Use case
A customer closes a browser and returns later. Their previous conversation is available.

### Code example

```python
@app.post("/chapter7/message")
async def store_message(req: ChatRequest):

    with get_db() as conn:
        cursor = conn.execute(
            """INSERT INTO messages
               (user_id, session_id, role, content)
               VALUES (?, ?, ?, ?)""",
            (req.user_id, req.session_id, "user", req.message)
        )

        message_id = cursor.lastrowid

    return {
        "message_id": message_id,
        "stored": True
    }


@app.get("/chapter7/messages/{session_id}")
async def retrieve_messages(session_id: str):

    with get_db() as conn:
        rows = conn.execute(
            """SELECT id, role, content, created_at
               FROM messages WHERE session_id=?
               ORDER BY id""",
            (session_id,)
        ).fetchall()

    return {"messages": rows}
```

### Expected output

```json
{
  "message_id": 15,
  "stored": true
}
```

# Chapter 8: Memory in LangChain

### What?
LangChain provides components for building applications that work with conversation history and memory.

Common concepts include:
- Chat message history.
- Runnable chains.
- Message placeholders.
- RunnableWithMessageHistory.
- LangGraph state and persistence.

### Why?
It reduces the amount of custom code needed to connect conversation history with an LLM.

### How?
Wrap an LLM chain with `RunnableWithMessageHistory`.

### Use case
A chatbot remembers messages from the same session.

### Code example

```python
from langchain_core.chat_history import InMemoryChatMessageHistory
from langchain_core.runnables.history import RunnableWithMessageHistory

from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder

store = {}

def get_session_history(session_id: str):
    if session_id not in store:
        store[session_id] = InMemoryChatMessageHistory()

    return store[session_id]


prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a helpful assistant."),
    MessagesPlaceholder("history"),
    ("human", "{question}")
])

chain = prompt | llm

chat_chain = RunnableWithMessageHistory(
    chain,
    get_session_history,
    input_messages_key="question",
    history_messages_key="history"
)


@app.post("/chapter8/chat")
async def langchain_memory(req: ChatRequest):

    result = await chat_chain.ainvoke(
        {"question": req.message},
        config={
            "configurable": {
                "session_id": req.session_id
            }
        }
    )

    return {"answer": result.content}
```

### Expected output

```json
{
  "answer": "Hello! How can I help you?"
}
```

**Production note:** Replace `InMemoryChatMessageHistory` with persistent database-backed history. Also validate that users are authorized to access the requested session.

# Chapter 9: Conversation Buffer Memory

### What?
Conversation buffer memory stores the conversation messages and provides them to the LLM.

### Why?
The model can understand previous messages without manually reconstructing the conversation every time.

### How?
Use message history as part of the prompt.

### Use case
A chatbot remembers the last few exchanges during a customer support conversation.

### Code example

```python
@app.post("/chapter9/chat")
async def conversation_buffer(req: ChatRequest):

    with get_db() as conn:
        rows = conn.execute(
            """SELECT role, content FROM messages
               WHERE user_id=? AND session_id=?
               ORDER BY id DESC LIMIT 10""",
            (req.user_id, req.session_id)
        ).fetchall()

    history = []

    for role, content in reversed(rows):
        if role == "user":
            history.append(HumanMessage(content=content))
        else:
            history.append(AIMessage(content=content))

    result = await llm.ainvoke([
        SystemMessage(content="You are a customer support assistant."),
        *history,
        HumanMessage(content=req.message)
    ])

    return {"answer": result.content}
```

### Expected output

```json
{
  "answer": "As we discussed earlier, your order is being processed."
}
```

**Important:** The code demonstrates buffer-based history. It does not automatically save the latest exchange. Save both the incoming user message and the assistant response in your application.

# Chapter 10: Conversation Summary Memory

### What?
Summary memory compresses older conversation messages into a shorter summary.

### Why?
Sending every historical message can increase token usage, latency, and cost.

### How?
Ask the LLM to summarize older messages, then include the summary in future prompts.

### Use case
A customer has a 100-message conversation. The chatbot uses a short summary rather than sending all 100 messages.

### Code example

```python
@app.post("/chapter10/summarize")
async def summarize_conversation(req: ChatRequest):

    with get_db() as conn:
        rows = conn.execute(
            """SELECT role, content FROM messages
               WHERE user_id=? AND session_id=?
               ORDER BY id LIMIT 100""",
            (req.user_id, req.session_id)
        ).fetchall()

    transcript = "\n".join(
        f"{role}: {content}" for role, content in rows
    )

    result = await llm.ainvoke([
        SystemMessage(
            content="Summarize important facts, decisions, preferences, and unresolved tasks."
        ),
        HumanMessage(content=transcript)
    ])

    return {"summary": result.content}
```

### Expected output

```json
{
  "summary": "The customer has an order delayed by two days. They prefer email updates. The issue remains unresolved."
}
```

**Production note:** Persist summaries with a version and timestamp. Preserve important facts and unresolved tasks when replacing older summaries.

# Chapter 11: Vector Store Memory

### What?
A vector store saves information as embeddings and retrieves relevant information using similarity search.

### Why?
A database keyword search may not find information expressed using different words. Vector search can find semantically similar content.

### How?
1. Convert text into embeddings.
2. Store embeddings in a vector database.
3. Search using a new query.
4. Retrieve relevant memories.

### Use case
Stored memory: "The user enjoys developing Python applications."

Question: "What programming language do I like?"

The vector store can retrieve the Python memory.

### Code example

```python
embeddings = OpenAIEmbeddings(
    model="text-embedding-3-small"
)

vector_store = Chroma(
    collection_name="user_memories",
    embedding_function=embeddings,
    persist_directory="./chroma_db"
)


@app.post("/chapter11/save")
async def save_vector_memory(req: ChatRequest):

    vector_store.add_texts(
        texts=[req.message],
        metadatas=[{"user_id": req.user_id}]
    )

    return {"saved": True}


@app.get("/chapter11/search")
async def search_vector_memory(user_id: str, query: str):

    results = vector_store.similarity_search(
        query,
        k=5,
        filter={"user_id": user_id}
    )

    return {
        "memories": [doc.page_content for doc in results]
    }
```

### Expected output

```json
{
  "memories": [
    "The user enjoys developing Python applications."
  ]
}
```

**Production note:** Use tenant-aware filtering, backups, access controls, and deletion workflows. Verify the vector database's persistence and filtering configuration before deployment.

# Chapter 13: Semantic Search and Retrieval

### What?
Semantic search finds information based on meaning rather than exact keyword matching.

Retrieval is the process of selecting relevant information and providing it to the LLM.

### Why?
Users may ask the same question in different ways.

### How?
Embed the query, search the vector store, retrieve matching documents, and pass them to the model.

### Use case
Stored information: "The user is preparing for a Python developer interview."

Question: "What job interview am I studying for?"

### Code example

```python
@app.post("/chapter13/ask")
async def semantic_ask(req: ChatRequest):

    docs = vector_store.similarity_search(
        req.message,
        k=3,
        filter={"user_id": req.user_id}
    )

    context = "\n".join(
        doc.page_content for doc in docs
    )

    result = await llm.ainvoke([
        SystemMessage(
            content="Answer using the retrieved memory. "
                    "If it does not contain the answer, say you do not know."
        ),
        HumanMessage(
            content=f"Memory:\n{context}\n\nQuestion:\n{req.message}"
        )
    ])

    return {
        "retrieved_context": context,
        "answer": result.content
    }
```

### Expected output

```json
{
  "retrieved_context": "The user is preparing for a Python developer interview.",
  "answer": "You are preparing for a Python developer interview."
}
```

# Chapter 15: Memory Persistence (Redis, SQL, etc.)

### What?
Persistence means storing memory so it remains available after an application restarts.

Common options:

- PostgreSQL – relational data and chat history.
- Redis – fast temporary storage and caching.
- SQLite – lightweight local database.
- ChromaDB – vector storage.
- Other vector databases – large-scale semantic retrieval.

### Why?
In-memory Python objects disappear when the application restarts.

### How?
Write data to a persistent database and retrieve it when required.

### Use case
A chatbot restarts after deployment but still has access to previous customer conversations.

### Code example

```python
@app.post("/chapter15/persist")
async def persist_memory(req: ChatRequest):

    with get_db() as conn:
        conn.execute(
            """INSERT INTO user_memories (user_id, memory)
               VALUES (?, ?)""",
            (req.user_id, req.message)
        )

    return {"persisted": True}


@app.get("/chapter15/load/{user_id}")
async def load_memory(user_id: str):

    with get_db() as conn:
        rows = conn.execute(
            "SELECT memory FROM user_memories WHERE user_id=?",
            (user_id,)
        ).fetchall()

    return {"memories": [row[0] for row in rows]}
```

### Expected output

```json
{
  "persisted": true
}
```

**Production note:** SQLite is useful for learning and small deployments. For a multi-worker production service, consider PostgreSQL with connection pooling, migrations, and backups. Use Redis when fast temporary state or caching is required.

# Chapter 16: Updating and Deleting Memories

### What?
Memory management includes creating, updating, and deleting stored information.

### Why?
User preferences change, stored information can become incorrect, and users may request deletion.

### How?
Use unique memory IDs and database operations such as `UPDATE` and `DELETE`.

### Use case
A user changes their preferred language from Java to Python.

### Code example

```python
@app.put("/chapter16/update/{memory_id}")
async def update_memory(
    memory_id: int,
    user_id: str,
    new_memory: str
):

    with get_db() as conn:
        cursor = conn.execute(
            """UPDATE user_memories SET memory=?
               WHERE id=? AND user_id=?""",
            (new_memory, memory_id, user_id)
        )

    if cursor.rowcount == 0:
        raise HTTPException(404, "Memory not found")

    return {"updated": True}


@app.delete("/chapter16/delete/{memory_id}")
async def delete_memory(memory_id: int, user_id: str):

    with get_db() as conn:
        cursor = conn.execute(
            """DELETE FROM user_memories
               WHERE id=? AND user_id=?""",
            (memory_id, user_id)
        )

    if cursor.rowcount == 0:
        raise HTTPException(404, "Memory not found")

    return {"deleted": True}
```

### Expected output

```json
{
  "updated": true
}
```

**Production note:** Also delete corresponding vector-store records, cached copies, and backups according to your retention policy. Authenticate users and verify ownership before allowing changes.

# Chapter 17: Memory Management and Token Limits

### What?
An LLM has a maximum context window. The input and output must fit within the model's token limits.

Memory management decides what information should be included in each request.

### Why?
Sending all conversation history can:
- Increase cost.
- Increase latency.
- Exceed context limits.
- Distract the model with irrelevant information.

### How?
Use a combination of:
- Recent messages.
- Conversation summaries.
- Relevant retrieved memories.
- Token budgets.

### Use case
A chatbot has 500 previous messages but only sends the latest 10 messages and a summary.

### Code example

```python
@app.post("/chapter17/manage-context")
async def manage_context(req: ChatRequest):

    with get_db() as conn:
        rows = conn.execute(
            """SELECT role, content FROM messages
               WHERE user_id=? AND session_id=?
               ORDER BY id DESC LIMIT 10""",
            (req.user_id, req.session_id)
        ).fetchall()

    history = []

    for role, content in reversed(rows):
        if role == "user":
            history.append(HumanMessage(content=content))
        else:
            history.append(AIMessage(content=content))

    result = await llm.ainvoke([
        SystemMessage(
            content="Answer clearly and concisely."
        ),
        *history,
        HumanMessage(content=req.message)
    ])

    return {"answer": result.content}
```

### Expected output

```json
{
  "answer": "Here is the answer based on the recent conversation..."
}
```

**Production note:** A fixed message count is only a simple approximation. Use token-aware trimming, reserve tokens for the response, and summarize older messages. Check the model's actual token limits.

# Chapter 18: Building Memory-Enabled Chatbots

### What?
A memory-enabled chatbot combines an LLM with persistent conversation history and relevant user memories.

### Why?
It creates a continuous and personalized user experience.

### How?
A typical flow:

1. Receive a user message.
2. Load recent conversation history.
3. Retrieve relevant long-term memories.
4. Construct the prompt.
5. Call the LLM.
6. Save the user message and response.

### Use case
A customer support chatbot remembers previous issues and customer preferences.

### Code example

```python
@app.post("/chapter18/chatbot")
async def memory_chatbot(req: ChatRequest):

    with get_db() as conn:

        history_rows = conn.execute(
            """SELECT role, content FROM messages
               WHERE user_id=? AND session_id=?
               ORDER BY id DESC LIMIT 10""",
            (req.user_id, req.session_id)
        ).fetchall()

        memory_rows = conn.execute(
            """SELECT memory FROM user_memories
               WHERE user_id=? ORDER BY id DESC LIMIT 10""",
            (req.user_id,)
        ).fetchall()

    history = []

    for role, content in reversed(history_rows):
        if role == "user":
            history.append(HumanMessage(content=content))
        else:
            history.append(AIMessage(content=content))

    memories = "\n".join(row[0] for row in memory_rows)

    result = await llm.ainvoke([
        SystemMessage(
            content=f"""
            You are a helpful customer support assistant.

            Relevant user memories:
            {memories}

            Use these memories when relevant.
            """
        ),
        *history,
        HumanMessage(content=req.message)
    ])

    with get_db() as conn:
        conn.executemany(
            """INSERT INTO messages
               (user_id, session_id, role, content)
               VALUES (?, ?, ?, ?)""",
            [
                (req.user_id, req.session_id, "user", req.message),
                (req.user_id, req.session_id, "assistant", result.content)
            ]
        )

    return {"answer": result.content}
```

### Expected output

```json
{
  "answer": "Welcome back! I remember your previous support issue. How can I help?"
}
```

# Chapter 19: Memory Evaluation and Optimization

### What?
Memory evaluation measures whether the system stores and retrieves useful information correctly.

### Why?
A memory system can retrieve irrelevant information, miss important facts, or remember outdated details.

### How?
Evaluate:
- Retrieval precision.
- Retrieval recall.
- Answer accuracy.
- Memory relevance.
- Latency.
- Token usage.
- Cost.

### Use case
Test whether a chatbot correctly recalls a user's preferred programming language across 100 test conversations.

### Code example

```python
@app.post("/chapter19/evaluate")
async def evaluate_memory(req: ChatRequest):

    docs = vector_store.similarity_search(
        req.message,
        k=3,
        filter={"user_id": req.user_id}
    )

    context = "\n".join(
        doc.page_content for doc in docs
    )

    result = await llm.ainvoke([
        SystemMessage(
            content="""
            Evaluate whether the retrieved memories answer
            the user's question.

            Return a short assessment and explain missing information.
            """
        ),
        HumanMessage(
            content=f"""
            Question: {req.message}

            Retrieved memories:
            {context}
            """
        )
    ])

    return {
        "retrieved_count": len(docs),
        "evaluation": result.content
    }
```

### Expected output

```json
{
  "retrieved_count": 2,
  "evaluation": "The retrieved memories contain the user's preferred programming language. Retrieval appears relevant."
}
```

**Production note:** Build a fixed test dataset with expected answers. Track retrieval metrics and model performance over time. Do not rely only on an LLM judging its own answers.

# Chapter 20: Security and Privacy in LLM Memory

### What?
Security and privacy protect stored user information from unauthorized access, exposure, and misuse.

### Why?
Memory may contain personal information, conversation history, or confidential business data.

### How?
Use:
- Authentication and authorization.
- User-level data isolation.
- Encryption at rest and in transit.
- Input validation.
- Data minimization.
- Retention and deletion policies.
- Audit logs.
- Secrets management.

### Use case
A user must not be able to retrieve another user's chat history by changing a URL parameter.

### Code example

```python
from fastapi import Header


async def verify_user(
    x_user_id: str = Header(...)
):
    # Demonstration only.
    # Replace with verified JWT/session authentication.
    if not x_user_id:
        raise HTTPException(401, "Authentication required")

    return x_user_id


from typing import Annotated
from fastapi import Depends


@app.get("/chapter20/private-memory")
async def private_memory(
    user_id: Annotated[str, Depends(verify_user)]
):

    with get_db() as conn:
        rows = conn.execute(
            """SELECT memory FROM user_memories
               WHERE user_id=?""",
            (user_id,)
        ).fetchall()

    return {
        "memories": [row[0] for row in rows]
    }
```

### Expected output

Authenticated request:

```http
GET /chapter20/private-memory
X-User-ID: user123
```

Response:

```json
{
  "memories": [
    "User prefers Python."
  ]
}
```

**Production note:** Never trust a user ID supplied directly in a header. Derive identity from a verified authentication token. Apply authorization to every memory operation and avoid logging sensitive memory content.
