# Building a SharePoint-to-S3 connector with recursive traversal, incremental synchronisation and retry handling

## 1. What we are building

Our connector transfers documents from SharePoint into Amazon S3.

The architecture is:

**SharePoint → Microsoft Graph REST API → Python (`requests`) → Amazon S3 (`boto3`)**

We are adding three important improvements to the original connector:

| Improvement | What it does | Why it matters |
|---|---|---|
| Recursive folder traversal | Enters folders and subfolders to find documents | Documents are rarely all stored in the root folder |
| Incremental synchronisation | Finds new, modified and deleted documents | Avoids downloading every document on every run |
| Retry and throttling handling | Retries requests when Microsoft Graph temporarily fails or limits requests | Makes the connector more reliable |

We will use direct REST API requests with `requests`. We will not use the Microsoft Graph SDK.

---

# 2. Improvement one: Recursive folder traversal

## What is recursive folder traversal?

Imagine your SharePoint document library has this structure:

```text
Documents
│
├── Finance
│   ├── invoices.pdf
│   └── budget.xlsx
│
├── HR
│   ├── policies.docx
│   └── employees.xlsx
│
└── IT
    ├── Systems
    │   └── architecture.pdf
    │
    └── security.docx
```

Our original connector used:

```python
url = (
    f"https://graph.microsoft.com/v1.0/"
    f"drives/{drive_id}/root/children"
)
```

This only lists the items directly inside the root folder.

It does not automatically enter Finance, HR or IT.

That means our original connector could miss documents stored in subfolders.

## What does recursion mean?

Recursion means a function calls itself.

For our connector, the process is:

1. Open the root folder.
2. Retrieve the items inside it.
3. If an item is a file, upload it to S3.
4. If an item is a folder, open that folder.
5. Check its contents.
6. Repeat until all folders have been examined.

For example:

```text
Open Documents
    |
    ├── Find Finance folder
    |       |
    |       └── Open Finance
    |               ├── Upload invoices.pdf
    |               └── Upload budget.xlsx
    |
    ├── Find HR folder
    |       |
    |       └── Open HR
    |               ├── Upload policies.docx
    |               └── Upload employees.xlsx
    |
    └── Find IT folder
            |
            └── Open IT
                    ├── Open Systems
                    |       └── Upload architecture.pdf
                    |
                    └── Upload security.docx
```

## How does Microsoft Graph identify a folder?

When you retrieve items from SharePoint, Microsoft Graph returns JSON data.

A folder typically contains a `folder` property:

```json
{
    "id": "FOLDER_ID",
    "name": "Finance",
    "folder": {
        "childCount": 2
    }
}
```

A file typically contains a `file` property:

```json
{
    "id": "FILE_ID",
    "name": "invoices.pdf",
    "file": {
        "mimeType": "application/pdf"
    }
}
```

Python can check these properties:

```python
if "folder" in item:
    print("This is a folder")

elif "file" in item:
    print("This is a file")
```

The important difference is:

- A folder requires another API request to retrieve its contents.
- A file requires a download request followed by an S3 upload.

## How do we access a folder's contents?

We use this Graph API endpoint:

```text
/drives/{drive_id}/items/{folder_id}/children
```

For example, if the folder ID is `12345`, the endpoint becomes:

```text
https://graph.microsoft.com/v1.0/drives/YOUR_DRIVE_ID/items/12345/children
```

The `{folder_id}` tells Microsoft Graph which folder we want to open.

Our recursive function will use this endpoint every time it finds a folder.

# 3. Improvement two: Incremental synchronisation

## What is incremental synchronisation?

Imagine your SharePoint library contains 10,000 documents.

On Monday, our connector uploads all 10,000 documents to S3.

On Tuesday, only three things happen:

- A new document is created.
- An existing document is modified.
- Another document is deleted.

A basic connector might download all 10,000 documents again.

That is inefficient.

Incremental synchronisation means the connector checks what has changed since its previous successful run.

It should identify:

| SharePoint change | Connector action |
|---|---|
| New document | Upload it to S3 |
| Modified document | Upload the updated version to S3 |
| Deleted document | Delete the corresponding S3 object |
| Unchanged document | Do nothing |

## How does Microsoft Graph support this?

Microsoft Graph provides an API feature called **delta query**.

It lets us track changes in a drive.

We use this endpoint:

```text
https://graph.microsoft.com/v1.0/drives/{drive_id}/root/delta
```

The first time we call this endpoint, Microsoft Graph returns the current items in the drive. This initial enumeration includes items in nested folders.

After processing the results, Microsoft Graph provides a special URL called:

```text
@odata.deltaLink
```

This URL is important.

It represents the point from which we can request changes during the next synchronisation.

For example:

```text
First run:
SharePoint → Retrieve current items → Upload to S3 → Save deltaLink

Second run:
SharePoint → Use saved deltaLink → Retrieve changes → Update S3

Third run:
SharePoint → Use updated deltaLink → Retrieve new changes → Update S3
```

## What is a deltaLink?

A `deltaLink` is a continuation URL supplied by Microsoft Graph.

We must save it because it allows the next run to continue checking changes from the previous synchronisation point.

We will store it in S3:

```text
connector-state/
    sharepoint/
        YOUR_DRIVE_ID/
            delta.json
```

This is connector state, not a SharePoint document.

It allows the connector to remember where it stopped, even if the Python program is restarted.

## What is a nextLink?

Microsoft Graph can split results into multiple pages.

It can return:

```json
{
    "value": [],
    "@odata.nextLink": "NEXT_PAGE_URL"
}
```

We must keep following `@odata.nextLink` until we receive the final page.

The final page can contain:

```json
{
    "value": [],
    "@odata.deltaLink": "DELTA_TRACKING_URL"
}
```

The difference is:

- `nextLink` means there are more results to retrieve in the current operation.
- `deltaLink` means we have reached the end and can use this URL for the next synchronisation.

## Important: Why use delta query if we have recursive traversal?

They solve related but different problems.

- Recursive traversal is useful when you want to manually scan the folder structure.
- Delta query is useful for tracking changes across the drive, including nested items.

The delta API can enumerate the drive hierarchy during its initial synchronisation. It is therefore a particularly useful way to establish an initial synchronisation and then continue incrementally.

We will include both techniques in the code.

# 4. Improvement three: Retry and throttling handling

## What is throttling?

Imagine our Python connector sends 500 requests to Microsoft Graph in a short period.

Microsoft may decide that the connector is sending too many requests.

It can respond with:

```text
HTTP 429 Too Many Requests
```

This is called throttling.

It does not necessarily mean our code is incorrect. It means the service is asking us to slow down.

Other temporary errors can include:

| HTTP status | Meaning |
|---|---|
| 429 | Too many requests |
| 500 | Internal server error |
| 502 | Bad gateway |
| 503 | Service unavailable |
| 504 | Gateway timeout |

We should not immediately abandon the entire synchronisation because of a temporary failure.

## What is retry handling?

Retry handling means attempting a failed request again.

For example:

```text
Request 1
    |
    └── HTTP 429
            |
            └── Wait
                    |
                    └── Request 2
                            |
                            └── Success
```

We will use a maximum number of attempts.

For example:

```python
max_attempts = 6
```

This means the connector can try a request up to six times before giving up.

## What is Retry-After?

When Microsoft Graph throttles a request, it can provide a response header called:

```text
Retry-After
```

For example:

```text
Retry-After: 10
```

This means we should wait 10 seconds before trying again.

Our code will:

1. Check the HTTP response status.
2. If it is a throttling or temporary server error, inspect `Retry-After`.
3. Wait for the specified period when provided.
4. Otherwise, use an increasing delay between attempts.
5. Try the request again.
6. Raise an error if all attempts fail.

This makes the connector more resilient.

# 5. How the complete connector works

The complete process will look like this:

```text
                 SHAREPOINT
                      |
                      |
             Microsoft Graph API
                      |
                      |
              Python Connector
                      |
           ┌──────────┴──────────┐
           |                     |
     Initial sync          Later syncs
           |                     |
     Delta enumeration      Saved deltaLink
           |                     |
           └──────────┬──────────┘
                      |
              Process each item
                      |
           ┌──────────┴──────────┐
           |          |          |
          File      Folder    Deleted item
           |          |          |
        Download   Traverse    Delete from S3
           |       recursively
           |          |
           └────┬─────┘
                |
             Amazon S3
                |
        Save updated deltaLink
```

Retry handling is used for requests to Microsoft Graph and the file download requests.

The code also saves its delta state in S3, so it does not depend on a local computer's files.

# 6. Complete Python code

## Before running the code


## Complete code

The code contains:

- Microsoft Graph API requests.
- Retry and throttling handling.
- Recursive folder traversal.
- Document download.
- S3 upload.
- Incremental synchronisation using delta query.
- S3 storage for the delta tracking URL.
- Handling for deleted files.
- Pagination.

```python
import json
import time
import random
import requests
import boto3

from datetime import datetime, timezone
from email.utils import parsedate_to_datetime
from botocore.exceptions import ClientError


# =====================================================
# 1. CONFIGURATION
# =====================================================

ACCESS_TOKEN = "YOUR_ACCESS_TOKEN"

DRIVE_ID = "YOUR_DRIVE_ID"

S3_BUCKET = "your-company-document-bucket"

AWS_REGION = "eu-west-1"

MAX_ATTEMPTS = 6

GRAPH_BASE_URL = "https://graph.microsoft.com/v1.0"

DOCUMENT_PREFIX = f"documents/sharepoint/{DRIVE_ID}/"

STATE_KEY = (
    f"connector-state/sharepoint/{DRIVE_ID}/delta.json"
)


# =====================================================
# 2. CREATE CONNECTIONS
# =====================================================

session = requests.Session()

graph_headers = {
    "Authorization": f"Bearer {ACCESS_TOKEN}"
}

s3_client = boto3.client(
    "s3",
    region_name=AWS_REGION
)


# =====================================================
# 3. RETRY AND THROTTLING FUNCTION
# =====================================================

def get_with_retry(url, headers=None, allow_redirects=True):

    for attempt in range(1, MAX_ATTEMPTS + 1):

        try:

            response = session.get(
                url,
                headers=headers,
                timeout=60,
                allow_redirects=allow_redirects
            )

            # Retry temporary errors
            if response.status_code in [
                429, 500, 502, 503, 504
            ]:

                if attempt == MAX_ATTEMPTS:
                    response.raise_for_status()

                retry_after = response.headers.get(
                    "Retry-After"
                )

                if retry_after:

                    try:
                        wait_seconds = float(retry_after)

                    except ValueError:

                        retry_date = parsedate_to_datetime(
                            retry_after
                        )

                        if retry_date.tzinfo is None:
                            retry_date = retry_date.replace(
                                tzinfo=timezone.utc
                            )

                        wait_seconds = max(
                            0,
                            (
                                retry_date -
                                datetime.now(timezone.utc)
                            ).total_seconds()
                        )

                else:

                    wait_seconds = min(
                        60,
                        (2 ** (attempt - 1)) + random.random()
                    )

                print(
                    f"Temporary error {response.status_code}. "
                    f"Retrying in {wait_seconds:.1f} seconds."
                )

                time.sleep(wait_seconds)

                continue

            # Raise other HTTP errors
            response.raise_for_status()

            return response

        except requests.RequestException:

            if attempt == MAX_ATTEMPTS:
                raise

            wait_seconds = min(
                60,
                (2 ** (attempt - 1)) + random.random()
            )

            print(
                f"Request failed. "
                f"Retrying in {wait_seconds:.1f} seconds."
            )

            time.sleep(wait_seconds)

    raise RuntimeError("Maximum request attempts reached.")


# =====================================================
# 4. DOWNLOAD A FILE FROM SHAREPOINT
# =====================================================

def download_file(item_id):

    download_url = (
        f"{GRAPH_BASE_URL}/drives/"
        f"{DRIVE_ID}/items/{item_id}/content"
    )

    # Request the Graph download endpoint without
    # automatically following its redirect.
    response = get_with_retry(
        download_url,
        headers=graph_headers,
        allow_redirects=False
    )

    # Graph commonly returns a redirect to a
    # temporary, preauthenticated download URL.
    if response.status_code in [301, 302, 303, 307, 308]:

        download_location = response.headers.get("Location")

        if not download_location:
            raise RuntimeError(
                "Graph returned a redirect without a Location header."
            )

        # The temporary download URL is already authorised.
        # Do not send the Graph access token to that URL.
        file_response = get_with_retry(
            download_location,
            headers=None
        )

    else:

        file_response = response

    return file_response.content


# =====================================================
# 5. UPLOAD A FILE TO AMAZON S3
# =====================================================

def upload_to_s3(item):

    item_id = item["id"]

    filename = item.get("name", "unnamed_file")

    mime_type = item.get("file", {}).get(
        "mimeType",
        "application/octet-stream"
    )

    print(f"Downloading: {filename}")

    file_content = download_file(item_id)

    # Use the SharePoint item ID as the stable S3 key.
    # This prevents filename collisions and means a
    # renamed file keeps the same S3 object key.
    s3_key = f"{DOCUMENT_PREFIX}{item_id}"

    s3_client.put_object(
        Bucket=S3_BUCKET,
        Key=s3_key,
        Body=file_content,
        ContentType=mime_type,
        Metadata={
            "sharepoint-item-id": item_id,
            "sharepoint-drive-id": DRIVE_ID,
            "sharepoint-name": filename
        }
    )

    print(f"Uploaded to S3: {s3_key}")


# =====================================================
# 6. RECURSIVE FOLDER TRAVERSAL
# =====================================================

def traverse_folder(folder_id):

    url = (
        f"{GRAPH_BASE_URL}/drives/"
        f"{DRIVE_ID}/items/{folder_id}/children"
    )

    while url:

        response = get_with_retry(
            url,
            headers=graph_headers
        )

        data = response.json()

        for item in data.get("value", []):

            if "folder" in item:

                folder_name = item.get("name")

                print(f"Entering folder: {folder_name}")

                # Function calls itself for subfolders.
                traverse_folder(item["id"])

            elif "file" in item:

                upload_to_s3(item)

        # Handle pagination
        url = data.get("@odata.nextLink")


def full_recursive_sync():

    print("Starting full recursive SharePoint scan.")

    root_folder_id = "root"

    traverse_folder(root_folder_id)

    print("Full recursive scan completed.")


# =====================================================
# 7. LOAD SAVED DELTA LINK FROM S3
# =====================================================

def load_delta_link():

    try:

        response = s3_client.get_object(
            Bucket=S3_BUCKET,
            Key=STATE_KEY
        )

        state_data = json.loads(
            response["Body"].read().decode("utf-8")
        )

        return state_data.get("delta_link")

    except ClientError as error:

        error_code = error.response.get(
            "Error", {}
        ).get("Code")

        if error_code in ["NoSuchKey", "404", "NotFound"]:

            print("No previous delta state found.")

            return None

        raise


# =====================================================
# 8. SAVE DELTA LINK TO S3
# =====================================================

def save_delta_link(delta_link):

    state_data = {
        "delta_link": delta_link,
        "updated_at": datetime.now(
            timezone.utc
        ).isoformat()
    }

    s3_client.put_object(
        Bucket=S3_BUCKET,
        Key=STATE_KEY,
        Body=json.dumps(state_data).encode("utf-8"),
        ContentType="application/json"
    )

    print("Delta tracking state saved to S3.")


# =====================================================
# 9. PROCESS A DELTA ITEM
# =====================================================

def process_delta_item(item):

    item_id = item.get("id")

    if not item_id:
        return

    s3_key = f"{DOCUMENT_PREFIX}{item_id}"

    # Check whether SharePoint reports a deletion.
    if "deleted" in item:

        if "folder" in item:

            print(
                f"Deleted folder detected: "
                f"{item.get('name', item_id)}"
            )

            print(
                "Folder descendants require separate "
                "cleanup tracking."
            )

            return

        print(
            f"Deleting SharePoint document from S3: "
            f"{item.get('name', item_id)}"
        )

        s3_client.delete_object(
            Bucket=S3_BUCKET,
            Key=s3_key
        )

        return

    # Delta query includes folder items.
    # Their child files are also represented in the
    # drive's delta enumeration/change results.
    if "folder" in item:

        return

    # Upload new or modified files.
    if "file" in item:

        upload_to_s3(item)


# =====================================================
# 10. INCREMENTAL SYNCHRONISATION
# =====================================================

def run_delta_sync(start_url):

    url = start_url

    latest_delta_link = None

    while url:

        print("Checking SharePoint changes...")

        response = get_with_retry(
            url,
            headers=graph_headers
        )

        data = response.json()

        for item in data.get("value", []):

            process_delta_item(item)

        # More pages remain in this operation.
        if "@odata.nextLink" in data:

            url = data["@odata.nextLink"]

        else:

            # Final page contains the next delta URL.
            latest_delta_link = data.get(
                "@odata.deltaLink"
            )

            url = None

    if not latest_delta_link:

        raise RuntimeError(
            "Microsoft Graph did not return a deltaLink."
        )

    # Save only after every page has been processed.
    save_delta_link(latest_delta_link)

    print("Incremental synchronisation completed.")


# =====================================================
# 11. MAIN CONNECTOR
# =====================================================

def main():

    print("SharePoint-to-S3 connector started.")

    delta_link = load_delta_link()

    if delta_link:

        print("Previous synchronisation found.")

        # Retrieve only changes since the last run.
        run_delta_sync(delta_link)

    else:

        print("First synchronisation detected.")

        initial_delta_url = (
            f"{GRAPH_BASE_URL}/drives/"
            f"{DRIVE_ID}/root/delta"
        )

        # Initial delta enumeration retrieves the
        # current drive items, including nested items.
        run_delta_sync(initial_delta_url)

    print("Connector finished successfully.")


# =====================================================
# 12. RUN CONNECTOR
# =====================================================

if __name__ == "__main__":

    main()
```

# 7. Understanding the important functions and parameters

## A. `get_with_retry()`

This is our central HTTP request function.

Instead of writing `requests.get()` throughout the connector, we use one function that handles temporary failures.

```python
def get_with_retry(url, headers=None, allow_redirects=True):
```

| Parameter | Meaning |
|---|---|
| `url` | The Microsoft Graph endpoint or temporary download URL |
| `headers` | HTTP headers, including the Graph access token when required |
| `allow_redirects` | Controls whether requests automatically follows HTTP redirects |

Inside the function:

```python
response = session.get(
    url,
    headers=headers,
    timeout=60,
    allow_redirects=allow_redirects
)
```

- `session.get()` sends an HTTP GET request.
- `url` specifies the resource.
- `headers` supplies authentication when required.
- `timeout=60` limits how long the request can wait.
- `allow_redirects` controls automatic redirect handling.

The code checks:

```python
if response.status_code in [
    429, 500, 502, 503, 504
]:
```

These are the temporary errors we want to retry.

The retry delay is based on `Retry-After` when available. Otherwise, the connector uses an increasing delay with a small random amount added.

This is called exponential backoff with jitter.

## B. `download_file()`

This function retrieves the actual file content from SharePoint.

```python
def download_file(item_id):
```

The parameter:

- `item_id` is the unique identifier of the SharePoint file.

The endpoint is:

```text
/drives/{drive_id}/items/{item_id}/content
```

This requests the document's contents, not just its metadata.

Microsoft Graph commonly responds with a redirect to a temporary download URL.

The code follows that redirect separately and does not send the Microsoft Graph access token to the temporary URL.

Finally:

```python
return file_response.content
```

`.content` gives us the file's binary data.

For example:

- A PDF is returned as PDF bytes.
- An Excel document is returned as Excel bytes.
- A Word document is returned as Word bytes.

## C. `upload_to_s3()`

This function transfers the downloaded document into S3.

```python
def upload_to_s3(item):
```

The parameter `item` is the SharePoint JSON object describing the file.

We extract:

```python
item_id = item["id"]

filename = item.get("name", "unnamed_file")

mime_type = item.get("file", {}).get(
    "mimeType",
    "application/octet-stream"
)
```

Here:

- `item["id"]` gets the SharePoint item ID.
- `.get("name", "unnamed_file")` gets the filename, using a fallback if the name is missing.
- `.get("file", {})` retrieves the file metadata.
- `.get("mimeType", ...)` retrieves the file's MIME type.

We then upload it:

```python
s3_client.put_object(
    Bucket=S3_BUCKET,
    Key=s3_key,
    Body=file_content,
    ContentType=mime_type
)
```

| Parameter | Meaning |
|---|---|
| `Bucket` | The destination S3 bucket |
| `Key` | The object's name and location within the bucket |
| `Body` | The actual file bytes |
| `ContentType` | The document's MIME type |

Our S3 object key is:

```python
s3_key = f"{DOCUMENT_PREFIX}{item_id}"
```

For example:

```text
documents/sharepoint/DRIVE123/FILE456
```

We use the SharePoint item ID rather than the filename as the object key.

Why?

Imagine two SharePoint folders both contain a document named:

```text
report.pdf
```

If we use only the filename, one document could overwrite the other.

A stable item-ID-based key avoids that collision and keeps the S3 key unchanged if a document is renamed.

The original filename is retained as S3 object metadata.

## D. `traverse_folder()`

This is our recursive folder function.

```python
def traverse_folder(folder_id):
```

The parameter:

- `folder_id` identifies the SharePoint folder we want to inspect.

It retrieves the folder's children:

```python
url = (
    f"{GRAPH_BASE_URL}/drives/"
    f"{DRIVE_ID}/items/{folder_id}/children"
)
```

Then it checks each item:

```python
if "folder" in item:
    traverse_folder(item["id"])

elif "file" in item:
    upload_to_s3(item)
```

The important instruction is:

```python
traverse_folder(item["id"])
```

The function calls itself when it finds another folder.

This is recursion.

The function also follows `@odata.nextLink`, so it can handle folders containing more items than Microsoft Graph returns in one page.

**Important:** The main connector uses the initial delta enumeration for its first sync. That enumeration includes nested items, so it does not need to call the recursive function for that initial run. `full_recursive_sync()` is included as a separate full-scan method when you explicitly want to walk the folder tree.

## E. `load_delta_link()`

This function retrieves the saved synchronisation state from S3.

```python
response = s3_client.get_object(
    Bucket=S3_BUCKET,
    Key=STATE_KEY
)
```

The important parameters are:

- `Bucket`: the S3 bucket containing our state.
- `Key`: the S3 object containing the saved delta URL.

We read its contents:

```python
state_data = json.loads(
    response["Body"].read().decode("utf-8")
)
```

This converts the stored JSON into a Python dictionary.

Then:

```python
return state_data.get("delta_link")
```

returns the previous delta URL.

If no state exists, the function returns `None`. This tells our main connector that it needs to perform an initial synchronisation.

## F. `save_delta_link()`

This function saves the latest delta URL to S3.

```python
def save_delta_link(delta_link):
```

The parameter `delta_link` is the URL returned by Microsoft Graph.

We store it as JSON:

```json
{
    "delta_link": "MICROSOFT_GRAPH_DELTA_URL",
    "updated_at": "2026-11-11T10:00:00+00:00"
}
```

The next time the connector runs, it reads this state and requests changes from that point.

## G. `process_delta_item()`

This function decides what to do with each item returned by delta query.

It handles three situations:

**New or modified file**

```python
if "file" in item:
    upload_to_s3(item)
```

The file is downloaded and uploaded to S3.

Uploading a modified file to the same stable S3 key replaces the current object. If S3 versioning is enabled, previous object versions can be retained.

**Folder**

```python
if "folder" in item:
    return
```

We do not upload folders as documents.

**Deleted file**

```python
if "deleted" in item:
    s3_client.delete_object(
        Bucket=S3_BUCKET,
        Key=s3_key
    )
```

This removes the corresponding S3 object.

There is an important limitation: deleting a folder can leave its child documents in S3 if Microsoft Graph does not return separate deletion records for those children. A production connector should maintain a file-to-folder manifest or another mapping so it can clean up all descendants of a deleted folder.

## H. `run_delta_sync()`

This is the main incremental synchronisation function.

```python
def run_delta_sync(start_url):
```

The parameter `start_url` can be:

- The initial `/root/delta` endpoint.
- A previously saved delta URL.

The function retrieves each page, processes the returned items and follows `@odata.nextLink`.

Once all pages have been processed, it retrieves:

```python
latest_delta_link = data.get("@odata.deltaLink")
```

It then saves that URL.

**Why do we save the delta URL after processing all pages?**

Imagine the connector fails halfway through processing a synchronisation.

If it had already saved the new delta URL, the next run might skip changes that were not successfully uploaded.

By saving the URL only after all pages have been processed, we can retry from the previous saved point.

The S3 uploads and deletes are designed to be repeatable, so processing the same change again should generally be safe.

# 9. Important production considerations

The code above is a learning implementation with several useful enterprise patterns, but it is not yet a complete production connector.

Before using it with large business document libraries, consider these points:

| Area | What needs improving |
|---|---|
| Large files | The example loads each file into memory. Use streaming and multipart uploads for large files |
| Deleted folders | Maintain a folder-to-file manifest to clean up descendants reliably |
| Delta expiration | Handle expired delta tokens, including HTTP 410, by starting a fresh synchronisation |
| Security | Retrieve the access token securely instead of hardcoding it |
| S3 permissions | S3 does not automatically preserve SharePoint document permissions |
| Monitoring | Record upload counts, failures, durations and synchronisation results |
| Concurrent runs | Prevent two connector instances from updating the same delta state at the same time |
| Recovery | Use a durable processing log if you need stronger recovery and auditing guarantees |

Also, the example's retry function is designed for HTTP GET requests. If you later add other HTTP methods, implement retry behaviour appropriate to those methods.

The connector uses one S3 object per SharePoint file. S3 object versioning is worth enabling if you want to retain previous versions after an updated file is uploaded.

# 10. What you have learned

You now have three important connector engineering concepts:

**Recursive traversal:** How to navigate nested SharePoint folders using a function that calls itself.

**Incremental synchronisation:** How to use Microsoft Graph delta query and save a `deltaLink` so future runs retrieve changes rather than repeatedly scanning every document.

**Retry and throttling handling:** How to handle temporary API failures, respect `Retry-After` and retry requests with exponential backoff.

Together, these improvements move the connector beyond a simple file-copying script towards a more reliable data ingestion process.

**The next logical improvement is large-file streaming:** transferring large SharePoint documents to S3 without loading the entire document into Python memory.
