# LangChain Conversation History and Memory — Complete Practical Guide

## 1. How LLM conversation history works

### What is conversation history?

Conversation history is the collection of messages exchanged between a user and an AI assistant.

For example:

```text
User: Hi, my name is John.

AI: Hello John! How can I help you?

User: What is my name?

AI: Your name is John.
```

The AI can answer the last question because the earlier messages are included in the context sent to the model.

### Does an LLM automatically remember previous messages?

No.

An LLM generally processes the messages included in its current request. It does not automatically retain the complete history of previous API requests.

For example, consider these two independent requests:

**Request 1**

```python
response = model.invoke("My name is John.")
```

**Request 2**

```python
response = model.invoke("What is my name?")
```

The second request does not automatically know that your name is John.

You must send the previous conversation again, or use a history mechanism that retrieves it.

### How does conversation history work?

A chat model receives a list of messages.

Common message types include:

| Message type | Meaning |
|---|---|
| `SystemMessage` | Instructions that guide the assistant |
| `HumanMessage` | Message sent by the user |
| `AIMessage` | Message generated by the AI |
| `ToolMessage` | Result returned by a tool |

Example:

```python
from langchain_core.messages import (
    SystemMessage,
    HumanMessage,
    AIMessage
)

messages = [
    SystemMessage(
        content="You are a helpful assistant."
    ),
    HumanMessage(
        content="My name is John."
    ),
    AIMessage(
        content="Nice to meet you, John!"
    ),
    HumanMessage(
        content="What is my name?"
    )
]

response = model.invoke(messages)

print(response.content)
```

**Illustrative output:**

```text
Your name is John.
```

### How does the application maintain history?

The typical workflow looks like this:

```text
         User Question
               |
               v
       Retrieve History
               |
               v
       Add Current Message
               |
               v
       Send Messages to LLM
               |
               v
       Receive AI Response
               |
               v
       Save User + AI Messages
               |
               v
       Return Response
```

The application, not the model itself, is responsible for storing and supplying conversation history.

### Why do we need conversation history?

Without history, every request is independent.

With history, an application can:

- Understand follow-up questions.
- Remember information from earlier in the conversation.
- Maintain conversational context.
- Avoid repeatedly asking the same questions.
- Support multi-turn chat applications.

## 2. Manually managing message history

### What does manual history management mean?

You maintain a Python list of messages and send that list to the model every time.

You are responsible for:

1. Storing user messages.
2. Storing AI responses.
3. Sending previous messages to the model.
4. Updating the history after every response.

### Why would we manage history manually?

Manual management is useful when:

- Learning how conversation history works.
- Building a simple chatbot.
- You need complete control over stored messages.
- You want to implement custom filtering or summarization.

### Complete example

```python
from langchain_openai import ChatOpenAI

from langchain_core.messages import (
    SystemMessage,
    HumanMessage,
    AIMessage
)

model = ChatOpenAI(
    model="gpt-4.1-mini",
    temperature=0
)

# STEP 1: Create conversation history

chat_history = [
    SystemMessage(
        content="You are a helpful assistant."
    )
]


# STEP 2: Create a function to chat

def chat(user_input):

    # Add the user's message
    chat_history.append(
        HumanMessage(content=user_input)
    )

    # Send complete history to the model
    response = model.invoke(chat_history)

    # Save the AI response
    chat_history.append(response)

    return response.content


# STEP 3: First conversation

print(chat("My name is John."))

# STEP 4: Second conversation

print(chat("What is my name?"))

# STEP 5: Inspect conversation history

for message in chat_history:
    print(message.type, ":", message.content)
```

### Illustrative output

```text
Nice to meet you, John!

Your name is John.

system : You are a helpful assistant.
human : My name is John.
ai : Nice to meet you, John!
human : What is my name?
ai : Your name is John.
```

The exact AI wording may vary.

### What happens internally?

After the first request:

```text
[
    SystemMessage("You are a helpful assistant."),
    HumanMessage("My name is John."),
    AIMessage("Nice to meet you, John!")
]
```

After the second request:

```text
[
    SystemMessage("You are a helpful assistant."),
    HumanMessage("My name is John."),
    AIMessage("Nice to meet you, John!"),
    HumanMessage("What is my name?"),
    AIMessage("Your name is John.")
]
```

### Important point

This example uses a Python list.

If your application restarts, the list is lost unless you save it somewhere persistent.

## 3. InMemoryChatMessageHistory

### What is InMemoryChatMessageHistory?

`InMemoryChatMessageHistory` is a LangChain class that stores chat messages in memory.

Instead of manually managing a normal Python list, you use a history object with methods to add, retrieve, and clear messages.

### Why do we need it?

It provides a convenient way to:

- Store messages.
- Retrieve conversation history.
- Add user and AI messages.
- Clear the conversation.
- Connect history to LangChain Runnable pipelines.

### Example

```python
from langchain_core.chat_history import (
    InMemoryChatMessageHistory
)

from langchain_core.messages import (
    HumanMessage,
    AIMessage
)

# Create history

history = InMemoryChatMessageHistory()

# Add user message

history.add_message(
    HumanMessage(content="My name is John.")
)

# Add AI response

history.add_message(
    AIMessage(content="Hello John!")
)

# Retrieve history

for message in history.messages:
    print(message.type, ":", message.content)
```

**Output:**

```text
human : My name is John.
ai : Hello John!
```

### Important methods

| Method | Purpose |
|---|---|
| `add_message()` | Add one message |
| `add_messages()` | Add multiple messages |
| `add_user_message()` | Add a user message |
| `add_ai_message()` | Add an AI message |
| `aget_messages()` | Retrieve messages asynchronously |
| `aadd_messages()` | Add messages asynchronously |
| `clear()` | Remove all messages |
| `aclear()` | Clear history asynchronously |

### Example: Clear history

```python
history.clear()

print(history.messages)
```

**Output:**

```text
[]
```

### Important attributes

| Attribute | Purpose |
|---|---|
| `messages` | List of stored messages |

### Important limitation

In-memory history is temporary.

```text
Application starts
       |
       v
Messages stored in RAM
       |
       v
Application runs
       |
       v
Application stops
       |
       v
History is lost
```

Use it for learning, testing, and simple demonstrations, not as your only storage mechanism for production conversations.

**Version note:** LangChain's current reference marks some older chat-history abstractions, including `InMemoryChatMessageHistory`, as deprecated in newer releases. The example is useful for understanding existing applications and the requested API. For new applications, consider LangGraph checkpointing. <https://reference.langchain.com/python/langchain-core/chat_history/InMemoryChatMessageHistory>

## 4. RunnableWithMessageHistory

### What is RunnableWithMessageHistory?

`RunnableWithMessageHistory` is a wrapper around another Runnable.

It automatically manages conversation history for that Runnable.

It handles:

1. Retrieving previous messages.
2. Passing history to the underlying Runnable.
3. Adding the current user message.
4. Saving the AI response.

### Why do we need it?

Without this wrapper, you have to write code to:

- Retrieve history.
- Append the user message.
- Call the model.
- Append the AI response.

`RunnableWithMessageHistory` handles these operations for you.

### How does it work?

```text
          User Input
               |
               v
    RunnableWithMessageHistory
               |
               v
       Get Session History
               |
               v
      Add Previous Messages
               |
               v
          Chat Prompt
               |
               v
          Chat Model
               |
               v
        AI Response
               |
               v
        Save Messages
               |
               v
        Return Response
```

### Complete example

```python
from langchain_openai import ChatOpenAI

from langchain_core.prompts import (
    ChatPromptTemplate,
    MessagesPlaceholder
)

from langchain_core.chat_history import (
    InMemoryChatMessageHistory
)

from langchain_core.runnables.history import (
    RunnableWithMessageHistory
)


# STEP 1: Create the model

model = ChatOpenAI(
    model="gpt-4.1-mini",
    temperature=0
)


# STEP 2: Create the prompt

prompt = ChatPromptTemplate.from_messages([
    (
        "system",
        "You are a helpful assistant. "
        "Use the conversation history to answer questions."
    ),

    MessagesPlaceholder(
        variable_name="history"
    ),

    (
        "human",
        "{question}"
    )
])


# STEP 3: Create the main chain

chain = prompt | model


# STEP 4: Create a history store

store = {}


# STEP 5: Retrieve history by session ID

def get_session_history(session_id):

    if session_id not in store:

        store[session_id] = (
            InMemoryChatMessageHistory()
        )

    return store[session_id]


# STEP 6: Wrap the chain

chain_with_history = RunnableWithMessageHistory(
    chain,
    get_session_history,
    input_messages_key="question",
    history_messages_key="history"
)


# STEP 7: First question

response1 = chain_with_history.invoke(
    {
        "question": "My name is John."
    },
    config={
        "configurable": {
            "session_id": "user_123"
        }
    }
)

print(response1.content)


# STEP 8: Second question

response2 = chain_with_history.invoke(
    {
        "question": "What is my name?"
    },
    config={
        "configurable": {
            "session_id": "user_123"
        }
    }
)

print(response2.content)


# STEP 9: Inspect history

for message in store["user_123"].messages:
    print(message.type, ":", message.content)
```

### Illustrative output

```text
Nice to meet you, John!

Your name is John.

human : My name is John.
ai : Nice to meet you, John!
human : What is my name?
ai : Your name is John.
```

### Understanding the important parameters

| Parameter | Explanation |
|---|---|
| `runnable` | The Runnable or chain to wrap |
| `get_session_history` | Function that retrieves the history object for a session |
| `input_messages_key` | Dictionary key containing the current user message |
| `history_messages_key` | Prompt variable where previous messages are inserted |
| `output_messages_key` | Key containing the AI message when the wrapped Runnable returns a dictionary |
| `history_factory_config` | Configuration fields passed to the history factory |

### Understanding MessagesPlaceholder

This part is important:

```python
MessagesPlaceholder(
    variable_name="history"
)
```

It tells the prompt to accept a list of existing messages.

For example:

```python
[
    HumanMessage(content="My name is John."),
    AIMessage(content="Hello John!")
]
```

These messages are inserted into the prompt at the placeholder's position.

### Understanding the session configuration

```python
config={
    "configurable": {
        "session_id": "user_123"
    }
}
```

This identifies which conversation history should be retrieved.

If the next request uses the same session ID, it retrieves the same history.

If it uses a different session ID, it retrieves a different history.

**Important:** `RunnableWithMessageHistory` is a useful API to understand and maintain, but it is not the same thing as LangGraph checkpointing. For new agent applications, consider the newer persistence approach discussed later.

## 5. Session IDs

### What is a session ID?

A session ID is a unique identifier for a conversation.

It tells your application which conversation history belongs to a particular chat.

For example:

```text
User A
  |
  +-- Session 101
  |
  +-- Session 102

User B
  |
  +-- Session 201
```

One user can have multiple conversations.

### Why do we need session IDs?

Without session IDs, messages from different users or conversations could become mixed together.

Session IDs help you:

- Separate conversations.
- Resume an existing conversation.
- Support multiple users.
- Maintain multiple chats for one user.
- Retrieve the correct history.

### Example: Multiple sessions

```python
from langchain_core.chat_history import (
    InMemoryChatMessageHistory
)

store = {}


def get_session_history(session_id):

    if session_id not in store:
        store[session_id] = InMemoryChatMessageHistory()

    return store[session_id]


# Session 1

history1 = get_session_history("session_101")

history1.add_user_message(
    "My name is John."
)

history1.add_ai_message(
    "Hello John!"
)


# Session 2

history2 = get_session_history("session_202")

history2.add_user_message(
    "My name is Sarah."
)

history2.add_ai_message(
    "Hello Sarah!"
)


# Display histories

print("Session 101:")

for message in history1.messages:
    print(message.type, message.content)


print("\nSession 202:")

for message in history2.messages:
    print(message.type, message.content)
```

**Output:**

```text
Session 101:
human My name is John.
ai Hello John!

Session 202:
human My name is Sarah.
ai Hello Sarah!
```

The two conversations are completely separate.

### Session ID vs User ID

These are not necessarily the same.

| ID | Meaning |
|---|---|
| User ID | Identifies the person using the application |
| Session ID | Identifies one conversation |
| Thread ID | Often identifies a conversation thread in LangGraph |

For example:

```text
user_id = "user_123"

session_id = "chat_001"
session_id = "chat_002"
```

Both chats can belong to the same user.

### Production security note

Do not trust a session ID supplied by a browser without checking ownership.

Your backend should verify that the authenticated user is authorized to access that session.

## 6. Persistent chat history

### What is persistent chat history?

Persistent history means saving conversation messages in storage that survives application restarts.

Unlike in-memory history, persistent history is not lost when the Python process stops.

Common storage options:

- Redis
- PostgreSQL
- MySQL
- SQLite
- MongoDB
- Other databases or storage services

### Why do we need persistent history?

Imagine you build a chatbot.

A user has a conversation today and returns tomorrow.

If you only use in-memory storage, the previous conversation may be gone.

Persistent storage allows you to retrieve it later.

### How does persistent history work?

```text
         User
          |
          v
       Chat API
          |
          v
     Retrieve History
          |
          v
       Database
          |
          v
       Chat Model
          |
          v
      AI Response
          |
          v
      Save History
          |
          v
       Database
```

### In-memory vs persistent history

| Feature | In-memory | Persistent |
|---|---|---|
| Storage | RAM | Database or external storage |
| Survives restart | No | Yes |
| Easy to set up | Yes | Requires storage setup |
| Multiple application instances | Difficult without shared storage | Supported when properly configured |
| Production use | Limited | Common |
| Typical examples | Python object, dictionary | Redis, PostgreSQL, MySQL |

## 7. Redis-backed chat history

### What is Redis?

Redis is an in-memory data store commonly used for caching, session data, and fast application storage.

It can also be used to store conversation messages.

### Why use Redis for chat history?

Redis can be useful when you need:

- Fast message retrieval.
- Shared history across application instances.
- Session expiration.
- Temporary conversation storage.
- High-throughput access.

### Installation

One available LangChain Redis integration is:

```bash
pip install -U langchain-community redis
```

You also need a running Redis server.

For example, with Docker:

```bash
docker run --name langchain-redis \
    -p 6379:6379 \
    -d redis
```

### Example using RedisChatMessageHistory

```python
from langchain_community.chat_message_histories import (
    RedisChatMessageHistory
)

from langchain_core.messages import (
    HumanMessage,
    AIMessage
)


# STEP 1: Create Redis history

history = RedisChatMessageHistory(
    session_id="user_123_chat_001",
    url="redis://localhost:6379/0",
    ttl=3600
)


# STEP 2: Add messages

history.add_messages([
    HumanMessage(
        content="My name is John."
    ),

    AIMessage(
        content="Hello John!"
    )
])


# STEP 3: Retrieve messages

for message in history.messages:
    print(message.type, ":", message.content)
```

**Output:**

```text
human : My name is John.
ai : Hello John!
```

### Important parameters

| Parameter | Explanation |
|---|---|
| `session_id` | Identifier for the conversation |
| `url` | Redis connection URL |
| `key_prefix` | Prefix used for Redis storage keys |
| `ttl` | Expiration time in seconds |

Example:

```python
ttl=3600
```

This configures a one-hour time-to-live for the stored history entries.

### Redis URL format

```text
redis://localhost:6379/0
```

| Part | Meaning |
|---|---|
| `redis://` | Redis connection scheme |
| `localhost` | Redis host |
| `6379` | Redis default port |
| `0` | Redis database number |

### Using Redis with RunnableWithMessageHistory

You can use Redis as the history backend instead of an in-memory dictionary.

```python
from langchain_openai import ChatOpenAI

from langchain_core.prompts import (
    ChatPromptTemplate,
    MessagesPlaceholder
)

from langchain_core.runnables.history import (
    RunnableWithMessageHistory
)

from langchain_community.chat_message_histories import (
    RedisChatMessageHistory
)


model = ChatOpenAI(
    model="gpt-4.1-mini",
    temperature=0
)


prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a helpful assistant."),
    MessagesPlaceholder("history"),
    ("human", "{question}")
])


chain = prompt | model


def get_session_history(session_id):

    return RedisChatMessageHistory(
        session_id=session_id,
        url="redis://localhost:6379/0"
    )


chat_chain = RunnableWithMessageHistory(
    chain,
    get_session_history,
    input_messages_key="question",
    history_messages_key="history"
)


response = chat_chain.invoke(
    {
        "question": "My name is John."
    },
    config={
        "configurable": {
            "session_id": "user_123_chat_001"
        }
    }
)

print(response.content)
```

**Illustrative output:**

```text
Nice to meet you, John!
```

The next invocation with the same session ID will retrieve the stored conversation.

**Note:** The Redis integration APIs have evolved, and some history classes are marked deprecated in newer releases. Check the installed integration's current reference before adopting this exact backend in a new production system. LangGraph checkpointing is another option for durable conversation state.

## 8. Database-backed chat history

### What is database-backed history?

Instead of storing messages in RAM or Redis, you store them in a database.

For example:

```text
chat_messages
------------------------------------------------
id | session_id | message_type | content
------------------------------------------------
1  | chat_001   | human        | My name is John.
2  | chat_001   | ai           | Hello John!
3  | chat_001   | human        | What is my name?
4  | chat_001   | ai           | Your name is John.
```

### Why do we need database storage?

A database is useful when you need:

- Long-term message retention.
- Historical reporting.
- Auditing.
- Structured queries.
- Integration with other application data.
- Data backup and recovery.

### Example using SQLChatMessageHistory

LangChain provides `SQLChatMessageHistory` through `langchain-community`.

Install:

```bash
pip install -U langchain-community sqlalchemy
```

### Complete example with SQLite

SQLite is convenient because you do not need a separate database server.

```python
from langchain_community.chat_message_histories import (
    SQLChatMessageHistory
)

from langchain_core.messages import (
    HumanMessage,
    AIMessage
)


# STEP 1: Create database-backed history

history = SQLChatMessageHistory(
    session_id="chat_001",
    connection_string="sqlite:///chat_history.db"
)


# STEP 2: Add messages

history.add_messages([
    HumanMessage(
        content="My name is John."
    ),

    AIMessage(
        content="Hello John!"
    )
])


# STEP 3: Retrieve history

for message in history.messages:
    print(message.type, ":", message.content)
```

**Output:**

```text
human : My name is John.
ai : Hello John!
```

A database file named `chat_history.db` will be created in the current working directory.

### Important parameters

| Parameter | Explanation |
|---|---|
| `session_id` | Identifies the conversation |
| `connection_string` | Database connection string, or use a database connection object |
| `table_name` | Name of the database table |
| `session_id_field_name` | Name of the session ID field |
| `connection` | Existing SQLAlchemy engine or connection |
| `engine_args` | Additional database engine settings |
| `async_mode` | Configures asynchronous database operation |

### Example: PostgreSQL connection string

A typical SQLAlchemy-style connection string looks like:

```text
postgresql+psycopg://username:password@localhost:5432/chatdb
```

You can use an appropriate PostgreSQL driver and a database engine with the SQL history integration.

### Important production considerations

- Keep database credentials in environment variables or a secret manager.
- Use connection pooling.
- Add database indexes for session lookups when appropriate.
- Define a retention policy.
- Protect sensitive conversation data.
- Consider concurrent writes and transaction handling.

**Note:** `SQLChatMessageHistory` is useful for understanding and implementing database-backed message storage. Its API and package placement can change, so check the current LangChain reference when upgrading.

## 9. Short-term memory

### What is short-term memory?

Short-term memory represents information needed during the current conversation or task.

For example:

```text
User: My name is John.

AI: Nice to meet you, John.

User: I live in Dublin.

AI: Got it.

User: Where do I live?

AI: You live in Dublin.
```

The assistant uses the current conversation context to answer.

### Why do we need short-term memory?

Short-term memory allows an AI application to:

- Understand follow-up questions.
- Refer to earlier messages.
- Maintain the current task.
- Keep track of recent user instructions.
- Maintain context during multi-step workflows.

### How does it work?

```text
Current Conversation
        |
        v
Store Recent Messages
        |
        v
Retrieve Relevant History
        |
        v
Include in Model Input
        |
        v
Generate Response
```

### Example using recent messages

```python
from langchain_core.messages import (
    HumanMessage,
    AIMessage
)

chat_history = [
    HumanMessage(
        content="My name is John."
    ),

    AIMessage(
        content="Hello John!"
    ),

    HumanMessage(
        content="I live in Dublin."
    ),

    AIMessage(
        content="Dublin sounds lovely!"
    )
]

# Keep only the most recent two messages

recent_history = chat_history[-2:]

for message in recent_history:
    print(message.type, ":", message.content)
```

**Output:**

```text
human : I live in Dublin.
ai : Dublin sounds lovely!
```

### Short-term memory in LangGraph

For new LangGraph agents, short-term memory is commonly implemented using a checkpointer and a thread ID.

Conceptually:

```python
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import StateGraph

# Build your graph first.

checkpointer = InMemorySaver()

# Compile the graph with the checkpointer.
# graph = builder.compile(checkpointer=checkpointer)

# Invoke using a thread identifier.
# graph.invoke(
#     {"messages": [...]},
#     config={
#         "configurable": {
#             "thread_id": "conversation_001"
#         }
#     }
# )
```

`InMemorySaver` keeps checkpoint state in memory. For durable production persistence, use an appropriate database-backed checkpointer.

## 10. Long-term memory

### What is long-term memory?

Long-term memory stores information that should remain useful across multiple conversations or sessions.

For example:

```text
Conversation 1:
User: My name is John.
User: I prefer Python examples.

Conversation 2:
User: Teach me API development.

AI: Let's use Python and FastAPI for the examples.
```

The second conversation can use information saved from the first conversation.

### Why do we need long-term memory?

Short-term memory is usually limited to a current conversation.

Long-term memory is useful for:

- User preferences.
- Persistent profile information.
- Repeated requirements.
- Important facts explicitly saved by the application.
- Knowledge that should be retrieved across conversations.

### Short-term vs long-term memory

| Short-term memory | Long-term memory |
|---|---|
| Current conversation context | Information retained across conversations |
| Usually tied to a thread | Usually tied to a user or knowledge record |
| Recent messages | Selected facts, summaries, or documents |
| Can grow quickly | Usually selectively stored |
| Often managed by a checkpointer | Often stored in a database or vector store |

### How does long-term memory work?

```text
         Conversation
               |
               v
       Identify Useful Facts
               |
               v
         Save Information
               |
               v
       Persistent Memory Store
               |
               v
      New Conversation Starts
               |
               v
        Retrieve Relevant Facts
               |
               v
          Supply to LLM
```

### Example: Simple long-term memory using a dictionary

This example demonstrates the concept. A dictionary is not persistent storage.

```python
# Simulated long-term memory

long_term_memory = {}


# Save information

def save_memory(user_id, key, value):

    if user_id not in long_term_memory:
        long_term_memory[user_id] = {}

    long_term_memory[user_id][key] = value


# Retrieve information

def get_memory(user_id):

    return long_term_memory.get(user_id, {})


# Save user preferences

save_memory(
    "user_123",
    "name",
    "John"
)

save_memory(
    "user_123",
    "preferred_language",
    "Python"
)


# Retrieve memories

print(get_memory("user_123"))
```

**Output:**

```python
{
    'name': 'John',
    'preferred_language': 'Python'
}
```

### How can long-term memory use a vector database?

Suppose a user has shared hundreds of preferences, facts, and project details.

You can:

1. Convert selected memories into embeddings.
2. Store those embeddings in a vector store.
3. Search for memories relevant to a new question.
4. Include the retrieved information in the prompt.

For example:

```text
Saved memory:
"John prefers Python examples."

New question:
"Show me how to build an API."

Retrieved memory:
"John prefers Python examples."

LLM input:
"Show how to build an API using Python."
```

This is a retrieval-based memory pattern.

**Important:** Long-term memory should be selective. Do not save every message as a permanent user fact. Apply privacy, consent, retention, and deletion rules.

## 11. Conversation summarization

### What is conversation summarization?

Conversation summarization means converting a large conversation history into a shorter summary.

For example, imagine the user has exchanged 100 messages with an assistant.

Sending all 100 messages every time may be expensive and may exceed the model's context window.

Instead, summarize older messages and retain recent messages.

### Why do we need summarization?

Summarization helps:

- Reduce token usage.
- Reduce request costs.
- Preserve important information.
- Keep conversations within context limits.
- Retain useful details from older messages.

### Example

Original conversation:

```text
User: My name is John.
AI: Hello John.

User: I live in Dublin.
AI: Nice!

User: I am learning Python.
AI: Great!

User: I want to become a backend developer.
AI: I can help you with that.

User: I prefer practical coding examples.
AI: Understood.
```

Possible summary:

```text
The user is John and lives in Dublin.
He is learning Python and wants to become
a backend developer. He prefers practical
coding examples.
```

The summary preserves useful context without keeping every word.

### How does summarization work?

```text
       Full Conversation
               |
               v
       Select Older Messages
               |
               v
         Summarization LLM
               |
               v
        Short Conversation Summary
               |
               v
        Keep Recent Messages
               |
               v
       Send Summary + Recent Messages
               |
               v
             Main LLM
```

### Example: Summarize history using ChatOpenAI

```python
from langchain_openai import ChatOpenAI

from langchain_core.messages import (
    HumanMessage,
    AIMessage
)

from langchain_core.prompts import (
    ChatPromptTemplate
)

from langchain_core.output_parsers import (
    StrOutputParser
)


# STEP 1: Create a summarization model

model = ChatOpenAI(
    model="gpt-4.1-mini",
    temperature=0
)


# STEP 2: Create a summarization prompt

summary_prompt = ChatPromptTemplate.from_messages([
    (
        "system",
        """
        Summarize the conversation.

        Preserve:
        - Important user facts
        - User preferences
        - Goals
        - Important decisions

        Keep the summary concise.
        """
    ),

    (
        "human",
        "{conversation}"
    )
])


# STEP 3: Create summarization chain

summary_chain = (
    summary_prompt
    | model
    | StrOutputParser()
)


# STEP 4: Create conversation history

chat_history = [
    HumanMessage(
        content="My name is John."
    ),

    AIMessage(
        content="Hello John!"
    ),

    HumanMessage(
        content="I live in Dublin."
    ),

    AIMessage(
        content="Nice to meet you!"
    ),

    HumanMessage(
        content="I am learning Python."
    ),

    AIMessage(
        content="Python is a great language."
    ),

    HumanMessage(
        content="I want to become a backend developer."
    ),

    AIMessage(
        content="I can help you learn backend development."
    )
]


# STEP 5: Convert messages into text

conversation = "\n".join(
    f"{message.type}: {message.content}"
    for message in chat_history
)


# STEP 6: Generate summary

summary = summary_chain.invoke({
    "conversation": conversation
})


# STEP 7: Print summary

print(summary)
```

### Illustrative output

```text
John lives in Dublin and is learning Python.
He wants to become a backend developer.
```

The exact summary will depend on the model.

### Better approach: Summary + recent messages

Instead of replacing all history with a summary, preserve recent messages as well.

```python
# Keep the last four messages

recent_messages = chat_history[-4:]

# Store the summary separately

conversation_summary = summary

# Use both when building the next model input
```

Your next prompt can contain:

```text
System:
You are a helpful assistant.

Conversation summary:
John lives in Dublin and is learning Python.
He wants to become a backend developer.

Recent messages:
[Last four conversation messages]

Current question:
What should I learn next?
```

This combines older context with the latest discussion.

### Important warning

A summary is a compressed representation, not a perfect copy of the conversation.

Important details can be omitted or incorrectly summarized. Preserve exact records separately if you need auditability or precise recall.

## 12. Managing context-window limits

### What is a context window?

A context window is the maximum amount of information a model can process in one request, measured in tokens.

It can include:

- System instructions.
- User messages.
- Previous conversation messages.
- Retrieved documents.
- Tool outputs.
- The current question.
- Space reserved for the model's response.

### Why do we need context-window management?

Imagine a model supports a context window of 100,000 tokens.

Your conversation has already consumed 98,000 tokens.

You cannot safely send another 10,000-token request and expect it to fit.

You need to manage the input size.

### Common context-management techniques

| Technique | Explanation |
|---|---|
| Trimming | Remove older or less important messages |
| Sliding window | Keep only the most recent messages |
| Summarization | Replace older messages with a compact summary |
| Retrieval | Include only relevant historical information |
| Message filtering | Remove irrelevant messages |
| Token budgeting | Reserve space for instructions, history, and output |

### Example 1: Keep only recent messages

```python
from langchain_core.messages import (
    HumanMessage,
    AIMessage
)

messages = [
    HumanMessage(content="Message 1"),
    AIMessage(content="Response 1"),

    HumanMessage(content="Message 2"),
    AIMessage(content="Response 2"),

    HumanMessage(content="Message 3"),
    AIMessage(content="Response 3"),

    HumanMessage(content="Message 4"),
    AIMessage(content="Response 4")
]


# Keep only the last four messages

recent_messages = messages[-4:]


for message in recent_messages:
    print(message.type, message.content)
```

**Output:**

```text
human Message 3
ai Response 3
human Message 4
ai Response 4
```

This is a simple sliding-window strategy.

### Example 2: Use LangChain trim_messages

LangChain provides `trim_messages()` to trim messages according to a token budget.

```python
from langchain_openai import ChatOpenAI

from langchain_core.messages import (
    SystemMessage,
    HumanMessage,
    AIMessage
)

from langchain_core.messages.utils import trim_messages


model = ChatOpenAI(
    model="gpt-4.1-mini"
)


messages = [
    SystemMessage(
        content="You are a helpful assistant."
    ),

    HumanMessage(
        content="Explain Python."
    ),

    AIMessage(
        content="Python is a programming language."
    ),

    HumanMessage(
        content="Explain Java."
    ),

    AIMessage(
        content="Java is another programming language."
    ),

    HumanMessage(
        content="Compare both languages."
    )
]


# Trim history to a token budget

trimmed_messages = trim_messages(
    messages,
    max_tokens=1000,
    token_counter=model,
    strategy="last",
    include_system=True,
    start_on="human"
)


# Display trimmed messages

for message in trimmed_messages:
    print(message.type, ":", message.content)
```

**Output:**

The exact output depends on the tokenizer and the selected token budget. If all messages fit within the budget, all messages may be retained.

### Understanding the parameters

| Parameter | Explanation |
|---|---|
| `messages` | Messages to trim |
| `max_tokens` | Maximum token budget for the trimmed messages |
| `token_counter` | Function or model used to estimate/count tokens |
| `strategy` | How messages are selected; `"last"` keeps the most recent content |
| `include_system` | Whether to preserve a system message |
| `start_on` | Message type at which the trimmed history should begin |
| `allow_partial` | Whether a message may be partially retained |
| `end_on` | Optional message type at which the history should end |

For ordinary chat history, retaining the system instructions and recent complete conversational turns is usually a good starting point.

### Example 3: Reserve tokens for the response

Suppose your model supports a 100,000-token context window.

You might allocate:

| Purpose | Token budget |
|---|---:|
| System instructions | 2,000 |
| Conversation history | 20,000 |
| Retrieved documents | 30,000 |
| Current user question | 2,000 |
| Reserved model response | 8,000 |
| Safety margin / other overhead | 38,000 |
| **Total** | **100,000** |

These are illustrative numbers, not model-specific limits.

The important idea is that the entire request must fit within the model's actual context limit.

### Example 4: Summarize and trim together

A practical strategy:

```text
Full History
     |
     v
Is History Too Large?
     |
     +---- No ----> Keep History
     |
     +---- Yes
             |
             v
      Summarize Older Messages
             |
             v
      Preserve Recent Messages
             |
             v
      Count Tokens
             |
             v
      Trim if Still Too Large
             |
             v
      Send to Model
```

This is more useful than simply deleting old messages because it can preserve important information.

## 13. How short-term and long-term memory work together

In a real chatbot, you may use both.

### Example scenario

A user has a profile:

```text
User ID: user_123

Long-term memory:
- Name: John
- Preferred programming language: Python
- Goal: Become a backend developer
```

The current conversation contains:

```text
Short-term history:
- User is learning FastAPI.
- User is building a REST API.
- User is having trouble with authentication.
```

When the user asks:

```text
How should I implement it?
```

The application can supply:

1. Long-term memory: John prefers Python and wants to become a backend developer.
2. Short-term history: The current topic is FastAPI authentication.
3. Current question: How should I implement it?

The model can then provide an answer relevant to the current conversation and the saved preferences.

### Combined architecture

```text
                 User
                  |
                  v
             Chat Backend
                  |
         +--------+--------+
         |                 |
         v                 v
   Short-term          Long-term
     Memory              Memory
         |                 |
         v                 v
  Recent Messages     Saved User Facts
         |                 |
         +--------+--------+
                  |
                  v
            Prompt Builder
                  |
                  v
              Chat Model
                  |
                  v
             AI Response
                  |
                  v
       Update Conversation History
```

### Important distinction

Saving conversation history does not automatically create useful long-term memory.

A history database may contain thousands of messages. Long-term memory usually requires selecting, extracting, indexing, and retrieving relevant information.

## 14. Modern alternative: LangGraph checkpointing

### Why should you learn LangGraph memory?

For new agent-based applications, LangGraph provides a more integrated way to persist graph state across multiple interactions.

Instead of managing message history separately from your workflow, you can use a checkpointer.

A checkpointer saves state associated with a thread.

### Important concepts

| Concept | Explanation |
|---|---|
| State | Information maintained by the graph |
| Checkpointer | Saves and retrieves graph state |
| Thread ID | Identifies a conversation thread |
| `InMemorySaver` | Stores checkpoints in memory |
| Database checkpointer | Stores checkpoints persistently |

### Simplified example

```python
from langchain_openai import ChatOpenAI

from langchain.agents import create_agent

from langgraph.checkpoint.memory import InMemorySaver


model = ChatOpenAI(
    model="gpt-4.1-mini"
)


# Create an in-memory checkpointer

checkpointer = InMemorySaver()


# Create an agent with persistent thread state

agent = create_agent(
    model=model,
    tools=[],
    checkpointer=checkpointer
)


# First message

result1 = agent.invoke(
    {
        "messages": [
            {
                "role": "user",
                "content": "My name is John."
            }
        ]
    },
    config={
        "configurable": {
            "thread_id": "conversation_001"
        }
    }
)


# Second message in the same thread

result2 = agent.invoke(
    {
        "messages": [
            {
                "role": "user",
                "content": "What is my name?"
            }
        ]
    },
    config={
        "configurable": {
            "thread_id": "conversation_001"
        }
    }
)


print(result2["messages"][-1].content)
```

**Illustrative output:**

```text
Your name is John.
```

The checkpointer preserves the graph state associated with `conversation_001`.

For a production application, use a suitable persistent checkpointer rather than `InMemorySaver`.

**Important:** A checkpointer saves graph state. It does not mean every historical message must always be sent to the model. You still need to manage the model's context input.

## 15. Common mistakes to avoid

### Mistake 1: Assuming the model remembers previous API calls

It does not automatically remember them. Supply history or use a history/checkpointing system.

### Mistake 2: Using one shared history for every user

This can mix conversations and expose one user's information to another.

Use separate, access-controlled session identifiers.

### Mistake 3: Using in-memory storage in production without understanding its limitations

Application restarts can destroy in-memory history.

Use persistent storage when history must survive restarts.

### Mistake 4: Sending the entire history forever

Conversation history grows over time.

Use trimming, summarization, filtering, or retrieval.

### Mistake 5: Confusing long-term memory with chat history

Chat history is a record of messages.

Long-term memory is selected information intended to remain useful across conversations.

### Mistake 6: Forgetting the system prompt when trimming

Your system instructions may be essential. Preserve them when constructing the trimmed conversation.

### Mistake 7: Assuming a session ID proves identity

A session ID identifies a conversation. Your backend must still authenticate the user and authorize access.

### Mistake 8: Treating a summary as a complete record

Summaries can omit details. Keep original records separately when exact history is important.

### Which approach should you use?

| Requirement | Suggested approach |
|---|---|
| Learning how history works | Manual message list |
| Simple local chatbot | In-memory history |
| Existing LCEL application | `RunnableWithMessageHistory` |
| Shared fast session storage | Redis |
| Durable SQL message records | SQL history |
| New agent with conversation state | LangGraph checkpointer |
| Remember preferences across chats | Long-term memory store |
| Very long conversations | Summarization + trimming |
| Large collection of historical facts | Retrieval-based memory |

### Final takeaway

Remember these four ideas:

1. **Conversation history:** Send previous messages to the model so it understands the conversation.
2. **Persistence:** Save messages outside RAM if you need to retrieve them later.
3. **Memory:** Use short-term memory for current tasks and long-term memory for selected information across conversations.
4. **Context management:** Trim, summarize, or retrieve relevant information so that the request fits the model's context window.
