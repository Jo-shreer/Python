We will use one small knowledge base throughout the examples so that you can understand how each advanced retrieval technique changes the same RAG system.

```python
documents = [
```

# 1. Multi-query retrieval

## What is multi-query retrieval?

Multi-query retrieval means generating multiple alternative search queries from one user question.

Instead of searching the vector database using only the original question, an LLM generates several variations of that question.

### Example

User asks:

```text
How does FastAPI improve API development?
```

The system generates:

```text
Query 1: How does FastAPI improve API development?

Query 2: What are the main benefits of using FastAPI?

Query 3: Which features make FastAPI useful for
         building Python APIs?

Query 4: How does FastAPI handle validation,
         asynchronous requests, and documentation?
```

The retriever searches using all four queries and combines the results.

## Why do we need it?

A single question may not use the same words as the documents.

For example:

- User asks: "How can I make my API faster?"
- Document says: "FastAPI supports asynchronous programming."

A search using only the original wording might not find all relevant information.

Multiple queries improve the chance of finding useful documents from different perspectives.

## How does it work?

```text
             User Question
                   |
                   v
              OpenAI LLM
                   |
                   v
          Generate Multiple Queries
             /      |      \
            v       v       v
          Query 1 Query 2 Query 3
            |       |       |
            v       v       v
          Vector Search (each query)
             \      |      /
              \     |     /
                   v
             Merge Documents
                   |
                   v
              Remove Duplicates
                   |
                   v
             Return Documents
```

## Example using OpenAI and FAISS

```python
from langchain_openai import (
    ChatOpenAI,
    OpenAIEmbeddings
)

from langchain_community.vectorstores import FAISS

from langchain_core.documents import Document

from langchain_classic.retrievers.multi_query import (
    MultiQueryRetriever
)


# 1. Create documents

docs = [
    Document(page_content=text)
    for text in documents
]


# 2. Create embeddings

embeddings = OpenAIEmbeddings(
    model="text-embedding-3-small"
)


# 3. Create vector store

vectorstore = FAISS.from_documents(
    docs,
    embeddings
)


# 4. Create base retriever

base_retriever = vectorstore.as_retriever(
    search_kwargs={"k": 3}
)


# 5. Create OpenAI model

llm = ChatOpenAI(
    model="gpt-4.1-mini",
    temperature=0
)


# 6. Create multi-query retriever

multi_query_retriever = MultiQueryRetriever.from_llm(
    retriever=base_retriever,
    llm=llm
)


# 7. Retrieve documents

results = multi_query_retriever.invoke(
    "How does FastAPI improve API development?"
)


# 8. Display results

for i, doc in enumerate(results, 1):
    print(f"\nDocument {i}:")
    print(doc.page_content)
```

### Example output

```text
Document 1:
FastAPI is a Python framework for building APIs.
It supports asynchronous programming, automatic
API documentation, and validation.

Document 2:
Python is a popular programming language.
It is used for web development, automation,
data science, and artificial intelligence.
```

The exact documents and ordering depend on the generated queries and vector search results.

### Important points

- The LLM generates alternative queries.
- Each query is searched independently.
- Results are combined and deduplicated.
- More queries can improve recall, but also increase latency and retrieval cost.

**When to use:** When users phrase questions in different ways or when a single query retrieves incomplete results.

# 2. Query rewriting

## What is query rewriting?

Query rewriting means transforming the user's original question into a better search query before retrieving documents.

Unlike multi-query retrieval, which creates several alternatives, query rewriting usually creates one improved query.

### Example

Conversation:

```text
User: What is FastAPI?

AI: FastAPI is a Python framework for building APIs.

User: What are its advantages?
```

The last question is incomplete by itself.

A query rewriter can transform it into:

```text
What are the advantages of using FastAPI
for building Python APIs?
```

This is a standalone search query.

## Why do we need it?

Query rewriting is particularly useful for:

- Follow-up questions.
- Pronouns such as "it", "they", and "that".
- Ambiguous questions.
- Spelling and terminology corrections.
- Long conversational questions.
- Questions containing irrelevant wording.

## How does it work?

```text
Conversation History
        +
Current Question
        |
        v
    OpenAI LLM
        |
        v
    Rewritten Query
        |
        v
    Retriever
        |
        v
    Relevant Documents
```

## Complete example

```python
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser


llm = ChatOpenAI(
    model="gpt-4.1-mini",
    temperature=0
)


rewrite_prompt = ChatPromptTemplate.from_messages([
    (
        "system",
        """
        Rewrite the user's latest question into a
        standalone search query.

        Use the conversation history to resolve
        references such as it, they, and that.

        Return only the rewritten query.
        """
    ),
    (
        "human",
        """
        Conversation history:
        {history}

        Latest question:
        {question}
        """
    )
])


rewrite_chain = (
    rewrite_prompt
    | llm
    | StrOutputParser()
)


rewritten_query = rewrite_chain.invoke({
    "history": """
    User: What is FastAPI?
    Assistant: FastAPI is a Python framework
    for building APIs.
    """,
    "question": "What are its advantages?"
})


print(rewritten_query)
```

### Example output

```text
What are the advantages of using FastAPI
for building Python APIs?
```

## Use the rewritten query for retrieval

```python
retrieved_docs = base_retriever.invoke(
    rewritten_query
)

for doc in retrieved_docs:
    print(doc.page_content)
```

### Multi-query vs query rewriting

| Multi-query retrieval | Query rewriting |
|---|---|
| Creates several queries | Usually creates one query |
| Searches from multiple perspectives | Makes the original question clearer |
| Useful for improving recall | Useful for resolving ambiguity |
| More retrieval operations | Usually one retrieval operation |

**When to use:** When a user asks follow-up questions that depend on previous conversation context.

# 3. Contextual compression

## What is contextual compression?

Contextual compression means retrieving documents and then removing information that is irrelevant to the user's current question.

Imagine retrieving a document containing 1,000 words.

Only 100 words may be relevant to the question.

Contextual compression attempts to keep the useful information and discard unnecessary content.

### Example

User asks:

```text
What are the advantages of FastAPI?
```

Retrieved document:

```text
FastAPI is a Python framework for building APIs.

It supports asynchronous programming.

It provides automatic API documentation.

Python is also used for data science.

Python is popular in machine learning.

FastAPI supports request validation.
```

Compressed context:

```text
FastAPI supports asynchronous programming,
automatic API documentation, and request validation.
```

## Why do we need it?

Normal retrieval can return documents containing both relevant and irrelevant information.

Sending entire documents to an LLM can:

- Increase token usage.
- Increase cost.
- Introduce distracting information.
- Reduce answer focus.
- Make it harder to fit context into the model window.

Compression helps reduce this noise.

## How does it work?

```text
User Question
     |
     v
Base Retriever
     |
     v
Retrieved Documents
     |
     v
OpenAI Compressor
     |
     v
Relevant Passages Only
     |
     v
Chat Model
```

## Example using OpenAI

We can implement compression directly using an OpenAI model.

```python
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser


llm = ChatOpenAI(
    model="gpt-4.1-mini",
    temperature=0
)


compression_prompt = ChatPromptTemplate.from_template(
    """
    Extract only the information from the context
    that is relevant to the question.

    Do not add new facts.

    If nothing is relevant, return:
    No relevant information found.

    Question:
    {question}

    Context:
    {context}
    """
)


compression_chain = (
    compression_prompt
    | llm
    | StrOutputParser()
)


context = """
FastAPI is a Python framework for building APIs.

It supports asynchronous programming.

It provides automatic API documentation.

Python is also used for data science.

Python is popular in machine learning.

FastAPI supports request validation.
"""


compressed_context = compression_chain.invoke({
    "question": "What are the advantages of FastAPI?",
    "context": context
})


print(compressed_context)
```

### Illustrative output

```text
FastAPI supports asynchronous programming,
automatic API documentation, and request validation.
```

## Important point

Compression should preserve the original meaning.

It should not invent information or turn an uncertain document into a confident claim.

# 4. ContextualCompressionRetriever

## What is ContextualCompressionRetriever?

`ContextualCompressionRetriever` is a LangChain retriever wrapper.

It combines:

1. A base retriever.
2. A document compressor.

It first retrieves documents and then passes them through the compressor.

## Why do we need it?

Instead of writing separate code for:

- Retrieving documents.
- Passing them to a compression model.
- Filtering irrelevant content.

You can wrap the retrieval process in a single retriever interface.

## How does it work?

```text
Question
   |
   v
Base Retriever
   |
   v
Retrieved Documents
   |
   v
Document Compressor
   |
   v
Compressed Documents
```

## Example with an OpenAI-powered compressor

```python
from langchain_openai import ChatOpenAI

from langchain_classic.retrievers.contextual_compression import (
    ContextualCompressionRetriever
)

from langchain_classic.retrievers.document_compressors import (
    LLMChainExtractor
)


llm = ChatOpenAI(
    model="gpt-4.1-mini",
    temperature=0
)


# Create compressor

compressor = LLMChainExtractor.from_llm(
    llm
)


# Wrap the base retriever

compression_retriever = ContextualCompressionRetriever(
    base_retriever=base_retriever,
    base_compressor=compressor
)


# Retrieve compressed documents

compressed_docs = compression_retriever.invoke(
    "What are the advantages of FastAPI?"
)


for doc in compressed_docs:
    print(doc.page_content)
```

### Example output

```text
FastAPI supports asynchronous programming,
automatic API documentation, and validation.
```

The exact extraction depends on the retrieved documents and model.

### Parameters

| Parameter | Explanation |
|---|---|
| `base_retriever` | Retriever that finds candidate documents |
| `base_compressor` | Compressor that filters or compresses documents |

**Important:** The class is in the classic retriever package in current LangChain versions. The exact compressor imports may differ by version.

**When to use:** When retrieval finds useful documents but returns too much irrelevant text.

# 5. Parent-document retrieval

## What is parent-document retrieval?

Parent-document retrieval searches using small chunks but returns a larger parent document or parent chunk.

This solves an important RAG problem.

Small chunks are good for precise search, but they may not contain enough context to answer a question.

Large chunks provide more context, but their embeddings may represent too many different topics.

Parent-document retrieval combines both.

### Example

Original document:

```text
FastAPI is a Python framework for building APIs.

It supports asynchronous programming.

It provides automatic API documentation.

It validates request data using Python type hints.

It can be used to build scalable backend services.
```

Split into smaller child chunks:

```text
Child 1:
FastAPI is a Python framework for building APIs.

Child 2:
It supports asynchronous programming.

Child 3:
It provides automatic API documentation.

Child 4:
It validates request data using Python type hints.
```

Search finds Child 3.

Instead of returning only Child 3, the retriever returns the larger parent document.

## Why do we need it?

- Small chunks improve search precision.
- Parent documents preserve surrounding context.
- Larger context can improve answer quality.
- You avoid embedding unnecessarily large text blocks.

## How does it work?

```text
             Parent Document
                    |
                    v
             Split into Chunks
                    |
          +---------+---------+
          |         |         |
          v         v         v
       Child 1   Child 2   Child 3
          |         |         |
          v         v         v
       Embeddings + Vector Store
                    |
                    v
                User Query
                    |
                    v
             Find Matching Child
                    |
                    v
             Look Up Parent ID
                    |
                    v
             Return Parent Document
```

## Example

```python
from langchain_openai import OpenAIEmbeddings

from langchain_community.vectorstores import FAISS

from langchain_core.documents import Document

from langchain_text_splitters import RecursiveCharacterTextSplitter

from langchain_classic.retrievers import ParentDocumentRetriever

from langchain_classic.storage import InMemoryStore


# Create parent documents

parent_docs = [
    Document(
        page_content="""
        FastAPI is a Python framework for building APIs.
        It supports asynchronous programming.
        It provides automatic API documentation.
        It validates request data using Python type hints.
        """
    )
]


# Create child splitter

child_splitter = RecursiveCharacterTextSplitter(
    chunk_size=100,
    chunk_overlap=20
)


# Create vector store

vectorstore = FAISS(
    OpenAIEmbeddings(
        model="text-embedding-3-small"
    ),
    faiss.IndexFlatL2(1536),
    InMemoryDocstore({}),
    {}
)


# Create parent document store

store = InMemoryStore()


# Create parent retriever

retriever = ParentDocumentRetriever(
    vectorstore=vectorstore,
    docstore=store,
    child_splitter=child_splitter
)


# Index parent documents

retriever.add_documents(parent_docs)


# Search

results = retriever.invoke(
    "What documentation features does FastAPI provide?"
)


for doc in results:
    print(doc.page_content)
```

### Example output

```text
FastAPI is a Python framework for building APIs.
It supports asynchronous programming.
It provides automatic API documentation.
It validates request data using Python type hints.
```

The returned result is the parent document, not just the matching child chunk.

**Note:** This example uses an in-memory parent store and FAISS. In production, use a persistent document store and vector database. The FAISS index dimension must match the embedding model dimension; `text-embedding-3-small` defaults to 1,536 dimensions.

**When to use:** When small chunks find the right information but the LLM needs more surrounding context.

# 6. Multi-vector retrieval

## What is multi-vector retrieval?

Multi-vector retrieval means creating multiple searchable embeddings for one original document.

A single document can have several representations.

For example:

Original document:

```text
FastAPI is a Python framework for building APIs.
It supports asynchronous programming and validation.
```

Possible vectors:

```text
Vector 1: Original document text

Vector 2: Summary of the document

Vector 3: Question:
         "What is FastAPI used for?"

Vector 4: Question:
         "Does FastAPI support async programming?"
```

All these vectors can point back to the same original document.

## Why do we need it?

Users may ask questions in a way that does not resemble the document's wording.

Hypothetical questions and summaries can provide additional search paths.

## How does it work?

```text
               Original Document
                       |
          +------------+------------+
          |            |            |
          v            v            v
        Summary    Question 1    Question 2
          |            |            |
          v            v            v
              Multiple Embeddings
                       |
                       v
                 Vector Search
                       |
                       v
                Parent Document ID
                       |
                       v
               Retrieve Original
```

## Example: Create question-based vectors

```python
from langchain_openai import ChatOpenAI, OpenAIEmbeddings

from langchain_core.prompts import ChatPromptTemplate

from langchain_core.output_parsers import StrOutputParser

from langchain_core.documents import Document

from langchain_community.vectorstores import FAISS

from langchain_classic.retrievers.multi_vector import (
    MultiVectorRetriever
)

from langchain_classic.storage import InMemoryStore

import uuid


llm = ChatOpenAI(
    model="gpt-4.1-mini",
    temperature=0
)


parent_doc = Document(
    page_content="""
    FastAPI is a Python framework for building APIs.
    It supports asynchronous programming,
    automatic documentation, and validation.
    """
)


# Generate hypothetical questions

question_prompt = ChatPromptTemplate.from_template(
    """
    Generate three questions that this document
    could answer.

    Return one question per line.

    Document:
    {document}
    """
)


question_chain = (
    question_prompt
    | llm
    | StrOutputParser()
)


generated_questions = question_chain.invoke({
    "document": parent_doc.page_content
})


questions = [
    q.strip("- ").strip()
    for q in generated_questions.splitlines()
    if q.strip()
]


# Create child documents

doc_id = str(uuid.uuid4())

child_docs = [
    Document(
        page_content=question,
        metadata={"doc_id": doc_id}
    )
    for question in questions
]


# Create vector store

vectorstore = FAISS.from_documents(
    child_docs,
    OpenAIEmbeddings(
        model="text-embedding-3-small"
    )
)


# Store original document

docstore = InMemoryStore()

docstore.mset([
    (doc_id, parent_doc)
])


# Create multi-vector retriever

retriever = MultiVectorRetriever(
    vectorstore=vectorstore,
    docstore=docstore,
    id_key="doc_id"
)


# Retrieve parent document

results = retriever.invoke(
    "Can FastAPI automatically document an API?"
)


for doc in results:
    print(doc.page_content)
```

### Illustrative output

```text
FastAPI is a Python framework for building APIs.
It supports asynchronous programming,
automatic documentation, and validation.
```

The generated questions can vary.

### Parent-document vs multi-vector retrieval

| Parent-document retrieval | Multi-vector retrieval |
|---|---|
| Commonly indexes small child chunks | Can index chunks, summaries, or hypothetical questions |
| Returns parent documents | Returns associated parent documents |
| Focuses on chunk-level search with parent context | Focuses on multiple representations of a document |
| Useful for preserving surrounding context | Useful for matching different query formulations |

**When to use:** When users ask varied questions about the same documents and ordinary chunk embeddings miss relevant content.

# 7. Hybrid search

## What is hybrid search?

Hybrid search combines two search approaches:

1. Semantic search using embeddings.
2. Keyword search using exact words or terms.

### Example

User asks:

```text
What does HTTP 429 mean?
```

A semantic search may find documents about API rate limiting.

A keyword search may find an exact occurrence of `HTTP 429`.

Combining both can produce better results.

## Why do we need it?

Semantic search is useful for meaning, but it can sometimes miss:

- Product codes.
- Error codes.
- Exact names.
- Technical identifiers.
- Rare keywords.

Keyword search is useful for exact terms, but it may miss semantically similar wording.

Hybrid search combines their strengths.

## How does it work?

```text
                User Query
                     |
            +--------+--------+
            |                 |
            v                 v
       Semantic Search   Keyword Search
            |                 |
            v                 v
       Vector Results     BM25 Results
            |                 |
            +--------+--------+
                     |
                     v
               Merge Results
                     |
                     v
                Final Results
```

## Example using OpenAI embeddings and BM25

```python
from langchain_community.vectorstores import FAISS

from langchain_community.retrievers import BM25Retriever

from langchain_classic.retrievers import EnsembleRetriever

from langchain_openai import OpenAIEmbeddings

from langchain_core.documents import Document


docs = [
    Document(page_content="HTTP 429 means too many requests."),
    Document(page_content="HTTP 404 means the resource was not found."),
    Document(page_content="FastAPI is a framework for building APIs."),
    Document(page_content="Rate limiting controls API request frequency.")
]


# Semantic retriever

vectorstore = FAISS.from_documents(
    docs,
    OpenAIEmbeddings(
        model="text-embedding-3-small"
    )
)

semantic_retriever = vectorstore.as_retriever(
    search_kwargs={"k": 3}
)


# Keyword retriever

bm25_retriever = BM25Retriever.from_documents(
    docs
)

bm25_retriever.k = 3


# Combine both

hybrid_retriever = EnsembleRetriever(
    retrievers=[
        semantic_retriever,
        bm25_retriever
    ],
    weights=[0.5, 0.5]
)


# Search

results = hybrid_retriever.invoke(
    "What does HTTP 429 mean?"
)


for doc in results:
    print(doc.page_content)
```

### Example output

```text
HTTP 429 means too many requests.
Rate limiting controls API request frequency.
HTTP 404 means the resource was not found.
```

The exact ranking depends on the retrieval results and ensemble configuration.

### Important parameters

| Parameter | Purpose |
|---|---|
| `retrievers` | List of retrievers to combine |
| `weights` | Relative contribution of each retriever |
| `k` | Number of results returned by a retriever |
| `c` | Rank-fusion parameter in implementations that use reciprocal rank fusion |

**When to use:** Technical documentation, product catalogues, code search, and datasets containing exact identifiers.

# 8. BM25 retrieval

## What is BM25?

BM25 stands for Best Matching 25.

It is a keyword-based information retrieval algorithm.

It scores documents according to how well their terms match a search query.

It considers factors such as:

- Term frequency: How often a query term occurs in a document.
- Inverse document frequency: How rare or informative a term is across documents.
- Document length: Longer documents are normalized so that they do not automatically dominate.

## Why do we need BM25?

Embeddings are not always ideal for exact keyword matching.

For example:

```text
Query: GPT-4.1
```

You may want documents containing that exact model identifier rather than documents that merely discuss language models.

BM25 is useful for this type of search.

## How does it work?

```text
Query
  |
  v
Tokenize Query
  |
  v
Find Matching Terms
  |
  v
Calculate BM25 Scores
  |
  v
Rank Documents
  |
  v
Return Top Results
```

## Example

```python
from langchain_community.retrievers import BM25Retriever

from langchain_core.documents import Document


docs = [
    Document(
        page_content="GPT-4.1 is an OpenAI model."
    ),
    Document(
        page_content="GPT-4.1-mini is a smaller model."
    ),
    Document(
        page_content="OpenAI provides text embedding models."
    ),
    Document(
        page_content="FastAPI is a Python API framework."
    )
]


retriever = BM25Retriever.from_documents(
    docs
)

retriever.k = 2


results = retriever.invoke(
    "GPT-4.1"
)


for doc in results:
    print(doc.page_content)
```

### Example output

```text
GPT-4.1 is an OpenAI model.
GPT-4.1-mini is a smaller model.
```

### BM25 vs semantic search

| BM25 | Semantic search |
|---|---|
| Keyword-based | Meaning-based |
| Excellent for exact terms | Excellent for related concepts |
| Does not require embeddings | Requires embeddings |
| Can miss synonyms | Can miss exact identifiers |
| Often fast and inexpensive | Requires embedding computation |

**When to use:** Exact technical terms, model names, error codes, product identifiers, and keyword-heavy documents.

# 9. Reranking

## What is reranking?

Reranking means taking an initial list of retrieved documents and sorting them again according to their relevance to the user's question.

A normal vector search might retrieve 10 documents.

A reranker examines the question and those documents more carefully, then selects the most relevant ones.

### Example

Question:

```text
What are FastAPI's validation features?
```

Initial retrieval:

```text
1. Python is used for data science.
2. FastAPI supports request validation.
3. LangChain provides prompt templates.
4. FastAPI generates API documentation.
5. Python supports asynchronous programming.
```

After reranking:

```text
1. FastAPI supports request validation.
2. FastAPI generates API documentation.
3. Python supports asynchronous programming.
```

## Why do we need it?

Embedding similarity is a useful first-stage ranking method, but it is not always a perfect measure of relevance.

Reranking improves precision by evaluating the query and candidate documents together.

## How does it work?

```text
             User Query
                 |
                 v
          Initial Retriever
                 |
                 v
         Retrieve Top 20
                 |
                 v
             Reranker
                 |
                 v
          Rank by Relevance
                 |
                 v
          Keep Top 5 Documents
                 |
                 v
                LLM
```

## Example using OpenAI as the reranker

This example asks an OpenAI model to score candidate documents.

```python
from langchain_openai import ChatOpenAI

from langchain_core.prompts import ChatPromptTemplate

from langchain_core.output_parsers import StrOutputParser


llm = ChatOpenAI(
    model="gpt-4.1-mini",
    temperature=0
)


rerank_prompt = ChatPromptTemplate.from_template(
    """
    Rank the document from 0 to 100 based on
    how relevant it is to the question.

    Return only an integer.

    Question:
    {question}

    Document:
    {document}
    """
)


rerank_chain = (
    rerank_prompt
    | llm
    | StrOutputParser()
)


def rerank_documents(question, docs):

    scored_docs = []

    for doc in docs:

        score_text = rerank_chain.invoke({
            "question": question,
            "document": doc.page_content
        })

        try:
            score = int(score_text.strip())
        except ValueError:
            score = 0

        scored_docs.append((score, doc))

    scored_docs.sort(
        key=lambda item: item[0],
        reverse=True
    )

    return scored_docs


question = "What are FastAPI's validation features?"

candidate_docs = base_retriever.invoke(
    question
)

ranked = rerank_documents(
    question,
    candidate_docs
)


for score, doc in ranked:
    print("Score:", score)
    print(doc.page_content)
    print()
```

### Illustrative output

```text
Score: 95
FastAPI is a Python framework for building APIs.
It supports asynchronous programming,
automatic API documentation, and validation.

Score: 45
Python is a popular programming language.
It is used for web development, automation,
data science, and artificial intelligence.
```

Scores and ordering will vary.

### Important production note

The example calls the model once per candidate document, which can be expensive and slow.

For production:

- Limit the candidate set.
- Batch scoring where practical.
- Use structured output for predictable scores.
- Evaluate the reranker on real questions.
- Consider a dedicated cross-encoder if non-OpenAI models are allowed.

**When to use:** When retrieval finds generally relevant documents but the most relevant documents are not consistently ranked first.

# 10. Metadata filtering

## What is metadata filtering?

Metadata filtering means searching documents using additional structured fields.

For example, each document can have metadata such as:

```python
{
    "category": "API",
    "year": 2025,
    "author": "John"
}
```

You can search only documents that match certain conditions.

### Example

User asks:

```text
Find API documentation published in 2025.
```

You want:

```text
category = API
year = 2025
```

## Why do we need it?

Metadata filtering helps:

- Restrict search to a particular category.
- Search by date.
- Separate departments or tenants.
- Filter by author.
- Restrict access to authorized documents.
- Improve retrieval precision.

## Example using FAISS metadata filters

```python
from langchain_openai import OpenAIEmbeddings

from langchain_community.vectorstores import FAISS

from langchain_core.documents import Document


docs = [
    Document(
        page_content="FastAPI supports request validation.",
        metadata={
            "category": "API",
            "year": 2025
        }
    ),

    Document(
        page_content="Python is used for data science.",
        metadata={
            "category": "Programming",
            "year": 2024
        }
    ),

    Document(
        page_content="LangChain provides RAG components.",
        metadata={
            "category": "AI",
            "year": 2025
        }
    )
]


vectorstore = FAISS.from_documents(
    docs,
    OpenAIEmbeddings(
        model="text-embedding-3-small"
    )
)


results = vectorstore.similarity_search(
    "framework documentation",
    k=3,
    filter={
        "category": "API",
        "year": 2025
    }
)


for doc in results:
    print(doc.page_content)
    print(doc.metadata)
```

### Example output

```text
FastAPI supports request validation.

{'category': 'API', 'year': 2025}
```

### Important point

Metadata filtering syntax varies by vector database.

For example, FAISS, Chroma, and Pinecone have different filter capabilities and expression formats.

Do not assume that a filter expression supported by one database works unchanged in another.

**When to use:** When the user specifies dates, categories, document types, departments, or other structured constraints.

# 11. Self-query retrieval

## What is self-query retrieval?

Self-query retrieval allows an LLM to translate a natural-language question into:

1. A semantic search query.
2. Structured metadata filters.

### Example

User asks:

```text
Find Python API documents published after 2023.
```

The LLM interprets the question as:

```python
{
    "query": "Python API",
    "filter": {
        "year": {"$gt": 2023}
    }
}
```

The vector store performs semantic search using the query and applies the metadata filter.

## Why do we need it?

Users should not need to understand database filter syntax.

They can ask questions naturally, and the LLM translates their request into a structured search.

## How does it work?

```text
          Natural Language Question
                     |
                     v
                  OpenAI
                     |
          +----------+----------+
          |                     |
          v                     v
    Search Query          Metadata Filter
          |                     |
          +----------+----------+
                     |
                     v
                Vector Store
                     |
                     v
             Filtered Documents
```

## Example using SelfQueryRetriever

The following uses the classic LangChain retriever abstraction.

```python
from langchain_openai import (
    ChatOpenAI,
    OpenAIEmbeddings
)

from langchain_community.vectorstores import FAISS

from langchain_core.documents import Document

from langchain_classic.retrievers.self_query.base import (
    SelfQueryRetriever
)

from langchain_classic.chains.query_constructor.base import (
    AttributeInfo
)


docs = [
    Document(
        page_content="FastAPI supports asynchronous APIs.",
        metadata={
            "year": 2025,
            "category": "API"
        }
    ),

    Document(
        page_content="Python is a programming language.",
        metadata={
            "year": 2022,
            "category": "Programming"
        }
    ),

    Document(
        page_content="LangChain supports RAG development.",
        metadata={
            "year": 2024,
            "category": "AI"
        }
    )
]


vectorstore = FAISS.from_documents(
    docs,
    OpenAIEmbeddings(
        model="text-embedding-3-small"
    )
)


metadata_field_info = [
    AttributeInfo(
        name="year",
        description="Publication year",
        type="integer"
    ),

    AttributeInfo(
        name="category",
        description="Document category",
        type="string"
    )
]


document_content_description = (
    "Technical documentation about software "
    "development and AI."
)


retriever = SelfQueryRetriever.from_llm(
    llm=ChatOpenAI(
        model="gpt-4.1-mini",
        temperature=0
    ),
    vectorstore=vectorstore,
    document_contents=document_content_description,
    metadata_field_info=metadata_field_info,
    enable_limit=True
)


results = retriever.invoke(
    "Find API documents published after 2023."
)


for doc in results:
    print(doc.page_content)
    print(doc.metadata)
```

### Illustrative output

```text
FastAPI supports asynchronous APIs.

{'year': 2025, 'category': 'API'}
```

### Important parameters

| Parameter | Purpose |
|---|---|
| `llm` | Model that interprets the natural-language query |
| `vectorstore` | Database used for semantic search |
| `document_contents` | Description of the indexed documents |
| `metadata_field_info` | Available metadata fields and their descriptions |
| `enable_limit` | Allows the query constructor to generate result limits |

### Important limitation

Not all vector stores support every generated filter operation.

Self-query retrieval also does not replace authorization checks. Always enforce access restrictions in your backend.

**When to use:** When users ask questions involving natural-language filters such as "after 2023", "from the finance department", or "only PDF documents".

# 12. Corrective RAG (CRAG)

## What is Corrective RAG?

Corrective RAG stands for Corrective Retrieval-Augmented Generation.

It adds an evaluation step after retrieval.

The system checks whether the retrieved documents are relevant enough to answer the question.

If the documents are poor, it can take corrective action.

Possible actions include:

- Rewrite the query.
- Retrieve again.
- Search another approved source.
- Use a different retrieval strategy.
- Refuse to answer if reliable evidence is unavailable.

## Why do we need it?

Basic RAG assumes that the retrieved documents are useful.

But retrieval can return:

- Irrelevant documents.
- Incomplete information.
- Outdated information.
- Documents that do not answer the question.

Corrective RAG reduces the risk of blindly trusting poor retrieval results.

## How does it work?

```text
           User Question
                 |
                 v
             Retriever
                 |
                 v
          Retrieved Documents
                 |
                 v
          Relevance Evaluator
                 |
          +------+------+
          |             |
          v             v
       Relevant      Irrelevant
          |             |
          v             v
       Generate     Rewrite Query
        Answer           |
                         v
                     Retrieve Again
                         |
                         v
                   Evaluate Again
```

## Example using OpenAI

We can implement a simple corrective RAG workflow using an OpenAI relevance evaluator.

```python
from langchain_openai import ChatOpenAI

from langchain_core.prompts import ChatPromptTemplate

from langchain_core.output_parsers import StrOutputParser


llm = ChatOpenAI(
    model="gpt-4.1-mini",
    temperature=0
)


# Step 1: Evaluate document relevance

grader_prompt = ChatPromptTemplate.from_template(
    """
    Decide whether the document contains information
    useful for answering the question.

    Return only:
    relevant
    or
    irrelevant

    Question:
    {question}

    Document:
    {document}
    """
)


grader_chain = (
    grader_prompt
    | llm
    | StrOutputParser()
)


def grade_documents(question, docs):

    relevant_docs = []

    for doc in docs:

        grade = grader_chain.invoke({
            "question": question,
            "document": doc.page_content
        })

        if "relevant" in grade.lower() and \
           "irrelevant" not in grade.lower():

            relevant_docs.append(doc)

    return relevant_docs


# Step 2: Retrieve initial documents

question = "What features does FastAPI provide?"

initial_docs = base_retriever.invoke(question)


# Step 3: Grade retrieved documents

relevant_docs = grade_documents(
    question,
    initial_docs
)


# Step 4: Corrective action

if not relevant_docs:

    rewritten_query = rewrite_chain.invoke({
        "history": "",
        "question": question
    })

    relevant_docs = base_retriever.invoke(
        rewritten_query
    )


# Step 5: Display relevant documents

for doc in relevant_docs:
    print(doc.page_content)
```

### Example output

```text
FastAPI is a Python framework for building APIs.
It supports asynchronous programming,
automatic API documentation, and validation.
```

This is a simplified corrective workflow. A production CRAG system should use structured evaluator outputs, explicit confidence thresholds, bounded retries, and a defined fallback policy.

**Important:** Searching the public web is not automatically the right fallback. Only use additional sources that your application has explicitly approved.

**When to use:** When retrieval quality is variable and incorrect evidence could lead to incorrect answers.

# 13. Adaptive RAG

## What is Adaptive RAG?

Adaptive RAG means choosing the retrieval strategy based on the user's question.

Not every question requires the same retrieval process.

For example:

```text
Question 1:
What is Python?

Strategy:
Simple retrieval.

Question 2:
Compare Python and Java for backend development.

Strategy:
Retrieve multiple documents.

Question 3:
What are the latest changes to FastAPI?

Strategy:
Use an approved up-to-date source if available.
```

## Why do we need it?

Using the same retrieval strategy for every question can be inefficient.

Some questions are simple.

Others require:

- Multiple queries.
- Query rewriting.
- Hybrid search.
- Reranking.
- External search.
- No retrieval at all.

Adaptive RAG chooses a strategy based on the query.

## How does it work?

```text
             User Question
                   |
                   v
             Query Classifier
                   |
       +-----------+-----------+
       |           |           |
       v           v           v
     Simple     Complex      Current
       |           |           |
       v           v           v
   Basic RAG   Multi-query   Approved
               + Reranking   Search
       |           |           |
       +-----------+-----------+
                   |
                   v
               LLM Answer
```

## Example using OpenAI

```python
from langchain_openai import ChatOpenAI

from langchain_core.prompts import ChatPromptTemplate

from langchain_core.output_parsers import StrOutputParser


llm = ChatOpenAI(
    model="gpt-4.1-mini",
    temperature=0
)


classifier_prompt = ChatPromptTemplate.from_template(
    """
    Classify the question into exactly one category:

    simple
    complex
    current

    simple:
    A straightforward question.

    complex:
    Requires multiple pieces of information
    or comparison across documents.

    current:
    Requires up-to-date information.

    Question:
    {question}

    Return only the category.
    """
)


classifier = (
    classifier_prompt
    | llm
    | StrOutputParser()
)


def adaptive_retrieve(question):

    category = classifier.invoke({
        "question": question
    }).strip().lower()

    if category == "simple":

        return base_retriever.invoke(question)

    elif category == "complex":

        return multi_query_retriever.invoke(question)

    elif category == "current":

        # Do not pretend that a static vector database
        # contains current information.
        return []

    else:

        return base_retriever.invoke(question)


question = "Compare the main features of FastAPI and LangChain."

results = adaptive_retrieve(question)

for doc in results:
    print(doc.page_content)
```

### Example output

```text
FastAPI is a Python framework for building APIs.
It supports asynchronous programming,
automatic API documentation, and validation.

LangChain is a framework for developing
applications powered by language models.
It provides prompts, models, retrievers,
tools, and document-processing components.
```

The classifier's choice can vary.

### Important point

The `current` branch above intentionally does not search the static vector store.

For a real application, connect that branch to a current and approved information source, or tell the user that the available knowledge base does not contain current information.

**When to use:** When you need to balance retrieval quality, response time, and cost across different question types.

# 14. Graph-based RAG

## What is Graph-based RAG?

Graph-based RAG uses relationships between entities to retrieve information.

Traditional RAG stores text chunks and their embeddings.

Graph RAG stores entities and relationships in a graph structure.

### Example

Suppose your knowledge base contains:

```text
FastAPI is written in Python.

FastAPI is used for building APIs.

LangChain is used for building LLM applications.

LangChain integrates with OpenAI.
```

A knowledge graph might look like:

```text
Python
  |
  | used by
  v
FastAPI
  |
  | builds
  v
APIs


LangChain
  |
  | integrates with
  v
OpenAI
```

## Why do we need Graph RAG?

Vector search is good at finding semantically similar text.

But some questions require relationships between multiple entities.

For example:

```text
Which framework uses Python to build APIs?
```

Or:

```text
Which framework integrates with OpenAI
to build LLM applications?
```

Graph-based retrieval can traverse relationships to find connected facts.

## How does it work?

```text
             Source Documents
                    |
                    v
          OpenAI Entity Extraction
                    |
                    v
           Extract Entities
                    |
                    v
         Extract Relationships
                    |
                    v
             Knowledge Graph
                    |
                    v
              User Question
                    |
                    v
          Identify Graph Entities
                    |
                    v
          Traverse Relationships
                    |
                    v
           Retrieve Graph Facts
                    |
                    v
                 OpenAI
                    |
                    v
              Final Answer
```

## Example using OpenAI and NetworkX

This is a small educational graph-RAG example.

Install:

```bash
pip install networkx
```

### Step 1: Extract entities and relationships

```python
from langchain_openai import ChatOpenAI

from langchain_core.prompts import ChatPromptTemplate

from pydantic import BaseModel, Field


class Relationship(BaseModel):

    source: str = Field(
        description="Starting entity"
    )

    relation: str = Field(
        description="Relationship between entities"
    )

    target: str = Field(
        description="Ending entity"
    )


class ExtractedKnowledge(BaseModel):

    relationships: list[Relationship]


llm = ChatOpenAI(
    model="gpt-4.1-mini",
    temperature=0
)


extractor = llm.with_structured_output(
    ExtractedKnowledge
)


text = """
FastAPI is written in Python.
FastAPI is used for building APIs.
LangChain is used for building LLM applications.
LangChain integrates with OpenAI.
"""


knowledge = extractor.invoke(
    f"Extract factual relationships from this text:\n{text}"
)


for relationship in knowledge.relationships:

    print(
        relationship.source,
        relationship.relation,
        relationship.target
    )
```

### Illustrative output

```text
FastAPI uses Python
FastAPI builds APIs
LangChain builds LLM applications
LangChain integrates with OpenAI
```

The exact extracted relationships can vary.

### Step 2: Build a knowledge graph

```python
import networkx as nx

graph = nx.DiGraph()


for relationship in knowledge.relationships:

    graph.add_edge(
        relationship.source,
        relationship.target,
        relation=relationship.relation
    )


print("Nodes:", list(graph.nodes))

print("Edges:", list(graph.edges(data=True)))
```

### Illustrative output

```text
Nodes:
['FastAPI', 'Python', 'APIs',
 'LangChain', 'LLM applications', 'OpenAI']

Edges:
[
 ('FastAPI', 'Python', {'relation': 'uses'}),
 ('FastAPI', 'APIs', {'relation': 'builds'}),
 ('LangChain', 'LLM applications', {'relation': 'builds'}),
 ('LangChain', 'OpenAI', {'relation': 'integrates with'})
]
```

### Step 3: Retrieve connected graph information

```python
def graph_search(entity):

    if entity not in graph:
        return []

    results = []

    for source, target, data in graph.out_edges(
        entity,
        data=True
    ):

        results.append(
            f"{source} {data['relation']} {target}"
        )

    return results


facts = graph_search("FastAPI")

for fact in facts:
    print(fact)
```

**Output:**

```text
FastAPI uses Python
FastAPI builds APIs
```

### Step 4: Use retrieved graph facts to answer

```python
from langchain_core.prompts import ChatPromptTemplate

from langchain_core.output_parsers import StrOutputParser


answer_prompt = ChatPromptTemplate.from_template(
    """
    Answer the question using only the graph facts.

    If the facts do not contain the answer,
    say that the information is unavailable.

    Facts:
    {facts}

    Question:
    {question}
    """
)


answer_chain = (
    answer_prompt
    | llm
    | StrOutputParser()
)


answer = answer_chain.invoke({
    "facts": "\n".join(facts),
    "question": "Which language does FastAPI use?"
})


print(answer)
```

**Illustrative output:**

```text
FastAPI uses Python.
```

### Important limitation

This is a small knowledge-graph demonstration, not a complete production Graph RAG system.

A production system needs:

- Entity resolution.
- Duplicate entity handling.
- Relationship validation.
- Provenance and source references.
- Graph persistence.
- Multi-hop traversal.
- Access controls.
- A strategy for updating and removing graph facts.

Graph RAG can also combine graph retrieval with vector retrieval. This is often useful because not every relevant fact is represented as an explicit relationship.

**When to use:** When questions require relationships, multi-hop reasoning, entity connections, or understanding how different parts of a knowledge base are related.

# 15. How all advanced RAG techniques fit together

You do not need to use all these techniques in every application.

A mature RAG system might look like this:

```text
                     User Question
                           |
                           v
                    Query Rewriting
                           |
                           v
                    Query Classification
                           |
             +-------------+-------------+
             |             |             |
             v             v             v
         Multi-query   Self-query    Simple query
             |             |             |
             v             v             v
         Hybrid Search + Metadata Filters
                           |
                           v
                    Initial Retrieval
                           |
                           v
                     Parent Lookup
                           |
                           v
                       Reranking
                           |
                           v
                 Contextual Compression
                           |
                           v
                  Relevance Evaluation
                           |
                  +--------+--------+
                  |                 |
                  v                 v
               Relevant         Not relevant
                  |                 |
                  v                 v
              Generate          Corrective
               Answer           Retrieval
                  |                 |
                  +--------+--------+
                           |
                           v
                      Final Answer
                           |
                           v
                  Source References
```

Graph retrieval can be added as another retrieval source when relationships between entities are important.

Adaptive RAG can choose which parts of this pipeline to execute.

# 16. Which advanced RAG technique should you use?

| Problem | Technique to consider |
|---|---|
| One question retrieves incomplete results | Multi-query retrieval |
| Follow-up question is ambiguous | Query rewriting |
| Retrieved documents contain too much irrelevant text | Contextual compression |
| Small chunks lack surrounding context | Parent-document retrieval |
| One document needs several searchable representations | Multi-vector retrieval |
| Exact keywords and semantic meaning both matter | Hybrid search |
| Exact terms, IDs, and codes matter | BM25 |
| Relevant documents are not ranked correctly | Reranking |
| Search must obey dates, categories, or departments | Metadata filtering |
| Users express filters in natural language | Self-query retrieval |
| Retrieved documents may be irrelevant | Corrective RAG |
| Different questions need different retrieval strategies | Adaptive RAG |
| Questions involve entity relationships and multiple hops | Graph-based RAG |

# 17. Recommended learning order

Learn these techniques in the following order:

1. Query rewriting.
2. Multi-query retrieval.
3. BM25 and hybrid search.
4. Reranking.
5. Metadata filtering.
6. Self-query retrieval.
7. Contextual compression.
8. Parent-document retrieval.
9. Multi-vector retrieval.
10. Corrective RAG.
11. Adaptive RAG.
12. Graph-based RAG.

Why this order?

Start with improving the query and the initial search. Then learn how to improve the quality of retrieved documents. Finally, learn how to make the retrieval process more intelligent and relationship-aware.

# 18. Quick summary

| Topic | One-line explanation |
|---|---|
| Multi-query retrieval | Generate multiple search queries from one question |
| Query rewriting | Convert an unclear question into a better standalone query |
| Contextual compression | Keep only information relevant to the question |
| `ContextualCompressionRetriever` | Wrap a retriever with a document compressor |
| Parent-document retrieval | Search small chunks and return larger parent documents |
| Multi-vector retrieval | Store several searchable vectors for one document |
| Hybrid search | Combine keyword and semantic search |
| BM25 | Rank documents based on keyword matching |
| Reranking | Reorder retrieved documents based on relevance |
| Metadata filtering | Restrict search using structured document fields |
| Self-query retrieval | Convert natural-language filters into structured search conditions |
| Corrective RAG | Evaluate retrieval and retry or correct when results are poor |
| Adaptive RAG | Select retrieval strategies based on the question |
| Graph-based RAG | Retrieve information using entities and relationships |

## Final takeaway

Basic RAG follows:

```text
Question
   |
   v
Retrieve Documents
   |
   v
Send Context to LLM
   |
   v
Generate Answer
```

Advanced RAG improves the process:

```text
Question
   |
   v
Understand and Rewrite Query
   |
   v
Choose Retrieval Strategy
   |
   v
Search Multiple Ways
   |
   v
Filter and Rerank Results
   |
   v
Compress Relevant Context
   |
   v
Evaluate Evidence
   |
   v
Generate Grounded Answer
   |
   v
Return Sources
```

**The most important lesson:** Advanced RAG is not about adding every possible retriever. It is about identifying why your current retrieval system fails and adding the smallest technique that solves that problem.
