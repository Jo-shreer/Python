# SOLID Principles in Python

SOLID is a set of five principles that help us write code that is:

* Easy to understand
* Easy to maintain
* Easy to test
* Easy to extend

```text
S → Single Responsibility Principle
O → Open/Closed Principle
L → Liskov Substitution Principle
I → Interface Segregation Principle
D → Dependency Inversion Principle
```

---

# 1. Single Responsibility Principle (SRP)
> A class should have **one responsibility** or **one reason to change**.

## ❌ Problem
One class is doing three different jobs:

```python
class Employee:
    def calculate_salary(self):
        print("Calculating salary")

    def save_to_database(self):
        print("Saving employee to database")

    def send_email(self):
        print("Sending email")
``
`Employee` is responsible for:

```text
Employee
├── Calculate salary
├── Save to database
└── Send email
```

If the email system changes, we have to modify the `Employee` class.
## ✅ Solution
Separate the responsibilities:

```python
class SalaryCalculator:
    def calculate_salary(self):
        print("Calculating salary")


class EmployeeRepository:
    def save(self):
        print("Saving employee to database")


class EmailService:
    def send_email(self):
        print("Sending email")
```
Now:

```text
SalaryCalculator   → Salary
EmployeeRepository → Database
EmailService       → Email
```

Each class has one main responsibility.
### Remember
**SRP = One class → One main job**

# 2. Open/Closed Principle (OCP)
> A class should be **open for extension but closed for modification**.
In simple words:
> We should be able to add new functionality without constantly modifying existing code.
## ❌ Problem
```python
class Payment:
    def pay(self, payment_type):
        if payment_type == "card":
            print("Paying by card")

        elif payment_type == "paypal":
            print("Paying by PayPal")
```
Now suppose we want to add Apple Pay:

```python
elif payment_type == "apple_pay":
    print("Paying by Apple Pay")
```

Then another payment method:
```python
elif payment_type == "bank":
    ...
```

The same class keeps getting modified.
## ✅ Solution
Create separate classes:

```python
class CardPayment:
    def pay(self):
        print("Paying by card")

class PayPalPayment:
    def pay(self):
        print("Paying by PayPal")

class ApplePayPayment:
    def pay(self):
        print("Paying by Apple Pay")
```
Now adding another payment method means adding another class:
```python
class BankPayment:
    def pay(self):
        print("Paying by bank")
```
We extended the system without modifying the existing payment classes.
### Remember
**OCP = Extend functionality instead of constantly modifying existing code.**

# 3. Liskov Substitution Principle (LSP)
> A child class should be usable wherever its parent class is expected **without breaking the program**.
Simple way to remember:
> **Child should be able to replace Parent without causing problems.**

## ❌ Problem
Suppose we create a `Bird` class:
```python
class Bird:
    def fly(self):
        print("Flying")
```

Then we create `Penguin` as a child:
```python
class Penguin(Bird):
    def fly(self):
        raise Exception("Penguins cannot fly")
```
Now we have a function:
```python
def make_bird_fly(bird):
    bird.fly()
```

And we pass a Penguin:

```python
penguin = Penguin()
make_bird_fly(penguin)
```

This causes an error.
Because `make_bird_fly()` expects a bird that can fly, but `Penguin` cannot fly.

Therefore:
```text
Bird
 ↓
Penguin
```
doesn't behave correctly as a substitute.

## ✅ Solution
Don't put `fly()` in the general `Bird` class.

```python
class Bird:
    pass

class FlyingBird(Bird):
    def fly(self):
        print("Flying")

class Penguin(Bird):
    def swim(self):
        print("Swimming")

def make_bird_fly(bird):
    bird.fly()

sparrow = FlyingBird()
make_bird_fly(sparrow)     # ✅ Flying
penguin = Penguin()
penguin.swim()             # ✅ Swimming
```

Now the design is:
```text
Bird
├── FlyingBird
│      └── fly()
│
└── Penguin
       └── swim()
```
We don't force `Penguin` to have a `fly()` method.
**LSP = Child should be able to replace Parent without breaking expected behavior.**

# 4. Interface Segregation Principle (ISP)
> A class should not be forced to implement methods that it doesn't need.
Python doesn't have traditional interfaces like some languages, but the principle still applies when designing classes, abstract classes, or protocols.

## ❌ Problem
Suppose we have:

```python
class Worker:
    def work(self):
        print("Working")

    def eat(self):
        print("Eating")
```
A human worker can work and eat:

```python
class Human(Worker):
    pass
```
But now suppose we create a robot:

```python
class Robot(Worker):
    def eat(self):
        raise Exception("Robot doesn't eat")
```
The robot is being forced to implement something it doesn't need.
## ✅ Solution

Separate the responsibilities:
```python
class Workable:
    def work(self):
        print("Working")

class Eatable:
    def eat(self):
        print("Eating")

class Human(Workable, Eatable):
    pass

class Robot(Workable):
    pass
```
Now:
```python
human = Human()
human.work()
human.eat()
robot = Robot()
robot.work()
```
The robot only has the behavior it needs.
```text
Workable
├── Human
└── Robot

Eatable
└── Human
```
**ISP = Don't force a class to implement things it doesn't need.**

# 5. Dependency Inversion Principle (DIP)
## Meaning
> High-level code should not depend directly on low-level implementations.

Instead:
> **Depend on abstractions and inject the dependency.**

## ❌ Problem
```python
class MySQLDatabase:
    def save(self, data):
        print("Saving to MySQL")


class UserService:
    def __init__(self):
        self.database = MySQLDatabase()

    def save_user(self, user):
        self.database.save(user)
```

The problem is:
```text
UserService
     ↓
MySQLDatabase
```

`UserService` is tightly connected to MySQL.

If we want PostgreSQL, we have to change `UserService`.

## ✅ Solution
Pass the database from outside:

```python
class MySQLDatabase:
    def save(self, data):
        print("Saving to MySQL")


class PostgreSQLDatabase:
    def save(self, data):
        print("Saving to PostgreSQL")


class UserService:
    def __init__(self, database):
        self.database = database

    def save_user(self, user):
        self.database.save(user)
```

Now we can choose which database to use:

```python
mysql = MySQLDatabase()
service = UserService(mysql)
service.save_user("John")
```

Or:
```python
postgres = PostgreSQLDatabase()
service = UserService(postgres)
service.save_user("John")
```

`UserService` doesn't care whether the database is MySQL or PostgreSQL.
It only cares that the object provides:

```python
database.save()
```
This is an example of **dependency injection**.
```text
                 UserService
                      ↓
              database dependency
                 ↙          ↘
             MySQL       PostgreSQL
```
**DIP = Don't tightly couple high-level code to a specific implementation.**

# SOLID Quick Revision
```text
S → Single Responsibility
    One class → One main job
O → Open/Closed
    Extend functionality → Don't constantly modify existing code
L → Liskov Substitution
    Child → Should replace Parent without breaking things
I → Interface Segregation
    Don't force classes to implement unnecessary methods
D → Dependency Inversion
    Depend on abstractions, not specific implementations
```
# Easy way to remember
```text
S → One job
O → Extend
L → Replace safely
I → Keep it small
D → Don't tightly couple
```
# Interview Definitions
### SRP
> A class should have one responsibility and one reason to change.
### OCP
> Software should be open for extension but closed for modification.
### LSP
> Subclasses should be replaceable for their base classes without breaking expected behavior.
### ISP
> Classes should not be forced to depend on methods they don't use.
### DIP
> High-level modules should depend on abstractions rather than concrete implementations.
