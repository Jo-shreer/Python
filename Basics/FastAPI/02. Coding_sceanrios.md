# Python REST API Interview Revision Guide

## 1. GET — Retrieve All Users

### Before
```python
@app.get("/users")
def get_users():
    result = []

    for user in users:
        result.append({
            "id": user["id"],
            "name": user["name"],
            "email": user["email"]
        })

    return result
```

### After
```python
from pydantic import BaseModel, EmailStr

class UserResponse(BaseModel):
    id: int
    name: str
    email: EmailStr

@app.get("/users", response_model=list[UserResponse])
def get_users():
    return users
```

### Why is the after version better?

- A list comprehension or returning validated data is cleaner than manually building a list.
- `response_model` defines the expected response structure.
- It helps prevent accidentally returning internal fields.
- FastAPI automatically serializes Python dictionaries and lists into JSON.
- A collection of users should normally be returned as a JSON array.

### Interview questions

**Q1. What is the difference between a list and a dictionary?**

- A list stores ordered items and is accessed by index.
- A dictionary stores key-value pairs and is accessed by key.
- A dictionary lookup is O(1) on average.
- Searching through a list is O(n).

**Q2. Why use a response model?**

To validate and control the response structure, document the API schema, and avoid exposing unwanted fields.

**Q3. What is the time complexity of retrieving all users?**

O(n), because every user must be processed.

## 2. GET — Retrieve a User by ID

### Before
```python
@app.get("/users/{user_id}")
def get_user(user_id: int):
    for user in users:
        if user["id"] == user_id:
            return user

    return {"message": "User not found"}
```

### After
Assume `users` is a dictionary indexed by user ID.

```python
from fastapi import HTTPException

@app.get("/users/{user_id}")
def get_user(user_id: int):
    user = users.get(user_id)

    if user is None:
        raise HTTPException(
            status_code=404,
            detail="User not found"
        )

    return user
```

### Why is the after version better?

- A list requires searching through records.
- A dictionary allows direct lookup by ID.
- Dictionary lookup is O(1) on average.
- `dict.get()` returns `None` when a key is missing.
- HTTP 404 is more appropriate than returning a normal successful response containing an error message.

### Interview questions

**Q1. What is the difference between `users.get(id)` and `users[id]`?**

- `.get()` returns `None` if the key does not exist, unless a default is supplied.
- `users[id]` raises a `KeyError` if the key does not exist.

**Q2. What data structure would you use for fast user lookup?**

A dictionary in an in-memory example, or a database table with an indexed primary key in a real application.

**Q3. Is dictionary lookup always O(1)?**

It is O(1) on average, but worst-case lookup can be O(n).

## 3. PUT — Update an Existing User

### Before
```python
@app.put("/users/{user_id}")
def update_user(user_id: int, name: str, email: str):
    for user in users:
        if user["id"] == user_id:
            user["name"] = name
            user["email"] = email
            return user

    return {"message": "User not found"}
```

### After
```python
from fastapi import HTTPException
from pydantic import BaseModel, EmailStr, Field

class UserUpdate(BaseModel):
    name: str = Field(min_length=2, max_length=50)
    email: EmailStr

@app.put("/users/{user_id}")
def update_user(user_id: int, request: UserUpdate):
    user = users.get(user_id)

    if user is None:
        raise HTTPException(
            status_code=404,
            detail="User not found"
        )

    user["name"] = request.name
    user["email"] = str(request.email)

    return user
```

### Why is the after version better?

- A Pydantic model validates the incoming request body.
- `EmailStr` validates email format.
- `Field` allows constraints such as minimum and maximum length.
- The endpoint has a clear request schema.
- Missing users produce a proper HTTP 404 response.

### Interview questions

**Q1. What is PUT?**

PUT generally replaces the resource representation with the supplied representation.

**Q2. What is the difference between PUT and PATCH?**

- PUT generally updates or replaces the complete resource representation.
- PATCH updates only the fields supplied by the client.

**Q3. What is Pydantic?**

A Python data validation library used by FastAPI to validate, parse, and serialize data.

## 4. PATCH — Partially Update a User

### Before
```python
@app.patch("/users/{user_id}")
def update_user(
    user_id: int,
    name: str = None,
    email: str = None
):
    for user in users:
        if user["id"] == user_id:
            if name:
                user["name"] = name

            if email:
                user["email"] = email

            return user

    return {"message": "User not found"}
```

### After
```python
from pydantic import BaseModel, EmailStr

class UserPatch(BaseModel):
    name: str | None = None
    email: EmailStr | None = None

@app.patch("/users/{user_id}")
def update_user(user_id: int, request: UserPatch):
    user = users.get(user_id)

    if user is None:
        raise HTTPException(
            status_code=404,
            detail="User not found"
        )

    update_data = request.model_dump(exclude_unset=True)
    user.update(update_data)

    return user
```

### Why is the after version better?

- PATCH should update only the fields the client sends.
- `model_dump(exclude_unset=True)` excludes fields the client did not provide.
- `user.update()` applies the supplied fields.
- It avoids writing a separate `if` condition for every field.

### Important: `exclude_unset` vs `exclude_none`

```python
request.model_dump(exclude_unset=True)
```

Excludes fields that were not supplied in the request. An explicitly supplied `null` is retained.

```python
request.model_dump(exclude_none=True)
```

Excludes fields whose value is `None`, including explicitly supplied null values.

Example:

```python
request = UserPatch(name="David", email=None)

request.model_dump(exclude_unset=True)
# {"name": "David", "email": None}
```

### Interview questions

**Q1. Why use `exclude_unset=True` for PATCH?**

Because we want to update only fields supplied by the client.

**Q2. What happens if a client sends an empty request body?**

The update dictionary is empty, so no fields are changed.

**Q3. What if the client sends `email: null`?**

With `exclude_unset=True`, the email field is retained as `None`. The API should explicitly decide whether null is allowed.

## 5. POST — Create a New User

### Before
```python
@app.post("/users")
def create_user(name: str, email: str):
    new_id = len(users) + 1

    new_user = {
        "id": new_id,
        "name": name,
        "email": email
    }

    users[new_id] = new_user

    return new_user
```

### After
```python
from uuid import uuid4
from fastapi import HTTPException
from pydantic import BaseModel, EmailStr, Field

class UserCreate(BaseModel):
    name: str = Field(min_length=2, max_length=50)
    email: EmailStr

existing_email = {
    user["email"] for user in users.values()
}

@app.post("/users", status_code=201)
def create_user(request: UserCreate):
    email = str(request.email)

    if email in existing_email:
        raise HTTPException(
            status_code=409,
            detail="Email already exists"
        )

    new_id = str(uuid4())

    new_user = {
        "id": new_id,
        "name": request.name,
        "email": email
    }

    users[new_id] = new_user
    existing_email.add(email)

    return new_user
```

### Why is the after version better?

- Pydantic validates incoming data.
- UUIDs avoid relying on `len(users) + 1` for ID generation.
- A set makes duplicate email checks efficient.
- Set membership is O(1) on average.
- HTTP 201 indicates that a resource was created.
- HTTP 409 indicates a conflict, such as a duplicate email.

### Important data structures

List comprehension:
```python
names = [user["name"] for user in users.values()]
```

Set comprehension:
```python
emails = {user["email"] for user in users.values()}
```

Dictionary comprehension:
```python
user_emails = {
    user["id"]: user["email"]
    for user in users.values()
}
```

### Production consideration

An in-memory set is only suitable for a demonstration or a small single-process example.

In production, use a database UNIQUE constraint on the email column. This protects against concurrent requests and multiple API instances creating the same email. Catch the database constraint violation and return HTTP 409.

### Interview questions

**Q1. Why use a set for duplicate checking?**

Set membership is O(1) on average, compared with O(n) when scanning a list.

**Q2. Why not use `len(users) + 1` for generating IDs?**

Deleting records can cause collisions, and concurrent requests can generate the same ID. UUIDs or database-generated IDs are safer.

**Q3. Why is HTTP 201 used?**

It indicates that a resource has been successfully created.

**Q4. What is the difference between a list, set, and dictionary?**

- List: ordered collection, allows duplicates.
- Set: unique values, efficient membership checks.
- Dictionary: key-value pairs, efficient key lookup.

## 6. DELETE — Delete a User

### Before
```python
@app.delete("/users/{user_id}")
def delete_user(user_id: int):
    for user in users:
        if user["id"] == user_id:
            users.remove(user)
            return {"message": "User deleted"}

    return {"message": "User not found"}
```

### After
Assume `users` is a dictionary indexed by user ID.

```python
from fastapi import HTTPException, Response

@app.delete("/users/{user_id}", status_code=204)
def delete_user(user_id: int):
    user = users.pop(user_id, None)

    if user is None:
        raise HTTPException(
            status_code=404,
            detail="User not found"
        )

    existing_email.discard(user["email"])

    return Response(status_code=204)
```

### Why is the after version better?

- `pop()` removes the item and returns its previous value.
- It avoids a separate search and deletion operation.
- `discard()` safely removes an email from the set without raising an error if it is absent.
- HTTP 204 means successful deletion with no response body.

### Interview questions

**Q1. What is the difference between `remove()` and `pop()`?**

- List `.remove(value)` removes the first matching value.
- List `.pop(index)` removes and returns an item at an index.
- Dictionary `.pop(key)` removes and returns the value for that key.

**Q2. What does HTTP 204 mean?**

The request succeeded, and there is no response body.

**Q3. Should a DELETE request return 404 if the user does not exist?**

Usually yes, if the API contract requires the resource to exist. Some APIs choose idempotent behavior that returns success even if it is already absent; the contract should be consistent.

**Q4. What else must be updated when deleting a user?**

Related data, caches, search indexes, and any in-memory collections must be considered. Database relationships and cascading rules also matter.

## 7. Path Parameters, Query Parameters, and Request Bodies

### Before
```python
@app.get("/users")
def get_users(page: str = "1"):
    return {"page": page}
```

This does not validate that the page is a positive integer.

### After
```python
from fastapi import Query

@app.get("/users/{user_id}")
def get_user(
    user_id: int,
    page: int = Query(1, ge=1),
    limit: int = Query(20, ge=1, le=100)
):
    return {
        "user_id": user_id,
        "page": page,
        "limit": limit
    }
```

### Difference

- Path parameter: identifies a resource, such as `/users/10`.
- Query parameter: filters or controls a request, such as `/users?page=2`.
- Request body: sends structured data, commonly used for POST, PUT, and PATCH.

### Interview questions

**Q1. When would you use a path parameter?**

When identifying a particular resource.

**Q2. When would you use a query parameter?**

For filtering, pagination, sorting, and optional request controls.

**Q3. Where should create-user data go?**

Usually in the JSON request body, validated using a Pydantic model.

## 8. Pagination, Filtering, and Sorting

### Before
```python
@app.get("/users")
def get_users():
    return users
```

This returns every user, which can become expensive for large datasets.

### After
```python
from fastapi import Query

@app.get("/users")
def get_users(
    page: int = Query(1, ge=1),
    limit: int = Query(20, ge=1, le=100),
    name: str | None = None,
    sort_by: str = "name"
):
    start = (page - 1) * limit
    end = start + limit

    result = users

    if name:
        result = [
            user for user in result
            if name.lower() in user["name"].lower()
        ]

    if sort_by not in {"name", "email"}:
        raise HTTPException(
            status_code=400,
            detail="Invalid sort field"
        )

    result = sorted(
        result,
        key=lambda user: user[sort_by]
    )

    return result[start:end]
```

### Why is the after version better?

- Pagination limits the amount of data returned.
- Filtering reduces unnecessary results.
- Sorting provides predictable ordering.
- Query validation prevents invalid values.

### Interview questions

**Q1. What is offset pagination?**

It uses a page number and limit to calculate which records to return.

**Q2. What is cursor pagination?**

It uses a stable cursor, often based on an ID or timestamp, to retrieve the next set of records. It can perform better than large offsets.

**Q3. Should pagination happen in Python or the database?**

For large datasets, pagination, filtering, and sorting should generally happen in the database.

**Q4. What is the risk of allowing arbitrary sort fields?**

It can cause invalid queries or unsafe database query construction. Use an allowlist of permitted fields.

## 9. Authentication and Authorization

### Before
```python
@app.get("/profile")
def get_profile():
    return {"message": "User profile"}
```

Anyone who can reach this endpoint can access it.

### After — Conceptual FastAPI example
```python
from fastapi import Depends, HTTPException
from fastapi.security import HTTPBearer, HTTPAuthorizationCredentials

security = HTTPBearer()

def get_current_user(
    credentials: HTTPAuthorizationCredentials = Depends(security)
):
    token = credentials.credentials

    # Verify signature, expiry, issuer and audience.
    # This is a placeholder, not actual token verification.
    user = verify_token_and_get_user(token)

    if user is None:
        raise HTTPException(
            status_code=401,
            detail="Invalid authentication credentials"
        )

    return user

@app.get("/profile")
def get_profile(current_user=Depends(get_current_user)):
    return current_user
```

### Why is the after version better?

- It introduces an authentication dependency.
- Protected routes require a verified identity.
- Token verification must check the signature and relevant claims.
- Authentication and authorization are separate concerns.

### Interview questions

**Q1. What is authentication?**

Verifying who a user or service is.

**Q2. What is authorization?**

Determining what an authenticated user or service is allowed to do.

**Q3. What is JWT?**

JSON Web Token. It is a compact token format often used to carry signed claims.

**Q4. Should you store passwords in plain text?**

No. Store password hashes produced by an appropriate password-hashing algorithm.

**Q5. What is OAuth2?**

An authorization framework used to grant limited access to resources. It is commonly used alongside token-based authentication.

**Q6. What is the difference between HTTP 401 and 403?**

- 401: authentication is missing or invalid.
- 403: the caller is authenticated but is not allowed to perform the action.

## 10. Error Handling and Exception Handlers

### Before
```python
@app.get("/users/{user_id}")
def get_user(user_id: int):
    return users[user_id]
```

If the user is missing, this can raise a `KeyError` and produce an unintended server error.

### After
```python
from fastapi import HTTPException

@app.get("/users/{user_id}")
def get_user(user_id: int):
```

### Why is the after version better?

- It handles expected errors explicitly.
- It returns the correct HTTP status.
- It avoids leaking internal exception details.
- It gives clients a predictable error response.

### Interview questions

**Q1. What is the difference between 4xx and 5xx errors?**

- 4xx: client-side request or authorization problem.
- 5xx: server-side failure.

**Q2. What is HTTP 422?**

The request content could not be processed because it failed validation. FastAPI commonly uses it for request validation errors.

**Q3. Why should you not return raw exception messages to clients?**

They may expose internal implementation details, database information, or secrets.

**Q4. What is a global exception handler?**

A handler that centralizes how a particular exception type is converted into an API response.

## 11. Database Integration — SQL and SQLAlchemy

### Before
```python
users = {
    1: {"id": 1, "name": "John"}
}

@app.get("/users/{user_id}")
def get_user(user_id: int):
    return users.get(user_id)
```

The data is held in memory and disappears when the application restarts.

### After — SQLAlchemy-style example
```python
from sqlalchemy import select
from fastapi import Depends, HTTPException
from sqlalchemy.orm import Session

@app.get("/users/{user_id}")
def get_user(
    user_id: int,
    db: Session = Depends(get_db)
):
    user = db.scalar(
        select(User).where(User.id == user_id)
    )

    if user is None:
        raise HTTPException(
            status_code=404,
            detail="User not found"
        )

    return user
```

### Why is the after version better?

- Database storage persists after application restarts.
- SQLAlchemy provides an ORM for mapping database tables to Python objects.
- A primary-key lookup can use a database index.
- A database can enforce constraints such as unique email addresses.
- A dependency can manage database sessions.

### Interview questions

**Q1. What is an ORM?**

Object Relational Mapper. It maps database tables and records to Python classes and objects.

**Q2. What is a primary key?**

A column or set of columns that uniquely identifies a row.

**Q3. What is a foreign key?**

A constraint that links a record to a referenced record in another table or the same table.

**Q4. What is a database index?**

A data structure that helps the database find records more efficiently, at the cost of additional storage and write overhead.

**Q5. Why use a database UNIQUE constraint for email?**

It enforces uniqueness at the database level, including when multiple requests arrive concurrently.

**Q6. What is a transaction?**

A group of database operations treated as one logical unit. Transactions help preserve data consistency.

## 12. Async APIs and Concurrency

### Before
```python
import requests

@app.get("/external-data")
def get_external_data():
    response = requests.get(
        "https://api.example.com/data"
    )
    return response.json()
```

This uses synchronous I/O. The request blocks the worker while waiting for the external service.

### After
```python
import httpx
from fastapi import HTTPException

@app.get("/external-data")
async def get_external_data():
    try:
        async with httpx.AsyncClient(timeout=10.0) as client:
            response = await client.get(
                "https://api.example.com/data"
            )
            response.raise_for_status()
            return response.json()

    except httpx.TimeoutException:
        raise HTTPException(
            status_code=504,
            detail="External API timed out"
        )

    except httpx.HTTPStatusError:
        raise HTTPException(
            status_code=502,
            detail="External API returned an error"
        )
```

### Why is the after version better?

- `async` allows the endpoint to yield control while waiting for I/O.
- `await` waits for the asynchronous operation without blocking the event loop.
- This can improve throughput when handling many I/O-bound requests.
- Timeouts and upstream errors are handled explicitly.

### Interview questions

**Q1. What is the difference between synchronous and asynchronous code?**

Synchronous code waits for an operation to finish before continuing. Asynchronous code can yield control while waiting for I/O.

**Q2. Does async automatically make CPU-heavy code faster?**

No. Async primarily helps with I/O-bound workloads. CPU-heavy tasks may need processes, workers, or other execution strategies.

**Q3. Can I use `requests` inside an async endpoint?**

You can, but it blocks the event loop during the network call. Prefer an async HTTP client such as HTTPX for asynchronous I/O.

**Q4. What is concurrency?**

Managing multiple tasks that make progress during overlapping periods.

## 14. REST API Best Practices and Versioning

### Before
```python
@app.get("/getAllUsers")
def get_all_users():
    return users

@app.post("/createUser")
def create_user():
    ...
```

The routes use action-oriented names.

### After
```python
@app.get("/api/v1/users")
def get_users():
    ...

@app.post("/api/v1/users")
def create_user():
    ...

@app.get("/api/v1/users/{user_id}")
def get_user(user_id: int):
    ...

@app.patch("/api/v1/users/{user_id}")
def update_user(user_id: int):
    ...

@app.delete("/api/v1/users/{user_id}")
def delete_user(user_id: int):
    ...
```

### Why is the after version better?

- Resource-oriented naming is consistent with REST conventions.
- HTTP methods describe the operation.
- Versioning allows an API to evolve while older clients continue using the previous version.
- Consistent response structures make integrations easier.

### Interview questions

**Q1. What does REST stand for?**

Representational State Transfer.

**Q2. What is a REST resource?**

An entity or concept exposed through an API, such as users, orders, or products.

**Q3. What does stateless mean in REST?**

Each request should contain the information needed to process it. The server should not depend on stored conversational session state between requests.

**Q4. Why version an API?**

To introduce breaking changes without unexpectedly breaking existing clients.

**Q5. What are idempotent HTTP methods?**

An operation is idempotent when repeating the same request has the same intended effect as making it once. GET, PUT, and DELETE are generally defined as idempotent; POST generally is not.

# 15. External API Integration — Important Interview Topic

An interviewer may ask:

- How do you call an external REST API from Python?
- Where do you store an external API URL?
- Should the URL be hardcoded?
- Where do you store API keys and tokens?
- How do you process an external API response?
- How do you handle timeouts and failures?
- How do you retry a failed request?
- How do you prevent an external API from slowing down your service?

## A. Calling an external API

### Before — Hardcoded URL and no error handling
```python
import requests

@app.get("/weather")
def get_weather():
    response = requests.get(
        "https://api.example.com/weather"
    )

    return response.json()
```

### Problems

- URL is hardcoded in the application.
- No timeout is specified.
- No HTTP status validation.
- No exception handling.
- The application may wait too long for an external service.
- The response is returned without checking whether it has the expected structure.

### After — URL from configuration and controlled error handling

```python
import os
import httpx

from fastapi import HTTPException

EXTERNAL_API_BASE_URL = os.getenv(
    "EXTERNAL_API_BASE_URL"
)

@app.get("/weather")
async def get_weather():
    if not EXTERNAL_API_BASE_URL:
        raise HTTPException(
            status_code=500,
            detail="External API is not configured"
        )

    try:
        async with httpx.AsyncClient(timeout=10.0) as client:
            response = await client.get(
                f"{EXTERNAL_API_BASE_URL}/weather"
            )

            response.raise_for_status()
            data = response.json()

            return {
                "temperature": data["temperature"],
                "condition": data["condition"]
            }

    except httpx.TimeoutException:
        raise HTTPException(
            status_code=504,
            detail="External API timeout"
        )

    except httpx.HTTPStatusError:
        raise HTTPException(
            status_code=502,
            detail="External API request failed"
        )

    except (httpx.RequestError, ValueError, KeyError):
        raise HTTPException(
            status_code=502,
            detail="Unable to process external API response"
        )
```

### Why is the after version better?

1. The base URL comes from configuration.
2. Different environments can use different URLs.
3. A timeout prevents requests from waiting indefinitely.
4. `raise_for_status()` detects unsuccessful HTTP responses.
5. The application extracts only the data it needs.
6. Errors are translated into controlled API responses.

## B. Where should an external API URL be stored?

A common interview answer:

**Store environment-specific URLs in configuration or environment variables, not hardcoded throughout the source code.**

Example environment variables:

```bash
EXTERNAL_API_BASE_URL=https://api.example.com
EXTERNAL_API_TIMEOUT=10
```

Read them in Python:

```python
import os

BASE_URL = os.getenv("EXTERNAL_API_BASE_URL")
TIMEOUT = float(
    os.getenv("EXTERNAL_API_TIMEOUT", "10")
)
```

Typical choices:

| Environment | Configuration approach |
|---|---|
| Local development | `.env` file, excluded from Git |
| Automated tests | Test configuration or mocked settings |
| AWS deployment | Environment variables or managed configuration |
| Sensitive credentials | AWS Secrets Manager or an appropriate secret store |

**Important distinction:**

- An API URL is usually configuration, not a secret.
- API keys, passwords, and client secrets are credentials and must be protected.
- Do not commit secrets to Git.
- Do not put credentials in URL query parameters unless the provider specifically requires it; URLs can be captured in logs and monitoring systems.

## C. Before vs after — API key handling

### Before
```python
API_KEY = "my-secret-api-key"

headers = {
    "Authorization": f"Bearer {API_KEY}"
}
```

### After
```python
import os
```

## D. Processing an external API response

### Before
```python
response = requests.get(url)
return response.json()
```

This returns the entire response without validating what the application actually needs.

### After
```python
from pydantic import BaseModel, ValidationError

class ExternalWeatherResponse(BaseModel):
    temperature: float
    condition: str

def process_weather_response(data: dict):
    try:
        weather = ExternalWeatherResponse.model_validate(data)

        return {
            "temperature": weather.temperature,
            "condition": weather.condition
        }

    except ValidationError:
        raise HTTPException(
            status_code=502,
            detail="Invalid external API response"
        )
```

### Why is the after version better?

- It validates the external response.
- It detects missing or incorrectly typed fields.
- It returns only the fields needed by our application.
- It reduces dependence on the external provider's full response structure.

## E. Handling external API failures

An external service may fail for several reasons:

| Problem | Possible handling |
|---|---|
| Timeout | Return a controlled gateway timeout |
| HTTP 400 | Check the request sent to the provider |
| HTTP 401/403 | Check credentials and permissions |
| HTTP 404 | Check the upstream endpoint or resource |
| HTTP 429 | Respect rate limits and `Retry-After` |
| HTTP 500/503 | Retry selectively with backoff |
| Invalid JSON | Treat it as an upstream response error |
| Unexpected response fields | Validate and reject or handle safely |

### Retry example

```python
import asyncio
import httpx

async def call_external_api(client: httpx.AsyncClient, url: str):
    for attempt in range(3):
        try:
            response = await client.get(url)
            response.raise_for_status()
            return response.json()

        except (httpx.TimeoutException, httpx.TransportError):
            if attempt == 2:
                raise

            await asyncio.sleep(2 ** attempt)

        except httpx.HTTPStatusError as exc:
            status = exc.response.status_code

            if status not in {429, 500, 502, 503, 504}:
                raise

            if attempt == 2:
                raise

            await asyncio.sleep(2 ** attempt)
```

### Why is retry logic useful?

- Temporary network problems may recover.
- Exponential backoff reduces repeated pressure on a failing service.
- Retries should be limited.
- Respect `Retry-After` when the provider supplies it.
- Do not blindly retry non-idempotent operations such as POST; use provider-supported idempotency keys when appropriate.

## F. Reusing HTTP connections

### Before
```python
async def call_api(url: str):
    async with httpx.AsyncClient() as client:
        response = await client.get(url)
        return response.json()
```

Creating a new client for every request can prevent efficient connection reuse.

### After — Reusable client managed by application lifespan

```python
from contextlib import asynccontextmanager
import httpx
from fastapi import FastAPI, Request

@asynccontextmanager
async def lifespan(app: FastAPI):
    async with httpx.AsyncClient(timeout=10.0) as client:
        app.state.http_client = client
        yield

app = FastAPI(lifespan=lifespan)

@app.get("/external-data")
async def get_external_data(request: Request):
    client = request.app.state.http_client

    response = await client.get(
        "https://api.example.com/data"
    )

    response.raise_for_status()
    return response.json()
```

### Why is this better?

- Reuses HTTP connections.
- Reduces connection setup overhead.
- Manages the client lifecycle.
- Centralizes timeout configuration.

## G. Security — Avoid SSRF

An interviewer may ask:

**What if a user can submit an arbitrary URL and your server calls it?**

This can create a Server-Side Request Forgery (SSRF) vulnerability.

An attacker might try to make your server access internal services or cloud metadata endpoints.

Safer approach:

- Use a fixed or allowlisted set of external hosts.
- Do not blindly fetch user-supplied URLs.
- Validate destinations and redirects.
- Block private, loopback, and link-local IP ranges where appropriate.
- Apply network egress restrictions.
- Never expose internal credentials or metadata responses.

### External API interview questions

**Q1. How do you call an external REST API in Python?**

Use an HTTP client such as `requests` for synchronous code or `httpx.AsyncClient` for asynchronous code. Specify timeouts, validate status codes, process the response, and handle exceptions.

**Q2. Where do you store an external API URL?**

In environment-specific configuration, such as environment variables or a managed configuration service. Avoid hardcoding it throughout the codebase.

**Q3. Where do you store API keys?**

Use a secrets manager or approved secret store. In AWS, AWS Secrets Manager is a common option. Never commit credentials to source control.

**Q4. What is the difference between an API URL and an API key?**

The URL identifies the service endpoint. The API key is a credential used to authenticate or authorize access.

**Q5. What is a timeout?**

The maximum time the application is willing to wait for an operation before treating it as failed.

**Q6. What is a retry?**

A repeated attempt after a transient failure. Retries should be limited and use backoff.

**Q7. What is exponential backoff?**

Increasing the delay between retries, commonly doubling it after each attempt.

**Q8. What is rate limiting?**

Restricting how many requests a client can make in a given period.

**Q9. What is a circuit breaker?**

A resilience pattern that temporarily stops calls to a failing dependency, allowing it to recover and preventing repeated failures from overwhelming the system.

**Q10. What is the difference between HTTP 502 and 504?**

- 502 Bad Gateway: an upstream service returned an invalid or unsuccessful response.
- 504 Gateway Timeout: an upstream service did not respond in time.

**Q11. How do you test an external API integration?**

Mock the HTTP client or use a test server. Test successful responses, timeouts, HTTP errors, invalid JSON, and unexpected response structures.

# 17. General Python Questions for API Interviews

**Q1. What is the difference between `is` and `==`?**

- `==` compares values.
- `is` checks whether two references point to the same object.

**Q2. What is the difference between a list and a tuple?**

- Lists are mutable.
- Tuples are immutable.

**Q3. What is a generator?**

A generator produces values lazily, one at a time, instead of building the entire collection in memory.

**Q4. What is a decorator?**

A function that wraps or modifies the behavior of another function. FastAPI route decorators such as `@app.get()` are examples.

**Q5. What is exception handling?**

Using `try`, `except`, `else`, and `finally` to handle errors and control program flow.

**Q6. What is the difference between shallow copy and deep copy?**

A shallow copy copies the outer container but retains references to nested objects. A deep copy recursively copies nested objects.

**Q7. What is a context manager?**

An object used with `with` to manage setup and cleanup, such as closing files or HTTP clients.

**Q8. What is the difference between `append()` and `extend()`?**

- `append()` adds one item.
- `extend()` adds each item from an iterable.

# 18. A Strong Interview Explanation: External API Integration

If asked, "How would you integrate an external API into your FastAPI application?", a strong answer would be:

"I would keep the external API base URL in environment-specific configuration rather than hardcoding it. I would store credentials separately in a secrets manager, such as AWS Secrets Manager.

For the HTTP call, I would use an appropriate HTTP client, such as HTTPX. If the endpoint is asynchronous, I would use `AsyncClient` and `await`.

I would configure timeouts, validate the upstream HTTP status, and validate the response structure using Pydantic. I would map the upstream response into our own response schema rather than blindly returning the entire external response.

For resilience, I would use limited retries with exponential backoff for transient failures, respect rate limits, and consider a circuit breaker for an unreliable dependency. I would log useful diagnostic information without logging secrets or sensitive data.

Finally, I would test success and failure scenarios by mocking the external HTTP client."
