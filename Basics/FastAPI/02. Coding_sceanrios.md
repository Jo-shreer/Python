# Python REST API Interview – Revision Notes

## 1. GET API – Fetch all users

### BEFORE – Original code

```python
@app.get("/users")
def get_users():
    result = []

    for user in users:
        result.append({
            "id": user["id"],
            "name": user["name"],
            "email": user["email"]
        })

    return result
```

### AFTER – Cleaner implementation

```python
@app.get("/users")
def get_users():
    result = [
        {
            "id": user["id"],
            "name": user["name"],
            "email": user["email"]
        }
        for user in users
    ]

    return result
```

### WHY?

- List comprehension makes the code cleaner and more Pythonic.
- Python lists and dictionaries are automatically serialised into JSON by FastAPI.
- No need to use `json.dumps()`.
- Multiple records are generally returned as a list of dictionaries.
- A single record is generally returned as a dictionary.

### Pagination for large datasets

```python
from fastapi import Query

@app.get("/users")
def get_users(
    page: int = Query(1, ge=1),
    limit: int = Query(20, ge=1, le=100)
):
    start = (page - 1) * limit
    end = start + limit

    return users[start:end]
```

WHY?
- Avoids returning all records in one response.
- Reduces response payload size.
- Improves API responsiveness.
- For large database tables, use database-level pagination rather than loading everything into memory.
- Cursor pagination can be better than offset pagination for very large datasets.

### Response model – prevent sensitive data exposure

```python
from pydantic import BaseModel

class UserResponse(BaseModel):
    id: int
    name: str
    email: str

@app.get("/users", response_model=list[UserResponse])
def get_users():
    return users
```

WHY?
- Validates outgoing response data.
- Exposes only the fields defined in the response model.
- Prevents accidental exposure of fields such as passwords.
- Provides consistent API response structure.

## 2. GET API – Fetch user by ID

### BEFORE – List of dictionaries

```python
users = [
    {"id": 1, "name": "John"},
    {"id": 2, "name": "Sarah"},
    {"id": 3, "name": "David"}
]

@app.get("/users/{user_id}")
def get_user(user_id: int):

    for user in users:
        if user["id"] == user_id:
            return user

    return {"message": "User not found"}
```

### AFTER – Dictionary lookup

```python
users = {
    1: {"id": 1, "name": "John"},
    2: {"id": 2, "name": "Sarah"},
    3: {"id": 3, "name": "David"}
}

from fastapi import HTTPException

@app.get("/users/{user_id}")
def get_user(user_id: int):

    user = users.get(user_id)

    if user is None:
        raise HTTPException(
            status_code=404,
            detail="User not found"
        )

    return user
```

### WHY?

- Original implementation uses a list of dictionaries.
- It loops through each record to find the matching ID.
- Dictionary lookup uses hashing.
- Average lookup complexity improves from O(n) to O(1).
- Dictionary lookup requires additional memory.

### List vs Dictionary

| Operation | List | Dictionary |
|---|---|---|
| Search by ID | O(n) | O(1) average |
| Access | Index | Key |
| Extra memory | Generally lower | Generally higher |

### Important Python distinction

List of dictionaries:

```python
users = [
    {"id": 1, "name": "John"},
    {"id": 2, "name": "Sarah"}
]

users[0]["id"]
```

Dictionary of dictionaries:

```python
users = {
    1: {"id": 1, "name": "John"},
    2: {"id": 2, "name": "Sarah"}
}

users[1]["id"]
```

Difference between dictionary access methods:

```python
users[10]        # Raises KeyError if key doesn't exist
users.get(10)    # Returns None if key doesn't exist
```

## 3. PUT API – Update an existing user

### BEFORE – Original implementation

```python
@app.put("/users/{user_id}")
def update_user(user_id: int, name: str, email: str):

    for user in users:
        if user["id"] == user_id:

            user["name"] = name
            user["email"] = email

            return user

    return {"message": "User not found"}
```

### AFTER – Pydantic validation and dictionary lookup

```python
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel, EmailStr, Field

app = FastAPI()

users = {
    1: {
        "id": 1,
        "name": "John",
        "email": "john@gmail.com"
    },
    2: {
        "id": 2,
        "name": "Sarah",
        "email": "sarah@gmail.com"
    }
}

# Request model
class UserUpdate(BaseModel):
    name: str = Field(min_length=2, max_length=50)
    email: EmailStr

# Response model
class UserResponse(BaseModel):
    id: int
    name: str
    email: EmailStr

@app.put("/users/{user_id}", response_model=UserResponse)
def update_user(user_id: int, request: UserUpdate):

    user = users.get(user_id)

    if user is None:
        raise HTTPException(
            status_code=404,
            detail="User not found"
        )

    user["name"] = request.name
    user["email"] = request.email

    return user
```

### WHY?

- Pydantic validates incoming request data.
- `UserUpdate` defines the expected input fields and types.
- `UserResponse` validates and controls the outgoing response.
- Dictionary lookup avoids the explicit loop.
- HTTP 404 is returned if the user doesn't exist.
- Invalid request data results in HTTP 422 by default in FastAPI.
- FastAPI automatically converts the returned dictionary into JSON.

Note: `EmailStr` requires the `email-validator` package.

### PUT vs PATCH

PUT:
- Generally replaces the resource representation.
- Usually expects all required fields.

PATCH:
- Updates only the fields supplied by the client.
- Existing fields not supplied should remain unchanged.

## 4. HTTP status codes to remember

| Status | Meaning |
|---|---|
| 200 | OK – successful request |
| 201 | Created – resource created |
| 204 | No Content – successful request with no response body |
| 400 | Bad Request |
| 401 | Unauthenticated |
| 403 | Forbidden |
| 404 | Resource not found |
| 409 | Conflict – for example, duplicate email |
| 422 | Validation error |
| 500 | Internal server error |

## 5. Important interview concepts

1. List comprehension improves readability but does not automatically reduce time complexity.
2. Dictionary lookup is O(1) on average because of hashing.
3. Dictionaries consume more memory than lists in typical use.
4. Pydantic BaseModel validates request and response data.
5. FastAPI automatically serialises dictionaries and lists into JSON.
6. Pagination prevents unnecessarily large API responses.
7. Database-level pagination is preferable for large production datasets.
8. Use HTTPException for proper HTTP error responses.
9. Use separate request and response models.
10. Never expose sensitive information in API responses.
