# SQLAlchemy 2.0 – Complete Interview Cheat Sheet

# 1. What is SQLAlchemy?

SQLAlchemy is a Python ORM (Object Relational Mapper) that allows us to interact with relational databases using Python objects instead of writing raw SQL for every operation.

It supports databases such as:
- PostgreSQL
- MySQL
- SQLite
- Microsoft SQL Server
- Oracle

SQLAlchemy has two main parts:

1. **Core:** SQL expression language for writing SQL queries using Python.
2. **ORM:** Maps Python classes to database tables and rows to Python objects.

Example:

Instead of writing:

```sql
SELECT * FROM users WHERE id = 1;
```

We can write:

```python
user = db.get(User, 1)
```

# 2. How to create a database table using SQLAlchemy

SQLAlchemy 2.0 uses `DeclarativeBase`, `Mapped`, and `mapped_column`.

### Step 1: Create base.py

```python
from sqlalchemy.orm import DeclarativeBase

class Base(DeclarativeBase):
    pass
```

All our ORM models inherit from this Base class.

### Step 2: Create models.py

```python
from sqlalchemy import String, Integer, Boolean, DateTime, func
from sqlalchemy.orm import Mapped, mapped_column
from app.db.base import Base


class User(Base):

    __tablename__ = "users"

    id: Mapped[int] = mapped_column(
        Integer,
        primary_key=True,
        index=True
    )

    name: Mapped[str] = mapped_column(
        String(100),
        nullable=False
    )

    email: Mapped[str] = mapped_column(
        String(255),
        unique=True,
        nullable=False,
        index=True
    )

    age: Mapped[int | None] = mapped_column(
        Integer,
        nullable=True
    )

    is_active: Mapped[bool] = mapped_column(
        Boolean,
        default=True
    )

    created_at: Mapped[DateTime] = mapped_column(
        DateTime(timezone=True),
        server_default=func.now()
    )
```

### Important concepts

| Parameter | Meaning |
|---|---|
| `__tablename__` | Specifies the database table name |
| `Mapped` | Declares an ORM-mapped Python attribute |
| `mapped_column()` | Defines a database column |
| `Integer` | Integer database type |
| `String(100)` | String with maximum length 100 |
| `primary_key=True` | Defines primary key |
| `nullable=False` | Column cannot contain NULL |
| `nullable=True` | Column can contain NULL |
| `unique=True` | Values must be unique |
| `index=True` | Creates a database index |
| `default=True` | Python-side default value |
| `server_default` | Default applied by the database |
| `ForeignKey()` | Defines a foreign key relationship |
| `onupdate` | Sets a value when SQLAlchemy updates a row |

**Important:** `String(100)` specifies a maximum length in databases that enforce VARCHAR length. Some database systems handle length differently.

# 3. SQLAlchemy column parameters

These are common arguments passed to `mapped_column()`.

## A. Primary key

```python
id: Mapped[int] = mapped_column(
    primary_key=True
)
```

Identifies each row uniquely.

A primary key is unique and cannot be NULL.

## B. Nullable

```python
name: Mapped[str] = mapped_column(
    String(100),
    nullable=False
)
```

The database does not allow NULL values.

Optional field:

```python
age: Mapped[int | None] = mapped_column(
    nullable=True
)
```

## C. Unique

```python
email: Mapped[str] = mapped_column(
    String(255),
    unique=True
)
```

Prevents duplicate email addresses.

## D. Index

```python
email: Mapped[str] = mapped_column(
    String(255),
    index=True
)
```

Creates an index to help the database find records faster.

Useful for frequently searched columns.

Remember: indexes improve many read queries but consume storage and can slow down writes.

## E. Default

```python
is_active: Mapped[bool] = mapped_column(
    default=True
)
```

Sets the default value on the Python/SQLAlchemy side when an INSERT is performed.

## F. Server default

```python
created_at: Mapped[DateTime] = mapped_column(
    DateTime(timezone=True),
    server_default=func.now()
)
```

The database supplies the default value.

Difference:

- `default`: Applied by SQLAlchemy.
- `server_default`: Defined and applied by the database.

## G. Autoincrement

```python
id: Mapped[int] = mapped_column(
    primary_key=True,
    autoincrement=True
)
```

Automatically generates an ID where supported by the database.

Integer primary keys commonly use autoincrement behavior automatically, so explicitly specifying it is often unnecessary.

## H. Foreign key

```python
department_id: Mapped[int] = mapped_column(
    ForeignKey("departments.id"),
    nullable=False
)
```

Links one table to another.

## I. onupdate

```python
updated_at: Mapped[DateTime] = mapped_column(
    DateTime(timezone=True),
    onupdate=func.now()
)
```

Sets the timestamp during SQLAlchemy-generated UPDATE operations.

Unlike a database trigger, this is not guaranteed to run for updates made outside SQLAlchemy.

# 5. SQLAlchemy constraints

Constraints are rules enforced by the database.

There are two main ways to define constraints:

1. Column-level constraints.
2. Table-level constraints.

## A. PrimaryKeyConstraint

```python
from sqlalchemy import PrimaryKeyConstraint

class User(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(Integer)

    __table_args__ = (
        PrimaryKeyConstraint("id"),
    )
```

Defines the primary key.

Normally, we use the simpler `primary_key=True` on the column.

## B. UniqueConstraint

Example: Multiple columns together must be unique.

```python
from sqlalchemy import UniqueConstraint

class User(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(primary_key=True)

    first_name: Mapped[str] = mapped_column(String(50))
    last_name: Mapped[str] = mapped_column(String(50))

    __table_args__ = (
        UniqueConstraint(
            "first_name",
            "last_name",
            name="uq_user_name"
        ),
    )
```

This means the combination of first name and last name must be unique.

## C. CheckConstraint

Restricts values based on a condition.

```python
from sqlalchemy import CheckConstraint

class User(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(primary_key=True)

    age: Mapped[int] = mapped_column(Integer)

    __table_args__ = (
        CheckConstraint(
            "age >= 18",
            name="check_user_age"
        ),
    )
```

The database rejects an age below 18.

## D. ForeignKeyConstraint

Defines a foreign key involving one or more columns.

```python
from sqlalchemy import ForeignKeyConstraint

class Employee(Base):
    __tablename__ = "employees"

    id: Mapped[int] = mapped_column(primary_key=True)
    department_id: Mapped[int] = mapped_column(Integer)

    __table_args__ = (
        ForeignKeyConstraint(
            ["department_id"],
            ["departments.id"],
            name="fk_employee_department"
        ),
    )
```

For a simple foreign key, use `ForeignKey()` directly on the column.

## E. Index

```python
from sqlalchemy import Index

class User(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(primary_key=True)
    first_name: Mapped[str] = mapped_column(String(50))
    last_name: Mapped[str] = mapped_column(String(50))

    __table_args__ = (
        Index(
            "ix_user_first_last",
            "first_name",
            "last_name"
        ),
    )
```

Creates a composite index on two columns.

### Constraint summary

| Constraint | Purpose |
|---|---|
| Primary Key | Unique identifier for each row |
| Foreign Key | Links records between tables |
| Unique | Prevents duplicate values |
| Check | Ensures a condition is satisfied |
| Not Null | Prevents NULL values |
| Index | Improves lookup performance; not itself a uniqueness constraint |
| Composite Unique | Enforces uniqueness across multiple columns |
| Composite Primary Key | Uses multiple columns as the primary key |

# 6. Foreign keys and relationships

Suppose we have two tables:

- Department
- Employee

One department can have many employees.

### Department model

```python
from sqlalchemy.orm import relationship

class Department(Base):
    __tablename__ = "departments"

    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(100))

    employees = relationship(
        "Employee",
        back_populates="department"
    )
```

### Employee model

```python
from sqlalchemy import ForeignKey

class Employee(Base):
    __tablename__ = "employees"

    id: Mapped[int] = mapped_column(primary_key=True)

    department_id: Mapped[int] = mapped_column(
        ForeignKey("departments.id")
    )

    department = relationship(
        "Department",
        back_populates="employees"
    )
```

### What is relationship()?

`ForeignKey()` defines the database-level link.

`relationship()` defines how SQLAlchemy navigates between related ORM objects.

Example:

```python
department = db.get(Department, 1)

print(department.employees)
```

This gives us the employees associated with the department.

### Relationship types

- One-to-one
- One-to-many
- Many-to-one
- Many-to-many

For many-to-many relationships, we generally use an association table.

# 7. Alembic – Database migrations

Alembic is the migration tool commonly used with SQLAlchemy.

It manages database schema changes over time.

For example:

- Create a users table.
- Add an email column.
- Add a unique constraint.
- Add an index.
- Rename a column.
- Remove a column.

**Important interview distinction:**

SQLAlchemy models define the intended database structure.

Alembic migrations apply schema changes to the actual database.

## Step 1: Install Alembic

```bash
pip install alembic sqlalchemy
```

## Step 2: Initialize Alembic

From the project root:

```bash
alembic init migrations
```

This creates:

```text
migrations/
    env.py
    script.py.mako
    versions/

alembic.ini
```

`versions/` stores individual migration files.

## Step 3: Configure database connection

In `alembic.ini`, you may see:

```ini
sqlalchemy.url = driver://user:password@localhost/dbname
```

For production, do not hardcode database passwords here.

Instead, load the connection URL securely through environment variables or application configuration.

## Step 4: Connect Alembic to SQLAlchemy models

In `migrations/env.py`, import your Base and all model modules.

Example:

```python
from app.db.base import Base
from app.models.user import User

target_metadata = Base.metadata
```

Why do we need this?

Alembic compares the metadata from SQLAlchemy models against the current database schema to identify changes when autogeneration is used.

**Important:** Every model must be imported so that its table is registered in `Base.metadata`.

## Step 5: Generate migration

After creating or changing a model:

```bash
alembic revision --autogenerate -m "create users table"
```

This creates a migration file inside:

```text
migrations/versions/
```

Example generated migration:

```python
from alembic import op
import sqlalchemy as sa

def upgrade():
    op.create_table(
        "users",
        sa.Column("id", sa.Integer(), nullable=False),
        sa.Column("name", sa.String(length=100), nullable=False),
        sa.Column("email", sa.String(length=255), nullable=False),
        sa.PrimaryKeyConstraint("id"),
        sa.UniqueConstraint("email")
    )


def downgrade():
    op.drop_table("users")
```

### What are upgrade() and downgrade()?

- `upgrade()` applies the database change.
- `downgrade()` reverses the change.

## Step 6: Apply migration

```bash
alembic upgrade head
```

This applies all migrations up to the latest revision.

## Step 7: Check migration history

```bash
alembic history
```

Shows migration history.

```bash
alembic current
```

Shows the current revision recorded in the database.

```bash
alembic heads
```

Shows the latest revision heads.

## Step 8: Roll back migration

```bash
alembic downgrade -1
```

Moves back one migration.

```bash
alembic downgrade base
```

Reverts all migrations.

Be careful: downgrades can drop tables or data. They are not automatically safe recovery mechanisms.

## Common Alembic commands

| Command | Purpose |
|---|---|
| `alembic init migrations` | Initialize Alembic |
| `alembic revision -m "message"` | Create an empty migration |
| `alembic revision --autogenerate -m "message"` | Generate migration from model changes |
| `alembic upgrade head` | Apply all pending migrations |
| `alembic upgrade +1` | Apply next migration |
| `alembic downgrade -1` | Roll back one migration |
| `alembic downgrade base` | Roll back all migrations |
| `alembic current` | Show current database revision |
| `alembic history` | Show migration history |
| `alembic heads` | Show latest revision heads |
| `alembic check` | Check whether model changes would generate a new migration |

### What should we be careful about with Alembic?

1. Always review autogenerated migration files before applying them.
2. Autogeneration is not perfect; it may miss some changes.
3. Make sure all model modules are imported into `env.py`.
4. Never casually edit an already-applied migration.
5. Use meaningful migration names.
6. Test migrations against a staging database before production.
7. Be careful when renaming or dropping columns because existing data may be affected.
8. For large production tables, consider whether adding a column, index, or constraint could lock the table.
9. Avoid running multiple independent migration processes at the same time.
10. Back up important production data and have a rollback/recovery plan.

### Production migration workflow

```text
Developer changes SQLAlchemy model
             |
             v
Generate Alembic migration
             |
             v
Review migration file
             |
             v
Test migration locally
             |
             v
Test against staging database
             |
             v
Deploy migration through release process
             |
             v
alembic upgrade head
             |
             v
Application uses updated schema
```

In production, migrations should normally be a controlled deployment step, not something every application instance runs automatically on startup.

# 8. Database connections – SQLAlchemy engine

The SQLAlchemy engine manages database connectivity and connection pooling.

Example:

```python
from sqlalchemy import create_engine

engine = create_engine(
    DATABASE_URL,
    echo=False,
    pool_pre_ping=True,
    pool_size=10,
    max_overflow=20,
    pool_timeout=30,
    pool_recycle=1800
)
```

### Important create_engine() parameters

| Parameter | Explanation |
|---|---|
| `url` | Database connection URL |
| `echo` | Logs generated SQL statements when enabled |
| `pool_pre_ping` | Checks whether a pooled connection is alive before using it |
| `pool_size` | Number of persistent connections maintained by the pool |
| `max_overflow` | Extra connections allowed beyond pool_size |
| `pool_timeout` | Maximum time to wait for a connection from the pool |
| `pool_recycle` | Recycles connections after a configured number of seconds |
| `connect_args` | Driver-specific connection arguments |
| `poolclass` | Selects a connection pool implementation |
| `future` | Legacy SQLAlchemy 1.4 option; not needed in SQLAlchemy 2.x |

### Explanation of connection pooling

Suppose:

```python
pool_size=10
max_overflow=20
```

The pool normally maintains up to 10 connections and can open up to 20 additional connections during demand.

The theoretical maximum for this engine is 30 simultaneous checked-out connections.

Remember: The total across all application workers and instances matters. If we run 5 application processes, each with a pool capable of 30 connections, the database could potentially see up to 150 connections from those processes.

This is especially important with AWS Aurora.

### pool_pre_ping

```python
engine = create_engine(
    DATABASE_URL,
    pool_pre_ping=True
)
```

Checks whether a pooled connection is still valid before returning it for use.

Useful when database connections may be closed by the database, network, or infrastructure.

### pool_recycle

```python
engine = create_engine(
    DATABASE_URL,
    pool_recycle=1800
)
```

Recycles connections older than 1800 seconds when they are checked out.

Useful for environments where connections have a maximum lifetime.

### connect_args

Allows driver-specific options.

Example:

```python
engine = create_engine(
    DATABASE_URL,
    connect_args={
        "connect_timeout": 10
    }
)
```

The exact argument depends on the database driver.

# 10. Session and sessionmaker

The engine manages connections.

A Session manages ORM operations and the transaction associated with those operations.

We create a session factory using `sessionmaker()`.

```python
from sqlalchemy.orm import sessionmaker

SessionLocal = sessionmaker(
    bind=engine,
    autoflush=False,
    expire_on_commit=False
)
```

### Important sessionmaker parameters

| Parameter | Explanation |
|---|---|
| `bind` | Engine or connection used by the session |
| `autoflush` | Automatically flushes pending changes before certain queries |
| `expire_on_commit` | Expires ORM object attributes after commit when True |
| `autocommit` | Legacy option; do not enable it in modern SQLAlchemy usage |
| `class_` | Custom session class |
| `info` | Additional information stored on the session |

### autoflush

```python
autoflush=False
```

Prevents automatic flushing before queries.

We can explicitly call:

```python
db.flush()
```

### expire_on_commit

```python
expire_on_commit=False
```

Keeps loaded ORM attributes available after commit rather than expiring them.

This can be useful when returning ORM objects from FastAPI endpoints.

It does not mean the object can be used after its session is closed for every possible operation. Unloaded relationships and expired attributes may still need database access.

# 11. FastAPI database session dependency

Create `db/session.py`:

```python
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker

engine = create_engine(
    DATABASE_URL,
    pool_pre_ping=True
)

SessionLocal = sessionmaker(
    bind=engine,
    autoflush=False,
    expire_on_commit=False
)


def get_db():

    db = SessionLocal()

    try:
        yield db

    finally:
        db.close()
```

Use it in the router:

```python
from fastapi import Depends
from sqlalchemy.orm import Session

@router.get("/users")
def get_users(
    db: Session = Depends(get_db)
):
    return user_service.get_users(db)
```

### Why do we close the session?

A session checks out a database connection when needed.

Closing the session releases its resources and returns the connection to the connection pool.

The connection is generally returned to the pool rather than physically closed.

# 12. SQLAlchemy Session methods – Important for interviews

These are commonly used ORM session methods.

| Method | Purpose |
|---|---|
| `db.add()` | Adds an ORM object to the session |
| `db.add_all()` | Adds multiple objects |
| `db.get()` | Gets an object by primary key |
| `db.execute()` | Executes a SQL statement |
| `db.scalar()` | Returns the first column of the first result row |
| `db.scalars()` | Returns scalar results, commonly ORM objects |
| `db.flush()` | Sends pending changes to the database without committing |
| `db.commit()` | Commits the current transaction |
| `db.rollback()` | Rolls back the current transaction |
| `db.refresh()` | Reloads an object from the database |
| `db.delete()` | Marks an ORM object for deletion |
| `db.close()` | Closes the session and releases resources |
| `db.begin()` | Starts a transaction context |
| `db.merge()` | Copies state into a session-managed object |
| `db.expire()` | Marks object attributes as needing reload |
| `db.expire_all()` | Expires all objects in the session |

### add()

```python
user = User(
    name="John",
    email="john@example.com"
)

db.add(user)
db.commit()
```

Adds a new ORM object to the session.

### add_all()

```python
db.add_all([
    User(name="John", email="john@example.com"),
    User(name="Mary", email="mary@example.com")
])

db.commit()
```

Adds multiple ORM objects.

### flush()

```python
db.add(user)
db.flush()

print(user.id)

db.commit()
```

Sends pending INSERT/UPDATE/DELETE operations to the database within the current transaction.

It does not commit the transaction.

### commit()

```python
db.commit()
```

Permanently commits the current transaction.

### rollback()

```python
try:
    db.add(user)
    db.commit()

except Exception:
    db.rollback()
    raise
```

Reverses uncommitted transaction changes after an error.

### refresh()

```python
db.commit()
db.refresh(user)
```

Reloads the object from the database.

Useful for retrieving generated values and database-side defaults.

### get()

```python
user = db.get(User, 1)
```

Fetches a row by its primary key.

It can use the session's identity map before querying the database.

# 13. SQLAlchemy query methods – select(), scalars(), scalar(), execute()

This is one of the most important interview topics.

SQLAlchemy 2.0 uses the `select()` statement as the modern query style.

## A. select()

Import:

```python
from sqlalchemy import select
```

Get all users:

```python
stmt = select(User)

result = db.scalars(stmt).all()
```

`select(User)` builds a SELECT statement.

It does not execute the query until it is passed to a session or connection.

## B. db.scalars()

```python
users = db.scalars(
    select(User)
).all()
```

Returns scalar values from the result.

When selecting an ORM model, it returns User objects.

Useful when we select one entity or one column.

## C. db.scalar()

```python
user = db.scalar(
    select(User).where(User.id == 1)
)
```

Returns the first column of the first result row, or `None` if there is no result.

For a single ORM entity, this returns a User object or None.

## D. db.execute()

```python
result = db.execute(
    select(User)
)

users = result.scalars().all()
```

`execute()` returns a Result object.

We can then use methods such as:
- `all()`
- `first()`
- `one()`
- `one_or_none()`
- `scalars()`
- `mappings()`

### Difference between execute(), scalars(), and scalar()

| Method | Returns |
|---|---|
| `db.execute(stmt)` | Result object |
| `db.scalars(stmt)` | ScalarResult |
| `db.scalar(stmt)` | First scalar value or None |

Example:

```python
# Execute
result = db.execute(select(User))

# Get ORM objects
users = result.scalars().all()

# Directly get ORM objects
users = db.scalars(select(User)).all()

# Get one ORM object
user = db.scalar(
    select(User).where(User.id == 1)
)
```

# 14. Common SQLAlchemy query operations

### Get all records

```python
users = db.scalars(
    select(User)
).all()
```

### Get by ID

```python
user = db.get(User, user_id)
```

Alternative:

```python
user = db.scalar(
    select(User).where(User.id == user_id)
)
```

### Get by email

```python
user = db.scalar(
    select(User).where(User.email == email)
)
```

### Filter

```python
users = db.scalars(
    select(User).where(User.age > 18)
).all()
```

### Multiple conditions – AND

```python
from sqlalchemy import and_

users = db.scalars(
    select(User).where(
        and_(
            User.age > 18,
            User.is_active == True
        )
    )
).all()
```

You can also use multiple arguments to `where()`:

```python
users = db.scalars(
    select(User).where(
        User.age > 18,
        User.is_active.is_(True)
    )
).all()
```

### OR

```python
from sqlalchemy import or_
```

# 15. Repository layer – CRUD examples

The repository contains database operations.

Example: `user_repository.py`

```python
from sqlalchemy import select
from sqlalchemy.orm import Session

from app.models.user import User


class UserRepository:

    # CREATE
    def create(self, db: Session, user: User):

        db.add(user)
        db.flush()

        return user

    # GET ALL
    def get_all(self, db: Session):

        return db.scalars(
            select(User)
        ).all()

    # GET BY ID
    def get_by_id(self, db: Session, user_id: int):

        return db.get(User, user_id)

    # GET BY EMAIL
    def get_by_email(self, db: Session, email: str):

        return db.scalar(
            select(User).where(
                User.email == email
            )
        )

    # UPDATE
    def update(self, db: Session, user: User):

        db.flush()

        return user

    # DELETE
    def delete(self, db: Session, user: User):

        db.delete(user)
        db.flush()
```

### Important interview point

Why do we not call `commit()` inside every repository method?

Because a service operation may involve multiple repository operations.

The service layer or unit-of-work layer should coordinate the transaction.

# 17. Transaction handling – Very important

A transaction groups database operations together.

Either all changes are committed or uncommitted changes are rolled back.

Example:

```python
try:

    user = User(
        name="John",
        email="john@example.com"
    )

    db.add(user)

    db.commit()

except Exception:

    db.rollback()
    raise
```

### Using transaction context manager

Another approach:

```python
with db.begin():

    user = User(
        name="John",
        email="john@example.com"
    )

    db.add(user)
```

The context manager commits if the block succeeds and rolls back if an exception occurs.

Do not call `commit()` again inside this transaction block.

### Interview explanation

"I normally coordinate transactions at the service or unit-of-work level. Repository methods perform database operations and flush changes, while the service ensures that all operations belonging to one business workflow are committed or rolled back together."

# 18. SQLAlchemy async database connection

For asynchronous FastAPI endpoints, we can use SQLAlchemy's async engine and AsyncSession.

Install:

```bash
pip install sqlalchemy asyncpg
```

Example PostgreSQL URL:

```python
DATABASE_URL = (
    "postgresql+asyncpg://username:password@host:5432/database"
)
```

### Async engine

```python
from sqlalchemy.ext.asyncio import (
    create_async_engine,
    async_sessionmaker,
    AsyncSession
)

engine = create_async_engine(
    DATABASE_URL,
    pool_pre_ping=True
)

AsyncSessionLocal = async_sessionmaker(
    bind=engine,
    expire_on_commit=False
)
```

### Async database dependency

```python
async def get_db():

    async with AsyncSessionLocal() as db:
        yield db
```

### Async query

```python
from sqlalchemy import select

async def get_users(db: AsyncSession):

    result = await db.scalars(
        select(User)
    )

    return result.all()
```

### Important differences

| Synchronous | Asynchronous |
|---|---|
| `create_engine()` | `create_async_engine()` |
| `Session` | `AsyncSession` |
| `sessionmaker()` | `async_sessionmaker()` |
| `def` | `async def` |
| `db.execute()` | `await db.execute()` |
| `db.commit()` | `await db.commit()` |
| `db.refresh()` | `await db.refresh()` |
| `db.close()` | `await db.close()` |

Use an async-compatible database driver such as `asyncpg` for PostgreSQL.

Do not use a synchronous SQLAlchemy session directly inside an async database workflow and assume it becomes non-blocking.

# 19. Production best practices

1. Use SQLAlchemy 2.0 typed ORM syntax.
2. Keep models and Pydantic schemas separate.
3. Use Alembic for database migrations.
4. Use connection pooling.
5. Configure `pool_pre_ping` where stale connections are a concern.
6. Store credentials securely.
7. Keep database queries inside repositories.
8. Keep business logic inside services.
9. Manage transactions at the service/unit-of-work level.
10. Use database constraints for data integrity.
11. Add indexes based on actual query patterns.
12. Use pagination for large result sets.
13. Avoid loading unnecessary columns or relationships.
14. Handle `IntegrityError` and roll back failed transactions.
15. Use `select()` rather than the legacy `Query` API for new SQLAlchemy 2.0 code.
16. Use AsyncSession consistently if the application uses async database access.
17. Configure pool limits based on total application instances and database capacity.
18. Test migrations and queries before deploying to production.

# 21. One-minute SQLAlchemy interview answer

"SQLAlchemy is a Python ORM that allows us to interact with relational databases using Python classes and objects.

First, I define a Base class using DeclarativeBase. Then I create ORM models using Mapped and mapped_column, defining the table name, columns, data types, primary keys, foreign keys, unique constraints, indexes, and defaults.

I use Alembic to manage database schema changes. I generate migration files, review them, and apply them using commands such as `alembic upgrade head`.

For database connectivity, I create an engine using create_engine and configure connection pooling. I use sessionmaker to create database sessions and provide them to FastAPI endpoints using Depends.

Inside the repository layer, I use SQLAlchemy 2.0 methods such as select, execute, scalars, scalar, and get to perform database operations.

The service layer coordinates business logic and transactions. I use flush to send pending changes, commit to save transactions, rollback to handle failures, and refresh to reload database-generated values.

For asynchronous applications, I use create_async_engine and AsyncSession with an async-compatible database driver."
