# Pydantic v2 with FastAPI — Detailed Complete Cheat Sheet

**Covers:** Pydantic v2, FastAPI, Python 3.10+

# 1. What is Pydantic?

Pydantic is a Python library used to validate, convert and structure data.

FastAPI uses Pydantic to validate data coming into your API and control the data going out.

Imagine your API receives this request:

```json
{
  "name": "John",
  "age": "25"
}
```

You expect `age` to be an integer, but the client sends a string.

Pydantic can convert compatible values automatically.

```python
from pydantic import BaseModel

class User(BaseModel):
    name: str
    age: int

user = User(name="John", age="25")

print(user.age)
# 25

print(type(user.age))
# <class 'int'>
```

If the client sends an invalid value:

```python
User(name="John", age="hello")
```

Pydantic raises a validation error.

**Why do we need Pydantic?**

Without Pydantic, you would have to write manual checks for every field:

- Is the name a string?
- Is the age an integer?
- Is the email valid?
- Is the password long enough?
- Are required fields present?
- Are unexpected fields being sent?

Pydantic handles much of this automatically.

# 2. BaseModel — The foundation of Pydantic

`BaseModel` is the main class you inherit from when creating a Pydantic model.

A model defines the structure of the data you expect.

```python
from pydantic import BaseModel

class User(BaseModel):
    id: int
    name: str
    email: str
    age: int
```

Here, `User` is a Pydantic model.

It says that a user must have:

- An integer ID.
- A string name.
- A string email.
- An integer age.

You can create an object using:

```python
user = User(
    id=1,
    name="John",
    email="john@example.com",
    age=25
)
```

## Important BaseModel attributes

| Attribute | What it means | Why you need it |
|---|---|---|
| `model_fields` | Contains definitions of all model fields | Inspect field types, defaults and metadata |
| `model_config` | Contains the model's configuration | Understand how the model is configured |
| `model_fields_set` | Contains fields explicitly provided when creating the model | Useful for PATCH operations |
| `model_extra` | Contains extra fields when `extra="allow"` is configured | Access additional input data |
| `model_computed_fields` | Contains definitions of computed fields | Inspect calculated properties |

Example:

```python
user = User(
    id=1,
    name="John",
    email="john@example.com",
    age=25
)

print(user.model_fields)
print(user.model_fields_set)
```

## Important BaseModel methods

### 1. model_dump()

Converts a Pydantic model into a Python dictionary.

Why do we need it?

You often need to pass model data to a database, another function or a service.

```python
user = User(
    id=1,
    name="John",
    email="john@example.com",
    age=25
)

print(user.model_dump())
```

Output:

```python
{
    "id": 1,
    "name": "John",
    "email": "john@example.com",
    "age": 25
}
```

### 2. model_dump_json()

Converts the model into a JSON string.

Why do we need it?

Useful when sending data to an external API or storing JSON in a system that expects a JSON string.

```python
print(user.model_dump_json())
```

Output:

```json
{"id":1,"name":"John","email":"john@example.com","age":25}
```

### 3. model_validate()

Validates a Python dictionary or other supported Python object against a model.

Why do we need it?

Useful when retrieving data from a database or another Python service and checking that it matches your expected structure.

```python
data = {
    "id": 1,
    "name": "John",
    "email": "john@example.com",
    "age": "25"
}

user = User.model_validate(data)
```

Pydantic validates the data and converts compatible values.

### 4. model_validate_json()

Validates a JSON string directly.

Why do we need it?

Useful when receiving JSON from an external service or reading JSON from a file.

```python
json_data = """
{
    "id": 1,
    "name": "John",
    "email": "john@example.com",
    "age": 25
}
"""

user = User.model_validate_json(json_data)
```

### 5. model_construct()

Creates a model without normal validation.

Why do we need it?

Useful in trusted internal situations where you already know the data is valid and want to avoid validation overhead.

```python
user = User.model_construct(
    id=1,
    name="John",
    email="john@example.com",
    age=25
)
```

**Warning:** Never use this as a replacement for validation of untrusted API input.

### 6. model_copy()

Creates a copy of an existing model.

Why do we need it?

Useful when you want to create an updated version without modifying the original object.

```python
new_user = user.model_copy(
    update={"name": "David"}
)
```

By default, this is a shallow copy. Use `deep=True` when you need a deep copy of nested objects.

Important: Values supplied through `update` are not validated automatically.

### 7. model_json_schema()

Generates a JSON Schema describing the model.

Why do we need it?

Useful for API documentation, schema generation and systems that need to understand your expected data structure.

```python
print(User.model_json_schema())
```

### 8. model_rebuild()

Rebuilds a model's internal schema.

Why do we need it?

Sometimes models refer to other models that have not been defined yet. Rebuilding can resolve those forward references.

```python
class Department(BaseModel):
    employees: list["Employee"]

class Employee(BaseModel):
    name: str

Department.model_rebuild()
```

### 9. model_post_init()

Runs after a model has been initialized and validated.

Why do we need it?

Useful for additional initialization that depends on validated model data.

```python
class User(BaseModel):
    name: str

    def model_post_init(self, context):
        print(f"Created user: {self.name}")
```

# 3. Field() — Defining rules for individual fields

`Field()` is one of the most important Pydantic functions.

It allows you to define rules, defaults, aliases and documentation for individual fields.

Without `Field()`:

```python
class User(BaseModel):
    name: str
    age: int
```

With `Field()`:

```python
from pydantic import Field

class User(BaseModel):
    name: str = Field(
        min_length=3,
        max_length=50
    )

    age: int = Field(
        gt=0,
        le=120
    )
```

Now Pydantic checks that:

- Name contains between 3 and 50 characters.
- Age is greater than 0.
- Age is no greater than 120.

## 3.1 Default values

### `default`

Defines the value used when the client does not provide a field.

Why do we need it?

Some fields do not need to be supplied by the client because your application can provide a sensible default.

```python
class User(BaseModel):
    name: str
    age: int = Field(default=18)
```

If the client sends:

```json
{
    "name": "John"
}
```

Pydantic sets `age` to 18.

### `default_factory`

Generates a value when a model instance is created.

Why do we need it?

Use it for values that should be generated separately for each object, particularly mutable values such as lists and dictionaries.

```python
class User(BaseModel):
    tags: list[str] = Field(default_factory=list)
```

Each user receives a separate list.

For a generated timestamp:

```python
from datetime import datetime

class User(BaseModel):
    created_at: datetime = Field(
        default_factory=datetime.now
    )
```

### `validate_default`

Controls whether Pydantic validates a default value.

Why do we need it?

By default, Pydantic does not validate default values in every case. Enable this when the default must follow the same rules as client-provided values.

```python
class User(BaseModel):
    age: int = Field(
        default="25",
        validate_default=True
    )
```

### `frozen`

Prevents reassignment of an individual field after model creation.

Why do we need it?

Useful when a field should not change after the object has been created.

```python
class User(BaseModel):
    user_id: int = Field(frozen=True)
```

This prevents:

```python
user.user_id = 200
```

Note that freezing a field does not make every nested mutable object deeply immutable.

## 3.2 String validation parameters

| Parameter | What it does | Why you need it |
|---|---|---|
| `min_length` | Minimum number of characters | Prevents empty or very short values |
| `max_length` | Maximum number of characters | Limits excessively long input |
| `pattern` | Regular expression the value must match | Enforces formats such as usernames or codes |

Example:

```python
class User(BaseModel):
    username: str = Field(
        min_length=3,
        max_length=20,
        pattern=r"^[a-zA-Z0-9_]+$"
    )
```

This allows usernames such as:

```text
john_123
```

But rejects:

```text
jo
john@123
```

## 3.3 Number validation parameters

| Parameter | What it does | Example |
|---|---|---|
| `gt` | Greater than | `Field(gt=0)` |
| `ge` | Greater than or equal to | `Field(ge=18)` |
| `lt` | Less than | `Field(lt=100)` |
| `le` | Less than or equal to | `Field(le=100)` |
| `multiple_of` | Must be a multiple of a number | `Field(multiple_of=5)` |

Why do we need these?

They enforce numerical business rules.

Example:

```python
class Product(BaseModel):
    price: float = Field(gt=0)
    quantity: int = Field(ge=1, le=1000)
    discount: int = Field(ge=0, le=100)
```

A product cannot have a negative price or a quantity of zero.

## 3.4 Decimal validation parameters

Use `Decimal` when precise decimal arithmetic matters, such as money.

| Parameter | What it does | Why you need it |
|---|---|---|
| `max_digits` | Maximum total number of digits | Limits the size of a decimal |
| `decimal_places` | Maximum number of digits after the decimal point | Controls precision |
| `allow_inf_nan` | Allows or rejects infinity and NaN | Prevents invalid numerical values |

Example:

```python
from decimal import Decimal

class Payment(BaseModel):
    amount: Decimal = Field(
        gt=0,
        max_digits=10,
        decimal_places=2,
        allow_inf_nan=False
    )
```

This is suitable for validating an amount such as `125.50`.

## 3.5 Aliases — Very important in FastAPI

An alias is an alternative name for a field.

Why do we need aliases?

Different systems often use different naming conventions.

For example:

- Python usually uses `snake_case`: `user_id`.
- JavaScript APIs commonly use `camelCase`: `userId`.
- An external API may use `UserID`.

Instead of changing your Python variable name, you can use an alias.

Example:

```python
class User(BaseModel):
    user_id: int = Field(alias="userId")
```

The client sends:

```json
{
    "userId": 101
}
```

Pydantic maps it to:

```python
user.user_id
```

You can access the value normally:

```python
print(user.user_id)
# 101
```

### Three important alias parameters

**1. `alias`**

Defines an alternative name for validation and serialization.

```python
class User(BaseModel):
    user_id: int = Field(alias="userId")
```

Use it when the external field name is different from your Python field name.

**2. `validation_alias`**

Defines the name Pydantic accepts when receiving input.

Why do we need it?

Sometimes an external system sends one name, but you want your output to use a different name.

```python
class User(BaseModel):
    user_id: int = Field(
        validation_alias="userId"
    )
```

Input:

```json
{
    "userId": 101
}
```

Internally:

```python
user.user_id
```

**3. `serialization_alias`**

Defines the name used when converting the model into output.

Why do we need it?

You may want to accept one naming convention but return another.

```python
class User(BaseModel):
    user_id: int = Field(
        validation_alias="userId",
        serialization_alias="userID"
    )
```

Input:

```json
{
    "userId": 101
}
```

Output:

```python
user.model_dump(by_alias=True)
```

Result:

```json
{
    "userID": 101
}
```

### `alias_priority`

Controls whether a field's explicit alias takes precedence over an alias generator.

Why do we need it?

If you configure an alias generator for the whole model but want to override the generated alias for a particular field, alias priority helps control that behaviour.

### Alias generator

You can automatically convert all field names to camelCase.

```python
from pydantic import BaseModel, ConfigDict
from pydantic.alias_generators import to_camel

class User(BaseModel):
    model_config = ConfigDict(
        alias_generator=to_camel,
        validate_by_name=True
    )

    user_id: int
    first_name: str
```

Input:

```json
{
    "userId": 101,
    "firstName": "John"
}
```

This is useful when your Python backend uses snake_case but your frontend uses camelCase.

## 3.6 Documentation and metadata parameters

These parameters do not normally change the actual business value. They describe fields and help generate API documentation and JSON Schema.

| Parameter | What it does | Why you need it |
|---|---|---|
| `title` | Gives a field a title | Makes generated documentation clearer |
| `description` | Describes the field | Explains what the client should send |
| `examples` | Provides example values | Helps API consumers understand the format |
| `json_schema_extra` | Adds custom JSON Schema information | Supports additional documentation metadata |
| `field_title_generator` | Generates field titles automatically | Avoids writing titles for every field |
| `deprecated` | Marks a field as deprecated | Warns API consumers that a field may be retired |

Example:

```python
class User(BaseModel):
    email: str = Field(
        title="Email Address",
        description="The user's registered email address",
        examples=["john@example.com"],
        deprecated=False
    )
```

## 3.7 Other Field parameters

| Parameter | What it does | Why you need it |
|---|---|---|
| `strict` | Disables normal coercion for the field | Prevents values such as `"25"` from being accepted as integer 25 |
| `coerce_numbers_to_str` | Allows numbers to be converted to strings in lax mode | Useful when accepting numeric identifiers as strings |
| `exclude` | Excludes a field during serialization | Prevents internal fields from appearing in output |
| `exclude_if` | Excludes a field when a condition is true | Controls conditional output |
| `discriminator` | Identifies the field used to select a union model | Helps validate different request structures |
| `union_mode` | Selects the union validation strategy | Controls how alternative types are checked |
| `fail_fast` | Stops validation early for supported collection types | Avoids collecting all collection errors |
| `repr` | Controls whether a field appears in the model representation | Keeps printed model output cleaner |
| `init` | Controls initialization behaviour for dataclass fields | Used with Pydantic dataclasses |
| `init_var` | Marks a dataclass initialization-only value | Passes temporary initialization data |
| `kw_only` | Requires a keyword argument for dataclass initialization | Makes initialization explicit |

Important: `init`, `init_var` and `kw_only` are primarily relevant to dataclass fields rather than ordinary `BaseModel` fields.

# 4. Required, Optional and Nullable fields

This is one of the most important concepts in FastAPI.

A field can be:

1. Required: the client must send it.
2. Nullable: the client is allowed to send `null`.
3. Optional to provide: the client can omit it.

These concepts are related but not identical.

```python
class User(BaseModel):
    name: str
    age: int = 18
    email: str | None
    phone: str | None = None
```

| Declaration | Must provide it? | Can be null? |
|---|---|---|
| `name: str` | Yes | No |
| `age: int = 18` | No | No |
| `email: str \| None` | Yes | Yes |
| `phone: str \| None = None` | No | Yes |

Important:

`Optional[str]` means the value can be a string or `None`. It does not automatically mean the client can omit the field.

For an optional field that defaults to None:

```python
email: str | None = None
```

# 5. Strict mode

Normally Pydantic attempts to convert compatible input values.

Example:

```python
class User(BaseModel):
    age: int

user = User(age="25")
```

Pydantic converts `"25"` into `25`.

Why might this be a problem?

Sometimes you want to reject unexpected types rather than silently convert them.

Use strict mode:

```python
class User(BaseModel):
    age: int = Field(strict=True)
```

Now a string `"25"` is rejected.

You can also enable strict mode for the entire model:

```python
from pydantic import ConfigDict

class User(BaseModel):
    model_config = ConfigDict(strict=True)

    age: int
```

Or use strict mode during validation:

```python
User.model_validate(
    {"age": "25"},
    strict=True
)
```

Strictness can vary by type and input method, so test the exact inputs your API accepts.

# 6. ConfigDict — Model-wide configuration

`ConfigDict` controls how an entire Pydantic model behaves.

Why do we need it?

Without model configuration, you would have to repeat the same rules on individual fields.

For example, suppose you want every string to have surrounding whitespace removed and every unknown field to be rejected.

You can configure that once.

```python
from pydantic import BaseModel, ConfigDict

class User(BaseModel):
    model_config = ConfigDict(
        extra="forbid",
        str_strip_whitespace=True
    )

    name: str
    age: int
```

## Important ConfigDict options

| Option | What it does | Why you need it |
|---|---|---|
| `title` | Sets the model title | Improves generated documentation |
| `str_to_lower` | Converts strings to lowercase | Normalizes values |
| `str_to_upper` | Converts strings to uppercase | Standardizes codes |
| `str_strip_whitespace` | Removes surrounding whitespace | Avoids accidental spaces |
| `str_min_length` | Sets minimum string length | Applies a common string rule |
| `str_max_length` | Sets maximum string length | Limits string size |
| `extra` | Controls unknown fields | Rejects, ignores or stores unexpected data |
| `frozen` | Prevents model attribute reassignment | Makes model instances immutable at the attribute level |
| `strict` | Enables strict validation | Prevents normal type coercion |
| `validate_default` | Validates default values | Ensures defaults follow validation rules |
| `validate_assignment` | Validates reassignment of fields | Prevents invalid values after creation |
| `arbitrary_types_allowed` | Allows arbitrary Python classes | Supports custom object types |
| `from_attributes` | Reads values from object attributes | Supports ORM objects |
| `populate_by_name` | Allows population using field names alongside aliases | Supports mixed naming conventions; newer versions provide more explicit alias controls |
| `validate_by_alias` | Controls validation by alias | Accepts external field names |
| `validate_by_name` | Controls validation by Python field name | Accepts internal field names |
| `serialize_by_alias` | Uses aliases by default during serialization | Standardizes output naming |
| `use_enum_values` | Uses enum values during validation | Simplifies serialized enum values |
| `allow_inf_nan` | Allows infinity and NaN | Controls special numeric values |
| `ser_json_bytes` | Controls byte serialization | Defines JSON representation of bytes |
| `val_json_bytes` | Controls byte validation | Defines how JSON bytes are interpreted |
| `ser_json_timedelta` | Controls timedelta serialization | Standardizes durations |
| `ser_json_temporal` | Controls date/time serialization | Controls temporal output representation |
| `val_temporal_unit` | Controls numeric date/time interpretation | Avoids ambiguity in timestamps |
| `ser_json_inf_nan` | Controls serialization of infinity and NaN | Controls special floating-point output |
| `json_encoders` | Provides custom encoders | Legacy customization; field/model serializers are generally preferred |
| `json_schema_extra` | Adds schema metadata | Customizes generated API documentation |
| `json_schema_mode_override` | Overrides schema generation mode | Controls input/output schema generation |
| `json_schema_serialization_defaults_required` | Controls serialization schema requiredness | Aligns schemas with output behaviour |
| `alias_generator` | Automatically generates aliases | Converts naming conventions |
| `ignored_types` | Ignores selected types during inspection | Supports special class attributes |
| `protected_namespaces` | Controls protected attribute prefixes | Avoids naming conflicts |
| `hide_input_in_errors` | Hides input values in errors | Reduces exposure of sensitive data |
| `loc_by_alias` | Uses aliases in error locations | Makes client-facing errors easier to understand |
| `defer_build` | Delays schema building | Helps with specialized initialization patterns |
| `plugin_settings` | Configures Pydantic plugins | Supports plugin integrations |
| `cache_strings` | Controls string caching | Can affect performance and memory use |
| `validation_error_cause` | Preserves underlying validation causes | Helps diagnose custom validator errors |
| `use_attribute_docstrings` | Uses attribute docstrings as descriptions | Improves documentation |

Some configuration options are version-sensitive. Check the installed Pydantic documentation before relying on newer settings.

## The `extra` setting

This is especially useful for API security and predictable request handling.

There are three values:

### `extra="ignore"`

Unknown fields are ignored.

```python
class User(BaseModel):
    model_config = ConfigDict(extra="ignore")

    name: str
```

If the client sends:

```json
{
    "name": "John",
    "admin": true
}
```

Pydantic ignores `admin`.

### `extra="allow"`

Unknown fields are stored on the model.

```python
class User(BaseModel):
    model_config = ConfigDict(extra="allow")

    name: str
```

The `admin` field can be accessed through the model's extra data.

### `extra="forbid"`

Unknown fields are rejected.

```python
class User(BaseModel):
    model_config = ConfigDict(extra="forbid")

    name: str
```

The previous request now produces a validation error.

**Production recommendation:** Use `extra="forbid"` when unexpected request fields should not be accepted.

# 7. Field validators — Custom validation for one field

Pydantic already validates standard types, but sometimes you need custom business rules.

For example:

- A username must not contain spaces.
- An email must belong to a particular domain.
- A password must contain a number.
- A phone number must follow a specific format.

Use `@field_validator`.

```python
from pydantic import BaseModel, field_validator

class User(BaseModel):
    username: str

    @field_validator("username")
    @classmethod
    def validate_username(cls, value):
        if len(value) < 3:
            raise ValueError("Username too short")

        return value.lower()
```

## Four validator modes

### 1. `mode="before"`

Runs before Pydantic performs normal validation.

Why use it?

Useful when you want to clean or transform the incoming value first.

```python
@field_validator("age", mode="before")
@classmethod
def clean_age(cls, value):
    if isinstance(value, str):
        return value.strip()

    return value
```

For example, `" 25 "` becomes `"25"` before integer validation.

### 2. `mode="after"`

Runs after normal type validation.

Why use it?

Useful when you want to work with the correctly typed value.

```python
@field_validator("age", mode="after")
@classmethod
def check_age(cls, value):
    if value < 18:
        raise ValueError("Must be at least 18")

    return value
```

This is generally a good default for custom field validation.

### 3. `mode="plain"`

Replaces normal validation for that field.

Why use it?

Useful when you want complete control over validation.

```python
@field_validator("code", mode="plain")
@classmethod
def validate_code(cls, value):
    if value == "INVALID":
        raise ValueError("Invalid code")

    return value
```

Be careful: normal Pydantic validation is bypassed, so your validator must enforce the necessary rules itself.

### 4. `mode="wrap"`

Wraps normal validation and gives you control over whether and when the normal validator runs.

Why use it?

Useful when you need to intercept validation, handle a validation failure or add custom logic around normal validation.

```python
@field_validator("name", mode="wrap")
@classmethod
def validate_name(cls, value, handler):
    print("Before validation")

    result = handler(value)

    print("After validation")

    return result
```

`handler(value)` calls the normal validation process.

# 8. Model validators — Validation across multiple fields

Sometimes one field depends on another field.

Example:

A booking has a start date and end date.

The end date must be after the start date.

A field validator is not the best place for this because the rule involves two fields.

Use `@model_validator`.

```python
from pydantic import BaseModel, model_validator

class Booking(BaseModel):
    start_date: int
    end_date: int

    @model_validator(mode="after")
    def check_dates(self):
        if self.end_date <= self.start_date:
            raise ValueError(
                "End date must be after start date"
            )

        return self
```

## Three modes

| Mode | What it does | When to use it |
|---|---|---|
| `before` | Runs before model validation | Transform or inspect the incoming object |
| `after` | Runs after model validation | Check relationships between validated fields |
| `wrap` | Wraps the entire model validation process | Intercept or customize model validation |

Example of `before`:

```python
@model_validator(mode="before")
@classmethod
def clean_input(cls, data):
    if isinstance(data, dict):
        data = data.copy()
        data.pop("unused_field", None)

    return data
```

Example of `after`:

```python
@model_validator(mode="after")
def check_passwords(self):
    if self.password != self.confirm_password:
        raise ValueError("Passwords do not match")

    return self
```

Use field validators for individual fields and model validators for relationships between fields.

# 9. Built-in Pydantic types

Pydantic supports standard Python types and additional specialized types.

## Common Python types

```python
class User(BaseModel):
    name: str
    age: int
    salary: float
    active: bool
    tags: list[str]
    scores: tuple[int, ...]
    settings: dict[str, str]
```

Pydantic validates the structure and types of these values.

## Optional and Union

```python
class Product(BaseModel):
    price: int | float
    description: str | None = None
```

`int | float` means either an integer or a float is accepted.

`str | None` means a string or `None` is accepted.

## Literal

Use `Literal` when a field must have one of a fixed set of values.

Why do we need it?

Useful for status fields, types and fixed choices.

```python
from typing import Literal

class Order(BaseModel):
    status: Literal["pending", "approved", "rejected"]
```

Other values are rejected.

## Enum

Use an Enum when you want named constants.

```python
from enum import Enum

class Status(str, Enum):
    PENDING = "pending"
    APPROVED = "approved"
    REJECTED = "rejected"

class Order(BaseModel):
    status: Status
```

Enums are useful when the same set of values is reused across your application.

## UUID

UUIDs are unique identifiers.

```python
from uuid import UUID
```

```python
from datetime import date, datetime, time, timedelta

class Event(BaseModel):
```

Useful when working with appointments, bookings, timestamps and durations.

```python
from pydantic import EmailStr, AnyUrl, HttpUrl
```

# 10. Nested models

A nested model means one Pydantic model is used as a field inside another model.

Why do we need it?

Real API requests often contain structured data.

For example, a user has an address, and an order has products.

```python
class Address(BaseModel):
    city: str
    country: str

class User(BaseModel):
    name: str
    address: Address
```

Request:

```json
{
    "name": "John",
    "address": {
        "city": "Dublin",
        "country": "Ireland"
    }
}
```

Pydantic validates both the user and address.

You can nest models multiple levels deep.

```python
class Product(BaseModel):
    name: str
    price: float

class Order(BaseModel):
    order_id: int
    products: list[Product]

class Customer(BaseModel):
    name: str
    orders: list[Order]
```

This is useful for APIs that accept complex JSON structures.

# 11. List validation

Use list constraints when an API accepts a collection of values.

```python
class Order(BaseModel):
    products: list[str] = Field(
        min_length=1,
        max_length=10
    )
```

Why do we need it?

It prevents requests with no products or an excessive number of products.

For nested models:

```python
class Product(BaseModel):
    name: str
    price: float

class Order(BaseModel):
    products: list[Product]
```

Now every product inside the list is validated independently.

# 12. Discriminated unions

A union means a field can contain one of several model types.

A discriminated union uses a particular field to identify which model should be used.

Why do we need it?

Imagine a payment API supporting card payments and bank transfers.

Each payment has different fields.

```python
from typing import Annotated, Literal
from pydantic import BaseModel, Field

class CardPayment(BaseModel):
    type: Literal["card"]
    card_number: str

class BankPayment(BaseModel):
    type: Literal["bank"]
    account_number: str

Payment = Annotated[
    CardPayment | BankPayment,
    Field(discriminator="type")
]
```

Card request:

```json
{
    "type": "card",
    "card_number": "123456"
}
```

Bank request:

```json
{
    "type": "bank",
    "account_number": "987654"
}
```

Pydantic checks `type` to decide which model to validate.

This is particularly useful for APIs with multiple request formats.

# 13. Serialization — Converting model data into output

Serialization means converting a Pydantic model into a dictionary or JSON representation.

Why do we need it?

Your Python application works with objects, but external systems commonly expect JSON.

## model_dump()

Converts the model into a dictionary.

```python
user.model_dump()
```

## model_dump_json()

Converts the model into a JSON string.

```python
user.model_dump_json()
```

## Important model_dump() parameters

| Parameter | What it does | Why you need it |
|---|---|---|
| `mode` | Chooses Python or JSON-compatible output | Controls how special types are represented |
| `include` | Includes selected fields | Returns only required data |
| `exclude` | Removes selected fields | Hides internal fields |
| `context` | Passes extra information to serializers | Supports context-dependent output |
| `by_alias` | Uses aliases as output names | Matches external naming conventions |
| `exclude_unset` | Excludes fields not explicitly supplied | Useful for PATCH updates |
| `exclude_defaults` | Excludes values equal to defaults | Reduces unnecessary output |
| `exclude_none` | Excludes fields with None | Removes null fields |
| `exclude_computed_fields` | Excludes calculated fields | Controls calculated output |
| `round_trip` | Uses serialization suitable for round-trip validation where supported | Helps preserve special types |
| `warnings` | Controls serialization warnings | Helps manage serialization issues |
| `fallback` | Handles values that cannot be serialized normally | Supports custom fallback behaviour |
| `serialize_as_any` | Uses duck-typed serialization in supported cases | Changes how runtime types are serialized |

Examples:

```python
# Return only name and email
user.model_dump(include={"name", "email"})

# Hide password
user.model_dump(exclude={"password"})

# Remove None values
user.model_dump(exclude_none=True)

# Remove fields that were not explicitly supplied
user.model_dump(exclude_unset=True)

# Use aliases
user.model_dump(by_alias=True)

# JSON-compatible Python values
user.model_dump(mode="json")
```

`model_dump_json()` provides corresponding serialization controls, including indentation.

# 14. Computed fields

A computed field is a value calculated from other model fields.

Why do we need it?

Sometimes you do not want the client to provide a value because your application can calculate it.

Example:

```python
from pydantic import BaseModel, computed_field

class Product(BaseModel):
    price: float
    quantity: int

    @computed_field
    @property
    def total(self) -> float:
        return self.price * self.quantity
```

Usage:

```python
product = Product(
    price=10,
    quantity=3
)

print(product.total)
# 30

print(product.model_dump())
```

The calculated `total` is included in serialization by default.

You can also provide metadata such as `alias`, `title`, `description`, `examples`, `repr` and `json_schema_extra` to computed fields.

# 15. Field and model serializers

Validators control what data is accepted.

Serializers control how validated data is returned.

## field_serializer

Customizes how one field is serialized.

Why do we need it?

For example, you may want to format a datetime field differently in API responses.

```python
from datetime import datetime
from pydantic import BaseModel, field_serializer

class Event(BaseModel):
    created_at: datetime

    @field_serializer("created_at")
    def serialize_date(self, value):
        return value.strftime("%Y-%m-%d")
```

## model_serializer

Customizes the serialization of the entire model.

Why do we need it?

Useful when the returned JSON structure needs to be different from the original model structure.

```python
from pydantic import BaseModel, model_serializer

class User(BaseModel):
    first_name: str
    last_name: str

    @model_serializer
    def serialize_model(self):
        return {
            "full_name": f"{self.first_name} {self.last_name}"
        }
```

Output:

```json
{
    "full_name": "John Smith"
}
```

# 19. FastAPI integration

FastAPI uses Pydantic models to validate incoming request data and structure outgoing responses.

## 19.1 Request body

A request body contains data sent by the client, commonly using POST or PUT.

```python
from fastapi import FastAPI
from pydantic import BaseModel, Field

app = FastAPI()

class UserCreate(BaseModel):
    name: str = Field(min_length=3)
    email: str
    age: int = Field(ge=18)

@app.post("/users")
def create_user(user: UserCreate):
    return user
```

Why use a Pydantic model here?

FastAPI automatically:

1. Reads the JSON request body.
2. Validates the fields using Pydantic.
3. Converts compatible types.
4. Returns a validation error for invalid data.
5. Generates API documentation.

Example request:

```json
{
    "name": "John",
    "email": "john@example.com",
    "age": 25
}
```

## 19.2 Path parameters

Path parameters are values included directly in the URL.

Example:

```text
/users/101
```

Here, `101` is the user ID.

```python
from fastapi import Path

@app.get("/users/{user_id}")
def get_user(
    user_id: int = Path(gt=0)
):
    return {"user_id": user_id}
```

Why use `Path()`?

It lets you validate URL parameters, such as ensuring an ID is positive.

Useful parameters include:

- `gt`, `ge`, `lt`, `le`: Numerical constraints.
- `min_length`, `max_length`: String length constraints.
- `pattern`: Regular expression constraint.
- `title`, `description`, `examples`: API documentation.
- `alias`: Alternative parameter name.
- `deprecated`: Marks a parameter as deprecated.

## 19.3 Query parameters

Query parameters appear after `?` in a URL.

Example:

```text
/users?page=2&limit=10
```

Here:

- `page=2` selects the second page.
- `limit=10` requests ten records.

```python
from fastapi import Query

@app.get("/users")
def get_users(
    page: int = Query(1, ge=1),
    limit: int = Query(10, ge=1, le=100)
):
    return {
        "page": page,
        "limit": limit
    }
```

Why use `Query()`?

It validates and documents query parameters.

Useful parameters include:

- `default`: Default value.
- `gt`, `ge`, `lt`, `le`: Numerical restrictions.
- `min_length`, `max_length`: String restrictions.
- `pattern`: Regex validation.
- `min_items` and `max_items` are legacy-style names; for current Pydantic list constraints, use `min_length` and `max_length` where supported.
- `alias`: External query parameter name.
- `description`: Documentation.
- `deprecated`: Marks the parameter as deprecated.

## 19.4 Response models

A response model controls what your API returns.

Why do we need it?

Your database may contain internal fields such as:

- Password hashes.
- Internal notes.
- Administrative flags.
- Audit information.

You do not want to return all of these to the client.

Example:

```python
class UserResponse(BaseModel):
    id: int
    name: str
    email: str

@app.get(
    "/users/{user_id}",
    response_model=UserResponse
)
def get_user(user_id: int):

    return {
        "id": user_id,
        "name": "John",
        "email": "john@example.com",
        "password": "secret"
    }
```

FastAPI filters the response to the fields defined in `UserResponse`.

Response models are an important part of API security.

# 20. PATCH requests and exclude_unset

PATCH requests are used to update only selected fields.

Imagine a user has:

```json
{
    "name": "John",
    "email": "john@example.com",
    "age": 25
}
```

The client wants to update only the email.

You do not want to overwrite the other fields.

Define an update model:

```python
class UserUpdate(BaseModel):
    name: str | None = None
    email: str | None = None
    age: int | None = None
```

Endpoint:

```python
@app.patch("/users/{user_id}")
def update_user(
    user_id: int,
    user: UserUpdate
):
    update_data = user.model_dump(
        exclude_unset=True
    )

    return {
        "user_id": user_id,
        "updates": update_data
    }
```

Request:

```json
{
    "email": "new@example.com"
}
```

Result:

```json
{
    "email": "new@example.com"
}
```

Why use `exclude_unset=True`?

It removes fields the client did not provide.

Important distinction:

- `exclude_unset=True`: Removes fields not explicitly supplied.
- `exclude_none=True`: Removes fields whose value is `None`.
- `exclude_defaults=True`: Removes fields equal to their default value.

These are not interchangeable.

If a client sends `"name": null`, `exclude_unset=True` keeps that field because it was explicitly supplied. Your update logic must decide whether null means clear the value or reject the request.

# 21. ORM integration with from_attributes

Sometimes your database returns an ORM object rather than a dictionary.

Example SQLAlchemy object:

```python
user = db.query(User).first()
```

The object has attributes such as:

```python
user.id
user.name
user.email
```

You can configure Pydantic to read those attributes.

```python
class UserResponse(BaseModel):

```

Now:

```python
response = UserResponse.model_validate(user)
```

Pydantic reads the attributes from the ORM object.

Why do we need it?

It lets you return database objects through Pydantic response models without manually converting every field into a dictionary.

# 23. Production-level example — User registration API

This example brings together the main concepts:

- Request model.
- Response model.
- Field validation.
- Custom validators.
- Email validation.
- SecretStr.
- Extra-field rejection.
- HTTP status code.
- Separation of input and output.

Install dependencies:

```bash
pip install fastapi uvicorn "pydantic[email]"
```

Complete example:

```python
from fastapi import FastAPI, HTTPException, status
from pydantic import (
    BaseModel,
    ConfigDict,
    EmailStr,
    Field,
    SecretStr,
    field_validator
)

app = FastAPI()


# INPUT MODEL
class UserCreate(BaseModel):

    model_config = ConfigDict(
        extra="forbid",
        str_strip_whitespace=True
    )

    name: str = Field(
        min_length=2,
        max_length=50,
        description="User's full name"
    )

    email: EmailStr

    password: SecretStr = Field(
        min_length=12,
        max_length=128
    )

    age: int = Field(
        ge=18,
        le=120
    )

    @field_validator("password")
    @classmethod
    def validate_password(cls, value):

        password = value.get_secret_value()

        if not any(char.isdigit() for char in password):
            raise ValueError(
                "Password must contain a digit"
            )

        return value


# OUTPUT MODEL
class UserResponse(BaseModel):

    id: int
    name: str
    email: EmailStr
    age: int


# ENDPOINT
@app.post(
    "/users",
    response_model=UserResponse,
    status_code=status.HTTP_201_CREATED
)
def create_user(user: UserCreate):

    # Production implementation should:
    # 1. Check email uniqueness in the database.
    # 2. Hash the password using Argon2id.
    # 3. Store the user in the database.
    # 4. Return the saved user's public information.

    return {
        "id": 101,
        "name": user.name,
        "email": user.email,
        "age": user.age
    }
```

### What happens when a request arrives?

Request:

```json
{
    "name": "John Smith",
    "email": "john@example.com",
    "password": "StrongPassword123",
    "age": 25
}
```

1. FastAPI receives the HTTP request.
2. Pydantic validates it using `UserCreate`.
3. `Field()` checks length and numerical restrictions.
4. `EmailStr` checks the email format.
5. `field_validator` checks the password rule.
6. FastAPI passes the validated model to the endpoint.
7. Your application performs database operations.
8. `UserResponse` controls the returned fields.
9. FastAPI returns HTTP 201 Created.


# 28. Pydantic Settings and Environment Variables

## 28.1 What is Pydantic Settings?

Pydantic Settings is a library used to manage application configuration.

It allows your FastAPI application to read configuration values from:

- Environment variables.
- `.env` files.
- Secret files.
- Default values.
- Custom configuration sources.

**Why do we need it?**

Imagine your application connects to a PostgreSQL database.

You need:

- Database host.
- Database port.
- Database username.
- Database password.
- Database name.

You should not hardcode these values in your Python code.

Bad practice:

```python
DATABASE_PASSWORD = "mysecretpassword"
DATABASE_HOST = "localhost"
```

Why is this bad?

- Secrets can accidentally be committed to Git.
- Development and production environments need different values.
- Changing configuration requires code changes.
- It makes applications harder to deploy securely.

Instead, use Pydantic Settings.

## 28.2 Installation

Pydantic Settings is a separate package.

```bash
pip install pydantic-settings
```

If you want `.env` file support:

```bash
pip install python-dotenv
```

## 28.3 BaseSettings

`BaseSettings` is the main class used to define application configuration.

Example:

```python
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):

    app_name: str = "My FastAPI App"
    database_host: str
    database_port: int = 5432
    database_username: str
    database_password: str

    model_config = SettingsConfigDict(
        env_file=".env",
        env_file_encoding="utf-8"
    )
```

What happens here?

1. `BaseSettings` tells Pydantic to load configuration from settings sources.
2. `database_host` is required because it has no default.
3. `database_port` defaults to `5432` if no value is supplied.
4. `env_file=".env"` tells Pydantic to read the `.env` file.
5. `env_file_encoding` defines how the file is read.

## 28.4 Environment variables

Environment variables are values stored outside your Python code and provided to your application at runtime.

Example:

```bash
DATABASE_HOST=localhost
DATABASE_PORT=5432
DATABASE_USERNAME=admin
DATABASE_PASSWORD=secret123
```

Pydantic automatically matches environment variable names to settings fields.

For example:

| Environment variable | Python setting |
|---|---|
| `DATABASE_HOST` | `database_host` |
| `DATABASE_PORT` | `database_port` |
| `DATABASE_USERNAME` | `database_username` |
| `DATABASE_PASSWORD` | `database_password` |

By default, Pydantic Settings uses the field name converted to uppercase for environment variable lookup.

## 28.5 The `.env` file

A `.env` file stores configuration values in key-value format.

Example project structure:

```text
project/
│
├── main.py
├── config.py
├── .env
└── .gitignore
```

`.env`:

```env

DATABASE_PORT=5432
DATABASE_USERNAME=admin

```

`config.py`:

```python

    app_name: str
    database_host: str
    database_port: int = 5432
    database_username: str
    database_password: str
```


Now your application reads configuration without hardcoding it.

**Important:** Add `.env` to `.gitignore`. Do not commit real passwords or secrets to Git.

An environment variable prefix adds a common prefix to every setting.

## 28.8 Field aliases in Settings

You can use aliases when your environment variable has a different name from your Python setting.

```python
from pydantic import Field

class Settings(BaseSettings):

    database_url: str = Field(
        validation_alias="DATABASE_URL"
    )
```

Environment variable:

```env
DATABASE_URL=postgresql://user:password@localhost/db
```

Access it using:

```python
settings.database_url
```

`validation_alias` is useful when the environment variable name does not follow the normal field-name convention.

## 28.9 Nested settings

Sometimes configuration is grouped into sections.

Example:

```python
from pydantic import BaseModel
from pydantic_settings import BaseSettings, SettingsConfigDict

class DatabaseSettings(BaseModel):
    host: str
    port: int = 5432

class Settings(BaseSettings):
    database: DatabaseSettings

    model_config = SettingsConfigDict(
        env_nested_delimiter="__"
    )
```

Environment variables:

```env
DATABASE__HOST=localhost
DATABASE__PORT=5432
```

Pydantic interprets these as:

```python
settings.database.host
settings.database.port
```

Why do we need this?

It keeps large application configurations organized.

## 28.10 SecretStr for sensitive configuration

Use `SecretStr` to prevent sensitive values from appearing in normal model representations.

```python
from pydantic import SecretStr
from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    database_password: SecretStr
    api_key: SecretStr
```

Access the actual value when needed:

```python
password = settings.database_password.get_secret_value()
```

Why do we need it?

It reduces accidental exposure when logging or printing settings.

Remember: `SecretStr` does not encrypt a password or protect it from every possible form of exposure.

## 28.11 Environment variable priority

When multiple sources provide the same setting, Pydantic Settings uses a priority order.

By default, the general order from highest to lowest is:

1. Values passed directly when creating `Settings`.
2. Environment variables.
3. Dotenv (`.env`) file values.
4. Secret files.
5. Default values defined in the model.

Example:

`.env`:

```env
DATABASE_HOST=localhost
```

System environment variable:

```bash
export DATABASE_HOST=production-db
```

Python:

```python
settings = Settings()
```

The environment variable wins, so the host becomes:

```text
production-db
```

This is useful because production deployment configuration can override local development configuration.

## 28.12 Caching settings

Creating settings repeatedly can be unnecessary.

FastAPI commonly uses `lru_cache` so configuration is loaded once and reused.

```python
from functools import lru_cache
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    database_url: str

    model_config = SettingsConfigDict(
        env_file=".env"
    )

@lru_cache
def get_settings():
    return Settings()
```

Use it in FastAPI:

```python
from fastapi import Depends, FastAPI

app = FastAPI()

@app.get("/")
def home(settings: Settings = Depends(get_settings)):
    return {
        "database_url_configured": bool(settings.database_url)
    }
```

Why do we need it?

- Avoids repeatedly creating the settings object.
- Gives the application a consistent configuration instance.
- Makes it easier to override settings in tests.

Note: Cached settings do not automatically reload when environment variables change. Restart the application or clear the cache when you need to reload them.

## 28.13 Production example — FastAPI configuration

`config.py`:

```python
from functools import lru_cache
from pydantic import SecretStr
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):

    app_name: str = "My API"
    environment: str = "development"

    database_url: SecretStr
    jwt_secret: SecretStr

    debug: bool = False

    model_config = SettingsConfigDict(
        env_file=".env",
        env_file_encoding="utf-8",
        extra="ignore"
    )

@lru_cache
def get_settings():
    return Settings()
```

`main.py`:

```python
from fastapi import Depends, FastAPI
from config import Settings, get_settings

settings = get_settings()

app = FastAPI(
    title=settings.app_name,
    debug=settings.debug
)

@app.get("/health")
def health_check(
    settings: Settings = Depends(get_settings)
):
    return {
        "status": "healthy",
        "environment": settings.environment
    }
```

`.env`:

```env
APP_NAME=Production API
ENVIRONMENT=production
DATABASE_URL=postgresql://user:password@localhost/mydb
JWT_SECRET=replace-with-a-long-random-secret
DEBUG=false
```

Production considerations:

- Do not commit `.env` files containing secrets.
- Use AWS Secrets Manager, AWS Systems Manager Parameter Store, or another secrets manager for production secrets.
- Use a least-privilege IAM role to retrieve secrets.
- Avoid logging secret values.
- Keep separate configuration for development, testing and production.
- Validate required settings at application startup.
- Remember that settings are loaded when the settings object is created.

## 28.14 Pydantic Settings vs Pydantic BaseModel

| Feature | BaseModel | BaseSettings |
|---|---|---|
| Main purpose | Validate application data | Load and validate application configuration |
| Request body validation | Yes | Not its primary purpose |
| Environment variables | Not automatically | Yes |
| `.env` support | Not built in | Yes, with dotenv support |
| Secret directory support | Not built in | Yes |
| Default values | Yes | Yes |
| Field validation | Yes | Yes |
| Custom validators | Yes | Yes |

**Remember:**

- `BaseModel` is mainly for request data, response data and structured application data.
- `BaseSettings` is mainly for application configuration, environment variables and secrets.

Official documentation: https://docs.pydantic.dev/latest/concepts/pydantic_settings/

### Important production considerations

- Never store plain-text passwords.
- Hash passwords using Argon2id or another appropriate password-hashing algorithm.
- Enforce email uniqueness in the database, not only in application code.
- Never return password hashes.
- Use database transactions for multi-step writes.
- Use authentication and authorization where needed.
- Add rate limiting to sensitive endpoints.
- Keep secrets in a secrets manager or secure environment configuration.
- Pydantic validation does not replace database constraints or business-rule checks.

# 24. Pydantic v1 vs v2 — Important differences

Many older tutorials use Pydantic v1 syntax.

| Pydantic v1 | Pydantic v2 |
|---|---|
| `@validator` | `@field_validator` |
| `@root_validator` | `@model_validator` |
| `.dict()` | `.model_dump()` |
| `.json()` | `.model_dump_json()` |
| `.parse_obj()` | `.model_validate()` |
| `.parse_raw()` | `.model_validate_json()` |
| `.schema()` | `.model_json_schema()` |
| `class Config:` | `model_config = ConfigDict(...)` |
| `orm_mode = True` | `from_attributes=True` |

When learning FastAPI today, focus on Pydantic v2 syntax.

# 27. The most important mental model

Think of Pydantic as having five main responsibilities:

**1. Structure**

`BaseModel` defines what your data should look like.

**2. Rules**

`Field()` and validators define what data is allowed.

**3. Configuration**

`ConfigDict` defines how the model behaves.

**4. Conversion**

Pydantic validates and converts compatible input values.

**5. Output**

Serializers and `model_dump()` control how data is represented when returned or passed to another system.

FastAPI uses these capabilities to validate incoming requests, document your API and control outgoing responses.
