## 103. Middleware Execution Order

### What is middleware execution order?

Middleware is code that runs before and after a request reaches your endpoint.

When an application has multiple middleware components, their execution order matters.

For example, imagine three middleware components:

- Middleware A: Request logging
- Middleware B: Authentication
- Middleware C: Request timing

The request passes through middleware in one order, and the response travels back in the reverse order.

### Example

```python
from fastapi import FastAPI, Request

app = FastAPI()


@app.middleware("http")
async def middleware_a(request: Request, call_next):
    print("A: Before request")

    response = await call_next(request)

    print("A: After response")
    return response


@app.middleware("http")
async def middleware_b(request: Request, call_next):
    print("B: Before request")

    response = await call_next(request)

    print("B: After response")
    return response


@app.get("/")
def home():
    print("Endpoint executed")
    return {"message": "Hello"}
```

With these decorator-based middleware registrations, the last registered middleware is outermost.

Expected output:

```text
B: Before request
A: Before request
Endpoint executed
A: After response
B: After response
```

### Visual flow

```text
Request
   |
   v
Middleware B (before)
   |
   v
Middleware A (before)
   |
   v
Endpoint
   |
   v
Middleware A (after)
   |
   v
Middleware B (after)
   |
   v
Response
```

### What about add_middleware()?

You can also register middleware using:

```python
app.add_middleware(MyMiddleware)
```

Starlette builds the middleware stack so that the most recently added user middleware is outermost among user middleware.

Framework-provided middleware, such as exception handling and server error handling, also participates in the overall stack. Therefore, distinguish user middleware ordering from the complete internal middleware stack.

### Why does order matter?

Consider authentication and logging:

- Logging outside authentication can record requests even when authentication fails.
- Authentication outside some application-level processing can reject requests before they reach that processing.
- Timing middleware placement determines which parts of request processing are measured.

**Production tip:** Put request logging and tracing where they can observe the failures and responses you need to monitor. Avoid logging passwords, tokens or sensitive request bodies.

## 104. Lifespan Events

### What are lifespan events?

Lifespan events allow you to execute code when a FastAPI application starts and when it shuts down.

Typical uses:

- Creating database connection pools.
- Initialising Redis connections.
- Loading machine learning models.
- Creating HTTP clients.
- Cleaning up resources when the application stops.

FastAPI recommends the lifespan approach for managing application startup and shutdown.

### Basic example

```python
from contextlib import asynccontextmanager
from fastapi import FastAPI


@asynccontextmanager
async def lifespan(app: FastAPI):

    print("Application starting")

    # Startup logic
    app.state.message = "Application is ready"

    yield

    # Shutdown logic
    print("Application shutting down")


app = FastAPI(lifespan=lifespan)


@app.get("/")
def home():
    return {
        "message": app.state.message
    }
```

### Explanation

**`@asynccontextmanager`**

Allows an asynchronous function to act as an asynchronous context manager.

**`yield`**

Separates startup logic from shutdown logic.

Everything before `yield` runs during startup.

Everything after `yield` runs during shutdown.

**`app.state`**

Stores application-level state that can be accessed by other parts of the application.

### Example: Manage an HTTP client

```python
from contextlib import asynccontextmanager

import httpx
from fastapi import FastAPI


@asynccontextmanager
async def lifespan(app: FastAPI):

    app.state.http_client = httpx.AsyncClient(
        timeout=10.0
    )

    yield

    await app.state.http_client.aclose()


app = FastAPI(lifespan=lifespan)
```

You can reuse the client instead of creating a new HTTP client for every request.

### Important points

- Startup code runs before the application begins serving requests.
- Shutdown code runs when the application shuts down gracefully.
- If startup fails before `yield`, the application does not finish starting.
- Cleanup should release resources such as database connections and HTTP clients.
- Each worker process has its own application lifespan and resources.

**Important:** Do not use lifespan to run a long-running job that must survive application restarts. Use a dedicated background worker system for that.

## 105. Startup and Shutdown Management

### What is startup management?

Startup management means preparing the application before it starts accepting requests.

Examples:

- Connecting to a database.
- Initialising Redis.
- Loading configuration.
- Checking required services.
- Loading machine learning models.

### What is shutdown management?

Shutdown management means cleaning up resources when the application stops.

Examples:

- Closing database pools.
- Closing Redis connections.
- Closing HTTP clients.
- Releasing resources.

### Complete example with multiple resources

```python
from contextlib import asynccontextmanager

import httpx
from fastapi import FastAPI


@asynccontextmanager
async def lifespan(app: FastAPI):

    print("Starting application")

    app.state.http_client = httpx.AsyncClient()

    app.state.cache = {
        "status": "connected"
    }

    try:
        yield

    finally:
        print("Closing application")

        await app.state.http_client.aclose()

        app.state.cache.clear()


app = FastAPI(lifespan=lifespan)
```

### What if startup fails?

Suppose your application requires a database connection.

If the database is unavailable, you may want startup to fail rather than allowing the application to serve requests that cannot succeed.

```python
from contextlib import asynccontextmanager
from fastapi import FastAPI


@asynccontextmanager
async def lifespan(app: FastAPI):

    database = await connect_to_database()

    app.state.database = database

    try:
        yield
    finally:
        await database.close()


app = FastAPI(lifespan=lifespan)
```

Here, `connect_to_database()` represents your database connection function.

### Are startup and shutdown event decorators still used?

You may encounter:

```python
@app.on_event("startup")
async def startup():
    print("Starting")


@app.on_event("shutdown")
async def shutdown():
    print("Stopping")
```

These are legacy event-handler APIs. Prefer the lifespan parameter for new applications.

### Lifespan versus startup/shutdown events

| Lifespan | Legacy event decorators |
|---|---|
| Recommended approach | Older approach |
| One context manager | Separate functions |
| Startup and cleanup are paired | Startup and shutdown are separate |
| Supports resource management naturally | Resource management needs more manual coordination |

## 106. Background Task Processing

### What are background tasks?

Background tasks allow FastAPI to send a response without waiting for certain additional work to finish.

For example:

A user registers on your website.

1. API creates the user.
2. API returns a response.
3. API sends a welcome email in the background.

### Example using BackgroundTasks

```python
from fastapi import FastAPI, BackgroundTasks

app = FastAPI()


def send_email(email: str):
    print(f"Sending email to {email}")


@app.post("/register")
def register_user(
    email: str,
    background_tasks: BackgroundTasks
):

    # Add task to execute after response handling
    background_tasks.add_task(
        send_email,
        email
    )

    return {
        "message": "User registered"
    }
```

### Explanation

**`BackgroundTasks`**

FastAPI provides this object to schedule functions to run after the response has been sent.

**`add_task()`**

Registers a function and its arguments.

Syntax:

```python
background_tasks.add_task(
    function,
    argument1,
    argument2
)
```

### Multiple background tasks

```python
@app.post("/orders")
def create_order(background_tasks: BackgroundTasks):

    background_tasks.add_task(send_email, "user@example.com")

    background_tasks.add_task(
        generate_invoice,
        101
    )

    return {
        "message": "Order created"
    }
```

### Async background task

```python
async def send_notification(email: str):
    await some_async_notification_service(email)
```

You can register an async function as a background task too.

### Important: BackgroundTasks versus Celery

FastAPI `BackgroundTasks` is suitable for relatively small tasks.

It is not a full distributed task queue.

| BackgroundTasks | Celery / distributed workers |
|---|---|
| Built into FastAPI | Separate worker infrastructure |
| Simple tasks | Complex or long-running tasks |
| Runs within the application process | Runs in separate worker processes |
| No built-in durable task queue | Can use brokers such as Redis or RabbitMQ |
| Task can be lost if process crashes | Can support retries and durable processing, depending on configuration |

### When should you use Celery or another worker system?

Use a dedicated task queue for:

- Large file processing.
- Video conversion.
- Bulk email campaigns.
- Long-running reports.
- Scheduled jobs.
- Tasks requiring retries.
- Tasks that must survive application restarts.

**Production tip:** A background task should not be treated as a guarantee that the work will finish. For important work, store the job in durable infrastructure and monitor its status.

## 107. WebSockets

### What are WebSockets?

HTTP normally follows a request-response model:

1. Client sends request.
2. Server sends response.
3. Connection can be closed.

WebSockets allow a persistent, two-way communication channel between client and server.

Both client and server can send messages without establishing a new HTTP request for each message.

### Common use cases

- Chat applications.
- Live notifications.
- Real-time dashboards.
- Multiplayer games.
- Live tracking.
- Collaborative applications.

### Basic WebSocket example

```python
from fastapi import FastAPI, WebSocket

app = FastAPI()


@app.websocket("/ws")
async def websocket_endpoint(websocket: WebSocket):

    await websocket.accept()

    while True:

        message = await websocket.receive_text()

        await websocket.send_text(
            f"Server received: {message}"
        )
```

### Explanation

**`@app.websocket("/ws")`**

Defines a WebSocket endpoint.

**`websocket.accept()`**

Accepts the WebSocket connection.

**`receive_text()`**

Receives a text message from the client.

**`send_text()`**

Sends a text message to the client.

### Handling disconnections

```python
from fastapi import WebSocket, WebSocketDisconnect


@app.websocket("/ws")
async def websocket_endpoint(websocket: WebSocket):

    await websocket.accept()

    try:

        while True:

            message = await websocket.receive_text()

            await websocket.send_text(message)

    except WebSocketDisconnect:

        print("Client disconnected")
```

### WebSocket with JSON messages

```python
@app.websocket("/ws-json")
async def websocket_json(websocket: WebSocket):

    await websocket.accept()

    while True:

        data = await websocket.receive_json()

        await websocket.send_json({
            "received": data
        })
```

### Broadcasting to multiple clients

For a simple single-process example:

```python
from fastapi import WebSocket, WebSocketDisconnect


class ConnectionManager:

    def __init__(self):
        self.connections = []

    async def connect(self, websocket: WebSocket):
        await websocket.accept()
        self.connections.append(websocket)

    def disconnect(self, websocket: WebSocket):
        self.connections.remove(websocket)

    async def broadcast(self, message: str):

        for connection in self.connections:
            await connection.send_text(message)


manager = ConnectionManager()


@app.websocket("/chat")
async def chat(websocket: WebSocket):

    await manager.connect(websocket)

    try:
        while True:

            message = await websocket.receive_text()

            await manager.broadcast(message)

    except WebSocketDisconnect:
        manager.disconnect(websocket)
```

This is a basic demonstration, not a production-ready multi-worker solution.

### Production considerations

- Authenticate WebSocket connections.
- Validate incoming messages.
- Handle disconnects and network failures.
- Use Redis Pub/Sub or another shared messaging system when broadcasting across multiple workers or instances.
- Apply rate limits and message-size limits.
- Consider heartbeat and connection cleanup strategies.

### HTTP versus WebSocket

| HTTP | WebSocket |
|---|---|
| Request-response | Two-way communication |
| Usually separate requests | Persistent connection |
| Suitable for CRUD APIs | Suitable for real-time messaging |
| Client normally initiates requests | Both sides can send messages |

## 108. File Uploads

### What are file uploads?

FastAPI supports uploading files through HTTP requests.

It provides:

- `UploadFile`
- `File`

`UploadFile` is generally preferred for larger files because it uses a spooled temporary file instead of loading the entire file into memory immediately.

### Install dependency

```bash
pip install python-multipart
```

### Example 1: Upload a file

```python
from fastapi import FastAPI, UploadFile, File

app = FastAPI()


@app.post("/upload")
async def upload_file(
    file: UploadFile = File(...)
):

    return {
        "filename": file.filename,
        "content_type": file.content_type
    }
```

### Important attributes

| Attribute | Purpose |
|---|---|
| `filename` | Original filename supplied by the client |
| `content_type` | Client-provided content type |
| `file` | Underlying file-like object |
| `size` | Not a standard guaranteed UploadFile attribute; calculate size by reading or inspecting the file |

### Example 2: Read uploaded content

```python
@app.post("/upload")
async def upload_file(file: UploadFile = File(...)):

    content = await file.read()

    return {
        "filename": file.filename,
        "size": len(content)
    }
```

Be careful with large files because `read()` without a size loads the complete content into memory.

### Example 3: Save a file in chunks

```python
from pathlib import Path

UPLOAD_DIR = Path("uploads")
UPLOAD_DIR.mkdir(exist_ok=True)


@app.post("/upload")
async def upload_file(file: UploadFile = File(...)):

    safe_filename = Path(file.filename or "upload.bin").name
    file_path = UPLOAD_DIR / safe_filename

    try:
        with file_path.open("wb") as output:

            while chunk := await file.read(1024 * 1024):
                output.write(chunk)

    finally:
        await file.close()

    return {
        "message": "File uploaded",
        "filename": safe_filename
    }
```

This demonstrates chunked reading, but production applications must also prevent filename collisions and validate the file before storing it.

### Example 4: Upload multiple files

```python
from typing import List
from fastapi import UploadFile, File


@app.post("/upload-multiple")
async def upload_multiple(
    files: List[UploadFile] = File(...)
):

    return {
        "filenames": [
            file.filename for file in files
        ]
    }
```

### Important production security checks

1. Set maximum upload size at the proxy/server or application layer.
2. Validate file extensions and actual file contents.
3. Do not trust `content_type` supplied by the client.
4. Generate safe server-side filenames.
5. Prevent path traversal.
6. Scan untrusted files when appropriate.
7. Store uploads outside publicly executable directories.
8. Use object storage such as S3 for scalable file storage.

## 109. Streaming Responses

### What is a streaming response?

Normally, an endpoint returns a complete response.

For example:

```python
@app.get("/data")
def get_data():
    return {
        "message": "Complete response"
    }
```

The server serialises the response and sends it to the client.

With streaming, the server sends data in chunks instead of preparing one complete response body first.

### Why use streaming?

- Large file downloads.
- Large datasets.
- Server-sent event streams.
- Generated content.
- Reducing memory use for suitable workloads.

### Example 1: Streaming text

```python
from fastapi.responses import StreamingResponse


def generate_data():

    for i in range(5):
        yield f"Data chunk {i}\n"


@app.get("/stream")
def stream_data():

    return StreamingResponse(
        generate_data(),
        media_type="text/plain"
    )
```

### Explanation

**`StreamingResponse`**

Sends an iterable or async iterable as a response stream.

**`yield`**

Produces one chunk at a time.

**`media_type`**

Defines the response content type.

### Example 2: Async streaming

```python
import asyncio
from fastapi.responses import StreamingResponse


async def generate_data():

    for i in range(5):

        yield f"Chunk {i}\n"

        await asyncio.sleep(1)


@app.get("/async-stream")
async def async_stream():

    return StreamingResponse(
        generate_data(),
        media_type="text/plain"
    )
```

### Example 3: Stream a large file

```python
from pathlib import Path
from fastapi.responses import StreamingResponse


@app.get("/download")
def download_file():

    file_path = Path("large_file.csv")

    def file_iterator():

        with file_path.open("rb") as file:

            while chunk := file.read(1024 * 1024):
                yield chunk

    return StreamingResponse(
        file_iterator(),
        media_type="text/csv",
        headers={
            "Content-Disposition": 'attachment; filename="data.csv"'
        }
    )
```

For ordinary file downloads, `FileResponse` is often simpler and supports file-specific features such as range requests.

### StreamingResponse versus JSONResponse

| StreamingResponse | JSONResponse |
|---|---|
| Sends chunks | Sends a complete response body |
| Useful for large or generated content | Useful for normal JSON APIs |
| Supports iterators and async iterators | Serialises JSON content |
| Does not automatically validate chunks against a Pydantic response model | Serialises JSON data |

### Production considerations

- Handle client disconnections.
- Close files and resources correctly.
- Avoid generating enormous chunks.
- Consider reverse proxy buffering.
- Set suitable response headers.
- Remember that streaming does not automatically make a slow database query faster.

## 110. Custom Request and Response Classes

### What are custom request and response classes?

FastAPI uses Starlette request and response infrastructure.

You can create custom classes when you need to change how request data is accessed or how responses are produced.

Common examples:

- Custom response formats.
- Custom serialisation.
- Special response headers.
- Custom request body handling.
- Integration with specialised response types.

### Part A: Custom Response Class

You can inherit from `Response` or an existing response class.

Example:

```python
from fastapi import FastAPI
from fastapi.responses import Response

app = FastAPI()


class PlainTextResponse(Response):

    media_type = "text/plain"

    def __init__(self, content: str):
        super().__init__(content=content)


@app.get("/hello")
def hello():

    return PlainTextResponse(
        "Hello from custom response"
    )
```

### Part B: Set a default response class

```python
from fastapi.responses import ORJSONResponse

app = FastAPI(
    default_response_class=ORJSONResponse
)
```

This uses `ORJSONResponse` as the default response class for routes that do not specify another response class.

Install its dependency:

```bash
pip install orjson
```

### Part C: Custom request class

Starlette allows you to subclass its `Request` class.

```python
from starlette.requests import Request


class CustomRequest(Request):

    @property
    def custom_client_ip(self):

        forwarded = self.headers.get(
            "x-forwarded-for"
        )

        if forwarded:
            return forwarded.split(",")[0].strip()

        return (
            self.client.host
            if self.client
            else None
        )
```

You can use this class directly when constructing a request in a custom ASGI component or helper.

For example, a custom ASGI middleware can construct it:

```python
from starlette.types import ASGIApp, Scope, Receive, Send


class CustomRequestMiddleware:

    def __init__(self, app: ASGIApp):
        self.app = app

    async def __call__(
        self,
        scope: Scope,
        receive: Receive,
        send: Send
    ):

        if scope["type"] == "http":

            request = CustomRequest(
                scope,
                receive=receive
            )

            scope.setdefault("state", {})
            scope["state"]["client_ip"] = (
                request.custom_client_ip
            )

        await self.app(scope, receive, send)
```

Then access the value:

```python
from fastapi import Request

@app.get("/client")
async def client(request: Request):

    return {
        "client_ip": request.state.client_ip
    }
```

### Important distinction

- `response_class` selects how FastAPI constructs a response from returned data.
- Returning a Response object directly bypasses some of FastAPI's automatic response-model processing.
- A custom Request class does not automatically replace FastAPI's request object everywhere. You must integrate it through an appropriate ASGI component or use it directly.

## 111. Custom OpenAPI Documentation

### What is OpenAPI?

OpenAPI is a machine-readable specification describing your API.

FastAPI automatically generates an OpenAPI schema.

Default URLs:

```text
/docs
/redoc
/openapi.json
```

### Why customise OpenAPI?

- Add API descriptions.
- Add contact information.
- Add licence information.
- Add authentication schemes.
- Add custom documentation metadata.
- Modify the generated schema.

### Example 1: Configure OpenAPI metadata

```python
from fastapi import FastAPI

app = FastAPI(
    title="E-commerce API",
    description="API for managing products and orders",
    version="2.0.0",
    contact={
        "name": "API Support",
        "email": "support@example.com"
    },
    license_info={
        "name": "MIT"
    }
)
```

### Example 2: Add tags and descriptions

```python
tags_metadata = [
    {
        "name": "Users",
        "description": "Operations related to users"
    },
    {
        "name": "Products",
        "description": "Operations related to products"
    }
]

app = FastAPI(
    openapi_tags=tags_metadata
)
```

### Example 3: Customise the OpenAPI schema

```python
from fastapi import FastAPI
from fastapi.openapi.utils import get_openapi

app = FastAPI(
    title="My API",
    version="1.0.0"
)


def custom_openapi():

    if app.openapi_schema:
        return app.openapi_schema

    openapi_schema = get_openapi(
        title=app.title,
        version=app.version,
        description="Custom API documentation",
        routes=app.routes
    )

    openapi_schema["info"]["x-company"] = "Example Company"

    app.openapi_schema = openapi_schema

    return app.openapi_schema


app.openapi = custom_openapi
```

### Explanation

**`get_openapi()`**

Generates an OpenAPI schema from the application's routes.

**`app.openapi_schema`**

Caches the generated schema.

**`app.openapi = custom_openapi`**

Replaces the default OpenAPI generation function.

### Important points

- OpenAPI describes your API; it does not implement authentication.
- Do not expose internal endpoints or sensitive information in public documentation.
- If you modify the schema, ensure it remains valid OpenAPI.
- Clear the schema cache if you change routes or schema metadata dynamically.

## 112. API Versioning

### What is API versioning?

API versioning allows you to introduce changes without unexpectedly breaking existing clients.

Imagine you have:

Version 1:

```json
{
  "first_name": "Alice",
  "last_name": "Smith"
}
```

Version 2:

```json
{
  "full_name": "Alice Smith"
}
```

Existing clients may still depend on the V1 response.

Instead of breaking them, provide separate API versions.

### Common API versioning approaches

**1. URL path versioning**

```text
/api/v1/users
/api/v2/users
```

This is straightforward and commonly used.

**2. Query parameter versioning**

```text
/users?version=1
/users?version=2
```

**3. Header versioning**

```http
GET /users
API-Version: 2
```

**4. Media type versioning**

```http
Accept: application/vnd.example.v2+json
```

### Example: Versioning with APIRouter

`routers/v1/users.py`

```python
from fastapi import APIRouter

router = APIRouter(
    prefix="/users",
    tags=["Users V1"]
)


@router.get("/")
def get_users():

    return {
        "version": 1,
        "users": ["Alice", "Bob"]
    }
```

`routers/v2/users.py`

```python
from fastapi import APIRouter

router = APIRouter(
    prefix="/users",
    tags=["Users V2"]
)


@router.get("/")
def get_users():

    return {
        "version": 2,
        "users": [
            {
                "full_name": "Alice"
            },
            {
                "full_name": "Bob"
            }
        ]
    }
```

`main.py`

```python
from fastapi import FastAPI

from app.routers.v1 import users as users_v1
from app.routers.v2 import users as users_v2

app = FastAPI()

app.include_router(
    users_v1.router,
    prefix="/api/v1"
)

app.include_router(
    users_v2.router,
    prefix="/api/v2"
)
```

Endpoints:

```text
GET /api/v1/users/
GET /api/v2/users/
```

### Best practices

- Keep old versions available during a planned migration period.
- Document breaking changes.
- Avoid maintaining unnecessary versions forever.
- Share business logic between versions where appropriate.
- Keep version-specific schemas and route behaviour separate.

**Important:** FastAPI does not impose one built-in API versioning strategy. You implement the approach that suits your API.

## 113. Pagination

### What is pagination?

Pagination divides a large result set into smaller pages.

Imagine a database contains 10,000 users.

Returning all users in one API response is inefficient.

Instead, return a limited number at a time.

### Common pagination approaches

1. Offset/limit pagination.
2. Page-number pagination.
3. Cursor-based pagination.

### Example 1: Offset and limit

```python
from fastapi import FastAPI, Query

app = FastAPI()

users = [
    {"id": i, "name": f"User {i}"}
    for i in range(1, 101)
]


@app.get("/users")
def get_users(
    skip: int = Query(0, ge=0),
    limit: int = Query(10, ge=1, le=100)
):

    return users[skip:skip + limit]
```

Request:

```text
GET /users?skip=10&limit=10
```

This returns records 11–20.

### Explanation

**`skip`**

Number of records to skip.

**`limit`**

Maximum number of records to return.

**`ge=0`**

Value must be greater than or equal to zero.

**`le=100`**

Value must be less than or equal to 100.

### Example 2: Page-number pagination

```python
@app.get("/users-page")
def get_users_page(
    page: int = Query(1, ge=1),
    page_size: int = Query(10, ge=1, le=100)
):

    offset = (page - 1) * page_size

    results = users[
        offset:offset + page_size
    ]

    return {
        "page": page,
        "page_size": page_size,
        "results": results
    }
```

Request:

```text
GET /users-page?page=2&page_size=10
```

### Example 3: Pagination response with metadata

```python
@app.get("/users-paginated")
def get_users_paginated(
    page: int = Query(1, ge=1),
    page_size: int = Query(10, ge=1, le=100)
):

    total = len(users)

    offset = (page - 1) * page_size

    results = users[
        offset:offset + page_size
    ]

    return {
        "items": results,
        "page": page,
        "page_size": page_size,
        "total": total,
        "total_pages": (total + page_size - 1) // page_size
    }
```

### Example response

```json
{
  "items": [
    {"id": 11, "name": "User 11"}
  ],
  "page": 2,
  "page_size": 10,
  "total": 100,
  "total_pages": 10
}
```

### Cursor-based pagination

Offset pagination can become expensive for large datasets because the database may need to scan and skip many rows.

Cursor pagination uses a stable value, such as the last returned ID.

Conceptual SQL:

```sql
SELECT *
FROM users
WHERE id > :last_seen_id
ORDER BY id
LIMIT :page_size;
```

Example endpoint logic:

```python
@app.get("/users-cursor")
def get_users_cursor(
    after_id: int = Query(0, ge=0),
    limit: int = Query(10, ge=1, le=100)
):

    results = [
        user for user in users
        if user["id"] > after_id
    ][:limit]

    next_cursor = (
        results[-1]["id"]
        if results
        else None
    )

    return {
        "items": results,
        "next_cursor": next_cursor
    }
```

This in-memory example illustrates the concept. A real database query should use an indexed, stable ordering and an opaque or signed cursor when appropriate.

### Pagination comparison

| Offset pagination | Cursor pagination |
|---|---|
| Easy to understand | More complex |
| Supports jumping to page numbers | Usually supports next/previous navigation |
| Large offsets can be expensive | Often more efficient for large datasets |
| Can be affected by inserts/deletes between pages | More stable with suitable cursor ordering |

## 114. Filtering and Sorting

### What is filtering?

Filtering means returning only records that match specified conditions.

Example:

```text
GET /products?category=electronics
```

### What is sorting?

Sorting means arranging records in a particular order.

Example:

```text
GET /products?sort_by=price&order=asc
```

### Example data

```python
products = [
    {"id": 1, "name": "Laptop", "category": "electronics", "price": 1000},
    {"id": 2, "name": "Phone", "category": "electronics", "price": 500},
    {"id": 3, "name": "Chair", "category": "furniture", "price": 150}
]
```

### Example 1: Filtering

```python
from typing import Optional
from fastapi import Query


@app.get("/products")
def get_products(
    category: Optional[str] = None,
    min_price: Optional[float] = Query(None, ge=0),
    max_price: Optional[float] = Query(None, ge=0)
):

    results = products

    if category:
        results = [
            p for p in results
            if p["category"] == category
        ]

    if min_price is not None:
        results = [
            p for p in results
            if p["price"] >= min_price
        ]

    if max_price is not None:
        results = [
            p for p in results
            if p["price"] <= max_price
        ]

    return results
```

Request:

```text
GET /products?category=electronics&min_price=400
```

### Example 2: Sorting

```python
@app.get("/products-sorted")
def get_products_sorted(
    sort_by: str = "price",
    order: str = "asc"
):

    allowed_fields = {
        "price",
        "name",
        "id"
    }

    if sort_by not in allowed_fields:
        raise HTTPException(
            status_code=400,
            detail="Invalid sort field"
        )

    if order not in {"asc", "desc"}:
        raise HTTPException(
            status_code=400,
            detail="Invalid sort order"
        )

    return sorted(
        products,
        key=lambda p: p[sort_by],
        reverse=(order == "desc")
    )
```

### Example 3: Combine filtering, sorting and pagination

```python
@app.get("/products-search")
def search_products(
    category: str | None = None,
    sort_by: str = "price",
    order: str = "asc",
    page: int = Query(1, ge=1),
    page_size: int = Query(10, ge=1, le=100)
):

    results = products

    if category:
        results = [
            p for p in results
            if p["category"] == category
        ]

    if sort_by not in {"id", "name", "price"}:
        raise HTTPException(400, "Invalid sort field")

    if order not in {"asc", "desc"}:
        raise HTTPException(400, "Invalid sort order")

    results = sorted(
        results,
        key=lambda p: p[sort_by],
        reverse=(order == "desc")
    )

    total = len(results)

    start = (page - 1) * page_size

    results = results[start:start + page_size]

    return {
        "items": results,
        "total": total,
        "page": page,
        "page_size": page_size
    }
```

### Production considerations

- Use database queries rather than filtering large datasets in Python.
- Whitelist allowed sort fields.
- Never insert untrusted user input directly into SQL.
- Add indexes to frequently filtered and sorted columns.
- Validate ranges and page sizes.
- Consider case-insensitive and partial matching requirements.

## 115. Bulk Operations

### What are bulk operations?

Bulk operations allow an API to process multiple records in a single request.

Examples:

- Create 100 users.
- Update multiple products.
- Delete selected records.
- Import a list of transactions.

Instead of sending one HTTP request per record, the client sends one request containing multiple records.

### Example 1: Bulk create

```python
from pydantic import BaseModel, EmailStr
from fastapi import HTTPException


class UserCreate(BaseModel):
    name: str
    email: EmailStr


@app.post("/users/bulk")
def bulk_create_users(users: list[UserCreate]):

    if len(users) > 100:
        raise HTTPException(
            status_code=400,
            detail="Maximum 100 users allowed"
        )

    created_users = []

    for index, user in enumerate(users, start=1):

        created_users.append({
            "id": index,
            **user.model_dump()
        })

    return {
        "created_count": len(created_users),
        "users": created_users
    }
```

Request:

```json
[
  {
    "name": "Alice",
    "email": "alice@example.com"
  },
  {
    "name": "Bob",
    "email": "bob@example.com"
  }
]
```

### Example 2: Bulk update

```python
class UserUpdate(BaseModel):
    id: int
    name: str


@app.put("/users/bulk")
def bulk_update_users(
    updates: list[UserUpdate]
):

    updated = []

    for user in updates:

        updated.append({
            "id": user.id,
            "name": user.name
        })

    return {
        "updated_count": len(updated),
        "users": updated
    }
```

This is an illustrative example. A production implementation would update actual database records.

### Example 3: Bulk delete

```python
class BulkDeleteRequest(BaseModel):
    ids: list[int]


@app.post("/users/bulk-delete")
def bulk_delete_users(
    request: BulkDeleteRequest
):

    return {
        "deleted_ids": request.ids,
        "deleted_count": len(request.ids)
    }
```

### Important production considerations

- Set a maximum batch size.
- Validate every item.
- Decide whether the operation is all-or-nothing or allows partial success.
- Use database transactions where appropriate.
- Return clear per-record errors when partial success is supported.
- Consider asynchronous processing for very large batches.
- Protect bulk endpoints with suitable permissions and rate limits.

**Important:** Bulk operations should have clearly defined transaction and failure semantics. Do not silently report success when some records failed.

## 116. Idempotency

### What is idempotency?

An operation is idempotent when repeating the same operation produces the same intended result as performing it once.

Example:

A client sends a payment request.

The server processes the payment, but the response is lost due to a network problem.

The client retries the request.

Without idempotency, the customer could be charged twice.

With idempotency, the server recognises the repeated request and returns the original result instead of processing the payment again.

### Common use cases

- Payment processing.
- Order creation.
- Booking systems.
- Financial transactions.
- External API calls.
- Retried requests.

### Idempotency-Key header

The client sends a unique key:

```http
POST /payments
Idempotency-Key: payment-12345
Content-Type: application/json
```

### Simplified in-memory example

```python
from fastapi import FastAPI, Header, HTTPException

app = FastAPI()

idempotency_store = {}


@app.post("/payments")
def create_payment(
    amount: float,
    idempotency_key: str = Header(...)
):

    if idempotency_key in idempotency_store:

        return idempotency_store[idempotency_key]

    if amount <= 0:
        raise HTTPException(
            status_code=400,
            detail="Invalid amount"
        )

    result = {
        "payment_id": "PAY-1001",
        "amount": amount,
        "status": "success"
    }

    idempotency_store[idempotency_key] = result

    return result
```

### How does this work?

First request:

```text
Idempotency-Key: payment-12345
```

The server processes the payment and stores the result.

Second request:

```text
Idempotency-Key: payment-12345
```

The server returns the stored result.

The payment is not processed again.

### Why is this example not production-ready?

An in-memory dictionary:

- Is lost when the application restarts.
- Is not shared across multiple workers.
- Does not safely handle simultaneous requests with the same key.
- Does not detect the same key being reused with a different request body.

### Production implementation

Use a persistent database or Redis with an atomic operation.

A robust idempotency record should typically store:

```text
idempotency_key
request_hash
status
response_body
created_at
expires_at
```

Recommended flow:

1. Client sends an idempotency key.
2. Server calculates a hash of the request payload.
3. Server atomically claims the key.
4. If the key already exists with the same payload, return or wait for the existing result.
5. If the key exists with a different payload, reject the request.
6. Process the operation.
7. Store the final result.
8. Return the result to the client.

Use database transactions and unique constraints where appropriate.

### Idempotent HTTP methods

| Method | Idempotent by HTTP semantics? |
|---|---|
| GET | Yes |
| HEAD | Yes |
| PUT | Yes |
| DELETE | Yes |
| POST | Not necessarily |
| PATCH | Not necessarily |

Idempotency does not mean the response must always be identical. It means the intended server-side effect of repeating the request is the same.

## 117. Caching with Redis

### What is caching?

Caching stores frequently accessed data so that it can be returned faster without repeating expensive work.

Example:

A product API reads product details from a database.

Without caching:

```text
Client
  |
  v
FastAPI
  |
  v
Database
  |
  v
Response
```

With caching:

```text
Client
  |
  v
FastAPI
  |
  v
Redis Cache
  |
  +---- Cache hit ----> Return cached data
  |
  +---- Cache miss ---> Database
                           |
                           v
                       Store in Redis
                           |
                           v
                       Return response
```

### Why Redis?

Redis is an in-memory data store commonly used for:

- Caching.
- Session storage.
- Rate limiting.
- Distributed locks.
- Messaging.
- Temporary data.

### Install Redis client

```bash
pip install redis
```

You also need a running Redis server.

### Example 1: Connect to Redis using lifespan

```python
from contextlib import asynccontextmanager

import redis.asyncio as redis
from fastapi import FastAPI


@asynccontextmanager
async def lifespan(app: FastAPI):

    app.state.redis = redis.from_url(
        "redis://localhost:6379",
        decode_responses=True
    )

    try:
        yield
    finally:
        await app.state.redis.aclose()


app = FastAPI(lifespan=lifespan)
```

### Example 2: Store and retrieve cached data

```python
import json
from fastapi import Request


@app.get("/products/{product_id}")
async def get_product(
    product_id: int,
    request: Request
):

    cache = request.app.state.redis

    cache_key = f"product:{product_id}"

    cached_data = await cache.get(cache_key)

    if cached_data:

        return json.loads(cached_data)

    # Normally retrieve this from the database
    product = {
        "id": product_id,
        "name": "Laptop",
        "price": 1000
    }

    await cache.set(
        cache_key,
        json.dumps(product),
        ex=300
    )

    return product
```

### Explanation

**`get()`**

Reads a value from Redis.

**`set()`**

Stores a value.

**`ex=300`**

Sets the expiration time to 300 seconds (5 minutes).

After expiration, Redis no longer returns that cached value.

### Example 3: Cache invalidation

When a product is updated, its cached value must be invalidated.

```python
@app.put("/products/{product_id}")
async def update_product(
    product_id: int,
    request: Request
):

    cache = request.app.state.redis

    # Update the database here

    await cache.delete(
        f"product:{product_id}"
    )

    return {
        "message": "Product updated"
    }
```

### Common caching strategies

**1. Cache-aside**

Application checks the cache first. If the data is missing, it reads from the database and stores the result in the cache.

**2. Write-through**

Application updates the cache and database as part of the write workflow.

**3. Write-behind**

Application writes to the cache first and persists to the database later. This requires careful durability and failure handling.

### Important Redis caching concepts

| Concept | Meaning |
|---|---|
| TTL | Time to live; how long a cache entry remains valid |
| Cache hit | Requested data exists in cache |
| Cache miss | Requested data is not in cache |
| Cache invalidation | Removing or refreshing stale cached data |
| Eviction | Removing data when Redis needs memory |
| Cache stampede | Many requests simultaneously recompute the same missing value |

### Production considerations

- Do not cache sensitive data without considering access control.
- Use appropriate TTL values.
- Invalidate or update cached values after writes.
- Use consistent cache keys.
- Handle Redis outages gracefully.
- Avoid caching data that must always be strongly consistent.
- Consider stampede protection for expensive queries.
- Monitor cache hit ratio and memory usage.

## 118. API Performance Optimisation

### What is API performance optimisation?

It means improving how quickly and efficiently an API handles requests.

Important performance measurements include:

- Latency: Time taken to process a request.
- Throughput: Number of requests handled per second.
- CPU usage.
- Memory usage.
- Database query time.
- Error rate.
- P95/P99 latency: Request latency percentiles.

### 1. Use async endpoints for I/O-bound work

Blocking endpoint:

```python
import requests

@app.get("/external")
def get_external_data():

    response = requests.get(
        "https://example.com/api"
    )

    return response.json()
```

`requests.get()` blocks the thread while waiting for the response.

Async version:

```python
import httpx

@app.get("/external")
async def get_external_data():

    async with httpx.AsyncClient() as client:

        response = await client.get(
            "https://example.com/api"
        )

    return response.json()
```

For production applications, reuse an `httpx.AsyncClient` through lifespan rather than creating a new client for every request.

**Important:** Async is particularly useful for I/O-bound operations. It does not automatically make CPU-intensive Python code faster.

### 2. Use database connection pooling

Creating a new database connection for every request can be expensive.

Use a connection pool to reuse connections.

Example with SQLAlchemy:

```python
from sqlalchemy.ext.asyncio import create_async_engine

engine = create_async_engine(
    "postgresql+asyncpg://user:password@localhost/db",
    pool_size=10,
    max_overflow=20,
    pool_pre_ping=True
)
```

**Important parameters:**

- `pool_size`: Number of connections maintained in the pool.
- `max_overflow`: Additional temporary connections allowed above the pool size.
- `pool_pre_ping`: Checks whether a connection is alive before using it.

Choose pool sizes based on database capacity and the total number of application workers.

### 3. Avoid N+1 database queries

Bad approach:

```python
users = await get_users()

for user in users:
    user.orders = await get_orders(user.id)
```

If there are 100 users, this can generate 101 database queries.

Better approach:

Fetch related data using a join, eager loading, or a batch query.

Conceptual SQL:

```sql
SELECT users.*, orders.*
FROM users
LEFT JOIN orders
ON users.id = orders.user_id;
```

This can reduce the number of database round trips.

### 4. Use pagination

Avoid returning thousands of records in a single response.

```python
@app.get("/users")
def get_users(
    page: int = 1,
    page_size: int = 20
):
    ...
```

Set reasonable maximum page sizes and use cursor pagination for suitable large datasets.

### 5. Use Redis caching

Cache frequently requested data.

```python
cached_data = await redis_client.get("products")

if cached_data:
    return cached_data
```

This can reduce repeated database queries.

### 6. Use response models

```python
from pydantic import BaseModel

class UserResponse(BaseModel):
    id: int
    name: str
    email: str


@app.get(
    "/users/{user_id}",
    response_model=UserResponse
)
async def get_user(user_id: int):
    ...
```

Response models provide validation, serialisation and control over the output.

They are not automatically faster in every situation. For very large or performance-sensitive responses, benchmark the serialisation path.

### 7. Avoid unnecessary response data

Do not return fields the client does not need.

Bad:

```json
{
  "id": 1,
  "name": "Alice",
  "email": "alice@example.com",
  "password_hash": "...",
  "internal_notes": "...",
  "audit_history": []
}
```

Better:

```json
{
  "id": 1,
  "name": "Alice",
  "email": "alice@example.com"
}
```

Smaller responses reduce network transfer and processing costs.

### 8. Use compression where appropriate

Compression can reduce response size.

For example:

```python
from fastapi.middleware.gzip import GZipMiddleware

app.add_middleware(
    GZipMiddleware,
    minimum_size=1000
)
```

Responses larger than the configured threshold can be compressed when the client supports compression.

Compression consumes CPU, so measure whether it benefits your workload.

### 9. Use efficient JSON serialisation when justified

FastAPI supports alternative response classes such as `ORJSONResponse`.

```python
from fastapi.responses import ORJSONResponse

app = FastAPI(
    default_response_class=ORJSONResponse
)
```

Benchmark before changing the default response class. Faster serialisation may not matter if database queries dominate request time.

### 10. Move CPU-intensive work out of request handling

Examples:

- Image processing.
- Machine learning inference.
- Video conversion.
- Large report generation.
- Complex data transformations.

Use separate worker processes or specialised compute infrastructure where appropriate.

A normal `async def` function does not make CPU-bound Python work non-blocking.

### 11. Use multiple application workers

Uvicorn can run multiple worker processes:

```bash
uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 4
```

Workers can improve throughput by using multiple CPU cores.

However:

- Each worker has its own memory.
- Each worker has its own lifespan resources.
- In-memory caches are not shared.
- Database connections multiply across workers.
- WebSocket connections are tied to the worker handling them.

Choose the number of workers based on CPU, memory, database capacity and measured workload.

### 12. Add request timeouts

External services should not be allowed to block requests indefinitely.

```python
import httpx

client = httpx.AsyncClient(
    timeout=httpx.Timeout(10.0)
)
```

For production, create and close the client through application lifespan.

### 13. Measure performance before optimising

Do not guess where the bottleneck is.

Measure:

- Endpoint latency.
- Database query duration.
- External API latency.
- Cache hit rate.
- CPU and memory.
- Error rates.
- P95 and P99 latency.

Use tools such as:

- Prometheus.
- Grafana.
- OpenTelemetry.
- Application performance monitoring platforms.
- Python profiling tools.

### Performance optimisation summary

| Technique | Benefit |
|---|---|
| Async I/O | Better concurrency for I/O-bound tasks |
| Connection pooling | Reduces connection creation overhead |
| Avoid N+1 queries | Reduces database round trips |
| Pagination | Limits response and query size |
| Redis caching | Reduces repeated expensive reads |
| Response models | Validates and controls output |
| Smaller responses | Reduces network transfer |
| Compression | Reduces response size |
| Background workers | Moves long-running work out of request handling |
| Multiple workers | Can improve multi-core throughput |
| Timeouts | Prevents indefinite waits |
| Monitoring | Identifies actual bottlenecks |
