# FastAPI APIRouter — Complete Practical Guide

## 1. Organising Routes into Multiple Files

### Why do we need APIRouter?

Without `APIRouter`, you might put every endpoint in `main.py`.

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/users")
def get_users():
    return ["Alice", "Bob"]

@app.get("/products")
def get_products():
    return ["Laptop", "Phone"]

@app.get("/orders")
def get_orders():
    return ["Order 1", "Order 2"]
```

This is manageable for small applications, but becomes difficult to maintain as the application grows.

### Using APIRouter

Create separate files for different features.

**routers/users.py**

```python
from fastapi import APIRouter

router = APIRouter()

@router.get("/")
def get_users():
    return ["Alice", "Bob"]

@router.get("/{user_id}")
def get_user(user_id: int):
    return {"user_id": user_id}
```

**routers/products.py**

```python
from fastapi import APIRouter

router = APIRouter()

@router.get("/")
def get_products():
    return ["Laptop", "Phone"]
```

**main.py**

```python
from fastapi import FastAPI
from routers import users, products

app = FastAPI()

app.include_router(users.router, prefix="/users")
app.include_router(products.router, prefix="/products")
```

Now the endpoints are:

| Method | URL | Purpose |
|---|---|---|
| GET | `/users/` | Get all users |
| GET | `/users/{user_id}` | Get one user |
| GET | `/products/` | Get products |

**Important:** `APIRouter()` creates a group of routes. `app.include_router()` registers that group with the main FastAPI application.

## 2. Router Prefixes and Tags

### Prefix

A prefix adds a common path to every route inside a router.

```python
from fastapi import APIRouter

router = APIRouter(prefix="/users")

@router.get("/")
def get_users():
    return ["Alice", "Bob"]

@router.get("/{user_id}")
def get_user(user_id: int):
    return {"user_id": user_id}
```

The resulting endpoints are:

```text
GET /users/
GET /users/{user_id}
```

You can define the prefix either when creating the router or when including it in the application.

```python
router = APIRouter()

app.include_router(router, prefix="/users")
```

Avoid defining the same prefix in both places unless you intentionally want to combine them.

### Tags

Tags group endpoints in the automatically generated Swagger documentation.

```python
router = APIRouter(
    prefix="/users",
    tags=["Users"]
)
```

You can also define tags when including a router:

```python
app.include_router(
    router,
    prefix="/users",
    tags=["Users"]
)
```

Example:

```python
@router.get("/")
def get_users():
    return ["Alice", "Bob"]
```

Swagger UI (`/docs`) displays this endpoint under the **Users** section.

**Difference:**

- `prefix` changes the URL.
- `tags` organise endpoints in API documentation.
- Neither one provides authentication or authorisation.

## 3. Route Dependencies

Dependencies let you reuse logic across endpoints.

Common examples include:

- Checking authentication.
- Getting the current user.
- Checking permissions.
- Creating database sessions.
- Validating request-related conditions.

### Example 1: Dependency on an individual route

```python
from fastapi import APIRouter, Depends, HTTPException

router = APIRouter()

def verify_token(token: str):
    if token != "secret-token":
        raise HTTPException(
            status_code=401,
            detail="Invalid token"
        )

@router.get("/profile")
def get_profile(
    token: str,
    _ = Depends(verify_token)
):
    return {"message": "Profile information"}
```

FastAPI executes `verify_token` before calling `get_profile`.

For a real application, credentials should normally be extracted using FastAPI security utilities or an appropriate authentication mechanism, rather than accepting a token as an ordinary query parameter.

### Example 2: Dependency for every route in a router

```python
router = APIRouter(
    prefix="/admin",
    dependencies=[Depends(verify_token)]
)

@router.get("/users")
def get_users():
    return ["Alice", "Bob"]

@router.get("/reports")
def get_reports():
    return ["Report 1"]
```

Both routes execute `verify_token`.

The dependency is executed even though its return value is not passed into the endpoint.

### Example 3: Dependency whose return value is needed

```python
def get_current_user():
    return {
        "id": 1,
        "username": "alice"
    }

@router.get("/profile")
def get_profile(
    current_user = Depends(get_current_user)
):
    return current_user
```

Here, the dependency's return value is injected into `current_user`.

### Where can dependencies be applied?

| Location | Scope |
|---|---|
| Individual route | One endpoint |
| `APIRouter(dependencies=...)` | Every route in that router |
| `include_router(dependencies=...)` | Routes included through that call |
| `FastAPI(dependencies=...)` | Application-wide routes |

**Important:** Dependencies can be used for both validation and reusable business logic. Use router-level dependencies for checks that should apply to every endpoint in that router.

## 4. Application Configuration

FastAPI allows you to configure the application when creating it.

```python
from fastapi import FastAPI

app = FastAPI(
    title="My API",
    description="A sample production API",
    version="1.0.0",
    docs_url="/docs",
    redoc_url="/redoc",
    openapi_url="/openapi.json"
)
```

### Common FastAPI configuration options

| Parameter | Purpose |
|---|---|
| `title` | API title |
| `description` | API description |
| `version` | API version |
| `docs_url` | Swagger UI URL |
| `redoc_url` | ReDoc URL |
| `openapi_url` | OpenAPI schema URL |
| `debug` | Enables debug mode |
| `middleware` | Middleware configuration |
| `dependencies` | Application-wide dependencies |
| `lifespan` | Startup and shutdown lifecycle management |
| `exception_handlers` | Custom exception handlers |
| `openapi_tags` | Metadata for documentation tags |
| `root_path` | Path prefix used behind certain proxies or gateways |

### Environment-based configuration

You may want different configurations for development and production.

```python
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    app_name: str = "My API"
    debug: bool = False
    environment: str = "production"

    model_config = SettingsConfigDict(
        env_file=".env",
        extra="ignore"
    )

settings = Settings()
```

Create the application using these settings:

```python
from fastapi import FastAPI

def create_app():
    app = FastAPI(
        title=settings.app_name,
        debug=settings.debug
    )

    return app
```

In production, store secrets in a secure secret manager or environment variables. Do not commit sensitive `.env` files to source control.

## 5. Project Folder Structure

A good folder structure separates routes, business logic, database access and configuration.

Example:

```text
my_project/
│
├── app/
│   ├── __init__.py
│   ├── main.py
│   ├── config.py
│   ├── dependencies.py
│   │
│   ├── routers/
│   │   ├── __init__.py
│   │   ├── users.py
│   │   ├── products.py
│   │   └── orders.py
│   │
│   ├── schemas/
│   │   ├── __init__.py
│   │   ├── user.py
│   │   └── product.py
│   │
│   ├── services/
│   │   ├── __init__.py
│   │   ├── user_service.py
│   │   └── product_service.py
│   │
│   ├── repositories/
│   │   ├── __init__.py
│   │   └── user_repository.py
│   │
│   ├── models/
│   │   ├── __init__.py
│   │   └── user.py
│   │
│   └── middleware/
│       ├── __init__.py
│       └── request_logging.py
│
├── tests/
│   ├── test_users.py
│   └── test_products.py
│
├── .env
├── requirements.txt
└── pyproject.toml
```

### What belongs in each folder?

| Folder/File | Responsibility |
|---|---|
| `main.py` | Application creation and router registration |
| `config.py` | Environment variables and settings |
| `dependencies.py` | Shared FastAPI dependencies |
| `routers/` | API endpoints |
| `schemas/` | Pydantic request and response models |
| `services/` | Business logic |
| `repositories/` | Database queries and persistence |
| `models/` | Database models |
| `middleware/` | Request and response processing |
| `tests/` | Automated tests |

**Important distinction:**

- Router: handles HTTP requests and responses.
- Service: implements business rules.
- Repository: interacts with the database.
- Schema: validates and serialises API data.
- Model: represents database entities, if using an ORM.

## 6. Modular FastAPI Architecture

A modular architecture keeps different responsibilities separate.

Consider a request to create a user.

The request travels through:

```text
Client
  |
  v
FastAPI Router
  |
  v
Pydantic Schema
  |
  v
Service Layer
  |
  v
Repository Layer
  |
  v
Database
```

### Step 1: Schema

`schemas/user.py`

```python
from pydantic import BaseModel, EmailStr

class UserCreate(BaseModel):
    name: str
    email: EmailStr

class UserResponse(BaseModel):
    id: int
    name: str
    email: EmailStr
```

### Step 2: Repository

`repositories/user_repository.py`

```python
def create_user(data: dict):
    # Normally, insert into the database here.
    return {
        "id": 1,
        **data
    }
```

### Step 3: Service

`services/user_service.py`

```python
from app.repositories.user_repository import create_user

def register_user(data: dict):
    # Business rules can be implemented here.
    return create_user(data)
```

### Step 4: Router

`routers/users.py`

```python
from fastapi import APIRouter
from app.schemas.user import UserCreate, UserResponse
from app.services.user_service import register_user

router = APIRouter(
    prefix="/users",
    tags=["Users"]
)

@router.post("/", response_model=UserResponse)
def create_user_endpoint(user: UserCreate):
    return register_user(user.model_dump())
```

### Step 5: Main application

`main.py`

```python
from fastapi import FastAPI
from app.routers import users

app = FastAPI()

app.include_router(users.router)
```

### Why use this architecture?

1. Easier to maintain.
2. Easier to test individual components.
3. Business logic can be reused by multiple endpoints.
4. Database implementation can change without rewriting route handlers.
5. Different developers can work on different modules.

For a small application, you do not need every layer. Add layers when they provide useful separation rather than creating folders just for the sake of it.

## 7. Application Factory Pattern

The application factory pattern means creating the FastAPI application inside a function instead of creating it directly as a global variable.

### Without application factory

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/")
def home():
    return {"message": "Hello"}
```

This is perfectly valid for simple applications.

### With application factory

```python
from fastapi import FastAPI

def create_app():
    app = FastAPI(
        title="My API",
        version="1.0.0"
    )

    @app.get("/")
    def home():
        return {"message": "Hello"}

    return app

app = create_app()
```

### Register routers inside the factory

```python
from fastapi import FastAPI
from app.routers import users, products

def create_app():
    app = FastAPI(
        title="My API",
        version="1.0.0"
    )

    app.include_router(users.router)
    app.include_router(products.router)

    return app

app = create_app()
```

### Why use an application factory?

**1. Testing**

You can create separate application instances with different configuration or dependency overrides.

```python
def create_app():
    app = FastAPI()
    return app
```

**2. Multiple configurations**

You can create applications with different settings for testing and production.

**3. Better organisation**

Application setup stays in one place.

### Running the application

If your file is `app/main.py` and it exposes `app = create_app()`:

```bash
uvicorn app.main:app --reload
```

If you expose only the factory function and do not create a global `app`, use:

```bash
uvicorn app.main:create_app --factory --reload
```

The `--factory` option tells Uvicorn to call the function to obtain the application.

## 8. Middleware

Middleware is code that runs around request processing.

It can execute code:

- Before the request reaches the endpoint.
- After the endpoint produces a response.
- While the response travels back to the client.

Typical uses:

- Request logging.
- Timing and performance measurement.
- CORS.
- Authentication-related processing.
- Adding response headers.
- Request tracing.

### Request and response flow

```text
Client Request
      |
      v
Middleware (before)
      |
      v
FastAPI Router
      |
      v
Endpoint
      |
      v
Middleware (after)
      |
      v
Client Response
```

### Built-in middleware example: CORS

CORS controls which browser-based origins can access your API.

```python
from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware

app = FastAPI()

app.add_middleware(
    CORSMiddleware,
    allow_origins=["https://example.com"],
    allow_credentials=True,
    allow_methods=["GET", "POST"],
    allow_headers=["Authorization", "Content-Type"]
)
```

### Important CORS parameters

| Parameter | Purpose |
|---|---|
| `allow_origins` | Allowed origins |
| `allow_credentials` | Allows credentials such as cookies |
| `allow_methods` | Allowed HTTP methods |
| `allow_headers` | Allowed request headers |
| `expose_headers` | Response headers accessible to browser JavaScript |
| `max_age` | How long browsers may cache preflight results |

Avoid using `allow_origins=["*"]` with credentials. For production, specify trusted origins.

## 9. Custom Middleware

You can create your own middleware to process requests and responses.

### Example 1: Request timing middleware

```python
import time
from fastapi import FastAPI, Request

app = FastAPI()

@app.middleware("http")
async def timing_middleware(request: Request, call_next):

    start_time = time.perf_counter()

    response = await call_next(request)

    process_time = time.perf_counter() - start_time

    response.headers["X-Process-Time"] = str(process_time)

    return response
```

### Explanation

**`request`**

Contains information about the incoming request.

```python
request.method
request.url
request.headers
request.client
```

**`call_next(request)`**

Passes the request to the next middleware or the application and waits for the response.

**`response`**

Contains the response returned by the application.

```python
response.status_code
response.headers
```

**`return response`**

Returns the response to the client.

The response includes a custom header:

```text
X-Process-Time: 0.0032
```

### Example 2: Request logging middleware

```python
import logging
from fastapi import FastAPI, Request

app = FastAPI()

logger = logging.getLogger(__name__)

@app.middleware("http")
async def logging_middleware(request: Request, call_next):

    logger.info(
        "Incoming request: %s %s",
        request.method,
        request.url.path
    )

    response = await call_next(request)

    logger.info(
        "Response status: %s",
        response.status_code
    )

    return response
```

This logs the request method, URL path and response status.

### Example 3: Add a custom response header

```python
@app.middleware("http")
async def custom_header_middleware(request: Request, call_next):

    response = await call_next(request)

    response.headers["X-App-Name"] = "My FastAPI App"

    return response
```

### Middleware versus dependencies

| Middleware | Dependencies |
|---|---|
| Can apply to many or all HTTP requests | Can apply to selected routes or applications |
| Runs around request processing | Runs as part of endpoint dependency resolution |
| Useful for logging, timing, headers and CORS | Useful for authentication, database sessions and permissions |
| Does not naturally inject a return value into an endpoint | Can inject values into endpoint parameters |

**Important:** Middleware is not a replacement for route dependencies. For example, use a dependency when an endpoint needs the authenticated user object.

## 10. Request and Response Processing

FastAPI processes requests and responses through several stages.

### Request processing

Consider this endpoint:

```python
from fastapi import FastAPI
from pydantic import BaseModel, EmailStr

app = FastAPI()

class UserCreate(BaseModel):
    name: str
    email: EmailStr

@app.post("/users")
def create_user(user: UserCreate):
    return {
        "message": "User created",
        "name": user.name
    }
```

The client sends:

```http
POST /users
Content-Type: application/json
```

```json
{
  "name": "Alice",
  "email": "alice@example.com"
}
```

FastAPI processes the request in roughly this order:

1. Middleware receives the request.
2. FastAPI matches the URL and HTTP method to a route.
3. Dependencies are resolved.
4. Request parameters and body are extracted.
5. Pydantic validates the request body.
6. The endpoint function executes.
7. The endpoint returns a result.
8. FastAPI validates and serialises the response, where applicable.
9. Middleware can process the response.
10. The response is sent to the client.

### What happens if validation fails?

For example:

```json
{
  "name": "Alice",
  "email": "invalid-email"
}
```

Pydantic rejects the invalid email.

FastAPI normally returns:

```json
{
  "detail": [
    {
      "type": "value_error",
      "loc": ["body", "email"],
      "msg": "value is not a valid email address"
    }
  ]
}
```

The exact error structure can vary by validation error and Pydantic version.

The endpoint function does not execute when request validation fails.

### Response processing with response_model

```python
from pydantic import BaseModel

class UserResponse(BaseModel):
    id: int
    name: str

@app.get("/users/{user_id}", response_model=UserResponse)
def get_user(user_id: int):
    return {
        "id": user_id,
        "name": "Alice",
        "password": "secret"
    }
```

The API response contains:

```json
{
  "id": 1,
  "name": "Alice"
}
```

The extra `password` field is excluded from the response because it is not part of the response model.

This helps control the data exposed by your API.

### Common request objects

```python
from fastapi import Request

@app.get("/request-info")
async def request_info(request: Request):

    return {
        "method": request.method,
        "url": str(request.url),
        "path": request.url.path,
        "headers": dict(request.headers),
        "client": request.client.host if request.client else None
    }
```

### Common response options

**1. Set a status code**

```python
from fastapi import status

@app.post("/users", status_code=status.HTTP_201_CREATED)
def create_user():
    return {"message": "Created"}
```

**2. Set response headers**

```python
from fastapi import Response

@app.get("/example")
def example(response: Response):
    response.headers["X-Custom-Header"] = "Hello"
    return {"message": "Success"}
```

**3. Return a specific response**

```python
from fastapi.responses import JSONResponse

@app.get("/custom")
def custom_response():
    return JSONResponse(
        content={"message": "Created"},
        status_code=201,
        headers={"X-App": "FastAPI"}
    )
```

# Putting Everything Together

A simplified production-style application might look like this:

```text
Client
  |
  v
Middleware
  |
  v
FastAPI Application
  |
  v
APIRouter
  |
  v
Dependencies
  |
  v
Pydantic Validation
  |
  v
Endpoint
  |
  v
Service Layer
  |
  v
Repository Layer
  |
  v
Database
  |
  v
Response Model
  |
  v
Middleware
  |
  v
Client
```

### Quick revision table

| Concept | Main purpose |
|---|---|
| `APIRouter` | Groups related endpoints |
| `include_router()` | Registers a router with the application |
| `prefix` | Adds a common URL path |
| `tags` | Groups endpoints in API documentation |
| Router dependencies | Apply shared dependency logic |
| Application configuration | Configures FastAPI behaviour |
| Project structure | Separates responsibilities |
| Modular architecture | Separates routes, services and data access |
| Application factory | Creates the FastAPI application through a function |
| Middleware | Processes requests and responses |
| Custom middleware | Implements your own request/response processing |
| Request processing | Extracts, validates and handles incoming data |
| Response processing | Validates, serialises and sends outgoing data |

### Important interview questions

1. What is the difference between `FastAPI()` and `APIRouter()`?
2. What is the difference between `prefix` and `tags`?
3. What is the difference between router-level and route-level dependencies?
4. What is the difference between middleware and dependencies?
5. Why should business logic be kept outside route handlers?
6. What is the application factory pattern?
7. What does `call_next(request)` do in middleware?
8. What is the purpose of `response_model`?
9. What happens when Pydantic request validation fails?
10. How does a request travel through a modular FastAPI application?

**Core idea:** `APIRouter` organises endpoints; dependencies provide reusable request-related logic; services handle business logic; repositories handle data access; middleware processes requests and responses; and the application factory brings the components together.
