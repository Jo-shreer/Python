# Part 6: Authentication and Authorisation — Complete FastAPI Guide

## 65. Authentication vs Authorisation

Authentication and authorisation are two different security concepts.

### Authentication — Who are you?

Authentication verifies the identity of a user.

For example:
- A user enters an email and password.
- The application checks whether the credentials are correct.
- If they are correct, the application identifies the user.

### Authorisation — What are you allowed to do?

Authorisation determines what an authenticated user can access or perform.

For example:
- A normal user can view their own profile.
- An admin can view all users.
- Only an admin can delete users.

### Real-world example

Imagine entering an office building.

1. You show your identity card at reception. This is authentication.
2. The security system checks whether you can enter the server room. This is authorisation.

### Comparison

| Feature | Authentication | Authorisation |
|---|---|---|
| Purpose | Verify identity | Check permissions |
| Question | Who are you? | What can you access? |
| Happens | Usually first | After authentication |
| Example | Login | Admin-only endpoint |
| Failure | 401 Unauthorized | 403 Forbidden |

### FastAPI example

```python
from fastapi import FastAPI, HTTPException, Depends

app = FastAPI()

def get_current_user():
    return {
        "username": "john",
        "role": "user"
    }

@app.get("/profile")
def profile(user=Depends(get_current_user)):
    return {
        "message": "Authentication successful",
        "user": user
    }

@app.delete("/users")
def delete_users(user=Depends(get_current_user)):
    if user["role"] != "admin":
        raise HTTPException(
            status_code=403,
            detail="You do not have permission"
        )

    return {"message": "Users deleted"}
```

Expected output for `GET /profile`:

```json
{
  "message": "Authentication successful",
  "user": {
    "username": "john",
    "role": "user"
  }
}
```

Expected output for `DELETE /users` as a normal user:

```json
{
  "detail": "You do not have permission"
}
```

Status code: `403 Forbidden`

**Important:** This example demonstrates the difference between the concepts. The `get_current_user()` function is mocked; it does not perform real authentication.

## 66. OAuth2 Fundamentals

OAuth2 is an authorisation framework that allows an application to access protected resources using tokens instead of sharing a user's password with every service.

### Why OAuth2 is needed

Imagine you have:
- A mobile application.
- A FastAPI backend.
- A user who wants to log in using an external identity provider.

The application should not need to collect and store the user's Google password.

OAuth2 provides a standard way to grant limited access through tokens.

### Important OAuth2 terms

| Term | Meaning |
|---|---|
| Resource Owner | User who owns the data |
| Client | Application requesting access |
| Authorisation Server | Server that issues tokens |
| Resource Server | API that protects resources |
| Access Token | Token used to access protected resources |
| Scope | Permission granted by the token |

### Common OAuth2 flows

**1. Authorisation Code Flow with PKCE**

Commonly used for:
- Mobile applications.
- Single-page applications.
- Web applications.

The user is redirected to an identity provider, authenticates there, and the application exchanges an authorisation code for tokens. PKCE protects the code exchange.

**2. Client Credentials Flow**

Used for machine-to-machine communication.

Example:

```text
Service A
   |
   | Requests token using client credentials
   v
Authorisation Server
   |
   | Returns access token
   v
Service A
   |
   | Calls protected API
   v
Service B
```

There is no end-user login in this flow.

**3. Resource Owner Password Credentials Flow**

This older flow sends the user's username and password directly to the client application.

It is deprecated in modern OAuth2 security guidance and should not be used for new systems.

### OAuth2 in FastAPI

FastAPI provides OAuth2 helper classes.

```python
from fastapi import FastAPI, Depends
from fastapi.security import OAuth2PasswordBearer

app = FastAPI()

oauth2_scheme = OAuth2PasswordBearer(
    tokenUrl="token"
)

@app.get("/profile")
def profile(token: str = Depends(oauth2_scheme)):
    return {
        "message": "Token received",
        "token": token
    }
```

Expected request:

```http
GET /profile
Authorization: Bearer my-access-token
```

Expected output:

```json
{
  "message": "Token received",
  "token": "my-access-token"
}
```

This example extracts the token but does not validate it. Token validation must be implemented separately.

**Important:** OAuth2 is primarily an authorisation framework. OpenID Connect (OIDC) builds on OAuth2 and adds a standard identity layer for authentication.

## 67. Password Hashing

Never store plain-text passwords in a database.

Instead, store a password hash.

### What is password hashing?

Hashing converts a password into a one-way representation.

Example:

```text
Original password:
MyPassword123

Password hash:
$argon2id$v=19$m=...
```

A secure password hashing algorithm is deliberately expensive to make password guessing more difficult.

### Hashing vs encryption

| Hashing | Encryption |
|---|---|
| One-way operation | Reversible with the correct key |
| Used for password storage | Used for protecting recoverable data |
| No decryption | Can be decrypted |
| Example: Argon2id | Example: AES |

### Recommended password hashing algorithms

- Argon2id — excellent modern default.
- bcrypt — widely used and supported.
- scrypt — memory-hard password hashing option.

Avoid fast general-purpose hashes such as MD5 and SHA-256 for directly storing passwords.

### Install the library

```bash
pip install "pwdlib[argon2]"
```

### Hash a password

```python
from pwdlib import PasswordHash

password_hash = PasswordHash.recommended()

password = "MyPassword123"

hashed_password = password_hash.hash(password)

print(hashed_password)
```

Expected output:

```text
$argon2id$v=19$m=65536,t=3,p=4$...
```

The exact output changes each time because password hashing uses a random salt.

### Verify a password

```python
from pwdlib import PasswordHash

password_hash = PasswordHash.recommended()

stored_hash = password_hash.hash("MyPassword123")

print(password_hash.verify(
    "MyPassword123",
    stored_hash
))

print(password_hash.verify(
    "WrongPassword",
    stored_hash
))
```

Expected output:

```text
True
False
```

### Why is salt important?

A salt is a random value included in the password hashing process.

Even if two users have the same password, their hashes should be different because they receive different salts.

This helps protect against precomputed password attacks and makes identical passwords harder to identify from stored hashes.

**Remember:**
- Never store plain-text passwords.
- Never log passwords.
- Never return password hashes in API responses.
- Use a password hashing library instead of implementing hashing yourself.

## 68. Login and Registration APIs

Most applications need two basic authentication endpoints:

1. Registration API — creates a new account.
2. Login API — verifies credentials and issues a token.

### Registration workflow

```text
Client
  |
  | POST /register
  v
FastAPI
  |
  | Validate user input
  v
Check whether email exists
  |
  | Hash password
  v
Save user in database
  |
  v
Return success response
```

### Login workflow

```text
Client
  |
  | POST /login
  v
FastAPI
  |
  | Find user by email
  v
Verify password hash
  |
  | If valid
  v
Generate access token
  |
  v
Return token
```

### Example using an in-memory database

Install:

```bash
pip install fastapi uvicorn "pwdlib[argon2]"
```

Create `main.py`:

```python
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel, EmailStr
from pwdlib import PasswordHash

app = FastAPI()

password_hash = PasswordHash.recommended()

# Demonstration storage only.
# Use a real database in production.
users_db = {}

class RegisterRequest(BaseModel):
    email: EmailStr
    password: str

class LoginRequest(BaseModel):
    email: EmailStr
    password: str

@app.post("/register")
def register(data: RegisterRequest):

    if data.email in users_db:
        raise HTTPException(
            status_code=400,
            detail="Email already registered"
        )

    hashed_password = password_hash.hash(
        data.password
    )

    users_db[data.email] = {
        "email": data.email,
        "password": hashed_password
    }

    return {
        "message": "User registered successfully"
    }

@app.post("/login")
def login(data: LoginRequest):

    user = users_db.get(data.email)

    if not user:
        raise HTTPException(
            status_code=401,
            detail="Invalid email or password"
        )

    if not password_hash.verify(
        data.password,
        user["password"]
    ):
        raise HTTPException(
            status_code=401,
            detail="Invalid email or password"
        )

    return {
        "message": "Login successful"
    }
```

Run:

```bash
uvicorn main:app --reload
```

### Test registration


**Important production improvements:**
- Use a persistent database.
- Add password length and strength validation.
- Add rate limiting to login attempts.
- Use generic login failure messages.
- Consider email verification and account recovery.
- Use a secure token mechanism after successful login.
- Do not allow users to choose privileged roles during public registration.

## 69. JWT Authentication

JWT stands for JSON Web Token.

It is a compact token format used to transfer signed information between systems.

A JWT can carry information about a user, such as:
- User ID.
- Subject.
- Role.
- Expiration time.
- Token identifier.

### JWT structure

A JWT contains three parts:

```text
HEADER.PAYLOAD.SIGNATURE
```

Example:

```text
xxxxx.yyyyy.zzzzz
```

**1. Header**

Contains information about the token type and signing algorithm.

Example:

```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

**2. Payload**

Contains claims about the token.

Example:

```json
{
  "sub": "john@example.com",
  "role": "user",
  "exp": 1900000000
}
```

**3. Signature**

Used to verify that the token has not been modified.

For an HS256 token, the signature is generated using a secret key.

### Important JWT claims

| Claim | Meaning |
|---|---|
| sub | Subject, usually the user ID |
| exp | Expiration timestamp |
| iat | Issued-at timestamp |
| iss | Issuer |
| aud | Intended audience |
| jti | Unique token identifier |

### Install PyJWT

```bash
pip install "PyJWT[crypto]"
```

### Generate a JWT

```python
import jwt
from datetime import datetime, timedelta, timezone

SECRET_KEY = "replace-with-a-secure-secret"
ALGORITHM = "HS256"

def create_access_token(username: str):

    payload = {
        "sub": username,
        "exp": datetime.now(timezone.utc)
        + timedelta(minutes=15)
    }

    token = jwt.encode(
        payload,
        SECRET_KEY,
        algorithm=ALGORITHM
    )

    return token

token = create_access_token("john@example.com")

print(token)
```

Expected output:

```text
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
```

The actual token will be longer and different.

### Decode and validate a JWT

```python
import jwt

decoded = jwt.decode(
    token,
    SECRET_KEY,
    algorithms=["HS256"]
)

print(decoded)
```

Expected output will resemble:

```python
{
    "sub": "john@example.com",
    "exp": 1900000000
}
```

The expiration value depends on when the token was generated.

### What happens if a JWT is modified?

Suppose a user changes:

```json
{
  "role": "user"
}
```

to:

```json
{
  "role": "admin"
}
```

The signature will no longer match. Proper JWT validation rejects the modified token.

### Important JWT security points

- A signed JWT is not automatically encrypted.
- Its payload can normally be decoded by anyone who has the token.
- Never put passwords or sensitive secrets in the payload.
- Always verify the signature and expiration.
- Restrict accepted signing algorithms.
- Validate issuer and audience when your system uses them.
- Use a strong secret or securely managed asymmetric keys.

## 70. Access Tokens

An access token is a credential that allows a client to access protected APIs.

After successful login, the server issues an access token.

The client sends it with subsequent requests.

### Access token workflow

```text
User
  |
  | Login
  v
FastAPI
  |
  | Validate credentials
  v
Generate access token
  |
  v
Client stores token
  |
  | Authorization: Bearer <token>
  v
Protected API
  |
  | Validate token
  v
Return protected data
```

### Example request

```http
GET /profile
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...
```

### Access token characteristics

| Property | Description |
|---|---|
| Purpose | Access protected resources |
| Lifetime | Usually short |
| Format | JWT or opaque token |
| Sent using | Authorization header |
| Security | Must be protected from theft |

A short lifetime reduces the period during which a stolen access token can be used.

### Example access token function

```python
import jwt
from datetime import datetime, timedelta, timezone

SECRET_KEY = "replace-with-a-secure-secret"

def create_access_token(user_id: str):

    payload = {
        "sub": user_id,
        "exp": datetime.now(timezone.utc)
        + timedelta(minutes=15),
        "iat": datetime.now(timezone.utc)
    }

    return jwt.encode(
        payload,
        SECRET_KEY,
        algorithm="HS256"
    )
```

### Why use short-lived access tokens?

Imagine an access token is stolen.

If it expires after 15 minutes, the attacker's opportunity to use it is limited compared with a token that remains valid for 30 days.

Short-lived tokens are usually combined with refresh tokens.

## 71. Refresh Tokens

A refresh token is a longer-lived credential used to obtain a new access token without requiring the user to log in again.

### Why do we need refresh tokens?

Suppose:
- Access token expires after 15 minutes.
- User is working in the application.
- The access token expires.

Without a refresh token, the user may have to log in again.

With a refresh token, the application can request a new access token.

### Access token vs refresh token

| Feature | Access Token | Refresh Token |
|---|---|---|
| Purpose | Access APIs | Obtain new access tokens |
| Lifetime | Short | Longer |
| Sent to | Resource APIs | Token endpoint |
| Frequency | Used frequently | Used occasionally |
| Storage | Protected client storage | Strongly protected storage |

### Refresh token workflow

```text
User logs in
    |
    v
Server returns:
    |
    +---- Access Token
    |
    +---- Refresh Token
              |
              v
       Access token expires
              |
              v
       Client sends refresh token
              |
              v
       Server validates refresh token
              |
              v
       Server issues new access token
```

### Refresh token example using opaque tokens

Refresh tokens do not have to be JWTs. A random opaque token is often a good choice because the server can track and revoke it.

```python
import secrets
import hashlib

def create_refresh_token():

    raw_token = secrets.token_urlsafe(48)

    token_hash = hashlib.sha256(
        raw_token.encode()
    ).hexdigest()

    return raw_token, token_hash

raw_token, stored_hash = create_refresh_token()

print("Refresh token created")
print("Stored hash:", stored_hash)
```

Expected output:

```text
Refresh token created
Stored hash: <64-character hexadecimal hash>
```

The raw refresh token is sent to the client. The hash is stored in the database.

### Verify a refresh token

```python
import hashlib
import hmac

def verify_refresh_token(
    received_token: str,
    stored_hash: str
):

    received_hash = hashlib.sha256(
        received_token.encode()
    ).hexdigest()

    return hmac.compare_digest(
        received_hash,
        stored_hash
    )

print(
    verify_refresh_token(
        raw_token,
        stored_hash
    )
)
```

Expected output:

```text
True
```

### Refresh token best practices

1. Store only a hash of the refresh token on the server.
2. Rotate refresh tokens after use.
3. Detect reuse of an already-rotated token.
4. Support token revocation and logout.
5. Associate refresh tokens with a user and device/session.
6. Set an expiry date.
7. Store tokens securely on the client.

For browser applications, a common design is to keep the refresh token in a Secure, HttpOnly, appropriately SameSite cookie and protect cookie-authenticated endpoints against CSRF.

## 72. OAuth2PasswordBearer

`OAuth2PasswordBearer` is a FastAPI security helper that extracts a Bearer token from the Authorization header.

It also describes the OAuth2 password flow in the generated OpenAPI documentation.

### Example

```python
from fastapi import FastAPI, Depends
from fastapi.security import OAuth2PasswordBearer

app = FastAPI()

oauth2_scheme = OAuth2PasswordBearer(
    tokenUrl="/token"
)

@app.get("/users/me")
def get_current_user(
    token: str = Depends(oauth2_scheme)
):

    return {
        "token": token
    }
```

### What happens internally?

When a request arrives:

```http
GET /users/me
Authorization: Bearer abc123
```

FastAPI extracts:

```text
abc123
```

The function receives that value in the `token` variable.

Expected output:

```json
{
  "token": "abc123"
}
```

### What if the token is missing?

Request:

```http
GET /users/me
```

Expected result:

```json
{
  "detail": "Not authenticated"
}
```

Status code:

```text
401 Unauthorized
```

### Important distinction

`OAuth2PasswordBearer` does not:
- Decode JWTs.
- Verify JWT signatures.
- Check whether a user exists.
- Check user roles.
- Check token revocation.

It only extracts the Bearer token and provides the OAuth2 security scheme metadata.

You must validate the token yourself or use an appropriate authentication library.

### Using auto_error=False

```python
oauth2_scheme = OAuth2PasswordBearer(
    tokenUrl="/token",
    auto_error=False
)
```

This allows the dependency to return `None` when no Bearer token is supplied instead of immediately raising an authentication error.

It can be useful when an endpoint supports both authenticated and anonymous access.

## 73. Role-Based Access Control (RBAC)

RBAC stands for Role-Based Access Control.

It controls access based on a user's assigned role.

### Example roles

| Role | Permissions |
|---|---|
| Admin | Manage users and system settings |
| Manager | View reports and manage teams |
| User | View own profile |
| Guest | Access public information |

Instead of assigning permissions individually to every user, permissions are grouped into roles.

### RBAC workflow

```text
User
  |
  v
Authenticate user
  |
  v
Get user's role
  |
  v
Check required role
  |
  +---- Allowed ----> Execute endpoint
  |
  +---- Denied -----> Return 403
```

### FastAPI RBAC example

```python
from fastapi import FastAPI, Depends, HTTPException

app = FastAPI()

def get_current_user():

    return {
        "username": "john",
        "role": "user"
    }

def require_admin(
    user=Depends(get_current_user)
):

    if user["role"] != "admin":

        raise HTTPException(
            status_code=403,
            detail="Admin access required"
        )

    return user

@app.get("/admin/dashboard")
def admin_dashboard(
    user=Depends(require_admin)
):

    return {
        "message": "Welcome to admin dashboard",
        "user": user["username"]
    }
```

### Test as a normal user

Expected output:

```json
{
  "detail": "Admin access required"
}
```

Status:

```text
403 Forbidden
```

### Test as an admin

If `get_current_user()` returns:

```python
{
    "username": "john",
    "role": "admin"
}
```

Expected output:

```json
{
  "message": "Welcome to admin dashboard",
  "user": "john"
}
```

### Reusable role checker

```python
def require_roles(*allowed_roles):

    def role_checker(
        user=Depends(get_current_user)
    ):

        if user["role"] not in allowed_roles:

            raise HTTPException(
                status_code=403,
                detail="Insufficient permissions"
            )

        return user

    return role_checker
```

Usage:

```python
@app.get("/reports")
def reports(
    user=Depends(
        require_roles("admin", "manager")
    )
):

    return {
        "message": "Reports available"
    }
```

Now both admins and managers can access the endpoint.

**Important:** Roles must come from trusted server-side data or verified token claims. Never trust a role supplied directly by the client.

## 74. Permission-Based Authorisation

Role-based authorisation checks a user's role.

Permission-based authorisation checks whether the user has a specific permission to perform an action.

### Example

A user might have:

```python
{
    "username": "john",
    "role": "manager",
    "permissions": [
        "users:read",
        "reports:read",
        "reports:export"
    ]
}
```

This user can:
- Read users.
- Read reports.
- Export reports.

But cannot:
- Delete users.
- Change system settings.

### Difference between roles and permissions

| RBAC | Permission-based |
|---|---|
| Checks role | Checks specific permission |
| Admin, manager, user | users:read, users:delete |
| Simpler | More flexible |
| Often maps roles to permissions | Can grant permissions directly |

In real systems, RBAC and permissions are often combined.

### FastAPI permission checker

```python
from fastapi import FastAPI, Depends, HTTPException

app = FastAPI()

def get_current_user():

    return {
        "username": "john",
        "permissions": [
            "users:read",
            "reports:read"
        ]
    }

def require_permission(permission: str):

    def permission_checker(
        user=Depends(get_current_user)
    ):

        if permission not in user["permissions"]:

            raise HTTPException(
                status_code=403,
                detail="Permission denied"
            )

        return user

    return permission_checker

@app.get("/users")
def get_users(
    user=Depends(
        require_permission("users:read")
    )
):

    return {
        "message": "Users retrieved successfully"
    }

@app.delete("/users")
def delete_users(
    user=Depends(
        require_permission("users:delete")
    )
):

    return {
        "message": "Users deleted successfully"
    }
```

Expected output for `GET /users`:

```json
{
  "message": "Users retrieved successfully"
}
```

Expected output for `DELETE /users`:

```json
{
  "detail": "Permission denied"
}
```

### Practical permission naming

A common naming convention is:

```text
resource:action
```

Examples:

```text
users:read
users:create
users:update
users:delete

orders:read
orders:create
orders:cancel

reports:read
reports:export
```

This makes permissions easier to understand and manage.

### Object-level permissions

Sometimes having `orders:read` is not enough.

A user may be allowed to read only their own orders.

For example:

```python
@app.get("/orders/{order_id}")
def get_order(
    order_id: int,
    user=Depends(get_current_user)
):

    order = {
        "id": order_id,
        "owner": "john@example.com"
    }

    if (
        order["owner"] != user["username"]
        and "orders:read:any" not in user["permissions"]
    ):
        raise HTTPException(
            status_code=403,
            detail="Cannot access this order"
        )

    return order
```

In a real application, retrieve the order from the database and compare its owner with the authenticated user's ID.

## 75. API Key Authentication

An API key is a credential used to identify or authorise a client application.

It is commonly used for:
- Internal services.
- Partner integrations.
- Developer APIs.
- Machine-to-machine access.

### Example

A client sends:

```http
GET /data
X-API-Key: my-secret-api-key
```

The server validates the API key before returning data.

### FastAPI API key example

```python
from fastapi import FastAPI, Depends, HTTPException
from fastapi.security import APIKeyHeader

app = FastAPI()

api_key_header = APIKeyHeader(
    name="X-API-Key"
)

API_KEY = "replace-with-a-secure-key"

def verify_api_key(
    api_key: str = Depends(api_key_header)
):

    if api_key != API_KEY:

        raise HTTPException(
            status_code=403,
            detail="Invalid API key"
        )

    return api_key

@app.get("/data")
def get_data(
    api_key=Depends(verify_api_key)
):

    return {
        "message": "API key accepted",
        "data": [1, 2, 3]
    }
```

Expected request:

```http
GET /data
X-API-Key: replace-with-a-secure-key
```

Expected output:

```json
{
  "message": "API key accepted",
  "data": [1, 2, 3]
}
```

### API key best practices

- Store keys securely, preferably as hashes when you can validate them without recovering the original.
- Never commit keys to Git.
- Use HTTPS.
- Support key rotation.
- Give keys scopes or permissions.
- Add expiration and revocation.
- Rate-limit API key usage.
- Log key identifiers, not the raw secrets.
- Avoid placing API keys in URLs because URLs can appear in logs and browser history.

### API key vs JWT

| API Key | JWT |
|---|---|
| Usually identifies a client | Can carry user or client claims |
| Often requires server-side lookup | Can be validated cryptographically |
| Common for service integrations | Common for user authentication |
| Usually opaque | Structured token format |
| Revocation often uses stored state | Revocation needs additional design |

API keys do not automatically replace user authentication.

## 76. Integrating AWS Cognito

Amazon Cognito is an AWS service for user authentication and identity management.

It can handle:
- User registration.
- User login.
- Password management.
- Email and phone verification.
- Multi-factor authentication.
- Token generation.
- Federated identity providers.

### Why use Cognito?

Without Cognito, you may need to build and maintain:
- Registration APIs.
- Login APIs.
- Password reset workflows.
- Token generation.
- MFA workflows.
- User verification.
- Account security controls.

Cognito provides managed identity capabilities.

### Important Cognito components

**1. User Pool**

A user directory that handles user registration, login, and authentication.

**2. Identity Pool**

Can provide AWS credentials to authenticated or unauthenticated identities so they can access supported AWS resources under configured IAM permissions.

These are different concepts. A user pool issues identity and access tokens; an identity pool can exchange identities for AWS credentials.

| Token | Purpose |
|---|---|

### Verify a Cognito access token in FastAPI

Cognito publishes public signing keys through its JSON Web Key Set (JWKS) endpoint.

The backend uses these public keys to verify token signatures.

Example:

```python
import jwt
import requests

from jwt import PyJWKClient
from fastapi import FastAPI, HTTPException, Depends
from fastapi.security import HTTPBearer, HTTPAuthorizationCredentials

app = FastAPI()

REGION = "eu-west-1"

USER_POOL_ID = "eu-west-1_XXXXXXXXX"

APP_CLIENT_ID = "your-app-client-id"

ISSUER = (
    f"https://cognito-idp.{REGION}.amazonaws.com/"
    f"{USER_POOL_ID}"
)

JWKS_URL = f"{ISSUER}/.well-known/jwks.json"

jwks_client = PyJWKClient(JWKS_URL)

security = HTTPBearer()

def verify_cognito_token(
    credentials: HTTPAuthorizationCredentials = Depends(security)
):

    token = credentials.credentials

    try:
        signing_key = jwks_client.get_signing_key_from_jwt(
            token
        )

        payload = jwt.decode(
            token,
            signing_key.key,
            algorithms=["RS256"],
            issuer=ISSUER,
            options={
                "require": ["exp", "iss", "sub", "token_use"]
            }
        )

        if payload.get("token_use") != "access":
            raise HTTPException(
                status_code=401,
                detail="Access token required"
            )

        if payload.get("client_id") != APP_CLIENT_ID:
            raise HTTPException(
                status_code=401,
                detail="Invalid client"
            )

        return payload

    except jwt.PyJWTError:
        raise HTTPException(
            status_code=401,
            detail="Invalid or expired token"
        )

@app.get("/profile")
def profile(
    user=Depends(verify_cognito_token)
):

    return {
        "message": "Cognito authentication successful",
        "user_id": user["sub"]
    }
```

Expected successful output:

```json
{
  "message": "Cognito authentication successful",
  "user_id": "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
}
```

The values in the example must be replaced with your actual Cognito configuration.

### Important Cognito validation details

- Validate the signature against the correct User Pool JWKS.
- Validate the issuer.
- Validate token expiration.
- Check `token_use` is `access`.
- Check the expected app client ID using the access token's `client_id` claim.
- Validate required scopes when using OAuth scopes.
- Use HTTPS.
- Cache JWKS keys rather than downloading them on every request.

In production, use a well-maintained JWT/JWKS validation approach and handle key rotation and network failures properly.

### Cognito vs custom JWT authentication

| Cognito | Custom JWT |
|---|---|
| Managed authentication service | You build authentication |
| Built-in user management | You manage users |
| Built-in verification options | You implement verification |
| MFA capabilities | You implement or integrate MFA |
| AWS-managed identity infrastructure | You manage signing keys and token lifecycle |

Cognito is useful when you want AWS-managed identity features rather than implementing the entire identity system yourself.

## 77. Securing API Endpoints

Securing an API means ensuring that only authorised clients and users can access protected resources.

### Common API security layers

**1. Authentication**

Verify who is making the request.

**2. Authorisation**

Verify whether the user can perform the requested action.

**3. Input validation**

Validate incoming data using Pydantic.

**4. HTTPS**

Encrypt traffic between clients and servers.

**5. Rate limiting**

Limit excessive requests.

**6. CORS**

Restrict which browser origins can access your API through cross-origin requests.

CORS is not an authentication mechanism.

**7. Security logging**

Record important security events without logging passwords or tokens.

### Example protected FastAPI endpoint

```python
from fastapi import (
    FastAPI,
    Depends,
    HTTPException
)

from fastapi.security import OAuth2PasswordBearer
import jwt

app = FastAPI()

SECRET_KEY = "replace-with-a-secure-secret"
ALGORITHM = "HS256"

oauth2_scheme = OAuth2PasswordBearer(
    tokenUrl="/token"
)

def get_current_user(
    token: str = Depends(oauth2_scheme)
):

    try:

        payload = jwt.decode(
            token,
            SECRET_KEY,
            algorithms=[ALGORITHM]
        )

        username = payload.get("sub")

        if not username:
            raise HTTPException(
                status_code=401,
                detail="Invalid token"
            )

        return {
            "username": username,
            "role": payload.get("role", "user")
        }

    except jwt.PyJWTError:

        raise HTTPException(
            status_code=401,
            detail="Invalid or expired token"
        )

@app.get("/profile")
def profile(
    user=Depends(get_current_user)
):

    return {
        "username": user["username"]
    }

@app.delete("/admin/users")
def delete_users(
    user=Depends(get_current_user)
):

    if user["role"] != "admin":

        raise HTTPException(
            status_code=403,
            detail="Admin access required"
        )

    return {
        "message": "Users deleted"
    }
```

This demonstrates JWT validation and role checks. A production implementation must also validate issuer, audience where applicable, and trusted role claims or retrieve current permissions from the database.

### HTTP status codes used in authentication

| Status | Meaning | Example |
|---|---|---|
| 200 | Success | Valid request |
| 201 | Created | Registration successful |
| 400 | Bad Request | Invalid registration data |
| 401 | Unauthorized | Missing or invalid credentials |
| 403 | Forbidden | User lacks permission |
| 404 | Not Found | Resource does not exist |
| 429 | Too Many Requests | Rate limit exceeded |
| 500 | Internal Server Error | Unexpected server error |

### 401 vs 403

**401 Unauthorized**

The request does not contain valid authentication credentials.

Example:

```json
{
  "detail": "Invalid or expired token"
}
```

**403 Forbidden**

The user is authenticated but does not have permission.

Example:

```json
{
  "detail": "Admin access required"
}
```

## 78. Authentication Best Practices

Authentication is a critical part of application security.

Follow these practices when building production APIs.

### 1. Never store plain-text passwords

Use Argon2id or another suitable password hashing algorithm.

### 2. Use HTTPS everywhere

Never send passwords, tokens, or API keys over unencrypted HTTP in production.

### 3. Use short-lived access tokens

For example:

```text
Access token: 10–15 minutes
Refresh token: longer, controlled lifetime
```

The exact lifetime should reflect your security and user-experience requirements.

### 4. Protect refresh tokens

- Store refresh token hashes server-side.
- Rotate refresh tokens.
- Detect token reuse.
- Revoke tokens on logout or compromise.
- Associate tokens with sessions or devices.

### 5. Use strong signing keys

Do not use simple secrets such as:

```python
SECRET_KEY = "password123"
```

Use cryptographically random secrets stored in a secret manager or secure environment configuration.

### 6. Never expose secrets in source code

Avoid:

```python
SECRET_KEY = "my-secret-key"
```

Prefer loading secrets from secure configuration:

```python
import os

SECRET_KEY = os.environ["JWT_SECRET_KEY"]
```

For production, use a secrets manager such as AWS Secrets Manager or an equivalent secure service.

### 7. Validate JWT claims

Validate:
- Signature.
- Expiration.
- Issuer.
- Audience where applicable.
- Token type.
- Required scopes or permissions.

### 8. Implement rate limiting

Protect login and password reset endpoints against brute-force attacks.

Example policy:

```text
Maximum 5 failed login attempts
within a configured time window
```

The exact policy should account for shared IP addresses and legitimate users. Use appropriate account-level and IP-level controls.

### 9. Avoid user enumeration

Avoid returning different error messages such as:

```text
Email does not exist
```

and:

```text
Incorrect password
```

for public login endpoints.

Prefer a generic response:

```json
{
  "detail": "Invalid email or password"
}
```

### 10. Implement Multi-Factor Authentication

MFA requires another authentication factor, such as:
- Authenticator application code.
- Security key.
- Passkey.
- Other supported verification methods.

### 11. Implement proper authorisation

Do not rely only on frontend restrictions.

Always check permissions on the backend.

### 12. Protect against CSRF where relevant

If browsers automatically send authentication cookies, protect state-changing endpoints against Cross-Site Request Forgery.

Use appropriate SameSite cookie settings and CSRF protections.

Bearer tokens explicitly attached by application code have a different CSRF threat profile, but still need protection against token theft.

### 13. Secure logout

Logout should invalidate or revoke the relevant refresh-token session.

Deleting a JWT from the browser alone does not invalidate a stateless access token that has already been issued. Short token lifetimes and, where necessary, server-side revocation mechanisms help address this.

### 14. Audit security events

Record events such as:
- Successful login.
- Failed login.
- Password change.
- Account lockout.
- Token refresh.
- Token revocation.
- Permission changes.

Never log raw passwords, access tokens, refresh tokens, or API keys.

### 15. Keep dependencies updated

Regularly update FastAPI, PyJWT, password hashing libraries, and other dependencies to receive security fixes.

# Common Interview Questions and Answers

### 1. What is the difference between authentication and authorisation?

Authentication verifies the identity of a user. Authorisation checks what that user is allowed to access.

### 2. What is JWT?

JWT is a compact token format containing claims that can be digitally signed or encrypted. In common API authentication designs, signed JWTs allow a server to verify token integrity and claims.

### 3. Is JWT encrypted?

Not necessarily. A normal signed JWT is readable by anyone who obtains it. Signing protects integrity, not confidentiality.

### 4. Why should passwords be hashed?

Hashing prevents the application from storing users' original passwords. A password hashing algorithm such as Argon2id makes offline password guessing more expensive.

### 5. What is an access token?

An access token is a credential used by a client to access protected APIs.

### 6. What is a refresh token?

A refresh token is used to obtain new access tokens after existing access tokens expire.

### 7. What is OAuth2?

OAuth2 is an authorisation framework that enables clients to obtain limited access to protected resources using tokens.

### 8. What is OAuth2PasswordBearer?

It is a FastAPI dependency that extracts a Bearer token from the Authorization header and describes the OAuth2 security scheme in OpenAPI.

### 9. Does OAuth2PasswordBearer validate a JWT?

No. It extracts the token. JWT signature and claim validation must be performed separately.

### 10. What is RBAC?

Role-Based Access Control grants permissions based on a user's role, such as admin, manager, or user.

### 11. What is permission-based authorisation?

It checks whether a user has a specific permission, such as `users:read` or `orders:delete`.

### 12. What is the difference between 401 and 403?

401 means valid authentication credentials are missing or unavailable. 403 means the request is understood but access is denied.

### 13. What is Amazon Cognito?

Amazon Cognito is an AWS identity service that provides managed user authentication, token issuance, user management, and related identity features.

### 14. What is the difference between Cognito User Pool and Identity Pool?

A User Pool provides user-directory and authentication functionality. An Identity Pool can provide AWS credentials for accessing AWS resources under configured IAM permissions.

### 15. Why should access tokens be short-lived?

Short-lived tokens reduce the time available for an attacker to use a stolen token.

### 16. Why should refresh tokens be rotated?

Rotation limits the usefulness of stolen refresh tokens and can help detect token reuse.

### 17. Can frontend code alone secure an API?

No. All important authentication and authorisation checks must be enforced by the backend.

### 18. What is the difference between an API key and a JWT?

An API key is generally an opaque client credential. A JWT is a structured token containing claims that can be cryptographically verified.

# Final Takeaway

A typical secure FastAPI authentication system follows this sequence:

1. Register the user.
2. Hash the password using Argon2id.
3. Store the user in a database.
4. Verify the password during login.
5. Issue a short-lived access token.
6. Issue and securely manage a refresh token.
7. Extract Bearer tokens using `OAuth2PasswordBearer` or another suitable security dependency.
8. Validate token signatures and claims.
9. Identify the authenticated user.
10. Check roles and permissions.
11. Protect sensitive API endpoints.
12. Log security events and support token revocation.

**Remember these distinctions:**

- Authentication = Who are you?
- Authorisation = What can you do?
- OAuth2 = How can a client obtain delegated access?
- JWT = A token format.
- Access token = Used to access APIs.
- Refresh token = Used to obtain new access tokens.
- Password hashing = Secure password storage.
- RBAC = Access based on roles.
- Permissions = Access based on specific actions.
- Cognito = AWS-managed identity service.

**Production reminder:** The code in this guide illustrates individual concepts. A production system should use persistent storage, secure secret management, token rotation and revocation, robust input validation, rate limiting, and appropriate monitoring. Do not combine the demonstration-only hard-coded secrets and in-memory databases into a production authentication system.
