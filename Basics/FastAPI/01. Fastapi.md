# FastAPI — Complete Notes

## 1. What is FastAPI?
**FastAPI** is a modern Python web framework used to build APIs.

It is built around:
* Python type hints
* Pydantic for data validation
* ASGI for asynchronous applications
* Automatic OpenAPI documentation

Typical use cases:

```text
REST APIs
Backend services
Microservices
ETL APIs
Internal services
Data processing APIs
```

---

## 2. Basic FastAPI Application

```python
from fastapi import FastAPI

app = FastAPI()


@app.get("/")
def home():
    return {"message": "API is running"}
```

Run it with:

```bash
uvicorn main:app --reload
```

If the file is called `main.py`:

```text
main → Python file
app  → FastAPI object
```

FastAPI automatically provides:

```text
/docs    → Swagger UI
/redoc   → ReDoc
/openapi.json → OpenAPI schema
```

---

## 3. HTTP Methods

The main HTTP methods used in REST APIs are:

```text
GET
POST
PUT
PATCH
DELETE
```

Example:

```python
from fastapi import FastAPI

app = FastAPI()


@app.get("/customers")
def get_customers():
    return {"customers": []}


@app.post("/customers")
def create_customer():
    return {"message": "Customer created"}


@app.put("/customers/{customer_id}")
def replace_customer(customer_id: int):
    return {"message": "Customer replaced"}


@app.patch("/customers/{customer_id}")
def update_customer(customer_id: int):
    return {"message": "Customer updated"}


@app.delete("/customers/{customer_id}")
def delete_customer(customer_id: int):
    return {"message": "Customer deleted"}
```

Meaning:

```text
GET     → Read
POST    → Create
PUT     → Replace
PATCH   → Partial update
DELETE  → Delete
```

## 4. Path Parameters

Path parameters identify a specific resource.

```python
from fastapi import FastAPI

app = FastAPI()


@app.get("/customers/{customer_id}")
def get_customer(customer_id: int):
    return {
        "customer_id": customer_id
    }
```

Request:

```text
GET /customers/101
```

FastAPI converts:

```text
"101"
```

into:

```python
101
```

because of:

```python
customer_id: int
```

If the client sends an invalid value:

```text
GET /customers/abc
```

FastAPI returns a validation error.

## 5. Query Parameters

Query parameters appear after `?`.

```python
from fastapi import FastAPI

app = FastAPI()


@app.get("/customers")
def get_customers(
    country: str = "Ireland",
    limit: int = 10
):
    return {
        "country": country,
        "limit": limit
    }
```

Request:

```text
GET /customers?country=Ireland&limit=20
```

FastAPI gives:

```python
country = "Ireland"
limit = 20
```

Common uses:

```text
Filtering
Searching
Sorting
Pagination
Optional parameters
```

## 6. Optional Query Parameters

Use `None` when a parameter is optional.

```python
from fastapi import FastAPI

app = FastAPI()


@app.get("/customers")
def get_customers(
    country: str | None = None,
    age: int | None = None
):
    return {
        "country": country,
        "age": age
    }
```

Possible request:

```text
/customers
```

or:

```text
/customers?country=Ireland
```

or:

```text
/customers?country=Ireland&age=30
```

## 7. Request Body

For POST/PUT/PATCH requests, data is commonly sent in the request body.

FastAPI commonly uses **Pydantic models** to define and validate the body.

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()


class Customer(BaseModel):
    name: str
    email: str
    age: int


@app.post("/customers")
def create_customer(customer: Customer):
    return {
        "name": customer.name,
        "email": customer.email,
        "age": customer.age
    }
```

Client sends:

```json
{
    "name": "John",
    "email": "john@example.com",
    "age": 30
}
```

FastAPI/Pydantic:

```text
JSON
 ↓
Pydantic model
 ↓
Validation
 ↓
Python object
 ↓
Endpoint function
```

## 8. Pydantic `BaseModel`

`BaseModel` comes from Pydantic.

```python
from pydantic import BaseModel


class Customer(BaseModel):
    name: str
    email: str
    age: int
```

It defines the expected data structure.

It is used for:

```text
Validation
Parsing
Serialization
API schemas
```

It does **not** automatically represent a database table.

## 9. Validation

Suppose:

```python
class Customer(BaseModel):
    name: str
    email: str
    age: int
```

Valid:

```json
{
    "name": "John",
    "email": "john@example.com",
    "age": 30
}
```

Invalid because `age` is missing:

```json
{
    "name": "John",
    "email": "john@example.com"
}
```

Invalid:

```json
{
    "name": "John",
    "email": "john@example.com",
    "age": "hello"
}
```

FastAPI returns a validation error and the endpoint function does not execute.

## 10. Response Models

A response model defines what the API should return.

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()


class CustomerResponse(BaseModel):
    id: int
    name: str
    email: str


@app.get(
    "/customers/{customer_id}",
    response_model=CustomerResponse
)
def get_customer(customer_id: int):

    return {
        "id": customer_id,
        "name": "John",
        "email": "john@example.com",
        "password": "secret123"
    }
```

The response model only exposes:

```text
id
name
email
```

The password is not included.

`response_model` is useful for:

* Response validation
* Consistent API contracts
* Filtering unwanted fields
* Documentation

## 11. Separate Create and Response Models

A good API commonly uses different models for input and output.

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()


class CustomerCreate(BaseModel):
    name: str
    email: str
    age: int


class CustomerResponse(BaseModel):
    id: int
    name: str
    email: str
    age: int


@app.post(
    "/customers",
    response_model=CustomerResponse
)
def create_customer(customer: CustomerCreate):

    return {
        "id": 1,
        "name": customer.name,
        "email": customer.email,
        "age": customer.age
    }
```

This prevents internal/database fields from automatically becoming part of the public API contract.

## 13. HTTPException

```python
def get_customer(customer_id: int):

    customer = None

    if customer is None:
        raise HTTPException(
            status_code=404,
            detail="Customer not found"
        )

    return customer
```

```json
{
```

## 14. CRUD

CRUD means:

```text
Create
Read
Update
Delete
```

Typical REST API:

```text
POST   /customers
GET    /customers
GET    /customers/{id}
PUT    /customers/{id}
PATCH  /customers/{id}
DELETE /customers/{id}
```

Example:

```python
from fastapi import FastAPI, HTTPException

app = FastAPI()

customers = {}


@app.post("/customers")
def create_customer(name: str):
    customer_id = len(customers) + 1

    customers[customer_id] = {
        "id": customer_id,
        "name": name
    }

    return customers[customer_id]


@app.get("/customers/{customer_id}")
def get_customer(customer_id: int):

    customer = customers.get(customer_id)

    if customer is None:
        raise HTTPException(
            status_code=404,
            detail="Customer not found"
        )

    return customer


@app.delete("/customers/{customer_id}")
def delete_customer(customer_id: int):

    if customer_id not in customers:
        raise HTTPException(
            status_code=404,
            detail="Customer not found"
        )

    del customers[customer_id]

    return {"message": "Customer deleted"}
```

## 15. PUT vs PATCH

### PUT

Usually represents replacing the resource.

```text
PUT /customers/101
```

The client generally sends the complete representation.

### PATCH

Usually represents a partial update.

```text
PATCH /customers/101
```

The client can send only the fields that need to change.

Example:

```json
{
    "email": "new@example.com"
}
```

## 16. Pagination

Never return millions of records from an API in one response.

A simple pagination approach:

```python
from fastapi import FastAPI

app = FastAPI()


@app.get("/customers")
def get_customers(
    page: int = 1,
    page_size: int = 100
):

    offset = (page - 1) * page_size

    return fetch_customers(
        offset=offset,
        limit=page_size
    )
```

Formula:

```text
offset = (page - 1) × page_size
```

For very large datasets, cursor/keyset pagination can be more efficient than large offsets.

## 18. Async and Await

FastAPI supports asynchronous endpoints.

```python
from fastapi import FastAPI

app = FastAPI()


@app.get("/customers")
async def get_customers():

    result = await fetch_from_database()

    return result
```

Use async when the underlying operations are asynchronous.

For example:

```text
async database driver
async HTTP client
async network operations
```

Making a function `async` does not automatically make blocking code asynchronous.

---

## 19. Synchronous vs Asynchronous Endpoint

Synchronous:

```python
@app.get("/customers")
def get_customers():
    return fetch_data()
```

Asynchronous:

```python
@app.get("/customers")
async def get_customers():
    return await fetch_data_async()
```

The important rule is:

```text
Async endpoint
      ↓
Use async-compatible I/O
```

Do not assume:

```python
async def
```

automatically makes every operation non-blocking.

## 20. Dependency Injection

FastAPI provides dependency injection through `Depends`.

```python
from fastapi import FastAPI, Depends

app = FastAPI()


def get_current_user():
    return {
        "id": 101,
        "name": "John"
    }


@app.get("/profile")
def profile(
    user=Depends(get_current_user)
):
    return user
```

FastAPI calls:

```text
get_current_user()
       ↓
Depends(...)
       ↓
profile()
```

Dependencies are useful for:

```text
Authentication
Authorization
Database sessions
Common parameters
Reusable business logic
Permissions
```

## 21. Database Dependency

A common pattern is creating a database session per request.

```python
from fastapi import FastAPI, Depends

app = FastAPI()


def get_db():

    db = create_database_session()

    try:
        yield db

    finally:
        db.close()


@app.get("/customers")
def get_customers(
    db=Depends(get_db)
):

    return db.query(Customer).all()
```

The important lifecycle is:

```text
Request
 ↓
Create DB session
 ↓
Endpoint uses session
 ↓
Request completes
 ↓
Close session
```

## 22. Authentication

Authentication answers:

> Who are you?

Authorization answers:

> What are you allowed to do?

A common API authentication approach is:

```text
Login
 ↓
Username/password
 ↓
Validate credentials
 ↓
Create access token
 ↓
Client sends token
 ↓
API validates token
```

FastAPI provides security utilities such as OAuth2 helpers.

Example:

```python
from fastapi import FastAPI, Depends
from fastapi.security import OAuth2PasswordBearer

app = FastAPI()

oauth2_scheme = OAuth2PasswordBearer(
    tokenUrl="token"
)


@app.get("/profile")
def profile(
    token: str = Depends(oauth2_scheme)
):

    return {
        "token": token
    }
```

In a real application, the token must be properly validated.

## 23. JWT

JWT stands for **JSON Web Token**.

A common flow:

```text
Client
  ↓
Login
  ↓
Server validates credentials
  ↓
Server creates JWT
  ↓
Client stores token
  ↓
Client sends:
Authorization: Bearer <token>
  ↓
Server validates token
  ↓
Request allowed
```

JWT commonly contains claims such as:

```text
sub
exp
iat
```

Never put sensitive secrets/passwords inside a JWT payload simply because it is encoded.

## 24. Middleware

Middleware runs around requests.

```python
from fastapi import FastAPI, Request

app = FastAPI()


@app.middleware("http")
async def log_requests(
    request: Request,
    call_next
):

    print(
        "Request:",
        request.method,
        request.url
    )

    response = await call_next(request)

    print(
        "Status:",
        response.status_code
    )

    return response
```

Flow:

```text
Request
   ↓
Middleware
   ↓
Endpoint
   ↓
Middleware
   ↓
Response
```

Common uses:

```text
Logging
Request timing
Request IDs
CORS
Security-related processing
```

## 25. CORS

CORS means **Cross-Origin Resource Sharing**.

It controls which browser origins can make requests to your API.

Example:

```python
from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware

app = FastAPI()


app.add_middleware(
    CORSMiddleware,
    allow_origins=[
        "https://example.com"
    ],
    allow_methods=["*"],
    allow_headers=["*"]
)
```

In production, avoid blindly allowing every origin.

## 26. Routers

As the application grows, don't put every endpoint in `main.py`.

Project structure:

```text
project/
│
├── main.py
│
├── routers/
│   ├── customers.py
│   └── orders.py
│
├── services/
│   ├── customer_service.py
│   └── order_service.py
│
├── repositories/
│   └── customer_repository.py
│
└── models/
    └── customer.py
```

Router:

```python
from fastapi import APIRouter

router = APIRouter()


@router.get("/customers")
def get_customers():
    return {"customers": []}
```

Main application:

```python
from fastapi import FastAPI
from routers.customers import router as customer_router

app = FastAPI()

app.include_router(customer_router)
```

Routers help organize large applications.

## 27. Service Layer

The service layer contains business logic.

Instead of:

```text
Router
 ↓
Database
```

use:

```text
Router
 ↓
Service
 ↓
Repository
 ↓
Database
```

Example:

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()


class CustomerCreate(BaseModel):
    name: str
    email: str


class CustomerService:

    def create(self, customer):
        return {
            "id": 1,
            "name": customer.name,
            "email": customer.email
        }


customer_service = CustomerService()


@app.post("/customers")
def create_customer(
    customer: CustomerCreate
):

    return customer_service.create(customer)
```

The endpoint should ideally remain thin.

## 28. Repository Layer

The repository handles database access.

Architecture:

```text
HTTP Request
     ↓
Router
     ↓
Service
     ↓
Repository
     ↓
Database
```

Example:

```python
class CustomerRepository:

    def save(self, customer):
        # database operation
        return customer

    def find_by_id(self, customer_id):
        # database query
        return None
```

The service can then use the repository:

```python
class CustomerService:

    def __init__(self, repository):
        self.repository = repository

    def create(self, customer):
        return self.repository.save(customer)
```

## 29. Error Handling

You can handle specific application exceptions globally.

```python
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

app = FastAPI()


@app.exception_handler(ValueError)
async def value_error_handler(
    request: Request,
    exc: ValueError
):

    return JSONResponse(
        status_code=400,
        content={
            "detail": str(exc)
        }
    )
```

Then:

```python
raise ValueError("Invalid customer")
```

can be converted into a controlled HTTP response.

## 31. BackgroundTasks

FastAPI provides lightweight background tasks.

```python
from fastapi import FastAPI, BackgroundTasks

app = FastAPI()


def write_log(message):
    print(message)


@app.post("/customers")
def create_customer(
    background_tasks: BackgroundTasks
):

    background_tasks.add_task(
        write_log,
        "Customer created"
    )

    return {
        "message": "Created"
    }
```

The response can be returned without waiting for the background task.

For serious durable workloads such as large ETL jobs, use a proper task queue/orchestration system rather than relying only on FastAPI `BackgroundTasks`.

## 38. FastAPI + ETL

A common mistake is putting a huge ETL job directly inside a normal HTTP request.

Instead of:

```text
POST /run-etl
      ↓
HTTP request waits
      ↓
2-hour ETL
      ↓
response
```

a better design is:

```text
POST /etl/jobs
      ↓
Create job
      ↓
Return job_id
      ↓
Background worker / queue / orchestrator
      ↓
ETL runs
      ↓
GET /etl/jobs/{job_id}
      ↓
Check status
```

Example:

```python
from fastapi import FastAPI

app = FastAPI()


@app.post("/etl/jobs")
def start_etl_job():

    job_id = "12345"

    # Submit job to a worker/queue/orchestrator.

    return {
        "job_id": job_id,
        "status": "started"
    }


@app.get("/etl/jobs/{job_id}")
def get_job_status(job_id: str):

    return {
        "job_id": job_id,
        "status": "running"
    }
```

This separates the API layer from the long-running ETL workload.

## 39. FastAPI + Async vs Threads

For async-compatible I/O:

```python
@app.get("/customer")
async def customer():

    result = await async_api_call()

    return result
```

For blocking synchronous I/O, threads can sometimes be appropriate.

The important distinction is:

```text
Async I/O
→ async/await

Blocking I/O
→ threads can help

CPU-heavy Python work
→ multiprocessing / separate workers
```

Don't blindly create a new thread for every request.

## 40. Complete FastAPI Example

This combines several important concepts:

```python
from fastapi import FastAPI, HTTPException, status
from pydantic import BaseModel


app = FastAPI()


class CustomerCreate(BaseModel):
    name: str
    email: str
    age: int


class CustomerResponse(BaseModel):
    id: int
    name: str
    email: str
    age: int


customers = {}


@app.post(
    "/customers",
    response_model=CustomerResponse,
    status_code=status.HTTP_201_CREATED
)
def create_customer(
    customer: CustomerCreate
):

    customer_id = len(customers) + 1

    new_customer = {
        "id": customer_id,
        "name": customer.name,
        "email": customer.email,
        "age": customer.age
    }

    customers[customer_id] = new_customer

    return new_customer


@app.get(
    "/customers/{customer_id}",
    response_model=CustomerResponse
)
def get_customer(
    customer_id: int
):

    customer = customers.get(customer_id)

    if customer is None:

        raise HTTPException(
            status_code=404,
            detail="Customer not found"
        )

    return customer


@app.patch(
    "/customers/{customer_id}",
    response_model=CustomerResponse
)
def update_customer(
    customer_id: int,
    customer: CustomerCreate
):

    if customer_id not in customers:

        raise HTTPException(
            status_code=404,
            detail="Customer not found"
        )

    updated_customer = {
        "id": customer_id,
        "name": customer.name,
        "email": customer.email,
        "age": customer.age
    }

    customers[customer_id] = updated_customer

    return updated_customer


@app.delete(
    "/customers/{customer_id}",
    status_code=status.HTTP_204_NO_CONTENT
)
def delete_customer(
    customer_id: int
):

    if customer_id not in customers:

        raise HTTPException(
            status_code=404,
            detail="Customer not found"
        )

    del customers[customer_id]
```

```text
                         ↓
                    HTTP Response
```

# 43. Interview Questions

### Q1. What is FastAPI?

> FastAPI is a modern Python web framework for building APIs. It uses Python type hints, Pydantic validation, ASGI, and automatically generates OpenAPI documentation.

### Q2. What is Pydantic `BaseModel`?

> `BaseModel` is used to define structured data models and validate/parse request and response data.

### Q3. What is dependency injection in FastAPI?

> FastAPI's dependency injection system allows reusable components such as authentication, database sessions, and common logic to be provided to endpoints using `Depends`.

### Q4. What is middleware?

> Middleware runs around the request/response lifecycle and is useful for concerns such as logging, request IDs, timing, and CORS.

### Q5. Difference between PUT and PATCH?

> PUT generally represents replacing a resource, while PATCH is used for partial updates.

### Q6. Difference between 401 and 403?

> 401 means the request has not been properly authenticated. 403 means the client is authenticated but does not have permission to perform the operation.

### Q7. How does FastAPI validate requests?

> FastAPI uses type hints and Pydantic models to parse and validate path parameters, query parameters, and request bodies before calling the endpoint.

### Q8. Why use `response_model`?

> It defines the expected response schema, validates the response, improves API documentation, and can prevent unwanted fields from being exposed.

### Q9. Why use routers?

> Routers allow a large FastAPI application to be split into modular groups of endpoints instead of putting everything in one file.

### Q10. How would you structure a production FastAPI application?

> I would separate routers, schemas/models, services, repositories, configuration, authentication, and database access. The router handles HTTP concerns, the service contains business logic, and the repository handles data access.

### Q11. When would you use async in FastAPI?

> I would use async endpoints when the underlying operations are asynchronous, particularly for high-concurrency I/O such as asynchronous database or HTTP calls.

### Q12. Would you run a 2-hour ETL job directly inside a FastAPI request?

> No. I would normally submit the ETL job to a background worker, queue, or orchestration system, return a job ID, and provide another endpoint for checking job status.

### Q13. How would you handle a large file upload?

> I would avoid loading the entire file into memory. I would process or stream the file incrementally and apply appropriate size limits and validation.

### Q14. How do you secure API credentials?

> I would not hardcode secrets. I would use environment variables or a dedicated secret-management system and restrict access appropriately.

### Q15. How do you test a FastAPI API?

> I would use FastAPI's `TestClient` with pytest to test status codes, response bodies, validation errors, authentication, and important business scenarios.

# 44. Final Interview Summary

> **FastAPI is a Python framework for building APIs using type hints, Pydantic validation, and ASGI. A production FastAPI application typically uses routers for API organization, Pydantic models for request/response schemas, dependencies for reusable logic such as authentication and database sessions, services for business logic, repositories for database access, middleware for cross-cutting concerns, and proper error handling/logging/testing. For long-running ETL jobs, the API should generally submit work to a worker or orchestration system rather than keeping an HTTP request open for the entire job.**
