# Part 7: Error Handling and Security — Complete FastAPI Guide

## 79. HTTPException

`HTTPException` is used in FastAPI to stop the execution of an API request and return an HTTP error response to the client.

It is useful when:
- A requested resource does not exist.
- A user is not authenticated.
- A user does not have permission.
- A request contains invalid business data.
- A requested operation cannot be completed.

### Why do we need HTTPException?

Imagine a user requests:

```http
GET /users/100
```

But user ID 100 does not exist in the database.

Instead of returning an empty response or an internal server error, we should return:

```json
{
  "detail": "User not found"
}
```

With status code:

```text
404 Not Found
```

### Basic syntax

```python
from fastapi import FastAPI, HTTPException

app = FastAPI()

@app.get("/users/{user_id}")
def get_user(user_id: int):

    if user_id != 1:
        raise HTTPException(
            status_code=404,
            detail="User not found"
        )

    return {
        "id": 1,
        "name": "John"
    }
```

### Test successful request

Request:

```http
GET /users/1
```

Expected output:

```json
{
  "id": 1,
  "name": "John"
}
```

Status:

```text
200 OK
```

### Test unsuccessful request

Request:

```http
GET /users/100
```

Expected output:

```json
{
  "detail": "User not found"
}
```

Status:

```text
404 Not Found
```

### Common HTTP status codes

| Status code | Meaning | Example |
|---|---|---|
| 400 | Bad Request | Invalid business request |
| 401 | Unauthorized | Missing or invalid credentials |
| 403 | Forbidden | User lacks permission |
| 404 | Not Found | User does not exist |
| 409 | Conflict | Duplicate email |
| 422 | Validation Error | Invalid request data |
| 429 | Too Many Requests | Rate limit exceeded |
| 500 | Internal Server Error | Unexpected server error |
| 503 | Service Unavailable | Dependency temporarily unavailable |

### Returning additional details

You can return a string or structured data in the `detail` field.

```python
from fastapi import FastAPI, HTTPException

app = FastAPI()

@app.get("/products/{product_id}")
def get_product(product_id: int):

    if product_id == 100:
        raise HTTPException(
            status_code=404,
            detail={
                "error_code": "PRODUCT_NOT_FOUND",
                "message": "Product does not exist",
                "product_id": product_id
            }
        )

    return {
        "id": product_id,
        "name": "Laptop"
    }
```

Expected output for `/products/100`:

```json
{
  "detail": {
    "error_code": "PRODUCT_NOT_FOUND",
    "message": "Product does not exist",
    "product_id": 100
  }
}
```

### Adding response headers

```python
raise HTTPException(
    status_code=401,
    detail="Invalid authentication",
    headers={
        "WWW-Authenticate": "Bearer"
    }
)
```

This is useful for authentication-related errors.

**Important:** Use appropriate HTTP status codes. Do not return status 200 for failed operations.

## 80. Custom Exception Classes

A custom exception class allows you to create application-specific errors.

Instead of writing `HTTPException` everywhere, you can define meaningful exceptions for your business logic.

### Why use custom exceptions?

Imagine an e-commerce application.

Possible errors include:

- ProductNotFound
- InsufficientStock
- PaymentFailed
- OrderAlreadyCancelled
- UserAlreadyExists

Using custom exceptions makes application code easier to understand and maintain.

### Basic Python example

```python
class InsufficientStockError(Exception):
    pass


def purchase_product(quantity, available_stock):

    if quantity > available_stock:
        raise InsufficientStockError(
            "Not enough stock available"
        )

    return "Purchase successful"


try:
    print(purchase_product(10, 5))

except InsufficientStockError as error:
    print(error)
```

Expected output:

```text
Not enough stock available
```

### Custom exception with additional information

```python
class ProductNotFoundError(Exception):

    def __init__(self, product_id):

        self.product_id = product_id

        super().__init__(
            f"Product {product_id} not found"
        )


try:
    raise ProductNotFoundError(100)

except ProductNotFoundError as error:

    print(error)
    print(error.product_id)
```

Expected output:

```text
Product 100 not found
100
```

### Using custom exceptions in FastAPI

```python
from fastapi import FastAPI, HTTPException

app = FastAPI()


class ProductNotFoundError(Exception):

    def __init__(self, product_id):

        self.product_id = product_id


def find_product(product_id):

    products = {
        1: "Laptop",
        2: "Mobile"
    }

    if product_id not in products:
        raise ProductNotFoundError(product_id)

    return products[product_id]


@app.get("/products/{product_id}")
def get_product(product_id: int):

    try:

        product = find_product(product_id)

        return {
            "product": product
        }

    except ProductNotFoundError as error:

        raise HTTPException(
            status_code=404,
            detail=f"Product {error.product_id} not found"
        )
```

Request:

```http
GET /products/100
```

Expected output:

```json
{
  "detail": "Product 100 not found"
}
```

### Recommended project structure

```text
app/
│
├── main.py
│
├── exceptions/
│   └── custom_exceptions.py
│
├── services/
│   └── product_service.py
│
└── routers/
    └── product_router.py
```

`custom_exceptions.py`:

```python
class ProductNotFoundError(Exception):
    pass


class InsufficientStockError(Exception):
    pass


class PaymentFailedError(Exception):
    pass
```

**Important:** Keep business exceptions independent of HTTP where possible. Your service layer should describe what went wrong; your API layer should decide which HTTP response represents that failure.

## 81. Global Exception Handlers

A global exception handler allows you to handle exceptions centrally across your FastAPI application.

Without global exception handlers, you may need to write similar `try-except` blocks in many endpoints.

### Why use global exception handlers?

Imagine your application has 50 endpoints.

If all endpoints need to handle a product-not-found error, repeating the same response logic creates unnecessary duplication.

A global exception handler solves this.

### Basic global exception handler

```python
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

app = FastAPI()


class ProductNotFoundError(Exception):
    pass


@app.exception_handler(ProductNotFoundError)
async def product_not_found_handler(
    request: Request,
    exc: ProductNotFoundError
):

    return JSONResponse(
        status_code=404,
        content={
            "error": "PRODUCT_NOT_FOUND",
            "message": "Product not found"
        }
    )


@app.get("/products/{product_id}")
def get_product(product_id: int):

    if product_id != 1:
        raise ProductNotFoundError()

    return {
        "id": 1,
        "name": "Laptop"
    }
```

Request:

```http
GET /products/100
```

Expected output:

```json
{
  "error": "PRODUCT_NOT_FOUND",
  "message": "Product not found"
}
```

Status:

```text
404 Not Found
```

Notice that the endpoint does not need a `try-except` block.

### Handling unexpected exceptions globally

You can also register a handler for unexpected exceptions.

```python
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

app = FastAPI()


@app.exception_handler(Exception)
async def global_exception_handler(
    request: Request,
    exc: Exception
):

    # Log the full exception securely in production.
    return JSONResponse(
        status_code=500,
        content={
            "error": "INTERNAL_SERVER_ERROR",
            "message": "An unexpected error occurred"
        }
    )


@app.get("/test")
def test():

    result = 10 / 0

    return {
        "result": result
    }
```

Expected API response:

```json
{
  "error": "INTERNAL_SERVER_ERROR",
  "message": "An unexpected error occurred"
}
```

Status:

```text
500 Internal Server Error
```

The full exception should be logged internally with a correlation or request ID. Do not expose stack traces or internal details to clients.

### Handling FastAPI HTTP exceptions

FastAPI's `HTTPException` inherits from Starlette's HTTP exception.

You can register a handler for Starlette's `HTTPException` to handle HTTP errors consistently.

```python
from fastapi import FastAPI, HTTPException, Request
from starlette.exceptions import HTTPException as StarletteHTTPException
from fastapi.responses import JSONResponse

app = FastAPI()


@app.exception_handler(StarletteHTTPException)
async def http_exception_handler(
    request: Request,
    exc: StarletteHTTPException
):

    return JSONResponse(
        status_code=exc.status_code,
        content={
            "error": "HTTP_ERROR",
            "message": exc.detail
        },
        headers=exc.headers
    )


@app.get("/users/{user_id}")
def get_user(user_id: int):

    if user_id != 1:
        raise HTTPException(
            status_code=404,
            detail="User not found"
        )

    return {
        "id": 1,
        "name": "John"
    }
```

Expected output:

```json
{
  "error": "HTTP_ERROR",
  "message": "User not found"
}
```

### Exception handling priority

More specific exception handlers are used for matching exception types before a general handler is used.

A useful design is:

1. Handle known business exceptions.
2. Handle HTTP exceptions.
3. Handle request validation exceptions.
4. Handle unexpected exceptions.

## 82. Request Validation Errors

FastAPI uses Pydantic to validate incoming request data.

When request data does not match the expected schema, FastAPI automatically returns a validation error.

### Why is request validation important?

Imagine an API expects:

```json
{
  "name": "John",
  "age": 25
}
```

But the client sends:

```json
{
  "name": "John",
  "age": "hello"
}
```

The `age` field should be an integer, but the client sends a string that cannot be converted into an integer.

FastAPI automatically rejects the request.

### Basic validation example

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()


class User(BaseModel):

    name: str
    age: int


@app.post("/users")
def create_user(user: User):

    return {
        "message": "User created",
        "user": user
    }
```

Valid request:

```json
{
  "name": "John",
  "age": 25
}
```

Expected output:

```json
{
  "message": "User created",
  "user": {
    "name": "John",
    "age": 25
  }
}
```

Invalid request:

```json
{
  "name": "John",
  "age": "hello"
}
```

Expected response:

```json
{
  "detail": [
    {
      "type": "int_parsing",
      "loc": [
        "body",
        "age"
      ],
      "msg": "Input should be a valid integer",
      "input": "hello"
    }
  ]
}
```

The exact validation response can vary depending on the Pydantic and FastAPI versions.

Status:

```text
422 Unprocessable Entity
```

### Add validation constraints

Pydantic provides validation tools such as:

- Field
- String length constraints
- Numeric limits
- Pattern matching
- Custom validators

Example:

```python
from fastapi import FastAPI
from pydantic import BaseModel, Field

app = FastAPI()


class User(BaseModel):

    username: str = Field(
        min_length=3,
        max_length=20
    )

    age: int = Field(
        ge=18,
        le=100
    )

    email: str


@app.post("/register")
def register(user: User):

    return {
        "message": "Registration successful",
        "user": user
    }
```

Valid input:

```json
{
  "username": "john123",
  "age": 25,
  "email": "john@example.com"
}
```

Expected output:

```json
{
  "message": "Registration successful",
  "user": {
    "username": "john123",
    "age": 25,
    "email": "john@example.com"
  }
}
```

Invalid input:

```json
{
  "username": "jo",
  "age": 15,
  "email": "john@example.com"
}
```

Expected result:

```text
422 Unprocessable Entity
```

The response contains validation details for the username and age fields.

**Important:** Request validation protects the structure and constraints of incoming data. It does not replace database constraints, authorisation, or business-rule validation.

## 83. Custom Error Responses

By default, FastAPI returns different response formats for different errors.

For example:

HTTPException:

```json
{
  "detail": "User not found"
}
```

Validation error:

```json
{
  "detail": [
    {
      "type": "missing",
      "loc": ["body", "name"],
      "msg": "Field required"
    }
  ]
}
```

A production application may prefer a consistent error response structure.

### Why standardise error responses?

Imagine the frontend receives errors from multiple endpoints.

Without a standard format, frontend developers need to handle many different response structures.

A standard response makes error handling easier.

### Recommended error response structure

```json
{
  "success": false,
  "error": {
    "code": "USER_NOT_FOUND",
    "message": "User does not exist"
  },
  "request_id": "req-123"
}
```

### Create a custom error handler

```python
from fastapi import FastAPI, HTTPException, Request
from fastapi.responses import JSONResponse

app = FastAPI()


@app.exception_handler(HTTPException)
async def custom_http_exception_handler(
    request: Request,
    exc: HTTPException
):

    return JSONResponse(
        status_code=exc.status_code,
        content={
            "success": False,
            "error": {
                "code": "HTTP_ERROR",
                "message": exc.detail
            }
        },
        headers=exc.headers
    )


@app.get("/users/{user_id}")
def get_user(user_id: int):

    if user_id != 1:
        raise HTTPException(
            status_code=404,
            detail="User not found"
        )

    return {
        "id": 1,
        "name": "John"
    }
```

Expected output:

```json
{
  "success": false,
  "error": {
    "code": "HTTP_ERROR",
    "message": "User not found"
  }
}
```

### Custom validation error response

```python
from fastapi import FastAPI, Request
from fastapi.exceptions import RequestValidationError
from fastapi.responses import JSONResponse

app = FastAPI()


@app.exception_handler(RequestValidationError)
async def validation_exception_handler(
    request: Request,
    exc: RequestValidationError
):

    errors = []

    for error in exc.errors():

        errors.append({
            "field": ".".join(
                str(item) for item in error["loc"]
            ),
            "message": error["msg"]
        })

    return JSONResponse(
        status_code=422,
        content={
            "success": False,
            "error": {
                "code": "VALIDATION_ERROR",
                "message": "Request validation failed",
                "details": errors
            }
        }
    )
```

Expected response for a missing `name` field:

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request validation failed",
    "details": [
      {
        "field": "body.name",
        "message": "Field required"
      }
    ]
  }
}
```

**Important:** Avoid returning sensitive submitted values from validation errors. Do not blindly expose the complete exception object or request body to clients.

## 84. CORS Configuration

CORS stands for Cross-Origin Resource Sharing.

It is a browser security mechanism that controls whether a web page from one origin can access resources from another origin.

### What is an origin?

An origin consists of:

```text
scheme + hostname + port
```

For example:

```text
Frontend:
http://localhost:3000

Backend:
http://localhost:8000
```

These are different origins because their ports are different.

When frontend JavaScript calls the backend, the browser applies CORS rules.

### Why do we need CORS?

Imagine:

- React frontend runs on port 3000.
- FastAPI backend runs on port 8000.

The frontend requests:

```text
http://localhost:8000/users
```

The browser checks whether the backend permits the frontend origin.

If the backend does not return the appropriate CORS headers, the browser blocks JavaScript from accessing the response.

### Configure CORS in FastAPI

```python
from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware

app = FastAPI()

app.add_middleware(
    CORSMiddleware,
    allow_origins=[
        "http://localhost:3000"
    ],
    allow_credentials=True,
    allow_methods=[
        "GET",
        "POST",
        "PUT",
        "DELETE"
    ],
    allow_headers=[
        "Authorization",
        "Content-Type"
    ]
)


@app.get("/users")
def get_users():

    return {
        "users": [
            "John",
            "David"
        ]
    }
```

### What do these settings mean?

| Setting | Purpose |
|---|---|
| allow_origins | Allowed frontend origins |
| allow_credentials | Allows credentials in CORS requests |
| allow_methods | Allowed HTTP methods |
| allow_headers | Allowed request headers |
| expose_headers | Headers browser JavaScript may read |

### Example browser request

```javascript
fetch("http://localhost:8000/users")
  .then(response => response.json())
  .then(data => console.log(data));
```

Expected console output:

```json
{
  "users": [
    "John",
    "David"
  ]
}
```

### What is a preflight request?

For certain cross-origin requests, the browser first sends an OPTIONS request to check whether the actual request is permitted.

Example:

```http
OPTIONS /users
Origin: http://localhost:3000
Access-Control-Request-Method: POST
Access-Control-Request-Headers: authorization,content-type
```

The server responds with appropriate CORS headers if the request is allowed.

### Important CORS security rules

Avoid this combination:

```python
allow_origins=["*"]
allow_credentials=True
```

Credentialed CORS requests require explicit allowed origins rather than a wildcard origin.

In production:

- Allow only trusted frontend origins.
- Allow only required HTTP methods.
- Allow only required headers.
- Configure credential support only when necessary.
- Do not treat CORS as authentication or authorisation.

CORS is enforced by browsers. It does not stop command-line clients, scripts, or other servers from calling your API.

## 85. SQL Injection Prevention

SQL injection is a security vulnerability where an attacker manipulates SQL queries through malicious input.

It happens when applications combine user input directly into SQL statements.

### Vulnerable example

Imagine an application has a login endpoint.

Unsafe code:

```python
username = input("Enter username: ")

query = (
    "SELECT * FROM users "
    f"WHERE username = '{username}'"
)

print(query)
```

Normal input:

```text
john
```

Generated SQL:

```sql
SELECT * FROM users WHERE username = 'john'
```

Malicious input:

```text
' OR '1'='1
```

Generated SQL:

```sql
SELECT * FROM users WHERE username = '' OR '1'='1'
```

The condition `'1'='1'` is always true.

Depending on the query and database, this may allow an attacker to bypass checks or access unintended records.

### Prevent SQL injection using parameterised queries

Use parameters rather than joining user input into SQL strings.

Example with SQLite:

```python
import sqlite3

connection = sqlite3.connect(":memory:")

cursor = connection.cursor()

cursor.execute("""
CREATE TABLE users (
    id INTEGER PRIMARY KEY,
    username TEXT
)
""")

cursor.execute(
    "INSERT INTO users (username) VALUES (?)",
    ("john",)
)

username = "john"

cursor.execute(
    "SELECT * FROM users WHERE username = ?",
    (username,)
)

print(cursor.fetchall())
```

Expected output:

```text
[(1, 'john')]
```

The database treats the parameter as data, not executable SQL syntax.

### SQLAlchemy example

Install:

```bash
pip install sqlalchemy
```

Use SQLAlchemy ORM:

```python
from sqlalchemy import (
    create_engine,
    String,
    select
)

from sqlalchemy.orm import (
    DeclarativeBase,
    Mapped,
    mapped_column,
    Session
)


class Base(DeclarativeBase):
    pass


class User(Base):

    __tablename__ = "users"

    id: Mapped[int] = mapped_column(
        primary_key=True
    )

    username: Mapped[str] = mapped_column(
        String(100)
    )


engine = create_engine("sqlite:///example.db")

Base.metadata.create_all(engine)

with Session(engine) as session:

    statement = select(User).where(
        User.username == "john"
    )

    users = session.scalars(statement).all()

    print([user.username for user in users])
```

Expected output if John exists:

```text
['john']
```

### SQL injection prevention rules

1. Use parameterised SQL queries.
2. Use SQLAlchemy ORM or properly parameterised SQL.
3. Never concatenate raw user input into SQL.
4. Validate input types and lengths.
5. Use database accounts with minimum required permissions.
6. Do not expose database error details.
7. Keep database software updated.

**Important:** SQLAlchemy does not automatically make every SQL statement safe. Avoid building raw SQL by string concatenation, even when using SQLAlchemy.

## 86. Input Validation and Sanitisation

Input validation and sanitisation help protect an application from invalid or malicious input.

They are related but different concepts.

### Input validation

Validation checks whether input follows the expected rules.

Example:

```text
Age must be an integer between 18 and 100.
```

### Input sanitisation

Sanitisation transforms or removes unwanted input where that transformation is appropriate.

Example:

```text
Remove unwanted control characters.
Normalise a value before processing it.
```

Do not assume that removing characters makes input safe for every context.

### Example Pydantic validation

```python
from fastapi import FastAPI
from pydantic import BaseModel, Field, EmailStr

app = FastAPI()


class UserCreate(BaseModel):

    username: str = Field(
        min_length=3,
        max_length=30,
        pattern=r"^[a-zA-Z0-9_]+$"
    )

    age: int = Field(
        ge=18,
        le=100
    )

    email: EmailStr


@app.post("/users")
def create_user(user: UserCreate):

    return {
        "message": "User created",
        "username": user.username,
        "age": user.age,
        "email": user.email
    }
```

Install the email validation dependency:

```bash
pip install email-validator
```

Valid request:

```json
{
  "username": "john_123",
  "age": 25,
  "email": "john@example.com"
}
```

Expected output:

```json
{
  "message": "User created",
  "username": "john_123",
  "age": 25,
  "email": "john@example.com"
}
```

Invalid username:

```json
{
  "username": "<script>",
  "age": 25,
  "email": "john@example.com"
}
```

Expected status:

```text
422 Unprocessable Entity
```

### Example of normalising input

```python
def normalise_username(username: str):

    return username.strip().lower()


print(normalise_username("  JOHN123  "))
```

Expected output:

```text
john123
```

### Preventing XSS

Cross-Site Scripting (XSS) happens when untrusted data is interpreted as executable browser content.

For example, a user submits:

```html
<script>alert('hacked')</script>
```

If the application inserts this directly into an HTML page without appropriate output encoding, it may execute in the browser.

Recommended protections:

- Use framework-provided HTML escaping.
- Avoid unsafe HTML rendering.
- Validate inputs according to their intended format.
- Encode output for the correct context.
- Use Content Security Policy as an additional protection.
- Avoid treating input sanitisation as a replacement for output encoding.

### Important distinction

| Technique | Purpose |
|---|---|
| Validation | Check whether data is acceptable |
| Sanitisation | Transform data where appropriate |
| Parameterisation | Keep data separate from SQL syntax |
| Output encoding | Prevent data being interpreted as executable content |

Validation alone does not prevent SQL injection or XSS.

## 87. Rate Limiting

Rate limiting controls how many requests a client can make within a specific period.

It protects APIs against:
- Brute-force login attempts.
- Excessive traffic.
- Automated abuse.
- Accidental request loops.
- Some denial-of-service patterns.

### Example rate limit

```text
Maximum 5 requests per minute
```

If a client sends more than five requests within the configured period, the API returns:

```text
429 Too Many Requests
```

### Install SlowAPI

```bash
pip install slowapi
```

### FastAPI rate-limiting example

```python
from fastapi import FastAPI, Request
from slowapi import Limiter, _rate_limit_exceeded_handler
from slowapi.util import get_remote_address
from slowapi.errors import RateLimitExceeded

app = FastAPI()

limiter = Limiter(
    key_func=get_remote_address
)

app.state.limiter = limiter

app.add_exception_handler(
    RateLimitExceeded,
    _rate_limit_exceeded_handler
)


@app.get("/test")
@limiter.limit("5/minute")
async def test(request: Request):

    return {
        "message": "Request successful"
    }
```

### Test the endpoint

Send five requests within one minute.

Expected response:

```json
{
  "message": "Request successful"
}
```

Send a sixth request within the same rate-limit window.

Expected result:

```text
429 Too Many Requests
```

The response typically includes a rate-limit error message and may include a `Retry-After` header depending on the implementation.

### How rate limiting works

```text
Client sends request
       |
       v
Check request counter
       |
       +---- Under limit ----> Process request
       |
       +---- Over limit -----> Return 429
```

### Rate-limiting strategies

| Strategy | Description |
|---|---|
| Fixed Window | Counts requests within fixed time windows |
| Sliding Window | Counts requests across a moving time period |
| Token Bucket | Allows bursts while controlling average rate |
| Leaky Bucket | Processes requests at a controlled rate |

### Production considerations

An in-memory rate limiter is not enough when you run multiple application workers or multiple servers.

For production:
- Use a shared store such as Redis.
- Apply limits to sensitive endpoints such as login and password reset.
- Consider limits by user, API key, and IP address.
- Return appropriate 429 responses.
- Use trusted proxy configuration carefully.

Never blindly trust client-supplied `X-Forwarded-For` headers when identifying the client IP. Configure trusted proxies correctly.

Rate limiting helps reduce abuse but does not replace infrastructure-level DDoS protection.

## 88. Secure Headers

HTTP security headers instruct browsers how to handle certain security-sensitive behaviours.

They help protect against attacks such as:
- Clickjacking.
- MIME-type sniffing.
- Some XSS attacks.
- Unencrypted connections.
- Unwanted resource loading.

### Important security headers

| Header | Purpose |
|---|---|
| Strict-Transport-Security | Enforces HTTPS in supporting browsers |
| X-Content-Type-Options | Prevents MIME-type sniffing |
| X-Frame-Options | Controls framing to reduce clickjacking |
| Content-Security-Policy | Restricts permitted content sources |
| Referrer-Policy | Controls referrer information |
| Permissions-Policy | Restricts browser features |

### Configure secure headers in FastAPI

```python
from fastapi import FastAPI, Request

app = FastAPI()


@app.middleware("http")
async def security_headers(
    request: Request,
    call_next
):

    response = await call_next(request)

    response.headers[
        "X-Content-Type-Options"
    ] = "nosniff"

    response.headers[
        "X-Frame-Options"
    ] = "DENY"

    response.headers[
        "Referrer-Policy"
    ] = "strict-origin-when-cross-origin"

    response.headers[
        "Content-Security-Policy"
    ] = "default-src 'self'"

    response.headers[
        "Permissions-Policy"
    ] = "camera=(), microphone=(), geolocation=()"

    return response


@app.get("/")
def home():

    return {
        "message": "Secure API"
    }
```

### Expected response headers

```http
HTTP/1.1 200 OK
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Referrer-Policy: strict-origin-when-cross-origin
Content-Security-Policy: default-src 'self'
Permissions-Policy: camera=(), microphone=(), geolocation=()
```

### Configure HSTS

HSTS tells browsers to use HTTPS for future requests to the domain.

Example:

```python
response.headers[
    "Strict-Transport-Security"
] = "max-age=31536000; includeSubDomains"
```

Only enable HSTS when your domain and all included subdomains are correctly configured for HTTPS.

### Important notes

- A strict Content Security Policy can break frontend applications if it does not account for their scripts, styles, images, and API connections.
- `X-Frame-Options: DENY` prevents all framing and may not suit applications that must be embedded.
- HSTS should only be sent over HTTPS.
- Security headers are additional protections, not replacements for authentication, authorisation, or input validation.

## 89. Secrets and Environment Configuration

Applications often require sensitive values such as:

- Database passwords.
- JWT signing keys.
- AWS access credentials.
- API keys.
- Third-party service tokens.

These are called secrets.

### Why should secrets not be hard-coded?

Unsafe example:

```python
DATABASE_PASSWORD = "mypassword123"

SECRET_KEY = "my-secret-key"
```

Problems:
- Secrets may be committed to Git.
- Developers may share secrets accidentally.
- Secrets may appear in logs.
- Rotation becomes difficult.
- Different environments need different credentials.

### Use environment variables

Environment variables allow configuration to be supplied separately from application source code.

Example:

```python
import os

DATABASE_URL = os.getenv(
    "DATABASE_URL"
)

SECRET_KEY = os.getenv(
    "SECRET_KEY"
)

print("Configuration loaded")
```

Set variables in the shell:

```bash
export DATABASE_URL="sqlite:///./app.db"

export SECRET_KEY="replace-with-a-secure-secret"
```

Expected output:

```text
Configuration loaded
```

### Use a .env file during local development

Install:

```bash
pip install python-dotenv
```

Create `.env`:

```text
DATABASE_URL=sqlite:///./app.db
SECRET_KEY=replace-with-a-secure-secret
```

Load it:

```python
from dotenv import load_dotenv
import os

load_dotenv()

DATABASE_URL = os.getenv("DATABASE_URL")

SECRET_KEY = os.getenv("SECRET_KEY")

print(DATABASE_URL)
print("Secret loaded:", SECRET_KEY is not None)
```

Expected output:

```text
sqlite:///./app.db
Secret loaded: True
```

Do not commit `.env` files containing real secrets.

Add to `.gitignore`:

```text
.env
.env.*
!.env.example
```

An `.env.example` should contain placeholders only:

```text
DATABASE_URL=your-database-url
SECRET_KEY=your-secret-key
```

### Use Pydantic Settings

For larger applications, use Pydantic Settings to manage configuration centrally.

Install:

```bash
pip install pydantic-settings
```

Create `config.py`:

```python
from pydantic_settings import (
    BaseSettings,
    SettingsConfigDict
)


class Settings(BaseSettings):

    database_url: str

    secret_key: str

    debug: bool = False

    model_config = SettingsConfigDict(
        env_file=".env",
        env_file_encoding="utf-8",
        extra="ignore"
    )


settings = Settings()
```

Use it:

```python
from fastapi import FastAPI
from config import settings

app = FastAPI(
    debug=settings.debug
)

@app.get("/")
def home():

    return {
        "message": "Application started",
        "debug": settings.debug
    }
```

Example `.env`:

```text
DATABASE_URL=sqlite:///./app.db
SECRET_KEY=replace-with-a-secure-secret
DEBUG=false
```

Expected output:

```json
{
  "message": "Application started",
  "debug": false
}
```

### AWS Secrets Manager

For AWS-hosted applications, AWS Secrets Manager can store and manage secrets such as:

```json
{
  "username": "app_user",
  "password": "database-password"
}
```

Your application can retrieve secrets using an IAM role with the required permissions.

Example architecture:

```text
FastAPI Application
       |
       | IAM role credentials
       v
AWS Secrets Manager
       |
       | Returns secret
       v
Application configuration
       |
       v
Database connection
```

### Environment configuration best practices

1. Never commit real secrets to source control.
2. Use separate credentials for development, testing, and production.
3. Use AWS Secrets Manager or another secret manager for production secrets.
4. Restrict secret access using IAM or equivalent access controls.
5. Rotate secrets periodically and after suspected exposure.
6. Do not print secrets in application logs.
7. Do not expose secrets through API responses.
8. Use least-privilege permissions.
9. Validate required configuration at startup.
10. Remember that environment variables are configuration, not encrypted storage.

**Important:** Setting `sensitive=True` in configuration tools may hide values from output, but it does not automatically encrypt stored secrets or Terraform state.

## 90. OWASP API Security Best Practices

OWASP is an organisation that publishes guidance for improving application and API security.

The OWASP API Security Top 10 identifies common API security risks.

The following list covers the 2023 edition.

### 1. Broken Object Level Authorisation (BOLA)

This happens when an API does not check whether the current user is allowed to access a specific object.

Example:

```http
GET /orders/100
```

An attacker changes the ID:

```http
GET /orders/200
```

If the API returns another user's order without checking ownership, the API has a BOLA vulnerability.

Prevention:

```python
@app.get("/orders/{order_id}")
def get_order(
    order_id: int,
    current_user=Depends(get_current_user)
):

    order = get_order_from_database(order_id)

    if order.owner_id != current_user.id:
        raise HTTPException(
            status_code=403,
            detail="Access denied"
        )

    return order
```

The example assumes `get_order_from_database()` and `get_current_user()` are implemented using trusted database and authentication logic.

### 2. Broken Authentication

This happens when authentication mechanisms are weak or incorrectly implemented.

Examples:
- Weak passwords.
- Missing rate limits.
- Insecure token validation.
- Poor refresh-token management.
- Weak session handling.

Prevention:
- Use secure password hashing.
- Use MFA where appropriate.
- Validate JWT signatures and claims.
- Rotate refresh tokens.
- Implement rate limiting.
- Protect account recovery workflows.

### 3. Broken Object Property Level Authorisation

This occurs when an API exposes or allows modification of object properties that the user should not access.

Example:

A normal user sends:

```json
{
  "name": "John",
  "role": "admin"
}
```

If the API blindly accepts the role field, the user may become an administrator.

Prevention:

Use separate request and response models.

```python
from pydantic import BaseModel

class UserUpdate(BaseModel):

    name: str
    email: str


class UserResponse(BaseModel):

    id: int
    name: str
    email: str
```

Do not allow public update models to modify privileged properties such as roles or account status.

### 4. Unrestricted Resource Consumption

An attacker may send too many requests or request excessively large resources.

Examples:
- Huge file uploads.
- Expensive database queries.
- Unbounded pagination.
- Repeated login attempts.
- Large batch operations.

Prevention:
- Apply rate limiting.
- Limit upload size.
- Set pagination limits.
- Apply query timeouts.
- Restrict expensive operations.
- Monitor CPU, memory, and database usage.

Example:

```python
from fastapi import FastAPI, Query

app = FastAPI()

@app.get("/users")
def get_users(
    limit: int = Query(
        default=10,
        ge=1,
        le=100
    )
):

    return {
        "limit": limit
    }
```

The client cannot request more than 100 records through this parameter.

### 5. Broken Function Level Authorisation

This occurs when users can call functions they should not be allowed to access.

Example:

```http
DELETE /admin/users/100
```

A normal user should not be allowed to delete users.

Prevention:

Check roles or permissions on the backend.

```python
@app.delete("/admin/users/{user_id}")
def delete_user(
    user_id: int,
    user=Depends(require_admin)
):

    return {
        "message": "User deleted"
    }
```

### 6. Unrestricted Access to Sensitive Business Flows

This occurs when an attacker abuses legitimate business operations.

Example:

A ticket booking API allows unlimited ticket reservations through automation.

Prevention:
- Apply business-specific rate limits.
- Limit reservations per user.
- Detect automated abuse.
- Use transaction controls.
- Require additional verification for risky operations.

### 7. Server Side Request Forgery (SSRF)

SSRF happens when an attacker tricks a server into making requests to unintended internal or external destinations.

Example:

An API accepts a URL:

```json
{
  "url": "http://127.0.0.1:8000/admin"
}
```

If the server fetches arbitrary URLs, an attacker may target internal services.

Prevention:
- Avoid accepting arbitrary URLs where possible.
- Use allowlists for permitted hosts.
- Block private, loopback, and link-local IP ranges.
- Validate resolved IP addresses.
- Disable redirects or revalidate every redirect destination.
- Apply network-level egress restrictions.

Do not rely on a simple string check alone. DNS resolution and redirects can introduce SSRF bypasses.

### 8. Security Misconfiguration

This happens when systems use insecure settings.

Examples:
- Debug mode enabled in production.
- Unrestricted CORS.
- Default passwords.
- Exposed documentation when it should be restricted.
- Detailed internal errors.
- Unnecessary open ports.

Prevention:
- Use secure production configuration.
- Disable debug mode.
- Restrict CORS.
- Review exposed endpoints.
- Remove unused services.
- Keep dependencies updated.
- Secure cloud and network permissions.

### 9. Improper Inventory Management

This happens when organisations fail to manage all API versions and endpoints.

Example:

The application has:

```text
/api/v1/users
/api/v2/users
```

The older `/api/v1/users` endpoint is no longer maintained but remains publicly accessible.

Prevention:
- Maintain an API inventory.
- Document versions.
- Remove unsupported endpoints.
- Monitor exposed environments.
- Secure development and staging APIs.

### 10. Unsafe Consumption of APIs

This happens when your application trusts data from third-party APIs without sufficient validation.

Example:

Your FastAPI application receives a response from an external payment provider and trusts all its fields.

Prevention:
- Validate external responses.
- Use HTTPS.
- Verify webhook signatures.
- Apply timeouts.
- Handle errors safely.
- Validate schemas and business rules.
- Do not blindly trust third-party data.

### OWASP API Security Summary

| OWASP risk | Main protection |
|---|---|
| BOLA | Check ownership and object-level access |
| Broken Authentication | Secure login and token management |
| Broken Object Property Level Authorisation | Control readable and writable fields |
| Unrestricted Resource Consumption | Rate limits and resource limits |
| Broken Function Level Authorisation | Check roles and permissions |
| Sensitive Business Flow Abuse | Apply business-specific controls |
| SSRF | Restrict outbound requests |
| Security Misconfiguration | Secure deployment configuration |
| Improper Inventory Management | Maintain API inventory |
| Unsafe API Consumption | Validate external responses |

# Common Interview Questions and Answers

### 1. What is HTTPException in FastAPI?

`HTTPException` is used to stop request processing and return an HTTP error response with a specific status code and message.

### 2. What is a custom exception?

A custom exception is an application-specific Python exception used to represent business errors, such as `ProductNotFoundError` or `InsufficientStockError`.

### 3. What is a global exception handler?

A global exception handler centrally handles a particular type of exception across the FastAPI application.

### 4. What is the default FastAPI validation status code?

FastAPI normally returns `422 Unprocessable Entity` when request validation fails.

### 5. What is CORS?

CORS is a browser security mechanism that controls whether frontend code from one origin can access resources from another origin.

### 6. Does CORS protect an API from unauthorised users?

No. CORS is not authentication or authorisation. Backend authentication and permission checks are still required.

### 7. What is SQL injection?

SQL injection occurs when attackers manipulate SQL queries through malicious input.

### 8. How do you prevent SQL injection?

Use parameterised queries, SQLAlchemy ORM, input validation, and database accounts with minimum permissions.

### 9. What is the difference between validation and sanitisation?

Validation checks whether data meets expected rules. Sanitisation transforms data where appropriate.

### 10. What is rate limiting?

Rate limiting controls the number of requests a client can make within a specific period.

### 11. What is HTTP 429?

It means the client has sent too many requests within a specified period.

### 12. What are secure HTTP headers?

They are response headers that instruct browsers to apply additional security protections, such as HTTPS enforcement and content restrictions.

### 13. Why should secrets be stored in environment variables?

They separate sensitive configuration from application source code, reducing accidental exposure through source control.

### 14. What is AWS Secrets Manager?

It is an AWS service used to securely store, manage, retrieve, and rotate secrets.

### 15. What is BOLA?

Broken Object Level Authorisation occurs when an API does not verify whether a user is allowed to access a particular object.

### 16. What is SSRF?

Server Side Request Forgery occurs when an attacker tricks an application into making requests to unintended destinations.

### 17. What is the difference between 401 and 403?

401 indicates missing or invalid authentication credentials. 403 indicates that access is denied despite the request being understood.

### 18. Why should we not expose stack traces?

Stack traces may reveal internal paths, implementation details, database information, or other sensitive information that helps attackers.
