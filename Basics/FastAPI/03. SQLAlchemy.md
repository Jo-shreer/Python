# Production-Level FastAPI + SQLAlchemy Architecture

## 1. How a production REST API is structured

In a production application, we should not put all our code inside one `main.py` file.

We separate responsibilities into layers so that the application is maintainable, testable, scalable, and easier to debug.

A typical project structure looks like this:

```text
app/
├── main.py
├── core/
│   └── config.py
├── db/
│   ├── base.py
│   └── session.py
├── models/
│   └── user.py
├── schemas/
│   └── user.py
├── repositories/
│   └── user_repository.py
├── services/
│   └── user_service.py
├── routers/
│   └── user_router.py
└── migrations/
    └── ... Alembic migration files
```

### Responsibility of each layer

| Layer | Responsibility |
|---|---|
| `main.py` | Creates FastAPI application and registers routers |
| `core/config.py` | Application configuration and environment variables |
| `db/` | Database connection, engine and session management |
| `models/` | SQLAlchemy database table definitions |
| `schemas/` | Pydantic request and response validation |
| `repositories/` | Database queries and CRUD operations |
| `services/` | Business logic and transaction coordination |
| `routers/` | API endpoints; act as controllers |
| `migrations/` | Database schema changes using Alembic |

## 2. Models: Defining database tables

We use SQLAlchemy models to define the structure of our database tables.

For example, `models/user.py`:

```python
from sqlalchemy import String
from sqlalchemy.orm import Mapped, mapped_column
from app.db.base import Base

class User(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(
        primary_key=True,
        index=True
    )

    name: Mapped[str] = mapped_column(
        String(50)
    )

    email: Mapped[str] = mapped_column(
        String(255),
        unique=True,
        index=True
    )
```

**Important interview point:**

Defining a SQLAlchemy model does not automatically create a database table.

In production, we generally use **Alembic migrations** to create and update database schemas.

For example:

```bash
alembic revision --autogenerate -m "create users table"
alembic upgrade head
```

This allows us to version-control database changes and deploy them safely.

We generally avoid relying on `Base.metadata.create_all()` during production application startup.

## 3. Database connection and session management

The application needs to connect to a database such as Amazon Aurora PostgreSQL or MySQL.

We configure the SQLAlchemy engine and session factory in `db/session.py`.

```python
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker

DATABASE_URL = "your-database-connection-string"

engine = create_engine(
    DATABASE_URL,
    pool_pre_ping=True
)

SessionLocal = sessionmaker(
    bind=engine,
    autoflush=False,
    autocommit=False,
    expire_on_commit=False
)

def get_db():
    db = SessionLocal()

    try:
        yield db
    finally:
        db.close()
```

### What is happening here?

- `create_engine()` creates the SQLAlchemy engine, which manages database connectivity and connection pooling.
- `sessionmaker()` creates a factory for database sessions.
- `SessionLocal()` creates an individual database session.
- `get_db()` provides a session to an API request.
- `yield` makes the session available to the endpoint.
- `finally` ensures the session is closed after the request.

We use FastAPI's dependency injection with `Depends(get_db)` to provide the database session.

**Production point:** Database credentials should not be hardcoded. We should load configuration from environment variables or a secure secret store such as AWS Secrets Manager.

## 4. Schemas: Request and response validation

SQLAlchemy models represent database tables.

Pydantic schemas represent the API request and response contracts.

We keep them separate because we do not want to expose every database field directly through our API.

Example: `schemas/user.py`

```python
from pydantic import BaseModel, EmailStr, Field, ConfigDict

class UserCreate(BaseModel):
    name: str = Field(min_length=2, max_length=50)
    email: EmailStr


class UserUpdate(BaseModel):
    name: str = Field(min_length=2, max_length=50)
    email: EmailStr


class UserPatch(BaseModel):
    name: str | None = Field(default=None, min_length=2, max_length=50)
    email: EmailStr | None = None


class UserResponse(BaseModel):
    model_config = ConfigDict(from_attributes=True)

    id: int
    name: str
    email: EmailStr
```

### Difference between PUT and PATCH schemas

- `UserUpdate`: Used for PUT. The client provides the complete set of fields required by the update operation.
- `UserPatch`: Used for PATCH. The client can provide only the fields it wants to change.
- `UserResponse`: Defines what the API returns to the client.

`from_attributes=True` allows Pydantic to create a response from an ORM object.

## 5. Repository layer: Database operations

The repository layer contains database queries.

It is responsible for interacting with SQLAlchemy models and the database.

Example: `repositories/user_repository.py`

```python
from sqlalchemy import select
from sqlalchemy.orm import Session
from app.models.user import User


class UserRepository:

    def get_by_id(self, db: Session, user_id: int):
        return db.get(User, user_id)

    def get_by_email(self, db: Session, email: str):
        return db.scalar(
            select(User).where(User.email == email)
        )

    def get_all(self, db: Session):
        return db.scalars(select(User)).all()

    def create(self, db: Session, user: User):
        db.add(user)
        db.flush()
        return user

    def update(self, db: Session, user: User):
        db.flush()
        return user

    def delete(self, db: Session, user: User):
        db.delete(user)
        db.flush()
```

### What does the repository do?

- Fetches records from the database.
- Inserts new records.
- Updates existing records.
- Deletes records.
- Contains reusable database queries.

**Important:** The repository should generally not contain business rules.

For example, checking whether a user is allowed to change their email is a business rule, so it belongs in the service layer.

In this architecture, the repository uses `flush()` to send pending changes to the database within the current transaction. It does not commit independently.

## 6. Service layer: Business logic

The service layer contains business rules and coordinates application operations.

For example:
- Check whether an email already exists.
- Check whether a user exists before updating.
- Validate whether an operation is permitted.
- Coordinate multiple repository operations.
- Commit or roll back a transaction.

Example: `services/user_service.py`

```python
from sqlalchemy.orm import Session
from app.models.user import User
from app.repositories.user_repository import UserRepository


class UserService:

    def __init__(self):
        self.repository = UserRepository()

    def create_user(self, db: Session, data):

        existing_user = self.repository.get_by_email(
            db, str(data.email)
        )

        if existing_user:
            raise ValueError("Email already exists")

        user = User(
            name=data.name,
            email=str(data.email)
        )

        try:
            self.repository.create(db, user)
            db.commit()
            db.refresh(user)
            return user

        except Exception:
            db.rollback()
            raise

    def get_user(self, db: Session, user_id: int):

        user = self.repository.get_by_id(db, user_id)

        if user is None:
            raise LookupError("User not found")

        return user

    def update_user(self, db: Session, user_id: int, data):

        user = self.get_user(db, user_id)

        user.name = data.name
        user.email = str(data.email)

        try:
            self.repository.update(db, user)
            db.commit()
            db.refresh(user)
            return user

        except Exception:
            db.rollback()
            raise

    def patch_user(self, db: Session, user_id: int, data):

        user = self.get_user(db, user_id)

        update_data = data.model_dump(exclude_unset=True)

        for field, value in update_data.items():
            setattr(user, field, value)

        try:
            self.repository.update(db, user)
            db.commit()
            db.refresh(user)
            return user

        except Exception:
            db.rollback()
            raise

    def delete_user(self, db: Session, user_id: int):

        user = self.get_user(db, user_id)

        try:
            self.repository.delete(db, user)
            db.commit()

        except Exception:
            db.rollback()
            raise
```

### Why does the service layer handle transactions?

Suppose one business operation needs to:
1. Create a user.
2. Create a user profile.
3. Assign a default role.

These operations might need to succeed or fail together.

The service layer coordinates them within one transaction.

If an operation fails, we roll back the transaction so we do not leave partially completed data.

**Production note:** This is a simplified example. A production implementation should use domain-specific exceptions, handle database `IntegrityError` appropriately, and use dependency injection for services and repositories where appropriate.

The database must enforce unique constraints too. Checking an email before inserting is useful for a friendly error message, but two concurrent requests could still pass that check. The database's UNIQUE constraint protects against that race condition.

## 7. Router layer: FastAPI endpoints acting as controllers

The router layer handles HTTP requests.

It acts like the controller layer in an MVC-style architecture.

It is responsible for:
- Receiving requests.
- Validating request data through Pydantic schemas.
- Getting the database session through dependency injection.
- Calling the service layer.
- Returning the appropriate HTTP response and status code.

Example: `routers/user_router.py`

```python
from fastapi import APIRouter, Depends, HTTPException
from sqlalchemy.orm import Session
from sqlalchemy.exc import IntegrityError

from app.db.session import get_db
from app.schemas.user import (
    UserCreate,
    UserUpdate,
    UserPatch,
    UserResponse
)
from app.services.user_service import UserService


router = APIRouter(prefix="/users", tags=["Users"])

user_service = UserService()


@router.post("/", response_model=UserResponse, status_code=201)
def create_user(
    request: UserCreate,
    db: Session = Depends(get_db)
):
    try:
        return user_service.create_user(db, request)

    except ValueError as exc:
        raise HTTPException(status_code=409, detail=str(exc))

    except IntegrityError:
        raise HTTPException(
            status_code=409,
            detail="Duplicate user data"
        )


@router.get("/{user_id}", response_model=UserResponse)
def get_user(
    user_id: int,
    db: Session = Depends(get_db)
):
    try:
        return user_service.get_user(db, user_id)

    except LookupError:
        raise HTTPException(
            status_code=404,
            detail="User not found"
        )


@router.put("/{user_id}", response_model=UserResponse)
def update_user(
    user_id: int,
    request: UserUpdate,
    db: Session = Depends(get_db)
):
    try:
        return user_service.update_user(db, user_id, request)

    except LookupError:
        raise HTTPException(
            status_code=404,
            detail="User not found"
        )

    except IntegrityError:
        raise HTTPException(
            status_code=409,
            detail="Duplicate user data"
        )


@router.patch("/{user_id}", response_model=UserResponse)
def patch_user(
    user_id: int,
    request: UserPatch,
    db: Session = Depends(get_db)
):
    try:
        return user_service.patch_user(db, user_id, request)

    except LookupError:
        raise HTTPException(
            status_code=404,
            detail="User not found"
        )

    except IntegrityError:
        raise HTTPException(
            status_code=409,
            detail="Duplicate user data"
        )


@router.delete("/{user_id}", status_code=204)
def delete_user(
    user_id: int,
    db: Session = Depends(get_db)
):
    try:
        user_service.delete_user(db, user_id)

    except LookupError:
        raise HTTPException(
            status_code=404,
            detail="User not found"
        )
```

**Production improvement:** Instead of repeating `try/except` blocks in every endpoint, use custom application exceptions and centralized FastAPI exception handlers. The service should roll back failed transactions before the exception is mapped to an HTTP response.

## 8. main.py: Application entry point

This is where we create the FastAPI application and register our routers.

```python
from fastapi import FastAPI
from app.routers import user_router

app = FastAPI(
    title="User Management API",
    version="1.0.0"
)

app.include_router(user_router.router)


@app.get("/health")
def health_check():
    return {"status": "healthy"}
```

The application can have multiple routers, such as:
- `user_router`
- `order_router`
- `payment_router`
- `product_router`

This keeps the code modular.

## 9. End-to-end request flow: POST /users/

Suppose a client sends:

```http
POST /users/
Content-Type: application/json
```

Request body:

```json
{
    "name": "John",
    "email": "john@example.com"
}
```

The flow is:

1. **Router:** FastAPI receives the POST request.
2. **Schema:** Pydantic validates the incoming request against `UserCreate`.
3. **Dependency injection:** `Depends(get_db)` provides a database session.
4. **Service:** The service checks the business rule, such as whether the email already exists.
5. **Repository:** The repository performs the database query and stages the new user.
6. **Service:** The service commits the transaction and refreshes the ORM object.
7. **Router:** The endpoint returns the user object.
8. **Response schema:** `UserResponse` serializes the response.
9. **Database dependency:** The session is closed after the request.

Example response:

```json
{
    "id": 1,
    "name": "John",
    "email": "john@example.com"
}
```

## 10. PUT vs PATCH in a production API

| Method | Purpose | Example |
|---|---|---|
| GET | Retrieve a resource | Get user by ID |
| POST | Create a resource | Create a user |
| PUT | Replace/update the resource representation | Update all required user fields |
| PATCH | Partially update a resource | Update only the user's name |
| DELETE | Delete a resource | Delete user by ID |

### PUT example

```json
{
    "name": "John Smith",
    "email": "johnsmith@example.com"
}
```

The client sends the complete set of fields required by the update schema.

### PATCH example

```json
{
    "name": "John Smith"
}
```

Only the supplied field is updated. Other fields remain unchanged.

For PATCH, we use:

```python
update_data = data.model_dump(exclude_unset=True)
```

This is important because it excludes fields that the client did not send.

## 11. Important production-level considerations

### Database and transactions
- Use connection pooling.
- Use Alembic migrations for schema changes.
- Use transactions for operations that must succeed or fail together.
- Roll back failed transactions.
- Add database constraints and indexes where appropriate.
- Avoid creating a new database engine for every request.

### Error handling
Use suitable HTTP status codes:

| Status | Meaning |
|---|---|
| 200 | Successful request |
| 201 | Resource created |
| 204 | Successful request with no response body |
| 400 | Bad request |
| 401 | Authentication required or invalid |
| 403 | Forbidden |
| 404 | Resource not found |
| 409 | Conflict, such as duplicate data |
| 422 | Request validation error |
| 500 | Internal server error |

### Security
- Use authentication and authorization.
- Use OAuth2/JWT where appropriate.
- Validate all incoming data.
- Store secrets in AWS Secrets Manager or another secure secret store.
- Apply least-privilege IAM permissions.
- Do not expose internal database fields in API responses.

### Performance and scalability
- Implement pagination for large result sets.
- Use filtering and sorting.
- Use async endpoints and `AsyncSession` when using asynchronous database access.
- Avoid unnecessary database queries.
- Add caching where appropriate.
- Configure connection pool limits for the application's expected workload.

### Testing
- Use Pytest.
- Use FastAPI `TestClient` for endpoint tests.
- Mock external services when appropriate.
- Test service and repository layers independently.
- Test database rollback and error scenarios.

## 12. Interview questions and answers

**Q1. Why do we separate models and schemas?**

Models define the database structure using SQLAlchemy. Schemas define the API request and response structure using Pydantic. Keeping them separate prevents us from exposing internal database fields and allows independent validation of API contracts.

**Q2. Why do we need a repository layer?**

The repository separates database access from business logic. It contains reusable queries and CRUD operations. This makes the service layer easier to test and keeps database-specific code in one place.

**Q3. What is the responsibility of the service layer?**

The service layer contains business rules and coordinates workflows. It can call multiple repositories and manage transactions when several database operations need to succeed or fail together.

**Q4. Are FastAPI routers equivalent to controllers?**

Yes. FastAPI route functions act as controllers. They receive HTTP requests, validate inputs, call the service layer, and return HTTP responses. They should not contain complex business logic or direct database queries.

**Q5. Where do we create database tables?**

We define SQLAlchemy models in the models directory. In production, we use Alembic migrations to create and modify the actual database tables.

**Q6. Where should we check whether an email already exists?**

The service layer decides whether the business rule is satisfied. It calls the repository to query the database. The database should also enforce a UNIQUE constraint to prevent duplicate values under concurrent requests.

**Q7. Why do we use `Depends(get_db)`?**

FastAPI dependency injection provides a database session to the endpoint. It also ensures that the session is closed after the request, including when an exception occurs.

**Q8. Why should the repository not commit every operation?**

A business operation may involve multiple database changes. If every repository method commits independently, we can end up with partially completed workflows. The service or unit-of-work layer should coordinate the transaction boundary.

**Q9. How would you handle duplicate email errors in production?**

I would enforce a UNIQUE constraint on the email column, check for an existing email in the service for a friendly error, catch database integrity violations, roll back the transaction, and return an appropriate conflict response such as HTTP 409.

**Q10. How would you connect this application to AWS Aurora?**

I would configure the SQLAlchemy connection using the Aurora database endpoint and securely managed credentials. I would use connection pooling, keep database access in the repository layer, manage schema changes with Alembic, and ensure the application has appropriate network access and security-group permissions.

## 13. Short interview explanation to remember

"If I am building a production REST API using FastAPI and SQLAlchemy, I follow a layered architecture.

First, I define database tables using SQLAlchemy models and manage database schema changes through Alembic migrations.

I use Pydantic schemas to validate incoming requests and control outgoing responses.

The database connection and session management are handled in a separate database module. FastAPI dependency injection provides a session to each request.

I keep database queries and CRUD operations inside the repository layer.

The service layer contains business logic, coordinates repositories, and manages transactions.

The router layer acts as the controller. It exposes GET, POST, PUT, PATCH, and DELETE endpoints, validates requests, calls the service layer, and returns the appropriate HTTP status codes.

Finally, main.py creates the FastAPI application and registers all the routers.

This separation makes the application maintainable, testable, reusable, and suitable for production."

**The key distinction to remember:**

- Migration = How do we safely change the database schema?
