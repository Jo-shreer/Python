============================================================
1. WHAT IS AMAZON REDSHIFT?
============================================================

Amazon Redshift is an AWS-managed cloud data warehouse used
for analytical processing (OLAP).

Typical use cases:
- Business intelligence
- Data warehousing
- Data analytics
- Historical reporting
- Large SQL queries
- ETL and ELT workloads
- Data lake integration with Amazon S3

Redshift uses Massively Parallel Processing (MPP).

MAIN COMPONENTS:

1. Leader node:
   - Receives SQL queries.
   - Creates query execution plans.
   - Coordinates compute nodes.
   - Returns query results.

2. Compute nodes:
   - Execute queries.
   - Process data in parallel.

3. Managed storage:
   - RA3 separates compute and storage.
   - Data storage is managed independently of compute.

4. Redshift Spectrum:
   - Queries data stored directly in S3.

5. Workload Management (WLM):
   - Controls query queues and resource allocation.

============================================================
2. REDSHIFT DEPLOYMENT OPTIONS
============================================================

A. PROVISIONED REDSHIFT

You select:
- Node type
- Number of nodes
- Cluster configuration

Best for predictable, continuous workloads.

Examples:
- RA3.xlplus
- RA3.4xlarge
- RA3.16xlarge

B. REDSHIFT SERVERLESS

AWS manages compute provisioning.

You configure:
- Namespace
- Workgroup
- Base capacity in RPUs
- Maximum capacity limits
- Security
- Database credentials

Best for variable workloads.

IMPORTANT:
Provisioned and Serverless use different Terraform resources.

4. COMPLETE REDSHIFT PARAMETER EXPLANATION
============================================================

A. CLUSTER IDENTIFICATION PARAMETERS

1. cluster_identifier

Terraform:
cluster_identifier = "company-prod-redshift"

Purpose:
Unique identifier for the cluster.

Example:
company-prod-redshift

Rules:
- Must be unique in the AWS account and Region.
- Used to identify the cluster.
- Used by monitoring and automation.

2. database_name

Terraform:
database_name = "analytics"

Purpose:
Creates the initial database.

Example:
analytics

3. master_username

Terraform:
master_username = "redshiftadmin"

Purpose:
Initial administrative database username.

Security:
- Do not use the master account for applications.
- Create separate application users and roles.
- Restrict administrator access.

4. manage_master_password

Terraform:
manage_master_password = true

Purpose:
AWS generates and manages the master password in
AWS Secrets Manager.

Recommended for production.

5. master_password

Terraform:
master_password = var.master_password

Purpose:
Manually supplies the administrator password.

Use only when you have a secure secret management design.
Never hardcode passwords in Terraform.

B. COMPUTE PARAMETERS

6. node_type

Terraform:
node_type = "ra3.xlplus"

Purpose:
Defines the compute node specification.

Examples:
ra3.xlplus
ra3.4xlarge
ra3.16xlarge

Selection:
- Smaller workload: Evaluate smaller RA3 capacity.
- Medium workload: Evaluate RA3.xlplus.
- Larger workload: Evaluate RA3.4xlarge or above.

Always benchmark actual queries before selecting capacity.

7. cluster_type

Terraform:
cluster_type = "single-node"

or:

cluster_type = "multi-node"

Purpose:
Defines cluster topology.

Single-node:
- One node.
- Useful for development and testing.
- Not a suitable general-purpose production HA design.

Multi-node:
- Multiple compute nodes.
- Parallel query processing.
- Better capacity and resilience.

8. number_of_nodes

Terraform:
number_of_nodes = 2

Purpose:
Defines the number of compute nodes.

Example:
2, 4, 8

For multi-node provisioned clusters, choose at least two.

C. NETWORK PARAMETERS

9. cluster_subnet_group_name

Terraform:
cluster_subnet_group_name = aws_redshift_subnet_group.prod.name

Purpose:
Places Redshift in selected VPC subnets.

Production:
Use private subnets across different AZs.

10. vpc_security_group_ids

Terraform:
vpc_security_group_ids = [
  aws_security_group.redshift.id
]

Purpose:
Controls network traffic.

Recommended:
Allow TCP 5439 only from approved application security groups.

11. publicly_accessible

Terraform:
publicly_accessible = false

Purpose:
Controls public accessibility.

Production:
false

12. port

Terraform:
port = 5439

Purpose:
Database connection port.

Default Redshift port:
5439

13. enhanced_vpc_routing

Terraform:
enhanced_vpc_routing = true

Purpose:
Routes COPY and UNLOAD traffic through your VPC.

Benefits:
- More network visibility.
- Can use VPC endpoints.
- Supports network access controls.

Important:
Configure appropriate S3 routes/endpoints and IAM permissions.

D. ENCRYPTION PARAMETERS

14. encrypted

Terraform:
encrypted = true

Purpose:
Enables encryption at rest.

15. kms_key_id

Terraform:
kms_key_id = aws_kms_key.redshift.arn

Purpose:
Selects the KMS key used for encryption.

16. master_password_secret_kms_key_id

Terraform:
master_password_secret_kms_key_id = aws_kms_key.redshift.arn

17. require_ssl

  name  = "require_ssl"

FILE 3: main.tf
------------------------------------------------------------

locals {
  tags = {
    Environment = "Production"
    Project     = var.project
    ManagedBy   = "Terraform"
  }
}

# KMS KEY

resource "aws_kms_key" "redshift" {
  description             = "Redshift production encryption"
  enable_key_rotation     = true
  deletion_window_in_days = 30

  tags = local.tags
}

resource "aws_kms_alias" "redshift" {
  name          = "alias/${var.project}-redshift"
  target_key_id = aws_kms_key.redshift.key_id
}

# IAM TRUST POLICY

data "aws_iam_policy_document" "redshift_assume" {
  statement {
    effect = "Allow"

    principals {
      type = "Service"

      identifiers = [
        "redshift.amazonaws.com"
      ]
    }

    actions = [
      "sts:AssumeRole"
    ]
  }
}

# IAM ROLE

resource "aws_iam_role" "redshift_s3" {
  name               = "${var.project}-redshift-s3"
  assume_role_policy = data.aws_iam_policy_document.redshift_assume.json

  tags = local.tags
}

# S3 IAM POLICY

data "aws_iam_policy_document" "s3_access" {
  statement {
    effect = "Allow"

    actions = [
      "s3:ListBucket"
    ]

    resources = [
      var.s3_bucket_arn
    ]
  }

  statement {
    effect = "Allow"

    actions = [
      "s3:GetObject",
      "s3:PutObject"
    ]

    resources = [
      "${var.s3_bucket_arn}/*"
    ]
  }
}

resource "aws_iam_role_policy" "redshift_s3" {
  name   = "${var.project}-s3-policy"
  role   = aws_iam_role.redshift_s3.id
  policy = data.aws_iam_policy_document.s3_access.json
}

# SSL PARAMETER GROUP

resource "aws_redshift_parameter_group" "prod" {
  name        = "${var.project}-parameters"
  family      = "redshift-2.0"
  description = "Production Redshift parameter group"

  parameter {
    name  = "require_ssl"
    value = "true"
  }

  tags = local.tags
}

# PRIVATE SUBNET GROUP

resource "aws_redshift_subnet_group" "prod" {
  name        = "${var.project}-subnets"
  description = "Production private subnets"

  subnet_ids = var.private_subnet_ids

  tags = local.tags
}

# SECURITY GROUP

resource "aws_security_group" "redshift" {
  name        = "${var.project}-redshift-sg"
  description = "Redshift private access"
  vpc_id      = var.vpc_id

  tags = local.tags
}

# ALLOW APPLICATION SECURITY GROUP

resource "aws_vpc_security_group_ingress_rule" "app" {
  security_group_id            = aws_security_group.redshift.id
  referenced_security_group_id = var.client_security_group_id

  ip_protocol = "tcp"
  from_port   = 5439
  to_port     = 5439

  description = "Application access to Redshift"
}

# REDSHIFT CLUSTER

resource "aws_redshift_cluster" "prod" {
  cluster_identifier = "${var.project}-redshift"

  database_name   = "analytics"
  master_username = "redshiftadmin"

  manage_master_password = true

  node_type      = var.node_type
  cluster_type   = "multi-node"
  number_of_nodes = var.number_of_nodes

  port = 5439

  cluster_subnet_group_name = (
    aws_redshift_subnet_group.prod.name
  )

  vpc_security_group_ids = [
    aws_security_group.redshift.id
  ]

  publicly_accessible = false

  encrypted = true
  kms_key_id = aws_kms_key.redshift.arn

  master_password_secret_kms_key_id = (
    aws_kms_key.redshift.arn
  )

  enhanced_vpc_routing = true

  cluster_parameter_group_name = (
    aws_redshift_parameter_group.prod.name
  )

  iam_roles = [
    aws_iam_role.redshift_s3.arn
  ]

  automated_snapshot_retention_period = (
    var.snapshot_retention_days
  )

  skip_final_snapshot = false

  final_snapshot_identifier = (
    "${var.project}-final-snapshot"
  )

  preferred_maintenance_window = "sun:02:00-sun:03:00"

  allow_version_upgrade = true

  apply_immediately = false

  tags = local.tags

  depends_on = [
    aws_iam_role_policy.redshift_s3
  ]
}

# CLOUDWATCH LOG GROUP

resource "aws_cloudwatch_log_group" "redshift" {
  name = "/aws/redshift/cluster/${aws_redshift_cluster.prod.id}"

  retention_in_days = 90

  kms_key_id = aws_kms_key.redshift.arn

  tags = local.tags
}

# REDSHIFT LOGGING

resource "aws_redshift_logging" "prod" {
  cluster_identifier   = aws_redshift_cluster.prod.id
  log_destination_type = "cloudwatch"

  log_exports = [
    "connectionlog",
    "userlog",
    "useractivitylog"
  ]

  depends_on = [
    aws_cloudwatch_log_group.redshift

8. BACKUP AND DISASTER RECOVERY
============================================================

Automated snapshots:

automated_snapshot_retention_period = 7

Manual snapshots:
- Created before major upgrades.
- Created before migrations.
- Retained independently of automated snapshots.

Final snapshot:

skip_final_snapshot = false

Cross-Region snapshot copies:
- Useful for disaster recovery.
- Can improve recovery options if a Region fails.
- Requires appropriate snapshot copy configuration and KMS permissions.

Important:
Snapshots are not a replacement for a tested DR strategy.

Define:
- RPO: Maximum acceptable data loss.
- RTO: Maximum acceptable recovery time.

12. IMPORTANT INTERVIEW QUESTIONS
============================================================

Q1. What is RA3?

RA3 is a Redshift node family that separates compute from
managed storage.

Q2. What is MPP?

Massively Parallel Processing distributes work across
multiple compute nodes.

Q3. What is Enhanced VPC Routing?

It routes COPY and UNLOAD traffic through the VPC.

Q4. What is the difference between encrypted and require_ssl?

encrypted = encryption at rest.

require_ssl = encryption in transit.

Q5. Why use a Redshift subnet group?

It identifies the VPC subnets where Redshift can be deployed.

Q6. Why use IAM roles?

They provide secure AWS service access without storing
static AWS credentials in the database.

Q7. Why use KMS?

It provides encryption key management and access control.

Q8. What is Redshift Spectrum?

It allows SQL queries against data stored in S3 without
loading all that data into Redshift.

Q9. What is WLM?

Workload Management controls how queries use available
resources.

Q10. What is the difference between Multi-AZ and multi-node?

Multi-node describes the compute cluster topology.

Multi-AZ provides deployment availability across
Availability Zones.

They are not interchangeable concepts.

13. IMPORTANT PRODUCTION CAVEATS
============================================================

1. The Terraform example assumes the VPC, subnets,
   application security group and S3 bucket already exist.

2. The example IAM role grants access to one S3 bucket.
   Add permissions for KMS-encrypted S3 objects if needed.

3. If enhanced VPC routing is enabled, validate S3
   endpoint routes, bucket policies and any other required
   network access before deployment.

4. The KMS key policy and deployment IAM permissions must
   permit the required Redshift and Secrets Manager operations.

5. CloudWatch logging retention must be configured
   separately from Redshift log export.

6. The example uses a standard multi-node RA3 cluster.
   Multi-AZ is not automatically enabled.

7. Test cluster restore, final snapshots and recovery
   procedures before production release.

8. Use a unique final snapshot naming strategy for repeated
   production deletion/replacement workflows.

9. Review the Terraform plan carefully because changes
   to cluster settings can trigger replacement or reboot.

10. Pin and test Terraform provider versions in your
    organisation's deployment pipeline.
