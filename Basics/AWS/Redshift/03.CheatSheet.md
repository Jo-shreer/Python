**1. WHAT IS AMAZON REDSHIFT?**

Amazon Redshift is a fully managed AWS cloud data warehouse designed for OLAP (Online Analytical Processing).

**Use cases:**
- Business intelligence and reporting.
- Data analytics.
- Historical data analysis.
- Large-scale SQL queries.
- ETL and ELT processing.
- Data lake integration with Amazon S3.
- Power BI, Tableau and QuickSight integration.

**Main architectural components:**

1. Leader Node:
   - Receives SQL queries.
   - Creates query execution plans.
   - Coordinates compute nodes.
   - Returns query results.

2. Compute Nodes:
   - Execute SQL queries.
   - Process data in parallel.
   - Perform analytical operations.

3. Managed Storage:
   - RA3 separates compute and storage.
   - Storage capacity can scale independently of compute.

4. MPP:
   - Massively Parallel Processing.
   - Distributes query execution across compute resources.

5. Redshift Spectrum:
   - Queries data stored directly in Amazon S3.

6. Workload Management (WLM):
   - Controls query queues.
   - Manages workload priorities.
   - Allocates resources to queries.

**2. REDSHIFT DEPLOYMENT TYPES**

**A. Provisioned Redshift**

You select:
- Node type.
- Number of nodes.
- Cluster configuration.
- Network configuration.
- Backup configuration.

Examples:
- RA3.xlplus
- RA3.4xlarge
- RA3.16xlarge

Best for predictable, continuously running workloads.

**B. Redshift Serverless**

AWS manages compute provisioning.

You configure:
- Namespace.
- Workgroup.
- Base RPU capacity.
- Maximum capacity.
- Security.
- Database credentials.

Best for variable workloads.

**Important architectural decision:**

Provisioned and Serverless are separate deployment models and use different Terraform resources.

**4. COMPLETE REDSHIFT TERRAFORM PARAMETER EXPLANATION**

**A. CLUSTER IDENTIFICATION PARAMETERS**

**1. cluster_identifier**

Example:

cluster_identifier = "company-prod-redshift"

Purpose:
- Unique cluster identifier.
- Identifies the Redshift cluster in AWS.
- Used by monitoring and automation.

**2. database_name**

Example:

database_name = "analytics"

Purpose:
- Creates the initial database.
- Applications connect to this database.

**3. master_username**

Example:

master_username = "redshiftadmin"

Purpose:
- Initial administrative database username.
- Used for administrative operations.

Security:
- Do not use the master user for applications.
- Create dedicated database users and roles.
- Restrict administrator permissions.

**4. manage_master_password**

Example:

manage_master_password = true

Purpose:
- AWS generates the administrator password.
- Password is managed through Secrets Manager.

Recommended for production.

**5. master_password**

Example:

master_password = var.master_password

Purpose:
- Supplies the administrator password manually.

Important:
- Never hardcode passwords.
- Use a secure secret management solution.

**B. COMPUTE PARAMETERS**

**6. node_type**

Example:

node_type = "ra3.xlplus"

Purpose:
Defines the compute node specification.

Examples:
- ra3.xlplus
- ra3.4xlarge
- ra3.16xlarge

Selection:
- Choose based on workload.
- Consider query complexity.
- Consider concurrency.
- Consider CPU and memory requirements.
- Benchmark before production deployment.

**7. cluster_type**

Example:

cluster_type = "multi-node"

Possible values:
- single-node
- multi-node

Purpose:
Defines the cluster topology.

Single-node:
- One compute node.
- Suitable for development and testing.
- Not a general-purpose production HA design.

Multi-node:
- Multiple compute nodes.
- Parallel query execution.
- Greater compute capacity.

**8. number_of_nodes**

Example:

number_of_nodes = 2

Purpose:
Defines the number of compute nodes.

Examples:
- 2
- 4
- 8

For multi-node provisioned clusters, configure at least two nodes.

data "aws_iam_policy_document" "redshift_assume" {

    effect = "Allow"

    principals {
      type = "Service"

      identifiers = [
        "redshift.amazonaws.com"
      ]
    }

    actions = [
      "sts:AssumeRole"
    ]
  }
}

# IAM ROLE

resource "aws_iam_role" "redshift_s3" {
  name               = "${var.project}-redshift-s3"
  assume_role_policy = data.aws_iam_policy_document.redshift_assume.json

  tags = local.tags
}

# S3 IAM POLICY

data "aws_iam_policy_document" "s3_access" {
  statement {
    effect = "Allow"

    actions = [
      "s3:ListBucket"
    ]

    resources = [
      var.s3_bucket_arn
    ]
  }

  statement {
    effect = "Allow"

    actions = [
      "s3:GetObject",
      "s3:PutObject"
    ]

    resources = [
      "${var.s3_bucket_arn}/*"
    ]
  }
}

resource "aws_iam_role_policy" "redshift_s3" {
  name   = "${var.project}-s3-policy"

**6. SECURITY EXPLANATION**

**Encryption at rest**

encrypted = true

Protects stored database data.

kms_key_id = aws_kms_key.redshift.arn

Specifies the encryption key.

**Encryption in transit**

require_ssl = true

Forces encrypted client connections.

Client:

sslmode=verify-full

Validates the server certificate and hostname.

**Network security**

publicly_accessible = false

Keeps the cluster private.

Security group:
- Allow TCP 5439.
- Allow only trusted application security groups.
- Avoid 0.0.0.0/0.

**IAM security**

Use IAM roles instead of static AWS access keys.

Follow least privilege.

**Credential security**

Use Secrets Manager.

Do not store passwords in:
- Terraform code.
- Git repositories.
- Plain-text variables.
- Application configuration files.

**11. IMPORTANT INTERVIEW QUESTIONS**

**Q1. What is RA3?**

RA3 is a Redshift node family that separates compute and managed storage.

**Q2. What is MPP?**

Massively Parallel Processing distributes query execution across compute resources.

**Q3. What is Enhanced VPC Routing?**

It routes COPY and UNLOAD traffic through the VPC.

**Q4. Difference between encrypted and require_ssl?**

encrypted = encryption at rest.

require_ssl = encryption in transit.

**Q5. Why use a Redshift subnet group?**

It specifies the VPC subnets where Redshift can be deployed.

**Q6. Why use IAM roles?**

They allow Redshift to access AWS services securely without static AWS credentials.

**Q7. Why use KMS?**

For encryption key management and access control.

**Q8. What is Redshift Spectrum?**

It allows SQL queries against data stored in S3 without loading all data into Redshift.

**Q9. What is WLM?**

Workload Management controls query queues and resource allocation.

**Q10. Difference between Multi-node and Multi-AZ?**

Multi-node describes compute topology.

Multi-AZ describes availability across Availability Zones.

They are different concepts.

**13. IMPORTANT PRODUCTION CAVEATS**

1. The example assumes the VPC, subnets, application security group and S3 bucket already exist.

2. The S3 IAM policy is a basic example. Restrict it to specific object prefixes.

3. Add KMS permissions if accessing KMS-encrypted S3 objects.

4. Enhanced VPC routing requires suitable VPC routes, endpoint policies and bucket policies.

5. The KMS key policy must permit required operations.

6. Multi-AZ is not automatically enabled by using multiple nodes or multiple subnets.

7. CloudWatch retention must be configured separately.

8. Terraform changes can cause cluster reboot or replacement. Always review the plan.

9. Use unique final snapshot names for repeated deletion or replacement operations.

10. Test backups and recovery before production release.

11. Validate the Redshift parameter group family and supported node types in your selected Region.

12. Validate every Terraform resource against the selected AWS provider version.
