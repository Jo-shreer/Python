
# Amazon Redshift with Terraform – Complete AWS Solutions Architect Study Guide

## 1. What is Amazon Redshift?

Amazon Redshift is a fully managed, petabyte-scale cloud data warehouse service provided by AWS.

It is designed to store and analyse large volumes of structured and semi-structured data using SQL.

Redshift is primarily used for analytical workloads, reporting, business intelligence (BI), dashboards and data analytics.

**Example use case:**

An online shopping company collects:
- Customer information
- Product details
- Orders
- Payments
- Website activity
- Delivery information

The company wants to analyse:
- Total sales per month
- Best-selling products
- Customer buying behaviour
- Revenue by country
- Customer retention
- Product performance

Redshift can store and analyse this information efficiently.

**Important:** Redshift is designed primarily for OLAP workloads, not high-volume transactional OLTP workloads.

## 2. What is the Difference Between OLTP and OLAP?

**OLTP – Online Transaction Processing**

OLTP systems handle everyday business transactions.

Examples:
- Creating customer accounts
- Processing payments
- Updating orders
- Booking flights
- Recording bank transactions

Typical AWS services:
- Amazon RDS
- Amazon Aurora
- Amazon DynamoDB

**OLAP – Online Analytical Processing**

OLAP systems analyse large volumes of historical and business data.

Examples:
- Monthly sales reports
- Revenue analysis
- Customer behaviour analysis
- Business intelligence dashboards
- Data warehouse reporting

Typical AWS services:
- Amazon Redshift
- Amazon Athena
- Amazon EMR

**Key difference:**

OLTP focuses on processing individual transactions. OLAP focuses on analysing large amounts of data.

## 3. How Does Amazon Redshift Work?

A provisioned Redshift cluster consists of computing resources called nodes.

The main components are:

**1. Leader node**

The leader node:
- Receives SQL queries from applications.
- Parses SQL statements.
- Creates query execution plans.
- Coordinates compute nodes.
- Aggregates query results.
- Returns results to the client.

**2. Compute nodes**

Compute nodes:
- Execute query workloads.
- Process data in parallel.
- Store and retrieve data.
- Work together to improve analytical performance.

**3. Managed storage**

RA3 node types use Redshift Managed Storage to separate compute capacity from storage capacity.

This allows compute and storage to scale more independently than traditional node architectures.

**4. Columnar storage**

Redshift stores table data in columns rather than relying only on traditional row-based storage.

For example, imagine a table containing:

| Customer ID | Name | Country | Revenue |
|---|---|---|---|
| 101 | John | Ireland | 500 |
| 102 | Sarah | UK | 800 |
| 103 | David | USA | 600 |

If a query only needs revenue, columnar storage allows Redshift to read the relevant column rather than unnecessarily reading every column.

**5. Massively Parallel Processing (MPP)**

Redshift distributes analytical processing across compute resources.

This allows large queries to be processed in parallel.

## 4. Amazon Redshift Deployment Options

There are two main ways to use Amazon Redshift.

**1. Provisioned Redshift**

You select and manage cluster compute capacity.

You choose:
- Node type
- Number of nodes
- Cluster configuration
- Networking
- Security
- Backup settings

Terraform resource:

`aws_redshift_cluster`

Provisioned Redshift is useful when workloads are relatively predictable and you want control over the compute configuration.

**2. Redshift Serverless**

AWS manages the underlying compute infrastructure.

You configure:
- Namespace
- Workgroup
- Base capacity
- Networking
- Security

Terraform resources include:

`aws_redshiftserverless_namespace`

`aws_redshiftserverless_workgroup`

Serverless can be useful for workloads with variable or intermittent demand.

**Important:** This guide focuses on provisioned Redshift because it provides a useful understanding of cluster architecture and production infrastructure.

## 5. What is a Redshift Node Type?

A node type determines the compute and storage characteristics of a Redshift cluster.

Common node families include:

**RA3 nodes**

RA3 nodes use Redshift Managed Storage.

Examples:
- `ra3.xlplus`
- `ra3.4xlarge`
- `ra3.16xlarge`

RA3 is an important family to understand when designing production Redshift environments.

**DC2 nodes**

DC2 nodes use local SSD storage.

Examples:
- `dc2.large`
- `dc2.8xlarge`

DC2 can be suitable for certain smaller or existing workloads, but it should not automatically be selected for a new production design.

**How to choose a node type**

Consider:
- Data volume
- Query complexity
- Concurrent users
- Query performance requirements
- Compute requirements
- Storage requirements
- AWS Region availability
- Cost

Do not select a node type only because it is the cheapest.

Benchmark representative workloads before making a production decision.

## 6. What is a Single-Node and Multi-Node Cluster?

**Single-node cluster**

A single-node cluster uses one node for both leader and compute functionality.

Example:

`cluster_type = "single-node"`

This is useful for learning and certain small workloads.

It is generally not recommended for production workloads that require higher availability and scalability.

**Multi-node cluster**

A multi-node cluster separates leader and compute functionality.

Example:

`cluster_type  = "multi-node"`

`number_of_nodes = 2`

The compute workload is distributed across multiple nodes.

For production, the correct node count depends on the workload and supported node family.

Some node families have minimum node requirements. Always check the supported configuration for the selected node type.

## 7. What is a Redshift Parameter Group?

A Redshift parameter group controls database engine configuration.

It is similar in concept to a parameter group in Amazon RDS.

You can use it to configure:
- SSL enforcement
- Query behaviour
- Logging-related settings
- Workload management settings
- Other database engine parameters

Terraform resource:

`aws_redshift_parameter_group`

**Important:** A parameter group is different from the Redshift cluster resource.

The cluster defines infrastructure. The parameter group defines supported database engine settings.

Example:

`family = "redshift-1.0"`

The `redshift-1.0` family is used in the current Terraform provider documentation examples for provisioned Redshift parameter groups. Confirm the supported family in your target Region and provider version.

## 8. What is SSL/TLS Encryption in Redshift?

SSL and TLS protect data travelling between a client and the Redshift cluster.

For example:

An application connects to Redshift using a database driver.

Without encrypted transport, network traffic could potentially be intercepted.

With TLS:
- The connection is encrypted.
- Data in transit is protected.
- The client can verify the server identity when certificate verification is configured correctly.

**SSL versus TLS**

SSL is the older protocol family.

TLS is its modern successor.

People commonly say SSL when referring to encrypted database connections, but modern secure connections use TLS.

**Important distinction:**

There are two different encryption configurations.

**1. Encryption at rest**

This protects stored data.

Terraform:

`encrypted = true`

**2. Encryption in transit**

This protects network connections between the client and Redshift.

Parameter group:

`require_ssl = true`

These settings solve different security problems.

**Example parameter group:**

    resource "aws_redshift_parameter_group" "production" {
      name        = "production-redshift-params"
      family      = "redshift-1.0"
      description = "Production Redshift security parameters"

      parameter {
        name  = "require_ssl"
        value = "true"
      }
    }

**Example client connection configuration:**

Use a supported Redshift JDBC or PostgreSQL-compatible driver with TLS enabled and certificate verification configured.

For example, a driver configuration may use:

`sslmode=verify-full`

Check the exact connection properties supported by the driver you use.

Do not disable certificate verification in production.

## 9. What is a VPC in Redshift?

A VPC is a logically isolated network in AWS.

A production Redshift cluster should normally be deployed inside a VPC.

The VPC provides:
- Network isolation
- Private IP addressing
- Routing
- Security groups
- Network ACLs
- VPC endpoints
- Connectivity to applications

A typical production design places Redshift in private subnets.

Applications running in the same VPC can connect to Redshift using private networking.

## 10. What is a Redshift Subnet Group?

A Redshift subnet group identifies the subnets in which Redshift can be deployed.

Terraform resource:

`aws_redshift_subnet_group`

Example:

    resource "aws_redshift_subnet_group" "production" {
      name        = "production-redshift-subnets"
      description = "Private subnets for Redshift"

      subnet_ids = var.private_subnet_ids

      tags = {
        Environment = "production"
        Application = "analytics"
      }
    }

**Parameters explained:**

`name`

The name of the Redshift subnet group.

Example:

`production-redshift-subnets`

`description`

Explains the purpose of the subnet group.

`subnet_ids`

The IDs of the existing VPC subnets that Redshift can use.

Example:

`["subnet-0123456789abcdef0", "subnet-0123456789abcdef1"]`

For production, use appropriately designed private subnets across Availability Zones.

A subnet group spanning multiple Availability Zones does not automatically mean the cluster is deployed in Multi-AZ mode.

## 11. What is a Security Group in Redshift?

A security group controls network traffic to and from the Redshift cluster.

It works as a virtual firewall.

For example, if Redshift listens on port 5439, you can allow traffic from an application security group.

Example:

    resource "aws_security_group" "redshift" {
      name        = "production-redshift-sg"
      description = "Allow Redshift access from application servers"
      vpc_id      = var.vpc_id

      ingress {
        description     = "Redshift from application servers"
        from_port       = 5439
        to_port         = 5439
        protocol        = "tcp"
        security_groups = [var.application_security_group_id]
      }

      egress {
        description = "Allow outbound traffic"
        from_port   = 0
        to_port     = 0
        protocol    = "-1"
        cidr_blocks = ["0.0.0.0/0"]
      }

      tags = {
        Environment = "production"
      }
    }

**Parameters explained:**

`name`

The security group name.

`description`

Explains why the security group exists.

`vpc_id`

The VPC where the security group is created.

`ingress`

Defines inbound traffic.

`from_port`

The first port in the allowed range.

`to_port`

The last port in the allowed range.

`protocol`

The network protocol.

`tcp` means TCP traffic.

`security_groups`

Allows traffic from resources associated with the specified security group.

`egress`

Defines outbound traffic.

**Production security recommendation:**

Do not allow Redshift access from:

`0.0.0.0/0`

Instead, restrict inbound access to the application security group, approved corporate network or other specifically authorised sources.

The example egress rule is broad for simplicity. Restrict it further where the architecture allows.

## 12. What is Publicly Accessible in Redshift?

Terraform parameter:

`publicly_accessible`

Example:

`publicly_accessible = false`

If set to true, the cluster can be configured for public network accessibility, subject to its network configuration.

If set to false, it is not publicly accessible.

**Production recommendation:**

Use:

`publicly_accessible = false`

Place the cluster in private subnets and allow access through controlled private network paths.

Avoid exposing a data warehouse directly to the internet.

## 13. What is Enhanced VPC Routing?

Enhanced VPC Routing controls how Redshift communicates with external data repositories.

For example, Redshift can use COPY to import data from S3 and UNLOAD to export data to S3.

With Enhanced VPC Routing enabled, COPY and UNLOAD traffic is forced through your VPC.

Terraform:

`enhanced_vpc_routing = true`

Benefits:
- Better control over data movement
- VPC endpoint policies can be used
- Network ACLs and security groups can help control traffic
- VPC Flow Logs can help monitor network activity

**Important prerequisite:**

Your VPC needs suitable connectivity to S3 and other required services.

Depending on the design, this can involve:
- S3 Gateway VPC endpoint
- NAT gateway
- Appropriate route tables
- Endpoint policies
- IAM permissions
- S3 bucket policies

Enhanced VPC Routing can introduce additional networking costs, so include NAT and endpoint costs in the design.

## 14. What is AWS KMS Encryption?

AWS Key Management Service (KMS) manages encryption keys.

Redshift can use KMS keys to encrypt data at rest.

Terraform parameters:

`encrypted = true`

`kms_key_id = var.redshift_kms_key_arn`

Example:

    encrypted = true
    kms_key_id = var.redshift_kms_key_arn

**Parameters explained:**

`encrypted`

Enables encryption at rest.

`kms_key_id`

Specifies the KMS key used for cluster encryption.

**Why use a customer-managed KMS key?**

A customer-managed key provides additional control over:
- Key policies
- Access permissions
- Key rotation settings
- Auditing
- Key lifecycle

**Important:** Encryption is a fundamental cluster property. Changing encryption configuration later can require migration to a new cluster rather than a simple in-place change.

## 15. What is AWS Secrets Manager for Redshift?

Secrets Manager stores and manages sensitive information such as database credentials.

Instead of placing a database password directly in Terraform configuration, you can allow Redshift to manage the master password through Secrets Manager.

Terraform:

`manage_master_password = true`

Example:

    resource "aws_redshift_cluster" "production" {
      cluster_identifier = "production-redshift"
      database_name      = "analytics"
      master_username    = "redshiftadmin"

      manage_master_password = true

      node_type    = "ra3.xlplus"
      cluster_type = "multi-node"
    }

**Benefits:**
- Avoids hardcoding the master password.
- AWS manages the master password secret.
- Applications can retrieve credentials through authorised IAM permissions.
- Credentials can be rotated using supported mechanisms.

**Important:** Secrets Manager has a separate charge. Terraform state and deployment permissions must still be protected.

## 16. What is IAM Role Integration with Redshift?

Redshift can use IAM roles to access other AWS services.

A common example is accessing S3.

Suppose your company stores sales data in S3:

`s3://company-data/sales/`

Redshift needs permission to read those files.

You can create an IAM role and attach it to the Redshift cluster.

The role should use a trust relationship that allows the Redshift service to assume it.

Example trust policy:

    {
      "Version": "2012-10-17",
      "Statement": [
        {
          "Effect": "Allow",
          "Principal": {
            "Service": "redshift.amazonaws.com"
          },
          "Action": "sts:AssumeRole"
        }
      ]
    }

**Example permissions policy:**

    {
      "Version": "2012-10-17",
      "Statement": [
        {
          "Effect": "Allow",
          "Action": [
            "s3:ListBucket"
          ],
          "Resource": "arn:aws:s3:::company-data"
        },
        {
          "Effect": "Allow",
          "Action": [
            "s3:GetObject"
          ],
          "Resource": "arn:aws:s3:::company-data/sales/*"
        }
      ]
    }

This example provides read access to the sales prefix.

If Redshift needs to write data to S3, add only the required write permissions, such as `s3:PutObject`, to the appropriate object prefix.

If the S3 objects use SSE-KMS encryption, the role may also need the appropriate KMS permissions.

**Production recommendation:**

Follow least privilege. Do not give Redshift unrestricted access to every S3 bucket in the AWS account.

## 17. What is a Redshift Snapshot?

A snapshot is a point-in-time backup of a Redshift cluster.

Snapshots help recover data if:
- Data is accidentally deleted.
- A deployment causes problems.
- A cluster needs to be restored.
- A disaster recovery event occurs.

There are two main types.

**1. Automated snapshots**

AWS creates automated snapshots according to the configured retention period.

Terraform:

`automated_snapshot_retention_period = 7`

This example configures a seven-day retention period.

**2. Manual snapshots**

Manual snapshots are created for specific backup or recovery requirements.

They can be retained independently of the cluster's normal automated backup lifecycle.

**Important production settings:**

- Select a retention period based on recovery requirements.
- Protect important manual snapshots.
- Consider cross-Region snapshot copying.
- Test restoration procedures.
- Understand the storage charges for retained backups.

## 18. What is a Final Snapshot?

A final snapshot is a snapshot created before a cluster is deleted.

Terraform:

`skip_final_snapshot = false`

When false, Redshift requires a final snapshot identifier so that a final snapshot can be created before deletion.

Example:

`final_snapshot_identifier = var.final_snapshot_identifier`

A final snapshot identifier must be unique when creating a new snapshot.

For production, use a controlled deployment or decommissioning process that supplies an unused identifier.

**Important:** Terraform's `prevent_destroy` lifecycle setting can also protect a production cluster from accidental destruction.

Example:

    lifecycle {
      prevent_destroy = true
    }

This blocks Terraform from destroying the resource while the lifecycle rule remains in place.

It must be deliberately removed or changed when a planned decommission is authorised.

## 19. What is Redshift Multi-AZ?

Multi-AZ is a high-availability deployment option for supported provisioned Redshift configurations.

Terraform:

`multi_az = true`

It allows Redshift to use infrastructure across Availability Zones to improve availability.

**Benefits:**
- Higher availability
- Improved resilience to certain Availability Zone failures
- Reduced dependence on a single Availability Zone

**Important:** Multi-AZ support depends on the selected Redshift configuration and AWS Region.

Do not assume every node type or cluster configuration supports it.

Multi-AZ is also not the same thing as placing subnets in multiple Availability Zones.

For production, evaluate the cost and availability requirements before enabling it.

## 20. What is Redshift Logging?

Logging helps administrators understand database activity and investigate problems.

Redshift logging can include:

**Connection logs**

Information about database connection attempts.

**User logs**

Information about database users and related activity.

**User activity logs**

Information about SQL activity.

Terraform uses:

`aws_redshift_logging`

Example:

    resource "aws_redshift_logging" "production" {
      cluster_identifier   = aws_redshift_cluster.production.id
      log_destination_type = "cloudwatch"

      log_exports = [
        "connectionlog",
        "userlog",
        "useractivitylog"
      ]
    }

**Parameters explained:**

`cluster_identifier`

Identifies the Redshift cluster whose logs should be exported.

`log_destination_type`

Specifies where logs are sent.

`cloudwatch`

Sends logs to Amazon CloudWatch Logs.

`log_exports`

Lists the log types to export.

**Production recommendation:**

Enable appropriate logging, configure retention according to security requirements, and monitor log volume because CloudWatch ingestion and storage can incur costs.

## 21. What is a Redshift Maintenance Window?

AWS performs maintenance on Redshift clusters.

The maintenance window defines when scheduled maintenance can take place.

Terraform:

`preferred_maintenance_window`

Example:

`sun:02:00-sun:03:00`

This represents a one-hour window on Sunday in UTC.

Choose a maintenance window that minimises business disruption.

## 22. What is Apply Immediately?

Terraform:

`apply_immediately`

Example:

`apply_immediately = false`

If false, changes that AWS allows to be deferred can be applied during a later maintenance window.

If true, eligible modifications are applied as soon as possible.

**Production recommendation:**

Use a controlled change process.

Do not assume every modification can be deferred. Some configuration changes may have their own immediate application or reboot requirements.

## 23. What is Allow Version Upgrade?

Terraform:

`allow_version_upgrade`

Example:

`allow_version_upgrade = true`

This controls whether automatic minor version upgrades are permitted during maintenance.

It does not mean that every major engine upgrade will automatically happen.

For production, understand the upgrade process and test application compatibility before planned engine upgrades.

## 24. Important Redshift Terraform Parameters Explained

The following are important arguments of the Terraform `aws_redshift_cluster` resource.

**Cluster identity**

`cluster_identifier`

- Required.
- Identifies the Redshift cluster.
- Must follow AWS naming rules.
- Example: `production-redshift`.

`database_name`

- Optional.
- Name of the initial database.
- Example: `analytics`.
- If omitted, Redshift creates its default database.

`master_username`

- Required unless restoring from a snapshot.
- Specifies the administrative database username.
- Example: `redshiftadmin`.

**Credentials**

`manage_master_password`

- Enables Secrets Manager-managed master credentials.
- Example: `true`.
- Use instead of directly configuring `master_password`.

`master_password`

- Directly supplies the master password.
- Avoid hardcoding it.
- Terraform state can contain sensitive values.

`master_password_wo`

- Write-only password argument supported by compatible Terraform and AWS provider versions.
- Can reduce password exposure in state.
- Requires the associated `master_password_wo_version`.

`master_password_secret_kms_key_id`

- Specifies the KMS key for the managed master password secret.

**Compute**

`node_type`

- Specifies the Redshift compute node family and size.
- Example: `ra3.xlplus`.
- Choose according to workload and budget.

`cluster_type`

- Specifies the cluster deployment type.
- Common values: `single-node` and `multi-node`.

`number_of_nodes`

- Specifies the number of compute nodes.
- Required for multi-node configurations.
- Example: `2`.

`multi_az`

- Enables supported Multi-AZ configurations.
- Example: `true`.

**Networking**

`cluster_subnet_group_name`

- Specifies the Redshift subnet group.
- Example: `production-redshift-subnets`.

`vpc_security_group_ids`

- Specifies the security groups attached to the cluster.
- Example: `[aws_security_group.redshift.id]`.

`publicly_accessible`

- Controls public network accessibility.
- Production recommendation: `false`.

`port`

- Specifies the database connection port.
- Redshift commonly uses `5439`.

`enhanced_vpc_routing`

- Forces COPY and UNLOAD traffic through the VPC.
- Example: `true`.

`availability_zone`

- Specifies the Availability Zone for supported configurations.

`availability_zone_relocation_enabled`

- Allows supported RA3 clusters to be relocated between Availability Zones.

**Encryption**

`encrypted`

- Enables encryption at rest.
- Example: `true`.

`kms_key_id`

- Specifies the KMS encryption key ARN.

**Database configuration**

`cluster_parameter_group_name`

- Associates a parameter group with the cluster.

**Backup**

`automated_snapshot_retention_period`

- Number of days automated snapshots are retained.
- Choose according to recovery requirements.

`skip_final_snapshot`

- Controls whether a final snapshot is created before deletion.

`final_snapshot_identifier`

- Name of the final snapshot created when deleting the cluster.

`snapshot_identifier`

- Identifies an existing snapshot used to restore a cluster.

**Maintenance**

`preferred_maintenance_window`

- Specifies the preferred weekly maintenance period.

`allow_version_upgrade`

- Controls whether automatic minor version upgrades are allowed.

`apply_immediately`

- Controls when eligible modifications are applied.

**IAM**

`iam_roles`

- Attaches IAM roles to the cluster.
- Useful for S3 access and other supported integrations.

`default_iam_role_arn`

- Sets the default IAM role for the cluster.

**Other**

`tags`

- Adds resource metadata.
- Useful for cost allocation and resource ownership.

`cluster_version`

- Controls the engine version where supported.
- Check the provider schema and AWS-supported versions before setting it.

**Important:** The full Terraform provider schema contains additional optional and feature-specific arguments. Not every argument applies to every cluster configuration. Always check the provider documentation for the version you have selected.

**Main architecture decisions:**

## 26. Production Prerequisites Before Running Terraform

Before deploying Redshift, prepare the following.

**1. AWS account**

You need an AWS account with permission to create:
- Redshift clusters
- VPC security groups
- Redshift subnet groups
- IAM roles and policies
- KMS integrations
- CloudWatch logging resources
- Secrets Manager secrets

**2. Terraform**

Install Terraform.

Verify:

    terraform version

Use a Terraform version compatible with your AWS provider.

**3. AWS CLI**

Install and configure the AWS CLI.

Verify:

    aws sts get-caller-identity

This confirms which AWS identity is being used.

**4. AWS credentials**

Use an appropriate IAM role, IAM Identity Center or another secure authentication method.

Avoid hardcoding AWS access keys in Terraform files.

**5. Existing VPC**

You need an existing VPC.

Example:

`vpc-0123456789abcdef0`

**6. Private subnets**

You need suitable private subnets in your VPC.

Example:

    [
      "subnet-0123456789abcdef0",
      "subnet-0123456789abcdef1"
    ]

**7. Application security group**

You need the security group used by the applications that should connect to Redshift.

Example:

`sg-0123456789abcdef0`

**8. KMS key**

For the example below, you need an existing customer-managed KMS key suitable for Redshift encryption.

**9. Terraform state backend**

For a team or production environment, use a remote state backend.

An S3 backend should have:
- Versioning enabled
- Encryption
- Restricted access
- Appropriate state recovery controls
- State locking

Terraform state may contain sensitive information, so protect it as carefully as database credentials.

## 27. Complete Terraform Production Example

This example creates:

- Redshift security group
- Redshift subnet group
- Redshift parameter group
- IAM role for S3 read access
- Redshift cluster
- CloudWatch logging configuration

**Assumptions:**

- Your VPC already exists.
- Your private subnets already exist.
- Your application security group already exists.
- Your KMS key already exists.
- Your S3 bucket already exists.
- Your AWS account has the necessary permissions.
- The selected RA3 node type is available in your Region and supports the chosen configuration.

**Directory structure:**

    redshift-terraform/
    |
    |-- versions.tf
    |-- variables.tf
    |-- main.tf
    |-- outputs.tf
    |-- terraform.tfvars
    |-- backend.tf

### 27.1 versions.tf

    terraform {
      required_version = ">= 1.11.0"

      required_providers {
        aws = {
          source  = "hashicorp/aws"
          version = "~> 6.0"
        }
      }
    }

    provider "aws" {
      region = var.aws_region

      default_tags {
        tags = {
          Project     = var.project_name
          Environment = var.environment
          ManagedBy   = "Terraform"
        }
      }
    }

**Explanation:**

`required_version`

Defines the minimum Terraform version.

`required_providers`

Defines which provider Terraform needs.

`source`

Specifies the official AWS provider.

`version`

Specifies the allowed provider version range.

`provider "aws"`

Configures the AWS provider.

`region`

Defines the AWS Region in which resources will be created.

`default_tags`

Automatically applies common tags to supported resources.

### 27.2 variables.tf

    variable "aws_region" {
      description = "AWS deployment Region"
      type        = string
    }

    variable "project_name" {
      description = "Project name"
      type        = string
    }

    variable "environment" {
      description = "Deployment environment"
      type        = string
