# 1. WHAT IS AMAZON REDSHIFT?

Amazon Redshift is a fully managed cloud data warehouse designed for analytical workloads (OLAP).

Use cases:
- Business intelligence and reporting.
- Data warehousing.
- Data lake analytics.
- ETL and ELT pipelines.
- Large-scale data aggregation.
- Integration with Tableau, Power BI and QuickSight.

Redshift is optimized for OLAP, not transactional OLTP workloads.

# 4. DISTRIBUTION STYLES

Distribution determines how Redshift distributes table rows across compute nodes.

| Distribution | Description | Use case |
|---|---|---|
| AUTO | Redshift chooses automatically | Recommended starting point |
| EVEN | Distributes rows evenly | No suitable distribution key |
| KEY | Distributes using a selected column | Frequently joined tables |
| ALL | Copies the entire table to every node | Small dimension tables |

Example:

```sql
CREATE TABLE customers (
    customer_id BIGINT,
    customer_name VARCHAR(100),
    country VARCHAR(50)
)
DISTSTYLE KEY
DISTKEY (customer_id);
```

Automatic distribution:

```sql
CREATE TABLE customers (
    customer_id BIGINT,
    customer_name VARCHAR(100)
)
DISTSTYLE AUTO;
```

Best practice:
- Start with DISTSTYLE AUTO.
- Avoid data skew.
- Choose distribution keys based on join patterns.
- Avoid unnecessary data redistribution.

# 5. SORT KEYS

Sort keys determine how data is physically ordered within Redshift tables.

Types:

- Compound sort key: Column order matters. Useful when queries filter on leading columns.
- Interleaved sort key: Gives multiple columns equal weight, but requires additional maintenance.

Example:

```sql
CREATE TABLE sales (
    sale_id BIGINT,
    sale_date DATE,
    customer_id BIGINT,
    amount DECIMAL(12,2)
)
DISTSTYLE AUTO
SORTKEY (sale_date);
```

Query using sort key:

```sql
SELECT *
FROM sales
WHERE sale_date >= '2026-01-01'
  AND sale_date < '2026-02-01';
```

Best practices:
- Select sort keys based on query patterns.
- Use date columns for time-based filtering where appropriate.
- Avoid choosing keys simply because they are primary keys.
- Consider automatic table optimization.

# 6. ESSENTIAL SQL COMMANDS

Create database:

```sql
CREATE DATABASE analytics;
```

Create schemas:

```sql
CREATE SCHEMA staging;
CREATE SCHEMA warehouse;
CREATE SCHEMA reporting;
```

Create table:

```sql
CREATE TABLE warehouse.customers (
    customer_id BIGINT,
    customer_name VARCHAR(150),
    email VARCHAR(255),
    created_at TIMESTAMP
)
DISTSTYLE AUTO
SORTKEY (created_at);
```

Insert:

```sql
INSERT INTO warehouse.customers
VALUES (
    1001,
    'John Smith',
    'john@example.com',
    GETDATE()
);
```

Select:

```sql
SELECT *
FROM warehouse.customers;
```

Update:

```sql
UPDATE warehouse.customers
SET email = 'new@example.com'
WHERE customer_id = 1001;
```

Delete:

```sql
DELETE FROM warehouse.customers
WHERE customer_id = 1001;
```

Truncate:

```sql
TRUNCATE TABLE warehouse.customers;
```

Drop:

```sql
DROP TABLE warehouse.customers;
```

# 7. LOADING DATA FROM S3

COPY is generally preferred for bulk loading data into Redshift.

CSV example:

```sql
COPY staging.customers
FROM 's3://my-data-bucket/customers/'
IAM_ROLE 'arn:aws:iam::123456789012:role/RedshiftS3Role'
FORMAT AS CSV
IGNOREHEADER 1
REGION 'eu-west-1';
```

Parquet example:

```sql
COPY staging.customers
FROM 's3://my-data-bucket/customers/'
IAM_ROLE 'arn:aws:iam::123456789012:role/RedshiftS3Role'
FORMAT AS PARQUET;
```

Supported formats include:
- CSV
- JSON
- Parquet
- Avro
- ORC

Best practices:
- Use IAM roles instead of hardcoded credentials.
- Prefer multiple reasonably sized files.
- Use manifest files when you need exact file selection.
- Monitor load errors.
- Validate record counts after loading.

# 8. EXPORTING DATA TO S3

Use UNLOAD to export query results.

```sql
UNLOAD ('SELECT * FROM warehouse.customers')
TO 's3://my-data-bucket/exports/customers/'
IAM_ROLE 'arn:aws:iam::123456789012:role/RedshiftS3Role'
FORMAT AS PARQUET
ALLOWOVERWRITE;
```

Use cases:
- Export data to a data lake.
- Share datasets with downstream applications.
- Create analytical extracts.
- Integrate with other AWS services.

# 9. QUERY PERFORMANCE OPTIMIZATION

| Practice | Benefit |
|---|---|
| Appropriate sort keys | Reduces unnecessary block scans |
| Appropriate distribution | Reduces data redistribution |
| Select specific columns | Avoids unnecessary data reads |
| COPY | Efficient bulk loading |
| Materialized views | Reuses precomputed results |
| Compression | Reduces storage and I/O |
| EXPLAIN | Helps analyze query execution |
| Redshift Advisor | Provides optimization recommendations |

Avoid:

```sql
SELECT *
FROM warehouse.sales;
```

Prefer:

```sql
SELECT
    sale_id,
    sale_date,
    amount
FROM warehouse.sales
WHERE sale_date >= '2026-01-01';
```

Inspect query plans:

```sql
EXPLAIN
SELECT *
FROM warehouse.sales
WHERE sale_date >= '2026-01-01';
```

Look for:
- Large sequential scans.
- Data redistribution.
- Broadcast operations.
- Expensive joins.
- Disk-based operations.

# 10. VACUUM AND ANALYZE

VACUUM helps reclaim deleted space and maintain sort order when needed.

```sql
VACUUM warehouse.sales;
```

Other options:

```sql
VACUUM DELETE ONLY warehouse.sales;

VACUUM SORT ONLY warehouse.sales;

VACUUM FULL warehouse.sales;
```

ANALYZE updates table statistics used by the query optimizer.

```sql
ANALYZE warehouse.sales;
```

Redshift also supports automatic maintenance, including automatic vacuum and analyze operations.

Do not run manual maintenance commands unnecessarily.

Example:

```sql
CREATE ROLE analyst_role;

GRANT USAGE ON SCHEMA reporting
TO ROLE analyst_role;

GRANT SELECT ON ALL TABLES IN SCHEMA reporting

```

Create user and assign role:

```sql

GRANT ROLE analyst_role
TO analyst_user;
```

Production best practices:
- Use least privilege.
- Prefer federated authentication.
- Encrypt data at rest and in transit.
- Restrict network access.
- Audit database activity.
- Never hardcode production credentials.

| Tool / View | Purpose |

Find recent queries:

```sql

    query_id,
    user_id,
    status,
    start_time,
    end_time

ORDER BY start_time DESC
```

# 15. PROVISIONED VS SERVERLESS

| Feature | Provisioned | Serverless |
|---|---|---|
| Infrastructure | Manage cluster capacity | Managed compute |
| Scaling | Resize cluster | Automatically scales |
| Pricing | Provisioned capacity | RPU consumption |
| Administration | More infrastructure control | Less infrastructure management |
| Best suited for | Predictable workloads | Variable workloads |

Choose based on workload patterns, performance requirements and cost.

# 17. TYPICAL AWS REDSHIFT DATA ARCHITECTURE

A typical modern data warehouse:

1. Data originates from operational databases, APIs and applications.
2. AWS DMS, Glue or other ingestion tools move data into S3.
3. S3 acts as the data lake and landing area.
4. Redshift loads data using COPY or queries external data using Spectrum.
5. SQL transformations populate staging, warehouse and reporting schemas.
6. QuickSight, Power BI or Tableau consumes analytical data.
7. CloudWatch, CloudTrail and IAM support monitoring, auditing and security.

# 18. TOP 10 THINGS TO REMEMBER

1. Redshift is designed for OLAP, not OLTP.
2. MPP enables parallel query processing.
3. COPY is preferred for bulk loading.
4. UNLOAD exports query results to S3.
5. DISTSTYLE AUTO is a good starting point.
6. Sort keys should reflect actual query patterns.
7. VACUUM and ANALYZE help maintain performance.
8. EXPLAIN helps understand query execution.
9. IAM, encryption and network isolation are essential.
10. Choose Serverless or Provisioned based on workload and cost.
