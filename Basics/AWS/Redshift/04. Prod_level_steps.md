# Production AWS Redshift Architecture with Terraform, SQLAlchemy, and Alembic

## 1. How should Redshift infrastructure and database schemas be managed?

In a production environment, separate infrastructure provisioning from database schema management.

Use:

- **Terraform** to provision and manage AWS infrastructure.
- **Alembic** to manage database schema changes through version-controlled migrations.
- **SQLAlchemy** to manage database connectivity, queries, and application-level database interactions.
- **ETL/ELT tools and SQL scripts** to load and transform warehouse data.

The general architecture looks like this:

```text
                 CI/CD Pipeline
                       |
          +------------+------------+
          |                         |
          v                         v
    Infrastructure              Database
      Pipeline                 Migration Pipeline
          |                         |
          v                         v
      Terraform                  Alembic
          |                         |
          v                         v
    AWS Infrastructure       Redshift Database
          |                         |
          +------------+------------+
                       |
                       v
              Application / ETL
                       |
                       v
                  SQLAlchemy
```

The important principle is:

**Terraform creates the Redshift infrastructure. Alembic manages the database schema. SQLAlchemy connects to and interacts with the database.**

## 2. What should Terraform manage?

Terraform should manage the AWS resources required to operate Redshift.

Typical resources include:

- Redshift provisioned cluster or Redshift Serverless workgroup.
- Redshift subnet group.
- VPC and security groups.
- IAM roles and policies.
- KMS encryption keys.
- Secrets Manager integration.
- Automated snapshots and retention settings.
- CloudWatch monitoring and alarms.
- Parameter groups.
- S3 access permissions.
- Network routing and connectivity.

Terraform should not normally be responsible for creating every table, view, or stored procedure.

Those belong in database migrations or other database deployment processes.

### Example Terraform configuration

The following is an illustrative provisioned Redshift cluster configuration.

```hcl
resource "aws_redshift_subnet_group" "redshift" {
  name       = "production-redshift-subnet-group"
  subnet_ids = var.private_subnet_ids

  tags = var.tags
}

resource "aws_redshift_parameter_group" "redshift" {
  name   = "production-redshift-parameters"
  family = "redshift-2.0"

  tags = var.tags
}

resource "aws_redshift_cluster" "warehouse" {
  cluster_identifier = "production-data-warehouse"

  database_name   = "analytics"
  node_type       = "ra3.xlplus"
  cluster_type    = "multi-node"
  number_of_nodes = 2

  cluster_version = var.redshift_version

  # Network configuration
  cluster_subnet_group_name = aws_redshift_subnet_group.redshift.name
  vpc_security_group_ids    = [var.redshift_security_group_id]

  publicly_accessible = false

  # Encryption
  encrypted  = true
  kms_key_id = var.kms_key_arn

  # Credentials managed by AWS Secrets Manager
  manage_master_password = true

  # S3 integration
  iam_roles = [
    var.redshift_s3_iam_role_arn
  ]

  # Operational settings
  enhanced_vpc_routing = true
  automated_snapshot_retention_period = 14

  skip_final_snapshot       = false
  final_snapshot_identifier = "production-redshift-final-snapshot"

  tags = var.tags

  lifecycle {
    prevent_destroy = true
  }
}
```

Example variables:

```hcl
variable "private_subnet_ids" {
  type = list(string)
}

variable "redshift_security_group_id" {
  type = string
}

variable "kms_key_arn" {
  type = string
}

variable "redshift_s3_iam_role_arn" {
  type = string
}

variable "redshift_version" {
  type = string
}

variable "tags" {
  type = map(string)
}
```

### Important production considerations

1. Keep Redshift in private subnets unless there is a specific, justified reason otherwise.
2. Restrict security group ingress to approved application, migration, and administration sources.
3. Use AWS Secrets Manager for managed master credentials.
4. Encrypt the cluster using KMS.
5. Enable automated snapshots and define a recovery strategy.
6. Use IAM roles for Redshift-to-S3 access rather than embedding AWS credentials.
7. Enable enhanced VPC routing where appropriate.
8. Protect critical infrastructure against accidental destruction.
9. Store Terraform state remotely and encrypt it, with appropriate access controls.
10. Select node type and node count based on workload, concurrency, storage, and performance requirements.

The example uses two RA3 nodes only as an illustration. It is not a universal production sizing recommendation.

Also, a multi-node cluster does not automatically mean Multi-AZ deployment. Evaluate the appropriate Redshift availability architecture separately.

## 3. What should Alembic manage?

Alembic should manage database schema changes.

For example:

- Creating schemas.
- Creating tables.
- Adding columns.
- Modifying table structures.
- Creating views.
- Creating materialized views.
- Creating stored procedures.
- Managing database permissions.
- Applying controlled schema changes.

Alembic maintains a migration history in a database table called:

```text
alembic_version
```

This allows the team to track which migrations have been applied.

### Example migration

Create a migration:

```bash
alembic revision -m "create warehouse schemas"
```

Example migration file:

```python
from alembic import op

revision = "001"
down_revision = None
branch_labels = None
depends_on = None


def upgrade():
    op.execute("""
        CREATE SCHEMA IF NOT EXISTS staging;
    """)

    op.execute("""
        CREATE SCHEMA IF NOT EXISTS warehouse;
    """)

    op.execute("""
        CREATE SCHEMA IF NOT EXISTS reporting;
    """)


def downgrade():
    op.execute("""
        DROP SCHEMA IF EXISTS reporting CASCADE;
    """)

    op.execute("""
        DROP SCHEMA IF EXISTS warehouse CASCADE;
    """)

    op.execute("""
        DROP SCHEMA IF EXISTS staging CASCADE;
    """)
```

For production, be careful with destructive downgrade operations. Dropping a schema with `CASCADE` can delete many dependent objects. A forward-fix migration is often safer.

### Example: Create a Redshift table

```python
from alembic import op

revision = "002"
down_revision = "001"
branch_labels = None
depends_on = None


def upgrade():
    op.execute("""
        CREATE TABLE warehouse.customers (
            customer_id BIGINT NOT NULL,
            customer_name VARCHAR(255),
            email VARCHAR(255),
            created_at TIMESTAMP
        )
        DISTSTYLE AUTO
        SORTKEY(created_at);
    """)


def downgrade():
    op.execute("""
        DROP TABLE IF EXISTS warehouse.customers;
    """)
```

Notice the use of:

```sql
DISTSTYLE AUTO
SORTKEY(created_at)
```

These are Redshift-specific physical table design options.

This is one reason explicit SQL migrations are often preferable to relying entirely on ORM-generated table creation.

## 4. What should SQLAlchemy manage?

SQLAlchemy is primarily responsible for database connectivity and application-level database interactions.

Typical responsibilities include:

- Creating database connections.
- Executing SQL queries.
- Managing connection pools.
- Mapping database tables to Python classes when appropriate.
- Reading and writing application data.
- Managing transactions where supported by the driver and database.

Install the dependencies:

```bash
pip install sqlalchemy sqlalchemy-redshift psycopg2-binary alembic
```

The Redshift SQLAlchemy dialect is provided by an external package. Verify compatibility between the dialect, SQLAlchemy version, and Redshift driver before adopting versions in production.

### Example SQLAlchemy connection

```python
from sqlalchemy import create_engine, text

DATABASE_URL = (
    "redshift+psycopg2://"
    "username:password@"
    "redshift-endpoint:5439/"
    "analytics"
)

engine = create_engine(
    DATABASE_URL,
    pool_pre_ping=True,
    pool_size=5,
    max_overflow=10
)

with engine.connect() as connection:
    result = connection.execute(
        text("SELECT current_database()")
    )

    print(result.fetchone())
```

For production, do not hardcode credentials in source code.

Retrieve credentials securely from AWS Secrets Manager or use an appropriate identity-based authentication approach.

Also, choose connection pool settings based on the application's concurrency and Redshift connection limits.

## 5. Important: Redshift is not PostgreSQL

Redshift is PostgreSQL-compatible, but it is not a standard PostgreSQL database.

There are important differences.

For example:

- Primary key constraints are informational.
- Foreign key constraints are informational.
- Unique constraints are informational.
- Distribution styles affect how data is distributed across nodes.
- Sort keys affect how data is stored and scanned.
- Some PostgreSQL features and SQL syntax are not supported.

This matters when using SQLAlchemy and Alembic.

### Why not rely entirely on SQLAlchemy ORM?

In a traditional PostgreSQL application, you might define a model:

```python
class Customer(Base):
    __tablename__ = "customers"

    customer_id = Column(Integer, primary_key=True)
    customer_name = Column(String)
    email = Column(String)
```

Then create tables using:

```python
Base.metadata.create_all(engine)
```

This approach is generally not recommended as the primary production schema-management mechanism for Redshift.

Why?

Because Redshift table design involves physical storage decisions such as:

- DISTSTYLE
- DISTKEY
- SORTKEY
- ENCODE

You need control over these choices.

For this reason, explicit SQL inside Alembic migrations is often a better approach.

You can still use SQLAlchemy models for application-level data access where they make sense.

## 6. How should the deployment pipeline work?

A production deployment should separate infrastructure deployment, database migrations, and application deployment.

### Pipeline 1: Infrastructure deployment

Responsible for creating or updating AWS infrastructure.

```bash
terraform init
terraform validate
terraform plan
terraform apply
```

This pipeline manages:

- Redshift infrastructure.
- Networking.
- IAM.
- Encryption.
- Security groups.
- Monitoring.
- S3 integration.

### Pipeline 2: Database migration deployment

Responsible for applying database schema changes.

```bash
alembic upgrade head
```

This pipeline manages:

- Schemas.
- Tables.
- Views.
- Stored procedures.
- Database permissions.
- Schema changes.

Migrations should run from a controlled deployment job with network access to Redshift and a dedicated, least-privilege migration identity.

Avoid running migrations automatically every time an application instance starts.

Ensure that only one migration process runs against a given environment at a time.

### Pipeline 3: Application deployment

Responsible for deploying application code.

The application uses SQLAlchemy to connect to Redshift and execute queries.

```text
Infrastructure Pipeline
        |
        v
     Terraform
        |
        v
  AWS Redshift Ready
        |
        v
 Database Migration Pipeline
        |
        v
    Alembic
        |
        v
  Database Schema Ready
        |
        v
 Application Deployment
        |
        v
    SQLAlchemy
        |
        v
   Redshift Queries
```

## 7. Where does data loading fit?

SQLAlchemy should not normally be the primary mechanism for bulk-loading large warehouse datasets.

For bulk data ingestion, use Redshift's COPY command.

Example:

```sql
COPY staging.customers
FROM 's3://my-data-bucket/customers/'
IAM_ROLE 'arn:aws:iam::123456789012:role/redshift-s3-role'
FORMAT AS PARQUET;
```

A typical data pipeline might look like:

```text
Source Systems
      |
      v
   Amazon S3
      |
      v
Redshift COPY
      |
      v
Staging Tables
      |
      v
SQL Transformations
      |
      v
Warehouse Tables
      |
      v
Reporting Tables
      |
      v
BI / Analytics
```

Use set-based SQL transformations for warehouse workloads rather than retrieving large datasets into Python and processing them row by row.

| Component | Responsibility |
|---|---|
| Terraform | AWS infrastructure provisioning |
| Redshift | Data warehouse compute and storage |
| Alembic | Database schema migrations |
| SQLAlchemy | Application database connectivity and queries |
| SQL scripts | Redshift-specific DDL and transformations |
| S3 | Data lake and bulk data storage |

| ETL/ELT pipeline | Data ingestion and transformation |
| CI/CD | Controlled deployment and migration execution |

## 9. Recommended production approach

For a production Redshift environment, I would use the following separation of responsibilities:

### Infrastructure layer

Use Terraform to provision:

- Redshift cluster or Serverless workgroup.
- Networking and security.
- IAM roles.
- KMS encryption.
- Secrets Manager integration.
- S3 integration.
- Snapshots and monitoring.

### Database layer

Use Alembic to manage:

- Database schemas.
- Tables.
- Views.
- Materialized views.
- Stored procedures.
- Permissions.
- Version-controlled DDL changes.

Use explicit SQL for Redshift-specific table design.

### Application layer

Use SQLAlchemy to manage:

- Database connections.
- Connection pooling.
- Queries.
- Application-level data access.

### Data engineering layer

Use:

- S3 for staging and data storage.
- COPY for bulk ingestion.
- SQL for transformations.
- UNLOAD for exporting data.
- Appropriate orchestration tools for scheduling and dependencies.

## 10. Final architecture

The overall production architecture should look like this:

```text
                       Git Repository
                             |
                             v
                        CI/CD System
                             |
             +---------------+---------------+
             |               |               |
             v               v               v
        Terraform         Alembic        Application
             |               |               |
             v               v               v
      AWS Infrastructure  Redshift DDL   SQLAlchemy
             |               |               |
             +---------------+---------------+
                             |
                             v
                       AWS Redshift
                             |
                  +----------+----------+
                  |                     |
                  v                     v
             Staging Tables       Warehouse Tables
                  |                     |
                  +----------+----------+
                             |
                             v
                      Reporting Tables
                             |
                             v
                       BI / Analytics
```

**The key takeaway:**

Do not use Terraform to manage every database table, and do not use SQLAlchemy's `create_all()` as your production Redshift schema deployment strategy.

Use Terraform for infrastructure, Alembic for version-controlled schema migrations, SQLAlchemy for application connectivity, and Redshift-native SQL for warehouse operations.
