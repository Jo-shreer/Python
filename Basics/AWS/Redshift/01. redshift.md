# Amazon Redshift – Complete AWS Service Reference

## 1. What is Amazon Redshift?

Amazon Redshift is a fully managed, petabyte-scale cloud data warehouse designed for analytical workloads.

It is primarily used for:

- Business intelligence (BI) and reporting.
- Data analytics and aggregation.
- Complex SQL queries across large datasets.
- Enterprise data warehouses.
- Centralized analytics across multiple data sources.
- Data lake analytics using Amazon S3.
- Data sharing between teams, applications, and AWS accounts.

Redshift uses:

- Columnar storage.
- Massively parallel processing (MPP).
- Distributed query execution.
- Data compression.
- SQL-based querying.

### Redshift vs transactional databases

| Feature         | Amazon Redshift              | RDS / Aurora                |
| --------------- | ---------------------------- | --------------------------- |
| Primary purpose | Analytics and reporting      | Application transactions    |
| Workload        | OLAP                         | OLTP                        |
| Data access     | Large scans and aggregations | Individual row reads/writes |
| Storage         | Columnar-oriented            | Generally row-oriented      |
| Query pattern   | Complex analytical SQL       | Frequent transactional SQL  |
| Typical use     | Data warehouse               | Application database        |

Redshift supports SQL operations, but it should not normally be selected as the primary database for a high-volume transactional application.

## 2. Main deployment types

Redshift offers two main deployment models.

### A. Provisioned Redshift

You provision and manage a Redshift cluster.

You choose:

- Node family and node type.
- Number of nodes.
- Compute capacity.
- Network configuration.
- Security configuration.
- Backup and maintenance settings.

AWS manages the underlying infrastructure, database engine maintenance, and supported operational tasks.

Use provisioned Redshift when:

- Workloads are relatively predictable.
- You want more direct control over compute sizing.
- You have sustained analytical workloads.
- You need specific provisioned-cluster capabilities.

### B. Redshift Serverless

You do not provision individual cluster nodes.

AWS automatically provisions and manages compute capacity according to workload demand.

You configure:

- Namespace.
- Workgroup.
- Base capacity in RPUs.
- Maximum capacity and usage limits.
- Network settings.
- Security settings.
- Encryption and monitoring.

Use Serverless when:

- Workloads are intermittent or unpredictable.
- You do not want to manage node capacity.
- You want automatic compute scaling.
- You want to pay for compute usage rather than keep a provisioned cluster running continuously.

Important: Serverless does not mean that storage, data transfer, snapshots, or every related feature is free when idle. Understand the separate billing components.

## 3. Redshift architecture

### Provisioned cluster architecture

A provisioned Redshift cluster consists of:

**Leader node**

- Receives SQL queries from clients.
- Parses and plans queries.
- Coordinates distributed query execution.
- Distributes work to compute nodes.
- Combines and returns query results.

**Compute nodes**

- Store and process data.
- Execute query operations in parallel.
- Perform scans, joins, aggregations, and sorting.

**Slices**

- Logical partitions of compute resources within compute nodes.
- Each slice processes a portion of the data in parallel.

The architecture allows Redshift to process large datasets using multiple compute resources.

### Serverless architecture

Serverless uses two important concepts:

**Namespace**

- Contains database objects and users.
- Includes schemas, tables, users, permissions, datashares, and snapshots.
- Represents the logical data environment.

**Workgroup**

- Contains the compute resources used to run queries.
- Has network and security configuration.
- Defines the workgroup endpoint used by clients.
- Has capacity and usage-control settings.

A namespace and workgroup are separate concepts: namespace represents the data environment, while workgroup represents compute and connectivity.

## 5. Provisioned cluster configuration parameters

When creating a provisioned Redshift cluster, important settings include:

### Cluster identification

- Cluster identifier: Unique cluster name within the applicable AWS account and Region.
- Database name: Initial database name.
- Master username: Initial administrator username.
- Master user password: Initial password, or supported secret-management approach.
- Node type: Compute node family and size.
- Number of nodes: Number of compute nodes.
- Cluster type: Single-node or multi-node, subject to supported node types and configurations.

### Node families

Important node families include:

**RA3**

- Separates compute capacity from managed storage.
- Uses local high-performance storage for frequently accessed data.
- Uses Redshift Managed Storage for data beyond local capacity.
- Useful when storage requirements grow independently of compute requirements.

**DC2**

- Uses local SSD storage.
- Compute and storage capacity are more closely coupled.
- Can suit certain smaller or performance-oriented workloads.
- Evaluate current availability and feature support before choosing it.

**RG**

- A newer provisioned node family available in supported Regions.
- Provides managed storage and compute options.
- Check regional availability and feature compatibility before selecting it.

Do not choose a node family solely by price. Compare workload characteristics, storage requirements, supported features, and regional availability.

### Cluster configuration

Important parameters include:

- Cluster subnet group.
- VPC security groups.
- Publicly accessible setting.
- Enhanced VPC routing.
- Availability zone.
- Encryption.
- KMS key.
- Automated snapshot retention.
- Maintenance window.
- Maintenance track.
- Automated snapshot configuration.
- Manual snapshot configuration.
- Parameter group.
- IAM roles.
- Logging configuration.
- Cluster tags.
- Deletion protection.
- Elastic resize or supported resize options.

### Important settings

**Publicly accessible**

- Determines whether the cluster can have a publicly accessible endpoint.
- Public accessibility does not automatically permit access.
- Security groups, routing, and other access controls still apply.

**Enhanced VPC routing**

- Routes COPY, UNLOAD, and supported Redshift data-transfer traffic through your VPC.
- Allows VPC network controls to apply to supported data-transfer paths.
- Useful when you need tighter network control over data movement.

**Encryption**

- Enables encryption at rest.
- Uses AWS KMS for supported cluster encryption configurations.
- Also configure encryption in transit for client connections.

**Deletion protection**

- Prevents accidental cluster deletion while enabled.
- Disable it deliberately when performing an authorized deletion.

## 7. Redshift storage architecture

Redshift uses columnar storage for analytical processing.

### Row storage vs columnar storage

In a row-oriented database, data for a row is stored together.

In a columnar database, values from the same column are stored together.

Example:

| Employee ID | Name  | Department | Salary |
| ----------- | ----- | ---------- | ------ |
| 1           | John  | IT         | 60000  |
| 2           | Mary  | Finance    | 70000  |
| 3           | David | IT         | 65000  |

If an analytical query only needs the Salary column, columnar storage can avoid reading unnecessary columns.

Benefits:

- Less data read for many analytical queries.
- Better compression opportunities.
- Efficient large-scale aggregations.
- Improved analytical query performance.

### Redshift Managed Storage

Redshift Managed Storage is associated with supported provisioned configurations, especially RA3, and is also used by Serverless.

It separates storage capacity from compute capacity.

Benefits:

- Scale storage independently of provisioned compute.
- Use local storage for frequently accessed data.
- Maintain larger datasets without requiring equivalent local SSD capacity.

## 10. Distribution styles and distribution keys

Data distribution is one of the most important Redshift performance concepts.

Redshift distributes table rows across compute resources.

The objective is to:

- Balance data across nodes.
- Minimize data movement during joins.
- Reduce query execution time.

### Distribution styles

**AUTO**

- Redshift chooses a suitable distribution style.
- Recommended as a starting point for many tables.
- Automatic optimization can change distribution as data grows.

**EVEN**

- Distributes rows evenly across slices.
- Does not use a particular column as the distribution key.
- Useful when there is no suitable join key.

**KEY**

- Distributes rows using the values of a selected column.
- Can improve joins when related tables use compatible distribution keys.
- Can create data skew if the selected column has highly uneven values.

**ALL**

- Replicates the entire table across compute nodes.
- Can help with small, relatively static dimension tables.
- Increases storage and data-loading costs.

### Distribution key example

Suppose you have:

- orders table
- customers table

Both tables are frequently joined using customer_id.

Using compatible KEY distribution on customer_id may reduce data redistribution during joins.

Important:

- Do not automatically choose a primary key as the distribution key.
- Evaluate join patterns and data cardinality.
- Watch for skew.
- AUTO is a sensible default until workload evidence justifies manual tuning.

## 11. Sort keys

Sort keys define how data is ordered on storage.

They help Redshift skip unnecessary data blocks when executing queries.

### Sort key types

**Compound sort key**

- Uses an ordered list of columns.
- The first column has the greatest influence on sorting.
- Useful when queries frequently filter using leading sort-key columns.

**Interleaved sort key**

- Gives multiple columns more equal importance in sort order.
- Has additional maintenance considerations.
- Generally prefer AUTO or compound keys unless a measured workload justifies interleaved sorting.

**AUTO sort key**

- Redshift automatically selects and manages sort-key choices where supported.

### Sort key example

A sales table may have:

- sale_date
- customer_id
- product_id
- amount

If queries frequently filter by date ranges, sale_date may be a useful leading sort key.

Example:

```sql
CREATE TABLE sales (
    sale_id BIGINT,
    sale_date DATE,
    customer_id BIGINT,
    amount DECIMAL(12,2)
)
DISTSTYLE AUTO
SORTKEY AUTO;
```

Important:

- Sort keys are not the same as primary keys.
- Sort keys do not enforce uniqueness.
- Choose based on actual filtering, joining, and query patterns.
- Automatic table optimization can reduce manual tuning.

## 13. Data loading into Redshift

Redshift supports several ways to ingest data.

### COPY command

COPY is the primary high-performance bulk-loading method.

Common sources:

- Amazon S3.
- DynamoDB.
- EMR-supported sources and workflows.
- Other supported data sources through appropriate integrations.

Example:

```sql
COPY sales
FROM 's3://my-data-bucket/sales/'
IAM_ROLE 'arn:aws:iam::123456789012:role/RedshiftS3Role'
FORMAT AS PARQUET;
```

Important COPY parameters and options include:

- FROM
- IAM_ROLE
- CREDENTIALS, where supported and appropriate
- FORMAT AS CSV
- FORMAT AS JSON
- FORMAT AS PARQUET
- FORMAT AS AVRO
- DELIMITER
- IGNOREHEADER
- DATEFORMAT
- TIMEFORMAT
- NULL AS
- EMPTYASNULL
- BLANKSASNULL
- ACCEPTINVCHARS
- COMPUPDATE
- STATUPDATE
- MAXERROR
- REGION
- MANIFEST
- GZIP
- BZIP2
- ENCRYPTED
- FILLRECORD
- TRUNCATECOLUMNS

Exact option compatibility depends on file format and COPY mode.

Production recommendations:

- Prefer IAM roles over embedded long-term credentials.
- Use compressed columnar formats such as Parquet where appropriate.
- Load multiple files in parallel.
- Avoid many extremely small files.
- Use manifests when you need precise control over input files.
- Validate source data before loading.
- Monitor rejected rows and load errors.

### INSERT

INSERT is supported for smaller or targeted data modifications.

It is generally not the preferred approach for large-scale bulk ingestion.

### UNLOAD

UNLOAD exports query results from Redshift to S3.

Example:

```sql
UNLOAD ('SELECT * FROM sales')
TO 's3://my-data-bucket/exports/sales_'
IAM_ROLE 'arn:aws:iam::123456789012:role/RedshiftS3Role'
FORMAT AS PARQUET;
```

Important UNLOAD options include:

## 14. Redshift Spectrum and S3 integration

Redshift Spectrum allows supported Redshift configurations to query data stored in Amazon S3 without first loading all that data into Redshift tables.

Example architecture:

- S3 stores raw data.
- AWS Glue Data Catalog stores table metadata.
- Redshift queries S3 data through Spectrum.
- Redshift joins external data with internal Redshift tables.

### Important components

**External schema**

- Defines the external schema in Redshift.
- Connects to an external metadata catalog or supported catalog configuration.

**External table**

- Represents data stored outside Redshift.
- Contains metadata describing the S3 data.

**AWS Glue Data Catalog**

- Stores table and schema metadata.
- Helps organize data lake datasets.

**IAM role**

- Allows Redshift to access S3 and the catalog as required.

Example SQL:

```sql
CREATE EXTERNAL SCHEMA spectrum_schema
FROM DATA CATALOG
DATABASE 'sales_catalog'
IAM_ROLE 'arn:aws:iam::123456789012:role/RedshiftSpectrumRole'
REGION 'eu-west-1';
```

Then:

```sql
SELECT *
FROM spectrum_schema.orders;
```

Important:

- External tables do not store the actual S3 data inside Redshift.
- S3 data format and partition layout affect performance.
- Partition pruning can reduce scanned data.
- Parquet and ORC are often efficient analytical formats.
- Spectrum usage and scanned data can have separate costs.
- Permissions must allow access to the catalog and S3 objects.

### B. Database authentication

Redshift supports database authentication options including:

- Database users and passwords.
- IAM-based database authentication.
- Federated identity approaches.
- AWS IAM Identity Center integration where supported.
- Secrets Manager integration for supported credential workflows.

Prefer short-lived credentials or federated authentication where possible.

### C. Database authorization

Database permissions control what authenticated users can do.

Examples:

- CREATE
- SELECT
- INSERT
- UPDATE
- DELETE
- REFERENCES
- USAGE
- EXECUTE
- TEMP
- ASSUMEROLE

Use:

- Database users.
- Database roles.
- Role grants.
- Schema permissions.
- Table permissions.
- View permissions.

Example:

```sql
CREATE ROLE reporting_role;

GRANT USAGE ON SCHEMA reporting
TO ROLE reporting_role;

GRANT SELECT ON ALL TABLES IN SCHEMA reporting
TO ROLE reporting_role;

GRANT ROLE reporting_role TO analyst_user;
```

Check default privileges and future-object permissions separately. Granting access to existing tables does not necessarily grant access to tables created later.

### D. Row-level security

Row-level security (RLS) restricts which rows a user can see.

Example use case:

- Finance users can see finance records.
- Regional managers can see their own region.
- Department users can access only their department's records.

RLS uses policies and user or role context.

### E. Dynamic data masking

Dynamic data masking can restrict visibility of sensitive column values.

Example:

- Analysts can see only partially masked email addresses.
- Customer support users can see selected customer details.
- Privileged roles can access unmasked data when authorized.

Validate masking policies, role permissions, and query behavior carefully.

## 17. VPC and networking architecture

Redshift is a VPC-connected service.

Unlike Lambda, which can run without VPC attachment, Redshift clusters and Serverless workgroups use VPC networking configurations.

### Provisioned Redshift networking

When creating a cluster, configure:

- VPC.
- Cluster subnet group.
- Subnets.
- Security groups.
- Route tables.
- Availability Zone.
- Public accessibility.
- Enhanced VPC routing.

A Redshift subnet group contains the subnets Redshift can use for the cluster.

Production recommendation:

- Use private subnets unless public connectivity is genuinely required.
- Restrict inbound rules to approved application and administration sources.
- Use separate security groups for application, BI, and administration access where appropriate.

### Redshift Serverless networking

Configure the workgroup with:

- VPC.
- Subnet IDs.
- Security groups.
- Public accessibility.
- Endpoint and port settings.
- Enhanced VPC routing where required.

### Common ports

The traditional Redshift connection port is 5439.

Serverless supports ports within documented ranges, including 5431–5455 and 8191–8215.

Always use the actual endpoint and configured port rather than assuming a default.

### Connectivity examples

Application running in private subnet → Redshift in VPC.

BI tool running in corporate network → VPN or Direct Connect → VPC → Redshift.

On-premises application → VPN / Direct Connect → Redshift private endpoint.

### Security group example

Allow inbound TCP 5439 from the application security group.

Do not expose Redshift to 0.0.0.0/0.

The exact port and source must match your configured endpoint and client network.

### Enhanced VPC routing

When enabled, supported COPY and UNLOAD traffic is routed through your VPC.

This allows network-level controls and visibility for supported data-transfer paths.

Important:

- Enhanced VPC routing does not automatically make Redshift private.
- It does not replace IAM permissions.
- It does not replace S3 bucket policies.
- Ensure required S3, Glue, and other service connectivity is available.

## 18. Redshift endpoints and private connectivity

Redshift provides connection endpoints for clients.

Examples:

- Provisioned cluster endpoint.
- Serverless workgroup endpoint.

Private access can be achieved through VPC networking, VPN, Direct Connect, and supported private connectivity options.

Redshift also supports managed VPC endpoint functionality for certain cross-VPC access scenarios.

Important distinction:

- A Redshift cluster/workgroup endpoint is the database connection address.
- A VPC endpoint is a private connectivity mechanism for supported AWS services or supported Redshift managed VPC endpoint scenarios.
- They are not interchangeable concepts.

For applications in the same VPC, private subnet routing and security groups are commonly sufficient.

## 19. Workload Management (WLM)

WLM controls how queries use available compute resources.

It helps manage:

- Query queues.
- Query concurrency.
- Memory allocation.
- Query prioritization.
- Workload isolation.

### Automatic WLM

Redshift manages query resources automatically.

It is generally the preferred starting point for many workloads.

### Manual WLM

You define queue configuration and resource allocation more directly.

Use only when you have measured workload requirements and understand the operational trade-offs.

### Query priorities

Workloads can be assigned priorities to influence resource allocation.

Examples:

- Critical dashboards.
- Scheduled ETL.
- Ad hoc analyst queries.
- Background maintenance.

### Short Query Acceleration (SQA)

SQA can prioritize eligible short-running queries so they are not unnecessarily delayed behind longer-running workloads.

### Concurrency scaling

Adds temporary compute capacity for eligible workloads during periods of high concurrency.

Feature availability and eligible query types depend on cluster configuration and current service support.

## 20. Performance optimization

Important optimization areas:

### Table design

- Choose suitable distribution styles.
- Choose suitable sort keys.
- Use AUTO optimization where appropriate.
- Avoid excessive data skew.
- Use appropriate compression.
- Avoid unnecessarily wide rows.

### Query design

- Select only required columns.
- Filter data early.
- Avoid SELECT \* in large production queries.
- Avoid unnecessary joins.
- Use appropriate join conditions.
- Avoid repeated expensive subqueries where reusable structures are appropriate.
- Use materialized views for suitable repeated analytical workloads.

### Data loading

- Use COPY for bulk loads.
- Use multiple reasonably sized input files.
- Prefer efficient columnar formats where suitable.
- Avoid loading huge numbers of tiny files.
- Use appropriate compression.
- Load data in batches.

### Maintenance

- Monitor table statistics.
- Monitor sort state.
- Use ANALYZE when appropriate.
- Understand VACUUM requirements and automatic maintenance.
- Review table optimization recommendations.
- Monitor long-running queries and queue wait time.

### System views and query monitoring

Useful monitoring sources include:

- SYS_QUERY_HISTORY.
- SYS_QUERY_DETAIL.
- SYS_LOAD_HISTORY.
- SYS_LOAD_ERROR_DETAIL.
- SVV_TABLE_INFO.
- SVV_TABLES.
- SVV_COLUMNS.
- STL and STV system tables and views where applicable.
- CloudWatch metrics.

Prefer newer SYS monitoring views for many modern monitoring workflows, while recognizing that older system views remain useful in supported contexts.

## 21. Snapshots and backups

### Automated snapshots

- Created according to configured retention and service behavior.
- Useful for operational recovery.
- Retention settings determine how long automated snapshots are retained.

### Manual snapshots

- Created explicitly.
- Retained until deleted.
- Useful before major changes, upgrades, or migrations.

### Snapshot configuration

Important settings:

- Snapshot identifier.
- Retention period.
- Snapshot schedule.
- KMS encryption key.
- Snapshot copy configuration.

### Cross-Region snapshot copy

- Snapshots are not a substitute for a complete disaster recovery plan.

## 22. Redshift data sharing

Data sharing allows supported Redshift environments to access live data without copying all shared datasets.

Important concepts:

**Producer**

- Owns and shares the data.

**Consumer**

- Receives access to the shared data.

**Datashare**

- Defines the database objects shared.

Benefits:

- Avoid unnecessary data duplication.
- Support separate workload environments.
- Share data across teams.
- Support cross-account and cross-Region scenarios where available.

Example:

- Central data warehouse is the producer.
- Finance analytics is a consumer.
- Marketing analytics is another consumer.

Important:

- Configure datashare permissions carefully.
- Verify supported object types and feature limitations.
- Cross-account and cross-Region sharing have specific requirements.
- Data sharing is not the same as granting unrestricted access to the producer database.

## 23. Streaming ingestion

Redshift supports streaming ingestion from supported streaming sources, including Amazon Kinesis Data Streams and Amazon Managed Streaming for Apache Kafka.

Common architecture:

Application → Kinesis Data Streams → Redshift streaming ingestion → Materialized view → Analytics queries.

Benefits:

- Lower-latency analytics.
- Reduced need for intermediate batch files.
- Continuous ingestion patterns.

Important:

- Configure the required IAM permissions.
- Configure the stream integration and materialized view.
- Monitor ingestion lag and errors.
- Consider duplicate handling and event ordering in downstream logic.
- Validate supported source, Region, and authentication requirements.

## 24. Redshift data pipelines

A typical data warehouse pipeline:

1. Applications generate operational data.
2. Data is collected from databases, APIs, and streams.
3. Raw data lands in S3.
4. Glue or another ETL tool transforms and catalogs the data.
5. COPY loads curated data into Redshift.
6. Redshift organizes data into analytical schemas.
7. BI tools query Redshift.
8. CloudWatch and audit tools monitor the environment.

Example architecture:

- S3: raw and curated storage.
-
- Glue: catalog and transformation.
- Redshift: analytical warehouse.
- QuickSight: dashboards.
- Step Functions: workflow orchestration.
- Lambda: event-driven automation.
- CloudWatch: metrics and alarms.

## 27. Important limits and exceptions

Always check current AWS quotas because limits vary by deployment type, Region, and feature.

Important considerations:

- Serverless and provisioned have different resource models.
- Serverless uses namespaces and workgroups rather than provisioned clusters and nodes.
- Not all node families support every Redshift feature.
- Data sharing has specific node and deployment requirements.
- Spectrum queries have separate data-scanning cost considerations.
- SQL compatibility is based on PostgreSQL but is not identical to PostgreSQL.
- Do not assume all PostgreSQL extensions or features are supported.
- Redshift is optimized for analytics, not general-purpose OLTP.
- Query concurrency and WLM behavior depend on configuration and workload.
- Snapshot restoration and cross-Region copy have encryption and permission requirements.
- COPY and UNLOAD options vary by file format.
- Serverless capacity and storage quotas differ from provisioned limits.
- Database object quotas can apply to namespaces.
- Large data loads should use COPY rather than a large number of individual INSERT statements.
- Public accessibility does not bypass security groups or authentication.
- Enhanced VPC routing does not automatically configure S3 permissions.
- A successful IAM API authorization does not guarantee SQL authorization.
- Materialized views may require refresh and have query-definition restrictions.
- RLS, masking, data sharing, and external catalog permissions have feature-specific restrictions.

## 28. Terraform example – Provisioned Redshift

This is a basic provisioned cluster example. It assumes that the VPC and private subnets already exist.

```hcl
resource "aws_redshift_subnet_group" "warehouse" {
  name       = "analytics-subnet-group"
  subnet_ids = var.private_subnet_ids

  tags = {
    Environment = "production"
  }
}

resource "aws_security_group" "redshift" {
  name        = "redshift-security-group"
  description = "Allow approved application access"
  vpc_id      = var.vpc_id

  ingress {
    description     = "Redshift from application security group"
    from_port       = 5439
    to_port         = 5439
    protocol        = "tcp"
    security_groups = [var.application_security_group_id]
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }

  tags = {
    Environment = "production"
  }
}

resource "aws_redshift_cluster" "warehouse" {
  cluster_identifier = "production-analytics"

  database_name   = "analytics"
  master_username = var.redshift_master_username
  master_password = var.redshift_master_password

  node_type       = "ra3.xlplus"
  number_of_nodes = 2

  cluster_subnet_group_name = aws_redshift_subnet_group.warehouse.name

  vpc_security_group_ids = [
    aws_security_group.redshift.id
  ]

  publicly_accessible = false
  enhanced_vpc_routing = true

  encrypted  = true
  kms_key_id = var.redshift_kms_key_arn

  automated_snapshot_retention_period = 7
  deletion_protection                = true

  skip_final_snapshot       = false
  final_snapshot_identifier = "production-analytics-final"

  tags = {
    Environment = "production"
    Application = "analytics"
  }
}
```

Important Terraform notes:

- Supply `private_subnet_ids`, `vpc_id`, and application security group ID.
- Supply credentials through a secure secret-management process.
- Do not commit passwords to source control or plain Terraform variable files.
- The example uses two RA3 nodes; validate node type, count, Region availability, and pricing before deployment.
- Configure IAM roles for S3, Glue, and other integrations separately.
- Configure Redshift audit logging and CloudWatch monitoring.
- Configure maintenance and backup policies to match your recovery requirements.
- Ensure the KMS key policy permits the required Redshift operations.
- Terraform state may contain sensitive values; protect and encrypt the state backend.
- A final snapshot identifier must be unique when a final snapshot is created.
- Review provider version and resource argument compatibility before applying.
