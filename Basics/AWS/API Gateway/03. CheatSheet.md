# Amazon API Gateway – Complete REST API Reference, Practical Implementation, Terraform and Cost Guide

# SECTION 1 – REST API: Complete Technical Reference

## 1. What is Amazon API Gateway?

Amazon API Gateway is a fully managed AWS service used to create, publish, secure, monitor, and manage APIs.

It acts as an entry point between API clients and backend services.

Typical architecture:

Client → API Gateway → Lambda → DynamoDB

Other possible architectures:

- Client → API Gateway → Application Load Balancer → ECS application
- Client → API Gateway → EC2 application
- Client → API Gateway → HTTP backend
- Client → API Gateway → SQS
- Client → API Gateway → Step Functions
- Client → API Gateway → AWS service integration

API Gateway can handle:

- HTTP request routing.
- Authentication and authorization.
- Request validation.
- Request and response transformation.
- Throttling and quotas.
- Caching.
- CORS.
- API versioning and stages.
- Logging and monitoring.
- Custom domains.
- Private API access.
- Integration with AWS and external services.

API Gateway is an AWS-managed service. You do not deploy the API Gateway service itself into your VPC.

## 2. API Gateway API types

There are three main API types.

### A. REST API

REST API provides extensive API management and configuration capabilities.

Important features:

- Resources and methods.
- Resource policies.
- IAM authorization.
- Cognito user pool authorization.
- Lambda authorizers.
- API keys and usage plans.
- Request validation.
- Request and response mapping templates.
- Gateway responses.
- Caching.
- Private API endpoints.
- Regional and edge-optimized endpoints.
- AWS service integrations.

Use REST API when you need advanced API management features or specific REST API capabilities.

### B. HTTP API

HTTP API is a simpler API Gateway option.

Important features:

- HTTP routes.
- Lambda integrations.
- HTTP proxy integrations.
- JWT authorization.
- IAM authorization.
- CORS.
- Custom domains.
- VPC Link integrations.

It is generally less expensive than REST API for comparable request volume.

Use HTTP API when you need straightforward HTTP routing and authorization without the additional REST API features.

### C. WebSocket API

WebSocket API supports persistent, two-way communication between clients and backend services.

Use cases:

- Chat applications.
- Live notifications.
- Real-time dashboards.
- Multiplayer applications.
- Interactive applications.

Important routes include:

- `$connect`
- `$disconnect`
- `$default`

## 3. REST API architecture and components

Understand these components before creating an API.

### API

The API is the overall API Gateway configuration.

It contains:

- Resources.
- Methods.
- Integrations.
- Authorizers.
- Models.
- Deployments.
- Stages.
- API settings.

### Resource

A resource represents a URL path.

Example:

`/users`

`/orders`

`/products`

A resource can have child resources.

Example:

`/users/{userId}/orders`

Here:

- `/users` is a resource.
- `{userId}` is a path parameter.
- `/orders` is a child resource.

### Method

A method defines the HTTP operation supported by a resource.

Common methods:

- GET
- POST
- PUT
- PATCH
- DELETE
- HEAD
- OPTIONS

Example:

`GET /users`

Retrieves users.

`POST /users`

Creates a user.

`GET /users/{userId}`

Retrieves one user.

### Integration

An integration defines where API Gateway sends the request.

Examples:

- Lambda function.
- HTTP endpoint.
- Private HTTP backend through VPC Link.
- AWS service such as SQS or Step Functions.
- MOCK integration.

### Deployment

A deployment is a snapshot of the API configuration.

Changes to resources, methods, integrations, or authorizers generally need to be deployed before they become active at a stage.

### Stage

A stage is an environment or published version of an API.

Examples:

- dev
- test
- staging
- prod

A stage has its own settings, such as:

- Logging.
- Metrics.
- Throttling.
- Caching.
- Variables.
- Deployment association.

### API endpoint

The API endpoint is the URL clients use to call the API.

Example:

`https://abc123.execute-api.eu-west-1.amazonaws.com/prod`

The endpoint contains:

- API identifier.
- AWS Region.
- API Gateway domain.
- Stage path.

Custom domains can replace the default endpoint.

## 4. REST API endpoint types

REST APIs support three endpoint types.

### Regional

The API endpoint is served from the selected AWS Region.

Useful for:

- Applications primarily used in one Region.
- Applications using CloudFront separately.
- Regional API deployments.

### Edge-optimized

API Gateway uses an AWS-managed CloudFront distribution to improve access for geographically distributed clients.

Useful for:

- Public APIs accessed globally.
- Clients distributed across different geographic locations.

The CloudFront distribution is managed by API Gateway.

### Private

A private REST API is accessible through an interface VPC endpoint for API Gateway.

It is intended for private access from a VPC.

Typical architecture:

Application in private subnet → execute-api interface endpoint → Private REST API

Important:

- Private REST API is not the same as a public API with a VPC Link.
- Private API access requires appropriate endpoint configuration, resource policy, DNS, and authorization.
- The interface endpoint has its own networking and cost considerations.

## 6. REST API integration types

The integration type determines how API Gateway invokes the backend.

### A. Lambda integration

API Gateway invokes a Lambda function.

Common configuration:

- Integration type: AWS_PROXY or AWS.
- Lambda function ARN.
- Integration HTTP method: POST.
- Credentials role, where required.
- Payload format and integration settings as applicable.

With Lambda proxy integration:

- API Gateway passes request information to Lambda.
- Lambda receives headers, path parameters, query parameters, body, and request context.
- Lambda returns status code, headers, and response body.

Example Lambda response:

```json
{
  "statusCode": 200,
  "headers": {
    "Content-Type": "application/json"
  },
  "body": "{\"message\":\"Order retrieved\"}"
}
```

The body is normally a string in the Lambda proxy response format.

Important:

- Lambda must have permission for API Gateway to invoke it.
- The Lambda resource-based policy commonly grants `lambda:InvokeFunction` to `apigateway.amazonaws.com`.
- Restrict the permission using the API execution ARN where possible.

### B. HTTP integration

API Gateway forwards requests to an HTTP endpoint.

Example:

API Gateway → `https://backend.example.com/orders`

Important settings:

- Integration type.
- HTTP method.
- Backend URL.
- Connection settings.
- Request mapping.
- Response mapping.
- TLS and certificate behavior.

Useful when the backend is an external HTTP service.

### C. HTTP proxy integration

API Gateway forwards requests and responses with limited transformation.

Useful when:

- You want to expose an existing HTTP backend.
- You do not need extensive request transformation.
- The backend already understands the API contract.

### D. AWS service integration

API Gateway directly invokes supported AWS services.

Examples:

- SQS.
- SNS.
- Step Functions.
- Other supported AWS service APIs.

Example:

Client → API Gateway → SQS SendMessage

This can avoid creating a Lambda function for a simple supported AWS service operation.

Important:

- Configure the appropriate IAM execution role.
- Map the incoming request into the AWS service request format.
- Configure integration and method responses correctly.
- Validate service-specific permissions and request formats.

### E. MOCK integration

A MOCK integration returns a configured response without invoking a backend.

Useful for:

- Testing.
- API development.
- OPTIONS preflight responses.
- Simulated responses.

A Lambda proxy event can contain:

- `resource`
- `path`
- `httpMethod`
- `headers`
- `multiValueHeaders`
- `queryStringParameters`
- `multiValueQueryStringParameters`
- `pathParameters`
- `stageVariables`

## 8. REST API authorization options

Authorization determines whether a caller can invoke an API method.

### A. NONE

No API Gateway authorization is required.

Use only when the endpoint is intentionally public.

Backend validation and application security are still required.

### B. AWS IAM authorization

The caller signs requests using AWS Signature Version 4.

Common use cases:

- Internal AWS applications.
- Applications using IAM roles.
- Service-to-service access.

Important:

- The caller needs `execute-api:Invoke`.
- The API method must use AWS_IAM authorization.
- Requests must be correctly signed.
- Cross-account access requires suitable IAM and resource policy configuration.

### C. Cognito user pool authorizer

Uses Amazon Cognito user pool tokens.

Common use cases:

- User authentication.
- Mobile applications.
- Web applications.
- User identity-based API access.

Important:

- Configure the Cognito user pool.
- Configure the authorizer.
- Select the required token source.
- Configure authorization scopes where applicable.
- Ensure token issuer, audience, and expiry are valid.

### D. Lambda authorizer

A Lambda function evaluates a caller's identity and returns an authorization policy.

Two main types:

**TOKEN authorizer**

- Uses a single identity token source, commonly an Authorization header.
- Lambda evaluates the token.

**REQUEST authorizer**

- Can use multiple identity sources.
- Can evaluate headers, query strings, stage variables, and supported request context values.

Important configuration:

- Authorizer name.
- Authorizer type.
- Lambda function ARN.
- Identity source.
- Token validation expression where applicable.
- Authorizer credentials role if configured.
- Authorizer result TTL.
- Identity validation and policy logic.

Lambda authorizer responses commonly include:

- Principal ID.
- IAM policy document.
- Context values.
- Usage identifier key where applicable.

Important:

- Authorizer caching can reuse authorization decisions.
- Make cache keys sufficiently specific.
- A cached authorization response can cause incorrect access decisions if identity sources are not designed carefully.
- Return least-privilege policies.

### E. Resource policy

A resource policy controls which principals or networks can invoke the API.

Can restrict access based on:

- AWS account.
- IAM principal.
- Organization.
- VPC endpoint.
- Source IP.
- Other supported condition keys.

Useful for private APIs and cross-account access.

A resource policy does not replace method authorization.

## 9. API keys and usage plans

API keys identify clients or applications for usage tracking and throttling.

A usage plan can define:

- API stages.
- API key associations.
- Throttling rate.
- Throttling burst.
- Quota limit.
- Quota period.

### API key

Important configuration:

- Key name.
- Key value.
- Enabled status.
- Tags.
- Usage plan association.

### Usage plan throttling

**Rate limit**

The average request rate.

**Burst limit**

The temporary request burst capacity.

### Usage quota

Can define a request quota over:

- DAY
- WEEK
- MONTH

Important security warning:

API keys are not authentication credentials.

Do not use API keys as the only protection for sensitive APIs.

Use IAM, Cognito, Lambda authorizers, or another suitable authentication mechanism.

Usage-plan throttles and quotas are best-effort controls, not guaranteed hard limits or billing protections.

## 10. Request validation

REST API supports request validation.

You can validate:

- Required path parameters.
- Required query parameters.
- Required headers.
- Request body against a configured model.

### Request validator types

- Validate body.
- Validate parameters.
- Validate body and parameters.

### Models

A model defines the expected JSON request structure.

Example:

```json
{
  "type": "object",
  "required": ["customerId", "amount"],
  "properties": {
    "customerId": {
      "type": "string"
    },
    "amount": {
      "type": "number",
      "minimum": 0
    }
  }
}
```

Important:

- Models are commonly based on JSON Schema draft 4 compatibility.
- Model validation is not a replacement for backend business validation.
- API Gateway validation does not automatically validate every possible business rule.

## 11. Request and response mapping

REST API supports request and response transformations.

### Mapping templates

Velocity Template Language (VTL) is used for mapping templates in supported REST API integrations.

Common objects include:

- `$input`
- `$context`
- `$stageVariables`
- `$util`

Common functions include:

- `$input.body`
- `$input.json('$')`
- `$input.path('$')`
- `$util.escapeJavaScript()`
- `$util.urlEncode()`
- `$util.base64Encode()`
- `$util.parseJson()`

### Request mapping

Transforms the client request before sending it to the backend.

Example:

Client request:

```json
{
  "orderId": "1001"
}
```

Backend request can be transformed to a different structure.

### Response mapping

Transforms backend responses before returning them to the client.

You can configure:

- Status code.
- Response headers.
- Response body.
- Header mapping.
- Body mapping templates.

Important:

Lambda proxy integration generally passes the Lambda response through rather than using the traditional integration-response mapping workflow.

## 12. Method responses and integration responses

These are separate concepts.

### Method response

Defines the response structure exposed by the API method.

Example:

- HTTP 200.
- HTTP 400.
- HTTP 500.

Can define:

- Status code.
- Response headers.
- Response models.

### Integration response

Defines how the backend response maps to the API method response.

Important settings:

- Status code mapping.
- Selection pattern.
- Response parameters.
- Response templates.

For non-proxy integrations, method responses and integration responses must be configured consistently.

## 13. CORS configuration

CORS controls whether browser applications hosted on one origin can call an API hosted on another origin.

Important response headers:

- `Access-Control-Allow-Origin`
- `Access-Control-Allow-Methods`
- `Access-Control-Allow-Headers`
- `Access-Control-Allow-Credentials`
- `Access-Control-Expose-Headers`
- `Access-Control-Max-Age`

### OPTIONS method

Browsers may send an OPTIONS preflight request before the actual request.

Configure OPTIONS behavior to return the appropriate CORS headers.

Important:

- Configure CORS for successful responses.
- Configure CORS for relevant error responses.
- If credentials are allowed, do not use wildcard `*` for allowed origin.
- Ensure actual backend responses contain the required CORS headers.
- Lambda proxy integration often requires the Lambda function to return CORS headers.

## 14. Stages and deployments

A stage represents a deployed environment.

Example:

- dev
- test
- staging
- prod

### Deployment

A deployment publishes an API configuration snapshot.

### Stage configuration

Important settings:

- Stage name.
- Deployment ID.
- Description.
- Stage variables.
- Cache configuration.
- Logging.
- Metrics.
- Tracing settings.
- Throttling.
- Canary settings.
- Client certificate configuration where supported.

### Stage variables

Stage variables are named values available to API Gateway mapping and integration configuration.

## 15. Caching

REST API supports API Gateway stage caching.

Important settings:

- Cache enabled.
- Cache cluster size.
- Cache TTL.
- Cache encryption.
- Cache key parameters.
- Cache namespace.
- Method-level caching.

### Cache key parameters

Can include selected:

- Path parameters.
- Query parameters.
- Headers.

Only include parameters that genuinely affect the backend response.

Important:

- Cache can reduce backend load.
- Incorrect cache keys can return one user's data to another user.
- Do not cache sensitive responses unless isolation and authorization behavior are thoroughly designed.
- Cache capacity is billed while enabled, even if traffic is low.
- Cache invalidation and flushing can affect performance and cost.

## 16. Throttling and quotas

REST API supports throttling at several levels:

- Account and Region.
- API stage.
- Method.
- Usage plan.
- Client API key.

Important concepts:

**Rate**

Average requests per second.

**Burst**

Temporary request capacity.

**Quota**

Request count over a configured period.

When throttled, clients can receive HTTP 429.

Important:

- Limits are subject to AWS account quotas.
- API Gateway throttling is generally best-effort.
- Backend services need their own protection.
- Use retries with exponential backoff and jitter.
- Do not assume usage-plan quotas guarantee a maximum bill.

## 17. Timeouts and payload limits

Important operational settings include:

- Integration timeout.
- Request payload size.
- Response payload size.
- Connection and backend timeout behavior.

REST API integration timeout is commonly up to 29 seconds by default, with higher limits available for eligible Regional and private REST APIs through quota adjustment. Increasing the timeout can require trade-offs with account-level throttling capacity.

The standard API Gateway payload limit is 10 MB for supported REST API requests and responses.

Important:

- API Gateway is not intended for very large file transfers.
- Use S3 presigned URLs for large file uploads and downloads.
- A synchronous API request is not suitable for long-running jobs.
- For long-running workflows, return a job identifier and process asynchronously.

## 19. Custom domains and TLS

A custom domain provides a stable, human-readable API address.

Example:

`api.example.com`

Important configuration:

- Custom domain name.
- ACM certificate.
- Regional or edge-optimized endpoint configuration.
- DNS record.
- API mapping.
- Base path mapping.
- Security policy.
- Mutual TLS where supported.

### ACM certificate

Use AWS Certificate Manager to manage the TLS certificate.

For Regional custom domains, the certificate must be in the same Region as the API.

For edge-optimized custom domains, the certificate must be in `us-east-1`.

### DNS

Use Route 53 or another DNS provider.

Configure the appropriate alias or CNAME record according to endpoint type.

### Mutual TLS

Mutual TLS allows the API to validate client certificates.

It is useful for APIs requiring certificate-based client authentication.

## 20. REST API private networking and VPC Link

These are frequently confused.

### Private REST API

A private REST API is reached through an API Gateway interface VPC endpoint.

Architecture:

Private application → execute-api interface endpoint → Private REST API

### VPC Link

VPC Link allows API Gateway to connect to private backend resources.

For REST API, VPC Link integrations support private integrations with supported Network Load Balancers.

For newer VPC Link V2 integrations, supported private integrations can include Application Load Balancers, Network Load Balancers, and Cloud Map depending on API type and configuration.

Check the current API type and integration compatibility before designing the connection.

### Important distinction

Public API + VPC Link:

Client → Public API Gateway endpoint → VPC Link → Private backend

Private API:

Private client → Interface VPC endpoint → Private API Gateway endpoint

A VPC Link does not make the public API endpoint private.

### Networking configuration

For a private backend integration, consider:

- VPC.
- Subnets.
- Load balancer.
- Target groups.
- Security groups.
- Listener.
- Backend port.
- Health checks.
- VPC Link configuration.
- API integration URI.
- Backend TLS configuration where applicable.

## 21. IAM and permissions

API Gateway requires appropriate permissions to invoke backends.

### Lambda integration

Use a Lambda resource-based policy to allow API Gateway invocation.

Example:

```bash
aws lambda add-permission \
  --function-name orders-function \
  --statement-id AllowApiGateway \
  --action lambda:InvokeFunction \
  --principal apigateway.amazonaws.com \
  --source-arn "arn:aws:execute-api:eu-west-1:123456789012:API_ID/*/GET/orders"
```

### AWS service integration

API Gateway can assume an IAM role to call supported AWS services.

Configure:

- IAM role.
- Trust relationship allowing API Gateway to assume the role.
- Required service actions.
- Resource restrictions.
- Integration credentials ARN.

### API invocation permission

For IAM-authenticated API callers, the caller requires `execute-api:Invoke`.

## 24. API Gateway integrations with other AWS services

Common architecture patterns:

### API Gateway + Lambda

Best for serverless application APIs.

### API Gateway + SQS

Best for asynchronous request processing.

Example:

Client → API Gateway → SQS → Worker Lambda

### API Gateway + Step Functions

Best for starting long-running business workflows.

Example:

Client → API Gateway → Step Functions → Lambda → DynamoDB

### API Gateway + SNS

Best for publishing notifications or events.

### API Gateway + ALB/NLB

Best for exposing private application services through supported VPC Link configurations.

## 25. API Gateway limits and exceptions

Always verify the current AWS Service Quotas and API type-specific documentation.

Important considerations:

- REST API, HTTP API, and WebSocket API have different capabilities and quotas.
- REST API has more advanced API management features.
- HTTP API supports JWT authorizers, while REST API uses its own authorization options.
- REST API request validation and mapping features differ from HTTP API.
- API Gateway payload limits make it unsuitable for large file transfers.
- Integration timeout limits can affect synchronous architecture.
- Usage-plan quotas and throttles are best-effort.
- Lambda concurrency can limit backend throughput.
- Account-level API Gateway throttling is shared across applicable APIs in a Region.
- API Gateway and backend throttling need to be designed together.
- Private APIs require correct interface endpoint and resource policy configuration.
- VPC Link supports specific integration types and load balancer configurations.
- API deployments must be updated after configuration changes.
- CORS must be handled for both normal and error responses.
- Caching must use appropriate cache keys to avoid data leakage.
- API keys are not authentication.
- CloudWatch logs can create significant cost at high request volume.
- Custom domain certificate Region requirements differ by endpoint type.

# SECTION 2 – REST API: Practical Production Implementation

## 26. Example application architecture

Build an Orders API.

Requirements:

- Users can create orders.
- Users can retrieve orders.
- Users can update orders.
- Users can delete orders.
- API requests are authenticated.
- Lambda handles application logic.
- DynamoDB stores order records.
- CloudWatch records API and Lambda activity.

Architecture:

Client → API Gateway REST API → Lambda → DynamoDB

For a production system, add:

- Cognito or another suitable authentication system.
- API Gateway throttling.
- Lambda concurrency controls.
- DynamoDB encryption.
- IAM least privilege.
- CloudWatch alarms.
- AWS WAF where appropriate.
- Deployment stages.
- Custom domain.

## 27. Step 1 – Create the REST API

In the AWS Console:

1. Open API Gateway.
2. Select Create API.
3. Select REST API.
4. Select Build.
5. Enter API name, such as `orders-api`.
6. Select Regional endpoint unless another endpoint type is required.
7. Create the API.

Important configuration:

- API name: `orders-api`.
- Endpoint type: Regional.
- Protocol: REST.
- API description: optional documentation.
- Tags: environment, application, owner, cost center.

Use Regional as a common starting point for a Regional application. Consider edge-optimized when the managed CloudFront distribution is appropriate for your use case.

## 28. Step 2 – Create API resources

Create these resources:

```text
/
└── orders
    └── {orderId}
```

Methods:

| Resource | Method | Purpose |
|---|---|---|
| `/orders` | GET | List orders |
| `/orders` | POST | Create order |
| `/orders/{orderId}` | GET | Retrieve one order |
| `/orders/{orderId}` | PUT | Replace/update an order |
| `/orders/{orderId}` | PATCH | Partially update an order |
| `/orders/{orderId}` | DELETE | Delete an order |

Do not create methods that your application does not need.

## 29. Step 3 – Create the Lambda backend

Create a Lambda function named:

`orders-function`

Runtime:

Choose a currently supported runtime that matches your application language.

Example Python handler:

```python
import json

def lambda_handler(event, context):
    method = event.get("httpMethod")
    path_params = event.get("pathParameters") or {}
    query_params = event.get("queryStringParameters") or {}
    body = event.get("body")

    if method == "GET":
        order_id = path_params.get("orderId")

        if order_id:
            result = {
                "orderId": order_id,
                "status": "PROCESSING"
            }
        else:
            result = {
                "orders": []
            }

        return {
            "statusCode": 200,
            "headers": {
                "Content-Type": "application/json"
            },
            "body": json.dumps(result)
        }

    if method == "POST":
        try:
            request_body = json.loads(body or "{}")
        except json.JSONDecodeError:
            return {
                "statusCode": 400,
                "headers": {
                    "Content-Type": "application/json"
                },
                "body": json.dumps({"message": "Invalid JSON"})
            }

        return {
            "statusCode": 201,
            "headers": {
                "Content-Type": "application/json"
            },
            "body": json.dumps({
                "message": "Order created",
                "order": request_body
            })
        }

    return {
        "statusCode": 405,
        "headers": {
            "Content-Type": "application/json"
        },
        "body": json.dumps({"message": "Method not allowed"})
    }
```

This is a demonstration handler. It does not persist orders.

For a real application:

- Validate the input.
- Authenticate the user.
- Authorize access to the specific order.
- Store data in DynamoDB or another database.
- Use structured logging.
- Handle exceptions safely.
- Implement idempotency for operations that may be retried.
- Return consistent error responses.

## 30. Step 4 – Connect API Gateway to Lambda

For each method:

1. Select the resource.
2. Select the HTTP method.
3. Choose Lambda integration.
4. Enable Lambda proxy integration.
5. Select the Lambda Region.
6. Select the Lambda function.
7. Save the integration.
8. Allow API Gateway to invoke Lambda.

## 31. Step 5 – Configure authentication

For a public user-facing application, Cognito user pool authorization is a common option.

Typical flow:

1. User signs in to the application.
2. Cognito authenticates the user.
3. Cognito issues tokens.
4. Client sends the access token in the Authorization header.
5. API Gateway validates the token using the configured authorizer.
6. API Gateway invokes Lambda if authorized.
7. Lambda applies application-level authorization.

Example header:

```http
Authorization: Bearer ACCESS_TOKEN
```

Important:

Authentication answers: who is the caller?

Authorization answers: what is the caller allowed to do?

Even if API Gateway validates a token, Lambda must still enforce object-level permissions.

For example, a user must not be able to retrieve another customer's order simply by changing `orderId`.

- Required customer ID.
- Valid amount.
- Supported currency.
- Expected JSON structure.

Enable the suitable request validator on the method.

Also validate business rules in Lambda.

Examples of business rules:

- Customer exists.
- Customer is active.
- Order amount is within permitted limits.
- User is permitted to create an order.

## 39. Practical production request flow

A normal request might work like this:

1. Client sends `POST /orders`.
2. API Gateway receives the request.
3. API Gateway evaluates the resource and method.
4. API Gateway checks authorization.
5. API Gateway performs configured request validation.
6. API Gateway invokes Lambda.
7. Lambda validates business rules.
8. Lambda writes the order to DynamoDB.
9. Lambda returns a response.
10. API Gateway returns the HTTP response to the client.
11. CloudWatch receives configured logs and metrics.

Important:

API Gateway does not automatically make the backend secure. Lambda must have appropriate IAM permissions, and the application must enforce its own business authorization.

## 40. When to use asynchronous processing

Do not make a client wait for a long-running task.

For example, generating a large report may take several minutes.

Better architecture:

Client → API Gateway → Lambda → SQS → Worker Lambda → S3

The initial API returns:

```json
{
  "jobId": "JOB-1001",
  "status": "ACCEPTED"
}
```

The client can later call:

`GET /jobs/{jobId}`

This architecture:

- Reduces synchronous timeout risk.
- Separates request acceptance from processing.
- Allows retries.
- Supports independent worker scaling.
- Improves resilience.

For complex workflows, use Step Functions.

## 41. Terraform example – API Gateway REST API with Lambda

This example creates:

- Regional REST API.
- `/orders` resource.
- GET method.
- Lambda proxy integration.
- Lambda invocation permission.
- Deployment.
- Production stage.
- Access logging.
- Stage throttling.
- CloudWatch log group.

It assumes that the Lambda function already exists.

### Terraform code

```hcl
variable "region" {
  type    = string
  default = "eu-west-1"
}

variable "lambda_function_name" {
  type = string
}

variable "lambda_function_invoke_arn" {
  type = string
}

variable "lambda_function_arn" {
  type = string
}

variable "api_name" {
  type    = string
  default = "orders-api"
}

variable "stage_name" {
  type    = string
  default = "prod"
}

provider "aws" {
  region = var.region
}

resource "aws_api_gateway_rest_api" "orders" {
  name        = var.api_name
  description = "Orders REST API"

  endpoint_configuration {
    types = ["REGIONAL"]
  }

  tags = {
    Environment = "production"
    Application = "orders"
  }
}

resource "aws_api_gateway_resource" "orders" {
  rest_api_id = aws_api_gateway_rest_api.orders.id
  parent_id   = aws_api_gateway_rest_api.orders.root_resource_id
  path_part   = "orders"
}

resource "aws_api_gateway_method" "get_orders" {
  rest_api_id   = aws_api_gateway_rest_api.orders.id
  resource_id   = aws_api_gateway_resource.orders.id
  http_method   = "GET"
  authorization = "NONE"
}

resource "aws_api_gateway_integration" "get_orders" {
  rest_api_id             = aws_api_gateway_rest_api.orders.id
  resource_id             = aws_api_gateway_resource.orders.id
  http_method             = aws_api_gateway_method.get_orders.http_method
  integration_http_method = "POST"

  type = "AWS_PROXY"

  uri = var.lambda_function_invoke_arn
}

resource "aws_lambda_permission" "allow_api_gateway" {
  statement_id  = "AllowOrdersApiGateway"
  action        = "lambda:InvokeFunction"
  function_name = var.lambda_function_name
  principal     = "apigateway.amazonaws.com"

  source_arn = "${aws_api_gateway_rest_api.orders.execution_arn}/*/GET/orders"
}

resource "aws_cloudwatch_log_group" "api_access" {
  name              = "/aws/apigateway/${var.api_name}"
  retention_in_days = 30
}

resource "aws_api_gateway_account" "account" {
  cloudwatch_role_arn = aws_iam_role.api_gateway_cloudwatch.arn
}

resource "aws_iam_role" "api_gateway_cloudwatch" {
  name = "${var.api_name}-cloudwatch-role"

  assume_role_policy = jsonencode({
    Version = "2012-10-17"

    Statement = [{
      Effect = "Allow"

      Principal = {
        Service = "apigateway.amazonaws.com"
      }

      Action = "sts:AssumeRole"
    }]
  })
}

resource "aws_iam_role_policy_attachment" "api_gateway_logs" {
  role       = aws_iam_role.api_gateway_cloudwatch.name
  policy_arn = "arn:aws:iam::aws:policy/service-role/AmazonAPIGatewayPushToCloudWatchLogs"
}

resource "aws_api_gateway_deployment" "orders" {
  rest_api_id = aws_api_gateway_rest_api.orders.id

  triggers = {
    redeployment = sha1(jsonencode([
      aws_api_gateway_resource.orders.id,
      aws_api_gateway_method.get_orders.id,
      aws_api_gateway_integration.get_orders.id
    ]))
  }

  lifecycle {
    create_before_destroy = true
  }

  depends_on = [
    aws_api_gateway_integration.get_orders
  ]
}

resource "aws_api_gateway_stage" "prod" {
  rest_api_id   = aws_api_gateway_rest_api.orders.id
  deployment_id = aws_api_gateway_deployment.orders.id
  stage_name    = var.stage_name

  access_log_settings {
    destination_arn = aws_cloudwatch_log_group.api_access.arn

    format = jsonencode({
      requestId          = "$context.requestId"
      sourceIp           = "$context.identity.sourceIp"
      httpMethod         = "$context.httpMethod"
      resourcePath       = "$context.resourcePath"
      status             = "$context.status"
      responseLength     = "$context.responseLength"
      integrationLatency = "$context.integrationLatency"
      responseLatency    = "$context.responseLatency"
    })
  }

  tags = {
    Environment = "production"
  }
}

resource "aws_api_gateway_method_settings" "all" {
  rest_api_id = aws_api_gateway_rest_api.orders.id
  stage_name  = aws_api_gateway_stage.prod.stage_name
  method_path = "*/*"

  settings {
    metrics_enabled    = true
    logging_level      = "INFO"
    data_trace_enabled = false

    throttling_rate_limit  = 100
    throttling_burst_limit = 200
  }
}

output "api_invoke_url" {
  value = "https://${aws_api_gateway_rest_api.orders.id}.execute-api.${var.region}.amazonaws.com/${aws_api_gateway_stage.prod.stage_name}/orders"
}
```

### Important Terraform notes

This is a minimal working starting point, not a complete secure production API.

The method uses `authorization = "NONE"` to keep the example straightforward.

For production:

- Configure Cognito or a suitable Lambda authorizer.
- Configure an API resource policy if access must be restricted.
- Configure WAF where appropriate.
- Add request validation.
- Add CORS if browser clients require it.
- Add custom domain and ACM certificate.
- Add alarms and dashboards.
- Add suitable API deployment and release controls.
- Add other HTTP methods and resources.
- Add Lambda concurrency and error handling.
- Restrict the Lambda execution role to only required backend resources.
- Review CloudWatch log retention and sensitive data handling.

The `aws_api_gateway_account` resource is account-and-Region scoped. Manage it carefully if multiple Terraform stacks use API Gateway in the same account and Region.

The CloudWatch role must be configured before API Gateway can publish execution logs. Access logging and execution logging are separate configurations.

For large APIs, use deployment triggers that include all relevant resources, methods, integrations, authorizers, models, and method responses. Otherwise, a change might not create a new deployment.

## 43. API Gateway REST API pricing

API Gateway pricing is based on several components.

The most important distinction is between:

- API request charges.
- Cache charges.
- Data transfer.
- Logging and monitoring.
- WAF.
- Backend service charges.
- Networking charges for private connectivity.

Do not calculate API Gateway cost alone and assume that it represents the full application cost.

## 44. REST API request pricing

REST API requests are generally charged per million API calls, with pricing dependent on endpoint type and AWS Region.

For illustration, a commonly published Regional/REST API request rate in some Regions has been approximately:

- First 333 million requests per month: $3.50 per million requests.
- Next 667 million requests: $2.80 per million requests.
- Above 1 billion requests: $2.38 per million requests.

These are illustrative historical reference rates, not a guaranteed November 2026 quote. Confirm the live price for your Region, endpoint type, and pricing tier using the AWS pricing page before budgeting.

### Request cost formula

`Request cost = Number of requests / 1,000,000 × Price per million requests`

Example at $3.50 per million:

| Monthly requests | Approximate request charge |
|---:|---:|
| 100,000 | $0.35 |
| 1 million | $3.50 |
| 10 million | $35 |
| 50 million | $175 |
| 100 million | $350 |

The example excludes cache, data transfer, logging, backend, and other costs.

## 45. REST API endpoint type and cost

Endpoint type affects pricing and architecture.

### Regional REST API

- Regional API request pricing.
- Suitable for Regional API access.
- CloudFront can be added separately if required.

### Edge-optimized REST API

- Uses an API Gateway-managed CloudFront distribution.
- Pricing differs from Regional endpoint pricing.
- Consider the global distribution benefits and cost.

### Private REST API

- API Gateway request pricing applies.
- Interface VPC endpoint charges apply separately.
- Data processing and data transfer charges can also apply.
- Private connectivity may introduce additional network costs.

For private APIs, include the hourly and data-processing cost of the interface VPC endpoint in the total estimate.

## 46. API Gateway cache pricing

REST API caching is billed based on the selected cache capacity and the time it is enabled.

Important:

- Cache capacity varies by configured cache size.
- Larger cache capacity costs more.
- Cache is billed while enabled, including periods of low traffic.
- Cache is billed separately from API requests.
- Cache encryption and other configuration choices can affect the available options and operational behavior.

Example cost model:

`Monthly cache cost = Cache hourly rate × Hours enabled`

Use the current regional API Gateway pricing table for the selected cache size.

Enable caching only where it provides measurable backend-load or latency benefits.

## 47. Data transfer charges

Data transfer can add cost.

Potential sources:

- API responses transferred to clients.
- Regional data transfer.
- Cross-AZ backend communication.
- Cross-Region communication.
- PrivateLink data processing.
- NAT Gateway traffic if your backend uses NAT for outbound connectivity.
- CloudFront transfer if used.

Important:

- Data transfer pricing depends on source, destination, Region, and service.
- AWS data transfer allowances and exceptions may apply.
- Do not assume all traffic within AWS is free.
- Large response payloads can materially increase data transfer cost.

Reduce unnecessary response payload size and avoid transferring large files through API Gateway.

## 48. Logging and monitoring costs

API Gateway logging can create significant costs at scale.

Potential costs:

### CloudWatch Logs

Charged for:

- Log ingestion.
- Storage.
- Retention beyond applicable allowances.
- Log queries using Logs Insights.

### CloudWatch metrics

Detailed metrics can create additional custom or detailed monitoring charges according to the applicable pricing model.

### CloudWatch alarms

Alarms can have separate charges depending on alarm type and quantity.

### X-Ray

Tracing can have separate charges based on recorded and retrieved trace data.

Cost optimization:

- Use access logs with only useful fields.
- Avoid unnecessary full request/response tracing.
- Do not log sensitive payloads.
- Set log retention.
- Enable detailed metrics only where operationally useful.
- Sample tracing where supported and appropriate.

## 49. WAF costs

If AWS WAF is associated with API Gateway, additional charges may include:

- Web ACL monthly charges.
- Rule charges.
- Managed rule group charges.
- Request inspection charges.

WAF is billed separately from API Gateway.

Use only the rule groups and controls required for your risk profile.

## 50. Private API and VPC endpoint costs

A private REST API typically requires an interface VPC endpoint for the `execute-api` service.

Potential costs:

- Endpoint hourly charges.
- Data processing charges.
- Cross-AZ traffic where applicable.
- Related network transfer charges.

A public Regional API does not require an execute-api interface endpoint merely to be called over the public internet.

Do not add interface endpoints without a clear private-connectivity requirement.

## 51. Backend costs

API Gateway invokes or forwards requests to other services. Those services have their own pricing.

### Lambda

Possible charges:

- Number of invocations.
- Execution duration.
- Allocated memory.
- Provisioned concurrency, if enabled.
- Other applicable features.

### DynamoDB

Possible charges:

- Read capacity or on-demand reads.
- Write capacity or on-demand writes.
- Storage.
- Backups.
- Streams.
- Data transfer and other features.

### SQS

Possible charges:

- API requests.
- Payload size and request units.
- FIFO-specific request behavior.
- Data transfer where applicable.

### Step Functions

Possible charges depend on workflow type:

- Standard state transitions.
- Express requests and duration.

### ALB or NLB

Possible charges can include:

- Load balancer hours.
- Capacity or processed data units.
- Data transfer.
- Related networking resources.

The total cost of an API-backed application is the combined cost of API Gateway and its backend.

## 52. Example monthly cost calculation

Assume:

- Regional REST API.
- 10 million API requests per month.

- No API Gateway cache.
- No WAF.
- No private interface endpoint.

API Gateway request cost:

`10,000,000 / 1,000,000 × $3.50 = $35`

- CloudWatch Logs.
- CloudWatch metrics.

`100,000,000 / 1,000,000 × $3.50 = $350`

## 53. REST API cost optimization

Use these practices:

1. Choose HTTP API instead of REST API if the advanced REST features are not needed.
2. Choose Regional endpoints when global edge optimization is unnecessary.
3. Avoid unnecessary API calls.
4. Use pagination for large result sets.
5. Reduce response payload size.
6. Use caching for safe, frequently requested responses.
7. Avoid cache for user-specific data unless cache isolation is correct.
8. Set sensible Lambda timeouts and memory.
9. Optimize database queries.
10. Use asynchronous processing for long-running operations.
11. Set CloudWatch log retention.
12. Avoid excessive data tracing.
13. Monitor 4XX and 5XX errors.
14. Monitor throttling and integration latency.
15. Avoid unnecessary private VPC endpoints.
16. Review data transfer and NAT Gateway usage.
17. Use usage plans for client management, but not as a guaranteed billing cap.
18. Set backend concurrency limits to prevent uncontrolled scaling.

## 54. REST API vs HTTP API: final decision

| Requirement | Better starting choice |
|---|---|
| Basic Lambda-backed API | HTTP API |
| Low-cost HTTP routing | HTTP API |
| JWT authorizer | HTTP API |
| API keys and usage plans | REST API |
| Request validation models | REST API |
| Advanced request/response mapping | REST API |
| Private API endpoint | REST API |
| REST API resource policies | REST API |
| API Gateway stage caching | REST API |
| Extensive API management | REST API |
| WebSocket communication | WebSocket API |

Always verify feature compatibility against current service documentation before choosing.

## 57. Final decision summary

- **REST API:** Choose when you need advanced API Gateway capabilities such as API keys, usage plans, private endpoints, request validation, caching, or detailed mapping.
- **HTTP API:** Choose for simpler, lower-cost HTTP APIs with supported authorization and routing requirements.
- **WebSocket API:** Choose for persistent, bidirectional client communication.
- **Lambda integration:** Choose for serverless application logic.
- **VPC Link:** Choose when API Gateway needs to reach supported private backend resources.
- **Private REST API:** Choose when the API itself must be accessible privately through a VPC interface endpoint.
- **SQS integration:** Choose for asynchronous request processing.
- **Step Functions integration:** Choose for multi-step business workflows.
- **S3 presigned URLs:** Choose for large file uploads and downloads instead of sending large files through API Gateway.

**Core takeaway:** API Gateway is the managed API entry point, not the application backend. It handles routing, authorization, validation, throttling, and API operations, while Lambda, containers, databases, and other services perform the actual business processing. In production, design the API, backend permissions, network path, timeouts, observability, and total application cost together.
