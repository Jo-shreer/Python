# DynamoDB Production Parameters — Terraform & AWS Reference

## 1. Table Configuration

| Parameter | Explanation | Example |
|---|---|---|
| `name` | Table name | `"orders-prod"` |
| `billing_mode` | Capacity mode | `"PAY_PER_REQUEST"` or `"PROVISIONED"` |
| `hash_key` | Table partition key | `"PK"` |
| `range_key` | Optional table sort key | `"SK"` |
| `table_class` | Storage pricing class | `"STANDARD"` or `"STANDARD_INFREQUENT_ACCESS"` |
| `read_capacity` | Provisioned read capacity units (RCUs) | `100` |
| `write_capacity` | Provisioned write capacity units (WCUs) | `50` |
| `deletion_protection_enabled` | Protects against supported table-delete operations | `true` |
| `stream_enabled` | Enables DynamoDB Streams | `true` |
| `stream_view_type` | Data captured in stream records | `"NEW_AND_OLD_IMAGES"` |
| `tags` | Ownership and cost-allocation metadata | `Environment = "prod"` |

Notes:
- `read_capacity` and `write_capacity` apply to provisioned mode.
- On-demand mode manages capacity without provisioned RCU/WCU configuration.
- `region` is normally configured on the AWS provider, not the table resource.

## 2. Key Attribute Definitions

| Parameter | Explanation | Example |
|---|---|---|
| `attribute.name` | Name of a key attribute | `"PK"` |
| `attribute.type` | Key attribute type | `"S"`, `"N"`, `"B"` |
| `hash_key` | Table partition key | `"PK"` |
| `range_key` | Optional table sort key | `"SK"` |

Types:
- `S` = String
- `N` = Number
- `B` = Binary

Terraform example:

```hcl
hash_key  = "PK"
range_key = "SK"

attribute {
  name = "PK"
  type = "S"
}

attribute {
  name = "SK"
  type = "S"
}
```

Only declare attributes required for the table's primary key and index keys. Regular item attributes do not need declarations.

## 3. Secondary Indexes

| Parameter | Explanation | Example |
|---|---|---|
| `global_secondary_index` | Index with alternate key attributes | Query orders by status |
| `name` | Index name | `"StatusIndex"` |
| `hash_key` | Index partition key | `"GSI1PK"` |
| `range_key` | Optional index sort key | `"GSI1SK"` |
| `projection_type` | Attributes copied into the index | `"ALL"`, `"KEYS_ONLY"`, `"INCLUDE"` |
| `non_key_attributes` | Additional attributes for `INCLUDE` projection | `["status", "createdAt"]` |
| `read_capacity` | Provisioned index read capacity | `50` |
| `write_capacity` | Provisioned index write capacity | `50` |
| `local_secondary_index` | Alternate sort key using the table partition key | `PK` + `createdAt` |

Example:

```hcl
global_secondary_index {
  name               = "StatusIndex"
  hash_key           = "GSI1PK"
  range_key          = "GSI1SK"
  projection_type    = "INCLUDE"
  non_key_attributes = ["status", "createdAt"]
}
```

Production notes:
- Provisioned GSIs need suitable read/write capacity settings.
- GSI writes consume additional write capacity and storage.
- A hot GSI partition can throttle writes to the base table.
- LSIs must be created with the table and have different constraints.

## 4. Autoscaling

Autoscaling uses separate Terraform resources: `aws_appautoscaling_target` and `aws_appautoscaling_policy`.

| Parameter | Explanation | Example |
|---|---|---|
| `min_capacity` | Minimum provisioned capacity | `20` |
| `max_capacity` | Maximum autoscaled capacity | `1000` |
| `resource_id` | Table or index being scaled | `"table/orders-prod"` |
| `service_namespace` | AWS service name | `"dynamodb"` |
| `scalable_dimension` | Read or write capacity | `"dynamodb:table:ReadCapacityUnits"` |
| `policy_type` | Scaling policy type | `"TargetTrackingScaling"` |
| `target_value` | Target utilization percentage | `70` |
| `scale_in_cooldown` | Cooldown after scaling in | `120` |
| `scale_out_cooldown` | Cooldown after scaling out | `60` |
| `predefined_metric_type` | Utilization metric | `"DynamoDBReadCapacityUtilization"` |

Example:

```hcl
resource "aws_appautoscaling_target" "orders_read" {
  min_capacity       = 20
  max_capacity       = 1000
  resource_id        = "table/orders-prod"
  scalable_dimension = "dynamodb:table:ReadCapacityUnits"
  service_namespace  = "dynamodb"
}
```

Production notes:
- Configure separate read and write scaling targets and policies.
- Configure provisioned GSIs separately where autoscaling is required.
- Autoscaling has a delay; throttling can still occur during sudden spikes.
- Choose maximum capacity using load tests, quotas, and cost limits.
- If autoscaling owns ongoing capacity, consider Terraform `lifecycle.ignore_changes` for the corresponding capacity fields.

## 5. Security and Encryption

| Parameter / Control | Explanation |
|---|---|
| `server_side_encryption.enabled` | Enables encryption at rest |
| `server_side_encryption.kms_key_arn` | Selects a customer-managed KMS key |
| IAM policies | Control permitted DynamoDB API actions |
| `aws:LeadingKeys` | Can restrict access based on partition keys |
| VPC gateway endpoint | Provides private VPC connectivity to DynamoDB |
| Endpoint policy | Restricts requests through the endpoint |
| CloudTrail | Audits supported AWS API activity |

Example:

```hcl
server_side_encryption {
  enabled     = true
  kms_key_arn = aws_kms_key.dynamodb.arn
}
```

Production notes:
- DynamoDB encrypts data at rest by default.
- A customer-managed KMS key is useful when additional key-management and audit controls are required.
- Follow least privilege and separate application access from administrative access.
- Protect Terraform state and credentials.
- Apply tenant-level IAM restrictions carefully and test them.

## 6. Backup and Recovery

| Parameter / Control | Explanation | Example |
|---|---|---|
| `point_in_time_recovery.enabled` | Enables point-in-time recovery | `true` |
| `recovery_period_in_days` | Configures the supported PITR recovery window | `35` |
| `deletion_protection_enabled` | Protects against accidental table deletion | `true` |
| `aws_dynamodb_table_backup` | Creates an on-demand table backup | Backup workflow |
| AWS Backup | Centralizes backup policies and retention | Daily backup plan |
| Restore testing | Validates recovery procedures | Restore to a separate table |

Example:

```hcl
point_in_time_recovery {
  enabled = true
}

deletion_protection_enabled = true
```

Production notes:
- Test restores regularly.
- PITR does not protect against every operational mistake; verify recovery requirements.
- Deletion protection does not prevent accidental item updates or deletes.

## 7. TTL and Streams

| Parameter | Explanation | Example |
|---|---|---|
| `ttl` | Enables automatic item expiration | `expiresAt` |
| `ttl.attribute_name` | Numeric Unix timestamp attribute | `"expiresAt"` |
| `ttl.enabled` | Enables or disables TTL | `true` |
| `stream_enabled` | Enables change records | `true` |
| `stream_view_type` | Chooses stream record contents | `"NEW_AND_OLD_IMAGES"` |

Example:

```hcl
ttl {
  attribute_name = "expiresAt"
  enabled        = true
}

stream_enabled   = true
stream_view_type = "NEW_AND_OLD_IMAGES"
```

Production notes:
- TTL deletion is asynchronous, not an exact-time scheduler.
- Stream retention is finite; consumers need retry handling and monitoring.
- Make stream processing idempotent.

## 8. Global Tables and Replication

| Parameter / Control | Explanation |
|---|---|
| `replica` | Defines another Region for a global table |
| `region_name` | Replica Region |
| KMS configuration | Controls encryption keys per Region |
| Replication monitoring | Detects replication delays or failures |
| Conflict handling | Defines application behavior for concurrent updates |

Example:

```hcl
replica {
  region_name = "us-east-1"
}
```

Production notes:
- Use global tables for defined multi-Region availability or latency requirements.
- Plan conflict resolution, regional failure behavior, and recovery objectives.
- Global tables do not replace backups.

## 9. Monitoring and CloudWatch

| Metric / Control | Purpose |
|---|---|
| `ConsumedReadCapacityUnits` | Measures consumed read capacity |
| `ConsumedWriteCapacityUnits` | Measures consumed write capacity |
| `ReadThrottleEvents` | Tracks throttled reads |
| `WriteThrottleEvents` | Tracks throttled writes |
| `SuccessfulRequestLatency` | Measures successful request latency |
| `SystemErrors` | Tracks server-side errors |
| `ThrottledRequests` | Helps monitor throttling |
| Contributor Insights | Identifies frequently accessed or throttled keys |
| CloudWatch alarms | Sends alerts when thresholds are breached |
| AWS Budgets | Tracks spending against budget thresholds |

Production notes:
- Alarm on throttling, latency, and capacity pressure.
- Monitor GSIs separately from the base table.
- Investigate hot partition keys when throttling occurs despite spare table capacity.
- Choose alarm thresholds based on service-level objectives and traffic baselines.

## 10. Terraform Lifecycle and Deployment Safety

| Parameter | Explanation | Example |
|---|---|---|
| `lifecycle.prevent_destroy` | Blocks Terraform plans that destroy the resource | `true` |
| `lifecycle.ignore_changes` | Ignores specified attributes changed by another controller | Capacity fields managed by autoscaling |
| `provider` | Defines AWS provider configuration | Region and credentials |
| `depends_on` | Defines explicit resource dependencies | Policy depends on target |
| `tags` | Adds ownership and cost metadata | `ManagedBy = "terraform"` |

Example:

```hcl
lifecycle {
  prevent_destroy = true
}
```

Production notes:
- Review Terraform plans before production changes.
- `prevent_destroy` does not protect against every deletion path outside Terraform.
- Use `ignore_changes` only when ownership of the ignored attributes is explicit.
- Pin provider versions and test upgrades before deployment.

## 11. Capacity and Cost Controls

| Parameter / Feature | Explanation |
|---|---|
| `on_demand_throughput.max_read_request_units` | Configures an on-demand read-throughput limit |
| `on_demand_throughput.max_write_request_units` | Configures an on-demand write-throughput limit |
| `warm_throughput` | Configures supported warm-throughput settings |
| `table_class` | Selects storage pricing class |
| GSI projection | Controls index attributes and storage |
| Reserved capacity | Can reduce cost for eligible steady provisioned workloads |
| Service quotas | Limits account or service capacity |
| Item-size limits | Constrain maximum item size |
| Request-size limits | Constrain supported request sizes |

Important:
- Verify parameter availability and constraints against your AWS provider version.
- Cost controls and throughput limits can cause throttling if configured too aggressively.
- Warm throughput settings do not solve poor partition-key distribution.

## 12. Production Table Example

```hcl
resource "aws_dynamodb_table" "orders" {
  name         = "orders-prod"
  billing_mode = "PAY_PER_REQUEST"

  hash_key  = "PK"
  range_key = "SK"

  attribute {
    name = "PK"
    type = "S"
  }

  attribute {
    name = "SK"
    type = "S"
  }

  deletion_protection_enabled = true

  point_in_time_recovery {
    enabled = true
  }

  server_side_encryption {
    enabled = true
  }

  tags = {
    Environment = "prod"
    ManagedBy   = "terraform"
    Service     = "orders"
  }

  lifecycle {
    prevent_destroy = true
  }
}
```

This is a baseline, not a complete production deployment. Add IAM, alarms, backup policies, network controls, and workload-specific capacity configuration.
