# AWS DynamoDB

## 1. What is DynamoDB?

Amazon DynamoDB is a **fully managed NoSQL database service** provided by AWS.

It is designed for:

* Very high request volumes
* Low-latency access
* Large amounts of data
* Horizontally scalable applications
* Serverless applications

Unlike a traditional relational database, DynamoDB does not use tables with fixed relational schemas and joins in the same way as systems such as PostgreSQL or MySQL.

---

# 2. Basic DynamoDB Structure

The basic model is:

```text
DynamoDB
   ↓
Table
   ↓
Items
   ↓
Attributes
```

Example:

```text
Customer Table

{
    "customer_id": "C123",
    "country": "Ireland",
    "county": "Dublin",
    "status": "ACTIVE"
}
```

Here:

```text
customer_id → Attribute
country     → Attribute
county      → Attribute
status      → Attribute
```

An item is roughly equivalent to a row in a relational database, but DynamoDB's data model and access patterns are different.

---

# 3. Primary Key

Every DynamoDB table needs a primary key.

There are two types:

### Simple Primary Key

Only a partition key:

```text
Partition Key
```

Example:

```text
customer_id
```

### Composite Primary Key

Contains:

```text
Partition Key + Sort Key
```

Example:

```text
Partition Key → customer_id
Sort Key      → order_id
```

---

# 4. Partition Key

The partition key determines how DynamoDB distributes items across its underlying storage partitions.

Example:

```text
customer_id
```

Suppose we have:

```text
C001
C002
C003
C004
C005
...
```

DynamoDB uses the partition-key values to distribute data.

### Important

Don't think:

```text
country = Ireland
        ↓
physical partition called Ireland
```

Instead:

> The partition key value is used by DynamoDB to determine where the item is stored and how requests are distributed.

---

# 5. Why Partition Key Design Matters

A good partition key should generally provide enough distribution of requests and data.

Bad design can cause a **hot partition**.

Example:

```text
Partition Key = status

ACTIVE
ACTIVE
ACTIVE
ACTIVE
ACTIVE
ACTIVE
...
```

If almost every request targets:

```text
ACTIVE
```

then the same logical partition-key value receives a disproportionate amount of traffic.

That can create a hot access pattern.

---

# 6. Sort Key

A sort key is used with a partition key in a composite primary key.

Example:

```text
Partition Key → customer_id
Sort Key      → order_date
```

Data:

```text
customer_id | order_date
------------|-----------
C001        | 2026-01-01
C001        | 2026-02-01
C001        | 2026-03-01
C002        | 2026-01-10
C002        | 2026-02-10
```

For `C001`, the sort key lets us organize/query its related items.

---

# 7. Composite Primary Key

Example:

```text
PK = customer_id
SK = order_id
```

Then:

```text
Customer C001
 ├── Order O001
 ├── Order O002
 └── Order O003

Customer C002
 ├── Order O004
 └── Order O005
```

This is a common DynamoDB modelling pattern.

---

# 8. DynamoDB Query

`Query` is used when you know the partition key.

Example:

```text
PK = customer_id
```

Query:

```text
customer_id = C001
```

Then you can optionally add conditions on the sort key.

Example:

```text
customer_id = C001
AND
order_date >= 2026-01-01
```

### Important interview point

> A Query requires an equality condition on the partition key.

---

# 9. DynamoDB Scan

`Scan` reads through the table/index and evaluates items.

Example:

```text
10 million items
      ↓
Scan
      ↓
Potentially examine huge amounts of data
```

This can be expensive and inefficient for large tables.

Therefore:

> Design DynamoDB around the access patterns you need instead of relying on Scan for common queries.

---

# 10. Query vs Scan

| Query                                  | Scan                               |
| -------------------------------------- | ---------------------------------- |
| Uses partition key                     | Reads through the table/index      |
| Efficient when access pattern is known | Can be expensive at scale          |
| Can use sort-key conditions            | Can filter results after reading   |
| Preferred for targeted retrieval       | Avoid for large frequent workloads |

Easy memory:

```text
Query
→ "I know what partition I need."

Scan
→ "Look through the data."
```

---

# 11. Your 10-Million Customer Scenario

Suppose we have:

```text
Customer table
        ↓
10 million customers
```

The business asks:

> "Give me all ACTIVE customers."

A beginner might do:

```text
Scan entire table
        ↓
Filter status = ACTIVE
```

Problem:

```text
10 million items
       ↓
Read huge amount of data
       ↓
High cost
       ↓
High latency
       ↓
Potential capacity pressure
```

---

# 12. GSI for the Active Customer Scenario

A possible solution is a **Global Secondary Index (GSI)**.

For example:

```text
Base Table

PK: customer_id
```

GSI:

```text
GSI PK: status
```

Then we can query:

```text
status = ACTIVE
```

instead of scanning the entire base table.

However, there is an important problem.

---

# 13. Low-Cardinality GSI Problem

Suppose:

```text
status = ACTIVE
```

for 9 million customers.

Then the GSI looks conceptually like:

```text
ACTIVE
 ├── Customer 1
 ├── Customer 2
 ├── Customer 3
 ├── ...
 └── Customer 9,000,000
```

All those items share the same GSI partition-key value.

This can create a **hot partition/access pattern**.

So simply saying:

> "Create a GSI on status"

is not always a complete production-quality answer.

---

# 14. Better GSI Design

We may need a more distributed key.

For example:

```text
GSI Partition Key = status#shard
```

Conceptually:

```text
ACTIVE#0
ACTIVE#1
ACTIVE#2
ACTIVE#3
...
```

Customers are distributed across shards.

Then the application can query multiple shards.

```text
ACTIVE#0 → customers
ACTIVE#1 → customers
ACTIVE#2 → customers
ACTIVE#3 → customers
```

This reduces concentration on a single logical partition key.

The exact design depends on the application's access pattern.

---

# 15. Important Point About "Get All Active Customers"

Even with a GSI:

```text
9 million ACTIVE customers
```

still means potentially retrieving millions of records.

A GSI doesn't magically make retrieving millions of records cheap.

For a requirement such as:

> "Give me every active customer"

we should ask:

* Does the application really need all 9 million records?
* Can we paginate?
* Can we process asynchronously?
* Can we export the data?
* Can we maintain a separate active-customer index?
* Can we use a data warehouse/data lake for analytics?

DynamoDB is usually best for **targeted, predictable access patterns**, not massive analytical scans.

---

# 16. What is a GSI?

**GSI = Global Secondary Index**

A GSI provides another way to query the same underlying data using a different key structure.

Example:

Base table:

```text
PK = customer_id
```

GSI:

```text
PK = status
SK = customer_id
```

Now we have another access pattern.

```text
Base Table
customer_id → customer information

GSI
status → customers by status
```

---

# 17. GSI Can Have Different Keys

Unlike an LSI, a GSI can have a different partition key from the base table.

Example:

```text
Base Table
PK = customer_id

GSI
PK = country
SK = customer_id
```

This gives another query pattern:

```text
Find customers for country = Ireland
```

---

# 18. GSI Can Be Added Later

A GSI does not have to be defined only when the table is initially created.

It can be added after the table exists.

This is one major difference from an LSI.

---

# 19. GSI Capacity

A GSI has its own capacity considerations.

With provisioned capacity, the GSI has its own read/write capacity settings.

Conceptually:

```text
Base Table
    ↓
Capacity

GSI
    ↓
Separate capacity
```

Poor GSI design can therefore cause GSI throttling even when the base table looks healthy.

---

# 20. What is an LSI?

**LSI = Local Secondary Index**

An LSI provides an alternative sort key while keeping the **same partition key as the base table**.

Example:

Base table:

```text
PK = customer_id
SK = order_id
```

LSI:

```text
PK = customer_id
SK = order_date
```

So:

```text
Same partition key
Different sort key
```

---

# 21. GSI vs LSI

| Feature                      | GSI                | LSI                                          |
| ---------------------------- | ------------------ | -------------------------------------------- |
| Partition key                | Can be different   | Must be same as base table                   |
| Sort key                     | Can be different   | Can be different                             |
| Created after table creation | Yes                | No                                           |
| Capacity                     | Separate capacity  | Shares base table capacity                   |
| Maximum default count        | 20 GSIs/table      | 5 LSIs/table                                 |
| Main purpose                 | New access pattern | Alternative sort order within same partition |

The exact service quotas can change, so always check current AWS quotas for production design.

---

# 22. LSI Example

Suppose:

```text
Customer table

PK = customer_id
SK = order_id
```

We want to retrieve a customer's orders by date.

We could create an LSI:

```text
PK = customer_id
SK = order_date
```

Then:

```text
C001
 ├── 2026-01-01
 ├── 2026-02-15
 └── 2026-03-20
```

The partition key remains:

```text
customer_id
```

# 23. Hot Partition

A **hot partition** happens when a disproportionate amount of traffic or data is concentrated on a particular partition-key value.

Example:

```text
PK = country

Ireland → 80% of requests
UK      → 10%
France  → 5%
Other   → 5%
```

Ireland could become a hot access pattern.

Another example:

```text
PK = status

ACTIVE → 95% of requests
```

Again, this is problematic because of the low-cardinality key.

---

# 24. How to Reduce Hot Partitions

Possible approaches:

### 1. Better partition-key design

Use a high-cardinality key where appropriate.

### 2. Write sharding

Distribute a popular logical key across multiple physical/logical key values.

Example:

```text
customer#0
customer#1
customer#2
...
```

### 3. Composite keys

Combine attributes to increase distribution.

### 4. Caching

For frequently requested data, caching can reduce database load.

### 5. Reconsider the access pattern

Sometimes the best solution is changing how the application retrieves the data.

---

# 25. DynamoDB Throughput

DynamoDB has limits on how much read/write traffic can be handled.

You can use:

### Provisioned capacity

You specify expected read/write capacity.

```text
Provisioned
 ↓
Configured capacity
```

Auto scaling can adjust provisioned capacity based on utilization.

### On-demand capacity

AWS automatically manages capacity based on workload, subject to service limits.

---

# 26. Throughput Exceeded

If your workload exceeds available capacity, DynamoDB can throttle requests.

Conceptually:

```text
Application
     ↓
DynamoDB
     ↓
Capacity exhausted
     ↓
Throttling
```

Depending on the situation, you may see exceptions such as:

```text
ProvisionedThroughputExceededException
```

or newer throttling-related exceptions depending on the API/workload.

---

# 27. Important: Total Capacity Isn't Everything

Suppose your table has enough total capacity:

```text
Total capacity = 10,000 WCU
```

but your traffic is badly distributed.

You could still experience throttling because one partition/access pattern is overloaded.

Therefore:

> DynamoDB performance is not only about total capacity; partition-key design and traffic distribution are critical.

---

# 28. Strong vs Eventual Consistency

DynamoDB supports different consistency options for reads.

### Eventually consistent read

The read may not immediately reflect the latest successful write.

### Strongly consistent read

The read reflects all successful writes that occurred before the read.

Strong consistency can have higher capacity cost/limitations depending on the operation.

For interview purposes:

```text
Eventually consistent
→ More common/default pattern

Strongly consistent
→ When immediate consistency is required
```

---

# 29. Conditional Writes

DynamoDB supports conditional expressions.

This is particularly useful for **idempotency**.

Example:

```python id="x3q3mv"
table.put_item(
    Item={
        "txn_id": "TXN123",
        "status": "PROCESSING"
    },
    ConditionExpression="attribute_not_exists(txn_id)"
)
```

Meaning:

> Only create this item if `txn_id` does not already exist.

This provides an atomic condition.

---

# 30. DynamoDB and Our Lambda Idempotency

Our processing flow could be:

```text id="ezx0f9"
Lambda
 ↓
DynamoDB conditional write
 ↓
Does file_key already exist?
      / \
    No   Yes
    ↓     ↓
Claim   Duplicate
    ↓
Process
```

For example:

```text
file_key = incoming/customer_20260829.csv
```

DynamoDB might contain:

```json id="f9r8ub"
{
    "file_key": "incoming/customer_20260829.csv",
    "status": "PROCESSING"
}
```

Then after successful processing:

```json id="5k9yxi"
{
    "file_key": "incoming/customer_20260829.csv",
    "status": "COMPLETED"
}
```

For production systems, also think about stale `PROCESSING` records and retry/recovery behavior.

# 32. Why DynamoDB Instead of S3 for Status?

S3 is excellent for storing objects/files.

DynamoDB is better for fast lookup/update of metadata.

For example:

```text id="x6r0id"
Question:
"What is the processing status of this file?"
```

DynamoDB can efficiently retrieve the record using the appropriate key.

We don't want to search through files in S3 to determine processing state.

---

# 33. DynamoDB Design Principle

A very important DynamoDB concept is:

> **Design the table around access patterns.**

Traditional relational thinking often starts with:

```text
"What data do I have?"
```

DynamoDB modelling should strongly consider:

```text
"What queries does my application need?"
```

Example:

Requirement:

```text
Find transaction by transaction_id
```

Possible key:

```text
PK = transaction_id
```

Requirement:

```text
Find orders for customer sorted by date
```

Possible design:

```text
PK = customer_id
SK = order_date
```

# 34. Common DynamoDB Interview Questions

## Q1. What is DynamoDB?
> DynamoDB is a fully managed NoSQL database designed for high-scale, low-latency workloads.
---
## Q2. What is a partition key?
> The partition key is the primary key component DynamoDB uses to determine the logical partitioning and distribution of items. Good partition-key design is important for distributing traffic evenly.
---
## Q3. What is a sort key?
> A sort key is the second component of a composite primary key. It allows multiple items with the same partition key and supports ordered/range-based queries within that partition-key value.
---
## Q4. Query vs Scan?
> Query targets a specific partition key and is generally preferred for known access patterns. Scan examines items across the table or index and can become expensive at scale.
---
## Q5. What is a GSI?
> A Global Secondary Index provides an additional access pattern and can have a different partition key and sort key from the base table.
---
## Q6. What is an LSI?
> A Local Secondary Index uses the same partition key as the base table but provides a different sort key.
---
## Q7. Can you create an LSI after the table is created?
> No. LSIs must be created when the DynamoDB table is created.
---
## Q8. Can you create a GSI after the table is created?
> Yes. GSIs can be added to an existing table.
---
## Q9. What is a hot partition?
> A hot partition occurs when traffic or data is disproportionately concentrated on a particular partition-key value, potentially causing throttling even when the table's overall capacity appears sufficient.
---
## Q10. How would you handle a hot partition?
> I would review the access pattern and partition-key design, consider a higher-cardinality or distributed key, use write sharding where appropriate, and consider caching or redesigning the access pattern if necessary.
---
# 35. 10-Million Customer Interview Question
### Interviewer:
> You have 10 million customers in DynamoDB and the business wants all active customers. What would you do?
### Weak answer:
> "I would scan the table and filter status = ACTIVE."
### Better answer:
> "I would avoid repeatedly scanning the entire table. If retrieving active customers is a regular access pattern, I would design an appropriate secondary index or access pattern. However, I would be careful about using `status` alone as a GSI partition key because ACTIVE is low cardinality and could create a hot partition.
If the result set itself contains millions of customers, I would also consider pagination, asynchronous processing, a distributed/sharded index, or moving analytical/export workloads to a more appropriate data-processing system."
This demonstrates that you understand both **DynamoDB indexing** and **large-scale access-pattern design**.

# 36. DynamoDB Troubleshooting Flow
If an application reports DynamoDB throttling:
```text id="2n0trb"
Application
     ↓
DynamoDB throttling
     ↓
Check CloudWatch metrics
     ↓
Check:
  ├── Read/write traffic
  ├── Throttled requests
  ├── Partition-key distribution
  ├── Hot partitions
  ├── GSI traffic
  └── Capacity configuration
```

Then determine whether the problem is:
```text
Capacity issue
        OR
Poor partition-key design
        OR
Hot GSI
        OR
Sudden traffic spike
```

> **DynamoDB is a highly scalable NoSQL database where good data modelling and partition-key design are critical. I use Query-based access patterns and secondary indexes where appropriate, avoid large table scans for frequent workloads, and use conditional writes for things like idempotency.**
