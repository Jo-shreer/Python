# AWS ECS – Complete Cheatsheet with Production Terraform Example

## 1. What is Amazon ECS?

Amazon ECS stands for **Amazon Elastic Container Service**.

It is a fully managed container orchestration service that helps you run Docker containers on AWS.

For example, imagine you have a Java Spring Boot application.

You:
1. Write your application.
2. Create a Dockerfile.
3. Build a Docker image.
4. Push the image to Amazon ECR.
5. Create an ECS Task Definition.
6. Deploy the task using an ECS Service.
7. ECS maintains the desired number of running containers.

### ECS architecture

```text
             Developer
                 |
                 v
          Application Code
                 |
                 v
             Dockerfile
                 |
                 v
            Docker Image
                 |
                 v
                ECR
                 |
                 v
           ECS Task Definition
                 |
                 v
             ECS Cluster
                 |
                 v
             ECS Service
                 |
          +------+------+
          |      |      |
          v      v      v
        Task 1 Task 2 Task 3
          |      |      |
          +------+------+
                 |
                 v
          Application Users
```

## 2. Important ECS components

| Component | Explanation | Example |
|---|---|---|
| ECS Cluster | Logical grouping of ECS resources | prod-cluster |
| Task Definition | Blueprint describing containers and resources | web-task |
| Task | Running instance of a task definition | One running container group |
| Container | Application packaged with its dependencies | Spring Boot application |
| ECS Service | Maintains the desired number of running tasks | 3 web tasks |
| Capacity Provider | Determines where tasks get compute capacity | FARGATE |
| Launch Type | Specifies compute infrastructure | FARGATE or EC2 |
| Container Instance | EC2 machine registered to an ECS cluster | EC2 worker |
| Task Role | Permissions available to application containers | Read from S3 |
| Execution Role | Permissions ECS agent needs to start the task | Pull ECR image |
| Service Discovery | Allows services to discover one another | Internal API DNS |
| Container Insights | Monitoring for ECS workloads | CPU and memory metrics |

### Cluster vs Task Definition vs Task vs Service

This is a very important interview topic.

**Cluster:** Where ECS workloads are logically grouped.

**Task Definition:** Instructions describing how containers should run.

**Task:** An actual running instance of that task definition.

**Service:** Keeps a specified number of tasks running.

Example:

```text
ECS Cluster: production-cluster
        |
        +--------------------------+
        |                          |
        v                          v
   ECS Service A              ECS Service B
   Desired Count: 3           Desired Count: 2
        |                          |
   +----+----+                  +--+--+
   |    |    |                  |     |
   v    v    v                  v     v
 Task Task Task                Task  Task
```

If one task crashes in Service A, ECS attempts to replace it to maintain the desired count.

## 3. ECS launch types and compute options

There are two traditional ECS launch types.

### A. Fargate

Fargate is serverless container compute.

You do not manage EC2 instances.

You specify:
- CPU.
- Memory.
- Container image.
- Networking.
- IAM roles.

AWS manages the underlying compute infrastructure.

Example:

```text
              ECS Cluster
                   |
                   v
              ECS Service
                   |
             Fargate Tasks
              /    |    \
             v     v     v
           Task 1 Task 2 Task 3
```

Use Fargate when:
- You do not want to manage EC2 servers.
- You have microservices.
- You want to scale containers independently.
- Your workload has variable traffic.
- You want simpler infrastructure management.

### B. EC2 launch type

Here, you manage EC2 instances that provide compute capacity for ECS containers.

```text
              ECS Cluster
                   |
             EC2 Capacity
                   |
           +-------+-------+
           |               |
           v               v
        EC2-01           EC2-02
           |               |
        Task 1           Task 2
        Task 2           Task 3
```

Use EC2 when:
- You need more control over the underlying servers.
- You need GPU instances or specialized hardware.
- You have predictable, high utilization.
- You need custom AMIs or host-level configuration.
- You need particular operating-system or kernel capabilities.

### C. ECS Managed Instances

ECS also offers ECS Managed Instances, where AWS manages the underlying EC2 infrastructure for ECS workloads.

This provides an option between fully serverless Fargate and directly managing EC2 container instances.

### Comparison

| Feature | Fargate | EC2 | Managed Instances |
|---|---|---|---|
| Server management | AWS | You | AWS |
| Instance selection | Limited infrastructure control | You select | Requirements-based |
| Billing | vCPU, memory and applicable storage | EC2 infrastructure | Managed compute pricing |
| Host access | No direct host management | Yes | More limited |
| Scaling | Task-level | Instance and task-level | Managed capacity |
| GPU/specialized hardware | Limited | Flexible | Supported configurations vary |
| Best use | Simple container operations | Maximum infrastructure control | Managed EC2 capacity |

**Recommendation:** Start with Fargate if you do not have a specific requirement for EC2-level control.

## 4. ECS use cases

| Use case | Example |
|---|---|
| Microservices | Run payment, inventory and order services separately |
| Web applications | Run Spring Boot or Node.js applications |
| REST APIs | Host backend APIs behind an ALB |
| Background workers | Process SQS messages |
| Batch processing | Run a container to process files |
| Scheduled jobs | Run a task every night |
| CI/CD workloads | Run deployment or build containers |
| Data processing | Process large datasets |
| Event-driven applications | Start tasks based on events |
| Machine learning | Run containerized inference workloads |

### Example: E-commerce application

Suppose you have three microservices:

- Order Service.
- Payment Service.
- Inventory Service.

You can deploy each as a separate ECS Service.

```text
                    ALB
                     |
          +----------+----------+
          |          |          |
          v          v          v
       Order      Payment    Inventory
       Service    Service     Service
          |          |          |
          v          v          v
       ECS Tasks  ECS Tasks  ECS Tasks
```

Each service can scale independently.

For example:
- Order Service: 4 tasks.
- Payment Service: 2 tasks.
- Inventory Service: 3 tasks.

## 5. ECS networking and Security Groups

This is particularly important for production deployments.

For Fargate, ECS tasks use `awsvpc` networking.

Each task receives its own Elastic Network Interface (ENI) and private IP address.

You can attach Security Groups to that task network interface through the ECS service's network configuration.

### Production networking architecture

```text
                  Internet
                     |
                     v
               Internet Gateway
                     |
                     v
              Public Subnets
                     |
                     v
              Application LB
                ALB SG
                     |
               HTTPS 443
                     |
                     v
              Private Subnets
                     |
                ECS Tasks
                  Task SG
                     |
                     v
                RDS Database
                   DB SG
```

Security Group rules:

**ALB Security Group**
- Inbound TCP 443 from permitted client IP ranges or the internet, depending on the application.
- Outbound application port to ECS task Security Group.

**ECS Task Security Group**
- Inbound application port only from the ALB Security Group.
- Outbound access to required application dependencies.

**RDS Security Group**
- Inbound database port only from the ECS task Security Group.

Important:
- Do not expose ECS tasks directly to the internet unnecessarily.
- Use private subnets for application tasks.
- Use NAT Gateway or suitable VPC endpoints for required outbound access.
- ECR image pulls, CloudWatch Logs and secrets retrieval need appropriate connectivity.
- For Fargate, use `network_mode = "awsvpc"`.

## 6. ECS task definition – important parameters

Terraform resource:

`aws_ecs_task_definition`

The task definition defines how the container should run.

| Parameter | Explanation | Example |
|---|---|---|
| family | Task definition family name | web-app |
| container_definitions | Container configuration in JSON | Image, port, CPU |
| cpu | Task-level CPU units | 512 |
| memory | Task-level memory in MiB | 1024 |
| network_mode | Container networking mode | awsvpc |
| requires_compatibilities | Supported compute type | FARGATE |
| execution_role_arn | ECS task execution role | Execution role ARN |
| task_role_arn | Application permissions role | App role ARN |
| runtime_platform | OS and CPU architecture | Linux, X86_64 |
| volumes | Storage volume definitions | EFS or task volume |
| ephemeral_storage | Extra temporary task storage | 50 GiB |
| ipc_mode | IPC namespace configuration | host or task where supported |
| pid_mode | Process namespace configuration | task or host where supported |
| proxy_configuration | ECS Service Connect/App Mesh-related proxy configuration where supported | Proxy settings |
| skip_destroy | Controls deregistration behavior for the Terraform resource | true/false |
| track_latest | Tracks the latest active revision in supported provider configurations | true/false |

Important:

For Fargate:
- `network_mode` must be `awsvpc`.
- CPU and memory must use supported combinations.
- `requires_compatibilities` must include `FARGATE`.

Not every parameter applies to Fargate. Some are specific to EC2 launch type or particular operating systems.

## 7. ECS Service – important Terraform parameters

Terraform resource:

`aws_ecs_service`

An ECS Service maintains the desired number of running tasks.

| Parameter | Explanation | Example |
|---|---|---|
| name | ECS service name | web-service |
| cluster | Cluster ID or ARN | production-cluster |
| task_definition | Task definition ARN or family:revision | web-task |
| desired_count | Desired running tasks | 2 |
| launch_type | Compute launch type | FARGATE |
| platform_version | Fargate platform version | LATEST |
| deployment_maximum_percent | Maximum tasks during rolling deployment | 200 |
| deployment_minimum_healthy_percent | Minimum healthy percentage | 100 |
| health_check_grace_period_seconds | Grace period for load balancer health checks | 60 |
| enable_execute_command | Enable ECS Exec | true |
| enable_ecs_managed_tags | Add ECS-managed tags | true |
| propagate_tags | Propagate tags from service or task definition | SERVICE |
| wait_for_steady_state | Wait for stable service state during apply | true |
| scheduling_strategy | REPLICA or DAEMON | REPLICA |
| deployment_controller | ECS, CODE_DEPLOY or EXTERNAL | ECS |
| deployment_circuit_breaker | Detect failed deployments and optionally roll back | enabled |
| network_configuration | Task networking | Subnets and SGs |
| load_balancer | Attach target group | ALB target group |
| capacity_provider_strategy | Select capacity providers | FARGATE |
| service_registries | Service discovery integration | Cloud Map |
| ordered_placement_strategy | EC2 task placement strategy | binpack |
| placement_constraints | EC2 placement constraints | distinctInstance |
| volume_configuration | Supported managed EBS volume configuration | EBS settings |
| triggers | Supported redeployment trigger configuration | Container deployment |
| force_new_deployment | Force new deployment | true |
| alarms | Configure deployment alarms where supported | CloudWatch alarms |
| lifecycle | Terraform lifecycle meta-argument | create_before_destroy |

## 10. Production Terraform example

Let's build a production-oriented ECS Fargate architecture.

### Architecture

```text
                     Internet
                        |
                        v
                 Application Load
                    Balancer
                        |
                        v
                  Public Subnets
                        |
                   ALB Security
                      Group
                        |
                     HTTP 80
                        |
                        v
                  Private Subnets
                        |
                  ECS Fargate
                     Service
                        |
              +---------+---------+
              |                   |
              v                   v
           ECS Task 1          ECS Task 2
              |                   |
              +---------+---------+
                        |
                  Task Security
                      Group
                        |
                        v
                 CloudWatch Logs
```

This example assumes:
- A VPC already exists.
- Two public subnets exist in different Availability Zones.
- Two private subnets exist in different Availability Zones.
- An ECR repository and application image already exist.
- The application listens on port 8080.
- The application exposes `/health`.
- NAT Gateway or appropriate VPC endpoints provide the private tasks with access to required AWS services.

For a real internet-facing production service, add an HTTPS listener with an ACM certificate and redirect HTTP to HTTPS. The example below uses HTTP to keep the deployment understandable.

### File 6: ECS execution role

The execution role is used by ECS/Fargate to:
- Pull container images from ECR.
- Send container logs to CloudWatch.
- Retrieve configured secrets when permissions are provided.

```hcl
resource "aws_iam_role" "ecs_execution_role" {
  name = "${var.environment}-ecs-execution-role"

  assume_role_policy = jsonencode({
    Version = "2012-10-17"

    Statement = [{
      Effect = "Allow"

      Principal = {
        Service = "ecs-tasks.amazonaws.com"
      }

      Action = "sts:AssumeRole"
    }]
  })
}

resource "aws_iam_role_policy_attachment" "ecs_execution_policy" {
  role = aws_iam_role.ecs_execution_role.name

  policy_arn = "arn:aws:iam::aws:policy/service-role/AmazonECSTaskExecutionRolePolicy"
}
```

### File 7: ECS application task role

The task role is used by the application running inside the container.

For example, if your Java application reads objects from S3, its S3 permissions belong here.

```hcl
resource "aws_iam_role" "ecs_task_role" {
  name = "${var.environment}-ecs-task-role"

  assume_role_policy = jsonencode({
    Version = "2012-10-17"

    Statement = [{
      Effect = "Allow"

      Principal = {
        Service = "ecs-tasks.amazonaws.com"
      }

      Action = "sts:AssumeRole"
    }]
  })
}
```

Add only the application-specific IAM permissions this role needs.

Do not confuse:
- Execution role = ECS infrastructure operations.
- Task role = Application permissions.

### File 8: Application Load Balancer Security Group

```hcl

    to_port         = var.container_port

    Name = "${var.environment}-alb-sg"
  }

```

### File 9: ECS task Security Group

```hcl
resource "aws_security_group" "ecs_task_sg" {
  name        = "${var.environment}-ecs-task-sg"
  description = "Security group for ECS tasks"
  vpc_id      = var.vpc_id

  ingress {
    description     = "Application traffic only from ALB"
    from_port       = var.container_port
    to_port         = var.container_port
    protocol        = "tcp"
    security_groups = [aws_security_group.alb_sg.id]
  }

  egress {
    description = "Outbound application dependencies"
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }

  tags = {
    Name = "${var.environment}-ecs-task-sg"
  }
}
```

In a stricter production environment, replace unrestricted egress with only the required destinations and ports, while accounting for ECR, logs, secrets and application dependencies.

### File 13: ECS Task Definition

```hcl
resource "aws_ecs_task_definition" "web" {
  family = "${var.environment}-web-task"

  network_mode = "awsvpc"

  requires_compatibilities = [
    "FARGATE"
  ]

  cpu    = "512"
  memory = "1024"

  execution_role_arn = aws_iam_role.ecs_execution_role.arn

  task_role_arn = aws_iam_role.ecs_task_role.arn

  runtime_platform {
    operating_system_family = "LINUX"
    cpu_architecture        = "X86_64"
  }

  container_definitions = jsonencode([
    {
      name      = "web-app"
      image     = var.container_image
      essential = true

      cpu    = 512
      memory = 1024

      portMappings = [
        {
          name          = "http"
          containerPort = var.container_port
          hostPort      = var.container_port
          protocol      = "tcp"
        }
      ]

      environment = [
        {
          name  = "ENVIRONMENT"
          value = var.environment
        }
      ]

      logConfiguration = {
        logDriver = "awslogs"

        options = {
          "awslogs-group"         = aws_cloudwatch_log_group.ecs.name
          "awslogs-region"        = var.aws_region
          "awslogs-stream-prefix" = "web"
        }
      }

      healthCheck = {
        command = [
          "CMD-SHELL",
          "curl -f http://localhost:${var.container_port}/health || exit 1"
        ]

        interval    = 30
        timeout     = 5
        retries     = 3
        startPeriod = 60
      }

      readonlyRootFilesystem = true

      stopTimeout = 30
    }
  ])

  tags = {
    Environment = var.environment
  }
}
```

Important:
- The image must exist in ECR or another accessible registry.
- The container must actually listen on the configured port.
- The health-check command requires `curl` to be installed in the image. If it is not installed, use an appropriate command or application health-check mechanism.
- A read-only root filesystem requires the application to write only to explicitly configured writable locations.
- If you use ARM images, change `cpu_architecture` to `ARM64` and ensure the image supports ARM64.

### File 14: ECS Service

```hcl
resource "aws_ecs_service" "web" {
  name            = "${var.environment}-web-service"
  cluster         = aws_ecs_cluster.main.id
  task_definition = aws_ecs_task_definition.web.arn

  desired_count = var.desired_count

  launch_type = "FARGATE"

  platform_version = "LATEST"

  enable_execute_command = true

  enable_ecs_managed_tags = true

  propagate_tags = "SERVICE"

  deployment_minimum_healthy_percent = 100
  deployment_maximum_percent         = 200

  health_check_grace_period_seconds = 60

  deployment_circuit_breaker {
    enable   = true
    rollback = true
  }

  network_configuration {
    subnets = var.private_subnet_ids

    security_groups = [
      aws_security_group.ecs_task_sg.id
    ]

    assign_public_ip = false
  }

  load_balancer {
    target_group_arn = aws_lb_target_group.ecs.arn
    container_name   = "web-app"
    container_port   = var.container_port
  }

  depends_on = [
    aws_lb_listener.http,
    aws_iam_role_policy_attachment.ecs_execution_policy
  ]

  tags = {
    Environment = var.environment
  }
}
```

Important settings:

- `desired_count = 2`: maintain two running tasks.
- `launch_type = FARGATE`: use serverless compute.
- `assign_public_ip = false`: tasks do not receive public IPv4 addresses.
- `private_subnets`: run application tasks privately.
- `deployment_circuit_breaker`: detect failed deployments and roll back.
- `enable_execute_command`: allows authorized operators to use ECS Exec.

### File 15: ECS Service Auto Scaling

This allows the ECS service to scale between 2 and 10 tasks based on average CPU utilization.

```hcl
resource "aws_appautoscaling_target" "ecs" {
  max_capacity = 10
  min_capacity = 2

  resource_id = "service/${aws_ecs_cluster.main.name}/${aws_ecs_service.web.name}"

  scalable_dimension = "ecs:service:DesiredCount"

  service_namespace = "ecs"
}
```

CPU scaling policy:

```hcl
resource "aws_appautoscaling_policy" "cpu" {
  name               = "${var.environment}-ecs-cpu-scaling"
  policy_type        = "TargetTrackingScaling"
  resource_id        = aws_appautoscaling_target.ecs.resource_id
  scalable_dimension = aws_appautoscaling_target.ecs.scalable_dimension
  service_namespace  = aws_appautoscaling_target.ecs.service_namespace

  target_tracking_scaling_policy_configuration {
    target_value = 60

    predefined_metric_specification {
      predefined_metric_type = "ECSServiceAverageCPUUtilization"
    }

    scale_in_cooldown  = 120
    scale_out_cooldown = 60
  }
}
```

Explanation:

- Minimum tasks: 2.
- Maximum tasks: 10.
- Target CPU utilization: 60%.
- ECS automatically adjusts the desired task count based on utilization.

For production, consider scaling on memory or ALB request count as well, depending on application behavior.

## 12. ECS deployment strategies

### A. Rolling deployment

ECS gradually replaces old tasks with new tasks.

Example:

```text
Old version: Task 1, Task 2

Deploy new version:

Old Task 1 + Old Task 2 + New Task 1

Then:

Old Task 2 + New Task 1 + New Task 2

Finally:

New Task 1 + New Task 2
```

This is the common default deployment approach.

### B. Blue/Green deployment

You run two environments:
- Blue = current version.
- Green = new version.

After validating the green environment, traffic switches to it.

Useful for reducing deployment risk.

ECS supports blue/green deployments through supported deployment controllers and integrations, including CodeDeploy.

### C. Canary deployment

You expose a small percentage of traffic to the new version and gradually increase it.

Useful when you want to observe application behavior before sending all traffic to a new release.

## 15. ECS security best practices

1. Run tasks in private subnets where possible.
2. Use task Security Groups to restrict inbound traffic.
3. Allow application traffic from the ALB Security Group, not from the entire internet.
4. Use separate task roles for different applications.
5. Keep execution role and task role separate.
6. Store secrets in Secrets Manager or Systems Manager Parameter Store.
7. Encrypt secrets and logs where appropriate.
8. Use ECR image scanning and trusted image sources.
9. Use immutable image tags or digests.
10. Enable CloudTrail and monitor ECS API activity.
11. Use ECS Exec only for authorized operators.
12. Avoid privileged containers unless essential.
13. Use a read-only root filesystem where the application supports it.
14. Apply least-privilege IAM permissions.
15. Patch base images and rebuild containers regularly.
16. Use deployment circuit breakers and health checks.
17. Avoid storing database credentials in plain-text environment variables.

## 16. ECS cost

Important: **ECS itself has no additional charge for the standard ECS orchestration service.** You pay for the compute infrastructure and supporting AWS services.

### A. Fargate pricing

Fargate pricing is based on:
- vCPU.
- Memory.
- Operating system.
- CPU architecture.
- Additional ephemeral storage, if configured.
- Task running duration.

Example:

Suppose you run:

- 2 ECS tasks.
- Each task has 0.5 vCPU.
- Each task has 1 GB memory.
- Tasks run continuously for 730 hours per month.

Total monthly usage:

| Resource | Calculation | Usage |
|---|---|---:|
| vCPU | 2 × 0.5 × 730 | 730 vCPU-hours |
| Memory | 2 × 1 × 730 | 1,460 GB-hours |

Your compute cost is:

```text
Fargate cost =
(vCPU-hours × regional vCPU rate)
+
(GB-hours × regional memory rate)
+
Applicable additional storage charges
```

This excludes other infrastructure charges.

### B. EC2 launch type pricing

With ECS on EC2, you pay for:
- EC2 instances.
- EBS volumes.
- Load Balancers.
- Data transfer.
- CloudWatch.
- Other supporting services.

ECS orchestration itself does not add a separate charge.

### C. Other production costs

| AWS resource | Cost consideration |
|---|---|
| Fargate | vCPU and memory usage |
| EC2 | Instance uptime and storage |
| ALB | Load Balancer hours and capacity units |
| NAT Gateway | Hourly charge and data processing |
| ECR | Image storage and data transfer |
| CloudWatch Logs | Ingestion and retention |
| Container Insights | Monitoring charges |
| Public IPv4 | Applicable public IPv4 charges |
| EFS | Storage and throughput |
| Data transfer | Depends on traffic and destination |

### D. Ways to reduce ECS costs

1. Right-size CPU and memory.
2. Use ARM64/Graviton images where compatible.
3. Scale tasks according to demand.
4. Use Fargate Spot for interruption-tolerant workloads.
5. Use EC2 capacity providers for suitable predictable workloads.
6. Reduce unnecessary log ingestion and retention.
7. Avoid unnecessary NAT Gateway data processing.
8. Use Savings Plans for stable Fargate usage where appropriate.
9. Remove unused container images.
10. Avoid running unnecessary tasks 24/7.

AWS pricing references:
- Fargate: https://aws.amazon.com/fargate/pricing/
- ECS: https://aws.amazon.com/ecs/pricing/

Always calculate costs using your selected region and actual task configuration.

## 17. Important ECS troubleshooting scenarios

| Problem | Possible reason |
|---|---|
| Task stops immediately | Application crash, bad command or missing configuration |
| Cannot pull image | ECR permissions, networking or incorrect image URI |
| Task stuck in PENDING | Insufficient capacity or placement constraints |
| ALB health check fails | Wrong port, path or application not ready |
| ECS service cannot start tasks | IAM, subnet, IP capacity or capacity problem |
| Container cannot access S3 | Task role missing permissions or networking issue |
| Cannot send logs | Execution role or CloudWatch connectivity issue |
| ECS deployment fails | Bad image, failed health checks or insufficient capacity |
| Task cannot retrieve secrets | Execution role or KMS permissions issue |
| ECS Exec does not work | Missing permissions, configuration or SSM connectivity |

## 18. ECS interview questions

**Q1. What is ECS?**

A fully managed AWS container orchestration service.

**Q2. What is the difference between ECS and EKS?**

ECS is AWS's native container orchestration service. EKS is AWS's managed Kubernetes service.

**Q3. What is the difference between ECS and Fargate?**

ECS manages container orchestration. Fargate provides serverless compute capacity to run ECS tasks.

**Q4. What is an ECS cluster?**

A logical grouping of ECS services and tasks.

**Q5. What is an ECS task definition?**

A blueprint describing how containers should run.

**Q6. What is an ECS task?**

A running instance of a task definition.

**Q7. What is an ECS service?**

A resource that maintains the desired number of running tasks.

**Q8. What is the difference between task role and execution role?**

Execution role allows ECS to perform startup operations such as pulling images and sending logs. Task role grants permissions to the application inside the container.

**Q9. Can ECS use an ALB?**

Yes. An Application Load Balancer can distribute traffic across ECS tasks.

**Q10. Why does Fargate use awsvpc networking?**

Each Fargate task gets its own network interface and private IP address.

**Q11. Can ECS run multiple containers in one task?**

Yes. A task definition can contain multiple containers, with a maximum of ten containers per task.

**Q12. What happens when an ECS task crashes?**

An ECS Service attempts to launch a replacement task to maintain the desired count.

**Q13. How does ECS scale?**

You can scale the service's desired task count using Application Auto Scaling and CloudWatch metrics.

**Q14. What is a capacity provider?**

It determines how ECS obtains compute capacity, such as Fargate or EC2 Auto Scaling capacity.

**Q15. How do you deploy a new version?**

Build and push a new image to ECR, register a new task definition revision, and update the ECS service.

**Q16. What is ECS Exec?**

A feature that allows authorized operators to execute commands inside a running container.

**Q17. What is the difference between ECS Service and RunTask?**

An ECS Service maintains a desired number of tasks. RunTask starts standalone tasks that are not automatically maintained by a service.

**Q18. What is the difference between desired count and running count?**

Desired count is how many tasks ECS should maintain. Running count is how many tasks are currently running.

**Q19. How do you secure ECS tasks?**

Use private subnets, Security Groups, task IAM roles, secrets management, encrypted storage and trusted container images.

**Q20. How do you reduce ECS costs?**

Right-size resources, autoscale, use Fargate Spot where appropriate, optimize logs and select the right capacity model.
