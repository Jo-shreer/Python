# AWS KMS — Interview Notes

## 1. What is AWS KMS?

**AWS Key Management Service (KMS) is a managed service for creating and managing encryption keys and performing cryptographic operations.**

Simple mental model:

```text
Application / AWS Service
          |
          | encrypt / decrypt
          v
         KMS
          |
          v
     Encryption Key
```

KMS is primarily about **key management and cryptographic operations**.

It is **not** a general-purpose password/secret store.

---

# 2. Why Do We Need KMS?

Suppose your application stores sensitive data:

```text
CSV
 ↓
S3
```

You don't want someone who obtains access to the underlying storage to automatically be able to read the data.

Encryption provides protection:

```text
Plaintext
   |
   v
Encryption
   |
   v
Ciphertext
```

To get the original data back:

```text
Ciphertext
   |
   v
Decryption
   |
   v
Plaintext
```

KMS helps manage the encryption keys used for this process.

---

# 3. Encryption at Rest vs Encryption in Transit

This distinction is important.

## Encryption at Rest

Protects data while it is stored.

Examples:

```text
S3
DynamoDB
SQS
RDS
Redshift
Secrets Manager
```

Conceptually:

```text
Application
     |
     v
Encrypted storage
```

---

## Encryption in Transit

Protects data while it is moving between systems.

For example:

```text
Client
  |
  | HTTPS/TLS
  v
API Gateway
```

KMS is primarily associated with **encryption at rest and key management**.

TLS certificates and protocols handle encryption in transit.

---

# 4. KMS Key

The central concept is the **KMS key**.

Conceptually:

```text
KMS
 |
 +--- Key A
 |
 +--- Key B
 |
 +--- Key C
```

Different keys can be used for different applications or security requirements.

For example:

```text
ETL encryption key
Application encryption key
Database encryption key
```

The exact key-management strategy depends on the organization's security architecture.

---

# 5. AWS-Managed vs Customer-Managed KMS Keys

Two important concepts:

### AWS-managed key

AWS manages the key for a particular AWS service/use case.

For example, services can provide AWS-managed encryption keys for common encryption scenarios.

### Customer-managed key

Your organization creates/manages the KMS key and has more control over things such as:

* Key policies
* Rotation configuration
* Access
* Grants
* Lifecycle

For interview purposes:

> **Customer-managed keys give the organization more direct control over key policies and usage.**

---

# 6. KMS Key Policy

This is extremely important.

A KMS key has a **key policy** that controls who can use/manage the key.

Conceptually:

```text
KMS Key
   |
   v
Key Policy
   |
   +--> Who can manage the key?
   |
   +--> Who can use the key?
```

This is different from a normal IAM permission policy.

KMS authorization can involve:

```text
IAM policy
     +
KMS key policy
     +
other AWS policy controls
```

So when troubleshooting KMS `AccessDenied`, don't look only at the Lambda IAM role.

---

# 7. KMS + IAM

Suppose Lambda needs to access an encrypted S3 object.

Architecture:

```text
Lambda
  |
  | S3 GetObject
  v
S3
  |
  | encrypted with KMS
  v
KMS
```

The Lambda execution role may need appropriate permissions to use the KMS key.

Depending on the configuration, permissions can include actions such as:

```text
kms:Decrypt
```

for decrypting data.

For encryption, you may see:

```text
kms:Encrypt
```

and for data-key workflows:

```text
kms:GenerateDataKey
```

The exact permissions depend on the service and integration.

---

# 8. KMS + S3

This is particularly relevant to your ETL project.

Your architecture:

```text
CSV
 ↓
S3
 ↓
Lambda
```

The S3 bucket can use encryption.

For example:

```text
S3 Object
    |
    v
SSE-KMS
    |
    v
KMS Key
```

When an authorized application reads the object, AWS handles the encryption/decryption integration.

You generally don't write code like:

```python
kms.decrypt(...)
```

every time you download an SSE-KMS encrypted S3 object.

The AWS service integration handles the encryption layer.

Your application needs the appropriate permissions.

---

# 9. KMS + SQS

SQS messages can also be encrypted.

Conceptually:

```text
Lambda 1
   |
   v
SQS
   |
   | encrypted
   v
KMS
```

This protects messages at rest.

In your project, the SQS message was something like:

```json
{
  "file_key": "incoming/customer_20260829.csv"
}
```

You could encrypt the queue so that the message data is protected while stored.

# 10. KMS + DynamoDB

DynamoDB supports encryption at rest.

Conceptually:

```text
Lambda
   |
   v
DynamoDB
   |
   v
Encryption
```

KMS can be involved depending on the encryption-key configuration.

Your metadata such as:

```json
{
  "file_key": "incoming/customer.csv",
  "status": "VALIDATED"
}
```

can therefore be protected while stored.

# 11. KMS + Secrets Manager

This is a very important distinction.

### KMS

```text
Manage encryption keys
```

### Secrets Manager

```text
Store application secrets
```

For example:

```text
Secrets Manager
       |
       v
Database password
```

Secrets Manager encrypts secrets at rest.

KMS provides the key-management/encryption capability behind that protection.

Conceptually:

```text
Application
     |
     v
Secrets Manager
     |
     | encrypted
     v
KMS
```

You normally retrieve the secret through Secrets Manager rather than manually implementing your own encryption scheme.

---

# 12. KMS vs Secrets Manager

Interview question:

> "What's the difference between KMS and Secrets Manager?"

Answer:

| KMS                       | Secrets Manager                           |
| ------------------------- | ----------------------------------------- |
| Manages encryption keys   | Stores secrets                            |
| Cryptographic operations  | Secret retrieval/management               |
| Encrypt/decrypt           | Passwords, API keys, tokens, credentials  |
| Key policies              | Secret policies                           |
| Used by many AWS services | Uses encryption to protect stored secrets |

Simple rule:

> **KMS manages keys; Secrets Manager manages secrets.**

---

# 13. Envelope Encryption

This is a useful interview concept.

Instead of using a KMS key to directly encrypt a huge file, applications/services commonly use a **data key**.

Conceptually:

```text
                 KMS
                  |
            Generate Data Key
                  |
          +-------+-------+
          |               |
     Plaintext         Encrypted
      data key          data key
          |               |
          v               v
      Encrypt data     Store safely
```

The actual data is encrypted using the data key.

The KMS key protects the data key.

This is called **envelope encryption**.

You don't necessarily need to implement this yourself because AWS services can handle these patterns for you.

---

# 14. Why Not Just Store the Encryption Key in S3?

Because then the key and encrypted data could be compromised together.

Bad design:

```text
S3
 |
 +--> encrypted-data.csv
 |
 +--> encryption-key.txt
```

Better:

```text
S3
 |
 +--> encrypted-data.csv

KMS
 |
 +--> encryption key
```

The key is managed separately with access controls and auditing.

---

# 15. Key Rotation

Encryption keys can have rotation strategies.

The goal is to reduce the risk associated with using the same cryptographic key indefinitely.

For interview purposes:

> "KMS supports key rotation mechanisms, and customer-managed keys can be configured according to the organization's security requirements."

Don't confuse **key rotation** with automatically re-encrypting every historical object yourself.

---

# 16. KMS Grants

KMS also supports **grants**, which can provide permissions to use a KMS key.

You don't need deep knowledge of grants for this interview.

Just know that KMS authorization can involve more than a simple IAM policy.

---

# 17. KMS and Least Privilege

Suppose Lambda only needs to decrypt using a particular key.

Don't give it broad permissions such as:

```text
kms:*
```

Prefer:

```text
kms:Decrypt
```

and restrict the permission to the required key/resource where appropriate.

This follows the principle of:

> **Least privilege.**

# 19. KMS AccessDenied Scenario

Interview question:

> "Lambda can access an S3 bucket, but it gets AccessDenied when reading an encrypted object. What would you check?"

A strong troubleshooting approach:

```text
Lambda
   |
   v
S3
   |
   v
KMS
```

Check:

1. Does the object exist?
2. Does Lambda have `s3:GetObject`?
3. Is the object encrypted with SSE-KMS?
4. Which KMS key is being used?
5. Does the Lambda execution role have the required KMS permissions?
6. Does the KMS key policy allow the required principal?
7. Is there an explicit deny?
8. Are there permissions boundaries or SCPs affecting access?

This demonstrates that you understand:

> **S3 permission and KMS permission are separate authorization concerns.**

# 20. Common Interview Trap

### Question:

> "If I give my Lambda `s3:GetObject`, can it always read the object?"

Not necessarily.
If the object is encrypted using a customer-managed KMS key, the Lambda may also need the appropriate KMS permissions.
Think:
```text
S3 access
   +
KMS access
   =
Ability to read encrypted object
```
Subject to the full AWS authorization evaluation.
---

# 21. KMS vs IAM
These services are also easy to confuse.
### IAM
Answers:
> **Who is allowed to perform which AWS actions?**
### KMS
Answers:
> **How are encryption keys managed and cryptographic operations performed?**

They work together.
```text
IAM
 |
 | Lambda allowed to use key
 v
KMS
 |
 v
Encryption key
```
---
# 22. KMS vs CloudTrail
Another useful distinction:
### KMS
Encryption/key management.
### CloudTrail
Auditing AWS API activity.
For example:

```text
Lambda
  |
  | kms:Decrypt
  v
KMS
```
CloudTrail can provide an audit trail of AWS API activity, depending on the event/logging configuration.
So:
```text
KMS      → encryption/key management
CloudTrail → API auditing
CloudWatch  → monitoring/observability
```
---

# 23. Interview Answer — "What is KMS?"
A strong answer:
> "AWS KMS is a managed key-management service used to create and control encryption keys and perform cryptographic operations. AWS services such as S3, SQS, DynamoDB, RDS and Secrets Manager can use KMS for encryption at rest. KMS also integrates with IAM and key policies to control who can use encryption keys."
---
# 24. Interview Answer — "How did you use KMS in an ETL architecture?"
If the interviewer asks about your architecture, don't claim specific implementation details you didn't personally manage.
A safe answer is:
> "KMS is relevant to securing the AWS services in the ETL architecture. For example, S3, SQS and DynamoDB can use encryption at rest, including KMS-backed encryption depending on the configuration. From an application perspective, the important part is ensuring the Lambda execution roles have the appropriate permissions to access encrypted resources."
If you actually configured KMS in the project, you can make this answer more specific.

---

# 25. Key Takeaways
Remember these four lines:
```text
IAM
→ Who can access what?
KMS
→ How are encryption keys managed?
Secrets Manager
→ Where do application secrets live?
CloudTrail
→ Who performed which AWS API activity?
```
And the most important KMS distinction:

> **KMS manages encryption keys; it is not a database for storing application passwords.**
