# AWS Lambda Configuration — Grouped by Owner

## Configuration Ownership Summary

| Owner | AWS resource / location | Main settings it controls |
|---|---|---|
| **Lambda Function Owner** | `aws_lambda_function` | Runtime, handler, memory, timeout, environment variables, architecture, layers, ephemeral storage |
| **IAM and Security Owner** | `aws_iam_role`, `aws_iam_role_policy`, `aws_lambda_permission` | Execution role, AWS API permissions, trust policy, who can invoke the function |
| **SQS Queue Owner** | `aws_sqs_queue` | Visibility timeout, message retention, encryption, long polling, redrive policy, DLQ |
| **Lambda Event Source Mapping Owner** | `aws_lambda_event_source_mapping` | Which SQS queue triggers Lambda, batch size, batching window, concurrency limit, partial batch failures |
| **Asynchronous Invocation Owner** | `aws_lambda_function_event_invoke_config` | Retry attempts and maximum event age for asynchronous Lambda invocations |
| **Logging and Monitoring Owner** | `aws_cloudwatch_log_group`, CloudWatch alarms | Log retention, encryption, metrics, alarms, monitoring |
| **Release and Endpoint Owner** | Lambda versions, aliases, API Gateway, or Function URL resources | Deployment versions, traffic routing, HTTP endpoints, authentication |
| **Application Reliability Owner** | Python application code and database | Idempotency, validation, business-level retries, transaction safety, error handling |

### Quick rules to remember

- **Function settings** control how Lambda runs.
- **IAM settings** control what Lambda can access and who can invoke it.
- **SQS queue settings** control how messages are stored and made available again.
- **Event source mapping settings** control how Lambda consumes messages from SQS.
- **Async invocation settings** apply to asynchronous Lambda invocations, not SQS queue redelivery.
- **Application code and database constraints** protect business operations against duplicate processing.

**Example:** If an SQS-triggered Lambda keeps processing a failed message, check the SQS visibility timeout, event source mapping behavior, queue redrive policy, and application error handling. These settings belong to different owners, so changing only the Lambda timeout may not solve the problem.

### Lambda workload	Suggested starting memory
- Simple API request / lightweight task	128–256 MB
- Small SQS message processor	256–512 MB
- API with moderate data processing	512–1,024 MB
- CSV / JSON data transformation	1,024–3,072 MB
- CPU-intensive processing	2,048–10,240 MB, benchmark first

## 1. Lambda Memory

### What the memory setting controls

-   Lambda memory is configured **per function**.
-   Memory is the RAM available to an invocation.
-   More configured memory also provides more CPU power, which can
    improve performance.
-   Memory and timeout are separate settings: a function can have
    sufficient memory but still time out, or run out of memory before
    its timeout.

### Memory range

-   AWS Lambda memory can be configured from **128 MB to 10,240 MB (10
    GB)** in 1 MB increments.
-   Choose a value based on measured memory use, duration, and cost
    rather than automatically choosing the maximum.

### Choosing a starting point

Illustrative starting points, not universal AWS recommendations:

  Workload                                  Possible starting range
  ------------------------------ ----------------------------------
  Lightweight API handler                               128--256 MB
  Small SQS message processor                           256--512 MB
  Moderate data transformation                        512--1,024 MB
  Larger data processing                            1,024--3,072 MB
  CPU-intensive processing         Benchmark higher memory settings

### How to tune it

Monitor CloudWatch metrics and logs, especially: - **Max Memory Used** -
**Duration** - **Errors** - **Throttles**, where relevant

If memory use is close to the configured limit, increase memory or
reduce the amount of data held at once. Benchmark different memory
settings because extra CPU may reduce duration enough to offset some of
the additional cost.

## 2. Processing Large Files: Memory vs. Chunking

Suppose a Lambda needs to process a 500 MB CSV file stored in S3.

### Loading the whole file

If code loads the entire file into a Python list, dictionaries, or a
DataFrame, RAM use can be much larger than the original file size.
Parsing creates additional objects and temporary copies.

### Processing in chunks

A more memory-efficient approach is to: 1. Store the original file in
S3. 2. Read a manageable number of rows or a portion of the file at a
time. 3. Transform and validate that portion. 4. Write the results. 5.
Release the chunk's memory before processing the next one.

Chunk size depends on the workload; a 5 MB chunk is only an example, not
a standard.

### When to choose each approach

-   **Moderate file and modest memory use:** increasing Lambda memory
    may be sufficient.
-   **Large file:** consider streaming or chunked processing.
-   **Work that can be split into independent units:** consider storing
    the file/chunks in S3 and sending work references through SQS.
-   **Long-running orchestration:** consider Step Functions or a service
    better suited to long-running batch work, such as AWS Batch or AWS
    Glue, depending on the task.

**Important:** Do not put large file contents directly into SQS
messages. Store the data in S3 and put a reference (for example, bucket,
object key, and possibly byte range or chunk identifier) in the SQS
message. Design retries and idempotency carefully.

## 3. SQS Standard vs. FIFO

### Standard queue

-   Provides **at-least-once delivery**.
-   Ordering is **best effort**, not guaranteed.
-   Duplicate deliveries can occur.
-   A Lambda event source mapping polls the queue and invokes the
    configured Lambda function with batches of messages.
-   It is not an arbitrary Lambda instance simply deciding to pick a
    message; the event source mapping connects the specific queue to the
    configured function.
-   Multiple batches can be processed concurrently, so do not rely on
    one message finishing before another.

### FIFO queue

-   Preserves ordering **within the same `MessageGroupId`**.
-   Messages in different message groups can be processed concurrently.
-   FIFO does not mean that all messages in the entire queue must be
    processed serially.
-   Deduplication helps with duplicate sends, but application-level
    idempotency is still important.

### Example

For one order, the sequence might be: 1. `OrderCreated` 2.
`PaymentCompleted` 3. `OrderShipped`

If these messages must be processed in sequence, use a FIFO queue and
give the messages for that order the same `MessageGroupId`. Other orders
can use different group IDs to allow concurrency.

### Summary

  -----------------------------------------------------------------------
  Feature                 Standard                FIFO
  ----------------------- ----------------------- -----------------------
  Ordering                Best effort             Guaranteed within a
                                                  message group

  Concurrent processing   Yes                     Across different
                                                  message groups

  Duplicate delivery      Possible                Still design for safe
                                                  duplicate handling

  Common use              Independent tasks       Tasks requiring ordered
                                                  processing
  -----------------------------------------------------------------------

## 4. Lambda ZIP Deployment Packages and Dependencies

### What is a deployment ZIP?

A ZIP package bundles the Lambda handler code and the Python
dependencies that need to be deployed with it.

For example, if the handler is configured as:

``` hcl
handler = "app.lambda_handler"
```

then `app.py` contains a function named `lambda_handler`.

### Dependencies

-   Python standard-library modules (such as `json`) do not need to be
    installed separately.
-   External libraries (for example, `requests`) must be packaged,
    supplied by a compatible Lambda Layer, or included in a container
    image.
-   AWS SDK libraries such as `boto3` are available in Lambda Python
    runtimes, but packaging a deliberately selected version can help
    control dependencies.

Example project:

``` text
process-payment/
├── app.py
├── requirements.txt
├── tests/
└── terraform/
```

A simplified ZIP build might look like:

``` bash
mkdir -p build/package
python -m pip install -r requirements.txt -t build/package/
cp app.py build/package/
cd build/package
zip -r ../../deployment.zip .
```

For production, install from a pinned/locked dependency set, use a build
environment compatible with the Lambda runtime and architecture, test
the package, and verify its contents and size.

### ZIP size limits

-   The combined **unzipped** size of the function package and attached
    Lambda Layers must not exceed **250 MB**.
-   The direct compressed ZIP upload limit is commonly 50 MB; S3 can be
    used to supply larger compressed deployment ZIPs.
-   Using S3 changes the upload path, not the 250 MB combined unzipped
    limit.

Always check the current AWS Lambda quotas documentation when limits or
deployment paths are relevant.

## 5. Lambda Layers

### What is a Layer?

A Lambda Layer is a separately packaged archive containing libraries or
other files that a ZIP-based Lambda function can use. A layer can be
attached to multiple functions.

A Python layer commonly uses this structure:

``` text
layer.zip
└── python/
    ├── requests/
    ├── urllib3/
    └── ...
```

### The five-layer limit

-   A ZIP-based Lambda function can attach **up to five layers**.
-   This is a limit on the number of layer archives attached to a
    function, not on the number of libraries inside a layer.
-   One layer can contain many compatible Python packages.
-   The combined unzipped size of the function package and all its
    layers must remain within the 250 MB limit.

### Can one layer be enough?

Yes. One layer is allowed, and it may be suitable if it has a clear
purpose and its dependencies are compatible.

For a production system, do not automatically put every dependency for
every function into one giant shared layer.

Potential issues with one giant layer: - Functions carry libraries they
do not use. - Dependency version requirements may conflict. - A shared
dependency update can affect many consumers. - The layer may make
deployments and ownership harder to manage. - The function package plus
layers can exceed the combined size limit.

### Production-oriented approach

Consider three dependency categories:

1.  **Function-specific dependencies:** package them with the function's
    code ZIP.
2.  **Stable, genuinely shared dependencies:** use a purpose-specific,
    versioned Layer when shared management is useful.
3.  **Large or complex dependency stacks:** consider a Lambda container
    image, especially when system libraries or package size make ZIP
    packaging awkward.

A layer is not mandatory. Its value is in sharing and managing
dependencies---not merely avoiding a few duplicated files.

### Layer versioning

-   Published Lambda Layer versions are immutable.
-   Publishing a new layer version does not automatically update
    functions already using an older version.
-   Update consumers deliberately after testing compatibility.
-   A separate layer pipeline can be useful when the layer has its own
    ownership or release lifecycle.

## 6. Lambda Container Images and ECR

A Lambda container image can include: - Application code - Python
dependencies - A Lambda-compatible runtime/base image - Required system
libraries

A typical workflow: 1. Build the image using a Dockerfile. 2. Run tests
and security scans. 3. Push the image to a private Amazon ECR
repository. 4. Configure Lambda to use the image. 5. Deploy and validate
the release.

Container images can be up to **10 GB uncompressed**, unlike the ZIP
package limit. Lambda container-image functions cannot have Lambda
Layers attached.

Production considerations: - Scan images for vulnerabilities. - Keep
base images and dependencies patched. - Use immutable image digests for
release identification rather than relying only on a mutable tag such as
`latest`. - Container images add build, security, and lifecycle
responsibilities, so use them when their benefits justify that
complexity.

## 7. S3, Artifact Storage, and Versioning

S3 can store deployment ZIPs and other build artifacts. A deployment
bucket might use keys such as:

``` text
s3://company-lambda-artifacts/
├── layers/
│   └── common-python/release-13/layer.zip
└── functions/
    ├── create-order/commit-a81f2c/function.zip
    └── process-payment/commit-c93f5a/function.zip
```

These names are illustrative.

### Distinguish three kinds of versioning

-   **S3 object versioning:** keeps prior versions of an object when a
    key is overwritten.
-   **Lambda Layer versioning:** a published layer version, referenced
    by a layer-version ARN.
-   **Lambda function versioning:** a published snapshot of function
    code and configuration.

Production recommendations: - Use unique, immutable artifact keys. -
Enable S3 versioning where appropriate, but do not rely on it alone as
the release strategy. - Restrict who can upload, overwrite, or delete
artifacts. - Apply retention and lifecycle policies carefully. - Record
artifact hashes/digests and release metadata so deployed artifacts can
be traced back to source code and pipeline runs.

S3 is managed storage: AWS operates the underlying infrastructure, but
the team remains responsible for permissions, encryption settings,
retention, versioning, and cost controls.

## 8. How CI/CD Processes Dependencies

### CI: Build and validate

A continuous integration pipeline typically: 1. Checks out the source
revision. 2. Sets up a compatible build environment. 3.
Resolves/installs dependencies from a pinned or locked definition. 4.
Builds the ZIP package, Layer ZIP, or container image. 5. Runs unit
tests and package/integration checks. 6. Scans dependencies and images
for vulnerabilities. 7. Checks artifact structure, runtime
compatibility, architecture, and size. 8. Publishes the tested artifact
to controlled artifact storage.

### CD: Release and deploy

A continuous delivery/deployment pipeline typically: 1. Retrieves the
approved build artifact. 2. Deploys infrastructure/configuration using
Terraform or another deployment tool. 3. Publishes a new Layer version
when deploying a Layer artifact. 4. Updates Lambda functions to
reference the intended layer version and code artifact. 5. Runs smoke
tests and checks logs/metrics. 6. Promotes the release through
environments such as staging and production, with approvals where
appropriate. 7. Maintains a rollback path.

Terraform normally manages AWS resources and configuration. It does not
automatically resolve and install Python dependencies; the CI build
process does that work.

### Build once, promote the same artifact

Build and test an artifact once, then promote that exact artifact
through environments. Do not rebuild a different set of dependencies for
production after testing another artifact in staging.

For container images, record and deploy the tested digest. For ZIPs and
layers, track the artifact hash, S3 location/version where applicable,
and published AWS version references.

## 9. Recommended Production Dependency Strategy

For a system with many Lambda functions:

-   Default to **per-function packages** for dependencies used only by
    that function.
-   Use **purpose-specific shared Layers** when common dependencies have
    compatible versions and a separately managed release is beneficial.
-   Use **container images** for large or complex dependency stacks that
    are awkward to manage as ZIP packages.
-   Avoid a giant shared Layer just to eliminate duplication.
-   Pin dependency versions and build in a compatible environment.
-   Test consumers before rolling out shared dependency changes.
-   Use CI/CD to scan, validate, version, and promote artifacts.
-   Keep releases traceable and reversible.

### Example release flow

``` text
Git commit
   |
   v
CI resolves locked dependencies
   |
   v
Build function ZIP and/or Layer ZIP
   |
   v
Tests + security scans + size/compatibility checks
   |
   v
Store immutable artifacts in S3
   |
   v
CD/Terraform publishes Layer version and deploys function
   |
   v
Smoke tests + monitoring
   |
   v
Promote the same tested artifact to production
```

**Core principle:** Share dependencies when doing so improves
maintainability, but preserve independently testable deployments. The
pipeline should make every deployed code package and dependency version
explicit, repeatable, secure, and traceable.
