## 1. What is AWS Lambda?

AWS Lambda is a serverless compute service that runs your code in response to events without requiring you to provision or manage servers.

You upload your code, configure its runtime and execution settings, and Lambda runs it when invoked.

You pay primarily for:
- Number of requests.
- Execution duration.
- Allocated memory.
- Additional features such as provisioned concurrency and certain data transfer or networking usage.

Lambda automatically manages the underlying compute infrastructure, including server allocation, operating system maintenance, and scaling.

### Typical use cases

- Backend APIs.
- Processing S3 uploads.
- Processing SQS messages.
- Consuming DynamoDB Streams.
- Scheduled jobs.
- Event-driven workflows.
- Data transformation.
- Real-time event processing.
- Step Functions tasks.
- Lightweight automation.

### When Lambda is a good choice

Use Lambda when:
- Workloads are event-driven.
- Execution time is bounded.
- You want automatic scaling.
- You do not want to manage servers.
- Traffic is variable or unpredictable.
- You want to pay for execution rather than continuously running compute.

Consider ECS, EKS, or another compute service when:
- Your application needs to run continuously.
- Workloads regularly exceed Lambda's execution limits.
- You need specialized host-level control.
- You need long-running processes or persistent local processes.

## 2. Lambda architecture

A typical Lambda execution flow:

1. An event source generates an event.
2. The event is delivered to Lambda directly or through an event source mapping.
3. Lambda identifies the function and checks whether it can execute.
4. Lambda creates or reuses an execution environment.
5. The runtime initializes your application.
6. Your handler processes the event.
7. The function returns a response or completes processing.
8. Lambda records execution metrics and sends configured logs to CloudWatch Logs.

### Important components

| Component | Description |
|---|---|
| Function | Your deployed application code and configuration |
| Runtime | Language runtime, such as Python, Node.js, Java, or .NET |
| Handler | Entry point invoked by Lambda |
| Execution role | IAM role assumed by Lambda |
| Execution environment | Isolated environment used to execute function code |
| Trigger | Event source that causes invocation |
| Layer | Reusable code or dependencies |
| Version | Immutable published snapshot of function code and configuration |
| Alias | Named pointer to a published version |
| Event source mapping | Polls supported event sources and invokes Lambda |
| Destination | Target for asynchronous invocation outcomes |
| Dead-letter queue | Destination for certain failed asynchronous events |
| Extension | Companion process that integrates with the execution environment |

## 3. Lambda invocation types

There are three important invocation models.

### A. Synchronous invocation

The caller waits for Lambda to finish and receives its response.

Examples:
- API Gateway.
- Application Load Balancer.
- AWS SDK Invoke API.
- Lambda function URL.
- Synchronous Step Functions tasks.

Flow:

Application → Lambda → Response

Characteristics:
- Caller receives the result.
- Function errors are returned to the caller.
- Lambda does not automatically retry a failed synchronous invocation.
- The caller controls its own retry behavior.
- The caller may have its own timeout limit.

Terraform permission example for API Gateway:

```hcl
resource "aws_lambda_permission" "allow_apigateway" {
  statement_id  = "AllowExecutionFromAPIGateway"
  action        = "lambda:InvokeFunction"
  function_name = aws_lambda_function.api.function_name
  principal     = "apigateway.amazonaws.com"

  source_arn = "${aws_apigatewayv2_api.api.execution_arn}/*/*"
}
```

### B. Asynchronous invocation

Lambda accepts the event and queues it internally. The caller does not wait for the function to finish.

Examples:
- S3 notifications.
- SNS notifications.
- EventBridge rules.
- Direct SDK invocation with asynchronous invocation type.

Flow:

Event source → Lambda internal queue → Function

Characteristics:
- The caller receives an acceptance response, not the function result.
- Lambda retries failures according to its asynchronous invocation configuration.
- Events can be delivered more than once.
- Processing should be idempotent.
- Events can expire or be discarded after configured retry and age limits.
- Configure destinations or a dead-letter queue to handle failures.

Terraform asynchronous invocation configuration:

```hcl
resource "aws_lambda_function_event_invoke_config" "async" {
  function_name = aws_lambda_function.worker.function_name

  maximum_event_age_in_seconds = 3600
  maximum_retry_attempts       = 2

  destination_config {
    on_failure {
      destination = aws_sqs_queue.failure_queue.arn
    }

    on_success {
      destination = aws_sqs_queue.success_queue.arn
    }
  }
}
```

### C. Poll-based invocation

Lambda polls an event source and invokes your function when records are available.

Examples:
- SQS.
- Kinesis Data Streams.
- DynamoDB Streams.
- Amazon MSK.
- Self-managed Kafka.
- Amazon MQ.

The event source mapping controls polling, batching, filtering, concurrency, and other processing settings.

Terraform SQS event source mapping:

```hcl
resource "aws_lambda_event_source_mapping" "sqs" {
  event_source_arn = aws_sqs_queue.jobs.arn
  function_name    = aws_lambda_function.worker.arn

  batch_size                         = 10
  maximum_batching_window_in_seconds = 5
  enabled                            = true
}
```

Important: SQS and stream-based event source mappings have different delivery and retry behavior. For example, SQS messages are deleted after successful processing, whereas Kinesis and DynamoDB Streams use checkpointing.

## 4. Lambda runtimes and handler

A runtime provides the language environment in which your function executes.

Common runtime families include:
- Python.
- Node.js.
- Java.
- .NET.
- Ruby.
- Go.
- Custom runtime using the Lambda Runtime API.

Check AWS documentation for currently supported runtime versions because older runtimes eventually reach deprecation.

### Python handler example

```python
import json

def lambda_handler(event, context):
    print("Received event:", json.dumps(event))

    return {
        "statusCode": 200,
        "body": json.dumps({
            "message": "Hello from Lambda"
        })
    }
```

### Handler format

For a Python deployment package:

```hcl
handler = "app.lambda_handler"
```

This means:
- `app` is the Python module or file.
- `lambda_handler` is the function inside that module.

For Node.js, a typical handler configuration looks like:

```hcl
handler = "index.handler"
```

### The event object

The event contains the input passed by the invoker.

Examples:
- API Gateway request.
- S3 object notification.
- SQS messages.
- DynamoDB Stream records.
- EventBridge event.

### The context object

The context provides runtime information, including:
- Function name.
- Function version.
- Request ID.
- Remaining execution time.
- Memory limit.
- Log group and log stream.

Python example:

```python
def lambda_handler(event, context):
    remaining = context.get_remaining_time_in_millis()

    print("Request ID:", context.aws_request_id)
    print("Remaining time:", remaining)

    return {"statusCode": 200}
```

Do not assume every event source has the same event structure. Build and test handlers against the actual event schema.

## 5. Lambda execution environment

Lambda runs a function inside an execution environment.

The environment can be reused for subsequent invocations.

It generally contains:
- Runtime.
- Function code.
- Configured layers.
- Environment variables.
- Temporary `/tmp` storage.
- Execution role credentials.
- Runtime and extension processes.

### Cold start

A cold start happens when Lambda needs to initialize a new execution environment.

It can involve:
- Environment provisioning.
- Runtime initialization.
- Loading function code.
- Loading dependencies.
- Static initialization.
- Extension initialization.

Cold starts can increase initial invocation latency.

### Warm invocation

When Lambda reuses an existing execution environment, it can avoid some initialization work.

Important:
- Warm reuse is not guaranteed.
- You must not depend on an environment remaining alive.
- Do not store important application state only in global variables.
- Do not assume `/tmp` contents survive indefinitely.
- Do not assume the same environment handles all requests.

### Best practices

- Initialize reusable SDK clients outside the handler.
- Keep initialization lightweight.
- Reuse database connections where appropriate.
- Avoid downloading large dependencies during every invocation.
- Keep function packages small.
- Use provisioned concurrency for latency-sensitive workloads.
- Use SnapStart where supported and appropriate.

## 7. Terraform: basic Lambda function

Example using a ZIP deployment package.

```hcl
resource "aws_iam_role" "lambda_role" {
  name = "example-lambda-role"

  assume_role_policy = jsonencode({
    Version = "2012-10-17"

    Statement = [{
      Effect = "Allow"

      Principal = {
        Service = "lambda.amazonaws.com"
      }

      Action = "sts:AssumeRole"
    }]
  })
}

resource "aws_iam_role_policy_attachment" "basic_execution" {
  role = aws_iam_role.lambda_role.name

  policy_arn = "arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole"
}

resource "aws_lambda_function" "example" {
  function_name = "example-function"

  role = aws_iam_role.lambda_role.arn

  runtime = "python3.12"
  handler = "app.lambda_handler"

  filename         = "${path.module}/function.zip"
  source_code_hash = filebase64sha256("${path.module}/function.zip")

  memory_size = 512
  timeout     = 30

  architectures = ["arm64"]

  environment {
    variables = {
      ENVIRONMENT = "production"
      LOG_LEVEL   = "INFO"
    }
  }

  ephemeral_storage {
    size = 1024
  }

  tracing_config {
    mode = "Active"
  }

  depends_on = [
    aws_iam_role_policy_attachment.basic_execution
  ]
}
```

Important:
- `source_code_hash` helps Terraform detect package changes.
- `runtime` must be a runtime currently supported by AWS.
- The ZIP must contain the handler module at the expected package path.
- The execution role is assumed by Lambda.
- The basic execution policy provides CloudWatch Logs permissions.
- This example uses a local ZIP file. A production pipeline may publish artifacts to S3 or ECR.

## 8. Lambda execution role and permissions

Every Lambda function has an execution role.

Lambda assumes this role when running the function.

The role determines what AWS resources the function can access.

Examples:
- Read objects from S3.
- Write items to DynamoDB.
- Send messages to SQS.
- Publish to SNS.
- Read secrets from Secrets Manager.
- Write logs to CloudWatch.
- Access KMS keys.

### Trust policy

The trust policy controls who can assume the role.

For Lambda, the trusted service principal is:

```json
{
  "Effect": "Allow",
  "Principal": {
    "Service": "lambda.amazonaws.com"
  },
  "Action": "sts:AssumeRole"
}
```

### Permission policy

The permission policy controls what the role can do.

Example: allow Lambda to read from a specific S3 bucket.

Terraform:

```hcl
resource "aws_iam_role_policy" "s3_read" {
  name = "lambda-s3-read"

  role = aws_iam_role.lambda_role.id

  policy = jsonencode({
    Version = "2012-10-17"

    Statement = [{
      Effect = "Allow"

      Action = [
        "s3:GetObject"
      ]

      Resource = "arn:aws:s3:::my-bucket/*"
    }]
  })
}
```

### Important permission distinction

There are two separate permission directions:

1. Execution role permissions:
   What the Lambda function is allowed to access.

2. Lambda resource-based permissions:
   Which external principals or services are allowed to invoke the function.

For example:
- Lambda execution role permits reading an S3 object.
- Lambda resource policy permits S3 to invoke the Lambda function.

Both may be needed in an integration.

### Least privilege

Avoid:
- `Action = "*"` unless genuinely necessary.
- `Resource = "*"` when resource-level restrictions are supported.
- Giving every Lambda the same broad execution role.
- Storing long-lived access keys in environment variables.

## 9. Lambda triggers and integrations

Lambda can be invoked by many AWS services.

### Common integrations

| Service | Integration model | Typical use |
|---|---|---|
| API Gateway | Synchronous | REST or HTTP backend |
| Application Load Balancer | Synchronous | HTTP application |
| S3 | Asynchronous | File processing |
| SNS | Asynchronous | Notifications |
| EventBridge | Asynchronous | Event-driven processing |
| SQS | Event source mapping | Queue processing |
| DynamoDB Streams | Event source mapping | Change data capture |
| Kinesis | Event source mapping | Stream processing |
| Step Functions | Sync or async task patterns | Workflow orchestration |
| CloudWatch Events / EventBridge Scheduler | Scheduled invocation | Scheduled jobs |
| Cognito | Synchronous trigger | Authentication workflows |
| CloudFormation | Custom resource invocation | Infrastructure lifecycle hooks |

The invocation model and retry behavior depend on the integration.

### A. S3 trigger

Example: invoke Lambda when an object is created.

```hcl
resource "aws_s3_bucket" "source" {
  bucket = "my-lambda-source-bucket"
}

resource "aws_s3_bucket_notification" "notification" {
  bucket = aws_s3_bucket.source.id

  lambda_function {
    lambda_function_arn = aws_lambda_function.example.arn
    events              = ["s3:ObjectCreated:*"]
    filter_prefix       = "uploads/"
    filter_suffix       = ".json"
  }

  depends_on = [
    aws_lambda_permission.allow_s3
  ]
}

resource "aws_lambda_permission" "allow_s3" {
  statement_id  = "AllowS3Invoke"
  action        = "lambda:InvokeFunction"
  function_name = aws_lambda_function.example.function_name
  principal     = "s3.amazonaws.com"
  source_arn    = aws_s3_bucket.source.arn
}
```

Important:
- S3 notification configuration is associated with the bucket.
- Only one notification configuration should be managed for a bucket in a Terraform state to avoid overwriting other notification rules.
- Avoid recursive triggers, such as writing processed objects back into the same prefix that triggers the function.
- Use prefixes and suffixes to filter events.
- S3 event notifications are delivered at least once and can be delayed or duplicated.

### B. SQS trigger

```hcl
resource "aws_sqs_queue" "jobs" {
  name                       = "lambda-jobs"
  visibility_timeout_seconds = 180
}

resource "aws_lambda_event_source_mapping" "sqs" {
  event_source_arn = aws_sqs_queue.jobs.arn
  function_name    = aws_lambda_function.example.arn

  batch_size                         = 10
  maximum_batching_window_in_seconds = 5
  function_response_types            = ["ReportBatchItemFailures"]
}
```

The Lambda execution role needs permission to consume messages, commonly through the AWS managed `AWSLambdaSQSQueueExecutionRole` policy or an equivalent least-privilege policy.

Important:
- The queue visibility timeout should be configured with Lambda execution and retry behavior in mind. AWS recommends at least six times the function timeout, plus the maximum batching window.
- Messages that repeatedly fail can eventually go to the SQS dead-letter queue if configured on the source queue.
- Partial batch response lets Lambda retry only failed messages rather than the entire batch.
- SQS event source mappings provide at-least-once processing, so implement idempotency.

### C. DynamoDB Streams trigger

```hcl
resource "aws_lambda_event_source_mapping" "dynamodb" {
  event_source_arn = aws_dynamodb_table.orders.stream_arn
  function_name    = aws_lambda_function.example.arn

  starting_position = "LATEST"

  batch_size                         = 100
  maximum_batching_window_in_seconds = 5

  function_response_types = ["ReportBatchItemFailures"]
}
```

The DynamoDB table must have Streams enabled.

Example Terraform table setting:

```hcl
stream_enabled   = true
stream_view_type = "NEW_AND_OLD_IMAGES"
```

The Lambda role needs appropriate DynamoDB Streams read permissions.

### D. EventBridge scheduled invocation

```hcl
resource "aws_cloudwatch_event_rule" "schedule" {
  name                = "lambda-every-five-minutes"
  schedule_expression = "rate(5 minutes)"
}

resource "aws_cloudwatch_event_target" "lambda" {
  rule = aws_cloudwatch_event_rule.schedule.name
  arn  = aws_lambda_function.example.arn
}

resource "aws_lambda_permission" "allow_eventbridge" {
  statement_id  = "AllowEventBridge"
  action        = "lambda:InvokeFunction"
  function_name = aws_lambda_function.example.function_name
  principal     = "events.amazonaws.com"
  source_arn    = aws_cloudwatch_event_rule.schedule.arn
}
```

For more sophisticated schedules, use EventBridge Scheduler.

### E. API Gateway integration

API Gateway invokes Lambda synchronously.

A common architecture:

Client → API Gateway → Lambda → DynamoDB

Lambda permission must allow API Gateway to invoke the function.

API Gateway handles the public HTTP endpoint, while Lambda handles application logic.

## 10. Lambda networking and VPC

Lambda is not required to run inside your VPC.

This is an important architectural distinction.

### Lambda outside your VPC

By default, Lambda runs in an AWS-managed network environment.

It can access supported AWS services without you attaching it to your VPC.

However, this does not mean the function has an automatically assigned public IP address or unrestricted inbound network access.

### Lambda inside your VPC

Attach Lambda to VPC subnets when it needs private access to resources such as:
- RDS.
- Aurora.
- ElastiCache.
- Internal services.
- Private EC2 instances.
- Private endpoints.

Terraform:

```hcl
resource "aws_lambda_function" "vpc_function" {
  function_name = "vpc-lambda"

  role    = aws_iam_role.lambda_role.arn
  runtime = "python3.12"
  handler = "app.lambda_handler"

  filename = "${path.module}/function.zip"

  vpc_config {
    subnet_ids = [
      aws_subnet.private_a.id,
      aws_subnet.private_b.id
    ]

    security_group_ids = [
      aws_security_group.lambda.id
    ]
  }
}
```

### Security group

```hcl
resource "aws_security_group" "lambda" {
  name   = "lambda-security-group"
  vpc_id = aws_vpc.main.id

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}
```

In production, restrict egress to the destinations and ports the function actually needs.

### Private subnet considerations

A Lambda function attached to private subnets can access:
- Private resources through VPC routing.
- AWS services through VPC endpoints.
- Public internet through NAT when correctly configured.

A Lambda function in a private subnet does not automatically receive internet access.

### NAT Gateway

Use NAT when the function needs outbound internet access or public AWS service endpoints that are not otherwise reachable through configured endpoints.

Typical flow:

Lambda → Private subnet → Route table → NAT Gateway → Internet Gateway → Internet

### VPC endpoints

Use VPC endpoints to access supported AWS services privately.

Examples:
- S3 gateway endpoint.
- DynamoDB gateway endpoint.
- Secrets Manager interface endpoint.
- CloudWatch Logs interface endpoint.
- ECR interface endpoints.

S3 and DynamoDB gateway endpoints are commonly used without NAT for those services.

### Important networking facts

- Lambda VPC attachment is optional.
- Lambda needs suitable subnet IP capacity for scaling.
- Lambda creates and manages Hyperplane ENIs for VPC connectivity.
- The execution role needs the permissions required for Lambda to manage VPC network interfaces; the AWS managed `AWSLambdaVPCAccessExecutionRole` policy is a common starting point.
- The function's security group controls its network traffic.
- Database security groups must permit traffic from the Lambda security group.
- A VPC-attached Lambda does not become a publicly reachable server.
- VPC attachment can affect cold-start and scaling behavior, although Hyperplane ENIs reduce the overhead of traditional per-environment ENI creation.

## 11. Lambda memory, CPU, timeout, and ephemeral storage

### Memory

`memory_size` controls allocated memory.

Supported range: 128 MB to 10,240 MB.

Memory also affects the amount of CPU available to the function.

More memory can improve:
- CPU-bound processing.
- Compression.
- Image processing.
- Data transformation.
- Network-intensive workloads in some cases.

Terraform:

```hcl
memory_size = 1024
```

Do not automatically choose the smallest memory setting. Benchmark execution time and total cost.

### Timeout

`timeout` controls the maximum execution duration.

Maximum Lambda timeout: 900 seconds (15 minutes).

Terraform:

```hcl
timeout = 60
```

Set a timeout based on:
- Expected workload duration.
- Downstream API timeouts.
- Database query timeouts.
- Retry behavior.
- Caller timeout constraints.

A function timeout should not exceed the timeout of a synchronous caller where the caller must receive the response.

### Ephemeral storage

Lambda provides temporary storage under `/tmp`.

Default: 512 MB.

Configurable range: 512 MB to 10,240 MB.

Terraform:

```hcl
ephemeral_storage {
  size = 2048
}
```

Use `/tmp` for:
- Temporary files.
- Downloaded objects.
- Intermediate processing data.
- Unzipped files.

It is not a durable storage service.

### Architecture

Lambda supports:
- `x86_64`
- `arm64`

Terraform:

```hcl
architectures = ["arm64"]
```

ARM can provide better price-performance for compatible workloads, but dependencies and native binaries must support the selected architecture.

## 12. Lambda concurrency and scaling

Concurrency means the number of function invocations running at the same time.

Approximate relationship:

Concurrency = Requests per second × Average execution duration in seconds

Example:

- 100 requests per second.
- Average duration: 2 seconds.

Approximate concurrency = 200.

### A. Unreserved concurrency

Lambda uses the account's available concurrency pool for functions without a reservation.

### B. Reserved concurrency

Reserved concurrency sets a concurrency reservation for a function.

It:
- Reserves capacity for that function.
- Limits the function's maximum concurrency.
- Protects other functions from being starved by this function.

Terraform:

```hcl
resource "aws_lambda_function" "example" {
  # Other function configuration omitted

  reserved_concurrent_executions = 100
}
```

Setting reserved concurrency to zero disables invocation processing for that function.

### C. Provisioned concurrency

Provisioned concurrency keeps a specified number of execution environments initialized and ready.

Useful for:
- APIs with strict latency requirements.
- User-facing applications.
- Predictable traffic patterns.
- Workloads sensitive to cold starts.

Provisioned concurrency is configured against a published version or alias.

Terraform:

```hcl
resource "aws_lambda_alias" "live" {
  name             = "live"
  function_name    = aws_lambda_function.example.function_name
  function_version = aws_lambda_function.example.version
}

resource "aws_lambda_provisioned_concurrency_config" "live" {
  function_name                     = aws_lambda_function.example.function_name
  qualifier                         = aws_lambda_alias.live.name
  provisioned_concurrent_executions = 5
}
```

### D. Maximum concurrency for event sources

Event source mappings can have their own concurrency controls, depending on the source.

For SQS, you can configure maximum concurrency:

```hcl
resource "aws_lambda_event_source_mapping" "sqs" {
  event_source_arn = aws_sqs_queue.jobs.arn
  function_name    = aws_lambda_function.example.arn

  scaling_config {
    maximum_concurrency = 50
  }
}
```

For Kinesis and DynamoDB Streams, parallelization and shard-level concurrency settings have different semantics.

### Important concurrency considerations

- Account concurrency quotas are regional.
- Function reserved concurrency consumes part of the account's concurrency capacity.
- Provisioned concurrency has additional cost.
- Downstream systems may not scale as quickly as Lambda.
- Limit concurrency when protecting databases or external APIs.
- Use SQS buffering to absorb bursts.

## 13. Lambda versions and aliases

### Version

A published Lambda version is an immutable snapshot of the function code and configuration.

Examples:
- Version 1.
- Version 2.
- Version 3.

Terraform:

```hcl
resource "aws_lambda_function" "example" {
  function_name = "versioned-function"

  role    = aws_iam_role.lambda_role.arn
  runtime = "python3.12"
  handler = "app.lambda_handler"

  filename         = "${path.module}/function.zip"
  source_code_hash = filebase64sha256("${path.module}/function.zip")

  publish = true
}
```

### Alias

An alias is a named pointer to a published version.

Examples:
- dev.
- test.
- staging.
- production.
- live.

Terraform:

```hcl
resource "aws_lambda_alias" "production" {
  name             = "production"
  function_name    = aws_lambda_function.example.function_name
  function_version = aws_lambda_function.example.version
}
```

### Weighted alias routing

You can gradually shift traffic between two versions.

Example:

```hcl
resource "aws_lambda_alias" "production" {
  name             = "production"
  function_name    = aws_lambda_function.example.function_name
  function_version = "10"

  routing_config {
    additional_version_weights = {
      "11" = 0.1
    }
  }
}
```

This sends approximately:
- 90% to version 10.
- 10% to version 11.

Use aliases for controlled deployments and rollbacks.

## 14. Lambda deployment package types

Lambda supports two main package types.

### A. ZIP package

Contains:
- Application code.
- Dependencies.
- Runtime-specific files.

Suitable for:
- Python.
- Node.js.
- Java.
- .NET.
- Go.
- Other supported runtimes.

Terraform:

```hcl
resource "aws_lambda_function" "zip_function" {
  function_name = "zip-function"

  package_type = "Zip"

  filename = "${path.module}/function.zip"

  source_code_hash = filebase64sha256(
    "${path.module}/function.zip"
  )

  role    = aws_iam_role.lambda_role.arn
  runtime = "python3.12"
  handler = "app.lambda_handler"
}
```

Useful for:

- Custom runtimes.
- Existing container build workflows.

Terraform:

```hcl
resource "aws_lambda_function" "container" {
  function_name = "container-lambda"

  package_type = "Image"

  image_uri = "123456789012.dkr.ecr.eu-west-1.amazonaws.com/my-lambda:latest"

  memory_size = 1024
```

- The ECR repository must be in the same Region as the function.
- The image must support the selected architecture.
- The image must implement the Lambda runtime interface.
- Lambda container images can be up to 10 GB uncompressed, including all layers.
- Container image deployment is not the same as deploying a conventional ECS service.

## 15. Lambda layers

A layer is a ZIP archive containing reusable code or dependencies.

Examples:
- Shared Python libraries.
- Common Node.js modules.
- Monitoring agents.
- Custom runtime components.

Terraform:

```hcl
resource "aws_lambda_layer_version" "common" {
  layer_name = "common-dependencies"

  filename = "${path.module}/layer.zip"

  compatible_runtimes = ["python3.12"]

  compatible_architectures = ["arm64"]
}
```

Attach it:

```hcl
resource "aws_lambda_function" "example" {
  # Other configuration omitted

  layers = [
    aws_lambda_layer_version.common.arn
  ]
}
```

Important:
- Layers are versioned.
- A function can attach up to five layers.
- The combined unzipped size of the function and layers must fit within Lambda's deployment package limits.
- A layer does not replace application dependency management.
- Container image functions use container image contents rather than Lambda layers.

## 16. Environment variables and secrets

Environment variables provide configuration to Lambda.

Terraform:

```hcl
environment {
  variables = {
    ENVIRONMENT = "production"
    TABLE_NAME  = "orders"
    LOG_LEVEL   = "INFO"
  }
}
```

Use them for non-sensitive configuration such as:
- Table names.
- Feature flags.
- Environment identifiers.
- Service URLs.
- Log levels.

Do not place plaintext passwords, API keys, or database credentials in Terraform configuration or Lambda environment variables.

### Secrets Manager

Store secrets in AWS Secrets Manager.

Terraform permission example:

```hcl
resource "aws_iam_role_policy" "secrets_access" {
  name = "lambda-secrets-access"
  role = aws_iam_role.lambda_role.id

  policy = jsonencode({
    Version = "2012-10-17"

    Statement = [{
      Effect = "Allow"

      Action = [
        "secretsmanager:GetSecretValue"
      ]

      Resource = aws_secretsmanager_secret.database.arn
    }]
  })
}
```

The function retrieves the secret at runtime using the AWS SDK.

If the secret uses a customer-managed KMS key, the function may also need appropriate `kms:Decrypt` permissions and the key policy must permit the operation.

### Systems Manager Parameter Store

Use Parameter Store for configuration and suitable secret-storage use cases.

The function needs the relevant `ssm:GetParameter` or `ssm:GetParameters` permission.

## 17. Lambda security

Important security controls:

### Execution role
- Use least privilege.
- Separate roles for different functions.
- Restrict resource ARNs.
- Avoid broad wildcard permissions.

### Resource-based policies
- Restrict which services and accounts can invoke the function.
- Use `source_arn` and, where appropriate, `source_account`.
- Review cross-account invocation permissions.

### Encryption
- Lambda encrypts environment variables at rest by default.
- Use customer-managed KMS keys when additional control is required.
- Encrypt data in S3, DynamoDB, SQS, and other downstream services.
- Protect secrets separately.

### Code integrity
- Use Lambda code signing where required.
- Restrict deployment permissions.
- Scan dependencies and container images.
- Pin dependencies and use trusted build pipelines.

### Network security
- Use private subnets when private resource access is required.
- Restrict security group egress.
- Use VPC endpoints where appropriate.
- Avoid exposing sensitive internal services.

### Logging security
- Do not log passwords, access tokens, secrets, or unnecessary personal information.
- Apply retention policies.
- Restrict access to CloudWatch log groups.

## 18. Lambda error handling and retries

Error handling depends on the invocation model.

### Synchronous invocation

The caller receives the function error.

The caller decides whether and when to retry.

### Asynchronous invocation

Lambda retries failed function executions according to asynchronous invocation configuration.

You can configure:
- Maximum retry attempts.
- Maximum event age.
- On-success destination.
- On-failure destination.
- Dead-letter queue for supported failure handling.

### SQS event source mapping

Lambda polls SQS and invokes the function with batches of messages.

Important:
- Failed messages become visible again after the visibility timeout.
- A redrive policy can move repeatedly failing messages to a DLQ.
- Partial batch responses help avoid retrying successfully processed messages.
- The function should handle duplicate messages safely.

### Kinesis and DynamoDB Streams

These use checkpointing and shard processing.

Important settings include:
- Batch size.
- Maximum batching window.
- Starting position.
- Maximum retry attempts.
- Maximum record age.
- Bisect batch on function error.
- On-failure destination.
- Parallelization factor.
- Partial batch failure reporting.

### Idempotency

Idempotency means processing the same event multiple times produces the intended result without duplicating side effects.

Examples:
- Use a unique event ID.
- Store processed event IDs in DynamoDB.
- Use conditional writes.
- Use transaction conditions.
- Use idempotency keys for payment operations.

Do not assume an event will be delivered exactly once.

## 19. Lambda destinations and dead-letter queues

### Destinations

Destinations are configured for asynchronous invocation outcomes.

They can route:
- Successful executions.
- Failed executions.

Supported destination types include:
- SQS.
- SNS.
- EventBridge.
- Another Lambda function.

### Dead-letter queue

A DLQ is used for certain failed asynchronous invocations.

SQS event source mapping failures are generally handled through the source queue's redrive policy, not the Lambda asynchronous DLQ setting.

### Example Terraform DLQ

```hcl
resource "aws_sqs_queue" "lambda_dlq" {
  name = "lambda-failure-dlq"
}
```

For asynchronous invocation, configure `dead_letter_config` on the Lambda function and give the execution role the required send-message permission.

Use destinations when you need richer invocation outcome records and separate success/failure routing.

## 21. Lambda SnapStart

SnapStart reduces cold-start latency by initializing a function and creating a snapshot that can be restored for later execution environments.

It is useful for supported runtimes and workloads with expensive initialization.

Terraform example:

```hcl
resource "aws_lambda_function" "java_function" {
  function_name = "java-snapstart"

  role    = aws_iam_role.lambda_role.arn
  runtime = "java21"
  handler = "example.Handler::handleRequest"

  filename = "${path.module}/function.zip"

  publish = true

  snap_start {
    apply_on = "PublishedVersions"
  }
}
```

Important:
- Runtime and feature support can change; check the current AWS compatibility documentation.
- SnapStart is configured for published versions.
- Applications must handle snapshot restoration correctly.
- Do not assume initialization-time connections, random values, or temporary credentials remain valid after restore.
- SnapStart and provisioned concurrency solve related but different latency problems; check compatibility before combining features.

## 22. Lambda and EFS

Lambda can mount Amazon EFS for shared persistent file storage.

Use EFS when:
- Functions need shared files.
- Data exceeds practical `/tmp` usage.
- Multiple execution environments need access to shared file data.
- Existing applications require a file system interface.

Terraform:

```hcl
resource "aws_lambda_function" "efs_function" {
  function_name = "efs-lambda"

  role    = aws_iam_role.lambda_role.arn
  runtime = "python3.12"
  handler = "app.lambda_handler"

  filename = "${path.module}/function.zip"

  file_system_config {
    arn              = aws_efs_access_point.lambda.arn
    local_mount_path = "/mnt/shared"
  }

  vpc_config {
    subnet_ids         = [aws_subnet.private_a.id]
    security_group_ids = [aws_security_group.lambda.id]
  }
}
```

Important:
- Lambda must be VPC-connected to mount EFS.
- EFS mount targets must be reachable.
- Security groups must permit NFS traffic on TCP port 2049.
- The execution role and EFS access point permissions must be configured correctly.
- EFS is persistent shared storage; `/tmp` is temporary local storage.

## 23. Lambda URLs

A Lambda function URL provides an HTTPS endpoint directly to a Lambda function.

It can be useful for simple HTTP workloads that do not need the full capabilities of API Gateway.

Terraform:

```hcl
resource "aws_lambda_function_url" "url" {
  function_name      = aws_lambda_function.example.function_name
  authorization_type = "AWS_IAM"

  cors {
    allow_origins = ["https://example.com"]
    allow_methods = ["GET", "POST"]
    allow_headers = ["content-type", "authorization"]
    max_age       = 300
  }
}
```

Authorization types:
- `AWS_IAM`: requests must be authorized using AWS IAM.
- `NONE`: endpoint is publicly accessible unless other controls restrict access.

Important:
- A function URL is associated with a function or alias.
- Configure resource-based permissions appropriately.
- `NONE` does not mean the endpoint is safe for unrestricted production use.
- Use API Gateway when you need richer API management, request validation, usage plans, API keys, advanced authorization, or API lifecycle features.

## 24. Lambda and Step Functions

Step Functions orchestrates workflows, while Lambda performs individual compute tasks.

Example:

Step Functions → Lambda A → Lambda B → DynamoDB

Use Step Functions when:
- Multiple tasks need orchestration.
- You need retry and catch logic.
- You need branching or parallel execution.
- You need long-running workflows.
- You need execution history and workflow visibility.

Avoid putting an entire complex workflow into one large Lambda function.

A useful design principle:

Lambda = compute unit.

Step Functions = workflow orchestration.

## 25. Lambda and database connections

Lambda can access:
- DynamoDB.
- RDS.
- Aurora.
- ElastiCache.
- OpenSearch.
- External databases.

### RDS connection problem

Lambda can scale rapidly, creating many concurrent database connections.

This can overwhelm a database.

Use:
- Amazon RDS Proxy.
- Connection pooling.
- Reserved concurrency.
- Short-lived transactions.
- Appropriate database timeouts.
- Query optimization.

### RDS Proxy

RDS Proxy manages and pools database connections.

It helps reduce connection overhead and improve database resilience.

The Lambda function still needs:
- VPC connectivity.
- Database credentials.
- IAM or database authentication as configured.
- Network access to the proxy.
- Appropriate database permissions.

## 26. Lambda limits and important exceptions

Always check current AWS quotas before production deployment.

Important limits include:

| Feature | Important limit or behavior |
|---|---|
| Maximum execution time | 15 minutes |
| Memory | 128 MB to 10,240 MB |
| `/tmp` storage | 512 MB to 10,240 MB |
| ZIP deployment package | 50 MB direct upload limit; larger packages can be uploaded through S3 |
| Combined unzipped code and layers | 250 MB |
| Container image | Up to 10 GB uncompressed |
| Layers | Up to 5 per function |
| Environment variables | 4 KB total |
| File descriptors | 1,024 |
| Execution processes/threads | 1,024 per execution environment |
| Payload | Invocation payload limits depend on invocation type; synchronous and asynchronous limits differ |
| Concurrency | Regional quota, adjustable through AWS Service Quotas |
| Function timeout | Up to 900 seconds |

Additional exceptions:
- Lambda does not provide durable local storage.
- Lambda does not guarantee execution environment reuse.
- Lambda is not designed for unlimited long-running processes.
- Lambda does not automatically make a VPC-attached function internet-accessible.
- Event source delivery is not universally exactly once.
- A function's timeout does not extend the timeout of its caller.
- Function URLs and API Gateway have different feature sets.
- Provisioned concurrency is not free.
- Lambda concurrency can overwhelm downstream services.
- Runtime deprecation can affect deployments and support.
- Event source mapping behavior differs between SQS, streams, Kafka, and other sources.

## 27. Lambda cost model

Lambda costs depend on:
- Number of requests.
- Execution duration.
- Allocated memory.
- Architecture.
- Provisioned concurrency.
- Additional services used by the function.

### Request charges

You pay based on the number of invocations, subject to applicable free-tier and pricing terms.

### Compute charges

Compute is based on allocated memory and execution duration.

A function with:
- 1 GB memory.
- 2-second execution.
- 1 million requests.

Consumes approximately 2 million GB-seconds of compute.

This is a simplified calculation; actual billing depends on AWS metering and applicable pricing rules.

### Other costs

You may also pay for:
- CloudWatch Logs ingestion and storage.
- X-Ray tracing.
- NAT Gateway.
- VPC interface endpoints.
- SQS, SNS, EventBridge.
- S3, DynamoDB, RDS.
- Provisioned concurrency.
- Data transfer.
- EFS storage and throughput.

### Cost optimization

- Benchmark memory settings.
- Use ARM where compatible.
- Reduce unnecessary initialization.
- Avoid excessive logging.
- Use SQS batching where appropriate.
- Avoid unnecessary NAT traffic.
- Use provisioned concurrency only when justified.
- Reduce repeated downstream calls.
- Set concurrency limits to protect expensive dependencies.

## 28. Production-ready Terraform example

This example combines:
- Lambda function.
- IAM execution role.
- CloudWatch logging.
- Environment variables.
- VPC attachment.
- Reserved concurrency.
- Active tracing.
- SQS event source mapping.
- Partial batch failure reporting.

```hcl
resource "aws_iam_role" "worker" {
  name = "production-worker-role"

  assume_role_policy = jsonencode({
    Version = "2012-10-17"

    Statement = [{
      Effect = "Allow"

      Principal = {
        Service = "lambda.amazonaws.com"
      }

      Action = "sts:AssumeRole"
    }]
  })
}

resource "aws_iam_role_policy_attachment" "basic" {
  role = aws_iam_role.worker.name

  policy_arn = "arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole"
}

resource "aws_iam_role_policy_attachment" "vpc" {
  role = aws_iam_role.worker.name

  policy_arn = "arn:aws:iam::aws:policy/service-role/AWSLambdaVPCAccessExecutionRole"
}

resource "aws_iam_role_policy_attachment" "sqs" {
  role = aws_iam_role.worker.name

  policy_arn = "arn:aws:iam::aws:policy/service-role/AWSLambdaSQSQueueExecutionRole"
}

resource "aws_cloudwatch_log_group" "worker" {
  name              = "/aws/lambda/production-worker"
  retention_in_days = 30
}

resource "aws_lambda_function" "worker" {
  function_name = "production-worker"

  role = aws_iam_role.worker.arn

  runtime = "python3.12"
  handler = "app.lambda_handler"

  filename         = "${path.module}/worker.zip"
  source_code_hash = filebase64sha256("${path.module}/worker.zip")

  memory_size = 1024
  timeout     = 60

  architectures = ["arm64"]

  reserved_concurrent_executions = 50

  environment {
    variables = {
      ENVIRONMENT = "production"
      LOG_LEVEL   = "INFO"
      QUEUE_NAME  = aws_sqs_queue.jobs.name
    }
  }

  vpc_config {
    subnet_ids = [
      aws_subnet.private_a.id,
      aws_subnet.private_b.id
    ]

    security_group_ids = [
      aws_security_group.lambda.id
    ]
  }

  tracing_config {
    mode = "Active"
  }

  logging_config {
    log_format = "JSON"
    log_group  = aws_cloudwatch_log_group.worker.name
  }

  depends_on = [
    aws_iam_role_policy_attachment.basic,
    aws_iam_role_policy_attachment.vpc,
    aws_iam_role_policy_attachment.sqs
  ]
}

resource "aws_lambda_event_source_mapping" "jobs" {
  event_source_arn = aws_sqs_queue.jobs.arn
  function_name    = aws_lambda_function.worker.arn

  batch_size                         = 10
  maximum_batching_window_in_seconds = 5

  function_response_types = [
    "ReportBatchItemFailures"
  ]

  scaling_config {
    maximum_concurrency = 25
  }
}
```

Production notes:
- The referenced VPC, subnets, security group, and SQS queue must exist.
- Configure the SQS visibility timeout appropriately for the function timeout and batching window.
- Add only the permissions the function actually needs.
- The example uses AWS managed policies for simplicity; production environments may prefer narrower custom policies.
- Ensure the function's handler implements partial batch failure reporting correctly.
- Configure an SQS redrive policy and DLQ.
- Add CloudWatch alarms.
- Configure deployment through CI/CD rather than manually uploading ZIP files.
- If the function accesses a database, consider RDS Proxy and concurrency controls.
- If the function requires public outbound access, configure NAT or suitable VPC endpoints.

## 29. Common Lambda errors

| Error | Common cause | Typical fix |
|---|---|---|
| AccessDeniedException | Missing IAM permission | Add least-privilege policy |
| Task timed out | Execution exceeds timeout | Optimize or increase timeout |
| TooManyRequestsException | Concurrency throttling | Review concurrency and quotas |
| Runtime.ImportModuleError | Missing dependency or incorrect package structure | Fix ZIP packaging |
| Handler not found | Incorrect handler configuration | Correct module and handler |
| Unable to import module | Runtime or dependency mismatch | Rebuild for correct runtime |
| Network connection timeout | VPC routing or security group issue | Check routes, NAT, endpoints, and security groups |
| Database connection exhaustion | Too many concurrent DB connections | Use RDS Proxy and limit concurrency |
| Function not invoked | Missing resource permission or trigger configuration | Check event source and Lambda resource policy |
| SQS messages repeatedly reappear | Processing failure or visibility timeout too short | Fix handler and visibility timeout |
| Lambda throttled | Reserved or account concurrency exhausted | Review concurrency settings |
| InvalidParameterValueException | Invalid configuration | Check runtime, architecture, package, and event mapping settings |

## 32. Quick revision summary
