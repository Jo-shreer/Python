# AWS STEP FUNCTIONS — COMPLETE REFERENCE NOTES

## 1. What Is AWS Step Functions?

AWS Step Functions is a managed workflow orchestration service. It coordinates tasks, AWS services, decisions, parallel operations, retries, and error handling.

It uses state machines to define the sequence of steps in a workflow.

Example:

Order received → Validate order → Check inventory → Charge payment → Update database → Send confirmation

If a step fails, the workflow can retry it, follow an error-handling path, or stop with a failure.

Typical AWS architecture:

API Gateway → Step Functions → Lambda → DynamoDB → SNS

Another example:

S3 file uploaded → Step Functions → Validate file → Process records → Store results → Notify user

Important distinction:
- Step Functions orchestrates the workflow.
- Lambda or another integration performs the actual task.
- DynamoDB, S3, and other data services store or retrieve data.
- API Gateway can start a workflow, but it is not required for every workflow.

Official documentation:
https://docs.aws.amazon.com/step-functions/latest/dg/welcome.html

## 2. Core Concepts

### State machine
The complete workflow definition, including its states, transitions, and error handling.

### State
One step or operation in the workflow.

Examples:
- Task
- Choice
- Wait
- Parallel
- Map
- Pass
- Succeed
- Fail

### Execution
One running instance of a state machine.

For example, processing 1,000 orders can create 1,000 executions of the same state machine.

### Input and output
Data passed between states.

Example input:

```json
{
  "orderId": "ORD-123",
  "customerId": "CUST-456",
  "amount": 150
}
```

A state can select input fields, transform data, invoke a service, and return output for the next state.

### Transition
The movement from one state to another, typically controlled by `Next`, `Choice`, or a terminal state.

### Amazon States Language (ASL)
The JSON-based language used to define state machines.

### Workflow execution history
A record of the events that occurred during an execution. Availability and retention depend on the workflow type and logging configuration.

## 3. Workflow Types: Standard vs Express

There are two primary workflow types.

### A. Standard Workflows

Purpose:
- Long-running workflows.
- Order processing.
- Business processes.
- Approval workflows.
- Multi-step orchestration.
- Workflows requiring execution history and durable progress tracking.

Key characteristics:
- Maximum execution duration: up to one year.
- Execution history is available through Step Functions.
- Exactly-once workflow execution semantics by default, subject to retries and the behavior of integrated services.
- Supports callback patterns and supported synchronous integration patterns.
- Suitable for workflows that may wait for human approval or external events.

Important:
Exactly-once workflow execution does not guarantee that an external side effect happens exactly once. A task may perform an operation and fail before its completion is recorded. Use idempotency controls for operations such as charging a payment.

### B. Express Workflows

Purpose:
- High-volume, short-duration workflows.
- Event processing.
- IoT events.
- Streaming or ingestion workloads.
- Lightweight orchestration.

Key characteristics:
- Maximum execution duration: five minutes.
- Designed for high event throughput.
- Asynchronous Express uses at-least-once execution semantics.
- Synchronous Express uses at-most-once execution semantics.
- CloudWatch Logs can be configured for execution logging; do not assume a Standard-style execution history is available.

Important:
- Express is not a substitute for a long-running Standard workflow.
- Asynchronous Express workflows may process an event more than once.
- Synchronous Express workflows should not be assumed to retry automatically.
- Design duplicate-safe operations where appropriate.

### Quick selection

Use Standard when:
- The process can last minutes, hours, or days.
- Durable workflow history is important.
- You need callback or long-running workflow patterns.
- The business process requires robust orchestration.

Use Express when:
- The process finishes within five minutes.
- High-volume event processing is important.
- The execution semantics fit the application.
- You can manage the logging and observability requirements.

Official documentation:
https://docs.aws.amazon.com/step-functions/latest/dg/choosing-workflow-type.html

## 4. State Types and Their Parameters

### A. Task

Purpose:
Performs work by invoking a supported integration.

Examples:
- Invoke Lambda.
- Write to DynamoDB.
- Send a message to SQS.
- Start another supported AWS service operation.
- Call a supported HTTP endpoint.

Common parameters:
- `Type`: `"Task"`
- `Resource`: Integration ARN or supported resource identifier.
- `Parameters`: Input parameters sent to the integration in JSONPath workflows.
- `Arguments`: Arguments used in supported JSONata workflows.
- `ResultSelector`: Selects fields from the integration result in JSONPath workflows.
- `ResultPath`: Controls where the result is placed in the state input in JSONPath workflows.
- `OutputPath`: Filters the state output in JSONPath workflows.
- `Next`: Next state.
- `End`: Ends the current workflow path.
- `Retry`: Retry policy.
- `Catch`: Error-handling transitions.
- `TimeoutSeconds`: Maximum time allowed for the task.
- `HeartbeatSeconds`: Maximum allowed interval between heartbeats for supported task patterns.

Important:
The valid fields depend on the query language and integration pattern. JSONata workflows use different data transformation fields from JSONPath workflows.

### B. Choice

Purpose:
Branches the workflow based on conditions.

Example:
- If payment status is `APPROVED`, continue.
- If payment status is `DECLINED`, reject the order.
- Otherwise, send the order for review.

Common parameters:
- `Choices`
- `Variable` and comparison operators in JSONPath rules.
- `Condition` in JSONata rules.
- `Next`
- `Default`

Important:
A Choice state must have a valid matching transition or a `Default` path for unmatched conditions.

### C. Pass

Purpose:
Passes input forward, adds data, or transforms data without calling an external service.

Common parameters:
- `InputPath`
- `Parameters`
- `Result`
- `ResultPath`
- `OutputPath`
- `Next`
- `End`

In JSONata workflows, use the corresponding supported transformation fields instead of assuming all JSONPath fields apply.

### D. Wait

Purpose:
Pauses the workflow for a specified time or until a specified time.

Common parameters include:
- `Seconds`
- `SecondsPath`
- `Timestamp`
- `TimestampPath`
- `Next`
- `End`

Use cases:
- Wait before retrying.
- Schedule a follow-up action.
- Delay between business steps.
- Allow time for an external process.

A Wait state is not the same as a callback task waiting for an external party to respond.

### E. Parallel

Purpose:
Executes multiple branches concurrently and combines their results.

Example:

Order processing
- Branch 1: Validate inventory.
- Branch 2: Calculate tax.
- Branch 3: Check customer eligibility.

The workflow proceeds when all required branches finish successfully, unless error handling changes the outcome.

Common parameters:
- `Branches`
- `Next`
- `End`
- `Retry`
- `Catch`

Important:
A Parallel state is suitable for a known set of branches. For processing large collections of items, consider a Map state instead.

### F. Map

Purpose:
Runs a workflow for each item in a collection.

Example:
A list of 500 order items is processed item by item, potentially with controlled concurrency.

Common parameters depend on the Map mode and query language, but can include:
- `ItemsPath` for JSONPath-based item selection.
- `Items` for supported JSONata-based item expressions.
- `ItemSelector` for constructing each iteration's input.
- `ItemProcessor` for defining the processing workflow.
- `MaxConcurrency`.
- `MaxConcurrencyPath` where supported.
- `ResultPath`.
- `ResultSelector`.
- `ItemReader` for supported external data sources.
- `ResultWriter` for exporting results in supported Distributed Map configurations.
- `ToleratedFailureCount` and `ToleratedFailurePercentage` in supported Distributed Map configurations.

There are two main modes:

Inline Map:
- Suitable for smaller, simpler collections.
- Runs iterations within the parent workflow's execution context.
- Subject to the applicable workflow and history quotas.

Distributed Map:
- Designed for large-scale parallel processing.
- Can create child workflow executions.
- Can read supported data sources, including supported S3 datasets.
- Can write results to supported destinations, depending on configuration.
- Has separate concurrency and failure-tolerance settings.

Important:
Choose concurrency carefully. High concurrency can overwhelm Lambda, databases, external APIs, or downstream services.

### G. Succeed

Purpose:
Marks a successful terminal state.

### H. Fail

Purpose:
Marks the execution as failed.

Common parameters:
- `Error`
- `Cause`

Avoid putting credentials or sensitive customer data in error descriptions.

Official documentation:
https://docs.aws.amazon.com/step-functions/latest/dg/concepts-statemachines.html

## 5. JSONPath vs JSONata

Step Functions supports two query languages for processing state data.

### JSONPath

Traditionally used in Step Functions definitions.

Common fields:
- `InputPath`
- `Parameters`
- `ResultSelector`
- `ResultPath`
- `OutputPath`

These fields control which input is sent to a task, how the request is constructed, and how the result is combined with the original input.

### JSONata

A newer query language supported by Step Functions for data transformation and expression evaluation.

Common field:
- `QueryLanguage`

JSONata-based states can use fields such as:
- `Arguments`
- `Output`
- `Assign`
- `Condition` in applicable Choice rules.

### Important exceptions

- Do not copy JSONPath examples into a JSONata state without adapting the fields.
- A state machine can use JSONata as its default query language, and supported configurations can override the query language at state level.
- If the query language is not explicitly configured, existing definitions generally use JSONPath behavior.
- Validate expressions and field compatibility when changing query languages.

Official documentation:
https://docs.aws.amazon.com/step-functions/latest/dg/transforming-data.html

## 6. Input, Output, and Data Flow

Understanding data flow is essential for reliable Step Functions workflows.

Consider the input:

```json
{
  "orderId": "ORD-123",
  "customerId": "CUST-456",
  "amount": 150
}
```

A Lambda task might return:

```json
{
  "paymentStatus": "APPROVED",
  "transactionId": "TXN-789"
}
```

The workflow must decide whether to:
- Replace the original input with the task result.
- Add the task result to the original input.
- Select only specific fields.
- Transform the result before passing it onward.

### JSONPath data flow

Important fields:

`InputPath`
Selects which portion of the incoming state data is used.

`Parameters`
Builds the input passed to a task or integration.

`ResultSelector`
Transforms or selects fields from the raw task result.

`ResultPath`
Controls where the result is placed relative to the state input.

`OutputPath`
Selects which portion of the resulting state data is passed forward.

### Payload size

Step Functions has a maximum state/task input or output payload size of 256 KiB.

This applies to data passed between states and to relevant task inputs and outputs.

Best practices:
- Pass S3 object keys instead of large file contents.
- Pass database identifiers instead of entire records where possible.
- Store large datasets in S3 or another suitable data store.
- Use Distributed Map and supported S3 integrations for large-scale data processing.
- Avoid accumulating unnecessary results across many states.

Important:
A task can succeed at its backend but the workflow can still fail if the resulting payload exceeds a Step Functions limit.

## 7. Error Handling: Retry and Catch

Step Functions provides declarative error handling.

### Retry

Retries a failed task according to a configured policy.

Common retry parameters:
- `ErrorEquals`: Error names to match.
- `IntervalSeconds`: Initial wait before retry.
- `MaxAttempts`: Maximum retry attempts.
- `BackoffRate`: Multiplier applied to the delay.
- `MaxDelaySeconds`: Maximum retry delay where supported.
- `JitterStrategy`: Controls supported retry jitter behavior.

Example:

```json
{
  "Retry": [
    {
      "ErrorEquals": [
        "Lambda.ServiceException",
        "Lambda.TooManyRequestsException"
      ],
      "IntervalSeconds": 2,
      "MaxAttempts": 3,
      "BackoffRate": 2
    }
  ]
}
```

The configured values must match the service's actual error behavior and the required latency budget.

### Catch

Routes a failed task to another state.

Common parameters:
- `ErrorEquals`
- `Next`
- `ResultPath`

Example:
- Payment task fails.
- Catch routes to `HandlePaymentFailure`.
- The workflow records the failure or initiates compensation.

### Common errors

Examples include:
- `States.Timeout`
- `States.TaskFailed`
- `States.Permissions`
- `States.ResultPathMatchFailure`
- `States.DataLimitExceeded`

Error names and catch behavior depend on the failure type. Some terminal errors, including `States.DataLimitExceeded` in relevant circumstances, are not handled like ordinary retryable task failures.

Important:
- Do not retry every error indiscriminately.
- Retry transient failures, throttling, and temporary service issues where appropriate.
- Route permanent validation or business failures to explicit handling states.
- Account for downstream side effects before retrying.
- Use idempotency keys for operations that must not be duplicated.
- Configure retries at the appropriate level to avoid multiplicative retry storms.

Official documentation:
https://docs.aws.amazon.com/step-functions/latest/dg/concepts-error-handling.html

# AWS Step Functions — Complete Notes with Terraform and Production Examples

## 1. What is AWS Step Functions?

AWS Step Functions coordinates multiple steps in a workflow. Each step is called a **state**.

**Production example:** An e-commerce order workflow:
1. Check payment.
2. Check inventory for every product.
3. Reserve available inventory.
4. Handle failures and retry temporary errors.
5. Return the order result.

Terraform creates the state machine. The state machine definition describes the workflow. Lambda functions perform the actual business logic.

## 2. State types

| State type | Purpose |
|---|---|
| `Task` | Performs work, such as calling Lambda |
| `Choice` | Chooses a path based on conditions |
| `Map` | Processes each item in an array |
| `Parallel` | Runs multiple branches concurrently |
| `Pass` | Passes or transforms data without calling a service |
| `Wait` | Pauses execution for a specified time |
| `Succeed` | Ends successfully |
| `Fail` | Ends with a failure |

Other important fields:

- `StartAt`: First state to execute.
- `Next`: State to execute next.
- `End: true`: Finishes the current workflow or branch.
- `Retry`: Retries a failed state.
- `Catch`: Routes execution to an error-handling state.
- `TimeoutSeconds`: Sets a timeout for a state.

# 3. Input and output processing

This is one of the most important Step Functions concepts.

A Task state can receive input, transform it, call Lambda, process Lambda's response, and produce output.

The processing order is:

1. `InputPath`
2. `Parameters`
3. Task execution
4. `ResultSelector`
5. `ResultPath`
6. `OutputPath`

## Example input

Suppose the workflow receives:

```json
{
  "orderId": "ORD-101",
  "customer": {
    "name": "John",
    "city": "Dublin"
  },
  "productId": "P1",
  "quantity": 2,
  "internalNotes": "Priority customer"
}
```

## 3.1 InputPath — Select input

`InputPath` selects which part of the incoming JSON a state receives.

```json
"InputPath": "$.customer"
```

The state receives:

```json
{
  "name": "John",
  "city": "Dublin"
}
```

Use case: Pass only the customer information to a state.

If `InputPath` is omitted, the state receives the full input.

## 3.2 Parameters — Construct task input

`Parameters` creates the JSON sent to a Task, including a Lambda invocation.

```json
"Parameters": {
  "orderId.$": "$.orderId",
  "productId.$": "$.productId",
  "quantity.$": "$.quantity"
}
```

The Task receives:

```json
{
  "orderId": "ORD-101",
  "productId": "P1",
  "quantity": 2
}
```

Use case: Send only the fields Lambda needs instead of passing customer details or internal notes.

**Important:** A key ending in `.$` means its value is evaluated as a JSONPath expression. A key without `.$` is a literal value.

## 3.3 ResultSelector — Shape the task result

`ResultSelector` selects and renames fields from the result returned by a Task before storing it.

Suppose Lambda returns:

```json
{
  "StatusCode": 200,
  "Payload": {
    "available": true,
    "warehouse": "Dublin",
    "debugInfo": "Internal processing details"
  }
}
```

Use:

```json
"ResultSelector": {
  "available.$": "$.Payload.available",
  "warehouse.$": "$.Payload.warehouse"
}
```

The selected result becomes:

```json
{
  "available": true,
  "warehouse": "Dublin"
}
```

Use case: Keep only useful response fields and discard unnecessary details.

**Important:** `ResultSelector` shapes the task result; it does not select the original state input.

## 3.4 ResultPath — Decide where the result goes

`ResultPath` determines where the task result is stored in the original state input.

Suppose the original state input is:

```json
{
  "orderId": "ORD-101",
  "productId": "P1",
  "quantity": 2
}
```

The Task result is:

```json
{
  "available": true
}
```

Use:

```json
"ResultPath": "$.inventory"
```

The resulting state output becomes:

```json
{
  "orderId": "ORD-101",
  "productId": "P1",
  "quantity": 2,
  "inventory": {
    "available": true
  }
}
```

Common `ResultPath` values:

- `$.inventory`: Store the result under `inventory`.
- `$`: Replace the entire state input with the task result.
- `null`: Discard the task result and preserve the original input.

If omitted, `ResultPath` defaults to `$`, meaning the task result replaces the state input.

## 3.5 OutputPath — Select final state output

`OutputPath` filters the state output that is passed to the next state.

Suppose the current state output is:

```json
{
  "orderId": "ORD-101",
  "productId": "P1",
  "quantity": 2,
  "inventory": {
    "available": true,
    "warehouse": "Dublin"
  }
}
```

Use:

```json
"OutputPath": "$.inventory"
```

The next state receives:

```json
{
  "available": true,
  "warehouse": "Dublin"
}
```

Use case: Pass only the inventory result to the next state.

**Difference to remember:**

- `InputPath`: Filters incoming data.
- `Parameters`: Constructs the Task input.
- `ResultSelector`: Filters the task result.
- `ResultPath`: Combines the result with the original state input.
- `OutputPath`: Filters the final state output.

```json
  "paymentStatus": "PAID",
  "items": [
    {
```

## 4.2 Map — How items reach CheckInventory

`ItemsPath: "$.items"` selects the array.

`ItemSelector` creates input for each Map iteration:

```json
{
  "orderId.$": "$.orderId",
  "item.$": "$$.Map.Item.Value"
}
```

For the first item, the inner workflow receives:

```json
{
  "orderId": "ORD-101",
  "item": {
    "productId": "P1",
    "quantity": 2
  }
}
```

Then `Parameters` inside `CheckInventory` builds the Lambda request:

```json
{
  "orderId": "ORD-101",
  "productId": "P1",
  "quantity": 2
}
```

**Key point:** `ItemSelector` supplies the per-item input to the inner workflow. `Parameters` shapes the input sent by the Task to Lambda.

## 4.3 Lambda response

The example assumes the optimized Lambda integration response has a `Payload` containing:

```json
{
  "available": true,
  "warehouse": "Dublin"
}
```

`ResultSelector` extracts these fields, and `ResultPath` stores them under `inventory`.

The next state receives:

```json
{
  "orderId": "ORD-101",
  "item": {
    "productId": "P1",
    "quantity": 2
  },
  "inventory": {
    "available": true,
    "warehouse": "Dublin"
  }
}
```

`IsAvailable` checks `$.inventory.available`. If it is `true`, stock is reserved. Otherwise, the item is marked out of stock.

**Important:** The example uses `arn:aws:lambda:...:function:...` as the Task resource. For the `Payload` response shape shown here, use the optimized Lambda integration ARN form `arn:aws:states:::lambda:invoke`. With that integration, the `Parameters` object must wrap the function ARN and input as `FunctionName` and `Payload`. Adjust the two Task resources accordingly for a deployable optimized-integration version.

# 5. Retry and Catch

## Retry

Retries a task when a matching error occurs.

```json
"Retry": [
  {
    "ErrorEquals": ["Lambda.ServiceException"],
    "IntervalSeconds": 2,
    "MaxAttempts": 3,
    "BackoffRate": 2
  }
]
```

- `ErrorEquals`: Errors that trigger retries.
- `IntervalSeconds`: Initial delay.
- `MaxAttempts`: Maximum retry attempts.
- `BackoffRate`: Multiplies the delay after each attempt.

Use case: Retry temporary service failures.

## Catch

Routes execution to another state after an error.

```json
"Catch": [
  {
    "ErrorEquals": ["States.ALL"],
    "ResultPath": "$.processingError",
    "Next": "HandleError"
  }
]
```

- `ErrorEquals`: Errors to catch.
- `ResultPath`: Where to store error information.
- `Next`: Error-handling state.

Use case: Log an error, mark an order as failed, or start compensation logic.

**Production warning:** Retrying a payment or inventory reservation can cause duplicate operations unless the operation is designed to be idempotent.

# 7. Parallel state example

A `Parallel` state executes multiple branches concurrently and returns an array of their outputs.

```json
"RunChecks": {
  "Type": "Parallel",
  "Branches": [
    {
```

A state machine requires an IAM execution role that trusts Step Functions and has permission to invoke the Lambda functions.

```hcl
resource "aws_iam_role" "sfn_role" {

    Version = "2012-10-17"

resource "aws_iam_role_policy" "sfn_lambda_policy" {

  policy = jsonencode({
    Version = "2012-10-17"

      Effect = "Allow"
```

# 9. Production checklist

- Use `InputPath`, `Parameters`, `ResultSelector`, `ResultPath`, and `OutputPath` deliberately to control JSON flow.
- Use `Retry` for transient errors and `Catch` for recovery.
- Make retryable operations idempotent.
- Keep IAM permissions least-privileged.
- Set suitable timeouts and handle failed executions.
- Avoid putting secrets in state-machine input or execution history.
- Test the workflow using representative inputs and failure scenarios before production deployment.


### Request-response

Step Functions sends a request and waits for the service operation to return.

Example:
Invoke Lambda and wait for the response.

### Run a job and wait

Supported integrations can start a job and wait for it to finish.

This pattern is often represented by the `.sync` integration suffix for supported services.

Examples can include supported AWS Batch, ECS, or other job-oriented integrations.

Important:
- `.sync` is not supported for every AWS service or operation.
- Permissions for polling, event monitoring, or completion handling may be required.
- The workflow can remain active while waiting.

### Callback with task token

Step Functions starts a task and waits for an external process to report completion using a task token.

Typical use:
- Human approval.
- Third-party processing.
- External job completion.
- Long-running activity coordinated outside the workflow.

Conceptual flow:

Step Functions → Send work to SQS → External worker processes request → Worker reports success or failure with task token

Important:
- Callback support depends on workflow type and integration.
- Task tokens must be protected like credentials.
- Tokens should not be exposed to untrusted clients.
- A task token is not a substitute for application authentication.
- Callback tasks require suitable timeout and heartbeat behavior where applicable.

### Optimized integrations

Step Functions provides optimized integrations for supported AWS services.

These can simplify the workflow definition and provide service-specific request and response handling.

### AWS SDK integrations

Supported AWS SDK service operations can be invoked directly without writing a Lambda function for every operation.

Important:
- Not every AWS API operation is supported by every integration path.
- The state machine execution role needs the appropriate IAM permissions.
- Service-specific request formats and error behavior still apply.

Official documentation:
https://docs.aws.amazon.com/step-functions/latest/dg/connect-to-services.html

## 9. Step Functions with Lambda

Common architecture:

API Gateway → Step Functions → Lambda A → Lambda B → DynamoDB

Use Step Functions when the business process requires multiple coordinated steps rather than a single function doing everything.

Benefits:
- Centralized workflow logic.
- Built-in retry and catch handling.
- Conditional branching.
- Parallel tasks.
- Execution history for Standard workflows.
- Reduced need to implement orchestration in application code.

Important configuration:
- Lambda function ARN.
- Integration pattern.
- Execution role permissions.
- Task timeout.
- Heartbeat where applicable.
- Retry policy.
- Catch paths.
- Input and output transformations.

Permissions are separate:
- The Step Functions execution role needs permission to invoke the Lambda function.
- The Lambda execution role needs permission to access DynamoDB, S3, or other backend services.
- The Lambda resource policy may also need to allow invocation by the state machine, depending on the integration and deployment configuration.

Important:
Do not put all business logic in the state machine definition. Use Lambda or another suitable service for complex computation and application logic.

## 10. Step Functions with SQS, SNS, and EventBridge

### SQS

Typical flow:
Step Functions → SQS → Worker → Result processing

Useful for:
- Decoupling workloads.
- Queue-based processing.
- Managing downstream throughput.

A successful SQS send only confirms that the message was accepted by the queue. It does not prove that the worker finished processing it.

### SNS

Typical flow:
Step Functions → SNS → Subscribers

Useful for:
- Sending notifications.
- Publishing business events.
- Notifying multiple consumers.

### EventBridge

EventBridge can trigger supported workflows based on events and can be used as part of an event-driven architecture.

Typical flow:
S3 or application event → EventBridge rule → Step Functions → Processing workflow

Important:
- Event delivery and downstream processing can be duplicated.
- Use idempotent handlers.
- Configure dead-letter handling and retries in the relevant eventing service where supported.
- Do not assume an event-triggered workflow is automatically an exactly-once business process.

## 11. IAM and Security

Step Functions uses IAM to control who can create, start, inspect, update, and stop workflows.

### State machine execution role

The execution role is assumed by Step Functions.

It grants permission to:
- Invoke Lambda.
- Start supported AWS service operations.
- Read or write relevant resources.
- Send messages.
- Perform callback operations where required.
- Access other integrations used by the workflow.

Use least privilege. Do not give the role broad administrator permissions just to make the workflow run.

### Caller permissions

A principal starting a workflow may need permissions such as:
- `states:StartExecution`
- `states:DescribeExecution`
- `states:StopExecution`
- `states:StartSyncExecution` for applicable synchronous Express use cases.
- Other `states:*` actions required by the application or deployment process.

Grant only the actions that are needed.

### Trust policy

The state machine role's trust policy must allow the Step Functions service principal to assume the role.

### Logging permissions

If execution logging is enabled, configure the required CloudWatch Logs permissions and resource settings.

### Sensitive data

Avoid passing or logging:
- Passwords.
- Access keys.
- Authorization tokens.
- Payment details that do not need to be present.
- Sensitive personal information.

Prefer passing references to secrets or data stored securely.

Official documentation:
https://docs.aws.amazon.com/step-functions/latest/dg/procedure-create-iam-role.html

## 12. Networking and VPC Placement

Step Functions is an AWS-managed orchestration service. You do not deploy its state machine engine into your own VPC subnets.

However, workflow tasks can access resources in private networks through supported integration architectures.

### Lambda in a VPC

Step Functions invokes Lambda. Lambda accesses private VPC resources using its own VPC configuration.

Example:

Step Functions → Lambda attached to VPC → Private RDS database

Step Functions itself does not need to be deployed in that VPC.

### Private HTTP backend

For supported HTTP Task integrations, configure the appropriate connection and network access model.

For an HTTP endpoint hosted in a VPC, a supported private connectivity configuration may be required. Verify the current Step Functions HTTP Task connection options and regional support.

### VPC endpoints

VPC endpoints may be needed by a backend running inside a VPC when that backend needs to call AWS services privately.

For example:
- Lambda in a private subnet → S3 through an S3 gateway endpoint.
- ECS worker → SQS through an appropriate interface endpoint.

These endpoints serve the backend's network path. They do not place the Step Functions orchestration engine inside the VPC.

Important:
A Lambda or ECS task that needs outbound internet access does not automatically receive it simply because it runs in a VPC. Configure NAT or suitable private service endpoints based on the required destinations.

## 13. Distributed Map and Large-Scale Processing

Distributed Map is designed for workflows that must process large collections of data in parallel.

Typical architecture:

S3 dataset → Distributed Map → Child workflow executions → Lambda or service tasks → Results in S3

Important configuration concepts:
- Item reader.
- Input source.
- Item selector.
- Child workflow definition.
- Child workflow type.
- Maximum concurrency.
- Failure tolerance.
- Result writer.
- Result output location.

Use cases:
- Processing millions of records across supported datasets.
- Parallel file processing.
- Large batch workloads.
- Running independent child workflows for many items.

Production considerations:
- Set concurrency based on downstream capacity.
- Monitor child workflow failures.
- Define the acceptable number or percentage of failed items.
- Design for duplicate-safe processing.
- Avoid unnecessarily returning every large result to the parent workflow.
- Store large outputs in S3.
- Check Distributed Map quotas, dataset formats, and supported integration constraints.

## 14. Callback and Human Approval Workflows

A Standard workflow can wait for a person or external system to complete a task using a supported callback pattern.

Example:

Order submitted → Validate order → Request approval → Wait → Approval received → Fulfil order

Possible implementation:
1. Step Functions generates a task token.
2. A notification is sent to an approval system.
3. An authorized process receives the approval or rejection.
4. The process calls the appropriate Step Functions task-success or task-failure API with the token.
5. The workflow continues or follows its failure path.

Security requirements:
- Protect the task token.
- Authenticate the approving user or system independently.
- Authorize the specific approval action.
- Set an appropriate timeout.
- Handle expired tokens and rejected approvals.
- Keep an auditable record of the decision.

Important:
The task token proves the callback belongs to a pending task; it does not independently establish that the human making the decision is authorized.

## 16. Observability and Troubleshooting

### Standard workflow history

Standard workflows provide detailed execution history through Step Functions.

Use it to identify:
- Which state failed.
- Input and output for a state, subject to logging and data-exposure considerations.
- Error names and causes.
- Retry attempts.
- Time spent in individual steps.

### CloudWatch Logs

CloudWatch Logs can be configured for workflow execution logging.

Consider:
- Log level.
- Execution data inclusion.
- Log group.
- Log retention.
- IAM permissions.
- Cost of ingestion and storage.

Express workflows especially need an intentional logging strategy because their execution history is not available in the same way as Standard workflow history.

### CloudWatch metrics and alarms

Monitor relevant metrics, such as:
- Executions started.
- Successful executions.
- Failed executions.
- Timed-out executions.
- Aborted executions.
- Execution duration.
- Throttled requests.
- State transition usage where relevant.

Metric names and availability depend on workflow type and configuration.

### X-Ray

AWS X-Ray tracing is available for supported Step Functions configurations and can help trace workflow activity across supported integrations.

### Common troubleshooting issues

`States.Permissions`
The execution role lacks permission for an integration or required operation.

`States.TaskFailed`
An integrated task failed. Inspect the task-specific error and cause.

`States.Timeout`
The task or workflow exceeded its configured or service-imposed time limit.

`States.ResultPathMatchFailure`
The configured result placement could not be applied to the input structure.

`States.DataLimitExceeded`
A relevant input, output, or state-data payload exceeded a service limit.

Integration error:
The service may reject the request because of invalid parameters, throttling, resource policy, or resource state.

Best practice:
Check the failing state, the execution role, integration permissions, input/output size, task timeout, and downstream service logs before changing the entire workflow.

## 17. Limits and Exceptions

Quotas depend on workflow type, Region, integration, and account configuration. Always check current AWS quotas before designing a high-throughput production workflow.

Important limits and behavior:
- Standard workflows can run for up to one year.
- Express workflows can run for up to five minutes.
- State/task input and output payloads are limited to 256 KiB.
- Standard execution history has a limit of 25,000 events per execution.
- Express does not provide Standard-style execution history.
- State transition throttling and API request throttling vary by Region and workflow type.
- Map concurrency and Distributed Map have their own limits.
- Some service integrations support `.sync` or callback patterns; others do not.
- Callback task support depends on the workflow type and integration.
- Some errors are not retryable or catchable in the same way as ordinary task errors.
- A backend operation may complete even if the workflow fails before recording its completion.
- Exactly-once workflow execution does not guarantee exactly-once external side effects.
- Express delivery semantics differ between asynchronous and synchronous executions.
- Large data should generally be stored externally, with references passed between states.
- Redrive is available only for eligible executions and supported workflow configurations.

Current quotas:
https://docs.aws.amazon.com/step-functions/latest/dg/limits-overview.html

## 19. Terraform Example — Standard Workflow

This example creates a Standard state machine that invokes an existing Lambda function.

It assumes:
- The Lambda function already exists.
- The deployment identity has the required IAM permissions.
- The Lambda function has its own execution role.

```hcl
variable "lambda_function_arn" {
  type = string
}

resource "aws_iam_role" "step_functions_role" {
  name = "application-step-functions-role"

  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect = "Allow"
      Principal = {
        Service = "states.amazonaws.com"
      }
      Action = "sts:AssumeRole"
    }]
  })
}

resource "aws_iam_role_policy" "invoke_lambda" {
  name = "invoke-application-lambda"
  role = aws_iam_role.step_functions_role.id

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect   = "Allow"
      Action   = ["lambda:InvokeFunction"]
      Resource = var.lambda_function_arn
    }]
  })
}

resource "aws_sfn_state_machine" "workflow" {
  name     = "application-workflow"
  role_arn = aws_iam_role.step_functions_role.arn
  type     = "STANDARD"

  definition = jsonencode({
    Comment = "Invoke a Lambda function"
    StartAt = "ProcessRequest"

    States = {
      ProcessRequest = {
        Type     = "Task"
        Resource = var.lambda_function_arn

        Retry = [{
          ErrorEquals = [
            "Lambda.ServiceException",
            "Lambda.TooManyRequestsException"
          ]
          IntervalSeconds = 2
          MaxAttempts     = 3
          BackoffRate     = 2
        }]

        Catch = [{
          ErrorEquals = ["States.ALL"]
          Next        = "WorkflowFailed"
        }]

        End = true
      }

      WorkflowFailed = {
        Type  = "Fail"
        Error = "ProcessingFailed"
        Cause = "The Lambda processing task failed"
      }
    }
  })

  depends_on = [
    aws_iam_role_policy.invoke_lambda
  ]
}
```

Important:
- The execution role grants Step Functions permission to invoke the Lambda function.
- The Lambda function still needs its own least-privilege execution role.
- The `Catch` path intentionally sends failures to a Fail state; adapt this for your business error handling.
- The `States.ALL` catcher should be reviewed against errors that cannot be handled through ordinary catch behavior.
- Configure logging, alarms, encryption requirements, tags, and deployment controls for production.
- Avoid embedding sensitive data in workflow definitions or error causes.
- Validate the Terraform AWS provider version and current service capabilities before deployment.

Terraform resource documentation:
https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/sfn_state_machine

## 20. Production-Ready Checklist

### Workflow design
- Choose Standard or Express based on duration, delivery semantics, and history needs.
- Keep each state focused on a clear operation.
- Define success and failure paths.
- Use Choice for business decisions.
- Use Parallel for independent branches.
- Use Map for collections and Distributed Map for large-scale processing.
- Store large datasets outside the state payload.

### Reliability
- Configure retries only for appropriate failures.
- Use Catch to handle permanent failures.
- Apply timeouts to tasks and workflows.
- Make external side effects idempotent.
- Use dead-letter and recovery patterns where relevant.
- Avoid retry storms and excessive downstream concurrency.
- Test failure and redrive behavior.

### Security
- Use least-privilege execution roles.
- Protect callback tokens.
- Keep secrets out of execution input and logs.
- Limit who can start, stop, update, or inspect workflows.
- Use encryption and logging controls appropriate to the data.
- Separate production and non-production roles and state machines.

### Observability
- Enable appropriate logging.
- Review Standard execution history when diagnosing failures.
- Monitor failed, timed-out, and throttled executions.
- Configure CloudWatch alarms.
- Set log retention.
- Use tracing when useful.
- Ensure error messages do not expose sensitive information.

### Cost and operations
- Monitor state transitions or Express usage.
- Control Map concurrency.
- Set budgets and alarms.
- Use infrastructure as code.
- Review service quotas.
- Document recovery and replay procedures.
- Test deployments before production.

## 21. Quick Decision Summary

Use Step Functions when:
- A process contains multiple dependent steps.
- You need retries, branching, or failure handling.
- Several AWS services must be coordinated.
- You need parallel processing.
- A process waits for an external event or human approval.
- Workflow progress and operational visibility matter.

Use Standard when:
- Workflows may run longer than five minutes.
- Durable execution history and long-running orchestration are required.
- Callback workflows or supported long-running integrations are needed.

Use Express when:
- Workflows complete within five minutes.
- High-volume, short-duration orchestration is needed.
- Its execution semantics and logging model fit the workload.

Use Lambda alone when:
- The task is relatively simple and does not need workflow orchestration.

Use SQS when:
- You need a durable queue to decouple producers and consumers.

Use Step Functions with SQS when:
- You need orchestration around queued work, including multi-step processing, branching, retries, or completion tracking.

Remember:
Step Functions coordinates the workflow. It does not replace the services performing the work, and its execution guarantees do not automatically make external business operations exactly once.
