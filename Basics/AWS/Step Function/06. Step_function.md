# AWS Step Functions — Interview Notes

## 1. What is AWS Step Functions?

**AWS Step Functions is a serverless workflow orchestration service.**

It lets you define a sequence of steps and control:

* What happens first
* What happens next
* Which path to take
* What to do when something fails
* Whether to retry
* Whether to run things in parallel
* How data moves between steps

### Simple mental model

Think of Step Functions as a **workflow manager**.

```text
             Step Functions
                   |
        +----------+----------+
        |          |          |
      Step 1     Step 2     Step 3
        |          |          |
     Lambda     Redshift     SNS
```

Step Functions **doesn't necessarily perform the actual business/data processing itself**.

Instead, it coordinates other AWS services.

# 3. Why did you use Step Functions?

The ETL process had multiple dependent steps.

For example:

```text
Clear staging
      ↓
Load staging
      ↓
Transform
      ↓
Load warehouse
```

You don't want these operations happening randomly or independently.

You want:

```text
Step 1 succeeds
      ↓
Step 2 starts
      ↓
Step 2 succeeds
      ↓
Step 3 starts
```

Step Functions gives you that workflow control.

It also gives you built-in workflow visibility and failure handling.

# 4. Important Step Functions Terminology

## State Machine

A **state machine** is the complete workflow definition.

Example:

```text
Start
  ↓
Validate
  ↓
Load Staging
  ↓
Transform
  ↓
Load Warehouse
  ↓
Success
```

The entire workflow is the **state machine**.

---

## State

A **state** represents one step in the workflow.

For example:

```text
"LoadStaging"
```

could be one state.

Another could be:

```text
"TransformData"
```

---

## Task

A **Task state** performs work.

It can integrate with services such as:

* Lambda
* DynamoDB
* SQS
* SNS
* Redshift
* AWS SDK APIs
* Many other AWS services

Conceptually:

```text
Step Functions
      |
      v
   Task State
      |
      v
  AWS Service
```

# 6. State Types You Should Know

You don't need to memorize every state type for the interview, but know these:

| State    | Purpose                      |
| -------- | ---------------------------- |
| Task     | Performs work                |
| Choice   | Conditional branching        |
| Pass     | Passes/transforms data       |
| Wait     | Waits for a period/event     |
| Parallel | Runs branches in parallel    |
| Map      | Iterates over multiple items |
| Succeed  | Successful completion        |
| Fail     | Failed completion            |

---

# 7. Choice State

A `Choice` state is basically an `if/else`.

For example:

```text
Check file status
       |
   +---+---+
   |       |
VALID   INVALID
   |       |
   v       v
Process   Fail
```

Conceptually:

```python
if status == "VALID":
    process_file()
else:
    fail_workflow()
```

---

# 8. Retry

Step Functions can automatically retry failed tasks.

For example:

```text
Call Redshift
      |
      X
      |
    Retry
      |
      X
      |
    Retry
      |
      X
      |
    Fail
```

This is useful for **transient failures**.

For example:

* Temporary service errors
* Network-related transient failures
* Throttling

You shouldn't blindly retry every error.

For example, if your SQL has a syntax error, repeatedly retrying probably won't fix it.

---

# 9. Catch

`Catch` lets you define what happens when a task ultimately fails.

Example:

```text
Process Data
     |
     X
     |
    Catch
     |
     v
Mark file FAILED
     |
     v
Notify
```

You could have:

```text
Task
 |
 +---- success ---> next step
 |
 +---- failure ---> error handling
```

---

# 10. Retry + Catch Together

A common production pattern is:

```text
          Task
           |
       +---+---+
       |       |
    Success   Error
       |       |
       v     Retry
      Next     |
               |
          still failing?
               |
               v
             Catch
               |
               v
          Error Handler
```

This is a very common interview topic.

# 11. Step Functions Input and Output

One thing that can initially be confusing is:

> "How do variables move between states?"

Each state can receive input and produce output.

For example:

```json
{
  "file_key": "incoming/customer.csv",
  "status": "VALIDATED"
}
```

A state can receive this data.

The next state can receive the result.

Conceptually:

```text
State A
  |
  | output
  v
State B
  |
  | output
  v
State C
```

So the workflow can carry information such as:

```text
file_key
transaction_id
customer_id
status
execution information
```

# 13. JSONPath

Step Functions can use **JSONPath** to select parts of state input/output.

Suppose the input is:

```json
{
  "file": {
    "key": "incoming/customer.csv",
    "bucket": "company-ingest"
  }
}
```

You could reference:

```text
$.file.key
```

to get:

```text
incoming/customer.csv
```

For interviews, understand the concept:

> JSONPath allows Step Functions to select and manipulate portions of JSON data flowing through the workflow.

# 17. Parallel State

`Parallel` allows independent branches to execute concurrently.

Example:

```text
             Start
               |
            Parallel
           /        \
          /          \
     Process A     Process B
          \          /
           \        /
             Join
```

For example, you might independently run two unrelated operations and wait for both to complete.

# 18. Standard vs Express

There are two main Step Functions workflow types:

### Standard Workflows

Best suited for:

* Long-running workflows
* Durable business processes
* Complex workflows
* Workflows where execution history is important

### Express Workflows

Best suited for:

* High-volume workflows
* Short-duration processing
* Event-processing workloads

For your ETL scenario, **Standard Workflows** are the more natural interview discussion because ETL orchestration can involve multiple database operations and meaningful execution tracking.

# 22. Important Idempotency Scenario

This is particularly important in your architecture.

Suppose:

```text
SQS
 ↓
Lambda 2
 ↓
Start Step Functions
 ↓
Success
```

But Lambda 2 crashes **after starting Step Functions and before successfully acknowledging the SQS message**.

SQS may deliver the message again.

Then:

```text
SQS
 ↓
Lambda 2
 ↓
Start Step Functions AGAIN
```

You could accidentally process the same file twice.

That's why your architecture should consider **idempotency**.

A file key can act as an idempotency/business identifier.

For example:

```text
incoming/customer_20260829.csv
```

DynamoDB can track:

```text
file_key
status
execution_arn
```

Then Lambda can determine whether that file has already been successfully started/processed.

# 23. Step Functions Execution

Every time you start a state machine, you create an **execution**.

Conceptually:

```text
State Machine
      |
      +--> Execution 1
      |
      +--> Execution 2
      |
      +--> Execution 3
```

For example:

```text
customer_20260829.csv
        |
        v
Execution ID / ARN
        |
        v
Step Functions workflow
```

Execution history is useful when troubleshooting.

You can see where the workflow:

* Started
* Succeeded
* Failed
* Retried
* Waited
* Transitioned

# 24. How You Would Troubleshoot a Failed Workflow

Interview question:

> "Your Step Functions workflow failed. What do you do?"

Strong answer:

1. Open the Step Functions execution.
2. Identify the failed state.
3. Inspect the error/cause.
4. Determine whether it is:

   * Lambda failure
   * IAM/AccessDenied
   * Redshift/database error
   * Timeout
   * Throttling
   * Invalid input
5. Check the relevant CloudWatch logs.
6. Check retry/catch configuration.
7. Check whether the operation is idempotent before retrying manually.
8. Fix the root cause and rerun safely.

The key is:

> **Don't just rerun the whole workflow blindly. First identify the failed state and understand whether repeating the operation is safe.**

# 25. Step Functions IAM

Step Functions often needs an IAM execution role.

The role determines what AWS services the state machine is allowed to interact with.

For example, if the workflow needs to invoke Lambda:

```text
Step Functions
      |
      | IAM role
      v
Lambda
```

If it needs to interact with another AWS service, the execution role needs the corresponding permissions.

Again remember:

```text
Trust policy
     ↓
Who can assume the role?

Permission policy
     ↓
What can the role do?
```
