# AWS Step Functions — Complete Terraform & Production Cheatsheet

## 1. What is AWS Step Functions?

AWS Step Functions is a serverless workflow orchestration service. It coordinates multiple AWS services and application components into a controlled sequence of steps.

Instead of writing complex orchestration logic inside one Lambda function, you define a workflow using **Amazon States Language (ASL)**.

Example:

```text
Order received
     |
     v
Validate order
     |
     v
Check inventory
     |
     v
Is stock available?
   /       \
 Yes        No
  |          |
  v          v
Charge     Reject order
payment
  |
  v
Create shipment
  |
  v
Send notification
  |
  v
Complete
```

### Common use cases

| Use case | Example |
|---|---|
| E-commerce | Order, payment, inventory, shipping |
| Data engineering | S3 file ingestion, Glue, Athena |
| ETL | Extract, transform, load |
| Microservices | Coordinate multiple services |
| Human approval | Manager approval before payment |
| Financial processing | Payment, settlement, reconciliation |
| Batch processing | Process thousands of files |
| AI/ML | Invoke models, validate output, store results |
| Infrastructure automation | Coordinate deployment and validation |
| Event-driven systems | EventBridge triggers workflows |

**Important:** Step Functions orchestrates work. It does not replace Lambda, ECS, SQS, SNS, DynamoDB, or other services that perform the actual work.

## 2. Standard vs Express workflows

| Feature | Standard | Express |
|---|---|---|
| Maximum execution duration | Up to 1 year | Up to 5 minutes |
| Execution semantics | Exactly-once workflow execution | Asynchronous at-least-once; synchronous at-most-once |
| Pricing | State transitions | Requests and execution duration |
| Execution history | Built-in execution history | CloudWatch Logs for execution details |
| Best for | Long-running business processes | High-volume short-running workloads |
| Human approval | Suitable | Usually unsuitable |
| Payment workflow | Suitable | Depends on business requirements |
| IoT/event processing | Possible | Often suitable |
| Long-running orchestration | Suitable | Not suitable |

**Production recommendation:**

- Use Standard for orders, payments, approvals, business transactions and long-running processes.
- Use Express for high-volume, short-running event processing.
- Do not select Express simply because it appears cheaper. Consider execution semantics, retries, observability and downstream side effects.

A workflow's exactly-once execution semantics do not automatically make an external payment or API operation exactly once. Your application must still implement idempotency.

## 3. Step Functions state types — complete reference

ASL defines the workflow. A state represents one step.

### 3.1 Pass

Passes input through or transforms data without calling an external service.

```json
{
  "Initialize": {
    "Type": "Pass",
    "Result": {
      "status": "STARTED"
    },
    "ResultPath": "$.workflow",
    "Next": "ValidateOrder"
  }
}
```

Use case: initialize variables or create a default value.

### 3.2 Task

Executes work by invoking Lambda, ECS, SNS, SQS, DynamoDB, Glue, or another supported integration.

```json
{
  "ValidateOrder": {
    "Type": "Task",
    "Resource": "arn:aws:states:::lambda:invoke",
    "Parameters": {
      "FunctionName": "validate-order",
      "Payload.$": "$"
    },
    "End": true
  }
}
```

Use case: call a Lambda function to validate an order.

### 3.3 Choice

Implements conditional branching.

```json
{
  "CheckPayment": {
    "Type": "Choice",
    "Choices": [
      {
        "Variable": "$.paymentStatus",
        "StringEquals": "SUCCESS",
        "Next": "CreateShipment"
      }
    ],
    "Default": "PaymentFailed"
  }
}
```

Use case: if payment succeeds, continue; otherwise reject the order.

### 3.4 Wait

Pauses workflow execution.

```json
{
  "WaitForApproval": {
    "Type": "Wait",
    "Seconds": 300,
    "Next": "CheckApproval"
  }
}
```

You can also use `SecondsPath`, `Timestamp`, or `TimestampPath` in JSONPath workflows.

Use case: wait five minutes before checking an approval or payment status.

### 3.5 Parallel

Executes independent branches concurrently.

```json
{
  "PostOrderTasks": {
    "Type": "Parallel",
    "Branches": [
      {
        "StartAt": "SendEmail",
        "States": {
          "SendEmail": {
            "Type": "Pass",
            "End": true
          }
        }
      },
      {
        "StartAt": "UpdateAnalytics",
        "States": {
          "UpdateAnalytics": {
            "Type": "Pass",
            "End": true
          }
        }
      }
    ],
    "End": true
  }
}
```

Use case: send an email and update analytics at the same time.

### 3.6 Map

Processes an array of items.

```json
{
  "ProcessItems": {
    "Type": "Map",
    "ItemsPath": "$.items",
    "MaxConcurrency": 10,
    "Iterator": {
      "StartAt": "ProcessItem",
      "States": {
        "ProcessItem": {
          "Type": "Pass",
          "End": true
        }
      }
    },
    "End": true
  }
}
```

Use case: process multiple orders, records, files or customers.

For newer definitions, use `ItemProcessor` rather than the legacy `Iterator` structure. Distributed Map is useful for large datasets and S3-backed processing.

### 3.7 Succeed

Ends the workflow successfully.

```json
{
  "Completed": {
    "Type": "Succeed"
  }
}
```

### 3.8 Fail

Ends the workflow with an error.

```json
{
  "OrderFailed": {
    "Type": "Fail",
    "Error": "OrderProcessingFailed",
    "Cause": "Payment could not be completed"
  }
}
```

## 4. ASL common fields and parameters

These are the important fields you will see in state definitions.

| Field | Meaning |
|---|---|
| `Type` | Required state type: Task, Pass, Choice, Wait, Map, Parallel, Succeed or Fail |
| `Comment` | Human-readable description |
| `Next` | Name of the next state |
| `End` | Marks a state as the end of its execution path |
| `StartAt` | First state in a state machine or nested branch |
| `States` | Collection of states |
| `QueryLanguage` | JSONPath or JSONata |
| `InputPath` | Selects which input reaches the state |
| `Parameters` | Constructs the input passed to a task or branch |
| `ResultSelector` | Shapes the result returned by a task |
| `ResultPath` | Controls where the task result is placed in the input |
| `OutputPath` | Selects the output passed to the next state |
| `Assign` | Stores variables in supported JSONata workflows |
| `Output` | Defines state output, particularly in JSONata workflows |
| `Retry` | Defines retry behaviour |
| `Catch` | Defines error handling and fallback transitions |
| `TimeoutSeconds` | Maximum task duration |
| `HeartbeatSeconds` | Maximum interval between task heartbeats |

### Important: InputPath, Parameters, ResultSelector, ResultPath and OutputPath

These are especially important when working with Lambda.

Suppose the original input is:

```json
{
  "orderId": "ORD-1001",
  "customer": "John",
  "amount": 100
}
```

A Task can use `Parameters` to pass only selected information to Lambda.

```json
{
  "Parameters": {
    "FunctionName": "validate-order",
    "Payload": {
      "orderId.$": "$.orderId",
      "amount.$": "$.amount"
    }
  }
}
```

The Lambda receives only the selected payload.

- `InputPath`: filters the original input before the state runs.
- `Parameters`: builds the request sent to the task.
- `ResultSelector`: transforms the task's returned result.
- `ResultPath`: places the result into the original input.
- `OutputPath`: filters the final state output before sending it onward.

Example:

```json
{
  "Type": "Task",
  "Resource": "arn:aws:states:::lambda:invoke",
  "Parameters": {
    "FunctionName": "validate-order",
    "Payload.$": "$"
  },
  "ResultSelector": {
    "validation.$": "$.Payload"
  },
  "ResultPath": "$.validationResult",
  "OutputPath": "$",
  "Next": "NextStep"
}
```

This keeps the original order information and stores the Lambda result under `validationResult`.

### Retry example

```json
"Retry": [
  {
    "ErrorEquals": [
      "Lambda.ServiceException",
      "Lambda.AWSLambdaException",
      "Lambda.SdkClientException"
    ],
    "IntervalSeconds": 2,
    "BackoffRate": 2,
    "MaxAttempts": 3
  }
]
```

| Parameter | Meaning |
|---|---|
| `ErrorEquals` | Error types that trigger a retry |
| `IntervalSeconds` | Initial wait before retry |
| `BackoffRate` | Multiplier applied to retry interval |
| `MaxAttempts` | Maximum retry attempts |

### Catch example

```json
"Catch": [
  {
    "ErrorEquals": ["States.ALL"],
    "ResultPath": "$.error",
    "Next": "HandleFailure"
  }
]
```

Use Retry for temporary failures. Use Catch to route failures into a recovery or failure-handling state.

Do not blindly retry business failures such as insufficient funds or invalid customer details.

# 5. Terraform — complete resource parameter explanation

Main resource:

```hcl
resource "aws_sfn_state_machine" "this" {
  name       = "order-processing"
  role_arn   = aws_iam_role.sfn_execution.arn
  type       = "STANDARD"
  definition = jsonencode({})
}
```

### 5.1 Top-level parameters

| Parameter | Required? | Explanation |
|---|---|---|
| `name` | Optional | Explicit state machine name |
| `name_prefix` | Optional | Automatically generated name beginning with a prefix; conflicts with `name` |
| `role_arn` | Required | IAM execution role assumed by Step Functions |
| `definition` | Required | ASL workflow definition as JSON |
| `type` | Optional | `STANDARD` or `EXPRESS`; defaults to Standard |
| `publish` | Optional | Publishes a version during creation or update |
| `tags` | Optional | Resource tags for ownership, cost and governance |
| `region` | Optional | Resource region; otherwise provider region is used |
| `logging_configuration` | Optional | CloudWatch Logs configuration |
| `tracing_configuration` | Optional | Enables X-Ray tracing |
| `encryption_configuration` | Optional | Configures encryption for state machine data |

**Important:** Workflow type cannot be changed in place after creation. Plan a replacement or migration if you need to change from Standard to Express.

### 5.2 `logging_configuration`

```hcl
logging_configuration {
  log_destination        = "${aws_cloudwatch_log_group.sfn.arn}:*"
  include_execution_data = false
  level                  = "ERROR"
}
```

| Parameter | Explanation |
|---|---|
| `log_destination` | CloudWatch log group ARN; it must end in `:*` |
| `include_execution_data` | Whether execution input/output data is included |
| `level` | `ALL`, `ERROR`, `FATAL` or `OFF` |

Production recommendation:

- Use `ERROR` or `FATAL` where possible.
- Avoid logging sensitive payment, personal or authentication data.
- Enable execution data only when there is a clear operational requirement.
- Set log retention rather than keeping logs indefinitely.

### 5.3 `tracing_configuration`

```hcl
tracing_configuration {
  enabled = true
}
```

Enables X-Ray tracing to help identify latency and dependencies across services.

### 5.4 `encryption_configuration`

```hcl
encryption_configuration {
  type                              = "CUSTOMER_MANAGED_KMS_KEY"
  kms_key_id                        = aws_kms_key.sfn.arn
  kms_data_key_reuse_period_seconds = 300
}
```

| Parameter | Explanation |
|---|---|
| `type` | `AWS_OWNED_KEY` or `CUSTOMER_MANAGED_KMS_KEY` |
| `kms_key_id` | KMS key ARN, key ID or supported alias |
| `kms_data_key_reuse_period_seconds` | Data-key reuse period for customer-managed encryption |

Use a customer-managed KMS key when you need tighter control over key policy, key access and audit requirements.

# 6. Production-style Terraform example

## Architecture

This example creates an order-processing workflow:

```text
Application / EventBridge
          |
          v
    Step Functions
          |
          v
     Validate Order
          |
          v
     Check Inventory
          |
          v
     Process Payment
          |
          v
      Payment OK?
        /    \
      Yes     No
       |       |
       v       v
 Create       Handle
 Shipment     Failure
       |
       v
 Send Notification
       |
       v
     Complete
```

The example provisions:

- Step Functions Standard workflow
- IAM execution role
- Least-privilege Lambda invocation policy
- CloudWatch log group
- KMS key
- X-Ray tracing
- Retry and Catch logic
- Input and result handling
- Terraform outputs

The Lambda functions are assumed to exist already. Their business logic is outside this Terraform example.

## 6.1 Project structure

```text
step-functions-project/
│
├── versions.tf
├── variables.tf
├── main.tf
├── iam.tf
├── kms.tf
├── logging.tf
├── outputs.tf
└── terraform.tfvars
```

## 6.2 versions.tf

```hcl
terraform {
  required_version = ">= 1.6.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
}

provider "aws" {
  region = var.aws_region

  default_tags {
    tags = {
      Project     = "order-processing"
      Environment = var.environment
      ManagedBy   = "Terraform"
    }
  }
}
```

**Explanation:**

- `required_version`: minimum Terraform version.
- `required_providers`: defines the AWS provider.
- `version`: constrains the provider version.
- `region`: deploys resources in the selected AWS region.
- `default_tags`: automatically applies standard tags.

Commit `.terraform.lock.hcl` to source control so deployments use the same resolved provider version.

  type        = string
}

variable "payment_lambda_arn" {
  description = "Payment Lambda ARN"

**Explanation:**

## 6.4 kms.tf

```hcl
resource "aws_kms_key" "sfn" {
  description             = "Step Functions state machine encryption"
  enable_key_rotation     = true
  deletion_window_in_days = 30

  tags = {
    Name = "order-processing-sfn-key"
  }
}

resource "aws_kms_alias" "sfn" {
  name          = "alias/order-processing-sfn"
  target_key_id = aws_kms_key.sfn.key_id
}
```

**Explanation:**

- `enable_key_rotation`: enables automatic annual rotation for the symmetric KMS key.
- `deletion_window_in_days`: waiting period before permanent key deletion.
- `aws_kms_alias`: creates a human-readable alias.

For a real deployment, review the KMS key policy and ensure only the required administrators and service principals can use the key.

## 6.5 logging.tf

```hcl
resource "aws_cloudwatch_log_group" "sfn" {
  name              = "/aws/vendedlogs/states/order-processing-prod"
  retention_in_days = 30

  kms_key_id = aws_kms_key.sfn.arn
}
```

**Explanation:**

- `name`: log group name.
- `retention_in_days`: deletes expired log events after the configured retention period.
- `kms_key_id`: encrypts log data using the selected KMS key.

The `/aws/vendedlogs/states` prefix helps avoid CloudWatch Logs resource policy size problems when many state machines send logs to CloudWatch.

## 6.6 iam.tf

### Step 1: Trust policy

```hcl
data "aws_iam_policy_document" "sfn_assume_role" {
  statement {
    effect  = "Allow"
    actions = ["sts:AssumeRole"]

    principals {
      type        = "Service"
      identifiers = ["states.amazonaws.com"]
    }
  }
}

resource "aws_iam_role" "sfn_execution" {
  name               = "order-processing-sfn-role"
  assume_role_policy = data.aws_iam_policy_document.sfn_assume_role.json
}
```

This allows the Step Functions service to assume the IAM role.

### Step 2: Lambda invocation permissions

```hcl
data "aws_iam_policy_document" "sfn_lambda" {
  statement {
    sid    = "InvokeApprovedOrderLambdas"
    effect = "Allow"

    actions = [
      "lambda:InvokeFunction"
    ]

    resources = [
      var.validate_lambda_arn,
      var.inventory_lambda_arn,
      var.payment_lambda_arn,
      var.shipment_lambda_arn,
      var.notification_lambda_arn
    ]
  }
}

resource "aws_iam_policy" "sfn_lambda" {
  name   = "order-processing-sfn-lambda-policy"
  policy = data.aws_iam_policy_document.sfn_lambda.json
}

resource "aws_iam_role_policy_attachment" "sfn_lambda" {
  role       = aws_iam_role.sfn_execution.name
  policy_arn = aws_iam_policy.sfn_lambda.arn
}
```

This allows the workflow to invoke only the five specified Lambda functions.

### Step 3: CloudWatch Logs permissions

```hcl
data "aws_iam_policy_document" "sfn_logs" {
  statement {
    effect = "Allow"

    actions = [
      "logs:CreateLogDelivery",
      "logs:GetLogDelivery",
      "logs:UpdateLogDelivery",
      "logs:DeleteLogDelivery",
      "logs:ListLogDeliveries",
      "logs:PutResourcePolicy",
      "logs:DescribeResourcePolicies",
      "logs:DescribeLogGroups"
    ]

    resources = ["*"]
  }
}

resource "aws_iam_policy" "sfn_logs" {
  name   = "order-processing-sfn-logs-policy"
  policy = data.aws_iam_policy_document.sfn_logs.json
}

resource "aws_iam_role_policy_attachment" "sfn_logs" {
  role       = aws_iam_role.sfn_execution.name
  policy_arn = aws_iam_policy.sfn_logs.arn

```

Some CloudWatch Logs delivery actions require `Resource: "*"`. This is an AWS service API permission requirement, not a reason to grant broad access to all log events.

## 6.7 main.tf — complete workflow

```hcl
resource "aws_sfn_state_machine" "order_processing" {
  name     = var.state_machine_name
  role_arn = aws_iam_role.sfn_execution.arn
  type     = "STANDARD"

  definition = jsonencode({
    Comment = "Production-style order processing workflow"

    StartAt = "ValidateOrder"

    States = {

      ValidateOrder = {
        Type     = "Task"
        Resource = "arn:aws:states:::lambda:invoke"

        Parameters = {
          FunctionName = var.validate_lambda_arn
          "Payload.$" = "$"
        }

        ResultSelector = {
          "Payload.$" = "$.Payload"
        }

        ResultPath = "$.validation"

        Retry = [{
          ErrorEquals = [
            "Lambda.ServiceException",
            "Lambda.AWSLambdaException",
            "Lambda.SdkClientException"
          ]
          IntervalSeconds = 2
          BackoffRate     = 2
          MaxAttempts     = 3
        }]

        Catch = [{
          ErrorEquals = ["States.ALL"]
          ResultPath  = "$.error"
          Next        = "HandleFailure"
        }]

        Next = "CheckInventory"
      }

      CheckInventory = {
        Type     = "Task"
        Resource = "arn:aws:states:::lambda:invoke"

        Parameters = {
          FunctionName = var.inventory_lambda_arn
          "Payload.$" = "$"
        }

        ResultSelector = {
          "Payload.$" = "$.Payload"
        }

        ResultPath = "$.inventory"

        TimeoutSeconds = 60

        Retry = [{
          ErrorEquals = [
            "Lambda.ServiceException",
            "Lambda.AWSLambdaException",
            "Lambda.SdkClientException"
          ]
          IntervalSeconds = 2
          BackoffRate     = 2
          MaxAttempts     = 3
        }]

        Catch = [{
          ErrorEquals = ["States.ALL"]
          ResultPath  = "$.error"
          Next        = "HandleFailure"
        }]

        Next = "ProcessPayment"
      }

      ProcessPayment = {
        Type     = "Task"
        Resource = "arn:aws:states:::lambda:invoke"

        Parameters = {
          FunctionName = var.payment_lambda_arn
          "Payload.$" = "$"
        }

        ResultSelector = {
          "Payload.$" = "$.Payload"
        }

        ResultPath = "$.payment"

        TimeoutSeconds = 60

        Retry = [{
          ErrorEquals = [
            "Lambda.ServiceException",
            "Lambda.AWSLambdaException",
            "Lambda.SdkClientException"
          ]
          IntervalSeconds = 2
          BackoffRate     = 2
          MaxAttempts     = 2
        }]

        Catch = [{
          ErrorEquals = ["States.ALL"]
          ResultPath  = "$.error"
          Next        = "HandleFailure"
        }]

        Next = "CheckPayment"
      }

      CheckPayment = {
        Type = "Choice"

        Choices = [{
          Variable     = "$.payment.Payload.status"
          StringEquals = "SUCCESS"
          Next         = "CreateShipment"
        }]

        Default = "HandleFailure"
      }

      CreateShipment = {
        Type     = "Task"
        Resource = "arn:aws:states:::lambda:invoke"

        Parameters = {
          FunctionName = var.shipment_lambda_arn
          "Payload.$" = "$"
        }

        ResultSelector = {
          "Payload.$" = "$.Payload"
        }

        ResultPath = "$.shipment"

        TimeoutSeconds = 60

        Catch = [{
          ErrorEquals = ["States.ALL"]
          ResultPath  = "$.error"
          Next        = "HandleFailure"
        }]

        Next = "SendNotification"
      }

      SendNotification = {
        Type     = "Task"
        Resource = "arn:aws:states:::lambda:invoke"

        Parameters = {
          FunctionName = var.notification_lambda_arn
          "Payload.$" = "$"
        }

        ResultPath = "$.notification"

        TimeoutSeconds = 60

        Catch = [{
          ErrorEquals = ["States.ALL"]
          ResultPath  = "$.notificationError"
          Next        = "OrderCompletedWithNotificationIssue"
        }]

        Next = "OrderCompleted"
      }

      OrderCompleted = {
        Type = "Succeed"
      }

      OrderCompletedWithNotificationIssue = {
        Type = "Succeed"
      }

      HandleFailure = {
        Type = "Fail"
        Error = "OrderProcessingFailed"
        Cause = "An order-processing step failed"
      }
    }
  })

  logging_configuration {
    log_destination        = "${aws_cloudwatch_log_group.sfn.arn}:*"
    include_execution_data = false
    level                  = "ERROR"
  }

  tracing_configuration {
    enabled = true
  }

  encryption_configuration {
    type                              = "CUSTOMER_MANAGED_KMS_KEY"
    kms_key_id                        = aws_kms_key.sfn.arn
    kms_data_key_reuse_period_seconds = 300
  }

  publish = true

  tags = {
    Application = "order-processing"
    Environment = var.environment
    Owner       = "platform-team"
    CostCenter  = "engineering"
  }

  depends_on = [
    aws_iam_role_policy_attachment.sfn_lambda,
    aws_iam_role_policy_attachment.sfn_logs,
    aws_iam_role_policy_attachment.sfn_kms,
    aws_iam_role_policy_attachment.sfn_xray
  ]
}
```

### Understand the production workflow

| Step | What happens |
|---|---|
| ValidateOrder | Invokes order validation Lambda |
| CheckInventory | Checks product availability |
| ProcessPayment | Invokes payment Lambda |
| CheckPayment | Checks payment response |
| CreateShipment | Creates shipment after successful payment |
| SendNotification | Sends customer notification |
| OrderCompleted | Ends successfully |
| HandleFailure | Terminates with a failure |

**Important production improvements before using this as a real payment system:**

1. Implement idempotency in payment processing using a stable order/payment idempotency key.
2. Distinguish transient technical errors from business failures.
3. Implement payment reversal or compensation if payment succeeds but shipment creation fails.
4. Send unrecoverable failures to an operational alert or dead-letter/reconciliation process.
5. Decide whether notification failure should fail the business transaction. This example deliberately allows the order to complete with a notification issue.
6. Validate the Lambda response schema. The payment Lambda must return a JSON payload containing `status`, such as `{"status":"SUCCESS"}`.
7. Ensure Lambda functions themselves have their own least-privilege execution roles, logging, encryption and network controls.

The example's `HandleFailure` is intentionally a terminal failure state, not a complete saga compensation implementation. A real financial workflow should include explicit refund, release-reservation and reconciliation steps where required.

### Three important integration patterns

**1. Request-response**

Step Functions calls a service and receives the response.

```text
Step Functions -> Lambda -> Response
```

**2. Run a job and wait for completion (`.sync`)**

```text

```

```text

      |
      v
Wait for task token
      |
      v
Human approves or rejects
      |
      v
Workflow continues
```

Useful for manual approval and external asynchronous systems.

# 9. Cost — how AWS charges

Step Functions has two principal pricing models.

## 9.1 Standard pricing

Standard workflows are charged by state transitions.

A state transition is counted when a state is entered. Retries create additional transitions.

Formula:

```text
Monthly cost =
(
  Executions per month
  x Average transitions per execution
  - Free transitions
)
x Price per transition
```

The AWS pricing page currently shows 4,000 free state transitions per month.

Example using the published EU (Germany) illustrative rate of €0.0000246714 per transition:

- 100,000 executions per month
- 10 state transitions per execution
- Total transitions = 1,000,000
- Less free allowance = 996,000
- Approximate Step Functions charge = €24.57

This is an illustration using the EU (Germany) rate, **not a confirmed Ireland regional quote**. Check the current regional rate for `eu-west-1`.

## 9.2 Express pricing

Express charges are based on:

1. Number of executions/requests.
2. Execution duration.
3. Memory consumed, billed in 64 MB chunks.

Formula:

```text
Express cost =
Request charges
+
Duration charges
```

Example using the published EU (Germany) illustrative rates:

- 1 million executions
- 30 seconds average duration
- 64 MB billed memory
- Request charge approximately €0.99
- Duration charge approximately €30.84
- Total approximately €31.84

The actual cost depends on the applicable duration tiers, memory usage and regional price.

## 9.3 Other costs to remember

Step Functions is only one component of the bill.

| Service | Possible cost |
|---|---|
| Lambda | Requests and execution duration |
| CloudWatch Logs | Ingestion, storage and retention |
| CloudWatch metrics | Custom metrics and alarms |
| X-Ray | Traces recorded and scanned |
| KMS | Key usage and API requests |
| ECS Fargate | vCPU and memory duration |
| SQS | Requests and data transfer |
| SNS | Publish and delivery |
| DynamoDB | Reads, writes and storage |
| PrivateLink | Endpoint hours and data processing |
| Data transfer | Applicable transfer charges |

### Cost optimisation

- Use Express for suitable high-volume short workflows.
- Avoid unnecessary Pass and Task states.
- Avoid excessive retries.
- Set realistic timeouts.
- Use Distributed Map only when its scale justifies the additional orchestration.
- Batch work where practical.
- Store large payloads in S3 and pass object references rather than large JSON objects.
- Use log retention.
- Avoid logging full execution input/output unnecessarily.
- Apply cost-allocation tags.

# 10. Security best practices

## IAM

- Use a dedicated execution role for each state machine or logical application.
- Restrict `lambda:InvokeFunction` to specific function ARNs.
- Avoid `AdministratorAccess`.
- Restrict who can start, stop, update or delete state machines.
- Separate deployment permissions from runtime execution permissions.
- Use resource-level permissions and tag-based access where supported.

## Encryption

- Encrypt sensitive workflow data at rest.
- Use customer-managed KMS keys when required by compliance.
- Restrict key administration and usage separately.
- Encrypt CloudWatch Logs.
- Never put passwords, API keys, payment card data or access tokens into workflow inputs.

## Network

Step Functions itself is a managed service and is not deployed into your VPC or attached to a security group.

However, it can orchestrate services that run inside a VPC, such as Lambda and ECS. Configure the network security of those target services independently.

For private endpoint integrations, assess supported PrivateLink or VPC Lattice connectivity and its associated permissions and costs.

## Workflow design

- Set explicit task timeouts.
- Use retries only for transient errors.
- Use Catch for expected failure paths.
- Implement idempotency for side effects.
- Avoid passing oversized payloads.
- Protect sensitive input/output from CloudWatch logging.
- Use Standard when durable execution history is important.
- Use alarms for failed executions and abnormal failure rates.

## 11.1 Checkov

Install:

```bash
pip install checkov
```

Scan:

```bash

```

Scan a Terraform plan:

```bash
terraform plan -out=tfplan

terraform show -json tfplan > tfplan.json

checkov -f tfplan.json --framework terraform_plan
```

Use Checkov to detect misconfigurations such as:

- Missing logging.
- Missing encryption.
- Insecure IAM policies.
- Missing tags.
- Weak or missing configuration controls.

Review the findings and suppress individual checks only with documented justification.

## 11.2 OPA / Rego policy

Example policy file:

`policy/stepfunctions.rego`

```rego
package terraform.stepfunctions

import rego.v1

resource_changes := object.get(
  input,
  ["resource_changes"],
  []
)

sfn_resources := [
  resource |
  some resource in resource_changes
  resource.type == "aws_sfn_state_machine"
  resource.change.actions[_] != "delete"
]

deny contains msg if {
  some resource in sfn_resources

  after := resource.change.after

  not object.get(after, "logging_configuration", null)

  msg := sprintf(
    "Step Functions %s must configure CloudWatch logging",
    [resource.address]
  )
}

deny contains msg if {
  some resource in sfn_resources

  after := resource.change.after

  not object.get(after, "tracing_configuration", null)

  msg := sprintf(
    "Step Functions %s must configure X-Ray tracing",
    [resource.address]
  )
}

deny contains msg if {
  some resource in sfn_resources

  after := resource.change.after

  not object.get(after, "tags", null)

  msg := sprintf(
    "Step Functions %s must have resource tags",
    [resource.address]
  )
}
```

This is a starter governance policy. Test it against actual Terraform plan JSON and adapt it to your provider version and organisation's requirements. For example, you may want to check that the logging level is not `OFF`, that the KMS key is customer-managed, or that specific mandatory tags are present.

### Run OPA

```bash
terraform plan -out=tfplan

terraform show -json tfplan > tfplan.json

opa eval \
  --data policy/stepfunctions.rego \
  --input tfplan.json \
  "data.terraform.stepfunctions.deny"
```

An empty result means these specific rules did not produce a denial. It does not mean the entire infrastructure is secure.

### Important metrics and signals

| Signal | Why it matters |
|---|---|
| ExecutionsStarted | Workflow volume |
| ExecutionsSucceeded | Successful execution count |
| ExecutionsFailed | Failed execution count |
| ExecutionsTimedOut | Workflow timeout count |
| ExecutionTime | Execution duration |
| ThrottledEvents | Throttling |
| Lambda errors | Downstream function failures |
| CloudWatch Logs | Detailed error investigation |
| X-Ray traces | Dependency and latency investigation |

### Common problems

| Problem | Likely cause | What to check |
|---|---|---|
| AccessDenied | Missing IAM permissions | Execution role policy |
| Lambda invocation failure | Incorrect function ARN or permissions | Lambda ARN and `InvokeFunction` |
| State machine creation fails | Invalid ASL | JSON structure and state transitions |
| Workflow stuck | Missing timeout or callback | Timeout and task-token handling |
| Workflow fails repeatedly | Incorrect retry policy | Error type and retry settings |
| Logs missing | Incorrect logging permissions | Role permissions and Logs resource policy |
| KMS error | Key policy or IAM permissions | KMS key policy |
| Payment duplicated | Missing idempotency | Payment key and transaction handling |
| Large payload failure | Payload limit exceeded | Use S3 references |
| Execution history limit | Excessive events in Standard workflow | Split workflow or use Distributed Map |

Standard workflows have an execution history quota of 25,000 events. Consider splitting long-running workflows or using Distributed Map for suitable workloads.

# 14. Interview questions and answers

**Q1. What is AWS Step Functions?**

A serverless orchestration service used to coordinate multiple services and application steps into workflows.

**Q2. What is ASL?**

Amazon States Language. It is the JSON-based language used to define Step Functions state machines.

**Q3. What is the difference between Standard and Express?**

Standard is designed for long-running workflows with durable execution history and exactly-once workflow execution semantics. Express is designed for high-volume, short-running workloads with request and duration-based pricing.

**Q4. What is a Task state?**

A state that performs work by calling a service such as Lambda, ECS, DynamoDB or SNS.

**Q5. What is a Choice state?**

A state that evaluates conditions and selects the next workflow state.

**Q6. What is a Parallel state?**

A state that executes multiple branches concurrently and waits for the branches to finish.

**Q7. What is a Map state?**

A state that processes multiple items from an array or dataset.

**Q8. What is the difference between Retry and Catch?**

Retry attempts the failed task again. Catch routes the execution to a fallback state after an error.

**Q9. How does Step Functions integrate with Lambda?**

It uses a Task state and Lambda service integration to invoke a function and receive its result.

**Q10. How do you secure Step Functions?**

Use least-privilege IAM roles, encryption, restricted logging, resource tagging and secure downstream services.

**Q11. How is Step Functions charged?**

Standard uses state-transition pricing. Express uses request and execution-duration pricing.

**Q12. Can Step Functions run inside a VPC?**

No. Step Functions is a managed service and does not attach to a VPC or security group. It can orchestrate VPC-connected services.

**Q13. How do you prevent duplicate payment processing?**

Use an idempotency key and enforce idempotent transaction handling in the payment service. Do not rely only on workflow retry settings.

**Q14. How do you implement human approval?**

Use a callback task token, send an approval request to the human approver and resume the workflow when the token is returned.

**Q15. How do you deploy Step Functions with Terraform?**

Create the IAM execution role, logging and encryption resources, define the ASL workflow and deploy it using `aws_sfn_state_machine`.
