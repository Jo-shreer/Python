# AWS S3 – Complete Cheatsheet (Fundamentals to Production)

# 1. What is Amazon S3?

Amazon S3 (Simple Storage Service) is an AWS object storage service used to store and retrieve any amount of data.

Examples:
- Images and videos
- Application logs
- Backup files
- Documents and PDFs
- Database exports
- Data lake files
- Static website content
- Application-generated files

S3 is an object storage service, not a traditional file system or block storage service.

### Important characteristics

- Highly durable: Designed for 99.999999999% (11 nines) durability.
- Scalable: Automatically scales as data grows.
- Highly available: Availability depends on the selected storage class.
- Secure: Supports IAM, bucket policies, ACLs, encryption and access points.
- Cost-effective: Multiple storage classes for different access patterns.
- Regional service: Buckets are created in a specific AWS Region.

# 2. S3 Architecture

S3 consists of three important concepts:

### A. Bucket

A bucket is a container used to store objects.

Example:

`company-prod-data`

Bucket names must be globally unique within the AWS partition.

### B. Object

An object is the actual file stored inside an S3 bucket.

An object consists of:
- Object key: Name/path of the object.
- Object data: Actual file content.
- Metadata: Additional information about the object.
- Version ID: Identifies a particular version if versioning is enabled.

Example:

`company-prod-data/documents/invoice.pdf`

Here:
- Bucket: company-prod-data
- Object key: documents/invoice.pdf
- Object: The actual invoice file.

### C. Prefix

S3 does not have actual directories like a traditional file system.

Instead, it uses object keys and prefixes to simulate folders.

Example:

```text
company-prod-data/
    application-logs/
        app1/
            log1.txt
            log2.txt
    backups/
        database/
            backup1.sql
    documents/
        invoice.pdf
```

The folder structure is based on object key prefixes.

# 3. S3 Storage Classes

Storage classes determine how S3 stores data and how much you pay for storage, retrieval and requests.

### A. S3 Standard

Used for frequently accessed data.

Examples:
- Application files
- Images
- Frequently accessed documents

Characteristics:
- High availability.
- Low latency.
- Designed for frequent access.
- No minimum storage duration.

### B. S3 Intelligent-Tiering

Automatically moves objects between access tiers based on access patterns.

Useful when:
- You don't know how frequently files will be accessed.
- Access patterns change.
- You want to optimise storage costs.

There can be monitoring and automation charges.

### C. S3 Standard-IA

IA means Infrequent Access.

Used for files accessed occasionally but requiring quick retrieval.

Examples:
- Monthly reports
- Backups
- Historical documents

Characteristics:
- Lower storage cost than Standard.
- Retrieval charges apply.
- Minimum storage duration of 30 days.
- Minimum billable object size of 128 KB.

### D. S3 One Zone-IA

Stores data in a single Availability Zone.

Used for:
- Re-creatable data.
- Secondary copies of data.
- Data that can tolerate AZ-level loss.

Cheaper than Standard-IA, but less resilient to the loss of an Availability Zone.

### E. S3 Glacier Instant Retrieval

Used for archive data that still needs immediate access.

Examples:
- Medical images.
- Historical records.
- Long-term archives occasionally accessed.

### F. S3 Glacier Flexible Retrieval

Used for long-term archival data where retrieval can take minutes to hours.

### G. S3 Glacier Deep Archive

Used for long-term archival data that is rarely accessed.

Examples:
- Compliance archives.
- Financial records.
- Long-term backups.

Retrieval can take hours.

### Storage class comparison

| Storage class | Typical use |
|---|---|
| Standard | Frequently accessed data |
| Intelligent-Tiering | Unknown/changing access patterns |
| Standard-IA | Infrequently accessed data |
| One Zone-IA | Re-creatable infrequent data |
| Glacier Instant Retrieval | Archive with immediate access |
| Glacier Flexible Retrieval | Long-term archive |
| Glacier Deep Archive | Very long-term archive |

Important: Storage costs are not the only costs. Consider retrieval charges, minimum storage durations, transitions and request charges.

# 4. S3 Versioning

Versioning allows you to maintain multiple versions of an object in the same bucket.

Example:

You upload:

`application.properties`

Later, you update the file.

Without versioning:
- The previous object is overwritten.

With versioning:
- S3 maintains the previous version.
- A new version is created.
- You can recover the previous version.

### Why use versioning?

- Accidental deletion recovery.
- Accidental overwrite recovery.
- Application rollback.
- Protection against certain types of user error.

### Delete marker

When you delete an object in a versioned bucket, S3 normally adds a delete marker rather than permanently deleting the previous versions.

You can recover the object by removing the delete marker, subject to permissions and retention controls.

### Important

Versioning can increase storage costs because previous versions continue consuming storage.

Use lifecycle policies to manage old versions.

# 5. S3 Lifecycle Management

Lifecycle policies automatically transition or delete objects based on age and other filters.

Example:

A company stores application logs in S3.

Requirements:
- First 30 days: Frequently accessed.
- After 30 days: Move to Standard-IA.
- After 90 days: Move to Glacier Flexible Retrieval.
- After 365 days: Delete expired data.

Lifecycle configuration can automate these operations.

### Important lifecycle actions

1. Transition current objects.
2. Transition noncurrent versions.
3. Expire current objects.
4. Permanently delete expired noncurrent versions.
5. Abort incomplete multipart uploads.

### Why abort incomplete multipart uploads?

Large files are uploaded in multiple parts.

If an upload is interrupted, uploaded parts can remain and incur storage charges.

An abort-incomplete-multipart-upload lifecycle rule cleans up these unused parts.

# 6. S3 Encryption

Encryption protects data stored in S3.

There are two major encryption categories.

### A. Encryption at Rest

Protects data stored inside S3.

Common options:

**SSE-S3**
- Encryption managed by Amazon S3.
- Uses Amazon-managed encryption keys.
- No separate KMS key management required.

**SSE-KMS**
- Uses AWS Key Management Service.
- Provides control over encryption keys.
- Supports key policies and auditing through CloudTrail.
- KMS API requests can incur additional charges.

**DSSE-KMS**
- Dual-layer server-side encryption using two layers of encryption.
- Used for specific higher-assurance requirements.

**SSE-C**
- Customer provides encryption keys with each request.
- AWS does not store the supplied key.
- The customer must securely manage the key.

### B. Encryption in Transit

Protects data while travelling between clients and S3.

Use HTTPS/TLS.

You can enforce HTTPS using a bucket policy that denies requests when `aws:SecureTransport` is false.

### Important production recommendation

Enable default bucket encryption and enforce secure transport.

For sensitive workloads, consider SSE-KMS with a customer-managed KMS key.

# 7. S3 Access Management

There are several ways to control access to S3.

### A. IAM Policies

IAM policies are attached to IAM users, groups or roles.

They define what an identity can do.

Example:

Allow an EC2 IAM role to upload files to a specific bucket.

### B. Bucket Policies

Bucket policies are resource-based policies attached directly to S3 buckets.

They define who can access the bucket and what actions are allowed or denied.

Example:
- Allow a specific IAM role to access the bucket.
- Deny access over HTTP.
- Deny access outside an approved network, if appropriately configured.

### C. S3 Access Control Lists (ACLs)

ACLs are an older access management mechanism.

For most modern workloads, use IAM policies and bucket policies instead.

Recommended setting:

`Bucket owner enforced`

This disables ACLs and makes policy-based access management the standard.

### D. S3 Access Points

Access Points provide separate access endpoints with individual policies for different applications or teams.

Example:

- Finance application uses one access point.
- Analytics application uses another access point.
- Each access point has its own access policy.

Useful for large organisations with complex access requirements.

# 8. S3 Block Public Access

S3 provides four public-access protection settings.

1. Block public ACLs.
2. Ignore public ACLs.
3. Block public bucket policies.
4. Restrict public bucket policies.

For production buckets, enable all four unless there is a specific, reviewed requirement for public access.

Important:

A bucket being private is not determined by its name. Public access is controlled through policies, ACLs and public access block settings.

# 9. S3 Replication

Replication automatically copies objects from one S3 bucket to another.

Two main types:

### A. Same-Region Replication (SRR)

Copies objects between buckets in the same AWS Region.

Use cases:
- Separate application environments.
- Centralised data collection.
- Separate accounts within the same region.

### B. Cross-Region Replication (CRR)

Copies objects to another AWS Region.

Use cases:
- Disaster recovery.
- Business continuity.
- Geographic data requirements.
- Regional resilience.

### Important replication requirements

- Source bucket versioning enabled.
- Destination bucket versioning enabled.
- Appropriate IAM replication role.
- Replication configuration.
- Appropriate KMS permissions if objects use SSE-KMS.

Replication is generally not retroactive for existing objects unless you use S3 Batch Replication.

Also, delete markers are not replicated by default in every replication configuration; check the relevant delete replication settings.

# 10. S3 Event Notifications

S3 can trigger events when objects are created, deleted or modified through supported operations.

Supported destinations include:

- Amazon SQS
- Amazon SNS
- AWS Lambda
- Amazon EventBridge

Example:

An application uploads an image to S3.

S3 triggers a Lambda function.

Lambda processes the image and creates a thumbnail.

Architecture:

```text
Application
    |
    v
S3 Bucket
    |
    v
S3 Object Created Event
    |
    v
Lambda Function
    |
    v
Process Image
```

Important:
- Configure the necessary permissions.
- S3 notifications can be delivered more than once.
- Design consumers to handle duplicate events.
- Avoid recursive Lambda triggers where the Lambda writes back into the same triggering prefix without appropriate filtering.

# 11. S3 Multipart Upload

Multipart upload is used to upload large objects.

Instead of uploading one large file, the file is split into multiple parts.

Advantages:
- Parallel uploads.
- Improved throughput.
- Failed parts can be retried individually.
- Suitable for large files.

AWS recommends multipart upload for objects around 100 MB or larger.

Important:
- Minimum part size is generally 5 MiB, except the final part.
- Maximum number of parts is 10,000.
- Maximum object size is 50 TB.

Use lifecycle policies to clean up incomplete multipart uploads.

# 12. S3 Performance

S3 automatically scales to support high request rates.

Important performance considerations:

- Use multipart upload for large files.
- Use parallel requests where appropriate.
- Use appropriate object key naming and partitioning for workload patterns.
- Use CloudFront for frequently accessed content distributed globally.
- Use S3 Transfer Acceleration for suitable long-distance uploads.
- Use S3 Express One Zone for workloads requiring very low latency in a supported architecture.

S3 provides strong read-after-write consistency for object PUTs and DELETEs.

# 13. S3 Gateway VPC Endpoint

This is particularly important when applications run inside private subnets.

Suppose EC2 in a private subnet needs to access S3.

You can create an S3 Gateway VPC Endpoint.

Architecture:

```text
EC2 (Private Subnet)
       |
       v
Route Table
       |
       v
S3 Gateway VPC Endpoint
       |
       v
Amazon S3
```

### Why use a Gateway Endpoint?

- No NAT Gateway required for S3 connectivity.
- No Internet Gateway required for the S3 connection.
- No endpoint hourly charge.
- No endpoint data processing charge.
- Traffic stays on the AWS network.

### Configuration

1. Navigate to VPC → Endpoints.
2. Create endpoint.
3. Select AWS services.
4. Select `com.amazonaws.<region>.s3`.
5. Choose Gateway endpoint.
6. Select the VPC.
7. Associate the private subnet route tables.
8. Configure an endpoint policy if required.
9. Create endpoint.

Important differences:

| Feature | S3 Gateway | S3 Interface |
|---|---|---|
| Endpoint type | Gateway | Interface |
| Route table association | Yes | No |
| Endpoint ENI | No | Yes |
| Security Group | No | Yes |
| Hourly endpoint charge | No | Yes |
| PrivateLink | No | Yes |

For ordinary S3 access from private EC2 instances in the same region, Gateway Endpoints are usually the cost-effective choice.

# 14. S3 Security Best Practices

For production environments:

1. Enable all four S3 Block Public Access settings.
2. Enable bucket versioning.
3. Enable default encryption.
4. Enforce HTTPS using a bucket policy.
5. Use IAM roles instead of hardcoded access keys.
6. Follow least-privilege IAM permissions.
7. Use bucket policies to restrict access.
8. Enable CloudTrail data events for sensitive buckets where required.
9. Configure lifecycle policies.
10. Enable replication for disaster recovery where required.
11. Consider S3 Object Lock for immutable compliance data.
12. Enable logging and monitoring.
13. Use AWS Config to monitor bucket security configurations.
14. Regularly review bucket policies and access permissions.

# 15. S3 Object Lock

Object Lock prevents objects from being deleted or overwritten for a specified retention period.

Useful for:
- Financial records.
- Regulatory compliance.
- Audit records.
- Immutable backups.

Two retention modes:

**Governance mode**
- Users with special permissions can bypass retention.

**Compliance mode**
- Protected objects cannot be overwritten or deleted before retention expires, including by the account root user.

Object Lock requires versioning.

# 16. S3 Static Website Hosting

S3 can host static websites containing:

- HTML
- CSS
- JavaScript
- Images

Example:

```text
index.html
style.css
app.js
images/
```

You can enable static website hosting through bucket properties.

Important:
- S3 static website endpoints are HTTP endpoints.
- They do not directly provide HTTPS.
- For production websites, CloudFront with HTTPS and an appropriate origin configuration is generally preferred.
- Do not make sensitive buckets public just to host a website.

# 17. S3 Cost Considerations

S3 charges depend on several factors.

### A. Storage Charges

Charged according to the storage class and amount of data stored.

### B. Request Charges

Different API requests can have different prices.

Examples:
- PUT
- GET
- LIST
- DELETE

### C. Retrieval Charges

Certain storage classes charge for retrieving data.

### D. Data Transfer Charges

Charges can apply when data is transferred out of AWS or across certain network boundaries.

### E. Replication Charges

Replication can introduce additional request, storage and data transfer charges.

### F. KMS Charges

SSE-KMS can introduce additional KMS API request charges.

### G. Monitoring Charges

CloudTrail data events, S3 Storage Lens advanced features and monitoring tools can have additional charges.

### Cost optimisation

- Choose storage classes based on access patterns.
- Configure lifecycle policies.
- Delete unnecessary object versions.
- Clean up incomplete multipart uploads.
- Use S3 Gateway Endpoints for private-subnet S3 access.
- Review retrieval charges before archiving.
- Use S3 Intelligent-Tiering when appropriate.
- Monitor costs through AWS Cost Explorer.

Official pricing:
https://aws.amazon.com/s3/pricing/


```bash
aws s3 sync ./local-folder s3://my-bucket-name/
```

```bash
aws s3 ls s3://my-bucket-name/
```

```bash

```

### Delete a bucket

```bash
aws s3 rb s3://my-bucket-name --force
```

Use the delete command carefully. With versioning enabled, removing current objects does not necessarily remove all historical versions.

# 19. Important S3 Interview Questions

**Q1. What is the difference between EBS and S3?**

EBS is block storage attached to EC2 instances. S3 is object storage accessed through APIs.

**Q2. Is S3 regional or global?**

S3 buckets are regional resources, but bucket names are globally unique within an AWS partition.

**Q3. What happens when versioning is enabled?**

S3 retains multiple versions of objects. Deleting an object normally creates a delete marker.

**Q4. What is the difference between SSE-S3 and SSE-KMS?**

SSE-S3 uses S3-managed encryption keys. SSE-KMS uses AWS KMS and provides additional key-management and auditing capabilities.

**Q5. What is the difference between SRR and CRR?**

SRR replicates objects within the same region. CRR replicates objects across regions.

**Q6. Can EC2 in a private subnet access S3 without NAT?**

Yes. Use an S3 Gateway VPC Endpoint.

**Q7. Can EC2 in a private subnet access SQS without NAT?**

Yes. Use an SQS Interface VPC Endpoint.

**Q8. What is the difference between a bucket policy and IAM policy?**

An IAM policy is attached to an identity. A bucket policy is attached to the S3 bucket.

**Q9. What is a lifecycle policy?**

It automatically transitions or deletes objects based on configured rules.

**Q10. What is S3 Object Lock?**

It protects objects from deletion or modification for a retention period.

**Q11. What is the difference between S3 Standard and Intelligent-Tiering?**

Standard is for frequently accessed objects. Intelligent-Tiering automatically moves eligible objects between access tiers based on usage.

**Q12. Does S3 support directories?**

Not as actual file-system directories. S3 uses object keys and prefixes to represent folder-like structures.

# 20. Production-Level Terraform Example – AWS S3

Now let's implement a production-style S3 bucket using Terraform.

### Production requirements

We want to create a bucket with:

1. Unique bucket name.
2. Private access.
3. All public access blocked.
4. Bucket owner enforced.
5. Versioning enabled.
6. Server-side encryption enabled.
7. Lifecycle management.
8. Automatic cleanup of incomplete multipart uploads.
9. HTTPS-only access.
10. Tags for cost allocation and environment identification.

For this example, we will use SSE-S3 encryption. For workloads requiring customer-managed encryption keys, SSE-KMS can be configured instead.

## File 1: versions.tf

```hcl
terraform {
  required_version = ">= 1.5.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}
```

## File 2: provider.tf

```hcl
provider "aws" {
  region = var.aws_region

  default_tags {
    tags = {
      Project     = "Production-Storage"
      Environment = var.environment
      ManagedBy   = "Terraform"
    }
  }
}
```

## File 3: variables.tf

```hcl
variable "aws_region" {
  description = "AWS region"
  type        = string
  default     = "eu-west-1"
}

variable "bucket_name" {
  description = "Globally unique S3 bucket name"
  type        = string
}

variable "environment" {
  description = "Environment name"
  type        = string
  default     = "production"
}

variable "transition_days" {
  description = "Days before transitioning objects to Standard-IA"
  type        = number
  default     = 30
}

variable "glacier_days" {
  description = "Days before transitioning objects to Glacier Flexible Retrieval"
  type        = number
  default     = 90
}

variable "expiration_days" {
  description = "Days before expiring current objects"
  type        = number
  default     = 365
}
```

## File 4: main.tf

### A. Create S3 Bucket

```hcl
resource "aws_s3_bucket" "production" {
  bucket = var.bucket_name

  force_destroy = false

  tags = {
    Name = var.bucket_name
  }
}
```

`force_destroy = false` ensures Terraform will not automatically empty the bucket to delete it.

### B. Enable Versioning

```hcl
resource "aws_s3_bucket_versioning" "production" {
  bucket = aws_s3_bucket.production.id

  versioning_configuration {
    status = "Enabled"
  }
}
```

This protects against accidental overwrites and deletions by retaining previous object versions.

### C. Block Public Access

```hcl
resource "aws_s3_bucket_public_access_block" "production" {
  bucket = aws_s3_bucket.production.id

  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}
```

All four public access protection settings are enabled.

### D. Configure Object Ownership

```hcl
resource "aws_s3_bucket_ownership_controls" "production" {
  bucket = aws_s3_bucket.production.id

  rule {
    object_ownership = "BucketOwnerEnforced"
  }
}
```

This disables ACLs and ensures bucket-owner ownership of uploaded objects.

### E. Configure Server-Side Encryption

```hcl
resource "aws_s3_bucket_server_side_encryption_configuration" "production" {
  bucket = aws_s3_bucket.production.id

  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm = "AES256"
    }

    bucket_key_enabled = true
  }
}
```

This enables SSE-S3 encryption by default.

Note: S3 Bucket Keys are primarily relevant to SSE-KMS encryption. They are not needed for SSE-S3 and can be omitted from this configuration.

### F. Configure Lifecycle Management

```hcl
resource "aws_s3_bucket_lifecycle_configuration" "production" {
  bucket = aws_s3_bucket.production.id

  rule {
    id     = "production-data-lifecycle"
    status = "Enabled"

    filter {}

    transition {
      days          = var.transition_days
      storage_class = "STANDARD_IA"
    }

    transition {
      days          = var.glacier_days
      storage_class = "GLACIER"
    }

    expiration {
      days = var.expiration_days
    }
  }

  rule {
    id     = "cleanup-noncurrent-versions"
    status = "Enabled"

    filter {}

    noncurrent_version_expiration {
      noncurrent_days = 90
    }
  }

  rule {
    id     = "abort-incomplete-multipart-uploads"
    status = "Enabled"

    filter {}

    abort_incomplete_multipart_upload {
      days_after_initiation = 7
    }
  }

  depends_on = [
    aws_s3_bucket_versioning.production
  ]
}
```

Explanation:

- After 30 days, current objects transition to Standard-IA.
- After 90 days, they transition to Glacier Flexible Retrieval.
- After 365 days, current objects expire.
- Noncurrent versions are expired after 90 days.
- Incomplete multipart uploads are cleaned up after 7 days.

Important: These are example retention settings, not universal production defaults. Validate business retention requirements before applying them. Lifecycle transitions have minimum-duration and eligibility rules, and expiration of current objects in a versioned bucket creates delete markers rather than automatically permanently deleting every historical version.

### G. Enforce HTTPS Access

```hcl
resource "aws_s3_bucket_policy" "production" {
  bucket = aws_s3_bucket.production.id

  policy = jsonencode({
    Version = "2012-10-17"

    Statement = [
      {
        Sid       = "DenyInsecureTransport"
        Effect    = "Deny"
        Principal = "*"

        Action = "s3:*"

        Resource = [
          aws_s3_bucket.production.arn,
          "${aws_s3_bucket.production.arn}/*"
        ]

        Condition = {
          Bool = {
            "aws:SecureTransport" = "false"
          }
        }
      }
    ]
  })

  depends_on = [
    aws_s3_bucket_public_access_block.production
  ]
}
```

This denies requests made over insecure HTTP.

### H. Outputs

```hcl
output "bucket_name" {
  description = "Production S3 bucket name"
  value       = aws_s3_bucket.production.id
}

output "bucket_arn" {
  description = "Production S3 bucket ARN"
  value       = aws_s3_bucket.production.arn

}

output "bucket_region" {
  description = "Production S3 bucket region"
  value       = aws_s3_bucket.production.region
}
```

## 22. Additional Production Considerations

The Terraform example provides a secure starting point, but a complete enterprise production implementation may also require:

- SSE-KMS with a customer-managed KMS key.
- CloudTrail S3 data events.
- S3 server access logging or CloudTrail-based audit logging.
- Cross-region replication.
- S3 Object Lock for immutable backups.
- AWS Backup where applicable.
- S3 event notifications.
- Bucket policies restricted to approved IAM roles.
- VPC Gateway Endpoint and endpoint policies for private EC2 access.
- Monitoring and cost alerts.
- Separate buckets for application data, backups and audit logs.

For production, keep the bucket name and other environment-specific settings in variables, use remote Terraform state with locking, and protect the state file because it may contain sensitive infrastructure information.
