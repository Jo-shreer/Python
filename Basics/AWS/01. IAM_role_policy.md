# AWS IAM — Identity and Access Management

## 1. What is IAM?

**IAM (Identity and Access Management)** controls:

> **Who can access AWS resources, what they can do, and which resources they can access.**

IAM is a core AWS security service.

Examples:

```text
Lambda → Can it read S3?
Lambda → Can it write DynamoDB?
Lambda → Can it send an SQS message?
Developer → Can they deploy Lambda?
```

IAM answers these questions.

---

# 2. The Basic IAM Model

Think of IAM as:

```text
Identity
   ↓
Policy
   ↓
Permission
   ↓
AWS Resource
```

For example:

```text
Lambda
  ↓
IAM Role
  ↓
IAM Policy
  ↓
s3:GetObject
  ↓
S3 Bucket/Object
```

---

# 3. IAM Users

An IAM user represents a person or application identity inside AWS.

Example:

```text
Developer
   ↓
IAM User
```

However, for modern AWS environments, workloads generally use **IAM roles** rather than long-lived access keys.

Avoid hardcoding:

```python
AWS_ACCESS_KEY_ID = "..."
AWS_SECRET_ACCESS_KEY = "..."
```

Instead, use IAM roles where possible.

---

# 4. IAM Roles

An IAM role is an identity that can be **assumed** by another trusted entity.

Examples:

```text
Lambda → assumes IAM role

EC2 → assumes IAM role

AWS service → assumes IAM role

User → assumes IAM role
```

For Lambda:

```text
Lambda
   ↓
Assume Role
   ↓
Lambda Execution Role
   ↓
Permissions
```

---

# 5. IAM Role Has Two Important Parts

A role typically has:

1. **Trust policy**
2. **Permission policy**

This distinction is very important for interviews.

---

# 6. Trust Policy

The trust policy answers:

> **Who is allowed to assume this role?**

For a Lambda execution role:

```text
Lambda service
      ↓
Can assume?
      ↓
IAM Role
```

Example:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Service": "lambda.amazonaws.com"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

The important part is:

```text
Principal → lambda.amazonaws.com
```

It says the Lambda service is trusted to assume this role.

---

# 7. Permission Policy

The permission policy answers:

> **Once the role is assumed, what can the role do?**

Example:

```text
Lambda Execution Role
        ↓
Permission Policy
        ↓
s3:GetObject
dynamodb:PutItem
sqs:SendMessage
```

Example policy:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject"
      ],
      "Resource": "arn:aws:s3:::my-ingest-bucket/*"
    }
  ]
}
```

This allows the identity to read objects from the specified S3 bucket.

---

# 8. Trust vs Permission Policy

This is a common interview question.

### Trust policy

```text
WHO can assume the role?
```

### Permission policy

```text
WHAT can the role do?
```

Easy way to remember:

```text
Trust
→ "Who are you?"

Permission
→ "What are you allowed to do?"
```

---

# 9. IAM Policy Structure

A policy generally contains:

```text
Effect
Action
Resource
```

Example:

```json
{
  "Effect": "Allow",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::my-bucket/*"
}
```

### Effect

Usually:

```text
Allow
Deny
```

### Action

What operation is allowed.

Examples:

```text
s3:GetObject
s3:PutObject

dynamodb:GetItem
dynamodb:PutItem

sqs:SendMessage
```

### Resource

Which resource the permission applies to.

---

# 10. Explicit Deny

This is one of the most important IAM rules:

> **Explicit Deny overrides Allow.**

Example:

```text
Policy A
Allow → s3:GetObject

Policy B
Deny → s3:GetObject
```

Final result:

```text
Deny
```

Even though there is an Allow.

Think:

```text
Allow + Explicit Deny
        ↓
      DENIED
```

---

# 11. Identity-Based Policy

An identity-based policy is attached to an identity such as:

* User
* Group
* Role

Example:

```text
Lambda Role
     ↓
IAM Policy
     ↓
Allow s3:GetObject
```

---

# 12. Resource-Based Policy

A resource-based policy is attached directly to a resource.

Examples:

* S3 bucket policy
* SQS queue policy
* SNS topic policy
* KMS key policy
* Lambda resource policy

Example:

```text
S3 Bucket
   ↓
Bucket Policy
   ↓
Allow another AWS principal
```

---

# 13. Identity Policy vs Resource Policy

### Identity policy

```text
Who is making the request?
        ↓
What can they do?
```

### Resource policy

```text
Who can access this resource?
        ↓
What can they do?
```

Both can be involved in the same request.

---

# 14. Permissions Boundary

A permissions boundary defines the **maximum permissions** an identity can receive.

Important:

> A permissions boundary does not grant permissions by itself.

Think of it as a ceiling.

```text
IAM Policy
    ↓
    Allow
    ↓
Permissions Boundary
    ↓
Maximum allowed permissions
```

Example:

```text
Policy says:
Allow S3 + DynamoDB + SQS

Boundary says:
Only S3 + DynamoDB

Effective permissions:
S3 + DynamoDB
```

Conceptually:

```text
Effective permissions
=
Permissions granted by policies
∩
Permissions allowed by boundary
```

---

# 15. SCP — Service Control Policy

SCPs are used with **AWS Organizations**.

They apply restrictions at the organization/account/OU level.

Example:

```text
AWS Organization
       ↓
OU
       ↓
AWS Account
       ↓
SCP
       ↓
Maximum permissions boundary for account
```

Important:

> An SCP does not grant permissions.

It establishes the maximum permissions available to identities in the affected account.

---

# 16. Permissions Boundary vs SCP

### Permissions Boundary

Applies to an identity.

```text
User / Role
    ↓
Permissions Boundary
```

### SCP

Applies at AWS Organizations level.

```text
Organization / OU / Account
    ↓
SCP
```

Easy memory:

```text
Boundary
→ Identity level

SCP
→ Organization/account level
```

---

# 17. Effective Permissions

AWS authorization can involve multiple layers.

Conceptually:

```text
Identity policies
       ↓
Resource policies
       ↓
Permissions boundary
       ↓
SCP
       ↓
Explicit Deny
```

The exact IAM evaluation logic has additional nuances, but the key interview rule is:

```text
Explicit Deny
     ↓
Overrides applicable Allows
```

---

# 18. Least Privilege

**Least privilege** means:

> Give an identity only the permissions it actually needs.

Bad:

```json
{
  "Effect": "Allow",
  "Action": "*",
  "Resource": "*"
}
```

Better:

```json
{
  "Effect": "Allow",
  "Action": [
    "s3:GetObject"
  ],
  "Resource": "arn:aws:s3:::etl-input-bucket/incoming/*"
}
```

Even better when possible:

```text
Only required action
+
Only required resource
```

# 20. Lambda 1 IAM Role

Lambda 1 validates the file and sends metadata to DynamoDB/SQS.

Conceptually:

```text
Lambda 1
   ↓
Execution Role
   ├── S3 permission
   ├── DynamoDB permission
   └── SQS permission
```

Possible permissions:

```text
s3:GetObject
dynamodb:PutItem
dynamodb:UpdateItem
sqs:SendMessage
```

We should restrict the resources to the required bucket/table/queue.

# 21. Lambda 2 IAM Role

Lambda 2 consumes SQS and starts the ETL workflow.

Conceptually:

```text
Lambda 2
   ↓
Execution Role
   ├── Read S3
   ├── Read/update DynamoDB
   └── Start Step Functions
```

Possible permissions:

```text
s3:GetObject
dynamodb:GetItem
dynamodb:UpdateItem
states:StartExecution
```

Again, use specific resource ARNs rather than broad permissions.

For example:

```text

       ├── Redshift

       ├── S3
       └── Other required services
```

The exact permissions depend on which integrations the state machine uses.

# 23. Example: Lambda → S3

Suppose Lambda needs to read:

```text
s3://etl-ingest/incoming/customer.csv
```

We don't want:

```text
s3:*
```

for every S3 bucket.

Instead:

```json
{
  "Effect": "Allow",
  "Action": [
    "s3:GetObject"
  ],
  "Resource": "arn:aws:s3:::etl-ingest/incoming/*"
}
```

This follows least privilege.

---

# 24. Example: Lambda → SQS

If Lambda 1 only needs to send messages:

```json
{
  "Effect": "Allow",
  "Action": [
    "sqs:SendMessage"
  ],
  "Resource": "arn:aws:sqs:eu-west-1:123456789012:file-processing-queue"
}
```

It doesn't necessarily need:

```text
sqs:*
```

---

# 25. Example: Lambda → DynamoDB

If Lambda only needs to insert/update records:

```text
dynamodb:PutItem
dynamodb:UpdateItem
```

rather than giving every DynamoDB permission.

---

# 26. IAM and Secrets Manager

Suppose Lambda needs a database password.

Don't hardcode:

```python
password = "MySecretPassword"
```

Instead:

```text
Lambda
   ↓
IAM Role
   ↓
secretsmanager:GetSecretValue
   ↓
Secrets Manager
   ↓
Database secret
```

This keeps secret management separate from application code.

---

# 27. IAM and KMS

KMS controls encryption keys.

For example:

```text
Lambda
   ↓
AWS service
   ↓
Encrypted resource
   ↓
KMS key
```

Depending on the architecture, the relevant IAM permissions and KMS key policy must allow the required cryptographic operation.

Important distinction:

```text
IAM
→ Authorization

KMS
→ Key management / cryptography
```

# 28. IAM Role Example in Terraform

A Lambda execution role can be created with Terraform.

```hcl
resource "aws_iam_role" "lambda_role" {
  name = "etl-validation-lambda-role"

  assume_role_policy = jsonencode({
    Version = "2012-10-17"

    Statement = [{
      Effect = "Allow"

      Principal = {
        Service = "lambda.amazonaws.com"
      }

      Action = "sts:AssumeRole"
    }]
  })
}
```

This is the **trust policy**.

It says:

```text
Lambda service
    ↓
is trusted to assume
    ↓
this role
```

---

# 29. Terraform Permission Policy

Then we can create a permission policy:

```hcl
resource "aws_iam_policy" "lambda_policy" {

  name = "etl-validation-lambda-policy"

  policy = jsonencode({
    Version = "2012-10-17"

    Statement = [
      {
        Effect = "Allow"

        Action = [
          "s3:GetObject"
        ]

        Resource = "arn:aws:s3:::my-company-etl-ingest-dev/*"
      },

      {
        Effect = "Allow"

        Action = [
          "dynamodb:PutItem",
          "dynamodb:UpdateItem"
        ]

        Resource = "arn:aws:dynamodb:eu-west-1:123456789012:table/file-metadata"
      },

      {
        Effect = "Allow"

        Action = [
          "sqs:SendMessage"
        ]

        Resource = "arn:aws:sqs:eu-west-1:123456789012:file-processing-queue"
      }
    ]
  })
}
```

Then attach the policy:

```hcl
resource "aws_iam_role_policy_attachment" "lambda_policy" {

  role = aws_iam_role.lambda_role.name

  policy_arn = aws_iam_policy.lambda_policy.arn
}
```

# 30. Common IAM Interview Questions

## Q1. What is IAM?

> IAM is AWS's identity and access management service. It controls authentication and authorization by defining who or what can access AWS resources and which actions they are allowed to perform.

---

## Q2. What is an IAM role?

> An IAM role is an identity that can be assumed by trusted entities such as AWS services, applications, users, or workloads. It provides temporary credentials and permissions without requiring long-lived credentials to be embedded in the application.

---

## Q3. Trust policy vs permission policy?

> The trust policy defines who can assume the role, while the permission policy defines what actions the assumed role is allowed to perform.

---

## Q4. What overrides an Allow?

> An explicit Deny overrides an Allow.

---

## Q5. What is least privilege?

> Least privilege means granting only the minimum permissions required to perform a task, ideally restricting both the actions and resources.

---

## Q6. What is a permissions boundary?

> A permissions boundary defines the maximum permissions an IAM user or role can receive. It does not grant permissions by itself.

---

## Q7. What is an SCP?

> A Service Control Policy is an AWS Organizations policy that defines the maximum available permissions for accounts or organizational units. It does not grant permissions by itself.

---

## Q8. Identity policy vs resource policy?

> An identity-based policy is attached to an identity such as a user or role. A resource-based policy is attached directly to a resource such as an S3 bucket, SQS queue, SNS topic, or KMS key.

---

# 31. Scenario Question

### Interviewer:

> Your Lambda needs to read a file from S3, update DynamoDB, and send a message to SQS. How would you give it access?

### Answer:

> I would create a dedicated Lambda execution role and attach a least-privilege IAM policy. The policy would allow only the required S3 `GetObject`, DynamoDB operations, and SQS `SendMessage` actions, restricted to the specific resources. The role's trust policy would allow the Lambda service to assume the role.

Architecture:

```text
Lambda
   ↓
Execution Role
   ↓
Least-Privilege Policy
   ├── s3:GetObject
   ├── dynamodb:PutItem / UpdateItem
   └── sqs:SendMessage
```

---

# 32. Scenario: Lambda Gets AccessDenied

Suppose Lambda logs:

```text
AccessDeniedException
```

Investigation:

```text
1. Identify which AWS API call failed
             ↓
2. Check Lambda execution role
             ↓
3. Check identity policy
             ↓
4. Check resource policy
             ↓
5. Check permissions boundary
             ↓
6. Check SCP
             ↓
7. Check for explicit Deny
             ↓
8. Check KMS permissions/key policy if encryption is involved
```

This is a strong troubleshooting approach.
