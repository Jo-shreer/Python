# AWS Security Groups — Complete Practical Guide

## 1. First understand what an AWS Security Group is

An AWS Security Group (SG) is a virtual firewall for controlling network traffic to and from supported resources in an Amazon Virtual Private Cloud (VPC).

Think of it this way:

- A VPC is your private network in AWS.
- A subnet is a section of that network.
- A resource, such as an EC2 instance or RDS database, needs network connectivity.
- A Security Group controls which network connections are allowed to reach that resource and which connections it can initiate.

A Security Group does not create an EC2 instance, database, load balancer, or application. It only controls network traffic for a resource that uses it.

### Important Security Group characteristics

1. Security Groups are stateful. If an allowed connection comes in, its response traffic is automatically allowed back out. The same applies to connections initiated outbound.
2. Security Groups contain allow rules, not deny rules.
3. Inbound traffic is denied by default until you add an inbound rule.
4. A newly created Security Group normally has an outbound rule allowing all traffic. You can change this.
5. You can associate multiple Security Groups with a supported resource. Their allowed rules are combined.
6. Security Groups are associated with a VPC.
7. Security Groups work at the resource/network-interface level, rather than being subnet-wide firewalls.

## 2. What is a Network Interface (ENI)?

This is one of the most important concepts to understand before learning Security Groups.

ENI means **Elastic Network Interface**.

An ENI is like a virtual network card attached to a computer.

Think about your physical laptop:
- Your laptop has a Wi-Fi network card.
- That network card allows the laptop to communicate with other computers and the internet.
- It has network addresses and network settings.

An EC2 instance also needs a virtual network card to communicate with other resources. AWS provides this through an Elastic Network Interface.

An ENI can have:
- A private IPv4 address.
- One or more secondary private IP addresses.
- IPv6 addresses, if configured.
- A MAC address.
- One or more associated Security Groups.
- A subnet association.

**Where does the Security Group fit?**

The Security Group is associated with the network interface. It controls the traffic that can reach and leave the resource through that interface.

Example:

Imagine an EC2 instance:

- EC2 instance: `web-server-01`
- Private IP: `10.0.1.25`
- ENI: `eni-123456`
- Security Group: `web-server-sg`

The EC2 instance uses its ENI to communicate over the VPC network. The Security Group associated with that ENI controls the allowed traffic.

The simplified relationship is:

EC2 instance → Network Interface (ENI) → Security Group rules

This is a conceptual relationship. You normally associate the Security Group with the EC2 instance through its network interface, rather than manually configuring the ENI every time.

### Do all AWS services have a network interface?

No. Only certain services and configurations use VPC network interfaces.

Some services have AWS-managed network interfaces. For example:
- EC2 instances have network interfaces.
- RDS uses VPC networking and Security Groups.
- Lambda functions configured for VPC access use network interfaces managed by AWS.
- ECS tasks using the `awsvpc` network mode use task network interfaces.
- Fargate tasks use VPC network interfaces.
- VPC interface endpoints use network interfaces in your subnets.

Other services, such as S3 buckets and SQS queues, do not have a Security Group attached to them.

This is why you should not assume that every AWS service needs a Security Group.

## 4. What are ingress and egress rules?

When you create a Security Group, you define rules to control network traffic.

There are two directions:

### Ingress = inbound traffic

Ingress means traffic coming into the resource.

Example:

You have an EC2 web server. A user opens a browser and visits your website.

The user's request travels to the EC2 web server.

You need an inbound rule allowing the appropriate web traffic.

Example:

- Type: HTTPS
- Protocol: TCP
- Port: 443
- Source: Internet (`0.0.0.0/0`), if the website is intentionally public

This allows incoming HTTPS connections.

### Egress = outbound traffic

Egress means traffic leaving the resource.

Example:

Your EC2 application needs to connect to an RDS database.

The application sends a request from EC2 to RDS.

The EC2 Security Group must allow the outbound connection to the database port if its egress rules are restrictive.

The RDS Security Group must allow inbound traffic from the EC2 application.

### Example: EC2 application connecting to RDS

Suppose you have:

- EC2 application server
- RDS PostgreSQL database
- PostgreSQL port: 5432

You configure:

**EC2 Security Group**

| Direction | Protocol | Port | Destination/source |
|---|---|---|---|
| Ingress | TCP | 8080 | ALB Security Group |
| Egress | TCP | 5432 | RDS Security Group |

**RDS Security Group**

| Direction | Protocol | Port | Destination/source |
|---|---|---|---|
| Ingress | TCP | 5432 | EC2 application Security Group |

Why do you need both?

The EC2 instance initiates the database connection. Its outbound rule must allow that connection. The database receives the connection, so its inbound rule must allow it.

Because Security Groups are stateful, you do not need to create a separate inbound rule on EC2 just to allow the response from RDS.

If you retain the default allow-all outbound rule on EC2, you do not need to add the specific outbound 5432 rule. However, the RDS inbound rule is still required.

## 5. What is a protocol? Why do we define TCP, UDP and ICMP?

A protocol is a set of rules that devices use to communicate over a network.

When creating a Security Group rule, you choose a protocol because AWS needs to know what kind of network traffic you want to allow.

### TCP — Transmission Control Protocol

TCP is a connection-oriented protocol.

It establishes a connection between two devices and helps ensure that data is delivered reliably and in the correct order.

Common uses:
- Websites.
- SSH.
- RDP.
- Database connections.
- Application-to-application communication.

Examples:

| Application | Protocol | Port |
|---|---|---|
| SSH | TCP | 22 |
| HTTP | TCP | 80 |
| HTTPS | TCP | 443 |
| Application server | TCP | 8080 |
| PostgreSQL | TCP | 5432 |
| MySQL | TCP | 3306 |

### UDP — User Datagram Protocol

UDP is a connectionless protocol.

It sends packets without establishing the same type of connection as TCP. It has less overhead and is useful when speed and low latency are important.

Common uses:
- DNS queries.
- DHCP.
- Voice and video traffic.
- Some streaming and gaming applications.
- Certain monitoring and network protocols.

Example:

DNS commonly uses UDP port 53 for queries. DNS can also use TCP port 53 for certain responses and other operations.

### ICMP — Internet Control Message Protocol

ICMP is used for network diagnostics and error reporting.

A common example is the `ping` command.

When you ping a server, your computer sends an ICMP Echo Request. The destination can respond with an ICMP Echo Reply.

Why allow ICMP?

- To test whether a server is reachable.
- To troubleshoot network connectivity.
- To help diagnose network problems.

ICMP is not TCP or UDP, so it does not use TCP/UDP port numbers in the same way.

### ICMPv6

ICMPv6 is the equivalent control and diagnostic protocol for IPv6. It also supports important IPv6 network functions, so blocking it indiscriminately can break IPv6 connectivity.

### All traffic (`-1`)

In AWS Security Group rules, `-1` represents all protocols.

It allows all protocols and ports for the specified destination or source.

Avoid using it for unrestricted inbound access unless there is a clear reason.

## 6. Why do we need ports 22, 80, 443, 8080 and database ports?

This is where many people get confused.

A port is a communication endpoint used by an application or service on a computer.

Think of an IP address as the building address and a port as the particular door or service inside the building.

For example:

- IP address: `10.0.1.25`
- Port: `443`

The IP address identifies the server. Port 443 identifies the HTTPS service listening on that server.

A Security Group rule allows or blocks network traffic to a particular port.

### Port 22 — SSH

<ins>What is SSH?</ins>

SSH stands for Secure Shell.

SSH is a secure way to remotely log in to and administer a Linux server.

Imagine you create an EC2 Linux instance in AWS. The instance is running, but you need to configure it.

You want to:
- Log in to the server.
- Install software.
- Check application logs.
- Restart services.
- Troubleshoot issues.
- Update configuration files.
- Run Linux commands.

You can connect to the instance from your computer using SSH.

Example:

`ssh -i my-key.pem ec2-user@PUBLIC-IP`

This connection normally uses TCP port 22.

**Why does the Security Group need port 22?**

Your computer sends an SSH connection request to the EC2 instance. The EC2 Security Group must allow inbound TCP port 22 from your computer's public IP address or an approved private management network.

Example inbound rule:

| Protocol | Port | Source |
|---|---|---|
| TCP | 22 | `203.0.113.10/32` |

Do not normally use `0.0.0.0/0` for SSH. That would expose the SSH port to connection attempts from anywhere on the internet.

You do not need port 22 open for a normal website to work. SSH is for server administration.

**What about Windows EC2?**

Windows servers commonly use RDP (Remote Desktop Protocol) on TCP port 3389.

RDP allows you to connect to the Windows desktop remotely.

### Port 80 — HTTP

HTTP stands for Hypertext Transfer Protocol.

It is used when a browser communicates with a web server without TLS encryption.

Example:

`http://example.com`

The default HTTP port is TCP 80.

Why do we need it?

If your web server accepts normal HTTP requests, it needs to listen on port 80 and its Security Group needs to permit the traffic.

A common use is redirecting HTTP requests to HTTPS.

For example:

1. User opens `http://example.com`.
2. The load balancer receives the request on port 80.
3. It redirects the user to `https://example.com`.
4. The browser reconnects using port 443.

### Port 443 — HTTPS

HTTPS is HTTP protected by TLS encryption.

It protects data exchanged between the client and server.

Examples:
- Logging in to a website.
- Sending passwords.
- Making online payments.
- Accessing an application.
- Calling a secure API.

The default HTTPS port is TCP 443.

Why do we need it?

A public website normally accepts secure browser connections on port 443.

Example inbound rule on an internet-facing ALB:

| Protocol | Port | Source |
|---|---|---|
| TCP | 443 | `0.0.0.0/0` |

The ALB uses an HTTPS listener and a TLS certificate to terminate the encrypted connection.

The ALB might then communicate with the backend EC2 application over HTTP on port 8080, or HTTPS on another configured port.

Important: Opening port 443 in the Security Group does not automatically enable HTTPS. You must also configure the application or load balancer to listen on 443 and configure TLS appropriately.

### Port 8080 — Application server port

Port 8080 is commonly used by application servers and web applications.

It is not a special AWS port. It is a commonly chosen application port.

Examples:
- Java Spring Boot applications.
- Apache Tomcat.
- Custom backend applications.
- Internal APIs.
- Development web servers.

Imagine you deploy a Java Spring Boot application on EC2.

Your application configuration might specify:

`server.port=8080`

This means your application listens for incoming connections on port 8080.

Now imagine your architecture:

Internet → ALB → EC2 application

The ALB accepts HTTPS connections on port 443. It forwards requests to the EC2 application on port 8080.

Therefore, the EC2 Security Group needs to allow inbound TCP 8080 from the ALB Security Group.

Example:

| Resource | Protocol | Port | Source |
|---|---|---|---|
| ALB Security Group | TCP | 443 | Internet |
| EC2 Security Group | TCP | 8080 | ALB Security Group |

Why should EC2 allow 8080 only from the ALB Security Group?

Because users should access the application through the load balancer, not directly through the EC2 instance.

If you allow 8080 from `0.0.0.0/0`, anyone can potentially bypass the load balancer and access the application directly, assuming the instance is otherwise reachable.

The exact application port depends on your application configuration. It could be 8080, 3000, 5000, 8000 or another port.

### Port 3389 — RDP

RDP means Remote Desktop Protocol.

It is commonly used to connect to Windows servers.

Example:

You create a Windows EC2 instance and want to open its desktop remotely.

You use an RDP client to connect to the instance on TCP port 3389.

Only allow this from an approved management IP or network.

### Port 5432 — PostgreSQL

PostgreSQL is a relational database management system.

A database stores application information such as:
- Customer details.
- User accounts.
- Orders.
- Payments.
- Product information.
- Application records.

Suppose you create an RDS PostgreSQL database.

Your application runs on EC2 and needs to read and write data in PostgreSQL.

PostgreSQL commonly listens on TCP port 5432.

The application connects to the RDS endpoint on port 5432.

Therefore, the RDS Security Group needs an inbound rule:

| Protocol | Port | Source |
|---|---|---|
| TCP | 5432 | EC2 application Security Group |

You should not normally allow PostgreSQL from the whole internet.

The database should accept connections only from the application servers or approved administration network.

### Port 3306 — MySQL

MySQL is another relational database.

It stores structured application data and is commonly used by websites and business applications.

MySQL normally uses TCP port 3306.

Example:

EC2 application → RDS MySQL database

The RDS Security Group allows inbound TCP 3306 from the EC2 application Security Group.

### Other common ports

| Port | Protocol | Service | Why it is used |
|---|---|---|---|
| 53 | UDP/TCP | DNS | Resolves domain names to IP addresses |
| 123 | UDP | NTP | Time synchronization |
| 1433 | TCP | Microsoft SQL Server | Database connections |
| 1521 | TCP | Oracle Database | Database connections |
| 2049 | TCP/UDP | NFS | Network file system access, depending on configuration |
| 3000 | TCP | Application | Common development/application port |
| 5000 | TCP | Application | Common application/API port |
| 6379 | TCP | Redis | Cache connections |
| 9092 | TCP | Kafka | Common Kafka broker listener |
| 5671 | TCP | Amazon MQ/RabbitMQ | AMQP over TLS |
| 61617 | TCP | Amazon MQ/ActiveMQ | Common ActiveMQ OpenWire over TLS listener |

These are common defaults, not universal requirements. Always check the actual listener configuration for the service you deploy.

## 7. Practical AWS architecture: why different Security Groups are required

Imagine you are building a three-tier application.

It has:
1. A public Application Load Balancer.
2. Private EC2 application servers.
3. A private RDS database.

The traffic flow is:

User → ALB → EC2 application → RDS database

Each component has a different job, so each needs different Security Group rules.

### Security Group 1: ALB Security Group

Purpose: Allow users to access the application through the load balancer.

Inbound:

| Protocol | Port | Source | Reason |
|---|---|---|---|
| TCP | 443 | Internet | Allow secure HTTPS requests |
| TCP | 80 | Internet | Optional HTTP-to-HTTPS redirect |

Outbound:

| Protocol | Port | Destination | Reason |
|---|---|---|---|
| TCP | 8080 | EC2 application SG | Forward application requests to EC2 |

### Security Group 2: EC2 Application Security Group

Purpose: Protect the application servers.

Inbound:

| Protocol | Port | Source | Reason |
|---|---|---|---|
| TCP | 8080 | ALB Security Group | Allow application traffic from the load balancer |
| TCP | 22 | Approved management IP or management SG | Optional Linux administration |

Outbound:

| Protocol | Port | Destination | Reason |
|---|---|---|---|
| TCP | 5432 | RDS Security Group | Allow PostgreSQL database connections |
| TCP | 443 | Required destinations | Allow secure outbound API calls, package downloads or AWS service access as required |

### Security Group 3: RDS Security Group

Purpose: Protect the database.

Inbound:

| Protocol | Port | Source | Reason |
|---|---|---|---|
| TCP | 5432 | EC2 application Security Group | Allow the application to connect to PostgreSQL |

Outbound:

Normally the default outbound rule can remain unless you have a specific reason to restrict it. Remember that the database response to an allowed inbound connection is automatically permitted by stateful Security Group behavior.

**Important lesson:** You do not open every port on every resource. You open only the ports needed for communication between the relevant components.

## 8. Terraform: creating Security Groups and rules

Terraform lets you create AWS Security Groups as infrastructure as code.

You define:
- The VPC where the Security Group belongs.
- Ingress rules for incoming traffic.
- Egress rules for outgoing traffic.
- Which resources will use the Security Group.

### Step 1: Create an EC2 Security Group

```hcl
resource "aws_security_group" "app_sg" {
  name        = "application-sg"
  description = "Allow traffic from the load balancer"
  vpc_id      = aws_vpc.main.id

  tags = {
    Name = "application-sg"
  }
}
```

This creates the Security Group. It does not create an EC2 instance.

### Step 2: Define ingress rules

Allow application traffic from the ALB:

```hcl
resource "aws_vpc_security_group_ingress_rule" "app_from_alb" {
  security_group_id            = aws_security_group.app_sg.id
  referenced_security_group_id = aws_security_group.alb_sg.id

  ip_protocol = "tcp"
  from_port   = 8080
  to_port     = 8080

  description = "Allow application traffic from ALB"
}
```

This means:

- Target Security Group: application Security Group.
- Protocol: TCP.
- Port: 8080.
- Source: ALB Security Group.

Only resources using the ALB Security Group can initiate matching connections to the application on port 8080, subject to the other network controls.

### Step 3: Allow SSH for administration (only if required)

```hcl
resource "aws_vpc_security_group_ingress_rule" "ssh" {
  security_group_id = aws_security_group.app_sg.id

  cidr_ipv4   = "203.0.113.10/32"
  ip_protocol = "tcp"
  from_port   = 22
  to_port     = 22

  description = "SSH from approved admin IP"
}
```

This allows SSH from one approved public IPv4 address.

In production, consider using AWS Systems Manager Session Manager rather than exposing SSH to the internet. If you use Session Manager, the instance needs the appropriate IAM permissions and connectivity to the Systems Manager endpoints.

### Step 4: Define an egress rule

Allow the application server to connect to PostgreSQL:

```hcl
resource "aws_vpc_security_group_egress_rule" "app_to_rds" {
  security_group_id            = aws_security_group.app_sg.id
  referenced_security_group_id = aws_security_group.rds_sg.id

  ip_protocol = "tcp"
  from_port   = 5432
  to_port     = 5432

  description = "Allow PostgreSQL connections to RDS"
}
```

This allows the application server to initiate connections to the RDS Security Group on port 5432.

### Step 5: Create the RDS Security Group

```hcl
resource "aws_security_group" "rds_sg" {
  name        = "rds-postgres-sg"
  description = "Allow PostgreSQL from application servers"
  vpc_id      = aws_vpc.main.id

  tags = {
    Name = "rds-postgres-sg"
  }
}
```

### Step 6: Allow PostgreSQL inbound to RDS

```hcl
resource "aws_vpc_security_group_ingress_rule" "rds_from_app" {
  security_group_id            = aws_security_group.rds_sg.id
  referenced_security_group_id = aws_security_group.app_sg.id

  ip_protocol = "tcp"
  from_port   = 5432
  to_port     = 5432

  description = "Allow PostgreSQL from application servers"
}
```

### Step 7: Attach the Security Group to EC2

```hcl
resource "aws_instance" "app" {
  ami           = var.ami_id
  instance_type = "t3.micro"
  subnet_id     = aws_subnet.private.id

  vpc_security_group_ids = [
    aws_security_group.app_sg.id
  ]
}
```

Here, Terraform creates an EC2 instance and associates the application Security Group with its network interface.

### Step 8: Attach the Security Group to RDS

```hcl
resource "aws_db_instance" "database" {
  identifier             = "application-db"
  engine                 = "postgres"
  instance_class         = "db.t3.micro"
  allocated_storage      = 20
  username               = var.db_username
  password               = var.db_password
  db_subnet_group_name   = aws_db_subnet_group.main.name
  vpc_security_group_ids = [aws_security_group.rds_sg.id]
  publicly_accessible    = false
  skip_final_snapshot    = true
}
```

The RDS resource uses the RDS Security Group to control database network access.

This example is for learning. Production database configurations should also include suitable credentials handling, encryption, backup, deletion protection and instance sizing.

### Terraform rule resource note

The examples use the newer standalone Terraform resources:
- `aws_vpc_security_group_ingress_rule`
- `aws_vpc_security_group_egress_rule`

You can also define inline `ingress` and `egress` blocks inside `aws_security_group`, but avoid managing the same rules through both inline blocks and standalone rule resources. Mixing management approaches can cause conflicts.

## 9. Which Security Groups should you create for common AWS services?

A practical naming and design approach is to create Security Groups based on the resource's role.

| Security Group name | Associated resource | Typical purpose |
|---|---|---|
| `alb-sg` | Application Load Balancer | Accept user traffic on 443 |
| `web-ec2-sg` | EC2 web server | Accept application traffic from ALB |
| `app-ec2-sg` | EC2 application server | Accept internal application requests |
| `bastion-sg` | Bastion EC2 instance | Allow approved administration access |
| `rds-sg` | RDS database | Allow database connections from application tier |
| `redis-sg` | ElastiCache Redis | Allow cache connections from application tier |
| `efs-sg` | EFS mount targets | Allow NFS traffic from approved clients |
| `lambda-sg` | Lambda VPC network interfaces | Control the function's VPC network traffic |
| `ecs-task-sg` | ECS task network interfaces | Control task network traffic |
| `eks-node-sg` | EKS worker nodes | Control node-level networking |
| `vpce-sg` | Interface VPC endpoint | Control access to the endpoint network interfaces |
| `msk-sg` | MSK broker networking | Allow approved Kafka client traffic |

You do not have to create one Security Group per AWS service. You should create Security Groups around similar network roles and access requirements.

For example, multiple EC2 application servers may share one application Security Group if they need the same access.

However, do not put your ALB, application servers and RDS into one Security Group just because they belong to the same application. Separate them according to their responsibilities.

## 10. More service-specific examples

### EC2

Use Security Groups to control access to EC2 network interfaces.

Examples:
- Port 22 for Linux SSH administration.
- Port 3389 for Windows RDP.
- Port 80 for HTTP.
- Port 443 for HTTPS.
- Port 8080 for a backend application.

### Application Load Balancer

An ALB Security Group controls traffic reaching the load balancer and traffic it can send to targets.

Example:
- Inbound 443 from users.
- Optional inbound 80 for redirecting to HTTPS.
- Outbound application port to the EC2 target Security Group.

### Network Load Balancer

An NLB can use Security Groups when configured with them. They control network access to the load balancer and its targets.

An NLB created without Security Groups cannot simply have one added later, so plan this when creating it.

### RDS and Aurora

Use Security Groups to control which application servers or approved clients can connect to the database.

Common default ports:
- PostgreSQL: 5432.
- MySQL: 3306.
- SQL Server: 1433.
- Oracle: 1521.

The database Security Group should generally accept connections from the application Security Group, not the entire internet.

### ElastiCache

ElastiCache provides in-memory caching.

Applications use it to retrieve frequently accessed data without repeatedly querying the primary database.

Common ports:
- Redis: 6379.
- Memcached: 11211.

The cache Security Group should allow traffic from the application tier.

### EFS

EFS is a shared network file system.

EC2 instances or other supported clients can mount it over NFS.

Common NFS port:
- TCP 2049.

The EFS mount-target Security Group should allow TCP 2049 from the client Security Group.

### Lambda

Lambda does not need a Security Group in every configuration.

When a Lambda function is configured to connect to resources in a VPC, you select subnets and Security Groups. AWS manages the network interfaces used for this VPC connectivity.

For example, a Lambda function accessing RDS might use:
- Lambda Security Group: outbound access to the database port.
- RDS Security Group: inbound access from the Lambda Security Group.

The Lambda Security Group does not make the function publicly reachable. Internet access also depends on subnet routing and the network architecture.

### ECS

For ECS tasks using `awsvpc` networking, each task gets its own network interface and can have Security Groups.

For ECS on EC2, the EC2 container host and the task networking configuration may have different Security Group requirements.

### EKS

EKS networking is more involved. Security Groups can protect:
- Worker node network interfaces.
- The EKS cluster/control-plane communication path.
- Pods using Security Groups for Pods, where configured.

Do not assume that one Security Group controls every pod in an EKS cluster. The result depends on the cluster networking mode and configuration.

### VPC Interface Endpoints

An interface endpoint provides private connectivity to supported AWS services through network interfaces in your VPC.

For example, an EC2 instance can access Secrets Manager using an interface endpoint without needing a public internet route.

The endpoint has a Security Group that controls which clients can connect to it.

Example:
- Endpoint Security Group inbound TCP 443 from the EC2 application Security Group.
- EC2 needs outbound TCP 443 to the endpoint if egress is restricted.

## 11. Security Group versus Network ACL

These are different AWS networking controls.

| Feature | Security Group | Network ACL |
|---|---|---|
| Applies to | Resource/network interface | Subnet |
| Stateful? | Yes | No |
| Rules | Allow only | Allow and deny |
| Rule evaluation | All matching allow rules are combined | Rules evaluated in number order |
| Return traffic | Automatically allowed for established connections | Must be allowed by rules in both directions |
| Common use | Control access to EC2, RDS and other supported resources | Additional subnet-level network protection |

Remember:

- Security Group = resource-level firewall.
- Network ACL = subnet-level firewall.

## 12. Common Security Group mistakes

1. Opening SSH (22) to `0.0.0.0/0`.
2. Opening database ports such as 3306 or 5432 to the entire internet.
3. Allowing port 8080 from everyone when only the ALB should access the application.
4. Assuming that port 443 automatically enables HTTPS without configuring TLS.
5. Forgetting the RDS inbound rule from the application Security Group.
6. Assuming that all AWS services need Security Groups.
7. Creating one Security Group for every resource without considering the network role.
8. Mixing inline Security Group rules with standalone Terraform rule resources.
9. Forgetting that Security Groups are stateful when configuring return traffic.
10. Assuming a Security Group alone provides internet connectivity. Routing, subnets, gateways, DNS and other network settings also matter.

## 13. How to troubleshoot Security Group connectivity

If an application cannot connect to another resource, check:

1. Is the correct Security Group attached to the resource?
2. Is the destination port correct?
3. Does the destination Security Group allow inbound traffic from the source?
4. Does the source Security Group allow outbound traffic, if egress is restricted?
5. Are the resources in reachable subnets and VPCs?
6. Are route tables configured correctly?
7. Are Network ACLs allowing the traffic and return traffic?
8. Is the application actually listening on the expected port?
9. Is the correct DNS name or private IP being used?
10. Are any host firewalls, such as Linux `iptables` or `firewalld`, blocking the connection?

Useful commands:

```bash
# Check listening ports on Linux
sudo ss -tulnp

# Check whether an application port is reachable
nc -vz <server-ip> 8080

# Test HTTPS connectivity
curl -v https://<hostname>

# Check DNS resolution
nslookup <hostname>
```

AWS CLI examples:

```bash
# List Security Groups
aws ec2 describe-security-groups

# Show a particular Security Group
aws ec2 describe-security-groups \
  --group-ids sg-0123456789abcdef0

# List EC2 network interfaces
aws ec2 describe-network-interfaces

# Show Security Groups associated with an EC2 instance
aws ec2 describe-instances \
  --instance-ids i-0123456789abcdef0 \
  --query "Reservations[].Instances[].SecurityGroups"
```

## 14. Key points to remember

- A Security Group is a virtual firewall.
- A Security Group is associated with a supported resource through its network interface or service networking configuration.
- An ENI is like a virtual network card.
- Ingress means incoming traffic.
- Egress means outgoing traffic.
- TCP is commonly used for web, SSH and database connections.
- UDP is commonly used for DNS and other low-overhead network traffic.
- ICMP is used for network diagnostics such as ping.
- Port 22 is for Linux SSH administration.
- Port 3389 is for Windows RDP administration.
- Port 80 is for HTTP.
- Port 443 is for HTTPS.
- Port 8080 is commonly used by application servers.
- Port 5432 is PostgreSQL.
- Port 3306 is MySQL.
- RDS needs a Security Group to control database network access.
- S3, SQS and DynamoDB do not have Security Groups attached directly.
- You do not need to create a Security Group for every AWS service.
- Only allow the minimum traffic required for the application to function.

**The most important real-world example to remember:**

When you build an application using AWS:

- ALB Security Group: allows users to access the application over HTTPS (443).
- EC2 Application Security Group: allows traffic from the ALB on the application's port (for example, 8080).
- RDS Security Group: allows database connections from the EC2 application on the database port (for example, 5432).
- SSH (22): only if you need direct Linux administration, and only from an approved source.

This is how Security Groups are used to secure communication between AWS resources.
