# AMAZON AURORA — COMPLETE PRODUCTION CHEAT SHEET

## 1. What is Amazon Aurora?

Amazon Aurora is a fully managed relational database engine provided by AWS as part of Amazon RDS.

It is compatible with:
- MySQL.
- PostgreSQL.

Aurora combines relational database capabilities with a distributed storage architecture designed for high availability, durability, and performance.

You use SQL and familiar relational database concepts:
- Tables.
- Rows.
- Columns.
- Primary keys.
- Foreign keys.
- Indexes.
- Joins.
- Transactions.
- Stored procedures.
- Database users and permissions.

AWS manages much of the underlying database infrastructure, including storage replication, hardware maintenance, backups, patching options, monitoring integration, and failover mechanisms.

### Aurora is useful when you need

- A relational database for transactional applications.
- High availability across Availability Zones.
- Read scaling through replicas.
- Automatic storage growth.
- Managed backups and point-in-time recovery.
- MySQL or PostgreSQL compatibility.
- Multi-Region disaster recovery.
- Variable database capacity through Aurora Serverless v2.

### Aurora is not

- A NoSQL database like DynamoDB.
- A data warehouse like Redshift.
- A cache like ElastiCache.
- A general-purpose file storage service like S3.
- A database that automatically removes the need for SQL optimization.

## 2. Aurora editions and deployment options

There are two primary Aurora-compatible database engines.

### A. Aurora MySQL-Compatible Edition

Aurora MySQL supports MySQL-compatible database applications.

Use it when:
- Your application already uses MySQL.
- You have MySQL drivers and ORM integrations.
- You want a managed relational database with Aurora storage and replication.
- You are migrating from MySQL or an appropriate MySQL-compatible RDS deployment.

Typical applications:
- E-commerce.
- Order management.
- Customer management.
- Booking systems.
- Inventory applications.
- Transactional APIs.

### B. Aurora PostgreSQL-Compatible Edition

Aurora PostgreSQL supports PostgreSQL-compatible applications.

Use it when:
- Your application uses PostgreSQL.
- You need PostgreSQL SQL capabilities.
- You use PostgreSQL extensions supported by Aurora.
- You need advanced relational querying and data types.
- You want to migrate an appropriate PostgreSQL workload.

Typical applications:
- Financial applications.
- SaaS applications.
- Enterprise applications.
- Complex transactional systems.
- Applications with advanced SQL queries.
- Geospatial applications where the required PostgreSQL extensions are supported.

### C. Provisioned Aurora

You select the database instance class, for example:

- `db.r7g.large`
- `db.r7g.xlarge`
- `db.r6g.large`
- Other supported instance families and sizes.

You pay for the provisioned database instances while they are running.

Best for:
- Predictable workloads.
- Consistent database utilization.
- Production databases with stable demand.
- Workloads requiring predictable instance capacity.

### D. Aurora Serverless v2

Aurora Serverless v2 automatically adjusts database compute capacity within a configured minimum and maximum ACU range.

ACU means Aurora Capacity Unit.

One ACU represents approximately 2 GiB of memory, along with corresponding CPU and networking capacity.

Example:
- Minimum capacity: 0.5 ACU.
- Maximum capacity: 16 ACUs.
- Database demand increases.
- Aurora scales capacity upward.
- Demand decreases.
- Aurora scales capacity downward.

Best for:
- Variable workloads.
- Development and testing.
- SaaS applications with unpredictable traffic.
- Applications with occasional bursts.
- Workloads where fixed instance sizing is inefficient.

Important: Serverless v2 is still an Aurora DB instance architecture. You configure the cluster capacity range and use the `db.serverless` DB instance class.

It is not the same as the older Aurora Serverless v1 architecture.

## 3. Aurora architecture

Understanding Aurora architecture is essential before designing it in Terraform.

Aurora has two major components:

1. Compute layer.
2. Distributed storage layer.

### A. Compute layer

The compute layer consists of database instances.

There are two important roles.

**Writer instance**

The writer instance:
- Handles write operations.
- Handles inserts.
- Handles updates.
- Handles deletes.
- Handles schema changes.
- Can also handle read queries.

An Aurora cluster has one primary writer at a time.

**Reader instances**

Reader instances:
- Serve read-only database traffic.
- Can distribute read workload.
- Can be used as failover targets.
- Can have different instance sizes in provisioned configurations.
- Can scale independently in suitable Serverless v2 configurations.

Example:

Application → Aurora writer endpoint → Writer instance

Application → Aurora reader endpoint → Reader instances

### B. Storage layer

Aurora uses a distributed, shared storage architecture.

Important characteristics:
- Storage is automatically managed.
- Storage grows as data grows.
- Data is replicated across three Availability Zones.
- Aurora maintains six copies of data across those three AZs.
- Storage replication is handled independently of the database instance replication model.
- You do not provision a conventional EBS volume for the Aurora database data.

The six copies are distributed as two copies in each of three AZs.

This is an important distinction:

**Aurora storage replication is not the same thing as creating six database instances.**

You can have one writer instance and no reader instances while the Aurora storage layer still maintains its distributed copies.

### C. Example architecture

Application tier:

- API Gateway.
- Lambda.
- ECS.
- EKS.
- EC2.

Database tier:

- Aurora writer.
- Aurora readers.
- Aurora distributed storage.

Example:

Client
  |
API Gateway
  |
Lambda
  |
Aurora cluster endpoint
  |
Aurora writer
  |
Aurora distributed storage

Read-heavy applications can also use the reader endpoint:

Application
  |
Aurora reader endpoint
  |
Reader instances

## 4. Aurora cluster vs DB instance

This distinction is very important.

### Aurora DB cluster

The cluster represents the overall database deployment.

It manages:
- Database engine.
- Storage.
- Backup configuration.
- Encryption.
- Cluster-level parameter group.
- Cluster endpoints.
- Serverless capacity range.
- Deletion protection.
- Global database configuration.
- Other cluster-level settings.

Terraform resource:

`aws_rds_cluster`

### Aurora DB instance

An instance represents a compute node in the cluster.

It manages:
- Instance class.
- Availability Zone placement.
- Instance-level parameter group.
- Promotion tier.
- Performance Insights settings.
- Monitoring configuration.
- Instance-specific settings.

Terraform resource:

`aws_rds_cluster_instance`

### Example

One Aurora cluster:

- One writer instance.
- Two reader instances.
- One shared distributed storage layer.

Terraform:

```hcl
resource "aws_rds_cluster" "main" {
  cluster_identifier = "production-aurora"
  engine              = "aurora-postgresql"
}

resource "aws_rds_cluster_instance" "writer" {
  identifier         = "production-writer"
  cluster_identifier = aws_rds_cluster.main.id
  instance_class     = "db.r7g.large"
}

resource "aws_rds_cluster_instance" "reader" {
  identifier         = "production-reader"
  cluster_identifier = aws_rds_cluster.main.id
  instance_class     = "db.r7g.large"
}
```

The writer and reader roles are managed by Aurora. You do not create a separate storage volume for each instance.

## 5. Aurora endpoints

Aurora provides different endpoints for different connection requirements.

This is one of the most important concepts for application architecture.

### A. Cluster endpoint — writer endpoint

The cluster endpoint connects to the current writer instance.

Use it for:
- INSERT.
- UPDATE.
- DELETE.
- DDL.
- Transactions that require writes.
- Read-after-write consistency requirements.

Example hostname:

`production.cluster-xxxxxxxx.eu-west-1.rds.amazonaws.com`

If Aurora fails over to another writer, the cluster endpoint automatically points to the new primary.

Your application should reconnect and retry transient failures.

### B. Reader endpoint

The reader endpoint distributes connections across available Aurora reader instances.

Use it for:
- Reporting queries.
- Search queries.
- Read-heavy API operations.
- Dashboard queries.
- Analytics queries that can tolerate replica lag.

Example hostname:

`production.cluster-ro-xxxxxxxx.eu-west-1.rds.amazonaws.com`

Important:
- It balances connections, not necessarily every individual SQL query.
- Connection pooling can affect how traffic is distributed.
- It does not guarantee perfectly fresh data.
- Reader instances can have replication lag.

### C. Instance endpoint

Each individual DB instance has its own endpoint.

Use it when:
- You need to connect to a particular instance.
- You are debugging a specific reader.
- You need to inspect an individual database node.

Avoid hardcoding instance endpoints for normal application failover behavior.

### D. Custom endpoint

A custom endpoint allows you to define a subset of instances for a particular workload.

Example:
- One reader group for reporting.
- Another reader group for application read traffic.
- A specific subset for specialized query workloads.

Terraform:

```hcl
resource "aws_rds_cluster_endpoint" "reporting" {
  cluster_identifier          = aws_rds_cluster.main.id
  cluster_endpoint_identifier = "reporting-endpoint"

  custom_endpoint_type = "READER"

  static_members = [
    aws_rds_cluster_instance.reporting.id
  ]
}
```

### Endpoint selection summary

| Requirement | Endpoint |
|---|---|
| Write queries | Cluster/writer endpoint |
| General read traffic | Reader endpoint |
| Specific DB instance | Instance endpoint |
| Dedicated reader workload | Custom endpoint |
| Failover-aware application connection | Cluster endpoint |

Official endpoint behavior: AWS Aurora cluster endpoint documentation.

## 6. Aurora use cases with practical examples

### Use case 1: E-commerce application

Requirements:
- Customers.
- Products.
- Orders.
- Payments.
- Inventory.
- Transaction consistency.

Suggested architecture:

API Gateway → Lambda → Aurora PostgreSQL

Example tables:

```sql
CREATE TABLE customers (
    customer_id BIGINT PRIMARY KEY,
    email VARCHAR(255) UNIQUE NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE orders (
    order_id BIGINT PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    order_status VARCHAR(50),
    total_amount DECIMAL(12,2),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (customer_id)
        REFERENCES customers(customer_id)
);

CREATE TABLE order_items (
    order_item_id BIGINT PRIMARY KEY,
    order_id BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    quantity INTEGER NOT NULL,
    unit_price DECIMAL(12,2),
    FOREIGN KEY (order_id)
        REFERENCES orders(order_id)
);
```

Why Aurora?
- Relational data model.
- Transactions.
- Foreign keys.
- Joins.
- ACID properties.
- Read replicas for read-heavy traffic.
- Managed backups and failover.

Example transaction:

```sql
BEGIN;

INSERT INTO orders (
    order_id,
    customer_id,
    order_status,
    total_amount
)
VALUES (
    1001,
    501,
    'CREATED',
    250.00
);

UPDATE inventory
SET available_quantity = available_quantity - 1
WHERE product_id = 9001
AND available_quantity >= 1;

COMMIT;
```

In a real application, verify the inventory update affected a row before committing. Otherwise, roll back the transaction.

### Use case 2: SaaS multi-tenant application

Requirements:
- Multiple customers.
- Each customer has separate application data.
- Variable traffic.
- Relational queries.
- Strong tenant isolation.

Possible design:

- One Aurora cluster.
- Shared database.
- Tenant ID in application tables.
- Tenant-aware database queries.
- Row-level security where appropriate for PostgreSQL.
- Separate schemas or databases where the isolation requirements justify them.

Example:

```sql
CREATE TABLE invoices (
    invoice_id BIGINT PRIMARY KEY,
    tenant_id BIGINT NOT NULL,
    amount DECIMAL(12,2),
    status VARCHAR(30)
);
```

Query:

```sql
SELECT *
FROM invoices
WHERE tenant_id = 1001;
```

Important:
- Enforce tenant isolation in the application and database security design.
- Never rely only on frontend filtering.
- Consider connection pooling.
- Consider Aurora Serverless v2 if demand changes significantly.
- Use separate clusters where regulatory or security boundaries require stronger isolation.

### Use case 3: Banking or financial transaction system

Requirements:
- ACID transactions.
- Consistent balances.
- Transaction history.
- Referential integrity.
- Auditability.

Aurora PostgreSQL can be appropriate.

Example:

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 100
WHERE account_id = 101
AND balance >= 100;

UPDATE accounts
SET balance = balance + 100
WHERE account_id = 202;

INSERT INTO transactions (
    transaction_id,
    source_account,
    destination_account,
    amount
)
VALUES (
    9001,
    101,
    202,
    100
);

COMMIT;
```

Production requirements:
- Verify both account updates succeeded.
- Use appropriate row locking or transaction isolation.
- Enforce idempotency for payment requests.
- Maintain audit records.
- Use least-privilege database users.
- Test failover and recovery.
- Consider regulatory and encryption requirements.

Aurora does not automatically make a financial application compliant or guarantee that application transactions are correct.

### Use case 4: Read-heavy application

Requirements:
- Many read queries.
- Fewer writes.
- Dashboards and reporting.
- Product catalog reads.

Architecture:

Application
  |
Writer endpoint → Writer
  |
Reader endpoint → Reader 1
                 → Reader 2
                 → Reader 3

Use:
- Writer endpoint for writes.
- Reader endpoint for eligible reads.
- Custom endpoints for specialized read workloads.

Remember that read replicas can lag behind the writer.

### Use case 5: Unpredictable traffic

Requirements:
- Traffic changes throughout the day.
- Some periods have very low usage.
- Traffic bursts occur.
- Fixed instance capacity may be inefficient.

Use Aurora Serverless v2.

Example:
- Minimum: 0.5 ACU.
- Maximum: 16 ACUs.
- Aurora scales according to database demand.

This can reduce the need to continuously run a large provisioned instance.

However, Serverless v2 does not mean the database has no minimum cost. Storage, backups, I/O, and other applicable resources can still be billed.

### Use case 6: Global application

Requirements:
- Users in multiple AWS Regions.
- Low-latency local reads.
- Disaster recovery.
- Cross-Region database replication.

Use Aurora Global Database.

Architecture:

Primary Region:
- Writer.
- Readers.
- Primary storage.

Secondary Region:
- Replicated storage.
- Optional reader instances.
- Promotable secondary cluster.

Useful for:
- Global SaaS platforms.
- International applications.
- Disaster recovery.
- Regional read workloads.

Cross-Region replication is asynchronous, so failover can involve a non-zero recovery point.

### Use case 7: Existing MySQL or PostgreSQL migration

You can migrate compatible databases to Aurora.

Possible approaches:
- AWS Database Migration Service (DMS).
- Native database dump and restore.
- Engine-specific migration methods.
- Snapshot-based migration where supported.

Before migration:
- Check engine and version compatibility.
- Check extensions and plugins.
- Check SQL compatibility.
- Review stored procedures.
- Review collation and character set behavior.
- Test application drivers.
- Benchmark queries.
- Plan cutover and rollback.

## 7. Prerequisites before creating Aurora

Before using Terraform to deploy Aurora, prepare the following.

### A. AWS account and Region

You need:
- An AWS account.
- A selected AWS Region.
- IAM permissions to create RDS resources.
- IAM permissions for VPC, subnet groups, security groups, and KMS if required.

Example Region:

`eu-west-1`

Choose a Region based on:
- Application users.
- Data residency.
- Availability of the required Aurora engine version.
- Availability of the instance class.
- Cost.
- Integration with other AWS services.

### B. VPC

Aurora runs inside a VPC.

You need:
- VPC.
- Private subnets.
- Route tables.
- Security groups.

For production, use private database subnets across at least two Availability Zones.

### C. DB subnet group

A DB subnet group tells RDS which subnets it can use for database instances.

The subnets should cover multiple AZs.

Terraform:

```hcl
resource "aws_db_subnet_group" "aurora" {
  name = "aurora-private-subnets"

  subnet_ids = [
    aws_subnet.private_a.id,
    aws_subnet.private_b.id,
    aws_subnet.private_c.id
  ]

  tags = {
    Name = "aurora-private-subnets"
  }
}
```

For Aurora, provide subnets across at least two Availability Zones. Three AZs are generally a good production design.

### D. Security group

Aurora needs inbound access from application resources.

For PostgreSQL:
- TCP 5432.

For MySQL:
- TCP 3306.

Example:

```hcl
resource "aws_security_group" "aurora" {
  name   = "aurora-security-group"
  vpc_id = aws_vpc.main.id

  ingress {
    description     = "PostgreSQL from application"
    from_port       = 5432
    to_port         = 5432
    protocol        = "tcp"
    security_groups = [aws_security_group.application.id]
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}
```

This is a PostgreSQL example. For Aurora MySQL, use port 3306.

Best practice:
- Permit access from the application security group.
- Do not expose the database to `0.0.0.0/0`.
- Do not make the database publicly accessible unless there is a justified and tightly controlled requirement.

### E. Database credentials

You need:
- Master username.
- Master password or managed master credentials.
- Application database users.

Prefer AWS-managed master credentials through Secrets Manager.

Avoid hardcoding passwords in:
- Terraform files.
- Git repositories.
- User data.
- Application source code.

### F. Engine and version

Choose:
- `aurora-postgresql`.
- `aurora-mysql`.

Then select a supported engine version in your Region.

Do not blindly copy a version from an old tutorial. Check the current supported versions and upgrade policy.

### G. Instance class or Serverless v2 capacity

Provisioned:
- Select a DB instance class.

Serverless v2:
- Configure minimum ACUs.
- Configure maximum ACUs.
- Use `db.serverless` for the DB instance class.

### H. KMS key

Aurora storage encryption uses AWS KMS.

You can use the AWS-managed RDS key or a customer-managed KMS key.

Use a customer-managed key when you need:
- Custom key policies.
- Separation of duties.
- Specific key administration.
- Centralized encryption controls.

## 9. Aurora Terraform parameters — cluster resource

The primary Terraform resource is:

`aws_rds_cluster`

It creates and configures the Aurora DB cluster.

Important attributes:

| Parameter | Explanation |
|---|---|
| cluster_identifier | Unique cluster identifier |
| engine | Aurora engine, such as aurora-postgresql or aurora-mysql |
| engine_version | Database engine version |
| database_name | Initial database name where supported |
| master_username | Master database username |
| master_password | Master password when managing it directly |
| manage_master_user_password | Let RDS manage the master password in Secrets Manager |
| master_user_secret_kms_key_id | KMS key for managed master secret |
| db_subnet_group_name | DB subnet group |
| vpc_security_group_ids | Security groups attached to the cluster |
| storage_encrypted | Enable encryption at rest |
| kms_key_id | KMS key ARN or ID |
| backup_retention_period | Automated backup retention in days |
| preferred_backup_window | Preferred backup window |
| preferred_maintenance_window | Preferred maintenance window |
| deletion_protection | Prevent accidental deletion |
| skip_final_snapshot | Whether to skip final snapshot when deleting |
| final_snapshot_identifier | Final snapshot name when required |
| copy_tags_to_snapshot | Copy cluster tags to snapshots |
| enabled_cloudwatch_logs_exports | Export supported database logs |
| db_cluster_parameter_group_name | Cluster parameter group |
| port | Database port |
| iam_database_authentication_enabled | Enable IAM database authentication where supported |
| apply_immediately | Apply modifications immediately where supported |
| storage_type | Storage configuration where supported |
| iops | IOPS configuration where applicable to the engine/storage type |
| backtrack_window | Aurora MySQL backtrack window, when supported |
| preferred_backup_window | Time range for backups |
| enable_http_endpoint | Enable Data API where supported |
| serverlessv2_scaling_configuration | Serverless v2 capacity settings |
| replication_source_identifier | Source cluster for supported replication configurations |
| tags | Resource tags |

Important:
- Not every parameter applies to both Aurora engines.
- Some settings are immutable or require replacement.
- Some modifications cause a reboot or failover.
- Some settings depend on the engine version.
- `engine_mode = "provisioned"` is used for provisioned clusters and Aurora Serverless v2 clusters. Serverless v2 is not configured by setting the old Serverless v1 engine mode.

### Cluster identifier

```hcl
cluster_identifier = "production-aurora"
```

A stable name for the DB cluster.

### Engine

```hcl
engine = "aurora-postgresql"
```

Or:

```hcl
engine = "aurora-mysql"
```

### Engine version

```hcl
engine_version = var.aurora_engine_version
```

Select a supported version based on compatibility and maintenance requirements.

### Database name

```hcl
database_name = "applicationdb"
```

This creates the initial database where supported.

It does not define all application tables.

### Master username

```hcl
master_username = "dbadmin"
```

Use a dedicated master account for administrative tasks.

Do not use the master account for normal application queries.

### Managed master password

```hcl
manage_master_user_password = true
```

This instructs RDS to manage the master password in Secrets Manager.

You can optionally specify a customer-managed KMS key for the secret.

Do not configure both managed master password and a manually supplied master password.

### Storage encryption

```hcl
storage_encrypted = true
```

Enable encryption at rest.

For a customer-managed key:

```hcl
kms_key_id = aws_kms_key.aurora.arn
```

### Backup retention

```hcl
backup_retention_period = 7
```

Retain automated backups for seven days.

Aurora supports a configurable retention period up to 35 days.

### Deletion protection

```hcl
deletion_protection = true
```

Prevents deletion through the RDS API until protection is disabled.

This is especially important in production.

### Final snapshot

```hcl
skip_final_snapshot       = false
final_snapshot_identifier = "production-aurora-final"
```

When deleting a production cluster, preserve a final snapshot.

Terraform resource destruction can fail if the final snapshot identifier is missing while `skip_final_snapshot` is false.

### CloudWatch log exports

For Aurora PostgreSQL, commonly exported log types include:

```hcl
enabled_cloudwatch_logs_exports = [
  "postgresql"
]
```

For Aurora MySQL, available log types depend on engine version and configuration. Check supported export types before applying.

## 10. Terraform parameters — DB instance resource

The second important resource is:

`aws_rds_cluster_instance`

This controls each Aurora compute instance.

Important attributes:

| Parameter | Explanation |
|---|---|
| identifier | Unique DB instance identifier |
| cluster_identifier | Cluster to which the instance belongs |
| instance_class | DB instance class or db.serverless |
| engine | Database engine |
| engine_version | Engine version |
| availability_zone | Preferred AZ |
| db_subnet_group_name | DB subnet group |
| db_parameter_group_name | Instance parameter group |
| publicly_accessible | Whether the instance receives a public IP where supported |
| auto_minor_version_upgrade | Allow automatic minor upgrades |
| promotion_tier | Failover priority |
| monitoring_interval | Enhanced Monitoring interval |
| monitoring_role_arn | IAM role for Enhanced Monitoring |
| performance_insights_enabled | Enable Performance Insights where supported |
| performance_insights_kms_key_id | KMS key for Performance Insights |
| performance_insights_retention_period | Performance Insights retention |
| apply_immediately | Apply supported changes immediately |
| preferred_maintenance_window | Instance maintenance window |
| copy_tags_to_snapshot | Copy tags to snapshots |
| tags | Resource tags |

### Instance class

Provisioned example:

```hcl
instance_class = "db.r7g.large"
```

Serverless v2 example:

```hcl
instance_class = "db.serverless"
```

### Availability Zone

```hcl
availability_zone = "eu-west-1a"
```

Choose an AZ that is included in your DB subnet group.

### Public accessibility

```hcl
publicly_accessible = false
```

Production Aurora databases should generally be private.

### Promotion tier

```hcl
promotion_tier = 1
```

Promotion tier determines the priority of a reader when Aurora selects a failover target.

Lower numerical values have higher promotion priority.

A reader with a high promotion priority can be selected before one with a lower priority.

### Enhanced Monitoring

```hcl
monitoring_interval = 60
```

Possible monitoring intervals include 1, 5, 10, 15, 30, and 60 seconds, or 0 to disable.

Enhanced Monitoring requires an IAM monitoring role.

### Performance Insights

```hcl
performance_insights_enabled = true
```

Performance Insights helps identify database load and query performance issues.

Availability, retention, and pricing depend on the engine, Region, and current AWS feature model.

## 11. Terraform example 1 — Production Aurora PostgreSQL provisioned cluster

This example creates:
- Aurora PostgreSQL cluster.
- Managed master password.
- Encrypted storage.
- Private DB subnet group.
- Application-only security group access.
- One writer.
- One reader.
- Automated backups.
- Deletion protection.
- CloudWatch log export.

### Variables

```hcl
variable "aurora_engine_version" {
  type        = string
  description = "Supported Aurora PostgreSQL engine version"
}

variable "vpc_id" {
  type = string
}

variable "private_subnet_ids" {
  type = list(string)
}

variable "application_security_group_id" {
  type = string
}
```

### DB subnet group

```hcl
resource "aws_db_subnet_group" "aurora" {
  name = "production-aurora-subnets"

  subnet_ids = var.private_subnet_ids

  tags = {
    Environment = "production"
    Application = "orders"
  }

```

### Security group

```hcl
resource "aws_security_group" "aurora" {
  name        = "production-aurora-sg"
  description = "Aurora PostgreSQL access from application"
  vpc_id      = var.vpc_id

  ingress {
    description     = "PostgreSQL from application"
    from_port       = 5432
    to_port         = 5432
    protocol        = "tcp"
    security_groups = [
      var.application_security_group_id
    ]
  }

  egress {
    from_port   = 0
```

## 12. Terraform example 2 — Aurora Serverless v2

Use this configuration when the database workload changes significantly over time.

### How Serverless v2 works

You define:
- Minimum ACU.
- Maximum ACU.
- DB instance class `db.serverless`.

Aurora adjusts capacity within that range.

Example:
- Minimum: 0.5 ACU.
- Maximum: 16 ACUs.

### Terraform cluster

```hcl

  ]

  backup_retention_period = 7

  deletion_protection = true

  serverlessv2_scaling_configuration {
    min_capacity = 0.5
    max_capacity = 16
  }

  tags = {
    Environment = "production"
    Compute     = "serverless-v2"
  }
}
```

```hcl

  db_subnet_group_name = aws_db_subnet_group.aurora.name
```

```hcl
resource "aws_rds_cluster_instance" "serverless_reader" {
```

Important:
- The cluster scaling configuration must exist before adding `db.serverless` instances.
- The permitted ACU range depends on engine and platform version.
- ACUs are configured in 0.5 increments.
- Each Serverless v2 instance can scale within the cluster's configured range.
- A reader adds another compute resource and can increase cost.
- Serverless v2 still has storage and other charges.
- Choose a maximum capacity that can handle your expected peak database load.

### Optional auto-pause

Some supported Aurora engine versions allow a minimum capacity of zero.

Example:

```hcl

  max_capacity             = 8
```

This allows eligible Serverless v2 instances to pause after the configured idle interval.

Important:
- Minimum zero is not supported by every engine version.
- Certain cluster features and connection patterns prevent auto-pause.
- Auto-pause is not suitable for applications requiring consistently low connection latency.
- A resumed database can take time to become available.
- Storage and other cluster costs remain while compute is paused.
- Test application retry behavior before enabling this in production.

## 14. Aurora high availability and failover

Aurora provides high availability through:
- Distributed storage across three AZs.
- Multiple database instances where configured.
- Automatic failure detection.
- Writer promotion.
- Cluster endpoint failover behavior.

### Scenario 1: Writer failure with a reader available

Example:
- Writer in AZ A.
- Reader in AZ B.
- Writer becomes unhealthy.

Aurora can promote a reader to writer.

The cluster endpoint is updated to point to the new writer.

Applications must reconnect and handle transient connection failures.

### Scenario 2: Writer failure without a reader

If the cluster has only one DB instance, Aurora can attempt to recover or recreate the writer.

However, this is not the same failover experience as having a ready reader instance.

For production systems with demanding recovery objectives, provision a reader in another AZ.

### Promotion tiers

Promotion tiers range from 0 to 15.

- Tier 0 has the highest promotion priority.
- Tier 15 has the lowest promotion priority.

You can use promotion tiers to influence which reader becomes writer during failover.

### Important distinction

Multi-AZ Aurora storage replication does not automatically mean you have multiple DB compute instances.

For better failover readiness, create at least one reader in another AZ.

## 15. Aurora backups and recovery

Aurora provides automated backups and manual snapshots.

### A. Automated backups

Configure:

```hcl
backup_retention_period = 14
```

Automated backups support point-in-time recovery within the retention window.

Aurora supports retention up to 35 days.

### B. Manual snapshots

Manual snapshots are retained until deleted.

Terraform:

```hcl
resource "aws_db_cluster_snapshot" "manual" {
  db_cluster_identifier = aws_rds_cluster.aurora.id

  db_cluster_snapshot_identifier = "orders-manual-snapshot"
}
```

Use manual snapshots:
- Before major upgrades.
- Before migrations.
- Before risky schema changes.
- Before major configuration changes.

### C. Point-in-time recovery

Point-in-time recovery creates a new cluster restored to a selected time within the available backup window.

It is not a process that simply rolls the existing cluster backward in place.

Terraform can manage restore resources, but the exact configuration depends on the source cluster and restore operation.

### D. AWS Backup

You can also manage Aurora backups through AWS Backup.

Useful for:
- Centralized backup management.
- Cross-account backup policies.
- Cross-Region backup policies.
- Organizational backup controls.
- Backup vault management.

### Production recommendation

Use:
- Automated backups.
- Manual snapshots before major changes.
- AWS Backup where centralized policies are required.
- Periodic restore testing.

A successful backup job does not prove that your application can recover correctly. Test actual restoration.

## 16. Aurora security and IAM authentication

### A. Encryption at rest

Aurora supports KMS-based encryption at rest.

```hcl
storage_encrypted = true
kms_key_id        = aws_kms_key.aurora.arn
```

Encryption protects supported database storage and backup data.

The encryption choice is important at cluster creation. Changing the encryption key of an existing encrypted cluster generally requires a migration or snapshot-copy/restore approach rather than simply changing the key in place.

### B. Encryption in transit

Use TLS for database connections.

Applications should:
- Require encrypted connections.
- Validate the server certificate.
- Use the appropriate AWS RDS certificate bundle.
- Avoid disabling certificate verification in production.

### C. IAM database authentication

Aurora supports IAM database authentication for supported engines and versions.

Terraform:

```hcl
iam_database_authentication_enabled = true
```

IAM authentication allows an application to generate a short-lived database authentication token.

The database user must also be configured to support IAM authentication.

The application needs appropriate IAM permission, commonly:

`rds-db:connect`

IAM authentication does not remove the need for database users and database-level privileges.

### D. Database users

Create separate database users for:
- Application runtime.
- Read-only reporting.
- Database administration.
- Migration tooling.
- Monitoring, where applicable.

Do not use the master user for routine application traffic.

### E. Secrets Manager

Aurora can manage the master password in Secrets Manager.

The application should retrieve its own database credentials or use IAM authentication.

### F. Network security

- Place Aurora in private subnets.
- Allow inbound database traffic only from required security groups.
- Do not expose database ports to the internet.
- Use VPC Flow Logs where appropriate.
- Review security group changes.
- Use VPC endpoints where required for private access to AWS services.

## 17. Aurora and RDS Proxy

RDS Proxy is useful when applications create many short-lived database connections.

This commonly happens with:
- Lambda.
- Serverless APIs.
- Bursty workloads.
- Microservices.
- Applications with many instances.

### Problem without RDS Proxy

Imagine:
- Lambda concurrency = 500.
- Each invocation creates a new database connection.

The database can receive a large number of concurrent connections.

This can lead to:
- Connection exhaustion.
- Increased memory usage.
- Slow connection establishment.
- Database instability.

### With RDS Proxy

Application → RDS Proxy → Aurora

RDS Proxy:
- Pools database connections.
- Reuses connections.
- Helps manage connection bursts.
- Can improve database connection resilience.

It does not eliminate the need for connection limits or good application design.

### Terraform example

```hcl
resource "aws_db_proxy" "aurora" {
  name                   = "orders-aurora-proxy"
  engine_family          = "POSTGRESQL"
  require_tls            = true
  role_arn               = aws_iam_role.rds_proxy.arn
  vpc_subnet_ids         = var.private_subnet_ids
  vpc_security_group_ids = [aws_security_group.proxy.id]

  auth {
    auth_scheme = "SECRETS"
    secret_arn  = aws_secretsmanager_secret.application.arn
    iam_auth    = "DISABLED"
  }
}
```

The proxy also requires:
- An IAM role that allows Secrets Manager access.
- Appropriate security group rules.
- A proxy target group.
- Registration of the Aurora cluster as a target.
- Correct database credentials.

RDS Proxy has its own costs.

## 18. Aurora read scaling

Aurora supports reader instances for read scaling.

Example:
- Writer handles all writes.
- Reader 1 handles application reads.
- Reader 2 handles reports.
- Reader 3 handles other read workloads.

Use the reader endpoint to distribute read connections.

### Read scaling limitations

- Readers can have replication lag.
- Read replicas do not automatically increase write capacity.
- Adding more readers increases compute cost.
- A reader endpoint balances connections, not necessarily each SQL query.
- Applications that use long-lived connection pools may not distribute traffic evenly.

### Application design

Classify queries:

Write operations:
- INSERT.
- UPDATE.
- DELETE.
- DDL.

Send to writer.

Read operations:
- SELECT.
- Reporting.
- Search.
- Read-only dashboards.

Send to reader only if replica lag is acceptable.

For read-after-write consistency, use the writer endpoint.

## 19. Aurora Global Database

Aurora Global Database is designed for multi-Region applications and disaster recovery.

Architecture:

Primary Region:
- Primary Aurora cluster.
- Writer.
- Readers.

Secondary Region:
- Secondary Aurora cluster.
- Replicated storage.
- Optional readers.

Benefits:
- Cross-Region replication.
- Regional read scaling.
- Disaster recovery.
- Lower-latency regional read access.

Important:
- Cross-Region replication is asynchronous.
- A secondary Region may have replication lag.
- Promotion of a secondary Region requires operational planning.
- Global Database adds costs in each Region.
- You must design application routing and DNS failover.
- Test the recovery procedure.

Do not assume Global Database is a substitute for application-level disaster recovery planning.

## 20. Aurora storage and I/O configuration

Aurora storage automatically grows with the data stored in the cluster.

You do not normally set a fixed storage volume size as you would for a conventional database instance.

Two important pricing configurations are available.

### A. Aurora Standard

You pay for:
- Database instances.
- Storage.
- Read and write I/O operations.

Suitable for:
- Many normal transactional workloads.
- Workloads with low to moderate I/O costs.
- Applications where pay-per-I/O is cost-effective.

### B. Aurora I/O-Optimized

You pay for:
- Database instances.
- Storage.

There are no separate read/write I/O operation charges under this configuration.

However, instance and storage pricing are higher than Standard.

Suitable for:
- I/O-intensive applications.
- High transaction workloads.
- Workloads with high I/O charges.
- Workloads where predictable I/O pricing is important.

AWS indicates that I/O-Optimized can be attractive when I/O costs exceed roughly 25% of total Aurora database spend, but calculate using your actual workload and Region.

### Choosing between them

Calculate:

Aurora Standard total =
Instance cost + Storage cost + I/O cost

Aurora I/O-Optimized total =
Higher instance cost + Higher storage cost

Choose the lower total cost for your workload.

## 25. Aurora cost model

Aurora is not priced as one fixed database subscription.

Your bill can contain several independent cost components.

### A. DB instance compute cost

For provisioned Aurora:

Number of instances × Hourly instance price × Hours used

Example:
- One writer.
- One reader.
- Both run continuously.
- Both are charged as DB instances.

Important: A reader is not free simply because it is a replica.

For Serverless v2:

ACU-hours × Regional ACU price

ACU capacity is billed based on consumption and the configured scaling behavior.

### B. Storage cost

Aurora charges for database storage consumed.

The amount of data grows as the database grows.

You do not need to pre-allocate a conventional fixed storage volume.

### C. I/O cost

Aurora Standard charges for I/O operations.

Aurora I/O-Optimized does not charge separately for read/write I/O operations, but its instance and storage rates are higher.

### D. Backup storage

Automated backup storage and manual snapshots can incur charges depending on usage and the applicable free backup allowance.

Long retention and many snapshots can increase cost.

### E. Data transfer

Possible charges include:
- Cross-Region data transfer.
- Data transfer to other AWS services where applicable.
- Internet data transfer.
- Global Database replication-related transfer.

### F. Additional features

Potential additional charges:
- RDS Proxy.
- Performance Insights features beyond included retention.
- Enhanced Monitoring-related CloudWatch ingestion.
- CloudWatch Logs.
- AWS Backup.
- Global Database secondary Regions.
- Data API where priced separately.
- KMS requests in some cases.
- NAT Gateway.
- Interface VPC endpoints.

- Optimize expensive SQL queries.
- Use connection pooling.
- Use RDS Proxy where appropriate.
- Consider Reserved Instances or Database Savings Plans for eligible predictable workloads.
- Monitor CloudWatch Logs costs.
- Avoid unnecessary NAT Gateway traffic.

## 30. Aurora vs RDS vs DynamoDB vs Redshift

| Requirement | Best fit |
|---|---|
| Managed relational MySQL-compatible database | Aurora MySQL or RDS MySQL |
| Managed relational PostgreSQL-compatible database | Aurora PostgreSQL or RDS PostgreSQL |
| Relational database with Aurora distributed storage | Aurora |
| Conventional relational database with simpler cost profile | RDS |
| Key-value or document access patterns | DynamoDB |
| Analytical data warehouse | Redshift |
| Relational database with variable compute demand | Aurora Serverless v2 |
| Very high-scale global relational application | Consider Aurora Global Database |
| In-memory cache | ElastiCache |

### Aurora vs RDS

Aurora:
- Distributed storage architecture.
- Aurora-specific cluster endpoints.
- Reader scaling.
- Aurora Serverless v2.
- Aurora-specific features and pricing.

RDS:
- Multiple conventional database engines.
- Different storage and replication options.
- Often simpler for workloads that do not need Aurora-specific features.

Aurora is not automatically cheaper or faster for every workload.

Benchmark using your actual application.

### Aurora vs DynamoDB

Aurora:
- SQL.
- Joins.
- Relational constraints.
- ACID transactions.
- Structured relational data.

DynamoDB:
- NoSQL.
- Partition-key-based access.
- High-scale key-value/document workloads.
- Different data modeling and query design.

### Aurora vs Redshift

Aurora:
- Operational transactions.
- OLTP.
- Application database.

Redshift:
- Analytics.
- OLAP.
- Large-scale aggregations.
- Data warehouse queries.

## 31. Aurora limitations and important exceptions

- Aurora supports MySQL-compatible and PostgreSQL-compatible engines, not every database engine.
- Engine features and extensions can differ from upstream MySQL or PostgreSQL.
- Engine versions have specific upgrade paths.
- Some parameter changes require reboot.
- Some cluster modifications can cause failover.
- Readers can have replication lag.
- Reader instances cost money.
- Serverless v2 is not zero-cost when idle unless eligible auto-pause is active; storage and other costs remain.
- Minimum and maximum ACUs depend on engine and platform version.
- Aurora storage grows automatically, but it is not unlimited.
- Aurora storage and I/O pricing varies by configuration.
- Cross-Region replication is asynchronous.
- Global Database failover requires planning.
- A single DB instance is not equivalent to a multi-instance HA deployment.
- A database endpoint is not a connection pool.
- A reader endpoint does not guarantee read-after-write consistency.
- A database connection storm can overload the database.
- A backup is not a substitute for a tested recovery procedure.
- Deletion protection must be disabled before deleting a protected cluster.
- Changing encryption configuration may require snapshot-copy and restore.
- Public accessibility should generally be disabled.
- Some advanced features are engine- or version-specific.
- Aurora Serverless v2 auto-pause can be prevented by certain configurations and open connections.
- Long-running transactions can interfere with operational behavior and resource scaling.

## 32. Common Aurora errors

| Error or problem | Likely cause | Resolution |
|---|---|---|
| Connection timed out | Security group, routing, subnet, or network issue | Check VPC routes and security groups |
| Password authentication failed | Incorrect secret or database user | Verify credentials and user permissions |
| Too many connections | Connection exhaustion | Use pooling, RDS Proxy, and connection limits |
| Writer endpoint unavailable | Failover or cluster issue | Retry connection and inspect cluster events |
| Reader lag | Heavy writes or replica delay | Monitor lag and route consistency-sensitive reads to writer |
| Terraform subnet group error | Subnets missing or not in enough AZs | Check subnet group and AZ placement |
| Invalid engine version | Unsupported engine version | Select a supported version |
| Invalid DB instance class | Class unavailable for engine or Region | Check orderable instance options |
| Serverless capacity error | Unsupported ACU range or engine version | Verify Serverless v2 capacity compatibility |
| Cannot delete cluster | Deletion protection or final snapshot configuration | Disable protection and configure final snapshot |
| IAM authentication failed | Missing IAM permission or database user setup | Check `rds-db:connect` and database user configuration |
| Slow queries | Missing indexes, poor SQL, locks, or resource constraints | Use Performance Insights and query plans |
| SSL connection error | Certificate or TLS configuration issue | Use the current RDS CA bundle and validate certificates |
| Application connection failures during failover | Connection pool retains stale connections | Implement reconnection and retry logic |

## 35. Quick revision summary

- Aurora is a managed relational database service.
- It supports MySQL-compatible and PostgreSQL-compatible engines.
- Aurora consists of a compute layer and a distributed storage layer.
- The cluster is the overall database deployment.
- DB instances provide compute.
- One instance is the writer.
- Additional instances can be readers.
- Aurora storage maintains six copies across three AZs.
- The cluster endpoint connects to the current writer.
- The reader endpoint distributes read connections.
- Instance endpoints connect to individual DB instances.
- Custom endpoints group selected instances.
- Aurora storage automatically grows.
- Aurora Standard charges for instances, storage, and I/O.
- Aurora I/O-Optimized removes separate I/O charges but has higher instance and storage rates.
- Provisioned Aurora uses fixed DB instance classes.
- Aurora Serverless v2 scales compute capacity using ACUs.
- Serverless v2 uses `db.serverless` DB instances.
- A minimum ACU of zero can enable auto-pause on supported configurations.
- `aws_rds_cluster` manages the cluster.
- `aws_rds_cluster_instance` manages each DB instance.
- `aws_db_subnet_group` defines database subnets.
- `aws_rds_cluster_parameter_group` configures cluster-level parameters.
- `aws_db_parameter_group` configures instance-level parameters.
- Use Secrets Manager for credentials.
- Use KMS for encryption.
- Use IAM database authentication where appropriate.
- Use RDS Proxy for connection pooling where appropriate.
- Use automated backups and test restoration.
- Use Global Database for cross-Region requirements.
- Use CloudWatch and Performance Insights for observability.
- Aurora is primarily an OLTP database, not a data warehouse.
