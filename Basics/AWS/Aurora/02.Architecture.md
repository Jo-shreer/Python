# Amazon Aurora – Architecture Explained

## 1. What is Aurora architecture?

Amazon Aurora is a relational database engine provided by AWS. Its architecture separates **compute (DB instances)** from **storage (the database data itself)**.

An Aurora cluster consists of:

1. Aurora DB cluster – the logical database environment.
2. Writer instance – processes reads and writes.
3. Reader instances – handle read workloads and provide failover capacity.
4. Shared distributed storage – stores the actual database data.
5. Endpoints – connection addresses applications use to connect to the database.
6. Backups and recovery – automated backup and point-in-time recovery capabilities.

The most important concept is that all DB instances in a standard Aurora cluster share the same underlying storage.

## 2. Overall Aurora architecture

```text
                 APPLICATION
                      |
                      |
                Aurora Endpoints
                      |
             +--------+--------+
             |                 |
        Writer Endpoint   Reader Endpoint
             |                 |
             |             +---+---+
             |             |       |
             |          Reader 1 Reader 2
             |             |       |
          Writer            |       |
             |             |       |
             +-------------+-------+
                      |
             SHARED AURORA STORAGE
                      |
              Distributed Storage
                Across 3 AZs
```

The application connects to Aurora using endpoints.

- Write queries generally go to the writer endpoint.
- Read queries can go to the reader endpoint.
- The writer and readers access the same shared storage.

## 3. Aurora DB Cluster

An Aurora DB cluster is the logical database environment.

It contains:

- One writer DB instance in a standard Aurora cluster.
- Zero or more reader DB instances.
- Shared cluster storage.
- Cluster endpoints.
- Backup and recovery configuration.

Example:

```text
                 Aurora Cluster
                       |
          +------------+------------+
          |            |            |
        Writer       Reader 1     Reader 2
          |            |            |
          +------------+------------+
                       |
                Shared Storage
```

The cluster is the overall unit. The individual DB instances provide the compute resources.

## 4. Writer Instance

The writer instance is the primary DB instance.

It handles:

- INSERT
- UPDATE
- DELETE
- CREATE
- ALTER
- SELECT
- Transactions and commits

Example:

```sql
INSERT INTO orders (order_id, amount)
VALUES (101, 500);
```

The application sends the query to the writer instance.

The writer processes the transaction and updates the shared Aurora storage.

Important points:

- A standard Aurora cluster has one writer at a time.
- The writer handles both read and write queries.
- If the writer fails, Aurora can promote a reader to become the new writer.
- The writer endpoint automatically points to the current writer after failover.

Aurora Limitless Database provides a separate distributed architecture for supported workloads, so its capabilities should not be confused with the standard single-writer cluster model.

## 5. Reader Instances

Reader instances are additional DB instances in the same Aurora cluster.

They are primarily used for read workloads.

Typical use cases:

- Product browsing.
- Reporting.
- Analytics queries.
- Dashboards.
- Read-heavy applications.

Example:

An e-commerce application receives:

- 1,000 product browsing requests.
- 100 order creation requests.

You can distribute the product browsing queries across reader instances and send order creation queries to the writer.

```text
                 APPLICATION
                      |
             +--------+--------+
             |                 |
         Read Queries      Write Queries
             |                 |
       Reader Endpoint    Writer Endpoint
             |                 |
         +---+---+           Writer
         |       |             |
      Reader 1 Reader 2        |
         |       |             |
         +---+---+-------------+
                 |
           Shared Storage
```

Important points:

- Readers share the same storage as the writer.
- Readers primarily handle read-only workloads.
- Reader instances can be promoted to writer during failover.
- A standard Aurora cluster supports up to 15 Aurora Replicas, subject to engine and configuration support.
- Readers may have replication lag.

Replication lag means a reader may not immediately reflect a recent write.

For example:

1. Application inserts an order using the writer.
2. Application immediately reads the order using a reader.
3. The reader may not yet show the newly inserted record.

For read-after-write consistency, use the writer endpoint.

## 6. Aurora Storage Architecture

This is one of the most important parts of Aurora.

Traditional database architectures often couple storage closely to the database server.

Aurora separates storage from compute.

```text
             Aurora DB Instances
             +--------+--------+
             |        |        |
           Writer  Reader 1  Reader 2
             |        |        |
             +--------+--------+
                      |
              Shared Storage
                      |
          +-----------+-----------+
          |           |           |
         AZ 1        AZ 2        AZ 3
          |           |           |
       2 copies    2 copies    2 copies
```

Aurora maintains six copies of data across three Availability Zones, with two copies in each AZ.

The distributed storage system is designed to tolerate failures without requiring each reader to maintain its own full copy of the database.

### How does Aurora use the six copies?

At a high level:

- Writes are acknowledged after at least four of the six storage copies confirm them.
- Reads use at least three of the six copies.

This quorum-based design helps Aurora maintain durability and availability despite individual storage failures.

### Important storage features

1. Shared storage: All instances access the same underlying cluster volume.
2. Distributed storage: Data is replicated across multiple Availability Zones.
3. Automatic growth: Storage grows as data increases.
4. No need to provision storage capacity in advance for standard Aurora storage.
5. Compute and storage scale independently.
6. Aurora manages the underlying storage infrastructure.

For standard Aurora clusters, storage can grow up to 128 TiB, subject to engine, version, and feature limitations.

## 7. Availability Zones (AZs)

An Availability Zone is an isolated location within an AWS Region.

For example:

```text
              AWS Region
                  |
       +----------+----------+
       |          |          |
      AZ A       AZ B       AZ C
       |          |          |
     Writer     Reader 1   Reader 2
       |          |          |
       +----------+----------+
                  |
           Shared Storage
```

Aurora storage is distributed across three AZs.

DB instances can also be placed in different AZs.

Why is this important?

Suppose the writer is running in AZ A and that instance becomes unavailable.

Aurora can promote a reader in AZ B or AZ C to become the new writer.

Having readers in other AZs improves compute failover readiness.

Important distinction:

- Multi-AZ storage provides storage-level resilience.
- Reader instances in different AZs provide additional compute and failover capacity.

Multi-AZ storage does not automatically mean you have a standby DB instance ready for immediate promotion.

## 8. Aurora Failover

Failover means moving the writer role to another DB instance when the current writer becomes unavailable.

Example:

Initially:

```text
Writer:  AZ A
Reader:  AZ B
Reader:  AZ C
```

Suppose the writer in AZ A fails.

Aurora promotes a reader:

```text
Writer:  AZ B  (promoted)
Reader:  AZ C
AZ A:    Failed instance
```

The cluster writer endpoint is updated to point to the newly promoted writer.

Important points:

- Aurora chooses a suitable reader for promotion.
- Promotion priority can be configured.
- Existing application connections may be interrupted.
- Applications should reconnect and retry failed transactions where safe.
- Having readers available in other AZs can reduce recovery time.

## 9. Aurora Endpoints

An endpoint is the connection address your application uses to connect to Aurora.

Aurora provides different endpoint types.

### A. Cluster Endpoint

The cluster endpoint connects to the current writer instance.

Used for:

- INSERT
- UPDATE
- DELETE
- Transactions
- Reads that require the latest committed data

Example:

```text
mydb.cluster-xxxx.eu-west-1.rds.amazonaws.com
```

Important:

After failover, the cluster endpoint automatically points to the new writer.

Use this endpoint for application writes.

### B. Reader Endpoint

The reader endpoint distributes connections across available Aurora reader instances.

Used for:

- SELECT queries.
- Reporting.
- Dashboards.
- Read-heavy workloads.

Example:

```text
mydb.cluster-ro-xxxx.eu-west-1.rds.amazonaws.com
```

Important:

The reader endpoint distributes connections, not necessarily every individual SQL query.

Connection pooling can affect how requests are distributed.

### C. Instance Endpoint

An instance endpoint connects directly to one particular DB instance.

Example:

```text
mydb-instance-1.xxxx.eu-west-1.rds.amazonaws.com
```

Used when you specifically need to connect to:

- A particular reader.
- The current writer instance.
- A particular instance for testing or troubleshooting.

Important:

An instance endpoint does not automatically redirect to a different instance if that instance fails.

### D. Custom Endpoint

A custom endpoint connects to a selected group of DB instances.

Example:

Suppose your cluster has:

- Writer.
- Reader 1.
- Reader 2.
- Reader 3.

You can create a custom endpoint that includes Reader 1 and Reader 2 for reporting workloads.

This helps separate workloads.

Example:

```text
Application
    |
    +-- Writer Endpoint
    |       |
    |     Writer
    |
    +-- Reader Endpoint
    |       |
    |    All Readers
    |
    +-- Custom Endpoint
            |
         Reader 1
         Reader 2
```

## 10. DB Instance Classes

When creating an Aurora DB instance, you select an instance class.

Example:

```text
db.r6g.large
```

Breakdown:

| Part | Meaning |
|---|---|
| db | Database instance |
| r | Memory-optimized family |
| 6 | Instance generation |
| g | AWS Graviton processor |
| large | Instance size |

### Common instance families

| Family | Purpose |
|---|---|
| db.t | Burstable general-purpose workloads |
| db.r | Memory-optimized workloads |
| db.x | High-memory workloads, where supported |

Availability depends on Aurora engine, version, and AWS Region.

### Instance sizes

Examples:

```text
db.r6g.large
db.r6g.xlarge
db.r6g.2xlarge
db.r6g.4xlarge
```

As instance size increases, CPU and memory resources generally increase.

Choose a larger instance when:

- CPU usage is consistently high.
- Memory pressure is high.
- Queries are competing for resources.
- You need to support more concurrent connections.
- Your database workload requires more compute capacity.

Important:

Increasing the DB instance size does not increase the database storage allocation.

Aurora compute and storage are independent.

## 11. Provisioned Aurora vs Serverless v2

Aurora provides different ways to manage compute capacity.

### A. Provisioned Aurora

You select a fixed instance class.

Example:

```text
Writer: db.r6g.large
Reader: db.r6g.large
```

You pay for the provisioned instance capacity while it is running.

Suitable for:

- Predictable workloads.
- Consistent traffic.
- Production applications with known capacity requirements.

### B. Aurora Serverless v2

You configure minimum and maximum compute capacity using Aurora Capacity Units (ACUs).

Example:

```text
Minimum: 0.5 ACU
Maximum: 8 ACU
```

Aurora adjusts compute capacity within the configured range based on workload.

One ACU represents a combination of processing and memory resources, approximately 2 GiB of memory.

Important:

- Serverless v2 still uses Aurora DB instances.
- It changes how compute capacity is allocated and scaled.
- You can configure Serverless v2 instances as writer or readers.
- You pay based on the capacity consumed over time.

Suitable for:

- Unpredictable traffic.
- Applications with variable workloads.
- Workloads that have quiet and busy periods.

## 12. Example: E-commerce Application Using Aurora

Suppose we are building an e-commerce application.

Requirements:

- Users browse products.
- Users create orders.
- Users view order history.
- Admins run reports.

Architecture:

```text
                USERS
                  |
             API Gateway
                  |
                Lambda
                  |
            Aurora Cluster
                  |
       +----------+----------+
       |          |          |
     Writer    Reader 1   Reader 2
       |          |          |
       +----------+----------+
                  |
           Shared Storage
```

How requests flow:

### Scenario 1: Browse products

1. User opens the product page.
2. API Gateway receives the request.
3. Lambda executes the application logic.
4. Lambda connects to the reader endpoint.
5. Aurora reader returns product information.

### Scenario 2: Place an order

1. User places an order.
2. API Gateway receives the request.
3. Lambda executes the order logic.
4. Lambda connects to the writer endpoint.
5. Writer executes INSERT and UPDATE queries.
6. Changes are stored in shared Aurora storage.

### Scenario 3: View order immediately after placing it

1. User places an order through the writer.
2. The order is committed.
3. The application immediately requests the order details.
4. The application uses the writer endpoint to avoid reader replication lag.

### Scenario 4: Writer failure

1. The current writer becomes unavailable.
2. Aurora promotes an available reader.
3. The cluster writer endpoint is updated.
4. The application reconnects to the writer endpoint.
5. Application requests continue after recovery.

## 13. Aurora Networking Architecture

Aurora normally runs inside a VPC.

A VPC is your private AWS network.

```text
                  AWS VPC
                     |
             Private DB Subnets
                     |
             Aurora DB Subnet Group
                     |
             +-------+-------+
             |               |
           AZ A             AZ B
             |               |
           Writer          Reader
             |               |
             +-------+-------+
                     |
              Aurora Storage
```

Important networking concepts:

### VPC

The network where your Aurora cluster runs.

### DB Subnet Group

A collection of subnets in different Availability Zones.

Aurora uses this to determine where it can place DB instances.

For production, use subnets spanning multiple AZs.

### Security Group

Controls inbound and outbound network traffic.

For example:

If Lambda connects to Aurora PostgreSQL:

```text
Lambda Security Group
          |
          | TCP 5432
          |
Aurora Security Group
```

Aurora security group inbound rule:

```text
Type: PostgreSQL
Port: 5432
Source: Lambda Security Group
```

For Aurora MySQL:

```text
Port: 3306
```

Important:

Do not expose the Aurora database directly to the public internet unless there is a specific, justified requirement. Normally, keep Aurora private and allow access from approved application resources.

| Term | Meaning |
|---|---|
| Cluster | Logical Aurora database environment |

| Reader | Instance primarily used for reads |
| Replica | Reader instance sharing Aurora storage |
| Shared storage | Storage accessed by all cluster instances |
| AZ | Availability Zone |
| Failover | Promoting another instance to become writer |
| Cluster endpoint | Connects to the current writer |
| Reader endpoint | Distributes connections across readers |
| Instance endpoint | Connects to a specific DB instance |

| ACU | Aurora Capacity Unit used by Serverless v2 |

## 15. Most Important Things to Remember

1. Aurora separates compute and storage.
2. DB instances provide CPU and memory.
3. Shared Aurora storage stores the database data.
4. All DB instances in a standard cluster share the same storage.
5. A standard Aurora cluster has one writer at a time.
6. Reader instances help distribute read workloads.
7. Readers can be promoted during writer failover.
8. Aurora storage is distributed across three AZs with six copies.
9. Cluster endpoint is used for writes.
10. Reader endpoint distributes connections across readers.
11. Instance endpoints connect to specific DB instances.
12. Compute and storage can scale independently.
13. Serverless v2 automatically adjusts compute capacity within configured limits.
14. Having multi-AZ storage does not mean you have a standby DB instance.
15. Applications should handle connection interruptions and retries during failover.

**The key architecture concept:** Aurora has multiple DB instances (compute) connected to one shared, distributed storage layer. This design enables read scaling, storage resilience, and faster failover.
