# PART 1 – UNDERSTANDING HOW AWS CALCULATES COST

## 1. How does AWS calculate the bill?

AWS follows a pay-as-you-go pricing model for many services.

You pay for the resources and usage consumed according to the pricing model of each service.

However, different services use different billing dimensions.

For example:

| AWS service | Main billing dimension |
|---|---|
| EC2 | Instance running time |
| EBS | Provisioned storage |
| S3 | Storage, requests, retrieval and transfer |
| Lambda | Requests and execution duration |
| API Gateway | API requests and data transfer |
| RDS | DB instance time, storage, I/O and backup |
| DynamoDB | Read/write requests or provisioned capacity |
| NAT Gateway | Hourly availability and data processing |
| ALB | Hours and Load Balancer Capacity Units |
| CloudWatch | Logs, metrics, alarms and queries |
| CloudFront | Data transfer and HTTP/HTTPS requests |
| EKS | Cluster control plane and underlying compute |
| ECS | Underlying EC2 or Fargate compute |
| SQS | API requests |
| SNS | Published messages and delivery |
| KMS | Key usage and cryptographic requests |
| Secrets Manager | Number of secrets and API calls |

## 2. General AWS cost formula

```text
TOTAL AWS COST =

COMPUTE COST
+ STORAGE COST
+ NETWORKING COST
+ DATABASE COST
+ REQUEST COST
+ DATA TRANSFER COST
+ MONITORING COST
+ SECURITY COST
+ BACKUP COST
+ ADDITIONAL SERVICE COSTS
- APPLICABLE DISCOUNTS
- APPLICABLE CREDITS
```

### Example production application

Imagine an application with:

- 3 EC2 instances.
- 1 Application Load Balancer.
- 1 NAT Gateway.
- 500 GB EBS storage.
- 1 S3 bucket containing 1 TB.
- 1 RDS database.
- API Gateway.
- Lambda.
- CloudWatch.

Even if your application receives very little traffic, some of these resources continue to generate charges because they are provisioned.

This is the most important thing to understand about AWS billing.

**A resource being idle does not necessarily mean it is free.**

## 3. Four important billing concepts

### A. Provisioned billing

You pay for capacity that has been allocated.

Examples:
- EC2 instances.
- EBS volumes.
- RDS provisioned instances.
- NAT Gateways.
- Load balancers.

### B. Consumption-based billing

You pay for actual usage.

Examples:
- Lambda requests and duration.
- S3 requests.
- DynamoDB on-demand requests.
- SQS requests.
- API Gateway calls.

### C. Reservation or commitment billing

You commit to a particular level of usage for a period in exchange for discounted pricing.

Examples:
- EC2 Savings Plans.
- Compute Savings Plans.
- Reserved Instances for eligible services.
- Database Savings Plans where supported.

### D. Tiered billing

The price per unit can change depending on the total usage.

Examples:
- S3 storage tiers.
- API Gateway request-volume tiers.
- Data transfer tiers.
- CloudFront data transfer tiers.

# PART 2 – AWS EC2 COST CALCULATION AND OPTIMISATION

## 4. Amazon EC2

EC2 is one of the most important services to optimise because it can generate continuous charges.

### 4.1 How EC2 cost is calculated

EC2 cost generally depends on:

1. Instance type.
2. Instance operating time.
3. Operating system and software licensing.
4. Purchase model.
5. Region.
6. Tenancy.
7. Dedicated capacity requirements.
8. Additional networking and storage.

### Cost formula

```text
EC2 COST =

INSTANCE HOURLY PRICE
× BILLABLE HOURS

+ ADDITIONAL LICENSING COST
+ ADDITIONAL EC2-RELATED CHARGES
```

Example:

Assume:

- 3 EC2 instances.
- Instance price: €0.10/hour each.
- Running 730 hours per month.

Calculation:

```text
3 × €0.10 × 730

= €219 per month
```

This is only an illustrative calculation. Actual instance prices depend on the Region, instance family, operating system and purchase option.

### 4.2 EC2 pricing models

| Pricing model | Description | When to use |
|---|---|---|
| On-Demand | Pay for usage | Unpredictable workloads |
| Savings Plans | Commit to hourly spend | Stable long-term compute |
| Reserved Instances | Commitment for eligible instance configurations | Predictable workloads |
| Spot | Use spare EC2 capacity | Fault-tolerant workloads |
| Dedicated Hosts | Dedicated physical host | Licensing and compliance requirements |
| Dedicated Instances | Dedicated hardware tenancy | Isolation requirements |

Spot can offer substantial savings, but instances can be interrupted.

AWS documents Spot savings of up to 90% compared with On-Demand in suitable circumstances.

### 4.3 EC2 parameters that affect cost

| Parameter | Cost impact | Recommendation |
|---|---|---|
| instance_type | Direct compute price | Select the smallest suitable type |
| ami | OS and licensing implications | Prefer appropriate Linux images where possible |
| monitoring | Detailed monitoring charges may apply | Enable only when needed |
| ebs_optimized | Depends on instance offering | Check instance pricing and performance |
| root_block_device.volume_size | EBS storage cost | Avoid oversized root disks |
| root_block_device.volume_type | Storage pricing | Select gp3 where suitable |
| root_block_device.iops | Provisioned IOPS costs where applicable | Avoid unnecessary high IOPS |
| root_block_device.throughput | Provisioned throughput costs where applicable | Match actual requirements |
| associate_public_ip_address | Public IPv4 cost implications | Avoid unnecessary public IPv4 |
| credit_specification | CPU credit behaviour | Monitor burstable workloads |
| instance_market_options | Purchase model | Use Spot where safe |
| hibernation | Additional storage considerations | Enable only if required |
| tenancy | Hardware tenancy price | Use shared tenancy unless dedicated hardware is needed |

### 4.4 Terraform cost-optimised EC2 example

```hcl
resource "aws_instance" "app" {

  ami           = var.ami_id

  instance_type = "t3.small"

  subnet_id = var.private_subnet_id

  associate_public_ip_address = false

  monitoring = false

  ebs_optimized = true

  root_block_device {

    volume_size = 20

    volume_type = "gp3"

    encrypted = true

    delete_on_termination = true
  }

  tags = {
    Name        = "application-server"
    Environment = "dev"
  }
}
```

The example assumes the application does not need detailed monitoring or a public IP. Adjust these choices according to actual operational requirements.

### 4.5 How to reduce EC2 costs

1. Right-size instances.
2. Stop unused development instances.
3. Schedule non-production environments.
4. Use Auto Scaling.
5. Use Spot for interruption-tolerant workloads.
6. Purchase Savings Plans for predictable usage.
7. Use Compute Optimizer.
8. Remove unused Elastic IP allocations.
9. Delete unattached EBS volumes.
10. Review operating system licensing.
11. Use Graviton instances where compatible.
12. Avoid oversized instances running at low CPU utilisation.

### 4.6 Production recommendation

For production:

- Use On-Demand capacity for initial workload uncertainty.
- Measure actual utilisation.
- Use Savings Plans for predictable baseline demand.
- Use Spot for appropriate background workloads.
- Configure Auto Scaling.
- Use multiple Availability Zones.
- Monitor CPU, memory and network utilisation.
- Schedule development and testing environments.

# PART 3 – AMAZON EBS COST OPTIMISATION

## 5. Amazon Elastic Block Store

EBS provides persistent block storage for EC2.

### 5.1 How EBS cost is calculated

Main cost dimensions:

- Provisioned volume size.
- Volume type.
- Provisioned IOPS.
- Provisioned throughput.
- Snapshot storage.
- Additional snapshot features.

Unlike EC2, an EBS volume can continue generating storage charges even after the associated EC2 instance has been stopped.

### Cost formula

```text
EBS COST =

PROVISIONED GB × PRICE PER GB-MONTH

+ ADDITIONAL IOPS COST

+ ADDITIONAL THROUGHPUT COST

+ SNAPSHOT STORAGE COST
```

### 5.2 EBS volume types

| Type | Description | Cost consideration |
|---|---|---|
| gp3 | General-purpose SSD | Often a good default |
| gp2 | Older general-purpose SSD | Consider gp3 migration |
| io1 | Provisioned IOPS SSD | Higher performance pricing |
| io2 | High-performance SSD | Use only when justified |
| st1 | Throughput-optimised HDD | Sequential workloads |
| sc1 | Cold HDD | Infrequent access workloads |

### 5.3 Important Terraform parameters

| Parameter | Meaning | Recommendation |
|---|---|---|
| volume_size | Provisioned capacity | Avoid excessive allocation |
| volume_type | Storage class | Prefer gp3 where suitable |
| iops | Provisioned IOPS | Set according to workload |
| throughput | Provisioned throughput | Avoid unnecessary throughput |
| encrypted | Encryption | Keep enabled |
| snapshot_id | Create from snapshot | Use only when needed |
| multi_attach_enabled | Multiple attachment support | Only when required |
| delete_on_termination | Delete with EC2 | Enable for disposable root disks |

### 5.4 Terraform example

```hcl
resource "aws_ebs_volume" "app_data" {

  availability_zone = "eu-west-1a"

  size = 50

  type = "gp3"

  encrypted = true

  tags = {
    Name = "application-data"
  }
}
```

### 5.5 Cost reduction

- Use gp3 instead of gp2 where suitable.
- Avoid unnecessary provisioned IOPS.
- Delete unattached volumes after verifying they are not required.
- Configure snapshot lifecycle policies.
- Remove obsolete snapshots carefully.
- Enable delete_on_termination for temporary root disks.
- Review volume utilisation.
- Avoid retaining multiple unnecessary backups.

### Production warning

Never automatically delete an EBS volume simply because it is unattached.

It may contain important recovery data.

Snapshot it first, validate ownership and retention requirements, then delete only when approved.

# PART 4 – AMAZON S3 COST OPTIMISATION

## 6. Amazon Simple Storage Service

S3 costs can become significant because of large data volumes, requests, retrieval, replication and data transfer.

### 6.1 S3 billing dimensions

1. Storage volume.
2. Storage class.
3. PUT, COPY, POST and LIST requests.
4. GET and other retrieval requests.
5. Data retrieval.
6. Data transfer.
7. Lifecycle transitions.
8. Replication.
9. Intelligent-Tiering monitoring and automation.
10. Inventory and analytics features.

### Cost formula

```text
S3 COST =

STORAGE COST

+ REQUEST COST

+ DATA RETRIEVAL COST

+ DATA TRANSFER COST

+ REPLICATION COST

+ OPTIONAL FEATURE COSTS
```

### 6.2 S3 storage classes

| Storage class | Usage | Cost consideration |
|---|---|---|
| S3 Standard | Frequently accessed | Higher storage price |
| S3 Intelligent-Tiering | Unknown or changing access patterns | Monitoring and automation charges apply |
| S3 Standard-IA | Infrequent access | Retrieval charges and minimum storage duration |
| S3 One Zone-IA | Infrequent, recreatable data | Single-AZ availability |
| S3 Glacier Instant Retrieval | Archive with millisecond retrieval | Retrieval and minimum duration charges |
| S3 Glacier Flexible Retrieval | Archive with slower retrieval | Retrieval charges |
| S3 Glacier Deep Archive | Long-term archival | Lowest storage cost, slow retrieval |

### 6.3 Important S3 Terraform parameters

| Parameter | Purpose | Cost optimisation |
|---|---|---|
| bucket | Bucket identifier | Use structured naming |
| versioning | Object version history | Expire old versions |
| lifecycle_rule | Storage transitions and expiration | Automate retention |
| transition | Move objects between storage classes | Use access patterns |
| expiration | Delete expired objects | Prevent unlimited growth |
| noncurrent_version_expiration | Remove old versions | Control version storage |
| abort_incomplete_multipart_upload | Remove incomplete uploads | Avoid orphaned parts |
| replication_configuration | Replicate objects | Replicate only when required |
| intelligent_tiering | Automatic tiering | Evaluate monitoring costs |
| server_side_encryption_configuration | Encryption | Use suitable encryption |
| request_payer | Requester pays configuration | Understand billing ownership |

### 6.4 Terraform S3 lifecycle example

```hcl
resource "aws_s3_bucket" "application" {

  bucket = "my-company-application-data"

}

resource "aws_s3_bucket_versioning" "application" {

  bucket = aws_s3_bucket.application.id

  versioning_configuration {
    status = "Enabled"
  }
}

resource "aws_s3_bucket_lifecycle_configuration" "application" {

  bucket = aws_s3_bucket.application.id

  rule {

    id = "archive-old-data"

    status = "Enabled"

    filter {}

    transition {

      days = 30

      storage_class = "STANDARD_IA"
    }

    transition {

      days = 90

      storage_class = "GLACIER"
    }

    expiration {

      days = 365
    }

    noncurrent_version_expiration {

      noncurrent_days = 90
    }

    abort_incomplete_multipart_upload {

      days_after_initiation = 7
    }
  }
}
```

The exact lifecycle transitions must comply with the minimum storage duration and object-size rules for the chosen storage class. Test lifecycle rules against your retention policy before deployment.

### 6.5 S3 cost reduction strategies

1. Enable lifecycle policies.
2. Delete incomplete multipart uploads.
3. Expire unnecessary object versions.
4. Archive old logs.
5. Use Intelligent-Tiering where access patterns justify it.
6. Avoid unnecessary cross-Region replication.
7. Reduce repeated GET requests through application caching.
8. Compress large objects.
9. Avoid storing duplicate files.
10. Monitor unexpected storage growth.
11. Review S3 Inventory and analytics costs.
12. Avoid unnecessary data retrieval from Glacier.

### Production recommendation

Use:

- Standard for active application data.
- Intelligent-Tiering for uncertain access patterns.
- Standard-IA for suitable infrequently accessed data.
- Glacier for archival.
- Lifecycle policies for log retention.
- Versioning where recovery is important.

Do not put every object into Glacier automatically. Retrieval time and retrieval charges may make the design unsuitable.

## 7. Amazon EFS

Elastic File System provides shared file storage.

### How EFS costs are calculated

- Storage by storage class.
- Throughput mode.
- Provisioned throughput where applicable.
- Data access and transfer implications.
- Replication and backup features.

### EFS cost formula

```text
EFS COST =

STORAGE GB-MONTH

+ PROVISIONED THROUGHPUT (IF USED)

+ BACKUP AND ADDITIONAL FEATURES
```

| Parameter | Purpose | Recommendation |
|---|---|---|

| lifecycle_policy | Move older files | Enable where appropriate |
| transition_to_ia | Move to infrequent access | Use for cold files |
| transition_to_archive | Move to archive | Use for long-term data |
| encrypted | Encryption | Enable |
| backup_policy | Backup protection | Match retention requirements |

### Cost reduction

- Enable lifecycle management.
- Use IA and archive tiers where appropriate.
- Avoid unnecessary provisioned throughput.
- Monitor storage utilisation.
- Delete abandoned file systems.
- Review backup retention.

# PART 6 – AMAZON RDS AND AURORA

## 9. Amazon RDS

RDS is one of the services where incorrect sizing can create substantial recurring expenditure.

### 9.1 How RDS cost is calculated

Main dimensions:

1. Database instance hours.
2. Instance family and size.
3. Database engine and licensing.
4. Storage capacity.
5. Storage type.
6. Provisioned IOPS.
7. Backup storage beyond applicable allowances.
8. Additional storage and data transfer.
9. Multi-AZ deployment.
10. Read replicas.

### RDS cost formula

```text
RDS COST =

DB INSTANCE COST

+ DATABASE STORAGE

+ PROVISIONED IOPS

+ ADDITIONAL BACKUP STORAGE

+ DATA TRANSFER

+ ADDITIONAL OPTIONS
```

### 9.2 RDS deployment choices

| Configuration | Cost impact |
|---|---|
| Single-AZ | Lower than comparable Multi-AZ configuration |
| Multi-AZ | Additional availability infrastructure |
| Read replica | Additional database instance charges |
| Provisioned storage | Pay for allocated storage |
| Provisioned IOPS | Additional I/O capacity cost |
| Aurora | Separate Aurora pricing model |
| RDS Proxy | Additional proxy capacity charges |

### 9.3 Important RDS Terraform parameters

| Parameter | Meaning | Cost optimisation |
|---|---|---|
| instance_class | DB compute size | Right-size |
| engine | Database engine | Compare licensing |
| engine_version | Database version | Maintain supported versions |
| allocated_storage | Provisioned storage | Avoid excessive allocation |
| max_allocated_storage | Storage autoscaling ceiling | Set sensible upper limit |
| storage_type | Storage type | Select suitable type |
| iops | Provisioned IOPS | Avoid unnecessary capacity |
| storage_throughput | Storage throughput | Match workload |
| multi_az | High availability | Use where required |
| backup_retention_period | Backup retention | Set policy |
| deletion_protection | Prevent deletion | Enable production |
| performance_insights_enabled | Performance monitoring | Evaluate feature pricing |
| monitoring_interval | Enhanced monitoring | Select required interval |
| publicly_accessible | Public access | Set false |
| auto_minor_version_upgrade | Minor upgrades | Enable as appropriate |
| apply_immediately | Apply modifications | Operational setting, not direct savings |

### 9.4 Terraform cost-conscious RDS example

```hcl
resource "aws_db_instance" "application" {

  identifier = "application-db"

  engine = "postgres"

  engine_version = var.postgres_version

  instance_class = "db.t4g.small"

  allocated_storage = 50

  max_allocated_storage = 100

  storage_type = "gp3"

  multi_az = false

  publicly_accessible = false

  backup_retention_period = 7

  storage_encrypted = true

  deletion_protection = true

  skip_final_snapshot = false

  db_subnet_group_name = aws_db_subnet_group.application.name

  vpc_security_group_ids = [
    aws_security_group.database.id
  ]
}
```

This example is suitable as a non-production starting configuration, not as a universal production recommendation.

Production may require Multi-AZ and larger capacity.

### 9.5 RDS cost reduction

- Right-size database instances.
- Stop eligible non-production databases when not needed.
- Use Reserved Instances or applicable database commitments for predictable workloads.
- Review database licensing.
- Reduce excessive storage allocation.
- Use storage autoscaling with a sensible ceiling.
- Review backup retention.
- Remove obsolete snapshots.
- Monitor CPU, memory, connections and IOPS.
- Optimise slow SQL queries.
- Use read replicas only when read scaling justifies the additional cost.
- Avoid Multi-AZ in temporary environments where availability requirements do not justify it.

Important: RDS stopped instances have limitations on how long they can remain stopped, and some storage and backup charges continue.

## 10. Amazon Aurora

Aurora has a different cost model from conventional provisioned RDS engines.

### Aurora cost dimensions

- DB instance hours for provisioned clusters.
- Aurora Serverless v2 capacity consumption.
- Storage.
- I/O operations under applicable configurations.
- Backup storage.
- Data transfer.
- Additional features.

### Aurora provisioned formula

```text
AURORA COST =

WRITER INSTANCE HOURS

+ READER INSTANCE HOURS

+ STORAGE

+ I/O CHARGES WHERE APPLICABLE

+ BACKUP AND DATA TRANSFER
```

### Aurora Serverless v2 formula

```text
SERVERLESS COMPUTE COST =

ACU CONSUMPTION

× TIME

× REGIONAL ACU PRICE

+ STORAGE

+ I/O AND OTHER CHARGES
```

### Important parameters

- engine_mode or applicable engine configuration.
- serverlessv2_scaling_configuration.
- min_capacity.
- max_capacity.
- instance_class.
- backup_retention_period.
- storage_encrypted.
- deletion_protection.
- performance_insights_enabled.

### Cost reduction

- Set a suitable minimum ACU.
- Set a sensible maximum ACU.
- Avoid unnecessarily high minimum capacity.
- Review idle reader instances.
- Optimise query patterns.
- Monitor storage and I/O.
- Use serverless for variable workloads where economically appropriate.
- Avoid oversized provisioned clusters.

Do not automatically choose Aurora Serverless because it says serverless. Compare expected capacity usage against provisioned pricing.

# PART 7 – AMAZON DYNAMODB

## 11. DynamoDB

DynamoDB pricing mainly depends on how the table is configured and how it is accessed.

### 11.1 DynamoDB billing models

A. On-Demand:

Pay for read and write requests consumed.

B. Provisioned:

Allocate read and write capacity units.

C. Provisioned with Auto Scaling:

Automatically adjust capacity according to utilisation targets.

### 11.2 DynamoDB cost dimensions

- Read request units.
- Write request units.
- Provisioned capacity where applicable.
- Storage.
- Backup and restore.
- Point-in-time recovery.
- Streams.
- Global Tables.
- Data export and import.
- Additional features.

### 11.3 Cost formula

On-Demand:

```text
DYNAMODB COST =

READ REQUEST COST

+ WRITE REQUEST COST

+ STORAGE COST

+ BACKUP COST

+ ADDITIONAL FEATURE COSTS
```

Provisioned:

```text
DYNAMODB COST =

PROVISIONED RCU HOURS

+ PROVISIONED WCU HOURS

+ STORAGE

+ BACKUP

+ ADDITIONAL FEATURES
```

### 11.4 Important Terraform parameters

| Parameter | Purpose | Recommendation |
|---|---|---|
| billing_mode | PAY_PER_REQUEST or PROVISIONED | Select based on traffic |
| read_capacity | Read capacity | Avoid excessive allocation |
| write_capacity | Write capacity | Avoid excessive allocation |
| hash_key | Partition key | Design for distribution |
| range_key | Sort key | Design access patterns |
| stream_enabled | DynamoDB Streams | Enable only when needed |
| point_in_time_recovery | Continuous recovery | Apply retention requirements |
| ttl | Automatic expiry | Remove expired records |
| server_side_encryption | Encryption | Enable |
| global_secondary_index | Additional access pattern | Avoid unnecessary indexes |
| global_table | Multi-Region replication | Use only when justified |

### 11.5 Terraform example

```hcl
resource "aws_dynamodb_table" "orders" {

  name = "orders"

  billing_mode = "PAY_PER_REQUEST"

  hash_key = "order_id"

  attribute {
    name = "order_id"
    type = "S"
  }

  point_in_time_recovery {
    enabled = true
  }

  server_side_encryption {
    enabled = true
  }

  ttl {
    attribute_name = "expires_at"
    enabled        = true
  }

  tags = {
    Environment = "production"
  }
}
```

### 11.6 Cost reduction

- Use on-demand for unpredictable workloads.
- Use provisioned capacity for predictable workloads where cheaper.
- Configure Auto Scaling.
- Reduce unnecessary reads.
- Use efficient partition and sort key design.
- Avoid unnecessary indexes.
- Use TTL for eligible temporary data.
- Monitor consumed capacity.
- Review backup retention.
- Avoid unnecessary Global Tables.
- Avoid excessively large items.
- Use appropriate caching.

Important: TTL deletes expired items asynchronously. It is not an immediate deletion mechanism, and storage/request charges can continue until deletion occurs.

# PART 8 – AMAZON LAMBDA

## 12. AWS Lambda

Lambda is serverless compute.

It does not require continuously running EC2 instances.

### 12.1 Lambda billing dimensions

- Number of requests.
- Execution duration.
- Allocated memory.
- Architecture.
- Provisioned concurrency.
- Ephemeral storage above included capacity.
- Additional features and data transfer.

### Lambda cost formula

```text
LAMBDA COST =

REQUEST CHARGES

+ COMPUTE DURATION CHARGES

+ PROVISIONED CONCURRENCY

+ ADDITIONAL EPHEMERAL STORAGE

+ ADDITIONAL FEATURES
```

Execution duration is measured in GB-seconds for pricing purposes.

### 12.2 Important Lambda parameters

| Parameter | Purpose | Cost impact |
|---|---|---|
| memory_size | Allocated memory | Higher memory increases compute rate but may reduce duration |
| timeout | Maximum runtime | Higher timeout can allow more consumption |
| reserved_concurrent_executions | Reserved concurrency | Capacity reservation and throttling control |
| provisioned_concurrent_executions | Warm capacity | Additional ongoing charges |
| ephemeral_storage | Temporary storage | Additional charges above included allocation |
| architecture | x86_64 or arm64 | Architecture pricing differences |
| runtime | Language runtime | Performance considerations |
| tracing_config | X-Ray tracing | Additional tracing costs |
| logging_config | Logging | Log ingestion and storage costs |
| layers | Shared dependencies | No direct layer fee, but packaging and runtime implications |

### 12.3 Terraform example

```hcl
resource "aws_lambda_function" "orders" {

  function_name = "orders-service"

  role = aws_iam_role.lambda_role.arn

  runtime = "python3.12"

  handler = "index.lambda_handler"

  filename = "lambda.zip"

  memory_size = 256

  timeout = 10

  architectures = ["arm64"]

  reserved_concurrent_executions = 50

  ephemeral_storage {
    size = 512
  }

  tags = {
    Environment = "production"
  }
}
```

### 12.4 Cost reduction

1. Optimise execution duration.
2. Select suitable memory.
3. Benchmark ARM64 where compatible.
4. Avoid unnecessary provisioned concurrency.
5. Reduce cold-start overhead.
6. Reuse database connections appropriately.
7. Reduce excessive logging.
8. Avoid unnecessary retries.
9. Batch event processing where suitable.
10. Prevent infinite invocation loops.
11. Use reserved concurrency to protect downstream systems.
12. Avoid large temporary storage unless needed.

### 12.5 Important production recommendation

Do not simply reduce Lambda memory to save money.

A function with more memory may finish significantly faster and cost less overall.

Benchmark different configurations using representative workloads.

# PART 9 – ECS, EKS AND FARGATE

## 13. Amazon ECS

ECS is a container orchestration service.

ECS itself has no additional control-plane charge in the usual ECS deployment model, but the infrastructure running the containers costs money.

### ECS cost depends on:

- EC2 capacity if using EC2 launch type.
- Fargate vCPU.
- Fargate memory.
- Runtime duration.
- Ephemeral storage above included allocation.
- EBS volumes where used.
- Load balancers.
- Networking.
- CloudWatch logs.

### ECS EC2 launch type

```text
ECS EC2 COST =

EC2 INSTANCE COST

+ EBS STORAGE

+ NETWORKING

+ MONITORING
```

### ECS Fargate launch type

```text
FARGATE COST =

vCPU ALLOCATION × RUNNING TIME × vCPU PRICE

+

MEMORY ALLOCATION × RUNNING TIME × MEMORY PRICE

+

ADDITIONAL STORAGE AND NETWORKING
```

### ECS Terraform cost-related parameters

- launch_type.
- capacity_provider_strategy.
- desired_count.
- cpu.
- memory.
- deployment_minimum_healthy_percent.
- deployment_maximum_percent.
- platform_version.
- ephemeral_storage.
- autoscaling_min_capacity.
- autoscaling_max_capacity.

### Cost reduction

# PART 10 – NETWORKING COST OPTIMISATION

## 15. NAT Gateway

NAT Gateway is a common source of unexpected AWS charges.

### How NAT Gateway cost is calculated

1. Hourly NAT Gateway availability.
2. Data processed through NAT Gateway.
3. Additional network transfer charges where applicable.

### Cost formula

```text
NAT COST =

NAT GATEWAY HOURS × HOURLY PRICE

+

GB PROCESSED × PROCESSING PRICE

+

OTHER APPLICABLE DATA TRANSFER
```

Example:

Assume:
- One NAT Gateway.
- 730 hours.
- Illustrative hourly price of €0.045.
- 1,000 GB processed.
- Illustrative processing price of €0.045/GB.

Calculation:

```text
730 × €0.045 = €32.85

1,000 × €0.045 = €45

Total = €77.85
```

This is an illustrative calculation, not an Ireland price quotation.

### Why NAT becomes expensive

Consider this architecture:

```text
PRIVATE EC2
     |
     v
NAT GATEWAY
     |
     v
INTERNET
     |
     v
AWS S3
```

If private EC2 instances repeatedly access S3 through NAT, unnecessary NAT data-processing charges can accumulate.

### Cost optimisation

Create an S3 Gateway VPC Endpoint.

New architecture:

```text
PRIVATE EC2
     |
     v
S3 GATEWAY ENDPOINT
     |
     v
S3
```

For supported S3 and DynamoDB gateway endpoint traffic, this can avoid NAT processing charges.

Other optimisation strategies:

- Use appropriate VPC endpoints.
- Reduce cross-AZ traffic.
- Avoid unnecessary NAT Gateways.
- Review data processing.
- Identify unexpected traffic sources.
- Use endpoints for supported AWS services.
- Avoid sending internal traffic through NAT.

### Production warning

Do not remove NAT Gateways from production without checking outbound internet dependencies.

A private instance may need NAT for package repositories, external APIs or third-party services.

# PART 20 – HOW TO IMPLEMENT FINOPS IN A PRODUCTION AWS ACCOUNT

## 50. Cost allocation tags

Every resource should have meaningful tags.

Example:

```hcl
tags = {
  Environment = "production"

  Project = "ecommerce"

  Application = "customer-platform"

  Owner = "platform-team"

  CostCenter = "engineering"

  ManagedBy = "terraform"
}
```

Recommended tags:

- Environment.
- Project.
- Application.
- Owner.
- CostCenter.
- BusinessUnit.
- ManagedBy.

Activate relevant cost allocation tags in AWS Billing.

Not all AWS charges can be allocated directly through resource tags.

## 51. Automated non-production shutdown

Development infrastructure does not always need to run 24/7.

Example schedule:

```text
START:
Monday-Friday 08:00

STOP:
Monday-Friday 19:00

WEEKENDS:
STOP
```

A continuously running resource operates approximately 730 hours in a 30-day month.

If it runs only 11 hours per weekday over 22 weekdays:

```text
11 × 22 = 242 hours

Hours avoided = 730 - 242

= 488 hours

Potential runtime reduction:

488 / 730 × 100

= 66.85%
```

This is a runtime reduction, not necessarily an identical percentage reduction in the entire AWS bill.

You can implement scheduling through:
- AWS Instance Scheduler.
- Systems Manager Automation.
- EventBridge and Lambda.
- Approved orchestration tools.

Check database, storage, networking and licence charges that continue when compute is stopped.

## 52. Monthly cost review process

Every month:

1. Open Cost Explorer.
2. Select the previous month.
3. Group by service.
4. Identify the five most expensive services.
5. Group each expensive service by usage type.
6. Identify unused resources.
7. Review data transfer.
8. Review NAT Gateway usage.
9. Review EBS and snapshot storage.
10. Review RDS and EC2 utilisation.
11. Review CloudWatch log ingestion.
12. Review commitments and discounts.
13. Compare actual versus forecast.
14. Create optimisation actions.
15. Measure savings in the next billing period.

# PART 21 – AWS COST OPTIMISATION INTERVIEW QUESTIONS

## 53. Basic questions

**Q1. What is AWS cost optimisation?**

Continuously matching AWS resource capacity and usage to actual business requirements while maintaining security, availability and performance.

**Q2. What is the difference between On-Demand and Spot?**

On-Demand provides normal requested capacity; Spot uses spare EC2 capacity and can be interrupted.

**Q3. What are Savings Plans?**

Commitment-based pricing models that offer discounts for eligible compute usage.

**Q4. Why is NAT Gateway expensive?**

It charges for provisioned hours and data processing, in addition to relevant transfer charges.

**Q5. How do you reduce EC2 cost?**

Rightsizing, scheduling, Auto Scaling, Spot and Savings Plans.

**Q6. How do you reduce S3 cost?**

Lifecycle policies, archival, deletion of old versions and optimisation of requests and retrieval.

**Q7. How do you reduce RDS cost?**

Rightsizing, database commitments, storage optimisation, backup review and query optimisation.

**Q8. How do you reduce Lambda cost?**

Optimise memory, execution duration, requests and concurrency.

**Q9. What is the difference between provisioned and on-demand DynamoDB?**

Provisioned allocates capacity; on-demand charges based on request usage.

**Q10. What is FinOps?**

A collaborative operational practice combining finance, engineering and business teams to manage cloud expenditure.

## 54. Scenario-based questions

**Q11. Your EC2 bill increased by 40%. How do you investigate?**

Answer:
- Open Cost Explorer.
- Group by usage type.
- Check instance hours.
- Review instance type changes.
- Check newly launched instances.
- Check EBS and data transfer.
- Compare previous billing periods.
- Review Auto Scaling and Spot usage.

**Q12. Your NAT Gateway costs are unexpectedly high. What do you do?**

Answer:
- Review NAT processed bytes.
- Identify source instances.
- Inspect destination traffic.
- Check S3 and DynamoDB access.
- Create appropriate gateway endpoints.
- Review cross-AZ routing.
- Check external API calls.

**Q13. Your CloudWatch bill is higher than expected.**

Answer:
- Review log ingestion.
- Review retention.
- Identify noisy applications.
- Review custom metrics.
- Review detailed monitoring.
- Check alarms and metric streams.
- Reduce unnecessary log queries.

**Q14. Your S3 storage is growing continuously.**

Answer:
- Enable S3 Inventory.
- Review storage classes.
- Check object versions.
- Configure lifecycle expiration.
- Delete incomplete multipart uploads.
- Review replication.
- Identify duplicate files.

**Q15. Your production RDS is underutilised. Can you reduce its size?**

Answer:
- Review CPU and memory.
- Review connections.
- Analyse IOPS and storage throughput.
- Review peak-period utilisation.
- Test a smaller instance.
- Confirm failover and availability requirements.
- Apply a controlled change.

**Q16. Should we always choose serverless to reduce costs?**

Answer:

No. Serverless is cost-effective for many variable workloads, but continuously high workloads may be cheaper with provisioned infrastructure or commitments.

**Q17. Why can a stopped EC2 instance still generate costs?**

Answer:

EBS volumes, snapshots, allocated public IPv4 addresses and other associated resources can continue generating charges.

**Q18. How do you prevent AWS bill surprises?**

Answer:
- AWS Budgets.
- Cost Anomaly Detection.
- Cost Explorer.
- Cost allocation tags.
- Resource scheduling.
- Usage alerts.
- Monthly reviews.

# FINAL PRINCIPLE

AWS cost optimisation is not about making every resource as small or cheap as possible.

It is about selecting the right service, the right pricing model, the right capacity and the right configuration for the workload.

Remember this sequence:

```text
1. IDENTIFY
   Which AWS service is generating the cost?

2. ANALYSE
   Which usage dimension is responsible?

3. MEASURE
   Is the resource actually being utilised?

4. OPTIMISE
   Which parameter or architecture can reduce waste?

5. AUTOMATE
   Can Terraform, Auto Scaling or scheduling enforce it?

6. MONITOR
   Did the change actually reduce the bill?

7. VALIDATE
   Did we preserve security, reliability and performance?
```

**The ultimate goal: Reduce unnecessary AWS expenditure without compromising production availability, performance, security or disaster recovery.**
