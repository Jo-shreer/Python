# AWS SQS – Complete Cheatsheet (Fundamentals to Production)

# 1. What is Amazon SQS?

Amazon SQS (Simple Queue Service) is a fully managed message queuing service provided by AWS.

It allows different applications and services to communicate asynchronously without needing to communicate directly with each other.

In simple terms, SQS acts as a middle layer between two applications.

Example:

An e-commerce application receives an order.

Instead of processing the order immediately, it places a message into SQS.

A backend worker retrieves the message and processes the order.

Architecture:

```text
Producer Application
        |
        | Send Message
        v
     SQS Queue
        |
        | Receive Message
        v
Consumer Application
        |
        v
Process Order
```

### Why use SQS?

- Decouples applications.
- Supports asynchronous processing.
- Handles traffic spikes.
- Improves application scalability.
- Provides message buffering.
- Supports retries and dead-letter queues.
- Reduces direct dependencies between services.

### Real-world example

An e-commerce website receives 10,000 orders within a short period.

Without SQS, the backend application may become overloaded.

With SQS:

1. The application sends order messages to SQS.
2. SQS stores the messages.
3. Multiple worker instances retrieve messages.
4. Workers process orders independently.
5. Successfully processed messages are deleted.

This allows the consumer application to process messages at its own pace.

# 2. SQS Architecture and Components

There are five important concepts.

### A. Producer

The application or service that sends messages to SQS.

Examples:
- EC2 application.
- Lambda function.
- ECS container.
- EKS application.
- Another AWS service.

API operation:

`SendMessage`

### B. Queue

A queue stores messages until consumers retrieve and process them.

Example:

`order-processing-queue`

### C. Message

A message is the actual data sent to the queue.

Example:

```json
{
  "order_id": "ORD1001",
  "customer_id": "CUST101",
  "amount": 250
}
```

### D. Consumer

The application that retrieves and processes messages.

API operation:

`ReceiveMessage`

### E. DeleteMessage

After successful processing, the consumer deletes the message from SQS.

API operation:

`DeleteMessage`

Important: Receiving a message does not automatically delete it from the queue.

The message becomes temporarily invisible to other consumers during the visibility timeout.

# 3. Types of SQS Queues

Amazon SQS supports two primary queue types.

## A. Standard Queue

Standard queues provide:

- Very high throughput.
- At-least-once message delivery.
- Best-effort ordering.
- Horizontal scalability.

Messages can occasionally be delivered more than once.

Message order is not guaranteed.

Example:

Messages sent:

```text
Message 1
Message 2
Message 3
```

Messages received could be:

```text
Message 2
Message 1
Message 3
```

Use cases:

- Background job processing.
- Image processing.
- Email notifications.
- Log processing.
- General asynchronous workloads.

## B. FIFO Queue

FIFO stands for First-In, First-Out.

FIFO queues provide:

- Ordering within a message group.
- Exactly-once processing semantics under the FIFO deduplication model.
- Deduplication support.
- Controlled message processing order.

Example:

Messages sent:

```text
Message 1
Message 2
Message 3
```

Messages are processed in order within the same message group.

Use cases:

- Banking transactions.
- Financial operations.
- Order processing where order matters.
- Inventory updates.
- Sequential business workflows.

### Standard vs FIFO

| Feature | Standard | FIFO |
|---|---|---|
| Ordering | Best effort | Guaranteed within message group |
| Delivery | At least once | Exactly-once processing semantics |
| Throughput | Very high | Higher throughput with batching and high-throughput mode |
| Deduplication | No built-in deduplication | Supported |
| Queue name | Normal name | Must end with `.fifo` |

Important: FIFO exactly-once processing semantics do not mean your application can ignore idempotency. Consumers should still handle retries and external side effects safely.

# 4. SQS Message Lifecycle

Understanding the message lifecycle is extremely important.

There are three main stages.

### Stage 1: Message Sent

Producer sends a message to SQS using:

`SendMessage`

The message becomes available in the queue.

### Stage 2: Message Received

Consumer calls:

`ReceiveMessage`

SQS returns the message and makes it temporarily invisible to other consumers.

This is controlled by the Visibility Timeout.

### Stage 3: Message Deleted

After successfully processing the message, the consumer calls:

`DeleteMessage`

The message is permanently removed from the queue.

Architecture:

```text
Producer
   |
   v
SendMessage
   |
   v
SQS Queue
   |
   v
ReceiveMessage
   |
   v
Visibility Timeout
   |
   v
Consumer Processes Message
   |
   v
DeleteMessage
```

If the consumer fails before deleting the message, the message becomes visible again after the visibility timeout expires.

# 5. Visibility Timeout

Visibility Timeout determines how long a received message remains invisible to other consumers.

Default:

30 seconds.

Maximum:

12 hours.

Example:

1. Consumer receives a message at 10:00.
2. Visibility timeout is 60 seconds.
3. The message becomes invisible until approximately 10:01.
4. If processing succeeds, the consumer deletes it.
5. If processing fails and the message is not deleted, it becomes available again.

### Why is visibility timeout important?

If it is too short:
- Messages can become visible while the original consumer is still processing them.
- Another consumer may process the same message concurrently.

If it is too long:
- Failed messages take longer to become available again.

Best practice:

Set visibility timeout longer than the expected processing duration.

For long-running tasks, extend the visibility timeout using `ChangeMessageVisibility`.

# 6. Message Retention Period

Message retention determines how long messages remain in SQS if they are not deleted.

Default:

4 days.

Minimum:

60 seconds.

Maximum:

14 days.

Example:

A message is sent to SQS but no consumer processes it.

If retention is configured for 7 days, SQS retains the message for up to 7 days before expiring it.

Retention is useful for:
- Handling temporary consumer failures.
- Recovering from application outages.
- Buffering messages during traffic spikes.

# 7. Delay Queues and Message Timers

SQS supports delayed message delivery.

### Delay Queue

A delay queue makes all new messages temporarily unavailable for a configured period.

Maximum delay:

15 minutes.

Example:

You want to process a job 5 minutes after it is submitted.

Configure:

`DelaySeconds = 300`

### Message Timer

A message timer delays an individual message rather than all messages in the queue.

Use cases:
- Delayed notifications.
- Scheduled processing.
- Retry workflows.

Important: For scheduling beyond 15 minutes or complex recurring schedules, use EventBridge Scheduler or another scheduling service.

# 8. Dead-Letter Queue (DLQ)

A Dead-Letter Queue stores messages that cannot be successfully processed after a configured number of attempts.

Example:

A consumer continuously fails while processing an order message.

Instead of retrying forever, SQS moves the message to a DLQ after the configured maximum receive count.

Architecture:

```text
Producer
   |
   v
Main SQS Queue
   |
   v
Consumer
   |
   | Processing fails
   |
   v
Retry
   |
   v
Maximum Receive Count Reached
   |
   v
Dead-Letter Queue
```

### Why use a DLQ?

- Prevents problematic messages from blocking normal processing.
- Helps troubleshoot failures.
- Supports manual investigation.
- Allows controlled redrive of messages.

### Redrive Policy

A redrive policy defines:

- Target DLQ ARN.
- Maximum receive count.

Example:

```json
{
  "deadLetterTargetArn": "arn:aws:sqs:eu-west-1:123456789012:orders-dlq",
  "maxReceiveCount": 5
}
```

This means a message can be received up to the configured threshold before being moved to the DLQ.

Important:
- The DLQ must have the same queue type as the source queue.
- FIFO queues require FIFO DLQs.
- Standard queues require Standard DLQs.
- For Standard queues, messages moved to a DLQ retain their original enqueue timestamp for expiration purposes.
- For FIFO queues, the enqueue timestamp resets when the message moves to the DLQ.

# 9. Message Size Limit

SQS supports messages up to 1 MiB in size.

If your application needs to send larger payloads:

1. Upload the actual file to S3.
2. Send the S3 bucket name and object key through SQS.
3. Consumer retrieves the object from S3.

Example message:

```json
{
  "bucket": "company-prod-data",
  "object_key": "orders/order1001.json"
}
```

This approach avoids sending large payloads directly through SQS.

# 10. Long Polling vs Short Polling

SQS supports two polling approaches.

### A. Short Polling

SQS returns a response immediately based on a subset of available servers.

It can return an empty response even when messages exist elsewhere.

Characteristics:
- More frequent API calls.
- Potentially more empty responses.
- Can increase request costs.

### B. Long Polling

SQS waits for messages to become available before returning a response, up to the configured wait time.

Maximum wait time:

20 seconds.

Configure:

`ReceiveMessageWaitTimeSeconds = 20`

Advantages:
- Reduces empty responses.
- Reduces unnecessary API requests.
- Improves consumer efficiency.
- Often reduces costs.

Recommended for most consumer applications.

# 11. Message Deduplication and Message Groups

These concepts are especially important for FIFO queues.

### A. Message Deduplication

Prevents duplicate messages from being accepted within the deduplication interval.

The deduplication interval is 5 minutes.

Two approaches:

1. Content-based deduplication.
2. Explicit MessageDeduplicationId.

### B. Message Group ID

FIFO queues use MessageGroupId to maintain message ordering.

Messages with the same MessageGroupId are processed in order.

Example:

```text
Message Group: Customer-101

Message 1
Message 2
Message 3
```

These messages maintain their order.

Different message groups can be processed concurrently.

Example:

```text
Customer-101
    Message 1
    Message 2

Customer-102
    Message 1
    Message 2
```

The two customer groups can be processed independently.

# 12. SQS Encryption

SQS supports encryption at rest and encryption in transit.

### A. Server-Side Encryption (SSE)

SQS encrypts messages at rest.

Options include:

**SSE-SQS**
- Uses SQS-managed encryption keys.
- Simpler key management.
- No separate KMS key management required.

**SSE-KMS**
- Uses AWS KMS.
- Allows customer-managed key policies.
- Supports additional key-management and auditing controls.
- KMS API charges can apply.

### B. Encryption in Transit

Use HTTPS/TLS when communicating with SQS.

SQS service endpoints support HTTPS.

For sensitive workloads, consider using a queue policy that denies insecure transport.

# 13. SQS Access Management and IAM

IAM determines which AWS identities can interact with SQS.

Common SQS permissions:

| IAM Action | Purpose |
|---|---|
| sqs:SendMessage | Send messages |
| sqs:ReceiveMessage | Receive messages |
| sqs:DeleteMessage | Delete messages |
| sqs:GetQueueAttributes | Read queue attributes |
| sqs:GetQueueUrl | Get queue URL |
| sqs:ChangeMessageVisibility | Change visibility timeout |
| sqs:PurgeQueue | Delete all messages |
| sqs:ListQueues | List available queues |

### Example IAM Policy

Allow an EC2 application to send and receive messages from a specific queue.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "sqs:SendMessage",
        "sqs:ReceiveMessage",
        "sqs:DeleteMessage",
        "sqs:GetQueueAttributes",
        "sqs:GetQueueUrl"
      ],
      "Resource": "arn:aws:sqs:eu-west-1:123456789012:orders-queue"
    }
  ]
}
```

Attach this policy to the EC2 IAM role.

### IAM Role vs Queue Policy

IAM Role:
- Defines what the EC2 application is allowed to do.

Queue Policy:
- Defines which identities or AWS services can access the queue.
- Can grant cross-account access.
- Can restrict access based on conditions.

Both policies must allow access where applicable, and explicit denies override allows.

# 14. SQS with Private Subnets – VPC Endpoint

Suppose an EC2 instance is running in a private subnet and needs to communicate with SQS.

By default, the instance may not have internet access.

We can create an Interface VPC Endpoint for SQS using AWS PrivateLink.

Service name:

`com.amazonaws.<region>.sqs`

Example:

`com.amazonaws.eu-west-1.sqs`

### Architecture

```text
EC2 Instance
(Private Subnet)
       |
       v
EC2 Security Group
       |
       | Outbound TCP 443
       |
       v
SQS Interface VPC Endpoint
       |
       | Inbound TCP 443
       |
       v
AWS PrivateLink
       |
       v
Amazon SQS
```

### Configuration Steps

1. Identify the VPC and private subnets.
2. Create an Interface VPC Endpoint for SQS.
3. Enable Private DNS.
4. Create or select an endpoint Security Group.
5. Allow inbound TCP 443 from the EC2 Security Group.
6. Ensure the EC2 Security Group allows outbound TCP 443.
7. Create an IAM Role for EC2.
8. Attach required SQS permissions.
9. Attach the IAM role to EC2.
10. Test connectivity using AWS CLI.

### Important

- Interface endpoints have hourly charges per Availability Zone.
- Data processing charges apply.
- No NAT Gateway is required for this SQS connection.
- VPC DNS support and DNS hostnames must be enabled for Private DNS.

# 15. SQS with Lambda

SQS can trigger Lambda functions for asynchronous processing.

Architecture:

```text
Producer
   |
   v
SQS Queue
   |
   v
Lambda Event Source Mapping
   |
   v
Lambda Function
   |
   v
Process Message
```

Lambda polls SQS on your behalf using an event source mapping.

### Important concepts

**Event Source Mapping**

Connects an SQS queue to a Lambda function.

**Batch Size**

Controls how many messages Lambda receives in one invocation.

**Batch Window**

Controls how long Lambda can wait to collect a batch before invoking the function.

**Partial Batch Failure**

Allows Lambda to report only failed messages instead of retrying an entire batch.

For partial batch failures, configure:

`ReportBatchItemFailures`

**Scaling**

Lambda can increase concurrent processing based on queue activity and configured concurrency limits.

### Important best practices

- Configure the Lambda timeout appropriately.
- Configure queue visibility timeout appropriately.
- Make processing idempotent.
- Use partial batch failure handling.
- Configure a DLQ or redrive policy.
- Monitor message age and queue depth.

For Lambda with SQS, AWS recommends setting the queue visibility timeout to at least six times the Lambda function timeout, plus the maximum batching window.

# 16. SQS Monitoring Using CloudWatch

Amazon SQS integrates with CloudWatch.

Important metrics:

| Metric | Meaning |
|---|---|
| ApproximateNumberOfMessagesVisible | Messages waiting to be processed |
| ApproximateNumberOfMessagesNotVisible | Messages currently being processed or invisible |
| ApproximateNumberOfMessagesDelayed | Messages delayed before becoming available |
| ApproximateAgeOfOldestMessage | Age of the oldest available message |
| NumberOfMessagesSent | Messages sent |
| NumberOfMessagesReceived | Messages received |
| NumberOfMessagesDeleted | Messages deleted |

### Important production alarms

Create CloudWatch alarms for:

1. Queue depth becoming too high.
2. Oldest message age exceeding acceptable limits.
3. DLQ containing messages.
4. Unusual processing or delivery patterns.

Important: Many SQS metrics are approximate. Do not treat them as exact real-time queue counts.

# 17. SQS Cost Considerations

SQS pricing is primarily based on requests.

### A. Request Charges

API operations can include:

- SendMessage
- ReceiveMessage
- DeleteMessage
- ChangeMessageVisibility
- GetQueueAttributes

SQS pricing counts requests in request units. A request involving multiple 64 KB payload chunks can consume multiple request units.

### B. FIFO Charges

FIFO queue pricing differs from Standard queue pricing.

### C. Long Polling

Long polling can reduce empty ReceiveMessage responses and therefore reduce unnecessary requests.

### D. Batch Operations

Batch APIs allow multiple messages to be sent, received or deleted in a single API call, subject to the API limits.

Batching can reduce request costs.

### E. KMS Charges

If using SSE-KMS, additional KMS request charges can apply.

### F. VPC Endpoint Charges

If using an Interface VPC Endpoint:
- Hourly endpoint charges per AZ.
- Data processing charges per GB.

### Cost Optimisation

- Use long polling.
- Use batch operations.
- Configure sensible retention periods.
- Avoid unnecessary polling.
- Monitor DLQ activity.
- Select Standard or FIFO based on application requirements.
- Review KMS and VPC endpoint costs.

Official pricing:

https://aws.amazon.com/sqs/pricing/

# 18. AWS CLI – Important SQS Commands

### Create a Standard Queue

```bash
aws sqs create-queue \
  --queue-name orders-queue \
  --region eu-west-1
```

### Create a FIFO Queue

```bash
aws sqs create-queue \
  --queue-name orders-queue.fifo \
  --attributes FifoQueue=true \
  --region eu-west-1
```

### List Queues

```bash
aws sqs list-queues \
  --region eu-west-1
```

### Get Queue URL

```bash
aws sqs get-queue-url \
  --queue-name orders-queue \
  --region eu-west-1
```

### Send Message

```bash
aws sqs send-message \
  --queue-url YOUR_QUEUE_URL \
  --message-body "Hello from SQS" \
  --region eu-west-1
```

### Receive Message

```bash
aws sqs receive-message \
  --queue-url YOUR_QUEUE_URL \
  --max-number-of-messages 10 \
  --wait-time-seconds 20 \
  --region eu-west-1
```

### Delete Message

```bash
aws sqs delete-message \
  --queue-url YOUR_QUEUE_URL \
  --receipt-handle YOUR_RECEIPT_HANDLE \
  --region eu-west-1
```

### Get Queue Attributes

```bash
aws sqs get-queue-attributes \
  --queue-url YOUR_QUEUE_URL \
  --attribute-names All \
  --region eu-west-1
```

### Purge Queue

```bash
aws sqs purge-queue \
  --queue-url YOUR_QUEUE_URL \
  --region eu-west-1
```

Warning: Purging removes messages from the queue. It cannot be undone.

# 19. Important SQS Interview Questions

**Q1. What is Amazon SQS?**

A fully managed message queuing service used for asynchronous communication between applications.

**Q2. What is the difference between Standard and FIFO queues?**

Standard provides very high throughput and best-effort ordering. FIFO provides ordered processing within message groups and deduplication support.

**Q3. What is visibility timeout?**

The period during which a received message remains invisible to other consumers.

**Q4. What happens if a consumer fails?**

If the message is not deleted, it becomes visible again after the visibility timeout expires.

**Q5. What is a DLQ?**

A queue used to isolate messages that repeatedly fail processing.

**Q6. What is long polling?**

SQS waits for messages to become available, up to the configured wait time, before returning a response.

**Q7. What is message retention?**

The period for which SQS retains messages before expiring them.

**Q8. What is MessageGroupId?**

An identifier used by FIFO queues to group messages and maintain ordering within each group.

**Q9. Can EC2 in a private subnet access SQS without NAT?**

Yes, using an SQS Interface VPC Endpoint.

**Q10. What is the maximum SQS message size?**

1 MiB.

**Q11. What is the maximum message retention period?**

14 days.

**Q12. What is the maximum visibility timeout?**

12 hours.

**Q13. What is the maximum long polling wait time?**

20 seconds.

**Q14. Does SQS automatically delete a message after receiving it?**

No. The consumer must call DeleteMessage after successful processing.

**Q15. What is the difference between SNS and SQS?**

SNS is a publish/subscribe notification service. SQS is a message queue that stores messages until consumers retrieve them.

**Q16. Can SQS integrate with Lambda?**

Yes. Lambda polls SQS through an event source mapping.

**Q17. What is the difference between delay queue and visibility timeout?**

Delay queue controls when a new message first becomes available. Visibility timeout controls how long a received message remains invisible.

**Q18. What is the difference between a queue policy and IAM policy?**

IAM policy controls identity permissions. Queue policy controls access to the SQS resource.

**Q19. What is the maximum number of messages returned by ReceiveMessage?**

10 messages per API request.

**Q20. What is a receipt handle?**

A unique identifier returned when a message is received. It is required to delete that particular received message or change its visibility.

## File 4: main.tf

### A. Create Dead-Letter Queue

```hcl
resource "aws_sqs_queue" "dlq" {
  name = var.dlq_name

  message_retention_seconds = 1209600

  sqs_managed_sse_enabled = true

  tags = {
    Name = var.dlq_name
  }
}
```

The DLQ retains messages for 14 days.

### B. Create Main SQS Queue

```hcl
resource "aws_sqs_queue" "main" {
  name = var.queue_name

  visibility_timeout_seconds = var.visibility_timeout

  message_retention_seconds = var.message_retention

  receive_wait_time_seconds = 20

  delay_seconds = 0

  max_message_size = 1048576

  sqs_managed_sse_enabled = true

  redrive_policy = jsonencode({
    deadLetterTargetArn = aws_sqs_queue.dlq.arn
    maxReceiveCount     = var.max_receive_count
  })

  tags = {
    Name = var.queue_name
  }
}
```

Explanation:

- Visibility timeout: 120 seconds.
- Message retention: 4 days.
- Long polling: 20 seconds.
- Maximum message size: 1 MiB.
- Encryption: SQS-managed encryption.
- Messages move to DLQ after the configured receive threshold.

### C. Configure Queue Policy

```hcl
resource "aws_sqs_queue_policy" "main" {
  queue_url = aws_sqs_queue.main.id

  policy = jsonencode({
    Version = "2012-10-17"

    Statement = [
      {
        Sid       = "DenyInsecureTransport"
        Effect    = "Deny"
        Principal = "*"

        Action = "sqs:*"

        Resource = aws_sqs_queue.main.arn

        Condition = {
          Bool = {
            "aws:SecureTransport" = "false"
          }
        }
      }
    ]
  })
}
```

This denies requests made over insecure transport.

The queue policy does not grant application permissions. Those are configured separately through IAM.

### D. CloudWatch Alarm – Main Queue Depth

```hcl
resource "aws_cloudwatch_metric_alarm" "queue_depth" {
  alarm_name          = "${var.queue_name}-high-message-count"
  comparison_operator = "GreaterThanThreshold"

  evaluation_periods = 2

  metric_name = "ApproximateNumberOfMessagesVisible"

  namespace = "AWS/SQS"

  period = 300

  statistic = "Average"

  threshold = 100

  alarm_description = "Main SQS queue has too many visible messages"

  dimensions = {
    QueueName = aws_sqs_queue.main.name
  }
}
```

This alarm triggers when the average visible message count exceeds 100 over two consecutive five-minute evaluation periods.

### E. CloudWatch Alarm – DLQ Messages

```hcl
resource "aws_cloudwatch_metric_alarm" "dlq_messages" {
  alarm_name          = "${var.dlq_name}-messages-detected"
  comparison_operator = "GreaterThanThreshold"

  evaluation_periods = 1

  metric_name = "ApproximateNumberOfMessagesVisible"

  namespace = "AWS/SQS"

  period = 60

  statistic = "Average"

  threshold = 0

  alarm_description = "Messages detected in the Dead Letter Queue"

  dimensions = {
    QueueName = aws_sqs_queue.dlq.name
  }
}
```

This alarm detects messages appearing in the DLQ.

For production notifications, connect the alarms to an SNS topic and configure the required notification subscribers.

# 21. Create IAM Role and Permissions Using Terraform

For EC2 applications that need to access the SQS queue, create an IAM role.

## File: iam.tf

### A. Create EC2 IAM Role

```hcl
resource "aws_iam_role" "ec2_sqs_role" {
  name = "EC2-SQS-Production-Role"

  assume_role_policy = jsonencode({
    Version = "2012-10-17"

    Statement = [
      {
        Effect = "Allow"

        Principal = {
          Service = "ec2.amazonaws.com"
        }

        Action = "sts:AssumeRole"
      }
    ]
  })
}
```

### B. Create IAM Policy

```hcl
resource "aws_iam_role_policy" "sqs_access" {
  name = "EC2-SQS-Access-Policy"

  role = aws_iam_role.ec2_sqs_role.id

  policy = jsonencode({
    Version = "2012-10-17"

    Statement = [
      {
        Effect = "Allow"

        Action = [
          "sqs:SendMessage",
          "sqs:ReceiveMessage",
          "sqs:DeleteMessage",
          "sqs:GetQueueAttributes",
          "sqs:GetQueueUrl",
          "sqs:ChangeMessageVisibility"
        ]

        Resource = [
          aws_sqs_queue.main.arn
        ]
      }
    ]
  })
}
```

This example allows the EC2 application to send, receive and delete messages from the main queue.

The DLQ is not directly accessible through this policy.

### C. Create Instance Profile

```hcl
resource "aws_iam_instance_profile" "ec2_profile" {
  name = "EC2-SQS-Production-Profile"

  role = aws_iam_role.ec2_sqs_role.name
}
```

Attach this instance profile to your existing EC2 instance.

If the EC2 instance is managed by Terraform, add:

iam_instance_profile = aws_iam_instance_profile.ec2_profile.name

# 22. Terraform – Create SQS Interface VPC Endpoint

If your EC2 instance is running in a private subnet and needs private connectivity to SQS, create an Interface VPC Endpoint.

## File: endpoint.tf

### A. Variables

```hcl
variable "vpc_id" {
  description = "Existing VPC ID"
  type        = string
}

variable "private_subnet_ids" {
  description = "Private subnet IDs"
  type        = list(string)
}

variable "ec2_security_group_id" {
  description = "Existing EC2 security group"
  type        = string
}
```

### B. Endpoint Security Group

```hcl
resource "aws_security_group" "sqs_endpoint" {
  name        = "sqs-endpoint-sg"
  description = "Allow HTTPS from EC2"
  vpc_id      = var.vpc_id

  ingress {
    description     = "HTTPS from EC2"
    from_port       = 443
    to_port         = 443
    protocol        = "tcp"
    security_groups = [var.ec2_security_group_id]
  }

  tags = {
    Name = "sqs-endpoint-sg"
  }
}
```

### C. Create Interface VPC Endpoint

```hcl
resource "aws_vpc_endpoint" "sqs" {
  vpc_id = var.vpc_id

  service_name = "com.amazonaws.${var.aws_region}.sqs"

  vpc_endpoint_type = "Interface"

  subnet_ids = var.private_subnet_ids

  security_group_ids = [
    aws_security_group.sqs_endpoint.id
  ]

  private_dns_enabled = true

  tags = {
    Name = "sqs-interface-endpoint"
  }
}
```

The endpoint creates private network interfaces in the selected subnets.

### D. EC2 Outbound Rule

If the existing EC2 Security Group restricts outbound traffic, add:

```hcl
resource "aws_vpc_security_group_egress_rule" "ec2_to_sqs" {
  security_group_id = var.ec2_security_group_id

  referenced_security_group_id = aws_security_group.sqs_endpoint.id

  ip_protocol = "tcp"

  from_port = 443

  to_port = 443
}
```

Do not add a duplicate rule if outbound HTTPS is already allowed.

# 24. Production-Level Best Practices

For production workloads, follow these recommendations:

1. Always configure a DLQ for important processing queues.
2. Use long polling to reduce unnecessary API calls.
3. Set visibility timeout according to actual processing duration.
4. Ensure message retention meets business requirements.
5. Use idempotent consumer applications.
6. Use batch operations where appropriate.
7. Encrypt messages at rest.
8. Use IAM roles instead of hardcoded AWS credentials.
9. Apply least-privilege permissions.
10. Use Interface VPC Endpoints for private SQS connectivity where required.
11. Monitor queue depth and oldest message age.
12. Alert on DLQ messages.
13. Configure CloudWatch alarms.
14. Use FIFO queues when ordering is a business requirement.
15. Consider S3 for large message payloads.
16. Review queue and KMS costs regularly.
17. Use infrastructure as code for consistent deployments.
18. Test failure scenarios and message redrive procedures.

# 25. Final SQS Revision Summary

| Topic | What to remember |
|---|---|
| SQS | Managed message queuing service |
| Producer | Sends messages |
| Consumer | Receives and processes messages |
| Standard Queue | High throughput, best-effort ordering |
| FIFO Queue | Ordered processing within message groups |
| Visibility Timeout | Time a received message remains invisible |
| Retention | How long messages remain in the queue |
| Delay Queue | Delays initial message availability |
| DLQ | Stores repeatedly failing messages |
| Redrive Policy | Defines when messages move to DLQ |
| Long Polling | Waits for messages, up to 20 seconds |
| Short Polling | Returns immediately |
| MessageGroupId | Maintains FIFO ordering within a group |
| Deduplication | Prevents duplicate FIFO messages within the deduplication interval |
| IAM Role | Authorises applications to access SQS |
| Queue Policy | Controls resource-level access |
| SSE-SQS | SQS-managed encryption |
| SSE-KMS | KMS-based encryption |
| VPC Endpoint | Private access without NAT for SQS |
| CloudWatch | Monitoring and alarms |
| Lambda | Asynchronous message processing |
