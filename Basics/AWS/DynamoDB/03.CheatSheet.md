# Amazon DynamoDB – Complete Cheat Sheet, Terraform Examples, Configuration, Practical Usage and Cost

# SECTION 1 – DynamoDB Fundamentals and Core Concepts

## 1. What is Amazon DynamoDB?

Amazon DynamoDB is a fully managed, serverless NoSQL database service provided by AWS.

It supports:

- Key-value data storage.
- Document data storage.
- High-throughput applications.
- Low-latency reads and writes.
- Automatic scaling.
- Multi-AZ availability.
- Global replication.
- Event-driven architectures.

Common use cases:

- User profiles.
- Shopping carts.
- Orders.
- Session management.
- Gaming leaderboards.
- IoT data.
- Application metadata.
- Product catalogs.
- Event-driven applications.
- Serverless applications.

### DynamoDB vs RDS vs Redshift

| Feature | DynamoDB | RDS/Aurora | Redshift |
|---|---|---|---|
| Database type | NoSQL | Relational | Data warehouse |
| Main workload | OLTP | OLTP | OLAP |
| Data model | Key-value/document | Tables and relations | Analytical tables |
| Schema | Flexible attributes | Defined schema | Defined analytical schema |
| Scaling | Managed horizontal scaling | Instance/storage scaling options | Analytical compute scaling |
| Query language | PartiQL and DynamoDB API | SQL | SQL |
| Joins | No traditional relational joins | Yes | Yes |
| Typical use | High-scale application data | Transactional applications | Analytics |

**Important:** DynamoDB is not a replacement for every relational database. Design your access patterns before designing tables.

## 2. DynamoDB architecture

DynamoDB is an AWS-managed service.

You do not provision:

- Database servers.
- Operating systems.
- Database nodes.
- Storage disks.
- Database subnet groups.

AWS manages the underlying infrastructure.

You configure:

- Table.
- Partition key.
- Sort key.
- Indexes.
- Capacity mode.
- Read/write capacity.
- Encryption.
- Backup.
- TTL.
- Streams.
- Replication.
- IAM permissions.

DynamoDB automatically distributes data across its managed infrastructure.

## 3. DynamoDB data model

DynamoDB uses tables, items, and attributes.

### Table

A table is a collection of items.

Example:

`Orders`

### Item

An item represents one record.

Example:

```json
{
  "PK": "CUSTOMER#1001",
  "SK": "ORDER#5001",
  "orderStatus": "PROCESSING",
  "amount": 150.50,
  "currency": "EUR"
}
```

### Attribute

An attribute is a property of an item.

Examples:

- customerId
- orderStatus
- amount
- currency
- createdAt

### Primary key

The primary key uniquely identifies an item.

It can be:

- Partition key only.
- Partition key + sort key.

### Partition key

Determines the logical partitioning key used by DynamoDB.

Example:

`customerId`

### Sort key

Orders related items within a partition-key value and supports range-based queries.

Example:

`ORDER#5001`

## 4. Primary key types

### A. Simple primary key

Contains only a partition key.

Example:

```text
Table: Users

Partition key: userId
```

Items:

```json
{
  "userId": "U1001",
  "name": "John"
}
```

```json
{
  "userId": "U1002",
  "name": "Mary"
}
```

Terraform:

```hcl
resource "aws_dynamodb_table" "users" {
  name         = "users"
  billing_mode = "PAY_PER_REQUEST"
  hash_key     = "userId"

  attribute {
    name = "userId"
    type = "S"
  }
}
```

### B. Composite primary key

Contains a partition key and sort key.

Example:

```text
Table: Orders

Partition key: customerId
Sort key: orderId
```

This allows multiple orders for one customer.

Terraform:

```hcl
resource "aws_dynamodb_table" "orders" {
  name         = "orders"
  billing_mode = "PAY_PER_REQUEST"

  hash_key  = "customerId"
  range_key = "orderId"

  attribute {
    name = "customerId"
    type = "S"
  }

  attribute {
    name = "orderId"
    type = "S"
  }
}
```

Important:

- Partition key must be unique by itself for a simple primary key.
- For a composite primary key, the combination must be unique.
- A sort key is optional.
- You cannot change a table's primary key after creation. A key redesign generally requires creating a new table and migrating data.

## 5. DynamoDB attribute data types

DynamoDB supports the following attribute types.

| Type | Code | Example |
|---|---|---|
| String | S | `"John"` |
| Number | N | `100` |
| Binary | B | Binary data |
| String Set | SS | `["red","blue"]` |
| Number Set | NS | `[10,20]` |
| Binary Set | BS | Binary values |
| Boolean | BOOL | `true` |
| Null | NULL | `true` |
| List | L | Array of values |
| Map | M | Nested object |

Example item:

```json
{
  "userId": "U1001",
  "age": 30,
  "active": true,
  "address": {
    "city": "Dublin",
    "country": "Ireland"
  },
  "orders": [
    "O1001",
    "O1002"
  ]
}
```

Important:

- DynamoDB is schemaless for non-key attributes.
- Key attributes have defined types.
- A table key cannot change from String to Number after table creation.
- Empty string and binary values are supported for non-key attributes, but key attributes cannot be empty.
- Numbers are stored as numeric values, not floating-point application strings.
- DynamoDB supports nested lists and maps.

## 6. Partitioning and partition key design

DynamoDB distributes data based on partition-key values.

Good partition keys distribute activity across many values.

Examples:

- userId
- orderId
- deviceId
- tenantId, if traffic is sufficiently distributed.

Poor partition keys can create hot partitions.

Example of a potentially poor partition key:

`status = ACTIVE`

If millions of requests use the same value, requests can concentrate on a limited number of partition-key values.

Better approaches depend on the access pattern.

Examples:

- Customer-specific records: `CUSTOMER#1001`
- Device-specific records: `DEVICE#5001`
- Sharded time-series records: `DEVICE#5001#SHARD#03`

Important:

- High-cardinality partition keys often help distribute traffic.
- High cardinality alone does not guarantee even traffic.
- A single very popular partition-key value can still become hot.
- Monitor partition-level throttling and access patterns.

## 7. Sort key design

Sort keys help organize related items.

Example:

```text
PK = CUSTOMER#1001
SK = PROFILE

PK = CUSTOMER#1001
SK = ORDER#1001

PK = CUSTOMER#1001
SK = ORDER#1002

PK = CUSTOMER#1001
SK = ADDRESS#HOME
```

This is a single-table design pattern.

You can query related records using:

- Exact sort-key match.
- Begins_with.
- Between.
- Greater-than.
- Less-than.
- Greater-than-or-equal.
- Less-than-or-equal.

Example:

Retrieve all orders for one customer using the prefix `ORDER#`.

## 8. Single-table and multi-table design

### Single-table design

Multiple entity types are stored in one table.

Example:

| PK | SK | Entity |
|---|---|---|
| CUSTOMER#1001 | PROFILE | Customer |
| CUSTOMER#1001 | ORDER#1001 | Order |
| CUSTOMER#1001 | ORDER#1002 | Order |
| CUSTOMER#1001 | ADDRESS#HOME | Address |

Advantages:

- Related data can be retrieved through one query.
- Can reduce request count.
- Supports efficient access patterns.
- Useful for high-performance applications.

Disadvantages:

- Requires careful key design.
- More complex to understand.
- Entity types may need different indexes and attribute conventions.

### Multi-table design

Separate tables for entities.

Examples:

- Users table.
- Orders table.
- Products table.
- Payments table.

Advantages:

- Simpler conceptual organization.
- Independent access and lifecycle.
- Often easier for teams learning DynamoDB.

Disadvantages:

- May require multiple requests to assemble related data.
- Does not provide relational joins.
- Cross-table transactions require explicit transactional APIs.

**Recommendation:** Start with clear access patterns. Use single-table design when it provides a measurable benefit, not merely because it is a DynamoDB best practice.

# SECTION 2 – DynamoDB Configuration and Query Operations

## 9. Terraform – Basic DynamoDB table

```hcl
resource "aws_dynamodb_table" "users" {
  name         = "users"
  billing_mode = "PAY_PER_REQUEST"

  hash_key = "userId"

  attribute {
    name = "userId"
    type = "S"
  }

  tags = {
    Environment = "production"
    Application = "user-service"
  }
}
```

Important parameters:

| Parameter | Purpose |
|---|---|
| `name` | Table name |
| `billing_mode` | PAY_PER_REQUEST or PROVISIONED |
| `hash_key` | Partition key |
| `range_key` | Sort key |
| `attribute` | Key/index attribute definitions |
| `tags` | Resource tags |
| `table_class` | STANDARD or STANDARD_INFREQUENT_ACCESS |
| `deletion_protection_enabled` | Prevents accidental deletion |
| `point_in_time_recovery` | Point-in-time recovery configuration |
| `server_side_encryption` | Encryption configuration |
| `stream_enabled` | Enables DynamoDB Streams |
| `stream_view_type` | Stream record contents |
| `ttl` | TTL configuration |
| `global_secondary_index` | GSI definitions |
| `local_secondary_index` | LSI definitions |
| `replica` | Global table replicas |
| `import_table` | Supported import configuration |

Important: Terraform's `attribute` blocks should normally define only attributes used by the table's primary key and index keys. You do not define every normal item attribute in Terraform.

## 10. Capacity modes

DynamoDB supports two main billing modes.

### A. On-demand capacity

Terraform:

```hcl
resource "aws_dynamodb_table" "orders" {
  name         = "orders"
  billing_mode = "PAY_PER_REQUEST"

  hash_key  = "customerId"
  range_key = "orderId"

  attribute {
    name = "customerId"
    type = "S"
  }

  attribute {
    name = "orderId"
    type = "S"
  }
}
```

Characteristics:

- No manual read/write capacity provisioning.
- Automatically accommodates traffic within service limits and scaling behavior.
- Pay for read and write request units.
- Suitable for unpredictable or variable workloads.

Use cases:

- New applications.
- Variable traffic.
- Development environments.
- Workloads with unpredictable request patterns.

### B. Provisioned capacity

Terraform:

```hcl
resource "aws_dynamodb_table" "orders" {
  name         = "orders"
  billing_mode = "PROVISIONED"

  read_capacity  = 10
  write_capacity = 5

  hash_key  = "customerId"
  range_key = "orderId"

  attribute {
    name = "customerId"
    type = "S"
  }

  attribute {
    name = "orderId"
    type = "S"
  }
}
```

Characteristics:

- You specify read capacity units.
- You specify write capacity units.
- You pay for provisioned capacity.
- Auto Scaling can adjust capacity.
- Suitable for predictable workloads.

### Read Capacity Unit (RCU)

One RCU provides:

- One strongly consistent read per second for an item up to 4 KB.
- Two eventually consistent reads per second for an item up to 4 KB.

### Write Capacity Unit (WCU)

One WCU provides:

- One write per second for an item up to 1 KB.

Transactional reads and writes consume more capacity than their nontransactional equivalents.

Important:

- Item size affects capacity consumption.
- Strongly consistent reads consume twice the capacity of eventually consistent reads for the same item size.
- Eventually consistent reads are not supported on global secondary indexes.
- Eventually consistent reads are the default for normal reads.
- A write that updates a large item can consume more capacity than a small item update.

## 11. DynamoDB Auto Scaling

Auto Scaling adjusts provisioned capacity based on utilization.

Important settings:

- Minimum capacity.
- Maximum capacity.
- Target utilization.
- Scaling policy.
- Read or write dimension.

Terraform example:

```hcl
resource "aws_appautoscaling_target" "orders_read" {
  max_capacity       = 100
  min_capacity       = 5
  resource_id        = "table/${aws_dynamodb_table.orders.name}"
  scalable_dimension = "dynamodb:table:ReadCapacityUnits"
  service_namespace  = "dynamodb"
}

resource "aws_appautoscaling_policy" "orders_read" {
  name               = "orders-read-scaling"
  policy_type        = "TargetTrackingScaling"
  resource_id        = aws_appautoscaling_target.orders_read.resource_id
  scalable_dimension = aws_appautoscaling_target.orders_read.scalable_dimension
  service_namespace  = aws_appautoscaling_target.orders_read.service_namespace

  target_tracking_scaling_policy_configuration {
    target_value       = 70
    scale_in_cooldown  = 60
    scale_out_cooldown = 60

    predefined_metric_specification {
      predefined_metric_type = "DynamoDBReadCapacityUtilization"
    }
  }
}
```

Create a separate scaling target and policy for write capacity.

For a GSI, configure scaling for the index separately.

Important:

- Auto Scaling is for provisioned mode.
- It is not a replacement for correct partition-key design.
- Scaling may not react immediately to sudden spikes.
- Configure minimum and maximum values based on business requirements.

## 12. Secondary indexes

Indexes allow queries using alternate access patterns.

Two types:

- Global Secondary Index (GSI).
- Local Secondary Index (LSI).

### A. Global Secondary Index (GSI)

A GSI can have a different partition key and sort key from the base table.

Example:

Base table:

- PK: customerId
- SK: orderId

GSI:

- GSI partition key: orderStatus
- GSI sort key: createdAt

This allows queries such as:

Find orders with status `PENDING`, sorted by creation time.

Terraform:

```hcl
resource "aws_dynamodb_table" "orders" {
  name         = "orders"
  billing_mode = "PAY_PER_REQUEST"

  hash_key  = "customerId"
  range_key = "orderId"

  attribute {
    name = "customerId"
    type = "S"
  }

  attribute {
    name = "orderId"
    type = "S"
  }

  attribute {
    name = "orderStatus"
    type = "S"
  }

  attribute {
    name = "createdAt"
    type = "S"
  }

  global_secondary_index {
    name            = "status-createdAt-index"
    hash_key        = "orderStatus"
    range_key       = "createdAt"
    projection_type = "ALL"
  }
}
```

GSI projection types:

**KEYS_ONLY**

Stores index keys and base-table primary-key attributes.

**INCLUDE**

Stores keys plus selected additional attributes.

**ALL**

Stores all base-table attributes.

Important:

- A GSI is eventually consistent.
- A GSI can have a different partition key and sort key.
- A GSI can be created after table creation.
- A GSI has separate capacity configuration in provisioned mode.
- A GSI consumes storage.
- GSI writes consume capacity.
- GSI queries cannot use strongly consistent reads.

### B. Local Secondary Index (LSI)

An LSI uses the same partition key as the base table but a different sort key.

Example:

Base table:

- PK: customerId
- SK: orderId

LSI:

- PK: customerId
- LSI SK: orderDate

Terraform:

```hcl
resource "aws_dynamodb_table" "customer_orders" {
  name         = "customer-orders"
  billing_mode = "PAY_PER_REQUEST"

  hash_key  = "customerId"
  range_key = "orderId"

  attribute {
    name = "customerId"
    type = "S"
  }

  attribute {
    name = "orderId"
    type = "S"
  }

  attribute {
    name = "orderDate"
    type = "S"
  }

  local_secondary_index {
    name            = "order-date-index"
    range_key       = "orderDate"
    projection_type = "ALL"
  }
}
```

Important:

- An LSI must be created when the table is created.
- An LSI cannot be added to an existing table.
- It uses the same partition key as the base table.
- It supports strongly consistent reads.
- The item collection size limit is 10 GB per partition-key value when LSIs are present.
- An LSI has no separate provisioned capacity setting.

### GSI vs LSI

| Feature | GSI | LSI |
|---|---|---|
| Partition key | Can differ | Same as table |
| Sort key | Can differ | Different |
| Create later | Yes | No |
| Strong consistency | No | Yes |
| Separate provisioned capacity | Yes | No |
| 10 GB item collection restriction | No LSI restriction | Applies |
| Main purpose | Alternate query pattern | Alternate sort order within same partition |

## 13. Query vs Scan

### Query

Query retrieves items using a partition-key value.

It can optionally apply sort-key conditions.

Example:

```text
PK = CUSTOMER#1001
SK begins_with ORDER#
```

Terraform table configuration does not define query commands; the application invokes DynamoDB APIs.

For example, in an AWS SDK application, a Query operation uses:

- TableName.
- KeyConditionExpression.
- ExpressionAttributeNames.
- ExpressionAttributeValues.
- FilterExpression, optionally.
- ProjectionExpression, optionally.
- IndexName, optionally.
- ScanIndexForward.
- ConsistentRead, where supported.
- Limit.
- ExclusiveStartKey.

### Scan

Scan reads items across a table or index.

Common parameters:

- TableName.
- IndexName.
- FilterExpression.
- ProjectionExpression.
- Limit.
- ExclusiveStartKey.
- ConsistentRead.
- Segment.
- TotalSegments.

Important:

- Query is generally preferable for predictable access patterns.
- Scan can read large portions of a table.
- FilterExpression is applied after the items are read.
- A filter does not reduce the read capacity consumed for the scanned data.
- Use pagination for large results.
- A Query or Scan response can be paginated using LastEvaluatedKey.

## 14. Read consistency

DynamoDB supports:

### Eventually consistent reads

- Default for base-table reads.
- May return slightly stale data immediately after a write.
- Consume less read capacity than strongly consistent reads.

### Strongly consistent reads

- Return the latest successful write for supported reads.
- Consume more capacity.
- Supported for base tables and LSIs.
- Not supported for GSIs or global table replicas in the same manner as local strongly consistent reads.

### Transactional reads

- Provide transactional read behavior.
- Consume additional read capacity.
- Use when multiple items need transactionally consistent handling.

## 15. Conditional writes

Conditional writes ensure an operation happens only when a condition is satisfied.

Examples:

- Create item only if it does not exist.
- Update only if the current status is PENDING.
- Delete only if the owner matches.
- Update only if a version number matches.

Common API parameters:

- ConditionExpression.
- ExpressionAttributeNames.
- ExpressionAttributeValues.
- ReturnValuesOnConditionCheckFailure where supported.

Terraform example for a table with version attribute:

```hcl
resource "aws_dynamodb_table" "inventory" {
  name         = "inventory"
  billing_mode = "PAY_PER_REQUEST"

  hash_key = "productId"

  attribute {
    name = "productId"
    type = "S"
  }
}
```

Application example concept:

```text
Update product quantity only if quantity >= requestedQuantity.
```

The condition is sent in the application API request, not configured as a permanent table-wide Terraform setting.

## 16. TTL – Time to Live

TTL automatically deletes expired items.

Common use cases:

- Sessions.
- Temporary tokens.
- Temporary records.
- Expiring cache entries.
- Short-lived application data.

Terraform:

```hcl
resource "aws_dynamodb_table" "sessions" {
  name         = "sessions"
  billing_mode = "PAY_PER_REQUEST"

  hash_key = "sessionId"

  attribute {
    name = "sessionId"
    type = "S"
  }

  ttl {
    attribute_name = "expiresAt"
    enabled        = true
  }
}
```

The application writes a Unix epoch timestamp in seconds into `expiresAt`.

Example:

```json
{
  "sessionId": "SESSION#1001",
  "expiresAt": 1793558400
}
```

Important:

- TTL deletion is asynchronous.
- Expired items can remain readable for some time.
- Do not rely on TTL for precise deletion timing.
- TTL deletes do not behave like immediate synchronous deletes.
- TTL deletion can appear in DynamoDB Streams.
- Global tables replicate TTL deletions, and replicated writes can have billing implications.

## 17. DynamoDB Streams

Streams capture item-level changes.

Stream view types:

- KEYS_ONLY
- NEW_IMAGE
- OLD_IMAGE
- NEW_AND_OLD_IMAGES

Terraform:

```hcl
resource "aws_dynamodb_table" "orders_stream" {
  name         = "orders-stream"
  billing_mode = "PAY_PER_REQUEST"

  hash_key  = "customerId"
  range_key = "orderId"

  attribute {
    name = "customerId"
    type = "S"
  }

  attribute {
    name = "orderId"
    type = "S"
  }

  stream_enabled   = true
  stream_view_type = "NEW_AND_OLD_IMAGES"
}
```

Use cases:

- Trigger Lambda functions.
- Synchronize search indexes.
- Create audit workflows.
- Send notifications.
- Update downstream systems.

Important:

- Streams retain records for 24 hours.
- Stream records are ordered by item key within the applicable stream shard.
- Consumers must handle retries and duplicate processing.
- Lambda event source mappings provide retry and batching controls.
- DynamoDB Streams and Kinesis Data Streams are different services and have different capabilities.

## 18. DynamoDB Streams + Lambda Terraform

Assumes the Lambda function and its execution role already exist.

```hcl
resource "aws_lambda_event_source_mapping" "orders_stream" {
  event_source_arn  = aws_dynamodb_table.orders_stream.stream_arn
  function_name     = var.lambda_function_arn
  starting_position = "LATEST"

  batch_size                         = 100
  maximum_batching_window_in_seconds = 5

  bisect_batch_on_function_error = true
  maximum_retry_attempts         = 3

  function_response_types = [
    "ReportBatchItemFailures"
  ]
}
```

Important:

- Lambda's execution role needs appropriate stream permissions.
- The Lambda function must be idempotent.
- Configure a failure destination or other recovery mechanism where appropriate.
- Batch size and batching window affect latency and throughput.
- Review shard concurrency and retry behavior.

## 19. DynamoDB transactions

DynamoDB supports transactional operations.

Two main operations:

### TransactWriteItems

Used for atomic writes across multiple items and tables.

Possible actions:

- Put.
- Update.
- Delete.
- ConditionCheck.

### TransactGetItems

Used to read multiple items transactionally.

Use cases:

- Transfer funds between accounts.
- Update order and inventory together.
- Maintain consistency across related records.

Important:

- Transactions are ACID within supported transaction boundaries.
- Transactions consume additional capacity.
- Transaction size and item limits apply.
- A transaction cannot contain multiple operations targeting the same item.
- Use idempotency tokens where appropriate for transaction retries.

Terraform example table:

```hcl
resource "aws_dynamodb_table" "accounts" {
  name         = "accounts"
  billing_mode = "PAY_PER_REQUEST"

  hash_key = "accountId"

  attribute {
    name = "accountId"
    type = "S"
  }
}
```

The transaction itself is executed by the application using the DynamoDB SDK. It is not a persistent table configuration.

## 20. Conditional writes and optimistic locking

Optimistic locking prevents overwriting newer changes.

Typical design:

- Each item contains a `version` attribute.
- Read the item.
- Update the item only if the stored version matches the version previously read.
- Increment the version on success.

Example:

```text
ConditionExpression:
version = :expectedVersion

UpdateExpression:
SET version = version + :one, status = :newStatus
```

This is useful for:

- Inventory.
- Order status.
- Shared records.
- Concurrent user updates.

# SECTION 3 – Security, Networking, Integrations and Production Configuration

## 21. DynamoDB encryption

DynamoDB encrypts data at rest.

Common key options:

- AWS owned key.
- AWS managed KMS key.
- Customer managed KMS key.

Terraform with a customer managed KMS key:

```hcl
resource "aws_dynamodb_table" "secure_orders" {
  name         = "secure-orders"
  billing_mode = "PAY_PER_REQUEST"

  hash_key = "orderId"

  attribute {
    name = "orderId"
    type = "S"
  }

  server_side_encryption {
    enabled     = true
    kms_key_arn = var.dynamodb_kms_key_arn
  }
}
```

Important:

- KMS key policies and IAM permissions must allow the required access.
- Encryption at rest does not replace TLS in transit.
- KMS key deletion or disabling can affect access to encrypted data.
- Consider KMS request charges and key lifecycle.

## 22. DynamoDB IAM permissions

IAM controls which principals can perform DynamoDB operations.

Common actions:

### Read

- `dynamodb:GetItem`
- `dynamodb:BatchGetItem`
- `dynamodb:Query`
- `dynamodb:Scan`
- `dynamodb:DescribeTable`

### Write

- `dynamodb:PutItem`
- `dynamodb:UpdateItem`
- `dynamodb:DeleteItem`
- `dynamodb:BatchWriteItem`

### Transactions

- `dynamodb:TransactGetItems`
- `dynamodb:TransactWriteItems`

### Table management

- `dynamodb:CreateTable`
- `dynamodb:DeleteTable`
- `dynamodb:UpdateTable`
- `dynamodb:DescribeTable`

### Streams

- `dynamodb:DescribeStream`
- `dynamodb:GetRecords`
- `dynamodb:GetShardIterator`
- `dynamodb:ListStreams`

Use least-privilege permissions.

Terraform example:

```hcl
resource "aws_iam_policy" "orders_read_write" {
  name = "orders-read-write"

  policy = jsonencode({
    Version = "2012-10-17"

    Statement = [
      {
        Effect = "Allow"

        Action = [
          "dynamodb:GetItem",
          "dynamodb:PutItem",
          "dynamodb:UpdateItem",
          "dynamodb:Query"
        ]

        Resource = [
          aws_dynamodb_table.orders.arn,
          "${aws_dynamodb_table.orders.arn}/index/*"
        ]
      }
    ]
  })
}
```

Attach this policy to the application's IAM role using an appropriate Terraform role-policy attachment.

Important:

- A Query against a GSI requires permission for the index ARN.
- Avoid granting Scan unless required.
- Do not grant table deletion permissions to normal application roles.
- Use IAM conditions and resource restrictions where appropriate.

## 23. DynamoDB VPC connectivity

DynamoDB is an AWS-managed service and does not run inside your VPC.

Applications can access it using:

- Public AWS service endpoints.
- NAT Gateway or other internet egress.
- DynamoDB Gateway VPC Endpoint.
- Supported private networking patterns.

### DynamoDB Gateway VPC Endpoint

A gateway endpoint provides private connectivity to DynamoDB from a VPC without requiring NAT Gateway or an internet gateway for that traffic.

Terraform:

```hcl
resource "aws_vpc_endpoint" "dynamodb" {
  vpc_id            = var.vpc_id
  service_name      = "com.amazonaws.${var.region}.dynamodb"
  vpc_endpoint_type = "Gateway"

  route_table_ids = var.private_route_table_ids

  tags = {
    Name = "dynamodb-gateway-endpoint"
  }
}
```

Important:

- Gateway endpoint routes are added to the selected route tables.
- Gateway endpoints do not use security groups.
- You can attach an endpoint policy.
- IAM policies still apply.
- DynamoDB table resource policies can also restrict access.
- The gateway endpoint is generally available without an hourly endpoint charge.
- Cross-Region access and some special endpoint scenarios require separate consideration.

### Endpoint policy example

```hcl
resource "aws_vpc_endpoint" "dynamodb_restricted" {
  vpc_id            = var.vpc_id
  service_name      = "com.amazonaws.${var.region}.dynamodb"
  vpc_endpoint_type = "Gateway"

  route_table_ids = var.private_route_table_ids

  policy = jsonencode({
    Version = "2012-10-17"

    Statement = [
      {
        Effect = "Allow"

        Principal = "*"

        Action = [
          "dynamodb:GetItem",
          "dynamodb:PutItem",
          "dynamodb:UpdateItem",
          "dynamodb:Query"
        ]

          var.orders_table_arn,

        ]
      }
    ]
  })
}
```

Important: The endpoint policy is an additional access control layer. It does not grant permissions that IAM or the table's resource policy otherwise denies.

## 24. DynamoDB global tables

Global tables replicate DynamoDB data across AWS Regions.

Use cases:

- Multi-Region applications.
- Low-latency regional access.
- Disaster recovery.
- Regional availability requirements.

Terraform example:

```hcl
resource "aws_dynamodb_table" "global_orders" {
  name         = "global-orders"
  billing_mode = "PAY_PER_REQUEST"

  hash_key = "orderId"

  attribute {
    name = "orderId"
    type = "S"
  }

  stream_view_type = "NEW_AND_OLD_IMAGES"

    region_name = "eu-west-1"
  }

    region_name = "us-east-1"
  }
}
```

Important:

- Replication increases write and storage costs.

## 25. DynamoDB backups and point-in-time recovery

Two important backup mechanisms:

### On-demand backups

Create explicit backups when needed.

Useful before:

- Major application releases.
- Data migrations.
- Risky schema or data changes.
- Recovery testing.

### Point-in-time recovery (PITR)

Allows restoration to a selected point within the supported recovery window.

Terraform:

```hcl
resource "aws_dynamodb_table" "orders_backup" {
  name         = "orders-backup"
  billing_mode = "PAY_PER_REQUEST"

  hash_key = "orderId"

  attribute {
    name = "orderId"
    type = "S"
  }

  point_in_time_recovery {
    enabled                 = true
    recovery_period_in_days = 35
  }
}
```

Important:

- PITR is continuous backup functionality.
- Restoration creates a new table.
- It does not restore data into the original table in place.
- Validate recovery procedures.
- Backup storage and restore operations can have separate costs.

### On-demand backup Terraform

```hcl
resource "aws_backup_vault" "dynamodb" {
  name = "dynamodb-backup-vault"
}

resource "aws_backup_plan" "dynamodb" {
  name = "dynamodb-backup-plan"

  rule {
    rule_name         = "daily-backup"
    target_vault_name = aws_backup_vault.dynamodb.name
    schedule          = "cron(0 2 * * ? *)"

    lifecycle {
      delete_after = 35
    }
  }
}

resource "aws_backup_selection" "dynamodb" {
  name         = "dynamodb-selection"
  plan_id      = aws_backup_plan.dynamodb.id
  iam_role_arn = var.backup_service_role_arn

  resources = [
    aws_dynamodb_table.orders_backup.arn
  ]
}
```

The backup service role must have the required AWS Backup permissions and trust relationship.

## 26. DynamoDB point-in-time recovery vs AWS Backup

| Feature | PITR | AWS Backup |
|---|---|---|
| Continuous recovery | Yes | Depends on configured backup plan |
| Scheduled backups | No, not its main purpose | Yes |
| Central backup management | Limited | Yes |
| Cross-account backup workflows | Depends on configuration | Supported workflows |
| Cross-Region backup | Different configuration | Supported workflows |
| Restore | New table | New table |

Choose based on recovery objectives and governance requirements. They can be used together.

## 39. Read and write capacity calculations

### Read capacity example

Suppose:

- Item size: 4 KB.
- Strongly consistent read.
- 100 reads per second.

One strongly consistent read of an item up to 4 KB consumes 1 RCU.

Therefore:

`100 reads/second × 1 RCU = 100 RCU`

For eventually consistent reads:

`100 reads/second × 0.5 RCU = 50 RCU`

### Write capacity example

Suppose:

- Item size: 1 KB.
- 100 writes per second.

One write of an item up to 1 KB consumes 1 WCU.

Therefore:

`100 writes/second × 1 WCU = 100 WCU`

### Larger item example

Suppose:

- Item size: 3 KB.
- 100 writes per second.

A write is rounded up to the next 1 KB boundary.

Therefore:

`100 × 3 WCU = 300 WCU`

Important:

- Read units are calculated in 4 KB blocks.
- Write units are calculated in 1 KB blocks.
- Transactional operations consume additional capacity.
- Item size includes attribute names as well as values.
- Index maintenance adds write capacity consumption.

## 41. Important DynamoDB limits and exceptions

Always check current AWS Service Quotas.

Important limits and design rules include:

- Maximum item size: 400 KB.
- Partition key and sort key have supported data-type and size constraints.
- A table can have a maximum of 20 GSIs and 5 LSIs.
- An LSI must be created with the table.
- An LSI item collection has a 10 GB size limit per partition-key value.
- A GSI is eventually consistent.
- TTL deletion is asynchronous.
- Streams retain records for 24 hours.
- Scan and Query operations paginate results.
- A single Query or Scan response is limited to 1 MB of returned data before pagination.
- BatchGetItem supports up to 100 items per request, subject to the aggregate response size limit.
- BatchWriteItem supports up to 25 put/delete operations per request, subject to request size limits.
- Batch operations can return unprocessed items that must be retried.
- Transactions have limits on action count and aggregate item size.
- Global tables have Region and feature compatibility requirements.
- A table's primary key cannot be changed after creation.
- Attribute definitions in the table schema apply to key attributes, not every item field.
- DynamoDB does not support traditional relational joins.
- FilterExpression does not reduce the read capacity consumed by the underlying Query or Scan.
- A successful write does not mean every GSI or replica is immediately updated.
- Hot partition keys can cause throttling even when overall table capacity appears sufficient.
- Provisioned capacity and on-demand scaling have service quotas.
- TTL must use a Number containing Unix epoch time in seconds.

## 42. Common DynamoDB errors

### ProvisionedThroughputExceededException

Cause:

- Capacity exceeded.
- Hot partition.
- GSI capacity shortage.

Solutions:

- Retry with exponential backoff and jitter.
- Review partition-key distribution.
- Increase provisioned capacity or use suitable on-demand capacity.
- Review GSI capacity.

### ConditionalCheckFailedException

Cause:

- Condition expression evaluated to false.

Solution:

- Re-read the item.
- Check expected version or state.
- Handle conflict in application logic.

### ResourceNotFoundException

Cause:

- Table or index does not exist.
- Wrong Region.
- Wrong account.
- Incorrect resource name.

### ValidationException

Cause:

- Incorrect key.
- Invalid expression.
- Wrong data type.
- Invalid request format.

Solution:

- Verify key schema.
- Verify expression attribute names and values.
- Check data types.

### TransactionCanceledException

Possible causes:

- Condition failure.
- Transaction conflict.
- Capacity issue.
- Invalid operation combination.

Solution:

- Inspect cancellation reasons where available.
- Retry transient failures safely.
- Use idempotency.
- Review transaction design.

**Core takeaway:** DynamoDB is designed around access patterns, not relational joins. The most important design decisions are the partition key, sort key, indexes, capacity mode, and item structure. For production, combine efficient key design with least-privilege IAM, encryption, backups, monitoring, retry handling, and a clear cost model. Terraform should manage the persistent infrastructure configuration, while the application code performs the actual item reads, writes, queries, and transactions.
