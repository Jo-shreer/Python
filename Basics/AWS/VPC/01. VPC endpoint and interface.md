# AWS VPC Endpoints – Complete Interview Cheat Sheet

## 1. What is a VPC Endpoint?

A VPC Endpoint allows resources inside an Amazon VPC to privately connect to supported AWS services without requiring an Internet Gateway, NAT Gateway, VPN or public internet connection for that service.

### Example scenario

Imagine:
- FastAPI application running on EC2 in a private subnet.
- The application needs to upload files to S3.
- The application also needs to retrieve credentials from Secrets Manager.
- It needs to send messages to SQS.

Without VPC endpoints, private EC2 instances commonly access public AWS service endpoints through a NAT Gateway.

With VPC endpoints, they can communicate with supported AWS services through private AWS network connectivity.

### Why do we use VPC endpoints?

1. Avoid sending supported AWS service traffic through the public internet.
2. Reduce NAT Gateway data-processing costs for traffic that can use endpoints.
3. Keep service communication private.
4. Restrict access using endpoint policies.
5. Improve network architecture and security.
6. Allow private subnets to access supported AWS services without requiring NAT for those destinations.

**Interview answer:**

A VPC endpoint provides private connectivity between resources in a VPC and supported AWS services. It helps avoid NAT or internet routing for supported destinations and allows us to control access using endpoint policies and other AWS security policies.

# 2. Types of VPC Endpoints

The two main types to understand are:

1. Gateway endpoint
2. Interface endpoint

There are also specialized endpoint types, including Gateway Load Balancer, Resource and Service Network endpoints.

## 2.1 Gateway Endpoint

A Gateway endpoint provides private connectivity to:

- Amazon S3
- Amazon DynamoDB

It works by adding a route to the route tables selected when creating the endpoint.

### How does it work?

Suppose:
- EC2 is running in a private subnet.
- The subnet uses route table `rtb-private`.
- The EC2 application uploads a file to S3.

The application calls S3 using the normal AWS SDK.

The route table contains a route for the S3 managed prefix list. Traffic matching that destination is routed to the Gateway endpoint.

### Traffic flow

```text
FastAPI application
        |
        v
EC2 in private subnet
        |
        v
S3 DNS hostname
        |
        v
Route table lookup
        |
        v
S3 prefix-list route
        |
        v
S3 Gateway endpoint
        |
        v
Amazon S3
```

Important:

- No endpoint network interface (ENI) is created.
- No endpoint private IP is assigned.
- No endpoint security group is required.
- No endpoint hourly charge.
- No endpoint data-processing charge.
- Route tables determine which subnets use the endpoint.

### Example route table

Before endpoint:

| Destination | Target |
|---|---|
| `10.0.0.0/16` | local |
| `0.0.0.0/0` | NAT Gateway |

After endpoint:

| Destination | Target |
|---|---|
| `10.0.0.0/16` | local |
| S3 managed prefix list | S3 Gateway endpoint |
| `0.0.0.0/0` | NAT Gateway |

The more-specific S3 prefix-list route takes precedence over the default route for matching S3 destinations.

The NAT Gateway route remains for other destinations.

# 3. Gateway Endpoint – Terraform Configuration

## 3.1 Basic Terraform configuration

```hcl
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
}

provider "aws" {
  region = "eu-west-1"
}

variable "vpc_id" {
  type = string
}

variable "private_route_table_ids" {
  type = list(string)
}

resource "aws_vpc_endpoint" "s3" {

  vpc_id = var.vpc_id

  service_name = "com.amazonaws.eu-west-1.s3"

  vpc_endpoint_type = "Gateway"

  route_table_ids = var.private_route_table_ids

  tags = {
    Name        = "private-s3-endpoint"
    Environment = "dev"
  }
}
```

Example `terraform.tfvars`:

```hcl
vpc_id = "vpc-123456"

private_route_table_ids = [
  "rtb-123456",
  "rtb-789012"
]
```

Deploy:

```bash
terraform init
terraform validate
terraform plan
terraform apply
```

## 3.2 Explain every Terraform parameter

### `resource`

```hcl
resource "aws_vpc_endpoint" "s3"
```

- `aws_vpc_endpoint` is the Terraform resource type.
- `s3` is the local Terraform resource name.
- It is how other Terraform resources refer to this endpoint.

### `vpc_id`

```hcl
vpc_id = var.vpc_id
```

Specifies the VPC in which the endpoint is created.

Example:

```hcl
vpc_id = "vpc-123456"
```

Required.

### `service_name`

```hcl
service_name = "com.amazonaws.eu-west-1.s3"
```

Identifies the AWS service to which the endpoint connects.

General pattern:

```text
com.amazonaws.<region>.<service>
```

Examples:

```text
com.amazonaws.eu-west-1.s3
com.amazonaws.eu-west-1.dynamodb
com.amazonaws.eu-west-1.secretsmanager
com.amazonaws.eu-west-1.sqs
```

The exact service name must be available for the selected Region and endpoint type.

### `vpc_endpoint_type`

```hcl
vpc_endpoint_type = "Gateway"
```

Defines the type of endpoint.

Common values:

```text
Gateway
Interface
GatewayLoadBalancer
Resource
ServiceNetwork
```

For this example, we use `Gateway`.

Terraform defaults to `Gateway` if this argument is omitted.

### `route_table_ids`

```hcl
route_table_ids = [
  "rtb-123456",
  "rtb-789012"
]
```

Specifies which route tables receive the Gateway endpoint route.

Important:
- Applicable to Gateway endpoints.
- Specify route table IDs, not subnet IDs.
- Every subnet that needs to use the endpoint must use an associated route table.
- You can associate multiple route tables.

### `tags`

```hcl
tags = {
  Name        = "private-s3-endpoint"
  Environment = "dev"
}
```

Used for identification, cost allocation and resource management.

# 4. Gateway Endpoint – Endpoint Policy

An endpoint policy controls which requests are permitted through the endpoint.

Example: allow access to one S3 bucket.

```hcl
resource "aws_vpc_endpoint" "s3" {

  vpc_id            = var.vpc_id
  service_name      = "com.amazonaws.eu-west-1.s3"
  vpc_endpoint_type = "Gateway"

  route_table_ids = var.private_route_table_ids

  policy = jsonencode({
    Version = "2012-10-17"

    Statement = [
      {
        Effect = "Allow"

        Principal = "*"

        Action = [
          "s3:GetObject",
          "s3:PutObject"
        ]

        Resource = [
          "arn:aws:s3:::my-private-bucket/*"
        ]
      }
    ]
  })
}
```

This policy permits:
- Reading objects.
- Uploading objects.
- Only under the specified bucket object ARN.

It does not independently grant the EC2 instance permission to access S3.

## Three important authorization checks

| Policy | Purpose |
|---|---|
| IAM role policy | Does the EC2 application identity have permission? |
| VPC endpoint policy | Is the operation allowed through this endpoint? |
| S3 bucket policy | Does the bucket permit this request? |

All applicable authorization policies must permit the request.

An explicit deny overrides an allow.

### Restrict bucket access to a particular VPC endpoint

An S3 bucket policy can use:

```json
{
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:*",
  "Resource": [
    "arn:aws:s3:::my-private-bucket",
    "arn:aws:s3:::my-private-bucket/*"
  ],
  "Condition": {
    "StringNotEquals": {
      "aws:SourceVpce": "vpce-123456"
    }
  }
}
```

This is a deny statement for requests that do not use the specified endpoint.

Be careful: this can also block legitimate access from administrators, CI/CD pipelines or other applications that do not use that endpoint. Test the policy before deploying it.

# 5. Gateway Endpoint – Services and Limitations

Gateway endpoints are supported for:

| AWS service | Gateway endpoint supported? |
|---|---|
| Amazon S3 | Yes |
| Amazon DynamoDB | Yes |
| Amazon SQS | No |
| Amazon SNS | No |
| Secrets Manager | No |
| KMS | No |
| CloudWatch Logs | No |
| ECR | No |
| Lambda API | No |
| STS | No |

Important: S3 and DynamoDB support both Gateway and Interface endpoints.

For normal traffic from resources inside the same VPC to S3 or DynamoDB, Gateway endpoints are often the simplest and most economical choice.

Gateway endpoints are not directly accessible from on-premises networks through VPN or Direct Connect, or from other VPCs through VPC peering.

# 6. Interface Endpoint

An Interface endpoint provides private connectivity using AWS PrivateLink.

It creates one or more Elastic Network Interfaces (ENIs) in the subnets you select.

Each ENI receives a private IP address.

Unlike Gateway endpoints, Interface endpoints:
- Use ENIs.
- Have private IP addresses.
- Use security groups.
- Can use private DNS.
- Are billed hourly and for data processing.
- Support many AWS services.

### Example services

- Amazon SQS
- Amazon SNS
- AWS Secrets Manager
- AWS Key Management Service (KMS)
- Amazon CloudWatch
- CloudWatch Logs
- Amazon ECR API
- Amazon ECR Docker Registry
- AWS Systems Manager
- AWS STS
- AWS Lambda API
- Amazon EC2 API

The exact supported service names and availability depend on the Region.

## 6.1 How does an Interface endpoint work?

Suppose a FastAPI application needs to retrieve a database password from Secrets Manager.

Without an endpoint, it might access the public Secrets Manager service endpoint through NAT.

With an Interface endpoint:

1. AWS creates an ENI in your selected subnet.
2. The ENI receives a private IP address.
3. Private DNS can make the normal Secrets Manager hostname resolve to the endpoint's private IP.
4. The application makes its normal HTTPS request.
5. Traffic reaches the endpoint ENI over the VPC network.
6. AWS PrivateLink provides connectivity to Secrets Manager.
7. Secrets Manager evaluates the request permissions.

### Traffic flow

```text
FastAPI application
        |
        v
EC2 private subnet
        |
        v
Secrets Manager DNS hostname
        |
        v
Private DNS resolution
        |
        v
Private IP of endpoint ENI
        |
        v
Interface VPC endpoint
        |
        v
AWS PrivateLink
        |
        v
AWS Secrets Manager
```

The application does not normally need to use a special endpoint URL when private DNS is enabled and correctly configured.

# 7. Interface Endpoint – Terraform Configuration

## 7.1 Security group for the endpoint

The endpoint needs to allow HTTPS traffic from the application.

```hcl
resource "aws_security_group" "endpoint_sg" {

  name        = "vpc-endpoint-sg"
  description = "Allow HTTPS from application"
  vpc_id      = var.vpc_id

  ingress {
    description     = "HTTPS from FastAPI EC2"
    from_port       = 443
    to_port         = 443
    protocol        = "tcp"
    security_groups = [aws_security_group.app_sg.id]
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }

  tags = {
    Name = "vpc-endpoint-sg"
  }
}
```

The `app_sg` represents the security group attached to the application EC2 instance.

In this example, endpoint ingress permits TCP 443 from that application security group.

For tightly restricted security, application outbound rules should also permit TCP 443 to the endpoint security group.

Security groups are stateful.

## 7.2 Create the Interface endpoint

```hcl
resource "aws_vpc_endpoint" "secrets_manager" {

  vpc_id = var.vpc_id

  service_name = "com.amazonaws.eu-west-1.secretsmanager"

  vpc_endpoint_type = "Interface"

  subnet_ids = var.private_subnet_ids

  security_group_ids = [
    aws_security_group.endpoint_sg.id
  ]

  private_dns_enabled = true

  tags = {
    Name        = "secrets-manager-endpoint"
    Environment = "dev"
  }
}
```

## 7.3 Explain every Interface endpoint parameter

### `vpc_id`

The VPC where the endpoint ENIs will be created.

Required.

### `service_name`

Identifies the service.

Example:

```hcl
service_name = "com.amazonaws.eu-west-1.secretsmanager"
```

Other examples:

```text
com.amazonaws.eu-west-1.sqs
com.amazonaws.eu-west-1.sns
com.amazonaws.eu-west-1.kms
com.amazonaws.eu-west-1.logs
com.amazonaws.eu-west-1.ecr.api
com.amazonaws.eu-west-1.ecr.dkr
```

### `vpc_endpoint_type`

```hcl
vpc_endpoint_type = "Interface"
```

Tells AWS to create an Interface endpoint using PrivateLink.

### `subnet_ids`

```hcl
subnet_ids = [
  "subnet-123456",
  "subnet-789012"
]
```

Specifies where AWS creates endpoint ENIs.

Best practice:
- Use private subnets.
- Usually select one subnet per Availability Zone where your application needs endpoint access.
- Consider Availability Zone resilience.
- Ensure the selected subnets have available IP addresses.

Interface endpoints cannot function without subnet assignments.

### `security_group_ids`

```hcl
security_group_ids = [
  aws_security_group.endpoint_sg.id
]
```

Specifies the security groups attached to the endpoint ENIs.

These control traffic entering the endpoint network interfaces.

If no security group is specified, the VPC default security group is used.

### `private_dns_enabled`

```hcl
private_dns_enabled = true
```

Enables private DNS integration for supported AWS service endpoints.

This is important.

Without private DNS, your application might need to connect using the endpoint-specific DNS name.

With private DNS enabled, the standard AWS service hostname can resolve to the endpoint's private IP addresses inside the VPC.

For example:

```text
secretsmanager.eu-west-1.amazonaws.com
```

can resolve privately inside the VPC.

Requirements include:
- VPC DNS resolution enabled.
- VPC DNS hostnames enabled.
- Service support for private DNS.
- Correct endpoint and DNS configuration.

### `tags`

Used for resource identification and management.

# 8. Other Important Terraform Parameters

The following arguments are available in the Terraform `aws_vpc_endpoint` resource. Not all apply to every endpoint type.

| Parameter | Purpose | Applicable endpoint types |
|---|---|---|
| `vpc_id` | VPC containing the endpoint | Required for standard VPC endpoint types |
| `service_name` | AWS or endpoint service name | Common service-based endpoints |
| `vpc_endpoint_type` | Endpoint type | Gateway, Interface and specialized types |
| `route_table_ids` | Route-table association | Gateway |
| `subnet_ids` | Subnets for endpoint ENIs | Interface, Gateway Load Balancer |
| `security_group_ids` | Security groups on endpoint ENIs | Interface |
| `private_dns_enabled` | Enables private DNS integration | Interface; supported service endpoints |
| `policy` | Endpoint access policy | Gateway and supported Interface endpoints |
| `auto_accept` | Automatically accepts an endpoint connection where supported | Mainly customer/provider endpoint services |
| `ip_address_type` | IPv4, IPv6 or dual-stack selection | Supported endpoint/service combinations |
| `dns_options` | Advanced DNS settings | Supported endpoint types |
| `subnet_configuration` | Custom IP assignments in endpoint subnets | Supported endpoint configurations |
| `service_region` | Region of the remote endpoint service | Supported cross-Region Interface endpoints |
| `region` | Region where Terraform manages the resource | Provider/resource configuration |
| `resource_configuration_arn` | VPC Lattice Resource Configuration ARN | Resource endpoint |
| `service_network_arn` | VPC Lattice Service Network ARN | ServiceNetwork endpoint |
| `tags` | Resource tags | Supported resources |

## 8.1 `auto_accept`

Used mainly with endpoint services shared by another AWS account.

Controls automatic acceptance of a connection request where supported.

For normal AWS service endpoints, you generally do not need to configure this.

## 8.2 `ip_address_type`

Possible values:

```hcl
ip_address_type = "ipv4"
```

```hcl
ip_address_type = "ipv6"
```

```hcl
ip_address_type = "dualstack"
```

Controls the IP address type used for endpoint connectivity.

The service and subnet configuration must support the requested address type.

## 8.3 `dns_options`

Provides advanced DNS settings.

Example:

```hcl
dns_options {
  dns_record_ip_type = "ipv4"
}
```

Possible DNS record types include:

- `ipv4`
- `ipv6`
- `dualstack`
- `service-defined`

Other advanced options include private DNS preferences for supported VPC Lattice Resource and ServiceNetwork endpoints.

One special option is:

```hcl
dns_options {
  private_dns_only_for_inbound_resolver_endpoint = true
}
```

This is a special configuration for supported services that offer both Gateway and Interface endpoint options. It requires private DNS to be enabled and a Gateway endpoint for that service to exist.

It supports a design where traffic from the VPC uses the Gateway endpoint while traffic arriving through an inbound Route 53 Resolver endpoint can use the Interface endpoint.

## 8.4 `subnet_configuration`

Allows you to specify particular IP addresses for endpoint ENIs.

Example:

```hcl
subnet_configuration {
  subnet_id = "subnet-123456"
  ipv4      = "10.0.1.50"
}
```

Use this only when you need specific endpoint IP assignments and the service supports them.

## 8.5 `service_region`

Used for supported cross-Region Interface endpoint connections.

Specifies the Region in which the endpoint service is located.

It is not required for an ordinary same-Region AWS service endpoint.

## 8.6 `region`

Specifies the Region where the Terraform resource is managed.

Normally, the AWS provider's configured Region is used.

## 8.7 Specialized endpoint arguments

`resource_configuration_arn` and `service_network_arn` are used for VPC Lattice connectivity.

They are not normal arguments for a simple S3, SQS or Secrets Manager endpoint.

# 9. Gateway vs Interface Endpoint – Comparison

| Feature | Gateway | Interface |
|---|---|---|
| Main technology | Route-table integration | AWS PrivateLink |
| Creates ENI | No | Yes |
| Private IP | No endpoint IP | Yes |
| Security group | No | Yes |
| Route table association | Yes | Not required for endpoint creation |
| Subnet association | No, uses route tables | Yes |
| Private DNS | Not needed for normal Gateway operation | Supported |
| Endpoint policy | Yes | Supported by some services |
| Hourly endpoint charge | No | Yes |
| Data-processing charge | No | Yes |
| Supported services | S3 and DynamoDB | Many AWS and supported partner services |

**Interview answer:**

Gateway endpoints are primarily used for S3 and DynamoDB. They work by adding routes to selected route tables and do not create ENIs or incur endpoint charges.

Interface endpoints use AWS PrivateLink, create ENIs in selected subnets, support security groups and private DNS, and are used for services such as SQS, SNS, Secrets Manager and KMS.

# 10. Which AWS Services Use Which Endpoint?

This is an important interview reference.

| AWS service | Recommended endpoint type for VPC access | Notes |
|---|---|---|
| Amazon S3 | Gateway | Interface also supported |
| DynamoDB | Gateway | Interface also supported |
| SQS | Interface | PrivateLink |
| SNS | Interface | PrivateLink |
| Secrets Manager | Interface | PrivateLink |
| KMS | Interface | PrivateLink |
| CloudWatch Logs | Interface | PrivateLink |
| CloudWatch Monitoring API | Interface | PrivateLink |
| ECR API | Interface | `ecr.api` endpoint |
| ECR Docker Registry | Interface | `ecr.dkr` endpoint |
| Systems Manager | Interface | Additional endpoints may be needed for features |
| STS | Interface | Private access to regional STS endpoint |
| Lambda API | Interface | Access Lambda service API |
| EC2 API | Interface | Access EC2 service API |
| RDS management API | Interface | Does not provide database connectivity |
| Aurora database | No ordinary VPC endpoint | Connect directly to the database endpoint |
| API Gateway | Interface | For supported private API access patterns |
| EventBridge | Interface | Private access to supported service API |

**Important distinctions:**

- ECR image pulls from private EC2 instances commonly need both `ecr.api` and `ecr.dkr` endpoints, plus S3 connectivity for image layers and the required IAM permissions.
- Systems Manager functionality can require additional endpoints such as `ssm`, `ssmmessages` and, depending on the feature and Region, `ec2messages`.
- Aurora is accessed directly through its private database endpoint and database port, not through a normal VPC endpoint.
- S3 and DynamoDB have both Gateway and Interface options.
- Service support and endpoint service names should be checked in the AWS Region being deployed.

# 11. VPC Endpoint Pricing

## 11.1 Gateway endpoint pricing

Gateway endpoints have no additional endpoint charges.

| Charge | Gateway endpoint |
|---|---|
| Endpoint creation | Free |
| Hourly endpoint charge | Free |
| Endpoint data-processing charge | Free |
| S3 storage | Normal S3 pricing |
| S3 requests | Normal S3 pricing |
| DynamoDB requests | Normal DynamoDB pricing |

Gateway endpoints can reduce NAT Gateway costs because traffic routed through them does not incur NAT Gateway processing charges.

## 11.2 Interface endpoint pricing

Interface endpoints have two main charge categories:

1. Endpoint-hours.
2. Data processed through the endpoint.

Endpoint-hour charges depend on the Region and the number of Availability Zones in which the endpoint is provisioned.

Example:

Suppose:
- One Interface endpoint.
- Two Availability Zones.
- Endpoint is running for a full month.

You are generally billed for two endpoint-AZ instances of usage, plus applicable data processing.

If you create separate endpoints for SQS, SNS, Secrets Manager and KMS, each endpoint has its own billing.

Exact prices depend on Region and current AWS pricing.

Check:

https://aws.amazon.com/privatelink/pricing/

## 11.3 NAT Gateway vs VPC Endpoint

| Scenario | NAT Gateway | Gateway endpoint |
|---|---|---|
| S3 traffic | NAT charges may apply | No endpoint processing charge |
| DynamoDB traffic | NAT charges may apply | No endpoint processing charge |
| Third-party payment API | Needed for IPv4 internet access from private subnet, or another egress design | Not applicable |
| Secrets Manager | Can use NAT | Interface endpoint |
| SQS | Can use NAT | Interface endpoint |

Remember:

A VPC endpoint does not replace NAT for all outbound traffic.

If your FastAPI application calls an external payment provider, you still need an appropriate internet egress design, such as NAT Gateway for IPv4 internet access from a private subnet.

# 12. Production Architecture Example

Suppose you have a FastAPI application running on EC2 in a private subnet.

The application needs to:
1. Upload documents to S3.
2. Read a database password from Secrets Manager.
3. Send messages to SQS.
4. Encrypt information using KMS.
5. Connect to Aurora PostgreSQL.
6. Call an external payment provider.

Recommended connectivity:

| Destination | Connectivity |
|---|---|
| S3 | Gateway endpoint |
| Secrets Manager | Interface endpoint |
| SQS | Interface endpoint |
| KMS | Interface endpoint |
| Aurora PostgreSQL | Direct private database connection |
| External payment provider | NAT Gateway or another approved egress path |

### Architecture flow

```text
                    AWS VPC
                       |
              Private application subnet
                       |
                  EC2 / FastAPI
                       |
       +---------------+----------------+
       |               |                |
       v               v                v
   S3 Gateway      Secrets Manager    SQS Interface
    endpoint        Interface          endpoint
                     endpoint
       |
       v
      S3

FastAPI ---------> KMS Interface endpoint

FastAPI ---------> Aurora private endpoint
                    TCP 5432

FastAPI ---------> NAT Gateway
                       |
                       v
                External payment API
```

For production, use IAM roles for EC2 rather than static AWS access keys.

# 13. Security Checklist

Before deploying a VPC endpoint, check:

- [ ] Correct VPC selected.
- [ ] Correct AWS Region.
- [ ] Correct service name.
- [ ] Correct endpoint type.
- [ ] Correct route tables for Gateway endpoints.
- [ ] Correct private subnets for Interface endpoints.
- [ ] Endpoint security group allows application traffic.
- [ ] Application security group permits outbound traffic if egress is restricted.
- [ ] Network ACLs permit required traffic and return traffic.
- [ ] VPC DNS resolution and hostnames enabled where needed.
- [ ] Private DNS configured correctly for Interface endpoints.
- [ ] IAM role has the required permissions.
- [ ] Endpoint policy is appropriate.
- [ ] Resource policy permits the request.
- [ ] Availability Zone resilience considered.
- [ ] Endpoint pricing and NAT cost savings reviewed.

# 14. Common Troubleshooting Questions

### Problem 1: EC2 cannot connect to S3 after creating Gateway endpoint.

Check:
1. Is the endpoint in `Available` state?
2. Is the EC2 subnet using the route table associated with the endpoint?
3. Does the route table contain the S3 prefix-list route?
4. Does the EC2 security group allow HTTPS outbound?
5. Do NACLs allow the traffic?
6. Does the EC2 IAM role allow the S3 operation?
7. Does the endpoint policy allow the operation?
8. Does the bucket policy allow the request?

### Problem 2: EC2 cannot connect to Secrets Manager.

Check:
1. Is the Interface endpoint in `Available` state?
2. Does it have ENIs in the required subnets?
3. Does the endpoint security group allow inbound TCP 443 from the application security group?
4. Does the application security group allow outbound TCP 443?
5. Is private DNS enabled?
6. Are VPC DNS hostnames and DNS resolution enabled?
7. Does the IAM role allow `secretsmanager:GetSecretValue`?
8. Does the endpoint policy permit the request?

### Problem 3: Application still uses NAT after creating Interface endpoint.

Possible reasons:
- Private DNS is disabled.
- DNS resolution is not configured correctly.
- The application uses a custom public endpoint URL.
- The application resolves DNS outside the VPC.
- The endpoint is not configured for the service hostname being used.

### Problem 4: Endpoint is available but requests return AccessDenied.

An endpoint being `Available` only confirms the endpoint is provisioned. It does not mean the request is authorized.

Check:
- IAM permissions.
- Endpoint policy.
- Resource policy.
- KMS key policy, where applicable.
- Organization SCPs and permission boundaries, where applicable.

# 16. Common Interview Questions and Answers

### Q1. What is a VPC endpoint?

A VPC endpoint provides private connectivity from a VPC to supported AWS services without requiring internet or NAT connectivity for those destinations.

### Q2. What are the main types?

Gateway and Interface endpoints.

Gateway endpoints use route tables and support S3 and DynamoDB. Interface endpoints use PrivateLink and ENIs and support many AWS services.

### Q3. What is AWS PrivateLink?

AWS PrivateLink provides private connectivity to services through private IP addresses and endpoint network interfaces.

Interface endpoints use PrivateLink.

### Q4. Does a Gateway endpoint create an ENI?

No. It adds routes to selected route tables.

### Q5. Does an Interface endpoint create an ENI?

Yes. AWS creates endpoint network interfaces in the selected subnets.

### Q6. Does a Gateway endpoint need a security group?

No.

### Q7. Does an Interface endpoint need a security group?

Yes, an endpoint security group controls traffic entering its network interfaces. If none is specified, the VPC default security group is used.

### Q8. Does a Gateway endpoint cost money?

There is no additional Gateway endpoint hourly or data-processing charge.

### Q9. Does an Interface endpoint cost money?

Yes. It has hourly charges per enabled Availability Zone and data-processing charges.

### Q10. Do we need to change application code after creating an endpoint?

Usually not. With normal AWS SDK usage and correct endpoint/DNS configuration, the application continues using the standard AWS service hostname.

### Q11. Does creating a VPC endpoint grant IAM permissions?

No. IAM and applicable resource policies must still permit the request.

### Q12. Can we access S3 without a NAT Gateway?

Yes. An S3 Gateway endpoint allows supported S3 traffic from associated route tables without NAT.

### Q13. Can we use a Gateway endpoint for SQS?

No. SQS uses an Interface endpoint for private VPC connectivity.

### Q14. Can we use an Interface endpoint for S3?

Yes. S3 supports both Gateway and Interface endpoints. Gateway is often the economical option for traffic originating in the same VPC.

### Q15. Does a VPC endpoint provide access to the public internet?

No. It only provides connectivity to the specified supported service or endpoint service.

### Q16. Can we connect to Aurora through a VPC endpoint?

Not through an ordinary AWS service VPC endpoint. Applications connect directly to the Aurora database endpoint using the database port and security groups.

### Q17. What happens if we delete a Gateway endpoint?

AWS removes the endpoint route from the associated route tables. Traffic may use another matching route, such as a NAT Gateway default route, if one exists.

### Q18. What happens if private DNS is disabled for an Interface endpoint?

The normal AWS service hostname might resolve to public service addresses. The application may need to use the endpoint-specific DNS name, depending on its configuration.

### Q19. Can multiple private subnets use one Interface endpoint?

Yes, when the endpoint is deployed in appropriate subnets and the routing, DNS and security configuration permits access. For high availability, deploy endpoint ENIs across the required Availability Zones.

### Q20. Is a VPC endpoint the same as a NAT Gateway?

No. A NAT Gateway provides outbound network translation for private-subnet resources, typically to reach public IPv4 destinations. A VPC endpoint provides private connectivity to a particular supported service.

## 18. A Strong Interview Explanation

If an interviewer asks you to explain VPC endpoints, you can say:

"VPC endpoints allow resources inside a VPC to privately access supported AWS services without going through the public internet or a NAT Gateway.

There are two main types: Gateway and Interface.

Gateway endpoints support S3 and DynamoDB. They work by adding routes to selected route tables. They do not create ENIs, do not require security groups and have no additional endpoint hourly or data-processing charges.

Interface endpoints use AWS PrivateLink. They create ENIs with private IP addresses in selected subnets. We attach security groups to control access and can enable private DNS so that standard AWS service hostnames resolve to the endpoint's private IP addresses. Interface endpoints are billed hourly and for data processing.

In a production application, I would generally use an S3 Gateway endpoint, Interface endpoints for services such as Secrets Manager, SQS and KMS, and direct private connectivity to Aurora. I would still use NAT or another approved egress architecture for external third-party APIs.

Finally, creating an endpoint does not grant permissions. IAM roles, endpoint policies and service resource policies must all be configured correctly."
