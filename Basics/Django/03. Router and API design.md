# Part 4: URL Routing and API Design — Django REST Framework

## 54. Django URL Configuration

### What is URL configuration?

URL configuration determines which view should handle an incoming HTTP request based on its URL.

In Django, URL configuration is handled using `urlpatterns` and `path()`.

For example, when a client sends:

```http
GET /employees/
```

Django checks its URL patterns to find the matching view.

### Step 1: Create a Django application

Suppose we have an application named `employees`.

```text
myproject/
    myproject/
        settings.py
        urls.py
    employees/
        models.py
        views.py
        urls.py
```

### Step 2: Define a view

`employees/views.py`

```python
from rest_framework.decorators import api_view
from rest_framework.response import Response

@api_view(['GET'])
def employee_list(request):
    return Response({
        "message": "Employee list"
    })
```

### Step 3: Create application URLs

`employees/urls.py`

```python
from django.urls import path
from .views import employee_list

urlpatterns = [
    path('employees/', employee_list, name='employee-list'),
]
```

### Step 4: Connect application URLs to project URLs

`myproject/urls.py`

```python
from django.contrib import admin
from django.urls import path, include

urlpatterns = [
    path('admin/', admin.site.urls),
    path('api/', include('employees.urls')),
]
```

### Result

The complete endpoint becomes:

```http
GET /api/employees/
```

Response:

```json
{
    "message": "Employee list"
}
```

### Understanding include()

```python
path('api/', include('employees.urls'))
```

This tells Django:

- Whenever a URL starts with `api/`, check `employees.urls`.
- The application URL configuration handles the remaining URL path.

For example:

```text
/api/employees/
```

Django combines:

```text
api/ + employees/
```

### Important URL functions

| Function | Purpose |
|---|---|
| `path()` | Defines a URL pattern |
| `include()` | Includes another URL configuration |
| `re_path()` | Defines a URL using regular expressions |
| `reverse()` | Generates a URL from its name |
| `resolve()` | Finds which URL pattern matches a path |

## 55. DRF Routers

### What is a router?

A router automatically generates URL patterns for ViewSets.

Without routers, you need to manually connect each ViewSet action to a URL.

With routers, DRF generates the URLs for you.

### Without a router

Suppose we have this ViewSet:

```python
from rest_framework.viewsets import ModelViewSet
from .models import Employee
from .serializers import EmployeeSerializer

class EmployeeViewSet(ModelViewSet):
    queryset = Employee.objects.all()
    serializer_class = EmployeeSerializer
```

Without a router, you must manually connect its actions:

```python
from django.urls import path
from .views import EmployeeViewSet

employee_list = EmployeeViewSet.as_view({
    'get': 'list',
    'post': 'create'
})

employee_detail = EmployeeViewSet.as_view({
    'get': 'retrieve',
    'put': 'update',
    'patch': 'partial_update',
    'delete': 'destroy'
})

urlpatterns = [
    path('employees/', employee_list),
    path('employees/<int:pk>/', employee_detail),
]
```

Notice how we manually map HTTP methods to ViewSet actions.

### With a router

The same setup becomes much shorter:

```python
from rest_framework.routers import DefaultRouter
from .views import EmployeeViewSet

router = DefaultRouter()

router.register(
    'employees',
    EmployeeViewSet,
    basename='employee'
)

urlpatterns = router.urls
```

The router automatically generates the standard URLs.

### Generated endpoints

| HTTP Method | URL | ViewSet action |
|---|---|---|
| GET | `/employees/` | `list` |
| POST | `/employees/` | `create` |
| GET | `/employees/1/` | `retrieve` |
| PUT | `/employees/1/` | `update` |
| PATCH | `/employees/1/` | `partial_update` |
| DELETE | `/employees/1/` | `destroy` |

### Why use routers?

1. Less repetitive URL configuration.
2. Automatic URL generation.
3. Consistent endpoint naming.
4. Easy integration with ViewSets.
5. Easier maintenance when APIs grow.

**Remember:** Routers are designed for ViewSets. They are not normally used to automatically generate URLs for ordinary function-based views or APIViews.

## 56. SimpleRouter

### What is SimpleRouter?

`SimpleRouter` is a DRF router that automatically generates URL patterns for registered ViewSets.

It generates the standard list and detail routes, along with routes for custom actions.

### Example

```python
from rest_framework.routers import SimpleRouter
from .views import EmployeeViewSet

router = SimpleRouter()

router.register(
    'employees',
    EmployeeViewSet,
    basename='employee'
)

urlpatterns = router.urls
```

### URLs generated by SimpleRouter

For a `ModelViewSet`, it generates:

| HTTP Method | URL | Action |
|---|---|---|
| GET | `/employees/` | list |
| POST | `/employees/` | create |
| GET | `/employees/1/` | retrieve |
| PUT | `/employees/1/` | update |
| PATCH | `/employees/1/` | partial_update |
| DELETE | `/employees/1/` | destroy |

### Does SimpleRouter generate an API root?

No. Unlike `DefaultRouter`, `SimpleRouter` does not generate an automatic API root page.

### When should you use SimpleRouter?

Use it when:
- You want automatic ViewSet URLs.
- You do not need an automatically generated API root.
- You prefer a simpler routing setup.

## 57. DefaultRouter

### What is DefaultRouter?

`DefaultRouter` works similarly to `SimpleRouter`, but it provides an additional feature: an automatically generated API root endpoint.

### Example

```python
from rest_framework.routers import DefaultRouter
from .views import EmployeeViewSet

router = DefaultRouter()

router.register(
    'employees',
    EmployeeViewSet,
    basename='employee'
)

urlpatterns = router.urls
```

### URLs generated

DefaultRouter generates:

```text
/
```

An API root page, along with:

```text
/employees/
/employees/1/
```

It also supports custom ViewSet actions.

### Example API root response

The browsable API root may show links similar to:

```json
{
    "employees": "http://127.0.0.1:8000/employees/"
}
```

### SimpleRouter vs DefaultRouter

| Feature | SimpleRouter | DefaultRouter |
|---|---|---|
| List routes | Yes | Yes |
| Detail routes | Yes | Yes |
| Custom action routes | Yes | Yes |
| Automatic API root | No | Yes |
| Format suffix routes | No | Yes |

DefaultRouter also supports optional format suffixes, such as `.json`.

### Which one should you choose?

Use `SimpleRouter` if you do not need an API root.

Use `DefaultRouter` if you want a browsable API root that lists available resources.

## 58. Registering ViewSets

### What does register() do?

The `register()` method tells a router which ViewSet it should generate URL patterns for.

Syntax:

```python
router.register(
    prefix,
    viewset,
    basename
)
```

The three arguments are:

1. `prefix`: The URL prefix.
2. `viewset`: The ViewSet class.
3. `basename`: The base name used for generated URL names.

### Example

```python
router.register(
    'employees',
    EmployeeViewSet,
    basename='employee'
)
```

This registers the EmployeeViewSet under the `employees` URL prefix.

### Register multiple ViewSets

```python
router.register(
    'employees',
    EmployeeViewSet,
    basename='employee'
)

router.register(
    'departments',
    DepartmentViewSet,
    basename='department'
)

router.register(
    'projects',
    ProjectViewSet,
    basename='project'
)
```

Generated resource URLs include:

```text
/employees/
/departments/
/projects/
```

### What is basename?

The basename is used to generate URL names.

For example:

```python
router.register(
    'employees',
    EmployeeViewSet,
    basename='employee'
)
```

Generated URL names include:

```text
employee-list
employee-detail
```

For a custom action, additional URL names are generated.

### Is basename always required?

Not necessarily.

If the ViewSet has a class-level `queryset` attribute, DRF can usually infer the basename.

For example:

```python
class EmployeeViewSet(ModelViewSet):
    queryset = Employee.objects.all()
    serializer_class = EmployeeSerializer
```

You can register it like this:

```python
router.register('employees', EmployeeViewSet)
```

But if you dynamically define the queryset and do not provide a class-level queryset, specify `basename` explicitly.

## 59. URL Parameters

### What are URL parameters?

URL parameters are values included directly in the URL path.

They are commonly used to identify a particular resource.

Example:

```http
GET /employees/5/
```

Here, `5` is a URL parameter identifying the employee.

### Defining URL parameters manually

```python
from django.urls import path
from .views import employee_detail

urlpatterns = [
    path(
        'employees/<int:pk>/',
        employee_detail,
        name='employee-detail'
    )
]
```

The `<int:pk>` part means:
- `int` is the path converter.
- `pk` is the parameter name.

### Accessing URL parameters in a function-based view

```python
@api_view(['GET'])
def employee_detail(request, pk):
    return Response({
        "employee_id": pk
    })
```

Request:

```http
GET /employees/5/
```

Response:

```json
{
    "employee_id": 5
}
```

### Common Django path converters

| Converter | Meaning | Example |
|---|---|---|
| `int` | Integer | `<int:id>` |
| `str` | Non-empty string without `/` | `<str:name>` |
| `slug` | Slug characters | `<slug:slug>` |
| `uuid` | UUID value | `<uuid:id>` |
| `path` | String that may contain `/` | `<path:filepath>` |

### URL parameters in ViewSets

When using a router, DRF automatically creates detail routes.

For example:

```http
GET /employees/5/
```

By default, the ViewSet uses `pk` as the lookup parameter.

```python
class EmployeeViewSet(ModelViewSet):
    queryset = Employee.objects.all()
    serializer_class = EmployeeSerializer
```

You can customize the lookup field:

```python
class EmployeeViewSet(ModelViewSet):
    queryset = Employee.objects.all()
    serializer_class = EmployeeSerializer

    lookup_field = 'employee_id'
```

Now DRF looks up employees using `employee_id` instead of the default `pk`.

## 60. Query Parameters

### What are query parameters?

Query parameters are values added after a question mark (`?`) in a URL.

They are commonly used for:
- Filtering
- Searching
- Sorting
- Pagination

Example:

```http
GET /employees/?department=IT
```

Here:

```text
department=IT
```

is a query parameter.

### Difference between URL parameters and query parameters

| URL parameter | Query parameter |
|---|---|
| Part of the URL path | Comes after `?` |
| Usually identifies a resource | Usually modifies a collection request |
| `/employees/5/` | `/employees/?department=IT` |
| Accessed through `kwargs` in a view | Accessed through `request.query_params` |

### Access query parameters in DRF

```python
@api_view(['GET'])
def employee_list(request):

    department = request.query_params.get('department')

    return Response({
        "department": department
    })
```

Request:

```http
GET /employees/?department=IT
```

Response:

```json
{
    "department": "IT"
}
```

### Multiple query parameters

Request:

```http
GET /employees/?department=IT&city=Dublin
```

Code:

```python
department = request.query_params.get('department')
city = request.query_params.get('city')
```

Response:

```json
{
    "department": "IT",
    "city": "Dublin"
}
```

### Filtering using query parameters

```python
@api_view(['GET'])
def employee_list(request):

    employees = Employee.objects.all()

    department = request.query_params.get('department')

    if department:
        employees = employees.filter(
            department=department
        )

    serializer = EmployeeSerializer(
        employees,
        many=True
    )

    return Response(serializer.data)
```

Example requests:

```http
GET /employees/
GET /employees/?department=IT
GET /employees/?department=HR
```

Each request can return a different collection of employees.

### Important method

In DRF, prefer:

```python
request.query_params
```

instead of:

```python
request.GET
```

Both can access query-string values, but `query_params` is the clearer, framework-independent DRF interface.

## 61. Request Data

### What is request data?

Request data is the information sent by a client to the API.

For example, when creating an employee, the client sends:

```http
POST /employees/
Content-Type: application/json
```

```json
{
    "name": "John",
    "email": "john@example.com",
    "department": "IT"
}
```

This JSON body contains the request data.

### Access request data in DRF

DRF provides:

```python
request.data
```

Example:

```python
@api_view(['POST'])
def create_employee(request):

    name = request.data.get('name')
    email = request.data.get('email')

    return Response({
        "name": name,
        "email": email
    })
```

Request body:

```json
{
    "name": "John",
    "email": "john@example.com"
}
```

Response:

```json
{
    "name": "John",
    "email": "john@example.com"
}
```

### Using serializers with request data

Instead of manually extracting every field, use a serializer.

```python
@api_view(['POST'])
def create_employee(request):

    serializer = EmployeeSerializer(
        data=request.data
    )

    if serializer.is_valid():
        serializer.save()

        return Response(
            serializer.data,
            status=201
        )

    return Response(
        serializer.errors,
        status=400
    )
```

### What does data=request.data mean?

It tells the serializer:

"Take the incoming client data and validate it against the serializer fields."

### What does is_valid() do?

It checks whether the incoming data satisfies the serializer's validation rules.

### What does save() do?

It creates or updates an object depending on how the serializer was initialized.

In this example, it creates a new employee because the serializer was initialized without an existing instance.

### Supported request formats

DRF supports different request content types through parsers.

Common examples:

| Content type | Typical use |
|---|---|
| `application/json` | JSON data |
| `application/x-www-form-urlencoded` | Form submissions |
| `multipart/form-data` | Forms with file uploads |

DRF's `request.data` provides a convenient interface for parsed request content.

## 62. Request Objects

### What is a Request object?

A Request object represents the incoming HTTP request.

Django provides an `HttpRequest` object, and DRF extends it with its own `Request` object.

In DRF views, you generally work with the DRF Request object.

Example:

```python
@api_view(['GET'])
def employee_list(request):
    ...
```

Here, `request` is the DRF Request object.

### Important Request attributes and properties

| Property | Purpose |
|---|---|
| `request.data` | Parsed request body |
| `request.query_params` | Query-string parameters |
| `request.method` | HTTP method |
| `request.user` | Authenticated user |
| `request.auth` | Authentication information |
| `request.headers` | Request headers |
| `request.content_type` | Request content type |
| `request.stream` | Underlying request body stream |

### Example: inspect the request

```python
@api_view(['GET'])
def inspect_request(request):

    return Response({
        "method": request.method,
        "user": str(request.user),
        "query_params": request.query_params,
        "content_type": request.content_type
    })
```

### Example request

```http
GET /inspect/?department=IT
```

Possible response:

```json
{
    "method": "GET",
    "user": "AnonymousUser",
    "query_params": {
        "department": "IT"
    },
    "content_type": null
}
```

The exact user value depends on authentication.

### request.user

Used to access the currently authenticated user.

```python
user = request.user
```

For example:

```python
@api_view(['GET'])
def my_profile(request):

    return Response({
        "username": request.user.username
    })
```

This requires an authenticated user if you expect a real account rather than an anonymous user.

### request.headers

Used to access incoming HTTP headers.

```python
authorization = request.headers.get('Authorization')
```

Example header:

```http
Authorization: Bearer your-token
```

Do not manually implement token verification just by reading this header. Use DRF's authentication classes.

### Request object vs request.data

Remember:

- `request` represents the entire incoming request.
- `request.data` contains the parsed body data.
- `request.query_params` contains URL query-string values.
- `request.method` tells you which HTTP method was used.

## 63. Response Objects

### What is a Response object?

DRF provides the `Response` class to return API responses.

Import it using:

```python
from rest_framework.response import Response
```

Example:

```python
@api_view(['GET'])
def employee_list(request):

    return Response({
        "message": "Employees retrieved successfully"
    })
```

### Why use DRF Response instead of JsonResponse?

Django provides `JsonResponse`, but DRF's `Response` offers additional API-specific functionality.

For example, DRF Response:
- Works with serialized data.
- Supports content negotiation.
- Can render output in different formats depending on configured renderers.
- Integrates with DRF's exception and response handling.

### Response syntax

```python
Response(
    data,
    status=None,
    headers=None
)
```

### Example with status code

```python
return Response(
    {
        "message": "Employee created"
    },
    status=201
)
```

### Common HTTP status codes

| Status | Meaning |
|---|---|
| 200 | OK |
| 201 | Created |
| 202 | Accepted |
| 204 | No Content |
| 400 | Bad Request |
| 401 | Unauthorized |
| 403 | Forbidden |
| 404 | Not Found |
| 405 | Method Not Allowed |
| 409 | Conflict |
| 500 | Internal Server Error |

### Example: successful response

```python
return Response(
    {
        "message": "Employee retrieved successfully",
        "data": serializer.data
    },
    status=200
)
```

### Example: error response

```python
return Response(
    {
        "error": "Employee not found"
    },
    status=404
)
```

### Important difference

`Response` is used to return data from a DRF view.

`request` is used to read incoming information.

## 64. Custom Response Formats

### What is a custom response format?

A custom response format means structuring the API output according to your application's requirements.

For example, instead of returning only:

```json
{
    "id": 1,
    "name": "John"
}
```

You may want:

```json
{
    "success": true,
    "message": "Employee retrieved successfully",
    "data": {
        "id": 1,
        "name": "John"
    }
}
```

### Why use a consistent response structure?

A consistent response format makes it easier for frontend applications to handle API responses.

For example, the frontend can always check:
- `success`
- `message`
- `data`
- `errors`

### Example: custom success response

```python
@api_view(['GET'])
def employee_detail(request, pk):

    employee = get_object_or_404(Employee, pk=pk)

    serializer = EmployeeSerializer(employee)

    return Response({
        "success": True,
        "message": "Employee retrieved successfully",
        "data": serializer.data
    })
```

### Example: custom error response

```python
return Response({
    "success": False,
    "message": "Validation failed",
    "errors": {
        "email": ["Enter a valid email address."]
    }
}, status=400)
```

### Example: custom response helper

If you use the same response structure frequently, create a helper function.

```python
def success_response(data, message="Success", status=200):

    return Response({
        "success": True,
        "message": message,
        "data": data
    }, status=status)
```

Usage:

```python
return success_response(
    serializer.data,
    "Employee retrieved successfully"
)
```

### Should every response have a custom wrapper?

Not necessarily.

Custom wrappers are a design choice, not a DRF requirement.

Some APIs return plain serialized objects and use HTTP status codes to communicate success or failure.

Choose one consistent approach and document it. Be especially careful with pagination responses because DRF provides its own pagination structure.

## 65. API Versioning

### What is API versioning?

API versioning allows an API to evolve without unexpectedly breaking applications that depend on older versions.

Imagine your API currently returns:

```json
{
    "id": 1,
    "name": "John"
}
```

Later, you redesign the response:

```json
{
    "employee_id": 1,
    "full_name": "John"
}
```

Existing frontend applications may break because they expect `id` and `name`.

Versioning lets you maintain different API versions.

### Common API versioning approaches

#### 1. URL path versioning

Example:

```text
/api/v1/employees/
/api/v2/employees/
```

DRF class:

```python
from rest_framework.versioning import URLPathVersioning
```

Settings:

```python
REST_FRAMEWORK = {
    'DEFAULT_VERSIONING_CLASS':
        'rest_framework.versioning.URLPathVersioning',

    'DEFAULT_VERSION': 'v1',

    'ALLOWED_VERSIONS': ['v1', 'v2'],

    'VERSION_PARAM': 'version',
}
```

URL configuration:

```python
urlpatterns = [
    path(
        'api/<str:version>/employees/',
        employee_list
    ),
]
```

Inside a DRF view:

```python
@api_view(['GET'])
def employee_list(request):

    version = request.version

    return Response({
        "api_version": version
    })
```

Request:

```http
GET /api/v1/employees/
```

Response:

```json
{
    "api_version": "v1"
}
```

#### 2. Query parameter versioning

Example:

```text
/api/employees/?version=v1
```

DRF class:

```python
from rest_framework.versioning import QueryParameterVersioning
```

Settings:

```python
REST_FRAMEWORK = {
    'DEFAULT_VERSIONING_CLASS':
        'rest_framework.versioning.QueryParameterVersioning',

    'DEFAULT_VERSION': 'v1',

    'ALLOWED_VERSIONS': ['v1', 'v2'],

    'VERSION_PARAM': 'version',
}
```

The version is available through:

```python
request.version
```

#### 3. Accept header versioning

Example:

```http
Accept: application/json; version=v1
```

DRF class:

```python
from rest_framework.versioning import AcceptHeaderVersioning
```

This approach places version information in the HTTP Accept header.

#### 4. Namespace versioning

Example:

```text
/api/v1/employees/
/api/v2/employees/
```

DRF class:

```python
from rest_framework.versioning import NamespaceVersioning
```

This approach uses Django URL namespaces to determine the version.

### Comparison

| Versioning type | Example |
|---|---|
| URL path | `/api/v1/employees/` |
| Query parameter | `/api/employees/?version=v1` |
| Accept header | `Accept: application/json; version=v1` |
| Namespace | URL namespace such as `v1` |

### Which approach is commonly used?

URL path versioning is a popular and easy-to-understand choice.

For example:

```text
/api/v1/employees/
/api/v2/employees/
```

It makes the API version visible and easy to test.

### Important note

Simply adding a version to the URL does not automatically create separate versions of your business logic or serializers. You must implement the appropriate routing and behavior for each version.

## 66. REST API Naming Conventions

### What are REST naming conventions?

REST naming conventions are guidelines for creating predictable, readable API endpoints.

The goal is to make URLs understandable and consistent.

### Rule 1: Use nouns instead of verbs

Prefer:

```text
GET /employees/
```

Avoid:

```text
GET /getEmployees/
```

The HTTP method already describes the action.

### Rule 2: Use plural resource names

Prefer:

```text
/employees/
/departments/
/projects/
```

This is a common convention for collection endpoints.

### Rule 3: Use HTTP methods to represent actions

| Method | Purpose |
|---|---|
| GET | Retrieve |
| POST | Create |
| PUT | Replace or fully update |
| PATCH | Partially update |
| DELETE | Delete |

Example:

```http
GET /employees/
POST /employees/
GET /employees/1/
PATCH /employees/1/
DELETE /employees/1/
```

### Rule 4: Use lowercase URLs

Prefer:

```text
/api/employees/
```

Avoid:

```text
/api/Employees/
```

### Rule 5: Use hyphens for multiword names

Prefer:

```text
/api/employee-records/
```

Avoid:

```text
/api/employee_records/
```

### Rule 6: Use nested URLs for clear relationships

Example:

```text
/departments/2/employees/
```

This means employees belonging to department 2.

Another example:

```text
/employees/5/projects/
```

This represents projects associated with employee 5.

Do not create unnecessarily deep nesting.

### Rule 7: Use query parameters for filtering and sorting

Examples:

```text
/employees/?department=IT
/employees/?city=Dublin
/employees/?ordering=name
/employees/?search=John
```

### Rule 8: Use consistent resource naming

If you use:

```text
/employees/
```

do not randomly switch to:

```text
/staff-members/
```

for the same resource elsewhere.

### Example of a well-designed Employee API

```text
GET     /api/employees/
POST    /api/employees/

GET     /api/employees/1/
PUT     /api/employees/1/
PATCH   /api/employees/1/
DELETE  /api/employees/1/

GET     /api/departments/
GET     /api/departments/2/
GET     /api/departments/2/employees/
```

## 67. Designing Resource-Based APIs

### What is a resource?

A resource is an object or concept that your API exposes to clients.

Examples:
- Employee
- Department
- Project
- Customer
- Product
- Order

In REST, APIs are generally organized around resources rather than individual operations.

### Example: employee resource

Suppose your database contains an Employee model:

```python
class Employee(models.Model):

    name = models.CharField(max_length=100)

    email = models.EmailField()

    department = models.CharField(max_length=100)
```

The resource is:

```text
employees
```

Its collection URL is:

```text
/api/employees/
```

An individual employee can be identified by:

```text
/api/employees/1/
```

### Resource-based API design

Think about the resources first.

For example:

```text
Employee
Department
Project
```

Then identify their relationships:

```text
Department has many Employees.

Employee can have many Projects.
```

Then design the URLs:

```text
/api/departments/
/api/departments/1/
/api/departments/1/employees/

/api/employees/
/api/employees/5/
/api/employees/5/projects/

/api/projects/
/api/projects/10/
```

### CRUD operations for resources

For the Employee resource:

| Operation | Method | URL |
|---|---|---|
| List employees | GET | `/employees/` |
| Create employee | POST | `/employees/` |
| Retrieve employee | GET | `/employees/1/` |
| Replace employee | PUT | `/employees/1/` |
| Partially update employee | PATCH | `/employees/1/` |
| Delete employee | DELETE | `/employees/1/` |

### Designing custom operations

Sometimes you need operations that are not ordinary CRUD operations.

For example:
- Activate an employee.
- Deactivate an employee.
- Promote an employee.

You can model some of these as resource updates.

For example:

```http
PATCH /employees/5/
```

Request:

```json
{
    "is_active": false
}
```

This is often preferable to creating an action-style endpoint such as:

```text
/employees/5/deactivate/
```

However, when an operation represents a distinct business action, a custom action endpoint may be appropriate.

With DRF:

```python
from rest_framework.decorators import action
from rest_framework.response import Response
from rest_framework.viewsets import ModelViewSet

class EmployeeViewSet(ModelViewSet):

    queryset = Employee.objects.all()
    serializer_class = EmployeeSerializer

    @action(
        detail=True,
        methods=['post']
    )
    def promote(self, request, pk=None):

        employee = self.get_object()

        employee.designation = "Senior Developer"
        employee.save()

        return Response({
            "message": "Employee promoted successfully"
        })
```

Generated URL:

```http
POST /employees/5/promote/
```

### Important API design principles

1. Organize endpoints around resources.
2. Use HTTP methods consistently.
3. Keep URLs predictable.
4. Avoid unnecessary nesting.
5. Use query parameters for filtering and sorting.
6. Use appropriate HTTP status codes.
7. Validate incoming data.
8. Keep response structures consistent.
9. Document your API.
10. Consider backward compatibility when changing API behavior.

## 68. Pagination-Friendly API Design

### What is pagination?

Pagination means dividing a large collection of records into smaller pages.

Imagine your database contains 10,000 employees.

Returning all 10,000 employees in one response can:
- Increase response size.
- Consume more memory.
- Slow down the API.
- Increase network usage.
- Make frontend rendering slower.

Instead, return a smaller number of records at a time.

### Example without pagination

```http
GET /employees/
```

The API might return thousands of employee records.

### Example with pagination

```http
GET /employees/?page=1
```

This returns only the first page.

```http
GET /employees/?page=2
```

This returns the second page.

### DRF pagination types

DRF provides three commonly used pagination classes:

1. PageNumberPagination
2. LimitOffsetPagination
3. CursorPagination

### 1. PageNumberPagination

This pagination style uses page numbers.

Example:

```http
GET /employees/?page=1
GET /employees/?page=2
GET /employees/?page=3
```

Configure it globally:

```python
REST_FRAMEWORK = {
    'DEFAULT_PAGINATION_CLASS':
        'rest_framework.pagination.PageNumberPagination',

    'PAGE_SIZE': 10
}
```

This tells DRF to return 10 records per page by default.

Example response:

```json
{
    "count": 50,
    "next": "http://127.0.0.1:8000/employees/?page=2",
    "previous": null,
    "results": [
        {
            "id": 1,
            "name": "John"
        },
        {
            "id": 2,
            "name": "David"
        }
    ]
}
```

Here:
- `count`: Total number of matching records.
- `next`: URL of the next page.
- `previous`: URL of the previous page.
- `results`: Records on the current page.

### 2. LimitOffsetPagination

This style uses `limit` and `offset`.

Example:

```http
GET /employees/?limit=10&offset=0
```

Meaning:
- `limit=10`: Return at most 10 records.
- `offset=0`: Start from the beginning.

Next request:

```http
GET /employees/?limit=10&offset=10
```

This skips the first 10 records and returns the next group.

Configuration:

```python
REST_FRAMEWORK = {
    'DEFAULT_PAGINATION_CLASS':
        'rest_framework.pagination.LimitOffsetPagination',

    'PAGE_SIZE': 10
}
```

### 3. CursorPagination

Cursor pagination uses a cursor to navigate through results.

It is useful for large datasets and APIs where stable traversal is important.

Example:

```http
GET /employees/
```

Response:

```json
{
    "next": "http://127.0.0.1:8000/employees/?cursor=some_cursor_value",
    "previous": null,
    "results": [
        {
            "id": 1,
            "name": "John"
        }
    ]
}
```

Configuration:

```python
from rest_framework.pagination import CursorPagination

class EmployeePagination(CursorPagination):

    page_size = 10

    ordering = 'id'
```

Apply it to a ViewSet:

```python
class EmployeeViewSet(ModelViewSet):

    queryset = Employee.objects.all()
    serializer_class = EmployeeSerializer
    pagination_class = EmployeePagination
```

Cursor pagination requires a suitable, stable ordering field. The ordering should be consistent and ideally unique for reliable navigation.

### Comparison of pagination types

| Pagination | How it works | Typical use |
|---|---|---|
| PageNumberPagination | Page numbers | General-purpose APIs |
| LimitOffsetPagination | Limit and offset | APIs needing flexible offsets |
| CursorPagination | Cursor navigation | Large, frequently changing collections |

### Custom pagination

You can create a custom pagination class:

```python
from rest_framework.pagination import PageNumberPagination

class CustomEmployeePagination(PageNumberPagination):

    page_size = 5

    page_size_query_param = 'page_size'

    max_page_size = 50
```

Now a client can request:

```http
GET /employees/?page=1&page_size=20
```

The API returns up to 20 records.

The maximum allowed page size is 50.

### Why is pagination-friendly API design important?

A good API should:
- Support pagination from the beginning.
- Avoid returning unnecessarily large collections.
- Provide navigation links or cursor information.
- Use predictable pagination parameters.
- Apply filtering and ordering consistently.
- Set reasonable page-size limits.

**Important:** DRF pagination is automatically applied to generic views and ViewSets that support pagination. A plain APIView or function-based view does not automatically paginate a queryset; you must use the pagination API yourself.
