# Django REST Framework (DRF): Exception Handling, API Security, and Throttling

# Part 1: DRF Exception Handling

Exception handling in Django REST Framework (DRF) is the process of catching errors that occur while processing API requests and returning meaningful HTTP responses.

Instead of returning an uncontrolled server error, we can return a structured response that tells the client:

- What went wrong?
- What HTTP status code describes the problem?
- Which field caused the error?
- What should the client do next?

For example, if a client requests a product that does not exist:

**Request**

```http
GET /api/products/999/
```

**Response**

```json
{
    "detail": "Not found."
}
```

HTTP status:

```http
404 Not Found
```

DRF provides several built-in exceptions and allows us to create custom exception handling.

---

# 1. APIException

## What is APIException?

`APIException` is the base class for most exceptions provided by Django REST Framework.

You can raise it when something goes wrong while processing an API request.

DRF catches supported API exceptions and converts them into HTTP responses.

For example:

```python
from rest_framework.exceptions import APIException

raise APIException("Something went wrong.")
```

Response:

```json
{
    "detail": "Something went wrong."
}
```

HTTP status:

```http
500 Internal Server Error
```

## Why do we use APIException?

We use `APIException` when:

- An API operation cannot be completed.
- We want to return a controlled API error.
- We need to create our own exception class.
- We want to define a custom HTTP status code.

## Important APIException attributes

### 1. `status_code`

Defines the HTTP status code returned to the client.

Example:

```python
from rest_framework.exceptions import APIException
from rest_framework import status

class ServiceUnavailable(APIException):
    status_code = status.HTTP_503_SERVICE_UNAVAILABLE
```

This exception returns HTTP 503.

### 2. `default_detail`

Defines the default error message.

Example:

```python
class ServiceUnavailable(APIException):
    status_code = 503
    default_detail = "The service is temporarily unavailable."
```

### 3. `default_code`

Defines a machine-readable error code.

Example:

```python
class ServiceUnavailable(APIException):
    status_code = 503
    default_detail = "The service is temporarily unavailable."
    default_code = "service_unavailable"
```

The error code can help frontend applications identify the type of error without depending on the exact message.

### 4. `detail`

Contains the actual error message or error details for an exception instance.

Example:

```python
raise APIException("Payment processing failed.")
```

You can also specify an error code:

```python
raise APIException(
    detail="Payment processing failed.",
    code="payment_failed"
)
```

## Complete practical example

```python
from rest_framework.exceptions import APIException
from rest_framework import status
from rest_framework.views import APIView
from rest_framework.response import Response


class PaymentGatewayError(APIException):
    status_code = status.HTTP_503_SERVICE_UNAVAILABLE
    default_detail = "Payment gateway is unavailable."
    default_code = "payment_gateway_error"


class PaymentView(APIView):

    def post(self, request):

        payment_success = False

        if not payment_success:
            raise PaymentGatewayError()

        return Response({
            "message": "Payment successful"
        })
```

Response:

```json
{
    "detail": "Payment gateway is unavailable."
}
```

Status:

```http
503 Service Unavailable
```

## When should you use APIException?

Use it when you need a controlled API error or want to define a custom exception.

## When should you not use APIException?

Do not use it for every possible Python error.

For example, avoid catching all exceptions and converting them into a 400 response. A programming bug, database outage, and invalid client input are different problems.

Unexpected exceptions should normally remain server errors and be logged appropriately.

# 2. ValidationError

## What is ValidationError?

`ValidationError` is raised when the data submitted by a client does not satisfy validation rules.

It is commonly used with serializers.

Example:

A product requires:

- A name.
- A positive price.
- A valid category.

If the client submits a negative price, validation should fail.

## Why do we use ValidationError?

Use it to validate:

- Required fields.
- Email addresses.
- Phone numbers.
- Numeric ranges.
- Business rules.
- Relationships between fields.
- Custom application conditions.

## Important ValidationError features

### 1. `detail`

Contains the validation error message or dictionary of errors.

Example:

```python
from rest_framework.exceptions import ValidationError

raise ValidationError({
    "price": "Price must be greater than zero."
})
```

Response:

```json
{
    "price": [
        "Price must be greater than zero."
    ]
}
```

### 2. `code`

Specifies a machine-readable validation error code.

Example:

```python
raise ValidationError(
    "Price must be greater than zero.",
    code="invalid_price"
)
```

### 3. Field-level validation: `validate_<field_name>()`

Use this method to validate one serializer field.

Example:

```python
from rest_framework import serializers


class ProductSerializer(serializers.Serializer):

    name = serializers.CharField(max_length=100)
    price = serializers.DecimalField(
        max_digits=10,
        decimal_places=2
    )

    def validate_price(self, value):

        if value <= 0:
            raise serializers.ValidationError(
                "Price must be greater than zero."
            )

        return value
```

Here, `value` is the submitted price.

### 4. Object-level validation: `validate()`

Use `validate()` when validation depends on multiple fields.

Example:

```python
class BookingSerializer(serializers.Serializer):

    start_date = serializers.DateField()
    end_date = serializers.DateField()

    def validate(self, attrs):

        if attrs["end_date"] < attrs["start_date"]:
            raise serializers.ValidationError({
                "end_date": "End date cannot be before start date."
            })

        return attrs
```

`attrs` contains the validated values of the serializer fields.

## Complete practical example

```python
from rest_framework import serializers
from rest_framework.views import APIView
from rest_framework.response import Response


class ProductSerializer(serializers.Serializer):

    name = serializers.CharField(max_length=100)
    price = serializers.DecimalField(
        max_digits=10,
        decimal_places=2
    )

    def validate_price(self, value):

        if value <= 0:
            raise serializers.ValidationError(
                "Price must be positive."
            )

        return value


class ProductView(APIView):

    def post(self, request):

        serializer = ProductSerializer(data=request.data)

        serializer.is_valid(raise_exception=True)

        return Response({
            "message": "Product created",
            "data": serializer.validated_data
        })
```

Invalid request:

```json
{
    "name": "Laptop",
    "price": -100
}
```

Response:

```json
{
    "price": [
        "Price must be positive."
    ]
}
```

Status:

```http
400 Bad Request
```

## When should you use ValidationError?

Use it for invalid client input and failed business validation.

## When should you not use ValidationError?

Do not use it for missing database records, authentication failures, or permission failures.

Use the appropriate exception for those situations.

# 3. NotFound

## What is NotFound?

`NotFound` represents an HTTP 404 error.

It means the requested resource does not exist or cannot be found.

Example:

```http
GET /api/products/500/
```

If product 500 does not exist, return 404.

## Why do we use NotFound?

Use it when:

- A product does not exist.
- An order cannot be found.
- A user profile is unavailable.
- A requested resource does not exist.

## Important attributes

### 1. `detail`

Defines the error message.

Example:

```python
from rest_framework.exceptions import NotFound

raise NotFound(
    detail="Product does not exist."
)
```

### 2. `code`

Defines a machine-readable error code.

Example:

```python
raise NotFound(
    detail="Product does not exist.",
    code="product_not_found"
)
```

## Complete practical example

```python
from rest_framework.views import APIView
from rest_framework.response import Response
from rest_framework.exceptions import NotFound
from rest_framework import status

from .models import Product


class ProductDetailView(APIView):

    def get(self, request, pk):

        try:
            product = Product.objects.get(pk=pk)

        except Product.DoesNotExist:
            raise NotFound(
                detail="Product not found.",
                code="product_not_found"
            )

        return Response({
            "id": product.id,
            "name": product.name
        })
```

## Alternative: `get_object_or_404()`

Django provides a shortcut that raises `Http404` when an object is missing.

DRF handles `Http404` and converts it into an API 404 response.

Example:

```python
from django.shortcuts import get_object_or_404

product = get_object_or_404(Product, pk=pk)
```

## When should you use NotFound?

Use it when a requested resource cannot be found.

## When should you not use NotFound?

Do not return 404 simply because the client submitted invalid data.

Use `ValidationError` for invalid input.

Also, in security-sensitive applications, returning 404 instead of 403 can sometimes be intentional to avoid revealing whether a protected resource exists.

# 4. PermissionDenied

## What is PermissionDenied?

`PermissionDenied` represents an HTTP 403 error.

It means the request is understood, but the user is not allowed to perform the requested operation.

Example:

A normal user attempts to delete an administrator-only resource.

## Why do we use PermissionDenied?

Use it when:

- A user lacks the required role.
- A user cannot access another user's resource.
- A user is not allowed to delete a record.
- A user lacks a required permission.

## Important attributes

### 1. `detail`

Defines the permission error message.

Example:

```python
from rest_framework.exceptions import PermissionDenied

raise PermissionDenied(
    detail="You cannot delete this product."
)
```

### 2. `code`

Defines the machine-readable error code.

Example:

```python
raise PermissionDenied(
    detail="You cannot delete this product.",
    code="delete_not_allowed"
)
```

## Complete practical example

```python
from rest_framework.views import APIView
from rest_framework.response import Response
from rest_framework.exceptions import PermissionDenied
from rest_framework import status

from .models import Product


class ProductDeleteView(APIView):

    def delete(self, request, pk):

        product = Product.objects.get(pk=pk)

        if product.owner_id != request.user.id:
            raise PermissionDenied(
                "You cannot delete another user's product."
            )

        product.delete()

        return Response(
            {"message": "Product deleted"},
            status=status.HTTP_200_OK
        )
```

In production, handle the missing product with `get_object_or_404()` or `NotFound`.

## When should you use PermissionDenied?

Use it when an authenticated user is not authorized to perform an action.

## When should you not use PermissionDenied?

Do not use it for an unauthenticated request that needs authentication.

Use `AuthenticationFailed` or the appropriate authentication behavior instead.

# 5. AuthenticationFailed

## What is AuthenticationFailed?

`AuthenticationFailed` represents an HTTP 401 Unauthorized response.

It means the authentication process failed.

Examples:

- Invalid username or password.
- Invalid authentication token.
- Expired or invalid credentials.
- Invalid authentication signature.

## Why do we use AuthenticationFailed?

Use it when the application cannot establish the identity of the client.

## Important attributes

### 1. `detail`

Defines the authentication error message.

Example:

```python
from rest_framework.exceptions import AuthenticationFailed

raise AuthenticationFailed(
    "Invalid authentication credentials."
)
```

### 2. `code`

Defines the machine-readable error code.

Example:

```python
raise AuthenticationFailed(
    detail="Token has expired.",
    code="token_expired"
)
```

## Complete practical example

```python
from rest_framework.authentication import BaseAuthentication
from rest_framework.exceptions import AuthenticationFailed


class CustomTokenAuthentication(BaseAuthentication):

    def authenticate(self, request):

        token = request.headers.get("Authorization")

        if not token:
            return None

        if token != "valid-demo-token":
            raise AuthenticationFailed(
                "Invalid token.",
                code="invalid_token"
            )

        # Demonstration only:
        # Real authentication must verify a securely issued token
        # and return an actual authenticated user.
        user = get_user_from_verified_token(token)

        return (user, token)
```

`get_user_from_verified_token()` represents application-specific token verification. It is not a built-in DRF function.

## Important: 401 vs 403

| Status | Meaning |
|---|---|
| 401 Unauthorized | Authentication is missing or failed |
| 403 Forbidden | The request is authenticated, but access is not allowed |

The exact response for unauthenticated requests can depend on the configured authentication class and its `WWW-Authenticate` behavior.

## When should you use AuthenticationFailed?

Use it when credentials are provided but cannot be authenticated.

## When should you not use AuthenticationFailed?

Do not use it for an authenticated user who lacks permission. Use `PermissionDenied`.

# 6. Custom Exception Handlers

## What is a custom exception handler?

A custom exception handler allows us to control the format of error responses returned by DRF.

By default, DRF may return different error structures depending on the exception.

For example, a validation error:

```json
{
    "email": [
        "Enter a valid email address."
    ]
}
```

A not-found error:

```json
{
    "detail": "Not found."
}
```

An application may want every error to follow the same structure.

For example:

```json
{
    "success": false,
    "status_code": 404,
    "message": "Product not found.",
    "errors": null
}
```

## Why do we use custom exception handlers?

- To standardize API errors.
- To make frontend error handling easier.
- To include consistent status codes.
- To provide machine-readable error codes.
- To centralize error formatting.
- To log unexpected application errors separately.

## Important configuration

### 1. `EXCEPTION_HANDLER`

This DRF setting identifies the custom exception handler.

Example:

```python
REST_FRAMEWORK = {
    "EXCEPTION_HANDLER": "core.exceptions.custom_exception_handler"
}
```

### 2. `context`

The exception handler receives a context dictionary.

It commonly includes:

- `request`: The current request.
- `view`: The view that raised the exception.
- `args`: Positional view arguments.
- `kwargs`: Keyword view arguments.

Example:

```python
def custom_exception_handler(exc, context):

    request = context.get("request")
    view = context.get("view")

    response = exception_handler(exc, context)

    return response
```

### 3. `exception_handler`

DRF provides a default exception handler.

Import it using:

```python
from rest_framework.views import exception_handler
```

Calling it allows your custom handler to preserve DRF's standard exception conversion.

## Complete custom exception handler

Create:

`core/exceptions.py`

```python
from rest_framework.views import exception_handler


def custom_exception_handler(exc, context):

    response = exception_handler(exc, context)

    # Let unexpected exceptions remain unexpected server errors.
    # They should be logged by the application's error monitoring.
    if response is None:
        return None

    error_data = {
        "success": False,
        "status_code": response.status_code,
        "message": "Request failed.",
        "errors": response.data
    }

    response.data = error_data

    return response
```

Configure it in `settings.py`:

```python
REST_FRAMEWORK = {
    "EXCEPTION_HANDLER": "core.exceptions.custom_exception_handler"
}
```

Now a 404 response might look like:

```json
{
    "success": false,
    "status_code": 404,
    "message": "Request failed.",
    "errors": {
        "detail": "Not found."
    }
}
```

A validation error might look like:

```json
{
    "success": false,
    "status_code": 400,
    "message": "Request failed.",
    "errors": {
        "email": [
            "Enter a valid email address."
        ]
    }
}
```

## Important limitation

A DRF custom exception handler handles exceptions raised during DRF's exception-handling process.

It does not automatically wrap every possible response.

For example, this response is not an exception:

```python
return Response(
    {"message": "Product created"},
    status=201
)
```

It will not automatically be converted into your error structure.

If you want a standardized success response too, implement that separately.

## When should you use a custom exception handler?

Use it when multiple API endpoints need a consistent error response format.

## When should you not use one?

Avoid adding unnecessary complexity to a small API that already has a clear and consistent error format.

Also, never expose internal stack traces, SQL queries, passwords, tokens, or sensitive server details in API errors.

# 7. Standardized API Error Responses

## What does standardized error response mean?

It means every API returns errors using a predictable structure.

Without standardization, different endpoints might return:

```json
{
    "detail": "Not found."
}
```

Another endpoint might return:

```json
{
    "email": [
        "Invalid email."
    ]
}
```

Another might return:

```json
{
    "message": "Something failed."
}
```

A standardized structure makes frontend development easier.

## Recommended error response structure

```json
{
    "success": false,
    "status_code": 400,
    "error_code": "validation_error",
    "message": "The submitted data is invalid.",
    "errors": {
        "email": [
            "Enter a valid email address."
        ]
    }
}
```

## Meaning of each attribute

### 1. `success`

Indicates whether the request succeeded.

Example:

```json
{
    "success": false
}
```

### 2. `status_code`

Contains the HTTP status code.

Example:

```json
{
    "status_code": 400
}
```

### 3. `error_code`

Contains a stable machine-readable code.

Example:

```json
{
    "error_code": "invalid_email"
}
```

### 4. `message`

Contains a human-readable summary.

Example:

```json
{
    "message": "The submitted email is invalid."
}
```

### 5. `errors`

Contains field-specific or general error details.

Example:

```json
{
    "errors": {
        "email": [
            "Enter a valid email address."
        ]
    }
}
```

## Complete standardized handler

```python
from rest_framework.views import exception_handler


def custom_exception_handler(exc, context):

    response = exception_handler(exc, context)

    if response is None:
        return None

    data = response.data

    error_code = getattr(exc, "default_code", "error")

    if isinstance(data, dict) and "detail" in data:
        message = str(data["detail"])
    else:
        message = "The submitted data is invalid."

    response.data = {
        "success": False,
        "status_code": response.status_code,
        "error_code": error_code,
        "message": message,
        "errors": data
    }

    return response
```

This is a basic implementation. For production, you may want to extract DRF's nested error codes and normalize messages more carefully, particularly for nested serializers and list errors.

## Example: validation error

```json
{
    "success": false,
    "status_code": 400,
    "error_code": "invalid",
    "message": "The submitted data is invalid.",
    "errors": {
        "price": [
            "Ensure this value is greater than or equal to 0."
        ]
    }
}
```

## Example: permission error

```json
{
    "success": false,
    "status_code": 403,
    "error_code": "permission_denied",
    "message": "You do not have permission to perform this action.",
    "errors": {
        "detail": "You do not have permission to perform this action."
    }
}
```

## Best practices

- Use consistent field names.
- Use stable machine-readable error codes.
- Return the correct HTTP status.
- Keep messages understandable.
- Do not expose sensitive information.
- Log unexpected server errors internally.
- Document the error format in your API schema.

# Part 2: DRF API Security

# 8. CORS Configuration

## What is CORS?

CORS stands for Cross-Origin Resource Sharing.

It is a browser security mechanism that controls whether a website from one origin can access resources from another origin.

An origin consists of:

- Scheme: `http` or `https`.
- Hostname: `example.com`.
- Port: `8000`, `3000`, etc.

For example:

Frontend:

```text
http://localhost:3000
```

Backend:

```text
http://localhost:8000
```

These are different origins because their ports are different.

The browser may block frontend JavaScript from reading the backend response unless the backend allows that origin through CORS headers.

## Why do we use CORS?

Use CORS when your frontend and backend run on different origins.

Examples:

- React frontend and Django backend.
- Angular frontend and Django REST API.
- A mobile/web application using an API hosted on another domain.

## Important: CORS is not authentication

CORS does not stop curl, Postman, or server-to-server clients from calling your API.

It is primarily enforced by browsers.

It is also not a replacement for authentication, permissions, or CSRF protection.

## How to configure CORS

Install:

```bash
pip install django-cors-headers
```

### 1. `INSTALLED_APPS`

Registers the CORS package with Django.

Example:

```python
INSTALLED_APPS = [
    "corsheaders",
    "django.contrib.admin",
    "django.contrib.auth",
    "django.contrib.contenttypes",
]
```

### 2. `MIDDLEWARE`

Registers the middleware that adds CORS headers.

Example:

```python
MIDDLEWARE = [
    "corsheaders.middleware.CorsMiddleware",
    "django.middleware.common.CommonMiddleware",
    "django.middleware.security.SecurityMiddleware",
]
```

Place `CorsMiddleware` high enough in the middleware list, especially before middleware that may generate responses.

### 3. `CORS_ALLOWED_ORIGINS`

Specifies which origins are allowed.

Example:

```python
CORS_ALLOWED_ORIGINS = [
    "http://localhost:3000",
    "https://frontend.example.com",
]
```

Only these origins are allowed to access the API through browser JavaScript.

### 4. `CORS_ALLOW_ALL_ORIGINS`

Allows requests from all origins.

Example:

```python
CORS_ALLOW_ALL_ORIGINS = True
```

This is generally inappropriate for production APIs unless you have a specific reason and understand the consequences.

Prefer an explicit allowlist.

### 5. `CORS_ALLOW_CREDENTIALS`

Allows browser requests to include credentials such as cookies.

Example:

```python
CORS_ALLOW_CREDENTIALS = True
```

When credentials are allowed, you cannot use `*` as the allowed origin. Use explicit origins.

### 6. `CORS_ALLOW_METHODS`

Controls which HTTP methods are allowed by CORS.

Example:

```python
from corsheaders.defaults import default_methods

CORS_ALLOW_METHODS = (
    *default_methods,
    "PATCH",
)
```

Common methods include GET, POST, PUT, PATCH, and DELETE.

### 7. `CORS_ALLOW_HEADERS`

Controls which request headers are permitted.

Example:

```python
from corsheaders.defaults import default_headers

CORS_ALLOW_HEADERS = (
    *default_headers,
    "x-request-id",
)
```

### 8. `CORS_EXPOSE_HEADERS`

Specifies which response headers browser JavaScript is allowed to read.

Example:

```python
CORS_EXPOSE_HEADERS = [
    "X-Request-ID",
]
```

## Complete practical configuration

```python
INSTALLED_APPS = [
    "corsheaders",
    "rest_framework",
]

MIDDLEWARE = [
    "corsheaders.middleware.CorsMiddleware",
    "django.middleware.common.CommonMiddleware",
    "django.middleware.security.SecurityMiddleware",
]

CORS_ALLOWED_ORIGINS = [
    "http://localhost:3000",
    "https://frontend.example.com",
]

CORS_ALLOW_CREDENTIALS = True
```

## When should you use CORS?

Use it when browser-based clients access your API from a different origin.

## When should you not use CORS?

Do not enable permissive CORS just to fix authentication or permission problems.

CORS does not grant users access to protected API resources.

# 9. CSRF Protection

## What is CSRF?

CSRF stands for Cross-Site Request Forgery.

It is an attack in which a malicious website tricks a user's browser into sending an unwanted request to another website where the user is already authenticated.

For example:

1. A user logs into a banking application.
2. The browser stores the session cookie.
3. The user visits a malicious website.
4. That website attempts to trigger a money-transfer request.
5. The browser may automatically attach the banking session cookie.

CSRF protection helps prevent this attack.

## Why do we use CSRF protection?

It is particularly important when authentication uses browser cookies or Django sessions.

## How does CSRF protection work?

Django uses a CSRF token.

For unsafe methods such as POST, PUT, PATCH, and DELETE, the client must provide a valid token when CSRF protection applies.

The token is commonly sent in a request header:

```http
X-CSRFToken: your-csrf-token
```

## Important CSRF settings and attributes

### 1. `CSRF_COOKIE_NAME`

Controls the name of the CSRF cookie.

Example:

```python
CSRF_COOKIE_NAME = "csrftoken"
```

### 2. `CSRF_HEADER_NAME`

Controls the request header Django reads for the CSRF token.

Example:

```python
CSRF_HEADER_NAME = "HTTP_X_CSRFTOKEN"
```

Django uses the `HTTP_`-prefixed internal header name.

### 3. `CSRF_TRUSTED_ORIGINS`

Specifies trusted origins for relevant CSRF origin checks.

Example:

```python
CSRF_TRUSTED_ORIGINS = [
    "https://frontend.example.com",
]
```

Include schemes such as `https://`.

This setting does not replace the CSRF token requirement.

### 4. `CSRF_COOKIE_SECURE`

Ensures the CSRF cookie is sent only over HTTPS.

Example:

```python
CSRF_COOKIE_SECURE = True
```

### 5. `CSRF_COOKIE_HTTPONLY`

Controls whether JavaScript can read the CSRF cookie.

Example:

```python
CSRF_COOKIE_HTTPONLY = False
```

A frontend that reads the CSRF cookie and copies it into a request header generally needs JavaScript access to the cookie. Alternatively, the application can provide the token through another secure mechanism.

### 6. `CSRF_COOKIE_SAMESITE`

Controls when the browser sends the CSRF cookie in cross-site contexts.

Example:

```python
CSRF_COOKIE_SAMESITE = "Lax"
```

Common values are `"Lax"`, `"Strict"`, and `"None"`.

`"None"` requires secure cookie handling in modern browsers.

## Example frontend request

```javascript
fetch("https://api.example.com/api/orders/", {
    method: "POST",
    credentials: "include",
    headers: {
        "Content-Type": "application/json",
        "X-CSRFToken": csrfToken
    },
    body: JSON.stringify({
        product_id: 10
    })
});
```

`credentials: "include"` tells the browser to include credentials such as cookies in a cross-origin request, subject to browser cookie and CORS rules.

## DRF authentication and CSRF

DRF's `SessionAuthentication` enforces CSRF checks for authenticated session-based requests.

Token-based authentication generally does not rely on browser session cookies in the same way, but the overall application must still be designed carefully.

Do not disable CSRF globally just because an API uses DRF.

## When should you use CSRF protection?

Use it when browser authentication relies on cookies or sessions.

## When should you not disable CSRF?

Do not disable it to work around a frontend integration issue without understanding the authentication mechanism.

# 10. SQL Injection Prevention

## What is SQL Injection?

SQL Injection occurs when an attacker manipulates a database query through untrusted input.

Unsafe example:

```python
query = "SELECT * FROM products WHERE name = '" + name + "'"
```

If the input contains malicious SQL, it may alter the intended query.

## Why is SQL Injection dangerous?

An attacker may be able to:

- Read unauthorized records.
- Modify records.
- Delete data.
- Bypass application restrictions.
- Access sensitive information.

## How does Django prevent SQL Injection?

Django ORM uses parameterized queries for normal ORM operations.

Safe example:

```python
Product.objects.filter(name=name)
```

Django treats `name` as a value, not as SQL syntax.

## Important ORM methods and safe usage

### 1. `filter()`

Filters records using ORM parameters.

Example:

```python
Product.objects.filter(price__gte=100)
```

### 2. `exclude()`

Excludes records matching a condition.

Example:

```python
Product.objects.exclude(status="deleted")
```

### 3. `get()`

Retrieves one matching object.

Example:

```python
Product.objects.get(pk=10)
```

### 4. `raw()`

Executes raw SQL. Use it only when necessary and parameterize values.

Unsafe:

```python
Product.objects.raw(
    f"SELECT * FROM shop_product WHERE name = '{name}'"
)
```

Safe:

```python
Product.objects.raw(
    "SELECT * FROM shop_product WHERE name = %s",
    [name]
)
```

The placeholder syntax depends on the database driver; Django's supported raw-query interface uses `%s` placeholders.

### 5. `RawSQL`

Allows raw SQL expressions inside ORM queries.

Example:

```python
from django.db.models.expressions import RawSQL

Product.objects.annotate(
    custom_value=RawSQL(
        "price * %s",
        [2]
    )
)
```

The value `2` is passed separately from the SQL expression.

## Important security rule: never trust user-supplied field names

This is dangerous:

```python
field = request.query_params.get("sort")
queryset = Product.objects.order_by(field)
```

A safer approach is to allow only known fields:

```python
allowed_fields = {
    "name",
    "price",
    "created_at",
}

field = request.query_params.get("sort", "name")

if field not in allowed_fields:
    raise ValidationError("Invalid sort field.")

queryset = Product.objects.order_by(field)
```

Also validate whether descending order is allowed, for example by explicitly handling a leading `-`.

## When should you use ORM queries?

Use Django ORM for normal database operations.

## When should you use raw SQL?

Use raw SQL only when the ORM cannot express a required query efficiently or clearly.

Always parameterize values and carefully review SQL structure.

# 11. XSS Protection

## What is XSS?

XSS stands for Cross-Site Scripting.

It occurs when an attacker injects malicious JavaScript into content that is later executed in another user's browser.

Example malicious input:

```html
<script>alert("Hacked")</script>
```

If an application displays this input as executable HTML, it may run in the browser.

## Why is XSS dangerous?

An attacker may:

- Steal accessible session information.
- Perform actions as the victim.
- Modify displayed content.
- Redirect users.
- Capture sensitive data entered into a page.

## How can Django and DRF help prevent XSS?

### 1. Django template autoescaping

Django templates escape HTML by default.

Example:

```django
<p>{{ product.name }}</p>
```

If the product name contains HTML or script content, it is normally rendered as escaped text.

Avoid using `safe` on untrusted data.

Unsafe:

```django
{{ product.name|safe }}
```

### 2. Do not trust API input

DRF serializers validate data types and business rules, but they do not automatically make every string safe to insert into HTML.

Example:

```python
class CommentSerializer(serializers.Serializer):
    comment = serializers.CharField(max_length=1000)
```

The application must still handle the comment safely when displaying it.

### 3. Frontend output encoding

When displaying API data in a browser, use safe text-rendering mechanisms.

React example:

```jsx
function Comment({ text }) {
    return <p>{text}</p>;
}
```

Avoid inserting untrusted HTML with `dangerouslySetInnerHTML`.

### 4. HTML sanitization

If users are allowed to submit rich HTML, sanitize it with a trusted HTML sanitization library and a strict allowlist.

Do not assume that basic serializer validation sanitizes HTML.

### 5. Content Security Policy

A Content Security Policy (CSP) can restrict which scripts and resources the browser is allowed to load.

Example policy:

```http
Content-Security-Policy: default-src 'self'; script-src 'self'
```

Deploy CSP carefully because an overly restrictive policy can break legitimate frontend functionality.

## When should you use HTML sanitization?

Use it when your application intentionally accepts rich HTML, such as formatted articles or comments.

## When should you not sanitize everything?

Do not blindly strip all HTML from every field. Some applications legitimately store formatted content.

The key is to encode output correctly and sanitize HTML only when HTML is intentionally permitted.

# 12. Secure Password Handling

## What is secure password handling?

It means storing, validating, and verifying passwords without exposing the original password.

Passwords should never be stored as plain text.

Unsafe example:

```python
user.password = "mypassword123"
```

## Why do we hash passwords?

If a database is compromised, attackers should not be able to immediately read every user's password.

Password hashing is designed to make recovering the original password computationally difficult.

## Django password handling

Django provides built-in password hashing and verification.

### 1. `set_password()`

Hashes a password and stores the resulting encoded value on the user object.

Example:

```python
user.set_password("StrongPassword123!")
user.save()
```

### 2. `check_password()`

Verifies a submitted password against the stored hash.

Example:

```python
if user.check_password("StrongPassword123!"):
    print("Password is correct")
```

### 3. `make_password()`

Creates a password hash without requiring an existing user instance.

Example:

```python
from django.contrib.auth.hashers import make_password

hashed_password = make_password("StrongPassword123!")
```

### 4. `check_password()` helper

Django also provides a standalone password verification helper.

Example:

```python
from django.contrib.auth.hashers import check_password

is_valid = check_password(
    "StrongPassword123!",
    hashed_password
)
```

### 5. `AUTH_PASSWORD_VALIDATORS`

Configures Django's password validation rules.

Example:

```python
AUTH_PASSWORD_VALIDATORS = [
    {
        "NAME": "django.contrib.auth.password_validation.UserAttributeSimilarityValidator",
    },
    {
        "NAME": "django.contrib.auth.password_validation.MinimumLengthValidator",
        "OPTIONS": {
            "min_length": 12,
        },
    },
    {
        "NAME": "django.contrib.auth.password_validation.CommonPasswordValidator",
    },
    {
        "NAME": "django.contrib.auth.password_validation.NumericPasswordValidator",
    },
]
```

What these validators do:

- `UserAttributeSimilarityValidator`: Checks whether the password is too similar to user attributes.
- `MinimumLengthValidator`: Enforces a minimum password length.
- `CommonPasswordValidator`: Rejects commonly used passwords.
- `NumericPasswordValidator`: Rejects passwords consisting entirely of numbers.

### 6. `validate_password()`

Runs the configured password validators.

Example:

```python
from django.contrib.auth.password_validation import validate_password

validate_password("StrongPassword123!", user)
```

## Complete registration example

```python
from django.contrib.auth import get_user_model
from django.contrib.auth.password_validation import validate_password
from rest_framework import serializers

User = get_user_model()


class RegisterSerializer(serializers.ModelSerializer):

    password = serializers.CharField(
        write_only=True
    )

    class Meta:
        model = User
        fields = ["username", "email", "password"]

    def validate_password(self, value):

        validate_password(value)

        return value

    def create(self, validated_data):

        password = validated_data.pop("password")

        user = User(**validated_data)
        user.set_password(password)
        user.save()

        return user
```

## Important password security practices

- Never store plain-text passwords.
- Never return passwords in API responses.
- Use Django's password hashing framework.
- Use HTTPS.
- Avoid logging passwords.
- Apply rate limiting to login endpoints.
- Use secure password reset workflows.
- Do not invent your own password hashing algorithm.
- Consider multi-factor authentication for sensitive applications.

## When should you use set_password()?

Whenever creating or changing a Django user's password.

## When should you not assign directly to `user.password`?

Never assign a raw password directly to the password field.

# Part 3: DRF Rate Limiting and Throttling

# 13. Rate Limiting and Throttling

## What is rate limiting?

Rate limiting restricts how many requests a client can make within a specified time period.

Example:

```text
A user can make 100 requests per hour.
```

If the user exceeds the limit, the API returns:

```http
429 Too Many Requests
```

## What is throttling in DRF?

DRF provides throttling classes to control API request rates.

Throttling can be applied globally or to individual views.

## Why do we use throttling?

- Reduce accidental excessive requests.
- Limit API abuse.
- Protect expensive endpoints.
- Reduce resource consumption.
- Apply different limits to different user groups.

## Important DRF settings

### 1. `DEFAULT_THROTTLE_CLASSES`

Defines the default throttling classes.

Example:

```python
REST_FRAMEWORK = {
    "DEFAULT_THROTTLE_CLASSES": [
        "rest_framework.throttling.AnonRateThrottle",
        "rest_framework.throttling.UserRateThrottle",
    ]
}
```

### 2. `DEFAULT_THROTTLE_RATES`

Defines request rates.

Example:

```python
REST_FRAMEWORK = {
    "DEFAULT_THROTTLE_RATES": {
        "anon": "20/hour",
        "user": "100/hour",
    }
}
```

The first value is the request count; the second is the time period.

Supported periods include seconds, minutes, hours, and days.

### 3. `throttle_classes`

Overrides the throttling classes for an individual view.

Example:

```python
from rest_framework.views import APIView
from rest_framework.throttling import UserRateThrottle


class ProductView(APIView):

    throttle_classes = [UserRateThrottle]
```

### 4. `throttle_scope`

Identifies a named rate limit for scoped throttling.

Example:

```python
class PaymentView(APIView):

    throttle_scope = "payments"
```

The matching rate must be configured in `DEFAULT_THROTTLE_RATES`.

## Example global configuration

```python
REST_FRAMEWORK = {
    "DEFAULT_THROTTLE_CLASSES": [
        "rest_framework.throttling.AnonRateThrottle",
        "rest_framework.throttling.UserRateThrottle",
    ],

    "DEFAULT_THROTTLE_RATES": {
        "anon": "20/hour",
        "user": "100/hour",
    }
}
```

When a client exceeds its configured limit, DRF normally returns a 429 response.

## Important limitation

DRF throttling is not a complete DDoS protection system.

Its built-in throttles use Django's cache and are not designed to provide precise, distributed request accounting under high concurrency.

For serious abuse prevention, combine application throttling with infrastructure-level controls such as a reverse proxy, API gateway, or WAF.

---

# 14. AnonRateThrottle

## What is AnonRateThrottle?

`AnonRateThrottle` limits requests from unauthenticated users.

Example:

```text
Anonymous user: 20 requests per hour.
```

It is useful for public API endpoints.

## Important attributes

### 1. `scope`

Defines the name used to look up the rate.

The default scope is:

```python
scope = "anon"
```

Example:

```python
class PublicThrottle(AnonRateThrottle):
    scope = "public"
```

### 2. `rate`

Can define the rate directly on a throttle class.

Example:

```python
class PublicThrottle(AnonRateThrottle):
    rate = "10/minute"
```

If `rate` is not defined on the class, DRF looks up the rate using the throttle scope in `DEFAULT_THROTTLE_RATES`.

### 3. `get_cache_key()`

Determines the cache key used to track requests.

Example override:

```python
def get_cache_key(self, request, view):

    if request.user and request.user.is_authenticated:
        return None

    return self.cache_format % {
        "scope": self.scope,
        "ident": self.get_ident(request)
    }
```

Returning `None` means this throttle does not apply to that request.

## Complete example

```python
from rest_framework.views import APIView
from rest_framework.response import Response
from rest_framework.throttling import AnonRateThrottle


class PublicAPIRateThrottle(AnonRateThrottle):
    rate = "10/minute"


class PublicProductView(APIView):

    throttle_classes = [PublicAPIRateThrottle]

    def get(self, request):

        return Response({
            "message": "Public product list"
        })
```

## When should you use AnonRateThrottle?

Use it for public endpoints where users do not need to log in.

Examples:

- Public product listing.
- Public search.
- Public information APIs.
- Public registration endpoints.

## When should you not use it?

Do not rely on anonymous throttling alone to protect authenticated endpoints.

Use `UserRateThrottle` or `ScopedRateThrottle` where appropriate.

---

# 15. UserRateThrottle

## What is UserRateThrottle?

`UserRateThrottle` limits the number of requests made by an authenticated user.

Each authenticated user receives a separate request limit.

Example:

```text
User A: 100 requests per hour.
User B: 100 requests per hour.
```

One user's requests do not normally consume another user's quota.

## Important attributes

### 1. `scope`

Identifies the configured rate.

Default:

```python
scope = "user"
```

Example:

```python
class PremiumUserThrottle(UserRateThrottle):
    scope = "premium"
```

### 2. `rate`

Defines the request limit directly.

Example:

```python
class PremiumUserThrottle(UserRateThrottle):
    rate = "500/hour"
```

### 3. `get_cache_key()`

Determines the cache key used to identify the user.

Example:

```python
def get_cache_key(self, request, view):

    if not request.user or not request.user.is_authenticated:
        return None

    return self.cache_format % {
        "scope": self.scope,
        "ident": request.user.pk
    }
```

The default implementation already handles user identification. Override it only when you need different behavior.

## Complete example

```python
from rest_framework.views import APIView
from rest_framework.response import Response
from rest_framework.throttling import UserRateThrottle


class PremiumUserThrottle(UserRateThrottle):
    rate = "500/hour"


class PremiumProductView(APIView):

    throttle_classes = [PremiumUserThrottle]

    def get(self, request):

        return Response({
            "message": "Premium product data"
        })
```

## When should you use UserRateThrottle?

Use it for authenticated APIs where each user should have an individual request quota.

## When should you not use it?

Do not assume that all users should receive the same rate.

For example, free and premium users may need different limits. Use separate throttle classes or scoped throttling for that.

---

# 16. ScopedRateThrottle

## What is ScopedRateThrottle?

`ScopedRateThrottle` applies different rate limits to different API endpoints or groups of endpoints.

Example:

```text
Product API: 100 requests per hour.
Payment API: 10 requests per hour.
Report API: 20 requests per hour.
```

This is useful when certain operations are more expensive or sensitive.

## Important attributes

### 1. `throttle_scope`

Defines which rate configuration applies to a view.

Example:

```python
class PaymentView(APIView):

    throttle_scope = "payments"
```

### 2. `scope_attr`

Identifies the view attribute used to find the throttle scope.

Its default is:

```python
scope_attr = "throttle_scope"
```

Normally, you do not need to override it.

### 3. `rate`

The rate is obtained from `DEFAULT_THROTTLE_RATES` using the view's scope.

Example:

```python
REST_FRAMEWORK = {
    "DEFAULT_THROTTLE_RATES": {
        "payments": "10/hour",
        "reports": "20/hour",
    }
}
```

### 4. `get_cache_key()`

Creates the cache key used to track requests for the relevant scope and client.

The default implementation handles the standard scoped behavior. Override it only for a specific custom identification requirement.

## Complete practical example

```python
from rest_framework.views import APIView
from rest_framework.response import Response
from rest_framework.throttling import ScopedRateThrottle


class PaymentView(APIView):

    throttle_classes = [ScopedRateThrottle]
    throttle_scope = "payments"

    def post(self, request):

        return Response({
            "message": "Payment request received"
        })


class ReportView(APIView):

    throttle_classes = [ScopedRateThrottle]
    throttle_scope = "reports"

    def get(self, request):

        return Response({
            "message": "Report generated"
        })
```

Settings:

```python
REST_FRAMEWORK = {
    "DEFAULT_THROTTLE_RATES": {
        "payments": "10/hour",
        "reports": "20/hour",
    }
}
```

## When should you use ScopedRateThrottle?

Use it when different API endpoints require different rate limits.

## When should you not use it?

Do not use it if every endpoint has the same rate limit and a simpler throttle class is sufficient.

---

# 17. Custom Throttling Classes

## What is a custom throttle?

A custom throttle is a class that defines your own request-limiting logic.

DRF allows you to extend `BaseThrottle` or `SimpleRateThrottle`.

Use a custom throttle when the built-in throttles do not meet your business requirements.

Examples:

- Limit requests based on an organization.
- Apply a special rate to a particular API key.
- Restrict expensive operations.
- Implement custom client identification.

## Option 1: Extend SimpleRateThrottle

`SimpleRateThrottle` already provides the basic rate-limiting mechanism.

You mainly need to define the scope and cache key.

### Important attributes and methods

#### 1. `scope`

Defines the configured rate name.

Example:

```python
scope = "organization"
```

#### 2. `get_cache_key(request, view)`

Returns a unique key for the client whose requests should be counted.

Example:

```python
def get_cache_key(self, request, view):

    if not request.user.is_authenticated:
        return None

    return self.cache_format % {
        "scope": self.scope,
        "ident": request.user.organization_id
    }
```

#### 3. `rate`

Defines the request rate directly, or the class can use its scope to retrieve a rate from settings.

Example:

```python
rate = "100/hour"
```

## Complete example

```python
from rest_framework.throttling import SimpleRateThrottle


class OrganizationThrottle(SimpleRateThrottle):

    scope = "organization"
    rate = "100/hour"

    def get_cache_key(self, request, view):

        user = request.user

        if not user or not user.is_authenticated:
            return None

        organization_id = getattr(
            user,
            "organization_id",
            None
        )

        if organization_id is None:
            return None

        return self.cache_format % {
            "scope": self.scope,
            "ident": organization_id
        }
```

Apply it:

```python
class OrganizationAPIView(APIView):

    throttle_classes = [OrganizationThrottle]
```

Users belonging to the same organization share the same throttle identity.

Make sure the organization identity comes from authenticated server-side data, not a client-supplied query parameter.

## Option 2: Extend BaseThrottle

Use `BaseThrottle` when you need to implement the full throttling decision yourself.

### Important methods

#### 1. `allow_request(request, view)`

Returns `True` if the request is allowed and `False` if it is throttled.

Example:

```python
def allow_request(self, request, view):
    return True
```

This example allows all requests; real implementations must perform the actual rate check.

#### 2. `wait()`

Returns the approximate number of seconds the client should wait before retrying.

Example:

```python
def wait(self):
    return 30
```

## When should you use a custom throttle?

Use it when you need limits based on a business-specific identity or rule.

## When should you not use a custom throttle?

Do not create one when `AnonRateThrottle`, `UserRateThrottle`, or `ScopedRateThrottle` already solves the problem.

Custom implementations require careful testing, especially with concurrent requests and distributed cache systems.

# Part 4: Additional API Security

# 18. Secure HTTP Headers

## What are secure HTTP headers?

Security headers are HTTP response headers that tell browsers how to handle content and protect users from certain attacks.

They help reduce risks such as:

- Clickjacking.
- MIME-type sniffing.
- Some XSS attack scenarios.
- Insecure resource loading.
- Information leakage.

## Important security headers

### 1. `Strict-Transport-Security`

Also called HSTS.

It tells browsers to use HTTPS for future connections to the domain.

Example:

```http
Strict-Transport-Security: max-age=31536000; includeSubDomains
```

Django setting:

```python
SECURE_HSTS_SECONDS = 31536000
```

`SECURE_HSTS_SECONDS` defines how long the browser should remember the HTTPS requirement.

### 2. `X-Content-Type-Options`

Prevents browsers from interpreting a response as a different content type.

Example:

```http
X-Content-Type-Options: nosniff
```

Django setting:

```python
SECURE_CONTENT_TYPE_NOSNIFF = True
```

### 3. `X-Frame-Options`

Controls whether a page can be embedded in a frame.

Example:

```http
X-Frame-Options: DENY
```

Django setting:

```python
X_FRAME_OPTIONS = "DENY"
```

Use `DENY` when the application should never be framed. If legitimate embedding is required, choose an appropriate alternative and use CSP `frame-ancestors` for modern control.

### 4. `Referrer-Policy`

Controls how much referrer information the browser sends.

Example:

```http
Referrer-Policy: strict-origin-when-cross-origin
```

Django can configure this with:

```python
SECURE_REFERRER_POLICY = "strict-origin-when-cross-origin"
```

### 5. `Content-Security-Policy`

Controls which sources the browser may load scripts, styles, images, and other resources from.

Example:

```http
Content-Security-Policy: default-src 'self'; script-src 'self'
```

CSP needs a policy that matches your frontend architecture. Django does not automatically provide a complete CSP policy simply by enabling security middleware; configure it using an appropriate CSP implementation or your web server.

### 6. `SECURE_SSL_REDIRECT`

Redirects HTTP requests to HTTPS.

Example:

```python
SECURE_SSL_REDIRECT = True
```

Only enable this after HTTPS and reverse-proxy configuration are correct.

### 7. `SESSION_COOKIE_SECURE`

Ensures session cookies are sent only over HTTPS.

Example:

```python
SESSION_COOKIE_SECURE = True
```

### 8. `CSRF_COOKIE_SECURE`

Ensures CSRF cookies are sent only over HTTPS.

Example:

```python
CSRF_COOKIE_SECURE = True
```

## Example production security configuration

```python
DEBUG = False

ALLOWED_HOSTS = [
    "api.example.com",
]

SECURE_SSL_REDIRECT = True

SECURE_HSTS_SECONDS = 31536000

SECURE_CONTENT_TYPE_NOSNIFF = True

SECURE_REFERRER_POLICY = "strict-origin-when-cross-origin"

SESSION_COOKIE_SECURE = True

CSRF_COOKIE_SECURE = True

X_FRAME_OPTIONS = "DENY"
```

Only enable HSTS after confirming HTTPS works correctly across the domain and any relevant subdomains.

## When should you use secure headers?

Use them in production applications, especially those accessed through browsers.

## When should you not blindly copy security header values?

Do not blindly apply policies that break legitimate application behavior.

For example, HSTS with subdomains can affect every subdomain, and a restrictive CSP can block scripts your frontend needs.

Test security headers before deploying them.

# 19. OWASP API Security Risks

## What is OWASP?

OWASP stands for Open Worldwide Application Security Project.

It provides security guidance, tools, and awareness resources for application developers.

The OWASP API Security Top 10 highlights common security risks in APIs.

The list below follows the OWASP API Security Top 10 (2023).

## 1. Broken Object Level Authorization (BOLA)

### What is it?

BOLA occurs when an API allows a user to access another user's object by changing an object ID.

Example:

```http
GET /api/orders/100/
```

A user changes the ID:

```http
GET /api/orders/101/
```

If order 101 belongs to another user and the API returns it, the API has an authorization vulnerability.

### How to prevent it

Always scope objects to the authenticated user or check object-level permissions.

Safe example:

```python
def get_queryset(self):

    return Order.objects.filter(
        user=self.request.user
    )
```

### When is it important?

Whenever users access records identified by IDs, UUIDs, or other object identifiers.

---

## 2. Broken Authentication

### What is it?

Occurs when authentication mechanisms can be bypassed, misconfigured, or abused.

Examples:

- Weak passwords.
- Poor token validation.
- Missing expiration checks.
- Insecure password reset.
- No protection against credential stuffing.

### How to prevent it

- Use secure password hashing.
- Use established authentication libraries.
- Validate token signatures and expiration.
- Apply login throttling.
- Use MFA where appropriate.
- Protect password reset workflows.

---

## 3. Broken Object Property Level Authorization

### What is it?

Occurs when an API exposes or allows modification of object properties that a user should not access.

Example:

A normal user sends:

```json
{
    "name": "John",
    "is_admin": true
}
```

If the serializer accepts the `is_admin` field, a user may be able to grant themselves administrator privileges.

### How to prevent it

Explicitly define serializer fields.

Safe example:

```python
class UserSerializer(serializers.ModelSerializer):

    class Meta:
        model = User
        fields = [
            "id",
            "username",
            "email"
        ]
        read_only_fields = ["id"]
```

Use separate serializers for administrative operations when appropriate.

---

## 4. Unrestricted Resource Consumption

### What is it?

Occurs when an API allows clients to consume excessive resources.

Examples:

- Unlimited requests.
- Huge pagination sizes.
- Expensive search queries.
- Large file uploads.
- Expensive report generation.

### How to prevent it

- Apply throttling.
- Set pagination limits.
- Restrict upload sizes.
- Validate query parameters.
- Set request timeouts.
- Monitor expensive database queries.

Example:

```python
class ProductPagination(PageNumberPagination):

    page_size = 20
    page_size_query_param = "page_size"
    max_page_size = 100
```

---

## 5. Broken Function Level Authorization

### What is it?

Occurs when a user can access functionality intended for another role.

Example:

A normal user accesses:

```http
DELETE /api/admin/users/10/
```

If the API does not check permissions, the user may delete an account.

### How to prevent it

Use permission classes and enforce role-based authorization.

Example:

```python
from rest_framework.permissions import IsAdminUser


class AdminUserView(APIView):

    permission_classes = [IsAdminUser]
```

Remember that `IsAdminUser` checks Django's `is_staff` flag. It does not automatically implement every custom business role.

---

## 6. Unrestricted Access to Sensitive Business Flows

### What is it?

Occurs when attackers abuse legitimate business operations at scale.

Examples:

- Creating thousands of accounts.
- Buying all available stock using automated requests.
- Abusing coupon redemption.
- Repeatedly triggering password reset messages.

### How to prevent it

- Apply business-specific throttling.
- Enforce transaction limits.
- Use fraud detection.
- Require additional verification for sensitive actions.
- Monitor unusual activity.

---

## 7. Server Side Request Forgery (SSRF)

### What is it?

SSRF occurs when an attacker tricks the server into making requests to unintended destinations.

Example:

An API accepts a URL and fetches its content.

```json
{
    "url": "http://internal-service/"
}
```

An attacker may attempt to access internal services or cloud metadata endpoints.

### How to prevent it

- Allowlist permitted domains.
- Block private and internal IP ranges where appropriate.
- Validate redirects and DNS resolution.
- Restrict outbound network access.
- Avoid fetching arbitrary user-provided URLs.

---

## 8. Security Misconfiguration

### What is it?

Occurs when application or infrastructure security settings are unsafe.

Examples:

- `DEBUG = True` in production.
- Weak `ALLOWED_HOSTS` configuration.
- Exposed admin interfaces.
- Missing security headers.
- Default credentials.
- Overly permissive CORS.

### How to prevent it

Example:

```python
DEBUG = False

ALLOWED_HOSTS = [
    "api.example.com",
]
```

Also:

- Keep dependencies updated.
- Store secrets outside source code.
- Review production settings.
- Disable unnecessary services.
- Use HTTPS.

---

## 9. Improper Inventory Management

### What is it?

Occurs when an organization does not properly track its API endpoints and versions.

Examples:

- Old API versions remain accessible.
- Test endpoints are exposed.
- Deprecated APIs are not removed.
- Internal endpoints become public.

### How to prevent it

- Maintain an API inventory.
- Document endpoints and versions.
- Remove obsolete endpoints.
- Restrict internal APIs.
- Scan deployed environments regularly.

---

## 10. Unsafe Consumption of APIs

### What is it?

Occurs when an API trusts data received from third-party APIs without properly validating it.

Example:

Your Django API consumes an external payment provider's response and assumes every returned field is trustworthy.

### How to prevent it

- Validate third-party responses.
- Use HTTPS.
- Verify signatures where required.
- Set timeouts.
- Handle malformed responses.
- Restrict outbound destinations.
- Avoid trusting external data as authorization proof.

# Part 5: Complete DRF Security Configuration Example

The following is a starting point for a production-oriented configuration. Adjust it to your application's authentication, frontend, deployment, and infrastructure requirements.

```python
# settings.py

DEBUG = False

ALLOWED_HOSTS = [
    "api.example.com",
]

INSTALLED_APPS = [
    "django.contrib.admin",
    "django.contrib.auth",
    "django.contrib.contenttypes",
    "django.contrib.sessions",
    "django.contrib.messages",
    "django.contrib.staticfiles",
    "rest_framework",
    "corsheaders",
]

MIDDLEWARE = [
    "django.middleware.security.SecurityMiddleware",
    "corsheaders.middleware.CorsMiddleware",
    "django.contrib.sessions.middleware.SessionMiddleware",
    "django.middleware.common.CommonMiddleware",
    "django.middleware.csrf.CsrfViewMiddleware",
    "django.contrib.auth.middleware.AuthenticationMiddleware",
    "django.contrib.messages.middleware.MessageMiddleware",
]

CORS_ALLOWED_ORIGINS = [
    "https://frontend.example.com",
]

CORS_ALLOW_CREDENTIALS = True

CSRF_TRUSTED_ORIGINS = [
    "https://frontend.example.com",
]

CSRF_COOKIE_SECURE = True
SESSION_COOKIE_SECURE = True

SECURE_SSL_REDIRECT = True
SECURE_HSTS_SECONDS = 31536000
SECURE_CONTENT_TYPE_NOSNIFF = True
SECURE_REFERRER_POLICY = "strict-origin-when-cross-origin"

X_FRAME_OPTIONS = "DENY"


REST_FRAMEWORK = {

    "DEFAULT_AUTHENTICATION_CLASSES": [
        "rest_framework.authentication.SessionAuthentication",
        "rest_framework.authentication.TokenAuthentication",
    ],

    "DEFAULT_PERMISSION_CLASSES": [
        "rest_framework.permissions.IsAuthenticated",
    ],

    "DEFAULT_THROTTLE_CLASSES": [
        "rest_framework.throttling.AnonRateThrottle",
        "rest_framework.throttling.UserRateThrottle",
    ],

    "DEFAULT_THROTTLE_RATES": {
        "anon": "20/hour",
        "user": "100/hour",
        "payments": "10/hour",
    },

    "EXCEPTION_HANDLER": "core.exceptions.custom_exception_handler",
}
```

Important notes:

1. Install and configure the authentication package you actually use. DRF's built-in token authentication requires the relevant token app to be installed and migrated.
2. Do not enable both session and token authentication automatically unless your application needs both.
3. `IsAuthenticated` as a default permission does not replace object-level authorization.
4. CORS and CSRF settings must match the actual frontend and cookie-authentication architecture.
5. HSTS and HTTPS redirects should be enabled only after the production HTTPS and proxy configuration is correct.
6. Configure a suitable shared cache backend for throttling in multi-instance deployments.

# Part 6: Interview Questions and Answers

## 1. What is exception handling in DRF?

Exception handling is the process of catching API errors and converting them into appropriate HTTP responses.

DRF provides built-in exceptions and supports custom exception handlers.

## 2. What is APIException?

`APIException` is the base class for most DRF API exceptions.

It can be extended to create custom exceptions with specific HTTP status codes and error messages.

## 3. What is the difference between ValidationError and NotFound?

`ValidationError` indicates invalid input, usually returning HTTP 400.

`NotFound` indicates that the requested resource cannot be found, returning HTTP 404.

## 4. What is the difference between AuthenticationFailed and PermissionDenied?

`AuthenticationFailed` means the authentication process failed.

`PermissionDenied` means the user is authenticated but is not authorized to perform the operation.

Typical responses are 401 and 403 respectively.

## 5. What is a custom exception handler?

It is a function that controls how DRF converts exceptions into HTTP responses.

It is configured using:

```python
REST_FRAMEWORK = {
    "EXCEPTION_HANDLER": "core.exceptions.custom_exception_handler"
}
```

## 6. Does a custom exception handler handle every response?

No.

It handles exceptions processed by DRF's exception-handling mechanism.

It does not automatically transform ordinary successful responses or every manually returned error response.

## 7. What is the difference between CORS and CSRF?

CORS controls whether browser JavaScript from one origin can access responses from another origin.

CSRF protection prevents unwanted authenticated requests made using a user's browser credentials, particularly cookies.

They solve different security problems.

## 8. Does CORS protect an API from Postman or curl?

No.

CORS is primarily enforced by browsers. Postman, curl, and server-to-server clients do not normally enforce browser CORS restrictions.

## 9. What is CSRF?

CSRF is an attack where a malicious website attempts to make a user's browser perform an unwanted authenticated action on another website.

Django provides CSRF middleware and token validation.

## 10. Does DRF require CSRF protection for every authentication method?

No.

DRF's `SessionAuthentication` enforces CSRF checks for authenticated session-based requests.

Other authentication methods have different security properties. Cookie-based authentication still requires careful CSRF protection.

## 11. What is SQL Injection?

SQL Injection is an attack where untrusted input changes the structure or behavior of a database query.

Use Django ORM or properly parameterized SQL to prevent it.

## 12. Is Django ORM safe from SQL Injection?

Django ORM safely parameterizes normal query values.

However, developers must still be careful with raw SQL, dynamic field names, and other query structures constructed from user input.

## 13. What is XSS?

XSS is an attack where malicious script content is injected into a page and executed in another user's browser.

Prevent it through safe output encoding, appropriate HTML sanitization, and security policies such as CSP.

## 14. Does DRF automatically prevent XSS?

No.

DRF serializers validate incoming data, but they do not automatically make all text safe for every HTML rendering context.

The frontend must render untrusted content safely.

## 15. How does Django store passwords securely?

Django uses password hashing.

Use:

```python
user.set_password("password")
```

Do not store raw passwords directly in the database.

## 16. What is the difference between hashing and encryption?

Hashing is designed to be one-way.

Encryption is designed to be reversible using the appropriate key.

Passwords should normally be stored using secure password hashing, not reversible encryption.

## 17. What is throttling in DRF?

Throttling limits the number of requests a client can make within a time period.

When the limit is exceeded, DRF normally returns HTTP 429.

## 18. What is AnonRateThrottle?

It limits requests from unauthenticated clients.

It is useful for public APIs.

## 19. What is UserRateThrottle?

It limits requests from authenticated users.

Each authenticated user generally has a separate request limit.

## 20. What is ScopedRateThrottle?

It allows different API views to use different named rate limits.

For example, a payment endpoint can have a stricter limit than a product listing endpoint.

## 21. What is the difference between UserRateThrottle and ScopedRateThrottle?

`UserRateThrottle` applies a user-based rate.

`ScopedRateThrottle` applies a configured rate based on a view's throttle scope, with the standard implementation tracking the relevant user or anonymous client identity.

## 22. What is SimpleRateThrottle?

It is a DRF base class that provides much of the standard rate-limiting logic.

Developers can extend it and implement `get_cache_key()` to define how clients are identified.

## 23. What is the difference between BaseThrottle and SimpleRateThrottle?

`BaseThrottle` requires you to implement the throttling decision yourself.

`SimpleRateThrottle` provides the standard rate-limiting mechanism, so you mainly customize the scope and client identification.

## 24. Is DRF throttling sufficient for DDoS protection?

No.

DRF throttling helps control application request rates but is not a complete DDoS defense.

Use infrastructure-level protection such as a WAF, reverse proxy, or API gateway as appropriate.

## 25. What are secure HTTP headers?

They are response headers that instruct browsers to apply security restrictions.

Examples include:

- Strict-Transport-Security
- X-Content-Type-Options
- X-Frame-Options
- Content-Security-Policy
- Referrer-Policy

## 26. What is HSTS?

HTTP Strict Transport Security tells browsers to use HTTPS for future connections to a domain.

It helps prevent downgrade attacks and accidental HTTP access.

## 27. What is Content Security Policy?

CSP is a browser security policy that restricts the sources from which a page can load scripts and other resources.

It helps reduce the impact of certain XSS attacks.

## 28. What is BOLA?

Broken Object Level Authorization occurs when an API does not properly verify whether a user is allowed to access a particular object.

For example, a user changes an order ID and accesses another user's order.

## 29. What is Broken Function Level Authorization?

It occurs when a user can access functionality that should be restricted to another role.

For example, a normal user accesses an administrator-only endpoint.

## 30. What is SSRF?

Server Side Request Forgery occurs when an attacker tricks an application server into making requests to unintended destinations, such as internal services.

Validate and allowlist destinations when fetching user-provided URLs.

## 31. What is the difference between authentication and authorization?

Authentication verifies who the user is.

Authorization determines what the authenticated user is allowed to do.

## 32. How do you secure a DRF API in production?

A strong baseline includes:

1. HTTPS everywhere.
2. Secure password hashing.
3. Appropriate authentication.
4. Object-level and function-level permissions.
5. Serializer validation.
6. SQL injection prevention.
7. Safe frontend output rendering.
8. Correct CORS and CSRF configuration.
9. Rate limiting.
10. Secure HTTP headers.
11. Secret management.
12. Logging and monitoring.
13. Dependency updates.
14. API inventory and version management.

# Final Learning Recommendation

Study these topics in this order:

1. **Exception handling:** Understand APIException, ValidationError, NotFound, PermissionDenied, and AuthenticationFailed.
2. **Standardized errors:** Build a custom exception handler and return a consistent error structure.
3. **Browser security:** Understand CORS and CSRF, especially the difference between them.
4. **Data security:** Learn SQL injection prevention, XSS protection, and secure password handling.
5. **Throttling:** Practice AnonRateThrottle, UserRateThrottle, ScopedRateThrottle, and custom throttles.
6. **Production security:** Configure secure HTTP headers and learn the OWASP API Security Top 10.
7. **Practical project:** Build a small API with authentication, permissions, validation, throttling, standardized errors, and secure deployment settings.

The most important point to remember is that **security is not one DRF setting**. A secure API combines authentication, authorization, input validation, safe database access, browser security, rate limiting, and infrastructure-level protection.
