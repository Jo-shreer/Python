# Django REST Framework (DRF) – Complete Views and Methods Guide

## 1. Understanding the four important view approaches

Django REST Framework provides different ways to build API endpoints.

The four approaches we need to understand are:

1. APIView
2. GenericAPIView
3. GenericAPIView + Mixins
4. Concrete Generic Views

Let's understand their relationship first.

### 1.1 APIView

`APIView` is the foundation for building class-based APIs in DRF.

It provides:
- Request handling.
- Authentication.
- Permission checking.
- Throttling.
- Exception handling.
- Response handling.

It does not automatically provide CRUD operations such as listing, creating, updating, or deleting database records.

You generally write those operations yourself.

### 1.2 GenericAPIView

`GenericAPIView` inherits from `APIView`.

It provides everything from `APIView`, plus reusable functionality for:
- Querysets.
- Serializers.
- Object lookup.
- Filtering.
- Pagination.

However, it does not automatically provide the five CRUD methods:
- `list()`
- `create()`
- `retrieve()`
- `update()`
- `destroy()`

These methods are provided by Mixins.

### 1.3 GenericAPIView + Mixins

Mixins provide reusable CRUD operations.

You combine the mixins you need with `GenericAPIView`.

For example:

```python
class EmployeeListView(
    mixins.ListModelMixin,
    generics.GenericAPIView
):
    queryset = Employee.objects.all()
    serializer_class = EmployeeSerializer

    def get(self, request, *args, **kwargs):
        return self.list(request, *args, **kwargs)
```

Here:
- `GenericAPIView` provides queryset and serializer functionality.
- `ListModelMixin` provides the `list()` method.
- `get()` connects the GET request to `list()`.

### 1.4 Concrete Generic Views

Concrete Generic Views are ready-made combinations of `GenericAPIView`, Mixins, and HTTP method handlers.

For example:

```python
class EmployeeListView(ListAPIView):
    queryset = Employee.objects.all()
    serializer_class = EmployeeSerializer
```

You do not need to write the `get()` method or manually call `self.list()`.

DRF already handles that.

# 2. Common example used throughout this guide

We will use an Employee API to understand all the methods.

### models.py

```python
from django.db import models

class Employee(models.Model):
    name = models.CharField(max_length=100)
    age = models.IntegerField()
    department = models.CharField(max_length=100)
    is_active = models.BooleanField(default=True)

    def __str__(self):
        return self.name
```

Suppose our database contains:

| id | name | age | department | is_active |
|---|---|---:|---|---|
| 1 | John | 25 | IT | True |
| 2 | Sarah | 30 | HR | True |
| 3 | David | 28 | Finance | False |

### serializers.py

```python
from rest_framework import serializers
from .models import Employee

class EmployeeSerializer(serializers.ModelSerializer):

    class Meta:
        model = Employee
        fields = "__all__"
```

The serializer converts Django model objects into JSON-compatible data and validates incoming data before saving it.

For example, an Employee model object can become:

```json
{
    "id": 1,
    "name": "John",
    "age": 25,
    "department": "IT",
    "is_active": true
}
```

# 3. APIView – Methods and explanations

Import:

```python
from rest_framework.views import APIView
from rest_framework.response import Response
from rest_framework import status
```

`APIView` inherits from Django's class-based `View`.

It provides DRF-specific request and response processing.

## 3.1 HTTP handler methods

These are the methods you normally define inside an APIView subclass.

| Method | HTTP method | Purpose |
|---|---|---|
| `get()` | GET | Retrieve data |
| `post()` | POST | Create data |
| `put()` | PUT | Update a resource |
| `patch()` | PATCH | Partially update a resource |
| `delete()` | DELETE | Delete a resource |
| `head()` | HEAD | Return headers without a response body |
| `options()` | OPTIONS | Return information about supported operations |

Important: APIView does not automatically implement all these CRUD operations. You write the handlers you need. DRF provides an `options()` implementation.

### Example: GET using APIView

```python
class EmployeeListView(APIView):

    def get(self, request):

        employees = Employee.objects.all()

        serializer = EmployeeSerializer(
            employees,
            many=True
        )

        return Response(serializer.data)
```

Let's understand every line.

**Line 1:**

```python
class EmployeeListView(APIView):
```

We create a class-based API view by inheriting from APIView.

**Line 2:**

```python
def get(self, request):
```

This method handles incoming GET requests.

**Line 3:**

```python
employees = Employee.objects.all()
```

This retrieves all Employee records from the database.

**Line 4:**

```python
serializer = EmployeeSerializer(employees, many=True)
```

We convert multiple Employee model objects into serialized data.

Why `many=True`?

Because we are serializing multiple employees rather than one employee.

**Line 5:**

```python
return Response(serializer.data)
```

We return the serialized data as an HTTP response.

### Expected output

Request:

```http
GET /employees/
```

Response:

```json
[
    {
        "id": 1,
        "name": "John",
        "age": 25,
        "department": "IT",
        "is_active": true
    },
    {
        "id": 2,
        "name": "Sarah",
        "age": 30,
        "department": "HR",
        "is_active": true
    },
    {
        "id": 3,
        "name": "David",
        "age": 28,
        "department": "Finance",
        "is_active": false
    }
]
```

HTTP status: `200 OK`

## 3.2 POST using APIView

```python
class EmployeeCreateView(APIView):

    def post(self, request):

        serializer = EmployeeSerializer(
            data=request.data
        )

        if serializer.is_valid():

            serializer.save()

            return Response(
                serializer.data,
                status=status.HTTP_201_CREATED
            )

        return Response(
            serializer.errors,
            status=status.HTTP_400_BAD_REQUEST
        )
```

### Explanation

**`request.data`**

Contains the incoming request body.

For example:

```json
{
    "name": "Michael",
    "age": 27,
    "department": "IT",
    "is_active": true
}
```

**`EmployeeSerializer(data=request.data)`**

Passes the incoming data to the serializer for validation.

**`serializer.is_valid()`**

Checks whether the incoming data satisfies the serializer's validation rules.

**`serializer.save()`**

Saves the new employee into the database.

**`serializer.data`**

Returns the serialized representation of the saved employee.

### Expected output

```json
{
    "id": 4,
    "name": "Michael",
    "age": 27,
    "department": "IT",
    "is_active": true
}
```

HTTP status: `201 Created`

If the data is invalid, for example the age is missing:

```json
{
    "age": [
        "This field is required."
    ]
}
```

HTTP status: `400 Bad Request`

## 3.3 PUT using APIView

```python
class EmployeeUpdateView(APIView):

    def put(self, request, pk):

        employee = Employee.objects.get(pk=pk)

        serializer = EmployeeSerializer(
            employee,
            data=request.data
        )

        if serializer.is_valid():

            serializer.save()

            return Response(serializer.data)

        return Response(
            serializer.errors,
            status=status.HTTP_400_BAD_REQUEST
        )
```

Example request:

```http
PUT /employees/1/
```

Request body:

```json
{
    "name": "John Smith",
    "age": 26,
    "department": "Engineering",
    "is_active": true
}
```

The existing employee is updated.

Response:

```json
{
    "id": 1,
    "name": "John Smith",
    "age": 26,
    "department": "Engineering",
    "is_active": true
}
```

HTTP status: `200 OK`

For PUT, the serializer normally expects all required fields to be supplied.

## 3.4 PATCH using APIView

```python
class EmployeePartialUpdateView(APIView):

    def patch(self, request, pk):

        employee = Employee.objects.get(pk=pk)

        serializer = EmployeeSerializer(
            employee,
            data=request.data,
            partial=True
        )

        if serializer.is_valid():

            serializer.save()

            return Response(serializer.data)

        return Response(
            serializer.errors,
            status=status.HTTP_400_BAD_REQUEST
        )
```

Request:

```http
PATCH /employees/1/
```

Request body:

```json
{
    "age": 29
}
```

Only the age changes.

Response:

```json
{
    "id": 1,
    "name": "John",
    "age": 29,
    "department": "IT",
    "is_active": true
}
```

HTTP status: `200 OK`

The important difference:

- PUT normally updates the complete resource.
- PATCH updates only the supplied fields.

## 3.5 DELETE using APIView

```python
class EmployeeDeleteView(APIView):

    def delete(self, request, pk):

        employee = Employee.objects.get(pk=pk)

        employee.delete()

        return Response(
            status=status.HTTP_204_NO_CONTENT
        )
```

Request:

```http
DELETE /employees/1/
```

Response:

```http
204 No Content
```

The employee is deleted from the database.

Note: In production, use `get_object_or_404()` or appropriate exception handling to return a 404 when the employee does not exist.

# 4. Important APIView inherited methods

APIView provides additional methods used internally by DRF.

| Method | Explanation |
|---|---|
| `dispatch()` | Receives the request and routes it to the appropriate HTTP handler |
| `initial()` | Performs initial request processing |
| `finalize_response()` | Prepares the final response |
| `perform_authentication()` | Performs authentication |
| `get_authenticators()` | Returns configured authentication classes |
| `check_permissions()` | Checks view-level permissions |
| `get_permissions()` | Returns configured permission classes |
| `check_object_permissions()` | Checks object-level permissions |
| `check_throttles()` | Checks request throttling |
| `get_throttles()` | Returns configured throttle classes |
| `handle_exception()` | Handles exceptions raised during request processing |
| `get_exception_handler()` | Returns the configured exception handler |

You normally configure authentication, permissions and throttling using class attributes rather than overriding all these methods.

Example:

```python
from rest_framework.permissions import IsAuthenticated

class EmployeeView(APIView):

    permission_classes = [IsAuthenticated]

    def get(self, request):
        return Response({"message": "Authenticated user"})
```

Only authenticated users can access this endpoint, subject to the configured authentication classes.

# 5. GenericAPIView – All important methods

Import:

```python
from rest_framework.generics import GenericAPIView
```

Remember:

`GenericAPIView` inherits from APIView.

Therefore, it has all APIView functionality.

It adds several important methods.

## 5.1 queryset

The queryset defines which database objects the view works with.

```python
class EmployeeListView(GenericAPIView):

    queryset = Employee.objects.all()
```

This means the view starts with all Employee records.

## 5.2 serializer_class

Defines which serializer the view should use.

```python
serializer_class = EmployeeSerializer
```

## 5.3 get_queryset()

Purpose: Returns the queryset for the current request.

Example:

```python
class EmployeeListView(GenericAPIView):

    queryset = Employee.objects.all()
    serializer_class = EmployeeSerializer

    def get(self, request):

        employees = self.get_queryset()

        return Response({
            "count": employees.count()
        })
```

Output:

```json
{
    "count": 3
}
```

Why use `get_queryset()` instead of directly writing `Employee.objects.all()`?

Because `get_queryset()` allows you to customize the queryset dynamically.

Example:

```python
def get_queryset(self):

    return Employee.objects.filter(
        is_active=True
    )
```

Output for our sample database:

```json
[
    {
        "id": 1,
        "name": "John",
        "age": 25,
        "department": "IT",
        "is_active": true
    },
    {
        "id": 2,
        "name": "Sarah",
        "age": 30,
        "department": "HR",
        "is_active": true
    }
]
```

Only active employees are returned.

## 5.4 get_serializer_class()

Purpose: Returns the serializer class used by the view.

Example:

```python
class EmployeeView(GenericAPIView):

    queryset = Employee.objects.all()
    serializer_class = EmployeeSerializer

    def get_serializer_class(self):

        return EmployeeSerializer
```

Why override it?

You might want different serializers for different HTTP methods.

Example:

```python
def get_serializer_class(self):

    if self.request.method == "GET":
        return EmployeeReadSerializer

    return EmployeeWriteSerializer
```

This allows you to use one serializer for reading and another for writing.

## 5.5 get_serializer()

Purpose: Creates and returns a serializer instance.

Example:

```python
def get(self, request):

    employees = self.get_queryset()

    serializer = self.get_serializer(
        employees,
        many=True
    )

    return Response(serializer.data)
```

Why use `self.get_serializer()`?

It automatically uses:
- The serializer returned by `get_serializer_class()`.
- The serializer context returned by `get_serializer_context()`.

You do not need to instantiate the serializer manually.

## 5.6 get_serializer_context()

Purpose: Provides additional context to the serializer.

By default, DRF includes useful information such as:
- `request`
- `view`
- `format`

Example:

```python
def get_serializer_context(self):

    context = super().get_serializer_context()

    context["company"] = "ABC Technologies"

    return context
```

Inside your serializer:

```python
class EmployeeSerializer(serializers.ModelSerializer):

    class Meta:
        model = Employee
        fields = "__all__"

    def to_representation(self, instance):

        data = super().to_representation(instance)

        company = self.context.get("company")

        data["company"] = company

        return data
```

Example output:

```json
{
    "id": 1,
    "name": "John",
    "age": 25,
    "department": "IT",
    "is_active": true,
    "company": "ABC Technologies"
}
```

## 5.7 get_object()

Purpose: Retrieves one object using the configured queryset and lookup configuration.

Example:

```python
class EmployeeDetailView(GenericAPIView):

    queryset = Employee.objects.all()
    serializer_class = EmployeeSerializer

    def get(self, request, *args, **kwargs):

        employee = self.get_object()

        serializer = self.get_serializer(employee)

        return Response(serializer.data)
```

URL:

```python
path(
    "employees/<int:pk>/",
    EmployeeDetailView.as_view()
)
```

Request:

```http
GET /employees/1/
```

Output:

```json
{
    "id": 1,
    "name": "John",
    "age": 25,
    "department": "IT",
    "is_active": true
}
```

Important: `get_object()` normally:
1. Gets the filtered queryset.
2. Applies the configured lookup field, normally `pk`.
3. Finds the matching object.
4. Raises a 404 if it does not exist.
5. Checks object-level permissions.

## 5.8 filter_queryset()

Purpose: Applies configured filter backends to a queryset.

Example:

```python
class EmployeeListView(GenericAPIView):

    queryset = Employee.objects.all()
    serializer_class = EmployeeSerializer

    filter_backends = [
        filters.SearchFilter
    ]

    search_fields = ["name", "department"]

    def get(self, request):

        queryset = self.filter_queryset(
            self.get_queryset()
        )

        serializer = self.get_serializer(
            queryset,
            many=True
        )

        return Response(serializer.data)
```

Request:

```http
GET /employees/?search=John
```

Output:

```json
[
    {
        "id": 1,
        "name": "John",
        "age": 25,
        "department": "IT",
        "is_active": true
    }
]
```

This example assumes the appropriate filter backend has been imported and configured.

## 5.9 Pagination methods

There are two important methods:

| Method | Purpose |
|---|---|
| `paginate_queryset()` | Returns one page of results |
| `get_paginated_response()` | Creates the paginated response |

Example:

```python
class EmployeeListView(GenericAPIView):

    queryset = Employee.objects.all()
    serializer_class = EmployeeSerializer

    def get(self, request):

        queryset = self.get_queryset()

        page = self.paginate_queryset(queryset)

        if page is not None:

            serializer = self.get_serializer(
                page,
                many=True
            )

            return self.get_paginated_response(
                serializer.data
            )

        serializer = self.get_serializer(
            queryset,
            many=True
        )

        return Response(serializer.data)
```

Example pagination configuration:

```python
from rest_framework.pagination import PageNumberPagination

class EmployeePagination(PageNumberPagination):

    page_size = 2
```

Add this to the view:

```python
pagination_class = EmployeePagination
```

Request:

```http
GET /employees/?page=1
```

Example output:

```json
{
    "count": 3,
    "next": "http://example.com/employees/?page=2",
    "previous": null,
    "results": [
        {
            "id": 1,
            "name": "John",
            "age": 25,
            "department": "IT",
            "is_active": true
        },
        {
            "id": 2,
            "name": "Sarah",
            "age": 30,
            "department": "HR",
            "is_active": true
        }
    ]
}
```

The second page contains David.

# 6. Mixins – All five CRUD methods

Import:

```python
from rest_framework import generics, mixins
```

There are five main Mixins in DRF.

Each Mixin provides a reusable CRUD operation.

## 6.1 ListModelMixin

Purpose: Retrieve multiple objects.

Main method:

```python
list()
```

Example:

```python
class EmployeeListView(
    mixins.ListModelMixin,
    generics.GenericAPIView
):

    queryset = Employee.objects.all()
    serializer_class = EmployeeSerializer

    def get(self, request, *args, **kwargs):

        return self.list(
            request,
            *args,
            **kwargs
        )
```

Request:

```http
GET /employees/
```

Output:

```json
[
    {
        "id": 1,
        "name": "John",
        "age": 25,
        "department": "IT",
        "is_active": true
    },
    {
        "id": 2,
        "name": "Sarah",
        "age": 30,
        "department": "HR",
        "is_active": true
    },
    {
        "id": 3,
        "name": "David",
        "age": 28,
        "department": "Finance",
        "is_active": false
    }
]
```

### How list() works internally

Conceptually:

```python
def list(self, request, *args, **kwargs):

    queryset = self.filter_queryset(
        self.get_queryset()
    )

    page = self.paginate_queryset(queryset)

    if page is not None:

        serializer = self.get_serializer(
            page,
            many=True
        )

        return self.get_paginated_response(
            serializer.data
        )

    serializer = self.get_serializer(
        queryset,
        many=True
    )

    return Response(serializer.data)
```

This is the main reason GenericAPIView and Mixins work so well together.

The Mixin uses methods provided by GenericAPIView.

## 6.2 CreateModelMixin

Purpose: Create one new object.

Main methods:

| Method | Purpose |
|---|---|
| `create()` | Validates and creates an object |
| `perform_create()` | Customizes how the object is saved |

Example:

```python
class EmployeeCreateView(
    mixins.CreateModelMixin,
    generics.GenericAPIView
):

    queryset = Employee.objects.all()
    serializer_class = EmployeeSerializer

    def post(self, request, *args, **kwargs):

        return self.create(
            request,
            *args,
            **kwargs
        )
```

Request:

```http
POST /employees/
```

Body:

```json
{
    "name": "Michael",
    "age": 27,
    "department": "IT",
    "is_active": true
}
```

Output:

```json
{
    "id": 4,
    "name": "Michael",
    "age": 27,
    "department": "IT",
    "is_active": true
}
```

HTTP status: `201 Created`

### How create() works internally

Conceptually:

```python
def create(self, request, *args, **kwargs):

    serializer = self.get_serializer(
        data=request.data
    )

    serializer.is_valid(
        raise_exception=True
    )

    self.perform_create(serializer)

    return Response(
        serializer.data,
        status=201
    )
```

### What is perform_create()?

It is a customization hook.

For example, automatically assign the currently logged-in user:

```python
def perform_create(self, serializer):

    serializer.save(
        created_by=self.request.user
    )
```

You do not normally call `perform_create()` yourself. The `create()` method calls it.

Purpose: Retrieve one object.


```python
class EmployeeDetailView(

```

Request:

```http
GET /employees/1/
```

Output:

```json
{
    "id": 1,
    "name": "John",
    "age": 25,
    "department": "IT",
    "is_active": true
}
```

### How retrieve() works internally

Conceptually:

```python
def retrieve(self, request, *args, **kwargs):

    instance = self.get_object()

```

## 6.4 UpdateModelMixin

Purpose: Update an existing object.

Main methods:

| Method | Purpose |
|---|---|
| `update()` | Performs a normal update |
| `partial_update()` | Performs a partial update |
| `perform_update()` | Customizes how an update is saved |

Example:

```python
class EmployeeUpdateView(
    mixins.UpdateModelMixin,
    generics.GenericAPIView
):

    queryset = Employee.objects.all()
    serializer_class = EmployeeSerializer

    def put(self, request, *args, **kwargs):

        return self.update(
            request,
            *args,
            **kwargs
        )

    def patch(self, request, *args, **kwargs):

        return self.partial_update(
            request,
            *args,
            **kwargs
        )
```

### PUT request

```http
PUT /employees/1/
```

Body:

```json
{
    "name": "John Smith",
    "age": 26,
    "department": "Engineering",
    "is_active": true
}
```

Output:

```json
{
    "id": 1,
    "name": "John Smith",
    "age": 26,
    "department": "Engineering",
    "is_active": true
}
```

### PATCH request

```http
PATCH /employees/1/
```

Body:

```json
{
    "age": 29
}
```

Output:

```json
{
    "id": 1,
    "name": "John",
    "age": 29,
    "department": "IT",
    "is_active": true
}
```

### How update() works internally

Conceptually:

```python
def update(self, request, *args, **kwargs):

    partial = kwargs.pop("partial", False)

    instance = self.get_object()

    serializer = self.get_serializer(
        instance,
        data=request.data,
        partial=partial
    )

    serializer.is_valid(
        raise_exception=True
    )

    self.perform_update(serializer)

    return Response(serializer.data)
```

The `partial` variable determines whether all required fields must be supplied.

### What is partial_update()?

Conceptually:

```python
def partial_update(self, request, *args, **kwargs):

    kwargs["partial"] = True

    return self.update(
        request,
        *args,
        **kwargs
    )
```

It calls `update()` but tells it to perform a partial update.

### What is perform_update()?

It is a customization hook.

Example:

```python
def perform_update(self, serializer):

    serializer.save(
        updated_by=self.request.user
    )
```

## 6.5 DestroyModelMixin

Purpose: Delete one object.

Main methods:

| Method | Purpose |
|---|---|
| `destroy()` | Deletes an object |
| `perform_destroy()` | Customizes deletion |

Example:

```python
class EmployeeDeleteView(
    mixins.DestroyModelMixin,
    generics.GenericAPIView
):

    queryset = Employee.objects.all()
    serializer_class = EmployeeSerializer

    def delete(self, request, *args, **kwargs):

        return self.destroy(
            request,
            *args,
            **kwargs
        )
```

Request:

```http
DELETE /employees/1/
```

Response:

```http
204 No Content
```

### How destroy() works internally

Conceptually:

```python
def destroy(self, request, *args, **kwargs):

    instance = self.get_object()

    self.perform_destroy(instance)

    return Response(status=204)
```

### What is perform_destroy()?

It is a customization hook.

Example:

```python
def perform_destroy(self, instance):

    instance.delete()
```

You can override this to perform additional actions before or during deletion.

---

# 7. All five Mixins – Summary table

| Mixin | Main CRUD method | Customization hook | HTTP method |
|---|---|---|---|
| `ListModelMixin` | `list()` | None | GET |
| `CreateModelMixin` | `create()` | `perform_create()` | POST |
| `RetrieveModelMixin` | `retrieve()` | None | GET |
| `UpdateModelMixin` | `update()` | `perform_update()` | PUT |
| `DestroyModelMixin` | `destroy()` | `perform_destroy()` | DELETE |

Remember:

`partial_update()` is also provided by `UpdateModelMixin` and is used for PATCH.

The methods `perform_create()`, `perform_update()` and `perform_destroy()` are customization hooks, not separate HTTP handlers.

# 8. GenericAPIView + Mixins – Complete example

Suppose we want:
- GET: List all employees.
- POST: Create an employee.
- DELETE: Delete one employee.

We can combine the required Mixins.

```python
from rest_framework import generics, mixins

class EmployeeCustomView(
    mixins.ListModelMixin,
    mixins.CreateModelMixin,
    mixins.DestroyModelMixin,
    generics.GenericAPIView
):

    queryset = Employee.objects.all()
    serializer_class = EmployeeSerializer

    def get(self, request, *args, **kwargs):

        return self.list(
            request,
            *args,
            **kwargs
        )

    def post(self, request, *args, **kwargs):

        return self.create(
            request,
            *args,
            **kwargs
        )

    def delete(self, request, *args, **kwargs):

        return self.destroy(
            request,
            *args,
            **kwargs
        )
```

Important: Because `DestroyModelMixin` uses `get_object()`, the DELETE request must include the employee's primary key.

A better URL arrangement is:

```python
urlpatterns = [
    path(
        "employees/",
        EmployeeCustomView.as_view()
    ),

    path(
        "employees/<int:pk>/",
        EmployeeCustomView.as_view()
    )
]
```

However, if you use one class for both collection and detail operations, make sure your handler and URL design are intentional. In a real project, separating the collection and detail views is often clearer.

Also, DELETE on a collection should not accidentally delete every employee. Bulk deletion is a separate operation that needs explicit implementation and safeguards.

# 12. Final comparison: APIView vs GenericAPIView vs Mixins vs Concrete Generic Views

| Feature | APIView | GenericAPIView | GenericAPIView + Mixins | Concrete Generic Views |
|---|---|---|---|---|
| Inherits from APIView | Yes | Yes | Yes, through GenericAPIView | Yes, through GenericAPIView |
| Queryset helpers | No | Yes | Yes | Yes |
| Serializer helpers | No | Yes | Yes | Yes |
| Object lookup helpers | No | Yes | Yes | Yes |
| List operation | Write yourself | Write yourself | ListModelMixin | Built in where supported |
| Create operation | Write yourself | Write yourself | CreateModelMixin | Built in where supported |
| Retrieve operation | Write yourself | Write yourself | RetrieveModelMixin | Built in where supported |
| Update operation | Write yourself | Write yourself | UpdateModelMixin | Built in where supported |
| Delete operation | Write yourself | Write yourself | DestroyModelMixin | Built in where supported |
| HTTP handlers | Write yourself | Write yourself | Write yourself | Already provided for supported methods |
| Custom operation combinations | Yes | Yes | Yes | Limited to existing combinations or customization |

## 13. When should you use each approach?

### Use APIView when:

- You need completely custom API logic.
- Your endpoint does not fit the normal CRUD pattern.
- You want to control the request processing yourself.

### Use GenericAPIView when:

- You need queryset functionality.
- You need serializer functionality.
- You need object lookup.
- You want to build custom logic using DRF's reusable helpers.

### Use GenericAPIView + Mixins when:

- You want to choose particular CRUD operations.
- The standard concrete view combinations do not match your requirements.
- You want reusable CRUD logic but need to control the HTTP handlers.

### Use Concrete Generic Views when:

- You are building normal CRUD endpoints.
- You want less code.
- The predefined HTTP method combinations meet your requirements.

# 15. The easiest way to remember everything

Think about the inheritance and functionality like this:

**APIView**
- Provides the foundation for DRF class-based APIs.
- You write your own business and CRUD logic.

**GenericAPIView**
- Extends APIView.
- Provides queryset, serializer, object lookup, filtering and pagination helpers.

**Mixins**
- Provide reusable CRUD methods.
- `list()`, `create()`, `retrieve()`, `update()`, `destroy()`.

**GenericAPIView + Mixins**
- You select the mixins you need.
- You connect their methods to HTTP handlers yourself.

**Concrete Generic Views**
- DRF has already combined common mixins and HTTP handlers.
- You only need to configure the queryset and serializer for ordinary CRUD operations.

### My recommendation for learning DRF

Understand these concepts in this order:

1. APIView
2. GenericAPIView
3. GenericAPIView methods
4. Five Mixins and their CRUD methods
5. Concrete Generic Views
6. ViewSets
7. Routers

Once you understand the first five topics, ViewSets and Routers will be much easier to understand.
