# Django REST Framework – Filtering, Searching, Ordering and Pagination

# Part 1: Understanding the concepts

Before learning the classes and their attributes, understand the four main operations.

| Concept | Meaning | Example |
|---|---|---|
| Filtering | Select records based on conditions | Products belonging to electronics |
| Searching | Find records matching text | Products containing "laptop" |
| Ordering | Arrange records in a particular sequence | Price from low to high |
| Pagination | Divide records into smaller result sets | Return 20 products per page |

Suppose an API contains 100,000 products.

A frontend sends:

```http
GET /api/products/?category=electronics&search=laptop&min_price=100&max_price=2000&ordering=-price&page=1&page_size=20
```

The API must:

1. Filter electronics products.
2. Search for products containing "laptop".
3. Filter prices between 100 and 2,000.
4. Sort products by descending price.
5. Return the first 20 matching products.

The normal DRF processing sequence is:

```text
Base QuerySet
     |
     v
Filtering
     |
     v
Searching
     |
     v
Ordering
     |
     v
Pagination
     |
     v
Serialization
     |
     v
JSON Response
```

# Part 3: DjangoFilterBackend

## 2. What is DjangoFilterBackend?

`DjangoFilterBackend` is provided by the django-filter package.

It connects Django model filtering with Django REST Framework.

Example:

```http
GET /api/products/?category=electronics
```

Internally, it applies filtering similar to:

```python
Product.objects.filter(
    category="electronics"
)
```

Import:

```python
from django_filters.rest_framework import DjangoFilterBackend
```

## 3. DjangoFilterBackend: Attributes and methods

First, understand the available configuration options.

### A. `filter_backends`

**What it does:** Defines which filtering backends a view uses.

It is a DRF view attribute, not an attribute of the DjangoFilterBackend class itself.

Example:

```python
from django_filters.rest_framework import DjangoFilterBackend

class ProductListView(generics.ListAPIView):

    filter_backends = [
        DjangoFilterBackend,
    ]
```

You can combine multiple backends:

```python
filter_backends = [
    DjangoFilterBackend,
    SearchFilter,
    OrderingFilter,
]
```

**When to use:** When an API needs structured filters, text search and sorting together.

### B. `filterset_fields`

**What it does:** Defines which model fields clients can filter.

Example:

```python
filterset_fields = [
    "category",
    "is_available",
]
```

API:

```http
GET /api/products/?category=electronics
```

You can also define supported lookup expressions:

```python
filterset_fields = {
    "price": ["exact", "gte", "lte"],
    "name": ["exact", "icontains"],
    "created_at": ["date", "date__gte", "date__lte"],
}
```

API examples:

```http
GET /api/products/?price__gte=100
GET /api/products/?price__lte=500
GET /api/products/?name__icontains=laptop
GET /api/products/?created_at__date=2026-01-01
```

**When to use:** Simple filters where you do not need a custom FilterSet class.

### C. `filterset_class`

**What it does:** Connects a custom FilterSet class to a DRF view.

Example:

```python
class ProductListView(generics.ListAPIView):

    queryset = Product.objects.all()

    serializer_class = ProductSerializer

    filter_backends = [
        DjangoFilterBackend,
    ]

    filterset_class = ProductFilter
```

The `ProductFilter` class contains the actual filtering definitions.

**When to use:** Price ranges, custom filtering methods, date ranges and related-model filters.

Use either `filterset_fields` or `filterset_class` for a view's filter configuration. Prefer `filterset_class` when you need more control.

### D. `get_filterset()`

**What it does:** Creates and returns the FilterSet instance for the current request.

Its signature:

```python
get_filterset(request, queryset, view)
```

Example of using it when extending the backend:

```python
class CustomFilterBackend(DjangoFilterBackend):

    def filter_queryset(self, request, queryset, view):

        filterset = self.get_filterset(
            request,
            queryset,
            view
        )

        if filterset is None:
            return queryset

        return filterset.qs
```

Normally, you do not need to call this method yourself because the backend already uses it.

### E. `get_filterset_class()`

**What it does:** Determines which FilterSet class should be used.

It can use:

- An explicitly declared `filterset_class`.
- An automatically generated FilterSet based on `filterset_fields`.

Example override:

```python
class CustomFilterBackend(DjangoFilterBackend):

    def get_filterset_class(self, view, queryset=None):

        if view.request.user.is_staff:
            return AdminProductFilter

        return ProductFilter
```

This is an advanced customization. Both FilterSet classes must be defined and compatible with the queryset.

### F. `get_filterset_kwargs()`

**What it does:** Returns the keyword arguments passed to the FilterSet constructor.

Example:

```python
class CustomFilterBackend(DjangoFilterBackend):

    def get_filterset_kwargs(
        self,
        request,
        queryset,
        view
    ):

        kwargs = super().get_filterset_kwargs(
            request,
            queryset,
            view
        )

        kwargs["user"] = request.user

        return kwargs
```

Your FilterSet must accept the extra argument:

```python
class ProductFilter(django_filters.FilterSet):

    def __init__(self, *args, user=None, **kwargs):

        super().__init__(*args, **kwargs)

        self.user = user
```

**When to use:** When filtering depends on the current user, organization or request context.

### G. `filter_queryset()`

**What it does:** Applies the filter to the queryset.

Signature:

```python
filter_queryset(request, queryset, view)
```

Example:

```python
class CustomFilterBackend(DjangoFilterBackend):

    def filter_queryset(self, request, queryset, view):

        queryset = super().filter_queryset(
            request,
            queryset,
            view
        )

        return queryset.filter(
            is_available=True
        )
```

This applies normal django-filter behavior and then restricts the results to available products.

### DjangoFilterBackend summary

| Attribute or method | Purpose |
|---|---|
| `filter_backends` | Select filtering backends |
| `filterset_fields` | Define simple filterable fields |
| `filterset_class` | Connect a custom FilterSet |
| `get_filterset()` | Construct a FilterSet instance |
| `get_filterset_class()` | Determine the FilterSet class |
| `get_filterset_kwargs()` | Customize constructor arguments |
| `filter_queryset()` | Apply filtering |

# Part 4: django-filter and FilterSet

## 4. What is FilterSet?

`django_filters.FilterSet` is the main class used to define custom filtering rules.

Import:

```python
import django_filters
```

Create a filter:

```python
class ProductFilter(django_filters.FilterSet):
    pass
```

Before creating a complete filter, understand its attributes and options.

## 5. FilterSet attributes and options

### A. `Meta.model`

Defines which Django model the FilterSet operates on.

Example:

```python
class ProductFilter(django_filters.FilterSet):

    class Meta:
        model = Product
```

The FilterSet will filter Product objects.

### B. `Meta.fields`

Defines the model fields that can be filtered.

Example:

```python
class Meta:
    model = Product

    fields = [
        "category",
        "is_available",
    ]
```

You can also define lookup expressions:

```python
class Meta:
    model = Product

    fields = {
        "price": ["exact", "gte", "lte"],
        "name": ["exact", "icontains"],
    }
```

Requests:

```http
GET /api/products/?price__gte=100
GET /api/products/?price__lte=500
GET /api/products/?name__icontains=laptop
```

### C. `Meta.exclude`

Excludes fields from automatically generated filters.

Example:

```python
class ProductFilter(django_filters.FilterSet):

    class Meta:
        model = Product

        fields = "__all__"

        exclude = [
            "internal_notes",
        ]
```

`internal_notes` will not be included in the automatically generated filter fields.

Prefer an explicit allowlist with `fields` in production.

### D. `field_name`

Specifies the model field that the filter should operate on.

Example:

```python
min_price = django_filters.NumberFilter(
    field_name="price"
)
```

Here:

- API parameter: `min_price`
- Model field: `price`

Request:

```http
GET /api/products/?min_price=100
```

### E. `lookup_expr`

Specifies the Django ORM lookup operation.

Example:

```python
min_price = django_filters.NumberFilter(
    field_name="price",
    lookup_expr="gte"
)
```

Equivalent ORM:

```python
Product.objects.filter(
    price__gte=100
)
```

Common lookup expressions:

| Lookup | Meaning | Example |
|---|---|---|
| `exact` | Exact match | `?price=100` |
| `iexact` | Exact match ignoring case | `?name__iexact=laptop` |
| `contains` | Contains text | `?name__contains=lap` |
| `icontains` | Contains ignoring case | `?name__icontains=LAP` |
| `startswith` | Starts with | `?name__startswith=Lap` |
| `istartswith` | Starts with ignoring case | `?name__istartswith=lap` |
| `endswith` | Ends with | `?name__endswith=top` |
| `gt` | Greater than | `?price__gt=100` |
| `gte` | Greater than or equal | `?price__gte=100` |
| `lt` | Less than | `?price__lt=500` |
| `lte` | Less than or equal | `?price__lte=500` |
| `in` | Match one of multiple values | `?id__in=1,2,3` |
| `isnull` | Check for NULL | `?brand__isnull=true` |
| `range` | Between two values | `?created_at__range=2026-01-01,2026-01-31` |

### F. `exclude`

Reverses the matching condition for a filter.

Example:

```python
unavailable = django_filters.BooleanFilter(
    field_name="is_available",
    exclude=True
)
```

Request:

```http
GET /api/products/?unavailable=true
```

This excludes products where `is_available` is true.

### G. `distinct`

Removes duplicate records from the filtered queryset.

Example:

```python
category_name = django_filters.CharFilter(
    field_name="categories__name",
    lookup_expr="icontains",
    distinct=True
)
```

Use it when filtering through a many-to-many relationship can produce duplicate rows.

### H. `method`

Calls a custom method to perform filtering.

Example:

```python
expensive = django_filters.BooleanFilter(
    method="filter_expensive"
)
```

Implement the method:

```python
def filter_expensive(self, queryset, name, value):

    if value:
        return queryset.filter(price__gte=1000)

    return queryset.filter(price__lt=1000)
```

Request:

```http
GET /api/products/?expensive=true
```

The method receives:

| Parameter | Meaning |
|---|---|
| `self` | Current FilterSet instance |
| `queryset` | Current queryset |
| `name` | Filter name |
| `value` | Validated parameter value |

### I. `label`

Defines a human-readable filter label.

Example:

```python
min_price = django_filters.NumberFilter(
    field_name="price",
    lookup_expr="gte",
    label="Minimum Price"
)
```

This mainly affects filter form presentation.

### J. `required`

Determines whether the filter must be supplied.

Example:

```python
category = django_filters.CharFilter(
    required=True
)
```

A request without the required category parameter will fail filter validation.

Use this carefully for list endpoints.

### K. `widget`

Controls the HTML widget used by the browsable API filter form.

Example:

```python
category = django_filters.CharFilter(
    widget=django_filters.widgets.LinkWidget
)
```

Another example:

```python
category = django_filters.CharFilter(
    widget=django_filters.widgets.TextInput(
        attrs={"placeholder": "Enter category"}
    )
)
```

This primarily affects the HTML form, not the underlying JSON filtering behavior.

### L. `filter_overrides`

Customizes the filter automatically generated for a model field type.

Example:

```python
from django.db import models
import django_filters


class ProductFilter(django_filters.FilterSet):

    class Meta:
        model = Product

        fields = ["name"]

        filter_overrides = {
            models.CharField: {
                "filter_class": django_filters.CharFilter,
                "extra": lambda field: {
                    "lookup_expr": "icontains"
                },
            },
        }
```

Now automatically generated CharField filters use case-insensitive partial matching.

### M. `base_filters`

Contains the filter definitions declared by the FilterSet.

Example:

```python
class ProductFilter(django_filters.FilterSet):

    min_price = django_filters.NumberFilter(
        field_name="price",
        lookup_expr="gte"
    )

    class Meta:
        model = Product
        fields = ["category"]


print(ProductFilter.base_filters.keys())
```

This is useful for inspecting available filters. It is not normally something you modify directly.

### N. `filters`

Contains the filters available on a FilterSet instance.

Example:

```python
filterset = ProductFilter(
    data={"min_price": "100"},
    queryset=Product.objects.all()
)

print(filterset.filters.keys())
```

Use this to inspect the filters on an instance.

### O. `data`

Contains the supplied filter input.

Example:

```python
filterset = ProductFilter(
    data={"min_price": "100"},
    queryset=Product.objects.all()
)

print(filterset.data)
```

This is useful when inspecting what the client submitted.

### P. `qs`

Returns the filtered queryset.

Example:

```python
filterset = ProductFilter(
    data={"min_price": "100"},
    queryset=Product.objects.all()
)

filtered_products = filterset.qs
```

This is one of the most useful FilterSet properties.

### Q. `is_valid()`

Checks whether the supplied filter data is valid.

Example:

```python
filterset = ProductFilter(
    data={"min_price": "abc"},
    queryset=Product.objects.all()
)

if filterset.is_valid():
    products = filterset.qs
else:
    print(filterset.errors)
```

### R. `errors`

Returns validation errors.

Example:

```python
filterset = ProductFilter(
    data={"min_price": "abc"},
    queryset=Product.objects.all()
)

filterset.is_valid()

print(filterset.errors)
```

This can contain an error indicating that the supplied value is not a valid number.

### FilterSet summary

| Attribute or option | Purpose |
|---|---|
| `Meta.model` | Model to filter |
| `Meta.fields` | Available filter fields |
| `Meta.exclude` | Excluded fields |
| `field_name` | Database field |
| `lookup_expr` | ORM lookup |
| `exclude` | Reverse matching |
| `distinct` | Remove duplicates |
| `method` | Custom filtering |
| `label` | Display label |
| `required` | Require a value |
| `widget` | HTML filter form widget |
| `filter_overrides` | Customize automatic filter generation |
| `base_filters` | Class-level filter definitions |
| `filters` | Instance filter definitions |
| `data` | Submitted filter data |
| `qs` | Filtered queryset |
| `is_valid()` | Validate filter data |
| `errors` | Validation errors |

Request:

```python
is_available = django_filters.BooleanFilter(
```

## 13. ChoiceFilter

Used when the value must be one of a defined set of choices.

```python
status = django_filters.ChoiceFilter(

        ("inactive", "Inactive"),

```

Request:

```http
GET /api/products/?status=active
```

## 14. MultipleChoiceFilter

Used when clients can select multiple choices.

```python
status = django_filters.MultipleChoiceFilter(
    field_name="status",
    choices=[
        ("active", "Active"),
        ("inactive", "Inactive"),
    ]
)
```

Request:

```http
GET /api/products/?status=active&status=inactive
```

The exact query parameter format depends on the filter and widget configuration. Verify the generated filter form and API behavior for your chosen version.

## 15. ModelChoiceFilter

Used to filter by a related model object.

Example:

```python
category = django_filters.ModelChoiceFilter(
    field_name="category",
    queryset=Category.objects.all()
)
```

Request:

```http
GET /api/products/?category=2
```

Here, `2` is the category's primary key.

## 16. ModelMultipleChoiceFilter

Used to filter by multiple related model objects.

```python
categories = django_filters.ModelMultipleChoiceFilter(
    field_name="category",
    queryset=Category.objects.all()
)
```

Example:

```http
GET /api/products/?categories=1&categories=2
```

Use these model-choice filters when the field represents a Django relationship and you want django-filter to validate the supplied IDs against an actual queryset.

# Part 7: SearchFilter

## 21. What is SearchFilter?

`SearchFilter` is a built-in DRF backend for text-based searching.

Import:

```python
from rest_framework.filters import SearchFilter
```

Example:

```http
GET /api/products/?search=laptop
```

It searches the fields specified in `search_fields`.

## 22. SearchFilter attributes and methods

### A. `search_fields`

Defines which model fields should be searched.

Example:

```python
search_fields = [
    "name",
    "description",
]
```

Related fields are supported:

```python
search_fields = [
    "name",
    "category__name",
    "brand__name",
]
```

Request:

```http
GET /api/products/?search=electronics
```

### B. `search_param`

Defines the query parameter name.

Default:

```python
search_param = "search"
```

Customize it:

```python
class ProductSearchFilter(SearchFilter):

    search_param = "q"
```

Request:

```http
GET /api/products/?q=laptop
```

Use this when your API contract requires `q` instead of `search`.

### C. `get_search_fields()`

Returns the search fields for the current view and request.

Example:

```python
class ProductSearchFilter(SearchFilter):

    def get_search_fields(self, view, request):

        if request.user.is_staff:
            return [
                "name",
                "description",
                "internal_code",
            ]

        return [
            "name",
            "description",
        ]
```

This assumes `internal_code` exists on the model.

Use it when search fields must vary based on the request.

### D. `get_search_terms()`

Extracts search terms from the request.

Signature:

```python
get_search_terms(request)
```

Example:

```python
class CustomSearchFilter(SearchFilter):

    def get_search_terms(self, request):

        terms = super().get_search_terms(request)

        return terms
```

This example preserves normal behavior. You would override it only if you need custom parsing.

### E. `filter_queryset()`

Applies the actual search to the queryset.

Signature:

```python
filter_queryset(request, queryset, view)
```

Example:

```python
class CustomSearchFilter(SearchFilter):

    def filter_queryset(self, request, queryset, view):

        queryset = super().filter_queryset(
            request,
            queryset,
            view
        )

        return queryset
```

Normally, you do not need to override this.

### SearchFilter summary

| Attribute or method | Purpose |
|---|---|
| `search_fields` | Model fields to search |
| `search_param` | Search query parameter |
| `get_search_fields()` | Determine search fields |
| `get_search_terms()` | Extract search terms |
| `filter_queryset()` | Apply search |

## 23. Search field prefixes

SearchFilter supports prefixes that change the lookup behavior.

| Prefix | Lookup | Meaning |
|---|---|---|
| No prefix | `icontains` | Contains text |
| `^` | `istartswith` | Starts with |
| `=` | `iexact` | Exact match |
| `@` | `search` | Full-text search lookup where supported |
| `$` | `iregex` | Case-insensitive regular expression |

Example:

```python
search_fields = [
    "^name",
    "description",
    "=sku",
]
```

Meaning:

- `name` starts with the search term.
- `description` contains the search term.
- `sku` matches the search term exactly, ignoring case.

## 24. Complete SearchFilter example

```python
from rest_framework import generics
from rest_framework.filters import SearchFilter


class ProductListView(generics.ListAPIView):

    queryset = Product.objects.all()

    serializer_class = ProductSerializer

    filter_backends = [
        SearchFilter,
    ]

    search_fields = [
        "name",
        "description",
        "category__name",
    ]
```

Request:

```http
GET /api/products/?search=laptop
```

Example response:

```json
[
    {
        "id": 1,
        "name": "Gaming Laptop",
        "description": "High performance gaming computer",
        "category": 1
    },
    {
        "id": 2,
```

# Part 8: OrderingFilter

## 25. What is OrderingFilter?

`OrderingFilter` allows clients to sort API results.

Import:

```python
from rest_framework.filters import OrderingFilter
```

Example:

```http
GET /api/products/?ordering=price
```

Ascending price.

```http
GET /api/products/?ordering=-price
```

Descending price.

## 26. OrderingFilter attributes and methods

### A. `ordering_fields`

Defines which model fields clients are allowed to sort by.

Example:

```python
ordering_fields = [
    "name",
    "price",
    "created_at",
]
```

Request:

```http
GET /api/products/?ordering=price
```

A client cannot successfully request arbitrary fields that are not permitted.

### B. `ordering`

Defines the default ordering.

Example:

```python
ordering = [
    "-created_at"
]
```

If the client does not provide an ordering parameter, results are ordered newest first.

### C. `ordering_param`

Defines the query parameter name.

Default:

```python
ordering_param = "ordering"
```

Customize it:

```python
class ProductOrderingFilter(OrderingFilter):

    ordering_param = "sort"
```

Request:

```http
GET /api/products/?sort=-price
```

### D. `get_ordering()`

Determines the requested or default ordering.

Signature:

```python
get_ordering(request, queryset, view)
```

Example:

```python
class CustomOrderingFilter(OrderingFilter):

    def get_ordering(self, request, queryset, view):

        ordering = super().get_ordering(
            request,
            queryset,
            view
        )

        return ordering
```

Normally, the built-in implementation is enough.

### E. `get_valid_fields()`

Returns the fields allowed for ordering.

Signature:

```python
get_valid_fields(queryset, view, context={})
```

Example:

```python
class CustomOrderingFilter(OrderingFilter):

    def get_valid_fields(

            queryset,
            view,
            context
        )

        return fields
```

Override this only when the allowed ordering fields need custom behavior.

### F. `remove_invalid_fields()`

Removes ordering fields that are not allowed.

Example:

```python
class CustomOrderingFilter(OrderingFilter):

    def remove_invalid_fields(
        self,
        queryset,
        fields,
        view,
        request

        return super().remove_invalid_fields(
            queryset,
            fields,
            view,
            request
```

Normally, you do not need to override this.

### G. `get_default_ordering()`

Returns the default ordering from the view.

Example:

```python
class CustomOrderingFilter(OrderingFilter):

    def get_default_ordering(self, view):
```

# Part 9: Custom Filter Backends

## 28. What is a custom filter backend?

A custom backend allows you to write your own reusable queryset filtering logic.

DRF provides:

```python
from rest_framework.filters import BaseFilterBackend
```

Your class inherits from `BaseFilterBackend` and implements `filter_queryset()`.

## 29. BaseFilterBackend methods

### A. `filter_queryset()`

This is the main method you must implement.

Signature:

```python
filter_queryset(request, queryset, view)
```

Example:

```python
from rest_framework.filters import BaseFilterBackend


class AvailableProductFilter(BaseFilterBackend):

    def filter_queryset(self, request, queryset, view):

        available = request.query_params.get(
            "available"
        )

        if available == "true":
            return queryset.filter(
                is_available=True
            )

        if available == "false":
            return queryset.filter(
                is_available=False
            )

        return queryset
```

### B. `to_html()`

Optionally returns HTML used by the browsable API.

Example:

```python
class AvailableProductFilter(BaseFilterBackend):

    def to_html(self, request, queryset, view):

        return "<p>Filter by availability</p>"
```

This is only a simplified demonstration. A real implementation should render a suitable form or HTML fragment.

### C. `get_schema_operation_parameters()`

Provides schema information for the backend's query parameters.

Example:

```python
class AvailableProductFilter(BaseFilterBackend):

    def get_schema_operation_parameters(self, view):

        return [
            {
                "name": "available",
                "required": False,
                "in": "query",
                "description": "Filter by availability",
                "schema": {
                    "type": "boolean"
                },
            }
        ]
```

This helps document custom query parameters in supported DRF schema generation.

## 30. Complete custom backend example

```python
class AvailableProductFilter(BaseFilterBackend):

    def filter_queryset(self, request, queryset, view):

        available = request.query_params.get(
            "available"
        )

        if available == "true":
            queryset = queryset.filter(
                is_available=True
            )

        elif available == "false":
            queryset = queryset.filter(
                is_available=False
            )

        return queryset
```

Use it:

```python
class ProductListView(generics.ListAPIView):

    queryset = Product.objects.all()

    serializer_class = ProductSerializer

    filter_backends = [
        AvailableProductFilter,
    ]
```

Requests:

```http
GET /api/products/?available=true
```

```http
GET /api/products/?available=false
```

## 31. Custom backend with user context

Suppose every product belongs to an organization.

```python
class OrganizationProductFilter(BaseFilterBackend):

    def filter_queryset(self, request, queryset, view):

        return queryset.filter(
            organization=request.user.organization
        )
```

This assumes the endpoint requires authentication and the user has an organization relationship.

This kind of restriction is also a security boundary. Never rely only on a client-supplied organization ID to protect tenant data.

**When to use custom backends:** Reusable business logic, user-dependent filters, organization restrictions and filtering that does not fit a normal FilterSet.

# Part 10: Query Parameter Validation

## 32. What is query parameter validation?

Query parameters are values supplied through the URL.

Example:

```http
GET /api/products/?min_price=100&max_price=500
```

The API should validate that these values are meaningful.

Invalid examples:

```http
GET /api/products/?min_price=abc
```

```http
GET /api/products/?min_price=-500
```

```http
GET /api/products/?min_price=1000&max_price=100
```

## 33. Common validation requirements

| Parameter | Validation |
|---|---|
| `min_price` | Valid non-negative number |
| `max_price` | Valid non-negative number |
| `category` | Valid category |
| `page` | Valid positive page number |
| `page_size` | Positive integer within maximum |
| `ordering` | Allowed ordering field |
| `search` | Maximum permitted length |
| `start_date` | Valid date |
| `end_date` | Valid date and valid range |

## 34. Validate using a DRF serializer

```python
from rest_framework import serializers


class ProductQuerySerializer(serializers.Serializer):

    min_price = serializers.DecimalField(
        max_digits=10,
        decimal_places=2,
        required=False,
        min_value=0
    )

    max_price = serializers.DecimalField(
        max_digits=10,
        decimal_places=2,
        required=False,
        min_value=0
    )

    category = serializers.CharField(
        required=False,
        max_length=100
    )

    def validate(self, attrs):

        minimum = attrs.get("min_price")
        maximum = attrs.get("max_price")

        if (
            minimum is not None
            and maximum is not None
            and minimum > maximum
        ):
            raise serializers.ValidationError(
                "min_price cannot exceed max_price."
            )

        return attrs
```

### Explanation of serializer parameters

| Parameter | Meaning |
|---|---|
| `max_digits` | Maximum total decimal digits |
| `decimal_places` | Maximum digits after decimal point |
| `required=False` | Parameter is optional |
| `min_value=0` | Reject negative values |
| `max_length=100` | Maximum text length |

## 35. Use the query serializer in a view

```python
class ProductListView(generics.ListAPIView):

    serializer_class = ProductSerializer

    def get_queryset(self):

        query_serializer = ProductQuerySerializer(
            data=self.request.query_params
        )

        query_serializer.is_valid(
            raise_exception=True
        )

        data = query_serializer.validated_data

        queryset = Product.objects.all()

        if "min_price" in data:
            queryset = queryset.filter(
                price__gte=data["min_price"]
            )

        if "max_price" in data:
            queryset = queryset.filter(
                price__lte=data["max_price"]
            )

        if "category" in data:
            queryset = queryset.filter(
                category__name=data["category"]
            )

        return queryset
```

Invalid request:

```http
GET /api/products/?min_price=1000&max_price=100
```

Example response:

```json
{
    "non_field_errors": [
        "min_price cannot exceed max_price."
    ]
}
```

**Recommendation:** Use FilterSet validation for individual filter values and serializers for validation involving multiple query parameters.

# Part 11: Pagination Fundamentals

## 36. What is pagination?

Pagination divides a large queryset into smaller result sets.

Suppose the database contains 10,000 products.

Instead of returning every product, the API returns 20 records per request.

DRF offers:

1. PageNumberPagination.
2. LimitOffsetPagination.
3. CursorPagination.
4. Custom pagination classes.

## 37. Common pagination configuration options

### A. `DEFAULT_PAGINATION_CLASS`

Defines the default pagination class globally.

Example:

```python
REST_FRAMEWORK = {
    "DEFAULT_PAGINATION_CLASS":
        "rest_framework.pagination.PageNumberPagination",
}
```

### B. `PAGE_SIZE`

Defines the default page size when the pagination class uses the global setting.

Example:

```python
REST_FRAMEWORK = {
    "DEFAULT_PAGINATION_CLASS":
        "rest_framework.pagination.PageNumberPagination",

    "PAGE_SIZE": 20,
}
```

### C. `pagination_class`

Defines pagination for an individual view.

Example:

```python
class ProductListView(generics.ListAPIView):

    pagination_class = ProductPagination
```

Disable pagination for a view:

```python
class SmallLookupView(generics.ListAPIView):

    pagination_class = None
```

Use this only when the result set is known to be small.

### D. `paginate_queryset()`

Takes a queryset and returns the current page of results.

Example:

```python
class ProductListView(generics.ListAPIView):

    def list(self, request, *args, **kwargs):

        queryset = self.filter_queryset(
            self.get_queryset()
        )

        page = self.paginate_queryset(queryset)

        if page is not None:
            serializer = self.get_serializer(
                page,
                many=True
            )

            return self.get_paginated_response(
                serializer.data
            )

        serializer = self.get_serializer(
            queryset,
            many=True
        )

        return Response(serializer.data)
```

Generic list views already perform this work, so you rarely need to write it yourself.

### E. `get_paginated_response()`

Creates the paginated response.

Example:

```python
response = self.get_paginated_response(
    serializer.data
)
```

You commonly override this method in a custom pagination class.

# Part 12: PageNumberPagination

## 38. What is PageNumberPagination?

PageNumberPagination uses page numbers to navigate through results.

Requests:

```http
GET /api/products/?page=1
GET /api/products/?page=2
GET /api/products/?page=3
```

## 39. PageNumberPagination attributes

### A. `page_size`

Defines the default number of records per page.

```python
class ProductPagination(PageNumberPagination):

    page_size = 20
```

The API returns up to 20 records per page.

### B. `page_query_param`

Defines the page number query parameter.

Default:

```python
page_query_param = "page"
```

Customize:

```python
page_query_param = "p"
```

Request:

```http
GET /api/products/?p=2
```

### C. `page_size_query_param`

Allows clients to choose how many records they want per page.

Example:

```python
page_size_query_param = "page_size"
```

Request:

```http
GET /api/products/?page=1&page_size=50
```

If it is `None`, clients cannot change the page size through this parameter.

### D. `max_page_size`

Defines the maximum page size clients may request.

Example:

```python
max_page_size = 100
```

If a client requests:

```http
GET /api/products/?page_size=1000
```

the page size is capped at the configured maximum.

### E. `last_page_strings`

Defines accepted strings for requesting the last page.

Default:

```python
last_page_strings = ("last",)
```

Request:

```http
GET /api/products/?page=last
```

### F. `template`

Defines the browsable API pagination template.

Example:

```python
template = "myapp/custom_pagination.html"
```

This affects the browsable API presentation, not the JSON response format.

### G. `django_paginator_class`

Defines which Django paginator class is used internally.

Example:

```python
from django.core.paginator import Paginator


class ProductPagination(PageNumberPagination):

    django_paginator_class = Paginator
```

The default is already Django's `Paginator`, so you normally do not need to change it.

### H. `get_page_size()`

Determines the page size from the request or configuration.

Example:

```python
class ProductPagination(PageNumberPagination):

    page_size = 20

    page_size_query_param = "page_size"

    max_page_size = 100

    def get_page_size(self, request):

        return super().get_page_size(request)
```

This example preserves default behavior. Override it when page-size selection requires custom logic.

### I. `get_page_number()`

Determines the requested page number.

Example:

```python
class ProductPagination(PageNumberPagination):

    def get_page_number(self, request, paginator):

        return super().get_page_number(
            request,
            paginator
        )
```

Normally, the default implementation is sufficient.

### J. `get_paginated_response()`

Creates the response.

Example:

```python
def get_paginated_response(self, data):

    return Response({
        "count": self.page.paginator.count,
        "next": self.get_next_link(),
        "previous": self.get_previous_link(),
        "results": data,
    })
```

### K. `get_next_link()`

Returns the URL for the next page.

Example:

```python
next_url = self.get_next_link()
```

### L. `get_previous_link()`

Returns the URL for the previous page.

Example:

```python
previous_url = self.get_previous_link()
```

These methods are generally called inside `get_paginated_response()`.

### PageNumberPagination summary

| Attribute or method | Purpose |
|---|---|
| `page_size` | Default page size |
| `page_query_param` | Page URL parameter |
| `page_size_query_param` | Client-selected page size |
| `max_page_size` | Maximum page size |
| `last_page_strings` | Last-page parameter values |
| `template` | Browsable API template |
| `django_paginator_class` | Django paginator implementation |
| `get_page_size()` | Determine page size |
| `get_page_number()` | Determine requested page |
| `get_paginated_response()` | Build response |
| `get_next_link()` | Next-page URL |
| `get_previous_link()` | Previous-page URL |

`pagination.py`:

# Part 14: CursorPagination

## 44. What is CursorPagination?

CursorPagination uses an opaque cursor to navigate through records.

Instead of requesting page numbers, clients follow the `next` URL returned by the API.

Common use cases:

- Social media feeds.
- Activity streams.
- Transaction histories.
- Notifications.
- Audit logs.
- Large chronological datasets.

## 45. CursorPagination attributes

### A. `page_size`

Defines the number of records returned per page.

```python
page_size = 20
```

### B. `cursor_query_param`

Defines the URL parameter used for the cursor.

Default:

```python
cursor_query_param = "cursor"
```

Request:

```http
GET /api/products/?cursor=encoded-value
```

Clients should follow the cursor URL returned by the server rather than constructing it.

### C. `ordering`

Defines the ordering field.

Example:

```python
ordering = "-created_at"
```

The ordering should be stable and preferably indexed.

### D. `offset_cutoff`

Limits the internal offset used when records share the same cursor position.

Example:

```python
offset_cutoff = 1000
```

You normally do not need to change this setting.

### E. `template`

Defines the browsable API pagination template.

Example:

```python
template = "myapp/cursor_pagination.html"
```

### F. `get_ordering()`

Determines the ordering used by the cursor paginator.

Example:

```python
class ProductCursorPagination(CursorPagination):

        return super().get_ordering(
            request,
            queryset,
            view
        )
```

### G. `paginate_queryset()`

Applies cursor pagination to the queryset.

Example:

```python
class ProductCursorPagination(CursorPagination):

        self,
        queryset,
        request,
        view=None
    ):

        return super().paginate_queryset(
            queryset,
            request,

        )
```

Normally, use the inherited implementation.

### H. `get_paginated_response()`

Builds the response.

Example:

```python
def get_paginated_response(self, data):

    return Response({
        "next": self.get_next_link(),
        "previous": self.get_previous_link(),
        "results": data,
    })
```

### I. `encode_cursor()`

Encodes cursor information.

Example:

```python
def encode_cursor(self, cursor):

    return super().encode_cursor(cursor)
```

### J. `decode_cursor()`

Decodes the cursor received from a request.

Example:

```python

    return super().decode_cursor(request)
```

These are advanced implementation methods. Most developers should not override them.

| `get_paginated_response()` | Build response |

| `decode_cursor()` | Decode cursor |

### Cursor ordering considerations

A good cursor ordering field should ideally be:

- Immutable.
- Non-null.
- Indexed.
- Unique or nearly unique.

For example:

```python

```

A timestamp may not be unique. DRF has internal handling for tied positions, but a stable ordering is important.

Cursor pagination is not intended for arbitrary page jumps.

**Recommendation:** Use it for chronological feeds and high-volume sequential navigation.

# Part 15: Custom Pagination

## 47. What is custom pagination?

Custom pagination lets you change pagination behavior or the response structure.

Default DRF response:

```json
{
    "count": 100,
    "next": "...",
    "previous": null,
    "results": []
}
```

A frontend might require:

```json
{
    "status": "success",
    "total_records": 100,
    "current_page": 1,
    "data": []
}
```

You can achieve this by extending a built-in pagination class.

## 48. Important methods

### A. `paginate_queryset()`

Controls how a queryset is divided into pages.

Example:

```python
def paginate_queryset(self, queryset, request, view=None):

    return super().paginate_queryset(
        queryset,
        request,
        view
    )
```

Override this only if you need different pagination behavior.

### B. `get_paginated_response()`

Controls the JSON response structure.

Example:

```python
def get_paginated_response(self, data):

    return Response({
        "total_records": self.page.paginator.count,
        "results": data,
    })
```

### C. `get_page_size()`

Determines the requested page size.

Example:

```python
def get_page_size(self, request):

    return super().get_page_size(request)
```

### D. `get_next_link()`

Returns the next page URL.

Example:

```python
next_url = self.get_next_link()
```

### E. `get_previous_link()`

Returns the previous page URL.

Example:

```python
previous_url = self.get_previous_link()
```

## 49. Complete custom pagination example

```python
from rest_framework.pagination import PageNumberPagination
from rest_framework.response import Response


class CustomPagination(PageNumberPagination):

    page_size = 20

    page_size_query_param = "page_size"

    max_page_size = 100

    def get_paginated_response(self, data):

        return Response({

            "status": "success",

            "total_records": self.page.paginator.count,

            "current_page": self.page.number,

            "total_pages": self.page.paginator.num_pages,

            "page_size": self.get_page_size(
                self.request
            ),

            "next": self.get_next_link(),

            "previous": self.get_previous_link(),

            "data": data,
        })
```

Use it:

```python
class ProductListView(generics.ListAPIView):

    queryset = Product.objects.all()

    serializer_class = ProductSerializer

    pagination_class = CustomPagination
```

Example response:

```json
{
    "status": "success",
    "total_records": 100,
    "current_page": 1,
    "total_pages": 5,
    "page_size": 20,
    "next": "http://example.com/api/products/?page=2",
    "previous": null,
    "data": [
        {
            "id": 1,
            "name": "Laptop"
        }
    ]
}
```

**Use custom pagination when:** Your API has a defined response contract or needs special pagination behavior.

Do not create custom pagination simply to rename fields unless the API contract requires it.

# Part 16: Pagination Performance

## 50. Does pagination automatically make queries fast?

No.

Pagination reduces the number of returned records, but database queries can still be expensive.

Performance depends on:

- Filtering.
- Ordering.
- Counting.
- Database indexes.
- Joins.
- Offset size.
- Serializer behavior.

## 51. Database indexes

Example:

```python
class Product(models.Model):

    category = models.CharField(
        max_length=100,
        db_index=True
    )

    created_at = models.DateTimeField(
        auto_now_add=True,
        db_index=True
    )
```

A composite index can help frequent combinations of filtering and ordering:

```python
class Meta:

    indexes = [
        models.Index(
            fields=["category", "-created_at"]
        )
    ]
```

Indexes consume storage and can slow down writes. Add them based on actual query patterns and database analysis.

## 52. Avoid N+1 queries

Suppose products have a ForeignKey to Category.

Potentially inefficient:

```python
products = Product.objects.all()
```

If the serializer accesses the category for every product, additional queries may be executed.

Better:

```python
products = Product.objects.select_related(
    "category"
)
```

For many-to-many relationships:

```python
products = Product.objects.prefetch_related(
    "tags"
)
```

| Method | Used for |
|---|---|
| `select_related()` | ForeignKey and OneToOne |
| `prefetch_related()` | ManyToMany and reverse relationships |

## 53. Restrict page size

Example:

```python
class ProductPagination(PageNumberPagination):

    page_size = 20

    page_size_query_param = "page_size"

    max_page_size = 100
```

This prevents clients from requesting an enormous page.

## 54. Avoid expensive counts when possible

PageNumberPagination and LimitOffsetPagination normally include a total count.

For large datasets, calculating the total can be expensive.

CursorPagination is useful when clients need next/previous navigation but do not need a total count.

## 55. Use efficient ordering

Example:

```python
ordering = "-created_at"
```

For deterministic ordering, use a unique tie-breaker:

```python
queryset = Product.objects.order_by(
    "-created_at",
    "-id"
)
```

This helps avoid ambiguous ordering when multiple records share the same timestamp.

## 56. Analyze database queries

Django provides `explain()`:

```python
queryset = Product.objects.filter(
    category="electronics"
).order_by("-created_at")

print(queryset.explain())
```

Inspect the query plan for:

- Table scans.
- Index usage.
- Expensive joins.
- Sorting costs.

## 57. Pagination performance comparison

| Pagination | Performance characteristics | Suitable use |
|---|---|---|
| PageNumberPagination | Large page numbers can be expensive | CRUD and dashboards |
| LimitOffsetPagination | Large offsets can be expensive | Flexible result windows |
| CursorPagination | Efficient sequential traversal with suitable ordering | Feeds and histories |
| Custom pagination | Depends on implementation | Special requirements |

# Part 20: Common mistakes

## Mistake 1: Returning all records

```python
queryset = Product.objects.all()
```

Without pagination, large datasets can produce enormous responses.

**Better:** Configure pagination for list endpoints.

## Mistake 2: Exposing every ordering field

```python
ordering_fields = "__all__"
```

**Better:**

```python
ordering_fields = [
    "name",
    "price",
    "created_at",
]
```

## Mistake 3: Allowing unlimited page size

**Better:**

```python
max_page_size = 100
```

## Mistake 4: Using huge offsets

Large offsets can be expensive.

**Better:** Consider CursorPagination for sequential navigation.

## Mistake 5: Forgetting deterministic ordering

**Better:**

```python
queryset = Product.objects.order_by(
    "-created_at",
    "-id"
)
```

## Mistake 6: Ignoring N+1 queries

**Better:**

```python
queryset = Product.objects.select_related(
    "category"
).prefetch_related(
    "tags"
)
```

## Mistake 7: Confusing filtering with authorization

Filtering is not automatically a security boundary.

Example:

```python
def get_queryset(self):

    return Product.objects.filter(
        organization=self.request.user.organization
    )
```

This restricts records to the current user's organization. The endpoint must also enforce appropriate authentication and permissions.

## Mistake 8: Accepting invalid query parameters

**Better:** Validate numeric values, dates, ranges and page sizes. Restrict ordering and search fields.

# Part 21: Interview questions and answers

### Q1. What is filtering in DRF?

Filtering restricts a queryset based on supplied query parameters.

Example:

```http
GET /api/products/?category=electronics
```

### Q2. What is DjangoFilterBackend?

It is a DRF backend that integrates django-filter to apply structured filters to querysets.

### Q3. What is the difference between filterset_fields and filterset_class?

`filterset_fields` defines simple model-field filters directly on a view.

`filterset_class` connects a custom FilterSet class for complex filtering.

### Q4. What is FilterSet?

It is a django-filter base class used to define filtering rules for a Django model.

### Q5. What is field_name?

It identifies the model field on which a filter operates.

### Q6. What is lookup_expr?

It defines the ORM lookup operation, such as `exact`, `icontains`, `gte` or `lte`.

### Q7. What is the difference between filter and exclude?

`filter()` returns matching records.

`exclude()` returns records that do not match the supplied condition.

### Q8. What is SearchFilter?

A built-in DRF backend that searches configured model fields using a search query parameter.

### Q9. What is search_fields?

It defines which fields SearchFilter searches.

### Q10. What is the difference between SearchFilter and DjangoFilterBackend?

SearchFilter performs text-based searching.

DjangoFilterBackend performs structured field filtering.

### Q11. What is OrderingFilter?

It allows clients to sort results using an ordering query parameter.

### Q12. What does a minus sign mean in ordering?

It indicates descending order.

```http
GET /api/products/?ordering=-price
```

### Q13. Why should we define ordering_fields?

It restricts which model fields clients can use for sorting and avoids exposing unintended or expensive ordering operations.

### Q14. What is a custom filter backend?

A class extending `BaseFilterBackend` that implements `filter_queryset()` to apply custom filtering logic.

### Q15. What is pagination?

Pagination divides a large queryset into smaller result sets.

### Q16. What are the three built-in DRF pagination classes?

1. PageNumberPagination.
2. LimitOffsetPagination.
3. CursorPagination.

### Q17. What is the difference between PageNumberPagination and LimitOffsetPagination?

PageNumberPagination uses page numbers:

```http
?page=2
```

LimitOffsetPagination uses limit and offset:

```http
?limit=20&offset=20
```

### Q18. What is CursorPagination?

It uses an opaque cursor to navigate through an ordered queryset.

It is useful for high-volume feeds and histories.

### Q19. Which pagination is best for large datasets?

It depends on the access pattern.

CursorPagination is often suitable for sequential navigation through large datasets. Page-number pagination is more convenient when users need direct page navigation.

### Q20. What is max_page_size?

It limits the maximum number of records a client can request in one page.

### Q21. Why is ordering important in pagination?

Stable ordering makes pagination predictable and reduces inconsistent results across requests.

### Q22. What is the difference between select_related and prefetch_related?

`select_related()` optimizes ForeignKey and OneToOne relationships.

`prefetch_related()` optimizes ManyToMany and reverse relationships.

### Q23. Does filtering happen before pagination?

Yes. DRF applies filter backends before pagination.

### Q24. Can SearchFilter, OrderingFilter and DjangoFilterBackend be combined?

Yes. A view can configure all three in its `filter_backends` list.

### Q25. Why can large offsets be slow?

The database may need to scan or skip many rows before returning the requested result window.

### Q26. How do you improve list API performance?

Use:

- Database indexes.
- Efficient querysets.
- `select_related()`.
- `prefetch_related()`.
- Restricted page sizes.
- Cursor pagination where appropriate.
- Efficient serializers.
- Database query-plan analysis.

### Q27. How would you build an e-commerce product listing API?

I would use:

- DjangoFilterBackend for category and price filters.
- SearchFilter for product names and descriptions.
- OrderingFilter for price and date sorting.
- PageNumberPagination for normal browsing.
- Database indexes based on actual query patterns.

### Q28. How do you prevent users from accessing another organization's records?

Restrict the queryset based on the authenticated user's organization and enforce suitable permissions.

Never trust an organization ID supplied by the client as the only authorization check.

# Final recommendation

For a typical production DRF project:

1. Use `django-filter` for structured filtering.
2. Use `SearchFilter` for simple text searches.
3. Use `OrderingFilter` with an explicit allowlist.
4. Use `PageNumberPagination` for ordinary CRUD APIs.
5. Use `CursorPagination` for large chronological feeds.
6. Use custom backends only when business logic requires them.
7. Validate query parameters.
8. Optimize database queries and indexes.

**Remember these four principles:**

- Filtering = Which records?
- Searching = Which records match this text?
- Ordering = In what sequence?
- Pagination = How many records at a time?

**Important learning note:** Configuration attributes such as `page_size`, `ordering_fields` and `filterset_class` are intended to be set in your application. Methods such as `get_filterset()`, `get_ordering()` and `paginate_queryset()` are usually framework implementation hooks. Learn what they do, but override them only when the default behavior does not meet your requirements.
