# Django REST Framework – Filtering, Searching, Ordering and Pagination

## 1. Understanding Filtering, Searching, Ordering and Pagination

These are essential features of almost every production REST API.

Imagine an e-commerce API containing 100,000 products.

A client might want to:

- Retrieve only products belonging to a particular category.
- Search for products containing the word "laptop".
- Sort products by price.
- Retrieve only 20 products per request.
- Navigate to the next page of results.

DRF provides built-in features and third-party integrations to handle these requirements.

### Difference between the four concepts

| Feature | Purpose | Example |
|---|---|---|
| Filtering | Select records matching conditions | Products with category = electronics |
| Searching | Find records containing specific text | Products containing "laptop" |
| Ordering | Sort the returned records | Price ascending |
| Pagination | Divide results into smaller pages | 20 products per page |

### Example API

```http
GET /api/products/?category=electronics&search=laptop&ordering=price&page=1
```

This request means:

1. Retrieve products in the electronics category.
2. Search for products matching "laptop".
3. Sort by price.
4. Return the first page.

**Industry recommendation:** Support filtering, searching, ordering and pagination in list endpoints. These features improve usability, reduce unnecessary data transfer, and make APIs scalable.

# 2. Django Filter Backend

## What is Django Filter Backend?

DRF provides a filtering architecture called `DjangoFilterBackend`.

It allows API clients to filter database records using URL query parameters.

For example:

```http
GET /api/products/?category=electronics
```

The API returns only products belonging to the electronics category.

## Why do we need filtering?

Without filtering, the API might return every record:

```python
class ProductListView(generics.ListAPIView):
    queryset = Product.objects.all()
    serializer_class = ProductSerializer
```

If the database contains 50,000 products, the API may need to process a very large queryset.

Filtering allows clients to retrieve only relevant records.

## When should we use it?

Use filtering when clients need to:

- Filter products by category.
- Retrieve orders by status.
- Filter employees by department.
- Retrieve customers from a particular country.
- Filter transactions by date.
- Retrieve published blog posts.

## Installation

DRF's `DjangoFilterBackend` is provided through the third-party `django-filter` package.

```bash
pip install django-filter
```

Add the application to `settings.py`:

```python
INSTALLED_APPS = [
    # Other applications
    "django_filters",
]
```

Configure DRF:

```python
REST_FRAMEWORK = {
    "DEFAULT_FILTER_BACKENDS": [
        "django_filters.rest_framework.DjangoFilterBackend",
    ],
}
```

## Basic example

Suppose we have this model:

```python
from django.db import models

class Product(models.Model):
    name = models.CharField(max_length=200)
    category = models.CharField(max_length=100)
    price = models.DecimalField(max_digits=10, decimal_places=2)
    is_available = models.BooleanField(default=True)
```

Create a list API:

```python
from rest_framework import generics
from django_filters.rest_framework import DjangoFilterBackend

class ProductListView(generics.ListAPIView):
    queryset = Product.objects.all()
    serializer_class = ProductSerializer

    filter_backends = [DjangoFilterBackend]

    filterset_fields = [
        "category",
        "is_available",
    ]
```

### API requests

Filter by category:

```http
GET /api/products/?category=electronics
```

Filter by availability:

```http
GET /api/products/?is_available=true
```

Combine filters:

```http
GET /api/products/?category=electronics&is_available=true
```

### Example response

```json
[
    {
        "id": 1,
        "name": "Laptop",
        "category": "electronics",
        "price": "1200.00",
        "is_available": true
    },
    {
        "id": 2,
        "name": "Monitor",
        "category": "electronics",
        "price": "300.00",
        "is_available": true
    }
]
```

### What happens internally?

The backend applies conditions to the queryset.

Conceptually:

```python
Product.objects.filter(
    category="electronics",
    is_available=True
)
```

Django ORM generates the corresponding SQL query.

## When should we NOT use it?

Avoid relying only on simple `filterset_fields` when:

- You need complex filtering logic.
- You need range filters.
- You need custom validation.
- You need filters spanning related models with special behavior.

For those cases, define a custom `FilterSet`.

# 3. django-filter Integration

## What is django-filter?

`django-filter` is a Django package that provides a flexible way to define filtering rules.

It integrates with DRF through `DjangoFilterBackend`.

While `filterset_fields` supports straightforward filters, a `FilterSet` gives you more control over:

- Exact matching.
- Case-insensitive matching.
- Greater-than and less-than conditions.
- Date ranges.
- Related model filtering.
- Custom filter methods.
- Filter validation.

## Why do we need it?

Consider a product API.

Clients may want to request:

```http
GET /api/products/?min_price=100&max_price=1000
```

Or:

```http
GET /api/products/?name=laptop
```

Simple field declarations do not cover every custom requirement conveniently.

## Example: Custom FilterSet

Create `filters.py`:

```python
import django_filters
from .models import Product


class ProductFilter(django_filters.FilterSet):

    min_price = django_filters.NumberFilter(
        field_name="price",
        lookup_expr="gte"
    )

    max_price = django_filters.NumberFilter(
        field_name="price",
        lookup_expr="lte"
    )

    name = django_filters.CharFilter(
        field_name="name",
        lookup_expr="icontains"
    )

    class Meta:
        model = Product
        fields = [
            "category",
            "is_available",
        ]
```

Configure the API:

```python
from rest_framework import generics
from django_filters.rest_framework import DjangoFilterBackend

from .filters import ProductFilter


class ProductListView(generics.ListAPIView):

    queryset = Product.objects.all()

    serializer_class = ProductSerializer

    filter_backends = [
        DjangoFilterBackend
    ]

    filterset_class = ProductFilter
```

### API requests

Find products costing at least 100:

```http
GET /api/products/?min_price=100
```

Find products costing at most 1000:

```http
GET /api/products/?max_price=1000
```

Find products between 100 and 1000:

```http
GET /api/products/?min_price=100&max_price=1000
```

Search product names:

```http
GET /api/products/?name=laptop
```

### Example response

```json
[
    {
        "id": 1,
        "name": "Gaming Laptop",
        "category": "electronics",
        "price": "850.00",
        "is_available": true
    }
]
```

## Common lookup expressions

| Lookup | Meaning | Example |
|---|---|---|
| exact | Exact match | `category=electronics` |
| icontains | Case-insensitive contains | `name=laptop` |
| contains | Case-sensitive contains | `name=Pro` |
| gt | Greater than | `price__gt=500` |
| gte | Greater than or equal | `price__gte=500` |
| lt | Less than | `price__lt=500` |
| lte | Less than or equal | `price__lte=500` |
| in | Match any supplied value | `id__in=1,2,3` |
| isnull | Check for NULL | `category__isnull=true` |

## Custom method filters

Sometimes filtering requires business logic.

Example: filter products by whether they are expensive.

```python
class ProductFilter(django_filters.FilterSet):

    expensive = django_filters.BooleanFilter(
        method="filter_expensive"
    )

    class Meta:
        model = Product
        fields = []

    def filter_expensive(self, queryset, name, value):

        if value:
            return queryset.filter(price__gte=1000)

        return queryset.filter(price__lt=1000)
```

Request:

```http
GET /api/products/?expensive=true
```

This returns products costing at least 1000.

## When should we use django-filter?

Use it for production APIs with structured filters, particularly:

- E-commerce product filters.
- Order management.
- Financial transactions.
- Employee management.
- Reporting APIs.
- Date and numeric ranges.

**Industry recommendation:** Prefer explicit `FilterSet` classes for complex APIs. They keep filtering logic separate from views and make the API easier to maintain.

# 4. SearchFilter

## What is SearchFilter?

`SearchFilter` is a built-in DRF filter backend that provides text-based searching.

It allows clients to search through one or more fields.

For example:

```http
GET /api/products/?search=laptop
```

## Why do we need it?

Filtering and searching are different.

Filtering usually matches structured values:

```http
GET /api/products/?category=electronics
```

Searching finds text matching a search term:

```http
GET /api/products/?search=laptop
```

## Basic configuration

```python
from rest_framework import generics
from rest_framework.filters import SearchFilter


class ProductListView(generics.ListAPIView):

    queryset = Product.objects.all()

    serializer_class = ProductSerializer

    filter_backends = [
        SearchFilter
    ]

    search_fields = [
        "name",
        "category",
    ]
```

### API request

```http
GET /api/products/?search=laptop
```

DRF searches the configured fields.

### Example response

```json
[
    {
        "id": 1,
        "name": "Gaming Laptop",
        "category": "electronics",
        "price": "1200.00"
    },
    {
        "id": 2,
        "name": "Laptop Stand",
        "category": "accessories",
        "price": "40.00"
    }
]
```

## Search across multiple fields

```python
search_fields = [
    "name",
    "category",
    "description",
]
```

Now the API searches all three fields.

## Search lookup prefixes

DRF supports special prefixes:

| Prefix | Lookup | Meaning |
|---|---|---|
| None | `icontains` | Case-insensitive partial match |
| `^` | `istartswith` | Starts with |
| `=` | `iexact` | Exact case-insensitive match |
| `@` | `search` | Full-text search lookup on supported databases |
| `$` | `iregex` | Case-insensitive regular expression |

Example:

```python
search_fields = [
    "^name",
    "description",
    "=sku",
]
```

This means:

- `name` must start with the search term.
- `description` is searched using partial matching.
- `sku` is matched exactly, ignoring case.

## Searching related models

You can also search related fields using Django ORM relationship notation.

Example:

```python
search_fields = [
    "name",
    "category__name",
    "brand__name",
]
```

Here, `category` and `brand` are related models.

## When should we use SearchFilter?

Use it for:

- Product search.
- Blog search.
- Customer lookup.
- Employee directories.
- Searching descriptions and titles.

## When should we NOT use it?

For large-scale, sophisticated search requirements, `SearchFilter` may not be sufficient.

Examples:

- Typo tolerance.
- Search relevance ranking.
- Synonyms.
- Complex language analysis.
- Faceted search.
- Very large search indexes.

Consider PostgreSQL full-text search or dedicated search platforms such as Elasticsearch or OpenSearch.

**Industry recommendation:** Use DRF `SearchFilter` for simple database-backed text search. Use a dedicated search solution when search becomes a major product feature.

# 5. OrderingFilter

## What is OrderingFilter?

`OrderingFilter` allows clients to sort API results.

For example:

```http
GET /api/products/?ordering=price
```

This sorts products by ascending price.

## Why do we need it?

Clients often need to sort results by:

- Price.
- Creation date.
- Name.
- Rating.
- Popularity.

Without ordering, the API should not promise a particular order unless the queryset explicitly defines one.

## Basic implementation

```python
from rest_framework import generics
from rest_framework.filters import OrderingFilter


class ProductListView(generics.ListAPIView):

    queryset = Product.objects.all()

    serializer_class = ProductSerializer

    filter_backends = [
        OrderingFilter
    ]

    ordering_fields = [
        "name",
        "price",
        "created_at",
    ]

    ordering = [
        "name"
    ]
```

## API requests

Ascending price:

```http
GET /api/products/?ordering=price
```

Descending price:

```http
GET /api/products/?ordering=-price
```

Ascending creation date:

```http
GET /api/products/?ordering=created_at
```

Newest first:

```http
GET /api/products/?ordering=-created_at
```

Multiple ordering fields:

```http
GET /api/products/?ordering=category,-price
```

This sorts by category first and then by price descending within each category.

## Example response

```json
[
    {
        "id": 1,
        "name": "Mouse",
        "price": "20.00"
    },
    {
        "id": 2,
        "name": "Keyboard",
        "price": "50.00"
    },
    {
        "id": 3,
        "name": "Laptop",
        "price": "1200.00"
    }
]
```

## Why should we define ordering_fields?

Avoid exposing every model field automatically.

For example:

```python
ordering_fields = "__all__"
```

This can expose unintended sorting options and may allow expensive database operations.

Prefer an explicit allowlist:

```python
ordering_fields = [
    "name",
    "price",
    "created_at",
]
```

## When should we use OrderingFilter?

Use it for:

- Product listings.
- Order history.
- Employee directories.
- Transaction lists.
- Article feeds.
- Reports.

**Industry recommendation:** Explicitly define allowed ordering fields and provide a stable default ordering.

# 6. Custom Filter Backends

## What is a custom filter backend?

A custom filter backend allows you to implement your own filtering logic.

DRF provides a base class called `BaseFilterBackend`.

You implement the `filter_queryset()` method.

## Why do we need it?

Sometimes standard filters cannot express your business rules conveniently.

Example requirements:

- Only show products available to the current user.
- Filter records based on the current user's organization.
- Exclude archived records by default.
- Apply tenant-specific restrictions.
- Filter by custom query parameters.

## Basic implementation

Create `filters.py`:

```python
from rest_framework.filters import BaseFilterBackend


class AvailableProductFilter(BaseFilterBackend):

    def filter_queryset(self, request, queryset, view):

        available = request.query_params.get("available")

        if available == "true":
            queryset = queryset.filter(is_available=True)

        elif available == "false":
            queryset = queryset.filter(is_available=False)

        return queryset
```

Use it in a view:

```python
class ProductListView(generics.ListAPIView):

    queryset = Product.objects.all()

    serializer_class = ProductSerializer

    filter_backends = [
        AvailableProductFilter
    ]
```

### API requests

```http
GET /api/products/?available=true
```

Returns available products.

```http
GET /api/products/?available=false
```

Returns unavailable products.

## Example: Filter by current user's organization

Suppose every product belongs to an organization.

```python
class OrganizationProductFilter(BaseFilterBackend):

    def filter_queryset(self, request, queryset, view):

        return queryset.filter(
            organization=request.user.organization
        )
```

This ensures the queryset is restricted to the user's organization.

Important: This example assumes that the authenticated user has an `organization` relationship.

For sensitive multi-tenant applications, enforce tenant isolation in the queryset or service layer even if other filters are also configured.

## Custom backend vs django-filter

| Feature | Custom Backend | django-filter |
|---|---|---|
| Simple filters | Possible | Excellent |
| Range filters | Manual implementation | Built-in support |
| Complex business logic | Excellent | Supported through methods |
| Reusability | Excellent | Excellent |
| Validation | You implement it | Built-in filter validation |
| Boilerplate | More | Less |

## When should we use custom backends?

Use them when:

- Filtering depends on the current user.
- Business rules control which records appear.
- Multiple views share the same custom filtering behavior.
- Filtering cannot be expressed cleanly using a `FilterSet`.

Avoid custom backends for ordinary field filtering when `django-filter` already solves the problem.

# 7. Query Parameter Validation

## What is query parameter validation?

Query parameters are values passed through the URL.

Example:

```http
GET /api/products/?min_price=100&max_price=500
```

The API must validate these values.

For example, what happens if a client sends:

```http
GET /api/products/?min_price=abc
```

Or:

```http
GET /api/products/?min_price=-500
```

Or:

```http
GET /api/products/?min_price=1000&max_price=100
```

An API should not silently accept invalid business inputs.

## Why do we need validation?

Validation protects the API from:

- Invalid data types.
- Negative values where they are not allowed.
- Incorrect date ranges.
- Unsupported sorting fields.
- Unexpected query parameters.
- Excessively expensive requests.

## Method 1: Validate using django-filter

```python
import django_filters


class ProductFilter(django_filters.FilterSet):

    min_price = django_filters.NumberFilter(
        field_name="price",
        lookup_expr="gte",
    )

    max_price = django_filters.NumberFilter(
        field_name="price",
        lookup_expr="lte",
    )

    class Meta:
        model = Product
        fields = []

    def clean(self):
        cleaned_data = super().clean()

        min_price = cleaned_data.get("min_price")
        max_price = cleaned_data.get("max_price")

        if (
            min_price is not None
            and max_price is not None
            and min_price > max_price
        ):
            raise django_filters.exceptions.ValidationError(
                "Minimum price cannot exceed maximum price."
            )

        return cleaned_data
```

The exact validation hooks available depend on the installed django-filter version and filter configuration. Another reliable approach is to validate a query parameter serializer before applying filters.

## Method 2: Use a DRF serializer

This is useful when query parameters have several related rules.

```python
from rest_framework import serializers


class ProductQuerySerializer(serializers.Serializer):

    min_price = serializers.DecimalField(
        max_digits=10,
        decimal_places=2,
        required=False,
        min_value=0,
    )

    max_price = serializers.DecimalField(
        max_digits=10,
        decimal_places=2,
        required=False,
        min_value=0,
    )

    category = serializers.CharField(
        required=False,
        max_length=100,
    )

    def validate(self, attrs):

        minimum = attrs.get("min_price")
        maximum = attrs.get("max_price")

        if (
            minimum is not None
            and maximum is not None
            and minimum > maximum
        ):
            raise serializers.ValidationError(
                "min_price cannot exceed max_price."
            )

        return attrs
```

Use it in a view:

```python
class ProductListView(generics.ListAPIView):

    serializer_class = ProductSerializer

    def get_queryset(self):

        params = ProductQuerySerializer(
            data=self.request.query_params
        )

        params.is_valid(raise_exception=True)

        data = params.validated_data

        queryset = Product.objects.all()

        if "min_price" in data:
            queryset = queryset.filter(
                price__gte=data["min_price"]
            )

        if "max_price" in data:
            queryset = queryset.filter(
                price__lte=data["max_price"]
            )

        if "category" in data:
            queryset = queryset.filter(
                category=data["category"]
            )

        return queryset
```

### Invalid request

```http
GET /api/products/?min_price=1000&max_price=100
```

Example response:

```json
{
    "non_field_errors": [
        "min_price cannot exceed max_price."
    ]
}
```

## Best practices

1. Validate numbers as numbers.
2. Validate date formats.
3. Restrict ordering fields.
4. Limit page sizes.
5. Reject invalid ranges.
6. Set maximum search lengths.
7. Avoid allowing arbitrary ORM field names from clients.
8. Return clear validation errors.

**Industry recommendation:** Use `django-filter` for normal filter validation and DRF serializers for cross-parameter business validation.

# 8. Pagination Fundamentals

## What is pagination?

Pagination divides a large result set into smaller groups called pages.

Suppose an API contains 10,000 products.

Returning all 10,000 products in one response is inefficient.

Instead, return 20 products per request.

## Why do we need pagination?

Pagination improves:

- Response size.
- Network performance.
- Database efficiency when appropriately implemented.
- Frontend responsiveness.
- User experience.
- Scalability.

## Without pagination

```python
class ProductListView(generics.ListAPIView):

    queryset = Product.objects.all()

    serializer_class = ProductSerializer
```

If pagination is not configured globally or locally, this may return the entire matching queryset.

## With pagination

A paginated API returns a limited number of records.

Example:

```json
{
    "count": 100,
    "next": "http://example.com/api/products/?page=2",
    "previous": null,
    "results": [
        {
            "id": 1,
            "name": "Laptop"
        },
        {
            "id": 2,
            "name": "Mouse"
        }
    ]
}
```

The response includes:

| Field | Meaning |
|---|---|
| count | Total number of matching records |
| next | URL for the next page |
| previous | URL for the previous page |
| results | Records on the current page |

## DRF pagination types

DRF provides three main pagination classes:

1. PageNumberPagination.
2. LimitOffsetPagination.
3. CursorPagination.

You can also implement custom pagination.

---

# 9. PageNumberPagination

## What is PageNumberPagination?

Page-number pagination allows clients to navigate through results using page numbers.

Example:

```http
GET /api/products/?page=1
GET /api/products/?page=2
GET /api/products/?page=3
```

## Why do we use it?

It is simple and easy to understand.

It is particularly useful for:

- Admin dashboards.
- Product catalogs.
- Blog listings.
- Employee directories.
- Search result pages.

## Configuration

Create `pagination.py`:

```python
from rest_framework.pagination import PageNumberPagination


class ProductPagination(PageNumberPagination):

    page_size = 10

    page_query_param = "page"

    page_size_query_param = "page_size"

    max_page_size = 50
```

Configure the view:

```python
class ProductListView(generics.ListAPIView):

    queryset = Product.objects.all()

    serializer_class = ProductSerializer

    pagination_class = ProductPagination
```

### API requests

First page:

```http
GET /api/products/?page=1
```

Second page:

```http
GET /api/products/?page=2
```

Change page size:

```http
GET /api/products/?page=1&page_size=20
```

The maximum page size is 50.

### Example response

```json
{
    "count": 100,
    "next": "http://example.com/api/products/?page=2",
    "previous": null,
    "results": [
        {
            "id": 1,
            "name": "Laptop"
        },
        {
            "id": 2,
            "name": "Mouse"
        }
    ]
}
```

## Global configuration

Instead of configuring pagination separately for each view:

```python
REST_FRAMEWORK = {
    "DEFAULT_PAGINATION_CLASS":
        "myapp.pagination.ProductPagination",

    "PAGE_SIZE": 10,
}
```

When the custom class defines its own `page_size`, that class setting takes precedence.

## Invalid page numbers

If a client requests a page that does not exist, DRF normally returns a 404 response.

Example:

```http
GET /api/products/?page=9999
```

Example response:

```json
{
    "detail": "Invalid page."
}
```

## Advantages

- Easy for frontend developers.
- Easy to understand.
- Provides total result count.
- Supports direct navigation to a page.

## Disadvantages

- Large page numbers can become expensive.
- Concurrent inserts and deletions can shift records between pages.
- Counting all matching records may be expensive for very large datasets.

**Industry recommendation:** PageNumberPagination is a good default for ordinary CRUD applications and admin interfaces.

# 10. LimitOffsetPagination

## What is LimitOffsetPagination?

Limit-offset pagination lets clients specify:

- `limit`: Maximum number of records to return.
- `offset`: Number of records to skip.

Example:

```http
GET /api/products/?limit=10&offset=20
```

This means:

- Skip the first 20 records.
- Return the next 10 records.

## Why do we use it?

It provides flexible control over result windows.

It is useful for:

- Data exploration.
- Reporting APIs.
- Applications that already use limit-offset conventions.
- APIs where clients control the result window.

## Configuration

```python
from rest_framework.pagination import LimitOffsetPagination


class ProductPagination(LimitOffsetPagination):

    default_limit = 10

    limit_query_param = "limit"

    offset_query_param = "offset"

    max_limit = 50
```

Use it:

```python
class ProductListView(generics.ListAPIView):

    queryset = Product.objects.all()

    serializer_class = ProductSerializer

    pagination_class = ProductPagination
```

### API requests

First 10 products:

```http
GET /api/products/?limit=10&offset=0
```

Next 10 products:

```http
GET /api/products/?limit=10&offset=10
```

Skip 50 and retrieve 20:

```http
GET /api/products/?limit=20&offset=50
```

### Example response

```json
{
    "count": 100,
    "next": "http://example.com/api/products/?limit=10&offset=30",
    "previous": "http://example.com/api/products/?limit=10",
    "results": [
        {
            "id": 21,
            "name": "Product 21"
        },
        {
            "id": 22,
            "name": "Product 22"
        }
    ]
}
```

## Advantages

- Flexible.
- Easy to implement.
- Clients can jump to a particular offset.
- Useful for APIs requiring arbitrary result windows.

## Disadvantages

Large offsets can become expensive.

For example:

```http
GET /api/products/?limit=20&offset=500000
```

The database may need to scan or skip a large number of rows.

Also, inserts and deletions can shift records between requests.

**Industry recommendation:** Use LimitOffsetPagination when clients genuinely need offset-based access. Avoid huge offsets for high-volume datasets.

# 11. CursorPagination

## What is CursorPagination?

Cursor pagination uses an opaque cursor to navigate through a dataset.

Instead of requesting a page number or an offset, the client receives a cursor URL.

Example:

```http
GET /api/products/
```

The response contains a `next` URL with a cursor.

The client follows that URL to retrieve the next group of records.

## Why do we need it?

For very large datasets, offset-based pagination can become inefficient.

Cursor pagination is designed for efficient traversal through consistently ordered records.

It is particularly useful for:

- Activity feeds.
- Transaction histories.
- Audit logs.
- Notifications.
- Event streams.
- Large datasets that are mostly read in sequence.

## Configuration

```python
from rest_framework.pagination import CursorPagination


class ProductCursorPagination(CursorPagination):

    page_size = 20

    ordering = "-created_at"
```

Use it:

```python
class ProductListView(generics.ListAPIView):

    queryset = Product.objects.all()

    serializer_class = ProductSerializer

    pagination_class = ProductCursorPagination
```

### API request

```http
GET /api/products/
```

Example response:

```json
{
    "next": "http://example.com/api/products/?cursor=cD0yMDI2...",
    "previous": null,
    "results": [
        {
            "id": 100,
            "name": "Laptop"
        },
        {
            "id": 99,
            "name": "Mouse"
        }
    ]
}
```

The actual cursor value is opaque. Clients should not construct or modify it.

### Next request

Use the complete `next` URL:

```http
GET /api/products/?cursor=cD0yMDI2...
```

DRF generates the next cursor.

## Important ordering requirement

Cursor pagination needs a consistent ordering field.

A good choice is a creation timestamp:

```python
ordering = "-created_at"
```

The ordering field should ideally be:

- Immutable.
- Indexed.
- Non-null.
- Unique or nearly unique.

A timestamp alone may not be unique. DRF's cursor implementation has position-plus-offset behavior for tied positions, but a unique, stable ordering key is preferable for predictable traversal.

## Advantages

- Avoids large offset scans.
- Works well for large feeds.
- Handles many concurrent insertions better than page-number pagination.
- Efficient sequential navigation.

## Disadvantages

- Clients cannot jump directly to page 50.
- Cursors are not designed for arbitrary page navigation.
- Ordering must be stable.
- Cursor pagination is more complex than page-number pagination.

## Example with an indexed timestamp

Model:

```python
class Product(models.Model):

    name = models.CharField(max_length=200)

    created_at = models.DateTimeField(
        auto_now_add=True,
        db_index=True
    )
```

Pagination:

```python
class ProductCursorPagination(CursorPagination):

    page_size = 20

    ordering = "-created_at"
```

**Industry recommendation:** Use CursorPagination for high-volume feeds and chronological histories where users move forward or backward through results rather than jumping to arbitrary pages.

# 12. Custom Pagination

## What is custom pagination?

Custom pagination means creating your own pagination response format or behavior.

DRF allows you to extend its pagination classes.

## Why do we need it?

Some APIs require a specific response format.

For example, a frontend may expect:

```json
{
    "status": "success",
    "total_records": 100,
    "page": 1,
    "page_size": 10,
    "data": []
}
```

DRF's default pagination response has different field names.

Custom pagination lets you adapt the output.

## Example: Custom PageNumberPagination

```python
from rest_framework.pagination import PageNumberPagination
from rest_framework.response import Response


class CustomPagination(PageNumberPagination):

    page_size = 10

    page_size_query_param = "page_size"

    max_page_size = 50

    def get_paginated_response(self, data):

        return Response({
            "status": "success",
            "total_records": self.page.paginator.count,
            "current_page": self.page.number,
            "total_pages": self.page.paginator.num_pages,
            "page_size": self.get_page_size(
                self.request
            ),
            "next": self.get_next_link(),
            "previous": self.get_previous_link(),
            "data": data,
        })
```

Use it:

```python
class ProductListView(generics.ListAPIView):

    queryset = Product.objects.all()

    serializer_class = ProductSerializer

    pagination_class = CustomPagination
```

### Example response

```json
{
    "status": "success",
    "total_records": 100,
    "current_page": 1,
    "total_pages": 10,
    "page_size": 10,
    "next": "http://example.com/api/products/?page=2",
    "previous": null,
    "data": [
        {
            "id": 1,
            "name": "Laptop"
        },
        {
            "id": 2,
            "name": "Mouse"
        }
    ]
}
```

## Custom pagination with LimitOffsetPagination

You can also customize limit-offset responses.

```python
from rest_framework.pagination import LimitOffsetPagination
from rest_framework.response import Response


class CustomLimitOffsetPagination(
    LimitOffsetPagination
):

    default_limit = 20

    max_limit = 100

    def get_paginated_response(self, data):

        return Response({
            "total": self.count,
            "limit": self.limit,
            "offset": self.offset,
            "next": self.get_next_link(),
            "previous": self.get_previous_link(),
            "results": data,
        })
```

## When should we use custom pagination?

Use it when:

- Your organization has a standard response format.
- The frontend requires specific pagination metadata.
- You need custom pagination behavior.
- Your API has additional metadata requirements.

Avoid creating custom pagination unnecessarily. Standard DRF pagination is easier to maintain and is already widely understood.

# 13. Pagination Performance

## Why is pagination performance important?

Pagination limits the number of returned records, but it does not automatically make every database query efficient.

For example:

```python
Product.objects.all()
```

Even when paginated, the database may still need to perform expensive operations depending on:

- Sorting.
- Filtering.
- Counting.
- Joins.
- Offset size.
- Database indexes.

## 13.1 Add database indexes

Suppose clients frequently filter products by category and sort by creation date.

```python
class Product(models.Model):

    name = models.CharField(max_length=200)

    category = models.CharField(
        max_length=100,
        db_index=True
    )

    created_at = models.DateTimeField(
        auto_now_add=True,
        db_index=True
    )
```

Indexes can improve filtering and ordering performance when they match actual query patterns.

However, indexes also consume storage and make writes more expensive.

For combined filters and ordering, a composite index may be useful:

```python
class Meta:
    indexes = [
        models.Index(
            fields=["category", "-created_at"]
        )
    ]
```

Choose indexes based on real query patterns and database query plans.

## 13.2 Avoid N+1 queries

Suppose each product has a related category.

Bad approach:

```python
products = Product.objects.all()
```

If the serializer accesses a related object for every product, Django may execute additional queries repeatedly.

Better:

```python
products = Product.objects.select_related(
    "category"
)
```

For many-to-many or reverse relationships:

```python
products = Product.objects.prefetch_related(
    "tags"
)
```

### Difference

| Method | Best use |
|---|---|
| select_related | ForeignKey and OneToOneField |
| prefetch_related | ManyToManyField and reverse relationships |

## 13.3 Limit the page size

Avoid allowing unlimited page sizes.

Bad:

```python
page_size_query_param = "page_size"
```

Without a maximum, clients might request huge result sets.

Better:

```python
class ProductPagination(PageNumberPagination):

    page_size = 20

    page_size_query_param = "page_size"

    max_page_size = 100
```

## 13.4 Avoid expensive counts where possible

PageNumberPagination and LimitOffsetPagination typically include a total count.

For very large datasets, calculating an exact count may be expensive.

CursorPagination avoids the normal total-count response and is useful when clients only need next/previous navigation.

## 13.5 Use efficient ordering

Ordering by an indexed field can improve query performance.

Example:

```python
ordering = "-created_at"
```

For stable pagination, add a unique tie-breaker when using ordinary offset-based pagination:

```python
queryset = Product.objects.order_by(
    "-created_at",
    "-id"
)
```

## 13.6 Use only necessary fields

If the API does not need every database column:

```python
queryset = Product.objects.only(
    "id",
    "name",
    "price"
)
```

Use this carefully: accessing deferred fields later can cause extra database queries.

## 13.7 Analyze queries

Django provides query inspection tools.

Example:

```python
queryset = Product.objects.filter(
    category="electronics"
).order_by("-created_at")

print(queryset.explain())
```

Use the database query plan to understand whether indexes are being used.

## Performance comparison

| Pagination type | Large dataset behavior | Best use |
|---|---|---|
| PageNumberPagination | Can become expensive at high page numbers | General CRUD |
| LimitOffsetPagination | Large offsets can be expensive | Flexible result windows |
| CursorPagination | Efficient sequential traversal with suitable ordering | Feeds and histories |
| Custom pagination | Depends on implementation | Special API requirements |

**Industry recommendation:** For high-volume APIs, consider cursor pagination, proper indexes, efficient serializers, and query optimization. Pagination alone is not a substitute for database optimization.

# 14. Filtering and Pagination Together

## Can we use filtering and pagination together?

Yes.

This is one of the most common DRF API patterns.

DRF applies filtering to the queryset before pagination is performed.

Conceptually:

1. Start with the base queryset.
2. Apply filter backends.
3. Apply pagination to the filtered queryset.
4. Serialize the current page.
5. Return the response.

## Example implementation

```python
from rest_framework import generics
from rest_framework.filters import (
    SearchFilter,
    OrderingFilter,
)
from django_filters.rest_framework import DjangoFilterBackend


class ProductListView(generics.ListAPIView):

    queryset = Product.objects.all()

    serializer_class = ProductSerializer

    filter_backends = [
        DjangoFilterBackend,
        SearchFilter,
        OrderingFilter,
    ]

    filterset_fields = [
        "category",
        "is_available",
    ]

    search_fields = [
        "name",
        "description",
    ]

    ordering_fields = [
        "price",
        "created_at",
        "name",
    ]

    ordering = [
        "-created_at"
    ]

    pagination_class = ProductPagination
```

## Example API requests

Filter by category:

```http
GET /api/products/?category=electronics
```

Search:

```http
GET /api/products/?search=laptop
```

Order by price:

```http
GET /api/products/?ordering=price
```

Combine filtering and search:

```http
GET /api/products/?category=electronics&search=laptop
```

Combine all features:

```http
GET /api/products/?category=electronics&search=laptop&ordering=-price&page=1&page_size=20
```

## Example response

```json
{
    "count": 35,
    "next": "http://example.com/api/products/?category=electronics&search=laptop&ordering=-price&page=2&page_size=20",
    "previous": null,
    "results": [
        {
            "id": 10,
            "name": "Gaming Laptop",
            "category": "electronics",
            "price": "1800.00",
            "is_available": true
        },
        {
            "id": 5,
            "name": "Business Laptop",
            "category": "electronics",
            "price": "1200.00",
            "is_available": true
        }
    ]
}
```

Notice that the count is 35, not the total number of products in the database.

It represents the number of records matching the filters.

## Important: Filtering happens before pagination

Suppose the database contains:

- 1,000 products.
- 100 electronics products.
- 30 electronics products matching "laptop".

If the client requests:

```http
GET /api/products/?category=electronics&search=laptop&page=1
```

The API paginates the 30 matching records, not all 1,000 products.

This is the expected behavior.

| File | Responsibility |
|---|---|

| filters.py | FilterSet and custom filter backends |
| pagination.py | Pagination classes |
| views.py | API view configuration |

| Use case | Recommended approach |
|---|---|

| Ordinary CRUD list | PageNumberPagination |

| Special response format | Custom pagination |

# 17. Common Mistakes

## Mistake 1: Returning all records

```python
queryset = Product.objects.all()
```

Without pagination, large responses can cause performance problems.

**Better:** Configure pagination for list endpoints.

## Mistake 2: Exposing all ordering fields

```python
ordering_fields = "__all__"
```

**Better:**

```python
ordering_fields = [
    "name",
    "price",
    "created_at",
]
```

## Mistake 3: Allowing unlimited page size

**Better:**

```python
max_page_size = 100
```

## Mistake 4: Using offset pagination for enormous datasets

Large offsets can become expensive.

**Better:** Consider CursorPagination for sequential navigation.

## Mistake 5: Forgetting stable ordering

Pagination without deterministic ordering can result in inconsistent pages.

**Better:**

```python
queryset = Product.objects.order_by(
    "-created_at",
    "-id"
)
```

## Mistake 6: Confusing filtering and permissions

Filtering a queryset is not always a substitute for authorization.

For example:

```python
queryset.filter(
    organization=request.user.organization
)
```

This restricts visible records, but the endpoint should also have suitable authentication and permission checks.

## Mistake 7: Ignoring database query performance

A paginated response can still execute many database queries.

**Better:** Use query optimization, appropriate indexes, and query-plan analysis.

# 18. Interview Questions and Answers

## Q1. What is filtering in Django REST Framework?

Filtering restricts the queryset based on query parameters.

Example:

```http
GET /api/products/?category=electronics
```

It returns products matching the requested category.

## Q2. What is DjangoFilterBackend?

It is a DRF filter backend that integrates with the `django-filter` package to filter querysets using declared model fields or a custom FilterSet.

## Q3. What is the difference between filterset_fields and filterset_class?

`filterset_fields` is convenient for simple field filtering.

```python
filterset_fields = ["category", "price"]
```

`filterset_class` points to a custom FilterSet for complex filtering.

```python
filterset_class = ProductFilter
```

## Q4. What is SearchFilter?

SearchFilter is a built-in DRF backend that allows clients to search configured fields using the `search` query parameter.

Example:

```http
GET /api/products/?search=laptop
```

## Q5. What is OrderingFilter?

OrderingFilter allows clients to sort results using the `ordering` query parameter.

Example:

```http
GET /api/products/?ordering=-price
```

The minus sign indicates descending order.

## Q6. What is the difference between filtering and searching?

Filtering usually uses structured fields and conditions.

Searching looks for text matches across one or more fields.

Example:

```http
?category=electronics
```

is filtering, while:

```http
?search=laptop
```

is searching.

## Q7. What is pagination?

Pagination divides a large queryset into smaller result sets so that the API does not return every record in one response.

## Q8. What are the three built-in DRF pagination classes?

1. PageNumberPagination.
2. LimitOffsetPagination.
3. CursorPagination.

## Q9. What is the difference between PageNumberPagination and LimitOffsetPagination?

PageNumberPagination uses page numbers:

```http
?page=2
```

LimitOffsetPagination uses a limit and offset:

```http
?limit=20&offset=20
```

## Q10. What is CursorPagination?

CursorPagination uses an opaque cursor to navigate through consistently ordered records.

It is especially useful for high-volume feeds and chronological histories.

## Q11. Which pagination is best for large datasets?

There is no universal answer.

CursorPagination is often a good choice for large datasets that are traversed sequentially.

The correct choice depends on the access pattern, database, ordering, and need for total counts or arbitrary page navigation.

## Q12. Why is ordering important in pagination?

Without deterministic ordering, records can appear inconsistently across pages.

A stable ordering makes navigation more predictable.

## Q13. Why should we use max_page_size?

It prevents clients from requesting excessively large result sets, protecting application and database resources.

## Q14. What is the difference between select_related and prefetch_related?

`select_related()` is used for ForeignKey and OneToOne relationships.

`prefetch_related()` is used for ManyToMany and reverse relationships.

Both help reduce unnecessary database queries.

## Q15. Does filtering happen before pagination?

Yes. DRF applies filter backends to the queryset before pagination.

Therefore, pagination operates on the filtered result set.

## Q16. Can we combine SearchFilter, OrderingFilter and DjangoFilterBackend?

Yes.

```python
filter_backends = [
    DjangoFilterBackend,
    SearchFilter,
    OrderingFilter,
]
```

Each backend contributes its own behavior.

## Q17. What is a custom filter backend?

It is a class extending `BaseFilterBackend` that implements `filter_queryset()` to apply custom filtering logic.

## Q18. What is the difference between pagination and filtering?

Filtering decides which records qualify.

Pagination decides how many qualifying records are returned in one response.

## Q19. Why can large offsets be slow?

The database may need to scan or skip many rows before returning the requested result window.

Cursor pagination can be more suitable for sequential traversal.

## Q20. How do you improve the performance of a DRF list API?

Common approaches include:

- Appropriate database indexes.
- Query optimization.
- `select_related()` and `prefetch_related()`.
- Restricting page sizes.
- Avoiding expensive counts when possible.
- Cursor pagination for feeds.
- Efficient serializers.
- Analyzing database query plans.

## Q21. How would you build an e-commerce product listing API?

I would combine:

- `DjangoFilterBackend` for category and price filters.
- `SearchFilter` for product names and descriptions.
- `OrderingFilter` for price and creation date.
- `PageNumberPagination` for ordinary product browsing.
- Database indexes based on the most common filter and ordering patterns.

## Q22. How do you prevent users from seeing another tenant's records?

Restrict the queryset using the authenticated user's tenant or organization, and enforce suitable permissions.

For example:

```python
def get_queryset(self):
    return Product.objects.filter(
        organization=self.request.user.organization
    )
```

Never rely on a client-provided organization ID alone to enforce tenant access.
