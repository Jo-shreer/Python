# Part 2: Serializers and Data Validation
## Django REST Framework (DRF) — Detailed Guide

This part explains how Django REST Framework serializers convert Django objects into JSON, convert incoming JSON into validated Python data, and protect your API from invalid or incomplete input.

We will build examples around a simple application containing users, categories, and products.

---

# 16. What Are Serializers?

## 16.1 Understanding serializers

A serializer is a component in Django REST Framework (DRF) that converts complex Python objects into data formats such as JSON and converts incoming data back into Python data.

For example, Django may return a Product model instance:

```python
product = Product(
    id=1,
    name="Laptop",
    price=1200
)
```

A client cannot directly use a Django model object. It expects JSON.

A serializer converts the model into a JSON-compatible dictionary:

```json
{
    "id": 1,
    "name": "Laptop",
    "price": "1200.00"
}
```

Serializers also validate incoming data before saving it to the database.

## 16.2 Two important operations

### A. Serialization

Serialization means converting a Python object into JSON-compatible data.

```text
Django Model
     |
     v
Serializer
     |
     v
Python Dictionary
     |
     v
JSON Response
```

Example:

```python
serializer = ProductSerializer(product)

print(serializer.data)
```

Output:

```python
{
    'id': 1,
    'name': 'Laptop',
    'price': '1200.00'
}
```

### B. Deserialization

Deserialization means accepting incoming data and converting it into validated Python data.

```text
JSON Request
     |
     v
Serializer
     |
     v
Validation
     |
     v
Validated Python Data
     |
     v
Database
```

Example:

```python
data = {
    "name": "Keyboard",
    "price": "50.00"
}

serializer = ProductSerializer(data=data)

if serializer.is_valid():
    print(serializer.validated_data)
else:
    print(serializer.errors)
```

Output:

```python
{
    'name': 'Keyboard',
    'price': Decimal('50.00')
}
```

## 16.3 Why do we need serializers?

Serializers help us:

1. Convert Django model objects into API responses.
2. Validate incoming request data.
3. Prevent invalid data from entering the database.
4. Control which fields are visible to clients.
5. Handle relationships between models.
6. Implement custom validation rules.
7. Keep API logic separate from database logic.

# 17. Serializer vs ModelSerializer

DRF provides two commonly used serializer types:

- Serializer
- ModelSerializer

Both can validate and transform data, but they work differently.

## 17.1 Serializer

A regular Serializer requires you to define its fields manually.

Example:

```python
from rest_framework import serializers

class ProductSerializer(serializers.Serializer):

    name = serializers.CharField(max_length=100)

    price = serializers.DecimalField(
        max_digits=10,
        decimal_places=2
    )

    description = serializers.CharField(
        required=False
    )
```

You must also implement `create()` and `update()` if you want to save or modify objects.

```python
def create(self, validated_data):
    return Product.objects.create(**validated_data)

def update(self, instance, validated_data):
    instance.name = validated_data.get(
        "name",
        instance.name
    )

    instance.price = validated_data.get(
        "price",
        instance.price
    )

    instance.save()

    return instance
```

## 17.2 ModelSerializer

ModelSerializer automatically generates serializer fields based on a Django model.

Example:

```python
from rest_framework import serializers
from .models import Product

class ProductSerializer(serializers.ModelSerializer):

    class Meta:
        model = Product

        fields = [
            "id",
            "name",
            "price",
            "description"
        ]
```

DRF automatically provides common create and update behavior.

## 17.3 Main differences

| Feature | Serializer | ModelSerializer |
|---|---|---|
| Fields | Manually defined | Generated from model or declared manually |
| Model integration | Manual | Built in |
| Create method | Usually implement yourself | Automatically provided |
| Update method | Usually implement yourself | Automatically provided |
| Validation | Supported | Supported |
| Custom logic | Supported | Supported |
| Best use | Custom data structures | Database-backed APIs |

## 17.4 When should you use each?

Use Serializer when:

- You are validating data that does not directly map to a model.
- You are creating login or registration input schemas.
- You are accepting external API data.
- You need complete control over saving behavior.

Use ModelSerializer when:

- You are exposing Django model data.
- You need standard create, retrieve, update, and delete operations.
- Your API fields mostly correspond to model fields.

# 20. Required and Optional Fields

A required field must be provided when creating an object.

An optional field can be omitted.

## 20.1 Required fields

By default, serializer fields are required unless their configuration or model-derived behavior says otherwise.

```python
class UserSerializer(serializers.Serializer):

    username = serializers.CharField(
        required=True
    )

    email = serializers.EmailField(
        required=True
    )
```

Input:

```python
{
    "username": "john"
}
```

Output:

```python
{
    'email': [
        ErrorDetail(
            string='This field is required.',
            code='required'
        )
    ]
}
```

## 20.2 Optional fields

Set `required=False`.

```python
class UserSerializer(serializers.Serializer):

    username = serializers.CharField()

    email = serializers.EmailField(
        required=False
    )
```

Input:

```python
{
    "username": "john"
}
```

Output:

```text
True
```

The email field can be omitted.

## 20.3 Important: required=False vs allow_blank=True

These settings have different meanings.

```python
class UserSerializer(serializers.Serializer):

    nickname = serializers.CharField(
        required=False,
        allow_blank=True
    )
```

- `required=False`: the field can be omitted.
- `allow_blank=True`: the field can contain an empty string.

For example:

```python
{}
```

Valid.

```python
{"nickname": ""}
```

Also valid.

Without `allow_blank=True`, an empty string is invalid for a CharField.

## 20.4 Partial updates

For PATCH requests, you usually want to update only the fields provided.

```python
serializer = ProductSerializer(
    instance=product,
    data={
        "name": "Updated Laptop"
    },
    partial=True
)

if serializer.is_valid():
    serializer.save()
```

`partial=True` means required fields that are omitted do not cause validation errors during this partial update.

# 21. Read-Only and Write-Only Fields

Sometimes an API field should be returned but not accepted from the client.

Other fields should be accepted but never returned.

DRF supports both.

## 21.1 Read-only fields

A read-only field appears in API responses but is ignored as an input field.

Example:

```python
class ProductSerializer(serializers.ModelSerializer):

    class Meta:
        model = Product

        fields = [
            "id",
            "name",
            "price",
            "created_at"
        ]

        read_only_fields = [
            "id",
            "created_at"
        ]
```

The client cannot set the ID or creation timestamp through this serializer.

## 21.2 Write-only fields

A write-only field is accepted as input but excluded from serialized output.

Example:

```python
class RegistrationSerializer(serializers.Serializer):

    username = serializers.CharField()

    email = serializers.EmailField()

    password = serializers.CharField(
        write_only=True
    )
```

Input:

```json
{
    "username": "john",
    "email": "john@example.com",
    "password": "secret123"
}
```

After validation, the password is available in `validated_data`, but it will not appear in `serializer.data`.

Example response:

```json
{
    "username": "john",
    "email": "john@example.com"
}
```

Important: `write_only=True` only controls serialization. It does not hash a password. Use Django's `set_password()` or `create_user()` to store passwords securely.

## 21.3 Read-only and write-only comparison

| Property | Read-only | Write-only |
|---|---|---|
| Accept input | No | Yes |
| Appear in output | Yes | No |
| Common example | ID, created_at | Password, secret |
| DRF option | read_only=True | write_only=True |

# 22. Default Values and Null Values

Defaults are used when a field is omitted. Null values represent an explicit absence of a value.

These are different concepts.

## 22.1 Default values

```python
class ProductSerializer(serializers.Serializer):

    name = serializers.CharField()

    is_available = serializers.BooleanField(
        default=True
    )
```

Input:

```python
{
    "name": "Laptop"
}
```

Validated data:

```python
{
    "name": "Laptop",
    "is_available": True
}
```

The default is applied because the client did not provide the field.

## 22.2 Allowing null values

```python
class ProductSerializer(serializers.Serializer):

    name = serializers.CharField()

    description = serializers.CharField(
        allow_null=True,
        required=False
    )
```

Input:

```python
{
    "name": "Laptop",
    "description": None
}
```

Valid.

## 22.3 Allowing blank strings

```python
description = serializers.CharField(
    allow_blank=True,
    required=False
)
```

Input:

```python
{
    "name": "Laptop",
    "description": ""
}
```

Valid.

## 22.4 Understanding the differences

| Setting | Meaning |
|---|---|
| required=False | Field may be omitted |
| default=True | Use True if omitted |
| allow_null=True | Accept None/null |
| allow_blank=True | Accept an empty string |

## 22.5 Important default behavior

A default is not normally applied to an omitted field during a partial update (`partial=True`).

For example, a PATCH request that omits `is_available` will not automatically reset it to the default.

Also, do not combine `default` with `required=True`. A default makes the field non-required in ordinary input validation.

# 23. Field-Level Validation

Field-level validation checks one specific field.

DRF supports a special method naming convention:

`validate_<field_name>()`

## 23.1 Example: Validate product price

```python
class ProductSerializer(serializers.Serializer):

    name = serializers.CharField()

    price = serializers.DecimalField(
        max_digits=10,
        decimal_places=2
    )

    def validate_price(self, value):

        if value <= 0:
            raise serializers.ValidationError(
                "Price must be greater than zero."
            )

        return value
```

Valid input:

```python
{
    "name": "Laptop",
    "price": "1200.00"
}
```

Output:

```text
True
```

Invalid input:

```python
{
    "name": "Laptop",
    "price": "-100.00"
}
```

Output:

```python
{
    'price': [
        ErrorDetail(
            string='Price must be greater than zero.',
            code='invalid'
        )
    ]
}
```

## 23.2 Example: Validate username

```python
class UserSerializer(serializers.Serializer):

    username = serializers.CharField()

    def validate_username(self, value):

        if len(value) < 5:
            raise serializers.ValidationError(
                "Username must contain at least 5 characters."
            )

        return value
```

Input:

```python
{"username": "john"}
```

Output:

```python
{
    'username': [
        ErrorDetail(
            string='Username must contain at least 5 characters.',
            code='invalid'
        )
    ]
}
```

## 23.3 Important rule

Always return the validated value.

```python
def validate_price(self, value):
    if value <= 0:
        raise serializers.ValidationError(
            "Price must be positive."
        )

    return value
```

If validation fails, raise `serializers.ValidationError`.

# 24. Object-Level Validation

Field-level validation checks individual fields.

Object-level validation checks multiple fields together.

Use the `validate()` method.

## 24.1 Example: Compare two fields

Suppose a product has:

- Original price
- Discounted price

The discounted price must not exceed the original price.

```python
class ProductSerializer(serializers.Serializer):

    name = serializers.CharField()

    original_price = serializers.DecimalField(
        max_digits=10,
        decimal_places=2
    )

    discounted_price = serializers.DecimalField(
        max_digits=10,
        decimal_places=2
    )

    def validate(self, attrs):

        original = attrs["original_price"]

        discounted = attrs["discounted_price"]

        if discounted > original:
            raise serializers.ValidationError(
                "Discounted price cannot exceed original price."
            )

        return attrs
```

Valid input:

```python
{
    "name": "Laptop",
    "original_price": "1500.00",
    "discounted_price": "1200.00"
}
```

Output:

```text
True
```

Invalid input:

```python
{
    "name": "Laptop",
    "original_price": "1000.00",
    "discounted_price": "1200.00"
}
```

Output:

```python
{
    'non_field_errors': [
        ErrorDetail(
            string='Discounted price cannot exceed original price.',
            code='invalid'
        )
    ]
}
```

`non_field_errors` is the default location for object-level validation errors.

## 24.2 Field-specific errors from object validation

You can attach an error to a particular field:

```python
from rest_framework import serializers

def validate(self, attrs):

    if attrs["discounted_price"] > attrs["original_price"]:

        raise serializers.ValidationError({
            "discounted_price": [
                "Discounted price cannot exceed original price."
            ]
        })

    return attrs
```

This produces an error associated with `discounted_price`.

## 24.3 When should you use object-level validation?

Use it for rules involving:

- Start date and end date.
- Password and password confirmation.
- Minimum and maximum values.
- Original price and discounted price.
- Check-in and check-out dates.
- Multiple related fields.

# 25. Custom Validators

Custom validators are reusable functions or callable objects that validate values.

They are useful when the same validation rule is needed in several serializers.

## 25.1 Function-based validator

Example: Product price must be positive.

```python
from rest_framework import serializers

def validate_positive_price(value):

    if value <= 0:
        raise serializers.ValidationError(
            "Price must be greater than zero."
        )
```

Use the validator:

```python
class ProductSerializer(serializers.Serializer):

    name = serializers.CharField()

    price = serializers.DecimalField(
        max_digits=10,
        decimal_places=2,
        validators=[validate_positive_price]
    )
```

Input:

```python
{
    "name": "Laptop",
    "price": "-50.00"
}
```

Output:

```python
{
    'price': [
        ErrorDetail(
            string='Price must be greater than zero.',
            code='invalid'
        )
    ]
}
```

## 25.2 Reusable email validator

```python
import re
from rest_framework import serializers

def validate_company_email(value):

    if not value.endswith("@company.com"):
        raise serializers.ValidationError(
            "Only company email addresses are allowed."
        )
```

Use it:

```python
class EmployeeSerializer(serializers.Serializer):

    email = serializers.EmailField(
        validators=[validate_company_email]
    )
```

Input:

```python
{
    "email": "john@gmail.com"
}
```

Output:

```python
{
    'email': [
        ErrorDetail(
            string='Only company email addresses are allowed.',
            code='invalid'
        )
    ]
}
```

## 25.3 Class-based validator

A callable class can store configuration.

```python
from rest_framework import serializers

class MinimumValueValidator:

    def __init__(self, minimum):
        self.minimum = minimum

    def __call__(self, value):

        if value < self.minimum:
            raise serializers.ValidationError(
                f"Value must be at least {self.minimum}."
            )
```

Use it:

```python
class ProductSerializer(serializers.Serializer):

    stock = serializers.IntegerField(
        validators=[
            MinimumValueValidator(10)
        ]
    )
```

Input:

```python
{"stock": 5}
```

Output:

```python
{
    'stock': [
        ErrorDetail(
            string='Value must be at least 10.',
            code='invalid'
        )
    ]
}
```

# 26. Validation Error Handling

When incoming data is invalid, DRF returns structured validation errors.

## 26.1 Using is_valid()

```python
serializer = ProductSerializer(data=request.data)

if serializer.is_valid():

    serializer.save()

else:

    print(serializer.errors)
```

`is_valid()` runs the serializer's validation process.

It returns:

- `True` if all data is valid.
- `False` if validation fails.

## 26.2 raise_exception=True

Instead of manually checking errors, you can write:

```python
serializer = ProductSerializer(data=request.data)

serializer.is_valid(raise_exception=True)

serializer.save()
```

If validation fails, DRF raises `ValidationError`.

DRF's default exception handling converts it into an HTTP 400 Bad Request response.

Example response:

```json
{
    "name": [
        "This field is required."
    ],
    "price": [
        "A valid number is required."
    ]
}
```

## 26.3 Custom API response for validation errors

You can customize the exception handler.

Inside `products/exceptions.py`:

```python
from rest_framework.views import exception_handler

def custom_exception_handler(exc, context):

    response = exception_handler(exc, context)

    if response is not None:

        response.data = {
            "success": False,
            "errors": response.data
        }

    return response
```

Configure it in `settings.py`:

```python
REST_FRAMEWORK = {
    "EXCEPTION_HANDLER":
        "products.exceptions.custom_exception_handler"
}
```

Example response:

```json
{
    "success": false,
    "errors": {
        "name": [
            "This field is required."
        ]
    }
}
```

## 26.4 Important HTTP status codes

| Status | Meaning |
|---|---|
| 200 | Successful request |
| 201 | Resource created |
| 400 | Invalid request or validation error |
| 401 | Authentication required or failed |
| 403 | Permission denied |
| 404 | Resource not found |
| 500 | Internal server error |

Never return internal Python tracebacks or sensitive database details to clients.

# 27. Nested Serializers

Nested serializers allow one serializer to contain another serializer.

They are useful when models have relationships.

For example:

- One category can contain many products.
- A product belongs to one category.

## 27.1 Create the models

`products/models.py`:

```python
from django.db import models

class Category(models.Model):

    name = models.CharField(max_length=100)

    def __str__(self):
        return self.name


class Product(models.Model):

    name = models.CharField(max_length=100)

    price = models.DecimalField(
        max_digits=10,
        decimal_places=2
    )

    category = models.ForeignKey(
        Category,
        on_delete=models.CASCADE,
        related_name="products"
    )

    def __str__(self):
        return self.name
```

Run migrations:

```bash
python manage.py makemigrations
python manage.py migrate
```

## 27.2 Create nested serializers

`products/serializers.py`:

```python
from rest_framework import serializers
from .models import Category, Product

class CategorySerializer(serializers.ModelSerializer):

    class Meta:
        model = Category
        fields = ["id", "name"]


class ProductSerializer(serializers.ModelSerializer):

    category = CategorySerializer(read_only=True)

    class Meta:
        model = Product

        fields = [
            "id",
            "name",
            "price",
            "category"
        ]
```

## 27.3 Example output

```json
{
    "id": 1,
    "name": "Laptop",
    "price": "1200.00",
    "category": {
        "id": 1,
        "name": "Electronics"
    }
}
```

Without a nested serializer, the category field might instead return only its primary key.

Nested serializers make the response more descriptive.

# 28. Writable Nested Serializers

A read-only nested serializer displays related data.

A writable nested serializer also accepts related data and saves it.

DRF does not automatically implement all writable nested create and update behavior. You must define it.

## 28.1 Example: Create a category and product together

Input:

```json
{
    "name": "Laptop",
    "price": "1200.00",
    "category": {
        "name": "Electronics"
    }
}
```

Serializer:

```python
from rest_framework import serializers
from .models import Category, Product

class CategorySerializer(serializers.ModelSerializer):

    class Meta:
        model = Category
        fields = ["id", "name"]


class ProductSerializer(serializers.ModelSerializer):

    category = CategorySerializer()

    class Meta:
        model = Product

        fields = [
            "id",
            "name",
            "price",
            "category"
        ]

    def create(self, validated_data):

        category_data = validated_data.pop("category")

        category = Category.objects.create(
            **category_data
        )

        product = Product.objects.create(
            category=category,
            **validated_data
        )

        return product
```

## 28.2 How does it work?

First:

```python
category_data = validated_data.pop("category")
```

This removes the nested category data from the main dictionary.

Next:

```python
category = Category.objects.create(**category_data)
```

This creates the category.

Finally:

```python
product = Product.objects.create(
    category=category,
    **validated_data
)
```

This creates the product using the newly created category.

## 28.3 Expected output

After a successful POST request:

```json
{
    "id": 1,
    "name": "Laptop",
    "price": "1200.00",
    "category": {
        "id": 1,
        "name": "Electronics"
    }
}
```

## 28.4 Use database transactions

When creating multiple related records, use transactions to avoid partial writes.

```python
from django.db import transaction

def create(self, validated_data):

    category_data = validated_data.pop("category")

    with transaction.atomic():

        category = Category.objects.create(
            **category_data
        )

        product = Product.objects.create(
            category=category,
            **validated_data
        )

    return product
```

If an error occurs inside the transaction, Django rolls back the database changes.

## 28.5 Updating nested objects

For updates, define an explicit policy.

For example, you might update the existing category rather than creating a new one:

```python
def update(self, instance, validated_data):

    category_data = validated_data.pop(
        "category",
        None
    )

    if category_data is not None:

        for field, value in category_data.items():
            setattr(instance.category, field, value)

        instance.category.save()

    for field, value in validated_data.items():
        setattr(instance, field, value)

    instance.save()

    return instance
```

In a real application, decide whether nested updates should:

- Update an existing related object.
- Create a new related object.
- Replace the relationship.
- Reject the update.

Do not leave this behavior ambiguous.

## 29.1 PrimaryKeyRelatedField

Returns the related object's primary key.

```python
class ProductSerializer(serializers.ModelSerializer):
```

```json
{

    "name": "Laptop",
    "category": 1
```

This field can also accept a category ID when writing, provided that the ID exists.

## 29.2 StringRelatedField

Returns the related object's string representation.

```python
class ProductSerializer(serializers.ModelSerializer):
```

# 30. Serializer Inheritance

Serializer inheritance allows one serializer to reuse fields and methods from another serializer.

It reduces duplicated code.

## 30.1 Basic inheritance

```python
from rest_framework import serializers

class BaseProductSerializer(serializers.Serializer):

    name = serializers.CharField(max_length=100)

    price = serializers.DecimalField(
        max_digits=10,
        decimal_places=2
    )


class ProductSerializer(BaseProductSerializer):

    description = serializers.CharField(
        required=False
    )
```

The child serializer inherits:

- name
- price

It also defines:

- description

## 30.2 ModelSerializer inheritance

```python
class BaseProductSerializer(serializers.ModelSerializer):

    class Meta:
        model = Product

        fields = [
            "id",
            "name",
            "price"
        ]


class DetailedProductSerializer(BaseProductSerializer):

    description = serializers.CharField(
        read_only=True
    )

    class Meta(BaseProductSerializer.Meta):

        fields = BaseProductSerializer.Meta.fields + [
            "description"
        ]
```

This is useful when multiple endpoints expose different versions of the same model.

## 30.3 Common use cases

- Base serializer for shared fields.
- Public serializer and internal serializer.
- List serializer and detail serializer.
- Reusing validation logic.
- Keeping API schemas consistent.

Be careful when overriding fields or Meta options: the child serializer can change the behavior inherited from the parent.

# 31. Serializer Method Fields

`SerializerMethodField` allows you to calculate a field dynamically.

The field is read-only.

## 31.1 Example: Product discount

Suppose the Product model contains:

- price
- original_price

We want to return the discount percentage.

```python
from rest_framework import serializers

class ProductSerializer(serializers.ModelSerializer):

    discount_percentage = serializers.SerializerMethodField()

    class Meta:
        model = Product

        fields = [
            "id",
            "name",
            "price",
            "original_price",
            "discount_percentage"
        ]

    def get_discount_percentage(self, obj):

        if not obj.original_price:
            return 0

        if obj.original_price <= 0:
            return 0

        discount = (
            (obj.original_price - obj.price)
            / obj.original_price
        ) * 100

        return round(discount, 2)
```

Example data:

```python
price = 800
original_price = 1000
```

Output:

```json
{
    "id": 1,
    "name": "Laptop",
    "price": "800.00",
    "original_price": "1000.00",
    "discount_percentage": 20.0
}
```

## 31.2 Access serializer context

Method fields can also use request context.

```python
class ProductSerializer(serializers.ModelSerializer):

    is_owner = serializers.SerializerMethodField()

    class Meta:
        model = Product
        fields = ["id", "name", "is_owner"]

    def get_is_owner(self, obj):

        request = self.context.get("request")

        if request is None or not request.user.is_authenticated:
            return False

        return obj.owner_id == request.user.id
```

Pass the request:

```python
serializer = ProductSerializer(
    product,
    context={"request": request}
)
```

This allows the output to depend on the current user.

Do not use method fields for expensive database queries on every serialized object. That can cause performance problems.

# 32. Custom Serializer Representation

Sometimes you need to change the final output structure.

Override `to_representation()`.

## 32.1 Example: Customize product output

Default output:

```json
{
    "id": 1,
    "name": "Laptop",
    "price": "1200.00"
}
```

We want:

```json
{
    "product_id": 1,
    "product_name": "Laptop",
    "price_details": {
        "amount": "1200.00",
        "currency": "EUR"
    }
}
```

Serializer:

```python
from rest_framework import serializers

class ProductSerializer(serializers.ModelSerializer):

    class Meta:
        model = Product
        fields = ["id", "name", "price"]

    def to_representation(self, instance):

        data = super().to_representation(instance)

        return {
            "product_id": data["id"],
            "product_name": data["name"],
            "price_details": {
                "amount": data["price"],
                "currency": "EUR"
            }
        }
```

## 32.2 Understanding super()

```python
data = super().to_representation(instance)
```

This calls the parent implementation first.

You then modify the resulting dictionary.

## 32.3 When should you override it?

Use `to_representation()` when:

- You need a custom response structure.
- You need to rename or group output fields.
- You need conditional output.
- You need to transform a value before returning it.

Avoid unnecessary representation customization. Standard fields and nested serializers are usually easier to maintain.

```python
data = {
```

Create the serializer:

```python
serializer = ProductSerializer(data=data)
```

# 34. Serializer Performance Optimisation

Serializer performance becomes important when your API returns hundreds or thousands of objects.

A serializer can be correct but still slow if it triggers too many database queries.

## 34.1 Problem: N+1 database queries

Suppose each product belongs to a category.

A serializer might be:

```python
class ProductSerializer(serializers.ModelSerializer):

    category_name = serializers.CharField(
        source="category.name",
        read_only=True
    )

    class Meta:
        model = Product

        fields = [
            "id",
            "name",
            "price",
            "category_name"
        ]
```

A naive queryset:

```python
products = Product.objects.all()

serializer = ProductSerializer(
    products,
    many=True
)
```

If 100 products each trigger an additional category query, you could execute approximately:

```text
1 query for products
100 queries for categories

Total: 101 queries
```

This is called the N+1 query problem.

## 34.2 Solution: select_related()

Use `select_related()` for foreign-key and one-to-one relationships.

```python
products = Product.objects.select_related(
    "category"
)
```

Now Django retrieves the product and related category data together using a SQL join.

Instead of approximately 101 queries, the result may require only one query.

Use it for:

- ForeignKey
- OneToOneField

## 34.3 Solution: prefetch_related()

Use `prefetch_related()` for many-to-many and reverse relationships.

Example:

```python
products = Product.objects.prefetch_related(
    "reviews"
)
```

This performs a separate query for the related reviews and joins the results in Python.

Use it for:

- ManyToManyField
- Reverse ForeignKey relationships
- Other multi-valued relationships

## 34.4 select_related vs prefetch_related

| Feature | select_related | prefetch_related |
|---|---|---|
| ForeignKey | Yes | Yes |
| OneToOneField | Yes | Yes |
| ManyToManyField | No | Yes |
| Reverse ForeignKey | No | Yes |
| Strategy | SQL JOIN | Separate queries, combined in Python |
| Typical use | Single-valued relationship | Multi-valued relationship |

## 34.5 Optimize serializer method fields

Poor example:

```python
class ProductSerializer(serializers.ModelSerializer):

    review_count = serializers.SerializerMethodField()

    class Meta:
        model = Product
        fields = ["id", "name", "review_count"]

    def get_review_count(self, obj):

        return obj.reviews.count()
```

If you serialize 100 products, this method may trigger 100 additional database queries.

Better approach: annotate the queryset.

```python
from django.db.models import Count

products = Product.objects.annotate(
    review_total=Count("reviews")
)
```

Then:

```python
class ProductSerializer(serializers.ModelSerializer):

    review_count = serializers.IntegerField(
        source="review_total",
        read_only=True
    )

    class Meta:
        model = Product
        fields = ["id", "name", "review_count"]
```

The count is calculated by the database query rather than repeatedly queried in Python.

## 34.6 Return only required fields

Avoid loading unnecessary columns.

Use:

```python
products = Product.objects.only(
    "id",
    "name",
    "price"
)
```

Or:

```python
products = Product.objects.defer(
    "description"
)
```

Be careful: accessing deferred fields later can cause additional database queries.

## 34.7 Use pagination

Avoid returning thousands of records in one response.

Configure pagination in `settings.py`:

```python
REST_FRAMEWORK = {
    "DEFAULT_PAGINATION_CLASS":
        "rest_framework.pagination.PageNumberPagination",

    "PAGE_SIZE": 20
}
```

Example response:

```json
{
    "count": 100,
    "next": "http://127.0.0.1:8000/products/?page=2",
    "previous": null,
    "results": [
        {
            "id": 1,
            "name": "Laptop",
            "price": "1200.00"
        }
    ]
}
```

The results array contains up to 20 products.

## 34.8 Avoid unnecessary nested serializers

Deeply nested serializers can produce:

- More database queries.
- Larger response payloads.
- More complex validation.
- Slower serialization.

Return only the data required by the client.

For large collections, consider returning related object IDs or summary fields instead of complete nested objects.

## 34.9 Profile query performance

Use Django Debug Toolbar during development.

Install:

```bash
pip install django-debug-toolbar
```

Add it to `INSTALLED_APPS` and configure its middleware and development URLs according to its documentation.

You can also inspect queries in Django:

```python
from django.db import connection

print(len(connection.queries))

for query in connection.queries:
    print(query["sql"])
```

Note: query logging through `connection.queries` is available when Django database query logging is enabled, typically with `DEBUG=True`. Do not enable detailed SQL logging indiscriminately in production.

## 34.10 Performance checklist

Before deploying a serializer-based API:

- Use `select_related()` for foreign-key relationships.
- Use `prefetch_related()` for many-to-many and reverse relationships.
- Avoid database queries inside serializer method fields.
- Use annotations for counts and aggregates.
- Avoid unnecessary nested serialization.
- Return only necessary fields.
- Add pagination.
- Profile database queries.
- Cache expensive, frequently requested results when appropriate.
- Keep response payloads reasonably small.

## Step 2: Serializer

`products/serializers.py`

```python
from rest_framework import serializers
from .models import Category, Product


class CategorySerializer(serializers.ModelSerializer):

    class Meta:
        model = Category
        fields = ["id", "name"]


class ProductSerializer(serializers.ModelSerializer):

    category = CategorySerializer(read_only=True)

    category_id = serializers.PrimaryKeyRelatedField(
        source="category",
        queryset=Category.objects.all(),
        write_only=True
    )

    class Meta:
        model = Product

        fields = [
            "id",
            "name",
            "price",
            "description",
            "is_available",
            "category",
            "category_id",
            "created_at"
        ]

        read_only_fields = [
            "id",
            "created_at"
        ]

    def validate_price(self, value):

        if value <= 0:
            raise serializers.ValidationError(
                "Price must be greater than zero."
            )

        return value

    def validate_name(self, value):

        if len(value.strip()) < 3:
            raise serializers.ValidationError(
                "Product name must contain at least 3 characters."
            )

        return value.strip()
```

Notice the two category fields:

- `category` is read-only and returns nested category information.
- `category_id` is write-only and accepts a category primary key.

This gives us a useful API design: clients can submit a simple category ID while receiving descriptive category data.
