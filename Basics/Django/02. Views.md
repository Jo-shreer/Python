# First: Understanding FBV and CBV

Before learning the topics, understand an important distinction.

Django supports two main ways of writing views.

## 1. Function-Based Views (FBV)

An FBV is a normal Python function that handles an HTTP request.

Example:

```python
from django.http import JsonResponse
from rest_framework.decorators import api_view

@api_view(["GET"])
def hello_api(request):

    return JsonResponse({
        "message": "Hello from Django REST Framework"
    })
```

Here:

- `@api_view` converts a Django-style function into a DRF API view.
- `["GET"]` specifies the allowed HTTP method.
- `request` contains the incoming request.
- The function returns a response.

## 2. Class-Based Views (CBV)

A CBV is a Python class that handles HTTP requests through methods such as `get()`, `post()`, `put()`, and `delete()`.

Example:

```python
from rest_framework.views import APIView
from rest_framework.response import Response

class HelloAPI(APIView):

    def get(self, request):

        return Response({
            "message": "Hello from APIView"
        })
```

Here:

- `APIView` is the parent class.
- `get()` handles GET requests.
- `request` contains the incoming request.
- `Response` returns JSON-compatible API data.

## FBV vs CBV

| Feature | FBV | CBV |
|---|---|---|
| Structure | Function | Class |
| Main syntax | `def` | `class` |
| HTTP methods | Decorators and conditions | Separate methods |
| Reusability | Function composition | Inheritance and mixins |
| Best for | Small, simple endpoints | Reusable and structured APIs |
| Complexity | Easy initially | More flexible for larger APIs |

**Important:** `APIView`, `GenericAPIView`, generic views, and ViewSets are all class-based approaches.

# 1. APIView

## What is APIView?

`APIView` is one of the fundamental class-based views provided by Django REST Framework.

It gives you control over how HTTP requests are handled.

Unlike Django's ordinary `View`, DRF's APIView provides additional API functionality, including:

- Request parsing.
- Response rendering.
- Authentication.
- Permissions.
- Throttling.
- Content negotiation.
- Exception handling.

You can implement individual HTTP methods inside the class.

## Basic syntax

```python
from rest_framework.views import APIView
from rest_framework.response import Response

class MyAPIView(APIView):

    def get(self, request):
        pass

    def post(self, request):
        pass

    def put(self, request):
        pass

    def patch(self, request):
        pass

    def delete(self, request):
        pass
```

## Important HTTP methods

| Method | Purpose | Example |
|---|---|---|
| GET | Retrieve data | Get all products |
| POST | Create data | Create a product |
| PUT | Replace/update data | Update a product |
| PATCH | Partially update data | Update product price |
| DELETE | Delete data | Delete a product |

## Example 1: Retrieve all products

`products/views.py`:

```python
from rest_framework.views import APIView
from rest_framework.response import Response

from .models import Product
from .serializers import ProductSerializer


class ProductListAPIView(APIView):

    def get(self, request):

        products = Product.objects.all()

        serializer = ProductSerializer(
            products,
            many=True
        )

        return Response(serializer.data)
```

## Important APIView attributes

APIView supports several class-level attributes that control request processing.

### 1. authentication_classes

Specifies which authentication classes are used.

```python
from rest_framework.authentication import (
    SessionAuthentication,
    BasicAuthentication
)

class ProductAPIView(APIView):

    authentication_classes = [
        SessionAuthentication,
        BasicAuthentication
    ]
```

Authentication identifies the user making the request.

Common authentication classes include:

- `SessionAuthentication`
- `BasicAuthentication`
- `TokenAuthentication`

JWT authentication is commonly supplied by an additional package such as Simple JWT.

### 2. permission_classes

Controls who is allowed to access the endpoint.

```python
from rest_framework.permissions import IsAuthenticated

class ProductAPIView(APIView):

    permission_classes = [
        IsAuthenticated
    ]
```

Common permissions:

| Permission | Meaning |
|---|---|
| AllowAny | Anyone can access |
| IsAuthenticated | User must be logged in |
| IsAdminUser | User must have staff status |
| IsAuthenticatedOrReadOnly | Everyone can read; authenticated users can perform other permitted methods |
| DjangoModelPermissions | Applies Django model permissions |

Example:

```python
permission_classes = [AllowAny]
```

This allows public access, subject to other applicable controls.

### 3. throttle_classes

Controls how frequently clients can make requests.

```python
from rest_framework.throttling import AnonRateThrottle

class ProductAPIView(APIView):

    throttle_classes = [
        AnonRateThrottle
    ]
```

Throttle classes are useful for reducing excessive API usage.

They are not a complete security or denial-of-service protection system.

### 4. parser_classes

Controls which incoming request formats can be parsed.

```python
from rest_framework.parsers import (
    JSONParser,
    FormParser,
    MultiPartParser
)

class ProductAPIView(APIView):

    parser_classes = [
        JSONParser,
        FormParser,
        MultiPartParser
    ]
```

Common parsers:

- `JSONParser`: JSON request body.
- `FormParser`: form-encoded data.
- `MultiPartParser`: multipart form data, commonly used for file uploads.
- `FileUploadParser`: raw file upload requests.

### 5. renderer_classes

Controls the response formats supported by the view.

```python
from rest_framework.renderers import (
    JSONRenderer,
    BrowsableAPIRenderer
)

class ProductAPIView(APIView):

    renderer_classes = [
        JSONRenderer,
        BrowsableAPIRenderer
    ]
```

### 6. content_negotiation_class

Controls how DRF chooses a renderer based on the request's accepted media types.

```python
content_negotiation_class = MyContentNegotiationClass
```

You normally keep the default unless you have a specific content-negotiation requirement.

### 7. metadata_class

Controls metadata returned for API OPTIONS requests.

```python
metadata_class = MyMetadataClass
```

### 8. versioning_class

Controls API versioning behavior.

```python
versioning_class = MyVersioningClass
```

You can also configure versioning globally through `REST_FRAMEWORK` settings.

## Important APIView methods

| Method | Purpose |
|---|---|
| `get(request, ...)` | Handle GET |
| `post(request, ...)` | Handle POST |
| `put(request, ...)` | Handle PUT |
| `patch(request, ...)` | Handle PATCH |
| `delete(request, ...)` | Handle DELETE |
| `options(request, ...)` | Handle OPTIONS |
| `head(request, ...)` | Handle HEAD |
| `dispatch()` | Routes request to the appropriate method |
| `initial()` | Performs initial request processing |
| `finalize_response()` | Prepares the final response |

### When should you use APIView?

Use APIView when:

- You need custom business logic.
- Your endpoint does not map directly to a model.
- You need complete control over request handling.
- You are building custom workflows.
- You need a non-standard response structure.

Example use cases:

- Login endpoint.
- Payment processing.
- OTP verification.
- Dashboard statistics.
- External API integration.

# 2. GenericAPIView

## What is GenericAPIView?

`GenericAPIView` extends APIView.

It provides reusable functionality for working with querysets and serializers.

It is the foundation of DRF's generic views.

Instead of manually implementing everything, you get methods for:

- Getting querysets.
- Getting serializers.
- Finding individual objects.
- Filtering querysets.
- Paginating results.

## Basic syntax

```python
from rest_framework.generics import GenericAPIView

class ProductGenericAPIView(GenericAPIView):

    queryset = Product.objects.all()

    serializer_class = ProductSerializer
```

However, GenericAPIView does not automatically implement GET, POST, PUT, PATCH, or DELETE behavior.

You combine it with methods or mixins.

## Important GenericAPIView attributes

### 1. queryset

Defines the default queryset used by the view.

```python
queryset = Product.objects.all()
```

This tells DRF which objects are available to the endpoint.

For dynamic behavior, override `get_queryset()` instead of directly changing a shared queryset.

### 2. serializer_class

Specifies which serializer should be used.

```python
serializer_class = ProductSerializer
```

### 3. lookup_field

Defines the model field used to find an individual object.

Default:

```python
lookup_field = "pk"
```

Example:

```python
lookup_field = "slug"
```

Then DRF can look up an object using its slug rather than its primary key.

### 4. lookup_url_kwarg

Defines the URL parameter used for lookup.

Default behavior uses the lookup field's name.

Example:

```python
lookup_field = "slug"
lookup_url_kwarg = "product_slug"
```

URL:

```python
path(
    "products/<slug:product_slug>/",
    ProductDetailView.as_view()
)
```

DRF uses `product_slug` from the URL to find the product's `slug` field.

### 5. filter_backends

Specifies the filtering systems applied to the queryset.

Example:

```python
filter_backends = [
    DjangoFilterBackend,
    SearchFilter,
    OrderingFilter
]
```

You must import and configure the required filter backends.

### 6. pagination_class

Specifies the pagination class used by the view.

```python
pagination_class = PageNumberPagination
```

Set it to `None` to disable pagination for that view.

## Important GenericAPIView methods

### 1. get_queryset()

Returns the queryset used by the view.

```python
def get_queryset(self):

    return Product.objects.filter(
        is_available=True
    )
```

Why use it?

Because the queryset can depend on the current user, request parameters, or other request-specific conditions.

### 2. get_serializer_class()

Returns the serializer class.

```python
def get_serializer_class(self):

    if self.request.method == "GET":
        return ProductReadSerializer

    return ProductWriteSerializer
```

Useful when GET and POST need different serializers.

### 3. get_serializer()

Creates and returns a serializer instance.

```python
serializer = self.get_serializer(
    data=request.data
)
```

It automatically passes the serializer context.

### 4. get_object()

Retrieves one object using the queryset and lookup configuration.

```python
product = self.get_object()
```

It also performs object-level permission checks.

### 5. filter_queryset()

Applies configured filter backends.

```python
queryset = self.filter_queryset(
    self.get_queryset()
)
```

### 6. paginate_queryset()

Applies pagination to a queryset.

```python
page = self.paginate_queryset(queryset)
```

### 7. get_paginated_response()

Returns the paginated response.

```python
return self.get_paginated_response(
    serializer.data
)
```

## Complete GenericAPIView example

```python
from rest_framework.generics import GenericAPIView
from rest_framework.response import Response
from rest_framework import status

from .models import Product
from .serializers import ProductSerializer


class ProductGenericAPIView(GenericAPIView):

    queryset = Product.objects.all()

    serializer_class = ProductSerializer

    def get(self, request):

        products = self.get_queryset()

        serializer = self.get_serializer(
            products,
            many=True
        )

        return Response(serializer.data)

    def post(self, request):

        serializer = self.get_serializer(
            data=request.data
        )

        serializer.is_valid(
            raise_exception=True
        )

        serializer.save()

        return Response(
            serializer.data,
            status=status.HTTP_201_CREATED
        )
```

### Expected POST response

```json
{
    "id": 4,
    "name": "Monitor",
    "price": "250.00",
    "description": "27-inch monitor",
    "is_available": true,
    "created_at": "2026-11-05T10:20:00Z"
}
```

### When should you use GenericAPIView?

Use it when:

- You need queryset and serializer functionality.
- You want to combine reusable mixins.
- You need custom request handling without writing everything from scratch.
- You want more control than a ready-made generic view provides.

# 3. Generic Views

## What are Generic Views?

Generic views are ready-made class-based views built on top of GenericAPIView and reusable mixins.

They reduce repetitive code.

For example, instead of implementing:

- Querying products.
- Serializing products.
- Validating input.
- Saving records.
- Finding objects.
- Updating records.

You can use a generic view that already implements these operations.

## Understanding mixins

DRF uses mixins to provide reusable CRUD operations.

| Mixin | Function |
|---|---|
| ListModelMixin | List multiple objects |
| RetrieveModelMixin | Retrieve one object |
| CreateModelMixin | Create an object |
| UpdateModelMixin | Update an object |
| DestroyModelMixin | Delete an object |

Example:

```python
from rest_framework.generics import GenericAPIView
from rest_framework.mixins import (
    ListModelMixin,
    CreateModelMixin
)

class ProductListCreateView(
    ListModelMixin,
    CreateModelMixin,
    GenericAPIView
):

    queryset = Product.objects.all()

    serializer_class = ProductSerializer

    def get(self, request, *args, **kwargs):
        return self.list(request, *args, **kwargs)

    def post(self, request, *args, **kwargs):
        return self.create(request, *args, **kwargs)
```

This view supports:

- GET: list products.
- POST: create a product.

The mixins implement the reusable logic.

## Important mixin methods

| Method | Purpose |
|---|---|
| `list()` | Returns a collection |
| `retrieve()` | Returns one object |
| `create()` | Creates an object |
| `update()` | Performs a full update |
| `partial_update()` | Performs a partial update |
| `destroy()` | Deletes an object |

## Why use generic views?

They reduce code duplication and provide standard API behavior.

For example:

```python
class ProductListView(ListAPIView):

    queryset = Product.objects.all()

    serializer_class = ProductSerializer
```

This small class provides a complete GET endpoint for listing products.

# 6. CreateAPIView

## What is CreateAPIView?

`CreateAPIView` creates a new object.

It supports:

```text
POST
```

DRF automatically:

1. Reads incoming data.
2. Creates a serializer.
3. Validates the data.
4. Saves the object.
5. Returns the serialized object.

## Example

```python
from rest_framework.generics import CreateAPIView

class ProductCreateAPIView(CreateAPIView):

    queryset = Product.objects.all()

    serializer_class = ProductSerializer
```

## URL

```python
path(
    "products/create/",
    ProductCreateAPIView.as_view(),
    name="product-create"
)
```

## Request

```http
POST /api/products/create/
Content-Type: application/json
```

Body:

```json
{
    "name": "Mouse",
    "price": "25.00",
    "description": "Wireless mouse",
    "is_available": true
}
```

## Expected response

```json
{
    "id": 3,
    "name": "Mouse",
    "price": "25.00",
    "description": "Wireless mouse",
    "is_available": true
}
```

HTTP status:

```text
201 Created
```

## Customizing creation

You can override `perform_create()`.

```python
class ProductCreateAPIView(CreateAPIView):

    queryset = Product.objects.all()

    serializer_class = ProductSerializer

    def perform_create(self, serializer):

        serializer.save()
```

This method is particularly useful when you need to automatically attach information such as the currently authenticated user.

For example, if Product has an `owner` foreign key:

```python
def perform_create(self, serializer):

    serializer.save(owner=self.request.user)
```

The serializer must support the `owner` field on saving, and the model must contain the corresponding relationship.

## When should you use CreateAPIView?

Use it for:

- User registration.
- Creating products.
- Creating orders.
- Creating comments.
- Submitting support tickets.

# 8. DestroyAPIView

## What is DestroyAPIView?

`DestroyAPIView` deletes an existing object.

It supports:

```text
DELETE
```

## Example

```python
from rest_framework.generics import DestroyAPIView

class ProductDeleteAPIView(DestroyAPIView):

    queryset = Product.objects.all()

    serializer_class = ProductSerializer
```

## URL

```python
path(
    "products/<int:pk>/delete/",
    ProductDeleteAPIView.as_view(),
    name="product-delete"
)
```

## Request

```http
DELETE /api/products/1/delete/
```

## Expected response

```text
HTTP 204 No Content
```

A 204 response normally has an empty body.

## Customizing deletion

Override `perform_destroy()`.

```python
def perform_destroy(self, instance):

    instance.delete()
```

You could also implement a soft-delete policy:

```python
def perform_destroy(self, instance):

    instance.is_deleted = True

    instance.save(update_fields=["is_deleted"])
```

The model must have an `is_deleted` field, and your queryset should normally exclude deleted objects.

## When should you use DestroyAPIView?

Use it for:

- Deleting products.
- Removing comments.
- Deleting draft posts.
- Removing user-owned resources.
- Deleting records from administrative systems.

Always apply suitable permissions before allowing deletion.

# 13. ViewSets

## What is a ViewSet?

A ViewSet groups multiple related API operations into a single class.

With generic views, you commonly create separate classes for:

- Listing.
- Creating.
- Retrieving.
- Updating.
- Deleting.

With a ViewSet, these operations can be placed in one class.

A router can automatically generate the corresponding URLs.

## Basic syntax

```python
from rest_framework.viewsets import ViewSet

class ProductViewSet(ViewSet):

    def list(self, request):
        pass

    def retrieve(self, request, pk=None):
        pass

    def create(self, request):
        pass

    def update(self, request, pk=None):
        pass

    def partial_update(self, request, pk=None):
        pass

    def destroy(self, request, pk=None):
        pass
```

## Important ViewSet actions

| Action | HTTP method | Purpose |
|---|---|---|
| list | GET | List objects |
| retrieve | GET | Retrieve one object |
| create | POST | Create object |
| update | PUT | Full update |
| partial_update | PATCH | Partial update |
| destroy | DELETE | Delete object |

A plain `ViewSet` does not automatically implement these operations. You write the action logic yourself.

## Example: Custom ViewSet

```python
from rest_framework.viewsets import ViewSet
from rest_framework.response import Response
from rest_framework import status

from .models import Product
from .serializers import ProductSerializer


class ProductViewSet(ViewSet):

    def list(self, request):

        products = Product.objects.all()

        serializer = ProductSerializer(
            products,
            many=True
        )

        return Response(serializer.data)

    def retrieve(self, request, pk=None):

        try:
            product = Product.objects.get(pk=pk)

        except Product.DoesNotExist:

            return Response(
                {"error": "Product not found"},
                status=status.HTTP_404_NOT_FOUND
            )

        serializer = ProductSerializer(product)

        return Response(serializer.data)

    def create(self, request):

        serializer = ProductSerializer(
            data=request.data
        )

        serializer.is_valid(
            raise_exception=True
        )

        serializer.save()

        return Response(
            serializer.data,
            status=status.HTTP_201_CREATED
        )
```

## Register a router

Inside `products/urls.py`:

```python
from rest_framework.routers import DefaultRouter
from .views import ProductViewSet

router = DefaultRouter()

router.register(
    "products",
    ProductViewSet,
    basename="product"
)

urlpatterns = router.urls
```

In `config/urls.py`:

```python
from django.urls import path, include

urlpatterns = [
    path("api/", include("products.urls")),
]
```

## Generated URLs

The router creates routes based on the actions provided by the ViewSet.

For the example above:

| URL | Method | Action |
|---|---|---|
| `/api/products/` | GET | list |
| `/api/products/` | POST | create |
| `/api/products/1/` | GET | retrieve |

Because we have not implemented update, partial_update, or destroy, those operations are not automatically available.

## Important ViewSet methods and attributes

### 1. action

Identifies the current ViewSet action.

Example:

```python
def get_serializer_class(self):

    if self.action == "list":
        return ProductListSerializer

    return ProductSerializer
```

The `action` attribute is especially useful for changing serializers and permissions depending on the operation.

### 2. get_queryset()

Returns the queryset.

```python
def get_queryset(self):

    return Product.objects.filter(
        is_available=True
    )
```

### 3. get_serializer_class()

Chooses a serializer based on the action.

```python
def get_serializer_class(self):

    if self.action == "list":
        return ProductListSerializer

    return ProductSerializer
```

### 4. get_permissions()

Returns permission instances for the current request.

```python
def get_permissions(self):

    if self.action == "list":
        permission_classes = [AllowAny]

    else:
        permission_classes = [IsAuthenticated]

    return [
        permission()
        for permission in permission_classes
    ]
```

Import the permissions:

```python
from rest_framework.permissions import (
    AllowAny,
    IsAuthenticated
)
```

### 5. get_serializer()

Creates the serializer instance with the appropriate context.

```python
serializer = self.get_serializer(
    data=request.data
)
```

### 6. get_object()

Retrieves the current object.

This method is provided by ModelViewSet and other GenericViewSet-based classes, not by the basic ViewSet itself.

## When should you use ViewSet?

Use ViewSet when:

- You want related API operations grouped together.
- You want automatic router-generated URLs.
- You are building standard REST resource endpoints.
- You want consistent routing across multiple resources.

# 16. Custom ViewSets

## What is a Custom ViewSet?

A custom ViewSet allows you to control which actions are available and how they work.

Use `ViewSet` or `GenericViewSet` depending on whether you need generic queryset and serializer functionality.

### Difference between ViewSet and GenericViewSet

| Feature | ViewSet | GenericViewSet |
|---|---|---|
| Base class | ViewSetMixin and APIView | ViewSetMixin and GenericAPIView |
| Standard CRUD logic | No | No, not by itself |
| `get_queryset()` | Not provided by the base class | Provided |
| `get_serializer()` | Not provided by the base class | Provided |
| Mixins | Can define actions manually | Can combine generic mixins |
| Use case | Fully custom behavior | Custom behavior with generic functionality |

## Example: Custom GenericViewSet

```python
from rest_framework.viewsets import GenericViewSet
from rest_framework.mixins import (
    ListModelMixin,
    RetrieveModelMixin
)

from .models import Product
from .serializers import ProductSerializer


class ProductCustomViewSet(
    ListModelMixin,
    RetrieveModelMixin,
    GenericViewSet
):

    queryset = Product.objects.all()

    serializer_class = ProductSerializer
```

This ViewSet provides only:

- List.
- Retrieve.

It does not provide create, update, or delete.

## Why use this approach?

Suppose your product catalog should allow:

- Anyone to view products.
- Only administrators to create products.
- Only administrators to update products.
- No deletion through the public API.

You can select exactly which mixins or actions to expose.

## Example: Custom action permissions

```python
from rest_framework.viewsets import ModelViewSet
from rest_framework.permissions import AllowAny, IsAdminUser

class ProductViewSet(ModelViewSet):

    queryset = Product.objects.all()

    serializer_class = ProductSerializer

    def get_permissions(self):

        if self.action in ["list", "retrieve"]:
            permission_classes = [AllowAny]

        else:
            permission_classes = [IsAdminUser]

        return [
            permission()
            for permission in permission_classes
        ]
```

Now:

- List and retrieve are public.
- Create, update, partial update, and destroy require staff access.

The actual authentication configuration must still be suitable for your application.

# 17. Custom Actions Using @action

## What is @action?

The `@action` decorator allows you to add custom endpoints to a ViewSet.

Standard ViewSet actions cover CRUD operations.

But real applications need additional operations.

Examples:

- Activate a product.
- Deactivate a product.
- Mark an order as completed.
- Get featured products.
- Retrieve a user's order history.
- Approve a payment.

You can implement these using `@action`.

## Basic syntax

```python
from rest_framework.decorators import action
from rest_framework.response import Response

@action(
    detail=True,
    methods=["post"],
    url_path="activate"
)
def activate(self, request, pk=None):

    pass
```

## Understanding @action parameters

### 1. detail

Controls whether the action operates on an individual object or the collection.

```python
detail=True
```

Means the action requires an individual object's URL.

Example:

```text
/api/products/1/activate/
```

```python
detail=False
```

Means the action operates on the collection.

Example:

```text
/api/products/featured/
```

### 2. methods

Specifies the HTTP methods accepted by the action.

```python
methods=["get"]
```

Or:

```python
methods=["post"]
```

You can also specify multiple methods:

```python
methods=["get", "post"]
```

Use HTTP methods according to the operation's intended behavior.

### 3. url_path

Specifies the custom URL path.

```python
url_path="activate"
```

Example:

```text
/api/products/1/activate/
```

If omitted, DRF normally derives the URL path from the method name.

### 4. url_name

Specifies the URL name used for reversing the route.

```python
url_name="activate-product"
```

### 5. permission_classes

Specifies permissions for the action.

```python
permission_classes=[IsAdminUser]
```

### 6. authentication_classes

Specifies authentication classes for the action.

```python
authentication_classes=[TokenAuthentication]
```

### 7. serializer_class

Specifies a different serializer for the action.

```python
serializer_class=ProductActionSerializer
```

### 8. throttle_classes

Specifies throttling classes for the action.

```python
throttle_classes=[UserRateThrottle]
```

### 9. filter_backends

Specifies filter backends for the action.

```python
filter_backends=[SearchFilter]
```

### 10. pagination_class

Specifies pagination behavior for the action.

```python
pagination_class=PageNumberPagination
```

These are useful for configuring custom actions independently from the ViewSet's normal behavior.

## Example 1: Activate a product

Suppose the Product model has an `is_available` field.

```python
from rest_framework.viewsets import ModelViewSet
from rest_framework.decorators import action
from rest_framework.response import Response

from .models import Product
from .serializers import ProductSerializer


class ProductViewSet(ModelViewSet):

    queryset = Product.objects.all()

    serializer_class = ProductSerializer

    @action(
        detail=True,
        methods=["post"],
        url_path="activate"
    )
    def activate(self, request, pk=None):

        product = self.get_object()

        product.is_available = True

        product.save(
            update_fields=["is_available"]
        )

        serializer = self.get_serializer(product)

        return Response(serializer.data)
```

### Request

```http
POST /api/products/1/activate/
```

### Expected response

```json
{
    "id": 1,
    "name": "Laptop",
    "price": "1200.00",
    "is_available": true
}
```

## Example 2: Deactivate a product

```python
@action(

    methods=["post"],
    url_path="deactivate"

def deactivate(self, request, pk=None):
```

This action operates on a collection, not an individual product.

```python
@action(
    detail=False,
    methods=["get"],
    url_path="featured"
)
def featured(self, request):

    products = Product.objects.filter(
        is_available=True
    )[:5]

    serializer = self.get_serializer(
        products,
        many=True
    )

    return Response(serializer.data)
```

Request:

```http
GET /api/products/featured/
```

Response:

```json
[
    {
        "id": 1,
```

## Understanding detail=True vs detail=False

| Feature | detail=True | detail=False |
|---|---|---|
| Operates on | One object | Collection |
| Requires object lookup | Usually | No |
| Example | Activate product 1 | Get featured products |
| Example URL | `/products/1/activate/` | `/products/featured/` |

## When should you use @action?

Use it when an operation is related to a ViewSet resource but is not a standard CRUD operation.

- `/products/featured/`
- `/users/1/change-password/`

For sensitive operations such as refunds or approvals, implement strict authorization, input validation, audit logging, and transaction handling.

# 18. Choosing Between APIView, Generic Views and ViewSets

This is one of the most important decisions when designing a DRF application.

All three approaches can build REST APIs, but they offer different levels of control and abstraction.

## 18.1 APIView

Use APIView when you need maximum control.

Example:

```python
class ProductStatisticsAPIView(APIView):

    def get(self, request):

        total_products = Product.objects.count()

        available_products = Product.objects.filter(
            is_available=True
        ).count()

        return Response({
            "total_products": total_products,
            "available_products": available_products
        })
```

Output:

```json
{
    "total_products": 100,
    "available_products": 80
}
```

Why APIView?

Because statistics are not simply a standard CRUD operation on one product.

Suitable use cases:

- Payment processing.
- Login and authentication workflows.
- Dashboard analytics.
- Complex business logic.
- External service integrations.

## 18.2 Generic Views

Use generic views when your endpoint follows a standard CRUD pattern but you want to expose only specific operations.

Example:

```python
class ProductListView(ListAPIView):

    queryset = Product.objects.all()

    serializer_class = ProductSerializer
```

Why Generic Views?

Because DRF already implements listing, validation, retrieval, and saving behavior.

Suitable use cases:

- List products.
- Create orders.
- Retrieve customer details.
- Update profiles.
- Delete records.

## 18.3 ViewSets

Use ViewSets when you want to group related resource operations and generate URLs through routers.

Example:

```python
class ProductViewSet(ModelViewSet):

    queryset = Product.objects.all()

    serializer_class = ProductSerializer
```

Why ViewSets?

Because standard CRUD operations are implemented automatically.

Suitable use cases:

- Product management.
- Customer management.
- Employee management.
- Blog management.
- Inventory management.

## 18.4 Comparison table

| Feature | APIView | Generic Views | ViewSets |
|---|---|---|---|
| Main purpose | Custom request handling | Reusable CRUD patterns | Grouped resource actions |
| Control | High | Medium to high | Medium to high |
| Automatic CRUD | No | Yes, depending on class | Yes with ModelViewSet |
| Serializer support | Manual integration | Built in | Built in for GenericViewSet-based classes |
| Queryset support | Manual | Built in | Built in for GenericViewSet-based classes |
| Router support | No automatic ViewSet routing | No automatic ViewSet routing | Yes |
| Best for | Custom endpoints | Standard individual endpoints | Resource-based APIs |

## 18.5 Decision guide

Choose APIView if:

- You are implementing a custom workflow.
- You need full control over the request and response.
- The endpoint is not a standard CRUD resource.

Choose Generic Views if:

- You need a standard list, create, retrieve, update, or delete endpoint.
- You want to expose only selected HTTP methods.
- You prefer explicit URL configuration.

Choose ViewSets if:

- You are building a resource-oriented API.
- You want related CRUD operations in one class.
- You want automatic router-generated URLs.
- You want to add custom actions using `@action`.

## 18.6 Practical example: E-commerce application

Imagine you are building an e-commerce backend.

| Feature | Recommended approach | Reason |
|---|---|---|
| Product listing | ListAPIView | Only list products |
| Product creation | CreateAPIView | Only create products |
| Product detail | RetrieveAPIView | Only retrieve products |
| Product management | ModelViewSet | Full CRUD |
| Featured products | `@action` | Custom collection action |
| Activate product | `@action` | Custom detail action |
| Payment processing | APIView | Custom business workflow |
| Dashboard statistics | APIView | Aggregated data |
| Public product catalog | ReadOnlyModelViewSet | Read-only resource API |
| Customer profile editing | RetrieveUpdateAPIView | Retrieve and update |

## Step 3: ModelViewSet

`products/views.py`

```python
from rest_framework.viewsets import ModelViewSet

from rest_framework.decorators import action

from rest_framework.response import Response

from rest_framework import status

from rest_framework.permissions import IsAuthenticatedOrReadOnly

from rest_framework.filters import SearchFilter, OrderingFilter

from .models import Product

from .serializers import ProductSerializer


class ProductViewSet(ModelViewSet):

    queryset = Product.objects.all()

    serializer_class = ProductSerializer

    permission_classes = [
        IsAuthenticatedOrReadOnly
    ]

    filter_backends = [
        SearchFilter,
        OrderingFilter
    ]

    search_fields = [
        "name",
        "description"
    ]

    ordering_fields = [
        "price",
        "created_at"
    ]

    ordering = [
        "name"
    ]

    def get_queryset(self):

        queryset = Product.objects.all()

        available = self.request.query_params.get(
            "available"
        )

        if available == "true":

            queryset = queryset.filter(
                is_available=True
            )

        elif available == "false":

            queryset = queryset.filter(
                is_available=False
            )

        return queryset

    @action(
        detail=True,
        methods=["post"]
    )
    def activate(self, request, pk=None):

        product = self.get_object()

        product.is_available = True

        product.save(
            update_fields=["is_available"]
        )

        return Response({
            "message": "Product activated successfully"
        })

    @action(
        detail=False,
        methods=["get"]
    )
    def featured(self, request):

        products = Product.objects.filter(
            is_available=True
        ).order_by("-created_at")[:5]

        serializer = self.get_serializer(
            products,
            many=True
        )

        return Response(serializer.data)
```

# Final Comparison: Which DRF View Should You Learn First?

| View | Operations supported |
|---|---|
| APIView | Whatever you implement |
| GenericAPIView | Foundation; behavior added using methods and mixins |
| ListAPIView | GET collection |
| RetrieveAPIView | GET one object |
| CreateAPIView | POST |
| UpdateAPIView | PUT, PATCH |
| DestroyAPIView | DELETE |
| ListCreateAPIView | GET collection, POST |
| RetrieveUpdateAPIView | GET one, PUT, PATCH |
| RetrieveDestroyAPIView | GET one, DELETE |
| RetrieveUpdateDestroyAPIView | GET one, PUT, PATCH, DELETE |
| ViewSet | Whatever actions you implement |
| ModelViewSet | Complete CRUD |
| ReadOnlyModelViewSet | List and retrieve |
| GenericViewSet | Generic functionality plus selected actions |
| Custom ViewSet | Custom API operations |
| `@action` | Additional custom ViewSet endpoint |

## Recommended learning order

1. Start with APIView to understand HTTP methods and request/response handling.
2. Learn GenericAPIView to understand querysets and serializers.
3. Learn mixins to understand reusable CRUD behavior.
4. Practice each generic view individually.
5. Learn ViewSet and router registration.
6. Learn ModelViewSet for complete CRUD.
7. Learn ReadOnlyModelViewSet for read-only APIs.
8. Learn custom ViewSets and `@action` for advanced API workflows.

## The most important practical rule

- Use **APIView** for custom business logic.
- Use **Generic Views** for standard operations when you want to expose only selected endpoints.
- Use **ModelViewSet** for complete CRUD APIs built around Django models.
- Use **ReadOnlyModelViewSet** when clients should only read resources.
- Use **@action** when you need additional operations beyond standard CRUD.

You do not need to use the most advanced class everywhere. Choose the simplest DRF view that meets the endpoint's requirements.
