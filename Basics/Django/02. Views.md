# First: Understanding FBV and CBV

Before learning the topics, understand an important distinction.

Django supports two main ways of writing views.

## 1. Function-Based Views (FBV)

An FBV is a normal Python function that handles an HTTP request.

Example:

```python
from django.http import JsonResponse
from rest_framework.decorators import api_view

@api_view(["GET"])
def hello_api(request):

    return JsonResponse({
        "message": "Hello from Django REST Framework"
    })
```

Here:

- `@api_view` converts a Django-style function into a DRF API view.
- `["GET"]` specifies the allowed HTTP method.
- `request` contains the incoming request.
- The function returns a response.

## 2. Class-Based Views (CBV)

A CBV is a Python class that handles HTTP requests through methods such as `get()`, `post()`, `put()`, and `delete()`.

Example:

```python
from rest_framework.views import APIView
from rest_framework.response import Response

class HelloAPI(APIView):

    def get(self, request):

        return Response({
            "message": "Hello from APIView"
        })
```

Here:

- `APIView` is the parent class.
- `get()` handles GET requests.
- `request` contains the incoming request.
- `Response` returns JSON-compatible API data.

## FBV vs CBV

| Feature | FBV | CBV |
|---|---|---|
| Structure | Function | Class |
| Main syntax | `def` | `class` |
| HTTP methods | Decorators and conditions | Separate methods |
| Reusability | Function composition | Inheritance and mixins |
| Best for | Small, simple endpoints | Reusable and structured APIs |
| Complexity | Easy initially | More flexible for larger APIs |

**Important:** `APIView`, `GenericAPIView`, generic views, and ViewSets are all class-based approaches.

# 1. APIView

## What is APIView?

`APIView` is one of the fundamental class-based views provided by Django REST Framework.

It gives you control over how HTTP requests are handled.

Unlike Django's ordinary `View`, DRF's APIView provides additional API functionality, including:

- Request parsing.
- Response rendering.
- Authentication.
- Permissions.
- Throttling.
- Content negotiation.
- Exception handling.

You can implement individual HTTP methods inside the class.

## Basic syntax

```python
from rest_framework.views import APIView
from rest_framework.response import Response

class MyAPIView(APIView):

    def get(self, request):
        pass

    def post(self, request):
        pass

    def put(self, request):
        pass

    def patch(self, request):
        pass

    def delete(self, request):
        pass
```

## Important HTTP methods

| Method | Purpose | Example |
|---|---|---|
| GET | Retrieve data | Get all products |
| POST | Create data | Create a product |
| PUT | Replace/update data | Update a product |
| PATCH | Partially update data | Update product price |
| DELETE | Delete data | Delete a product |

## Example 1: Retrieve all products

`products/views.py`:

```python
from rest_framework.views import APIView
from rest_framework.response import Response

from .models import Product
from .serializers import ProductSerializer


class ProductListAPIView(APIView):

    def get(self, request):

        products = Product.objects.all()

        serializer = ProductSerializer(
            products,
            many=True
        )

        return Response(serializer.data)
```

## Important APIView attributes

APIView supports several class-level attributes that control request processing.

### 1. authentication_classes

Specifies which authentication classes are used.

```python
from rest_framework.authentication import (
    SessionAuthentication,
    BasicAuthentication
)

class ProductAPIView(APIView):

    authentication_classes = [
        SessionAuthentication,
        BasicAuthentication
    ]
```

Authentication identifies the user making the request.

Common authentication classes include:

- `SessionAuthentication`
- `BasicAuthentication`
- `TokenAuthentication`

JWT authentication is commonly supplied by an additional package such as Simple JWT.

### 2. permission_classes

Controls who is allowed to access the endpoint.

```python
from rest_framework.permissions import IsAuthenticated

class ProductAPIView(APIView):

    permission_classes = [
        IsAuthenticated
    ]
```

Common permissions:

| Permission | Meaning |
|---|---|
| AllowAny | Anyone can access |
| IsAuthenticated | User must be logged in |
| IsAdminUser | User must have staff status |
| IsAuthenticatedOrReadOnly | Everyone can read; authenticated users can perform other permitted methods |
| DjangoModelPermissions | Applies Django model permissions |

Example:

```python
permission_classes = [AllowAny]
```

This allows public access, subject to other applicable controls.

### 3. throttle_classes

Controls how frequently clients can make requests.

```python
from rest_framework.throttling import AnonRateThrottle

class ProductAPIView(APIView):

    throttle_classes = [
        AnonRateThrottle
    ]
```

Throttle classes are useful for reducing excessive API usage.

They are not a complete security or denial-of-service protection system.

### 4. parser_classes

Controls which incoming request formats can be parsed.

```python
from rest_framework.parsers import (
    JSONParser,
    FormParser,
    MultiPartParser
)

class ProductAPIView(APIView):

    parser_classes = [
        JSONParser,
        FormParser,
        MultiPartParser
    ]
```

Common parsers:

- `JSONParser`: JSON request body.
- `FormParser`: form-encoded data.
- `MultiPartParser`: multipart form data, commonly used for file uploads.
- `FileUploadParser`: raw file upload requests.

### 5. renderer_classes

Controls the response formats supported by the view.

```python
from rest_framework.renderers import (
    JSONRenderer,
    BrowsableAPIRenderer
)

class ProductAPIView(APIView):

    renderer_classes = [
        JSONRenderer,
        BrowsableAPIRenderer
    ]
```

### 6. content_negotiation_class

Controls how DRF chooses a renderer based on the request's accepted media types.

```python
content_negotiation_class = MyContentNegotiationClass
```

You normally keep the default unless you have a specific content-negotiation requirement.

### 7. metadata_class

Controls metadata returned for API OPTIONS requests.

```python
metadata_class = MyMetadataClass
```

### 8. versioning_class

Controls API versioning behavior.

```python
versioning_class = MyVersioningClass
```

You can also configure versioning globally through `REST_FRAMEWORK` settings.

## Important APIView methods

| Method | Purpose |
|---|---|
| `get(request, ...)` | Handle GET |
| `post(request, ...)` | Handle POST |
| `put(request, ...)` | Handle PUT |
| `patch(request, ...)` | Handle PATCH |
| `delete(request, ...)` | Handle DELETE |
| `options(request, ...)` | Handle OPTIONS |
| `head(request, ...)` | Handle HEAD |
| `dispatch()` | Routes request to the appropriate method |
| `initial()` | Performs initial request processing |
| `finalize_response()` | Prepares the final response |

### When should you use APIView?

Use APIView when:

- You need custom business logic.
- Your endpoint does not map directly to a model.
- You need complete control over request handling.
- You are building custom workflows.
- You need a non-standard response structure.

Example use cases:

- Login endpoint.
- Payment processing.
- OTP verification.
- Dashboard statistics.
- External API integration.

# 2. GenericAPIView

## What is GenericAPIView?

`GenericAPIView` extends APIView.

It provides reusable functionality for working with querysets and serializers.

It is the foundation of DRF's generic views.

Instead of manually implementing everything, you get methods for:

- Getting querysets.
- Getting serializers.
- Finding individual objects.
- Filtering querysets.
- Paginating results.

## Basic syntax

```python
from rest_framework.generics import GenericAPIView

class ProductGenericAPIView(GenericAPIView):

    queryset = Product.objects.all()

    serializer_class = ProductSerializer
```

However, GenericAPIView does not automatically implement GET, POST, PUT, PATCH, or DELETE behavior.

You combine it with methods or mixins.

## Important GenericAPIView attributes

### 1. queryset

Defines the default queryset used by the view.

```python
queryset = Product.objects.all()
```

This tells DRF which objects are available to the endpoint.

For dynamic behavior, override `get_queryset()` instead of directly changing a shared queryset.

### 2. serializer_class

Specifies which serializer should be used.

```python
serializer_class = ProductSerializer
```

### 3. lookup_field

Defines the model field used to find an individual object.

Default:

```python
lookup_field = "pk"
```

Example:

```python
lookup_field = "slug"
```

Then DRF can look up an object using its slug rather than its primary key.

### 4. lookup_url_kwarg

Defines the URL parameter used for lookup.

Default behavior uses the lookup field's name.

Example:

```python
lookup_field = "slug"
lookup_url_kwarg = "product_slug"
```

URL:

```python
path(
    "products/<slug:product_slug>/",
    ProductDetailView.as_view()
)
```

DRF uses `product_slug` from the URL to find the product's `slug` field.

### 5. filter_backends

Specifies the filtering systems applied to the queryset.

Example:

```python
filter_backends = [
    DjangoFilterBackend,
    SearchFilter,
    OrderingFilter
]
```

You must import and configure the required filter backends.

### 6. pagination_class

Specifies the pagination class used by the view.

```python
pagination_class = PageNumberPagination
```

Set it to `None` to disable pagination for that view.

## Important GenericAPIView methods

### 1. get_queryset()

Returns the queryset used by the view.

```python
def get_queryset(self):

    return Product.objects.filter(
        is_available=True
    )
```

Why use it?

Because the queryset can depend on the current user, request parameters, or other request-specific conditions.

### 2. get_serializer_class()

Returns the serializer class.

```python
def get_serializer_class(self):

    if self.request.method == "GET":
        return ProductReadSerializer

    return ProductWriteSerializer
```

Useful when GET and POST need different serializers.

### 3. get_serializer()

Creates and returns a serializer instance.

```python
serializer = self.get_serializer(
    data=request.data
)
```

It automatically passes the serializer context.

### 4. get_object()

Retrieves one object using the queryset and lookup configuration.

```python
product = self.get_object()
```

It also performs object-level permission checks.

### 5. filter_queryset()

Applies configured filter backends.

```python
queryset = self.filter_queryset(
    self.get_queryset()
)
```

### 6. paginate_queryset()

Applies pagination to a queryset.

```python
page = self.paginate_queryset(queryset)
```

### 7. get_paginated_response()

Returns the paginated response.

```python
return self.get_paginated_response(
    serializer.data
)
```

## Complete GenericAPIView example

```python
from rest_framework.generics import GenericAPIView
from rest_framework.response import Response
from rest_framework import status

from .models import Product
from .serializers import ProductSerializer


class ProductGenericAPIView(GenericAPIView):

    queryset = Product.objects.all()

    serializer_class = ProductSerializer

    def get(self, request):

        products = self.get_queryset()

        serializer = self.get_serializer(
            products,
            many=True
        )

        return Response(serializer.data)

    def post(self, request):

        serializer = self.get_serializer(
            data=request.data
        )

        serializer.is_valid(
            raise_exception=True
        )

        serializer.save()

        return Response(
            serializer.data,
            status=status.HTTP_201_CREATED
        )
```

### Expected POST response

```json
{
    "id": 4,
    "name": "Monitor",
    "price": "250.00",
    "description": "27-inch monitor",
    "is_available": true,
    "created_at": "2026-11-05T10:20:00Z"
}
```

### When should you use GenericAPIView?

Use it when:

- You need queryset and serializer functionality.
- You want to combine reusable mixins.
- You need custom request handling without writing everything from scratch.
- You want more control than a ready-made generic view provides.

# 3. Generic Views

## What are Generic Views?

Generic views are ready-made class-based views built on top of GenericAPIView and reusable mixins.

They reduce repetitive code.

For example, instead of implementing:

- Querying products.
- Serializing products.
- Validating input.
- Saving records.
- Finding objects.
- Updating records.

You can use a generic view that already implements these operations.

## Understanding mixins

DRF uses mixins to provide reusable CRUD operations.

| Mixin | Function |
|---|---|
| ListModelMixin | List multiple objects |
| RetrieveModelMixin | Retrieve one object |
| CreateModelMixin | Create an object |
| UpdateModelMixin | Update an object |
| DestroyModelMixin | Delete an object |

Example:

```python
from rest_framework.generics import GenericAPIView
from rest_framework.mixins import (
    ListModelMixin,
    CreateModelMixin
)

class ProductListCreateView(
    ListModelMixin,
    CreateModelMixin,
    GenericAPIView
):

    queryset = Product.objects.all()

    serializer_class = ProductSerializer

    def get(self, request, *args, **kwargs):
        return self.list(request, *args, **kwargs)

    def post(self, request, *args, **kwargs):
        return self.create(request, *args, **kwargs)
```

This view supports:

- GET: list products.
- POST: create a product.
