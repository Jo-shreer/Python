# Django Development vs Production – Complete Guide

# 1. Understanding Django Development vs Production

First, let's understand the difference between development and production environments.

## 1.1 Development environment

A development environment is where developers write code, debug errors, build APIs, and test functionality.

Typical setup:

```text
Developer
   |
   v
Django Development Server
   |
   v
Django Application
   |
   v
Local Database
```

Start the development server:

```bash
python manage.py runserver
```

By default, Django runs on:

```text
http://127.0.0.1:8000/
```

Development configuration:

```python
DEBUG = True

ALLOWED_HOSTS = ["localhost", "127.0.0.1"]
```

Development characteristics:

- Debugging information is available.
- Code changes can trigger automatic reloads.
- Local databases are commonly used.
- Developers can use local files.
- Development tools can be installed.
- Security settings may be relaxed for convenience.

## 1.2 Production environment

Production is where real users access the application.

A production application must handle:

- Multiple users.
- High traffic.
- Security.
- Database connections.
- Application failures.
- Performance.
- Logging.
- Monitoring.
- Scaling.
- Deployment updates.

Typical architecture:

```text
                  Users
                    |
                    v
                 Internet
                    |
                    v
                  Nginx
                    |
                    v
              Gunicorn/Uvicorn
                    |
                    v
              Django Application
                    |
          +---------+---------+
          |         |         |
          v         v         v
         RDS       Redis      S3
```

Production settings:

```python
DEBUG = False

ALLOWED_HOSTS = [
    "example.com",
    "api.example.com",
]
```

### Development vs Production

| Feature | Development | Production |
|---|---|---|
| Server | Django runserver | Gunicorn/Uvicorn |
| Debug mode | True | False |
| Database | Local DB | Managed/production DB |
| Static files | Django development serving | Nginx/CDN/storage |
| Media files | Local storage | S3 or shared storage |
| Logging | Console | Centralized logging |
| Security | Relaxed settings | Strict security |
| HTTPS | Often optional locally | Required for public applications |
| Monitoring | Manual debugging | Automated monitoring |
| Deployment | Manual | CI/CD |
| Scaling | Usually one process | Multiple workers/instances |

**Important:** Never use Django's development server as your production application server.

# 2. WSGI and Gunicorn

## 2.1 What is WSGI?

WSGI stands for Web Server Gateway Interface.

It is a standard interface between Python web applications and web servers.

It allows web servers to communicate with Python frameworks such as Django.

In simple terms:

WSGI defines how an HTTP server communicates with a synchronous Python web application.

Architecture:

```text
Client
  |
  v
Web Server
  |
  v
WSGI Server
  |
  v
Django Application
  |
  v
Database
```

Django provides a WSGI application in:

```text
config/wsgi.py
```

Example:

```python
import os

from django.core.wsgi import get_wsgi_application

os.environ.setdefault(
    "DJANGO_SETTINGS_MODULE",
    "config.settings.production"
)

application = get_wsgi_application()
```

The `application` object is the WSGI entry point.

## 2.2 What is Gunicorn?

Gunicorn stands for Green Unicorn.

It is a production WSGI HTTP server for Python applications.

It runs Django using multiple worker processes.

Why do we need it?

Django's development server is designed for development, not production.

Gunicorn provides a production-oriented server that manages application worker processes.

## 2.3 Gunicorn architecture

```text
              Client Requests
                     |
                     v
                   Nginx
                     |
                     v
                  Gunicorn
                     |
          +----------+----------+
          |          |          |
          v          v          v
       Worker 1   Worker 2   Worker 3
          |          |          |
          +----------+----------+
                     |
                     v
                  Django
                     |
                     v
                 PostgreSQL
```

Each worker can handle application requests.

## 2.4 Install Gunicorn

```bash
pip install gunicorn
```

## 2.5 Run Django using Gunicorn

```bash
gunicorn config.wsgi:application
```

Specify the port:

```bash
gunicorn config.wsgi:application --bind 0.0.0.0:8000
```

Specify workers:

```bash
gunicorn config.wsgi:application \
    --workers 3 \
    --bind 0.0.0.0:8000
```

Important Gunicorn options:

| Option | Purpose |
|---|---|
| `--workers` | Number of worker processes |
| `--bind` | Address and port |
| `--timeout` | Worker timeout |
| `--access-logfile` | Access log destination |
| `--error-logfile` | Error log destination |
| `--max-requests` | Restart worker after a request count |
| `--graceful-timeout` | Time allowed for graceful worker shutdown |

Example:

```bash
gunicorn config.wsgi:application \
    --workers 4 \
    --bind 0.0.0.0:8000 \
    --timeout 60 \
    --max-requests 1000 \
    --max-requests-jitter 100 \
    --access-logfile - \
    --error-logfile -
```

The `-` sends logs to standard output or standard error, which is convenient in Docker and container environments.

## 2.6 How many Gunicorn workers should we use?

A commonly cited starting formula is:

```text
workers = (2 × CPU cores) + 1
```

For example:

```text
2 CPU cores

Workers = (2 × 2) + 1

Workers = 5
```

However, this is only a starting point, not a universal production rule.

The correct number depends on:

- Available memory.
- Request duration.
- Database connection limits.
- CPU utilization.
- Traffic.
- Whether workers perform blocking operations.

Measure actual resource usage and tune accordingly.

## 2.7 When should we use Gunicorn?

Use Gunicorn when deploying a conventional synchronous Django application through WSGI.

# 3. ASGI and Uvicorn

## 3.1 What is ASGI?

ASGI stands for Asynchronous Server Gateway Interface.

It is an interface between asynchronous Python applications and application servers.

Unlike traditional WSGI, ASGI supports asynchronous application execution and long-lived connections.

It is useful for:

- WebSockets.
- Real-time applications.
- Asynchronous views.
- Long-lived connections.
- Applications using Django Channels.

Architecture:

```text
Client
  |
  v
ASGI Server
  |
  v
Django ASGI Application
  |
  +----> HTTP Requests
  |
  +----> WebSockets
  |
  +----> Async Operations
```

Django provides:

```text
config/asgi.py
```

Example:

```python
import os

from django.core.asgi import get_asgi_application

os.environ.setdefault(
    "DJANGO_SETTINGS_MODULE",
    "config.settings.production"
)

application = get_asgi_application()
```

## 3.2 What is Uvicorn?

Uvicorn is an ASGI server.

It runs ASGI-compatible Python applications, including Django.

Install:

```bash
pip install uvicorn
```

Run Django:

```bash
uvicorn config.asgi:application
```

Run on a specific address:

```bash
uvicorn config.asgi:application \
    --host 0.0.0.0 \
    --port 8000
```

## 3.3 WSGI vs ASGI

| Feature | WSGI | ASGI |
|---|---|---|
| Interface | Synchronous | Synchronous and asynchronous |
| Long-lived connections | Not natively supported | Supported |
| WebSockets | Not natively supported | Supported |
| Async Django views | Not fully async-capable through WSGI | Supported |
| Typical server | Gunicorn | Uvicorn |
| Common use | Traditional Django applications | Async and real-time applications |

Important: ASGI does not automatically make every part of Django asynchronous. Synchronous middleware, database operations, and other blocking code can still limit concurrency.

## 3.4 Gunicorn with Uvicorn workers

You can also run an ASGI Django application through Gunicorn using Uvicorn worker support.

Install:

```bash
pip install gunicorn uvicorn
```

Run:

```bash
gunicorn config.asgi:application \
    --workers 4 \
    --worker-class uvicorn_worker.UvicornWorker \
    --bind 0.0.0.0:8000
```

For current deployments, the separate `uvicorn-worker` package is the recommended source of Gunicorn's Uvicorn worker class.

## 3.5 When should we use ASGI?

Use ASGI when your application needs:

- WebSocket communication.
- Asynchronous views.
- Django Channels.
- Long-lived connections.
- Async application integrations.

For a normal CRUD-based REST API, WSGI with Gunicorn is often sufficient.

# 4. Nginx Reverse Proxy

## 4.1 What is Nginx?

Nginx is a web server that can also act as a reverse proxy.

A reverse proxy receives requests from clients and forwards them to backend application servers.

In Django production deployments, Nginx commonly sits in front of Gunicorn or Uvicorn.

Architecture:

```text
              Client
                 |
                 v
               Nginx
                 |
                 v
             Gunicorn
                 |
                 v
               Django
```

## 4.2 Why do we need Nginx?

Nginx provides:

1. Reverse proxying.
2. HTTPS termination.
3. Static-file serving.
4. Request buffering.
5. Connection handling.
6. Request routing.
7. Access controls and rate-limiting features.

## 4.3 Nginx configuration for Django

Create:

```text
/etc/nginx/sites-available/django
```

Example:

```nginx
server {
    listen 80;

    server_name example.com;

    location /static/ {
        alias /var/www/myproject/static/;
    }

    location /media/ {
        alias /var/www/myproject/media/;
    }

    location / {
        proxy_pass http://127.0.0.1:8000;

        proxy_set_header Host $host;

        proxy_set_header X-Real-IP $remote_addr;

        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

Enable the configuration:

```bash
sudo ln -s \
/etc/nginx/sites-available/django \
/etc/nginx/sites-enabled/
```

Test:

```bash
sudo nginx -t
```

Restart:

```bash
sudo systemctl restart nginx
```

## 4.4 How does reverse proxying work?

Suppose a user requests:

```text
https://example.com/api/products/
```

The flow is:

1. Request reaches Nginx.
2. Nginx receives the HTTP request.
3. Nginx forwards it to Gunicorn.
4. Gunicorn passes it to Django.
5. Django queries PostgreSQL.
6. Django returns the response.
7. Gunicorn sends the response to Nginx.
8. Nginx returns it to the client.

## 4.5 Nginx vs Gunicorn

| Nginx | Gunicorn |
|---|---|
| Web server/reverse proxy | Python application server |
| Handles incoming connections | Runs Django application |
| Serves static files | Executes Django code |
| Handles TLS termination when configured | Normally receives proxied application traffic |
| Forwards requests | Processes requests through WSGI |

# 5. Dockerising Django

## 5.1 What is Docker?

Docker is a platform for packaging applications into containers.

A container includes the application code, runtime, and required dependencies.

Without Docker:

```text
Developer Machine
   |
   +-- Python 3.12
   +-- Django 5.x
   +-- Dependencies
```

Production might have different versions and configuration.

With Docker:

```text
Django Docker Image
   |
   +-- Python
   +-- Django
   +-- Dependencies
   +-- Application Code
```

The same image can be run across development, testing, and production.

## 5.2 Dockerfile for Django

Example:

```dockerfile
FROM python:3.12-slim

ENV PYTHONDONTWRITEBYTECODE=1
ENV PYTHONUNBUFFERED=1

WORKDIR /app

COPY requirements.txt .

RUN pip install --no-cache-dir -r requirements.txt

COPY . .

EXPOSE 8000

CMD [
    "gunicorn",
    "config.wsgi:application",
    "--bind",
    "0.0.0.0:8000",
    "--workers",
    "3"
]
```

Explanation:

- `FROM`: Selects the base image.
- `ENV`: Configures Python behavior.
- `WORKDIR`: Sets the working directory.
- `COPY`: Copies project files.
- `RUN`: Executes commands while building the image.
- `EXPOSE`: Documents the application port.
- `CMD`: Starts the application.

## 5.3 Build Docker image

```bash
docker build -t django-app .
```

## 5.4 Run Docker container

```bash
docker run -p 8000:8000 django-app
```

Access:

```text
http://localhost:8000
```

## 5.5 Important Docker production practices

- Use a slim, supported Python base image.
- Pin dependencies.
- Use a non-root user.
- Do not include `.env` or secrets in the image.
- Use `.dockerignore`.
- Avoid unnecessary build tools in the final image.
- Run the application through Gunicorn or Uvicorn.
- Send logs to stdout and stderr.
- Use a proper container health check or orchestration health check.

Example `.dockerignore`:

```text
.git
.venv
venv
__pycache__
*.pyc
.env
media
staticfiles
```

## 5.6 Multi-stage Docker builds

Multi-stage builds use separate stages for building and running an application.

Example:

```dockerfile
FROM python:3.12-slim AS builder

WORKDIR /app

RUN python -m venv /opt/venv

ENV PATH="/opt/venv/bin:$PATH"

COPY requirements.txt .

RUN pip install --no-cache-dir -r requirements.txt


FROM python:3.12-slim AS runtime

WORKDIR /app

ENV PATH="/opt/venv/bin:$PATH"
ENV PYTHONDONTWRITEBYTECODE=1
ENV PYTHONUNBUFFERED=1

COPY --from=builder /opt/venv /opt/venv

COPY . .

RUN useradd --create-home appuser

USER appuser

EXPOSE 8000

CMD [
    "gunicorn",
    "config.wsgi:application",
    "--bind",
    "0.0.0.0:8000"
]
```

The final stage contains the runtime environment rather than all build-time tools.

For native Python packages, ensure the runtime image includes the required shared libraries.

# 6. Docker Compose

## 6.1 What is Docker Compose?

Docker Compose is a tool for defining and running multi-container Docker applications.

A typical Django project may need:

- Django application.
- PostgreSQL database.
- Redis.
- Celery worker.

Instead of starting each container separately, Docker Compose manages them through one YAML configuration.

Architecture:

```text
              Docker Compose
                    |
          +---------+---------+
          |         |         |
          v         v         v
        Django   PostgreSQL  Redis
          |
          v
        Celery
        Worker
```

## 6.2 docker-compose.yml

Example:

```yaml
services:

  web:
    build: .
    command: gunicorn config.wsgi:application --bind 0.0.0.0:8000
    ports:
      - "8000:8000"
    env_file:
      - .env
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_healthy

  db:
    image: postgres:16
    environment:
      POSTGRES_DB: ecommerce
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: postgres
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres -d ecommerce"]
      interval: 10s
      timeout: 5s
      retries: 5

  redis:
    image: redis:7
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 5s
      retries: 5

volumes:
  postgres_data:
```

This is a local example, not a production-ready secrets or database deployment configuration.

## 6.3 Start containers

```bash
docker compose up --build
```

Run in background:

```bash
docker compose up -d
```

Check running containers:

```bash
docker compose ps
```

View logs:

```bash
docker compose logs -f web
```

Stop containers:

```bash
docker compose down
```

## 6.4 Docker vs Docker Compose

| Docker | Docker Compose |
|---|---|
| Builds and runs containers | Defines multi-container applications |
| Uses Dockerfile | Uses Compose YAML |
| Manages individual containers | Manages multiple related services |
| Example: `docker run` | Example: `docker compose up` |

**Important:** Docker Compose is commonly used for local development and smaller deployments. ECS, Kubernetes, or another orchestrator is usually more appropriate for larger production deployments.

# 7. Static Files and Media Files

This is a very important Django interview topic.

## 7.1 What are static files?

Static files are application assets.

Examples:

- CSS
- JavaScript
- Logos
- Fonts
- Admin interface assets

Example:

```text
static/
   |
   +-- css/
   |     +-- style.css
   |
   +-- js/
   |     +-- app.js
   |
   +-- images/
         +-- logo.png
```

## 7.2 What are media files?

Media files are uploaded by users.

Examples:

- Profile pictures.
- Product images.
- Documents.
- Videos.
- Invoices.

Example:

```text
media/
   |
   +-- profiles/
   |     +-- user1.png
   |
   +-- products/
         +-- product1.jpg
```

## 7.3 Static vs Media

| Static files | Media files |
|---|---|
| Created by developers or included in packages | Uploaded or generated by users |
| CSS, JS, fonts, logos | Images, documents, videos |
| Collected using collectstatic | Stored through Django storage |
| Often served through CDN or web server | Often stored in S3 |
| Usually deployed with application assets | Managed independently of application deployments |

## 7.4 Configure Django static files

In settings:

```python
STATIC_URL = "/static/"

STATIC_ROOT = BASE_DIR / "staticfiles"
```

Collect static files:

```bash
python manage.py collectstatic --noinput
```

This collects static files into `STATIC_ROOT`.

In production, serve them through Nginx, S3/CDN, or an appropriate static-file storage service.

## 7.5 Configure media files

```python
MEDIA_URL = "/media/"

MEDIA_ROOT = BASE_DIR / "media"
```

For development only, Django can serve media files through URL configuration:

```python
from django.conf import settings
from django.conf.urls.static import static

urlpatterns = [
    # API URLs
]

if settings.DEBUG:
    urlpatterns += static(
        settings.MEDIA_URL,
        document_root=settings.MEDIA_ROOT
    )
```

Do not use this as the production media-serving strategy.

## 7.6 Production storage architecture

A common architecture:

```text
Django Application
       |
       +----> Static Files
       |          |
       |          v
       |       S3 / CDN
       |
       +----> Media Files
                  |
                  v
                 S3
```

S3 is particularly useful when multiple application containers need to access the same uploaded files.

# 8. Production Database Configuration

## 8.1 Development database

Developers commonly use SQLite locally.

Example:

```python
DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.sqlite3",
        "NAME": BASE_DIR / "db.sqlite3",
    }
}
```

## 8.2 Production database

For production, PostgreSQL is a common choice.

You may use:

- Amazon RDS PostgreSQL.
- Amazon Aurora PostgreSQL.
- Managed PostgreSQL from another provider.

Example:

```python
import os

DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.postgresql",
        "NAME": os.environ["DB_NAME"],
        "USER": os.environ["DB_USER"],
        "PASSWORD": os.environ["DB_PASSWORD"],
        "HOST": os.environ["DB_HOST"],
        "PORT": os.getenv("DB_PORT", "5432"),
        "CONN_MAX_AGE": 60,
    }
}
```

## 8.3 What is CONN_MAX_AGE?

`CONN_MAX_AGE` controls the lifetime of persistent database connections in Django.

Example:

```python
"CONN_MAX_AGE": 60
```

Django can reuse a database connection rather than creating a new connection for every request.

This can reduce connection setup overhead.

However, connection capacity must be considered when running many application workers.

## 8.4 Database connection management

Suppose:

```text
ECS Task 1
   |
   +-- Gunicorn Worker 1
   +-- Gunicorn Worker 2
   +-- Gunicorn Worker 3

ECS Task 2
   |
   +-- Gunicorn Worker 1
   +-- Gunicorn Worker 2
   +-- Gunicorn Worker 3
```

Multiple workers may open database connections.

You need to consider:

- Number of application replicas.
- Number of workers per replica.
- Maximum database connections.
- Connection pooling.
- Persistent connection configuration.

For larger deployments, consider RDS Proxy or an appropriate PostgreSQL connection pooler.

## 8.5 Production database best practices

1. Use private database networking.
2. Enable encryption.
3. Use strong credentials.
4. Enable automated backups.
5. Monitor connection count.
6. Monitor slow queries.
7. Use database indexes appropriately.
8. Run migrations through controlled deployment steps.
9. Use least-privilege database users.
10. Test database recovery procedures.

# 9. Environment Variables

## 9.1 What are environment variables?

Environment variables are configuration values provided to an application from outside its source code.

They allow the same application code to run in different environments.

Example:

Development:

```text
DEBUG=True
DB_HOST=localhost
```

Production:

```text
DEBUG=False
DB_HOST=production-db.example.internal
```

The application code remains the same.

## 9.2 Why do we use environment variables?

Without environment variables:

```python
SECRET_KEY = "my-secret-key"

DB_PASSWORD = "password123"
```

This creates security and maintenance problems.

Instead:

```python
import os

SECRET_KEY = os.environ["DJANGO_SECRET_KEY"]

DEBUG = os.getenv("DEBUG", "False").lower() == "true"
```

## 9.3 Example .env file

```env
DEBUG=True

DJANGO_SECRET_KEY=local-development-secret

DB_NAME=ecommerce

DB_USER=postgres

DB_PASSWORD=postgres

DB_HOST=localhost

DB_PORT=5432
```

Install python-decouple if you want to use its configuration interface:

```bash
pip install python-decouple
```

Example:

```python
from decouple import config

DEBUG = config("DEBUG", default=False, cast=bool)

SECRET_KEY = config("DJANGO_SECRET_KEY")

DB_PASSWORD = config("DB_PASSWORD")
```

## 9.4 Environment variables in Docker Compose

```yaml
services:
  web:
    build: .
    env_file:
      - .env
```

## 9.5 Environment variables in AWS ECS

ECS task definitions can provide environment variables directly or reference values from Secrets Manager and Systems Manager Parameter Store.

For production, avoid putting sensitive credentials directly in the plaintext `environment` section of a task definition.

# 10. Secrets Management

## 10.1 What are secrets?

Secrets are sensitive values used by applications.

Examples:

- Django SECRET_KEY.
- Database passwords.
- API tokens.
- Payment gateway credentials.
- AWS access keys.
- Redis credentials.

## 10.2 Why should secrets not be stored in Git?

Imagine committing:

```python
SECRET_KEY = "super-secret-key"
```

Anyone who can access the repository may obtain the secret.

If the repository is public, the secret can be exposed.

Even in private repositories, secrets should not be treated as safe source-code configuration.

## 10.3 AWS Secrets Manager

AWS Secrets Manager is used to store and manage secrets securely.

Example secret:

```json
{
  "DJANGO_SECRET_KEY": "example-secret",
  "DB_PASSWORD": "example-password",
  "PAYMENT_API_KEY": "example-token"
}
```

Django can retrieve secrets through its runtime environment or through an AWS SDK integration.

A common ECS approach is:

1. Create a secret in Secrets Manager.
2. Grant the ECS task execution role permission to retrieve it.
3. Reference the secret in the ECS task definition.
4. Provide the secret to the container as an environment variable.
5. Read the variable in Django.

Example task definition fragment:

```json
{
  "secrets": [
    {
      "name": "DB_PASSWORD",
      "valueFrom": "arn:aws:secretsmanager:REGION:ACCOUNT_ID:secret:django-db-password"
    }
  ]
}
```

The actual ARN and IAM permissions must match your AWS configuration.

## 10.4 Secrets Manager vs Parameter Store

| Secrets Manager | Systems Manager Parameter Store |
|---|---|
| Designed for secrets management | General configuration and parameter management |
| Supports secret rotation integrations | Supports parameter versioning |
| Secret-management features | Standard and advanced parameter tiers |
| Additional service cost may apply | Standard parameters have different pricing characteristics |

Use the service that best fits your rotation, access-control, operational, and cost requirements.

## 10.5 Production best practices

- Never hardcode secrets.
- Never commit `.env` files.
- Use IAM roles.
- Restrict secret access.
- Rotate credentials where appropriate.
- Avoid printing secrets in logs.
- Use different credentials for development and production.

# 11. HTTPS and TLS

## 11.1 What is HTTP?

HTTP is the protocol used for communication between clients and servers.

Example:

```text
http://example.com
```

Data is not encrypted by HTTP itself.

## 11.2 What is HTTPS?

HTTPS is HTTP secured using TLS.

Example:

```text
https://example.com
```

TLS protects data in transit.

It provides:

- Encryption.
- Integrity protection.
- Server authentication through certificates.

## 11.3 HTTPS architecture with Nginx

```text
             Browser
                |
                |
             HTTPS
                |
                v
              Nginx
                |
                |
              HTTP
                |
                v
             Gunicorn
                |
                v
              Django
```

Nginx terminates TLS and forwards the request to Django.

In a cloud deployment, an ALB can also terminate TLS.

## 11.4 Configure Django security settings

```python
DEBUG = False

SECURE_SSL_REDIRECT = True

SESSION_COOKIE_SECURE = True

CSRF_COOKIE_SECURE = True

SECURE_HSTS_SECONDS = 31536000
```

Only enable HSTS after confirming that HTTPS is correctly configured for the domain and its relevant subdomains.

Also configure:

```python
SECURE_PROXY_SSL_HEADER = (
    "HTTP_X_FORWARDED_PROTO",
    "https",
)
```

Only trust forwarded headers from trusted proxy infrastructure.

## 11.5 TLS certificate management

You can use:

- Let's Encrypt with Certbot for supported Nginx deployments.
- AWS Certificate Manager for AWS load balancers and supported integrations.

Example Nginx HTTPS configuration:

```nginx
server {
    listen 443 ssl;

    server_name example.com;

    ssl_certificate /etc/letsencrypt/live/example.com/fullchain.pem;

    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:8000;

        proxy_set_header Host $host;

        proxy_set_header X-Forwarded-Proto $scheme;
```

# 13. Health Check Endpoints

## 13.1 What is a health check?

A health check is an endpoint that reports whether an application is functioning.

Load balancers and orchestration platforms use health checks to decide whether an application instance should receive traffic.

Example:

```text
ALB
 |
 +-- Django Task 1: Healthy
 |
 +-- Django Task 2: Unhealthy
 |
 +-- Django Task 3: Healthy
```

The load balancer can stop routing new requests to an unhealthy target.

## 13.2 Create a Django health endpoint

```python
from django.http import JsonResponse

def health_check(request):
    return JsonResponse({
        "status": "healthy"
    })
```

URL:

```python
from django.urls import path

urlpatterns = [
    path("health/", health_check),
]
```

Response:

```json
{
  "status": "healthy"
}
```

## 13.3 Liveness vs Readiness

These are two important concepts.

### Liveness check

Checks whether the application process is alive and functioning.

Example:

```text
GET /health/live/
```

### Readiness check

Checks whether the application is ready to receive traffic.

Example:

```text
GET /health/ready/
```

A readiness check might verify essential dependencies, such as database connectivity, depending on the application's architecture.

Avoid making liveness checks depend on external services: a temporary database outage should not necessarily cause every application process to restart.

## 13.4 Example endpoints

```python
from django.http import JsonResponse
from django.db import connection
from django.db.utils import DatabaseError

def liveness(request):
    return JsonResponse({"status": "alive"})

def readiness(request):
    try:
        with connection.cursor() as cursor:
            cursor.execute("SELECT 1")

        return JsonResponse({"status": "ready"})

    except DatabaseError:
        return JsonResponse(
            {"status": "not_ready"},
            status=503
        )
```

For production, consider caching dependency-check results or using short timeouts so that health checks do not overload the database.

# 15. Graceful Shutdown

## 15.1 What is graceful shutdown?

Graceful shutdown means stopping an application without abruptly interrupting active requests or background tasks.

Suppose we are deploying a new version.

Old containers must stop, but they may still be processing requests.

A graceful shutdown allows them to finish within a configured period.

## 15.2 Normal shutdown vs graceful shutdown

Normal abrupt shutdown:

```text
Application
    |
    v
Stop Immediately
    |
    v
Active Requests Interrupted
```

Graceful shutdown:

```text
Application
    |
    v
Stop Accepting New Work
    |
    v
Finish Active Requests
    |
    v
Close Connections
    |
    v
Exit
```

## 15.3 Gunicorn graceful shutdown

Gunicorn handles termination signals and can gracefully stop workers.

Relevant configuration:

```bash
gunicorn config.wsgi:application \
    --workers 3 \
    --timeout 60 \
    --graceful-timeout 30
```

The graceful timeout controls how long workers have to finish during graceful shutdown.

## 15.4 Docker considerations

Docker sends SIGTERM when stopping a container, then sends SIGKILL after its stop timeout.

Example:

```yaml
services:
  web:
    build: .
    stop_grace_period: 40s
```

The application server should handle termination signals correctly.

## 15.5 ECS considerations

ECS deployments may stop old tasks after new tasks are running.

Configure:

- Load balancer health checks.
- ECS deployment health settings.
- Appropriate container stop timeout.
- Application server graceful shutdown.
- ALB deregistration delay.

For background workers, stop consuming new jobs and finish or safely release in-progress jobs.

## 16.1 What is a worker?

A worker is a process that handles requests or background jobs.

Django production applications may have:

- Gunicorn web workers.

- Celery workers.
- Scheduled task workers.

## 16.2 Gunicorn worker architecture

```text
             Gunicorn Master
                    |
         +----------+----------+
         |          |          |
         v          v          v
      Worker 1   Worker 2   Worker 3
         |          |          |
         +----------+----------+
                    |
                    v

```

The Gunicorn master process manages the worker processes.

## 16.3 Celery workers

Celery workers execute background tasks.

```text

    |

    |
    v
Celery Worker
    |
    v
Send Email
```


For an EC2 deployment, systemd can manage Gunicorn.

Example:

```ini

Description=Gunicorn Django
After=network.target

[Service]
User=ubuntu
Group=www-data
WorkingDirectory=/home/ubuntu/project
ExecStart=/home/ubuntu/project/.venv/bin/gunicorn \
```

## 16.5 Process management in containers

In Docker and ECS, the container's main process should be the application server or a proper process supervisor.

A common pattern is:

```text

```

This allows each workload to scale independently.

# 19. Database Migration Strategies

## 19.1 What are Django migrations?

Migrations are Django's way of managing database schema changes.

Suppose we create a model:

```python
class Product(models.Model):

    name = models.CharField(max_length=200)

    price = models.DecimalField(
        max_digits=10,
        decimal_places=2
    )
```

Create migration:

```bash
python manage.py makemigrations
```

Apply migration:

```bash
python manage.py migrate
```

Django generates migration files that describe schema changes.

## 19.2 Why are migrations important in production?

Suppose your application has thousands of users.

You add a new field to the Product model.

You must update the database schema without breaking the existing application.

This requires a controlled migration strategy.

## 19.3 Safe migration example

Suppose we want to add a new field:

```python
class Product(models.Model):

    name = models.CharField(max_length=200)

    description = models.TextField(
        null=True,
        blank=True
    )
```

Generate migration:

```bash
python manage.py makemigrations
```

Apply migration:

```bash
python manage.py migrate
```

Adding a nullable field is often easier to deploy safely than adding a non-null field requiring an immediate default across existing records.

The actual impact depends on the database, table size, and migration operation.

## 19.4 Expand and contract migration strategy

This is a very important production concept.

Suppose we want to rename a database field.

Instead of immediately renaming it while old application instances are running, use an expand-and-contract approach.

### Phase 1: Expand

Add the new column while keeping the old column.

```text
Database
  |
  +-- old_name
  |
  +-- new_name
```

### Phase 2: Deploy compatible code

Update the application so it can read and write both fields where necessary.

### Phase 3: Backfill

Copy existing data from the old field into the new field.

### Phase 4: Switch reads

Change the application to use the new field.

### Phase 5: Contract

After all old application versions are gone and the new field is fully in use, remove the old field.

This strategy reduces deployment risks when old and new application versions overlap.

## 19.5 Running migrations in Docker

```bash
docker compose exec web python manage.py migrate
```

For ECS, use a one-off task using the same image and production configuration.

Do not let every Django replica independently execute migrations when it starts.

## 19.6 Migration best practices

- Review generated migrations.
- Test migrations against realistic data volumes.
- Back up important production data.
- Avoid long-running table locks.
- Use backward-compatible schema changes.
- Separate schema changes from large data backfills.
- Run migrations in a controlled deployment stage.
- Have a recovery plan.
- Do not assume application rollback automatically reverses database changes.

# 20. Production Troubleshooting

This is one of the most practical topics for a Django developer.

Let's examine common production issues.

## Scenario 1: Django application is not starting

Possible causes:

- Missing dependencies.
- Incorrect environment variables.
- Wrong WSGI or ASGI module.
- Database connection failure.
- Python import error.

Check logs:

```bash
sudo journalctl -u gunicorn -f
```

For Docker:

```bash
docker logs -f container_name
```

For ECS:

Check the task logs in CloudWatch.

## Scenario 2: 502 Bad Gateway

A 502 error often means Nginx could not get a valid response from the upstream application server.

Possible causes:

- Gunicorn is not running.
- Incorrect proxy address.
- Wrong port.
- Application crashed.
- Network connection refused.

Check:

```bash
sudo systemctl status gunicorn
```

Check Nginx logs:

```bash
sudo tail -f /var/log/nginx/error.log
```

Check whether Gunicorn is listening:

```bash
sudo ss -ltnp
```

## Scenario 3: 504 Gateway Timeout

A 504 means the proxy or gateway did not receive a response within its timeout.

Possible causes:

- Slow database query.
- External API taking too long.
- Gunicorn worker blocked.
- Insufficient worker capacity.
- Long-running application code.

Troubleshooting:

1. Check application logs.
2. Inspect slow database queries.
3. Check worker utilization.
4. Check external API latency.
5. Review timeout settings.
6. Optimize the slow operation.

Do not simply increase timeouts without identifying the bottleneck.

## Scenario 4: Database connection error

Possible causes:

- Incorrect DB credentials.
- Incorrect hostname.
- Database unavailable.
- Security group blocks port 5432.
- Database connection limit reached.

Check:

```bash
python manage.py check --database default
```

This performs Django system checks for the database configuration; it is not a full replacement for testing real connectivity.

## Scenario 5: Static files are not loading

Possible causes:

- `collectstatic` was not executed.
- Incorrect `STATIC_ROOT`.
- Nginx alias path is wrong.
- S3 permissions are incorrect.
- CDN cache contains stale content.

Check:

```bash
python manage.py collectstatic --noinput
```

Verify that Nginx or the configured storage backend points to the correct location.

## Scenario 6: Media upload failure

Possible causes:

- S3 IAM permission problem.
- Bucket name is incorrect.
- Incorrect region.
- Invalid upload configuration.
- Object-size restrictions.
- Missing multipart parser configuration.

Check:

- Django logs.
- S3 bucket configuration.
- IAM permissions.
- Network connectivity.
- Upload request content type.

## Scenario 7: High CPU usage

Possible causes:

- Too many worker processes.
- Inefficient Python code.
- High request volume.
- CPU-intensive serialization.
- Expensive database operations.

Use CloudWatch or another monitoring system to investigate.

## Scenario 8: High memory usage

Possible causes:

- Too many workers.
- Memory leaks.
- Large query results.
- Large file uploads.
- Excessive caching.

Possible solutions:

- Reduce worker count.
- Paginate large querysets.
- Stream large files.
- Profile memory.
- Set worker recycling limits where appropriate.

## Scenario 9: Application works locally but fails in production

Possible causes:

- Missing environment variables.
- Different Python versions.
- Different package versions.
- Incorrect `ALLOWED_HOSTS`.
- Database differences.
- Missing static files.
- Permissions issues.
- Incorrect network configuration.

Compare development and production configuration, dependency versions, and infrastructure.

## Scenario 10: Deployment succeeds but users still see old code

Possible causes:

- Old containers are still running.
- Image tag was reused.
- ECS service did not update to the intended image.
- CDN or browser cache contains old assets.
- Deployment has not completed.

Best practice:

Use immutable Docker image tags, such as a Git commit SHA.

```text
django-api:a81b23f
```

This makes it easier to identify exactly which application version is deployed.

# 23. Django Development vs Production Interview Questions

### Q1. What is the difference between development and production?

Development is used for coding and debugging, whereas production is the environment where real users access the application.

Production requires secure configuration, scalable servers, proper logging, monitoring, backups, and reliable deployment processes.

### Q2. Why should we not use runserver in production?

Django's development server is intended for development and does not provide the production server capabilities and operational characteristics expected for public deployments.

We use Gunicorn or Uvicorn instead.

### Q3. What is WSGI?

WSGI is the standard interface between synchronous Python web applications and web servers.

### Q4. What is ASGI?

ASGI is an interface supporting synchronous and asynchronous Python applications, including long-lived connections such as WebSockets.

### Q5. What is the difference between Gunicorn and Uvicorn?

Gunicorn is commonly used as a WSGI server and process manager.

Uvicorn is an ASGI server used for asynchronous applications.

### Q6. Can Django use both WSGI and ASGI?

Yes. Django provides both WSGI and ASGI entry points.

### Q7. What is Nginx?

Nginx is a web server and reverse proxy that can handle incoming traffic and forward requests to application servers.

### Q8. What is a reverse proxy?

A reverse proxy receives client requests and forwards them to backend servers.

### Q9. Why do we use Nginx with Gunicorn?

Nginx handles incoming connections, TLS termination when configured, static files, and proxying. Gunicorn runs the Django application.

### Q10. What is Dockerising Django?

It means packaging the Django application and its runtime dependencies into a Docker image so that it can run consistently across environments.

### Q11. What is Docker Compose?

Docker Compose is used to define and manage multiple related containers using a YAML configuration file.

### Q12. What is the difference between static files and media files?

Static files are application assets such as CSS and JavaScript.

Media files are uploaded or generated files such as images and documents.

### Q13. What is collectstatic?

`collectstatic` gathers static files from configured locations into `STATIC_ROOT` so they can be served by production infrastructure.

### Q14. Why do we use PostgreSQL in production?

PostgreSQL provides a robust relational database with transactions, indexing, constraints, and advanced query capabilities.

### Q15. What are environment variables?

Environment variables are external configuration values used by an application without hardcoding environment-specific settings in source code.

### Q16. What is secrets management?

It is the secure storage, access, distribution, and rotation of sensitive information such as database passwords and API keys.

### Q17. What is HTTPS?

HTTPS is HTTP secured using TLS, which provides encryption and integrity protection for data in transit.

### Q18. What is production logging?

Production logging records application and infrastructure events to help diagnose errors and understand application behavior.

### Q19. What is a health check endpoint?

A health check endpoint reports application health so infrastructure can decide whether a service is healthy and ready to receive traffic.

### Q20. What is the difference between liveness and readiness?

Liveness determines whether the application process is alive.

Readiness determines whether it is ready to receive traffic.

### Q21. What is monitoring?

Monitoring continuously observes metrics, logs, traces, and infrastructure health.

### Q22. What is graceful shutdown?

Graceful shutdown stops accepting new work, allows active requests or tasks to finish within a configured period, closes resources, and then exits.

### Q23. What are Gunicorn workers?

Gunicorn workers are separate processes that handle application requests.

### Q24. What is Celery?

Celery is a distributed task queue used to execute background tasks asynchronously.

### Q25. What is CI/CD?

CI/CD automates code validation, testing, building, and deployment.

### Q26. What is GitLab CI/CD?

It is GitLab's integrated pipeline automation platform, configured primarily through `.gitlab-ci.yml`.

### Q27. What are Django migrations?

Migrations are files that describe database schema changes and allow those changes to be applied consistently.

### Q28. How do you safely deploy database changes?

I use backward-compatible changes, expand-and-contract migrations, controlled migration jobs, and testing against realistic data.

### Q29. What is a 502 Bad Gateway?

It generally indicates that a gateway or proxy could not obtain a valid response from its upstream server.

### Q30. What is a 504 Gateway Timeout?

It indicates that a gateway or proxy did not receive a response within the configured timeout.

### Q31. How do you troubleshoot a Django application that works locally but fails in production?

I check environment variables, package versions, application logs, database connectivity, networking, permissions, static-file configuration, and production security settings.

### Q32. How do you manage Gunicorn in production?

I configure the number of workers, timeouts, graceful shutdown, logging, and process supervision through systemd or a container orchestrator.

### Q33. Why should we use immutable Docker image tags?

They identify the exact image version and prevent ambiguity caused by repeatedly overwriting tags such as `latest`.

### Q34. What is zero-downtime deployment?

It is a deployment strategy that replaces application versions while maintaining service availability through health checks, rolling or blue/green deployment, and compatible database changes.

### Q35. How do you handle database migrations in CI/CD?

I execute migrations in a controlled deployment stage, usually using a one-off task, before or during rollout as appropriate. I ensure schema changes remain compatible with currently running application versions.
