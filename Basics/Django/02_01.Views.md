# Django REST Framework – ViewSets Complete Guide

# 1. What are ViewSets?

Before understanding ViewSets, let's remember what we learned about APIView and Generic Views.

Suppose we want to create an Employee CRUD API.

We need the following operations:

| HTTP method | Operation | Endpoint |
|---|---|---|
| GET | Get all employees | `/employees/` |
| POST | Create an employee | `/employees/` |
| GET | Get one employee | `/employees/1/` |
| PUT | Update an employee | `/employees/1/` |
| PATCH | Partially update an employee | `/employees/1/` |
| DELETE | Delete an employee | `/employees/1/` |

Using Concrete Generic Views, we normally create two classes.

### Collection view

```python
class EmployeeListCreateView(ListCreateAPIView):

    queryset = Employee.objects.all()
    serializer_class = EmployeeSerializer
```

### Detail view

```python
class EmployeeDetailView(
    RetrieveUpdateDestroyAPIView
):

    queryset = Employee.objects.all()
    serializer_class = EmployeeSerializer
```

We then connect both classes to URLs.

This works perfectly.

However, notice something:

We have two different classes for the same Employee resource.

What if we could manage all these operations inside one class?

That is where ViewSets come in.

## 1.1 Definition of ViewSet

A ViewSet is a DRF class that groups related API operations into a single class.

Instead of writing separate `get()`, `post()`, `put()`, `patch()` and `delete()` methods, we define actions such as:

- `list()`
- `create()`
- `retrieve()`
- `update()`
- `partial_update()`
- `destroy()`

DRF and its Router connect HTTP requests to these actions.

For example:

| HTTP method | ViewSet action |
|---|---|
| GET `/employees/` | `list()` |
| POST `/employees/` | `create()` |
| GET `/employees/1/` | `retrieve()` |
| PUT `/employees/1/` | `update()` |
| PATCH `/employees/1/` | `partial_update()` |
| DELETE `/employees/1/` | `destroy()` |

The important difference:

In APIView, you write HTTP handlers such as `get()` and `post()`.

In ViewSets, you generally work with actions such as `list()` and `create()`.

# 3. ModelViewSet

## 3.1 What is ModelViewSet?

`ModelViewSet` is a ready-made ViewSet that provides all the standard CRUD operations for a model.

It combines the functionality of:

- `GenericAPIView`
- `ListModelMixin`
- `CreateModelMixin`
- `RetrieveModelMixin`
- `UpdateModelMixin`
- `DestroyModelMixin`

Therefore, it supports all five CRUD operations.

### The methods provided by ModelViewSet

| Method | Purpose | HTTP method |
|---|---|---|
| `list()` | Get all employees | GET |
| `create()` | Create an employee | POST |
| `retrieve()` | Get one employee | GET |
| `update()` | Fully update an employee | PUT |
| `partial_update()` | Partially update an employee | PATCH |
| `destroy()` | Delete an employee | DELETE |

## 3.2 Creating a ModelViewSet

### views.py

```python
from rest_framework.viewsets import ModelViewSet

from .models import Employee
from .serializers import EmployeeSerializer


class EmployeeViewSet(ModelViewSet):

    queryset = Employee.objects.all()

    serializer_class = EmployeeSerializer
```

That's it!

We have created a complete Employee CRUD API.

Notice something important:

We did not write:

```python
def get(self, request):
    pass

def post(self, request):
    pass

def put(self, request):
    pass

def patch(self, request):
    pass

def delete(self, request):
    pass
```

We also did not manually write:

```python
def list(self):
    pass

def create(self):
    pass
```

Why?

Because `ModelViewSet` already provides the standard CRUD actions.

## 3.4 Understanding how ModelViewSet works internally

Conceptually, `ModelViewSet` is structured like this:

```python
class ModelViewSet(
    CreateModelMixin,
    RetrieveModelMixin,
    UpdateModelMixin,
    DestroyModelMixin,
    ListModelMixin,
    GenericViewSet
):
    pass
```

This is a simplified representation of its inheritance.

The important point is:

`ModelViewSet` combines all five CRUD Mixins with `GenericViewSet`.

`GenericViewSet` itself provides the GenericAPIView functionality.

Therefore:

```text
ModelViewSet
    |
    |-- GenericViewSet
    |      |
    |      |-- GenericAPIView
    |              |
    |              |-- APIView
    |
    |-- ListModelMixin
    |-- CreateModelMixin
    |-- RetrieveModelMixin
    |-- UpdateModelMixin
    |-- DestroyModelMixin
```

This is why ModelViewSet provides so much functionality with very little code.

# 4. Routers – How URLs are created automatically

Before moving to other ViewSets, we need to understand Routers.

When using normal Generic Views, we manually create URL patterns.

For example:

```python
urlpatterns = [
    path(
        "employees/",
        EmployeeListCreateView.as_view()
    ),

    path(
        "employees/<int:pk>/",
        EmployeeDetailView.as_view()
    )
]
```

With ViewSets, DRF provides Routers.

A Router automatically generates URL patterns for ViewSets.

## 4.1 Using DefaultRouter

### urls.py

```python
from rest_framework.routers import DefaultRouter

from .views import EmployeeViewSet

router = DefaultRouter()

router.register(
    "employees",
    EmployeeViewSet,
    basename="employee"
)

urlpatterns = router.urls
```

Let's understand each line.

### Import DefaultRouter

```python
from rest_framework.routers import DefaultRouter
```

This imports DRF's router.

### Create a router

```python
router = DefaultRouter()
```

Creates a router instance.

### Register a ViewSet

```python
router.register(
    "employees",
    EmployeeViewSet,
    basename="employee"
)
```

There are three arguments.

**First:**

```python
"employees"
```

This is the URL prefix.

**Second:**

```python
EmployeeViewSet
```

This is the ViewSet class that should handle the URLs.

**Third:**

```python
basename="employee"
```

This provides the base name for automatically generated URL names.

### Add generated URLs

```python
urlpatterns = router.urls
```

This includes the generated URL patterns in your application.

In a larger Django project, you can also include them in the project URL configuration:

```python
urlpatterns = [
    path("api/", include("employees.urls"))
]
```

## 4.2 What URLs does DefaultRouter generate?

For our EmployeeViewSet:

| HTTP method | URL | Action |
|---|---|---|
| GET | `/employees/` | `list()` |
| POST | `/employees/` | `create()` |
| GET | `/employees/{pk}/` | `retrieve()` |
| PUT | `/employees/{pk}/` | `update()` |
| PATCH | `/employees/{pk}/` | `partial_update()` |
| DELETE | `/employees/{pk}/` | `destroy()` |

The Router connects these HTTP methods to the correct actions.

You don't manually write separate URL patterns for each CRUD operation.

## 4.3 DefaultRouter vs SimpleRouter

DRF provides two commonly used routers.

| Feature | DefaultRouter | SimpleRouter |
|---|---|---|
| Automatic CRUD URLs | Yes | Yes |
| Custom action URLs | Yes | Yes |
| API root endpoint | Yes | No |
| Automatically generated format suffix patterns | Yes | No |

Example:

```python
from rest_framework.routers import SimpleRouter

router = SimpleRouter()

router.register(
    "employees",
    EmployeeViewSet,
    basename="employee"
)
```

Both routers generate the standard ViewSet routes.

# 5. ReadOnlyModelViewSet

## 5.1 What is ReadOnlyModelViewSet?

`ReadOnlyModelViewSet` provides only read operations.

It allows users to retrieve data but not create, update or delete records through the standard actions.

It provides two main actions:

| Action | HTTP method | Purpose |
|---|---|---|
| `list()` | GET | Get all records |
| `retrieve()` | GET | Get one record |

It does not provide:

- `create()`
- `update()`
- `partial_update()`
- `destroy()`

## 5.2 Example

Imagine you are building a public employee directory.

Visitors should be able to see employee details, but they should not be able to modify the records.

### views.py

```python
from rest_framework.viewsets import ReadOnlyModelViewSet

class EmployeeReadOnlyViewSet(ReadOnlyModelViewSet):

    queryset = Employee.objects.all()

    serializer_class = EmployeeSerializer
```

## 5.3 Register it with a Router

```python
router.register(
    "employees",
    EmployeeReadOnlyViewSet,
    basename="employee"
)
```

## 5.4 Supported requests

### GET all employees

```http
GET /employees/
```

Output:

```json
[
    {
        "id": 1,
        "name": "John",
        "age": 25,
        "department": "IT",
        "is_active": true
    },
    {
        "id": 2,
        "name": "Sarah",
        "age": 30,
        "department": "HR",
        "is_active": true
    }
]
```

### GET one employee

```http
GET /employees/1/
```

Output:

```json
{
    "id": 1,
    "name": "John",
    "age": 25,
    "department": "IT",
    "is_active": true
}
```

### What happens if someone tries POST?

```http
POST /employees/
```

The standard POST action is not available.

DRF normally returns:

`405 Method Not Allowed`

The same applies to standard PUT, PATCH and DELETE requests.

Important: ReadOnlyModelViewSet does not make the underlying database read-only. It only omits the standard write actions from this API endpoint.

# 6. Custom ViewSets

Now let's understand Custom ViewSets.

Sometimes ModelViewSet provides more functionality than you need.

Sometimes ReadOnlyModelViewSet provides too little functionality.

Sometimes you want to control exactly which actions your ViewSet supports.

DRF provides different levels of ViewSets.

## 6.1 ViewSet

Import:

```python
from rest_framework.viewsets import ViewSet
```

`ViewSet` is a base class for creating ViewSets.

It does not automatically provide:
- Queryset handling.
- Serializer handling.
- CRUD Mixins.
- Object lookup.

You implement the actions yourself.

Example:

```python
from rest_framework.viewsets import ViewSet
from rest_framework.response import Response

class EmployeeViewSet(ViewSet):

    def list(self, request):

        employees = Employee.objects.all()

        serializer = EmployeeSerializer(
            employees,
            many=True
        )

        return Response(serializer.data)

    def retrieve(self, request, pk=None):

        employee = get_object_or_404(
            Employee,
            pk=pk
        )

        serializer = EmployeeSerializer(employee)

        return Response(serializer.data)
```

This ViewSet supports listing and retrieving employees.

However, you write the queryset lookup and serialization logic yourself.

## 6.2 GenericViewSet

Import:

```python
from rest_framework.viewsets import GenericViewSet
```

`GenericViewSet` inherits from GenericAPIView.

Therefore, it provides:
- `get_queryset()`
- `get_serializer()`
- `get_serializer_class()`
- `get_object()`
- Filtering support.
- Pagination support.

However, it does not automatically provide CRUD actions.

You combine it with Mixins.

Example:

```python
from rest_framework import mixins
from rest_framework.viewsets import GenericViewSet

class EmployeeViewSet(
    mixins.ListModelMixin,
    mixins.RetrieveModelMixin,
    GenericViewSet
):

    queryset = Employee.objects.all()

    serializer_class = EmployeeSerializer
```

This provides:

- `list()`
- `retrieve()`

But it does not provide the standard create, update or delete actions.

When you register this ViewSet with a Router, DRF generates the routes corresponding to the available actions.

## 6.3 ViewSet vs GenericViewSet

| Feature | ViewSet | GenericViewSet |
|---|---|---|
| Base APIView functionality | Yes | Yes |
| Queryset helpers | No | Yes |
| Serializer helpers | No | Yes |
| Object lookup helpers | No | Yes |
| CRUD Mixins included automatically | No | No |
| Can combine Mixins | Yes, but usually less convenient | Yes |
| Requires Router for automatic action routing | Commonly used with one | Commonly used with one |

### When should you use ViewSet?

Use `ViewSet` when you want to define your own actions and manage the underlying logic yourself.

### When should you use GenericViewSet?

Use `GenericViewSet` when you want to build custom combinations of actions while retaining GenericAPIView functionality.

# 7. Custom Actions using @action

This is one of the most useful features of ViewSets.

Suppose we have an Employee API.

We already support:

- List employees.
- Create employees.
- Retrieve an employee.
- Update an employee.
- Delete an employee.

But now the business requirement changes.

We need an additional API:

**Get all active employees.**

Or:

**Activate an employee.**

Or:

**Get employees belonging to a particular department.**

These are custom operations that do not fit directly into the five standard CRUD actions.

DRF provides the `@action` decorator for this.

## 7.1 What is @action?

`@action` allows us to add custom endpoints to a ViewSet.

Import:

```python
from rest_framework.decorators import action
```

Example:

```python
class EmployeeViewSet(ModelViewSet):

    queryset = Employee.objects.all()

    serializer_class = EmployeeSerializer

    @action(
        detail=False,
        methods=["get"]
    )
    def active(self, request):

        employees = Employee.objects.filter(
            is_active=True
        )

        serializer = self.get_serializer(
            employees,
            many=True
        )

        return Response(serializer.data)
```

Let's understand every detail.

### A. @action

```python
@action(...)
```

This tells DRF that the method should become a custom API action.

Without the decorator, a method is not automatically registered as a custom Router endpoint.

### B. detail=False

```python
detail=False
```

This means the custom action operates on the collection of employees rather than one specific employee.

The generated URL is:

```http
GET /employees/active/
```

### C. methods=["get"]

```python
methods=["get"]
```

This specifies that the action accepts GET requests.

You can also specify multiple methods:

```python
methods=["get", "post"]
```

### D. def active()

```python
def active(self, request):
```

This is your custom action method.

You can give it any valid Python method name.

### E. self.get_serializer()

```python
serializer = self.get_serializer(
    employees,
    many=True
)
```

This uses the serializer configured for the ViewSet.

### F. return Response()

```python
return Response(serializer.data)
```

Returns the result to the API client.

## 7.2 Expected output

Request:

```http
GET /employees/active/
```

Output:

```json
[
    {
        "id": 1,
        "name": "John",
        "age": 25,
        "department": "IT",
        "is_active": true
    },
    {
        "id": 2,
        "name": "Sarah",
        "age": 30,
        "department": "HR",
        "is_active": true
    }
]
```

Only active employees are returned.

## 7.3 Understanding detail=True

Now suppose we want an endpoint to activate one employee.

We use:

```python
@action(
    detail=True,
    methods=["post"]
)
def activate(self, request, pk=None):

    employee = self.get_object()

    employee.is_active = True

    employee.save()

    serializer = self.get_serializer(employee)

    return Response(serializer.data)
```

Why `detail=True`?

Because this operation applies to one particular employee.

Generated URL:

```http
POST /employees/1/activate/
```

The `pk` identifies the employee.

Inside the method:

```python
employee = self.get_object()
```

DRF retrieves the employee identified by the URL.

Then:

```python
employee.is_active = True
employee.save()
```

Updates the employee.

### Expected output

```json
{
    "id": 1,
    "name": "John",
    "age": 25,
    "department": "IT",
    "is_active": true
}
```

## 7.4 detail=False vs detail=True

This is extremely important.

| Setting | Meaning | Example URL |
|---|---|---|
| `detail=False` | Action applies to a collection | `/employees/active/` |
| `detail=True` | Action applies to one object | `/employees/1/activate/` |

Remember:

- `detail=False`: No individual object lookup is implied.
- `detail=True`: DRF provides an object lookup route and you can use `self.get_object()`.

## 7.5 Custom URL path using url_path

By default, DRF uses the custom method name to generate the URL path.

Example:

```python
@action(
    detail=False,
    methods=["get"]
)
def active_employees(self, request):
    pass
```

Generated URL:

```http
GET /employees/active_employees/
```

But you can customize it:

```python
@action(
    detail=False,
    methods=["get"],
    url_path="active"
)
def active_employees(self, request):
    pass
```

Generated URL:

```http
GET /employees/active/
```

## 7.6 Custom URL name using url_name

You can also customize the generated URL name.

```python
@action(
    detail=False,
    methods=["get"],
    url_path="active",
    url_name="active-employees"
)
def active_employees(self, request):
    pass
```

This affects the URL name used for reverse URL lookup.

## 7.7 Custom action with a different serializer

Sometimes you want a custom serializer for a particular action.

Example:

```python
@action(
    detail=False,
    methods=["get"],
    serializer_class=EmployeeSummarySerializer
)
def summary(self, request):

    employees = self.get_queryset()

    serializer = self.get_serializer(
        employees,
        many=True
    )

    return Response(serializer.data)
```

This allows the summary action to use a different serializer from the standard CRUD actions.

You can also override `get_serializer_class()` for more complex serializer selection.

## 7.8 Custom action with POST

Example: Promote an employee.

```python
@action(
    detail=True,
    methods=["post"]
)
def promote(self, request, pk=None):

    employee = self.get_object()

    employee.department = "Management"

    employee.save()

    serializer = self.get_serializer(employee)

    return Response(serializer.data)
```

Request:

```http
POST /employees/1/promote/
```

Output:

```json
{
    "id": 1,
    "name": "John",
    "age": 25,
    "department": "Management",
    "is_active": true
}
```

Custom actions are useful for operations such as:
- Activate employee.
- Deactivate employee.
- Promote employee.
- Approve an order.
- Cancel an order.
- Reset a password.
- Generate a report.

Important: Custom actions should still have appropriate authentication, permission and validation rules.

# 8. Complete ModelViewSet example with Custom Actions

Now let's combine everything.

### views.py

```python
from rest_framework.viewsets import ModelViewSet

from rest_framework.decorators import action

from rest_framework.response import Response

from .models import Employee

from .serializers import EmployeeSerializer


class EmployeeViewSet(ModelViewSet):

    queryset = Employee.objects.all()

    serializer_class = EmployeeSerializer

    # Custom action 1:
    # Get all active employees

    @action(
        detail=False,
        methods=["get"]
    )
    def active(self, request):

        employees = self.get_queryset().filter(
            is_active=True
        )

        serializer = self.get_serializer(
            employees,
            many=True
        )

        return Response(serializer.data)

    # Custom action 2:
    # Activate one employee

    @action(
        detail=True,
        methods=["post"]
    )
    def activate(self, request, pk=None):

        employee = self.get_object()

        employee.is_active = True

        employee.save()

        serializer = self.get_serializer(employee)

        return Response(serializer.data)

    # Custom action 3:
    # Deactivate one employee

    @action(
        detail=True,
        methods=["post"]
    )
    def deactivate(self, request, pk=None):

        employee = self.get_object()

        employee.is_active = False

        employee.save()

        serializer = self.get_serializer(employee)

        return Response(serializer.data)
```

### urls.py

```python
from rest_framework.routers import DefaultRouter

from .views import EmployeeViewSet

router = DefaultRouter()

router.register(
    "employees",
    EmployeeViewSet,
    basename="employee"
)

urlpatterns = router.urls
```

### Generated endpoints

| HTTP method | URL | Action |
|---|---|---|
| GET | `/employees/` | List |
| POST | `/employees/` | Create |
| GET | `/employees/1/` | Retrieve |
| PUT | `/employees/1/` | Update |
| PATCH | `/employees/1/` | Partial update |
| DELETE | `/employees/1/` | Destroy |
| GET | `/employees/active/` | Custom active action |
| POST | `/employees/1/activate/` | Custom activate action |

With one ViewSet, we have created all these endpoints.

# 9. Choosing Between APIView, Generic Views and ViewSets

Now let's understand the most important practical question.

When should you use each approach?

## 9.1 APIView

APIView gives you maximum control over request handling.

Example:

```python
class EmployeeReportView(APIView):

    def get(self, request):

        total = Employee.objects.count()

        active = Employee.objects.filter(
            is_active=True
        ).count()

        inactive = Employee.objects.filter(
            is_active=False
        ).count()

        return Response({
            "total_employees": total,
            "active_employees": active,
            "inactive_employees": inactive
        })
```

Output:

```json
{
    "total_employees": 3,
    "active_employees": 2,
    "inactive_employees": 1
}
```

Why APIView?

Because this endpoint is a custom report rather than a standard CRUD operation.

## 9.2 Generic Views

Use Generic Views for normal CRUD operations when you want separate collection and detail endpoints.

Example:

```python
class EmployeeListCreateView(ListCreateAPIView):

    queryset = Employee.objects.all()

    serializer_class = EmployeeSerializer


class EmployeeDetailView(
    RetrieveUpdateDestroyAPIView
):

    queryset = Employee.objects.all()

    serializer_class = EmployeeSerializer
```

Why Generic Views?

Because DRF provides the standard CRUD logic and you only need to configure the queryset and serializer.

## 9.3 ViewSets

Use ViewSets when you want to group related resource operations into one class and use Routers to generate URLs.

Example:

```python
class EmployeeViewSet(ModelViewSet):

    queryset = Employee.objects.all()

    serializer_class = EmployeeSerializer
```

Why ViewSets?

Because you can manage the entire Employee resource in one class.

## 9.4 Comparison table

| Feature | APIView | Generic Views | ViewSets |
|---|---|---|---|
| Custom request logic | Excellent | Yes | Yes |
| Built-in CRUD functionality | No | Yes | Yes, depending on class |
| Queryset helpers | No | Yes | Yes in GenericViewSet-based classes |
| Serializer helpers | No | Yes | Yes in GenericViewSet-based classes |
| Automatic URL generation | No | No | Yes, using Routers |
| Custom actions | Write HTTP handlers | Write HTTP handlers or customize methods | `@action` |
| Number of classes for normal CRUD | Usually several | Usually two | Usually one ModelViewSet |
| Best for | Custom endpoints | Standard CRUD endpoints | Resource-oriented APIs |

# 12. Important difference: HTTP methods vs ViewSet actions

This is a very important concept.

In APIView:

```python
def get(self, request):
    pass
```

The method name represents the HTTP method.

In a ViewSet:

```python
def list(self, request):
    pass
```

The method name represents the action.

The Router maps HTTP methods to these actions.

Example:

```text
GET  /employees/     → list()
POST /employees/     → create()

GET    /employees/1/ → retrieve()
PUT    /employees/1/ → update()
PATCH  /employees/1/ → partial_update()
DELETE /employees/1/ → destroy()
```

This mapping is one of the most important things to understand about ViewSets.

# 13. Complete practical example: Employee Management API

Let's put everything together.

### models.py

```python
from django.db import models

class Employee(models.Model):

    name = models.CharField(max_length=100)

    age = models.IntegerField()

    department = models.CharField(max_length=100)

    is_active = models.BooleanField(default=True)
```

### serializers.py

```python
from rest_framework import serializers

from .models import Employee


class EmployeeSerializer(serializers.ModelSerializer):

    class Meta:

        model = Employee

        fields = "__all__"
```

### views.py

```python
from rest_framework.viewsets import ModelViewSet

from rest_framework.decorators import action

from rest_framework.response import Response

from .models import Employee

from .serializers import EmployeeSerializer


class EmployeeViewSet(ModelViewSet):

    queryset = Employee.objects.all()

    serializer_class = EmployeeSerializer

    def get_queryset(self):

        return Employee.objects.all().order_by("id")

    @action(
        detail=False,
        methods=["get"]
    )
    def active(self, request):

        employees = self.get_queryset().filter(
            is_active=True
        )

        serializer = self.get_serializer(
            employees,
            many=True
        )

        return Response(serializer.data)

    @action(
        detail=True,
        methods=["post"]
    )
    def activate(self, request, pk=None):

        employee = self.get_object()

        employee.is_active = True

        employee.save()

        serializer = self.get_serializer(employee)

        return Response(serializer.data)

    @action(
        detail=True,
        methods=["post"]
    )
    def deactivate(self, request, pk=None):

        employee = self.get_object()

        employee.is_active = False

        employee.save()

        serializer = self.get_serializer(employee)

        return Response(serializer.data)
```

### urls.py

```python
from django.urls import path, include

from rest_framework.routers import DefaultRouter

from .views import EmployeeViewSet


router = DefaultRouter()

router.register(
    "employees",
    EmployeeViewSet,
    basename="employee"
)


urlpatterns = [

    path(
        "",
        include(router.urls)
    )

]
```

### API endpoints

| HTTP method | URL | Function |
|---|---|---|
| GET | `/employees/` | List employees |
| POST | `/employees/` | Create employee |
| GET | `/employees/1/` | Retrieve employee |
| PUT | `/employees/1/` | Update employee |
| PATCH | `/employees/1/` | Partial update |
| DELETE | `/employees/1/` | Delete employee |
| GET | `/employees/active/` | Get active employees |
| POST | `/employees/1/activate/` | Activate employee |
| POST | `/employees/1/deactivate/` | Deactivate employee |

We created a complete API with standard CRUD operations and custom business operations.

# 14. Common mistakes to avoid

### Mistake 1: Using get() instead of list() in a ViewSet

Incorrect:

```python
class EmployeeViewSet(ModelViewSet):

    def get(self, request):
        pass
```

Correct:

```python
class EmployeeViewSet(ModelViewSet):

    def list(self, request, *args, **kwargs):
        return super().list(request, *args, **kwargs)
```

A ViewSet uses actions rather than the normal HTTP handler methods.

### Mistake 2: Forgetting the Router

A ViewSet does not automatically create URL patterns just because you define the class.

Register it with a Router or explicitly map actions using `.as_view()`.

### Mistake 3: Using detail=True for collection operations

Incorrect for listing all active employees:

```python
@action(detail=True, methods=["get"])
def active(self, request):
    pass
```

Correct:

```python
@action(detail=False, methods=["get"])
def active(self, request):
    pass
```

### Mistake 4: Using detail=False for a single-object operation

For activating one employee, use:

```python
@action(detail=True, methods=["post"])
def activate(self, request, pk=None):
    pass
```

### Mistake 5: Thinking ModelViewSet always needs custom actions

You don't need `@action` for standard CRUD operations.

ModelViewSet already provides them.

Use `@action` for additional business operations.

# 15. Final revision – Which ViewSet should you use?

| Requirement | Recommended class |
|---|---|
| Complete CRUD operations | `ModelViewSet` |
| Only GET operations | `ReadOnlyModelViewSet` |
| Completely custom actions without generic helpers | `ViewSet` |
| Custom CRUD combination with queryset and serializer helpers | `GenericViewSet` + Mixins |
| Additional business operation | `@action` on a suitable ViewSet |

## Final takeaway

Remember these five concepts:

1. **ModelViewSet:** Provides all standard CRUD actions.
2. **ReadOnlyModelViewSet:** Provides only list and retrieve.
3. **Custom ViewSets:** Let you define your own actions and choose which operations to support.
4. **@action:** Adds custom endpoints such as activate, deactivate, approve or cancel.
5. **Routers:** Automatically generate URL patterns and connect HTTP methods to ViewSet actions.

The most important distinction:

APIView uses HTTP handlers (`get`, `post`, `put`, etc.).

Generic Views use predefined CRUD handlers and mixins.

ViewSets group related operations into actions (`list`, `create`, `retrieve`, etc.) and Routers map URLs to those actions.

This is the foundation for understanding ViewSets in real Django REST Framework projects.
