# PART 6 — AUTHENTICATION IN DJANGO REST FRAMEWORK

# SECTION A — DRF AUTHENTICATION ARCHITECTURE

## 1. What is authentication?

Authentication is the process of verifying the identity of a user.

For example, when a user logs into an application using:

- Username and password
- Session cookie
- API token
- JWT access token

The application verifies the supplied credentials and identifies the user.

### Why do we need authentication?

Imagine an employee management API:

```text
GET    /api/employees/
POST   /api/employees/
GET    /api/profile/
DELETE /api/employees/5/
```

You might want:

- Logged-in employees to view employee records.
- Administrators to create employees.
- Each employee to view only their own profile.
- Only administrators to delete employees.

The API must know who is making each request before it can enforce these rules.

## 2. How authentication works in DRF

The general process is:

```text
Client
  |
  | HTTP Request + Credentials
  |
  v
Django REST Framework
  |
  v
Authentication Classes
  |
  v
Identify User
  |
  v
Set request.user and request.auth
  |
  v
Permission Classes
  |
  v
Check Access
  |
  v
API View
  |
  v
HTTP Response
```

### Step 1: Client sends credentials

For example, a client sends:

```http
GET /api/profile/
Authorization: Bearer eyJhbGciOi...
```

The token is the credential.

### Step 2: Authentication class checks credentials

DRF runs the configured authentication class.

For example:

```python
JWTAuthentication
```

It validates the JWT and identifies the user.

### Step 3: DRF sets request.user

```python
request.user
```

This represents the authenticated user.

### Step 4: DRF sets request.auth

```python
request.auth
```

This contains authentication information returned by the authentication class. Its value depends on the authentication method.

### Step 5: Permission classes check access

For example:

```python
permission_classes = [IsAuthenticated]
```

This checks whether the request has an authenticated user.

### Step 6: View executes

If permission is granted, DRF executes the view and returns the response.

# SECTION B — ALL MAIN BUILT-IN DRF AUTHENTICATION CLASSES

Authentication classes answer this question:

**Who is making this API request?**

DRF provides four main built-in authentication classes.

1. BasicAuthentication
2. SessionAuthentication
3. TokenAuthentication
4. RemoteUserAuthentication

JWT authentication is commonly used with DRF, but it is not included in DRF core. It is generally provided by the third-party Simple JWT package.

## 3. BasicAuthentication

### What is BasicAuthentication?

BasicAuthentication verifies a username and password sent in the HTTP Authorization header.

The client sends credentials using HTTP Basic authentication.

Example:

```http
Authorization: Basic am9objoxMjM0NQ==
```

The value after `Basic` is Base64-encoded username and password information.

It is encoding, NOT encryption.

### Why do we need it?

It provides a straightforward way for a client to authenticate using a username and password.

### How does it work?

1. Client sends username and password.
2. The credentials are Base64-decoded.
3. DRF checks the credentials against Django authentication.
4. If valid, the user is authenticated.
5. DRF sets `request.user`.

### Configuration

```python
REST_FRAMEWORK = {
    "DEFAULT_AUTHENTICATION_CLASSES": [
        "rest_framework.authentication.BasicAuthentication",
    ],
}
```

### Example view

```python
from rest_framework.views import APIView
from rest_framework.permissions import IsAuthenticated
from rest_framework.response import Response

class ProfileView(APIView):

    permission_classes = [IsAuthenticated]

    def get(self, request):
        return Response({
            "username": request.user.username,
            "message": "Authenticated successfully"
        })
```

### Request

```http
GET /api/profile/
Authorization: Basic am9objoxMjM0NQ==
```

### Possible response

```json
{
    "username": "john",
    "message": "Authenticated successfully"
}
```

### When should you use it?

- Simple development or testing.
- Trusted internal tools.
- Certain controlled server-to-server integrations.

### When should you avoid it?

- Public production APIs without HTTPS.
- Mobile applications where repeatedly sending passwords is undesirable.
- Applications needing revocable, short-lived credentials.

**Important:** Basic authentication must be used over HTTPS because the credentials are only Base64-encoded, not encrypted.

## 4. SessionAuthentication

### What is SessionAuthentication?

SessionAuthentication uses Django's existing login session to authenticate API requests.

It is commonly used when your frontend and backend are part of the same Django-based website.

### Why do we need it?

Suppose a user logs into a Django website.

Django creates a session and sends a session cookie to the browser.

The browser automatically sends that cookie with subsequent requests to the same site.

DRF can use that session to identify the user.

### How does it work?

1. User logs in through Django.
2. Django creates a session.
3. Browser receives a session cookie.
4. Browser sends the cookie with API requests.
5. DRF validates the session.
6. DRF identifies the logged-in user.

### Configuration

```python
REST_FRAMEWORK = {
    "DEFAULT_AUTHENTICATION_CLASSES": [
        "rest_framework.authentication.SessionAuthentication",
    ],
}
```

### Example login view

You can use Django's `login()` function:

```python
from django.contrib.auth import authenticate, login
from rest_framework.views import APIView
from rest_framework.response import Response
from rest_framework import status

class LoginView(APIView):

    authentication_classes = []
    permission_classes = []

    def post(self, request):

        username = request.data.get("username")
        password = request.data.get("password")

        user = authenticate(
            request,
            username=username,
            password=password
        )

        if user is None:
            return Response(
                {"error": "Invalid credentials"},
                status=status.HTTP_400_BAD_REQUEST
            )

        login(request, user)

        return Response({
            "message": "Login successful"
        })
```

### Example response

```json
{
    "message": "Login successful"
}
```

The browser receives a session cookie through Django's response.

### What is CSRF protection?

CSRF means Cross-Site Request Forgery.

It is an attack in which a malicious website attempts to make a user's browser perform an unwanted action using the user's existing authenticated session.

Because browsers automatically send cookies, session-authenticated unsafe requests need CSRF protection.

For example:

```http
POST /api/employees/
```

DRF's SessionAuthentication enforces CSRF validation for authenticated requests.

### When should you use it?

- Django templates.
- Same-site React or Vue frontends.
- Internal dashboards.
- Applications using Django's normal login and session system.

### When should you avoid it?

- When you need stateless authentication for mobile clients.
- When your architecture is based on independent services.
- When a client cannot conveniently manage cookies and CSRF tokens.

## 5. TokenAuthentication

### What is TokenAuthentication?

TokenAuthentication authenticates a user using a token stored in the database.

Unlike BasicAuthentication, the client sends a token instead of sending the username and password with every request.

### Why do we need it?

Suppose a mobile application has a user who logs in once.

Instead of repeatedly sending their password, the application can send a token with subsequent API requests.

### How does it work?

1. User submits username and password.
2. Server verifies the credentials.
3. Server creates or retrieves the user's token.
4. Client stores the token securely.
5. Client sends the token with future requests.
6. DRF validates the token and identifies the user.

### Step 1: Install or enable DRF token support

DRF includes the token application.

Add it to `INSTALLED_APPS`:

```python
INSTALLED_APPS = [
    "rest_framework",
    "rest_framework.authtoken",
]
```

Run migrations:

```bash
python manage.py migrate
```

### Step 2: Configure authentication

```python
REST_FRAMEWORK = {
    "DEFAULT_AUTHENTICATION_CLASSES": [
        "rest_framework.authentication.TokenAuthentication",
    ],
}
```

### Step 3: Create a token

```python
from rest_framework.authtoken.models import Token

token, created = Token.objects.get_or_create(
    user=user
)

print(token.key)
```

Example output:

```text
a1b2c3d4e5f678901234567890abcdef12345678
```

### Step 4: Send the token

```http
GET /api/profile/
Authorization: Token a1b2c3d4e5f678901234567890abcdef12345678
```

Notice that the prefix is `Token`, not `Bearer`.

### Step 5: Protect the API

```python
from rest_framework.views import APIView
from rest_framework.permissions import IsAuthenticated
from rest_framework.response import Response

class ProfileView(APIView):

    permission_classes = [IsAuthenticated]

    def get(self, request):
        return Response({
            "username": request.user.username
        })
```

### Example response

```json
{
    "username": "john"
}
```

### Important limitations

DRF's built-in token authentication:

- Uses a relatively simple, persistent token.
- Does not automatically expire tokens.
- Does not provide a built-in refresh-token system.
- Does not provide JWT-style claims.

### When should you use it?

- Simple applications.
- Small APIs.
- Internal projects where persistent tokens are sufficient.

### When should you avoid it?

- Applications needing short-lived access tokens.
- Applications needing refresh tokens.
- Applications needing token rotation.
- Systems requiring advanced token claims or distributed validation.

For those requirements, JWT or an OAuth2-based approach may be more appropriate.

## 6. RemoteUserAuthentication

### What is RemoteUserAuthentication?

RemoteUserAuthentication allows Django to trust an authenticated username supplied by a trusted web server or authentication proxy.

For example, an organization might use a central identity system.

The user logs in through that system, and the trusted proxy forwards the authenticated username to Django.

### Why do we need it?

Organizations sometimes use:

- Enterprise single sign-on.
- Reverse proxies.
- Centralized authentication systems.
- Existing corporate identity infrastructure.

They may not want every application to handle the initial login itself.

### How does it work?

1. User authenticates with the trusted upstream system.
2. The upstream system verifies the identity.
3. It forwards an authenticated username in a server-controlled HTTP header.
4. Django's remote-user authentication backend identifies or creates the corresponding Django user.
5. DRF sets `request.user`.

### Configuration example

```python
REST_FRAMEWORK = {
    "DEFAULT_AUTHENTICATION_CLASSES": [
        "rest_framework.authentication.RemoteUserAuthentication",
    ],
}
```

Django must also have an appropriate authentication backend configured:

```python
AUTHENTICATION_BACKENDS = [
    "django.contrib.auth.backends.RemoteUserBackend",
]
```

### When should you use it?

- Enterprise environments.
- Trusted reverse-proxy authentication.
- Systems with an established upstream login mechanism.

### When should you avoid it?

- When clients can directly supply arbitrary identity headers.
- When the proxy is not securely configured.
- When there is no trusted upstream authentication system.

**Security warning:** The application must ensure that untrusted clients cannot forge the remote-user header. The proxy should remove incoming versions of that header and set its own verified value.

---

## 7. Comparison of DRF authentication classes

| Class | Credential | Common use |
|---|---|---|
| BasicAuthentication | Username and password | Simple integrations |
| SessionAuthentication | Django session cookie | Django websites |
| TokenAuthentication | Database token | Simple mobile/API clients |
| RemoteUserAuthentication | Trusted remote username | Enterprise SSO |

JWTAuthentication is commonly added using Simple JWT.

# SECTION C — DRF PERMISSION CLASSES

Authentication answers:

**Who are you?**

Permissions answer:

**What are you allowed to do?**

DRF permissions control access to API views and individual objects.

## 8. AllowAny

### What is it?

Allows everyone to access the endpoint, including unauthenticated users.

### Why do we need it?

Some endpoints should be public.

Examples:

- Registration.
- Public product lists.
- Public blog posts.
- Public information.

### Example

```python
from rest_framework.permissions import AllowAny
from rest_framework.views import APIView
from rest_framework.response import Response

class PublicProductsView(APIView):

    permission_classes = [AllowAny]

    def get(self, request):
        return Response({
            "message": "Anyone can access products"
        })
```

### Output

```json
{
    "message": "Anyone can access products"
}
```

### When should you use it?

When the endpoint is intentionally public.

### When should you avoid it?

When the endpoint returns private information or performs sensitive operations.

---

## 9. IsAuthenticated

### What is it?

Allows only authenticated users to access an endpoint.

### Why do we need it?

Some API endpoints should be available only to logged-in users.

Examples:

- User profile.
- Order history.
- Account dashboard.
- Private messages.

### Example

```python
from rest_framework.permissions import IsAuthenticated

class ProfileView(APIView):

    permission_classes = [IsAuthenticated]

    def get(self, request):
        return Response({
            "username": request.user.username
        })
```

### Unauthenticated response

```json
{
    "detail": "Authentication credentials were not provided."
}
```

The HTTP status may be 401 or 403 depending on the configured authentication classes.

### Authenticated response

```json
{
    "username": "john"
}
```

### When should you use it?

When every authenticated user can access the endpoint.

### When should you avoid it?

When an endpoint must be publicly accessible, or when authentication alone is insufficient to enforce more specific business rules.

---

## 10. IsAdminUser

### What is it?

Allows access only to users whose Django `is_staff` property is true.

It does not simply mean that the user is a superuser.

### Why do we need it?

For staff-only endpoints such as:

- Admin dashboards.
- Employee management.
- Internal reports.
- Administrative operations.

### Example

```python
from rest_framework.permissions import IsAdminUser

class AdminDashboardView(APIView):

    permission_classes = [IsAdminUser]

    def get(self, request):
        return Response({
            "message": "Welcome administrator"
        })
```

### Example output

```json
{
    "message": "Welcome administrator"
}
```

A normal user with `is_staff=False` will be denied.

### When should you use it?

When access should be limited to Django staff users.

### When should you avoid it?

When your application has more detailed business roles, such as manager, HR, accountant and employee. Use custom permissions for those roles.

---

## 11. IsAuthenticatedOrReadOnly

### What is it?

Allows everyone to perform read-only operations, but requires authentication for unsafe operations.

Read-only methods are:

```python
GET
HEAD
OPTIONS
```

Other methods, such as POST, PUT, PATCH and DELETE, require authentication.

### Why do we need it?

Consider a public blog.

Anyone can read posts, but only authenticated users can create, edit or delete them.

### Example

```python
from rest_framework.permissions import IsAuthenticatedOrReadOnly

class BlogView(APIView):

    permission_classes = [
        IsAuthenticatedOrReadOnly
    ]

    def get(self, request):
        return Response({
            "message": "Anyone can read blog posts"
        })

    def post(self, request):
        return Response({
            "message": "Authenticated user created a post"
        })
```

### When should you use it?

For public read-only resources where logged-in users can make changes.

### When should you avoid it?

When only administrators should create or delete resources. Authentication alone may allow too many users to make changes.

---

## 12. DjangoModelPermissions

### What is it?

DjangoModelPermissions checks Django model permissions before allowing access.

Django provides model permissions such as:

- `add`
- `change`
- `delete`
- `view`

These permissions are associated with a model.

### Why do we need it?

Suppose you have an Employee model.

You might want:

- Users with `view_employee` to view employees.
- Users with `add_employee` to create employees.
- Users with `change_employee` to update employees.
- Users with `delete_employee` to delete employees.

### Example

```python
from rest_framework.permissions import DjangoModelPermissions
from rest_framework.viewsets import ModelViewSet

class EmployeeViewSet(ModelViewSet):

    queryset = Employee.objects.all()
    serializer_class = EmployeeSerializer

    permission_classes = [
        DjangoModelPermissions
    ]
```

DRF maps HTTP methods to Django model permissions.

A simplified mapping is:

| HTTP method | Permission |
|---|---|
| GET | `view` |
| POST | `add` |
| PUT/PATCH | `change` |
| DELETE | `delete` |

The exact behavior depends on the method-to-permission mapping.

### Important note

By default, DjangoModelPermissions requires authentication and checks model permissions. Its default mapping does not require a model permission for GET, HEAD or OPTIONS.

If you want GET requests to require `view_model`, configure the mapping appropriately.

### When should you use it?

When you want to use Django's existing user and group permission system.

### When should you avoid it?

When your access rules depend on ownership, complex roles, or business-specific conditions rather than model-level permissions alone.

---

## 13. DjangoModelPermissionsOrAnonReadOnly

### What is it?

This permission class allows anonymous users to perform read-only requests.

Authenticated users must have the appropriate model permissions for write operations.

### Why do we need it?

Imagine a public product catalogue.

- Anyone can view products.
- Only authenticated users with the required model permission can add or modify products.

### Example

```python
from rest_framework.permissions import (
    DjangoModelPermissionsOrAnonReadOnly
)

class ProductViewSet(ModelViewSet):

    queryset = Product.objects.all()
    serializer_class = ProductSerializer

    permission_classes = [
        DjangoModelPermissionsOrAnonReadOnly
    ]
```

### When should you use it?

For public resources where write operations are controlled by Django model permissions.

### When should you avoid it?

When all write operations should be available to any authenticated user, or when access depends on custom ownership or role rules.

---

## 14. DjangoObjectPermissions

### What is it?

DjangoObjectPermissions checks permissions on individual objects rather than only checking model-level permissions.

### Why do we need it?

Imagine an application with many projects.

A user might be allowed to view Project A but not Project B.

Model-level permission alone cannot express that distinction.

Object-level permissions can.

### Example concept

```python
from rest_framework.permissions import DjangoObjectPermissions

class ProjectViewSet(ModelViewSet):

    queryset = Project.objects.all()
    serializer_class = ProjectSerializer

    permission_classes = [
        DjangoObjectPermissions
    ]
```

This permission class works with an object-permission backend that supports the required object-level checks.

Django's default permission backend does not provide object-level permissions by itself.

### When should you use it?

When users have different permissions for different records.

### When should you avoid it?

When you do not have an object-permission backend configured.

Also remember that list endpoints need additional care: object-level permissions are not automatically applied to every item in a queryset. You may need queryset filtering or custom list logic.

---

## 15. Custom permission classes

### What are custom permissions?

Custom permissions allow you to define your own access rules.

### Why do we need them?

Real applications often have roles and rules that built-in permissions cannot fully express.

For example:

- HR can view all employees.
- Employees can view only their own profiles.
- Managers can update their team members.
- Only administrators can delete employees.

### Example: Only managers can access an endpoint

```python
from rest_framework.permissions import BasePermission

class IsManager(BasePermission):

    def has_permission(self, request, view):

        return (
            request.user
            and request.user.is_authenticated
            and request.user.groups.filter(
                name="Managers"
            ).exists()
        )
```

Use it:

```python
class ManagerDashboardView(APIView):

    permission_classes = [IsManager]

    def get(self, request):
        return Response({
            "message": "Welcome manager"
        })
```

### Example: Users can access only their own objects

```python
from rest_framework.permissions import BasePermission

class IsOwner(BasePermission):

    def has_object_permission(
        self,
        request,
        view,
        obj
    ):

        return obj.user == request.user
```

Use it:

```python
class EmployeeDetailView(RetrieveAPIView):

    queryset = Employee.objects.all()
    serializer_class = EmployeeSerializer

    permission_classes = [
        IsAuthenticated,
        IsOwner
    ]
```

The object must be retrieved and object permissions checked by the view. Generic DRF detail views do this as part of their normal object lookup flow.

### Two important custom permission methods

#### has_permission()

Checks access to the view or endpoint.

```python
def has_permission(self, request, view):
    return request.user.is_authenticated
```

#### has_object_permission()

Checks access to a specific object.

```python
def has_object_permission(
    self,
    request,
    view,
    obj
):
    return obj.user == request.user
```

### When should you use custom permissions?

When your rules involve:

- User roles.
- Ownership.
- Departments.
- Teams.
- Business-specific access.
- Different rules for different HTTP methods.

# SECTION D — JWT AUTHENTICATION

## 17. What is JWT authentication?

JWT stands for JSON Web Token.

It is a way to authenticate API requests using digitally signed tokens.

A JWT is commonly used when a frontend and backend communicate over an API.

For example:

```text
React Frontend
      |
      | Login credentials
      v
Django REST Framework
      |
      | Verify credentials
      v
Generate JWT
      |
      v
React stores token securely
      |
      | Authorization: Bearer <token>
      v
Protected API
```

### Why do we need JWT?

Consider a mobile application.

A user logs in with a username and password.

Instead of sending the password with every request, the backend issues an access token.

The mobile application sends that token with subsequent API requests.

JWT is useful for:

- Mobile applications.
- Separate frontend and backend applications.
- Stateless API authentication.
- Distributed systems.
- Applications requiring short-lived access tokens.

### What does a JWT look like?

A JWT commonly contains three parts separated by dots:

```text
HEADER.PAYLOAD.SIGNATURE
```

Example:

```text
eyJhbGciOiJIUzI1NiJ9.eyJ1c2VyX2lkIjoxLCJleHAiOjE3MDAwMDAwMDB9.signature
```

### Part 1: Header

Contains information about the token type and signing algorithm.

Example:

```json
{
    "typ": "JWT",
    "alg": "HS256"
}
```

### Part 2: Payload

Contains claims about the token.

Example:

```json
{
    "user_id": 1,
    "exp": 1800000000
}
```

### Part 3: Signature

The signature helps the server verify that the token has not been modified.

### Important security point

JWT payloads are normally encoded, not encrypted.

Anyone who obtains a JWT can usually decode its header and payload.

Never put passwords, secrets or sensitive personal information inside an ordinary signed JWT payload.

# SECTION E — SIMPLE JWT CONFIGURATION

## 18. What is Simple JWT?

Simple JWT is a third-party Django REST Framework package that provides JWT authentication.

It provides:

- JWT authentication.
- Access tokens.
- Refresh tokens.
- Token obtain and refresh endpoints.
- Token rotation.
- Token blacklisting.

### Step 1: Install Simple JWT

```bash
pip install djangorestframework-simplejwt
```

### Step 2: Configure DRF

In `settings.py`:

```python
REST_FRAMEWORK = {
    "DEFAULT_AUTHENTICATION_CLASSES": [
        "rest_framework_simplejwt.authentication.JWTAuthentication",
    ],
}
```

This tells DRF to authenticate requests using JWT.

### Step 3: Configure token lifetimes

```python
from datetime import timedelta

SIMPLE_JWT = {
    "ACCESS_TOKEN_LIFETIME": timedelta(minutes=5),
    "REFRESH_TOKEN_LIFETIME": timedelta(days=1),
}
```

This means:

- Access token expires after five minutes.
- Refresh token expires after one day.

These are example values, not universal requirements.

### Step 4: Configure token URLs

In your main `urls.py`:

```python
from django.urls import path
from rest_framework_simplejwt.views import (
    TokenObtainPairView,
    TokenRefreshView,
)

urlpatterns = [
    path(
        "api/token/",
        TokenObtainPairView.as_view(),
        name="token_obtain_pair"
    ),

    path(
        "api/token/refresh/",
        TokenRefreshView.as_view(),
        name="token_refresh"
    ),
]
```

### Step 5: Obtain tokens

Send a POST request:

```http
POST /api/token/
Content-Type: application/json
```

Request body:

```json
{
    "username": "john",
    "password": "password123"
}
```

Example response:

```json
{
    "refresh": "your_refresh_token",
    "access": "your_access_token"
}
```

The actual token strings will be long signed values.

### Step 6: Protect an API

```python
from rest_framework.views import APIView
from rest_framework.permissions import IsAuthenticated
from rest_framework.response import Response

class DashboardView(APIView):

    permission_classes = [IsAuthenticated]

    def get(self, request):
        return Response({
            "message": "JWT authentication successful",
            "username": request.user.username
        })
```

### Step 7: Send the access token

```http
GET /api/dashboard/
Authorization: Bearer your_access_token
```

Example response:

```json
{
    "message": "JWT authentication successful",
    "username": "john"
}
```

# SECTION F — ACCESS TOKENS

## 19. What is an access token?

An access token is a short-lived JWT used to access protected API endpoints.

### Why do we need it?

Sending a username and password with every API request would be inconvenient and increase exposure of credentials.

Instead, the client sends an access token.

### How does it work?

1. User logs in.
2. Server issues an access token.
3. Client sends the access token with API requests.
4. DRF validates the token.
5. DRF identifies the user.
6. Protected endpoint executes if permissions allow it.

### Example

```http
GET /api/profile/
Authorization: Bearer your_access_token
```

### What happens when it expires?

Suppose the access token lifetime is five minutes.

After five minutes, the token expires.

The client can no longer use it to access protected endpoints.

The client can use a valid refresh token to obtain a new access token.

### When should you use access tokens?

For normal authenticated API requests.

### When should you avoid using them?

Do not use an access token as a permanent credential. Keep its lifetime limited and protect it from theft.

---

# SECTION G — REFRESH TOKENS

## 20. What is a refresh token?

A refresh token is a longer-lived token used to obtain a new access token.

### Why do we need it?

Imagine an application where the access token expires every five minutes.

It would be frustrating if the user had to enter their username and password every five minutes.

A refresh token allows the application to obtain a new access token without asking the user to log in again.

### How does it work?

1. User logs in.
2. Server returns an access token and refresh token.
3. Access token expires.
4. Client sends refresh token to the refresh endpoint.
5. Server validates the refresh token.
6. Server returns a new access token.

### Request

```http
POST /api/token/refresh/
Content-Type: application/json
```

```json
{
    "refresh": "your_refresh_token"
}
```

### Example response

```json
{
    "access": "new_access_token"
}
```

Depending on the configuration, the refresh endpoint may also return a new refresh token.

### Difference between access and refresh tokens

| Access token | Refresh token |
|---|---|
| Used to access APIs | Used to obtain new access tokens |
| Short-lived | Usually longer-lived |
| Sent with normal API requests | Sent to refresh endpoint |
| Should be short-lived | Requires especially careful protection |

### When should you use refresh tokens?

When users need to remain logged in without repeatedly entering their credentials.

### When should you avoid them?

When your application does not need long-lived login sessions or cannot securely protect refresh tokens.

# SECTION H — TOKEN ROTATION AND BLACKLISTING

## 21. What is token rotation?

Token rotation means issuing a new refresh token when an existing refresh token is used.

The old refresh token is then invalidated when the appropriate rotation and blacklist configuration is enabled.

### Why do we need it?

If a refresh token is stolen, an attacker may be able to use it to obtain new access tokens.

Rotation reduces the usefulness of a previously used refresh token.

### Configuration

Add the blacklist app:

```python
INSTALLED_APPS = [
    "rest_framework",
    "rest_framework.authtoken",
    "rest_framework_simplejwt.token_blacklist",
]
```

Run migrations:

```bash
python manage.py migrate
```

Configure Simple JWT:

```python
SIMPLE_JWT = {
    "ROTATE_REFRESH_TOKENS": True,
    "BLACKLIST_AFTER_ROTATION": True,
}
```

### What happens?

1. Client sends a refresh token.
2. Server validates it.
3. Server issues a new access token.
4. Server issues a replacement refresh token.
5. The old refresh token is blacklisted.

### What is token blacklisting?

Blacklisting means marking a token as no longer valid.

Simple JWT provides a blacklist application to track outstanding and blacklisted refresh or sliding tokens.

### Why do we need blacklisting?

For example, when a user logs out, the application may want to invalidate the refresh token so it cannot be used again.

### When should you use rotation and blacklisting?

- Applications with longer login sessions.
- Mobile applications.
- Applications where refresh-token theft is a concern.
- Applications requiring logout or token revocation.

### When should you avoid them?

For a very simple application that does not need refresh-token management, they may introduce unnecessary database and operational complexity.

Remember: blacklisting refresh tokens does not automatically invalidate every already-issued access token. A stolen access token can generally remain usable until it expires unless you implement additional revocation controls.

# SECTION I — CUSTOM AUTHENTICATION CLASSES

## 22. What is a custom authentication class?

A custom authentication class is a class you create when the built-in authentication classes do not meet your application's requirements.

### Why do we need it?

Imagine your company has its own authentication system.

It sends a special header:

```http
X-API-KEY: company-secret-key
```

You want DRF to authenticate requests using that header.

You can create a custom authentication class.

### How to create one

DRF provides `BaseAuthentication`.

Example:

```python
from rest_framework.authentication import BaseAuthentication
from rest_framework.exceptions import AuthenticationFailed
from django.contrib.auth import get_user_model

User = get_user_model()

class APIKeyAuthentication(BaseAuthentication):

    def authenticate(self, request):

        api_key = request.headers.get("X-API-KEY")

        if not api_key:
            return None

        if api_key != "my-secret-key":
            raise AuthenticationFailed(
                "Invalid API key"
            )

        user = User.objects.get(username="john")

        return (user, api_key)
```

### What does `authenticate()` return?

It normally returns:

```python
(user, auth)
```

Where:

- `user` is the authenticated Django user.
- `auth` is the authentication information.

If the authentication class does not find credentials that it handles, it can return `None`.

If credentials are present but invalid, it can raise `AuthenticationFailed`.

### Configure it

```python
REST_FRAMEWORK = {
    "DEFAULT_AUTHENTICATION_CLASSES": [
        "myapp.authentication.APIKeyAuthentication",
    ],
}
```

### Important security note

The example uses a hard-coded key only to demonstrate the mechanism.

A real implementation should:

- Store API keys securely.
- Support key revocation.
- Avoid exposing secrets in source code.
- Use HTTPS.
- Consider associating keys with specific users or service accounts.
- Avoid using one shared key for every client.

### When should you use custom authentication?

When integrating with:

- External identity systems.
- API key systems.
- Internal gateways.
- Special enterprise authentication mechanisms.

### When should you avoid it?

When a standard, maintained authentication package already solves your problem.

Custom authentication code creates security and maintenance responsibilities.

# SECTION J — OAUTH2 AUTHENTICATION

## 23. What is OAuth2?

OAuth2 is an authorization framework that allows an application to access resources on behalf of a user without requiring the application to know the user's password.

For example, you use an application and choose:

"Sign in with Google."

The application redirects you to Google's authorization system.

Google handles authentication and consent, then provides authorization information to the application.

### Why do we need OAuth2?

Suppose you build a calendar application.

You want users to allow your application to access their Google Calendar.

You do not need to collect their Google password.

OAuth2 allows the user to grant limited access.

### How does it work?

A common Authorization Code flow works like this:

1. User clicks "Connect with Google."
2. Application redirects the user to the authorization provider.
3. User authenticates and grants consent.
4. Provider redirects back with an authorization code.
5. Backend exchanges the code for tokens.
6. Application uses the resulting access token to access permitted resources.

### OAuth2 in Django REST Framework

OAuth2 support is commonly implemented using a third-party package such as Django OAuth Toolkit.

```python
    path("o/", include("oauth2_provider.urls", namespace="oauth2_provider")),

```

Run migrations:

```bash
python manage.py migrate
```

### When should you use OAuth2?

- Third-party integrations.
- Delegated access.
- Enterprise authorization.
- Applications connecting to external APIs.

### When should you avoid it?

When you only need simple first-party login and JWT authentication is sufficient.

OAuth2 is an authorization framework, not simply another name for JWT. OAuth2 access tokens may be opaque or JWT-based.

# SECTION L — AWS COGNITO INTEGRATION

## 25. What is AWS Cognito?

Amazon Cognito is an identity service from AWS.

It can handle user registration, login, authentication, and token issuance.

Instead of implementing every authentication feature yourself, you can use Cognito as your identity provider.

### Why do we need Cognito?

Suppose you build a large application with:

- Web frontend.
- Mobile application.
- Django backend.
- Thousands of users.

You may want a centralized authentication service.

Cognito can manage user identities and issue tokens.

### How does it work?

1. User registers or logs in through Cognito.
2. Cognito verifies the user's credentials.
3. Cognito issues tokens.
4. Client sends an access token to Django.
5. Django verifies the token using Cognito's published signing keys and expected claims.
6. Django identifies the user and applies permissions.

### Example request

```http
GET /api/profile/
Authorization: Bearer cognito_access_token
```

### What must Django verify?

A secure Cognito integration should verify:

- Token signature.
- Token expiration.
- Issuer.
- Token use, such as access token versus ID token.
- Expected client or application identifier where appropriate.
- Required scopes or groups if your authorization design uses them.

### How do you integrate it?

You can use a maintained JWT verification library or implement a custom DRF authentication class that validates Cognito-issued tokens.

Conceptually:

```python
class CognitoAuthentication(BaseAuthentication):

    def authenticate(self, request):

        token = extract_bearer_token(request)

        if not token:
            return None

        claims = verify_cognito_token(token)

        user = get_or_create_local_user(claims)

        return (user, claims)
```

This is illustrative pseudocode: `extract_bearer_token`, `verify_cognito_token`, and `get_or_create_local_user` must be implemented with secure token validation and your application's user-mapping rules.

### When should you use Cognito?

- Applications already hosted on AWS.
- Centralized identity management.
- Multiple applications sharing one user directory.
- Applications needing managed sign-up and sign-in.

### When should you avoid it?

When your application is small and Django's built-in authentication already meets your needs.

# SECTION N — USER REGISTRATION API

## 27. What is a registration API?

A registration API allows a new user to create an account.

### Why do we need it?

Users need a way to join your application without an administrator manually creating every account.

### How does it work?

1. Client sends registration information.
2. Backend validates the input.
3. Backend checks whether the username or email is already used.
4. Backend hashes the password.
5. Backend creates the user.
6. Backend returns a success response.

### Serializer

```python
from rest_framework import serializers
from django.contrib.auth import get_user_model

User = get_user_model()

class RegisterSerializer(serializers.ModelSerializer):

    password = serializers.CharField(
        write_only=True,
        min_length=8
    )

    class Meta:
        model = User
        fields = [
            "username",
            "email",
            "password"
        ]

    def create(self, validated_data):

        user = User.objects.create_user(
            username=validated_data["username"],
            email=validated_data["email"],
            password=validated_data["password"]
        )

        return user
```

### View

```python
from rest_framework.generics import CreateAPIView
from rest_framework.permissions import AllowAny

class RegisterView(CreateAPIView):

    queryset = User.objects.all()
    serializer_class = RegisterSerializer
    permission_classes = [AllowAny]
```

### URL

```python
path(
    "api/register/",
    RegisterView.as_view(),
    name="register"
)
```

### Request

```http
POST /api/register/
Content-Type: application/json
```

```json
{
    "username": "john",
    "email": "john@example.com",
    "password": "StrongPassword123"
}
```

### Example response

```json
{
    "username": "john",
    "email": "john@example.com"
}
```

The password is not returned because it is write-only.

### When should you use it?

When users need to register themselves.

### When should you avoid it?

When accounts must be created only by administrators or through an invitation system.

**Security:** Add email verification, rate limiting, appropriate password validation and protection against account enumeration where required. Never use `User.objects.create(password=...)` for raw passwords; use `create_user()` or `set_password()`.

# SECTION P — LOGOUT API

## 29. What is a logout API?

A logout API allows a user to end their authenticated session or invalidate a refresh token.

### Why do we need it?

When users log out, the application should prevent the old login credentials from being reused where possible.

### How does logout work with JWT?

JWT access tokens are normally self-contained.

Simply deleting a token from the browser does not invalidate a copy that an attacker may have stolen.

A common Simple JWT approach is to blacklist the refresh token.

### Step 1: Enable blacklisting

```python
INSTALLED_APPS = [
    "rest_framework",
    "rest_framework_simplejwt.token_blacklist",
]
```

Run:

```bash
python manage.py migrate
```

### Step 2: Create logout serializer

```python
from rest_framework import serializers
from rest_framework_simplejwt.tokens import RefreshToken

class LogoutSerializer(serializers.Serializer):

    refresh = serializers.CharField()

    def validate(self, attrs):

        try:
            token = RefreshToken(attrs["refresh"])
            token.blacklist()

        except Exception:
            raise serializers.ValidationError(
                "Invalid or expired refresh token"
            )

        return attrs
```

### Step 3: Create logout view

```python
from rest_framework.views import APIView
from rest_framework.permissions import IsAuthenticated
from rest_framework.response import Response
from rest_framework import status

class LogoutView(APIView):

    permission_classes = [IsAuthenticated]

    def post(self, request):

        serializer = LogoutSerializer(
            data=request.data
        )

        serializer.is_valid(raise_exception=True)

        return Response(
            {"message": "Logged out successfully"},
            status=status.HTTP_205_RESET_CONTENT
        )
```

### Request

```http
POST /api/logout/
Authorization: Bearer access_token_here
```

```json
{
    "refresh": "refresh_token_here"
}
```

### Example response

```json
{
    "message": "Logged out successfully"
}
```

### What does this invalidate?

It blacklists the supplied refresh token.

It does not automatically invalidate an already-issued access token. That token generally remains usable until its expiration unless you add a separate access-token revocation mechanism.

### When should you use it?

When your application uses refresh tokens and wants to revoke them during logout.

### When should you avoid it?

If you assume that deleting a token from the frontend alone securely revokes it on the server. Client-side deletion is not server-side revocation.

# SECTION Q — PASSWORD HASHING

## 30. What is password hashing?

Password hashing converts a password into a one-way representation that can be stored in the database.

Django does not normally store a user's original password.

Instead, it stores a salted password hash.

### Why do we need password hashing?

Imagine your database stores passwords like this:

```text
username     password
john         password123
```

If someone steals the database, they immediately know every user's password.

This is dangerous.

With password hashing, the database stores a value similar to:

```text
pbkdf2_sha256$...$...$...
```

The original password is not stored.

### How does Django hash passwords?

Django provides secure password-handling functions.

For example:

```python
user.set_password("StrongPassword123")
user.save()
```

Django hashes the password using the configured password hasher.

### How do you verify a password?

```python
user.check_password("StrongPassword123")
```

Output:

```text
True
```

For an incorrect password:

```python
user.check_password("wrongpassword")
```

Output:

```text
False
```

### How does registration use password hashing?

This is correct:

```python
user = User.objects.create_user(
    username="john",
    password="StrongPassword123"
)
```

This is also correct:

```python
user = User(
    username="john"
)

user.set_password("StrongPassword123")
user.save()
```

This is incorrect:

```python
user = User.objects.create(
    username="john",
    password="StrongPassword123"
)
```

The last example stores the raw password rather than hashing it.

### When should you use password hashing?

Always use Django's password-management functions when storing user passwords.

### When should you avoid it?

Never replace password hashing with:

- Plain-text password storage.
- Reversible encryption for normal password storage.
- Simple MD5 or SHA-256 hashing without a password-hashing scheme.

# SECTION R — PASSWORD RESET API

## 31. What is a password reset API?

A password reset API allows a user who has forgotten their password to create a new password after proving control of a trusted recovery channel, usually their registered email address.

### Why do we need it?

Users forget passwords.

Without password recovery, they may lose access to their accounts.

### How does it work?

A typical password reset flow is:

1. User submits their email address.
2. Backend generates a secure, time-limited reset token.
3. Backend sends a reset link to the registered email address.
4. User opens the link.
5. Frontend submits the token and new password.
6. Backend validates the token.
7. Backend updates the password using Django's password hashing.
8. User can log in using the new password.

### Step 1: Create a password reset request

Django provides:

```python
from django.contrib.auth.tokens import default_token_generator
```

You can use it to generate a password reset token.

### Step 2: Create a reset request serializer

```python
from rest_framework import serializers

class PasswordResetRequestSerializer(serializers.Serializer):

    email = serializers.EmailField()
```

### Step 3: Create a reset request view

The following is a simplified example of the core flow:

```python
from django.contrib.auth import get_user_model
from django.contrib.auth.tokens import default_token_generator
from django.utils.encoding import force_bytes
from django.utils.http import urlsafe_base64_encode

from rest_framework.views import APIView
from rest_framework.response import Response
from rest_framework.permissions import AllowAny

User = get_user_model()

class PasswordResetRequestView(APIView):

    permission_classes = [AllowAny]

    def post(self, request):

        email = request.data.get("email")

        user = User.objects.filter(
            email=email,
            is_active=True
        ).first()

        if user:
            uid = urlsafe_base64_encode(
                force_bytes(user.pk)
            )

            token = default_token_generator.make_token(
                user
            )

            reset_link = (
                f"https://frontend.example.com/reset-password/"
                f"?uid={uid}&token={token}"
            )

            # Send reset_link using your email service.

        return Response({
            "message": (
                "If an account exists for that email, "
                "password reset instructions will be sent."
            )
        })
```

The URL above is illustrative. Replace it with your real frontend URL and send the link through a configured email service.

Notice that the response does not reveal whether the email exists.

### Step 4: Validate the reset token and change the password

```python
from django.contrib.auth.tokens import default_token_generator
from django.utils.encoding import force_str
from django.utils.http import urlsafe_base64_decode

from rest_framework import serializers
from rest_framework.views import APIView
from rest_framework.response import Response
from rest_framework.permissions import AllowAny
from rest_framework import status

class PasswordResetConfirmView(APIView):

    permission_classes = [AllowAny]

    def post(self, request):

        uid = request.data.get("uid")
        token = request.data.get("token")
        new_password = request.data.get("new_password")

        try:
            user_id = force_str(
                urlsafe_base64_decode(uid)
            )

            user = User.objects.get(pk=user_id)

        except Exception:
            return Response(
                {"error": "Invalid reset link"},
                status=status.HTTP_400_BAD_REQUEST
            )

        if not default_token_generator.check_token(
            user,
            token
        ):
            return Response(
                {"error": "Invalid or expired token"},
                status=status.HTTP_400_BAD_REQUEST
            )

        # Apply Django's configured password validators.
        from django.contrib.auth.password_validation import (
            validate_password
        )

        try:
            validate_password(new_password, user)
        except Exception as exc:
            return Response(
                {"error": list(exc.messages)},
                status=status.HTTP_400_BAD_REQUEST
            )

        user.set_password(new_password)
        user.save()

        return Response({
            "message": "Password reset successful"
        })
```

### Example request

```json
{
    "uid": "MQ",
    "token": "reset-token-value",
    "new_password": "NewStrongPassword123"
}
```

### Example response

```json
{
    "message": "Password reset successful"
}
```

### When should you use it?

When users need self-service password recovery.

### When should you avoid it?

Do not create password reset links that never expire, use predictable tokens, or reveal whether an email address is registered.

### Important security recommendations

- Use HTTPS.
- Use time-limited, single-use reset tokens.
- Do not reveal whether an account exists.
- Rate-limit reset requests.
- Validate the new password.
- Do not send passwords through email.
- Consider invalidating existing sessions or refresh tokens after a password change.
- Do not log reset tokens.

# SECTION S — IMPORTANT SECURITY PRACTICES

## 32. Authentication security checklist

1. Always use HTTPS in production.
2. Never store raw passwords.
3. Use Django's `create_user()` or `set_password()`.
4. Keep access tokens short-lived.
5. Protect refresh tokens carefully.
6. Enable refresh-token rotation where appropriate.
7. Use blacklisting when token revocation is required.
8. Validate JWT signatures and claims.
9. Never trust a JWT just because it can be decoded.
10. Use permission classes to protect private endpoints.
11. Apply object-level checks when users can access individual records.
12. Protect session-authenticated unsafe requests with CSRF.
13. Rate-limit login and password-reset endpoints.
14. Avoid exposing secrets in source code or logs.
15. Plan custom user models before the first migration.

# SECTION T — INTERVIEW QUESTIONS AND ANSWERS

## Authentication questions

### Q1. What is authentication?

Authentication is the process of verifying the identity of a user.

### Q2. What is the difference between authentication and authorization?

Authentication verifies who the user is. Authorization determines what the user is allowed to access or perform.

### Q3. What are authentication classes in DRF?

Authentication classes identify the user making an API request. DRF's main built-in classes are BasicAuthentication, SessionAuthentication, TokenAuthentication and RemoteUserAuthentication.

### Q4. What is the difference between SessionAuthentication and TokenAuthentication?

SessionAuthentication uses Django's session cookie. TokenAuthentication uses a database-backed token sent in the Authorization header.

### Q5. Is JWT authentication built into DRF?

No. JWT authentication is commonly added using third-party packages such as Simple JWT.

### Q6. What is the difference between authentication and permission classes?

Authentication identifies the user. Permission classes decide whether that user can access the endpoint or object.

## Permission questions

### Q7. What does AllowAny do?

It allows authenticated and unauthenticated users to access the endpoint.

### Q8. What does IsAuthenticated do?

It allows only authenticated users.

### Q9. What does IsAdminUser check?

It checks whether the user has `is_staff=True`.

### Q10. What is IsAuthenticatedOrReadOnly?

It allows anyone to perform safe read-only operations, while requiring authentication for unsafe operations.

### Q11. What is DjangoModelPermissions?

It checks whether the user has the appropriate Django model permissions.

### Q12. What is DjangoObjectPermissions?

It checks permissions on individual objects, provided an appropriate object-permission backend is configured.

### Q13. What is the difference between has_permission() and has_object_permission()?

`has_permission()` checks access to the view. `has_object_permission()` checks access to a particular object.

## JWT questions

### Q14. What is JWT?

JWT stands for JSON Web Token. It is a digitally signed token format commonly used to authenticate API requests.

### Q15. What are the three parts of a JWT?

Header, payload and signature.

### Q16. Is JWT encrypted?

Not necessarily. A typical signed JWT is encoded and signed, not encrypted. Its payload can be decoded, so sensitive information should not be stored in it.

### Q17. What is an access token?

A short-lived token used to access protected APIs.

### Q18. What is a refresh token?

A longer-lived token used to obtain a new access token.

### Q19. Why do we need refresh tokens?

They allow users to remain logged in without repeatedly entering their credentials when access tokens expire.

### Q20. What is token rotation?

Token rotation means issuing a replacement refresh token when a refresh token is used.

### Q21. What is token blacklisting?

It marks supported tokens as invalid so they cannot be used again.

### Q22. Does blacklisting a refresh token automatically invalidate an access token?

No. An access token usually remains valid until expiration unless an additional revocation mechanism is implemented.

### Q23. What is Simple JWT?

Simple JWT is a third-party package that provides JWT authentication for Django REST Framework.

### Q24. What is the Authorization header for JWT?

```http
Authorization: Bearer <access_token>
```

### Q25. What is the difference between DRF TokenAuthentication and JWTAuthentication?

DRF TokenAuthentication uses a database-backed token that generally does not expire automatically. JWTAuthentication validates signed JWTs that can contain expiry and other claims.

## Advanced authentication questions

### Q26. What is OAuth2?

OAuth2 is an authorization framework that allows an application to obtain limited access to resources on behalf of a user.

### Q27. What is OpenID Connect?

OpenID Connect is an identity layer built on OAuth2. It is commonly used for login and identity verification.

### Q28. What is social authentication?

It allows users to authenticate using an external identity provider such as Google, GitHub or Apple.

### Q29. What is AWS Cognito?

AWS Cognito is a managed identity service that can handle user registration, authentication and token issuance.

### Q30. Why create a custom user model?

To support additional user fields, different login requirements or application-specific user behavior.

### Q31. Why use create_user() instead of create()?

`create_user()` hashes the password automatically. `create()` does not automatically hash a raw password assigned to the password field.

### Q32. How does Django store passwords?

Django stores salted password hashes using its configured password-hashing algorithms.

### Q33. What does set_password() do?

It hashes a supplied password and assigns the resulting hash to the user's password field.

### Q34. What does check_password() do?

It checks whether a supplied password matches the stored password hash.

### Q35. Why do we need a password reset API?

It allows users to regain account access securely when they forget their passwords.
