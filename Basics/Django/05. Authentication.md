# PART 1: Authentication vs Authorization

## 1. What is Authentication?

Authentication means verifying the identity of a user or application.

It answers:

**Who are you?**

For example, imagine a user logs in to an e-commerce application.

They provide:

```json
{
    "email": "john@example.com",
    "password": "MyPassword123"
}
```

The backend checks:

1. Does this user exist?
2. Is the password correct?
3. Is the account active?
4. Are additional authentication requirements satisfied?

If everything is valid, the backend establishes an authenticated identity.

Depending on the authentication method, it may establish a session or issue tokens.

## 2. What is Authorization?

Authorization determines what an authenticated user is allowed to do.

It answers:

**What are you allowed to access?**

Imagine these users:

| User | Role | Allowed actions |
|---|---|---|
| John | Customer | View own orders |
| Mary | Staff | Manage customer orders |
| Admin | Administrator | Manage products and users |

All three users can authenticate successfully.

However, they do not have the same permissions.

For example:

```text
GET /api/orders/
```

A customer might see only their own orders.

An administrator might see all orders.

This is authorization.

## 3. Authentication vs Authorization

| Feature | Authentication | Authorization |
|---|---|---|
| Purpose | Verify identity | Control access |
| Question | Who are you? | What can you do? |
| Happens | Before permission checks | After identity is established |
| Main mechanisms | Session, password, token, JWT | Permissions, roles, scopes, policies |
| DRF component | Authentication classes | Permission classes |
| Example | Verify JWT | Check whether user owns an order |

## 4. Real-world example

Suppose a user accesses:

```text
GET /api/orders/100/
```

The process is:

**Step 1: Authentication**

The client sends:

```http
Authorization: Bearer YOUR_ACCESS_TOKEN
```

DRF validates the token.

The request now has:

```python
request.user
```

containing the authenticated user.

**Step 2: Authorization**

The application checks:

```python
if order.user != request.user:
    raise PermissionDenied()
```

If the order belongs to another user, the request is denied.

Expected response:

```json
{
    "detail": "You do not have permission to perform this action."
}
```

HTTP status:

```text
403 Forbidden
```

## 5. What are the main industry patterns?

| Application | Common approach |
|---|---|
| Traditional Django website | Session authentication |
| Django admin | Session authentication |
| SPA with separate API | JWT or secure cookie-based sessions |
| Mobile application | JWT or OAuth/OIDC-based authentication |
| Enterprise SSO | OpenID Connect |
| Third-party delegated API access | OAuth 2.0 |
| AWS-hosted application | Amazon Cognito or another identity provider |
| Internal microservices | OAuth2 client credentials, workload identity, or signed credentials |

**Industry recommendation:** Do not select JWT automatically for every application. Session authentication can be simpler and safer for a traditional same-site web application. JWT is useful when independently deployed clients and services need portable credentials.

# 1. DRF Authentication Architecture

## What is DRF Authentication Architecture?

Django REST Framework uses pluggable authentication classes.

An authentication class examines the incoming request and attempts to identify the user.

Common authentication classes include:

```python
SessionAuthentication
BasicAuthentication
TokenAuthentication
JWTAuthentication
```

The first three are provided by DRF. `JWTAuthentication` is provided by the third-party Simple JWT package.

## How does authentication work?

Consider this request:

```http
GET /api/profile/
Authorization: Bearer eyJhbGciOi...
```

The processing flow is:

```text
Client Request
      |
      v
DRF Request
      |
      v
Authentication Classes
      |
      v
Validate Credentials
      |
      v
Set request.user
      |
      v
Permission Checks
      |
      v
Execute View
      |
      v
Return Response
```

### Important: request.user and request.auth

DRF exposes two important properties.

#### request.user

Represents the authenticated user.

Example:

```python
def get(self, request):

    user = request.user

    return Response({
        "username": user.username
    })
```

#### request.auth

Represents additional authentication credentials.

For JWT authentication, this is generally the validated token.

For DRF's built-in TokenAuthentication, it is the token model instance.

For SessionAuthentication, it is normally `None`.

## Configure authentication globally

Inside `settings.py`:

```python
REST_FRAMEWORK = {

    "DEFAULT_AUTHENTICATION_CLASSES": [

        "rest_framework_simplejwt.authentication.JWTAuthentication",

    ],

    "DEFAULT_PERMISSION_CLASSES": [

        "rest_framework.permissions.IsAuthenticated",

    ],

}
```

This configuration means:

- JWT is used to authenticate requests by default.
- Requests must be authenticated unless a view overrides the default permission.

## Configure authentication per view

```python
from rest_framework.views import APIView
from rest_framework.response import Response

from rest_framework.permissions import IsAuthenticated

from rest_framework_simplejwt.authentication import JWTAuthentication


class ProfileAPIView(APIView):

    authentication_classes = [
        JWTAuthentication
    ]

    permission_classes = [
        IsAuthenticated
    ]

    def get(self, request):

        return Response({
            "username": request.user.username,
            "email": request.user.email
        })
```

## Important DRF authentication attributes

| Attribute | Purpose |
|---|---|
| `authentication_classes` | Defines authentication methods for a view |
| `permission_classes` | Defines access rules |
| `request.user` | Authenticated user |
| `request.auth` | Additional authentication credentials |
| `DEFAULT_AUTHENTICATION_CLASSES` | Global authentication configuration |
| `DEFAULT_PERMISSION_CLASSES` | Global permission configuration |
| `UNAUTHENTICATED_USER` | User object for unauthenticated requests |
| `UNAUTHENTICATED_TOKEN` | Authentication object for unauthenticated requests |

## Authentication vs permission example

```python
from rest_framework.permissions import IsAuthenticated

class MyAPIView(APIView):

    permission_classes = [
        IsAuthenticated
    ]

    def get(self, request):

        return Response({
            "message": "You are authenticated",
            "user": request.user.username
        })
```

If the client sends no valid credentials, it cannot access the protected view.

### HTTP 401 vs HTTP 403

**401 Unauthorized**

Usually means the request has not provided valid authentication credentials.

**403 Forbidden**

Usually means the request is not allowed, even if the user is authenticated.

There are some authentication-scheme-specific differences in DRF's response behavior. For example, SessionAuthentication commonly returns 403 for unauthenticated permission failures, while token or bearer schemes can return 401 with an authentication challenge.

## When should you use DRF authentication classes?

Use them whenever your API needs to identify the user or client making a request.

## When should you not use authentication?

You may deliberately allow public access for endpoints such as:

- Public product catalogs.
- Public documentation.
- Public health checks.
- Public registration endpoints.

For these endpoints, configure `AllowAny` explicitly.

# 2. Session Authentication

## What is Session Authentication?

Session authentication uses Django's built-in session framework.

Instead of sending a username and password with every request, a user logs in once.

Django creates a session and the browser stores a session identifier in a cookie.

The browser automatically sends that cookie with subsequent requests.

## How does it work?

```text
User enters username/password
           |
           v
Django validates credentials
           |
           v
Django creates session
           |
           v
Browser receives session cookie
           |
           v
Browser sends cookie on requests
           |
           v
Django identifies user
```

Example cookie:

```http
Cookie: sessionid=abc123xyz
```

The session data is normally stored server-side using Django's configured session backend.

## Why use Session Authentication?

It is convenient for applications where:

- Django serves the frontend and backend.
- A browser interacts with the same application.
- Users already log in through Django's normal login system.
- You need straightforward session invalidation.

## Configure SessionAuthentication

Inside `settings.py`:

```python
REST_FRAMEWORK = {

    "DEFAULT_AUTHENTICATION_CLASSES": [

        "rest_framework.authentication.SessionAuthentication",

    ],

    "DEFAULT_PERMISSION_CLASSES": [

        "rest_framework.permissions.IsAuthenticated",

    ]

}
```

## Example protected API

```python
from rest_framework.views import APIView
from rest_framework.response import Response

from rest_framework.permissions import IsAuthenticated


class ProfileAPIView(APIView):

    authentication_classes = [
        SessionAuthentication
    ]

    permission_classes = [
        IsAuthenticated
    ]

    def get(self, request):

        return Response({
            "username": request.user.username,
            "email": request.user.email
        })
```

Import:

```python
from rest_framework.authentication import SessionAuthentication
```

## What is CSRF?

CSRF means Cross-Site Request Forgery.

It is an attack in which a malicious website attempts to make a browser send an unwanted authenticated request to another website.

Because browsers automatically send cookies, cookie-based authentication needs CSRF protection for unsafe operations.

Unsafe methods include:

```text
POST
PUT
PATCH
DELETE
```

With DRF SessionAuthentication, authenticated unsafe requests must include a valid CSRF token.

Example:

```http
POST /api/profile/update/

Cookie: sessionid=abc123

X-CSRFToken: csrf-token-value
```

## When should you use Session Authentication?

Use it for:

- Traditional Django websites.
- Django templates with AJAX requests.
- Same-origin browser applications.
- Internal web dashboards.

## When should you not use Session Authentication?

It may not be the best fit when:

- Your mobile application needs bearer-token authentication.
- You have multiple independently deployed clients.
- Your services require portable credentials.
- You need delegated authorization through OAuth2.

Session authentication is not inherently insecure. It requires correct cookie, HTTPS, and CSRF configuration.

## Interview question

**Q: Why does SessionAuthentication require CSRF protection?**

Answer:

Because browsers automatically send cookies with requests. An attacker may exploit that behavior to make an authenticated browser perform an unwanted action. CSRF tokens help verify that unsafe requests originated from the expected application context.

# 3. Basic Authentication

## What is Basic Authentication?

HTTP Basic Authentication sends a username and password in the Authorization header.

The credentials are Base64-encoded.

Example:

```http
Authorization: Basic am9objpwYXNzd29yZA==
```

This decodes to:

```text
john:password
```

Important: Base64 is encoding, not encryption.

Anyone who intercepts the request can decode the credentials if the connection is not protected.

## Configure Basic Authentication

```python
REST_FRAMEWORK = {

    "DEFAULT_AUTHENTICATION_CLASSES": [

        "rest_framework.authentication.BasicAuthentication",

    ],

    "DEFAULT_PERMISSION_CLASSES": [

        "rest_framework.permissions.IsAuthenticated",

    ]

}
```

## Example API

```python
from rest_framework.authentication import BasicAuthentication

from rest_framework.permissions import IsAuthenticated

from rest_framework.views import APIView

from rest_framework.response import Response


class DashboardAPIView(APIView):

    authentication_classes = [
        BasicAuthentication
    ]

    permission_classes = [
        IsAuthenticated
    ]

    def get(self, request):

        return Response({
            "message": "Welcome",
            "user": request.user.username
        })
```

## Request using curl

```bash
curl -u john:password123 \
http://127.0.0.1:8000/api/dashboard/
```

Expected response:

```json
{
    "message": "Welcome",
    "user": "john"
}
```

## Why use Basic Authentication?

It is easy to understand and useful for:

- Local development.
- Testing APIs.
- Simple scripts.
- Temporary internal integrations.

## When should you not use Basic Authentication?

Avoid using it as the normal end-user authentication mechanism for modern public APIs.

Reasons:

1. The client repeatedly sends reusable credentials.
2. It does not provide built-in token expiry.
3. It does not provide refresh-token workflows.
4. It is less suitable for mobile and SPA authentication.

If used, require HTTPS and protect credential storage.

## Interview question

**Q: Is Basic Authentication encrypted?**

Answer:

No. It Base64-encodes credentials, but Base64 is reversible. HTTPS provides transport encryption. Basic Authentication should not be used over plain HTTP.

# 4. Token Authentication

## What is Token Authentication?

Token Authentication allows a user to authenticate using a token instead of repeatedly sending their password.

DRF includes a built-in implementation through:

```python
rest_framework.authtoken
```

After successful login, the server provides a token.

The client sends the token in future requests.

Example:

```http
Authorization: Token 9944b09199c62bcf9418ad846dd0e4bbdfc6ee4b
```

## How does it work?

```text
User Login
    |
    v
Validate Username and Password
    |
    v
Generate Token
    |
    v
Client Stores Token
    |
    v
Client Sends Token
    |
    v
Server Looks Up Token
    |
    v
Identify User
```

## Step 1: Install configuration

DRF's token authentication is included in the DRF package.

Inside `settings.py`:

```python
INSTALLED_APPS = [

    "django.contrib.admin",
    "django.contrib.auth",
    "django.contrib.contenttypes",
    "django.contrib.sessions",

    "rest_framework",

    "rest_framework.authtoken",

]
```

Run:

```bash
python manage.py migrate
```

## Step 2: Configure authentication

```python
REST_FRAMEWORK = {

    "DEFAULT_AUTHENTICATION_CLASSES": [

        "rest_framework.authentication.TokenAuthentication",

    ],

    "DEFAULT_PERMISSION_CLASSES": [

        "rest_framework.permissions.IsAuthenticated",

    ]

}
```

## Step 3: Create a token

```python
from rest_framework.authtoken.models import Token

from django.contrib.auth import get_user_model

User = get_user_model()

user = User.objects.get(username="john")

token, created = Token.objects.get_or_create(
    user=user
)

print(token.key)
```

Example output:

```text
9944b09199c62bcf9418ad846dd0e4bbdfc6ee4b
```

## Step 4: Add token login URL

```python
from django.urls import path

from rest_framework.authtoken.views import obtain_auth_token


urlpatterns = [

    path(
        "api/token/",
        obtain_auth_token,
        name="api-token"
    ),

]
```

Send:

```http
POST /api/token/
Content-Type: application/json
```

Body:

```json
{
    "username": "john",
    "password": "password123"
}
```

Expected response:

```json
{
    "token": "9944b09199c62bcf9418ad846dd0e4bbdfc6ee4b"
}
```

## Step 5: Use the token

```http
GET /api/profile/

Authorization: Token 9944b09199c62bcf9418ad846dd0e4bbdfc6ee4b
```

## Limitations of DRF's built-in TokenAuthentication

The standard implementation has important limitations:

- One token per user by default.
- No built-in access-token expiration.
- No built-in refresh-token workflow.
- No built-in token rotation.
- No built-in refresh-token blacklist.

You can implement additional behavior or use a package such as Knox.

## When should you use TokenAuthentication?

Use it for:

- Simple API clients.
- Internal services.
- Small applications.
- Applications where token lifecycle requirements are limited.

## When should you not use it?

Avoid relying on the built-in implementation if your requirements include:

- Short-lived access tokens.
- Refresh tokens.
- Token rotation.
- Per-device sessions.
- Advanced revocation.
- Fine-grained OAuth scopes.

For these cases, consider Simple JWT, Knox, or an OAuth/OIDC provider.

# 5. JWT Authentication

## What is JWT?

JWT stands for JSON Web Token.

It is a compact token format used to transfer claims between parties.

A JWT typically consists of three parts:

```text
HEADER.PAYLOAD.SIGNATURE
```

Example structure:

```text
eyJhbGciOiJIUzI1NiJ9
.
eyJzdWIiOiIxMjMiLCJleHAiOjE3...
.
signature-value
```

A JWT is generally signed, not encrypted.

Do not put passwords, secrets, or sensitive personal information in its payload.

## 5.1 JWT Header

The header contains information about the token.

Example:

```json
{
    "alg": "HS256",
    "typ": "JWT"
}
```

`alg` identifies the signing algorithm.

`typ` identifies the token type.

## 5.2 JWT Payload

The payload contains claims.

Example:

```json
{
    "user_id": 10,
    "username": "john",
    "exp": 1794000000
}
```

Common JWT claims:

| Claim | Meaning |
|---|---|
| `sub` | Subject |
| `iss` | Issuer |
| `aud` | Audience |
| `exp` | Expiration time |
| `iat` | Issued-at time |
| `nbf` | Not-before time |
| `jti` | Unique token identifier |

Applications can also add custom claims.

## 5.3 JWT Signature

The signature protects the token against unauthorized modification.

For example, if the payload is modified, signature verification should fail.

With HMAC signing, the same secret is used for signing and verification.

With asymmetric signing, a private key signs and a public key verifies.

## How JWT authentication works

```text
Client Sends Login Credentials
           |
           v
Django Validates Credentials
           |
           v
Server Creates JWT
           |
           v
Client Stores Tokens
           |
           v
Client Sends Access Token
           |
           v
Server Verifies Signature and Claims
           |
           v
DRF Identifies User
           |
           v
Permission Checks
           |
           v
API Response
```

## Example request

```http
GET /api/profile/

Authorization: Bearer ACCESS_TOKEN
```

Notice that JWT normally uses the `Bearer` authorization scheme.

## Why use JWT?

Advantages:

1. Tokens can be verified without looking up a token record in the database on every request.
2. They work well across independently deployed services.
3. They are suitable for mobile and SPA clients.
4. They support expiration and refresh workflows.
5. They can carry claims and scopes.

## Disadvantages

1. A stolen access token can be used until it expires or is otherwise rejected.
2. Immediate revocation is difficult without additional infrastructure.
3. Token storage in browsers requires careful security decisions.
4. Large tokens increase request size.
5. Incorrect signing-key management can compromise the entire system.

## When should you use JWT?

Use it for:

- Mobile APIs.
- Distributed applications.
- Multiple backend services.
- SPA-to-API communication.
- Federated identity integrations.

## When should you not use JWT?

It may be unnecessary for:

- Simple server-rendered Django websites.
- Small applications that can use normal Django sessions.
- Applications that require immediate server-side session invalidation without additional token infrastructure.

# 6. Simple JWT Configuration

## What is Simple JWT?

Simple JWT is a package that integrates JWT authentication into Django REST Framework.

It provides:

- JWT authentication.
- Access tokens.
- Refresh tokens.
- Token obtain endpoints.
- Token refresh endpoints.
- Token verification endpoints.
- Optional token blacklisting.
- Custom token claims.

## Step 1: Install Simple JWT

```bash
pip install djangorestframework-simplejwt
```

## Step 2: Configure settings.py

```python
from datetime import timedelta


INSTALLED_APPS = [

    "django.contrib.admin",
    "django.contrib.auth",
    "django.contrib.contenttypes",
    "django.contrib.sessions",

    "rest_framework",

    "rest_framework_simplejwt",

]
```

Configure DRF:

```python
REST_FRAMEWORK = {

    "DEFAULT_AUTHENTICATION_CLASSES": [

        "rest_framework_simplejwt.authentication.JWTAuthentication",

    ],

    "DEFAULT_PERMISSION_CLASSES": [

        "rest_framework.permissions.IsAuthenticated",

    ],

}
```

Configure Simple JWT:

```python
SIMPLE_JWT = {

    "ACCESS_TOKEN_LIFETIME": timedelta(
        minutes=15
    ),

    "REFRESH_TOKEN_LIFETIME": timedelta(
        days=7
    ),

    "ROTATE_REFRESH_TOKENS": True,

    "BLACKLIST_AFTER_ROTATION": True,

    "AUTH_HEADER_TYPES": ("Bearer",),

    "UPDATE_LAST_LOGIN": True,

}
```

These are illustrative settings. Adjust lifetimes and rotation policies to your application's risk and user-experience requirements.

## Step 3: Configure JWT URLs

Inside `config/urls.py`:

```python
from django.urls import path

from rest_framework_simplejwt.views import (
    TokenObtainPairView,
    TokenRefreshView,
    TokenVerifyView,
)


urlpatterns = [

    path(
        "api/token/",
        TokenObtainPairView.as_view(),
        name="token-obtain-pair"
    ),

    path(
        "api/token/refresh/",
        TokenRefreshView.as_view(),
        name="token-refresh"
    ),

    path(
        "api/token/verify/",
        TokenVerifyView.as_view(),
        name="token-verify"
    ),

]
```

## Step 4: Start the server

```bash
python manage.py runserver
```

## Step 5: Obtain a token pair

Request:

```http
POST /api/token/
Content-Type: application/json
```

Body:

```json
{
    "username": "john",
    "password": "password123"
}
```

Response:

```json
{
    "refresh": "REFRESH_TOKEN_VALUE",
    "access": "ACCESS_TOKEN_VALUE"
}
```

The values above are placeholders.

## Step 6: Access protected APIs

```http
GET /api/profile/

Authorization: Bearer ACCESS_TOKEN_VALUE
```

## Step 7: Refresh the access token

```http
POST /api/token/refresh/
Content-Type: application/json
```

Body:

```json
{
    "refresh": "REFRESH_TOKEN_VALUE"
}
```

Response when refresh rotation is disabled:

```json
{
    "access": "NEW_ACCESS_TOKEN"
}
```

With refresh rotation enabled, the response also includes a new refresh token.

## Important Simple JWT settings

| Setting | Purpose |
|---|---|
| `ACCESS_TOKEN_LIFETIME` | Access token validity |
| `REFRESH_TOKEN_LIFETIME` | Refresh token validity |
| `ROTATE_REFRESH_TOKENS` | Issue a new refresh token during refresh |
| `BLACKLIST_AFTER_ROTATION` | Blacklist the old refresh token after rotation |
| `AUTH_HEADER_TYPES` | Accepted Authorization header prefixes |
| `SIGNING_KEY` | Key used for token signing |
| `ALGORITHM` | JWT signing algorithm |
| `ISSUER` | Expected issuer claim |
| `AUDIENCE` | Expected audience claim |
| `LEEWAY` | Clock-skew allowance |
| `UPDATE_LAST_LOGIN` | Update user's last login on token creation |

**Security recommendation:** Do not casually use Django's `SECRET_KEY` as the JWT signing key. Use a separate, securely managed signing key. Consider asymmetric signing and key rotation for larger systems.

# 7. Access Tokens

## What is an Access Token?

An access token is a credential that allows a client to access protected APIs.

Example:

```http
GET /api/orders/

Authorization: Bearer ACCESS_TOKEN
```

The server validates the token and identifies the user.

## Why are access tokens short-lived?

Imagine an access token is stolen.

If it remains valid for 30 days, the attacker may have access for a long time.

If it expires in 15 minutes, the exposure window is much smaller.

That is why access tokens are generally short-lived.

Example configuration:

```python
SIMPLE_JWT = {

    "ACCESS_TOKEN_LIFETIME": timedelta(
        minutes=15
    ),

}
```

## Example protected endpoint

```python
from rest_framework.views import APIView

from rest_framework.response import Response

from rest_framework.permissions import IsAuthenticated


class MyProfileAPIView(APIView):

    permission_classes = [
        IsAuthenticated
    ]

    def get(self, request):

        return Response({

            "id": request.user.id,

            "username": request.user.username,

            "email": request.user.email

        })
```

## Expected response

```json
{
    "id": 10,
    "username": "john",
    "email": "john@example.com"
}
```

## What happens when the access token expires?

The client receives an authentication failure when it attempts to access a protected endpoint.

It should use a valid refresh token to obtain a new access token, provided the refresh token is still valid.

## Where should access tokens be stored?

This depends on the client architecture.

### Browser applications

A common secure design is to use:

- Short-lived access tokens.
- Secure, HttpOnly cookies where appropriate.
- CSRF protection for cookie-authenticated unsafe requests.
- A carefully designed refresh-token strategy.

Avoid casually storing long-lived credentials in browser local storage because JavaScript can access local storage and an XSS vulnerability can expose its contents.

### Mobile applications

Use the platform's secure storage facilities where possible.

## When should you use access tokens?

Whenever your API uses bearer-token authentication.

## Interview question

**Q: Why should access tokens be short-lived?**

Answer:

Short-lived access tokens reduce the period during which a stolen token can be reused. A refresh token can provide a controlled way to obtain new access tokens without asking the user to log in repeatedly.

# 8. Refresh Tokens

## What is a Refresh Token?

A refresh token is a credential used to obtain a new access token after the existing access token expires.

It is not normally used to access protected business endpoints directly.

Example:

```json
{
    "refresh": "REFRESH_TOKEN_VALUE"
}
```

## Why are refresh tokens needed?

Imagine a mobile application.

The user logs in at 9 AM.

The access token expires after 15 minutes.

Without refresh tokens, the user would need to log in every 15 minutes.

That would be a poor user experience.

With a refresh token, the application can obtain a new access token without asking for the password again.

## Access token vs Refresh token

| Feature | Access Token | Refresh Token |
|---|---|---|
| Purpose | Access protected API | Obtain new access token |
| Lifetime | Short | Longer |
| Sent to business APIs | Yes | Normally no |
| Used to refresh | No | Yes |
| Security impact if stolen | API access until expiry | Can enable continued token renewal |
| Storage | Carefully protected | More strongly protected |

## Example workflow

```text
User Login
    |
    v
Access Token + Refresh Token
    |
    v
Access Token Expires
    |
    v
Client Sends Refresh Token
    |
    v
Server Validates Refresh Token
    |
    v
New Access Token Issued
    |
    v
Client Continues Using API
```

## Refresh API example

```http
POST /api/token/refresh/
Content-Type: application/json
```

Body:

```json
{
    "refresh": "VALID_REFRESH_TOKEN"
}
```

Response without rotation:

```json
{
    "access": "NEW_ACCESS_TOKEN"
}
```

## When should you use refresh tokens?

Use them when:

- Access tokens expire quickly.
- Users should remain logged in.
- You need controlled session renewal.
- You support mobile or SPA clients.

## When should you not use refresh tokens?

They may not be needed for:

- Very short-lived one-time API credentials.
- Simple machine-to-machine calls where credentials can be obtained through another secure mechanism.
- Applications where every operation intentionally requires a new login.

Refresh tokens are high-value credentials. They should be stored securely and protected from theft and replay.

# 9. Token Rotation and Blacklisting

## What is Token Rotation?

Token rotation means issuing a new refresh token when an existing refresh token is used.

Suppose the client has:

```text
Refresh Token A
```

It uses that token to request a new access token.

The server issues:

```text
Access Token B
Refresh Token B
```

The old refresh token is invalidated or blacklisted.

This makes it harder for an attacker to reuse a stolen refresh token indefinitely.

## Why is rotation important?

Consider this scenario:

1. A user logs in.
2. An attacker steals the refresh token.
3. The user continues using the application.
4. Both the user and attacker attempt to refresh the token.

Refresh-token rotation can help detect reuse of an already rotated token, especially when the blacklist and token-family handling are designed correctly.

However, rotation alone is not a complete replay-detection system. Your application must handle concurrent refresh attempts carefully and define what happens when token reuse is detected.

## Configure rotation

```python
SIMPLE_JWT = {

    "ROTATE_REFRESH_TOKENS": True,

    "BLACKLIST_AFTER_ROTATION": True,

}
```

## What is Blacklisting?

Blacklisting means marking a token as invalid before its natural expiration.

For example, a user logs out.

The application blacklists the refresh token so that it cannot be used to obtain new access tokens.

## Step 1: Install blacklist app

In `settings.py`:

```python
INSTALLED_APPS = [

    "django.contrib.admin",

    "django.contrib.auth",

    "rest_framework",

    "rest_framework_simplejwt",

    "rest_framework_simplejwt.token_blacklist",

]
```

Run migrations:

```bash
python manage.py migrate
```

## Step 2: Configure rotation

```python
SIMPLE_JWT = {

    "ROTATE_REFRESH_TOKENS": True,

    "BLACKLIST_AFTER_ROTATION": True,

}
```

## Step 3: Create logout endpoint

```python
from rest_framework.views import APIView

from rest_framework.response import Response

from rest_framework.permissions import IsAuthenticated

from rest_framework import status

from rest_framework_simplejwt.tokens import RefreshToken

from rest_framework import serializers


class LogoutSerializer(serializers.Serializer):

    refresh = serializers.CharField()


class LogoutAPIView(APIView):

    permission_classes = [
        IsAuthenticated
    ]

    def post(self, request):

        serializer = LogoutSerializer(
            data=request.data
        )

        serializer.is_valid(
            raise_exception=True
        )

        try:

            token = RefreshToken(
                serializer.validated_data["refresh"]
            )

            token.blacklist()

        except Exception:

            return Response(
                {"detail": "Invalid refresh token."},
                status=status.HTTP_400_BAD_REQUEST
            )

        return Response(
            {"message": "Logged out successfully."},
            status=status.HTTP_200_OK
        )
```

In production, catch the specific token exceptions you expect rather than broadly catching every exception.

## Request

```http
POST /api/logout/

Authorization: Bearer ACCESS_TOKEN

Content-Type: application/json
```

Body:

```json
{
    "refresh": "REFRESH_TOKEN_VALUE"
}
```

Response:

```json
{
    "message": "Logged out successfully."
}
```

## Important limitation

Blacklisting a refresh token does not automatically invalidate every already-issued access token.

If an access token is self-contained and its signature and expiry remain valid, it may continue working until it expires unless you implement additional revocation checks.

That is one reason access tokens should have a short lifetime.

## When should you use rotation and blacklisting?

Use them when:

- You need logout functionality.
- Users can log in from multiple devices.
- Refresh tokens are long-lived.
- Security and token revocation matter.
- You need stronger protection against refresh-token replay.

# 10. Custom Authentication Classes

## What is a Custom Authentication Class?

A custom authentication class allows you to define your own authentication logic.

For example, your application might receive credentials through a custom header:

```http
X-API-KEY: company-secret-key
```

Or you might need to validate a signed request from an external service.

DRF allows you to create custom authentication classes by extending:

```python
BaseAuthentication
```

## Important method

The main method is:

```python
authenticate(self, request)
```

It should return:

```python
(user, auth)
```

when authentication succeeds.

It should return:

```python
None
```

if the authentication scheme was not attempted.

It should raise:

```python
AuthenticationFailed
```

if credentials were supplied but are invalid.

## Example: API key authentication

For demonstration, suppose we have a database model for API keys.

`models.py`:

```python
from django.db import models

from django.conf import settings


class APIKey(models.Model):

    user = models.ForeignKey(
        settings.AUTH_USER_MODEL,
        on_delete=models.CASCADE
    )

    key_hash = models.CharField(
        max_length=128,
        unique=True
    )

    is_active = models.BooleanField(
        default=True
    )
```

A production implementation should store a hash of the API key, not the raw key.

`authentication.py`:

```python
import hashlib
import hmac

from rest_framework.authentication import BaseAuthentication

from rest_framework.exceptions import AuthenticationFailed

from .models import APIKey


class APIKeyAuthentication(BaseAuthentication):

    def authenticate(self, request):

        api_key = request.headers.get(
            "X-API-KEY"
        )

        if not api_key:

            return None

        key_hash = hashlib.sha256(
            api_key.encode()
        ).hexdigest()

        try:

            api_key_object = APIKey.objects.select_related(
                "user"
            ).get(
                key_hash=key_hash,
                is_active=True
            )

        except APIKey.DoesNotExist:

            raise AuthenticationFailed(
                "Invalid API key"
            )

        return (
            api_key_object.user,
            api_key_object
        )
```

For an especially sensitive implementation, use a constant-time comparison when comparing stored and supplied hashes, and consider key expiry, scopes, rotation, rate limits, and audit records.

Use it when:

- Integrating with a legacy identity system.
- Authenticating third-party services.

# 11. OAuth2 Authentication

## What is OAuth 2.0?

OAuth 2.0 is an authorization framework.

It allows an application to obtain limited access to a resource on behalf of a user or as a client application.

For example:

You have an application called:

```text
MyShoppingApp
```

You want it to access a user's information from another service without asking for that service's password.

OAuth2 provides a way to obtain access tokens with defined permissions.

## Important distinction: OAuth2 vs OpenID Connect

OAuth2 is primarily about authorization.

OpenID Connect (OIDC) adds an identity layer on top of OAuth2.

OIDC provides an ID token and standardized identity information.

Use:

- OAuth2 when you need delegated API access.
- OIDC when you need user authentication and identity.

## Main OAuth2 roles

| Role | Meaning |
|---|---|
| Resource Owner | Usually the user |
| Client | Application requesting access |
| Authorization Server | Issues tokens |
| Resource Server | API that accepts tokens |

## Example

Imagine a user clicks:

```text
Sign in with Company Account
```

The application redirects the user to an identity provider.

The provider authenticates the user.

The user approves the requested permissions.

The application receives an authorization code and exchanges it for tokens.

## OAuth2 authorization code flow with PKCE

This is commonly used for browser-based and mobile applications.

```text
User
 |
 v
Client Application
 |
 v
Authorization Server
 |
 v
User Authenticates
 |
 v
Authorization Code
 |
 v
Client Exchanges Code + PKCE Verifier
 |
 v
Access Token
 |
 v
Protected API
```

PKCE helps protect the authorization code exchange against interception attacks.

## Common OAuth2 grant types

| Grant | Use case |
|---|---|
| Authorization Code + PKCE | User-facing web and mobile apps |
| Client Credentials | Machine-to-machine communication |
| Refresh Token | Renew access |
| Device Authorization | Devices with limited input capabilities |
| Resource Owner Password Credentials | Legacy flow; should not be used for new applications |

## OAuth scopes

Scopes describe the permissions requested or granted to a client.

Examples:

```text

write:orders
read:profile
```

A client with:

```text
read:orders
```

should not automatically be allowed to modify orders.

## When should you use OAuth2?

Use it when:

- Third-party applications access your APIs.
- You need delegated access.
- You support enterprise integrations.
- You need client credentials for service-to-service access.
- You integrate with an identity provider.

## When should you not use OAuth2?

Do not introduce a complete OAuth authorization server just to solve a simple login requirement if Django sessions or a JWT package are sufficient.

Also, do not confuse an OAuth access token with an ID token.

# 12. Social Authentication

## What is Social Authentication?

Social authentication allows users to sign in through an external identity provider.

Examples:

- Google.
- Apple.
- Facebook.
- Microsoft.
- GitHub.

Instead of creating a new password for every application, the user authenticates with an existing provider.

## How does social authentication work?

Example: Google login.

```text
User Clicks Google Login
          |
          v
Application Redirects to Google
          |
          v
User Authenticates
          |
          v
Google Returns Authorization Code
          |
          v
Backend or Client Exchanges Code
          |
          v
Application Validates Identity
          |
          v
Application Creates or Finds Local User
          |
          v
Application Establishes Its Own Session or Token
```

## Why use social authentication?

Advantages:

1. Easier onboarding.
2. Users do not need another password.
3. External provider handles credential verification.
4. Can support enterprise SSO.
5. Can reduce password-management responsibilities.

## Why not use social authentication?

Potential disadvantages:

- Dependency on external providers.
- Provider outages can affect login.
- Account-linking complexity.
- Additional privacy considerations.
- More complicated callback and token-validation logic.

## Example architecture

Your application may use:

```text
Google OAuth/OIDC
       |
       v
Identity Validation
       |
       v
Local Django User
       |
       v
Application JWT
```

The important point is that the external provider proves the user's identity. Your application still needs its own authorization rules.

## Common packages

Examples include:

```bash
pip install social-auth-app-django
```

Or:

```bash
pip install django-allauth
```

For DRF applications, packages such as `dj-rest-auth` can provide API-oriented authentication endpoints alongside compatible social-auth integrations.

Package versions and configuration vary, so follow the documentation for the specific versions you install.

## When should you use social authentication?

Use it for:

- Consumer applications.
- SaaS products.
- Applications with Google or Apple login.
- Enterprise applications with Microsoft identity.
- Applications that need federated login.

## Important security rule

Do not trust an email address supplied directly by the frontend.

Validate the provider's identity response and relevant token claims.

Also, account linking must be carefully designed so an attacker cannot link an external identity to another user's account merely by claiming the same email address.

# 13. AWS Cognito Integration

## What is AWS Cognito?

Amazon Cognito is an AWS identity service.

It provides user authentication, user management, federation, and token issuance.

A Cognito User Pool can act as an OpenID Connect identity provider.

It supports:

- User registration.
- User login.
- Password recovery.
- Multi-factor authentication.
- Social login federation.
- JWT issuance.
- OAuth2/OIDC flows.

## Why use Cognito?

Suppose you are building an application on AWS.

Instead of implementing all identity-management features yourself, you can use Cognito to manage:

- User credentials.
- Sign-in.
- Sign-up.
- Password recovery.
- Token generation.
- Identity federation.

Your Django API then validates the tokens issued by Cognito.

## Architecture

```text
Frontend / Mobile Application
            |
            v
     AWS Cognito
            |
            v
    User Authentication
            |
            v
      JWT Tokens
            |
            v
       Django API
            |
            v
    Validate Cognito JWT
            |
            v
      DRF Permissions
            |
            v
       API Response
```

## Cognito User Pool vs Identity Pool

These are different services and should not be confused.

| Feature | User Pool | Identity Pool |
|---|---|---|
| Main purpose | User directory and sign-in | AWS credential federation |
| Issues user JWTs | Yes | Not in the same way |
| Supports OIDC | Yes | Uses identity providers |
| Provides AWS credentials | Not directly | Yes |
| Typical use | Authenticate application users | Grant access to AWS resources |

| Token | Purpose |
|---|---|
| ID token | Contains identity claims |
| Access token | Authorizes API access and scopes |
| Refresh token | Obtains new tokens |

Cognito publishes public signing keys through a JWKS endpoint.

```text

```

The API uses these public keys to verify token signatures.

## Step 5: Custom Cognito authentication class

The following is a teaching example. It demonstrates the essential validation checks. A production implementation should use a robust JWKS cache, controlled network timeouts, key-rotation handling, and comprehensive exception handling.

`authentication.py`:

```python
import os
import jwt
import requests

from jwt import PyJWKClient

from django.contrib.auth import get_user_model

from rest_framework.authentication import BaseAuthentication

from rest_framework.exceptions import AuthenticationFailed


User = get_user_model()


REGION = os.environ["COGNITO_REGION"]

USER_POOL_ID = os.environ["COGNITO_USER_POOL_ID"]

CLIENT_ID = os.environ["COGNITO_CLIENT_ID"]


ISSUER = (
    f"https://cognito-idp.{REGION}.amazonaws.com/"
    f"{USER_POOL_ID}"
)

JWKS_URL = f"{ISSUER}/.well-known/jwks.json"


jwks_client = PyJWKClient(JWKS_URL)


class CognitoAuthentication(BaseAuthentication):

    def authenticate(self, request):

        header = request.headers.get(
            "Authorization"
        )

        if not header:

            return None

        parts = header.split()

        if len(parts) != 2 or parts[0].lower() != "bearer":

            raise AuthenticationFailed(
                "Invalid authorization header"
            )

        token = parts[1]

        try:

            signing_key = jwks_client.get_signing_key_from_jwt(
                token
            )

            payload = jwt.decode(

                token,

                signing_key.key,

                algorithms=["RS256"],

                issuer=ISSUER,

                options={
                    "verify_aud": False
                }

            )

            if payload.get("token_use") != "access":

                raise AuthenticationFailed(
                    "Access token required"
                )

            if payload.get("client_id") != CLIENT_ID:

                raise AuthenticationFailed(
                    "Invalid Cognito client"
                )

            username = payload.get("username")

            if not username:

                raise AuthenticationFailed(
                    "Token has no username claim"
                )

        except AuthenticationFailed:

            raise

        except Exception:

            raise AuthenticationFailed(
                "Invalid or expired Cognito token"
            )

        user, created = User.objects.get_or_create(

            username=f"cognito_{username}"

        )

        return (
            user,
            payload
        )
```

Important production considerations:

- Verify the exact claims required by your Cognito app configuration.
- Validate issuer and token use.
- Validate the expected client or audience where applicable.
- Validate scopes for protected API operations.
- Cache JWKS keys rather than downloading them for every request.
- Handle key rotation.
- Set network timeouts.
- Synchronize external identities with local users.
- Do not automatically trust arbitrary user attributes.

This example uses a username mapping for illustration. A production application should normally use a stable provider subject identifier, such as the Cognito `sub` claim, as the external identity key.

# 15. User Registration API

## What is a Registration API?

A registration API allows a new user to create an account.

Example:

```http
POST /api/register/
```

The user sends registration details.

The backend:

1. Validates the input.
2. Checks whether the email already exists.
3. Validates password strength.
4. Hashes the password.
5. Creates the user.
6. Returns a safe response.

## Step 1: Create registration serializer

`accounts/serializers.py`:

```python
from django.contrib.auth import get_user_model

from django.contrib.auth.password_validation import validate_password

from rest_framework import serializers


User = get_user_model()


class RegisterSerializer(serializers.ModelSerializer):

    password = serializers.CharField(

        write_only=True,

        required=True,

        validators=[validate_password]

    )

    password2 = serializers.CharField(

        write_only=True,

        required=True

    )

    class Meta:

        model = User

        fields = [

            "id",

            "username",

            "email",

            "password",

            "password2"

        ]

        read_only_fields = [
            "id"
        ]

    def validate(self, attrs):

        if attrs["password"] != attrs["password2"]:

            raise serializers.ValidationError({

                "password": "Passwords do not match."

            })

        return attrs

    def create(self, validated_data):

        validated_data.pop("password2")

        password = validated_data.pop("password")

        user = User(**validated_data)

        user.set_password(password)

        user.save()

        return user
```

Important:

`set_password()` hashes the password.

Never save a raw password directly into the database.

# 16. Login API

## What is a Login API?

A login API validates a user's credentials and establishes an authenticated session or issues authentication tokens.

With Simple JWT, the default login endpoint is:

```text
POST /api/token/
```

But in real applications, you may want a custom login endpoint that returns user details and tokens in a consistent response.

## Step 1: Configure custom token serializer

`accounts/serializers.py`:

```python
from rest_framework_simplejwt.serializers import TokenObtainPairSerializer


class CustomTokenObtainPairSerializer(TokenObtainPairSerializer):

    @classmethod
    def get_token(cls, user):

        token = super().get_token(user)

        token["username"] = user.username

        token["email"] = user.email

        return token
```

This adds claims to the refresh token and consequently to access tokens derived from it.

Only add claims that are safe to expose. Do not put passwords or secrets in JWT claims.

## Step 2: Create custom login view

`accounts/views.py`:

```python
from rest_framework_simplejwt.views import TokenObtainPairView

from .serializers import CustomTokenObtainPairSerializer


class LoginAPIView(TokenObtainPairView):

```


# 17. Logout API

## What is a Logout API?

A logout API ends an authenticated session or invalidates a refresh credential.

With session authentication, Django can delete the session.

With JWT authentication, logout usually means blacklisting the refresh token and removing the tokens from the client.

## Session logout example

```python
from django.contrib.auth import logout

from rest_framework.views import APIView

from rest_framework.response import Response

from rest_framework.permissions import IsAuthenticated


class SessionLogoutAPIView(APIView):

    permission_classes = [
        IsAuthenticated
    ]

    def post(self, request):

        logout(request)

        return Response({
            "message": "Logged out successfully"
        })
```

## JWT logout example

Use the logout endpoint from Topic 9.

Request:

```http
POST /api/logout/

Authorization: Bearer ACCESS_TOKEN

Content-Type: application/json
```

Body:

```json
{
    "refresh": "REFRESH_TOKEN_VALUE"
}
```

Response:

```json
{
    "message": "Logged out successfully."
}
```

## What should the frontend do?

After successful logout:

1. Remove locally stored access and refresh tokens.
2. Clear authenticated application state.
3. Redirect the user to the login screen.
4. Do not reuse the old refresh token.

## Important JWT logout limitation

Blacklisting a refresh token prevents future refresh operations with that token.

It does not automatically revoke every access token already issued from it.

If immediate access-token revocation is a requirement, consider:

- Very short access-token lifetimes.
- A server-side token-version or session-version check.
- A denylist for access-token identifiers.
- An opaque-token or server-side session architecture.

Each option has performance and operational trade-offs.

## When should you use logout?

Always provide a logout mechanism when your application supports persistent sessions or refresh tokens.

For applications with multiple devices, consider a separate logout-all-devices feature.

# 18. Password Hashing

## What is Password Hashing?

Password hashing transforms a password into a stored representation that is designed to be computationally difficult to reverse.

Example:

Original password:

```text
MyPassword123!
```

Stored representation:

```text
pbkdf2_sha256$...$...$...
```

The stored value is not the original password.

## Why do we need password hashing?

Suppose an attacker gains access to your user database.

If passwords are stored in plain text, the attacker immediately obtains users' passwords.

If passwords are stored using an appropriate password-hashing algorithm, the attacker has a much harder task.

## Hashing vs Encryption

| Feature | Hashing | Encryption |
|---|---|---|
| Purpose | One-way password storage | Reversible protection of data |
| Reversible | Not designed to be reversed | Yes, with the key |
| Typical use | Password storage | Protecting data that must be recovered |
| Password example | PBKDF2, Argon2 | Not recommended for password storage |

## Django password hashing

Django provides a built-in password-hashing framework.

By default, Django uses PBKDF2 with SHA-256.

It also supports other password hashers, including Argon2.

## Example 1: Create a hashed password

```python
from django.contrib.auth.hashers import make_password


password = "MyPassword123!"

hashed_password = make_password(password)

print(hashed_password)
```

Example output:

```text
pbkdf2_sha256$...$...$...
```

The exact output changes because Django uses a random salt.

## Example 2: Verify a password

```python
from django.contrib.auth.hashers import check_password


password = "MyPassword123!"

is_valid = check_password(
    password,
    hashed_password
)

print(is_valid)
```

Output:

```text
True
```

Wrong password:

```python
print(
    check_password(
        "WrongPassword",
        hashed_password
    )
)
```

Output:

```text
False
```

## Example 3: Using set_password()

For Django users, the preferred approach is:

```python
user.set_password(
    "MyPassword123!"
)

user.save()
```

To authenticate:

```python
from django.contrib.auth import authenticate


user = authenticate(

    username="john",

    password="MyPassword123!"

)

if user is not None:

    print("Login successful")

else:

    print("Invalid credentials")
```

For an email-based custom user model, ensure your authentication backend and username argument are configured appropriately.

## Configure password validators

Inside `settings.py`:

```python
AUTH_PASSWORD_VALIDATORS = [

    {
        "NAME":
        "django.contrib.auth.password_validation.UserAttributeSimilarityValidator"
    },

    {
        "NAME":
        "django.contrib.auth.password_validation.MinimumLengthValidator"
    },

    {
        "NAME":
        "django.contrib.auth.password_validation.CommonPasswordValidator"
    },

    {
        "NAME":
        "django.contrib.auth.password_validation.NumericPasswordValidator"
    },

]
```

## What is Argon2?

Argon2 is a modern password-hashing algorithm.

It is designed to make password guessing more expensive through configurable memory and computational requirements.

Install:

```bash
pip install django[argon2]
```

Configure:

```python
PASSWORD_HASHERS = [

    "django.contrib.auth.hashers.Argon2PasswordHasher",

    "django.contrib.auth.hashers.PBKDF2PasswordHasher",

    "django.contrib.auth.hashers.PBKDF2SHA1PasswordHasher",

    "django.contrib.auth.hashers.BCryptSHA256PasswordHasher",

]
```

Django uses the first hasher for new password hashes and retains the others for verifying existing hashes and upgrading them when appropriate.

## When should you use password hashing?

Always use Django's password-hashing facilities when storing passwords.

## What should you never do?

Never:

- Store plain-text passwords.
- Store passwords in JWT payloads.
- Use MD5 for password storage.
- Use plain SHA-256 as a substitute for password hashing.
- Log passwords.
- Return passwords in API responses.
- Encrypt passwords with a reversible key instead of using a password hasher.

# 19. Password Reset API

## What is a Password Reset API?

A password reset API allows users to recover access when they forget their password.

A secure password reset flow normally has two stages:

1. Request a password reset.
2. Confirm the reset using a time-limited, single-use token.

## Why do we need password reset?

Imagine a user forgets their password.

They should be able to reset it without contacting an administrator.

The backend should verify that the person requesting the reset controls the registered email address.

## Recommended password reset flow

```text
User Requests Password Reset
             |
             v
Backend Accepts Email
             |
             v
Generate Secure Reset Token
             |
             v
Send Email with Reset Link
             |
             v
User Opens Link
             |
             v
Frontend Sends Token + New Password
             |
             v
Backend Validates Token
             |
             v
Update Password
             |
             v
Reset Successful
```

## Important security requirements

- Use a time-limited token.
- Make tokens single-use.
- Do not reveal whether an email address exists.
- Rate-limit reset requests.
- Do not send passwords by email.
- Use HTTPS.
- Do not log reset tokens.
- Invalidate or re-evaluate existing sessions after password changes.
- Send a confirmation notification after successful reset.

## Step 1: Create password reset request serializer

`accounts/serializers.py`:

```python
from rest_framework import serializers


class PasswordResetRequestSerializer(serializers.Serializer):

    email = serializers.EmailField()
```

## Step 2: Create reset request API

Django provides a password reset token generator.

`accounts/views.py`:

```python
from django.contrib.auth import get_user_model

from django.contrib.auth.tokens import default_token_generator

from django.utils.encoding import force_bytes

from django.utils.http import urlsafe_base64_encode

from django.core.mail import send_mail

from django.conf import settings

from rest_framework.views import APIView

from rest_framework.response import Response

from rest_framework import status

from rest_framework.permissions import AllowAny

from .serializers import PasswordResetRequestSerializer


User = get_user_model()


class PasswordResetRequestAPIView(APIView):

    permission_classes = [
        AllowAny
    ]

    authentication_classes = []

    def post(self, request):

        serializer = PasswordResetRequestSerializer(
            data=request.data
        )

        serializer.is_valid(
            raise_exception=True
        )

        email = serializer.validated_data["email"]

        users = User.objects.filter(
            email__iexact=email,
            is_active=True
        )

        for user in users:

            uid = urlsafe_base64_encode(
                force_bytes(user.pk)
            )

            token = default_token_generator.make_token(
                user
            )

            reset_link = (
                f"https://frontend.example.com/reset-password/"
                f"?uid={uid}&token={token}"
            )

            send_mail(

                subject="Password Reset",

                message=(
                    f"Use this link to reset your password: "
                    f"{reset_link}"
                ),

                from_email=settings.DEFAULT_FROM_EMAIL,

                recipient_list=[user.email],

                fail_silently=False

            )

        return Response({

            "message": (
                "If an account exists for this email, "
                "password reset instructions will be sent."
            )

        }, status=status.HTTP_200_OK)
```

The generic response prevents the endpoint from revealing whether an account exists.

In production, enqueue email delivery using a background task system and apply rate limiting.

## Step 4: Create reset confirmation API

```python
from django.contrib.auth import get_user_model

from django.contrib.auth.tokens import default_token_generator

from django.utils.encoding import force_str

from django.utils.http import urlsafe_base64_decode

from rest_framework.views import APIView

from rest_framework.response import Response

from rest_framework import status

from rest_framework.permissions import AllowAny

from .serializers import PasswordResetConfirmSerializer


User = get_user_model()


class PasswordResetConfirmAPIView(APIView):

    permission_classes = [
        AllowAny
    ]

    authentication_classes = []

    def post(self, request):

        serializer = PasswordResetConfirmSerializer(
            data=request.data
        )

        serializer.is_valid(
            raise_exception=True
        )

        uid = serializer.validated_data["uid"]

        token = serializer.validated_data["token"]

        new_password = serializer.validated_data["new_password"]

        try:

            user_id = force_str(
                urlsafe_base64_decode(uid)
            )

            user = User.objects.get(
                pk=user_id
            )

        except (TypeError, ValueError, OverflowError, User.DoesNotExist):

            return Response({

                "detail": "Invalid reset link."

            }, status=status.HTTP_400_BAD_REQUEST)

        if not default_token_generator.check_token(
            user,
            token
        ):

            return Response({

                "detail": "Invalid or expired reset token."

            }, status=status.HTTP_400_BAD_REQUEST)

        user.set_password(
            new_password
        )

        user.save()

        return Response({

            "message": "Password reset successful."

        }, status=status.HTTP_200_OK)
```

Django's default token generator is designed to prevent reuse after the password changes and incorporates relevant user state into its token validity checks.

For high-security applications, consider whether you also need to revoke refresh tokens, invalidate existing sessions, and notify the user.

# PART 5: Common Security Mistakes

Avoid these mistakes in production.

## Mistake 1: Storing plain-text passwords

Incorrect:

```python
user.password = request.data["password"]
user.save()
```

Correct:

```python
user.set_password(
    request.data["password"]
)

user.save()
```

## Mistake 2: Using IsAuthenticated without ownership checks

Incorrect:

```python
permission_classes = [
    IsAuthenticated
]
```

This alone does not prevent a user from accessing another user's resource.

Correct:

```python
def get_queryset(self):

    return Order.objects.filter(
        user=self.request.user
    )
```

Also implement object-level authorization where appropriate.

## Mistake 3: Making access tokens too long-lived

Incorrect:

```python
"ACCESS_TOKEN_LIFETIME": timedelta(days=30)
```

This increases the time a stolen access token can remain usable.

Better starting point:

```python
"ACCESS_TOKEN_LIFETIME": timedelta(minutes=15)
```

Choose a duration based on risk and client requirements.

## Mistake 4: Putting sensitive information in JWT payloads

JWT payloads are generally readable by anyone holding the token.

Do not include:

- Passwords.
- API secrets.
- Private keys.
- Payment card information.
- Sensitive personal data.

## Mistake 5: Assuming logout automatically revokes access tokens

Blacklisting a refresh token does not automatically invalidate already-issued access tokens.

Use a revocation strategy appropriate to your security requirements.

## Mistake 6: Trusting frontend roles

Incorrect:

```json
{
    "username": "john",
    "role": "admin"
}
```

Never trust a role supplied by an untrusted client.

Load roles and permissions from trusted server-side data or validated identity-provider claims.

## Mistake 7: Forgetting CSRF protection

If your browser application uses cookie-based authentication, protect unsafe requests with appropriate CSRF controls.

## Mistake 8: No rate limiting on login

Attackers can repeatedly try passwords.

Use throttling, monitoring, account-protection mechanisms, and other anti-abuse controls.

## Mistake 9: Exposing account existence

A password reset endpoint should not return:

```text
Email address does not exist.
```

A generic response helps reduce account enumeration.

## Mistake 10: Not using HTTPS

Authentication credentials and tokens must be protected in transit.

Use HTTPS for all production authentication endpoints.

# PART 6: Interview Questions and Answers

## Beginner-level questions

### Q1. What is authentication?

Authentication is the process of verifying a user's identity.

For example, checking an email and password during login.

### Q2. What is authorization?

Authorization determines what an authenticated user is allowed to access or perform.

For example, a customer can view their own orders but cannot access the administrator dashboard.

### Q3. What is the difference between authentication and authorization?

Authentication answers who the user is.

Authorization answers what the user can do.

### Q4. What is authentication in DRF?

DRF authentication classes identify the user associated with an incoming request and populate `request.user` and `request.auth`.

### Q5. What is SessionAuthentication?

It uses Django's session framework to identify users through browser session cookies.

### Q6. What is Basic Authentication?

It sends a username and password in the HTTP Authorization header using Base64 encoding.

It must be protected by HTTPS.

### Q7. What is TokenAuthentication?

It uses a token sent in the Authorization header to authenticate API requests.

### Q8. What is JWT?

JWT is a compact token format containing claims that can be cryptographically signed.

### Q9. What are the three parts of a JWT?

Header, payload, and signature.

### Q10. Is JWT encrypted?

Not necessarily. A typical signed JWT is readable but protected against unauthorized modification through signature verification.

---

## Intermediate-level questions

### Q11. What is the difference between JWT and DRF TokenAuthentication?

DRF's built-in token authentication uses a database-backed token associated with a user.

JWT authentication uses a signed token containing claims that can generally be validated without a database lookup for the token itself.

JWT supports expiration and refresh-token workflows through packages such as Simple JWT.

### Q12. What is an access token?

An access token is a credential used to access protected APIs.

It is usually short-lived.

### Q13. What is a refresh token?

A refresh token is used to obtain a new access token after the old access token expires.

### Q14. Why do we need refresh tokens?

They allow users to remain logged in without repeatedly entering their password.

### Q15. What is token rotation?

Token rotation issues a new refresh token when an existing refresh token is used, allowing the old token to be invalidated.

### Q16. What is token blacklisting?

Token blacklisting marks a token as invalid before its natural expiry.

### Q17. Does JWT support logout automatically?

No. JWT is a token format, not a complete session-management system.

An application must implement a logout and revocation strategy.

### Q18. What is `IsAuthenticated`?

It is a DRF permission class that allows access only to authenticated users.

### Q19. What is `AllowAny`?

It allows any request to access the endpoint, subject to other applicable controls.

### Q20. What is `IsAdminUser`?

It allows access to users whose Django `is_staff` attribute is true.

---

## Advanced-level questions

### Q21. What is the difference between OAuth2 and JWT?

OAuth2 is an authorization framework.

JWT is a token format.

OAuth2 access tokens can be JWTs or opaque tokens.

They are not competing technologies.

### Q22. What is OpenID Connect?

OpenID Connect is an identity layer built on top of OAuth2.

It standardizes user authentication and provides ID tokens.

### Q23. What is PKCE?

Proof Key for Code Exchange is a security extension used with the OAuth2 authorization code flow.

It helps prevent authorization-code interception attacks.

### Q24. What is the difference between access token and ID token?

An access token is intended to authorize access to resources.

An ID token communicates authenticated user identity to an OIDC client.

Do not use an ID token as a substitute for an API access token.

### Q25. What is a custom authentication class in DRF?

It is a class extending `BaseAuthentication` that implements custom credential-validation logic through `authenticate()`.

### Q26. What does `authenticate()` return?

It returns:

```python
(user, auth)
```

if authentication succeeds.

It returns `None` if the scheme was not attempted.

It raises `AuthenticationFailed` if attempted credentials are invalid.

### Q27. Why should we use a custom user model?

It allows the application to customize identity fields and authentication requirements.

For example, email-based login.

### Q28. What is the difference between AbstractUser and AbstractBaseUser?

`AbstractUser` provides the standard Django user functionality.

`AbstractBaseUser` provides core authentication functionality but requires more implementation work.

### Q29. Why should passwords be hashed?

Hashing prevents the original password from being directly recovered from the stored password representation.

### Q30. Why should we use `set_password()`?

It uses Django's configured password-hashing system rather than storing a raw password.

### Q31. What is CSRF?

Cross-Site Request Forgery is an attack that attempts to make a browser perform an unwanted authenticated action.

Cookie-based authentication needs CSRF protection.

### Q32. What is the difference between 401 and 403?

401 generally means valid authentication credentials are missing or invalid.

403 means access is denied.

DRF's exact unauthenticated response depends partly on the authentication class.

### Q33. How do you secure a password reset API?

Use time-limited tokens, single-use validation, generic responses, rate limiting, HTTPS, and secure email delivery.

### Q34. How does Cognito integrate with Django?

Cognito authenticates users and issues tokens. Django validates the tokens using Cognito's public signing keys and then applies its own authorization rules.

### Q35. Why is storing JWT in localStorage risky?

JavaScript can access localStorage. An XSS vulnerability can therefore expose tokens stored there.

Use an appropriate browser credential-storage strategy, secure cookie configuration, CSRF controls where needed, and strong XSS prevention.

# PART 7: Scenario-Based Interview Questions

### Q36. Your application has a React frontend and Django REST backend. Which authentication approach would you consider?

Answer:

I would evaluate JWT or a secure cookie-based session architecture.

For a bearer-token architecture, Simple JWT is a common DRF option.

I would use short-lived access tokens, protected refresh tokens, refresh rotation where appropriate, and DRF permission classes.

### Q37. Your application is a traditional Django website. Would you choose JWT?

Answer:

Not automatically.

Django SessionAuthentication may be simpler because Django already manages login sessions and browser cookies.

### Q38. A user can log in successfully but cannot access another user's order. What concept is this?

Answer:

Authorization.

Authentication has identified the user, while an object-level permission or queryset filter prevents access to another user's order.

### Q39. A token is stolen. What would you do?

Answer:

I would revoke the refresh-token session, invalidate affected credentials where possible, and rely on short access-token lifetimes to limit exposure.

I would also investigate the compromise, rotate affected secrets if necessary, and consider forcing reauthentication.

### Q40. An administrator should access all orders, but a customer should see only their own. How would you implement this?

Answer:

I would filter the queryset according to the authenticated user and allow administrators broader access.

Example:

```python
def get_queryset(self):

    user = self.request.user

    if user.is_staff:

        return Order.objects.all()

    return Order.objects.filter(
        user=user
    )
```

I would also enforce permissions for any write operations.

### Q41. How would you implement login using Google?

Answer:

I would integrate Google through OpenID Connect or a maintained social-authentication package.

I would validate the provider's response, map the external identity to a local account, and establish the application's own session or token.

### Q42. How would you implement authentication for an AWS-hosted application?

Answer:

If the application needs managed user authentication and federation, I would evaluate Amazon Cognito User Pools.

The frontend authenticates through Cognito, receives tokens, and sends the appropriate access token to Django.

Django verifies the token's signature and claims, then applies application-level permissions.

### Q43. Why should registration and login endpoints be rate-limited?

Answer:

To reduce brute-force attacks, credential stuffing, automated account creation, and abuse.

### Q44. What happens if a JWT signing key is compromised?

Answer:

An attacker may be able to forge tokens if they possess the signing key.

I would rotate the key, invalidate affected tokens where possible, investigate the compromise, and review key-management controls.

With asymmetric signing, protecting the private signing key and distributing only public verification keys helps reduce the impact on consumers.

### Q45. Why is a custom user model recommended at the beginning of a Django project?

Answer:

Because changing the user model after database migrations and relationships have been established can be difficult.

Defining the model at the start avoids many migration and dependency problems.
