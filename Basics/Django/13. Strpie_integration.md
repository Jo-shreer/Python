# Complete Django Payment Gateway Integration – Stripe

## 1. What is payment gateway integration?

Payment gateway integration means connecting your Django application to an external payment provider such as:

- Stripe
- PayPal
- Razorpay
- Adyen
- Paystack

The payment gateway securely handles the customer's payment details and communicates the payment result to your application.

For example, imagine an e-commerce application:

1. Customer adds products to the cart.
2. Customer clicks **Pay Now**.
3. Django creates an order.
4. Django asks Stripe to create a Checkout Session.
5. Stripe returns a checkout URL.
6. The frontend redirects the customer to Stripe.
7. Customer enters their card details on Stripe's hosted payment page.
8. Stripe processes the payment.
9. Stripe sends a webhook to Django with the payment result.
10. Django verifies the webhook and updates the order as paid.
11. Customer sees the order confirmation.

**Important:** Never mark an order as paid just because the customer returns to your success URL. A customer can visit that URL without completing payment. The verified Stripe webhook is the reliable way to confirm the payment.

# 3. Stripe account and API credentials

First, create a Stripe account:

https://dashboard.stripe.com/register

Open the Stripe Dashboard and find the API keys in the Developers section.

You will generally receive:

```text
Publishable key: pk_test_...
Secret key: sk_test_...
```

You will also obtain a webhook signing secret when configuring a webhook endpoint:

```text
Webhook secret: whsec_...
```

### What is the publishable key?

The publishable key is designed for frontend use.

It identifies your Stripe account and can be used with Stripe's frontend libraries.

It is not a replacement for backend authentication or payment verification.

### What is the secret key?

The secret key allows your backend to perform privileged Stripe operations, such as:

- Creating Checkout Sessions
- Creating refunds
- Retrieving payment information
- Managing customers

Never expose this key in frontend JavaScript, mobile applications, GitHub, or public repositories.

### What is the webhook secret?

The webhook secret verifies that a webhook request genuinely came from Stripe.

It prevents an attacker from simply sending a fake HTTP request claiming that a payment succeeded.

### Why do we use environment variables?

We should not hardcode secrets inside Python files.

Bad approach:

```python
stripe.api_key = "sk_test_123456"
```

Better approach:

```python
stripe.api_key = settings.STRIPE_SECRET_KEY
```

Benefits:

- Keeps credentials outside the source code.
- Makes it easier to use different keys in development and production.
- Reduces the chance of accidentally exposing credentials.
- Makes deployment configuration easier.

For production, use your hosting provider's secret manager or environment configuration rather than relying on a committed `.env` file.

# 6. Create database models

## File: `payments/models.py`

We need three main database models:

1. Order
2. Payment
3. WebhookEvent

Why do we need three models?

- `Order` represents what the customer is purchasing.
- `Payment` stores the payment attempt and Stripe identifiers.
- `WebhookEvent` stores the Stripe event IDs we have processed to prevent duplicate processing.

```python
import uuid

from django.conf import settings
from django.db import models


class Order(models.Model):

    class Status(models.TextChoices):
        PENDING = "pending", "Pending"
        PAID = "paid", "Paid"
        CANCELLED = "cancelled", "Cancelled"
        FAILED = "failed", "Failed"
        REFUNDED = "refunded", "Refunded"

    user = models.ForeignKey(
        settings.AUTH_USER_MODEL,
        on_delete=models.PROTECT,
        related_name="orders"
    )

    order_number = models.UUIDField(
        default=uuid.uuid4,
        unique=True,
        editable=False
    )

    amount = models.DecimalField(
        max_digits=10,
        decimal_places=2
    )

    currency = models.CharField(
        max_length=3,
        default="eur"
    )

    status = models.CharField(
        max_length=20,
        choices=Status.choices,
        default=Status.PENDING
    )

    created_at = models.DateTimeField(
        auto_now_add=True
    )

    updated_at = models.DateTimeField(
        auto_now=True
    )

    def __str__(self):
        return str(self.order_number)


class Payment(models.Model):

    class Status(models.TextChoices):
        CREATED = "created", "Created"
        PENDING = "pending", "Pending"
        SUCCEEDED = "succeeded", "Succeeded"
        FAILED = "failed", "Failed"
        REFUNDED = "refunded", "Refunded"

    order = models.ForeignKey(
        Order,
        on_delete=models.PROTECT,
        related_name="payments"
    )

    public_id = models.UUIDField(
        default=uuid.uuid4,
        unique=True,
        editable=False
    )

    stripe_session_id = models.CharField(
        max_length=255,
        blank=True,
        null=True,
        unique=True
    )

    stripe_payment_intent_id = models.CharField(
        max_length=255,
        blank=True,
        null=True,
        unique=True
    )

    amount = models.DecimalField(
        max_digits=10,
        decimal_places=2
    )

    currency = models.CharField(
        max_length=3
    )

    status = models.CharField(
        max_length=20,
        choices=Status.choices,
        default=Status.CREATED
    )

    failure_reason = models.TextField(
        blank=True
    )

    created_at = models.DateTimeField(
        auto_now_add=True
    )

    updated_at = models.DateTimeField(
        auto_now=True
    )

    def __str__(self):
        return f"{self.order.order_number} - {self.status}"


class WebhookEvent(models.Model):

    stripe_event_id = models.CharField(
        max_length=255,
        unique=True
    )

    event_type = models.CharField(
        max_length=100
    )

    processed = models.BooleanField(
        default=False
    )

    created_at = models.DateTimeField(
        auto_now_add=True
    )

    def __str__(self):
        return self.stripe_event_id
```

## Detailed explanation of model parameters

### A. Order model

**`user`**

```python
user = models.ForeignKey(
    settings.AUTH_USER_MODEL,
    on_delete=models.PROTECT
)
```

What: Connects the order to the customer.

Why: We need to know which customer owns the order.

How: Django creates a foreign-key relationship with the configured user model.

Why `settings.AUTH_USER_MODEL` instead of directly importing `User`?

Because a project may use a custom user model. Referencing `settings.AUTH_USER_MODEL` makes the relationship compatible with that configuration.

Why `on_delete=models.PROTECT`?

It prevents deleting a user if that user still has related orders. This helps preserve financial and order history.

**`order_number`**

```python
order_number = models.UUIDField(
    default=uuid.uuid4,
    unique=True,
    editable=False
)
```

What: A unique order identifier.

Why: We need a reference that can be shared with the customer and used in APIs.

How: `uuid.uuid4` generates a random UUID.

`unique=True` prevents duplicate order numbers.

`editable=False` prevents ordinary editing through Django forms and admin.

**`amount`**

```python
amount = models.DecimalField(
    max_digits=10,
    decimal_places=2
)
```

What: Stores the order's monetary amount.

Why: We need to know how much the customer must pay.

Why `DecimalField` instead of `FloatField`?

Floating-point values can produce precision errors. Decimal values are more suitable for financial calculations.

Example:

```text
100.50 EUR
250.99 EUR
```

**`currency`**

```python
currency = models.CharField(max_length=3, default="eur")
```

What: Stores the ISO currency code.

Examples:

```text
eur
usd
gbp
inr
```

Why: A payment gateway needs to know which currency should be charged.

The supported currency and payment method depend on Stripe's current rules and your account configuration.

**`status`**

```python
status = models.CharField(
    max_length=20,
    choices=Status.choices,
    default=Status.PENDING
)
```

What: Represents the order's business status.

Why: We need to distinguish unpaid orders from paid, cancelled, and refunded orders.

Example:

```text
pending
paid
failed
cancelled
refunded
```

An important design point: an order's status and a payment attempt's status are not always identical. One order can have several payment attempts.

### B. Payment model

**`order`**

Connects a payment attempt to the order.

Why: One order may have multiple payment attempts if the customer retries after a declined card.

For example:

```text
Order #1001
    |
    |-- Payment attempt 1: Failed
    |
    |-- Payment attempt 2: Succeeded
```

**`public_id`**

A UUID used to identify the payment record inside your application.

Why: It is safer and more convenient to expose a non-sequential identifier in an API than a simple database integer.

It is not an authorization mechanism. Always check that the logged-in user owns the related order.

**`stripe_session_id`**

Stores the Stripe Checkout Session ID.

Example:

```text
cs_test_abc123
```

Why: It allows the backend to associate a Stripe Checkout Session with your local payment record.

**`stripe_payment_intent_id`**

Stores the Stripe PaymentIntent ID.

Example:

```text
pi_abc123
```

What is a PaymentIntent?

It represents Stripe's payment lifecycle for a particular payment.

It tracks payment confirmation, processing, success, and failure.

**`amount` and `currency`**

Store the exact amount and currency associated with this payment attempt.

Why duplicate these values when they also exist in the Order?

Because a payment record should preserve what was attempted at the time of payment. If an order changes later, historical payment information should not silently change.

**`failure_reason`**

Stores a useful internal failure description.

Do not expose sensitive gateway responses or raw internal exception details to customers.

### C. WebhookEvent model

**`stripe_event_id`**

Stores the unique ID of an incoming Stripe event.

Why: Stripe may deliver the same webhook more than once.

For example:

```text
evt_12345
evt_12345
evt_12345
```

The unique database constraint prevents the application from processing the same event as three separate payments.

**`event_type`**

Examples:

```text
checkout.session.completed
payment_intent.payment_failed
checkout.session.async_payment_succeeded
```

Why: It helps us identify what happened.

**`processed`**

Indicates whether our application completed the event handling.

Why: It helps with tracking and investigating webhook processing.

# 8. Create the Stripe payment service

## File: `payments/services.py`

This file contains the business logic for communicating with Stripe.

Why separate the Stripe code from views?

Because payment logic should not be duplicated across multiple API endpoints.

It also makes the code easier to test and maintain.

```python
from decimal import Decimal, ROUND_HALF_UP

import stripe

from django.conf import settings

from .models import Order, Payment


stripe.api_key = settings.STRIPE_SECRET_KEY


def convert_to_minor_units(amount):
    """
    Convert a decimal currency amount to an integer
    in the currency's smallest unit.
    """

    value = Decimal(amount)

    return int(
        (value * Decimal("100")).quantize(
            Decimal("1"),
            rounding=ROUND_HALF_UP
        )
    )


def create_stripe_checkout_session(payment):
    """
    Create a Stripe Checkout Session for a local payment.
    """

    order = payment.order

    amount_in_minor_units = convert_to_minor_units(
        payment.amount
    )

    session = stripe.checkout.Session.create(

        mode="payment",

        payment_method_types=["card"],

        line_items=[
            {
                "price_data": {
                    "currency": payment.currency,

                    "product_data": {
                        "name": f"Order {order.order_number}",
                    },

                    "unit_amount": amount_in_minor_units,
                },

                "quantity": 1,
            }
        ],

        client_reference_id=str(order.order_number),

        metadata={
            "order_number": str(order.order_number),
            "payment_id": str(payment.public_id),
        },

        payment_intent_data={
            "metadata": {
                "order_number": str(order.order_number),
                "payment_id": str(payment.public_id),
            }
        },

        success_url=(
            f"{settings.FRONTEND_URL}/payment/success"
            f"?session_id={{CHECKOUT_SESSION_ID}}"
        ),

        cancel_url=(
            f"{settings.FRONTEND_URL}/payment/cancel"
        ),

        idempotency_key=f"checkout-{payment.public_id}",
    )

    payment.stripe_session_id = session.id
    payment.status = Payment.Status.PENDING

    payment.save(
        update_fields=[
            "stripe_session_id",
            "status",
            "updated_at"
        ]
    )

    return session


def create_refund(payment, amount=None):
    """
    Create a Stripe refund.

    amount=None means refund the remaining refundable amount.
    """

    if not payment.stripe_payment_intent_id:
        raise ValueError(
            "Payment does not have a Stripe PaymentIntent."
        )

    params = {
        "payment_intent": payment.stripe_payment_intent_id,
        "reason": "requested_by_customer",
    }

    if amount is not None:
        refund_amount = Decimal(str(amount))

        if refund_amount <= 0:
            raise ValueError("Refund amount must be positive.")

        if refund_amount > payment.amount:
            raise ValueError(
                "Refund amount cannot exceed the payment amount."
            )

        params["amount"] = convert_to_minor_units(
            refund_amount
        )

    return stripe.Refund.create(
        **params,
        idempotency_key=f"refund-{payment.public_id}",
    )
```

## Detailed explanation of Stripe parameters

### 1. `mode="payment"`

What: Tells Stripe that this Checkout Session is for a one-time payment.

Why: Our example is for purchasing a product or service once.

Other common modes include:

- `payment`: One-time payment.
- `subscription`: Recurring subscription.
- `setup`: Save a payment method for future use without charging immediately.

### 2. `payment_method_types=["card"]`

What: Specifies the payment method types accepted by this Checkout Session.

Why: This example accepts card payments.

Other payment methods may be available depending on your Stripe account, country, currency, and configuration.

Stripe Checkout can also support dynamically configured payment methods. If using that approach, configure and verify the supported methods in your Stripe Dashboard.

### 3. `line_items`

What: Contains the items the customer is purchasing.

```python
line_items=[
    {
        "price_data": {
            "currency": payment.currency,
            "product_data": {
                "name": f"Order {order.order_number}",
            },
            "unit_amount": amount_in_minor_units,
        },
        "quantity": 1,
    }
]
```

**`price_data`**

Defines the price directly when creating the Checkout Session.

**`currency`**

Defines the payment currency.

**`product_data`**

Describes the item being purchased.

**`name`**

The product name shown during checkout.

**`unit_amount`**

The price of one item in the currency's smallest unit.

For example:

```text
€10.50 = 1050 cents
$25.00 = 2500 cents
```

Do not assume every currency has two decimal places. Some currencies have zero or three decimal places. For a production system supporting multiple currencies, use a currency-aware amount conversion function rather than multiplying everything by 100.

**`quantity`**

Number of units being purchased.

If the customer purchases three units at €10 each:

```text
unit_amount = 1000
quantity = 3
total = 3000 cents
```

Important: Never accept the final payment amount directly from the frontend. Calculate the price using trusted product and order information stored on the backend.

### 4. `client_reference_id`

```python
client_reference_id=str(order.order_number)
```

What: An optional reference that helps associate the Checkout Session with your own order.

Why: It makes it easier to identify the local order when investigating payment records.

### 5. `metadata`

```python
metadata={
    "order_number": str(order.order_number),
    "payment_id": str(payment.public_id),
}
```

What: Custom key-value information stored with the Stripe object.

Why: It helps identify which local payment and order are associated with a Stripe event.

For example, when Stripe sends a webhook, we can use the metadata to find the local payment.

Do not store passwords, card numbers, or other sensitive personal information in metadata.

### 6. `payment_intent_data`

```python
payment_intent_data={
    "metadata": {
        "order_number": str(order.order_number),
        "payment_id": str(payment.public_id),
    }
}
```

What: Passes configuration to the PaymentIntent created by Checkout.

Why: We also want our internal identifiers to be available on the PaymentIntent itself.

This is useful because some webhook events relate to PaymentIntents rather than Checkout Sessions.

### 7. `success_url`

```python
success_url=(
    "http://localhost:3000/payment/success"
    "?session_id={CHECKOUT_SESSION_ID}"
)
```

What: The URL Stripe redirects the customer to after a successful Checkout flow.

Why: The frontend can show a confirmation or retrieve the payment status from your backend.

Important: Reaching this URL does not prove that the payment has been received. Verify the payment using the webhook.

### 8. `cancel_url`

What: The URL Stripe redirects the customer to when they cancel Checkout.

Why: The frontend can show a message such as:

```text
Payment cancelled. You can try again.
```

Do not automatically mark the order as failed just because the customer visits the cancellation URL. The customer may still retry payment, and the Checkout Session's actual status should be handled appropriately.

### 9. `idempotency_key`

```python
idempotency_key=f"checkout-{payment.public_id}"
```

What: A unique key identifying a particular API operation.

Why: Network problems can occur after Stripe creates a Checkout Session but before Django receives the response.

If Django retries the same request using the same idempotency key, Stripe can recognize it as the same operation rather than creating a second Checkout Session.

This reduces accidental duplicate operations.

Use a new payment-attempt identifier for a genuinely new payment attempt. Do not reuse an old idempotency key for a different payment.

# 9. Create the request serializer

## File: `payments/serializers.py`

The serializer validates API input.

In our example, the customer sends only the order ID. The customer does not send the payment amount or currency.

```python
from rest_framework import serializers

from .models import Order


class CreatePaymentSerializer(serializers.Serializer):

    order_number = serializers.UUIDField(
        required=True
    )

    def validate_order_number(self, value):

        request = self.context["request"]

        try:
            order = Order.objects.get(
                order_number=value,
                user=request.user
            )
        except Order.DoesNotExist:
            raise serializers.ValidationError(
                "Order not found."
            )

        if order.status != Order.Status.PENDING:
            raise serializers.ValidationError(
                "This order is not available for payment."
            )

        if order.amount <= 0:
            raise serializers.ValidationError(
                "Order amount must be greater than zero."
            )

        return value
```

### Parameter explanation

**`serializers.Serializer`**

Creates a serializer for validating incoming API data.

**`order_number`**

The UUID supplied by the frontend.

**`required=True`**

Means the customer must provide this field.

**`self.context["request"]`**

Provides access to the current HTTP request.

Why do we need it?

Because we must check that the requested order belongs to the logged-in customer.

**`Order.objects.get()`**

Finds the order using both:

- The order number.
- The authenticated user.

This prevents one customer from initiating payment for another customer's order.

**`validate_order_number()`**

A field-level validation method.

Django REST Framework automatically calls this method when validating `order_number`.

Why validate the order status?

We should not accept a payment for an already paid or cancelled order.

# 10. Create the payment API view

## File: `payments/views.py`

```python
import stripe

from django.db import transaction

from rest_framework.views import APIView
from rest_framework.permissions import IsAuthenticated
from rest_framework.response import Response
from rest_framework import status

from .models import Order, Payment
from .serializers import CreatePaymentSerializer
from .services import create_stripe_checkout_session


class CreatePaymentView(APIView):

    permission_classes = [IsAuthenticated]

    def post(self, request):

        serializer = CreatePaymentSerializer(
            data=request.data,
            context={"request": request}
        )

        serializer.is_valid(raise_exception=True)

        order_number = serializer.validated_data[
            "order_number"
        ]

        try:

            with transaction.atomic():

                order = Order.objects.select_for_update().get(
                    order_number=order_number,
                    user=request.user
                )

                if order.status != Order.Status.PENDING:
                    return Response(
                        {"error": "Order is not payable."},
                        status=status.HTTP_400_BAD_REQUEST
                    )

                payment = Payment.objects.create(
                    order=order,
                    amount=order.amount,
                    currency=order.currency,
                    status=Payment.Status.CREATED
                )

            session = create_stripe_checkout_session(
                payment
            )

            return Response(
                {
                    "message": "Checkout session created.",
                    "payment_id": str(payment.public_id),
                    "checkout_url": session.url,
                    "session_id": session.id,
                    "publishable_key": (
                        stripe.api_key is not None
                        and None
                    ),
                },
                status=status.HTTP_201_CREATED
            )

        except stripe.StripeError:
            return Response(
                {
                    "error": (
                        "Unable to create payment. "
                        "Please try again."
                    )
                },
                status=status.HTTP_502_BAD_GATEWAY
            )
```

For the response, the publishable key should normally be configured on the frontend or exposed through a dedicated public configuration endpoint. It is not needed in this Checkout redirect response. Therefore, remove the `publishable_key` entry from the response above. The final response should be:

```python
return Response(
    {
        "message": "Checkout session created.",
        "payment_id": str(payment.public_id),
        "checkout_url": session.url,
        "session_id": session.id,
    },
    status=status.HTTP_201_CREATED
)
```

## Explanation of each important part

### `APIView`

```python
class CreatePaymentView(APIView):
```

Provides a class-based REST API endpoint.

Why: It allows us to define HTTP methods such as `get()`, `post()`, `put()`, and `delete()`.

### `permission_classes = [IsAuthenticated]`

What: Requires the user to be logged in.

Why: Anonymous customers should not be allowed to initiate payments against arbitrary orders.

### `post(self, request)`

What: Handles an HTTP POST request.

Why: Creating a payment session changes server-side state, so POST is appropriate.

### `serializer.is_valid(raise_exception=True)`

What: Validates the incoming request data.

Why: It stops invalid data from reaching the payment logic.

### `transaction.atomic()`

What: Runs database operations inside a transaction.

Why: If a database operation fails, changes made within the transaction are rolled back.

### `select_for_update()`

What: Locks the selected order row until the database transaction finishes.

Why: It helps prevent two concurrent requests from simultaneously performing certain operations on the same order.

Important: Database locking behavior depends on the database engine. Use a database such as PostgreSQL for this type of row-locking workflow.

### `Payment.objects.create()`

Creates a local payment attempt before calling Stripe.

Why: We need an internal payment record to associate with the Stripe Checkout Session.

### `create_stripe_checkout_session(payment)`

Calls our service function to create the Stripe Checkout Session.

### `session.url`

Stripe returns the hosted Checkout URL.

The frontend redirects the customer to this URL.

### `status.HTTP_201_CREATED`

Means the server successfully created a resource.

### `stripe.StripeError`

Catches Stripe-specific errors.

Why: Stripe may return errors because of invalid requests, authentication problems, network issues, or service problems.

For production, log the internal exception details securely and consider a controlled retry strategy. Do not expose raw gateway errors to the customer.

**Production note:** The example is a learning implementation. Before production, add stronger handling for concurrent payment attempts, abandoned sessions, Stripe API timeouts, and recovery of payments created by Stripe when the local request fails. Do not hold a database transaction open while waiting for an external API call.

# 12. Implement Stripe webhooks

## What is a webhook?

A webhook is an HTTP request sent by one application to another application when a particular event occurs.

For example:

```text
Customer completes payment
        |
        v
Stripe processes payment
        |
        v
Stripe sends webhook
        |
        v
Django receives event
        |
        v
Django verifies signature
        |
        v
Django updates payment and order
```

Why do we need webhooks?

Because the frontend may close, lose internet connectivity, or never return to your success URL.

Stripe can still notify Django about the payment result.

## File: `payments/webhooks.py`

```python
import json
import logging

import stripe

from django.conf import settings
from django.db import transaction
from django.http import HttpResponse, HttpResponseBadRequest
from django.views.decorators.csrf import csrf_exempt

from .models import Order, Payment, WebhookEvent


logger = logging.getLogger(__name__)


@csrf_exempt
def stripe_webhook(request):

    if request.method != "POST":
        return HttpResponseBadRequest(
            "Only POST requests are allowed."
        )

    payload = request.body

    signature = request.headers.get(
        "Stripe-Signature"
    )

    if not signature:
        return HttpResponseBadRequest(
            "Missing Stripe signature."
        )

    try:

        event = stripe.Webhook.construct_event(
            payload=payload,
            sig_header=signature,
            secret=settings.STRIPE_WEBHOOK_SECRET
        )

    except ValueError:
        return HttpResponseBadRequest(
            "Invalid payload."
        )

    except stripe.SignatureVerificationError:
        return HttpResponseBadRequest(
            "Invalid webhook signature."
        )

    event_id = event["id"]
    event_type = event["type"]

    try:

        with transaction.atomic():

            webhook_event, created = (
                WebhookEvent.objects.get_or_create(
                    stripe_event_id=event_id,
                    defaults={
                        "event_type": event_type,
                        "processed": False,
                    }
                )
            )

            if not created and webhook_event.processed:
                return HttpResponse(status=200)

            if not created:
                webhook_event = (
                    WebhookEvent.objects.select_for_update()
                    .get(pk=webhook_event.pk)
                )

                if webhook_event.processed:
                    return HttpResponse(status=200)

            handle_stripe_event(event)

            webhook_event.processed = True
            webhook_event.save(
                update_fields=["processed"]
            )

    except Payment.DoesNotExist:
        logger.exception(
            "Payment not found for Stripe event %s",
            event_id
        )
        return HttpResponse(status=500)

    except Exception:
        logger.exception(
            "Failed to process Stripe event %s",
            event_id
        )
        return HttpResponse(status=500)

    return HttpResponse(status=200)


def handle_stripe_event(event):

    event_type = event["type"]
    data = event["data"]["object"]

    if event_type in [
        "checkout.session.completed",
        "checkout.session.async_payment_succeeded",
    ]:

        payment_id = data.get("metadata", {}).get(
            "payment_id"
        )

        if not payment_id:
            logger.error(
                "Missing payment_id in Checkout Session metadata."
            )
            return

        payment = Payment.objects.select_for_update().get(
            public_id=payment_id
        )

        if data.get("payment_status") == "paid":

            payment.status = Payment.Status.SUCCEEDED

            payment.stripe_session_id = data["id"]

            payment.stripe_payment_intent_id = (
                data.get("payment_intent")
            )

            payment.save(
                update_fields=[
                    "status",
                    "stripe_session_id",
                    "stripe_payment_intent_id",
                    "updated_at",
                ]
            )

            order = payment.order

            order.status = Order.Status.PAID

            order.save(
                update_fields=["status", "updated_at"]
            )

    elif event_type == "checkout.session.async_payment_failed":

        payment_id = data.get("metadata", {}).get(
            "payment_id"
        )

        if payment_id:

            payment = Payment.objects.select_for_update().get(
                public_id=payment_id
            )

            payment.status = Payment.Status.FAILED

            payment.failure_reason = (
                "Asynchronous payment failed."
            )

            payment.save(
                update_fields=[
                    "status",
                    "failure_reason",
                    "updated_at",
                ]
            )

    elif event_type == "payment_intent.payment_failed":

        payment_intent_id = data["id"]

        payment = Payment.objects.select_for_update().filter(
            stripe_payment_intent_id=payment_intent_id
        ).first()

        if payment:

            payment.status = Payment.Status.FAILED

            payment.failure_reason = (
                data.get("last_payment_error", {}).get(
                    "message",
                    "Payment failed."
                )
            )

            payment.save(
                update_fields=[
                    "status",
                    "failure_reason",
                    "updated_at",
                ]
            )
```

## Detailed explanation of webhook parameters

### 1. `@csrf_exempt`

What: Disables Django's normal CSRF check for this particular endpoint.

Why: Stripe is an external service and cannot provide your Django user's CSRF token.

Security requirement: Disabling CSRF must not mean accepting unverified requests. Always validate the Stripe webhook signature.

### 2. `request.body`

What: The raw HTTP request body.

Why: Stripe's signature verification requires the original request payload.

Do not parse and re-serialize the JSON before verifying the signature. Even small differences in the payload can break signature verification.

### 3. `request.headers.get("Stripe-Signature")`

What: Retrieves Stripe's signature header.

Why: Stripe uses this header together with the webhook signing secret to verify the request.

### 4. `stripe.Webhook.construct_event()`

```python
event = stripe.Webhook.construct_event(
    payload=payload,
    sig_header=signature,
    secret=settings.STRIPE_WEBHOOK_SECRET
)
```

**`payload`**

The raw HTTP body sent by Stripe.

**`sig_header`**

The signature header from the incoming request.

**`secret`**

The webhook signing secret configured in your environment.

What happens?

Stripe's SDK checks the signature and parses the event.

If verification fails, the application rejects the request.

### 5. `event["id"]`

Unique Stripe event ID.

Why: Used for webhook idempotency.

### 6. `event["type"]`

Identifies the event.

Examples:

```text
checkout.session.completed
checkout.session.async_payment_succeeded
checkout.session.async_payment_failed
payment_intent.payment_failed
```

### 7. `WebhookEvent.objects.get_or_create()`

Checks whether this event has already been recorded.

Why: Stripe can retry webhook delivery.

The unique constraint on `stripe_event_id` protects against inserting duplicate event records.

### 8. `transaction.atomic()`

Makes database updates together as one transaction.

Why: We should not mark the webhook as processed if the payment and order updates fail.

### 9. `select_for_update()`

Locks the relevant payment record while it is being updated.

Why: It helps prevent concurrent webhook processing from modifying the same payment simultaneously.

### 10. `payment.status = Payment.Status.SUCCEEDED`

Updates the local payment attempt to successful.

### 11. `order.status = Order.Status.PAID`

Updates the order's business status.

Why: Once the payment is verified as successful, the application can proceed with fulfilment.

### Important production improvements

This webhook example demonstrates the main pattern, but production payment processing needs additional safeguards:

1. Check that the Checkout Session's `payment_status` is actually `paid` before marking an order paid.
2. Compare the Stripe amount and currency against the stored payment amount and currency.
3. Ensure the PaymentIntent belongs to the expected payment.
4. Make every event handler safe to run more than once.
5. Handle `payment_intent.succeeded` as well if your application uses PaymentIntents directly.
6. Handle refunds using Stripe refund events such as `charge.refunded`.
7. Handle delayed payment methods and asynchronous events.
8. Record events that cannot yet be matched to a local payment for investigation.
9. Return a non-2xx response if a temporary failure means the event was not processed.
10. Use a durable background job or outbox pattern for slow operations such as sending emails or fulfilment.

A particularly important point: the sample handler currently returns normally when metadata is missing. In a production system, distinguish between intentionally ignored events and events that should be retried or flagged for investigation.

# 16. How to implement a payment status API

A customer should be able to retrieve the current status of their payment.

For example:

```http
GET /api/payments/<payment_id>/status/
```

A basic view:

```python
from rest_framework.views import APIView
from rest_framework.permissions import IsAuthenticated
from rest_framework.response import Response
from rest_framework import status

from .models import Payment


class PaymentStatusView(APIView):

    permission_classes = [IsAuthenticated]

    def get(self, request, payment_id):

        payment = Payment.objects.filter(
            public_id=payment_id,
            order__user=request.user
        ).select_related("order").first()

        if not payment:
            return Response(
                {"error": "Payment not found."},
                status=status.HTTP_404_NOT_FOUND
            )

        return Response(
            {
                "payment_id": str(payment.public_id),
                "payment_status": payment.status,
                "order_number": str(
                    payment.order.order_number
                ),
                "order_status": payment.order.status,
                "amount": str(payment.amount),
                "currency": payment.currency,
            },
            status=status.HTTP_200_OK
        )
```

Add the URL:

```python
path(
    "<uuid:payment_id>/status/",
    PaymentStatusView.as_view(),
    name="payment-status"
),
```

Why use `select_related("order")`?

Because the view accesses `payment.order`.

`select_related()` retrieves the related order through a SQL join, reducing additional database queries.

Why check `order__user=request.user`?

Because a customer should only retrieve the status of their own payment.

# 17. How to implement refunds

A refund means returning some or all of the money to the customer.

There are two common refund types:

**Full refund:** Return the entire refundable amount.

**Partial refund:** Return only a portion of the payment.

Example:

```text
Original payment: €100
Partial refund: €30
Remaining amount: €70
```

The `create_refund()` function in `services.py` shows how to call Stripe's refund API.

However, a production refund endpoint must also:

1. Require an authorized staff user or an appropriate customer action.
2. Verify the payment belongs to the expected order.
3. Check the amount already refunded.
4. Prevent the total refund from exceeding the amount captured.
5. Store the Stripe Refund ID.
6. Handle refund events from Stripe.
7. Update the local refund and order status based on verified results.

For a production system, create a separate `Refund` model rather than storing only one refund status on `Payment`. One payment can have multiple partial refunds.

Example model:

```python
class Refund(models.Model):

    payment = models.ForeignKey(
        Payment,
        on_delete=models.PROTECT,
        related_name="refunds"
    )

    stripe_refund_id = models.CharField(
        max_length=255,
        unique=True
    )

    amount = models.DecimalField(
        max_digits=10,
        decimal_places=2
    )

    status = models.CharField(
        max_length=30
    )

    created_at = models.DateTimeField(
        auto_now_add=True
    )
```

Why separate refunds?

Because a payment may have:

```text
Payment: €100

Refund 1: €20
Refund 2: €30
Refund 3: €10

Total refunded: €60
Remaining refundable: €40
```

The refund model preserves the history of each refund.

# 18. Important payment integration features

These are important concepts to understand for production development and interviews.

## A. Idempotency

What: Ensures repeating the same operation does not create duplicate effects.

Why: A client may retry a request because of a timeout or network failure.

Example:

```text
Customer clicks Pay
       |
       v
Django sends request to Stripe
       |
       v
Stripe creates Checkout Session
       |
       v
Network timeout occurs
       |
       v
Django retries
```

Without idempotency, duplicate Checkout Sessions may be created.

Use Stripe idempotency keys for API operations and database uniqueness constraints for local identifiers.

Webhook processing also needs idempotency because events can be delivered repeatedly.

## B. Webhook signature verification

What: Verifies that an incoming webhook was signed by Stripe.

Why: Attackers could otherwise send a fake request such as:

```json
{
    "payment_status": "paid"
}
```

Never update the payment status based only on incoming JSON.

## C. Payment state management

A useful payment state flow:

```text
CREATED
   |
   v
PENDING
   |
   +-----------> SUCCEEDED
   |
   +-----------> FAILED
   |
   +-----------> REFUNDED
```

Real payment flows can be more complex.

For example, a delayed payment method can remain processing after the customer finishes Checkout.

Do not assume that every Checkout completion means the payment is immediately settled.

## D. Database transactions

What: A transaction groups database operations into a single unit.

Why: If updating a payment and order must happen together, both updates should succeed or fail together.

Example:

```python
from django.db import transaction

with transaction.atomic():

    payment.status = Payment.Status.SUCCEEDED
    payment.save()

    order.status = Order.Status.PAID
    order.save()
```

Important: Database transactions do not automatically include external Stripe API calls. Stripe and PostgreSQL are separate systems.

For reliable workflows, use idempotency, durable event handling, reconciliation, and sometimes the transactional outbox pattern.

## E. Payment reconciliation

What: Comparing your local payment records with Stripe's records.

Why: Network problems, failed webhook processing, and operational mistakes can cause temporary differences between the two systems.

A reconciliation process can:

1. Find payments stuck in pending status.
2. Retrieve their corresponding Stripe objects.
3. Compare amounts, currencies, and statuses.
4. Update records when the Stripe state is verified.
5. Flag mismatches for manual investigation.

## F. Logging and monitoring

Log useful identifiers:

```text
order_number
payment_id
stripe_session_id
stripe_payment_intent_id
stripe_event_id
event_type
```

Avoid logging:

- Secret API keys.
- Full card numbers.
- CVC values.
- Sensitive authentication information.
- Unnecessary personal information.

Use structured logging and monitoring tools such as Sentry or your organization's observability platform.

## G. Retry and timeout handling

External services can become temporarily unavailable.

A production integration should define:

- Connection timeouts.
- Read timeouts.
- Retry rules.
- Exponential backoff.
- Maximum retry attempts.
- Alerting when retries are exhausted.

Do not blindly retry every payment operation. Use idempotency keys and understand whether an operation is safe to repeat.

## H. Payment security

Important practices:

1. Use HTTPS.
2. Store API secrets securely.
3. Never trust the payment amount from the frontend.
4. Verify webhook signatures.
5. Authenticate payment creation requests.
6. Check order ownership.
7. Prevent duplicate payment attempts.
8. Keep an audit trail.
9. Do not store raw card details.
10. Use Stripe-hosted Checkout or appropriately validated Stripe payment components.

Using Stripe Checkout reduces your direct exposure to card data, but you still need to follow the relevant PCI DSS requirements for your integration.

# 19. Payment integration interview questions and answers

## Q1. What is a payment gateway?

A payment gateway is a service that enables an application to accept and process payments securely.

Examples include Stripe, PayPal, Razorpay, and Adyen.

It communicates with payment networks and returns the payment result to the merchant application.

## Q2. Explain the complete payment flow in Django.

First, the customer selects an order and clicks Pay Now.

Django verifies the order and calculates the amount using backend data.

It creates a local payment record and calls Stripe to create a Checkout Session.

Stripe returns a Checkout URL, and Django sends that URL to the frontend.

The frontend redirects the customer to Stripe.

After payment, Stripe sends a webhook to Django.

Django verifies the webhook signature, checks for duplicate events, and updates the payment and order status.

## Q3. What is a Stripe Checkout Session?

A Checkout Session represents a customer's session on Stripe's hosted checkout page.

It contains information such as:

- Payment mode.
- Currency.
- Line items.
- Amount.
- Success URL.
- Cancellation URL.
- Metadata.

It provides a convenient way to integrate payments without building your own card-entry page.

## Q4. What is a PaymentIntent?

A PaymentIntent represents the lifecycle of a payment.

It helps Stripe manage the payment confirmation process and track whether a payment succeeds, fails, or requires additional action.

A Checkout Session in payment mode generally creates a PaymentIntent.

## Q5. What is the difference between Checkout Session and PaymentIntent?

| Checkout Session | PaymentIntent |
|---|---|
| Manages the hosted Checkout experience | Manages the payment lifecycle |
| Contains Checkout page information | Tracks payment confirmation and status |
| Provides a Checkout URL | Does not represent a hosted checkout page |
| Useful for hosted payment pages | Useful for direct payment integrations |

## Q6. Why do we use webhooks?

Because the frontend cannot reliably communicate payment success.

The customer might close the browser or lose their internet connection.

Stripe webhooks notify our backend directly about payment events.

## Q7. Why do we verify webhook signatures?

To confirm that the webhook request genuinely came from Stripe.

Without signature verification, someone could send a fake payment-success request.

## Q8. What is idempotency?

Idempotency means repeating the same request does not produce duplicate effects.

It is useful when network timeouts or client retries occur.

Stripe supports idempotency keys for API operations.

## Q9. What happens if Stripe processes payment but Django does not receive the response?

The application should not assume the payment failed.

It should use the same idempotency key when safely retrying the operation, and use webhooks or Stripe API retrieval to determine the actual payment status.

## Q10. What happens if Stripe sends the same webhook multiple times?

Django checks the event ID against the `WebhookEvent` table.

If the event was already processed, it returns a successful response without repeating the payment update.

## Q11. What happens if the customer closes the browser after paying?

Stripe can still send the webhook to Django.

The backend updates the payment status even though the frontend is no longer open.

## Q12. Why should we not trust the frontend payment-success response?

Frontend data can be manipulated.

A customer can visit a success page without completing payment.

The backend should trust verified gateway events or independently retrieved Stripe payment information.

## Q13. How do you prevent duplicate payments?

Use several protections:

- Database constraints.
- Payment-attempt identifiers.
- Stripe idempotency keys.
- Webhook event deduplication.
- Order state validation.
- Appropriate database locking.
- Reconciliation.

## Q14. How do you handle payment failure?

Stripe sends the relevant failure event.

Django verifies the event, identifies the payment, records the failure, and keeps the order in an appropriate unpaid state.

The customer can then retry if business rules allow it.

## Q15. What is a partial refund?

A partial refund returns only part of the original payment.

For example, if the customer paid €100, the merchant may refund €25.

The application should store each refund separately and ensure the total refunded amount never exceeds the captured amount.

## Q16. How do you secure payment integration?

I use environment variables for secrets, HTTPS, authenticated payment APIs, backend-side amount calculations, webhook signature verification, idempotency, and careful logging.

I never store raw card details in my application database.

## Q17. What is payment reconciliation?

Payment reconciliation compares the local database with the payment gateway's records.

It helps identify missing webhook updates, payments stuck in pending status, and discrepancies.

## Q18. What is the difference between synchronous and asynchronous payment processing?

In synchronous processing, the application waits for the external API response before continuing.

In asynchronous processing, the application can accept an event or enqueue work and process it later.

Payment gateway API calls are commonly initiated synchronously, while webhook-triggered follow-up tasks such as emails and order fulfilment can be processed asynchronously using Celery.

## Q19. How would you handle high payment traffic?

I would:

- Keep payment APIs stateless where possible.
- Use database indexes.
- Use connection pooling where appropriate.
- Avoid long database transactions.
- Process non-critical tasks asynchronously.
- Use idempotency.
- Monitor gateway response times.
- Use queues for fulfilment and notifications.
- Apply rate limiting and sensible retry policies.

## Q20. What would you do if a payment is successful in Stripe but failed in your database?

I would first retrieve the Stripe payment information and verify the amount, currency, and payment identifier.

Then I would inspect webhook delivery and application logs.

I would reconcile the local record with the verified Stripe state and make the update idempotently.

I would also investigate why the original webhook update failed.

                    |

                    |
                    v
             STRIPE WEBHOOK
                    |
                    v
          WEBHOOK VERIFICATION
                    |
                    v
            PAYMENT DATABASE
                    |
                    v
              CELERY QUEUE
                    |
          +---------+----------+
          |                    |
          v                    v
      SEND EMAIL          UPDATE INVENTORY
          |                    |
          v                    v
      CUSTOMER              ORDER
      NOTIFICATION          FULFILMENT

### Why use Celery?

Some tasks should not delay the webhook response.

For example:

- Sending confirmation emails.
- Generating invoices.
- Updating external CRM systems.
- Notifying warehouse services.
- Updating analytics.

A common approach is:

1. Verify the webhook.
2. Save the payment update in the database.
3. Record a durable job or outbox event in the same database transaction.
4. Return a successful webhook response.
5. Process the follow-up work asynchronously.

The outbox pattern helps prevent a situation where the payment is marked successful but the application crashes before publishing the notification job.

# 21. Common mistakes in payment integration

| Mistake | Why it is a problem | Correct approach |
|---|---|---|
| Trusting frontend success | Can be manipulated | Verify Stripe webhook |
| Hardcoding secret key | Exposes credentials | Use secret storage |
| Taking amount from frontend | Customer can change price | Calculate on backend |
| Not checking order ownership | Unauthorized payments | Check authenticated user |
| Not using idempotency | Duplicate operations | Use idempotency keys |
| Not handling webhook retries | Duplicate updates | Store unique event IDs |
| Ignoring payment failures | Incorrect order status | Handle failure events |
| Not checking currency | Incorrect payment records | Compare currency |
| Storing card details | Creates serious security risk | Use Stripe-hosted payment UI |
| Sending email inside webhook | Slow webhook processing | Use background tasks |
| Assuming success URL means paid | Payment may not be complete | Use verified payment status |
| Not reconciling payments | Records can become inconsistent | Scheduled reconciliation |

# 22. How to explain this project in an interview

You can explain the implementation like this:

"I integrated Stripe payment gateway into a Django REST Framework application.

First, I created Order and Payment models to maintain order information and payment attempts separately.

When a customer clicks Pay Now, the backend validates the order, checks ownership, and calculates the amount using trusted database information.

Then I create a local payment record and use the Stripe SDK to create a Checkout Session. Stripe returns a hosted checkout URL, which I send to the frontend.

The frontend redirects the customer to Stripe to complete the payment.

After the payment, Stripe sends a webhook to my Django backend. I verify the webhook signature using the Stripe webhook secret, check the event ID to avoid duplicate processing, and update the payment and order status.

I also handle payment failures, retries, refunds, and webhook events.

For security, I use environment variables for credentials, backend-side amount calculation, authenticated APIs, webhook verification, and idempotency keys.

For production readiness, I would also implement payment reconciliation, monitoring, durable asynchronous processing, and audit logging."
