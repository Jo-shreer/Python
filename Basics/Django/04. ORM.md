# Part 5: Django ORM Fundamentals

# Introduction: What is Django ORM?

ORM stands for **Object-Relational Mapping**.

Django ORM allows us to interact with a relational database using Python code instead of writing SQL queries manually.

For example, suppose we have an Employee table in PostgreSQL.

Without ORM, we might write:

```sql
SELECT * FROM employee;
```

Using Django ORM:

```python
Employee.objects.all()
```

Both retrieve employee records.

Similarly, SQL:

```sql
INSERT INTO employee (name, email)
VALUES ('John', 'john@example.com');
```

Django ORM:

```python
Employee.objects.create(
    name='John',
    email='john@example.com'
)
```

Django ORM translates Python operations into SQL queries and executes them against the configured database.

## Why use Django ORM?

1. You can work with databases using Python.
2. It reduces the amount of SQL you need to write.
3. It supports multiple database engines.
4. It provides model relationships.
5. It helps protect against SQL injection when used correctly.
6. It supports transactions.
7. It provides query optimization techniques.
8. It integrates with Django models, serializers and admin.

## How does Django ORM work?

Consider this flow:

```text
Django Application
       |
       v
Django ORM
       |
       v
SQL Query Generation
       |
       v
Database
       |
       v
Query Result
       |
       v
Django Model Objects
```

For example:

```python
employees = Employee.objects.all()
```

Django ORM generates an SQL query similar to:

```sql
SELECT * FROM employee;
```

The database returns the records, and Django converts them into Python model objects.

# 69. Models and Model Fields

## What is a Model?

A Django model is a Python class that represents a database table.

Each model attribute generally represents a database column.

For example:

```python
from django.db import models

class Employee(models.Model):

    name = models.CharField(max_length=100)

    email = models.EmailField()

    age = models.IntegerField()

    salary = models.DecimalField(
        max_digits=10,
        decimal_places=2
    )

    joining_date = models.DateField()

    is_active = models.BooleanField(default=True)
```

This model represents an Employee database table.

### How does it map to a database?

| Django model field | Database column |
|---|---|
| `name` | VARCHAR |
| `email` | VARCHAR |
| `age` | INTEGER |
| `salary` | DECIMAL |
| `joining_date` | DATE |
| `is_active` | BOOLEAN |

The exact SQL types can vary by database backend.

### What happens when Django creates the table?

Run:

```bash
python manage.py makemigrations
```

This creates a migration file describing the model changes.

Then:

```bash
python manage.py migrate
```

This applies the migration to the database.

Django normally creates a primary key automatically if you do not define one.

For example, the database table will have an automatically generated `id` field.

You can access it using:

```python
employee.id
```

or:

```python
employee.pk
```

`pk` is Django's generic shortcut for the primary key.

## Common Django Model Fields

### 1. CharField

Used for short strings.

```python
name = models.CharField(max_length=100)
```

Example values:

```text
John
David
Software Engineer
```

Why use it?

Use it for names, titles, department names and other relatively short text.

Important: `max_length` is required.

### 2. TextField

Used for longer text.

```python
description = models.TextField()
```

Example:

```text
Employee is responsible for backend development...
```

When to use it?

Use it for descriptions, comments, notes and long-form content.

### 3. IntegerField

Used for integer values.

```python
age = models.IntegerField()
```

Example:

```text
25
30
45
```

### 4. DecimalField

Used for precise decimal numbers.

```python
salary = models.DecimalField(
    max_digits=10,
    decimal_places=2
)
```

Example:

```text
55000.50
```

Why use it?

Use it for financial values such as salaries, prices and payments.

Avoid using `FloatField` for financial calculations when exact decimal precision matters.

### 5. FloatField

Used for floating-point numbers.

```python
rating = models.FloatField()
```

Example:

```text
4.5
3.75
```

### 6. BooleanField

Used for True/False values.

```python
is_active = models.BooleanField(default=True)
```

Example:

```python
employee.is_active = False
employee.save()
```

### 7. DateField

Stores a date.

```python
joining_date = models.DateField()
```

Example:

```text
2026-01-15
```

### 8. DateTimeField

Stores a date and time.

```python
created_at = models.DateTimeField(auto_now_add=True)

updated_at = models.DateTimeField(auto_now=True)
```

Difference:

- `auto_now_add=True`: Sets the value when the object is first created.
- `auto_now=True`: Updates the value whenever the model is saved.

### 9. EmailField

Used for email addresses.

```python
email = models.EmailField(unique=True)
```

Django provides email-format validation through its model field validation mechanisms.

`unique=True` also creates a database uniqueness constraint.

### 10. URLField

Used for URLs.

```python
website = models.URLField()
```

### 11. FileField

Used to upload files.

```python
resume = models.FileField(
    upload_to='resumes/'
)
```

Files are stored using the configured storage system. The database stores the file name or path, not normally the file contents.

### 12. ImageField

Used to upload images.

```python
profile_image = models.ImageField(
    upload_to='employee_images/'
)
```

ImageField requires Pillow to be installed.

```bash
pip install Pillow
```

## Important Model Field Options

### null=True

Allows the database column to contain SQL NULL.

```python
phone = models.CharField(
    max_length=20,
    null=True
)
```

### blank=True

Allows the field to be empty during Django form and model validation.

```python
phone = models.CharField(
    max_length=20,
    blank=True
)
```

### default

Provides a default value.

```python
is_active = models.BooleanField(default=True)
```

### unique=True

Ensures that values are unique in the database.

```python
email = models.EmailField(unique=True)
```

### db_index=True

Creates a database index for a field.

```python
email = models.EmailField(db_index=True)
```

### primary_key=True

Defines the primary key.

```python
employee_code = models.CharField(
    max_length=20,
    primary_key=True
)
```

If you define your own primary key, Django will not add its normal automatic primary key.

## null=True vs blank=True

This is a very important distinction.

| Option | Meaning |
|---|---|
| `null=True` | Database can store NULL |
| `blank=True` | Django validation permits an empty value |

Example:

```python
phone = models.CharField(
    max_length=20,
    blank=True,
    null=True
)
```

For string fields, Django commonly recommends using `blank=True` without `null=True`, so that empty strings represent empty values consistently.

## When should you use models?

Use Django models whenever your application needs to store and manage structured database information.

Examples:

- Employee management
- E-commerce products
- Customer records
- Orders and payments
- Blog posts
- User profiles

# 70. Model Relationships

## What are model relationships?

Model relationships define how database tables are connected.

For example:

An Employee belongs to a Department.

A Department can have many Employees.

An Employee can have a Profile.

An Employee can work on multiple Projects.

These relationships are represented using Django relationship fields.

Django provides three main relationship types:

1. One-to-One
2. One-to-Many
3. Many-to-Many

### Example database structure

```text
Department
    |
    | One-to-Many
    |
 Employee
    |
    | One-to-One
    |
EmployeeProfile
    |
    | Many-to-Many
    |
 Project
```

Each relationship serves a different purpose.

---

# 71. One-to-One Relationships

## What is a One-to-One relationship?

A One-to-One relationship means one record in a table is associated with only one record in another table, and vice versa.

Example:

One Employee has one EmployeeProfile.

One EmployeeProfile belongs to one Employee.

### Real-world example

An Employee table:

| id | name |
|---|---|
| 1 | John |
| 2 | David |

An EmployeeProfile table:

| id | employee_id | address |
|---|---|---|
| 1 | 1 | Dublin |
| 2 | 2 | London |

Each employee has one profile.

## How to implement One-to-One in Django

```python
from django.db import models

class Employee(models.Model):

    name = models.CharField(max_length=100)

    email = models.EmailField()


class EmployeeProfile(models.Model):

    employee = models.OneToOneField(
        Employee,
        on_delete=models.CASCADE,
        related_name='profile'
    )

    address = models.CharField(max_length=200)

    phone = models.CharField(max_length=20)
```

### Understanding OneToOneField

```python
employee = models.OneToOneField(
    Employee,
    on_delete=models.CASCADE,
    related_name='profile'
)
```

- `Employee`: The model being connected.
- `on_delete=models.CASCADE`: If the employee is deleted, the related profile is deleted.
- `related_name='profile'`: Defines how to access the profile from the employee.

## Creating records

```python
employee = Employee.objects.create(
    name='John',
    email='john@example.com'
)

profile = EmployeeProfile.objects.create(
    employee=employee,
    address='Dublin',
    phone='123456789'
)
```

## Accessing the profile

From the Employee:

```python
employee = Employee.objects.get(id=1)

print(employee.profile.address)
```

Output:

```text
Dublin
```

From the Profile:

```python
profile = EmployeeProfile.objects.get(id=1)

print(profile.employee.name)
```

Output:

```text
John
```

### What if the profile does not exist?

Accessing:

```python
employee.profile
```

may raise:

```python
EmployeeProfile.DoesNotExist
```

You can handle this using:

```python
try:
    profile = employee.profile
except EmployeeProfile.DoesNotExist:
    profile = None
```

## Why use One-to-One?

Use it when you want to separate optional or additional information from the main model.

Examples:

- User and UserProfile
- Employee and EmployeeProfile
- Customer and CustomerDetails
- Product and ProductSpecification

Why not put every field into one table?

Separating related information can make the database design cleaner and keep the main model focused.

# 72. One-to-Many Relationships

## What is a One-to-Many relationship?

One record in a parent table can be associated with many records in another table.

However, each child record belongs to one parent.

Example:

One Department can have many Employees.

One Employee belongs to one Department.

### Database example

Department table:

| id | name |
|---|---|
| 1 | IT |
| 2 | HR |

Employee table:

| id | name | department_id |
|---|---|---|
| 1 | John | 1 |
| 2 | David | 1 |
| 3 | Sarah | 2 |

Notice:

- John belongs to IT.
- David belongs to IT.
- Sarah belongs to HR.

The foreign key is stored in the Employee table.

## How to implement One-to-Many

In Django, use `ForeignKey`.

```python
from django.db import models

class Department(models.Model):

    name = models.CharField(max_length=100)


class Employee(models.Model):

    name = models.CharField(max_length=100)

    email = models.EmailField()

    department = models.ForeignKey(
        Department,
        on_delete=models.CASCADE,
        related_name='employees'
    )
```

### Understanding ForeignKey

```python
department = models.ForeignKey(
    Department,
    on_delete=models.CASCADE,
    related_name='employees'
)
```

- `Department`: The parent model.
- `ForeignKey`: Creates a many-to-one relationship from Employee to Department.
- `on_delete=models.CASCADE`: Deleting the department also deletes its employees.
- `related_name='employees'`: Allows reverse access from Department to Employee records.

## Creating records

```python
department = Department.objects.create(
    name='IT'
)

Employee.objects.create(
    name='John',
    email='john@example.com',
    department=department
)

Employee.objects.create(
    name='David',
    email='david@example.com',
    department=department
)
```

## Accessing the department from an employee

```python
employee = Employee.objects.get(id=1)

print(employee.department.name)
```

Output:

```text
IT
```

## Accessing employees from a department

```python
department = Department.objects.get(id=1)

employees = department.employees.all()

for employee in employees:
    print(employee.name)
```

Output:

```text
John
David
```

This is called reverse relationship access.

### What if related_name is not specified?

Django creates a default reverse accessor.

For example:

```python
department.employee_set.all()
```

Using `related_name='employees'` allows:

```python
department.employees.all()
```

## Why use One-to-Many?

Use it when many records belong to one parent record.

Examples:

- Department → Employees
- Customer → Orders
- Author → Books
- Category → Products
- Blog → Posts

One-to-Many is one of the most common database relationships.

# 73. Many-to-Many Relationships

## What is a Many-to-Many relationship?

A Many-to-Many relationship means multiple records in one table can be associated with multiple records in another table.

Example:

An Employee can work on many Projects.

A Project can have many Employees.

### Database example

Employee table:

| id | name |
|---|---|
| 1 | John |
| 2 | David |

Project table:

| id | name |
|---|---|
| 1 | Website |
| 2 | Mobile App |

Relationship table:

| employee_id | project_id |
|---|---|
| 1 | 1 |
| 1 | 2 |
| 2 | 1 |

This means:

- John works on Website.
- John works on Mobile App.
- David works on Website.

The relationship is stored in a separate intermediate table.

## How to implement Many-to-Many

Use `ManyToManyField`.

```python
from django.db import models

class Employee(models.Model):

    name = models.CharField(max_length=100)

    projects = models.ManyToManyField(
        'Project',
        related_name='employees'
    )


class Project(models.Model):

    name = models.CharField(max_length=100)
```

Django automatically creates an intermediate relationship table.

## Creating records

```python
employee1 = Employee.objects.create(
    name='John'
)

employee2 = Employee.objects.create(
    name='David'
)

project1 = Project.objects.create(
    name='Website'
)

project2 = Project.objects.create(
    name='Mobile App'
)
```

## Adding relationships

```python
employee1.projects.add(project1)

employee1.projects.add(project2)

employee2.projects.add(project1)
```

You can add multiple projects at once:

```python
employee1.projects.add(
    project1,
    project2
)
```

## Accessing projects for an employee

```python
employee = Employee.objects.get(id=1)

projects = employee.projects.all()

for project in projects:
    print(project.name)
```

Output:

```text
Website
Mobile App
```

## Accessing employees for a project

```python
project = Project.objects.get(id=1)

employees = project.employees.all()

for employee in employees:
    print(employee.name)
```

Output:

```text
John
David
```

## Other Many-to-Many methods

### add()

Adds relationships.

```python
employee.projects.add(project1)
```

### remove()

Removes a relationship without deleting either object.

```python
employee.projects.remove(project1)
```

### clear()

Removes all relationships for that employee.

```python
employee.projects.clear()
```

### set()

Replaces the existing relationships.

```python
employee.projects.set([
    project1,
    project2
])
```

## What is through in ManyToManyField?

Sometimes the relationship itself needs additional information.

For example:

An Employee works on a Project, but we also want to store:

- Assigned date
- Role
- Hours worked

In that case, create a custom intermediate model.

```python
class Employee(models.Model):

    name = models.CharField(max_length=100)

    projects = models.ManyToManyField(
        'Project',
        through='EmployeeProject',
        related_name='employees'
    )


class Project(models.Model):

    name = models.CharField(max_length=100)


class EmployeeProject(models.Model):

    employee = models.ForeignKey(
        Employee,
        on_delete=models.CASCADE
    )

    project = models.ForeignKey(
        Project,
        on_delete=models.CASCADE
    )

    assigned_date = models.DateField()

    role = models.CharField(max_length=100)

    class Meta:
        constraints = [
            models.UniqueConstraint(
                fields=['employee', 'project'],
                name='unique_employee_project'
            )
        ]
```

Now the relationship contains additional business information.

Create a relationship:

```python
EmployeeProject.objects.create(
    employee=employee1,
    project=project1,
    assigned_date='2026-01-15',
    role='Backend Developer'
)
```

## When to use Many-to-Many?

Examples:

- Students ↔ Courses
- Employees ↔ Projects
- Products ↔ Categories
- Users ↔ Groups
- Articles ↔ Tags

# 74. QuerySets

## What is a QuerySet?

A QuerySet is a collection of database records returned by a Django ORM query.

Example:

```python
employees = Employee.objects.all()
```

Here, `employees` is a QuerySet.

It represents all Employee records.

## What is a Manager?

A Manager is the interface through which Django models interact with the database.

The default manager is:

```python
Employee.objects
```

Therefore:

```python
Employee.objects.all()
```

means:

Use the Employee model's default manager to retrieve all records.

## Example

```python
employees = Employee.objects.all()

for employee in employees:
    print(employee.name)
```

Output:

```text
John
David
Sarah
```

## QuerySets are lazy

This is an important concept.

Django QuerySets are generally lazy.

That means Django does not necessarily execute the SQL query immediately when you construct a QuerySet.

Example:

```python
employees = Employee.objects.filter(
    department__name='IT'
)
```

At this point, Django has constructed a QuerySet.

The database query is normally executed when the QuerySet is evaluated.

Examples of evaluation include:

```python
for employee in employees:
    print(employee.name)
```

```python
list(employees)
```

```python
len(employees)
```

```python
bool(employees)
```

```python
employees.exists()
```

The exact query execution behavior varies by operation.

## QuerySet chaining

You can combine multiple filters.

```python
employees = Employee.objects.filter(
    is_active=True
).filter(
    age__gte=25
)
```

You can also write:

```python
employees = Employee.objects.filter(
    is_active=True,
    age__gte=25
)
```

Both represent records matching both conditions.

## QuerySet methods

| Method | Purpose |
|---|---|
| `all()` | Retrieves all matching records |
| `filter()` | Retrieves matching records |
| `exclude()` | Excludes matching records |
| `get()` | Retrieves one matching record |
| `order_by()` | Sorts records |
| `values()` | Returns dictionaries |
| `values_list()` | Returns tuples or flat values |
| `distinct()` | Removes duplicate results |
| `count()` | Counts matching records |
| `exists()` | Checks whether matching records exist |
| `first()` | Returns the first matching object |
| `last()` | Returns the last matching object |

## Ordering example

```python
employees = Employee.objects.order_by('name')
```

Ascending order:

```text
David
John
Sarah
```

Descending order:

```python
employees = Employee.objects.order_by('-name')
```

## values()

Returns dictionaries instead of model objects.

```python
employees = Employee.objects.values(
    'id',
    'name',
    'email'
)
```

Example result:

```python
[
    {
        'id': 1,
        'name': 'John',
        'email': 'john@example.com'
    },
    {
        'id': 2,
        'name': 'David',
        'email': 'david@example.com'
    }
]
```

## values_list()

Returns tuples by default.

```python
Employee.objects.values_list(
    'name',
    'email'
)
```

Example:

```python
[
    ('John', 'john@example.com'),
    ('David', 'david@example.com')
]
```

For a single field:

```python
Employee.objects.values_list(
    'name',
    flat=True
)
```

Example:

```python
['John', 'David']
```

## When to use QuerySets?

Use QuerySets whenever you need to retrieve, filter, sort, count or otherwise work with database records.

They are the foundation of most Django ORM operations.

# 75. Filtering and Excluding Records

## What is filter()?

`filter()` retrieves records that match specified conditions.

Example:

```python
employees = Employee.objects.filter(
    is_active=True
)
```

This retrieves only active employees.

Equivalent SQL:

```sql
SELECT *
FROM employee
WHERE is_active = TRUE;
```

## Filtering by exact value

```python
Employee.objects.filter(
    name='John'
)
```

## Filtering by greater than

```python
Employee.objects.filter(
    age__gt=25
)
```

This retrieves employees older than 25.

## Filtering by greater than or equal

```python
Employee.objects.filter(
    age__gte=25
)
```

## Filtering by less than

```python
Employee.objects.filter(
    age__lt=30
)
```

## Filtering by less than or equal

```python
Employee.objects.filter(
    age__lte=30
)
```

## Filtering by contains

```python
Employee.objects.filter(
    name__contains='Jo'
)
```

Matches names containing `Jo`.

## Case-insensitive contains

```python
Employee.objects.filter(
    name__icontains='jo'
)
```

This can match `John`, `JOHN` or `john`.

## Starts with

```python
Employee.objects.filter(
    name__startswith='J'
)
```

## Ends with

```python
Employee.objects.filter(
    name__endswith='n'
)
```

## IN lookup

```python
Employee.objects.filter(
    department__name__in=['IT', 'HR']
)
```

Retrieves employees belonging to IT or HR.

## Date filtering

```python
Employee.objects.filter(
    joining_date__year=2026
)
```

Or:

```python
Employee.objects.filter(
    joining_date__month=1
)
```

## Relationship filtering

Django allows filtering across related models using double underscores.

```python
Employee.objects.filter(
    department__name='IT'
)
```

This retrieves employees whose department name is IT.

## What is exclude()?

`exclude()` returns records that do not match the given condition.

Example:

```python
Employee.objects.exclude(
    department__name='HR'
)
```

This returns employees who are not in HR.

Equivalent SQL is conceptually:

```sql
SELECT *
FROM employee
WHERE NOT (department_name = 'HR');
```

## Multiple conditions

```python
Employee.objects.filter(
    is_active=True,
    age__gte=25
)
```

Both conditions must match.

## Using Q objects for OR conditions

By default, multiple filter conditions are combined using AND.

But sometimes we need OR.

Example:

Employees belonging to IT OR HR.

```python
from django.db.models import Q

employees = Employee.objects.filter(
    Q(department__name='IT') |
    Q(department__name='HR')
)
```

### AND using Q

```python
employees = Employee.objects.filter(
    Q(is_active=True) &
    Q(age__gte=25)
)
```

### NOT using Q

```python
employees = Employee.objects.filter(
    ~Q(department__name='HR')
)
```

## Why use filter() and exclude()?

Use them to retrieve only the data your application needs.

This is especially important in REST APIs because returning unnecessary database records increases response size and processing time.

# 76. get(), filter() and all()

These three methods are among the most commonly used Django ORM methods.

## 1. all()

Returns a QuerySet containing all records matching the manager or existing QuerySet.

```python
employees = Employee.objects.all()
```

Use it when you want to retrieve a collection.

Result:

```text
<QuerySet [Employee object (1), Employee object (2)]>
```

## 2. filter()

Returns a QuerySet containing records matching the conditions.

```python
employees = Employee.objects.filter(
    is_active=True
)
```

Important:

`filter()` can return:
- Zero records.
- One record.
- Multiple records.

It does not raise an exception merely because no records match.

## 3. get()

Returns one object matching the condition.

```python
employee = Employee.objects.get(
    id=1
)
```

It expects exactly one matching record.

### What happens if no record exists?

It raises:

```python
Employee.DoesNotExist
```

### What happens if multiple records match?

It raises:

```python
Employee.MultipleObjectsReturned
```

## Comparison

| Method | Return type | Multiple records? | No match? |
|---|---|---|---|
| `all()` | QuerySet | Yes | Empty QuerySet |
| `filter()` | QuerySet | Yes | Empty QuerySet |
| `get()` | Model object | No | Raises DoesNotExist |

## Example: get()

```python
try:
    employee = Employee.objects.get(id=10)

    print(employee.name)

except Employee.DoesNotExist:
    print('Employee not found')
```

## Example: filter()

```python
employees = Employee.objects.filter(
    department__name='IT'
)

for employee in employees:
    print(employee.name)
```

## When should you use each?

Use `all()` when you need all records.

Use `filter()` when you need zero or more matching records.

Use `get()` when you expect exactly one record, commonly when retrieving an object by its unique identifier.

In DRF, `get_object_or_404()` is often useful when retrieving a single object because it converts a missing object into an HTTP 404 response.

Example:

```python
from django.shortcuts import get_object_or_404

employee = get_object_or_404(
    Employee,
    id=10
)
```

# 77. select_related()

## What is select_related()?

`select_related()` is a Django ORM optimization method that retrieves related objects using SQL JOINs.

It is primarily used for:

- ForeignKey relationships.
- OneToOneField relationships.

## Why do we need it?

Consider:

Department:

| id | name |
|---|---|
| 1 | IT |
| 2 | HR |

Employee:

| id | name | department_id |
|---|---|---|
| 1 | John | 1 |
| 2 | David | 1 |
| 3 | Sarah | 2 |

Suppose we want to display every employee's department name.

### Without select_related()

```python
employees = Employee.objects.all()

for employee in employees:
    print(
        employee.name,
        employee.department.name
    )
```

Potential query behavior:

1. One query to retrieve employees.
2. One query to retrieve John's department.
3. Another query to retrieve David's department.
4. Another query to retrieve Sarah's department.

This is an example of the N+1 query problem.

### With select_related()

```python
employees = Employee.objects.select_related(
    'department'
)

for employee in employees:
    print(
        employee.name,
        employee.department.name
    )
```

Django retrieves the employee and department information using a SQL JOIN.

Conceptual SQL:

```sql
SELECT employee.*, department.*
FROM employee
INNER JOIN department
ON employee.department_id = department.id;
```

This can reduce multiple queries to one query.

## Multiple relationships

```python
Employee.objects.select_related(
    'department',
    'profile'
)
```

This retrieves the employee along with its related department and profile.

## Nested relationships

```python
Employee.objects.select_related(
    'department__company'
)
```

This follows the relationship from Employee to Department to Company.

## When should you use select_related()?

Use it when you retrieve records and need related data through:

- ForeignKey.
- OneToOneField.

Example:

You display an employee list with the department name for each employee.

## Important limitation

`select_related()` is not designed for ManyToManyField or reverse ForeignKey collections.

For those relationships, use `prefetch_related()`.

# 78. prefetch_related()

## What is prefetch_related()?

`prefetch_related()` is a Django ORM optimization method used to retrieve related records through separate database queries and combine them in Python.

It is commonly used for:

- ManyToManyField.
- Reverse ForeignKey relationships.
- Other multi-valued relationships.

## Why do we need it?

Suppose an Employee can work on multiple Projects.

```python
class Employee(models.Model):

    name = models.CharField(max_length=100)

    projects = models.ManyToManyField(
        Project,
        related_name='employees'
    )
```

We want to display employees and their projects.

### Without prefetch_related()

```python
employees = Employee.objects.all()

for employee in employees:

    for project in employee.projects.all():
        print(employee.name, project.name)
```

Django may execute:

1. One query to retrieve employees.
2. One query per employee to retrieve projects.

This can create the N+1 query problem.

### With prefetch_related()

```python
employees = Employee.objects.prefetch_related(
    'projects'
)

for employee in employees:

    for project in employee.projects.all():
        print(employee.name, project.name)
```

Django typically executes:

1. One query to retrieve employees.
2. One query to retrieve the related projects.

It then associates the results in Python.

## Reverse ForeignKey example

Suppose:

```python
class Employee(models.Model):

    name = models.CharField(max_length=100)

    department = models.ForeignKey(
        Department,
        on_delete=models.CASCADE,
        related_name='employees'
    )
```

To retrieve departments and their employees:

```python
departments = Department.objects.prefetch_related(
    'employees'
)

for department in departments:

    for employee in department.employees.all():
        print(department.name, employee.name)
```

## Custom Prefetch

You can use `Prefetch` when you need to customize the related queryset.

```python
from django.db.models import Prefetch

employees = Employee.objects.prefetch_related(
    Prefetch(
        'projects',
        queryset=Project.objects.filter(
            is_active=True
        )
    )
)
```

This prefetches only active projects.

## select_related() vs prefetch_related()

| Feature | select_related() | prefetch_related() |
|---|---|---|
| Main technique | SQL JOIN | Separate queries |
| ForeignKey | Yes | Yes |
| OneToOne | Yes | Yes |
| ManyToMany | No | Yes |
| Reverse ForeignKey collections | No | Yes |
| Best use | Single-valued relationships | Multi-valued relationships |

### Can we combine them?

Yes.

```python
employees = Employee.objects.select_related(
    'department'
).prefetch_related(
    'projects'
)
```

This retrieves:
- Employees and their departments using JOINs.
- Related projects using prefetching.

This is especially useful when building DRF APIs that serialize related objects.

# 79. Database Joins

## What is a database JOIN?

A JOIN combines data from multiple database tables using related columns.

For example, the Employee table contains:

```text
id | name | department_id
```

The Department table contains:

```text
id | name
```

The `department_id` column connects the two tables.

### Example SQL JOIN

```sql
SELECT
    employee.name,
    department.name
FROM employee
INNER JOIN department
ON employee.department_id = department.id;
```

Result:

```text
John  | IT
David | IT
Sarah | HR
```

## Types of JOINs

### 1. INNER JOIN

Returns rows with matching records in both tables.

Example:

```sql
SELECT *
FROM employee
INNER JOIN department
ON employee.department_id = department.id;
```

### 2. LEFT JOIN

Returns all records from the left table and matching records from the right table.

If no matching right-side record exists, its columns are NULL.

Example:

```sql
SELECT *
FROM employee
LEFT JOIN department
ON employee.department_id = department.id;
```

### 3. RIGHT JOIN

Returns all records from the right table and matching records from the left table.

### 4. FULL OUTER JOIN

Returns matching and non-matching records from both tables.

The database backend determines which JOIN features are supported.

## How does Django ORM use JOINs?

Django automatically creates JOINs when you filter or retrieve fields through relationships.

Example:

```python
employees = Employee.objects.filter(
    department__name='IT'
)
```

Django generates SQL involving a JOIN between Employee and Department.

You generally do not need to write the JOIN manually.

## Accessing related fields

```python
employees = Employee.objects.values(
    'name',
    'department__name'
)
```

Example output:

```python
[
    {
        'name': 'John',
        'department__name': 'IT'
    },
    {
        'name': 'David',
        'department__name': 'IT'
    }
]
```

## When should you understand JOINs?

You should understand JOINs when:

- Filtering through relationships.
- Retrieving related model data.
- Optimizing database queries.
- Understanding `select_related()`.
- Writing complex ORM queries.
- Investigating slow API responses.

# 80. Aggregation and Annotation

Aggregation and annotation are used to perform calculations on database records.

Django provides these operations through:

```python
from django.db.models import Count, Sum, Avg, Max, Min
```

## What is Aggregation?

Aggregation calculates a single summary result from a collection of records.

Example:

Calculate the total salary of all employees.

```python
from django.db.models import Sum

result = Employee.objects.aggregate(
    total_salary=Sum('salary')
)

print(result)
```

Example output:

```python
{
    'total_salary': Decimal('150000.00')
}
```

### Common aggregate functions

| Function | Purpose |
|---|---|
| `Count()` | Counts records |
| `Sum()` | Calculates total |
| `Avg()` | Calculates average |
| `Max()` | Finds maximum |
| `Min()` | Finds minimum |

### Example: Count employees

```python
Employee.objects.aggregate(
    total_employees=Count('id')
)
```

Output:

```python
{
    'total_employees': 3
}
```

### Example: Average salary

```python
Employee.objects.aggregate(
    average_salary=Avg('salary')
)
```

### Example: Highest salary

```python
Employee.objects.aggregate(
    highest_salary=Max('salary')
)
```

### Example: Lowest salary

```python
Employee.objects.aggregate(
    lowest_salary=Min('salary')
)
```

## What is Annotation?

`annotate()` adds calculated values to each object in a QuerySet.

For example, we want to retrieve each department with its employee count.

```python
from django.db.models import Count

departments = Department.objects.annotate(
    employee_count=Count('employees')
)
```

Now each department object has an additional calculated attribute:

```python
for department in departments:

    print(
        department.name,
        department.employee_count
    )
```

Example output:

```text
IT 2
HR 1
Finance 0
```

Notice that `employee_count` is not necessarily a real database column.

It is a calculated value added to the QuerySet result.

## Another annotation example

Calculate the number of projects assigned to each employee.

```python
employees = Employee.objects.annotate(
    project_count=Count('projects')
)
```

Use:

```python
for employee in employees:
    print(
        employee.name,
        employee.project_count
    )
```

## Aggregation vs Annotation

| Aggregation | Annotation |
|---|---|
| Calculates summary values | Adds calculated values to each object |
| Usually returns a dictionary | Returns a QuerySet |
| Example: total salary | Example: salary per employee with a bonus calculation |
| Uses `aggregate()` | Uses `annotate()` |

### When should you use Aggregation?

Use it for:
- Dashboard statistics.
- Total sales.
- Average salary.
- Total employees.
- Maximum and minimum values.

### When should you use Annotation?

Use it when each record needs additional calculated information.

Examples:
- Employee project count.
- Department employee count.
- Customer order count.
- Product review count.

# 81. Transactions

## What is a database transaction?

A database transaction is a group of database operations treated as one logical unit of work.

A transaction should satisfy the ACID principles:

1. Atomicity
2. Consistency
3. Isolation
4. Durability

## Example: Bank transfer

Suppose John transfers €100 to David.

Initial balances:

```text
John:  €500
David: €200
```

Two operations are required:

1. Subtract €100 from John.
2. Add €100 to David.

Expected balances:

```text
John:  €400
David: €300
```

### What can go wrong without a transaction?

Imagine:

1. John loses €100 successfully.
2. The application crashes before David receives €100.

Now the money has disappeared from the application balances.

This is an inconsistent state.

A transaction ensures that both operations succeed together or are rolled back together.

## Understanding ACID

### 1. Atomicity

All operations succeed, or none of them are committed.

### 2. Consistency

A transaction should preserve database rules and constraints.

### 3. Isolation

Concurrent transactions should not interfere in ways that violate the database's isolation guarantees.

The exact behavior depends on the database isolation level.

### 4. Durability

Once a transaction commits, its changes are persisted according to the database's durability guarantees.

## Why use transactions?

Use transactions when multiple database operations must succeed or fail together.

Examples:

- Bank transfers.
- Creating an order and its order items.
- Payment processing records.
- Inventory updates.
- Booking systems.
- Creating multiple related records.

# 82. atomic() and Database Consistency

## What is transaction.atomic()?

Django provides `transaction.atomic()` to execute database operations within a transaction.

Import it:

```python
from django.db import transaction
```

### Example: bank transfer

Suppose we have an Account model:

```python
from django.db import models

class Account(models.Model):

    owner = models.CharField(max_length=100)

    balance = models.DecimalField(
        max_digits=12,
        decimal_places=2
    )
```

Now implement the transfer:

```python
from django.db import transaction
from django.db.models import F

def transfer_money(
    from_account_id,
    to_account_id,
    amount
):

    with transaction.atomic():

        from_account = Account.objects.get(
            id=from_account_id
        )

        to_account = Account.objects.get(
            id=to_account_id
        )

        if from_account.balance < amount:
            raise ValueError(
                'Insufficient balance'
            )

        from_account.balance = (
            F('balance') - amount
        )

        from_account.save(
            update_fields=['balance']
        )

        to_account.balance = (
            F('balance') + amount
        )

        to_account.save(
            update_fields=['balance']
        )
```

### What happens here?

The code inside:

```python
with transaction.atomic():
```

is executed as one transaction.

If an exception escapes the atomic block, Django rolls back the transaction.

If all operations complete successfully, Django commits the transaction.

### Why use F() expressions?

`F()` allows the database to perform calculations using the existing database value.

For example:

```python
Account.objects.filter(
    id=1
).update(
    balance=F('balance') - 100
)
```

This performs the arithmetic in the database rather than calculating it from a potentially stale Python value.

### Important: handling concurrent transfers

The previous example demonstrates atomicity, but production banking-style operations need additional protections against concurrent updates.

One approach is to lock account rows:

```python
from django.db import transaction

def transfer_money(
    from_account_id,
    to_account_id,
    amount
):

    if amount <= 0:
        raise ValueError('Amount must be positive')

    with transaction.atomic():

        accounts = Account.objects.select_for_update().filter(
            id__in=[
                from_account_id,
                to_account_id
            ]
        ).order_by('id')

        account_map = {
            account.id: account
            for account in accounts
        }

        from_account = account_map[from_account_id]
        to_account = account_map[to_account_id]

        if from_account.balance < amount:
            raise ValueError('Insufficient balance')

        from_account.balance -= amount
        to_account.balance += amount

        from_account.save(
            update_fields=['balance']
        )

        to_account.save(
            update_fields=['balance']
        )
```

`select_for_update()` locks selected rows until the transaction completes on databases that support row-level locking.

Ordering the locks consistently helps reduce deadlock risk.

For production financial applications, also consider:
- Database constraints.
- Idempotency.
- Audit records.
- Currency precision.
- Concurrency testing.
- Appropriate isolation levels.

### Atomic decorator

You can also use `@transaction.atomic`.

```python
from django.db import transaction

@transaction.atomic
def create_employee():

    employee = Employee.objects.create(
        name='John'
    )

    EmployeeProfile.objects.create(
        employee=employee,
        address='Dublin'
    )

    return employee
```

If profile creation fails and the exception escapes the function, the employee creation is rolled back too.

## Nested atomic blocks

Django supports nested atomic blocks.

```python
with transaction.atomic():

    employee = Employee.objects.create(
        name='John'
    )

    with transaction.atomic():

        EmployeeProfile.objects.create(
            employee=employee,
            address='Dublin'
        )
```

Nested blocks usually use database savepoints rather than independent transactions.

## Important transaction rule

Do not catch and silently ignore database exceptions inside an atomic block and then continue using the same transaction.

A database error may mark the transaction as broken until the relevant atomic block rolls back.

Instead, catch exceptions outside the atomic block or use a nested atomic block when you need to recover from a particular operation.

# 83. Database Indexing

## What is a database index?

A database index is a data structure that helps the database find records more efficiently.

Think of an index in a book.

Without an index, you may need to read every page to find a topic.

With an index, you can locate the relevant page much faster.

A database index works similarly.

## Example without an index

Suppose the Employee table contains one million records.

We frequently search using email:

```python
Employee.objects.get(
    email='john@example.com'
)
```

Without a suitable index, the database may need to scan many records.

This is called a table scan.

## Creating an index

You can create an index using:

```python
class Employee(models.Model):

    name = models.CharField(max_length=100)

    email = models.EmailField(
        db_index=True
    )
```

Django creates the appropriate database index through migrations.

## Index using Meta

You can also define indexes inside the model's Meta class.

```python
class Employee(models.Model):

    name = models.CharField(max_length=100)

    department = models.CharField(max_length=100)

    class Meta:

        indexes = [
            models.Index(
                fields=['department'],
                name='employee_department_idx'
            )
        ]
```

## Composite indexes

A composite index covers multiple fields.

Example:

```python
class Employee(models.Model):

    department = models.CharField(max_length=100)

    is_active = models.BooleanField(default=True)

    class Meta:

        indexes = [
            models.Index(
                fields=[
                    'department',
                    'is_active'
                ],
                name='dept_active_idx'
            )
        ]
```

This can help queries that filter using those fields together.

## Unique indexes and constraints

```python
email = models.EmailField(unique=True)
```

A uniqueness requirement is enforced by a database constraint, generally backed by a unique index depending on the database.

## Advantages of indexes

1. Faster lookups.
2. Faster filtering for suitable queries.
3. Improved performance for certain ordering operations.
4. Faster joins in some cases.
5. Efficient enforcement of uniqueness.

## Disadvantages of indexes

1. Consume additional disk space.
2. Make inserts slower.
3. Make updates slower when indexed fields change.
4. Require maintenance by the database.

## When should you create indexes?

Consider indexes for fields frequently used in:

- Filtering.
- Joining.
- Ordering.
- Uniqueness checks.
- Lookup operations.

However, do not index every field automatically.

Use database query plans and real performance measurements to decide.

# 84. Query Optimisation

## What is query optimization?

Query optimization means improving database query performance.

The goal is to retrieve the required data while reducing:

- Number of database queries.
- Amount of data retrieved.
- Database processing time.
- Application memory usage.
- Unnecessary calculations.

This is especially important in Django REST Framework because a slow ORM query can make an API endpoint slow.

## 1. Avoid the N+1 query problem

Bad:

```python
employees = Employee.objects.all()

for employee in employees:

    print(employee.department.name)
```

Better:

```python
employees = Employee.objects.select_related(
    'department'
)
```

## 2. Use prefetch_related()

Bad:

```python
employees = Employee.objects.all()

for employee in employees:

    print(list(employee.projects.all()))
```

Better:

```python
employees = Employee.objects.prefetch_related(
    'projects'
)
```

## 3. Use only() to retrieve selected fields

```python
employees = Employee.objects.only(
    'id',
    'name'
)
```

This initially retrieves only those fields.

Be careful: accessing a deferred field later can cause an additional query.

## 4. Use defer() to exclude fields

```python
employees = Employee.objects.defer(
    'description'
)
```

This avoids retrieving the description field initially.

Again, accessing the deferred field later can trigger another query.

## 5. Use values() when model objects are unnecessary

```python
employees = Employee.objects.values(
    'id',
    'name'
)
```

This returns dictionaries rather than full model instances.

Useful for simple reporting and data extraction.

## 6. Use exists() instead of retrieving records just to check

Less efficient:

```python
if Employee.objects.filter(
    is_active=True
):
    print('Active employees exist')
```

Clearer:

```python
if Employee.objects.filter(
    is_active=True
).exists():

    print('Active employees exist')
```

## 7. Use count() when you only need a count

```python
total = Employee.objects.count()
```

Avoid retrieving all records just to calculate the total.

## 8. Use bulk_create()

Instead of creating many objects one by one:

```python
Employee.objects.create(name='John')
Employee.objects.create(name='David')
Employee.objects.create(name='Sarah')
```

Use:

```python
employees = [
    Employee(name='John'),
    Employee(name='David'),
    Employee(name='Sarah')
]

Employee.objects.bulk_create(employees)
```

This can reduce the number of database queries significantly.

Be aware that bulk operations do not behave exactly like individual `save()` calls. In particular, model `save()` methods and save signals are not called for objects created through `bulk_create()`.

## 9. Use bulk_update()

```python
employees = Employee.objects.filter(
    department__name='IT'
)

for employee in employees:
    employee.is_active = False

Employee.objects.bulk_update(
    employees,
    ['is_active']
)
```

This can update many records efficiently.

## 10. Use update() for direct database updates

```python
Employee.objects.filter(
    id=1
).update(
    is_active=False
)
```

This performs an SQL UPDATE without loading the object and calling its `save()` method.

## 11. Use iterator() for large QuerySets

```python
employees = Employee.objects.all().iterator(
    chunk_size=1000
)

for employee in employees:
    process_employee(employee)
```

This can reduce QuerySet result caching when processing large datasets.

## 12. Use explain()

Django allows you to inspect the database query plan.

```python
print(
    Employee.objects.filter(
        department__name='IT'
    ).explain()
)
```

The database explains how it plans to execute the query.

For PostgreSQL, the output can include information about:
- Sequential scans.
- Index scans.
- Joins.
- Estimated costs.
- Estimated row counts.

Use this to understand whether indexes and query structure are helping.

## 13. Avoid unnecessary database queries

Bad:

```python
for employee_id in employee_ids:

    employee = Employee.objects.get(
        id=employee_id
    )

    print(employee.name)
```

Better:

```python
employees = Employee.objects.filter(
    id__in=employee_ids
)

for employee in employees:
    print(employee.name)
```

## How to identify slow queries?

Django provides query logging and testing tools.

For example, in tests:

```python
from django.test.utils import CaptureQueriesContext
from django.db import connection

with CaptureQueriesContext(connection) as queries:

    employees = list(
        Employee.objects.select_related(
            'department'
        )
    )

print(len(queries))
```

You can also use Django Debug Toolbar during development to inspect SQL queries and their execution times.

## Important optimization principle

Do not optimize based only on assumptions.

Measure the queries, identify the bottleneck, make a change, and measure again.

# 85. Raw SQL in Django

## What is Raw SQL?

Raw SQL means writing SQL queries directly instead of using Django ORM methods.

Django ORM can handle most database operations, but sometimes raw SQL is useful for:

- Complex database-specific queries.
- Specialized reporting.
- Advanced SQL features.
- Queries that are difficult to express clearly through the ORM.
- Legacy database integration.

## Method 1: Using raw()

Django provides `raw()` to execute a raw SELECT query and return model instances.

Example:

```python
employees = Employee.objects.raw(
    'SELECT * FROM employees_employee'
)

for employee in employees:
    print(employee.name)
```

Important:
- The query should return the model's primary key.
- The result is an iterable of model instances.
- `raw()` is intended for SELECT queries returning model rows.

## Using parameters safely

```python
employees = Employee.objects.raw(
    '''
    SELECT *
    FROM employees_employee
    WHERE age > %s
    ''',
    [25]
)
```

Use parameters rather than inserting user input directly into SQL strings.

## Method 2: Using connection.cursor()

For more general SQL queries, use a database cursor.

```python
from django.db import connection

with connection.cursor() as cursor:

    cursor.execute(
        '''
        SELECT name, email
        FROM employees_employee
        WHERE age > %s
        ''',
        [25]
    )

    rows = cursor.fetchall()

for row in rows:
    print(row)
```

### fetchall()

Returns all rows.

### fetchone()

Returns one row.

Example:

```python
with connection.cursor() as cursor:

    cursor.execute(
        '''
        SELECT name
        FROM employees_employee
        WHERE id = %s
        ''',
        [1]
    )

    row = cursor.fetchone()
```

## Method 3: Using cursor for INSERT or UPDATE

```python
from django.db import connection

with connection.cursor() as cursor:

    cursor.execute(
        '''
        UPDATE employees_employee
        SET is_active = %s
        WHERE id = %s
        ''',
        [False, 1]
    )
```

For ordinary updates, Django ORM is generally easier:

```python
Employee.objects.filter(
    id=1
).update(
    is_active=False
)
```

## SQL injection warning

Never do this:

```python
query = (
    "SELECT * FROM employees_employee "
    "WHERE name = '" + user_input + "'"
)

cursor.execute(query)
```

An attacker may provide malicious input that changes the SQL query.

Instead:

```python
cursor.execute(
    '''
    SELECT *
    FROM employees_employee
    WHERE name = %s
    ''',
    [user_input]
)
```

Parameter placeholders and parameter values must be passed separately.

Do not use Python string formatting or concatenation to insert user input into SQL.

## When should you use Raw SQL?

Use ORM by default.

Use raw SQL when:
- The ORM cannot express a required operation cleanly.
- A database-specific feature is needed.
- A carefully measured performance issue justifies it.
- You are integrating with an existing database structure.

Raw SQL increases database-specific code and requires extra care around security and portability.

# 86. Database Migrations

## What are migrations?

Migrations are Django's system for applying changes to your database schema over time.

Suppose your Employee model initially has:

```python
class Employee(models.Model):

    name = models.CharField(max_length=100)
```

Later, you add:

```python
email = models.EmailField()
```

The database table must also change.

Django migrations handle this process.

## Why do we need migrations?

Without migrations, you would have to manually update database tables whenever models change.

Migrations help you:
- Create tables.
- Add columns.
- Remove columns.
- Modify fields.
- Add indexes.
- Add constraints.
- Track schema changes.

## Important migration commands

### 1. makemigrations

```bash
python manage.py makemigrations
```

Creates migration files based on changes detected in models.

Example output:

```text
Migrations for 'employees':
  employees/migrations/0001_initial.py
    + Create model Employee
```

### 2. migrate

```bash
python manage.py migrate
```

Applies migrations to the database.

### 3. showmigrations

```bash
python manage.py showmigrations
```

Displays migration status.

Example:

```text

 [X] 0001_initial

```

### 4. sqlmigrate

```bash

```

## Migration workflow

Whenever you change a model:

```text
1. Edit models.py
       |
       v
2. makemigrations
       |
       v
3. Review migration file
       |
       v
4. migrate
       |
       v
5. Database schema updated
```

## Example migration file

A simplified migration may look like:

```python
from django.db import migrations, models

class Migration(migrations.Migration):

    dependencies = []

    operations = [

        migrations.CreateModel(
            name='Employee',

            fields=[
                (
                    'id',
                    models.BigAutoField(
                        primary_key=True,
                        serialize=False
                    )
                ),

                (
                    'name',
                    models.CharField(
                        max_length=100
                    )
                )
            ]
        )
    ]
```

## Important migration rules

1. Do not casually edit migrations that have already been applied.
2. Commit migration files to version control.
3. Review migrations before deploying.
4. Back up important production databases.
5. Be careful when adding non-nullable fields to tables containing existing data.
6. Do not delete migration files simply to fix a migration problem.
7. Keep migration history consistent across environments.

## Data migrations

Sometimes you need to modify existing database data as part of a migration.

Django provides `RunPython`.

Example:

```python
from django.db import migrations

def make_employees_active(apps, schema_editor):

    Employee = apps.get_model(
        'employees',
        'Employee'
    )

    Employee.objects.filter(
        is_active__isnull=True
    ).update(
        is_active=True
    )


class Migration(migrations.Migration):

    dependencies = [
        ('employees', '0001_initial')
    ]

    operations = [
        migrations.RunPython(
            make_employees_active,
            migrations.RunPython.noop
        )
    ]
```

Use historical models from `apps.get_model()` inside migrations rather than importing the current model directly.

This ensures the migration works against the model state appropriate to that point in migration history.

# 88. Connection Management

## What is a database connection?

A database connection is a communication channel between your Django application and the database.

When Django executes an ORM query, it uses a database connection to communicate with the database server.

Example:

```python
employees = Employee.objects.all()
```

Django sends the generated SQL through the configured database connection.

## Why is connection management important?

Imagine your API receives 1,000 requests.

If each request creates unnecessary new database connections, the database may become overloaded.

Connection management helps control:
- Connection creation.
- Connection reuse.
- Connection cleanup.
- Connection limits.
- Database resource usage.

## 1. Django database configuration

Example:

```python
DATABASES = {

    'default': {

        'ENGINE': 'django.db.backends.postgresql',

        'NAME': 'employee_db',

        'USER': 'employee_user',

        'PASSWORD': 'your_password',

        'HOST': 'localhost',

        'PORT': '5432',

        'CONN_MAX_AGE': 60,
    }
}
```

### What is CONN_MAX_AGE?

`CONN_MAX_AGE` controls persistent database connection reuse.

For example:

```python
'CONN_MAX_AGE': 60
```

This allows Django to reuse connections for up to 60 seconds, subject to connection health checks and request lifecycle behavior.

Use:

```python
'CONN_MAX_AGE': 0
```

to disable persistent connections.

Use:

```python
'CONN_MAX_AGE': None
```

to allow connections to remain persistent indefinitely, subject to connection handling and infrastructure behavior.

The appropriate setting depends on your deployment.

## 2. CONN_HEALTH_CHECKS

Django supports connection health checks.

```python
DATABASES = {

    'default': {

        'ENGINE': 'django.db.backends.postgresql',

        'NAME': 'employee_db',

        'USER': 'employee_user',

        'PASSWORD': 'your_password',

        'HOST': 'localhost',

        'PORT': '5432',

        'CONN_MAX_AGE': 60,

        'CONN_HEALTH_CHECKS': True,
    }
}
```

This helps Django check persistent connections before reuse.

## 3. Close old connections

Django provides:

```python
from django.db import close_old_connections
```

This can be useful in long-running processes and background workers.

Example:

```python
from django.db import close_old_connections

def background_task():

    close_old_connections()

    employees = Employee.objects.all()

    for employee in employees:
        print(employee.name)
```

For long-running tasks, follow the connection lifecycle guidance of the framework or task-processing system you use.

## 4. Database connection limits

PostgreSQL has a maximum connection setting.

If your Django application opens too many connections, new connections may be rejected.

You should consider:
- Number of application workers.
- Number of threads.
- Database connection limits.
- Persistent connection settings.
- Connection pooling.

## 5. Connection pooling

Connection pooling reuses a smaller number of database connections across application requests.

For example, PgBouncer is a popular PostgreSQL connection pooler.

It can help when applications have many workers or need to manage database connections efficiently.

Be careful when combining transaction pooling with session-dependent database features. Configure Django and the pooler according to the pooler's supported mode.

## When should you care about connection management?

Especially when:
- Deploying Django to production.
- Running multiple application workers.
- Using background jobs.
- Handling high traffic.
- Using PostgreSQL with limited connections.
- Experiencing database connection errors.

# 89. Handling Database Exceptions

## What are database exceptions?

Database exceptions are errors that occur while Django communicates with or performs operations on the database.

Examples:

- Trying to retrieve a record that does not exist.
- Creating a duplicate unique value.
- Violating a foreign key constraint.
- Losing the database connection.
- Executing invalid SQL.
- Violating a database constraint.

Handling these exceptions properly helps prevent application crashes and provides meaningful API responses.

## Important Django database exceptions

Import:

```python
from django.db import (
    DatabaseError,
    IntegrityError,
    OperationalError,
    ProgrammingError,
    DataError,
    InterfaceError
)
```

### 1. DoesNotExist

Occurs when `get()` cannot find a matching record.

Example:

```python
employee = Employee.objects.get(
    id=100
)
```

If employee 100 does not exist:

```python
Employee.DoesNotExist
```

Handle it:

```python
try:

    employee = Employee.objects.get(
        id=100
    )

except Employee.DoesNotExist:

    print('Employee not found')
```

### 2. MultipleObjectsReturned

Occurs when `get()` returns more than one matching record.

Example:

```python
employee = Employee.objects.get(
    department__name='IT'
)
```

If multiple employees belong to IT, this raises:

```python
Employee.MultipleObjectsReturned
```

Use `filter()` when multiple records are expected.

### 3. IntegrityError

Occurs when a database integrity constraint is violated.

Examples:

- Duplicate unique email.
- Foreign key constraint violation.
- Check constraint violation.

Example:

```python
class Employee(models.Model):

    email = models.EmailField(unique=True)
```

Attempting to create a duplicate email may cause an IntegrityError.

Handle it:

```python
from django.db import IntegrityError

try:

    Employee.objects.create(
        name='John',
        email='john@example.com'
    )

except IntegrityError:

    print('Database integrity constraint violated')
```

### Important: catch IntegrityError around a transaction boundary

For operations inside a transaction, catch the exception outside the atomic block.

```python
from django.db import transaction, IntegrityError

try:

    with transaction.atomic():

        Employee.objects.create(
            name='John',
            email='john@example.com'
        )

except IntegrityError:

    print('Unable to create employee')
```

This allows Django to roll back the failed transaction before your code handles the exception.

### 4. OperationalError

Occurs when a database operation cannot be performed due to an operational problem.

Possible causes:
- Database server unavailable.
- Connection lost.
- Connection timeout.
- Some database-level operational failures.

Example:

```python
from django.db import OperationalError

try:

    employees = list(
        Employee.objects.all()
    )

except OperationalError:

    print('Database connection problem')
```

### 5. ProgrammingError

Occurs when the database reports a programming-related error.

Examples:
- Invalid SQL.
- Referencing a nonexistent table or column.
- Some SQL syntax errors.

This often indicates a coding, schema or migration issue.

### 6. DataError

Occurs when data is invalid for a database operation.

Examples:
- A value outside the allowed range.
- An invalid value for a database column.
- Some database type conversion errors.

### 7. InterfaceError

Occurs when there is a problem with the database driver's interface or connection interaction.

## Example: robust database operation

```python
from django.db import (
    IntegrityError,
    OperationalError
)

def create_employee(name, email):

    try:

        employee = Employee.objects.create(
            name=name,
            email=email
        )

        return {
            'success': True,
            'employee_id': employee.id
        }

    except IntegrityError:

        return {
            'success': False,
            'message': 'Email already exists or another integrity rule was violated'
        }

    except OperationalError:

        return {
            'success': False,
            'message': 'Database temporarily unavailable'
        }
```

In a real application, you should log the underlying exception and avoid exposing internal database details to clients.

## Handling database exceptions in DRF

Suppose we have a DRF API endpoint that creates employees.

```python
from rest_framework.decorators import api_view
from rest_framework.response import Response
from rest_framework import status

from django.db import IntegrityError, OperationalError

@api_view(['POST'])
def create_employee(request):

    serializer = EmployeeSerializer(
        data=request.data
    )

    if not serializer.is_valid():

        return Response(
            serializer.errors,
            status=status.HTTP_400_BAD_REQUEST
        )

    try:

        employee = serializer.save()

        return Response(
            {
                'message': 'Employee created successfully',
                'data': EmployeeSerializer(employee).data
            },
            status=status.HTTP_201_CREATED
        )

    except IntegrityError:

        return Response(
            {
                'message': 'The employee could not be created because a database constraint was violated'
            },
            status=status.HTTP_409_CONFLICT
        )

    except OperationalError:

        return Response(
            {
                'message': 'Database temporarily unavailable'
            },
            status=status.HTTP_503_SERVICE_UNAVAILABLE
        )
```

### Why use these HTTP status codes?

| Status | Meaning | Example |
|---|---|---|
| 400 | Bad Request | Invalid request data |
| 404 | Not Found | Employee does not exist |
| 409 | Conflict | Duplicate value or conflicting state |
| 503 | Service Unavailable | Database temporarily unavailable |

The exact mapping depends on the application's API contract and the nature of the error.

Do not expose raw SQL, database credentials, stack traces or internal exception messages in API responses.

## Model validation vs database constraints

These are related but different.

### Model validation

Example:

```python
class Employee(models.Model):

    age = models.IntegerField()

    def clean(self):

        if self.age < 18:

            from django.core.exceptions import ValidationError

            raise ValidationError(
                'Employee must be at least 18'
            )
```

Django does not automatically call `full_clean()` every time you call `save()`.

If you need model validation, call it explicitly or use a suitable form or serializer validation process.

### Database constraints

Example:

```python
class Employee(models.Model):

    age = models.IntegerField()

    class Meta:

        constraints = [

            models.CheckConstraint(
                condition=models.Q(age__gte=18),
                name='employee_age_at_least_18'
            )

        ]
```

This creates a database-level rule.

The database enforces the constraint even when the record is inserted through code that bypasses normal Django model validation.

### Why use database constraints?

They protect data integrity regardless of which application code path performs the database operation.

For important business rules, application validation and database constraints can complement each other.

        indexes = [

            )

        return self.name

## Most important differences for interviews

### 1. ForeignKey vs OneToOneField vs ManyToManyField

- `ForeignKey`: Many-to-one relationship.
- `OneToOneField`: One-to-one relationship.
- `ManyToManyField`: Many-to-many relationship.

### 2. get() vs filter()

- `get()` returns one object and raises exceptions if zero or multiple objects match.
- `filter()` returns a QuerySet and can return zero, one or many objects.

### 3. select_related() vs prefetch_related()

- `select_related()` uses SQL JOINs for single-valued relationships.
- `prefetch_related()` uses separate queries and combines the results in Python for related collections.

### 4. aggregate() vs annotate()

- `aggregate()` calculates a summary for the QuerySet.
- `annotate()` adds calculated values to individual records.

### 5. null vs blank

- `null=True` affects database storage.
- `blank=True` affects Django validation.

### 6. makemigrations vs migrate

- `makemigrations` creates migration files.
- `migrate` applies migrations to the database.

### 7. atomic() vs ordinary database operations

- Ordinary operations may commit independently when not inside a transaction.
- `atomic()` groups operations into a transaction that can be rolled back if an exception escapes the block.

### 8. ORM vs Raw SQL

- ORM uses Python methods and QuerySets.
- Raw SQL allows direct execution of SQL statements.
