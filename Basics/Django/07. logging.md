# Django REST Framework (DRF) Logging – Complete Guide with Production-Level Examples

# 1. What is Logging?

Logging is the process of recording important events that happen inside an application.

In a Django REST Framework application, logging helps us understand:

- Which API endpoint was called.
- Who made the API request.
- When the request happened.
- How long the API took to respond.
- Whether the API succeeded or failed.
- What exception occurred.
- Whether a database or external service failed.
- Whether suspicious activity is happening.

For example, suppose a user calls:

```http
POST /api/orders/
```

The API encounters a database error.

Without logging, we might only see a 500 response.

With logging, we can record:

```text
2026-11-06 13:20:10 ERROR orders.views
Order creation failed. user_id=25 request_id=abc123
```

This helps developers investigate the problem.

## Why do we need logging?

Logging is important for:

1. Debugging application errors.
2. Monitoring API performance.
3. Tracking failed requests.
4. Investigating production incidents.
5. Detecting suspicious activity.
6. Tracking business operations.
7. Understanding application behavior.
8. Meeting operational and audit requirements.

## Logging vs print()

A common beginner mistake is using `print()` everywhere.

Example:

```python
print("User login successful")
```

This may be useful during local debugging, but it is not suitable for production applications.

Use Python's logging framework instead:

```python
import logging

logger = logging.getLogger(__name__)

logger.info("User login successful")
```

Logging supports different severity levels, formatting, handlers, filtering, and centralized log collection.

# 2. Python Logging Fundamentals

Python provides a built-in logging module.

Import it:

```python
import logging
```

## 2.1 Logger

### What is a logger?

A logger is the object your application uses to create log messages.

Example:

```python
import logging

logger = logging.getLogger(__name__)

logger.info("Product API called")
```

### Important attributes and methods

**`logging.getLogger(name)`**

Creates or retrieves a logger with the given name.

Example:

```python
logger = logging.getLogger("products")
```

Using `__name__` is common because the logger name reflects the Python module.

Example:

```python
logger = logging.getLogger(__name__)
```

**`logger.name`**

Returns the logger's name.

Example:

```python
logger = logging.getLogger("products")

print(logger.name)
```

Output:

```text
products
```

**`logger.setLevel()`**

Sets the minimum severity level that the logger processes.

Example:

```python
logger.setLevel(logging.DEBUG)
```

This allows DEBUG and higher-severity messages to be processed by that logger.

**`logger.disabled`**

Indicates whether the logger is disabled.

Example:

```python
logger.disabled = False
```

Usually, you should configure logging centrally instead of manually changing this property.

# 3. Logging Levels

Python provides five commonly used logging levels.

| Level | Numeric value | Purpose |
|---|---:|---|
| DEBUG | 10 | Detailed debugging information |
| INFO | 20 | Normal application events |
| WARNING | 30 | Something unexpected happened, but the application can continue |
| ERROR | 40 | An operation failed |
| CRITICAL | 50 | A serious failure affecting application operation |

## 3.1 DEBUG

Used for detailed diagnostic information.

Example:

```python
logger.debug("Product queryset generated")
```

Use it when investigating application behavior.

Do not normally enable verbose DEBUG logging indiscriminately in production.

## 3.2 INFO

Used for normal application events.

Example:

```python
logger.info("Product created successfully")
```

Use it for meaningful application milestones.

## 3.3 WARNING

Used when something unexpected happens, but the application can continue.

Example:

```python
logger.warning("Payment retry attempted")
```

Use it for unusual conditions that do not necessarily indicate a failed operation.

## 3.4 ERROR

Used when an operation fails.

Example:

```python
logger.error("Unable to create order")
```

Use it when a request or operation cannot be completed.

## 3.5 CRITICAL

Used for very serious failures.

Example:

```python
logger.critical("Database service unavailable")
```

Use it for failures requiring immediate attention.

## Choosing the correct logging level

Example:

```python
logger.debug("Received product query parameters")

logger.info("Product created successfully")

logger.warning("Inventory level is low")

logger.error("Payment provider returned an error")

logger.critical("Application cannot connect to its primary database")
```

Important: Do not log every event as ERROR. If everything is an error, meaningful errors become difficult to identify.

# 4. Important Logging Methods

## 4.1 `logger.debug()`

Records detailed diagnostic messages.

Example:

```python
logger.debug("Product ID: %s", product_id)
```

The `%s` placeholder allows the logging framework to format the message when needed.

## 4.2 `logger.info()`

Records normal application events.

Example:

```python
logger.info(
    "Product created successfully. product_id=%s",
    product.id
)
```

## 4.3 `logger.warning()`

Records warnings.

Example:

```python
logger.warning(
    "Low inventory for product_id=%s",
    product.id
)
```

## 4.4 `logger.error()`

Records errors.

Example:

```python
logger.error(
    "Order creation failed. order_id=%s",
    order_id
)
```

## 4.5 `logger.exception()`

Records an error message and automatically includes the current exception traceback.

Use it inside an exception handler.

Example:

```python
try:
    result = 10 / 0

except ZeroDivisionError:
    logger.exception("Calculation failed")
```

This is particularly useful in production because it records the exception type and traceback.

## 4.6 `logger.log()`

Allows you to specify the logging level dynamically.

Example:

```python
logger.log(
    logging.WARNING,
    "Inventory is running low"
)
```

Use it when the severity level is determined dynamically.

## 4.7 `logger.exception()` vs `logger.error()`

Example:

```python
try:
    process_order()

except Exception:
    logger.error("Order processing failed")
```

This logs the message but does not automatically include the exception traceback.

Using:

```python
try:
    process_order()

except Exception:
    logger.exception("Order processing failed")
```

includes the traceback.

You can also use:

```python
logger.error(
    "Order processing failed",
    exc_info=True
)
```

Use `logger.exception()` when you are already inside an exception handler and want the traceback.

# 5. Understanding Logging Configuration in Django

Django uses Python's logging framework.

Logging is generally configured in `settings.py` using the `LOGGING` dictionary.

Example:

```python
LOGGING = {
    "version": 1,
    "disable_existing_loggers": False,
}
```

Let's understand each attribute.

## 5.1 `version`

Specifies the logging configuration format version.

Example:

```python
"version": 1
```

Python's standard dictionary-based logging configuration uses version 1.

## 5.2 `disable_existing_loggers`

Controls whether existing loggers should be disabled when applying the logging configuration.

Example:

```python
"disable_existing_loggers": False
```

For most Django projects, `False` is a sensible starting point because it preserves existing loggers unless you explicitly configure them.

Setting it to `True` can unexpectedly disable existing loggers.

## 5.3 `formatters`

Formatters define how log messages appear.

Example:

```python
"formatters": {
    "simple": {
        "format": "{levelname} {message}",
        "style": "{",
    }
}
```

Important formatter attributes:

**`format`**

Defines the log message structure.

Example:

```python
"format": "{asctime} {levelname} {message}"
```

**`style`**

Defines the formatting syntax.

Example:

```python
"style": "{"
```

Common styles:

- `%` – percent-style formatting.
- `{` – `str.format()` style.
- `$` – template-style formatting.

**`datefmt`**

Controls the timestamp format.

Example:

```python
"datefmt": "%Y-%m-%d %H:%M:%S"
```

Complete formatter:

```python
"formatters": {
    "verbose": {
        "format": (
            "{asctime} {levelname} "
            "{name} {message}"
        ),
        "style": "{",
        "datefmt": "%Y-%m-%d %H:%M:%S",
    }
}
```

Example output:

```text
2026-11-06 13:20:10 ERROR orders.views Order creation failed
```

## 5.4 `handlers`

Handlers determine where log messages are sent.

Common handlers include:

- Console handler.
- File handler.
- Rotating file handler.
- Timed rotating file handler.
- Email handler.
- Network or custom handlers.

Example:

```python
"handlers": {
    "console": {
        "class": "logging.StreamHandler",
    }
}
```

**`class`**

Specifies the Python logging handler class.

Example:

```python
"class": "logging.StreamHandler"
```

This sends logs to a stream, commonly standard error.

**`level`**

Sets the minimum logging level accepted by that handler.

Example:

```python
"level": "INFO"
```

**`formatter`**

Specifies which formatter the handler should use.

Example:

```python
"formatter": "verbose"
```

## 5.5 `loggers`

Defines named loggers and their configuration.

Example:

```python
"loggers": {
    "django": {
        "handlers": ["console"],
        "level": "INFO",
    }
}
```

Important attributes:

**`handlers`**

Specifies which handlers receive messages from the logger.

Example:

```python
"handlers": ["console"]
```

**`level`**

Sets the minimum severity level for the logger.

Example:

```python
"level": "WARNING"
```

**`propagate`**

Controls whether messages are passed to parent loggers.

Example:

```python
"propagate": False
```

When `True`, messages can travel up the logger hierarchy.

When `False`, they stop propagating beyond that logger.

Use this carefully to avoid duplicate messages.

## 5.6 `root`

Configures the root logger.

Example:

```python
"root": {
    "handlers": ["console"],
    "level": "WARNING",
}
```

The root logger is the top-level logger in Python's logging hierarchy.

# 6. Your First Complete Django Logging Configuration

Let's configure logging in `settings.py`.

```python
import os

BASE_DIR = os.path.dirname(
    os.path.dirname(os.path.abspath(__file__))
)

LOGGING = {

    "version": 1,

    "disable_existing_loggers": False,

    "formatters": {

        "verbose": {
            "format": (
                "{asctime} {levelname} "
                "{name} {message}"
            ),
            "style": "{",
            "datefmt": "%Y-%m-%d %H:%M:%S",
        },

    },

    "handlers": {

        "console": {
            "class": "logging.StreamHandler",
            "level": "INFO",
            "formatter": "verbose",
        },

    },

    "loggers": {

        "django": {
            "handlers": ["console"],
            "level": "INFO",
            "propagate": False,
        },

        "products": {
            "handlers": ["console"],
            "level": "DEBUG",
            "propagate": False,
        },

    },

}
```

Now create a logger in your application.

```python
import logging

logger = logging.getLogger("products")


def get_products():

    logger.info("Fetching products")

    logger.debug("Product queryset created")
```

The logger named `products` uses the configuration defined in `settings.py`.

# 7. Logging to a File

## What is file logging?

File logging stores application log messages in files instead of only displaying them in the terminal.

Example:

```text
logs/
    application.log
```

This is useful for troubleshooting application behavior after a deployment.

## FileHandler

Python provides `logging.FileHandler`.

Example:

```python
"file": {
    "class": "logging.FileHandler",
    "filename": "/var/log/myapp/application.log",
    "level": "INFO",
    "formatter": "verbose",
}
```

Important attributes:

- `class`: Handler implementation.
- `filename`: Destination file.
- `level`: Minimum accepted severity.
- `formatter`: Log format.

Make sure the application process has permission to create and write to the directory.

## Complete file logging configuration

```python
LOGGING = {

    "version": 1,

    "disable_existing_loggers": False,

    "formatters": {
        "verbose": {
            "format": (
                "{asctime} {levelname} "
                "{name} {message}"
            ),
            "style": "{",
        },
    },

    "handlers": {

        "file": {
            "class": "logging.FileHandler",
            "filename": "/var/log/myapp/application.log",
            "level": "INFO",
            "formatter": "verbose",
        },

    },

    "loggers": {

        "products": {
            "handlers": ["file"],
            "level": "INFO",
            "propagate": False,
        },

    },

}
```

For a containerized production deployment, sending logs to stdout/stderr and collecting them through the container platform is often preferable to writing files inside the container.

# 8. Rotating File Logging

## What is log rotation?

If an application runs continuously, its log file can grow very large.

Log rotation automatically creates new files when a configured size or time condition is reached.

Example:

```text
application.log
application.log.1
application.log.2
application.log.3
```

## 8.1 RotatingFileHandler

Rotates files when the current file reaches a maximum size.

Example:

```python
"file": {
    "class": "logging.handlers.RotatingFileHandler",
    "filename": "/var/log/myapp/application.log",
    "maxBytes": 10485760,
    "backupCount": 5,
    "level": "INFO",
    "formatter": "verbose",
}
```

Important attributes:

### `maxBytes`

Maximum size of the current log file before rotation.

Example:

```python
"maxBytes": 10485760
```

This represents approximately 10 MB.

### `backupCount`

Number of backup log files to retain.

Example:

```python
"backupCount": 5
```

Older backup files are removed as new ones are created.

## 8.2 TimedRotatingFileHandler

Rotates files based on time.

Example:

```python
"file": {
    "class": "logging.handlers.TimedRotatingFileHandler",
    "filename": "/var/log/myapp/application.log",
    "when": "midnight",
    "interval": 1,
    "backupCount": 14,
    "level": "INFO",
    "formatter": "verbose",
}
```

Important attributes:

### `when`

Defines the rotation interval.

Example:

```python
"when": "midnight"
```

Other supported intervals include seconds, minutes, hours, and days.

### `interval`

Defines how many of the selected intervals should pass before rotation.

Example:

```python
"interval": 1
```

For a daily rotation, this means every one day.

### `backupCount`

Defines how many old files to retain.

Example:

```python
"backupCount": 14
```

This keeps up to 14 backup files.

## When should you use rotation?

Use it when you manage log files directly and need to control disk usage.

## When should you not use application-managed rotation?

If your deployment platform already collects and rotates stdout/stderr logs, avoid adding a second competing rotation mechanism without a clear reason.

# 9. Logging in DRF Views

## What is API-level logging?

API-level logging records important events inside views and viewsets.

For example:

- Product created.
- Product updated.
- Order cancelled.
- Payment failed.
- User profile changed.

## Complete example

```python
import logging

from rest_framework.views import APIView
from rest_framework.response import Response
from rest_framework import status

from .models import Product
from .serializers import ProductSerializer

logger = logging.getLogger(__name__)


class ProductListCreateView(APIView):

    def get(self, request):

        logger.info(
            "Product list requested. user_id=%s",
            request.user.pk if request.user.is_authenticated else None
        )

        products = Product.objects.all()

        serializer = ProductSerializer(
            products,
            many=True
        )

        return Response(serializer.data)

    def post(self, request):

        serializer = ProductSerializer(data=request.data)

        serializer.is_valid(raise_exception=True)

        product = serializer.save()

        logger.info(
            "Product created. product_id=%s user_id=%s",
            product.pk,
            request.user.pk if request.user.is_authenticated else None
        )

        return Response(
            serializer.data,
            status=status.HTTP_201_CREATED
        )
```

## Why use `__name__`?

Instead of writing:

```python
logger = logging.getLogger("products")
```

You can write:

```python
logger = logging.getLogger(__name__)
```

This automatically uses the current module's name.

For example:

```text
products.views
```

This makes logs easier to organize by application module.

# 10. Logging Exceptions in DRF

## Why do we need exception logging?

Production applications sometimes fail because of:

- Database connection issues.
- External API failures.
- Unexpected Python exceptions.
- Invalid application state.
- Payment gateway errors.

Logging exceptions allows developers to investigate the cause.

## Example

```python
import logging

from rest_framework.views import APIView
from rest_framework.response import Response
from rest_framework.exceptions import APIException

logger = logging.getLogger(__name__)


class PaymentView(APIView):

    def post(self, request):

        try:

            result = process_payment(request.data)

            return Response({
                "message": "Payment successful"
            })

        except PaymentGatewayError:

            logger.exception(
                "Payment gateway failed"
            )

            raise APIException(
                "Payment could not be processed."
            )
```

Important: The example assumes `process_payment()` and `PaymentGatewayError` are defined by your application or payment integration.

Do not expose internal exception details to the API client.

## Important production practice

Do not catch every exception just to hide it.

For example:

```python
except Exception:
    return Response({"error": "Failed"})
```

This can hide programming bugs and make troubleshooting difficult.

If you catch an unexpected exception, log it with its traceback, return a safe response, and ensure your monitoring system receives the failure.

For DRF views, unhandled exceptions can also be logged centrally through Django's logging configuration and error-monitoring infrastructure.

# 11. Logging with a Custom DRF Exception Handler

A custom exception handler can log API exceptions centrally.

Create:

`core/exceptions.py`

```python
import logging

from rest_framework.views import exception_handler

logger = logging.getLogger("api.exceptions")


def custom_exception_handler(exc, context):

    response = exception_handler(exc, context)

    request = context.get("request")
    view = context.get("view")

    if response is not None:

        logger.warning(
            "API exception. method=%s path=%s status=%s view=%s",
            request.method if request else None,
            request.path if request else None,
            response.status_code,
            view.__class__.__name__ if view else None
        )

        return response

    logger.exception(
        "Unhandled API exception. path=%s",
        request.path if request else None
    )

    return None
```

Configure:

```python
REST_FRAMEWORK = {
    "EXCEPTION_HANDLER": "core.exceptions.custom_exception_handler",
}
```

## Why is this useful?

You can centrally record:

- API exception status codes.
- Endpoint paths.
- HTTP methods.
- View names.
- Unexpected exceptions.

## Important limitation

This handler receives exceptions processed by DRF.

It is not a universal handler for all errors occurring outside DRF, such as every middleware failure or infrastructure error.

Avoid logging full request bodies or authorization headers here because they may contain sensitive information.

Also avoid duplicate exception logs if Django, your application, and an external monitoring service are already recording the same exception.

# 12. Logging API Requests and Responses Using Middleware

## What is logging middleware?

Middleware runs during Django's request/response processing.

It can be used to record information about incoming requests and outgoing responses.

For example:

```text
GET /api/products/ 200 45ms
POST /api/orders/ 201 120ms
GET /api/products/999/ 404 12ms
```

## Why use middleware?

Use it when you need centralized request logging across many endpoints.

Instead of adding logging code to every API view, middleware can record common request metadata.

## Important middleware methods

### `__init__(self, get_response)`

Called when Django initializes the middleware.

Example:

```python
def __init__(self, get_response):
    self.get_response = get_response
```

`get_response` is the next callable in Django's middleware chain.

### `__call__(self, request)`

Processes a request and obtains its response.

Example:

```python
def __call__(self, request):

    response = self.get_response(request)

    return response
```

### `process_view()`

An optional middleware hook called just before Django invokes the view.

Example:

```python
def process_view(self, request, view_func, view_args, view_kwargs):
    return None
```

Returning `None` allows processing to continue.

Returning an HTTP response prevents the view from being called.

### `process_exception()`

An optional hook for exceptions raised by a view.

Example:

```python
def process_exception(self, request, exception):
    return None
```

It can log an exception and return `None` to allow normal exception handling to continue.

## Complete request logging middleware

Create:

`core/middleware.py`

```python
import logging
import time

logger = logging.getLogger("api.requests")


class RequestLoggingMiddleware:

    def __init__(self, get_response):

        self.get_response = get_response

    def __call__(self, request):

        start_time = time.monotonic()

        response = self.get_response(request)

        duration = time.monotonic() - start_time

        user_id = None

        if hasattr(request, "user") and request.user.is_authenticated:
            user_id = request.user.pk

        logger.info(
            "API request completed. "
            "method=%s path=%s status=%s "
            "duration_ms=%.2f user_id=%s",
            request.method,
            request.path,
            response.status_code,
            duration * 1000,
            user_id
        )

        return response
```

Register it in `settings.py`:

```python
MIDDLEWARE = [
    "django.middleware.security.SecurityMiddleware",
    "django.contrib.sessions.middleware.SessionMiddleware",
    "django.middleware.common.CommonMiddleware",
    "django.middleware.csrf.CsrfViewMiddleware",
    "django.contrib.auth.middleware.AuthenticationMiddleware",
    "core.middleware.RequestLoggingMiddleware",
]
```

Place it after authentication middleware if you want `request.user` to be available.

## Example log output

```text
2026-11-06 13:20:10 INFO api.requests API request completed. method=GET path=/api/products/ status=200 duration_ms=45.22 user_id=25
```

## Important production considerations

The simple middleware above logs completed responses.

However:

- If an exception escapes before a response is produced, the log statement may not run.
- Streaming responses may continue after the middleware returns the response.
- Logging every health-check request can create unnecessary volume.
- Query strings may contain sensitive data, so avoid logging them without a clear need.
- Client IP addresses should be handled carefully, especially behind proxies.
- Use request IDs to correlate logs across services.

For a production application, consider using an established request-logging integration or carefully extending middleware with exception-safe handling and streaming-response support.

# 13. Request ID / Correlation ID Logging

## What is a request ID?

A request ID is a unique identifier assigned to an individual request.

Example:

```text
request_id=abc123
```

It allows developers to find all logs associated with the same API request.

This becomes especially useful when an application calls:

- A database.
- A payment provider.
- Another internal API.
- A background task.

## Why do we need request IDs?

Imagine an API request generates five log entries.

Without a request ID, finding the five related entries can be difficult.

With a request ID:

```text
request_id=abc123 Product API started
request_id=abc123 Database query completed
request_id=abc123 Payment service called
request_id=abc123 API response returned
```

All entries can be searched together.

## Example middleware

```python
import logging
import uuid

logger = logging.getLogger("api.requests")


class RequestIDMiddleware:

    def __init__(self, get_response):

        self.get_response = get_response

    def __call__(self, request):

        request_id = uuid.uuid4().hex

        request.request_id = request_id

        response = self.get_response(request)

        response["X-Request-ID"] = request_id

        return response
```

Register it in `MIDDLEWARE`.

## Important attributes

**`uuid.uuid4()`**

Generates a random UUID.

Example:

```python
request_id = uuid.uuid4().hex
```

**`request.request_id`**

Stores the ID on the request object so views and middleware can access it.

Example:

```python
logger.info(
    "Order created. request_id=%s",
    request.request_id
)
```

**`response["X-Request-ID"]`**

Adds the request ID to the response headers.

Example:

```http
X-Request-ID: abc123
```

## Should we trust a client-provided request ID?

Not automatically.

A production system can accept an incoming request ID for distributed tracing, but it should validate its length and format and prevent log injection.

A safer approach is to generate a new internal request ID and separately record a validated external correlation ID if needed.

For distributed systems, consider standard trace-context propagation and OpenTelemetry rather than inventing a custom tracing protocol.

# 14. Logging Performance: How Long Does an API Take?

## What is performance logging?

It records how much time an API operation takes.

Example:

```text
GET /api/products/ completed in 45 ms
```

## Why is it useful?

It helps identify:

- Slow database queries.
- Slow serializers.
- External API delays.
- Expensive business logic.
- Performance regressions.

## Example using `time.monotonic()`

```python
import logging
import time

logger = logging.getLogger(__name__)


def generate_report():

    start_time = time.monotonic()

    result = create_report()

    duration = time.monotonic() - start_time

    logger.info(
        "Report generated in %.2f ms",
        duration * 1000
    )

    return result
```

## Why use `time.monotonic()`?

It measures elapsed time and is not affected by normal system clock adjustments.

For measuring durations, it is generally preferable to `time.time()`.

## Production recommendation

Do not log every database query in production without a specific need.

Use metrics and tracing tools to measure performance at scale.

Logging describes events; metrics measure trends; tracing follows a request across multiple components.

# 15. Logging Sensitive Information: What NOT to Log

This is one of the most important production topics.

Never log:

- Passwords.
- Access tokens.
- Refresh tokens.
- API keys.
- Authorization headers.
- Session cookies.
- CSRF tokens.
- Full payment card details.
- Sensitive personal information unless explicitly justified and protected.

Unsafe example:

```python
logger.info("Request data: %s", request.data)
```

Why is this dangerous?

A login request may contain:

```json
{
    "username": "john",
    "password": "secret123"
}
```

Logging the entire request body would expose the password.

## Safer example

```python
logger.info(
    "Login request received. username=%s",
    request.data.get("username")
)
```

Even usernames and email addresses can be personal data. Log them only when necessary and according to your privacy policy.

## Redaction example

```python
SENSITIVE_FIELDS = {
    "password",
    "token",
    "access_token",
    "refresh_token",
    "api_key",
    "secret",
}


def redact_data(data):

    if not isinstance(data, dict):
        return data

    cleaned = {}

    for key, value in data.items():

        if key.lower() in SENSITIVE_FIELDS:
            cleaned[key] = "[REDACTED]"

        else:
            cleaned[key] = value

    return cleaned
```

Usage:

```python
logger.info(
    "Request data: %s",
    redact_data(request.data)
)
```

This is only a basic example.

Production redaction should also handle nested dictionaries, lists, case variations, authorization headers, and application-specific sensitive fields.

The safest default is to log an explicit allowlist of non-sensitive fields rather than attempting to redact every possible secret.

# 16. Structured JSON Logging

## What is structured logging?

Structured logging stores log messages as structured data, commonly JSON, rather than only plain text.

Plain-text example:

```text
INFO Product created product_id=10 user_id=5
```

JSON example:

```json
{
    "level": "INFO",
    "event": "product_created",
    "product_id": 10,
    "user_id": 5,
    "request_id": "abc123"
}
```

## Why use structured logging?

It is easier to:

- Search logs.
- Filter by user ID.
- Filter by request ID.
- Build dashboards.
- Analyze production incidents.
- Send logs to centralized monitoring systems.

## Example using Python's JSON formatter

Python's standard library does not provide a complete production JSON formatter with all structured logging features. You can use a maintained package such as `python-json-logger`, or implement a formatter for a simple application.

Install:

```bash
pip install python-json-logger
```

Example configuration:

```python
LOGGING = {

    "version": 1,

    "disable_existing_loggers": False,

    "formatters": {

        "json": {
            "()": "pythonjsonlogger.json.JsonFormatter",
            "format": (
                "%(asctime)s %(levelname)s "
                "%(name)s %(message)s"
            ),
        },

    },

    "handlers": {

        "console": {
            "class": "logging.StreamHandler",
            "formatter": "json",
            "level": "INFO",
        },

    },

    "loggers": {

        "django": {
            "handlers": ["console"],
            "level": "INFO",
            "propagate": False,
        },

    },

}
```

Example usage:

```python
logger.info(
    "Product created",
    extra={
        "product_id": 10,
        "user_id": 5,
        "event": "product_created",
    }
)
```

The exact JSON output depends on the installed formatter version and configuration.

Important: Do not put sensitive information into `extra` fields.

# 17. Logging Database and External API Failures

## Database failure logging

Example:

```python
import logging

from django.db import DatabaseError

logger = logging.getLogger(__name__)


def create_order():

    try:

        order = Order.objects.create(
            status="pending"
        )

        return order

    except DatabaseError:

        logger.exception(
            "Database failure while creating order"
        )

        raise
```

Why use `raise`?

It re-raises the original exception so Django/DRF can handle it normally.

Avoid silently swallowing database exceptions.

## External API failure logging

Example:

```python
import logging
import requests

logger = logging.getLogger(__name__)


def call_payment_service():

    try:

        response = requests.post(
            "https://payments.example.com/charge",
            json={"amount": 100},
            timeout=5
        )

        response.raise_for_status()

        return response.json()

    except requests.RequestException:

        logger.exception(
            "Payment provider request failed"
        )

        raise
```

Important production practices:

- Set connection and response timeouts.
- Avoid logging authorization headers.
- Avoid logging full payment payloads.
- Handle provider-specific failures.
- Use retry policies carefully.
- Avoid retrying non-idempotent operations without an idempotency strategy.

# 18. Production-Level Logging Architecture

A production application should not depend only on developers reading log files manually.

A typical architecture looks like this:

```text
Client
  |
  v
Django REST Framework API
  |
  +--> Application logs
  |
  +--> Request/response logs
  |
  +--> Exception logs
  |
  +--> Performance metrics
  |
  v
stdout / stderr or log collector
  |
  v
Centralized logging platform
  |
  +--> Search logs
  +--> Dashboards
  +--> Alerts
  +--> Incident investigation
```

## Common production tools

### 1. <span> </span> <span>ELK Stack</span>

- Elasticsearch: Stores and indexes logs.
- Logstash: Processes and transforms logs.
- Kibana: Searches and visualizes logs.

### 2. Grafana Loki

A log aggregation system commonly used with Grafana dashboards.

### 3. Datadog

Provides log management, application monitoring, and distributed tracing.

## Logs vs metrics vs traces

A production system often needs all three.

# 19. Complete Production-Oriented Django Logging Configuration

The following is a practical starting point for a Django/DRF project.

It:

- Logs application events.
- Logs Django errors.
- Sends logs to the console.
- Uses structured, readable formatting.
- Keeps application and request loggers separate.
- Avoids hardcoding log file paths.
- Supports centralized log collection.

## Step 1: Configure logging in settings.py

```python
import logging.config

LOGGING = {

    "version": 1,

    "disable_existing_loggers": False,

    "formatters": {

        "verbose": {
            "format": (
                "{asctime} {levelname} "

            ),
            "style": "{",
            "datefmt": "%Y-%m-%d %H:%M:%S",
        },

    },

    "handlers": {

        "console": {
            "class": "logging.StreamHandler",
            "level": "INFO",
            "formatter": "verbose",
        },

    },

    "loggers": {

        "django": {
            "handlers": ["console"],
            "level": "INFO",
            "propagate": False,
        },

        "django.request": {
            "handlers": ["console"],
            "level": "WARNING",
            "propagate": False,
        },

        "api": {
            "handlers": ["console"],
            "level": "INFO",
            "propagate": False,
        },

        "api.exceptions": {
            "handlers": ["console"],
            "level": "WARNING",
            "propagate": False,
        },

        "orders": {
            "handlers": ["console"],
            "level": "INFO",
            "propagate": False,
        },

        "products": {
            "handlers": ["console"],
            "level": "INFO",
            "propagate": False,
        },

    },

}
```

## Step 2: Create an application logger

In `products/views.py`:

```python
import logging

logger = logging.getLogger(__name__)
```

## Step 3: Log important events

```python
logger.info(
    "Product created. product_id=%s",
    product.id
)
```

## Step 4: Log exceptions

```python
try:

    product.save()

except Exception:

    logger.exception(
        "Unexpected error while saving product"
    )

    raise
```

## Step 5: Send logs to a centralized platform

In a container-based deployment, the application writes logs to stdout/stderr.

The container platform or log collector forwards them to the centralized logging service.

This avoids depending on log files stored inside temporary application containers.

## Step 6: Set production log levels

A typical starting point:

| Environment | Application log level |
|---|---|
| Local development | DEBUG |
| Testing | INFO or WARNING |
| Staging | INFO |
| Production | INFO or WARNING |

Choose levels according to the volume of logs and the diagnostic information you need.

Avoid enabling DEBUG logs for every component in production.

# 20. Common Logging Mistakes

## Mistake 1: Using print() instead of logging

Incorrect:

```python
print("Order created")
```

Better:

```python
logger.info("Order created")
```

## Mistake 2: Logging passwords

Incorrect:

```python
logger.info("Request data: %s", request.data)
```

Better:

```python
logger.info("Login attempt received")
```

## Mistake 3: Using ERROR for everything

Incorrect:

```python
logger.error("Product list requested")
```

Better:

```python
logger.info("Product list requested")
```

## Mistake 4: Catching exceptions without logging

Incorrect:

```python
try:
    process_payment()

except Exception:
    pass
```

Better:

```python
try:
    process_payment()

except Exception:
    logger.exception("Payment processing failed")
    raise
```

## Mistake 5: Logging too much information

Logging every request body and every database query can create:

- Excessive storage usage.
- Performance overhead.
- Privacy risks.
- Difficult-to-search logs.

Log meaningful events and use metrics or tracing for high-volume performance analysis.

## Mistake 6: No request ID

Without correlation IDs, investigating requests across services becomes difficult.

Use a request ID or distributed tracing context.

## Mistake 7: No log retention policy

Production logs should have an appropriate retention period based on operational, legal, and privacy requirements.

Do not retain sensitive logs indefinitely.

## Mistake 8: Duplicate logging

If a view logs an exception, then the DRF handler logs it, and Django also logs it, you may get duplicate entries.

Decide which layer owns each event and configure logger propagation carefully.

# Part 21: Interview Questions and Answers

## 1. What is logging in Django?

Logging is the process of recording application events, errors, warnings, and diagnostic information.

Django uses Python's built-in logging framework.

## 2. Why should we use logging instead of print()?

Logging supports severity levels, formatting, handlers, filtering, centralized configuration, and production monitoring.

`print()` does not provide these capabilities.

## 3. What are the five main logging levels?

DEBUG, INFO, WARNING, ERROR, and CRITICAL.

## 4. What is a logger?

A logger is an object that creates log messages.

Example:

```python
logger = logging.getLogger(__name__)
```

## 5. What is a handler?

A handler determines where log messages are sent.

Examples include console, file, rotating file, and email handlers.

## 6. What is a formatter?

A formatter defines the structure and appearance of a log message.

For example, it can include a timestamp, log level, logger name, and message.

## 7. What is the difference between logger and handler?

A logger creates and processes log messages.

A handler sends accepted messages to a destination.

## 8. What is the difference between FileHandler and RotatingFileHandler?

`FileHandler` writes logs to a file.

`RotatingFileHandler` also writes to a file but creates backup files when a configured size is reached.

## 9. What is TimedRotatingFileHandler?

It rotates log files based on a time interval, such as daily or hourly.

## 10. What is `disable_existing_loggers`?

It controls whether existing loggers should be disabled when a new logging configuration is applied.

In most Django applications, `False` is a sensible starting point.

## 11. What is `propagate`?

It determines whether log messages are passed to parent loggers.

Set it to `False` when you want to prevent a logger's messages from being processed again by parent loggers.

## 12. What is `logger.exception()`?

It logs a message with the current exception traceback.

It should normally be used inside an exception handler.

## 13. What is the difference between logger.error() and logger.exception()?

`logger.error()` records an error message.

`logger.exception()` records an error message and automatically includes the current exception traceback.

## 14. How do you configure logging in Django?

Use the `LOGGING` dictionary in `settings.py`.

It supports formatters, handlers, loggers, and the root logger.

## 15. How do you log API requests in DRF?

You can log request details inside views or create Django middleware to record common request and response information centrally.

## 16. How do you log exceptions centrally in DRF?

Create a custom exception handler and configure it using:

```python
REST_FRAMEWORK = {
    "EXCEPTION_HANDLER": "core.exceptions.custom_exception_handler"
}
```

## 17. What is middleware logging?

It is logging performed during Django's request/response processing.

It can capture information about requests, responses, and request processing duration.

## 18. What is a request ID?

A request ID uniquely identifies a request.

It helps correlate log entries belonging to the same API call.

## 19. What is structured logging?

Structured logging stores log events in machine-readable formats such as JSON.

It is useful for centralized log search and dashboards.

## 20. What should never be logged?

Avoid logging passwords, access tokens, refresh tokens, API keys, session cookies, payment card data, and unnecessary sensitive personal information.

## 21. What is log rotation?

Log rotation automatically creates new log files based on size or time so that log files do not grow indefinitely.

## 22. What is the difference between logs, metrics, and traces?

- Logs describe individual events.
- Metrics measure numerical trends.
- Traces show the journey and timing of a request across services.

## 23. How do you log an external API failure?

Use exception handling and `logger.exception()` to record the failure and traceback.

Also configure timeouts and avoid logging credentials or sensitive payloads.

## 24. What is centralized logging?

Centralized logging collects logs from multiple application instances and services into one searchable platform.

Examples include ELK, Grafana Loki, and Datadog.

## 25. How do you implement production-level logging?

A good implementation includes:

1. Centralized logging configuration.
2. Appropriate logging levels.
3. Structured log messages.
4. Request IDs.
5. Exception logging.
6. Request duration logging.
7. Sensitive-data redaction.
8. Log aggregation.
9. Retention policies.
10. Monitoring and alerting.

# Final Production Recommendation

For a real-world Django REST Framework application, I recommend this approach:

1. Configure Python logging centrally in `settings.py`.
2. Use `logging.getLogger(__name__)` in every application module.
3. Use INFO for important business events.
4. Use WARNING for recoverable unusual situations.
5. Use ERROR or `logger.exception()` for failures.
6. Add request IDs for request correlation.
7. Use middleware for request duration and status logging.
8. Use a custom DRF exception handler for centralized API exception logging.
9. Use structured JSON logs in production.
10. Send logs to stdout/stderr or a centralized logging platform.
11. Never log passwords, tokens, or sensitive request payloads.
12. Configure retention, monitoring, and alerts.

**The key principle:** Production logging should help you answer three questions quickly:

- What happened?
- Where did it happen?
- Why did it happen?

Good logging makes production debugging, monitoring, and incident investigation significantly easier.
