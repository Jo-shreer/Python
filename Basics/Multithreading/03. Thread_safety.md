# 22. Thread Safety

Thread-safe code behaves correctly when multiple threads access it concurrently.

Example of shared data:

```python
counter = 0
```

If multiple threads modify it, you can have synchronization problems.
---

# 23. Race Condition
A race condition occurs when multiple threads access shared state and the final result depends on the timing/order of execution.
Example:

```python
import threading
counter = 0

def increment():
    global counter

    for _ in range(100000):
        counter += 1

threads = [
    threading.Thread(target=increment)
    for _ in range(5)
]

for thread in threads:
    thread.start()

for thread in threads:
    thread.join()

print(counter)
```
When shared state is involved, you should not rely on the GIL to make application logic thread-safe.
---

# 24. Lock
A `Lock` allows only one thread at a time to enter a critical section.

```python
import threading

counter = 0
lock = threading.Lock()

def increment():
    global counter
    for _ in range(100000):
        with lock:
            counter += 1

threads = [
    threading.Thread(target=increment)
    for _ in range(5)
]

for thread in threads:
    thread.start()

for thread in threads:
    thread.join()

print(counter)
```

The important part is:
```python
with lock:
    counter += 1
```
Only one thread can execute that protected section at a time.
---

# 25. `acquire()` and `release()`
A lock can also be used manually:

```python
import threading

lock = threading.Lock()
lock.acquire()

try:
    # critical section
    print("Protected code")

finally:
    lock.release()
```

Using:
```python
with lock:
```
is usually safer because the lock is released automatically.

---

# 26. RLock
`RLock` means **Reentrant Lock**.
The same thread can acquire the lock multiple times.
```python
import threading

lock = threading.RLock()

def function_a():
    with lock:
        function_b()

def function_b():
    with lock:
        print("Inside function B")


thread = threading.Thread(target=function_a)
thread.start()
thread.join()
```
A normal `Lock` could deadlock if the same thread tried to acquire it again before releasing it.
`RLock` allows the same thread to acquire it repeatedly.
---

# 27. Semaphore
A `Semaphore` limits how many threads can access a resource at the same time.

```python
import threading
import time

semaphore = threading.Semaphore(2)

def task(number):
    with semaphore:
        print(f"Task {number} started")
        time.sleep(2)
        print(f"Task {number} finished")


threads = [
    threading.Thread(
        target=task,
        args=(number,)
    )
    for number in range(5)
]

for thread in threads:
    thread.start()

for thread in threads:
    thread.join()
```

Only two threads can enter the protected section at once.

This is useful for:
* API concurrency limits
* database connections
* limited resources
* controlling external service load

# 28. Event
`Event` allows one thread to signal another thread.
```python
import threading
import time

event = threading.Event()

def worker():
    print("Worker waiting...")
    event.wait()
    print("Worker received signal")

thread = threading.Thread(target=worker)
thread.start()
time.sleep(2)
print("Main thread sending signal")
event.set()
thread.join()
```
Important methods:

```python
event.set()
event.clear()
event.wait()
event.is_set()
```

# 29. Condition

A `Condition` allows threads to wait until some condition becomes true.
```python
import threading

condition = threading.Condition()
data_ready = False

def consumer():
    global data_ready
    with condition:
        while not data_ready:
            condition.wait()
        print("Consumer received data")

def producer():
    global data_ready
    with condition:
        data_ready = True
        condition.notify()

consumer_thread = threading.Thread(target=consumer)
producer_thread = threading.Thread(target=producer)

consumer_thread.start()
producer_thread.start()

consumer_thread.join()
producer_thread.join()
```

A common pattern is:

```text
Consumer
   ↓
wait()

Producer
   ↓
notify()

Consumer continues
```

# 30. Queue
`queue.Queue` is thread-safe and is commonly used for producer-consumer patterns.

```python
import threading
import queue

q = queue.Queue()

def producer():
    for number in range(5):
        q.put(number)

def consumer():
    while True:
        item = q.get()
        if item is None:
            break
        print("Processing:", item)
        q.task_done()

producer_thread = threading.Thread(target=producer)
consumer_thread = threading.Thread(target=consumer)

producer_thread.start()
consumer_thread.start()

producer_thread.join()
q.put(None)
consumer_thread.join()
```
The queue handles synchronization between threads.
---

# 31. Producer-Consumer Pattern
Typical architecture:

```text
Producer Threads
       ↓
     Queue
       ↓
Consumer Threads
```
Example use cases:

* API data → queue → transformation
* files → queue → processing
* messages → queue → database loading
This prevents threads from directly sharing complex mutable state.

# 32. Deadlock
A deadlock occurs when threads wait forever for resources held by each other.
Conceptually:

```text
Thread A
  holds Lock 1
  waits for Lock 2

Thread B
  holds Lock 2
  waits for Lock 1
```

Neither can continue.
### Avoid deadlocks by:

* acquiring locks in a consistent order
* keeping critical sections small
* avoiding unnecessary locks
* using timeouts where appropriate

---

# 33. Lock Timeout
You can use:
```python
lock.acquire(timeout=2)
```
Example:

```python
import threading

lock = threading.Lock()

if lock.acquire(timeout=2):
    try:
        print("Lock acquired")
    finally:
        lock.release()

else:
    print("Could not acquire lock")
```

This prevents a thread from waiting forever.

# 34. ThreadPoolExecutor with Exceptions
A practical pattern:
```python
from concurrent.futures import ThreadPoolExecutor, as_completed

def process_customer(customer_id):
    if customer_id == 3:
        raise ValueError("Customer processing failed")
    return {
        "id": customer_id,
        "status": "processed"
    }

def main():
    customer_ids = [1, 2, 3, 4, 5]
    with ThreadPoolExecutor(max_workers=3) as executor:
        futures = {
            executor.submit(
                process_customer,
                customer_id
            ): customer_id
            for customer_id in customer_ids
        }
        for future in as_completed(futures)
            customer_id = futures[future]
            try:
                result = future.result()
                print(
                    f"Customer {customer_id}: "
                    f"{result}"
                )
            except Exception as e:
                print(
                    f"Customer {customer_id} failed: {e}"
                )
if __name__ == "__main__":
    main()
```
This pattern is very useful for production ETL.

# 35. Multithreading for API Calls

API calls are usually I/O-bound, so threads can be useful.

```python
from concurrent.futures import ThreadPoolExecutor, as_completed
import requests

def call_api(customer_id):

    response = requests.get(
        f"https://api.example.com/customers/{customer_id}",
        timeout=10
    )

    response.raise_for_status()
    return response.json()

def main():
    customer_ids = [1, 2, 3, 4, 5]
    results = []
    with ThreadPoolExecutor(max_workers=5) as executor:
        futures = {
            executor.submit(
                call_api,
                customer_id
            ): customer_id
            for customer_id in customer_ids
        }
        for future in as_completed(futures):
            customer_id = futures[future]
            try:
                result = future.result()
                results.append(result)
            except requests.RequestException as e:
                print(
                    f"API failed for {customer_id}: {e}"
                )
    return results

if __name__ == "__main__":
    results = main()
    print(results)
```

# 36. Timeouts in Threaded API Calls
Always consider timeouts when calling external services.

```python
response = requests.get(
    url,
    timeout=10
)
```
Without a timeout, a network operation can potentially wait for a very long time.

# 37. Retries with Threads
For temporary failures, you can retry.

```python
import time
import requests

def call_api(url, retries=3):
    for attempt in range(retries):
        try:
            response = requests.get(
                url,
                timeout=10
            )
            response.raise_for_status()
            return response.json()
        except requests.RequestException as e:
            if attempt == retries - 1:
                raise
            time.sleep(2 ** attempt)
```

The delays are:

```text
attempt 1 → 1 second
attempt 2 → 2 seconds
attempt 3 → 4 seconds
```
This is called **exponential backoff**.
In production, retry only errors that are appropriate to retry and consider jitter/rate limits.

# 38. Thread Naming
Naming threads helps debugging and logging.

```python
from concurrent.futures import ThreadPoolExecutor
import threading

def task(number):
    print(
        threading.current_thread().name,
        number

with ThreadPoolExecutor(
    max_workers=3,
    thread_name_prefix="ETL"
) as executor:
    futures = [
        executor.submit(task, number)
        for number in range(5)
    ]
    for future in futures:
        future.result()
```

Example thread names:

```text
ETL_0
ETL_1
ETL_2
```

# 39. Context Manager and Executor Shutdown

Prefer:

```python
with ThreadPoolExecutor(max_workers=5) as executor:
    ...
```

instead of manually managing the executor.

The context manager automatically shuts down the executor after the block completes.

Equivalent conceptually to:

```python
executor = ThreadPoolExecutor(max_workers=5)

try:
    ...
finally:
    executor.shutdown()
```

# 40. Threading vs ThreadPoolExecutor

### `threading.Thread`

Good when you need direct control over individual threads.

```python
thread = threading.Thread(target=task)
thread.start()
thread.join()
```

### `ThreadPoolExecutor`

Good when you have many similar tasks.

```python
with ThreadPoolExecutor(max_workers=10) as executor:
    futures = [
        executor.submit(task, item)
        for item in items
    ]
```

For ETL/API workloads, `ThreadPoolExecutor` is often the more convenient choice.

# 41. GIL

The **Global Interpreter Lock (GIL)** is a CPython mechanism that allows only one thread at a time to execute Python bytecode.

Therefore:

```text
CPU-bound Python code
→ threads usually don't provide true CPU parallelism
```

But:

```text
I/O-bound code
→ threads can still be very useful
```

While one thread waits for I/O, another thread can execute.

Examples:

```text
API request
Database query
File read
Network operation
```

---

# 42. Why Threads Are Useful Despite the GIL

Suppose:

```text
Thread 1 → API request → waiting
Thread 2 → API request → waiting
Thread 3 → API request → waiting
```

While the threads are waiting for I/O, the CPU can work on other available tasks.

Therefore, threads can significantly improve throughput for I/O-bound workloads.

# 43. Shared Memory

Threads within the same process share memory.

Example:

```python
import threading


data = []


def add_data(value):
    data.append(value)


threads = [
    threading.Thread(
        target=add_data,
        args=(number,)
    )
    for number in range(5)
]

for thread in threads:
    thread.start()

for thread in threads:
    thread.join()

print(data)
```

Shared memory makes communication easy, but it also creates the need for synchronization when mutable state is accessed concurrently.

# 44. Avoid Unnecessary Shared Mutable State

Instead of having many threads modify the same object:

```python
shared_results = []
```

a better pattern can be:

```text
Thread
  ↓
returns result
  ↓
main thread collects result
```

For example:

```python
from concurrent.futures import ThreadPoolExecutor


def task(number):
    return number * 2


with ThreadPoolExecutor(max_workers=3) as executor:

    results = list(
        executor.map(task, range(5))
    )

print(results)
```

This is simpler and reduces synchronization problems.

# 45. Multithreading for ETL

A common ETL architecture is:

```text
Source
  ↓
Read records
  ↓
ThreadPoolExecutor
  ↓
API / Database / Network calls
  ↓
Transform
  ↓
Load
```

Example:

```python
from concurrent.futures import ThreadPoolExecutor, as_completed
import requests


def fetch_customer(customer_id):

    response = requests.get(
        f"https://api.example.com/customers/{customer_id}",
        timeout=10
    )

    response.raise_for_status()

    return response.json()


def transform(customer):

    customer["name"] = customer["name"].strip()

    return customer


def process(customer_id):

    customer = fetch_customer(customer_id)

    return transform(customer)


def run_etl(customer_ids):

    results = []

    with ThreadPoolExecutor(max_workers=10) as executor:

        futures = {
            executor.submit(
                process,
                customer_id
            ): customer_id
            for customer_id in customer_ids
        }

        for future in as_completed(futures):

            customer_id = futures[future]

            try:

                result = future.result()

                results.append(result)

            except Exception as e:

                print(
                    f"Customer {customer_id} failed: {e}"
                )

    return results


if __name__ == "__main__":

    customer_ids = [1, 2, 3, 4, 5]

    results = run_etl(customer_ids)

    print(results)
```

# 46. Production Considerations for Threaded ETL

Do not simply create hundreds of threads.

Consider:

```text
1. max_workers
2. API rate limits
3. database connection limits
4. request timeouts
5. retries
6. exponential backoff
7. exception handling
8. logging
9. memory usage
10. batch size
11. graceful shutdown
12. idempotency
```

Example:

```text
100,000 records
      ↓
batch of 1,000
      ↓
10 worker threads
      ↓
API calls
      ↓
transform
      ↓
load
      ↓
next batch
```

This is generally safer than submitting 100,000 tasks at once.

# 47. Threading Best Practices

### Use threads for I/O-bound work

```text
API
DB
Network
File I/O
```

### Use `ThreadPoolExecutor` for pools of similar tasks

```python
with ThreadPoolExecutor(max_workers=10) as executor:
    ...
```

### Always handle exceptions

```python
try:
    result = future.result()
except Exception as e:
    ...
```

### Use timeouts for external calls

```python

```

### Avoid excessive threads

More threads can increase:

* context switching
* memory usage
* contention
* API/database pressure

### Avoid unnecessary shared state

Prefer returning results rather than having many threads modify the same objects.

### Use synchronization when shared state is unavoidable

```python
Lock
RLock
Semaphore
Condition
Event
Queue
```

# 49. Interview Questions

### Q1. What is multithreading?

> Multithreading allows multiple threads to execute within the same process. It is particularly useful for I/O-bound operations such as API calls, database queries, and network operations.

### Q2. When would you use multithreading?

> I would use multithreading mainly for I/O-bound workloads where threads spend significant time waiting for external resources.

### Q3. Why not use multithreading for CPU-bound tasks in Python?

> In CPython, the GIL prevents multiple threads from executing Python bytecode in parallel, so multiprocessing is generally more appropriate for CPU-bound Python workloads.

### Q4. What is the difference between `start()` and `run()`?

> `start()` creates and starts a new thread, which then executes `run()`. Calling `run()` directly executes the function in the current thread and does not create a new thread.

### Q5. What does `join()` do?

> `join()` makes the calling thread wait until the target thread finishes.

### Q6. What is a race condition?

> A race condition occurs when multiple threads access shared mutable state concurrently and the result depends on the timing of their execution.

### Q7. What is a Lock?

> A Lock provides mutual exclusion, allowing only one thread at a time to execute a protected critical section.

### Q8. What is a deadlock?

> A deadlock occurs when threads are waiting indefinitely for resources held by each other.

### Q9. What is `ThreadPoolExecutor`?

> `ThreadPoolExecutor` is a high-level API that manages a pool of worker threads and allows tasks to be submitted without manually creating and joining individual threads.

### Q10. What is a Future?

> A Future represents the result of an asynchronous task and provides methods such as `result()`, `done()`, `exception()`, and `cancel()`.

### Q11. Difference between `map()` and `submit()`?

> `map()` is convenient for applying the same function to multiple inputs and returns results in input order. `submit()` returns individual Futures, giving more control over exception handling, cancellation, and completion tracking.

### Q12. What is `as_completed()`?

> `as_completed()` allows us to process Futures as soon as their corresponding tasks finish, rather than waiting for results in submission order.

### Q13. Does the GIL make Python threads useless?

> No. Threads are still useful for I/O-bound workloads because while one thread is waiting for I/O, another thread can make progress.

### Q14. How would you use multithreading in ETL?

> I would use a bounded `ThreadPoolExecutor` for I/O-bound operations such as fetching data from APIs or databases. I would also implement timeouts, retries, backoff, exception handling, logging, rate limiting, and batch processing.

### Q15. How do you handle exceptions in `ThreadPoolExecutor`?

> I submit tasks and keep their Futures. When processing each Future, I call `future.result()` inside a `try/except` block. Any exception raised by the worker is then available through `result()`.
